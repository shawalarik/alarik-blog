## 第一篇：框架设计概览

### 第 1 章：权衡的艺术

> **"框架设计里到处都体现了权衡的艺术。"**

这是全书的开篇立论。作者认为，在深入各个模块的实现细节之前，必须先从全局角度理解框架的定位与方向，否则很容易被细节困住、看不清全貌。

#### 1.1 命令式和声明式：两种范式的根本分歧

作者从最基本的问题切入：**视图层框架应该是命令式的还是声明式的？**

##### 命令式：关注过程

早年间 jQuery 是典型代表。作者举了一个非常直观的自然语言到代码的映射例子：

```js
// 任务描述：
// 1. 获取 id 为 app 的 div 标签
// 2. 它的文本内容为 hello world
// 3. 为其绑定点击事件
// 4. 当点击时弹出提示：ok

// jQuery 写法 —— 与自然语言一一对应
$('#app')                    // 第1步：获取 div
  .text('hello world')       // 第2步：设置文本内容
  .on('click', () => {       // 第3步：绑定点击事件
    alert('ok')
  })

// 原生 JS 等价写法
const div = document.querySelector('#app')   // 第1步
div.innerText = 'hello world'              // 第2步
div.addEventListener('click', () => {       // 第3步
  alert('ok')
})
```

可以看到，**自然语言描述能够与命令式代码产生一一对应的关系**，代码本身描述的是"做事的过程"。

##### 声明式：关注结果

同样的事情，Vue.js 只需要一行模板：

```html
<div @click="() => alert('ok')">hello world</div>
```

我们提供的是一个**结果**，至于如何实现这个结果，我们并不关心。就像在告诉 Vue.js：

> "嘿，Vue.js，看到没，我要的就是一个 div，文本内容是 hello world，它有个事件绑定，你帮我搞定吧。"

至于实现该"结果"的过程，则由 **Vue.js 帮我们封装好了**。

由此引出了一个极其关键的洞察：

> **Vue.js 的内部实现一定是命令式的，而暴露给用户的却是声明式的。**

换句话说——**声明式 = 封装了过程的命令式**。这个认识是理解后续所有性能讨论的根本前提。

#### 1.2 性能与可维护性的权衡：全书最重要的公式 🎯

这一节是整本书精华中的精华。

作者首先抛出一个反直觉但严谨的结论：

> **声明式代码的性能不优于命令式代码的性能。**

为什么？用一个数学公式说清楚一切：

```js
// 场景：将 div 的文本从 'hello world' 改为 'hello vue3'

// 命令式 —— 你明确知道改什么，直接改
div.textContent = 'hello vue3'
// 性能消耗 = A（直接修改 DOM 的开销）

// 声明式 —— 框架要找出差异再修改
// 框架内部最终执行的仍然是：
div.textContent = 'hello vue3'
// 但在此之前需要先对比前后差异
// 性能消耗 = B（找出差异）+ A（直接修改 DOM）
```

用公式表达：

```
命令式代码的更新性能消耗 = A
声明式代码的更新性能消耗 = B + A
```

- **A**：直接修改 DOM 的性能消耗
- **B**：找出前后差异的性能消耗

**结论**：声明式永远多出一个 B，所以理论上它的性能不可能超越命令式。即使 B 趋近于 0，最多也只能做到和命令式一样好，无法超越——因为框架本身就是通过封装命令式代码来实现声明式的。

那么问题来了——既然命令式性能更好，为什么 Vue.js 选择声明式？

答案就在**可维护性**：

| 维度 | 命令式 | 声明式 |
|------|--------|--------|
| **关注点** | 如何一步步实现 | 要达到什么效果 |
| **心智负担** | 巨大——需手动维护整个 DOM 操作链 | 小——只描述目标 |
| **可维护性** | 差——复杂度随规模爆炸 | 好——代码即意图 |
| **性能上限** | 理论最优 | 有固定损耗 (B+A) |

这就引出了**框架设计的核心命题**：

> **在采用声明式提升可维护性的同时，性能就会有一定的损失，而框架设计者要做的就是：在保持可维护性的同时让性能损失最小化。**

这句话值得反复品味。**框架的本质就是——替开发者承担复杂度的同时，尽可能少地引入额外的性能开销。**

#### 1.3 虚拟 DOM 的真正使命

既然声明式的性能瓶颈在于"找出差异"（B），那虚拟 DOM 的使命就非常清晰了：

> **虚拟 DOM 就是为了最小化"找出差异"这一步的性能消耗而出现的。**

作者澄清了几个常见误解：

##### 误解一："虚拟 DOM 比 innerHTML 快"

不能简单下定论。作者通过详细分析创建页面和更新页面两种场景得出：

**创建页面时**：

```
innerHTML: HTML字符串拼接计算量 + innerHTML的DOM计算量
虚拟DOM:   创建JS对象(VNode)计算量 + 创建真实DOM计算量
```

两者都在同一个数量级上——都需要新建所有 DOM 元素，差距不大。

**更新页面时**：

```
innerHTML: 重新拼接HTML + 销毁全部旧DOM + 创建全部新DOM（全量更新）
虚拟DOM:   创建新的VNode树 + Diff找差异 + 只更新变化的DOM（精确更新）
```

关键区别：**无论页面多大，虚拟 DOM 只会更新变化的部分；而 innerHTML 页面越大，全量重建的代价越大。**

##### 误解二："虚拟 DOM 最快"

理论上原生 JavaScript 操作 DOM 最快（没有 B 的开销）。但实际上：

> **在大部分情况下，我们很难写出绝对优化的命令式代码，尤其是应用程序规模很大的时候。即使你写出了极致优化的代码，也一定耗费了巨大的精力，投入产出比不高。**

虚拟 DOM 保证了一个不错的**性能下限**——你不需要成为 DOM 操作专家就能写出性能还不错的应用。

作者给出了三维对比：

| | 心智负担 | 可维护性 | 性能 |
|---|---------|---------|------|
| 原生 JS（createElement）| 最大 | 最差 | 最高 |
| innerHTML | 中等 | 较差 | 取决于场景 |
| 虚拟 DOM | 最小 | **最好** | 接近最优 |

#### 1.4 运行时 vs 编译时：三种框架形态

作者用一个极简的例子讲清楚了三者的本质差异。假设用户提供的树型数据如下：

```js
const obj = {
  tag: 'div',
  children: [{ tag: 'span', children: 'hello' }]
}
```

##### 纯运行时

提供一个 `Render` 函数，用户直接传入上述对象，Render 函数递归地将其渲染为 DOM 元素。

- **优点**：灵活，任何合法的 JS 对象都能渲染
- **缺点**：没有编译步骤，**无法分析用户提供的内容做优化**

```js
function Render(obj, root) {
  const el = document.createElement(obj.tag)
  if (typeof obj.children === 'string') {
    el.textContent = obj.children
  } else if (Array.isArray(obj.children)) {
    obj.children.forEach(child => Render(child, el))
  }
  root.appendChild(el)
}
```

##### 运行时 + 编译时（Vue.js 的选择）

先用编译器把 HTML 模板编译成上述树型结构（或更优化的渲染函数），再交给 Render 函数处理。

- **优点**：既能分析内容做优化，又保留运行时的灵活性
- **缺点**：构建工具更复杂

```js
// 编译器：HTML 字符串 → 渲染函数或树型结构
function Compiler(template) {
  // 解析模板，生成 render 函数或 VNode 描述
  return renderFunction // 或树型数据
}

// 运行时：接收编译产物并渲染
function Render(compiledOutput, root) { /* ... */ }
```

##### 纯编译时（如 Svelte）

直接将 HTML 编译成命令式 DOM 操作代码，不需要任何运行时：

```js
// 编译前
<h1>{{ title }}</h1>

// 编译后（纯命令式代码）
const h1 = document.createElement('h1')
h1.textContent = title.value
// ...当 title 变化时直接执行 h1.textContent = newValue
```

- **优点**：理论上性能最好（没有运行时开销）
- **缺点**：有损灵活性，**必须编译后才能使用**

作者对三者做了总结：

| 类型 | 代表框架 | 优点 | 缺点 |
|------|---------|------|------|
| 纯运行时 | Vue 2（部分场景）| 极其灵活 | 无法做编译优化 |
| 运行时+编译时 | **Vue.js 3** | 兼得灵活性与高性能 | 构建较复杂 |
| 纯编译时 | Svelte | 性能理论最优 | 灵活性受限 |

作者的判断：

> Vue.js 3 仍然保持了运行时 + 编译时的架构，在保持灵活性的基础上能够尽可能地去优化。等到后面讲解编译优化相关内容时，你会看到 **Vue.js 3 在保留运行时的情况下，其性能甚至不输纯编译时的框架**。

#### 1.5 本章总结

作者用一段话概括了第一章的全部要点：

1. **命令式关注过程，声明式关注结果**
2. **命令式理论上可以做到极致优化，但要承受巨大心智负担；声明式有效减轻心智负担，但性能上有牺牲**
3. **虚拟 DOM 的意义是最小化"找出差异"的性能消耗**
4. **Vue.js 3 是一个编译时 + 运行时的框架，兼顾灵活性和性能**

### 第 2 章：框架设计的核心要素

功能开发完成不等于大功告成。本章讨论框架设计者在工程层面必须考虑的非功能性要素。

#### 2.1 提升用户的开发体验

##### 友好的警告信息

衡量框架是否优秀的重要指标之一就是**开发体验**。以 Vue.js 为例：

```js
createApp(App).mount('#not-exist')
```

挂载到一个不存在的节点时，Vue.js 会输出一条清晰的警告：

```
[Vue warn]: Failed to mount app: mount target selector "#not-exist" returned null.
```

如果框架不做处理，开发者只能看到 `Uncaught TypeError: Cannot read property 'xxx' of null`，根本不知道哪里出了问题。

作者强调：**大多数情况下"框架"要比开发者更清楚问题出在哪里，因此在框架层面抛出有意义的警告信息是非常必要的。**

##### 自定义 Console Formatter

Vue.js 3 还有一个贴心的细节：在开发环境下，打印 ref 数据时默认显示的是 RefImpl 对象（非常不直观）。Vue.js 通过 `initCustomFormatter` 函数初始化浏览器自定义 formatter，开启后在控制台能看到直观的值。

#### 2.2 控制框架代码的体积：__DEV__ 的魔法

提供越完善的警告信息意味着越大的体积。Vue.js 通过预定义常量 `__DEV__` 解决这个问题：

```js
// 框架源码中
if (__DEV__ && !res) {
  warn(`Failed to mount app: mount target selector "${container}" returned null.`)
}
```

构建流程：

| 产物 | 文件名 | __DEV__ 值 | 用途 |
|------|--------|-----------|------|
| 开发版 | vue.global.js | true | 包含完整警告信息 |
| 生产版 | vue.global.prod.js | false | 不包含警告相关代码（被 Tree-Shaking 掉） |

这样**线上代码体积不受开发体验代码的影响**。

#### 2.3 Tree-Shaking：模块级按需引入

Tree-Shaking 是一种排除 dead code 的机制。前提条件：**模块必须是 ESM 格式**。

```js
// utils.js
export function foo(obj) { obj && obj.foo }
export function bar(obj) { obj && obj.bar }

// input.js — 只导入了 foo
import { foo } from './utils.js'
foo()
```

使用 rollup 构建后，bar 函数不会出现在 bundle 中——这就是 Tree-Shaking。

但有一个陷阱：**副作用（side effect）**。如果函数调用可能对外部产生影响（如修改全局变量），构建工具就不敢移除它。为此 Vue.js 大量使用了 `/*#__PURE__*/` 注解来辅助构建工具：

```ts
export const isHTMLTag = /*#__PURE__*/ makeMap(HTML_TAGS)
```

告诉构建工具："放心吧，这段代码不会产生副作用，可以 Tree-Shaking 掉。"

#### 2.4 构建产物的多样性

Vue.js 针对不同使用场景输出不同格式：

| 产物格式 | 文件示例 | 使用方式 |
|---------|---------|---------|
| IIFE | vue.global.js | `<script src="">` 直接引用 |
| ESM (浏览器) | vue.esm-browser.js | `<script type="module">` 引用 |
| ESM (打包工具) | vue.esm-bundler.js | webpack / vite 打包时使用 |
| UMD | vue.global.js | CommonJS / AMD / 全局变量 |

其中两种 ESM 的关键区别在于对 `__DEV__` 的处理：
- esm-browser.js：**直接替换为字面量 true/false**（因为浏览器不支持 process.env）
- esm-bundler.js：**替换为 `process.env.NODE_ENV !== 'production'`**（由打包工具进一步替换）

#### 2.5 特性开关

框架有时出于兼容性提供多种 API 完成同一任务。例如 Vue.js 中选项式 API 和组合式 API 都能开发页面。如果你明确只用组合式 API：

```js
// vite.config.js 或 vue.config.js
defineConfig({
  __VUE_OPTIONS_API__: false,     // 关闭 Options API
  __VUE_PROD_DEVTOOLS__: false,   // 关闭生产环境 devtools 支持
})
```

关闭的特性代码会在 Tree-Shaking 时被排除，进一步减小包体积。

#### 2.6 错误处理：统一的异常接口

框架的错误处理做得好坏直接决定了**用户应用程序的健壮性**和**开发者处理错误的心智负担**。

作者用一个工具模块的例子说明了设计思路：

```js
// ❌ 差的做法：让用户自己 try-catch
utils.foo(() => {
  // 用户必须在每个回调里加错误处理
})

// ✅ 好的做法：框架统一处理，暴露注册接口
let handleError = null

export default {
  foo(fn) { callWithErrorHandling(fn) },
  bar(fn) { callWithErrorHandling(fn) },
  // 用户注册统一的错误处理函数
  registerErrorHandler(fn) { handleError = fn },
}

function callWithErrorHandling(fn) {
  try {
    fn && fn()
  } catch (e) {
    handleError?.(e)  // 将错误传递给用户处理程序
  }
}
```

Vue.js 就是这么做的：

```js
app.config.errorHandler = (err, instance, info) => {
  // 处理所有框架异常 — 上报监控、展示降级 UI 等
}
```

底层就是 `callWithErrorHandling` 函数包裹所有用户回调。

#### 2.7 TypeScript 类型支持

作者指出了一个常见的**认知误区**：

> **使用 TypeScript 编写框架 ≠ 框架对 TS 类型支持友好。这是两件完全不同的工作。**

举例说明：

```ts
// ❌ 类型支持不好 — 返回值类型丢失为 any
function foo(val: any) {
  return val  // res 的类型变成了 any，而非实际传入的类型
}

// ✅ 类型支持好 — 泛型正确推导返回值类型
function foo<T extends any>(val: T): T {
  return val  // res 的类型能正确推断为传入值的类型
}
```

为了实现完善的 TS 类型支持，Vue.js 源码中 `defineComponent.ts` 文件**接近 200 行代码，但真正在浏览器中运行的只有 3 行**——其余全是为类型服务。作者感叹：**为了让框架提供更加友好的类型支持，甚至要花费比实现框架功能本身更多的时间和精力。**

### 第 3 章：Vue.js 3 的设计思路

本章从全局视角介绍 Vue.js 3 各个模块是如何协作的有机整体。

#### 3.1 声明式地描述 UI

编写前端页面涉及四个要素：DOM 元素、属性、事件、层级结构。Vue.js 为每个要素提供了声明式描述方式：

| 要素 | 声明式写法 | 说明 |
|------|-----------|------|
| DOM 元素 | `<div>` | 与 HTML 标签一致 |
| 属性 | `<div id="app">` | 与 HTML 属性一致 |
| 动态绑定 | `<div :id="dynamicId">` | 使用 v-bind 或 : |
| 事件 | `<div @click="handler">` | 使用 v-on 或 @ |
| 层级结构 | `<div><span></span></div>` | 与 HTML 嵌套一致 |

除了模板，还可以用 JavaScript 对象（即虚拟 DOM）来描述：

```js
// 虚拟 DOM 本质就是一个 JS 对象
const vnode = {
  tag: 'h1',
  props: { onClick: handler },
  children: [{ tag: 'span' }]
}

// h() 函数只是辅助创建虚拟 DOM 的语法糖
// import { h } from 'vue'
// h('h1', { onClick: handler }, [h('span')])
```

**虚拟 DOM 比模板更灵活**。例如动态标签名：

```js
// 虚拟 DOM：一行搞定
let level = 3
const vnode = { tag: `h${level}` }  // h3 标签

// 模板：必须穷举（不够灵活）
<h1 v-if="level === 1"></h1>
<h2 v-else-if="level === 2"></h2>
<h3 v-else-if="level === 3"></h3>
<!-- ... -->
```

#### 3.2 初识渲染器

**渲染器的作用就是把虚拟 DOM 对象渲染为真实 DOM 元素。**

最简渲染器的实现：

```ts
function renderer(vnode, container) {
  // 1. 创建元素
  const el = document.createElement(vnode.tag)

  // 2. 处理 props（属性和事件）
  for (const key in vnode.props) {
    if (/^on/.test(key)) {
      // 事件
      el.addEventListener(key.slice(2).toLowerCase(), vnode.props[key])
    } else {
      // 属性
      el.setAttribute(key, vnode.props[key])
    }
  }

  // 3. 处理子节点
  if (typeof vnode.children === 'string') {
    el.textContent = vnode.children
  } else if (Array.isArray(vnode.children)) {
    vnode.children.forEach(child => renderer(child, el))
  }

  // 4. 挂载到容器
  container.appendChild(el)
}
```

#### 3.3 组件的本质

作者给出的定义直击本质：

> **组件本质上就是一组 DOM 元素的封装。**

一个组件要渲染的内容是通过**渲染函数**（render function）来描述的，Vue.js 会根据 render 函数的返回值拿到虚拟 DOM，然后交给渲染器渲染出来。

#### 3.4 模板的工作原理

`.vue` 单文件组件中的 `<template>` 不是 HTML——它是 Vue.js 特有的领域特定语言（DSL）。模板的工作流程：

```
<template>  →  编译器(Compiler)  →  渲染函数(render function)  →  虚拟 DOM  →  渲染器  →  真实 DOM
```

编译器在构建时完成，所以模板编译不会有运行时性能开销。

#### 3.5 模块的协同关系

Vue.js 3 的各模块组成一个有机整体：

```
用户编写 .vue 组件
        │
        ▼
   ┌─────────┐
   │ 编译器   │ ← 将模板编译成渲染函数
   └────┬────┘
        │ 渲染函数返回 VNode
        ▼
   ┌─────────┐
   │ 渲染器   │ ← 将 VNode 渲染为真实 DOM
   └────┬────┘
        │
   ┌────┴────────┐
   │             │
   ▼             ▼
响应系统      组件系统
(track/trigger) (状态/生命周期/slots)
```

## 第二篇：响应系统

### 第 4 章：响应系统的作用与实现 —— 从零构建

这是全书最硬核的一章。作者采用**由简入繁**的方式，从一个最简单的副作用函数开始，逐步推导出完整的响应式系统。每一步都先发现问题，再给出解决方案。

#### 4.1 起点：什么是副作用函数

```js
function effect() {
  document.body.innerText = obj.text
}
```

这个函数会**对外部产生影响**（修改 DOM），所以叫"副作用函数"（side effect function / effect function）。**响应系统的目标就是：当 `obj.text` 变化时，自动重新执行 `effect`。**

#### 4.2 第一版：最简单的响应系统

```js
// 存储副作用函数的桶
const bucket = new Set()

// 当前正在执行的副作用函数
let activeEffect

// 注册副作用函数
function effect(fn) {
  activeEffect = fn
  fn()  // 执行时会触发 Proxy get → 收集依赖
}

// 响应式数据
const data = { text: 'hello' }
const obj = new Proxy(data, {
  get(target, key) {
    if (activeEffect) bucket.add(activeEffect)  // 收集依赖
    return target[key]
  },
  set(target, key, newVal) {
    target[key] = newVal
    bucket.forEach(fn => fn())  // 触发更新
    return true
  }
})
```

**问题来了**：设置一个不存在的属性也会触发所有副作用函数重新执行：

```js
effect(() => {
  document.body.innerText = obj.text  // 只读了 text
})
obj.notExist = 'value'  // 并没读 notExist，但还是触发了 effect！
```

原因：桶只是一个 Set，**副作用函数和被操作的字段之间没有明确联系**——无论读哪个属性都会往同一个 Set 里塞，无论改哪个属性都会取出全部执行。

#### 4.3 第二版：建立精确的联系

解决方案：**重新设计"桶"的数据结构**，在三个角色之间建立联系：

```
target（原始对象）
  └── key（字段名）
      └── effectFn（副作用函数）
```

这是一个树型结构。用 WeakMap + Map + Set 实现：

```js
// bucket 的结构：WeakMap<target, Map<key, Set<effect>>>
const bucket = new WeakMap()

let activeEffect

function effect(fn) {
  const effectFn = () => {
    activeEffect = effectFn
    fn()
  }
  effectFn.deps = []  // 反向记录（用于 cleanup）
  effectFn()
}

const obj = new Proxy(data, {
  get(target, key) {
    track(target, key)  // 收集依赖
    return Reflect.get(target, key, receiver)
  },
  set(target, key, newVal, receiver) {
    trigger(target, key)  // 触发更新
    return Reflect.set(target, key, newVal, receiver)
  }
})

function track(target, key) {
  if (!activeEffect) return

  let depsMap = bucket.get(target)
  if (!depsMap) bucket.set(target, (depsMap = new Map()))

  let deps = depsMap.get(key)
  if (!deps) depsMap.set(key, (deps = new Set()))

  deps.add(activeEffect)
  activeEffect.deps.push(deps)  // 反向映射
}

function trigger(target, key) {
  const depsMap = bucket.get(target)
  if (!depsMap) return

  const effects = depsMap.get(key)
  effects && effects.forEach(effect => effect())
}
```

现在 `obj.notExist = 'value'` 不会触发 effect 了——因为它不在 `obj.text` 的依赖集合中。

#### 4.4 第三篇：分支切换与 cleanup

又一个问题出现——**遗留副作用**：

```js
const data = { ok: true, text: 'hello world' }
const obj = reactive(data)

effect(() => {
  document.body.innerText = obj.ok ? obj.text : 'not'
})

// 此时建立了两个依赖关系：
// obj.ok → effect,  obj.text → effect

obj.ok = false
// 现在不再读 obj.text 了，但旧的依赖关系还在！
// 修改 obj.text 仍会无谓触发 effect：
obj.text = 'hello vue3'  // ← 多余的更新
```

**解决思路**：每次副作用函数执行前，先把它从**所有关联的依赖集合中删除**，执行完毕后再重新建立联系。

```js
function effect(fn) {
  const effectFn = () => {
    cleanup(effectFn)        // ★ 先清除旧依赖
    activeEffect = effectFn
    fn()                     // ★ 重新收集依赖
  }
  effectFn.deps = []
  effectFn()
}

function cleanup(effectFn) {
  for (const dep of effectFn.deps) {
    dep.delete(effectFn)     // 从每个关联的集合中移除自身
  }
  effectFn.deps.length = 0
}
```

这样分支切换后，不再读取的属性就不会保留旧依赖。

#### 4.5 第四版：嵌套 effect 与 effect 栈

如果一个 effect 内部还有另一个 effect，`activeEffect` 会被内层的覆盖，导致外层的依赖收集丢失：

```js
// 外层 effect
effect(() => {
  console.log('outer')
  // 内层 effect
  effect(() => {
    console.log('inner')
    console.log(obj.innerText)
  })
  console.log(obj.outerText)  // ← 这里的 activeEffect 已经被内层覆盖了！
})
```

解决方案：**效果栈（effectStack）**：

```js
const effectStack = []

function effect(fn) {
  const effectFn = () => {
    cleanup(effectFn)
    activeEffect = effectFn
    effectStack.push(effectFn)  // 入栈
    fn()
    effectStack.pop()            // 出栈
    activeEffect = effectStack[effectStack.length - 1]  // 恢复上一个
  }
  // ...
}
```

嵌套执行时，栈顶始终是当前活跃的 effect，保证每次 track 都能正确记录"谁在读"。

#### 4.6 避免无限递归循环

如果 effect 内部修改了自己依赖的数据：

```js
effect(() => {
  obj.num++  // 读 num → track; 写 num → trigger → 又执行...
})
```

会导致无限循环。解决方案：**trigger 时跳过当前活跃的 effect**：

```js
function trigger(target, key) {
  const effectsToRun = new Set()
  // ...
  effectsToRun.forEach(effect => {
    if (effect !== activeEffect) {  // ★ 跳过自身
      effect()
    }
  })
}
```

#### 4.7 调度执行：从同步到异步批处理

默认情况下，数据变更立即同步执行副作用函数。但这可能导致多次重复渲染。解决方案是**调度器（scheduler）**：

```js
function effect(fn, options = {}) {
  const effectFn = () => {
    cleanup(effectFn)
    activeEffect = effectFn
    effectStack.push(effectFn)
    fn()
    effectStack.pop()
    activeEffect = effectStack[effectStack.length - 1]
  }

  effectFn.options = options
  // ...
  effectFn()
}

// 在 scheduler 中控制执行时机
const jobQueue = new Set()
let isFlushing = false

function flushJob() {
  jobQueue.forEach(job => job())
  jobQueue.clear()
  isFlushing = false
}

// 修改 trigger 中的执行逻辑
// 当 options.scheduler 存在时，将副作用函数放入调度器
if (effect.scheduler) {
  effect.scheduler(effect)
} else {
  effect()
}
```

Vue 3 默认将调度器设为微任务队列（`Promise.resolve().then()`），实现**异步批处理**。

#### 4.8 computed：懒执行的缓存派生值

计算属性本质上是一个带 `_dirty` 脏标记的懒执行 effect：

```js
function computed(getter) {
  let value
  let dirty = true  // 脏标记：是否需要重新计算

  const effectFn = effect(getter, {
    lazy: true,  // 不立即执行
    scheduler() {
      if (!dirty) {
        dirty = true
        // ★ 通知外部 effect：此 computed 过期了
        trigger(obj, 'value')
      }
    }
  })

  const obj = {
    get value() {
      track(obj, 'value')  // ★ 让外部 effect 能追踪 computed
      if (dirty) {
        value = effectFn()  // 只有脏了才重算
        dirty = false
      }
      return value
    }
  }

  return obj
}
```

关键设计：

1. **lazy: true**：创建时不立即执行 getter，只在 `.value` 被访问时才算
2. **dirty 标记**：数据没变时直接返回缓存的值，避免重复计算
3. **scheduler**：依赖数据变化时只标记 dirty=true + trigger，不立即重算
4. **手动的 track/trigger**：使 computed 可以参与到外部的依赖收集中

#### 4.9 watch 和 watchEffect

watch 本质上是封装了 effect + scheduler + lazy:

```js
function watch(source, cb, options = {}) {
  let getter
  if (typeof source === 'function') {
    getter = source
  } else {
    getter = () => traverse(source)  // 递归读取所有属性以建立依赖
  }

  let oldValue, newValue

  const job = () => {
    newValue = effectFn()
    cb(newValue, oldValue)
    oldValue = newValue
  }

  const effectFn = effect(
    () => getter(),
    {
      lazy: true,
      scheduler() {
        // flush: 'post' → 微任务队列（DOM 更新后执行）
        // flush: 'pre'  → 组件更新前执行
        // flush: 'sync' → 同步执行
        if (options.flush === 'post') {
          Promise.resolve().then(job)
        } else {
          job()
        }
      }
    }
  )

  if (options.immediate) {
    job()  // 立即执行一次
  } else {
    oldValue = effectFn()
  }
}
```

#### 4.10~4.11 立即执行的 watch 与过期副作用

watch 回调可以通过 `immediate: true` 立即执行（此时旧值为 undefined）。还有一个重要的特性——**过期副作用的处理**（竞态问题）：

```js
let finalData
watch(obj, async (newValue, oldValue, onInvalidate) => {
  let expired = false
  
  // 注册过期回调
  onInvalidate(() => {
    expired = true
  })

  const res = await fetch('/api/data')
  
  // 如果已过期（期间 obj 又变了），丢弃这次结果
  if (!expired) finalData = res
})
```

当 watch 的 source 在请求期间再次变化，上一次的回调会被标记为"过期"，其结果会被丢弃。这对避免竞态问题至关重要。

### 第 5 章：非原始值的响应式方案 —— 深入 ECMAScript 规范

这一章从规范层面讲解 Proxy 和 Reflect 的工作原理，以及如何正确地代理各种类型的对象。

#### 5.1~5.3 为什么是 Proxy 而非 Object.defineProperty

Proxy 相比 Vue 2 的 defineProperty 有决定性优势：

| 能力 | defineProperty | Proxy |
|------|---------------|-------|
| 拦截新增属性 | 不能（需 `$set`） | 天然支持 |
| 拦截数组索引变化 | 不能（需重写数组方法） | 天然支持 |
| 拦截 `in` 操作符 | 不能 | has 拦截 |
| 拦截 `delete` | 不能（需 `$delete`） | deleteProperty 拦隔 |
| 拦截 `for...in` | 不能 | ownKeys 拦截 |
| 深层响应 | 初始化全量递归 | **按需懒代理**（访问时才递归） |
| Map/Set/WeakMap | 不支持 | 完整支持 |

#### 5.4 合理地触发响应

设置属性时需要区分操作类型：

```js
set(target, key, newVal, receiver) {
  const hadKey = Object.prototype.hasOwnProperty.call(target, key)
  const oldVal = target[key]

  const res = Reflect.set(target, key, newVal, receiver)

  if (target === receiver.raw) {  // 避免原型链触发的重复更新
    if (!hadKey) {
      trigger(target, 'ADD')      // 新增属性
    } else if (oldVal !== newVal) {
      trigger(target, 'SET')      // 修改属性
    }
  }

  return res
}
```

区分 ADD 和 SET 很重要——对于数组，ADD 可能意味着 length 变化了，需要额外通知遍历 length 的 effect。

#### 5.5 浅响应与深响应

- **shallowReactive**：只有顶层属性是响应式的，嵌套对象不自动代理
- **reactive**：深度响应——访问嵌套对象时自动将其转为 reactive

```js
const shallow = shallowReactive({ foo: { bar: 1 } })
// shallow.foo.bar = 2  ← 不会触发更新（foo 未被代理）

const deep = reactive({ foo: { bar: 1 } })
// deep.foo.bar = 2  ← 触发更新（访问 foo 时已自动代理）
```

#### 5.6 只读和浅只读

四种变体覆盖所有组合：

| API | 深度 | 只读 |
|-----|------|------|
| reactive | 深响应 | 否 |
| shallowReactive | 浅响应 | 否 |
| readonly | 深响应 | **是** |
| shallowReadonly | 浅响应 | **是** |

readonly 在 get/set 拦截中直接报警告而不允许修改，但仍会 track（以便 computed/watch 能正常工作）。

#### 5.7 代理数组的特殊处理

数组的代理有几个著名的坑：

**数组的 length 和索引的双向联动**：

```js
arr[100] = 'x'  // 设置索引 → length 自动变为 101
arr.length = 0  // 设置 length → 所有元素被删除
```

两者互相影响，需要在 set 拦截中特殊处理。

**查找方法的兼容**：`includes`、`indexOf`、`lastIndexOf` 方法需要特殊处理——因为代理对象和原始对象的引用不同：

```js
const arr = reactive([{}])
arr.includes(arr[0])  // 应该返回 true，但默认返回 false！

// 解决：先在代理对象中找，找不到再去原始数组找
arrayInstrumentations.includes = function(...args) {
  let res = Array.prototype.includes.apply(this, args)
  if (res === false) {
    res = Array.prototype.includes.apply(this.raw, args)
  }
  return res
}
```

**隐式修改 length 的方法导致死循环**：

```js
const arr = reactive([])
effect(() => arr.push(1))
effect(() => arr.push(1))
// 栈溢出！
```

原因：push 会间接读写 length，导致两个 effect 互相触发对方。解决方案是用一个 `shouldTrack` 标记位临时禁止 track。

#### 5.8 代理 Set 和 Map

Set/Map 的代理更加复杂——它们的方法会同时读写内部数据。核心原则：**不污染原始数据**。所有操作都在代理对象上进行，通过 `raw` 属性访问原始数据来做比较和查找。

### 第 6 章：原始值的响应式方案 —— ref 的诞生

基本类型（number/string/boolean）无法被 Proxy 代理——因为 Proxy 的 target 必须是对象。

#### 6.1 引入 ref

解决方案：用**类的 getter/setter** 来拦截值的读写：

```ts
class RefImpl<T> {
  private _value: T
  public dep: Dep = new Set()
  public readonly __v_isRef = true

  constructor(value: T, shallow: boolean) {
    this._value = shallow ? value : toReactive(value)  // 对象自动转 reactive
  }

  get value() {
    trackRefValue(this)  // 读取时 track
    return this._value
  }

  set value(newVal) {
    if (hasChanged(newVal, this._rawValue)) {
      this._rawValue = newVal
      this._value = toReactive(newVal)
      triggerRefValue(this)  // 写入时 trigger
    }
  }
}
```

#### 6.2 响应丢失问题

解构 reactive 对象会丢失响应性：

```js
const state = reactive({ count: 0 })
let { count } = state  // 解构后 count 只是普通数字
count++               // 不会触发更新！
```

**解决方法：用 `toRefs()` 把每个属性转为 ref**：

```js
const state = reactive({ count: 0 })
const { count } = toRefs(state)  // count 是 ref
count.value++                      // ✓ 正常触发更新
```

#### 6.3 自动脱 ref

在模板中使用 ref 时无需 `.value`，是因为编译器会自动添加 `.value`。而在 JSX / 渲染函数中也可以通过 `unref()` 或自动脱 ref 机制省略 `.value`。

## 第三篇：渲染器

### 第 7~8 章：渲染器设计与挂载更新

#### 渲染器与响应系统的结合

```js
effect(() => {
  renderer(subTree, container)  // 响应式数据变化 → 自动重新渲染
})
```

这就是渲染器和响应系统的结合方式——**effect 包裹渲染调用**。

#### 自定义渲染器：跨平台的关键

Vue 3 将渲染器抽象为可配置的对象：

```ts
const renderer = createRenderer({
  createElement(tag) { /* 自定义 */ },
  insert(el, parent) { /* 自定义 */ },
  patchProp(el, key, prevVal, nextVal) { /* 自定义 */ },
  setText(el, text) { /* 自定义 */ },
  setElementText(el, text) { /* 自定义 */ },
  createText(text) { /* 自定义 */ },
})

// 渲染到任意目标
renderer.createApp(App).mount(canvasElement)  // Canvas
renderer.createApp(App).mount(nativeView)     // Native
```

这种设计使得 Vue 3 可以渲染到浏览器 DOM、Canvas、WebGL、移动端原生组件甚至终端。

#### 挂载与更新的核心：patch 函数

渲染器的核心是一个 `patch` 函数（也叫 diff 过程），它负责对比新旧虚拟 DOM，并将变更应用到真实 DOM：

```ts
function patch(n1, n2, container, anchor) {
  // n1: 旧 VNode（可能不存在，表示首次挂载）
  // n2: 新 VNode
  // container: 容器
  // anchor: 锚点（插入位置参考）

  if (n1 == null) {
    // 挂载：n1 不存在，直接创建
  } else if (n1.type !== n2.type) {
    // 替换：类型不同，卸载旧的，挂载新的
  } else {
    // 更新：类型相同，进行 Diff
    if (typeof n2.type === 'string') {
      // 普通 Element 的更新
      patchElement(n1, n2)
    } else if (n2.type === Text) {
      // 文本节点的更新
    } else if (n2.type === Component) {
      // 组件的更新
      processComponent(n1, n2)
    }
  }
}
```

### 第 9~11 章：三种 Diff 算法的演进

Vue 3 的 Diff 算法演进体现了**渐进优化**的思想：

| 章节 | 算法 | 思路 | 时间复杂度 |
|------|------|------|-----------|
| 第 9 章 | **简单 Diff** | 双层循环，在新节点中找复用节点后移动 | O(mn) ~ O(n²) |
| 第 10 章 | **双端 Diff** | 同时从新旧节点的两端开始比较 | O(n) |
| 第 11 章 | **快速 Diff** | 先处理前后置相同节点，再用 LIS 算法求最小移动量 | O(n) |

#### 快速 Diff 算法（Vue 3 最终采用）

这是目前最高效的算法，分为五个步骤：

```
1. 同步前置节点：从头部开始，新旧节点相同的位置直接复用
2. 同步后置节点：从尾部开始，新旧节点相同的位置直接复用
3. 处理新增/卸载节点：如果旧节点耗尽则挂载剩余新节点；如果新节点耗尽则卸载剩余旧节点
4. 判断是否需要移动：如果剩余节点中有相同 key 且位置不变，则不需要移动
5. 移动节点：使用最长递增子序列（LIS）算法求出最小移动量
```

最长递增子序列保证了**移动次数最少**，这在大量节点的列表更新场景中优势明显。

## 第四篇：组件化

### 第 12 章：组件的实现原理

#### 组件的本质（再次强调）

> **组件本质上就是一组 DOM 元素的封装。**

这意味着组件系统的全部设计都围绕以下问题展开：

1. **自更新**：组件有自己的状态（data/reactive），状态变化触发自身 re-render
2. **被动更新**：组件接收外部状态（props），props 变化由父组件驱动更新
3. **生命周期**：mounted / updated / unmounted —— 在合适的时机执行逻辑
4. **通信机制**：emit（子→父）、slots（父→子内容分发）、provide/inject（跨层级）

#### setup 函数的作用

Composition API 的核心就是 `setup` 函数。它在组件**创建时、props 解析之后**执行，返回的数据会暴露给模板使用：

```ts
export default {
  props: ['title'],
  setup(props, { emit, slots, attrs, expose }) {
    const count = ref(0)

    // 返回的所有东西都可以在模板中直接使用
    return { count, doubled: computed(() => count.value * 2) }
  }
}
```

setup 中的 `this` 是 `undefined`（为了避免与 Options API 的 this 语义冲突）。

### 第 13 章：异步组件与函数式组件

#### 异步组件

`defineAsyncComponent` 解决的问题是：**大型组件的延迟加载**。

```ts
const AsyncComp = defineAsyncComponent({
  loader: () => import('./HeavyComponent.vue'),  // 动态导入
  loadingComponent: LoadingComponent,            // 加载中显示
  errorComponent: ErrorComponent,                // 加载失败显示
  delay: 200,                                   // 延迟多久才显示 loading（防闪烁）
  timeout: 10000,                                // 超时时间
})
```

实现原理涉及 Promise 管理、超时计时器、重试机制等多个细节。

### 第 14 章：内建组件

#### KeepAlive：组件缓存的艺术

KeepAlive 不是简单的"隐藏/显示"，而是真正的**缓存与恢复**：

- **激活（activate）**：从缓存中取出之前渲染过的 DOM，直接挂载
- **失活（deactivate）**：卸载 DOM 但**不销毁组件实例**，存入缓存
- **LRU 缓存策略**：缓存满时淘汰最久未使用的实例
- **include/exclude**：通过组件名匹配控制缓存范围

#### Teleport：传送门

解决的问题：**将组件渲染输出传送到 DOM 树的其他位置**。

典型的场景是模态框（modal）：虽然 modal 在逻辑上属于某个组件，但其视觉上应该挂载到 body 下（避免被父组件的 overflow / z-index 影响）。

#### Transition：过渡动画

Transition 的本质是**在恰当的时机插入 CSS 过渡类名**：

```
进入阶段：before-enter → enter → enter-to
离开阶段：before-leave → leave → leave-to
```

Vue.js 在 DOM 更新的时机点自动添加/移除这些类名，开发者只需编写对应的 CSS transition/animation 即可。

## 第五篇：编译器

### 第 15 章：编译器核心技术概览

编译器的工作流水线：

```
HTML 模板字符串
    │
    ▼
Parser（解析器）
    │  利用有限状态机（FSM）递归下降解析
    ▼
模板 AST（Abstract Syntax Tree）
    │  节点类型：Element / Text / Comment / Expression / Attribute 等
    ▼
Transform（转换器）
    │  插件化架构（enter/exit 钩子）
    │  - 分析静态/动态节点
    │  - 生成 PatchFlags
    ▼
JavaScript AST
    │
    ▼
Generator（代码生成器）
    │  生成可执行的渲染函数代码
    ▼
渲染函数（render function）
```

### 第 16 章：解析器

模板解析器的核心是**有限状态机（Finite State Machine）**。解析过程分为几个主要状态：

- **初始状态**：等待标签开始 `<`
- **标签打开状态**：解析标签名
- **属性解析状态**：解析属性名和值
- **文本解析状态**：解析标签之间的文本内容（含插值表达式 `{{ }}`）
- **注释/CDATA 状态**：特殊内容的处理
- **闭合标签状态**：匹配对应的开始标签

解析器还需要遵循 WHATWG 的 HTML 规范，包括 HTML 实体解码（命名实体 `&amp;`、数字实体 `&#65;` 等）。

### 第 17 章：编译优化 —— Vue 3 性能的秘密武器 ⚡

这是全书最令人兴奋的部分之一。Vue 3 的编译器不只是"翻译"，它在编译阶段就注入了大量优化信息。

#### 17.1 动态节点收集与 PatchFlags

编译器会对每个节点进行静态分析，标记其变化类型：

```html
<!-- 原始模板 -->
<div class="container">
  <p :class="dynamicClass">{{ msg }}</p>
  <span>static text</span>
</div>
```

```js
// 编译后生成的渲染函数（简化）
export function render(_ctx, _cache) {
  return (_openBlock(), _createElementBlock('div', _hoisted_1, [
    _hoisted_2,                                    // 静态节点（提升）
    createVNode('p', { class: _ctx.dynamicClass },  // PATCH_CLASS (2)
      toDisplayString(_ctx.msg), 2                 // PATCH_TEXT (1)
    )
  ], 0 /* 无 PatchFlag */))
}
```

PatchFlags 定义（位掩码，可叠加）：

```ts
enum PatchFlags {
  TEXT = 1,           // 只有文本动态
  CLASS = 2,          // 只有 class 动态
  STYLE = 4,          // 只有 style 动态
  PROPS = 8,          // 除 class/style 外的 props 动态
  FULL_PROPS = 16,    // 所有 props 都可能动态
  HYDRATE_EVENTS = 32,// 有事件监听器（SSR hydration 用）
  STABLE_FRAGMENT = 64, // 稳定 Fragment（子节点顺序不变）
  PROPS_NEEDS_PATCH = 128, // 需要 fullPathness 检查
  UNKEYED_FRAGMENT = 256,  // 无 key 的 Fragment
  NEED_PATCH = 512,    // 可能需要 patch（如 ref、directives）
  DYNAMIC_SLOTS = 1024, // 动态插槽
  DEV_ROOT_FRAGMENT = 2048, // 开发环境根 Fragment
  HOISTED = -1,        // 静态提升
  BAIL = -2,           // 整棵子树都是动态的
}
```

Diff 时只需检查对应标记位即可，完全跳过静态部分。

#### 17.2 Block Tree

Block 收集该节点下**所有动态子节点**的集合。Diff 时只遍历 Block 中的动态节点，**完全跳过静态子树**。

对于 `v-if` 分支，每个分支都是一个独立的 Block；对于 `v-for` 列表，整个列表构成一个 Block。

#### 17.3 静态提升（Hoist Static）

静态不变的子树被提升到渲染函数外部，只创建一次：

```js
// 编译前：每次 render 都创建静态 VNode
function render() {
  return h('div', null, [
    h('p', null, 'static1'),
    h('p', null, 'static2'),
    h('span', null, dynamicContent)
  ])
}

// 编译后：静态节点只创建一次
const _hoisted = [
  h('p', null, 'static1'),
  h('p', null, 'static2')
]

function render() {
  return h('div', null, [
    ..._hoisted,              // 直接引用，不重建
    h('span', null, dynamicContent)
  ])
}
```

#### 17.4 预字符串化

对于连续的大段纯静态节点，直接序列化为 HTML 字符串，渲染时 `innerHTML` 一次性插入：

```js
const _hoisted = createStaticVNode('<p>a</p><p>b</p><p>c</p>', 3)
// 参数 3 表示包含 3 个静态节点
```

比逐个创建 VNode 再渲染快得多。

#### 17.5 缓存内联事件处理函数

```html
<button @click="handleClick">Click</button>
<!-- 编译后会缓存 handleClick 的引用 -->
```

如果不缓存，每次 render 创建的新函数引用会让子组件误判 props 变了从而不必要的更新。

#### 17.6 v-once

标记为 `v-once` 的节点只渲染一次：

```html
<p v-once>This will never change: {{ msg }}</p>
```

msg 的值只在首次渲染时取一次，后续更新完全跳过。

#### 编译优化的综合效果

这些优化手段配合使用后：

> **一个结构稳定但数据变化的页面，Vue 3 的 Diff 成本可以做到 \(O(1)\)**——只检查标记了 PatchFlag 的少量动态节点，静态部分全程零开销。

## 第六篇：服务端渲染

### 第 18 章：同构渲染

| 方案 | 渲染位置 | 首屏速度 | SEO | 交互延迟 | 实现复杂度 |
|------|---------|---------|-----|---------|-----------|
| **CSR** | 浏览器 | 慢 | 差 | 无 | 低 |
| **SSR** | 服务器 | 快 | 好 | 有 | 中 |
| **同构** | 两端兼有 | **快** | **好** | **无** | 高 |

同构渲染的关键挑战：

1. **客户端激活（Hydration）**：服务器输出的静态 HTML 需要"激活"为可交互的 Vue 组件——Vue 3 的 `createSSRApp` + `hydrate()` 完成
2. **生命周期兼容**：`mounted` 在 CSR 中执行一次，在 SSR 中不执行（已在服务端完成）；`onServerPrefetch` 仅 SSR 中执行
3. **跨平台 API 限制**：只能使用浏览器和 Node.js 都支持的 API（如 `window` / `document` 在 SSR 中不可用）
4. **状态管理**：避免交叉请求的状态污染——每个请求必须有独立的状态实例
5. **`ClientOnly` 组件**：某些第三方库只能在浏览器中使用（如地图、图表）

## 总结：优秀前端框架设计的共性原则

通读全书后，可以归纳出几条超越 Vue.js 本身的通用设计原则：

| 原则 | 书中的体现 | 适用范围 |
|------|-----------|---------|
| **权衡意识** | 声明式 vs 命令式、运行时 vs 编译时 | 每个架构决策都有代价 |
| **分层解耦** | 响应系统 / 渲染器 / 编译器各自独立又协作 | 模块间低耦合是可扩展的基础 |
| **渐进增强** | 先保证正确（简单 Diff），再追求效率（快速 Diff） | 正确性 > 性能 |
| **下限保障** | 编译器帮新手做的优化 | 让普通代码也能跑得不错 |
| **灵活性与约束并存** | 自定义渲染器 + 编译器插件 | 给高级玩家自由度的同时不给新手挖坑 |

正如尤雨溪在序言中所说的：

> **即使抛开具体的实现，这本书也可以作为现代前端框架设计的一个非常有价值的参考。**
