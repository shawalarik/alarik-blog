这一模块聚焦 React 状态更新的执行模型，理解调度策略、闭包语义与并发渲染。

## React 的响应式哲学

React 的响应式理念与 Vue 有本质不同：

| 维度 | Vue（响应式） | React（不可变） |
|------|-------------|----------------|
| **核心理念** | 数据变化自动驱动视图更新 | 数据不可变，调用 setState 触发重渲染 |
| **状态管理** | 可变数据 + Proxy 劫持 | 不可变数据（Immutable Data） |
| **更新粒度** | 属性级细粒度追踪 | 组件级重新渲染 |
| **开发者心智** | "改了就自动更新" | "创建新状态，告诉 React 重绘" |

> React 并没有传统意义上的"响应式系统"，它通过**不可变数据 + 调度渲染**实现了类似效果。理解这一点是学习 React 状态管理的起点。

## setState 原理

### 基础行为

```jsx
class Counter extends React.Component {
  state = { count: 0 };

  increment = () => {
    // 1. setState 是异步批量合并的
    this.setState({ count: this.state.count + 1 });

    console.log(this.state.count);  // 还是 0！不是 1
  };

  render() {
    return (
      <>
        <p>{this.state.count}</p>
        <button onClick={this.increment}>+1</button>
      </>
    );
  }
}
```

### 异步批量更新

React 16/17 的 `setState` 在**事件处理器和生命周期函数中是异步批量的**：

```jsx
handleClick = () => {
  this.setState({ a: 1 });   // 不立即更新
  this.setState({ b: 2 });   // 合并到同一个批次
  this.setState({ c: 3 });   // 合并到同一个批次

  // 最终只触发一次重渲染
  // state = { count: 0, a: 1, b: 2, c: 3 }
};
```

但在**异步场景**（setTimeout、Promise、原生事件）中则是同步的：

```jsx
componentDidMount() {
  // setTimeout 中 —— 同步执行
  setTimeout(() => {
    this.setState({ a: 1 });   // 立即触发一次重渲染
    this.setState({ b: 2 });   // 立即触发另一次重渲染
    // 共 2 次重渲染！
  });

  // Promise 中 —— 同步执行
  fetch('/api/data').then(() => {
    this.setState({ data: res });  // 立即重渲染
  });
}
```

### 函数式更新

当新状态依赖于前一个状态时，**必须使用函数式更新**来避免异步导致的脏读问题：

```jsx
// ❌ 错误：可能基于过期值计算
incrementThreeTimes = () => {
  this.setState({ count: this.state.count + 1 });
  this.setState({ count: this.state.count + 1 });
  this.setState({ count: this.state.count + 1 });
  // 结果可能是 +1 而不是 +3（因为三次读取的都是同一个旧值）
};

// ✅ 正确：函数式更新保证顺序执行
incrementThreeTimes = () => {
  this.setState(prev => ({ count: prev.count + 1 }));
  this.setState(prev => ({ count: prev.count + 1 }));
  this.setState(prev => ({ count: prev.count + 1 }));
  // 结果一定是 +3
};
```

### React 18 的 Automatic Batching

React 18 通过 `ReactDOM.createRoot()` 将批量更新推广到了**所有场景**：

```jsx
// React 18：所有 setState 都是批量处理的
function handleClick() {
  fetch('/api').then(() => {
    // 即使在 Promise 回调中也批量处理！
    setStateA(1);   // 不立即渲染
    setStateB(2);   // 合并批次
    // 只触发一次重渲染
  });
}

// 启用方式
const root = ReactDOM.createRoot(document.getElementById('app'));
root.render(<App />);
```

如需退出批量更新，使用 `flushSync`：

```jsx
import { flushSync } from 'react-dom';

flushSync(() => {
  setStateA(1);  // 立即同步重渲染
});
console.log(ref.current.textContent);  // 已更新

setStateB(2);   // 下一次批量
```

## useState 闭包陷阱

这是 React 开发中最常见的响应式相关陷阱之一。

### 问题根源

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // ⚠️ 这里的 count 永远是 0！—— 闭包陷阱
      console.log(count);  // 始终输出 0
      setCount(count + 1);  // 永远是 0 + 1 = 1
    }, 1000);

    return () => clearInterval(id);
  }, []);  // 空依赖数组意味着回调只创建一次

  // 结果：count 显示为 1 就不动了
  return <p>{count}</p>;
}
```

**原因分析**：`useEffect` 的回调在首次渲染时创建并捕获了当时的 `count`（即 0）。由于依赖数组为空，这个回调永远不会重建，所以它永远看到的是旧的 `count`。

### 解决方案

```jsx
// 方案一：函数式更新（推荐）
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);  // c 是最新的状态值
  }, 1000);
  return () => clearInterval(id);
}, []);

// 方案二：将 count 加入依赖数组
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);
  }, 1000);
  return () => clearInterval(id);
}, [count]);  // 每次 count 变化都重建定时器（性能稍差）

// 方案三：useRef 保持最新值的引用
const countRef = useRef(0);
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    countRef.current += 1;
    setCount(countRef.current);
  }, 1000);
  return () => clearInterval(id);
}, []);
```

### 更多闭包陷阱示例

```jsx
// 陷阱：事件处理器中的过期状态
function List({ items }) {
  const [selectedId, setSelectedId] = useState(null);

  useEffect(() => {
    // 当 items 从外部 prop 改变时...
    // selectedId 引用的可能是旧的 item（已被删除）
    const selectedItem = items.find(i => i.id === selectedId);
    console.log(selectedItem);  // 可能是 undefined
  }, [items]);
}

// 修复方案
useEffect(() => {
  setSelectedId(prev => {
    // 用函数式更新确保拿到最新值
    return items.some(i => i.id === prev) ? prev : null;
  });
}, [items]);
```

## Fiber 架构下的更新调度

### Fiber 简介

Fiber 是 React 16 引入的重构架构，将渲染工作分解为**可中断的小任务单元**：

```
传统栈递归渲染：
  render() → createElement → diff → patch（不可中断，一次性完成）

Fiber 架构：
  Work Loop → 每个 Fiber 节点独立处理 → 可中断/恢复 → 时间分片
```

```js
// 简化的 Fiber 调度循环
function workLoop(hasTimeRemaining, currentTime) {
  while (currentTask && hasTimeRemaining(currentTime)) {
    currentTask = performUnitOfWork(currentTask);
  }

  if (currentTask) {
    // 还有未完成的任务 —— 让出主线程
    requestCallback(workLoop);
  }
}

// requestCallback 基于 MessageChannel / setTimeout 实现
// 让浏览器有机会处理高优先级的交互（点击、输入等）
```

### 优先级系统

React 为不同类型的更新定义了优先级：

| 优先级 | 类型 | 示例 | 说明 |
|--------|------|------|------|
| **同步最高** | Discrete | 用户输入、点击 | 必须立即响应 |
| **高** | UserBlocking | hover、滚动 | 用户交互反馈 |
| **普通** | Normal | 数据获取、网络请求 | 默认优先级 |
| **低** | Idle | 分析、日志记录 | 空闲时才做 |
| **最低** | Offscreen | 隐藏内容 | 几乎不做 |

```jsx
// 不同操作对应不同优先级
<button onClick={handleClick}>       {/* 同步优先级 */}
<input onChange={handleChange}>      {/* UserBlocking */}
<div onMouseEnter={handleHover}>      {/* Normal */}
{showAnalytics && <Analytics />}     {/* 低/Idle */}
```

## 并发更新（Concurrent Rendering）

React 18 引入的并发特性彻底改变了状态更新的调度方式。

### Concurrent Features

```jsx
// 1. Transitions —— 区分紧急和非紧急更新
import { startTransition, useTransition } from 'react';

function SearchBox() {
  const [inputValue, setInputValue] = useState('');
  const [searchResults, setSearchResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    // 紧急更新：立即响应用户输入
    setInputValue(e.target.value);

    // 非紧急更新：搜索结果可以延迟
    startTransition(() => {
      setSearchResults(search(e.target.value));  // 低优先级
    });
  }

  return (
    <div>
      <input value={inputValue} onChange={handleChange} />
      {isPending && <Spinner />}
      <ResultList results={searchResults} />
    </div>
  );
}

// 2. Suspense —— 异步数据加载
<Suspense fallback={<Loading />}>
  <AsyncComponent />
</Suspense>

// 3. useDeferredValue —— 延迟非关键部分的更新
function LargeList({ filterText }) {
  const deferredText = useDeferredValue(filterText);

  return (
    <>
      <Input value={filterText} />                    {/* 立即更新 */}
      <List items={items.filter(match(deferredText))} /> {/* 延迟更新 */}
    </>
  );
}
```

### 并发模式下的状态一致性

并发模式下可能出现** tearing（撕裂）**问题——同一状态的多次读取可能不一致：

```jsx
// 理论上的撕裂问题（React 内部已解决）
function Counter() {
  const [count, setCount] = useState(0);

  // 高优先级中断可能导致：
  // 第一次读到 count=5，中断后第二次读到 count=6
  // 同一次渲染中出现不一致
  return (
    <div>
      {count} {/* 可能显示不同的值？ */} + {count}
    </div>
  );
}
```

React 通过以下机制避免撕裂：
- **状态队列化**：每次更新进入队列，按顺序应用
- **双缓冲渲染**：在内存中构建完整的虚拟 DOM 树后再提交
- **不可变性保证**：每次渲染看到的都是一个一致的状态快照

### Suspense 与数据流

```jsx
// 结合 Suspense 的响应式数据流
function UserProfile({ userId }) {
  return (
    <Suspense fallback={<Skeleton />}>
      <AsyncBoundary>
        {/* 数据请求作为"特殊的状态更新"触发 Suspense */}
        <UserDetails userId={userId} />
        <UserPosts userId={userId} />
      </AsyncBoundary>
    </Suspense>
  );
}

// 内部实现（简化）
function UserDetails({ userId }) {
  // 这个 hook 会"抛出"Promise，触发 Suspense 边界
  const user = use(fetchUser(userId));

  return <Card>{user.name}</Card>;
}
```

## 小结

| 概念 | 要点 |
|------|------|
| **setState 异步批量** | 事件/生命周期内批量；React 18 全场景批量（createRoot）；`flushSync` 强制同步 |
| **函数式更新** | `setState(prev => newValue)` 避免基于过期状态计算 |
| **闭包陷阱** | useEffect/useCallback/useMemo 的依赖数组决定闭包是否刷新；ref 可绕过此限制 |
| **Fiber 调度** | 可中断的增量渲染；时间分片避免阻塞主线程 |
| **优先级系统** | 离散 > 用户阻塞 > 普通 > 空闲 > 后台 |
| **Concurrent Features** | Transition 区分紧急/非紧急更新；Suspense 处理异步状态；useDeferredValue 延迟非关键部分 |

React 的状态更新机制虽然不像 Vue 那样"自动"，但它提供了更精细的控制力——开发者可以明确决定何时、以何种优先级更新 UI。
