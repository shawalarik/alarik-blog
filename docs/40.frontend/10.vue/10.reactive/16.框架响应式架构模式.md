这一模块把响应式放回架构语境，梳理不同模式下的数据流、职责边界与可扩展性。

## 架构模式演进史

```
1979  MVC (Smalltalk-80)
 │
 ├→ 1987  MVP (Taligent)
 │
 ├→ 2004  MVVM (WPF / Martin Fowler's Presentation Model)
 │
 └→ 2009+ 前端架构革命
      ├── 2013  Flux (Facebook)
      ├── 2015  Redux (Dan Abramov)
      ├── 2017  MVI (Cycle.js / Model-View-Intent)
      └── 2020+ Signal-based Architectures
```

## MVC（Model-View-Controller）

### 经典定义

```
┌─────────────────────────────────────┐
│              用户交互                  │
│                 ▼                    │
│  ┌──────┐   操作    ┌──────────┐    │
│  │ View │──────────▶│Controller│    │
│  └──────┘            └────┬─────┘    │
│       ▲                   │ 更新     │
│       │ 渲染              ▼         │
│  ┌────┴────┐          ┌────────┐    │
│  │  Model  │◀─────────│        │    │
│  └─────────┘  数据查询 │        │    │
│                       └────────┘    │
└─────────────────────────────────────┘

职责：
- Model: 数据和业务逻辑
- View: UI 展示（被动，被 Controller 操作）
- Controller: 处理用户输入，协调 M 和 V
```

### 前端中的变体

```js
// 简化的前端 MVC 示例
// Model
const TodoModel = {
  items: [],
  add(text) {
    this.items.push({ id: Date.now(), text, done: false });
    this.notify('change');
  },
  toggle(id) {
    const item = this.items.find(i => i.id === id);
    if (item) item.done = !item.done;
    this.notify('change');
  },
  listeners: [],
  onChange(fn) { this.listeners.push(fn); return () => { /* remove */ }; },
  notify(event) { this.listeners.forEach(l => l(event, this.items)); },
};

// View
function renderTodoView(model, container) {
  model.onChange((event, items) => {
    container.innerHTML = `
      <ul>${items.map(item => `
        <li data-id="${item.id}" class="${item.done ? 'done' : ''}">
          ${item.text}
          <button action="toggle">Toggle</button>
        </li>
      `).join('')}</ul>
    `;

    // 事件委托给 Controller
    container.addEventListener('click', (e) => {
      const target = e.target.closest('[action]');
      if (target) {
        const id = Number(target.closest('[data-id]').dataset.id);
        TodoController.handle(target.getAttribute('action'), id);
      }
    });
  });
}

// Controller
const TodoController = {
  handle(action, payload) {
    switch(action) {
      case 'toggle': TodoModel.toggle(payload); break;
    }
  },

  init() {
    renderTodoView(TodoModel, document.getElementById('app'));
  },
};
```

**MVC 在前端的困境：** View 和 Controller 的界限模糊（尤其是事件驱动的 Web 应用），Model 和 View 容易产生双向依赖。

## MVP（Model-View-Presenter）

### 核心变化：View 被动化

```
MVC 中：View 和 Model 可以直接通信
MVP 中：所有通信必须经过 Presenter（View 是完全被动的）

┌──────┐    用户操作    ┌───────────┐
│ View │─────────────▶│ Presenter  │
│(被动) │◀────────────│           │
│       │   更新 UI    │  业务逻辑  │
└──────┘              └─────┬─────┘
                           │ 读写
                           ▼
                      ┌─────────┐
                      │  Model  │
                      └─────────┘
```

```typescript
interface ITodoView {
  showItems(items: TodoItem[]): void;
  showLoading(): void;
}

class TodoPresenter {
  constructor(private view: ITodoView, private model: TodoModel) {}

  async loadTodos() {
    this.view.showLoading();
    const items = await this.model.fetchAll();
    this.view.showItems(items);
  }

  toggleTodo(id: number) {
    this.model.toggle(id);
    this.view.showItems(this.model.getItems());
  }
}
```

**优点：** View 完全被动，易于测试（可以 Mock View）。  
**缺点：** Presenter 容易变成"上帝对象"（God Object），承担过多职责。

## MVVM（Model-View-ViewModel）

Vue 就是 MVVM 模式的代表实现。

```
┌──────────┐   数据绑定    ┌──────────────┐
│  View    │◀────────────▶│ ViewModel    │
│ (Template)│────────────▶│ (响应式状态)   │
└──────────┘   用户操作    └──────┬───────┘
                                  │ 读写
                                  ▼
                             ┌─────────┐
                             │  Model   │
                             └─────────┘

关键机制：
- 双向数据绑定（View ↔ ViewModel）
- ViewModel 是 View 的"建模"（包含展示逻辑但不引用 DOM）
- Observer 模式自动同步
```

### Vue 组件就是 MVVM

```vue
<!-- View: 模板 -->
<template>
  <div>
    <input v-model="searchQuery" placeholder="Search..." />
    <div v-if="loading">Loading...</div>
    <ul v-else>
      <li v-for="item in filteredItems" :key="item.id">
        {{ item.text }}
      </li>
    </ul>
  </div>
</template>

<script setup lang="ts">
// ViewModel: 响应式状态 + 展示逻辑
import { ref, computed, onMounted } from 'vue';

const searchQuery = ref('');
const rawItems = ref<Item[]>([]);
const loading = ref(false);

// ViewModel 包含派生状态 —— 这就是 "Model of the View"
const filteredItems = computed(() =>
  rawItems.value.filter(item =>
    item.text.toLowerCase().includes(searchQuery.value.toLowerCase())
  )
);

onMounted(async () => {
  loading.value = true;
  rawItems.value = await api.fetchItems();
  loading.value = false;
});
</script>

<style scoped>/* 视觉样式 */</style>
```

## Flux（单向数据流）

Flux 由 Facebook 在 2014 年提出，是 React 生态的架构基础。

```
┌──────┐  Action   ┌─────────┐  Dispatch  ┌──────────┐
│ View │─────────▶│  Action  │──────────▶│ Callback │
│      │          │ Creator  │           │ Registry │
└──▲───┘          └─────────┘           └─────┬────┘
   │                                           │
   │ Change                              所有 Store
   │ notification                        接收并处理
   │                                           │
   │                                    ┌─────▼─────┐
   │                                    │   Store   │
   │                                    │ (State)   │
   │                                    └─────┬─────┘
   │                                          │ emit
   │                                          │ change
└──────────────────────────────────────────┘
```

### 核心概念

| 概念 | 职责 | 类比 |
|------|------|------|
| **Action** | 描述发生了什么（纯对象） | 新闻标题 |
| **Dispatcher** | 分发 Action 到所有注册的回调 | 广播站 |
| **Store** | 状态 + 逻辑（接收 Action 后更新） | 部门经理 |
| **View** | 监听 Store 变化后重新渲染 | 显示屏 |

## Redux（Flux 的最佳实践）

Redux 将 Flux 形式化为三个严格原则：

```
1. Single Source of Truth（单一数据源）
2. State is Read-Only（只读状态）
3. Changes are Made with Pure Functions（纯函数修改）

┌─────────────────────────────────────────────────┐
│                                                 │
│  ┌─────────┐                                   │
│  │  Store  │◀── Reducer(state, action) → newState │
│  │ (State) │                                    │
│  └────┬────┘                                    │
│       │                                         │
│       │ subscribe(listener)                     │
│       ▼                                         │
│  ┌─────────┐     dispatch(action)    ┌─────────┐ │
│  │  View   │───────────────────────▶│  Action  │ │
│  │(React)  │                        │ Creators│ │
│  └─────────┘                        └─────────┘ │
│                                               │
│  Middleware (可选):                            │
│  dispatch → middleware1 → middleware2 → reducer  │
│                                               │
└─────────────────────────────────────────────────┘
```

### Redux 与响应式的关系

Redux 本身不是响应式的——它是一个**可预测的状态容器**。React 通过 `react-redux` 的 `connect`/`useSelector` 将 Redux state 变为"类响应式"：

```tsx
// useSelector 本质上创建了一个订阅：
// store.subscribe → 对比 selector 结果 → 有变化则触发 re-render

function UserProfile({ userId }: Props) {
  // 只有 user.name 变化才重渲染
  const userName = useSelector(
    (state: RootState) => state.users.entities[userId]?.name
  );

  return <h1>{userName}</h1>;
}
```

这实际上是一种 **手动声明式的细粒度响应式**——开发者通过 selector 函数显式声明了"我依赖什么"，类似于 Vue computed 的 getter 函数。

## MVI（Model-View-Intent）

MVI 来自 Cycle.js 和 Android Jetpack，强调函数式和不可变性。

```
┌────────┐   Intent    ┌─────────┐  Model update   ┌─────────┐
│  View  │───────────▶│  Model  │───────────────▶│  State  │
│(React/ │◀──────────│(Update  )│                │ (Immutable)│
│ Vue)   │   State   │ fn)      │                └─────────┘
└────────┘           └─────────┘
                          │
                          │ Side Effects
                          ▼
                     ┌──────────┐
                     │ Sources  │
                     │(HTTP/WS/ │
                     │ DOM etc.)│
                     └──────────┘
```

### MVI 核心要素

| 要素 | 说明 | 特点 |
|------|------|------|
| **Intent** | 用户意图的纯描述（非命令） | 类似 Action 但语义更明确 |
| **Model** | 纯函数：State × Intent → State | 可预测、可测试 |
| **View** | State → UI 的纯映射 | 无副作用 |
| **Side Effects** | 通过 sink/source 处理 | 与主循环解耦 |

```typescript
// MVI 实现（简化版）
type Intent = { type: 'INCREMENT' } | { type: 'DECREMENT' } | { type: 'RESET' };
type State = { count: number };

const initialState: State = { count: 0 };

function model(state: State, intent: Intent): State {
  switch (intent.type) {
    case 'INCREMENT': return { count: state.count + 1 };
    case 'DECREMENT': return { count: Math.max(0, state.count - 1) };
    case 'RESET': return initialState;
  }
}

// View 是一个纯函数
function view(state: State): VNode {
  return h('div', [
    h('span', {}, `Count: ${state.count}`),
    h('button', { onClick: () => send({ type: 'INCREMENT' }) }, '+'),
    h('button', { onClick: () => send({ type: 'DECREMENT' }) }, '-'),
  ]);
}

// 主循环
let state = initialState;
function send(intent: Intent) {
  state = model(state, intent);
  render(view(state));  // 重新渲染
}
```

## 模式对比总结

| 维度 | MVC | MVP | MVVM | Flux/Redux | MVI |
|------|-----|-----|------|-----------|-----|
| **数据方向** | 允许双向 | 单向（经 P） | 双向绑定 | 严格单向 | 严格单向 |
| **状态管理** | 分散在 M/V/C |集中在 P | VM 中集中 | 单一 Store | 纯函数推导 |
| **可测试性** | 中等 | 高 | 高 | 极高 | 极高 |
| **学习曲线** | 低 | 中 | 低-中 | 中-高 | 高 |
| **适合规模** | 小型 | 中型 | 中-大型 | 大型 | 中-大型 |
| **响应式程度** | 手动 | 手动 | 自动（框架） | 半自动（selector） | 手动（需自建） |
| **主要使用者** | Backbone.js | 传统桌面应用 | Vue/WPF/Angular | React 生态 | Cycle.js/Android |

## 选择建议

```
你的项目特征是什么？

小型项目 / 原型：
  → MVVM（Vue SFC 最快上手）、或简单 MVC

中型项目 / 单团队：
  → MVVM（Vue）或 Redux（React 团队熟悉的话）

大型项目 / 多团队协作：
  → Redux（严格约束）或分层 MVVM + Pinia

需要极致的可测试性和可追溯性：
  → MVI 或 Elm Architecture

微前端 / 跨框架共享：
  → 独立状态层 + 各框架各自的适配层（参见第14章）
```

## 小结

架构模式没有银弹。选择的核心依据：

1. **团队规模和能力** —— 复杂的模式需要更高的学习成本
2. **项目的预期生命周期** —— 短期原型不需要 Redux
3. **是否多人协作** —— 严格的单向数据流减少协作摩擦
4. **测试要求** —— 纯函数架构（Redux/MVI）最易测试
5. **性能敏感度** —— 细粒度响应式（MVVM/Signal）优于组件级重绘

现代趋势是在**保持架构简洁的同时引入响应式能力**——MVVM 的自动更新便利性 + Redux 的可预测性 = Pinia / Zustand / Jotai 等新一代方案。
