# Hooks 设计哲学

## 1. 为什么需要 Hooks

### 1.1 类组件的痛点

在 Hooks 出现之前（React 16.8 之前），组件逻辑复用面临严重困境：

```
┌─────────────────────────────────────────────┐
│           组件逻辑复用的"三座大山"            │
├─────────────────────────────────────────────┤
│                                             │
│  1. Mixins (已废弃)                         │
│     → 隐式依赖、命名冲突、难以理解           │
│                                             │
│  2. HOC (高阶组件)                          │
│     → Wrapper Hell（嵌套地狱）              │
│     → <WithTheme(WithAuth(WithData(App)))> │
│                                             │
│  3. Render Props                           │
│     → 深层嵌套的回调金字塔                   │
│     → <Fetcher>{({data}) => <List data={data}/>}</Fetcher>
│                                             │
│  共同问题：                                 │
│     • 逻辑代码被拆散到不同生命周期中          │
│     • 相关逻辑无法组织在一起                 │
│     • this 绑定问题                         │
│     • 难以在组件之间共享有状态逻辑           │
└─────────────────────────────────────────────┘
```

### 1.2 Hooks 的解决方案

```jsx
// ====== 之前：类组件 + HOC 的痛苦 ======
class UserProfile extends React.Component {
  constructor(props) { /* ... */ }
  componentDidMount() { /* 获取用户数据 */ }
  componentDidUpdate(prevProps) { /* 监听 props 变化 */ }
  componentWillUnmount() { /* 清理订阅 */ }
  render() { return <div>{/* ... */}</div>; }
}
export default withAuth(withTheme(withLogger(UserProfile)));

// ====== 之后：Hooks 的优雅 ======
function UserProfile({ userId }) {
  const user = useUser(userId);        // 数据获取逻辑
  const theme = useTheme();             // 主题逻辑
  const logger = useLogger('Profile');  // 日志逻辑

  // 所有相关逻辑紧密排列在一起！
  if (!user) return <Loading />;
  return (
    <Card theme={theme}>
      <h1>{user.name}</h1>
      {/* ... */}
    </Card>
  );
}

// 没有 Wrapper Hell，没有 this，没有生命周期分散！
```

## 2. Hooks 的设计原则

### 2.1 核心设计目标

| 目标 | 说明 |
|------|------|
| **完全向后兼容** | 类组件继续可用，渐进迁移 |
| **无破坏性变更** | 不重写任何现有概念 |
| **组合优于继承** | 通过组合多个 Hook 实现复杂逻辑 |
| **灵活性** | 不强制特定模式，提供底层原语 |

### 2.2 设计约束

React 团队在设计中遵循了两个硬性约束：

#### 约束一：顶层调用规则

```jsx
// ❌ 错误：在条件语句中调用 Hooks
function BadComponent({ showCounter }) {
  const [name, setName] = useState('');   // ✅ 第 1 个 hook，索引 0
  
  if (showCounter) {
    // ⚠️ 如果 showCounter 为 false，这个 hook 就不会执行
    // 导致下一个 hook 的索引错乱！
    const [count, setCount] = useState(0);  // ❌ 条件中的 hook
  }
  
  useEffect(() => { /* ... */ });  // ⚠️ 索引可能变成 1 或 2
}

// ✅ 正确：始终在组件顶层调用
function GoodComponent() {
  const [name, setName] = useState('');
  const [count, setCount] = useState(0);  // 始终执行
  
  useEffect(() => { /* ... */ });         // 始终执行
  
  if (showCounter) {  // 条件判断放在 hook 之后
    return <span>{count}</span>;
  }
  
  return null;
}
```

**为什么必须这样？** React 内部通过**调用顺序**来识别每个 Hook 对应的状态：

```
第一次渲染:
  useState('Alarik')  → 创建 state #0 = 'Alarik'
  useState(0)         → 创建 state #1 = 0
  useEffect(fn)       → 存储 effect #0

第二次渲染:
  useState(?)         → 读取 state #0 ('Alarik')
  useState(?)         → 读取 state #1 (0)
  useEffect(fn)       → 替换 effect #0

如果顺序变了 → 读错了 state → BUG!
```

#### 约束二：只在 React 函数中调用

```jsx
// ✅ 允许的位置：
function MyComponent() {          // 函数组件内
  useState();
}

function useCustomHook() {        // 自定义 Hook 内
  useState();                     // 自定义 Hook 本质也是函数
}

// ❌ 不允许的位置：
class MyClass extends Component {  // 类组件内
  render() {
    useState();                   // ❌
  }
}

function regularFunction() {      // 普通 JS 函数内
  useState();                     // ❌
}
```

### 2.3 为什么不使用静态分析替代调用顺序？

有人可能会问：为什么不用编译器/静态分析来确保正确性？

> React 团队考虑过多种方案，但最终选择了运行时约束。原因是：
> 1. 编译方案会增加工具链依赖和构建复杂度
> 2. 运行时检查简单可靠，且可以通过 ESLint 插件在开发时捕获违规
> 3. 保持 JavaScript 的动态特性，不过度依赖编译器

## 4. 自定义 Hooks —— 逻辑复用的新范式

### 4.1 基本模式

```jsx
// 自定义 Hook：命名必须以 "use" 开头
function useLocalStorage(key, initialValue) {
  const [storedValue, setStoredValue] = useState(() => {
    try {
      const item = window.localStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch {
      return initialValue;
    }
  });

  const setValue = (value) => {
    try {
      const valueToStore = value instanceof Function ? value(storedValue) : value;
      setStoredValue(valueToStore);
      window.localStorage.setItem(key, JSON.stringify(valueToStore));
    } catch (error) {
      console.error(error);
    }
  };

  return [storedValue, setValue];
}

// 使用
function App() {
  const [name, setName] = useLocalStorage('name', 'Alarik');
  
  return (
    <input 
      value={name} 
      onChange={e => setName(e.target.value)} 
    />
  );
}
```

### 4.2 自定 Hook 的本质

```jsx
// 一个自定义 Hook 只是一个函数而已：
// - 名字以 "use" 开头（让 ESLint 插件能识别）
// - 可以调用其他 Hooks
// - 返回任意值

// 这就是一个合法的自定义 Hook
function useDoubleCount(initial) {
  const [count, setCount] = useState(initial);
  const doubled = count * 2;
  return [count, doubled, setCount];
}

// 使用
const [c, dc, setC] = useDoubleCount(5);  // c=5, dc=10
```

### 4.3 Hook 组合的力量

```jsx
// 复杂功能由简单 Hook 组合而成
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine);

  useEventListener('online', () => setIsOnline(true));
  useEventListener('offline', () => setIsOnline(false));

  return isOnline;
}

function useUserSession() {
  const [user, setUser] = useState(null);
  const isOnline = useOnlineStatus();

  useEffect(() => {
    if (!isOnline) return;  // 组合其他 Hook 的返回值
    
    fetch('/api/me').then(res => res.json()).then(setUser);
  }, [isOnline]);

  return user;
}

// 更复杂的场景：Hook 调用 Hook
function useDataFetching(url, options = {}) {
  const { debounceMs = 300 } = options;
  const debouncedUrl = useDebounce(url, debounceMs);
  const { data, error, loading } = useAsync(
    () => fetch(debouncedUrl).then(r => r.json()),
    [debouncedUrl]
  );
  return { data, error, loading };
}
```

## 5. 函数组件 vs 类组件的思维模型差异

```jsx
// ====== 类组件思维 ======
// 实例化一次，this 持有可变状态
// 生命周期方法在不同时机执行
// 状态分散在 constructor / 各个 lifecycle 中
class Timer extends React.Component {
  constructor(props) {
    super(props);
    this.state = { seconds: 0 };
  }
  componentDidMount() {
    this.interval = setInterval(() => {
      this.setState({ s: this.state.s + 1 });
    }, 1000);
  }
  componentWillUnmount() {
    clearInterval(this.interval);
  }
  render() { return <p>{this.state.seconds}s</p>; }
}

// ====== Hooks 思维 ======
// 每次渲染都是一次独立的函数调用
// 状态通过闭包保持
// 相关逻辑放在一起
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
    return () => clearInterval(id);  // cleanup 与 setup 在一起！
  }, []);

  return <p>{seconds}s</p>;
}
```

**关键心智模型转变**：

| | 类组件 | 函数组件 + Hooks |
|--|--------|----------------|
| 渲染概念 | 实例的方法调用 | 纯函数执行 |
| 状态存储 | `this`（实例属性） | 闭包（useState） |
| 副作用位置 | 分散在各生命周期 | 集中在 useEffect |
| 代码组织 | 按生命周期类型分组 | 按**关注点**分组 |
| 组件间共享 | HOC / Render Props | 自定义 Hook |

## 6. 常见误区与 FAQ

### Q1: Hooks 会取代类组件吗？

不会。React 团队明确表示**没有计划移除类组件**。两者可以共存。但新代码推荐使用 Hooks。

### Q2: Hooks 性能更差吗？

不一定。实际上函数组件 + Hooks 在某些场景下性能更好：

- 没有 `this` 绑定开销
- 没有 class 实例化的开销
- React 内部对函数组件有更多优化空间
- `React.memo` 比 `shouldComponentUpdate` 更简洁高效

### Q3: Hooks 让代码更难调试吗？

恰恰相反——因为相关逻辑集中在一起，追踪数据流更容易。

### Q4: 可以只在部分组件中使用 Hooks 吗？

可以。Hooks 是**增量采用**的，不需要一次性改造整个项目。一个文件一个文件地迁移即可。

## 7. 总结

```
┌──────────────────────────────────────────────────┐
│         Hooks 设计哲学要点                        │
├──────────────────────────────────────────────────┤
│ 动机: 解决类组件的逻辑复用困境                    │
│ 核心: 状态逻辑可以在组件间自由复用                │
│ 规则: 只在顶层调用，只在 React 函数中调用          │
│ 原理: 依赖调用顺序关联 state 和 hook              │
│ 力量: 自定义 Hook 实现组合式逻辑复用              │
│ 心智: 从"实例生命周期"转向"渲染即函数调用"         │
│ 迁移: 渐进式，新旧可共存                          │
└──────────────────────────────────────────────────┘
```
