# useContext 与跨组件共享

## 1. Props Drilling 问题

在没有 Context 时，跨层级传递数据需要逐层传递 props——这被称为 **Props Drilling（Props 穿透）**：

```jsx
// ====== Props Drilling 痛苦示例 ======
function App() {
  const [theme, setTheme] = useState('dark');
  const [currentUser, setCurrentUser] = useState(null);
  
  return (
    <PageLayout 
      theme={theme}           // ← 传给 PageLayout
      currentUser={currentUser}
      setCurrentUser={setCurrentUser}
    />
  );
}

function PageLayout({ theme, currentUser, setCurrentUser }) {
  return (
    <NavBar 
      theme={theme}           // ← 只是转发，自己不用
      currentUser={currentUser}
      setCurrentUser={setCurrentUser}
    >
      <MainContent 
        theme={theme}        // ← 又是转发
        currentUser={currentUser}
        setCurrentUser={setCurrentUser}
      />
    </NavBar>
  );
}

// NavBar 和 MainContent 都只是中间层...
// 实际使用 theme 和 user 的是深层子组件
```

**问题**：中间层组件被迫接收它们**根本不使用**的 props，增加了耦合度和维护成本。

## 2. Context API 基础

Context 提供了一种在组件树中**跨层级传递数据**的方式，无需手动逐层传递 props。

### 2.1 三步走

```jsx
import { createContext, useContext } from 'react';

// Step 1: 创建 Context
const ThemeContext = createContext('light');  // 默认值

// Step 2: 提供 Provider
function App() {
  const [theme, setTheme] = useState('dark');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <PageLayout />   {/* 子树内的任何组件都可以访问 theme */}
    </ThemeContext.Provider>
  );
}

// Step 3: 消费 Context
function DeepChild() {
  // 无需 props 穿透！直接获取
  const { theme, setTheme } = useContext(ThemeContext);

  return (
    <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
      Current: {theme}
    </button>
  );
}
```

**Props Drilling vs Context 对比**：

```
Props Drilling:
  App → PageLayout → NavBar → Header → ThemeButton
       ↓ theme     ↓ theme   ↓ theme   ↓ theme    (每层都传)

Context:
  App(Provider)
  └→ PageLayout
     └→ NavBar
        └→ Header
           └→ ThemeButton (useContext 直接取值!)
```

## 3. Context 最佳实践

### 3.1 将 Provider 和 Consumer 封装为自定义 Hook

```jsx
// theme-context.jsx
import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext(undefined);

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('dark');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const context = useContext(ThemeContext);
  
  if (context === undefined) {
    throw new Error('useTheme must be used within a ThemeProvider');
  }
  
  return context;
}

// 使用
function Button() {
  const { theme } = useTheme();  // 类型安全 + 自动检查 provider 包裹
  return <button className={`btn-${theme}`}>Click</button>;
}

// 入口处
<ThemeProvider>
  <App />
</ThemeProvider>
```

### 3.2 分离静态值和动态值

```jsx
// ⚠️ 不好的做法：所有东西都放一个 Context
const AppContext = createContext({
  theme: 'light',
  user: null,
  locale: 'zh-CN',
  config: { apiUrl: '/api' },
  // ... 太多内容，任何一个变化都导致所有消费者重渲染
});

// ✅ 好的做法：按关注点分离
const ThemeContext = createContext();
const UserContext = createContext();
const LocaleContext = createContext();
const ConfigContext = createContext();

// 每个 Context 只管自己的领域
```

### 3.3 避免 Context 导致的不必要重渲染

**问题**：当 Context value 变化时，**所有消费该 Context 的组件都会重渲染**，即使只用到了其中一部分数据。

```jsx
// ⚠️ 性能问题
const AppStateContext = createContext();

function Provider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const [notifications, setNotifications] = useState([]);
  
  // 任何一个 state 变化 → 整个 value 对象重建 → 所有消费者重渲染！
  const value = { user, setUser, theme, setTheme, notifications, setNotifications };
  
  return (
    <AppStateContext.Provider value={value}>
      {children}
    </AppStateContext.Provider>
  );
}

function NotificationBadge() {
  const { notifications } = useContext(AppStateContext);
  // 即使只是 theme 变了，这里也会重渲染！
  return <Badge count={notifications.length} />;
}
```

**解决方案**：拆分 Context 或使用 `memo` + 独立选择：

```jsx
// 方案1：拆分成细粒度的 Context
const ThemeContext = createContext();
const NotificationContext = createContext();

// 方案2：使用状态管理库的 selector 机制（如 Zustand/Jotai）
// 方案3：将不变的部分从 context 中剥离
const StaticConfig = { apiUrl: '/api', version: '1.0' };  // 不变的常量
const DynamicContext = createContext();  // 只放会变的部分
```

## 4. Context vs 组合（Composition）

### 4.1 组合模式的替代方案

有时 **children prop（组合）**比 Context 更合适：

```jsx
// ========== 组合模式 ==========
function Card({ header, footer, children }) {
  return (
    <div className="card">
      <div className="card-header">{header}</div>
      <div className="card-body">{children}</div>
      {footer && <div className="card-footer">{footer}</div>}
    </div>
  );
}

<Card
  header={<h3>Title</h3>}
  footer={<button>Action</button>}
>
  <p>This content is passed via composition.</p>
</Card>

// ========== 何时用哪种？ ==========
// 
// Context: 全局/跨区域的主题、用户认证、语言偏好
//         "很多深层不同类型的组件都需要的数据"
//
// Composition: UI 结构性的布局、插槽
//              "父组件控制子组件应该显示什么"
```

| 维度 | Context | Composition (children prop) |
|------|---------|---------------------------|
| 数据范围 | 全局/跨多级 | 父子之间 |
| 数据类型 | 任意（主题、用户、配置） | 主要是 JSX/UI |
| 解耦程度 | 高（消费者不知道 Provider 在哪） | 低（显式的父子关系） |
| 重渲染风险 | 较高（value 变化波及全部消费者） | 较低 |
| 可测试性 | 需要 Mock Provider | 天然容易测试 |

## 5. Context 的典型应用场景

### 5.1 主题切换

```tsx
interface Theme {
  colors: {
    primary: string;
    background: string;
    text: string;
  };
  spacing: Record<string, number>;
}

const ThemeContext = createContext<Theme>(defaultTheme);

function ThemedButton() {
  const theme = useContext(ThemeContext);
  return (
    <button style={{
      backgroundColor: theme.colors.primary,
      color: theme.colors.text,
      padding: `${theme.spacing.sm}px ${theme.spacing.md}px`,
    }}>
      Click me
    </button>
  );
}
```

### 5.2 当前用户信息

```jsx
const AuthContext = createContext<{
  user: User | null;
  login: (credentials) => Promise<void>;
  logout: () => void;
}>(null!);

function useAuth() {
  return useContext(AuthContext);
}

// 受保护的路由
function ProtectedRoute({ children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" />;
  return <>{children}</>;
}
```

### 5.3 国际化（i18n）

```jsx
const LocaleContext = createContext('en-US');
const TranslationContext = createContext<Record<string, string>>({});

function I18nProvider({ locale, messages, children }) {
  return (
    <LocaleContext.Provider value={locale}>
      <TranslationContext.Provider value={messages[locale]}>
        {children}
      </TranslationContext.Provider>
    </LocaleContext.Provider>
  );
}

function t(key: string) {
  const messages = useContext(TranslationContext);
  return messages[key] ?? key;
}

// 使用
<p>{t('greeting')}!</p>  {/* 自动根据当前 locale 显示 */}
```

## 6. 注意事项与陷阱

### 6.1 默认值的含义

```jsx
const MyContext = createContext(defaultValue);

// 当消费组件没有被 Provider 包裹时，使用默认值
// 这对于测试很有用（不需要 mock provider）
// 但在生产环境中可能导致隐蔽 bug

// 推荐：在自定义 hook 中检查 undefined
function useMyContext() {
  const ctx = useContext(MyContext);
  if (ctx === defaultValue && process.env.NODE_ENV !== 'test') {
    throw new Error('<MyProvider> must wrap this component');
  }
  return ctx;
}
```

### 6.2 Provider 的 value 引用稳定性

```jsx
// ⚠️ 每次 render 都创建新的 value 对象 → 子组件不必要的重渲染
<SomeContext.Provider value={{ a, b, c }}>
  {children}
</SomeContext.Provider>

// ✅ 用 useMemo 或 state 保持引用稳定
const value = useMemo(() => ({ a, b, c }), [a, b, c]);
// 或者
const [state, setState] = useState(() => ({ a, b, c }));

<SomeContext.Provider value={value}>
  {children}
</SomeContext.Provider>
```

### 6.3 Context 不适合高频更新的数据

```jsx
// ⚠️ 不适合：鼠标位置（每秒数十次更新）
const MouseContext = createContext({ x: 0, y: 0 });

function App() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  
  useEffect(() => {
    const handler = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);
  
  return (
    <MouseContext.Provider value={pos}>  // 极高频更新！
      {children}  // 所有消费者疯狂重渲染
    </MouseContext.Provider>
  );
}

// ✅ 替代方案：用 ref + 自定义事件 或 状态管理库
// 或者用 useSyncExternalStore（React 18）
```

## 7. Context vs 状态管理库

| 特性 | Context API | Zustand / Jotai / Redux |
|------|------------|------------------------|
| 学习成本 | 低（内置 API） | 中等（需引入库） |
| 适用规模 | 小~中型应用 | 中~大型应用 |
| 性能优化 | 需要手动拆分 Context | 内建 selector 机制 |
| DevTools | 无 | 有（Redux DevTools 等） |
| 中间件支持 | 无 | 支持（logger, persist 等） |
| 服务端渲染 | 需额外处理 | 大多有 SSR 方案 |

**经验法则**：先用 Context；当遇到性能问题或状态变得复杂时再引入专门的状态管理库。

## 8. 总结

```
┌──────────────────────────────────────────────────┐
│         Context 要点速查                           │
├──────────────────────────────────────────────────┤
│ 目的: 解决 Props Drilling，跨层级共享数据          │
│ 三步: createContext → Provider → useContext       │
│ 封装: Provider + 自定义 Hook (useXxx)            │
│ 拆分: 按关注点分离，避免单一巨型 Context          │
│ 性能: value 变化会导致所有消费者重渲染            │
│ 选择: Context 用于全局状态，Composition 用于布局   │
│ 不适合: 高频更新数据（如鼠标位置）                │
│ 稳定性: value 用 useMemo/state 保持引用稳定        │
└──────────────────────────────────────────────────┘
```
