# 内置状态管理概览

## 1. React 状态的分类

在讨论状态管理之前，首先要理解 **React 应用中的状态不是同一种东西**：

```
┌─────────────────────────────────────────────────────┐
│                  状态分类体系                          │
│                                                     │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐   │
│  │ Local    │  │ UI       │  │ Server           │   │
│  │ State    │  │ State    │  │ State            │   │
│  ├──────────┤  ├──────────┤  ├──────────────────┤   │
│  │ useState │  │ Modal开/关│  │ 用户数据          │   │
│  │ useReducer│ │ 输入框焦点│  │ 文章列表          │   │
│  │ useRef   │ │ 表单步骤  │  │ API 返回数据      │   │
│  │          │ │ 悬停状态  │  │ 权限信息          │   │
│  └────┬─────┘  └────┬─────┘  └──────┬───────────┘   │
│       │             │               │                │
│       ▼             ▼               ▼                │
│  组件内部        组件树局部      跨组件/跨会话         │
│  不需共享       少数组件共享     需要持久化/同步      │
│                                                     │
│  ┌──────────────────────────────────────────┐       │
│  │ URL / Communication State (通信状态)      │       │
│  ├──────────────────────────────────────────┤       │
│  │ URL 参数、路由状态、WebSocket 连接状态     │       │
│  └──────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────┘
```

| 状态类型 | 存储位置 | 生命周期 | 典型方案 |
|---------|---------|---------|---------|
| **Local State** | 单个组件内 | 组件挂载→卸载 | `useState` / `useReducer` |
| **UI State** | 几个相关组件间 | 用户交互期间 | `useState` + props / Context |
| **Server State** | 全局或远端 | 异步获取、可过期 | TanStack Query / SWR |
| **URL State** | 浏览器地址栏 | 导航周期 | `useSearchParams` / router state |
| **Global Client State** | 全局 | 应用运行期间 | Zustand / Jotai / Redux |

## 2. Props 逐层传递（Props Drilling）

### 2.1 什么是 Props Drilling

```
App (拥有 theme, user)
  └→ Header
      └→ NavigationBar
          └→ UserMenu
              └→ Avatar (需要 theme 和 user)
              
问题：Header、NavigationBar 都不需要 theme/user，
但必须一层层传递下去！
```

### 2.2 代码示例

```jsx
function App() {
  const [theme, setTheme] = useState('dark');
  const [user, setUser] = useState(null);
  
  return (
    <PageLayout 
      theme={theme}           // ← 只是为了传给深层子组件
      setTheme={setTheme}
      user={user}
      setUser={setUser}
    />
  );
}

function PageLayout({ theme, setTheme, user, setUser }) {
  return (
    <NavBar 
      theme={theme}           // ← 自己不用，只是转发
      setTheme={setTheme}
      user={user}
      setUser={setUser}
    >
      <MainContent 
        theme={theme}        // ← 又是转发
        user={user}
      />
    </NavBar>
  );
}

// 实际使用这些 props 的可能是第 5 层的子组件
```

**Props Drilling 的代价**：

| 问题 | 说明 |
|------|------|
| 耦合增加 | 中间组件被迫声明不属于自己的 props |
| 维护困难 | 改一个 prop 名要改整条链路 |
| 代码噪音 | 大量无意义的 prop 转发 |
| 重构风险 | 删掉中间某层的传递可能破坏深层组件 |

## 3. Context API —— 内置的轻量级解决方案

React 内置的 Context API 是解决 Props Drilling 的**第一道防线**：

```jsx
// 创建 Context
const ThemeContext = createContext({ theme: 'light', toggle: () => {} });

// 在顶层提供
<ThemeContext.Provider value={{ theme, toggle }}>
  <App />
</ThemeContext.Provider>

// 在任意深层消费
function DeepChild() {
  const { theme } = useContext(ThemeContext);
  return <div className={theme}>I know the theme!</div>;
}
```

### 3.1 Context 的局限

```
Context 的性能陷阱:

当 value 变化时 → 所有消费该 Context 的组件都重渲染
即使某个组件只用到 value 中不变的部分！

示例：
value = { theme, user, notifications }
  → ThemeButton 只用 theme
  → UserAvatar 只用 user  
  → NotificationBadge 只用 notifications
  
当 user 变化时 → ThemeButton 也跟着重渲染！（不必要的）
```

**结论**：Context 适合**低频变化的全局配置**（如主题、语言），不适合**高频变化的细粒度状态**。

## 4. useReducer — 复杂本地状态

当单个组件的状态逻辑变得复杂时，`useReducer` 是比多个 `useState` 更好的选择：

```jsx
// 多个 useState → 难以维护关联关系
const [items, setItems] = useState([]);
const [filter, setFilter] = useState('all');
const [sortOrder, setSortOrder] = useState('asc');
const [selectedIds, setSelectedIds] = useState(new Set());

// 升级为 useReducer → 所有转换逻辑集中管理
const initialState = {
  items: [],
  filter: 'all',
  sortOrder: 'asc',
  selectedIds: new Set(),
};

function reducer(state, action) {
  switch (action.type) {
    case 'ADD_ITEM':
      return { ...state, items: [...state.items, action.payload] };
    case 'TOGGLE_SELECT':
      const newSet = new Set(state.selectedIds);
      newSet.has(action.id) ? newSet.delete(action.id) : newSet.add(action.id);
      return { ...state, selectedIds: newSet };
    case 'SET_FILTER':
      return { ...state, filter: action.payload };
    default:
      return state;
  }
}
```

## 5. 内置方案的适用边界

```
                    复杂度 / 数据量
                       ↑
                       │
              第三方库  │  ● Redux / Zustand / Jotai
              (全局状态)  │  ● MobX / Recoil
                       │
              ─────────┼────────  ← 分界线
              Context   │
              +Reducer  │
                       │
              useState  │  ● 组件本地状态
              (本地)    │  ● UI 交互状态
                       │
                       └──────────→ 共享范围
```

### 决策流程图

```
你的状态需要在哪里使用？
  ├── 仅当前组件内部
  │   → useState（简单）或 useReducer（复杂）
  │
  ├── 当前组件及少数直接子组件
  │   → Props 传递（简单场景）
  │
  ├── 跨多层组件但低频变化（主题、语言）
  │   → Context API
  │
  ├── 跨多组件且高频变化 / 需要精细控制更新范围
  │   → Zustand / Jotai / Valtio
  │
  ├── 服务端数据（API 返回、需要缓存/同步/失效策略）
  │   → TanStack Query / SWR
  │
  ├── 复杂业务状态机（审批流、游戏角色状态、向导）
  │   → XState
  │
  └── 大型团队协作 / 严格架构要求
      → Redux Toolkit
```

## 6. 各内置 API 快速对比

| API | 定位 | 适用规模 | 性能特点 | 学习成本 |
|-----|------|---------|---------|---------|
| `useState` | 组件内单一值 | 小 | 高（精准触发） | ★☆☆☆☆ |
| `useReducer` | 组件内复杂逻辑 | 中 | 高 | ★★☆☆☆ |
| `useContext` | 跨层级共享 | 中~大 | 低（value 变化波及全部消费者） | ★★☆☆☆ |
| `useRef` | 不触发渲染的存储 | 小 | 最高（不触发渲染） | ★☆☆☆☆ |
| `useSyncExternalStore` | 订阅外部 store | 中~大 | 可控 | ★★★☆☆ |

## 7. 总结

```
┌──────────────────────────────────────────────────┐
│         内置状态管理要点速查                        │
├──────────────────────────────────────────────────┤
│ 状态分四类: Local / UI / Server / URL / Global    │
│ Props Drilling: 跨层级传递的痛点                   │
│ Context: 解决 Drilling 但有性能陷阱               │
│   → 适合低频全局配置，不适合高频细粒度状态          │
│ useReducer: 复杂本地状态的升级选择                 │
│ 选型核心: 根据共享范围和变化频率决定方案            │
│ 内置够用就不引入第三方库                           │
└──────────────────────────────────────────────────┘
```
