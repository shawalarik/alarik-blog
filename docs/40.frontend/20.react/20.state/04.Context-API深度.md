# Context API 深度解析

## 1. 核心概念

Context 提供了一种在**组件树中跨层级传递数据**的方式，无需逐层手动传递 props。

```
传统方式 (Props Drilling):
  App → A → B → C → D → Target (需要 data)

Context 方式:
  App (Provider 提供 data)
   ├── A
   ├── B
   └── C
       └── D
           └── Target (useContext 直接取 data)
```

## 2. API 详解

### 2.1 createContext

```tsx
// 创建一个 Context 对象
interface ThemeContextType {
  theme: 'light' | 'dark';
  toggleTheme: () => void;
}

// defaultValue：当组件没有被 Provider 包裹时的默认值
const ThemeContext = createContext<ThemeContextType>({
  theme: 'light',
  toggleTheme: () => {},
});

// React DevTools 中显示的名字
ThemeContext.displayName = 'ThemeContext';  // 可选
```

### 2.2 Provider

```jsx
<ThemeContext.Provider value={/* 某个值 */}>
  {/* 子树中的任何组件都可以读取这个值 */}
</ThemeContext.Provider>
```

**Provider 的工作机制**：

```jsx
function App() {
  const [theme, setTheme] = useState('dark');

  // value 可以是任何 JavaScript 值
  const contextValue = useMemo(() => ({
    theme,
    toggleTheme: () => setTheme(t => t === 'dark' ? 'light' : 'dark'),
  }), [theme]);

  return (
    <ThemeContext.Provider value={contextValue}>
      {/* 整棵子树都可以访问 theme 和 toggleTheme */}
      <PageLayout />
    </ThemeContext.Provider>
  );
}
```

### 2.3 useContext

```jsx
import { useContext } from 'react';

function DeepComponent() {
  // 读取最近的 Provider 提供的 value
  const { theme, toggleTheme } = useContext(ThemeContext);

  return (
    <div className={`app-${theme}`}>
      Current theme: {theme}
      <button onClick={toggleTheme}>Toggle</button>
    </div>
  );
}

// 等价于 Class 组件中的 <ThemeContext.Consumer>
// 但 useContext 更简洁
```

### 2.4 Consumer（遗留 API）

```jsx
// Class 组件或函数组件中不使用 Hook 时可用
class DeepComponent extends React.Component {
  render() {
    return (
      <ThemeContext.Consumer>
        {(context) => (
          <div className={`app-${context.theme}`}>
            {/* 使用 context */}
          </div>
        )}
      </ThemeContext.Consumer>
    );
  }
}
```

> **注意**：新代码推荐使用 `useContext`。Consumer 主要用于不支持 Hooks 的场景（如高阶组件内部）。

## 3. 最佳实践：封装为自定义 Hook

```jsx
// theme-context.tsx
import { createContext, useContext, useState, useMemo, useCallback } from 'react';

interface Theme {
  mode: 'light' | 'dark';
  primaryColor: string;
  fontSize: number;
}

interface ThemeContextValue {
  theme: Theme;
  setMode: (mode: Theme['mode']) => void;
  isDark: boolean;
}

const ThemeContext = createContext<ThemeContextValue>(null!);

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [mode, setMode] = useState<Theme['mode']>('dark');

  const theme = useMemo((): Theme => ({
    mode,
    primaryColor: mode === 'dark' ? '#61dafb' : '#20232a',
    fontSize: mode === 'dark' ? 16 : 15,
  }), [mode]);

  const value = useMemo((): ThemeContextValue => ({
    theme,
    setMode,
    isDark: mode === 'dark',
  }), [theme, setMode]);

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme(): ThemeContextValue {
  const context = useContext(ThemeContext);
  
  if (!context) {
    throw new Error(
      'useTheme must be used within a ThemeProvider. '
      + 'Wrap your component tree with <ThemeProvider>.'
    );
  }
  
  return context;
}
```

**这种模式的好处**：

| 优势 | 说明 |
|------|------|
| 类型安全 | TS 自动推断返回类型 |
| 必检包裹 | 忘记 Provider 会抛出明确错误 |
| 隐藏实现 | 消费者无需知道 Context 内部结构 |
| 易于测试 | Mock Provider 即可 |

## 4. 性能优化

### 4.1 核心问题：Context value 变化导致所有消费者重渲染

```jsx
// ⚠️ 性能陷阱
function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const [notifications, setNotifications] = useState([]);

  // ❌ 每次渲染都创建新的对象引用
  // 即使只变了 notifications，theme 和 user 的消费者也会重渲染
  return (
    <AppContext.Provider value={{ user, theme, notifications, setUser, setTheme, setNotifications }}>
      <Dashboard />  {/* 包含很多子组件 */}
    </AppContext.Provider>
  );
}
```

### 4.2 解决方案一：拆分为细粒度 Context

```jsx
// ✅ 按关注点拆分
<UserContext.Provider value={{ user, setUser }}>
  <ThemeContext.Provider value={{ theme, setTheme }}>
    <NotificationContext.Provider value={{ notifications, setNotifications }}>
      <Dashboard />
    </NotificationContext.Provider>
  </ThemeContext.Provider>
</UserContext.Provider>

// 各自独立，互不影响
```

### 4.3 解决方案二：分离静态和动态部分

```jsx
// 将不变的配置和变化的数据分开
const StaticConfig = { apiUrl: '/api', version: '1.0' };  // 永远不变

function App() {
  const [dynamicData, setDynamicData] = useState(initial);

  return (
    <>
      <StaticConfigContext.Provider value={StaticConfig}>
        {/* 这个 Context 的 consumers 永远不会因数据变化而重渲染 */}
      </StaticConfigContext.Provider>
      
      <DataContext.Provider value={{ dynamicData, setDynamicData }}>
        {/* 只有这个会影响其 consumers */}
      </DataContext.Provider>
    </>
  );
}
```

### 4.4 解决方案三：使用 state-splitting 模式

```jsx
// 将一个大 Context 的 value 拆成多个独立的 Context
function App() {
  return (
    <UserProvider>
      <ThemeProvider>
        <NotificationProvider>
          <Children />
        </NotificationProvider>
      </ThemeProvider>
    </UserProvider>
  );
}

// 每个组件只订阅自己需要的 Context
function UserName() {
  const { user } = useUser();  // 只依赖 UserContext
  return <span>{user.name}</span>;
}

function ThemeToggle() {
  const { theme, toggle } = useTheme();  // 只依赖 ThemeContext
  return <button onClick={toggle}>{theme}</button>;
}
```

## 5. 多层 Context 嵌套

```jsx
function AppProviders({ children }: { children: React.ReactNode }) {
  return (
    <ErrorBoundary>
      <AuthProvider>
        <ThemeProvider>
          <QueryClientProvider client={queryClient}>
            <Router>{children}</Router>
          </QueryClientProvider>
        </ThemeProvider>
      </AuthProvider>
    </ErrorBoundary>
  );
}

// 使用顺序：从外到内
// 1. Error Boundary — 最外层，捕获所有错误
// 2. Auth — 路由和主题都依赖认证状态
// 3. Theme — 影响视觉呈现
// 4. Query Client — 数据获取基础设施
// 5. Router — 最内层，决定页面结构
```

## 6. Context 的典型反模式

### 6.1 用 Context 存储高频变化的数据

```jsx
// ❌ 鼠标位置每秒变化数十次
const MouseContext = createContext({ x: 0, y: 0 });

function App() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  
  useEffect(() => {
    const handler = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);

  // ⚠️ 所有 MouseContext 消费者疯狂重渲染！
  return <MouseContext.Provider value={pos}><App /></MouseContext.Provider>;
}

// ✅ 替代方案：用事件总线 / ref / 或专门的响应式库
```

### 6.2 默认值的误导性

```jsx
// ⚠️ 默认值只在"没有 Provider 包裹"时生效
// 如果不小心包裹了但传了 undefined，默认值不会生效！
const MyCtx = createContext(defaultValue);

<MyCtx.Provider value={undefined}>  {/* 不是用默认值，而是传了 undefined */}
  <Child />  /* useContext(MyCtx) 得到的是 undefined */
</MyCtx.Provider>
```

## 7. Context vs 其他方案对比

| 特性 | Context | Zustand/Jotai | Redux |
|------|---------|--------------|-------|
| 安装依赖 | 无（内置） | 需安装 | 需安装 |
| 学习成本 | 低 | 低 | 中 |
| 性能优化能力 | 弱（全量通知） | 强（原子粒度） | 强（selector） |
| DevTools | 无 | 有（zundo 等） | Redux DevTools |
| 中间件支持 | 无 | 有（persist/devtools） | 丰富生态 |
| 服务端渲染 | 支持（需处理） | 支持 | 支持 |
| 适用规模 | 小~中应用 | 小~大应用 | 中~大型应用 |

## 8. 总结

```
┌──────────────────────────────────────────────────┐
│         Context API 要点速查                       │
├──────────────────────────────────────────────────┤
│ 核心: createContext → Provider → useContext       │
│ 封装: 总是封装为 useXxx 自定义 Hook               │
│ 性能: 拆分 Context 按关注点隔离                   │
│ 避免: 高频变化数据、巨型单 Context                 │
│ 嵌套: 从外到内按依赖顺序排列 Providers            │
│ 默认值: 仅无 Provider 时生效                      │
│ 选择: 简单全局状态用 Context，复杂的考虑第三方库    │
└──────────────────────────────────────────────────┘
```
