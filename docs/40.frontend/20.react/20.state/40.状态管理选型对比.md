## 2. 主流方案详细对比

### 2.1 核心特性对比

| 特性 | Zustand | Jotai | MobX | Valtio | Redux(RTK) | Recoil | Context |
|------|---------|-------|------|--------|-------------|--------|--------|
| **包大小 (gzip)** | ~1.5KB | ~5KB | ~16KB | ~2KB | ~45KB+ | ~19KB | 0 (内置) |
| **API 风格** | 函数式 | 函数式 | OOP (Class) | 函数式 | Object config | Object config | Hook |
| **是否需要 Provider** | ❌ | ❌ | 需要 observer | ❌ | Provider | `<RecoilRoot>` | `<Provider>` |
| **DevTools** | zundo | jotai-devtools | mobx-devtools | valtio/devtools | Redux DevTools | recoilize | — |
| **持久化中间件** | ✅ 内建 | ✅ utils | 需第三方 | valtio-persist | redux-persist | @recoil/persist | 需自写 |
| **TypeScript** | ★★★★★ | ★★★★★ | ★★★★☆ | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★★☆ |
| **并发模式兼容** | ✅ | ✅ | ✅ | ✅ | ✅ | β | ✅ |
| **SSR 支持** | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ | ✅ |
| **学习成本** | 极低 | 低 | 低~中 | 极低 | 中 | 中 | 低 |
| **社区活跃度** | 非常高 | 高 | 中 | 中 | 非常高 | 低 (维护模式) | — |
| **GitHub Stars** | ~55k+ | ~18k+ | ~27k+ | ~5k+ | ~62k+ | ~19k+ | — |

### 2.2 性能特征对比

| 维度 | Zustand | Jotai | MobX | Valtio | Redux | Context |
|------|---------|-------|------|--------|-------|--------|
| **更新粒度** | Selector 级别 | Atom 级别 | 属性级 | 属性级 | Selector 级别 | Context 级别 |
| **不必要的重渲染** | 取决于 selector | 极少（原子粒度） | 极少（属性追踪） | 极少（快照追踪） | 取决于 selector | 易发生（value 整体比较） |
| **内存开销** | 低 | 中（atom 注册表） | 中（依赖图） | 低（Proxy 包装） | 中（store + subscriptions） | 低 |
| **初始化速度** | 最快 | 快 | 较慢（类实例化） | 最快 | 较慢（middleware 链） | 快 |

## 3. 场景化推荐

### 3.1 按 项目规模推荐

```
小型项目 (1~3 人周):
  ├─ useState / useReducer / Context
  └─ 如果需要全局状态 → Zustand (最快上手)

中型项目 (1~6 月):
  ├─ Client State: Zustand 或 Jotai
  ├─ Server State: TanStack Query
  └─ 复杂表单/流程: XState (可选)

大型项目 (6月~年+):
  ├─ Client State: Zustand + slices 或 Redux Toolkit
  ├─ Server State: TanStack Query / RTK Query
  ├─ 复杂业务流: XState
  └─ 团队规范: 强制架构约定 + ESLint rules
```

### 3.2 按团队偏好推荐

```
喜欢函数式编程 / Hooks 思维?
  → Zustand (最简) / Jotai (最灵活)

喜欢 OOP / Class / Vue 体验?
  → MobX (最像 Vue reactive)

喜欢"直接修改对象"的直觉感?
  → Valtio (Proxy 原生)

需要严格的架构约束 / 团队规模大?
  → Redux Toolkit (生态最成熟)

项目已有大量 Redux 代码?
  → 继续用 Redux Toolkit (迁移成本太高)

追求极致包体积 / 性能?
  → Zustand (~1.5KB) 或 Jotai (~5KB)

需要细粒度派生状态 / 原子化?
  → Jotai > Zustand > Redux
```

## 4. 组合方案（推荐）

大多数现代项目采用 **组合策略** 而非单一方案：

```
推荐的 "黄金组合":

  Client Global State
  └── Zustand (或 Jotai)
      ├── userSlice      # 用户信息
      ├── themeSlice     # 主题设置
      └── appSlice       # 应用配置

  Server State
  └── TanStack Query
      ├── useQuery (读取)
      └── useMutation (写入)

  Complex Logic
  └── XState (按需)
      ├── formStateMachine
      └── approvalWorkflow

  Local Component State
  └── useState / useReducer (内置)
      └── 每个 component 自己管自己的 UI 状态
```

**为什么不用一个库解决所有问题？**

```
因为不同类型的状态有本质区别:

  Client State:
    - 你完全拥有和控制
    - 变化由用户交互驱动
    - 需要即时响应
    → Zustand / Jotai 最擅长

  Server State:
    - 你不完全拥有（服务方可随时改变）
    - 变更是异步的（网络延迟）
    - 有缓存/过期/失效问题
    → TanStack Query 专门设计来解决这个问题

  Machine State:
    - 状态之间有明确的合法转移路径
    - 需要可视化和调试
    → XState 是这个领域的专家
```

## 5. 迁移指南

### 5.1 从 Context 到 Zustand

```diff
- const ThemeCtx = createContext(defaults);
- export const ThemeProvider = ({ children }) => (
-   <ThemeCtx.Provider value={value}>{children}</ThemeCtx.Provider>
- );
- export const useTheme = () => useContext(ThemeCtx);
+ import { create } from 'zustand';
+
+ export const useThemeStore = create<ThemeState>((set) => ({
+   mode: 'dark',
+   setMode: (mode) => set({ mode }),
+ }));

- // 使用不变（只需去掉 Provider 包裹）
```

### 5.2 从 Redux RTK 到 Zustand

```
迁移步骤:
1. 安装 zustand
2. 为每个 slice 创建独立的 create() store
3. 用 useStore(selector) 替代 useSelector()
4. 用 store.getState().dispatch 替代 useDispatch()
5. 逐步删除 Provider / connect / mapStateToProps
6. 删除 @reduxjs/toolkit 和 react-redux 依赖
```

### 5.3 从 MobX 到 Valtio

```
相似度很高！主要改动:
1. class Store → proxy({})
2. makeAutoObservable → 直接写属性
3. observer(Component) → useSnapshot(proxy)
4. action 方法 → 直接修改
5. computed getter → derive()
```

## 6. 2026 年推荐总结

| 排名 | 方案 | 推荐指数 | 最佳场景 |
|------|------|----------|---------|
| 🥇 | **Zustand** | ★★★★★ | 通用首选、零门槛、全栈友好 |
| 🥈 | **Jotai** | ★★★★☆ | 原子化需求、精细性能控制 |
| 🥉 | **TanStack Query** | ★★★★★ | 服务端数据（几乎必备） |
| 4 | **XState** | ★★★☆☆ | 复杂状态机（按需引入） |
| 5 | **Redux Toolkit** | ★★★☆☆ | 大型团队 / 已有代码库 |
| 6 | **Valtio** | ★★★☆☆ | 喜欢 Proxy 直觉的开发者 |
| 7 | **MobX** | ★★★☆☆ | OOP 团队 / 从 Vue 转过来 |
| 8 | **Recoil** | ★★☆☆☆ | 仅维护已有项目，新项目不推荐 |
| 9 | **Context** | ★★☆☆☆ | 简单的全局配置（主题/语言） |
| 10 | **useState** | N/A | 组件内部本地状态（始终首选） |

## 7. 最终建议

```
对于 90% 的 React 项目:

  默认选择:  Zustand + TanStack Query
  
  这两个组合覆盖了:
  ✅ 全局客户端状态
  ✅ 服务端状态管理
  ✅ 缓存 / 去重 / 同步
  ✅ 持久化
  ✅ DevTools
  ✅ TypeScript
  ✅ SSR
  ✅ 极小体积 (~17KB 合计)
  ✅ 活跃社区
  ✅ 学习成本低

  只在有明确需求时才引入第三个库:
  → XState (复杂状态机)
  → Jotai (如果 Zustand 的 selector 不够精细)
  → MobX/Valtio (团队风格偏好)
  → Redux (企业级架构要求)
└─────────────────────────────────────────────────┘
```
