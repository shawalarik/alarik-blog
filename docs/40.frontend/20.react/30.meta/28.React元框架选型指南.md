## 二、各框架定位详解

### 2.1 Next.js — 全能选手

**最适合**：企业级应用、电商平台、SaaS 产品、需要 SSR + SEO 的复杂应用

```bash
# 优势
✅ RSC — 显著减少客户端 JS
✅ ISR — 内容更新无需重建
✅ Vercel 零配置部署 + Analytics
✅ 最大社区 + 最丰富的教程
✅ App Router + Pages Router 双模式共存

# 劣势
⚠️ 部署偏向 Vercel（其他平台需额外配置）
⚠️ 抽象层较多，调试有时困难
⚠️ 升级 breaking changes 较频繁
```

### 2.2 Remix — Web 标准主义者

**最适合**：CRUD 密集的管理后台、表单重的应用、不想被平台锁定的团队

```bash
# 优势
✅ 渐进增强 — JS 禁用仍可正常工作
✅ 嵌套路由 — 自然映射 UI 层级
✅ Form + Action — 最佳表单开发体验
✅ 部署灵活 — 任意 Node.js 平台
✅ Loader/Action 数据模型清晰

# 劣势
⚠️ 社区较小（但 Shopify 收购后在增长）
⚠️ 无 RSC（v2 计划中）
⚠️ 图片/字体优化需自行处理
⚠️ 学习曲线较陡峭
```

### 2.3 Astro — 内容站之王

**最适合**：博客、文档站、营销页、作品集、内容驱动的网站

```bash
# 优势
✅ 零 JS 默认 — 岛屿架构 (Islands)
✅ 极速构建 — 比 Next.js 快 5-20x
✅ 多框架支持 — React/Vue/Svelte/Astro 混用
✅ Content Collections — 类型安全的内容管理
✅ View Transitions — MPA 中的类 SPA 体验
✅ Astro 5 Streaming — 服务端流式渲染

# 劣势
❌ 不适合重度交互的应用
⚠️ SSR/Hybrid 模式相对新，生态不如 Next.js 成熟
⚠️ 交互组件需要 hydrate（增加 JS bundle）
```

### 2.4 Gatsby — 插件生态巨头

**最适合**：已有大量 Gatsby 插件需求的项目、需要 GraphQL 统一数据层的团队

```bash
# 优势
✅ 4000+ 插件 — 覆盖几乎所有数据源和服务
✅ GraphQL 数据层 — 统一的查询接口
✅ 图片管道 — 最佳图片优化体验之一
✅ PWA 内置 — Service Worker / Manifest / Offline

# 劣势
❌ 构建速度慢（大型项目瓶颈）
⚠️ 维护节奏放缓（团队重心转移）
⚠️ GraphQL 对简单项目过重
⚠️ 升级常伴随 breaking changes
```

### 2.5 Expo / React Native — 跨平台移动端

**最适合**：iOS/Android/Web 跨平台应用

```bash
# 优势
✅ 原生性能 — 非 WebView
✅ 一套代码三端运行
✅ Expo Go 即时预览
✅ 丰富的原生模块生态

# 劣势
❌ 不是 Web 框架（虽然也支持 Web）
⚠️ 性能不如纯原生
⚠️ 调试相对复杂
```

## 三、场景化推荐

### 3.1 决策树

```
你的项目是什么类型？
│
├─ 内容型网站（博客/文档/营销页）
│  ├─ 需要 React 交互？
│  │  ├─ 是 → Next.js (SSG) 或 Astro (Islands)
│  │  └─ 否 → Astro（零 JS，最快）
│  │
├─ 全栈 Web 应用
│  ├─ 需要 RSC / ISR？
│  │  ├─ 是 → Next.js
│  │  └─ 否 ↓
│  │
│  ├─ 表单交互为主？
│  │  ├─ 是 → Remix（Form + Action 天然优势）
│  │  └─ 否 → Next.js（更全面的生态）
│  │
├─ 管理后台 / CRM / ERP
│  ├─ CRUD 操作密集？
│  │  ├─ 是 → Remix 或 Next.js + tRPC
│  │  └─ 简单后台 → Vite + React Router + TanStack Table
│  │
├─ 电商平台
│  ├─ SEO 要求高？
│  │  ├─ 是 → Next.js (SSR + ISR)
│  │  └─ 否 → Remix 或纯 SPA + SSR 骨架
│  │
├─ 移动端 App
│  └─ → Expo (React Native)
│
└─ 企业内部工具
   └─ → Vite + React (无需元框架)
```

### 3.2 按项目规模

| 规模 | 推荐 | 理由 |
|------|------|------|
| **个人博客** | Astro / VitePress | 零运维、极速构建、免费托管 |
| **小型创业项目** | Next.js | 快速迭代、全栈能力、部署简单 |
| **中型产品 (5-20人)** | Next.js 或 Remix | 取决于团队对 Web 标准的偏好 |
| **大型企业 (>50人)** | Next.js | 人才招聘容易、生态完善、企业级支持 |
| **营销站群** | Astro 或 Gatsby | 多站点管理、内容优先 |

## 五、迁移路线图

### 5.1 Create React App → 元框架

```
CRA 应用
  │
  ├─ 纯 SPA，无需 SEO
  │  └─ Vite + React Router（轻量迁移）
  │
  └─ 需要 SEO / SSR
     ├─ 渐进式 → Next.js（Pages Router 先行，再迁 App Router）
     └─ 全面重构 → Remix（如果表单交互多）
```

### 5.2 Gatsby → 其他框架

```
Gatsby 项目
  │
  ├─ 主要痛点是构建速度
  │  └─ → Astro（内容型）/ Next.js SSG（需交互）
  │
  ├─ 依赖大量 Gatsby 插件
  │  └─ → 评估替代方案，可能需要自建数据获取层
  │
  └─ 想要更好的 DX
     └─ → Next.js（生态更大）或 Astro（更快）
```

## 六、2026 年趋势预测

| 趋势 | 影响的框架 | 说明 |
|------|-----------|------|
| **RSC 成为标配** | Next.js 引领，其他框架跟随 | Server Components 将改变 React 开发范式 |
| **边缘计算普及** | 所有框架都在增加 Edge 支持 | 全球低延迟成为基本需求 |
| **AI 集成** | Vercel AI SDK / Vercel SDK | AI 生成的内容需要新的渲染策略 |
| **部分 hydration / Islands** | Astro 引领，React 也跟进 | Resumability 可能取代 Rehydration |
| **构建速度竞赛** | 所有框架都在优化 | Turbopack / Rolldown / esbuild 取代 webpack |
| **元框架收敛** | 市场可能整合 | 长期看 2-3 个主流框架胜出 |

## 七、最终建议

```
不知道怎么选？
│
├─ 大多数情况 → 选 Next.js
│   （最保险的选择，社区最大，招聘最容易）
│
├─ 内容站 / 博客 / 文档 → 选 Astro
│   （最快的构建速度，最好的默认性能）
│
├─ 表单重 / 不想被 Vercel 锁定 → 选 Remix
│   （最纯粹的 Web 体验）
│
└─ 已有 Gatsby 项目且运转良好 → 暂时不迁移
    （除非构建速度成为严重瓶颈）
```
