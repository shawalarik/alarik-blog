## 概述

[语义化版本（SemVer）](https://semver.org/lang/zh-CN/)是一套规范的版本号格式：`MAJOR.MINOR.PATCH`。它解决了"我升级这个依赖会不会搞崩我的项目"这一根本问题，是整个 npm 生态系统协作的基石。

## 版本号组成

```
MAJOR.MINOR.PATCH[-prerelease] [+build]
 │      │     │          │            │
 │      │     │          │            └─ 构建元数据（不影响版本优先级）
 │      │     │          └─ 预发布标签（alpha/beta/rc）
 │      │     └─ 补丁版本：向后兼容的问题修复
 │      └─ 次版本号：向后兼容的功能新增
 └─ 主版本号：不兼容的 API 变更
```

### 各版本号的升级时机

| 类型 | 场景 | 示例 |
|------|------|------|
| **PATCH** | Bug 修复、文档更正、安全补丁 | `1.0.0` → `1.0.1` |
| **MINOR** | 新增功能（不影响已有 API）、新特性开关 | `1.0.0` → `1.1.0` |
| **MAJOR** | API 删除/变更、破坏性重构、依赖升级 | `1.0.0` → `2.0.0` |
| **PRERELEASE** | 内测/公测/候选版本 | `2.0.0-beta.1` |

## 版本范围前缀详解

### 三种前缀符号

```jsonc
{
  "dependencies": {
    "lodash": "^4.17.21",    // ^ 前缀（最常用）
    "express": "~4.18.2",    // ~ 前缀
    "core-js": "3.35.0"      // 无前缀（锁定版本）
  }
}
```

### `^` — 兼容主版本的最新版（Caret Range）

**规则**：允许左闭右区间 `[currentVersion, nextMajor)`

```js
"^1.2.3" = ">=1.2.3 <2.0.0"   // 主版本不变，次/补丁均可升级
"^0.2.3" = ">=0.2.3 <0.3.0"   // 0.x 主版本：次版本不变！
"^0.0.3" = ">=0.0.3 <0.0.4"   // 0.0.x：仅补丁可升级！
"^1.2.x" = ">=1.2.0 <2.0.0"   // 通配符写法
"^0.0.x" = ">=0.0.0 <0.1.0"

// 特殊情况
"^0.0.0" = ">=0.0.0 <0.0.1"   // 几乎无意义
"^1.x"   = ">=1.0.0 <2.0.0"
"^*"     = ">=0.0.0"           // 等同于 "*"
```

**⚠️ 0.x 版本的 `^` 行为特殊**：因为 0.x 代表不稳定开发阶段，SemVer 视其为"可能随时破坏"，所以 `^0.2.3` 只允许升级到 `<0.3.0`。

### `~` — 兼容次版本的最新版（Tilde Range）

**规则**：允许左闭右区间 `[currentVersion, nextMinor)`

```js
"~1.2.3" = ">=1.2.3 <1.3.0"   // 仅允许补丁升级
"~1.2"   = ">=1.2.0 <1.3.0"   // 等效于 ~1.2.0
"~1"     = ">=1.0.0 <2.0.0"   // 等效于 ^1.0.0
"~0.2.3" = ">=0.2.3 <0.3.0"   // 0.x 行为一致
```

### 无前缀 — 精确匹配

```js
"1.2.3" = "=1.2.3"             // 仅此版本
"*"     = ">=0.0.0"             // 任意版本（等同于 latest）
""      = "*"                   // 空串等同 *
"x"     = "*"
```

### 比较运算符组合

```js
">=1.0.0 <2.0.0"               // 范围指定
">=1.2.0 <1.5.0 || >=2.0.0"    // 多范围用 || 连接
"1.2.0 - 2.0.0"                 // 连字符范围（含两端）
"1.0.0 - 2.0.0" = ">=1.0.0 <=2.0.0"
```

## 前缀选择决策指南

```
你的场景                    推荐前缀     原因
──────────────────────────────────────────────────────
应用依赖（dependencies）     ^           平衡稳定性与获得修复
框架/核心库                  ~ 或锁定     极度重视稳定性
CLI 工具                     ^           通常独立使用，风险低
组件库                       ^           需要跟随主库更新
Monorepo 内部依赖            workspace:  直接链接本地包
CI/CD 环境                   无前缀       绝对可重现
发布给他人使用的库            ^           让使用者自行决定
```

## 预发布标签（Prerelease）

### 格式规则

```
MAJOR.MINOR.PATCH-[prerelease-tag].[number]
```

```js
"2.0.0-alpha.1"   // Alpha 内测
"2.0.0-alpha.2"   // 第二轮内测
"2.0.0-beta.1"    // Beta 公测
"2.0.0-rc.1"      // Release Candidate
"2.0.0"           // 正式发布！
```

### 预发布的版本排序

```js
// 数字越小越早，字母排序在数字之后
1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta.1 < 1.0.0-rc.1 < 1.0.0

// 预发布 < 正式版
1.0.0-alpha.1 < 1.0.0
```

### 预发布与范围前缀的交互

```js
// ^ 对预发布的行为：不会自动跳过预发布
"^1.0.0-alpha"  // 匹配 1.0.0-alpha.x 系列
"^1.0.0-beta"   // 不会匹配 1.0.0-alpha.x（比 beta 更早）

// 如果当前版本就是预发布版
"^1.0.0-alpha.1"  // 匹配 >=1.0.0-alpha.1 且 <2.0.0
// 但如果最新稳定版是 1.0.0，则 ^1.0.0-alpha.1 也会匹配 1.0.0
```

### 实际工作流

```bash
# 开发新功能（预发布阶段）
npm version prerelease --preid alpha
# 1.0.0 → 1.1.0-alpha.0

# 继续迭代 alpha
npm version prerelease --preid alpha
# 1.1.0-alpha.0 → 1.1.0-alpha.1

# 进入 beta
npm version prerelease --preid beta
# 1.1.0-alpha.1 → 1.1.0-beta.0

# 正式发布
npm version minor
# 1.1.0-beta.0 → 1.1.0
```

## lock 文件与版本锁定

### package-lock.json vs pnpm-lock.yaml vs yarn.lock

| 特性 | npm (lock v3) | pnpm | Yarn (Berry) |
|------|--------------|------|-------------|
| 文件名 | `package-lock.json` | `pnpm-lock.yaml` | `yarn.lock` |
| 格式 | JSON | YAML | 文本（类 YAML） |
| 内容完整性校验 | ✅ integrity hash | ✅ integrity hash | ✅ checksum |
| 重现性保证 | 强 | 最强 | 强 |
| 合并友好度 | 一般（JSON 冲突多） | 好（YAML 结构清晰） | 较好 |

### lock 文件的作用

```
开发者 A 安装 lodash@^4.17.21
→ lock 记录精确版本: "lodash": {"version": "4.17.21", ...}

开发者 B 执行 npm install
→ 读取 lock 文件，安装完全相同的 4.17.21
→ 即使此时最新版已是 4.17.22
```

**没有 lock 文件的后果**：
- 团队成员安装不同版本的间接依赖
- CI 环境与本地环境行为不一致
- "在我电脑上能跑"的经典问题

### lock 文件冲突解决

```bash
# 方案一：重新生成（最简单）
rm package-lock.json
npm install

# 方案二：基于队友的 lock 更新
cp ../teammate/package-lock.json .
npm install  # 自动调整以适配当前 package.json

# 方案三：手动合并（高风险）
# 对比两份 lock 的差异，保留双方都接受的版本
```

**pnpm 的 lock 冲突处理更好**：YAML 格式使 git merge 冲突更容易解决。

### should-lockfile 策略

```bash
# 应用项目：✅ 务必提交 lock
# 库/包项目：⚠️ 观点不一
#   支持：保证开发/测试环境一致
#   反对：lock 文件对安装者无意义，增加仓库体积

# npm 默认行为：
# 应用（无 "type": "module" 且无 "exports"）：自动生成 lock
# 库（有 exports/private:false）：也建议提交 lock
```

## 常见版本问题排查

### 依赖树冲突

```bash
# 查看为什么装了某个版本
npm why lodash
# lodash@4.17.21
# node_modules/lodash -> lodash@4.17.21

# npm ls 查看实际安装版本树
npm ls react
# my-app@1.0.0
# └── react@18.2.0

# 发现重复安装
npm ls react --depth=0
# 可能出现：
# ├── react@18.2.0
# └── react@17.0.2  （某个依赖锁定了旧版）

# 解决：使用 overrides 强制统一版本
```

### npm overrides（强制覆盖）

```jsonc
{
  "overrides": {
    "lodash": "^4.17.21"        // 强制所有子树使用此版本
  }
}
```

### pnpm overrides

```jsonc
{
  "pnpm": {
    "overrides": {
      "lodash": "^4.17.21"
    }
  }
}
```

## SemVer 最佳实践总结

| 规则 | 说明 |
|------|------|
| **公开 API 变更才升 MAJOR** | 不要因为内部重构就升大版本 |
| **PATCH 可以包含小改动** | 但绝不能改变公开 API |
| **0.x 版本是特殊的** | 表示初始开发期，不做任何兼容承诺 |
| **预发布版本可能不稳定** | 生产环境谨慎使用 |
| **先发 PRERELEASE 再正式** | alpha → beta → rc → release |
| **始终提交 lock 文件** | 保证团队一致性 |
| **使用自动化工具管理版本** | standard-version/release-it/semantic-release |
| **记录 BREAKING CHANGES** | 在 CHANGELOG 中标注破坏性变更 |

> **记住一句话**：SemVer 的本质是一种**契约**——你向使用者承诺"在这个范围内升级不会破坏我的代码"。遵守这份契约，就是对生态的贡献。
