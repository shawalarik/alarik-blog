## 概述

npm 提供了 5 种依赖类型，每种类型决定了依赖的安装时机和可见范围。正确区分它们是构建高质量包的基础，尤其在开发组件库和插件时至关重要。

## 五种依赖类型全景图

```
┌─────────────────────────────────────────────┐
│              npm install                    │
│                                             │
│  ┌──────────────┐  ┌────────────────────┐  │
│  │ dependencies │  │ peerDependencies   │  │
│  │ (必选运行时)  │  │ (宿主提供)         │  │
│  └──────────────┘  └────────────────────┘  │
│                                             │
│  ┌──────────────┐  ┌────────────────────┐  │
│  │ devDependen. │  │ optionalDependen.  │  │
│  │ (仅开发时)    │  │ (可选功能)         │  │
│  └──────────────┘  └────────────────────┘  │
│                                             │
│  ┌────────────────────────────────────┐    │
│  │ bundledDependencies (内置打包)       │    │
│  └────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

## dependencies — 运行时依赖

### 定义

包正常运行所必需的依赖，**最终用户安装你的包时会自动安装**。

### 何时放入

```jsonc
{
  "dependencies": {
    // ✅ 你的代码直接 import/require 了这些
    "axios": "^1.6.0",
    "lodash-es": "^4.17.21",
    "dayjs": "^1.11.10",
    "zod": "^3.22.0"
  }
}
```

**判断标准**：
- 代码中有 `import xxx from 'xxx'` 或 `require('xxx')`
- 该代码会在**生产环境**中被执行
- 缺少它会导致包无法正常工作

### 常见错误

```js
// ❌ 把开发工具放进了 dependencies
import { build } from 'esbuild';  // 这应该进 devDependencies！

// ❌ 把类型定义放进了 dependencies
import type { Options } from 'some-types';  // 应该是 devDependencies
```

## devDependencies — 开发依赖

### 定义

仅在开发和构建时需要的依赖，**最终用户安装你的包时不会安装**。

### 何时放入

```jsonc
{
  "devDependencies": {
    // 构建工具
    "typescript": "^5.4.0",
    "tsup": "^8.0.0",
    "rollup": "^4.0.0",
    "vite": "^5.0.0",
    "esbuild": "^0.20.0",

    // 测试工具
    "vitest": "^1.0.0",
    "jest": "^29.0.0",
    "@testing-library/react": "^14.0.0",

    // 代码质量
    "eslint": "^8.57.0",
    "prettier": "^3.2.0",
    "husky": "^9.0.0",
    "lint-staged": "^15.0.0",

    // 类型定义（TS 项目）
    "@types/node": "^20.11.0",
    "@types/react": "^18.2.0"
  }
}
```

### 关键区别

```
场景                        安装 dependencies？  安装 devDependencies？
──────────────────────────────────────────────────────────────────
npm install your-pkg              ✅                  ❌
npm install your-pkg -D           ✅                  ✅
从 GitHub clone 后 npm install     ✅                  ✅
```

## peerDependencies — 对等依赖（重点）

### 定义

**声明你的包期望宿主环境已经提供的依赖**，不会自动安装，但会**版本校验**。

### 为什么需要它？

```
场景：开发一个 React 组件库 @my-org/ui-kit

❌ 如果把 react 放入 dependencies：
  npm install @my-org/ui-kit
  → 自动安装 react@18.2.0
  → 但用户的 App 已经用了 react@18.2.0
  → 出现两个 React 实例！→ Hooks 失效、Context 断裂、性能爆炸

✅ 正确做法：把 react 放入 peerDependencies：
  npm install @my-org/ui-kit
  → 不自动安装 react
  → 检查用户是否已安装了符合要求的 react
  → 复用用户已有的 react 实例
```

### 正确用法

```jsonc
{
  "name": "@my-org/ui-button",
  "peerDependencies": {
    "react": ">=16.8.0 <19.0.0",
    "react-dom": ">=16.8.0 <19.0.0"
  },
  "devDependencies": {
    "react": "^18.2.0",
    "react-dom": "^18.2.0",
    "@types/react": "^18.2.0"
  }
}
```

### 版本范围写法指南

```jsonc
{
  "peerDependencies": {
    // ✅ 推荐：明确支持的范围
    "react": ">=16.8.0 || ^17.0.0 || ^18.0.0",
    
    // ✅ 简洁：支持某主版本以上
    "vue": "^3.3.0",
    
    // ⚠️ 过于严格：限制太死
    "react": "18.2.0",        // 只接受精确版本
    
    // ❌ 危险：范围太大
    "react": "*",             // 任何版本都行（失去保护意义）
    
    // ✅ 多版本支持
    "typescript": ">=4.5.0 <5.7.0"
  }
}
```

### peerDependenciesMeta — 标记可选的对等依赖

```jsonc
{
  "peerDependencies": {
    "react-dom": ">=16.8.0",
    "@my-org/theme": ">=1.0.0"    // 主题包，不是所有人都会用
  },
  "peerDependenciesMeta": {
    "@my-org/theme": {
      "optional": true   // 声明为可选
    }
  }
}
```

### 实战案例：Vue 插件

```jsonc
// vue-router 的 package.json（简化）
{
  "name": "vue-router",
  "peerDependencies": {
    "vue": "^3.3.0"
  },
  "devDependencies": {
    "vue": "^3.3.4",           // 开发测试用
    "vitest": "^1.0.0",
    "typescript": "^5.3.0"
  }
}

// 用户侧
// npm install vue vue-router
// vue-router 不会自带 vue，复用用户安装的 vue
```

### Vite 插件的典型配置

```jsonc
{
  "name": "vite-plugin-my-feature",
  "peerDependencies": {
    "vite": "^5.0.0 || ^4.0.0"   // 兼容多个 Vite 大版本
  },
  "devDependencies": {
    "vite": "^5.0.0"              // 本地开发用的主版本
  }
}
```

### ESLint 插件的典型配置

```jsonc
{
  "name": "eslint-plugin-my-rules",
  "peerDependencies": {
    "eslint": ">=8.0.0"
  }
}
```

### 常见踩坑

```jsonc
// ❌ 错误：同时放在 dependencies 和 peerDependencies
{
  "dependencies": { "react": "^18.0.0" },
  "peerDependencies": { "react": "^18.0.0" }
}
// 这会导致安装两个 React！

// ❌ 错误：缺少 devDependencies 导致开发报错
{
  "peerDependencies": { "react": "^18.0.0" }
  // 没有 devDependencies: { "react": "^18.0.0" }
  // 开发时 import React 会找不到！
```

## optionalDependencies — 可选依赖

### 定义

安装失败不会中断整体安装过程的依赖。用于提供增强功能，缺失时不影响核心功能。

### 典型用法

```jsonc
{
  "optionalDependencies": {
    // 平台特定的可选依赖
    "fsevents": "^2.3.3",        // macOS 文件系统事件监听
    "windows-foreground-love": "^0.3.0",  // Windows 特定功能
    
    // 可选的编解码器
    "sharp": "^0.33.0"            // 图片处理（回退方案用 jimp）
  }
}
```

### 代码中使用

```js
let imageProcessor;

try {
  imageProcessor = require('sharp');     // 高性能原生模块
} catch {
  imageProcessor = require('./fallback/jimp');  // 纯 JS 回退
}

imageProcessor.resize(input, output);
```

### 与 peerDependenciesMeta 的区别

| 特性 | optionalDependencies | peerDependenciesMeta |
|------|---------------------|---------------------|
| 安装行为 | 尝试安装，失败不阻塞 | 不自动安装 |
| 缺失提示 | 无警告 | 有警告（除非标记 optional） |
| 适用场景 | 平台特定/增强功能 | 对等依赖的可选项 |

## bundledDependencies — 打捆依赖

### 定义

发布时将指定依赖**打包进 tarball**，不从 registry 下载。

```jsonc
{
  "bundledDependencies": [
    "my-internal-utils",
    "my-custom-dep"
  ]
}
```

**注意**：拼写是 `bundledDependencies`（完整），不是 `bundleDependencies`（缩写也可用）。

### 使用场景

```js
// 场景 1：离线部署包
// 所有依赖都打包在一起，无需网络下载

// 场景 2：发布私有/未公开的依赖
// 将内部包捆绑发布，避免单独维护私有源

// 场景 3：简化部署
// npm pack 后得到的 tarball 是自包含的
```

### 实际操作

```bash
# 打包验证
npm pack
# 生成 my-pkg-1.0.0.tgz，包含 bundledDependencies 中的内容

# 安装打包好的 tgz
npm install ./my-pkg-1.0.0.tgz
```

## 依赖安装顺序与嵌套结构

### npm v3+ 的扁平化安装

```
node_modules/
├── react/                  # 提升至顶层
├── react-dom/              # 提升至顶层
├── my-component/
│   └── node_modules/
│       └── lodash/         # 只有版本冲突时才嵌套
├── another-pkg/
│   └── node_modules/
│       └── lodash@3.10.1/  # 版本冲突，嵌套安装
└── lodash/                 # 大多数情况提升至顶层
```

### pnpm 的严格结构

```
node_modules/
├── .pnpm/
│   ├── react@18.2.0/node_modules/react
│   ├── lodash@4.17.21/node_modules/lodash
│   └── ...
├── react → .pnpm/react@18.2.0/node_modules/react
├── my-component → .pnpm/my-component@1.0.0/node_modules/my-component
└── ...
```

pnpm 使用**符号链接**实现严格的依赖树，避免了 phantom dependencies 问题。

## 依赖审计与清理

```bash
# 查看依赖树
npm ls --depth=0

# 查找未被使用的依赖（需 depcheck）
npx depcheck

# 安全审计
npm audit

# 自动修复已知漏洞
npm audit fix

# 查看过期的依赖
npm outdated

# 清除未使用的依赖（需 knip）
npx knip
```

## 快速参考表

| 类型 | 自动安装？ | 安装失败？ | 典型用途 |
|------|-----------|-----------|---------|
| **dependencies** | ✅ | 阻止安装 | 运行时必需 |
| **devDependencies** | 仅 -D | 阻止安装 | 构建/测试/ lint |
| **peerDependencies** | ❌ | 警告 | 宿主环境提供 |
| **optionalDependencies** | 尝试 | 忽略并继续 | 增强功能/平台特性 |
| **bundledDependencies** | 打包进 tgz | N/A | 离线/私有依赖 |

> **黄金法则**：开发组件库/插件时，**永远把宿主框架放 `peerDependencies`**，同时在 `devDependencies` 中保留一份用于开发测试。
