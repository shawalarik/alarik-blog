## 概述

Monorepo（单仓库多包管理）已成为前端工程化的主流模式。npm 7+ 内置的 **Workspaces** 功能提供了原生的 Monorepo 支持，而 pnpm 的 workspaces 实现更为完善。本文全面解析 Workspaces 配置、包间依赖、以及主流 Monorepo 工具对比。

## 什么是 Monorepo？

```
Polyrepo（传统多仓库）          Monorepo（单仓库）
┌─────────┐ ┌─────────┐        ┌─────────────────────────┐
│ repo-a  │ │ repo-b  │        │                         │
│ pkg-a   │ │ pkg-b   │        │  packages/              │
└─────────┘ └─────────┘        │  ├─ ui/        ← 包 A  │
                              │  ├─ utils/     ← 包 B  │
                              │  ├─ config/    ← 包 C  │
                              │  └─ app/       ← 应用   │
                              │  package.json          │
                              └─────────────────────────┘

问题：                          优势：
• 版本同步困难                   • 共享依赖，节省磁盘/安装
• 跨仓库修改麻烦                 • 统一构建/测试/lint
• CI 成本高                      • 原子化提交
• 代码共享靠 copy 或私有 npm     • 跨包 refactoring
```

## npm Workspaces 基础配置

### 目录结构

```
my-monorepo/
├── packages/
│   ├── ui/                    # UI 组件库
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   ├── utils/                 # 工具函数库
│   │   ├── src/
│   │   ├── package.json
│   │   └── tsconfig.json
│   └── config/                # 共享配置
│       ├── eslint-config/
│       ├── tsconfig/
│       └── package.json
├── apps/
│   └── web/                   # Web 应用
│       ├── src/
│       └── package.json
├── package.json               # 根 package.json（workspaces 配置）
├── pnpm-workspace.yaml        # pnpm 工作区配置
└── turbo.json                 # Turborepo 配置
```

### 根 package.json 配置

```jsonc
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "packages/*",
    "apps/*"
  ],
  "scripts": {
    "build": "npm run build -ws",
    "test": "npm run test -ws",
    "lint": "eslint \"packages/*/src/**\" \"apps/*/src/**\""
  },
  "devDependencies": {
    "typescript": "^5.4.0",
    "eslint": "^8.57.0",
    "prettier": "^3.2.0"
  }
}
```

### `-w` / `-ws` 标志说明

```bash
npm run build -w @myorg/ui       # 只构建 ui 包
npm run build -ws                 # 构建所有 workspace
npm install -w @myorg/utils       # 只在 utils 里安装依赖
npm install                      # 安装所有 workspace 的依赖（提升 hoist）
```

## 包间依赖引用

### workspace 协议（推荐）

```jsonc
// packages/ui/package.json
{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "dependencies": {
    // ✅ 使用 workspace: 前缀
    "@myorg/utils": "workspace:*",       // 始终链接本地
    "@myorg/utils": "workspace:^",       // 语义化版本链接
    "@myorg/utils": "workspace:~",       
    "@myorg/utils": "workspace:1.0.0",   // 精确版本链接
  }
}
```

**workspace: 协议的优势**：
- 开发时：自动创建符号链接，改代码立即生效
- 发布时 (`npm publish`)：自动替换为真实版本号
- pnpm / yarn 都支持此协议

### 传统的 `*` 版本

```jsonc
// ❌ 旧方式（仍然可用但不推荐）
{
  "dependencies": {
    "@myorg/utils": "*"
  }
}
// 问题：publish 时需要手动替换版本号，容易遗忘
```

### 包间引用实战

```js
// packages/ui/src/Button.tsx
import { cn } from '@myorg/utils';  // 直接引用 workspace 中的包

export function Button({ className, ...props }) {
  return (
    <button className={cn('btn-base', className)}>
      {props.children}
    </button>
  );
}
```

```js
// apps/web/src/App.tsx
import { Button } from '@myorg/ui';
import { formatDate } from '@myorg/utils';

function App() {
  return (
    <Button onClick={() => console.log(formatDate(new Date()))}>
      Click Me
    </Button>
  );
}
```

## 依赖提升（Hoisting）机制

### npm 的 Hoisting 行为

```
安装前                          安装后（hoist）
packages/
├── ui/node_modules/lodash      packages/
├── utils/node_modules/lodash   ├── ui → 符号链接
├── web/node_modules/lodash     ├── utils → 符号链接
                               ├── web → 符号链接
                               node_modules/
                                 ├── lodash@4.17.21  ← 提升！唯一副本
                                 ├── react@18.2.0
                                 └── ...
```

**好处**：减少重复安装，节省磁盘空间  
**风险**：phantom dependencies（能 require 到未声明的依赖）

### pnpm 严格的 non-hoist

```
.pnpm/
  lodash@4.17.21/
    node_modules/lodash        ← 只有一份（内容寻址存储）
node_modules/
  .pnpm/
    @myorg/ui@1.0.0/node_modules/@myorg/ui
    @myorg/utils@1.0.0/node_modules/@myorg/utils
  @myorg/ui → .pnpm/@myorg/ui@1.0.0/...
  @myorg/utils → .pnpm/@myorg/utils@1.0.0/...
```

**pnpm 的优势**：
- 避免 phantom dependencies
- 安装更快（全局缓存 + 硬链接）
- 更安全（严格的依赖树）

## pnpm Workspaces 配置

### pnpm-workspace.yaml

```yaml
packages:
  - 'packages/*'
  - 'apps/*'
  - 'tools/*'
```

### .npmrc 配置

```ini
# 根目录 .npmrc
link-workspace-packages=true       # 启用 workspace 链接
save-exact=true                    # 锁定精确版本
save-workspace-protocol=true       # 默认使用 workspace: 协议

# 严格模式（推荐用于库）
 shamefully-hoist=false

# 宽松模式（某些老旧包需要）
# shamefully-hoist=true
```

### 常用命令对照

| 操作 | npm | pnpm | yarn (v1/v3) |
|------|-----|------|---------------|
| 安装全部 | `npm install` | `pnpm install` | `yarn install` |
| 添加依赖 | `npm i <pkg>` | `pnpm add <pkg>` | `yarn add <pkg>` |
| 添加开发依赖 | `npm i -D <pkg>` | `pnpm add -D <pkg>` | `yarn add -D <pkg>` |
| 添加到指定包 | `npm i -w @pkg/a <dep>` | `pnpm add --filter @pkg/a <dep>` | `yarn workspace @pkg/a add <dep>` |
| 运行所有脚本 | `npm run <script> -ws` | `pnpm -r run <script>` | `yarn workspaces run <script>` |
| 运行指定包脚本 | `npm run <script> -w @pkg` | `pnpm --filter @pkg run <script>` | `yarn workspace @pkg <script>` |

## Monorepo 工具对比

### 三大包管理器对比

| 维度 | npm workspaces | pnpm workspaces | Yarn (Berry) |
|------|---------------|-----------------|-------------|
| **磁盘效率** | 低（重复复制） | 最高（内容寻址+硬链接） | 高（Plug'n'Play） |
| **安装速度** | 中等 | 最快 | 快 |
| **Phantom Deps** | 存在 | 不存在 | 不存在（PnP） |
| **Workspace 协议** | ✅ `workspace:` | ✅ `workspace:` | ✅ `workspace:` |
| **过滤语法** | `-w` | `--filter` | `workspace` |
| **生态成熟度** | 高 | 高（快速增长） | 中等 |
| **学习成本** | 低 | 低 | 中等（零安装概念） |
| **适合场景** | 简单 monorepo | 所有场景 | 大型复杂 monorepo |

### 选择建议

```
你的情况                          推荐
──────────────────────────────────────────
刚入门 monorepo                   npm workspaces（够用即可）
追求极致性能和磁盘空间             pnpm + workspaces（强烈推荐）
大型企业级项目（100+ 包）          pnpm 或 Yarn Berry
需要与现有工具链深度集成           pnpm（生态最活跃）
团队熟悉 yarn                     Yarn Berry（保持一致）
```

## 构建编排工具

### Turborepo（最流行）

```jsonc
// turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],    // 先构建依赖
      "outputs": ["dist/**"]      // 缓存依据
    },
    "test": {
      "dependsOn": ["build"],
      "inputs": ["src/**/*.tsx", "test/**/*.tsx"]
    },
    "lint": {
      "outputs": []               // 无输出，不缓存
    },
    "dev": {
      "cache": false,             // 开发模式不缓存
      "persistent": true          // 长时间运行的进程
    }
  }
}
```

```bash
# 使用 turborepo
pnpm add -Dw turbo -g

# 运行所有包的 build（自动缓存 + 并行）
turbo run build

# 仅运行变化的包
turbo run build --filter='[@myorg/*](http://twitter.com/myorg/*)'

# 远程缓存（团队共享）
turbo run build --team
```

### Nx（功能最全）

```bash
# 创建 Nx monorepo
npx create-nx-workspace@latest myorg --preset=react

# 图形化查看依赖关系
nx graph

# 受影响的项目
nx affected:build
```

**Turborepo vs Nx**：

| 维度 | Turborepo | Nx |
|------|----------|-----|
| 定位 | 构建编排 | 全功能 monorepo 工具 |
| 体积 | 轻量 (~5MB) | 较重 |
| 学习曲线 | 低 | 中等 |
| 插件生态 | 少 | 丰富（生成器、迁移） |
| 图形界面 | 无 | ✅ Nx Console |
| 代码生成 | 无 | ✅ Generators |
| 适合场景 | 已有项目的增量引入 | 从零开始的新项目 |

## 常见陷阱与解决方案

### 循环依赖检测

```bash
# pnpm 检测循环依赖
pnpm ls --depth=-1 --recursive | find-cycles

# 或者使用 madge
npx madge packages/*/src/index.ts --circular
```

### 解决循环依赖的方法

```
方案一：提取公共模块
  A ← → B → C ← A    变成    A → C ← B
                           ↘ ↑ ↗
                             B

方案二：依赖反转（DI）
  A 直接 import B     变成    A 接收 B 作为参数

方案三：事件解耦
  A 调用 B.method()   变成    A emit event → B on event
```

### 版本策略

```jsonc
// 方案一：统一版本（简单）
// 所有包一起发版，版本号相同
// 适合：内部 monorepo，不对外发布

// 方案二：独立版本（复杂）
// 每个包独立发版
// 工具：changesets / lerna / rush

// changesets 方式
// .changeset/feature-nice-bears.md
---
"@myorg/ui": minor
"@myorg/utils": patch
---

// 执行
pnpm changeset version    # 自动 bump 版本
pnpm changeset publish    # 发布所有变更的包
```

## 小结

| 要点 | 建议 |
|------|------|
| 包管理器 | **pnpm** + workspaces（首选） |
| Workspace 协议 | 始终使用 `workspace:*` |
| 构建编排 | **Turborepo**（轻量高效） |
| 版本管理 | **Changesets**（语义化变更日志） |
| 依赖提升 | pnpm 默认 strict（避免 phantom deps） |
| CI 缓存 | Turborepo Remote Cache（加速团队构建） |
