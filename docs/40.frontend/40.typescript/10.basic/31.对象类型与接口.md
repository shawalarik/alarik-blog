# 对象类型与接口——interface 的基本用法、可选/只读属性

> JavaScript 中万物皆对象，TypeScript 中对象类型的表达自然也是重中之重。
>
> 这篇文章将从最基本的对象字面量类型出发，一步步讲到 interface 的高级用法，帮你彻底掌握 TS 中"描述一个对象长什么样"的所有方式。

## 一、对象类型字面量

### 1.1 最基本的写法

在 TypeScript 中，你可以直接用花括号 `{}` 来定义对象的形状：

```typescript
// 定义一个对象类型：有 name（字符串）和 age（数字）两个属性
let person: { name: string; age: number } = {
  name: "Alarik",
  age: 25,
};

// ✅ 正确赋值
person = { name: "Alice", age: 30 };

// ❌ 错误：缺少 age 属性
person = { name: "Bob" };

// ❌ 错误：多出了 gender 属性
person = { name: "Charlie", age: 35, gender: "male" };

// ❌ 错误：name 类型不对
person = { name: 123, age: 25 };
```

### 1.2 属性之间用分号还是逗号？

两种都可以，TS 都认：

```typescript
// 分号分隔（更常见）
let a: { x: number; y: string } = { x: 1, y: "hello" };

// 逗号分隔（也完全 OK）
let b: { x: number, y: string } = { x: 2, y: "world" };
```

**个人推荐**：用分号，因为这与 interface 和 type 中的风格保持一致。

### 1.3 生活化类比

想象你在填写一张**个人信息表**：

| 现实中的表单 | TypeScript 对象类型 |
|-------------|---------------------|
| 姓名（必填，文字） | `name: string` |
| 年龄（必填，数字） | `age: number` |
| 电话（选填，文字） | `phone?: string` |
| 身份证号（填写后不可修改） | `readonly idCard: string` |

这张表单的格式就是你的 **类型定义**，你填的具体内容就是 **值**。类型系统就是那个严格的审核员——填错了格式直接打回。

## 二、interface 定义

### 2.1 基本 interface 声明

当同一个对象类型要在多处使用时，每次都内联写一串 `{ ... }` 太麻烦了。这时我们使用 `interface` 来给它起个名字：

```typescript
// 用 interface 定义一个 Person 接口
interface Person {
  name: string;
  age: number;
}

// 现在可以到处使用了
let user: Person = { name: "Alarik", age: 25 };
let admin: Person = { name: "Admin", age: 30 };

function greet(person: Person) {
  console.log(`你好，${person.name}！你今年 ${person.age} 岁。`);
}

greet(user);    // ✅
greet(admin);   // ✅
greet({ name: "Test", age: 99 }); // ✅
```

### 2.2 为什么叫"接口"？

**Interface（接口）** 这个词来源于软件工程中的一个核心概念：**接口定义了"契约"或"协议"，规定了交互双方必须遵守的规则**。

- 在现实生活中，**USB 接口**规定了设备的形状和针脚定义——任何符合 USB 规范的设备都能插入 USB 插口
- 在 TypeScript 中，**interface** 规定了对象的结构——任何符合该结构的值都能被当作该类型使用

### 2.3 interface 的命名约定

社区通用的命名规范：

```typescript
// ✅ 推荐：大驼峰命名（PascalCase）
interface UserInfo { }
interface HttpRequestConfig { }
interface ApiResponse<T> { }

// ⚠️ 不推荐但也有人用：加 I 前缀（C# 风格）
interface IUser { }        // TS 社区一般不这么做
interface IPerson { }

// ❌ 错误：小驼峰（用于变量/函数）
interface myInterface { }
```

**为什么 TS 社区不用 I 前缀？**
因为 TypeScript 有完整的类型系统，不需要通过命名来区分"这是类型"。看到 `Person` 就知道它是个类型，不需要写成 `IPerson`。I 前缀只会增加噪音。

## 三、可选属性

### 3.1 基本语法

在属性名后加上 `?`，表示这个属性是**可选的**：

```typescript
interface UserProfile {
  username: string;       // 必填
  email: string;          // 必填
  avatar?: string;        // 可选 —— 可能有头像，可能没有
  bio?: string;           // 可选 —— 个人简介不是必填的
  phone?: string;         // 可选 —— 手机号
}

// ✅ 只提供必填属性
const basicUser: UserProfile = {
  username: "alarik",
  email: "test@example.com",
};

// ✅ 提供所有属性（包括可选的）
const fullUser: UserProfile = {
  username: "alice",
  email: "alice@example.com",
  avatar: "https://example.com/avatar.jpg",
  bio: "Hello, I'm Alice!",
  phone: "13800138000",
};
```

### 3.2 可选属性的影响

可选属性的存在会影响后续代码的类型：

```typescript
interface Config {
  name: string;
  timeout?: number;    // 可选
}

function setup(config: Config) {
  console.log(config.name);     // ✅ 一定是 string

  // timeout 可能是 undefined！
  console.log(config.timeout);  // 类型是 number | undefined
}
```

**使用前需要做检查**：

```typescript
function setup(config: Config) {
  const actualTimeout = config.timeout ?? 5000; // 默认 5 秒
  // 或者
  if (config.timeout !== undefined) {
    // 这里 config.timeout 被收窄为 number
    console.log(`超时时间: ${config.timeout}ms`);
  }
}
```

### 3.3 实际应用场景

可选属性最常见的用途是表示"渐进式信息"或"非必填字段"：

```typescript
// API 响应
interface ApiResult<T> {
  code: number;
  message: string;
  data: T;
  error?: {         // 只有出错时才有
    type: string;
    detail: string;
  };
  pagination?: {    // 只有列表接口才有
    page: number;
    pageSize: number;
    total: number;
  };
}

// 表单数据
interface RegisterForm {
  username: string;
  password: string;
  inviteCode?: string;      // 邀请码（可选）
  referrerId?: string;      // 推荐人 ID（可选）
}
```

## 四、只读属性

### 4.1 基本语法

使用 `readonly` 修饰符声明**不可修改的属性**：

```typescript
interface User {
  readonly id: number;      // 创建后不能修改 —— 类似数据库主键
  name: string;             // 可以修改
  readonly createdAt: Date; // 创建时间不应被修改
}

let user: User = {
  id: 1,
  name: "Alarik",
  createdAt: new Date(),
};

user.name = "Bob";            // ✅ 可以修改
user.id = 2;                  // ❌ 无法分配到 "id"，因为它是只读属性
user.createdAt = new Date();  // ❌ 无法分配到 "createdAt"
```

### 4.2 readonly vs const 的区别

这是一个常见的混淆点：

```typescript
// readonly —— 用于属性（对象/接口的字段）
interface Point {
  readonly x: number;
  readonly y: number;
}

// const —— 用于变量声明
const origin = { x: 0, y: 0 }; // 变量本身不能重新赋值

// 对比：
const p: Point = { x: 1, y: 2 };
p.x = 10;  // ❌ readonly 限制的是属性
p = { x: 3, y: 4 }; // ❌ const 限制的是变量绑定
```

**简单记忆**：
- `const` → 变量不能指向别的东西（指针不变）
- `readonly` → 属性值不能改（内容不变）

### 4.3 浅层只读 vs 深层只读

TypeScript 的 `readonly` 是**浅层的**：

```typescript
interface Container {
  readonly items: string[];
}

const container: Container = {
  items: ["a", "b", "c"],
};

container.items = [];              // ❌ 不能替换整个数组
container.items.push("d");         // ✅ 但是可以修改数组内容！（浅只读）
container.items[0] = "x";          // ✅ 也可以修改单个元素
```

如果需要深层只读，可以使用工具类型 `Readonly<T>` 或 `ReadonlyDeep<T>`（后者在某些版本中需要自定义或使用第三方库）：

```typescript
// 浅层只读
type ShallowReadonly = Readonly<Container>;
// container.items 不能重新赋值，但 items 内部可变

// 手动实现深层只读（简化版）
type DeepReadonly<T> = {
  readonly [P in keyof T]: T[P] extends object ? DeepReadonly<T[P]> : T[P];
};

type StrictContainer = DeepReadonly<Container>;
// 现在 container.items.push("d") 也会报错
```

## 五、索引签名

### 5.1 什么是索引签名？

当对象可以有**任意数量的额外属性**时，使用索引签名：

```typescript
// 定义一个可以有任意字符串键的对象
interface Dictionary {
  [key: string]: string;
}

const colors: Dictionary = {
  red: "#ff0000",
  green: "#00ff00",
  blue: "#0000ff",
  // 可以有任意数量的键值对
};

colors.yellow = "#ffff00"; // ✅ 动态添加也可以
console.log(colors["red"]); // ✅ 访问也 OK
```

### 5.2 索引签名的实际应用

```typescript
// 场景一：字典/映射表
interface StringMap {
  [key: string]: unknown;
}

function getValue(map: StringMap, key: string): unknown {
  return map[key];
}

// 场景二：CSS 样式对象
interface CSSStyles {
  [property: string]: string | number;
}

const styles: CSSStyles = {
  color: "red",
  fontSize: 16,
  backgroundColor: "#fff",
};

// 场景三：HTTP Headers
interface HttpHeaders {
  [headerName: string]: string;
}

const headers: HttpHeaders = {
  "Content-Type": "application/json",
  "Authorization": "Bearer token123",
};
```

### 5.3 索引签名的限制

索引签名有一些重要限制：

```typescript
interface Mixed {
  [key: string]: string; // 所有属性的值都必须是 string
  name: string;          // ✅ 与索引签名兼容
  age: number;           // ❌ 错误！number 不能赋值给 string
}
```

**解决方法**：使用联合类型作为索引签名值：

```typescript
interface FlexibleDict {
  [key: string]: string | number | boolean;
  name: string;     // ✅
  age: number;      // ✅
  active: boolean;  // ✅
}
```

## 六、方法类型定义

在接口中定义方法有两种等价写法：

### 6.1 方法语法

```typescript
interface Greeter {
  // 写法一：方法语法（更像类的方法定义）
  greet(): string;

  // 写法二：属性语法（明确标注为函数类型的属性)
  farewell: () => string;
}

const greeter: Greeter = {
  greet() {
    return "Hello!";    // 对应方法语法
  },
  farewell: () => {     // 对应属性语法
    return "Goodbye!";
  },
};
```

### 6.2 带参数和返回值的完整方法

```typescript
interface Calculator {
  add(a: number, b: number): number;
  subtract(a: number, b: number): number;
  multiply(a: number, b: number): number;
  divide(a: number, b: number): number;
  describe(): string;
}

const calc: Calculator = {
  add(a, b) { return a + b; },
  subtract(a, b) { return a - b; },
  multiply(a, b) { return a * b; },
  divide(a, b) {
    if (b === 0) throw new Error("Cannot divide by zero");
    return a / b;
  },
  describe() {
    return "This is a simple calculator";
  },
};
```

### 6.3 方法签名的选择建议

| 写法 | 特点 | 适用场景 |
|------|------|----------|
| `greet()` | 更简洁，类似 class 中的方法 | 大多数情况 |
| `greet: () => void` | 明确是函数属性，支持箭头函数特性 | 需要保留 this 绑定时 |

## 七、接口的扩展（继承）

### 7.1 使用 extends 继承

接口可以通过 `extends` 关键字继承其他接口：

```typescript
// 基础接口
interface BasicInfo {
  name: string;
  age: number;
}

// 扩展接口 —— 包含 BasicInfo 的所有成员
interface Employee extends BasicInfo {
  employeeId: string;
  department: string;
}

// 使用
const emp: Employee = {
  name: "Alarik",       // 来自 BasicInfo
  age: 25,              // 来自 BasicInfo
  employeeId: "E001",   // 自身属性
  department: "工程部",  // 自身属性
};
```

### 7.2 多重继承

一个接口可以继承多个接口：

```typescript
interface HasId {
  id: string | number;
}

interface HasTimestamps {
  createdAt: Date;
  updatedAt: Date;
}

interface HasName {
  name: string;
}

// 同时继承三个接口
interface User extends HasId, HasTimestamps, HasName {
  email: string;
  role: 'admin' | 'user';
}

const newUser: User = {
  id: "u001",
  createdAt: new Date(),
  updatedAt: new Date(),
  name: "Alarik",
  email: "test@example.com",
  role: "admin",
};
```

### 7.3 继承时覆盖属性

子接口可以覆盖父接口的属性类型（但必须兼容）：

```typescript
interface Shape {
  color: string;
}

interface Circle extends Shape {
  color: string;           // 可以重新声明（相同类型）
  radius: number;
}

interface RedCircle extends Shape {
  color: "red";            // 收窄为字面量类型（合法）
  radius: number;
}
```

## 八、交叉类型（Intersection Types）

### 8.1 使用 & 合并类型

除了 `extends`，还可以用 `&` 操作符来合并类型：

```typescript
type HasName = { name: string };
type HasAge = { age: number };

type Person = HasName & HasAge;

const person: Person = {
  name: "Alarik",
  age: 25,
};
```

### 8.2 交叉类型 vs 接口继承

它们很相似，但有微妙区别：

```typescript
// 接口继承
interface A { a: string }
interface B extends A { b: string }
// B = { a: string; b: string }

// 交叉类型
type X = { x: string };
type Y = { y: string };
type Z = X & Y;
// Z = { x: string; y: string }
```

**主要区别**：

| 特性 | interface extends | type & (交叉) |
|------|-------------------|---------------|
| 目标 | 只能用于 interface | 可合并任何类型（含 union、primitive） |
| 冲突处理 | 子覆盖父 | 必须兼容否则产生 never |
| 可声明合并 | 支持 | 不支持 |
| 适用范围 | 面向对象/类风格 | 函数式/组合风格 |

```typescript
// 交叉类型可以做一些 interface 做不到的事
type StringAndNumber = string & { customProp: boolean };
// 这种"原始类型 & 对象类型"的交叉，interface extends 做不到

// 但冲突会产生 never
type Conflict = { a: string } & { a: number };
// a 的类型是 string & number = never（不存在既是 string 又是 number 的值）
```

## 九、interface vs type 初步对比

对于对象类型来说，`interface` 和 `type` 大部分时候可以互换：

```typescript
// interface 方式
interface PersonI {
  name: string;
  age: number;
}

// type 方式
type PersonT = {
  name: string;
  age: number;
};

// 两者效果几乎相同
let p1: PersonI = { name: "A", age: 1 };
let p2: PersonT = { name: "B", age: 2 };
p1 = p2; // ✅ 兼容
p2 = p1; // ✅ 兼容
```

### 9.1 各自的独有能力

```typescript
// ✅ interface 独有：声明合并（Declaration Merging）
interface Window {
  myCustomProperty: string;
}
// 可以多次声明同名的 interface，它们会自动合并

// ✅ type 独有：联合类型、元组、原始类型别名
type ID = string | number;
type Pair = [string, number];
type Name = string;

// ✅ type 独有：条件类型、映射类型（高级用法）
type Readonly<T> = {
  readonly [P in keyof T]: T[P];
};
```

### 9.2 选择建议

> **简单规则**：能用 interface 就用 interface，需要 type 独有功能时再用 type。

具体来说：
- **优先 interface**：描述对象结构、公共 API 的形状
- **使用 type**：联合类型、元组、工具类型、映射类型、条件类型

## 十、多余属性检查（Excess Property Checks）

### 10.1 它是什么？

TypeScript 会对**对象字面量**进行额外的严格检查——如果你给了多余的属性，会报错：

```typescript
interface Person {
  name: string;
  age: number;
}

// 直接传入对象字面量 —— 会触发多余属性检查
function printPerson(p: Person) {
  console.log(`${p.name}, ${p.age}`);
}

printPerson({ name: "Alarik", age: 25 });                    // ✅
printPerson({ name: "Alarik", age: 25, gender: "male" });     // ❌ 多余的 gender 属性！
```

### 10.2 为什么要有这种检查？

为了捕获拼写错误和无效数据：

```typescript
// 你想传 email 但拼错了
printPerson({
  name: "Alarik",
  age: 25,
  emial: "test@example.com", // ❌ 拼写错误！多余属性检查救了你
});
```

### 10.3 如何绕过多余属性检查

有时候你就是需要传额外的属性，有以下方法：

**方法一：先赋值给变量**

```typescript
// 把对象先存到变量中，再传递
const data = { name: "Alarik", age: 25, gender: "male" };
printPerson(data); // ✅ 不触发检查（不再是对象字面量上下文）
```

**方法二：类型断言**

```typescript
// 使用 as 断言
printPerson({ name: "Alarik", age: 25, gender: "male" } as Person); // ✅
```

**方法三：索引签名**

```typescript
// 给接口添加索引签名
interface FlexiblePerson {
  name: string;
  age: number;
  [key: string]: unknown; // 允许任意额外属性
}

printPerson({ name: "Alarik", age: 25, gender: "male" }); // ✅
```

**方法四：使用 satisfies（TS 4.9+）**

```typescript
// satisfies 会验证类型但不阻止额外属性
const data = {
  name: "Alarik",
  age: 25,
  gender: "male",
} satisfies Person; // ✅ 通过验证
```

## 十一、可辨识联合（Discriminated Union）

### 11.1 基本概念

可辨识联合是一种强大的模式，用于处理**可能有不同形状但共享某个共同标识符**的对象：

```typescript
// 每种形状都有一个共同的"辨识字段"
interface SuccessResult {
  status: 'success';    // 辨识字段
  data: string;
}

interface ErrorResult {
  status: 'error';      // 辨识字段（同样的字段名）
  error: { code: string; message: string };
}

type Result = SuccessResult | ErrorResult;

function handleResult(result: Result) {
  // 通过辨识字段进行区分
  switch (result.status) {
    case 'success':
      console.log(`数据: ${result.data}`);     // result 被收窄为 SuccessResult
      break;
    case 'error':
      console.log(`错误: ${result.error.message}`); // result 被收窄为 ErrorResult
      break;
  }
}
```

### 11.2 为什么叫"可辨识联合"？

- **可辨识**：每个成员有一个独特的"标签"（如 `status`），用来区分它是哪种类型
- **联合**：整体是一个联合类型（`SuccessResult | ErrorResult`）

这是 TypeScript 中处理多态数据的**最常用模式之一**，尤其在处理 API 响应、状态机、表单验证等场景中非常实用。

### 11.3 实际应用示例

```typescript
// API 请求状态管理
interface LoadingState {
  status: 'loading';
}

interface SuccessState {
  status: 'success';
  data: UserData;
}

interface ErrorState {
  status: 'error';
  error: string;
}

type AppState = LoadingState | SuccessState | ErrorState;

function render(state: AppState) {
  switch (state.status) {
    case 'loading':
      return <Spinner />;
    case 'success':
      return <UserProfile data={state.data} />;
    case 'error':
      return <ErrorMessage message={state.error} />;
  }
}
```

## 十二、接口的声明合并

### 12.1 什么是声明合并？

TypeScript 允许你**多次声明同一个 interface 名称**，它们的成员会被自动合并：

```typescript
// 第一次声明
interface User {
  name: string;
}

// 第二次声明 —— 自动合并
interface User {
  age: number;
}

// 最终 User 等价于
interface User {
  name: string;
  age: number;
}

// 使用
const u: User = { name: "Alarik", age: 25 }; // ✅ 需要两个属性都有
```

### 12.2 实际应用：扩展全局类型

声明合并最实用的场景是**扩展第三方库或全局对象的类型**：

```typescript
// 扩展 Window 接口
declare global {
  interface Window {
    __APP_VERSION__: string;
    __INITIAL_STATE__: Record<string, unknown>;
  }
}

// 现在可以在任何地方安全地使用这些新属性
window.__APP_VERSION__ = "1.0.0"; // ✅ TS 认识它了
console.log(window.__INITIAL_STATE__); // ✅
```

### 12.3 合并时的冲突规则

如果两次声明的同名属性类型不一致，会报错：

```typescript
interface Box {
  contents: string;
}

interface Box {
  contents: number;  // ❌ 后续属性声明必须属于同一类型
}
```

但方法可以正常合并（只要签名兼容）：

```typescript
interface Document {
  getElementById(id: string): HTMLElement | null;
}

interface Document {
  querySelector(selector: string): Element | null;
}
// 两个方法共存，没问题
```


### 13.2 接口设计原则

**原则一：面向行为而非数据来设计接口**

```typescript
// ❌ 只是数据容器
interface UserData {
  firstName: string;
  lastName: string;
  email: string;
}

// ✅ 表达意图和能力
interface User {
  getFullName(): string;
  contactEmail: string;
  canAccess(resource: string): boolean;
}
```

**原则二：保持接口小而聚焦**

```typescript
// ❌ 上帝接口（God Object）
interface User {
  id: string;
  name: string;
  email: string;
  password: string;
  avatar: string;
  settings: {...};
  preferences: {...};
  notifications: [...];
  // ...50+ 个属性
}

// ✅ 拆分为多个小接口
interface BasicUserInfo { id: string; name: string; email: string; }
interface UserSettings { theme: string; language: string; }
interface NotificationPrefs { email: boolean; push: boolean; sms: boolean; }
```

**原则三：依赖倒置——依赖接口而非实现**

```typescript
// ✅ 好：函数依赖接口
function sendNotification(notifier: INotifier, user: User, message: string) {
  notifier.send(user, message);
}

// 这样可以轻松替换通知实现
class EmailNotifier implements INotifier { /* ... */ }
class SmsNotifier implements INotifier { /* ... */ }
class PushNotifier implements INotifier { /* ... */ }
```

### 13.3 export/import 最佳实践

```typescript
// types/user.ts
export interface User {
  id: string;
  name: string;
  email: string;
}

export interface CreateUserInput {
  name: string;
  email: string;
  password: string;
}

export interface UpdateUserInput {
  name?: string;
  email?: string;
  avatar?: string;
}

// 使用处
import type { User, CreateUserInput, UpdateUserInput } from '@/types/user';

async function createUser(input: CreateUserInput): Promise<User> {
  // ...
}
```

使用 `import type` 可以确保只在编译时导入类型，不会影响打包体积。

## 十四、个人总结与心得

### 14.1 核心知识图谱

```
对象类型体系
│
├─ 字面量类型 { k: T }     → 一次性使用
├─ interface               → 可复用的对象契约
│  ├─ 可选属性 ?           → 表示非必填字段
│  ├─ 只读属性 readonly    → 表示不可变性
│  ├─ 方法定义             → 行为描述
│  ├─ extends 继承        → 复用和扩展
│  └─ 声明合合并           → 全局扩展能力
├─ type 别名               → 更灵活的类型组合
│  └─ 交叉类型 &           → 组合多个类型
├─ 索引签名               → 动态键支持
└─ 可辨识联合             → 多态数据处理
```

### 14.2 我的经验法则

经过大量项目的实践，我的心得是：

1. **先用 interface，需要时再换 type** —— 对于纯粹的对象类型，interface 的语义更好
2. **可选属性要谨慎使用** —— 每个可选属性都意味着调用方要做空值检查，不要过度使用
3. **readonly 是好习惯** —— 尤其是对于 ID、创建时间这类"一旦确定就不应该改变"的字段
4. **善用可辨识联合** —— 这是处理多种状态的银弹模式，比一堆 `if-else` 加类型断言优雅得多
5. **注意多余属性检查** —— 它是你的朋友，帮你抓 bug；如果确实需要绕过，了解各种方式的代价

### 14.3 关于"面向接口编程"

TypeScript 的 interface 不仅仅是一个类型检查工具，它还能引导你写出更好的代码架构：

> **好的 interface 设计 = 好的抽象边界 = 好的系统架构**

当你发现自己在纠结"这个属性该放哪个 interface"的时候，其实就是在思考系统的模块边界——这本身就是一种架构设计能力的锻炼。

---

> **一句话总结**：interface 是 TypeScript 中描述对象形状的核心工具。掌握了 interface，就等于掌握了 TypeScript 类型系统中最重要的部分。记住：好的接口设计源于对业务领域的深刻理解，而不是对语法的机械堆砌。
