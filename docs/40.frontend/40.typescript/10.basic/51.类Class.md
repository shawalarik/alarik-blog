# 类（Class）

> **一句话总结**：TypeScript 的类是 ES6 类的"增强版"——它不仅能在运行时创建对象，还能在编译时提供完整的类型检查。字段声明、访问修饰符、参数属性等特性让类的定义更简洁、更安全。

## 一、ES6 Class 回顾

在深入了解 TypeScript 的类之前，先快速回顾一下 ES6 中类的基本概念：

```javascript
// 纯 JavaScript（ES6+）
class Person {
  // 构造函数
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  // 实例方法
  greet() {
    return `你好，我是 ${this.name}，今年 ${this.age} 岁`;
  }

  // 静态方法
  static createAnonymous() {
    return new Person('匿名', 0);
  }
}

const p = new Person('张三', 25);
console.log(p.greet()); // 你好，我是 张三，今年 25 岁
```

**ES6 类的问题**：
- 字段必须 `this.xxx = xxx` 在构造函数中赋值——容易遗漏
- 没有访问控制——所有属性都是公开的
- 没有类型信息——传错参数类型只有运行时才能发现

TypeScript 的类就是在 ES6 类的基础上，解决了以上问题。

## 二、TypeScript Class 增强

### 2.1 class 基本结构

```typescript
class Person {
  // ✅ TS 允许直接声明实例字段（ES6 不支持，需要实验性支持）
  name: string;      // 字段声明
  age: number;

  // 构造函数
  constructor(name: string, age: number) {
    this.name = name;   // 赋值给声明的字段
    this.age = age;
  }

  // 方法
  greet(): string {
    return `你好，我是 ${this.name}`;
  }
}

// 使用
const person = new Person('李四', 30);
console.log(person.greet());  // 你好，我是 李四
console.log(person.name);     // 李四
console.log(person.age);      // 30
```

### 2.2 字段（Field/Property）声明及初始化

#### 基本字段声明

```typescript
class Car {
  // 必须声明字段的类型
  brand: string;          // 声明但未初始化 → 构造函数中必须赋值
  model: string;
  year: number;
  
  // 可以带默认值
  color: string = 'white';
  isElectric: boolean = false;

  constructor(brand: string, model: string, year: number) {
    this.brand = brand;   // ✅ 赋值给已声明的字段
    this.model = model;
    this.year = year;
    // color 和 isElectric 有默认值，不需要在这里赋值
  }
}

const car = new Car('Tesla', 'Model 3', 2024);
console.log(car.color);      // 'white' （使用默认值）
console.log(car.isElectric); // false
```

#### 可选字段

```typescript
class UserProfile {
  username: string;
  avatar?: string;       // 可选字段（可能为 undefined）
  bio?: string;
  lastLoginAt?: Date;

  constructor(username: string) {
    this.username = username;
    // avatar 和 bio 是可选的，不赋值也没关系
  }
}

const user1 = new UserProfile('alice');
console.log(user1.avatar); // undefined —— 安全，不会报错

user1.bio = 'Hello world!'; // 之后可以随时赋值
```

#### readonly 只读字段

```typescript
class ImmutableConfig {
  readonly appId: string;        // 只读——只能在构造函数中赋值
  readonly version: string;
  readonly createdAt: Date = new Date();

  constructor(appId: string, version: string) {
    this.appId = appId;           // ✅ 构造函数中可以赋值
    this.version = version;
  }
}

const config = new ImmutableConfig('my-app', '1.0.0');
console.log(config.appId);  // 'my-app'

config.appId = 'new-app';   // ❌ 无法分配到 "appId"，因为它是只读属性
config.version = '2.0';     // ❌ 同样不行
```

**设计理念**：`readonly` 提供了编译时的不可变性保证，类似于 `const` 对变量的作用。它在 API 设计中特别有用——确保某些关键属性一旦创建就不能被意外修改。

## 三、构造函数（Constructor）

### 3.1 基本用法

```typescript
class Product {
  id: number;
  name: string;
  price: number;

  constructor(id: number, name: string, price: number) {
    this.id = id;
    this.name = name;
    this.price = price;
  }

  getDiscountedPrice(discountRate: number): number {
    return this.price * (1 - discountRate);
  }
}

const product = new Product(1, '笔记本电脑', 5999);
console.log(product.getDiscountedPrice(0.1)); // 5399.1
```

### 3.2 参数属性（Parameter Properties）——语法糖！

这是 TypeScript 最方便的特性之一。你可以在构造函数参数前直接加访问修饰符，自动创建并赋值对应的字段：

```typescript
// ❌ 传统写法——冗长
class Person {
  name: string;
  age: number;
  
  constructor(name: string, age: number) {
    this.name = name;   // 重复三遍 name
    this.age = age;     // 重复三遍 age
  }
}

// ✅ TypeScript 参数属性写法——简洁！
class Person {
  constructor(
    public name: string,   // public 自动创建 this.name 并赋值
    public age: number     // public 自动创建 this.age 并赋值
  ) {}
  // 不需要额外声明字段！不需要手动赋值！
}
```

**生活类比**：就像去酒店入住时填表——传统写法是你先声明"我需要一间房"，然后在表格里再填一遍名字；参数属性则是前台直接根据你的身份证帮你把一切都办好了。

```typescript
// 更实际的例子
class HttpService {
  constructor(
    private baseUrl: string,    // private：外部不可访问
    private timeout: number = 5000,
    public version: string = '1.0'  // public：外部可访问
  ) {}

  async request(endpoint: string) {
    const url = `${this.baseUrl}${endpoint}`;
    console.log(`请求: ${url}, 超时: ${this.timeout}ms`);
    // ...
  }
  
  getVersion() {
    return this.version;
  }
}

const api = new HttpService('https://api.example.com');
// api.baseUrl  → ❌ 私有的，不能访问
// api.timeout → ❌ 私有的，不能访问
// api.version → ✅ 公开的，可以访问
api.request('/users');         // ✅
api.getVersion();              // ✅
```

## 四、方法（Method）定义

### 4.1 实例方法

```typescript
class Calculator {
  // 普通方法
  add(a: number, b: number): number {
    return a + b;
  }

  // 返回对象的方法
  createPoint(x: number, y: number): { x: number; y: number } {
    return { x, y };
  }

  // 异步方法
  async fetchData(url: string): Promise<Response> {
    const response = await fetch(url);
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }
    return response;
  }

  // 返回 this 的方法——链式调用
  log(value: string): this {
    console.log(value);
    return this;
  }
}

const calc = new Calculator();
calc.log('开始计算').log('1 + 2 =').log(String(calc.add(1, 2)));
```

### 4.2 方法重载签名

TypeScript 支持为同一个方法定义多个**调用签名**：

```typescript
class StringUtil {
  // 重载签名——只定义类型，没有实现
  repeat(str: string, count: number): string;
  repeat(str: string, count: string): string;
  
  // 实现签名——必须兼容所有重载签名
  repeat(str: string, count: number | string): string {
    const n = typeof count === 'string' ? parseInt(count, 10) : count;
    return str.repeat(n);
  }
}

const util = new StringUtil();
util.repeat('ha', 3);     // ✅ 返回 'hahaha'
util.repeat('ha', '3');   // ✅ 也返回 'hahaha'
```

### 4.3 方法中的 this 问题

```typescript
class Button {
  constructor(private label: string) {}

  click(): void {
    console.log(`按钮 "${this.label}" 被点击了`);
  }
}

const button = new Button('提交');

button.click();                    // ✅ 正常工作

const onClick = button.click;
onClick();                          // ❌ 运行时错误：this 是 undefined！
// 因为 onClick 调用时丢失了 this 绑定

// 解决方案 1：箭头函数（推荐）
class SafeButton {
  constructor(private label: string) {}

  click = (): void => {            // 箭头函数作为字段
    console.log(`按钮 "${this.label}" 被点击了`);
  };
}

const safeButton = new SafeButton('取消');
const safeOnClick = safeButton.click;
safeOnClick();                      // ✅ 箭头函数绑定 this

// 解决方案 2：使用 bind
const boundClick = button.click.bind(button);
boundClick();                       // ✅ 手动绑定
```

**💡 个人心得**：这是 JavaScript/TypeScript 新手最容易踩的坑之一。如果方法会被当作回调函数传递（如 `setTimeout`、事件监听器、数组方法），要么用箭头函数字段，要么在使用处 `.bind(this)`。

## 五、访问修饰符（Access Modifiers）

TypeScript 提供三种访问修饰符来控制类成员的可访问性：

| 修饰符 | 类内部 | 子类 | 外部 |
|--------|-------|------|------|
| `public`（默认） | ✅ | ✅ | ✅ |
| `protected` | ✅ | ✅ | ❌ |
| `private` | ✅ | ❌ | ❌ |

### 5.1 public——公开的

```typescript
class PublicExample {
  // 所有成员默认都是 public
  public name: string;       // 显式 public
  age: number;               // 隐式 public（省略修饰符等同于 public）
  
  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }

  public introduce() {       // 显式 public
    return `${this.name}, ${this.age}岁`;
  }
}

const pub = new PublicExample('Alice', 28);
pub.name;          // ✅ 可以访问
pub.age;           // ✅ 可以访问
pub.introduce();   // ✅ 可以调用
```

### 5.2 private——私有的

```typescript
class BankAccount {
  private balance: number;       // 私有字段
  private _pin: string;          // 私有字段（下划线前缀是命名约定）
  
  constructor(initialBalance: number, pin: string) {
    this.balance = initialBalance;
    this._pin = pin;
  }

  deposit(amount: number): void {
    if (amount > 0) {
      this.balance += amount;     // ✅ 内部可以访问私有字段
    }
  }

  withdraw(amount: number, pin: string): boolean {
    if (pin !== this._pin) {
      console.error('密码错误！');
      return false;
    }
    if (amount > this.balance) {
      console.error('余额不足！');
      return false;
    }
    this.balance -= amount;
    return true;
  }

  getBalance(pin: string): number | null {
    if (pin !== this._pin) return null;
    return this.balance;
  }
}

const account = new BankAccount(10000, '1234');

account.balance;      // ❌ 属性 "balance" 为私有属性，只能在类 "BankAccount" 中访问
account._pin;         // ❌ 同样私有
account.deposit(500); // ✅ 通过公开方法间接操作
account.withdraw(1000, '1234'); // ✅ 需要密码验证
```

**⚠️ 注意**：TypeScript 的 `private` 是**编译时**检查，编译后的 JavaScript 代码中这些属性仍然是可访问的。如果需要真正的运行时隐私性，可以使用 `#private field`（ES2020 私有字段）或 `WeakMap`。

```typescript
// 使用 # 私有字段实现真正的运行时隐私
class TrulyPrivate {
  #secret: string;          // JS 原生私有字段

  constructor(secret: string) {
    this.#secret = secret;
  }

  getSecret(): string {
    return this.#secret;
  }
}

const tp = new TrulyPrivate('机密');
tp.#secret;  // ❌ 编译和运行都会报错
```

### 5.3 protected——受保护的

```typescript
class Employee {
  constructor(
    protected name: string,       // protected：子类可以访问
    protected salary: number
  ) {}

  getInfo(): string {
    return `${this.name}: ¥${this.salary}`;
  }
}

class Manager extends Employee {
  private bonus: number;

  constructor(name: string, salary: number, bonus: number) {
    super(name, salary);
    this.bonus = bonus;
  }

  getTotalCompensation(): number {
    // ✅ 子类可以访问 protected 成员
    return this.salary + this.bonus;
  }

  getInfo(): string {
    // ✅ 子类可以读取 protected 字段
    return `经理 ${this.name}：月薪 ¥${this.salary} + 奖金 ¥${this.bonus}`;
  }
}

const emp = new Employee('普通员工', 8000);
emp.name;    // ❌ protected 不能在外部访问
emp.salary;  // ❌ 同上

const mgr = new Manager('王经理', 15000, 5000);
mgr.name;    // ❌ protected 不能在外部访问
mgr.getTotalCompensation();  // ✅ 通过公开方法访问
mgr.getInfo();              // ✅
```

### 5.4 访问修饰符的设计理念

访问修饰符体现了**封装（Encapsulation）**原则——隐藏内部实现细节，只暴露必要的接口。

```typescript
// ❌ 反模式：所有字段都公开
class BadCounter {
  public value: number = 0;   // 任何人都能直接修改！

  increment() {
    this.value++;
  }
}

const bad = new BadCounter();
bad.value = -9999;  // 💥 直接破坏内部状态！

// ✅ 好的做法：封装内部状态
class GoodCounter {
  private _value: number = 0;   // 私有——外部无法触碰

  increment(): void {
    this._value++;
  }

  decrement(): void {
    if (this._value > 0) {       // 可以添加业务规则
      this._value--;
    }
  }

  getValue(): number {
    return this._value;           // 只读访问
  }
}

const good = new GoodCounter();
good.increment();
good.increment();
console.log(good.getValue()); // 2
// good._value = -9999;      // ❌ 编译错误，保护了内部状态
```

## 六、继承（extends）——重中之重

> **为什么继承是重中之重？** 因为继承是面向对象编程（OOP）的核心机制之一，它不仅是代码复用的手段，更是建立**类型层次结构**、实现**多态行为**的基础。在 TypeScript 中，继承与类型系统深度结合——继承关系直接影响类型的**赋值兼容性**。不理解继承，就无法真正理解 TypeScript 的类型系统。

### 6.1 生活化类比：理解继承的本质

想象一下**汽车制造**的过程：

```
🏭 汽车工厂的继承体系

交通工具（Vehicle）          ← 基类：所有交通工具的共同特征
  ├── 引擎、轮子数量、载客量
  ├── 启动()、停止()、行驶()
  │
  ├── 汽车（Car）            ← 子类：继承了交通工具的一切
  │     ├── 增加了：方向盘、车门数
  │     └── 覆写了：行驶方式（公路）
  │
  ├── 公交车（Bus）           ← 子类：继承了交通工具的一切
  │     ├── 增加了：路线编号、座位数
  │     └── 覆写了：行驶方式（固定路线）
  │
  └── 自行车（Bicycle）       ← 子类：继承了交通工具的一切
        ├── 增加了：脚踏板、铃铛
        └── 覆写了：动力来源（人力）
```

**核心思想**：
- **基类（Parent）** 定义了"是什么"（共性）
- **子类（Child）** 定义了"有什么不同"（特性）
- 子类 **自动拥有** 父类的所有能力，同时可以 **添加新能力** 或 **改变现有能力**

#### 为什么叫"继承"？——从现实世界到编程世界

在现实生活中，"继承"通常指财产或基因的传递。编程中的继承借用了这个概念，但含义稍有不同：

```
现实世界的继承：
  你继承了父亲的眼睛颜色、母亲的身高 → 这是被动的、不可选择的

编程世界的继承：
  Dog extends Animal → 我们主动选择让 Dog 拥有 Animal 的能力
  这是一种设计决策，不是随机发生的
```

**更准确的理解方式**：

你可以把继承想象成 **"模板 + 定制"** 的模式：
- **父类 = 基础模板**（定义了通用的骨架）
- **子类 = 定制化版本**（在模板基础上做修改和扩展）

这就像装修房子：
- 开发商交房时给你一个 **毛坯房**（父类）：有墙、有地板、有水电
- 你可以根据自己的喜好 **精装修**（子类）：刷墙、铺地砖、装吊灯
- 但无论怎么装，它依然是一个房子——基础结构没变

#### 从另一个角度：继承是"分类学"

生物学上的分类体系就是最好的继承模型：

```
界 (Animalia)          ← 最抽象：都是生物
  └── 门 (Chordata)      ← 有脊椎
       └── 纲 (Mammalia)  ← 哺乳动物
            └── 目 (Carnivora)  ← 肉食动物
                 └── 科 (Canidae)    ← 犬科
                      └── 属 (Canis)
                           └── 种 (Canis lupus familiaris)  ← 家狗
```

每一层都比上一层 **更具体**、**信息量更大**。TypeScript 的继承体系完全遵循这个思想。每一层子类都 **包含** 父类的全部特征，同时 **新增** 自己独有的特征。

这就是为什么 `Dog` 可以赋值给 `Animal` 类型变量——因为在分类学上，狗确实属于动物，它拥有动物的一切基本属性。反过来不成立——不是所有动物都是狗。

### 6.2 基本继承语法

```typescript
// ====== 父类（基类/超类 Base/Super class）======
class Animal {
  // 父类的字段
  name: string;
  age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }

  // 父类的方法 —— 所有子类都会自动拥有
  eat(): void {
    console.log(`${this.name} 正在吃东西...`);
  }

  sleep(): void {
    console.log(`${this.name} 正在睡觉... 💤`);
  }

  move(distance: number): void {
    console.log(`${this.name} 移动了 ${distance} 米`);
  }

  introduce(): string {
    return `我是 ${this.name}，今年 ${this.age} 岁`;
  }
}

// ====== 子类（派生类 Derived/Sub class）=======
class Dog extends Animal {
  // 子类新增的字段
  breed: string;   // 品种

  constructor(name: string, age: number, breed: string) {
    super(name, age);   // ⚠️ 第一件事：必须先调用父类构造函数！
    this.breed = breed; // 然后才能使用 this
  }

  // 子类新增的方法
  bark(): void {
    console.log(`${this.name}（${this.breed}）：汪汪汪！🐕`);
  }

  fetch(item: string): void {
    console.log(`${this.name} 去捡回了 ${item}`);
  }
}

// ====== 另一个子类 ======
class Cat extends Animal {
  furColor: string;  // 毛色
  isIndoor: boolean; // 是否室内猫

  constructor(name: string, age: number, furColor: string, isIndoor: boolean = true) {
    super(name, age);
    this.furColor = furColor;
    this.isIndoor = isIndoor;
  }

  // 子类新增的方法
  meow(): void {
    console.log(`${this.name}（${this.furColor}猫）：喵喵喵！🐱`);
  }

  scratch(): void {
    if (this.isIndoor) {
      console.log(`${this.name} 在抓沙发... 🛋️💥`);
    } else {
      console.log(`${this.name} 在抓树干... 🌳`);
    }
  }
}
```

#### 使用继承后的效果

```typescript
// 创建子类实例
const dog = new Dog('旺财', 3, '柴犬');
const cat = new Cat('咪咪', 2, '橘色', true);

// ========== 子类可以访问自己新增的成员 ==========
dog.bark();           // 旺财（柴犬）：汪汪汪！🐕
dog.fetch('飞盘');     // 旺财 去捡回了 飞盘
cat.meow();           // 咪咪（橘色猫）：喵喵喵！🐱
cat.scratch();        // 咪咪 在抓沙发... 🛋️💥

// ========== 子类自动拥有父类的所有成员 ==========
dog.eat();            // 旺财 正在吃东西...      ← 来自 Animal
dog.sleep();          // 旺财 正在睡觉... 💤      ← 来自 Animal
dog.move(100);        // 旺财 移动了 100 米        ← 来自 Animal
dog.introduce();      // 我是 旺财，今年 3 岁      ← 来自 Animal

cat.eat();            // 咪咪 正在吃东西...
cat.introduce();      // 我是 咪咪，今年 2 岁

// ========== 访问字段 ==========
console.log(dog.name);    // 旺财        ← 父类字段
console.log(dog.age);     // 3           ← 父类字段
console.log(dog.breed);   // 柴犬        ← 子类字段
console.log(cat.furColor); // 橘色       ← 子类字段
```

#### 理解继承的"全有或全无"特性

当你写 `class Dog extends Animal` 时，Dog 会 **100% 继承** Animal 的所有公开和保护成员。这不是"选择性的"——你不能只继承 `eat()` 而不继承 `sleep()`。这就像你继承了某个人的遗产：你不能说"我要钱但不要债务"，要么全要，要么全不要（当然 private 成员是例外，它们确实不会被继承）。

**这带来的影响**：
- ✅ **好处**：不需要手动声明每个继承来的成员，代码简洁
- ⚠️ **代价**：如果父类有很多成员你用不到，子类的"接口"会很臃肿——这就是为什么有些情况下组合比继承更合适

> **类比**：想象你在一家公司实习，你的导师把他的所有权限都转交给了你（包括一些你可能永远用不到的权限）。这很方便（不用一个个申请），但也可能带来风险（误操作不熟悉的权限）。

### 6.3 三条铁律——必须牢记

```typescript
// ❌ 错误1：忘记调用 super()
class BadDog extends Animal {
  breed: string;

  constructor(name: string, age: number, breed: string) {
    // 忘记 super(name, age)!
    this.breed = breed;  // ❌ 编译错误：在访问 'this' 之前必须先调用 'super()'
  }
}

// ❌ 错误2：super() 不是第一条语句
class BadCat extends Animal {
  furColor: string;

  constructor(name: string, age: number, furColor: string) {
    this.furColor = furColor;  // ❌ 不能在 super() 之前使用 this!
    super(name, age);
  }
}

// ❌ 错误3：在 super() 之前访问 this
class BadBird extends Animal {
  wingspan: number;

  constructor(name: string, wingspan: number) {
    this.wingspan = wingspan * 2;  // ❌ 还没调 super() 就用 this 了
    super(name, 1);
  }
}

// ✅ 正确做法
class GoodDog extends Animal {
  breed: string;

  constructor(name: string, age: number, breed: string) {
    super(name, age);        // ① 第一步：先调用 super()
    this.breed = breed;      // ② 第二步：然后才可以用 this
  }
}
```

**为什么有这个限制？**

这是 JavaScript 语言规范的要求。原因在于初始化顺序：

```
创建子类实例时的执行顺序：

  ① 先创建父类的作用域（让 super() 能工作）
  ② 调用 super() → 触发父类构造函数 → 初始化父类的 this
  ③ super() 返回后，this 才完全就绪
  ④ 这时才能安全地使用 this 来操作子类自己的字段

如果跳过 super() 就用 this，相当于"房子还没盖好就想进去装修"
```

#### 深入理解：为什么 JavaScript 要强制这个规则？

这个限制不是 TypeScript 发明的——它来自 **ECMAScript 2015 (ES6) 的类规范**。原因涉及 JavaScript 对象模型的底层原理：

**1. `this` 在子类构造函数中到底是什么？**

在 JavaScript 中，`this` 的值取决于函数是如何被调用的。对于构造函数：

```javascript
// 简化版内部流程（概念性说明）
function Child() {
  // 此时 this 还不存在！
  // 必须先调用 super()，super() 内部会：
  //   ① 创建一个新的对象
  //   ② 将这个对象的原型设为 Parent.prototype
  //   ③ 用这个对象作为 this 执行 Parent 的构造函数体
  //   ④ 返回这个初始化好的对象
  super();   // 只有执行完这行后，this 才可用
  
  // 现在 this 已经指向一个完整的、继承了父类的对象了
  this.childProp = 'hello';  // ✅ 安全
}
```

**2. 如果不调 `super()` 就用 `this` 会怎样？**

想象一下：
- 父类构造函数可能做了重要的初始化工作（比如设置必要的属性、建立内部数据结构）
- 如果跳过这些直接操作 `this`，对象处于 **半初始化** 状态
- 后续的代码可能会依赖父类设置的某些属性，而这些属性还不存在 → **运行时错误**

**3. 为什么是"必须在第一条语句"？**

这是为了 **简化语言规范** 和 **保证一致性**。如果允许在 `super()` 之前写代码，那么这些代码就无法访问 `this`，但它们又属于构造函数的一部分——这会造成语义混乱。JavaScript 规范选择了一刀切的方式：**先完成父类初始化，再做自己的事**。

> **类比**：就像你继承了一家公司的经营权。法律要求你必须先完成正式的交接手续（签字、盖章、核验资产），然后才能开始经营。你不能在交接完成前就开始动用公司的资金。

**4. 唯一的例外**

有一种情况不需要显式调用 `super()` —— 当你的子类构造函数 **没有定义** 时：

```typescript
class SimpleChild extends Parent {
  // 如果不写 constructor，JavaScript 会自动生成一个空的 constructor，
  // 其中自动包含 super()
  // 相当于：constructor(...args) { super(...args); }
}

const s = new SimpleChild('hello');  // ✅ 自动调用父类构造函数
```

### 6.4 super 关键字的两种用法

`super` 是一个特殊关键字，在子类中有两种完全不同的用途：

#### 用法一：`super(参数)` — 调用父类构造函数

```typescript
class Entity {
  id: string;
  createdAt: Date;

  constructor(id: string) {
    this.id = id;
    this.createdAt = new Date();
    console.log(`Entity 创建完成: id=${this.id}`);
  }
}

class User extends Entity {
  name: string;
  email: string;

  // super(...) 把参数传给父类构造函数
  constructor(id: string, name: string, email: string) {
    super(id);  // 调用 Entity 的 constructor(id)
                // 此时 this.id 和 this.createdAt 已经被设置好了
    this.name = name;
    this.email = email;
    console.log(`User 创建完成: name=${this.name}`);
  }
}

const user = new User('u001', '张三', 'zhangsan@test.com');
// 输出：
// Entity 创建完成: id=u001
// User 创建完成: name=张三
```

#### 用法二：`super.方法名(参数)` — 调用父类方法

这是覆写（Override）时最常用的模式——在子类方法中 **扩展** 父类行为，而不是完全替换它。

```typescript
class Vehicle {
  constructor(public brand: string) {}

  start(): string {
    return `[${this.brand}] 引擎启动中...`;
  }

  stop(): string {
    return `[${this.brand}] 已停车`;
  }

  getInfo(): string {
    return `品牌: ${this.brand}`;
  }
}

class ElectricCar extends Vehicle {
  batteryLevel: number;
  range: number;

  constructor(brand: string, batteryLevel: number = 100, range: number = 500) {
    super(brand);
    this.batteryLevel = batteryLevel;
    this.range = range;
  }

  // ✅ 覆写 + 调用 super —— "增强"父类行为
  start(): string {
    if (this.batteryLevel < 10) {
      return `[${this.brand}] ⚠️ 电量不足(${this.batteryLevel}%)，无法启动`;
    }
    const baseMessage = super.start();  // 调用父类的 start()
    return `${baseMessage} 🔋 电量: ${this.batteryLevel}%`;
  }

  stop(): string {
    const baseMessage = super.stop();
    return `${baseMessage} | 剩余续航: ${this.getRemainingRange()}km`;
  }

  getInfo(): string {
    // 调用父类 getInfo() 获取基础信息，再追加电动车特有信息
    const baseInfo = super.getInfo();
    return `${baseInfo} | 类型: 纯电 | 续航: ${this.range}km`;
  }

  private getRemainingRange(): number {
    return Math.floor(this.range * (this.batteryLevel / 100));
  }
}

const tesla = new ElectricCar('Tesla Model 3', 85, 556);
console.log(tesla.start());   // [Tesla Model 3] 引擎启动中... 🔋 电量: 85%
console.log(tesla.getInfo()); // 品牌: Tesla Model 3 | 类型: 纯电 | 续航: 556km
console.log(tesla.stop());    // [Tesla Model 3] 已停车 | 剩余续航: 472km

const lowBattery = new ElectricCar('BYD Seal', 5, 700);
console.log(lowBattery.start());
// [BYD Seal] ⚠️ 电量不足(5%)，无法启动
```

**关键点**：`super.method()` 让你能在保留父类原有逻辑的基础上 **追加** 新逻辑，这是 OOP 中非常重要的 **开闭原则（OCP）** 的体现——对扩展开放，对修改关闭。

#### 理论深入：`super` 在内存中的真实面貌

很多初学者以为 `super` 是一个对象或类的引用。但实际上，`super` 的行为 **取决于上下文**：

```typescript
class Parent {
  name = 'Parent';
  static staticName = 'StaticParent';
  
  method() { return 'Parent method'; }
  static staticMethod() { return 'Parent static method'; }
}

class Child extends Parent {
  name = 'Child';
  
  // 在普通方法中
  testMethod() {
    console.log(super.name);        // 'Parent' → 指向父类原型上的属性
    console.log(this.name);        // 'Child' → 指向当前实例的属性
    console.log(super.method());   // 'Parent method' → 以 this 身份调用父类方法
  }
  
  // 在静态方法中
  static testStatic() {
    console.log(super.staticName);     // 'StaticParent'
    console.log(Child.staticName);    // 'Child'
    console.log(super.staticMethod()); // 'Parent static method'
  }
}
```

**关键区别**：
- 在实例方法中：`super` 类似于 `Object.getPrototypeOf(Child.prototype)` —— 指向 **父类的原型**
- 在静态方法中：`super` 类似于 `Object.getPrototypeOf(Child)` —— 指向 **父类构造函数**
- 调用 `super.method()` 时，方法内部的 `this` 仍然绑定的是 **当前子类实例**（不是父类！）

这就是为什么在覆写方法中调用 `super.method()` 时，如果父类方法内部使用了 `this.xxx`，它访问到的仍然是子类的属性——因为 `this` 始终指向实际创建的实例。

> **通俗理解**：`super.method()` 就像是"借父类的工具来处理我自己的材料"。工具是父类的（方法逻辑），但操作的对象是你自己的（this）。

#### 什么时候用 `super(...)`，什么时候用 `super.method()`？

很多初学者容易混淆这两个。记住一个简单的区分方式：

| | `super(参数)` | `super.method(参数)` |
|---|---|---|
| **在哪里** | 只能在构造函数中用 | 在普通方法和静态方法中都能用 |
| **时机** | 创建实例时执行一次 | 每次调用方法时都可以执行 |
| **作用** | 让父类帮你初始化对象 | 让父类的方法参与当前逻辑 |
| **类比** | 买房时让开发商做基础装修 | 做饭时借用爸爸的秘制配方 |

**一个常见误区**：以为 `super` 是父类的实例。不是的！`super` 不是对象，它是一个特殊的关键字——在构造函数中它代表父类构造函数，在方法中它代表父类原型。

### 6.5 方法覆写（Override）

#### 什么是覆写？

当子类定义了一个与父类 **同名同参数** 的方法时，子类的方法会 **覆盖（替换）** 父类的方法。这就是覆写。

```typescript
class Parent {
  greet(): string {
    return '你好，我是父类';
  }
}

class Child extends Parent {
  // 覆写了父类的 greet 方法
  greet(): string {
    return '你好，我是子类';
  }
}

const parent = new Parent();
const child = new Child();

parent.greet();  // '你好，我是父类'  — 调用的是父类的版本
child.greet();   // '你好，我是子类'  — 调用的是子类的覆写版本
```

#### `override` 关键字（TypeScript 4.3+）

TypeScript 提供了可选的 `override` 关键字，用来 **显式标记** 这个方法是覆写父类的：

```typescript
class Printer {
  print(text: string): void {
    console.log(text);
  }
}

// ✅ 使用 override 关键字（推荐）
class UpperCasePrinter extends Printer {
  override print(text: string): void {  // 明确声明：我在覆写
    console.log(text.toUpperCase());
  }
}

// ❌ 如果不小心拼错了方法名
class WrongPrinter extends Printer {
  override prnt(text: string): void {  // ❌ TS 报错：没有名为 "prnt" 的方法可覆写
    console.log(text);
  }
}

// 不用 override 的话，上面的错误不会被发现
class SilentWrongPrinter extends Printer {
  prnt(text: string): void {  // 没加 override → TS 不报错
                            // 但这其实是一个新方法，不是覆写！
    console.log(text);
  }
}
```

**为什么推荐用 `override`？**
- **防拼写错误**：方法名写错了立刻报错
- **文档作用**：一看就知道这个方法是覆写的
- **重构安全**：如果父类改名了，子类会立刻报错提示

#### 覆写中的三种策略

| 策略 | 说明 | 示例场景 |
|------|------|----------|
| **完全替换** | 不调用 super，全新实现 | 完全不同的行为 |
| **增强（Enhance）** | 先调 super 再追加逻辑 | 日志、校验 |
| **条件拦截** | 根据条件决定是否调 super | 权限检查 |

```typescript
class BaseService {
  getData(): object[] {
    console.log('[BaseService] 从数据库获取数据...');
    return [{ id: 1 }, { id: 2 }];
  }
}

// === 策略1：完全替换 ===
class MockService extends BaseService {
  override getData(): object[] {
    // 完全不用 super，返回模拟数据
    console.log('[MockService] 返回 mock 数据...');
    return [{ id: 999, mock: true }];
  }
}

// === 策略2：增强 ===
class LoggingService extends BaseService {
  private serviceName: string;

  constructor(serviceName: string) {
    super();
    this.serviceName = serviceName;
  }

  override getData(): object[] {
    const startTime = Date.now();
    console.log(`[${this.serviceName}] 开始查询...`);

    const result = super.getData();  // 先调用父类

    const duration = Date.now() - startTime;
    console.log(`[${this.serviceName}] 查询完成，耗时 ${duration}ms，返回 ${result.length} 条`);

    return result;  // 可以对结果做进一步处理
  }
}

// === 策略3：条件拦截 ===
class SecureService extends BaseService {
  private isAuthenticated: boolean;

  constructor(authenticated: boolean) {
    super();
    this.isAuthenticated = authenticated;
  }

  override getData(): object[] {
    if (!this.isAuthenticated) {
      console.warn('⚠️ 未认证，拒绝访问！');
      throw new Error('Unauthorized');
    }
    // 只有认证通过才调父类
    return super.getData();
  }
}
```

#### 理论深入：方法查找链（Method Resolution Order）

当你在子类实例上调用一个方法时，JavaScript 引擎是如何找到正确的方法的？这涉及到 **原型链（Prototype Chain）** 上的方法查找：

```
dog.bark() 的查找过程：

dog 对象
  │
  ├─ dog 自身有 bark() 方法吗？ → ✅ 有！直接执行
  │   （如果没有，继续往下找）
  │
  └─ Dog.prototype
       │
       ├─ Dog.prototype 有 bark() 吗？
       │
       └─ Animal.prototype （通过 [[Prototype]] 链接）
            │
            ├─ Animal.prototype 有 bark() 吗？ → ❌ 没有
            │   但有 eat(), sleep(), move()
            │
            └─ Object.prototype
                 └─ 最终到达 null（链的末端）
```

**覆写的本质**：在 Dog.prototype 上定义了一个和 Animal.prototype 同名的方法。由于查找是从自身开始的，所以 **先找到的就是最终执行的那个**。

这就是为什么覆写能"覆盖"父类行为——不是真的删除了父类方法，而是在查找时 **优先匹配到了子类版本**。

#### 理论深入：为什么 TypeScript 需要类型层面的覆写？

JavaScript 中覆写是纯粹的运行时行为——只要同名就覆写，不管参数是否一致。但 TypeScript 在编译时就能帮你发现问题：

```typescript
class Parent {
  greet(name: string): string {
    return `Hello, ${name}`;
  }
}

// JavaScript 允许这样做——运行时不报错
class BadChild extends Parent {
  greet(): string {           // 参数签名不同！
    return 'Hi!';             // JS 不管这个
  }
}

// 但 TypeScript 默认不报错！因为 TS 认为这是有意为之
// 加了 noImplicitOverride 或 override 关键字后才会检查

// 更危险的情况：返回类型不兼容
class DangerChild extends Parent {
  // 返回 string | undefined 而不是 string
  greet(name: string): string | undefined {
    if (!name) return undefined;  // 可能返回 undefined
    return `Hi, ${name}`;
  }
}

const c = new DangerChild();
const result: string = c.greet('Alice');  // 实际可能是 undefined！TS 不一定报错
```

> **经验法则**：如果你的覆写改变了方法的"契约"（参数数量、返回值含义），那可能不是真正的覆写，而是设计上有问题。覆写应该保持 **里氏替换原则 (LSP)** —— 子类应该能在任何使用父类的地方无缝替代父类。

### 6.6 继承与访问修饰符的交互

继承关系中，访问修饰符决定了哪些成员能被子类访问：

```
┌─────────────────────────────────────────────────────┐
│                   父类 Person                        │
│                                                     │
│  public    name: string    ← 所有人都能看到          │
│  protected salary: number  ← 只有自己和子类能看到    │
│  private   ssn: string    ← 只有自己能看到          │
│                                                     │
│  ──────────────────────────────────────────────     │
│              ↓ extends                              │
│                                                     │
│              子类 Employee                           │
│                                                     │
│  ✅ 可以访问 name（public）                          │
│  ✅ 可以访问 salary（protected）                     │
│  ❌ 不能访问 ssn（private）                          │
└─────────────────────────────────────────────────────┘
```

```typescript
class Person {
  constructor(
    public name: string,         // 公开的 —— 任何地方都可以访问
    protected salary: number,     // 受保护的 —— 子类可以访问
    private ssn: string          // 私有的 —— 只有 Person 内部能访问
  ) {}

  showInfo(): string {
    return `${this.name}, 薪资 ¥${this.salary}, SSN: ${this.ssn}`;
  }
}

class Employee extends Person {
  constructor(
    name: string,
    salary: number,
    ssn: string,
    private bonus: number       // 子类自己的私有字段
  ) {
    super(name, salary, ssn);
  }

  // ✅ 子类可以访问 public 成员
  getName(): string {
    return this.name;
  }

  // ✅ 子类可以访问 protected 成员
  getTotalPay(): number {
    return this.salary + this.bonus;   // salary 是父类的 protected 字段
  }

  // ✅ 子类可以调用父类的公开方法（间接访问私有数据）
  getFullInfo(): string {
    return super.showInfo() + `, 奖金: ¥${this.bonus}`;
  }

  // ❌ 子类不能访问父类的私有成员
  // getSSN(): string {
  //   return this.ssn;   // 编译错误！ssn 是私有的
  // }
}

const emp = new Employee('张三', 15000, '110101***', 5000);

emp.getName();        // ✅ 张三（通过子类方法访问 public）
emp.getTotalPay();    // ✅ 20000（子类访问 protected salary + 子类私有 bonus）
emp.getFullInfo();    // ✅ 通过 super 方法间接访问所有数据
emp.name;             // ✅ 外部可以访问 public
// emp.salary;         // ❌ 外部不能访问 protected
// emp.ssn;            // ❌ 外部不能访问 private
```

**设计原则总结**：
- `public`：暴露给所有人使用的 API
- `protected`：留给子类扩展的 **钩子（hook）**
- `private`：内部实现细节，连子类都不应该知道

#### 理论深入：访问控制与"封装"的本质

**封装（Encapsulation）** 是 OOP 的三大支柱之一（另外两个是继承和多态）。但什么是"封装"？很多人误以为封装就是"把东西藏起来"。其实封装的核心含义是：

> **隐藏复杂性，暴露简洁性。**

就像你开车时不需要知道引擎怎么喷油点火——那些复杂机制被"封装"在方向盘和油门后面。你只需要知道"踩油门就加速"就够了。

继承体系中的三种修饰符，本质上是在回答 **"谁有权知道这个信息？"** 的问题：

```
private    → 只有我自己知道（比如我的日记本）
protected → 我和家人都知道（比如家里的保险柜密码）
public    → 所有人都可以知道（比如我的名字）
```

**实际项目中的设计策略**：

1. **字段几乎总是 private** —— 直接暴露字段会让外部代码与你的内部实现耦合。一旦你想改字段名或类型，所有用到的地方都要改。

2. **方法通常是 public** —— 方法代表对象能做什么，这是对外契约。

3. **protected 的黄金使用场景** —— 当你写一个框架/基类，预期别人来继承它时，把"扩展点"标记为 protected。这样子类可以访问必要的内部状态，而普通使用者不能。

```typescript
// 好的设计：protected 作为框架的"后门"
abstract class BaseWidget {
  private _state = {};           // 内部实现，谁都不让碰
  protected setState(key: string, value: any): void {   // 子类可以用的工具方法
    this._state[key] = value;
    this.render();             // 改了状态就重新渲染
  }
  
  abstract render(): void;      // 子类必须实现的接口
}
```

### 6.7 多层继承（继承链）

TypeScript（和 JavaScript）支持多层继承——子类的子类仍然是类：

```
Animal（动物）
  └── Mammal（哺乳动物）  extends Animal
        └── Dog（狗）      extends Mammal
              └── Labrador（拉布拉多）  extends Dog
```

```typescript
// 第一层：基础动物
class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
  breathe(): void { console.log(`${this.name} 在呼吸`); }
}

// 第二层：哺乳动物
class Mammal extends Animal {
  furColor: string;
  constructor(name: string, furColor: string) {
    super(name);
    this.furColor = furColor;
  }
  nurse(): void { console.log(`${this.name} 在哺乳幼崽`); }
}

// 第三层：犬科
class Canine extends Mammal {
  howl(): void { console.log(`${this.name}: 嗷~~~~~~🐺`); }
}

// 第四层：具体品种
class Labrador extends Canine {
  constructor(name: string, furColor: string = '黄色') {
    super(name, furColor);
  }
  fetch(): void { console.log(`${this.name} 高兴地去捡球了! 🎾`); }
  swim(): void { console.log(`${this.name} 喜欢游泳! 🏊`)`; }
}

// ====== 使用 ======
const labrador = new Labrador('小黑');

// Labrador 自己的方法
labrador.fetch();    // 小黑 高兴地去捡球了! 🎾
labrador.swim();     // 小黑 喜欢游泳! 🏊

// 继承自 Canine
labrador.howl();     // 小黑: 嗷~~~~~~🐺

// 继承自 Mammal
labrador.nurse();    // 小黑 在哺乳幼崽

// 继承自 Animal
labrador.breathe();  // 小黑 在呼吸

// 访问各层的字段
console.log(labrador.name);     // 小黑    ← Animal
console.log(labrador.furColor); // 黄色    ← Mammal
```

**注意**：JavaScript/TypeScript 只支持 **单继承**（一个类只能有一个直接父类），但可以通过多层继承形成长长的继承链。不过实际开发中，**超过 3 层的继承链通常意味着设计有问题**——优先考虑组合（Composition）。

#### 理论深入：多层继承的利与弊

**多层继承的好处**：

```
每一层都可以添加新的能力：
Animal    → 基本生命行为（吃、睡、动）
  Mammal   → 温血动物特性（哺乳、毛发）
    Canine  → 犬科特征（嗅觉灵敏、群居）
      Dog   → 家养狗（训练性、忠诚）
        Labrador → 具体品种（温顺、游泳）
```

这就像搭积木——每层都基于前一层往上叠加。代码复用率极高。

**多层继承的风险** —— "脆弱基类问题"（Fragile Base Class Problem）：

```
假设 Animal 有一个方法 changeName()
  Mammal 覆写了它，加了日志
    Canine 又覆写了它，转成大写
      Dog 再次覆写，做了格式校验

现在你想修改 Animal.changeName() 的基本逻辑 → 
  所有子类的覆写可能都会受影响！
因为很多子类的 super.changeName() 依赖父类的原始行为。
```

> **经验法则**：如果发现自己在写超过 4 层的继承链，停下来想想：这些类之间真的是 "is-a" 关系吗？还是可以用组合来解耦？

### 6.8 继承中的类型关系

这是 TypeScript 继承中最重要也最容易被忽略的部分：**继承即子类型化（Inheritance implies Subtyping）**。

```typescript
class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
}

class Dog extends Animal {
  breed: string;
  constructor(name: string, breed: string) {
    super(name);
    this.breed = breed;
  }
}

// ====== 核心规则：子类实例可以赋给父类类型的变量 ======

let animal: Animal = new Dog('旺财', '柴犬');  // ✅ 合法！

// 为什么？因为 Dog IS-A Animal（狗是一种动物）
// Dog 拥有 Animal 的所有成员，所以放在 Animal 类型的变量里完全没问题

animal.name;    // ✅ '旺财'
animal.breed;   // ❌ 编译错误！Animal 类型没有 breed 属性
                 // （虽然运行时实际上存在，但编译器只认 Animal 类型）

// ====== 反过来不行 ======

// let dog: Dog = new Animal('某动物');  // ❌ 编译错误！
// 动物不一定是狗，不能把父类实例赋给子类类型
```

#### 实际应用：多态（Polymorphism）

```typescript
// 利用"子类可以当作父类使用"的特性，写出通用代码
class Shape {
  constructor(public color: string) {}
  area(): number { return 0; }
  describe(): string { return `${this.color}色的形状` };
}

class Circle extends Shape {
  constructor(color: string, public radius: number) {
    super(color);
  }
  override area(): number { return Math.PI * this.radius ** 2; }
  override describe(): string { return `${this.color}圆形, r=${this.radius}`; }
}

class Rectangle extends Shape {
  constructor(color: string, public width: number, public height: number) {
    super(color);
  }
  override area(): number { return this.width * this.height; }
  override describe(): string { return `${this.color}矩形, ${this.width}×${this.height}`; }
}

class Triangle extends Shape {
  constructor(color: string, public base: number, public height: number) {
    super(color);
  }
  override area(): number { return 0.5 * this.base * this.height; }
  override describe(): string { return `${this.color}三角形` };
}

// ====== 关键：用父类类型接收所有子类实例 ======

const shapes: Shape[] = [
  new Circle('红', 5),
  new Rectangle('蓝', 10, 20),
  new Triangle('绿', 6, 4),
  new Circle('黄', 3),
];

// 通用处理函数——不需要知道具体是什么形状
function totalArea(shapes: Shape[]): number {
  let total = 0;
  for (const shape of shapes) {
    // 这里体现了多态：同一个方法调用，根据实际类型执行不同代码
    console.log(shape.describe(), `→ 面积: ${shape.area().toFixed(1)}`);
    total += shape.area();
  }
  return total;
}

totalArea(shapes);
// 红圆形, r=5 → 面积: 78.5
// 蓝矩形, 10×20 → 面积: 200.0
// 绿三角形 → 面积: 12.0
// 黄圆形, r=3 → 面积: 28.3
// 总面积: 318.8
```

**这就是继承的真正威力**——你可以编写 **不依赖具体类型** 的通用代码，通过多态让每个子类用自己的方式响应同一消息。

#### 理论深入：多态——OOP 的灵魂

**"多态"（Polymorphism）这个词来自希腊语：poly（多）+ morph（形态）= "多种形态"。**

它描述的是同一个接口/方法，在不同类型的对象上有不同的行为表现。继承是实现多态的 **主要手段之一**（但不是唯一手段，接口也能实现）。

**生活中的多态无处不在**：

```
你喊一声 "叫！" （同一个指令）
  → 狗：汪汪汪！     ← 不同反应
  → 猫：喵喵喵！     ← 不同反应
  → 鸭：嘎嘎嘎！     ← 不同反应

这就是多态 —— 同一个消息，不同的响应。
```

**代码中的价值**：

```typescript
// ❌ 没有多态的写法 —— 大量 if-else / switch-case
function makeSound(animal: any): void {
  if (animal.type === 'dog') {
    console.log('汪汪！');
  } else if (animal.type === 'cat') {
    console.log('喵喵！');
  } else if (animal.type === 'duck') {
    console.log('嘎嘎！');
  }
  // 每加一种动物，就要改这个函数！违反开闭原则
}

// ✅ 有多态的写法 —— 不需要知道具体类型
function makeSoundBetter(animal: Animal): void {
  // 只要知道 animal 能发出声音就行，具体怎么叫由它自己决定
  // 如果以后新增了 Cow 类，这个函数完全不用改！
}
```

**多态的三个要素**：
1. **继承关系**：子类可以当作父类使用
2. **方法覆写**：子类用自己的版本替换父类的方法
3. **父类型引用**：用父类类型的变量来引用子类实例

三者结合才能实现真正的多态。缺少任何一个都不行：
- 没有继承 → 无法统一引用不同类型
- 没有覆写 → 所有子类行为相同，没有差异化
- 不用父类引用 → 还是得针对每种类型写不同逻辑

#### 里氏替换原则 (LSP)

多态的理论基础是 **里氏替换原则（Liskov Substitution Principle, LSP）**：

> **如果 S 是 T 的子类型，那么程序中所有使用 T 对象的地方，都可以用 S 对象替换，而不会改变程序的正确性。**

换句话说：**子类必须在任何地方都能完美替代父类**。

违反 LSP 的例子：

```typescript
class Rectangle {
  constructor(public width: number, public height: number) {}
  setWidth(w: number): void { this.width = w; }
  setHeight(h: number): void { this.height = h; }
  getArea(): number { return this.width * this.height; }
}

// ❌ 违反 LSP！正方形不应该继承矩形
class Square extends Rectangle {
  constructor(side: number) { super(side, side); }
  
  override setWidth(w: number): void {
    this.width = w;
    this.height = w;   // 正方形：宽改了，高也要改！
  }
  
  override setHeight(h: number): void {
    this.height = h;
    this.width = h;   // 正方形：高改了，宽也要改！
  }
}

// 问题来了：
function processRect(r: Rectangle): void {
  r.setWidth(5);
  r.setHeight(10);       // 对于 Square，这行会把 width 也改成 10
  console.log(r.getArea());  // 期望 50，实际 100！💥
}

const sq = new Square(3);
processRect(sq);  // 行为异常！Square 不能安全替代 Rectangle
```

这就是为什么 `Square extends Rectangle` 是经典的 **反模式**。虽然直觉上"正方形是一种矩形"，但在可变对象的行为上它们不兼容。

#### instanceof 类型守卫

在需要区分具体子类型时，使用 `instanceof`：

```typescript
function processShape(shape: Shape): void {
  console.log(shape.describe());

  // instanceof 检查：缩小类型范围
  if (shape instanceof Circle) {
    // 这里 shape 的类型被收窄为 Circle
    console.log(`  直径: ${shape.radius * 2}`);
  } else if (shape instanceof Rectangle) {
    // 这里 shape 的类型被收窄为 Rectangle
    console.log(`  对角线: ${Math.sqrt(shape.width**2 + shape.height**2).toFixed(1)}`);
  } else {
    console.log(`  面积: ${shape.area()}`);
  }
}
```

### 6.9 继承 vs 组合——什么时候该用哪个？

这是一个经典的 OOP 设计问题。虽然继承很强大，但 **组合优于组合（Composition over Inheritance）** 是业界广泛认可的实践原则。

```typescript
// ====== 方案A：用继承 ======
// 问题：强行建立"is-a"关系，即使逻辑上并不合适

class Logger {
  log(msg: string): void { console.log(`[LOG] ${msg}`); }
}

// ❌ User "is-a" Logger? 用户不是日志器！语义不对
class User extends Logger {
  constructor(public name: string) { super(); }
  introduce(): string { return `我是 ${this.name}`; }
}


// ====== 方案B：用组合 ======
// ✅ User "has-a" Logger? 用户有一个日志功能。语义正确！

class BetterLogger {
  log(msg: string): void { console.log(`[LOG] ${msg}`); }
  error(msg: string): void { console.error(`[ERR] ${msg}`); }
}

class BetterUser {
  private logger: BetterLogger;   // 组合：持有一个 logger 实例

  constructor(
    public name: string,
    logger?: BetterLogger
  ) {
    this.logger = logger ?? new BetterLogger();
  }

  introduce(): string {
    this.logger.log(`${self.name} 进行了自我介绍`);
    return `我是 ${this.name}`;
  }
}
```

#### 选择指南

```
问自己一个问题：A 和 B 之间的关系是什么？

┌─────────────────────┬──────────────────┬──────────────────┐
│     A 和 B 的关系    │   使用继承        │   使用组合        │
├─────────────────────┼──────────────────┼──────────────────┤
│ A **是** 一种 B     │ ✅ 继承          │                  │
│   (is-a)            │ Dog extends      │                  │
│                      │ Animal          │                  │
├─────────────────────┼──────────────────┼──────────────────┤
│ A **有** 一个 B     │                  │ ✅ 组合           │
│   (has-a)           │                  │ Car has-a Engine │
├─────────────────────┼──────────────────┼──────────────────┤
│ A **像** B（行为）  │                  │ ✅ 接口 + 组合     │
│   (behaves-like)    │                  │ implements       │
└─────────────────────┴──────────────────┴──────────────────┘

✅ 用继承的场景：
  - 狗是动物 → Dog extends Animal ✓
  - 圆形是形状 → Circle extends Shape ✓
  - 错误是异常 → NotFoundError extends Error ✓

✅ 用组合的场景：
  - 汽车有引擎 → Car { engine: Engine } ✓
  - 用户有日志功能 → User { logger: Logger } ✓
  - 页面有路由 → Page { router: Router } ✓

#### 理论深入：继承 vs 组合的本质区别

**继承（Inheritance）** 是 **"是"关系（IS-A）** —— 编译期绑定，类型系统级别的：

```
class Dog extends Animal {
  // Dog 在编译时就被确定为 Animal 的子类
  // 这种关系写在代码里，无法在运行时改变
}
```

**组合（Composition）** 是 **"有"关系（HAS-A）** —— 运行时绑定，更灵活：

```typescript
class Dog {
  constructor(private behavior: Behavior) {}
  // behavior 可以在运行时替换！今天叫，明天可以学别的行为
}

const dog = new Dog(new BarkBehavior());
// 随时可以改变：
dog.setBehavior(new MeowBehavior());  // 理论上可行（如果设计允许）
```

**为什么 GoF（Gang of Four）说"优先用组合"？**

1. **灵活性**：组合可以在运行时改变组件；继承在编译时就固定了
2. **封装性更好**：组合只暴露你想暴露的接口；继承会把父类的所有 public/protected 成员都带过来
3. **避免脆弱基类问题**：修改父类可能破坏所有子类；组合中各组件独立变化
4. **更容易测试**：组合的组件可以单独 mock；继承的子类依赖父类的实现

> **但不要走极端**！继承不是毒药。当你的需求确实满足 "is-a" 关系、且不需要运行时灵活性的情况下，继承是最简洁、最直观的选择。TypeScript 的 `extends` 配合 `protected` 修饰符，在很多场景下非常好用。

**实际项目中的经验法则**：
- 写业务代码（页面/组件/服务）→ 多用组合
- 写基础库/框架（如 React.Component / Vue.Component）→ 继承很常见
- 写数据模型（Entity / DTO / VO）→ 看情况，两者皆可
```

### 6.10 构造函数签名的继承细节

当父类构造函数有参数时，子类构造函数的处理方式：

```typescript
class Base {
  a: number;
  b: string;

  constructor(a: number, b: string) {
    this.a = a;
    this.b = b;
  }
}

// ====== 模式1：子类构造函数接受更多参数 ======
class Child1 extends Base {
  c: boolean;

  constructor(a: number, b: string, c: boolean) {
    super(a, b);   // 把需要的参数传给父类
    this.c = c;    // 处理自己的参数
  }
}

// ====== 模式2：子类简化父类参数（提供默认值）=====
class Child2 extends Base {
  constructor(b: string) {
    super(42, b);   // 固定 a 的值
  }
}

// ====== 模式3：子类完全不新增参数 ======
class Child3 extends Base {
  constructor(a: number, b: string) {
    super(a, b);
    // 可能在这里做额外初始化
    console.log(`Child3 created with a=${a}, b=${b}`);
  }
}

// ====== 模式4：子类使用参数属性简化 ======
class Child4 extends Base {
  // 参数属性 + 继承的组合
  constructor(
    a: number,
    b: string,
    public extra: string   // 子类独有的参数属性
  ) {
    super(a, b);
    // extra 已自动赋值，不需要手动 this.extra = extra
  }
}
```

#### 理论深入：构造函数签名设计的考量

子类构造函数的参数设计是一个经常被忽视但又很重要的问题。一个好的构造函数设计应该遵循以下原则：

**1. 向后兼容**：
如果父类构造函数新增了可选参数，子类不应该被破坏。这就是为什么推荐把新增参数放在最后并设为默认值。

**2. 参数委托（Parameter Forwarding）模式**：

```typescript
class Base {
  constructor(
    public required: string,
    public optional?: string,
    public withDefault: string = 'hello'
  ) {}
}

// 好的设计：子类只关心自己新增的参数
class GoodChild extends Base {
  constructor(required: string, public childOnly: number) {
    super(required);   // 只传必要的，其他用默认值
  }
}

// 有问题的设计：子类必须了解父类的所有参数细节
class BadChild extends Base {
  constructor(
    required: string,
    optional: string | undefined,   // 必须知道父类有哪些参数
    withDefault?: string,            // 还要记住默认值是什么
    public childOnly: number
  ) {
    super(required, optional, withDefault);  // 繁琐且容易出错
  }
}
```

**3. 工厂方法替代复杂构造函数**：
当子类构造函数参数变得很复杂时，考虑使用静态工厂方法来简化对象的创建——这在后面的实战案例中已经展示过。

### 6.11 继承中的静态成员

静态成员也会被继承：

```typescript
class Base {
  static typeName: string = 'Base';

  static create(): Base {
    return new Base();
  }

  static info(): string {
    return `This is ${Base.typeName}`;
  }
}

class Derived extends Base {
  // 静态成员会被继承
  static typeName: string = 'Derived';   // 覆写静态属性

  static create(): Derived {             // 覆写静态方法
    return new Derived();
  }

  instanceMethod(): string {
    // 注意：这里访问的是 Derived 的静态成员（因为是通过 Derived 调用的）
    return `I'm a ${Derived.typeName}`;
  }
}

console.log(Base.typeName);      // 'Base'
console.log(Derived.typeName);   // 'Derived'（覆盖了父类的值）

const base = Base.create();
const derived = Derived.create();  // 返回的是 Derived 实例

console.log(derived.instanceMethod()); // I'm a Derived
```

#### 理论深入：静态成员继承的"陷阱"

静态成员虽然会被"继承"，但它的行为和实例成员有很大不同。理解这一点能帮你避免很多困惑：

**1. 静态属性是"按类共享"还是"各自独立"？**

```typescript
class Parent {
  static count: number = 0;   // 静态属性

  increment() { Parent.count++; }
}

class ChildA extends Parent {}
class ChildB extends Parent {}

ChildA.increment();
console.log(Parent.count);  // 1
console.log(ChildA.count);    // 1 ← 继承了！值相同

ChildB.increment();
console.log(Parent.count);  // 2
console.log(ChildA.count);    // 2 ← 也变了！因为引用的是同一个
```

**关键发现**：子类继承的静态属性，实际上是指向 **同一个值的引用**（对于原始类型会有拷贝行为，但对于对象则是同一引用）。修改任何一个都会影响所有。

**2. 静态方法中的 `this` 指向什么？**

```typescript
class Parent {
  name = 'Parent';
  
  static whoAmI(): string {
    // 注意：在静态方法中 this 指向构造函数本身！
    return this.name;
  }
}

class Child extends Parent {
  static name = 'Child';
}

console.log(Parent.whoAmI());  // 'Parent'
console.log(Child.whoAmI());   // 'Child' ← 各自看到自己的名字
```

**3. 实际应用场景：工厂方法模式 + 继承**

静态成员 + 继承的一个经典用法是 **工厂方法的层级化**：

```typescript
abstract class Database {
  abstract query(sql: string): Promise<any[]>;
  
  // 静态工厂 —— 子类可以覆写来创建不同类型的连接
  static async connect(config: any): Promise<Database> {
    throw new Error('Subclass must implement connect()');
  }
  
  static async executeQuery(sql: string, config: any): Promise<any[]> {
    const db = await this.connect(config);
    return db.query(sql);
  }
}

class MySQL extends Database {
  constructor(private connection: any) { super(); }
  
  static async connect(config: any): Promise<MySQL> {
    const conn = await mysql.createConnection(config);
    return new MySQL(conn);
  }
  
  async query(sql: string): Promise<any[]> {
    return this.connection.execute(sql);
  }
}

// 使用：不需要知道具体是哪个数据库类
const results = await Database.executeQuery('SELECT * FROM users', mysqlConfig);
```

### 6.12 实战案例：完整的继承体系设计

下面用一个真实项目中常见的例子——**组件库的按钮体系**——来展示继承的综合运用：

```typescript
// ==================== 基础组件 ====================
abstract class UIComponent {
  // 所有 UI 组件的公共属性
  id: string;
  className: string = '';
  styles: Record<string, string> = {};
  isVisible: boolean = true;

  constructor(id: string) {
    this.id = id;
  }

  // 公共方法
  show(): void { this.isVisible = true; }
  hide(): void { this.isVisible = false; }
  toggle(): void { this.isVisible = !this.isVisible; }

  addClass(cls: string): void {
    this.className += ` ${cls}`.trim();
  }

  setStyle(key: string, value: string): void {
    this.styles[key] = value;
  }

  // 抽象方法：每个子类必须实现自己的渲染逻辑
  abstract render(): string;
}

// ==================== 交互型组件 ====================
abstract class InteractiveComponent extends UIComponent {
  disabled: boolean = false;
  loading: boolean = false;

  enable(): void { this.disabled = false; }
  disable(): void { this.disabled = true; }
  setLoading(isLoading: boolean): void { this.loading = isLoading; }

  // 抽象事件处理
  abstract handleClick(): void;
}

// ==================== 具体组件：按钮 ====================
class Button extends InteractiveComponent {
  label: string;
  variant: 'primary' | 'secondary' | 'danger' = 'primary';
  size: 'sm' | 'md' | 'lg' = 'md';

  constructor(id: string, label: string) {
    super(id);
    this.label = label;
  }

  handleClick(): void {
    if (this.disabled || this.loading) return;
    console.log(`Button [${this.id}]: "${this.label}" clicked!`);
  }

  render(): string {
    const classes = [
      'btn',
      `btn-${this.variant}`,
      `btn-${this.size}`,
      this.disabled ? 'disabled' : '',
      this.loading ? 'loading' : '',
      !this.isVisible ? 'hidden' : '',
    ].filter(Boolean).join(' ');

    const loadingIcon = this.loading ? '⏳ ' : '';
    return `<button id="${this.id}" class="${classes}">${loadingIcon}${this.label}</button>`;
  }
}

// ==================== 具体组件：图标按钮 ====================
class IconButton extends Button {
  icon: string;
  iconPosition: 'left' | 'right' = 'left';

  constructor(id: string, label: string, icon: string) {
    super(id, label);
    this.icon = icon;
  }

  render(): string {
    // 调用父类的 render 获取基础 HTML
    const baseHtml = super.render();
    // 在此基础上修改（简化演示）
    const iconEl = `<span class="icon">${this.icon}</span>`;
    const content = this.iconPosition === 'left'
      ? `${iconEl} ${this.label}`
      : `${this.label} ${iconEl}`;
    return baseHtml.replace(this.label, content).trim();
  }
}

// ==================== 具体组件：提交按钮（带确认）====================
class SubmitButton extends Button {
  confirmMessage: string;
  requiresConfirm: boolean = false;

  constructor(id: string, label: string, confirmMessage?: string) {
    super(id, label);
    this.confirmMessage = confirmMessage || `确定要${label}吗？`;
    this.requiresConfirm = !!confirmMessage;
  }

  handleClick(): void {
    if (this.requiresConfirm && this.disabled || this.loading) return;
    if (this.requiresConfirm) {
      const confirmed = window.confirm(this.confirmMessage);
      if (!confirmed) return;
    }
    console.log(`SubmitButton [${this.id}]: 表单已提交！`);
    super.handleClick();  // 调用父类的点击处理
  }
}

// ==================== 使用 ====================
const submitBtn = new SubmitButton('submit-form', '提交表单', '确定提交吗？数据不可恢复');
submitBtn.setStyle('marginTop', '10px');
submitBtn.addClass('form-button');

console.log(submitBtn.render());
// <button id="submit-form" class="btn btn-primary btn-md form-button" style="margin-top:10px">提交表单</button>

submitBtn.handleClick();
// 弹出确认框 → 确认后输出：SubmitButton [submit-form]: 表单已提交！

// 多态使用：所有组件都可用 UIComponent 类型引用
const components: UIComponent[] = [
  new Button('btn1', '普通按钮'),
  new IconButton('btn2', '保存', '💾'),
  new SubmitButton('btn3', '删除', '确定要删除吗？'),
];

components.forEach(comp => comp.render());  // 多态调用
components.forEach(comp => comp.hide());    // 都能隐藏
```

#### 理论深入：这个实战案例体现了哪些设计模式？

这个 UI 组件继承体系其实暗含了多个经典设计模式：

**1. 模板方法模式（Template Method Pattern）**

```
UIComponent 定义了 render() 作为抽象方法（模板中的"空缺"）
InteractiveComponent 在中间层添加了通用逻辑
具体组件（Button/IconButton）填充最终实现

这就像填空题：父类出题（留空），子类答题（填空）
```

**2. 装饰器模式的简化版（Decorator-like）**

`IconButton` 和 `SubmitButton` 都通过覆写 `render()` 和 `handleClick()` 来"装饰"原始 Button 的行为，而不需要修改 Button 本身的代码。这就是开闭原则的体现。

**3. 组合 + 继承的混合使用**

注意这个案例中：
- 继承：Button extends InteractiveComponent → 复用代码
- 组合：Button 内部持有 label、variant 等（字段组合）

两者不是互斥的——实际项目中经常混合使用。

### 6.13 继承的常见陷阱与避坑指南

#### 陷阱 1：覆写时改变了方法的返回类型

```typescript
class Parent {
  getValue(): number { return 42; }
}

class Child extends Parent {
  // ❌ 不能把返回值改成不兼容的类型
  // getValue(): string { return 'hello'; }  // 编译错误！

  // ✅ 但可以返回更具体的类型（协变 covariant）
  // getValue(): 42 { return 42; }  // 字面量类型，是 number 的子类型
}
```

#### 陷阱 2：构造函数中 super() 之前的字段初始化问题

```typescript
class Base {
  x: string = 'base';
  constructor() {
    console.log(`Base: x = ${this.x}`);  // 打印什么？
  }
}

class Derived extends Base {
  x: string = 'derived';  // 这会在 super() 之后执行
  constructor() {
    super();  // 先执行父类构造函数，此时 x 还是 'base'！
    console.log(`Derived: x = ${this.x}`);  // 这里才是 'derived'
  }
}

const d = new Derived();
// 输出：
// Base: x = base        ← super() 时，子类字段尚未初始化
// Derived: x = derived  ← super() 之后，子类字段才初始化
```

**教训**：不要在父类构造函数里依赖子类的字段值，因为此时它们还没初始化。

#### 陷阱 3：覆写方法时丢失了父类行为

```typescript
class Counter {
  private count: number = 0;

  increment(): void {
    this.count++;
    console.log(`count = ${this.count}`);
  }
}

class LoggedCounter extends Counter {
  override increment(): void {
    console.log('Before increment');  // 加了日志
    // 忘记调用 super.increment()！父类的计数逻辑丢了！
    console.log('After increment');
  }
}

const lc = new LoggedCounter();
lc.increment();
lc.increment();
// Before increment
// After increment
// Before increment
// After increment
// count 永远是 0！因为父类的 increment() 从未被调用

// ✅ 正确做法
class FixedLoggedCounter extends Counter {
  override increment(): void {
    console.log(`Before: about to increment`);
    super.increment();   // 别忘了调用父类方法！
    console.log(`After: done`);
  }
}
```

#### 陷阱 4：不要滥用继承

```typescript
// ❌ 滥用继承：ArrayList 继承了 Array
// 问题：ArrayList 的所有方法都被暴露了，有些可能不安全
class ArrayList<T> extends Array<T> {
  // 继承了 Array 的所有方法，包括 splice、pop 等
  // 用户可以直接 arr.pop() 绕过你的封装
}

// ✅ 更好的做法：组合
class BetterArrayList<T> {
  private items: T[] = [];  // 内部持有数组，但不暴露

  add(item: T): void { this.items.push(item); }
  get(index: number): T | undefined { return this.items[index]; }
  size(): number { return this.items.length; }
  // 只暴露你想暴露的操作
}
```

#### 陷阱 5：循环依赖的初始化

```typescript
class Parent {
  child: Child;

  constructor() {
    this.child = new Child(this);  // Parent 需要 Child 的实例
  }
}

class Child extends Parent {
  constructor(parent: Parent) {
    super();  // 但 Child 构造函数需要先调 super() → Parent 又需要 Child
    // 💥 无限递归！Stack Overflow!
  }
}

// ✅ 解决方案1：延迟初始化
class FixedParent {
  child: Child | null = null;
  
  constructor() {
    // 不在构造函数中创建 Child
  }
  
  initChild(): void {
    this.child = new Child(this as any);
  }
}

// ✅ 解决方案2：使用依赖注入
class BetterChild extends Parent {
  constructor(private parent: Parent) {
    super();
    // parent 是从外部传入的，不是在这里创建的
  }
}
```

#### 陷阱 6：覆写 getter/setter 时的意外行为

```typescript
class BankAccount {
  protected _balance: number = 0;
  
  get balance(): number { return this._balance; }
  
  set balance(v: number) {
    if (v < 0) throw new Error('余额不能为负数');
    this._balance = v;
  }
}

class OverdraftAccount extends BankAccount {
  overdraftLimit: number = 1000;
  
  override get balance(): number {
    return this._balance + this.overdraftLimit;   // 虚拟透支额度
  }
  
  // ❌ 忘记覆写 setter！
  // set balance(v: number) { ... } 没写 → 使用父类的 setter
  // 父类 setter 会检查 v >= 0
  // 但子类 getter 返回的是 balance + overdraft（可能 > 0）
  // 导致逻辑不一致！
}
```

> **教训**：如果覆写了 getter，通常也需要检查是否应该同步覆写 setter。TypeScript 不会提醒你这个——因为它们在类型系统中是两个独立的方法。

#### 陷阱 7：私有字段不会真正被"继承"

```typescript
class SecretHolder {
  private secret = 'I am a secret';
  
  revealSecret(): string { return this.secret; }  // 唯一的访问方式
}

class Spy extends SecretHolder {
  stealSecret(): string {
    // return this.secret;  // ❌ 编译错误！private 对子类也不可见
    // 即使你是子类也不能直接访问父类的 private 成员
    // 这与 C++/Java 的 private 行为不同！
    return this.revealSecret();  // ✅ 只能通过公开方法间接获取
  }
}
```

**记住 TypeScript 中 `private` 的真正含义是"类级别私有"，而不是"实例级别私有"。同一个类的不同实例之间可以互相访问对方的 private 成员。

#### 理论深入：TypeScript 继承的编译输出

你可能好奇：TypeScript 的继承代码编译成 JavaScript 后长什么样？

```typescript
// TypeScript 源码
class Animal {
  name: string;
  constructor(name: string) { this.name = name; }
  greet() { return `I'm ${this.name}`; }
}

class Dog extends Animal {
  breed: string;
  constructor(name: string, breed: string) {
    super(name);
    this.breed = breed;
  }
  override greet() { return `Woof! I'm ${this.name} the ${this.breed}`; }
  bark() { console.log('Woof!'); }
}
```

编译后（ES5 target）：

```javascript
// 编译后的 JavaScript —— 使用 __extends 帮助函数
var __extends = (this && this.__extends) || function (d, b) {
  // 设置原型链
  for (var p in b) if (b.hasOwnProperty(p)) d[p] = b[p];
  function __( ) { this.constructor = d; }
  d.prototype = b === null ? Object.create(b) : (__.prototype = b.prototype, new __());
};

var Animal = (function () {
  function Animal(name) {
    this.name = name;           // 字段声明变成了构造函数中的赋值
  }
  Animal.prototype.greet = function () {   // 方法放到原型上（节省内存）
    return "I'm " + this.name;
  };
  return Animal;
})();

var Dog = (function (__super) {
  // Dog.prototype.__proto__ === Animal.prototype（原型链）
  // Dog.prototype.constructor === Dog
  __extends(Dog, __super);
  
  function Dog(name, breed) {
    // super(name) 变成了 __super.call(this, name)
    // 用父类构造函数来初始化 this
    __super.call(this, name);
    this.breed = breed;
  }
  // 親写的方法直接在 Dog.prototype 上重新定义
  Dog.prototype.greet = function () {     // 覆盖了父类的 greet
    return "Woof! I'm " + this.name + " the " + this.breed;
  };
  Dog.prototype.bark = function () {       // 子类新增的方法
    console.log("Woof!");
  };
  return Dog;
})(Animal);  // 立即执行，传入父类作为参数
```

**关键观察**：
1. **`extends` 关键字被编译为原型链操作**：`Dog.prototype.__proto__ = Animal.prototype`
2. **方法都挂载在 prototype 上**，而不是每个实例一份——这是为了内存效率
3. **`super()` 变成了 `ParentClass.call(this, ...)`** —— 在子类实例的上下文中调用父类构造函数
4. **字段声明变成了构造函数中的赋值语句**

> 这就是为什么说 TypeScript 类是"语法糖"——它让你用更清晰的语法写出底层基于原型的 JavaScript 代码。理解编译产物有助于你 debug 复杂继承问题。

#### 理论深入：Mixins —— 模拟多重继承

由于 JavaScript 只支持单继承，当你需要从多个"来源"获取能力时，可以用 Mixin 模式：

```typescript
// Mixin 是一个函数，接收一个类，返回一个扩展后的新类
function Timestamped<TBase extends new (...args: any[]) => any>(Base: TBase) {
  return class extends Base {
    timestamp = new Date();
    getAge(): number {
      return Date.now() - this.timestamp.getTime();
    }
  };
}

function Serializable<TBase extends new (...args: any[]) => any>(Base: TBase) {
  return class extends Base {
    serialize(): string {
      return JSON.stringify(this);
    }
  };
}

// 组合使用多个 mixin
const EnhancedUser = Timestamped(Serializable(class User {
  constructor(public name: string) { super(); }
  greet() { return `Hi, I'm ${this.name}`; }
}));

const user = new EnhancedUser('Alice');
console.log(user instanceof User);        // true
console.log(user.getAge());             // 时间差（毫秒）
console.log(user.serialize());          // JSON 字符串
```

Mixin 本质上是用高阶函数模拟多继承的效果。Vue 2 的组件就大量使用了这种模式。

### 6.14 个人总结：关于继承的核心认知

1. **继承的本质是类型关系的建立**：`Dog extends Animal` 不仅意味着 Dog 复用了 Animal 的代码，更重要的是它在类型系统中建立了 **Dog 是 Animal 子类型** 的关系。这影响了赋值、函数参数匹配等一切类型相关操作。

2. **super() 是桥梁**：它连接了父子两代构造函数。记住它的两个角色——`super(..)` 初始化父类部分，`super.method()` 复用父类行为。

3. **覆写 != 替换（除非你要完全替代）**：好的覆写通常是"增强"而非"覆盖"。先用 `super.` 调用父类逻辑，再追加子类特有逻辑。这样当父类行为变化时，子类自动受益。

4. **组合 > 继承**：能用组合解决的问题就不要用继承。继承是最强的耦合关系（is-a），而组合是更灵活的关系（has-a）。当你犹豫时，选组合。

5. **继承链不要太长**：超过 3 层的继承链通常是设计问题的信号。每增加一层，理解和维护的成本就指数级增长。扁平优于嵌套。

6. **protected 是继承的灵魂**：如果没有 `protected` 修饰符，子类和外部使用者没有任何区别，继承的意义大打折扣。`protected` 为子类提供了专有的扩展点。

- 但所有人都受宪法保护——这就是继承的威力。

## 七、getter/setter 访问器

TypeScript 支持 ECMAScript 的 getter/setter 语法，允许你对属性的读写进行拦截和控制：

```typescript
class Temperature {
  private _celsius: number = 0;

  // getter —— 读取时调用
  get celsius(): number {
    return this._celsius;
  }

  // setter —— 写入时调用
  set celsius(value: number) {
    if (value < -273.15) {
      throw new Error('温度不能低于绝对零度 (-273.15°C)');
    }
    this._celsius = value;
  }

  // 计算属性 —— 华氏度（基于摄氏度换算）
  get fahrenheit(): number {
    return this._celsius * 9 / 5 + 32;
  }

  set fahrenheit(value: number) {
    this.celsius = (value - 32) * 5 / 9;  // 复用 celsius setter 的校验逻辑
  }
}

const temp = new Temperature();

temp.celsius = 25;           // ✅ 设置摄氏度
console.log(temp.celsius);   // 25
console.log(temp.fahrenheit); // 77（自动计算）

temp.fahrenheit = 100;       // ✅ 通过华氏度设置
console.log(temp.celsius);   // 37.777...

temp.celsius = -300;         // ❌ 抛出错误：温度不能低于绝对零度
```

## 八、静态成员（static）

静态成员属于**类本身**而不是实例，通过类名直接访问：

```typescript
class MathUtil {
  // 静态属性
  static PI: number = Math.PI;
  static E: number = Math.E;
  static counter: number = 0;

  // 静态方法
  static max(a: number, b: number): number {
    return a > b ? a : b;
  }

  static min(a: number, b: number): number {
    return a < b ? a : b;
  }

  static clamp(value: number, min: number, max: number): number {
    return MathUtil.max(min, MathUtil.min(value, max));
  }

  // 静态方法也可以返回实例
  static createIdentityMatrix(size: number): number[][] {
    const matrix: number[][] = [];
    for (let i = 0; i < size; i++) {
      matrix[i] = [];
      for (let j = 0; j < size; j++) {
        matrix[i][j] = i === j ? 1 : 0;
      }
    }
    return matrix;
  }
}

// 使用静态成员——通过类名访问，不需要 new
MathUtil.PI;                              // 3.14159...
MathUtil.max(10, 20);                     // 20
MathUtil.clamp(-5, 0, 100);               // 0
MathUtil.createIdentityMatrix(3);         // [[1,0,0],[0,1,0],[0,0,1]]

// 静态属性是共享的
MathUtil.counter++;     // 1
MathUtil.counter++;     // 2
```

## 九、抽象类（abstract class）

抽象类是不能被直接实例化的类，它作为其他类的**模板**存在：

```typescript
// abstract 关键字声明抽象类
abstract class Shape {
  // 普通字段
  color: string;

  constructor(color: string) {
    this.color = color;
  }

  // 普通方法——已有实现
  describe(): string {
    return `这是一个${this.color}色的图形`;
  }

  // 抽象方法——只有签名，没有实现
  // 子类必须实现所有抽象方法
  abstract area(): number;
  abstract perimeter(): number;
}

// ❌ 不能实例化抽象类
// const shape = new Shape('red'); // 错误：无法创建抽象类的实例

// 具体子类必须实现所有抽象方法
class Circle extends Shape {
  constructor(color: string, public radius: number) {
    super(color);
  }

  area(): number {                  // 实现抽象方法
    return Math.PI * this.radius ** 2;
  }

  perimeter(): number {             // 实现抽象方法
    return 2 * Math.PI * this.radius;
  }
}

class Rectangle extends Shape {
  constructor(
    color: string,
    public width: number,
    public height: number
  ) {
    super(color);
  }

  area(): number {
    return this.width * this.height;
  }

  perimeter(): number {
    return 2 * (this.width + this.height);
  }
}

// 使用
const circle = new Circle('蓝色', 5);
console.log(circle.area());        // 78.54...
console.log(circle.describe());    // 这是一个蓝色的图形（继承的方法）

const rect = new Rectangle('绿色', 10, 20);
console.log(rect.area());          // 200
console.log(rect.perimeter());     // 60
```

### 抽象类 vs 接口的选择

| 特征 | 抽象类 (`abstract class`) | 接口 (`interface`) |
|------|--------------------------|-------------------|
| 能否包含实现代码 | ✅ 可以 | ❌ 不能（TS 接口纯类型） |
| 能否包含构造函数 | ✅ 可以 | ❌ 不能 |
| 能否实例化 | ❌ 不能 | ❌ 不能 |
| 能否被 `implements` | ✅ 可以 | ✅ 本身就是 |
| 能否被 `extends` | ✅ 可以 | ✅ 接口可以 extends 接口 |
| 一个类可以实现多少个 | 只能 extends 一个 | 可以 implements 多个 |
| 适用场景 | 有共同实现的基类 | 纯契约/规范 |

**选择建议**：
- 如果多个类共享一些**实现代码**→ 用抽象类
- 如果只需要定义**契约/形状**→ 用接口
- 实际开发中经常两者结合：接口定义契约 + 抽象类提供部分实现

    this.items.push(item);

## 十二、implements 实现接口

类可以使用 `implements` 关键字来实现一个或多个接口，强制自己满足接口的契约：

```typescript
// 定义接口——"合同"
interface Drawable {
  draw(ctx: CanvasRenderingContext2D): void;
}

interface Resizable {
  resize(scaleX: number, scaleY: number): void;
}

interface HasPosition {
  x: number;
  y: number;
}

// 类实现接口——履行"合同"
class Circle implements Drawable, Resizable, HasPosition {
  x: number;
  y: number;
  radius: number;

  constructor(x: number, y: number, radius: number) {
    this.x = x;
    this.y = y;
    this.radius = radius;
  }

  // 实现 Drawable 接口
  draw(ctx: CanvasRenderingContext2D): void {
    ctx.beginPath();
    ctx.arc(this.x, this.y, this.radius, 0, Math.PI * 2);
    ctx.fill();
  }

  // 实现 Resizable 接口
  resize(scaleX: number, scaleY: number): void {
    this.radius *= (scaleX + scaleY) / 2;
  }
}

// 如果漏实现了接口要求的方法，TS 会报错：
// class BadCircle implements Drawable {
//   // ❌ 缺少 draw 方法
// }
```

## 十三、完整实战：User 类设计

让我们用一个综合性的例子串联以上所有知识点：

```typescript
/**
 * 用户模型 —— 综合运用类的各项特性
 */

// ====== 类型定义 ======
type UserRole = 'admin' | 'editor' | 'viewer';

type UserStatus = 'active' | 'inactive' | 'suspended';

interface IUser {
  readonly id: string;
  name: string;
  email: string;
  role: UserRole;
  status: UserStatus;
  createdAt: Date;
}

// ====== 抽象基类 ======
abstract class BaseEntity {
  constructor(
    public readonly id: string,
    public readonly createdAt: Date = new Date()
  ) {}

  abstract validate(): string[];
  
  getAgeInDays(): number {
    const now = new Date();
    return Math.floor((now.getTime() - this.createdAt.getTime()) / (1000 * 60 * 60 * 24));
  }
}

// ====== 用户类 ======
class User extends BaseEntity implements IUser {
  // 私有字段——封装敏感操作
  private _passwordHash: string;
  private _loginAttempts: number = 0;
  private _lastLoginAt: Date | null = null;

  constructor(
    id: string,
    public name: string,
    public email: string,
    passwordHash: string,
    public role: UserRole = 'viewer',
    public status: UserStatus = 'active'
  ) {
    super(id);
    this._passwordHash = passwordHash;
  }

  // Getter / Setter
  get passwordHash(): string {
    throw new Error('不允许直接读取密码哈希');
  }

  get lastLoginAt(): Date | null {
    return this._lastLoginAt;
  }

  // 方法
  validate(): string[] {
    const errors: string[] = [];
    
    if (!this.name || this.name.length < 2) {
      errors.push('用户名至少需要 2 个字符');
    }
    
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (!emailRegex.test(this.email)) {
      errors.push('邮箱格式无效');
    }
    
    return errors;
  }

  login(passwordHash: string): boolean {
    if (this.status !== 'active') {
      throw new Error(`账户状态为 ${status}，无法登录`);
    }

    if (passwordHash !== this._passwordHash) {
      this._loginAttempts++;
      if (this._loginAttempts >= 5) {
        this.status = 'suspended';
        throw new Error('登录失败次数过多，账户已锁定');
      }
      return false;
    }

    this._loginAttempts = 0;
    this._lastLoginAt = new Date();
    return true;
  }

  changeRole(newRole: UserRole, adminPassword: string): void {
    // 这里应该验证管理员权限...
    this.role = newRole;
    console.log(`${this.name} 的角色已更改为 ${newRole}`);
  }

  // 静态工厂方法
  static createAdmin(name: string, email: string, passwordHash: string): User {
    return new User(generateId(), name, email, passwordHash, 'admin');
  }

  static createViewer(name: string, email: string, passwordHash: string): User {
    return new User(generateId(), name, email, passwordHash, 'viewer');
  }
}

// ====== 使用 ======
const admin = User.createAdmin('管理员', 'admin@example.com', 'hashed_password_123');
console.log(admin.role);           // 'admin'
console.log(admin.validate());     // [] （无错误）

admin.login('wrong_password');     // false
admin.login('wrong_password2');    // false
admin.login('hashed_password_123'); // true
console.log(admin.lastLoginAt);    // 当前时间

const viewer = User.createViewer('访客', 'viewer@test.com', 'hash_456');
console.log(viewer.getAgeInDays()); // 0（刚创建）
```

## 十四、常见问题与坑点

### 14.1 初始化顺序

```typescript
class Base {
  name = 'base';
  constructor() {
    console.log(this.name); // 先打印自己的 name
  }
}

class Derived extends Base {
  name = 'derived';
  constructor() {
    super();        // ⚠️ super() 先执行，此时 name 还是 'base'！
    console.log(this.name); // 这里才是 'derived'
  }
}

const d = new Derived();
// 输出：base（super 时）
// 输出：derived（之后）
```

**规则**：JavaScript 规定 `super()` 必须在 `this` 访问之前调用，而基类构造函数执行时，子类的字段尚未初始化。

### 14.2 this 在回调中的丢失

前面已经提过，这里再强调一个常见场景：

```typescript
class EventEmitter {
  private handlers: Map<string, Function[]> = new Map();

  on(event: string, handler: Function): this {
    const handlers = this.handlers.get(event) || [];
    handlers.push(handler);
    this.handlers.set(event, handlers);
    return this;
  }

  emit(event: string, ...args: any[]): void {
    const handlers = this.handlers.get(event) || [];
    handlers.forEach(handler => handler(...args));
  }
}

// ❌ 危险用法
class MyApp {
  constructor(private emitter: EventEmitter) {
    emitter.on('click', this.handleClick); // this 可能丢失！
  }

  handleClick() {
    console.log('clicked!');
  }
}

// ✅ 安全做法
class SafeApp {
  constructor(private emitter: EventEmitter) {
    // 方案1：箭头函数包装
    emitter.on('click', () => this.handleClick());

    // 方案2：bind
    emitter.on('click', this.handleClick.bind(this));
  }

  handleClick = () => {  // 方案3：箭头函数字段
    console.log('clicked!');
  };
}
```

## 十五、个人总结与心得

学完 TypeScript 的类，我有几点深刻体会：

1. **TypeScript 让类变得"可信"**：纯 JavaScript 的类全靠自觉——该私有的属性谁都能改、该必填的参数可能没传。TypeScript 用类型系统和访问修饰符把这些"约定"变成了"规则"，违反就报错。

2. **参数属性是效率神器**：`constructor(public name: string)` 这一行替代了三行样板代码。刚开始可能觉得奇怪，习惯了之后真的回不去。

3. **组合优于继承是真理**：虽然 TypeScript 的继承体系很完善，但在实际项目中，组合（Composition）往往比继承更灵活。能用 `interface + implements` 解决的问题就不一定要用 `extends`。

4. **抽象类是"半成品工厂"**：它既提供了公共实现（比接口强），又强制子类完成特定行为（比普通类严格）。在设计框架或基础库时特别好用。

5. **类也是类型**：不要忘记类名本身就是一种类型。这意味着你可以把类用在变量声明、函数参数、泛型约束等各种需要类型的地方。这种"值与类型统一"的设计让 TypeScript 的类型系统更加一致和优雅。
