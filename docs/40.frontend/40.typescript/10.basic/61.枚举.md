## 什么是枚举（Enum）

想象你在一家餐厅点菜，菜单上写着「小份、中份、大份」。你不会说"我要 1 号"、"我要 2 号"——你会用**有名字的选项**来交流。枚举（Enum）就是编程世界里的这种"有名字的选项集合"。

**枚举 = 一组命名常量的集合。**

### 为什么叫"枚举"？——词源与本质

"枚举"这个词来自中文"逐一列举"的意思，对应的英文 Enumerate 是"数/列"的意思。在编程语境中，它的核心思想是：**把所有可能的情况一一列举出来，不允许超出这个范围。**

这和数学中的"集合穷举"是同一思维——如果你能明确列出所有可能的值，那就用枚举来约束它。

> **更深层理解**：枚举的本质是一种 **"封闭域"（Closed Domain）** 的声明方式。
>
> - **开放域**（Open Domain）：比如 `number` 类型——有无穷多个可能的值，你无法全部列举
> - **封闭域**（Closed Domain）：比如"一周的星期几"——只有周一到周日这 7 种可能，完全可以枚举出来
>
> 当你在编程中发现自己在用 if-else 或 switch 处理一组有限的、已知的选项时，这就是一个信号：**这里应该用枚举。**

### 枚举解决了什么问题？

在 JavaScript 中，我们通常用普通对象或纯字符串来表示一组固定的值。但这种方式有两个根本性的缺陷：

**缺陷一：没有类型安全（编译时无法拦截错误）**

你可以传入任意字符串，即使拼写错了编译器也不会拦住你。就像你给餐厅服务员说"我要大份大份份"——服务员虽然会觉得奇怪，但不会阻止你这么说。只有在真正执行的时候才会发现问题。

**缺陷二：语义分散（值和含义没有绑定）**

当你写 `if (status === 'active')` 时，`'active'` 这个字符串本身不携带任何上下文信息。它只是一个裸字符串，读者不知道它还有哪些合法的兄弟值（`inactive`? `pending`? `deleted`?）。你必须去翻代码或文档才能知道完整的选项列表。

而枚举把**所有选项集中声明在一个地方**——这就是所谓的 **"单一真相源"（Single Source of Truth）**。任何需要了解有哪些可选值的人，只需要看枚举定义就够了。

### 枪举在编程史上的位置

枚举并不是 TypeScript 发明的。它在编程语言中的历史可以追溯到 20 世纪 50 年代的 Fortran，后来 C 语言用 `#define` 和 `enum` 引入了这个概念，C++、Java、C#、Swift、Rust 等语言都有完善的枚举实现。

TypeScript 的 enum 设计主要借鉴了 **C#**（因为 TS 的主设计师 Anders Hejlsberg 也是 C# 的之父），所以你会发现 TS 的枚举行为和 C# 非常相似。

> **有趣的事实**：JavaScript 曾经有一个提案要给 JS 加上原生的 enum 语法（Stage 1），但因为社区分歧太大而被搁置了。主流观点是 JS 应该保持简单，类型的事情交给 TypeScript 就好。这也是为什么 enum 是 TS 的独占语法而不是标准 JS 的一部分。

```typescript
enum Direction {
  Up,      // 自动赋值为 0
  Down,    // 自动赋值为 1
  Left,    // 自动赋值为 2
  Right    // 自动赋值为 3
}

// 类型安全：只能用 Direction 的成员
let d: Direction = Direction.Up   // ✅
d = 99                             // ❌ Error: 不能将类型 "number" 分配给类型 "Direction"
d = 'Up'                           // ❌ Error: 不能将类型 "string" 分配给类型 "Direction"
```

## 数字枚举（Numeric Enum）

数字枚举是最常见的枚举形式，也是 TypeScript 枚举的默认行为。

### 基本用法

**生活类比**：就像军队的军衔——列兵(0)、士官(1)、尉官(2)、校官(3)。每个级别都有一个对应的数字编号。编号本身没有特殊含义，只是用来区分不同级别。

如果不指定值，TypeScript 会从 **0 开始自动递增赋值**。这个设计来自 C 语言的惯例——在 C 语言中，枚举默认从 0 开始，因为 0 在底层表示中是"最自然"的起始值（对应内存地址偏移、数组下标等概念）。

> **为什么默认从 0 开始？**
>
> 这不是随意的决定。计算机科学中大量基础概念都以 0 为起点：数组第一个元素的下标是 0、一周的第一天在很多系统中是 0、二进制最低位是第 0 位……
>
> 从 0 开始的枚举值天然适合做**数组索引**和**位标志（bit flag）**操作。如果你不需要映射到外部系统（比如 HTTP 状态码），保持默认的 0 起始通常是最省心的选择。

### 手动赋值的深层含义

你可以手动指定起始值或每个成员的值。这不仅仅是"改个数字"那么简单——手动赋值的灵活性让枚举可以**桥接到真实世界的编码体系**。

**设计理念**：很多现实世界的编码系统本身就是数字化的——HTTP 状态码、操作系统错误代码、数据库状态标志等等。如果你的枚舟能直接对应这些已有编码，就能避免维护一套额外的映射表。

比如 HTTP 状态码：
- `200` = 成功（Ok）
- `201` = 已创建（Created）
- `400` = 请求错误（BadRequest）
- `404` = 未找到（NotFound）

这些数字是 **IETF RFC 标准定义的**，不是你随便编的。如果用枚举来封装它们，既获得了类型安全，又保持了与外部协议的一致性。

> **什么时候应该手动指定起始值？**
>
> - 当枚举值需要与**外部系统对齐**时（HTTP 状态码、错误码、协议版本号等）
> - 当枚举值需要在**数据库/存储层**中使用且已有约定时
> - 当你需要为未来的扩展**预留空间**时（比如从 1000 开始，前面留给系统保留值）

### 跳号与重复值

```typescript
enum Weird {
  A = 1,
  B = 5,        // 跳过 2,3,4
  C,            // 6 (接着 B 的值递增)
  D = 10,
  E             // 11
}

enum Duplicate {
  X = 0,
  Y = 0,        // ⚠️ 允许重复值！但一般不推荐
  Z = 1,
  W = 1         // ⚠️ 也允许
}
```

> **坑点**：TypeScript 允许枚举成员拥有相同的值。这在逻辑上是合法的，但会导致反向映射时出现"多对一"的情况，可能引发难以排查的 bug。
>
> **什么时候重复值是有意为之的？** 极少数场景下，你可能希望两个不同名称指向同一个底层值——比如 `Color.Red` 和 `Color.Crimson` 都等于 `0xFF0000`，作为"别名"使用。但这种做法会让代码阅读者困惑，通常不如直接用一个名字清晰。

### 反向映射（Reverse Mapping）

这是数字枚举**最独特也最有趣的功能**，也是 TypeScript 枚举区别于大多数其他语言枚举的核心特性。

#### 什么是反向映射？

普通的"正向映射"是：你知道枚举成员的名字，想得到它对应的数字值。这很好理解——就像你问"Admin 角色的编号是什么？"，答案是 0。

**反向映射则反过来**：你手里有一个数字（比如从后端 API 返回的状态码），想知道这个数字对应哪个枚举成员的名字。就像你拿到了一个工牌号 0，想查这个人的名字叫什么。

#### 为什么其他语言的枚举没有反向映射？

在 Java、C#、Swift 等语言中，枚举本质上是一个**类/对象**，枚举成员是该类的实例。这些语言中，枚举成员和它的底层值之间没有双向绑定——你只能从成员找到值，不能从值找到成员（除非你自己写查找逻辑）。

TypeScript 不同。TS 的设计目标之一是 **"编译到 JavaScript 后仍然可用"**——因为 TS 编译后的代码需要在普通 JS 运行时环境中运行，而 JS 没有原生的枚举概念。所以 TS 用一个特殊的 IIFE 结构来同时实现正向和反向两个方向的映射，让枚举在运行时既可以用名字访问值，也可以用值反查名字。

#### 反向映射的实际价值

**场景一：API 状态码翻译**

后端接口返回的是纯数字（比如 HTTP 状态码或自定义业务状态码），前端需要把这些数字转换成人类可读的中文名称来展示。如果没有反向映射，你就得自己手写一堆 if-else 或 switch-case 来做数字→字符串的映射——而有了反向映射，一行代码就搞定。

**场景二：调试日志**

在生产环境的日志中，你可能会记录状态的数字值（节省存储空间）。当排查问题时，你需要把日志中的数字还原成有意义的名称。反向映射让这个过程自动化。

**场景三：序列化/反序列化**

当你需要把枚举值存入数据库（存数字），再读取出来还原为可读形式时，反向映射充当了天然的解码器角色。

> **生活类比强化**：反向映射就像电话簿的双向功能。
>
> - 正向：你知道"张三"，查他的电话号码 → `Role.Admin → 0`
> - 反向：你有一个来电号码 "0"，查是谁打来的 → `Role[0] → 'Admin'`
>
> 如果没有反向映射功能，每次接到 "0" 号的电话你都只能干瞪眼——不知道这是谁打来的。

```typescript
enum Role {
  Admin = 0,
  Editor = 1,
  Viewer = 2
}

// 正向映射：名称 → 数字
Role.Admin    // → 0
Role.Editor   // → 1
Role.Viewer   // → 2

// 反向映射：数字 → 名称
Role[0]       // → 'Admin'
Role[1]       // → 'Editor'
Role[2]       // → 'Viewer'
```

**编译后的 JavaScript 长这样**：

```javascript
var Role;
(function (Role) {
  Role[Role["Admin"] = 0] = "Admin";
  Role[Role["Editor"] = 1] = "Editor";
  Role[Role["Viewer"] = 2] = "Viewer";
})(Role || (Role = {}));
```

这段 IIFE（立即执行函数）的巧妙之处在于：`Role["Admin"] = 0` 这行代码的**返回值是赋值后的值（即 0）**，然后 `Role[0] = "Admin"` 用这个返回值作为 key 再做一次赋值。一行代码同时完成了正向和反向两个方向的映射！

**为什么需要反向映射？**

```typescript
// 场景：后端返回数字状态码，前端需要显示对应的中文名称
function getRoleName(code: number): string {
  return Role[code] ?? '未知角色'  // 反向映射派上用场了！
}

getRoleName(0)  // → 'Admin'
getRoleName(1)  // → 'Editor'

// 场景：日志记录——保存数字节省空间，调试时还原名称
console.log(`用户角色变更: ${Role[newRole]} (原: ${Role[oldRole]})`)
```

**生活类比**：就像电话簿——你可以通过人名查号码（正向），也可以通过号码查姓名（反向）。

## 字符串枚举（String Enum）

**字符串枚举的特点：**

1. **没有自增机制**：必须为每个成员显式赋值（因为字符串没法像数字那样"递增"——你没法说 "GET" 的下一个值是什么）
2. **没有反向映射**：字符串枚举编译后只产生单向映射（名字 → 值），不能从值反查名字
3. **更利于调试**：运行时看到的是有意义的字符串而非冷冰冰的数字

### 为什么字符串枚举没有反向映射？

技术上完全可以实现字符串的反向映射（就像数字那样用 `obj[value] = name`）。但 TypeScript 团队选择了不这么做，原因很务实：

- **性能考虑**：反向映射需要额外的属性赋值，对于通常比数字长得多的字符串来说，这个开销不值得
- **实际需求低**：你几乎不会遇到"拿到一个字符串 'GET' 需要查找它对应哪个成员名"的场景——字符串本身就已经足够可读了
- **键冲突风险**：如果枚举值恰好和 JavaScript 的原型链属性同名（比如 `'toString'`、`'constructor'`），反向映射会产生意外行为

### 字符串枚举 vs 数字枚举的选择逻辑

这本质上是在问：**你的枚举值主要是给机器看的，还是给人看的？**

- **给机器看的** → 用数字。数值紧凑、运算高效、存储占用小。适合内部状态码、位标志、数组索引
- **给人看的** → 用字符串。可读性强、调试友好、序列化后自解释。适合 API 协议字段、配置项、日志标签、UI 显示文本

> **一个实用的判断标准**：
>
> 如果你在代码中写 `console.log(status)` 希望看到 `0, 1, 2` → 数字枚举 OK
>
> 如果你在控制台或日志中希望看到 `"pending", "active", "done"` → 用字符串枚举
>
> 如果你两者都需要……那可能说明同一个枚举承担了太多职责，该拆开了

```typescript
// 字符串枚举编译结果——简洁清晰
var HttpMethod;
(function (HttpMethod) {
    HttpMethod["Get"] = "GET";
    HttpMethod["Post"] = "POST";
    HttpMethod["Put"] = "PUT";
    HttpMethod["Delete"] = "DELETE";
    HttpMethod["Patch"] = "PATCH";
})(HttpMethod || (HttpMethod = {}));

// 注意：没有反向映射！HttpMethod['GET'] 是 undefined
```

### 什么时候选字符串枚举 vs 数字枚举？

| 特性 | 数字枚举 | 字符串枚举 |
|------|---------|-----------|
| 自增 | ✅ 支持 | ❌ 必须手动 |
| 反向映射 | ✅ 有 | ❌ 无 |
| 序列化体积 | 小（数字） | 大（字符串） |
| 可读性/调试友好度 | 差（看到的是数字） | 好（看到的是字符串） |
| 适用场景 | 内部状态码、索引 | API协议、配置项、日志 |

**个人经验法则**：如果这个值会在日志、网络请求或 UI 中展示给人类看，用字符串枚举；如果是纯粹的内部状态管理，数字枚举更轻量。

## 异构枚举（Heterogeneous Enum）

混合使用数字和字符串值的枚举。

**⚠️ 强烈不推荐使用！**

原因不仅仅是上面列出的四点。从更深层次看：

**语义一致性原则被破坏了**

一个枚举代表的是 **"同一类事物的不同取值"**。就像"性别"这个枚举，不管用数字还是字符串，所有成员都应该用同一种方式表示——因为它们是"同一个维度的不同选项"。

异构枚举意味着你的"选项"跨越了两个不同的维度（数字和字符串），这通常暗示你的数据模型设计有问题。

> **社区共识**：如果你发现自己需要一个异构枚举，大概率说明你应该把它拆成两个独立的枚举，或者改用联合类型来建模。唯一勉强合理的场景是**向后兼容迁移**：你有一个旧的数字枚举需要逐步替换为新的字符串值，过渡期间两者并存——但这应该是暂时的。

## const enum —— 编译时枚举

`const enum` 是 TypeScript 提供的一种特殊枚举，它会在**编译时内联**所有引用，最终生成的 JavaScript 中**不会有任何枚举相关的代码**。

### const enum 的本质：编译期的"查找-替换"

你可以把 `const enum` 理解为 C/C++ 语言中的 **`#define` 宏**——它在编译阶段就把所有的引用替换成实际的字面量值，运行时完全不留下任何痕迹。

普通枚举在运行时是一个真实的 JavaScript 对象，你可以遍历它、动态访问它的属性、把它当字典用。但 `const enum` 在编译完成后就**彻底消失了**——它在运行时不占用任何内存，也不产生任何对象创建的开销。

### 为什么会有这种设计？

这个特性的诞生背景和 TypeScript 的早期定位有关：

1. **性能敏感场景**：有些团队希望枚举的访问成本降到最低——连属性查找都不想做
2. **输出体积优化**：对于大量使用枚举的库来说，省掉枚举对象的定义代码可以显著减小包体积
3. **与 C# 的习惯对齐**：C# 开发者习惯了枚举在 Release 编译中被内联优化的行为

```typescript
// 普通 enum
enum NormalColor {
  Red,
  Green,
  Blue
}
let nc: NormalColor = NormalColor.Red;

// const enum
const enum ConstColor {
  Red,
  Green,
  Blue
}
let cc: ConstColor = ConstColor.Red;  // 编译后变成 let cc = 0 /* Red */;
```

**编译输出的差异巨大：**

```javascript
// 普通 enum — 生成了完整的枚举对象 + 反向映射
var NormalColor;
(function (NormalColor) {
    NormalColor[NormalColor["Red"] = 0] = "Red";
    NormalColor[NormalColor["Green"] = 1] = "Green";
    NormalColor[NormalColor["Blue"] = 2] = "Blue";
})(NormalColor || (NormalColor = {}));
var nc = NormalColor.Red;  // 运行时查找

// const enum — 完全内联，零运行时开销
var cc = 0 /* Red */;  // 直接替换为字面量值
```

### const enum 的优势

1. **零运行时开销**：没有额外的对象生成代码
2. **更好的 tree-shaking**：由于值被内联，未使用的成员不会出现在输出中
3. **访问更快**：不需要属性查找，直接就是字面量

### const enum 的局限

```typescript
const enum Status {
  Pending,
  Active
}

// ❌ 无法遍历 const enum
for (const s in Status) { }  // Error: 'const' 枚举成员仅在属性访问时可以进行内联

// ❌ 无法将 const enum 作为值传递
function printStatus(s: Status) { }
printStatus(Status.Active)  // 可以（内联为 1）
printStatus(Status as any)  // 不可以！Status 在运行时不存在

// ❌ 无法通过动态 key 访问
const key = 'Active' as const
Status[key]  // Error
```

**核心问题**：`const enum` 在编译时就被"抹除"了，运行时根本不存在这个对象。所以任何需要在运行时"把枚举当对象用"的操作都不行。

### 为什么 const enum 有争议？

`const enum` 是 TypeScript **独有的特性**，不是 ECMAS 标准。这导致了几个实际问题：

1. **工具链分裂**：Babel、esbuild、SWC 等非 tsc 编译工具无法正确处理。因为要实现"编译期内联"，编译器必须看到枚举定义和使用处在同一次编译中——而 Babel 等工具是单文件编译的
2. **`.d.ts` 发布困境**：发布 TS 库后，使用方会发现类型声明文件里根本没有这个枚举的实现（被内联掉了）
3. **isolatedModules 冲突**：Next.js、Vite 等框架默认开启 isolatedModules，要求每个文件独立编译，const enum 天然违反这个约束

> **趋势判断**：随着前端工程化发展（模块化构建、tree-shaking 优先、多工具链协作），const enum 的生存空间正在急剧缩小。Vue 3 源码已全面弃用枚举，TS 标准库也在逐步用 as const 对象替代。
>
> 建议：新项目中优先考虑 `as const` 对象 + `typeof` 联合类型，完全符合 ECMAScript 标准。

## 联合枚举（Const Enum Members）—— 枚举的双重身份

当一个枚举的所有成员都是**字面量值**（没有计算值）时，它就是一个"联合枚举"。此时枚举不仅是**值**，还是**类型**！

### 什么是"双重身份"？

这是 TypeScript 中一个非常独特的设计。在大多数语言中，枚举要么是值（运行时的对象），要么是类型（编译时的约束），不会两者都是。但 TypeScript 的联合枚举打破了这种二元对立。

- **作为值使用**：你可以写 `let pet = Animal.Dog`，把枚举成员赋给变量
- **作为类型使用**：你可以写 `let myPet: Animal`，用枚举名来标注变量的类型

当你在类型位置使用联合枚举的名字时，TypeScript 会把它"展开"为一个由所有成员的值组成的**联合类型（Union Type）**。比如 `Animal` 类型等价于 `'dog' | 'cat' | 'bird'`。

### 为什么计算值的枚举不能做类型？

如果枚举中有任何成员的值是在**运行时才能确定**的（比如调用了函数、使用了表达式），TypeScript 就无法在编译期知道所有可能的取值是什么——自然也就无法生成对应的联合类型。

> **通俗理解**：想象你要列出一组彩票的所有可能中奖号码。
>
> - 如果号码是**预先固定好**的（1, 2, 3, 5, 8），你可以把它们全列出来 → 对应字面量枚举
> - 如果有一个号码是**摇号决定的**（Math.random()），你无法预知结果 → 对应计算值枚举
>
> 第一种情况下，TS 可以说"这些就是全部可能"；第二种情况 TS 只能说"这可能是任意数字"。

```typescript
// 所有成员都是字面量 → 联合枚举
enum Animal {
  Dog = 'dog',
  Cat = 'cat',
  Bird = 'bird'
}

// Animal 同时是值和类型！
let myPet: Animal = Animal.Dog    // ✅
myPet = 'dog'                     // ✅ （等价于 Animal.Dog 的值）
myPet = 'fish'                    // ❌ Type '"fish"' is not assignable to type 'Animal'

// 函数参数也能用枚举类型约束
function adopt(pet: Animal): void {
  console.log('Adopted:', pet)
}

adopt(Animal.Cat)    // ✅
adopt('bird')         // ✅
adopt('dragon')       // ❌
```

**对比：包含计算值的枚举无法作为类型使用**

```typescript
enum Special {
  A = Math.random(),  // 计算值！
  B = 'hello'
}

// 此时 Special 只能作为值使用，不能作为类型
let s: Special  // ❌ Error: Special 只引用了类型，但在此处却作为值在使用
```

**原理**：只有当所有成员的字面量值都能在编译时确定时，TypeScript 才能把这些值提取出来组成一个联合类型。计算值的成员打破了这一前提条件。

## 枚举 vs 字面量联合类型 —— 深度对比

这是现代 TypeScript 社区**讨论最激烈的话题之一**。让我们全方位比较这两种方案：

### 为什么会有这场争论？

TypeScript 2.x 时代，枚举是"表示一组有限选项"的唯一选择。但从 TypeScript 3.0+ 开始，随着 `as const` 断言、`typeof` 类型查询、模板字面量类型等特性的成熟，一种新的模式逐渐流行起来：**用 `const` 对象 + `typeof` 来模拟枚举的行为**。

这种模式之所以能兴起，核心原因是一个哲学分歧：**TypeScript 的类型应该是"纯编译时产物"，还是可以容忍一些运行时的开销？**

- **枚举派**认为：运行时有对象是合理的代价——它提供了反向映射、遍历等实用能力
- **联合类型派**认为：JavaScript 已经有足够表达力了（对象 + 联合类型），不需要额外的语法糖

两种观点各有道理，最终的选择取决于你的项目约束和团队偏好。

### 方案一：传统枚举

```typescript
enum Direction {
  Up = 'UP',
  Down = 'DOWN',
  Left = 'LEFT',
  Right = 'RIGHT'
}
```

### 方案二：字面量联合类型 + const 对象

```typescript
// 使用 as const 断言 + typeof
const Direction = {
  Up: 'UP',
  Down: 'DOWN',
  Left: 'LEFT',
  Right: 'RIGHT'
} as const

type Direction = (typeof Direction)[keyof typeof Direction]
// 等价于 type Direction = 'UP' | 'DOWN' | 'LEFT' | 'RIGHT'
```

### 多维度对比表

| 维度 | enum | 联合类型 + const 对象 |
|------|------|---------------------|
| **运行时存在性** | ✅ 运行时存在对象 | ✅ 对象也存在 |
| **输出体积** | 较大（尤其数字枚举的反向映射） | 更紧凑 |
| **tree-shaking** | ❌ 整个枚举对象会被保留 | ✅ 未使用的属性可被消除 |
| **反向映射** | ✅ 数字枚举支持 | ❌ 不支持（除非自己实现） |
| **IDE 自动补全** | ✅ 成员名补全 | ✅ 属性名补全（几乎一样好） |
| **可迭代/遍历** | ✅ `for..in` / `Object.values()` | ✅ 同样支持 |
| **命名空间污染** | ⚠️ 枚举名成为全局变量 | ✅ 只是普通变量 |
| **ECMAScript 标准性** | ❌ TS 私有语法 | ✅ 标准 JS + TS 类型 |
| **跨工具链兼容** | ⚠️ const enum 不被 Babel 支持 | ✅ 所有工具链都支持 |
| **switch穷尽检查** | ✅ 支持 | ✅ 同样支持 |
| **作为字典使用** | ✅ 天然支持 | ✅ 同样支持 |

### 输出体积的实际对比

```typescript
// ====== enum 版本 ======
enum Color { R, G, B }

// 编译输出（约 180 字节）：
// var Color; (function(Color){...反向映射...})(Color||(Color={}));

// ====== 联合类型版本 ======
export const Color = { R: 0, G: 1, B: 2 } as const
export type Color = (typeof Color)[keyof typeof Color]

// 编译输出（约 40 字节）：
// export var Color = {R:0,G:1,B:2};
```

对于大型应用来说，如果使用了大量枚举，这个差异会被放大。

### switch 穷尽检查对比

两种方案都支持 TypeScript 的穷尽检查（exhaustiveness checking）：

```typescript
// === enum 版本 ===
enum Pet { Dog, Cat, Bird }

function speak(pet: Pet): string {
  switch (pet) {
    case Pet.Dog: return '汪!'
    case Pet.Cat: return '喵~'
    case Pet.Bird: return '啾!'
    default:
      // 如果新增 Fish 但忘记处理这里，TS 会警告
      const _exhaustive: never = pet
      return _exhaustive
  }
}

// === 联合类型版本 ===
type Pet = 'dog' | 'cat' | 'bird'

function speak(pet: Pet): string {
  switch (pet) {
    case 'dog': return '汪!'
    case 'cat': return '喵~'
    case 'bird': return '啾!'
    default:
      const _exhaustive: never = pet
      return _exhaustive
  }
}
```

两种写法在穷尽检查方面**完全等效**。

### 我的建议：什么时候用什么？

**适合用枚举的场景：**
- 需要**反向映射**功能时（如 HTTP 状态码 ↔ 名称）
- 项目已有大量枚举，统一风格更重要
- 与后端协议强绑定，且后端也是枚举模式
- 遗留代码库中大量使用枚举，改造成本过高

**适合用联合类型的场景：**
- 新项目、新代码
- 需要更好的 tree-shaking（特别是库/包的开发）
- 需要跨工具链兼容（使用 Babel/esbuild）
- 开启了 `isolatedModules` 的项目
- 值只需要单向映射（名称 → 值）

### 场景 1：HTTP/API 状态码

```typescript
enum HttpStatusCode {
  Continue = 100,
  Ok = 200,
  Created = 201,
  BadRequest = 400,
  Unauthorized = 401,
  Forbidden = 403,
  NotFound = 404,
  InternalServerError = 500

// 反向映射用于错误信息展示
class ApiError extends Error {
  constructor(
    public code: HttpStatusCode,
    message?: string
  ) {
    super(message ?? `API Error: ${HttpStatusCode[code]} (${code})`)
    this.name = 'ApiError'
  }
}

throw new ApiError(HttpStatusCode.NotFound)
// → Error: API Error: NotFound (404)
```

### 场景 2：角色权限系统

```typescript
// 推荐用字符串枚举——权限标识通常需要序列化传输
enum Role {
  SuperAdmin = 'super_admin',
  Admin = 'admin',
  Editor = 'editor',
  Viewer = 'viewer'
}

enum Permission {
  UserRead = 'user:read',
  UserWrite = 'user:write',
  ContentRead = 'content:read',
  ContentWrite = 'content:write',
  SettingsManage = 'settings:manage'
}

// 角色到权限的映射
const ROLE_PERMISSIONS: Record<Role, Permission[]> = {
  [Role.SuperAdmin]: Object.values(Permission),
  [Role.Admin]: [
    Permission.UserRead, Permission.UserWrite,
    Permission.ContentRead, Permission.ContentWrite,
    Permission.SettingsManage
  ],
  [Role.Editor]: [Permission.ContentRead, Permission.ContentWrite],
  [Role.Viewer]: [Permission.ContentRead],
}

function hasPermission(role: Role, permission: Permission): boolean {
  return ROLE_PERMISSIONS[role]?.includes(permission) ?? false
}
```

## 个人总结

枚举是 TypeScript 从 C#、Java 等语言借鉴过来的特性，它在早期确实解决了 JavaScript 缺乏枚举类型的问题。但随着 TypeScript 生态的发展——字面量联合类型越来越强大、`as const` 让普通对象获得精确类型推断、tree-shaking 成为性能优化关键、跨工具链一致性越来越重要——枚举的优势正在逐渐缩小。

### 我的建议

- **学习/教学项目中**：大胆使用枚举。它是理解 TypeScript 类型系统的好工具——特别是"值和类型双重身份"、"编译时 vs 运行时行为差异"等概念，通过枚举能非常直观地理解
- **新项目**：优先考虑 `const 对象 + typeof` 联合类型模式。它更现代、更标准、更符合前端工程化趋势
- **已有大量枚举的遗留项目**：不必急着改。保持一致性的价值远大于追求技术潮流。如果团队已经习惯了 enum，继续用就好
- **库/包的开发**：避免使用 `const enum`，优先用联合类型。因为你的使用者可能使用任何构建工具，const enum 会给他们带来不必要的麻烦

### 一句话记住枚举

> 枚举是 TypeScript 给 JavaScript 补上的一块"类型安全拼图"。它让有限的选项集合变得**可列举、可约束、可追溯**。虽然现代 TS 生态有了更轻量的替代方案，但理解枚举的原理和取舍，仍然是每个 TypeScript 开发者的必修课。

枚举本身不是一个"坏特性"，它只是在某些场景下不再是**最优选择**。理解它的原理和取舍，才能在不同场景下做出正确的决策。
