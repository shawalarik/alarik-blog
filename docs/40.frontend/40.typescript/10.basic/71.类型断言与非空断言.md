# 类型断言与非空断言——as、!、as const

> "有时候，你比 TypeScript 更了解你的代码。" 这就是类型断言存在的意义。

## 一、什么是类型断言（Type Assertion）

### 1.1 核心概念

**类型断言（Type Assertion）** 是一种告诉 TypeScript 编译器"相信我，我知道这个值到底是什么类型"的机制。它不会在运行时对值做任何转换或检查，纯粹是编译时的类型信息覆盖。

用一个生活化的类比来理解：

> **类比：快递签收**
>
> 你在网上买了一箱苹果。快递员送来一个密封的箱子，标签上写着"水果"（这是 TS 推断的宽泛类型）。
>
> **类型断言**就像你对快递员说："我知道这里面装的是苹果，直接帮我登记成'苹果'就行，不用拆开看了。"
>
> ——但问题是，如果里面其实装的是榴莲呢？那"断言"就错了。

### 1.2 为什么需要类型断言

TypeScript 的类型推断虽然强大，但并非无所不能。以下场景中，TS 无法准确推断类型：

```typescript
// 场景1: DOM 元素获取 — TS 不知道页面上具体是什么元素
const myInput = document.getElementById('my-input');
// TS 推断为 HTMLElement | null
// 但你知道它肯定是一个 HTMLInputElement

// 场景2: 联合类型 — 运行时逻辑已经确定了具体类型
function getLength(input: string | number): number {
  // 我们知道这里 input 是 string，但 TS 不确定
  return (input as string).length;
}

// 场景3: 第三方库的类型声明不完善
const data = someLibrary.getData(); // 返回 any 或不够精确的类型
```

## 二、as 语法——类型断言的基本写法

### 2.1 两种语法形式

TypeScript 提供了两种类型断言语法：

```typescript
// 写法1: as 语法（推荐）
let value1: unknown = 'hello';
let str1 = value1 as string;

// 写法2: 尖括号语法（JSX 中不可用）
let value2: unknown = 'hello';
let str2 = <string>value2;
```

### 2.2 为什么推荐 `as` 语法

尖括号语法 `<Type>value` 在 `.tsx` 文件（React JSX）中会产生歧义，因为 JSX 本身也用尖括号表示标签。因此：

```tsx
// ❌ 在 .tsx 文件中会报错
const element = <string>someValue;

// ✅ as 语法在所有场景下都能正常工作
const element = someValue as string;
```

**最佳实践：统一使用 `as` 语法，保持代码风格一致。**

### 2.3 类型断言的限制

类型断言不能随意转换任意两种类型——它们之间必须有**重叠（交集）**：

```typescript
let str = 'hello';

// ✅ 合法：string 和 any 有重叠
let a = str as any;

// ✅ 合法：unknown 可以被断言为任何类型
let b: unknown = 'hello';
let c = b as string;

// ❌ 非法：number 和 string 没有重叠
// let d = 123 as string; // Error: Conversion of type 'number' to type 'string'
```

## 三、双重断言（Double Assertion）

### 3.1 什么是双重断言

当两个类型完全没有重叠时，可以使用 **双重断言** 先转到 `unknown`（或 `any`），再转目标类型：

```typescript
let num = 123;

// ❌ 直接断言会报错
// let str = num as string; // Error!

// ✅ 双重断言：先到 unknown，再到 string
let str = num as unknown as string; // 编译通过！但运行时 str 的值仍然是 123
```

### 3.2 工作原理图解

```
原始类型: number ──(直接断言)──> string   ❌ 无交集，禁止!
     │
     ├───(as unknown)──> unknown           ✅ unknown 与一切类型有交集
     │                        │
     │                   (as string)       ✅ 从 unknown 到 string 合法
     │                        │
     ▼                       ▼
    结果: 编译通过，但运行时可能出问题
```

### 3.3 ⚠️ 双重断言的危险性

双重断言本质上是在**欺骗类型系统**，绕过所有的类型安全检查：

```typescript
interface User {
  name: string;
  age: number;
}

// 假设我们从某个地方拿到了一个不确定的数据源
const rawData: object = { name: '张三', age: 25 };

// 使用双重断言
const user = rawData as unknown as User;
console.log(user.name); // 编译时安全 ✓
console.log(user.address); // 编译时不报错！但运行时是 undefined

// 更危险的情况：
const dangerous = 'not a user at all' as unknown as User;
console.log(dangerous.name); // undefined — 静默失败！
```

**原则：双重断言应该是最后的手段，使用前务必三思。**

## 四、as 的适用场景

### 4.1 DOM 元素获取

这是最常见的使用场景之一。DOM API 返回的类型往往比较宽泛：

```typescript
// 获取输入框
const inputEl = document.getElementById('username') as HTMLInputElement;
// 现在 TS 知道这是一个 input 元素，可以访问 .value 属性
inputEl.value = '默认用户名'; // ✅ 正确访问 input 特有的属性

// 获取 canvas 元素
const canvas = document.getElementById('game-canvas') as HTMLCanvasElement;
const ctx = canvas.getContext('2d'); // ✅ 只有 Canvas 元素才有 getContext 方法

// 获取自定义数据属性
const div = document.getElementById('info-card') as HTMLDivElement;
const userId = div.dataset.userId; // ✅ 访问 dataset 属性
```

> **为什么 DOM 操作经常需要断言？**
>
> 因为 `document.getElementById()` 的签名返回 `HTMLElement | null`，而 `HTMLElement` 是所有 HTML 元素的基类，只包含通用的属性和方法（如 `id`, `className`, `style`）。具体的子类型属性（如 `<input>` 的 `value`，`<canvas>` 的 `getContext`）不在基类定义中。
>
> 作为开发者，我们通过 `id` 名称或其他上下文知道具体是什么元素，所以可以用断言告知 TS。

### 4.2 联合类型收窄

当变量是联合类型，且运行时逻辑已经确定其具体类型时：

```typescript
type Cat = { type: 'cat', meow: () => void };
type Dog = { type: 'dog', bark: () => void };
type Pet = Cat | Dog;

function makeSound(pet: Pet) {
  if (pet.type === 'cat') {
    // 虽然 TS 能通过 pet.type 收窄，但在某些复杂情况下可能需要辅助
    const cat = pet as Cat;
    cat.meow();
  }
}

// 更实际的例子：处理 API 返回的不同格式
type ApiResponse =
  | { success: true; data: { id: number; name: string } }
  | { success: false; error: { code: number; message: string } };

function handleResponse(response: ApiResponse) {
  if (response.success) {
    // response 已经被收窄，但有时为了代码清晰，我们会赋给新变量
    const result = response.data;
    console.log(result.name); // TS 自动收窄后可访问
  } else {
    console.log(response.error.message);
  }
}
```

### 4.3 第三方库的类型不足

有些第三方 JavaScript 库没有完善的 TypeScript 类型定义，或者类型定义不够精确：

```typescript
// 假设某个老旧库返回的类型是 any 或不够精确
import { oldLibrary } from 'some-old-library';

const result = oldLibrary.fetchData(); // 类型是 any

// 用断言提供更精确的类型信息
interface UserData {
  id: string;
  email: string;
  avatarUrl: string;
}

const userData = result as userData;
console.log(userData.email.split('@')); // 现在有完整的类型提示

// 另一种常见情况：动态导入模块
async function loadModule() {
  // 动态 import 返回 Promise<any>，我们需要断言
  const module = await import('./my-module') as {
    default: () => void;
    helper: (x: number) => string;
  };
  module.default();
}
```

### 4.4 字面量类型的精确指定

```typescript
// 常量配置对象
const config = {
  theme: 'dark',
  language: 'zh-CN',
  debug: false,
} as const;

// 没有 as const 时，theme 的类型是 string
// 有了 as const 后，theme 的类型是字面量 'dark'

function setTheme(theme: 'light' | 'dark'): void {
  document.documentElement.dataset.theme = theme;
}

setTheme(config.theme); // ✅ 因为 config.theme 的类型是 'dark'，精确匹配
```

## 五、非空断言（Non-null Assertion Operator）

### 5.1 基本用法

非空断言操作符 `!`（也叫**后缀感叹号操作符**）告诉 TypeScript："我保证这个值不是 `null` 也不是 `undefined`"。

```typescript
// 基本语法
value!  // 表示 value 不是 null/undefined
```

### 5.2 典型应用场景

```typescript
// 场景1: DOM 元素获取 — 我们确信元素一定存在
const button = document.getElementById('submit-button')!;
// 去掉了 null 类型，button 的类型现在是 HTMLElement（不是 HTMLElement | null）

// 场景2: 可选属性访问
interface Post {
  title: string;
  content?: string; // 可能为 undefined
}

function renderPost(post: Post): void {
  // 如果我们确定 content 一定存在（比如已经做过校验）
  const length = post.content!.length;
  console.log(`文章长度: ${length}`);
}

// 场景3: 可能未初始化的类成员
class ApiService {
  private httpClient!: AxiosInstance;

  constructor() {
    this.initHttpClient();
  }

  private initHttpClient(): void {
    this.httpClient = axios.create({ baseURL: '/api' });
  }

  getData(): void {
    // TS 不知道 initHttpClient 已经在构造函数中被调用
    // 使用 ! 告诉 TS: 我保证它已经被初始化了
    this.httpClient.get('/data');
  }
}

// 场景4: 回调函数中的参数
['a', 'b', 'c'].forEach((item, index, array) => {
  // array.find 返回 string | undefined，但我们知道一定能找到
  const found = array.find(x => x === item)!;
});
```

### 5.3 ! 的工作原理

```typescript
let maybeString: string | undefined = 'hello';

// 不使用 !
if (maybeString !== undefined) {
  console.log(maybeString.length); // TS 自动收窄为 string
}

// 使用 ! — 相当于跳过了空值检查
console.log(maybeString!.length); // TS 认为它是 string
```

从编译结果来看，`!` 操作符**完全不会产生任何运行时代码**——它只是告诉编译器忽略可能的 `null` 和 `undefined`：

```typescript
// 源码
let x: string | null = 'hello';
console.log(x!.length);

// 编译后的 JS（完全一样，没有任何额外检查）
var x = 'hello';
console.log(x.length);
```

### 5.4 ⚠️ 非空断言的危险性

这是整个 TypeScript 中最容易导致运行时 bug 的特性之一：

```typescript
// 危险示例1: 实际上可能是 null
function getUserById(id: number): User | null {
  return database.find(id); // 可能找不到用户
}

const user = getUserById(999)!; // 断言不为空
console.log(user.name); // 如果用户不存在 → 运行时报错: Cannot read property 'name' of null

// 危险示例2: 异步操作中的竞态条件
let data: ResponseData | undefined;

fetchData().then(result => {
  data = result;
});

// data 此时可能还没被赋值！
console.log(data!.status); // 可能是 undefined → 运行时报错

// 危险示例3: DOM 元素实际不存在
const el = document.getElementById('non-existent-element')!;
el.click(); // TypeError: Cannot read properties of null (reading 'click')
```

> **真实事故案例**
>
> 笔者曾在项目中见过这样的代码：
>
> ```typescript
> const userId = localStorage.getItem('user_id')!;
> await fetch(`/api/users/${userId}/profile`);
> ```
>
> 当用户清除浏览器缓存或首次访问时，`localStorage.getItem()` 返回 `null`，非空断言让 TS 放行了这行代码，结果请求发成了 `/api/users/null/profile`——服务端返回了一堆奇怪的错误数据，前端页面崩溃。
>
> **教训：永远不要对来自外部的输入（localStorage、API 响应、URL 参数等）使用非空断言。**

### 5.5 安全替代方案

与其用 `!`，不如用更安全的方式处理可能的空值：

```typescript
// 方案1: 条件判断（最安全）
const el = document.getElementById('submit-btn');
if (el) {
  el.click(); // TS 在这里自动收窄类型
} else {
  console.error('按钮未找到');
}

// 方案2: 空值合并运算符提供默认值
const username: string | null = localStorage.getItem('username');
const displayName = username ?? '匿名用户'; // 如果为 null/undefined，使用默认值

// 方案3: 可选链 + 默认值
interface Config {
  apiUrl?: string;
}
const config: Config = {};
const url = config.apiUrl ?? 'https://api.default.com';

// 方案4: 抛出明确的错误（比静默失败好）
function getElement<T extends HTMLElement>(id: string): T {
  const el = document.getElementById(id);
  if (!el) {
    throw new Error(`找不到 ID 为 "${id}" 的元素`);
  }
  return el as T;
}
// 使用时不需要 !
const btn = getElement<HTMLButtonElement>('submit-btn');
```

## 六、as const——常量断言

### 6.1 问题引入

先看一个普通变量的类型推断行为：

```typescript
// 普通情况：TS 会将字面量推断为更宽泛的基础类型
let name = 'Alarik';          // 类型: string（不是 'Alarik'）
let age = 25;                  // 类型: number（不是 25）
let isActive = true;           // 类型: boolean（不是 true）

const direction = 'up';        // 类型: 'up'（const 声明时会推断为字面量类型）

// 对象和数组的情况
const config = {
  url: '/api/users',
  timeout: 5000,
  methods: ['GET', 'POST'],
};
/*
config.url 的类型是 string（不是 '/api/users'）
config.timeout 的类型是 number（不是 5000）
config.methods 的类型是 string[]（不是 ['GET', 'POST']）
*/
```

**问题：当我们需要一个精确的字面量类型作为参数传入函数时，普通推断太宽泛了。**

### 6.2 as const 的作用

`as const` 将表达式中的**所有层级**都转换为最精确的字面量类型，并且变成 **readonly**：

```typescript
const config = {
  url: '/api/users',
  timeout: 5000,
  methods: ['GET', 'POST'],
} as const;

/*
config 的类型变为:
{
  readonly url: '/api/users';
  readonly timeout: 5000;
  readonly readonly methods: readonly ['GET', 'POST'];
}

注意变化:
- url: string → '/api/users' （字面量类型）
- timeout: number → 5000 （字面量类型）
- methods: string[] → readonly ['GET', 'POST'] （只读元组 + 字面量）
*/
```

### 6.3 详细对比

```typescript
// ========== 普通 const ==========
const normalObj = {
  name: 'Alice',
  age: 30,
  hobbies: ['coding', 'reading'],
};

// 类型推断结果：
// normalObj.name:     string
// normalObj.age:      number
// normalObj.hobbies:  string[]
//
// 可以修改：
normalObj.name = 'Bob';         // ✅ 允许
normalObj.hobbies.push('gaming'); // ✅ 允许


// ========== as const ==========
const literalObj = {
  name: 'Alice',
  age: 30,
  hobbies: ['coding', 'reading'],
} as const;

// 类型推断结果：
// literalObj: {
//   readonly name: 'Alice';
//   readonly age: 30;
//   readonly hobbies: readonly ['coding', 'reading'];
// }
//
// 不能修改（全部 readonly）：
// literalObj.name = 'Bob';              // ❌ Cannot assign to 'name' because it is read-only
// literalObj.hobbies.push('gaming');    // ❌ Property 'push' does not exist on type...
```

### 6.4 as const 的实际应用

#### 应用1: 精确匹配联合类型

```typescript
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';

function request(url: string, method: HttpMethod): Promise<Response> {
  return fetch(url, { method });
}

// ❌ 不用 as const — method 的类型是 string，不能传给期望 HttpMethod 的参数
const options = { method: 'GET' }; // options.method 的类型是 string
request('/api/data', options.method); // Error: Argument of type 'string' is not assignable to parameter of type 'HttpMethod'

// ✅ 使用 as const — method 的类型是 'GET'
const options2 = { method: 'GET' } as const; // options2.method 的类型是 'GET'
request('/api/data', options2.method); // ✅ 'GET' 是 HttpMethod 的子类型
```

#### 应用2: 定义配置映射表

```typescript
// 定义主题颜色映射 — 要求 key 和 value 都是字面量类型
const THEME_COLORS = {
  primary: '#1890ff',
  success: '#52c41a',
  warning: '#faad14',
  error: '#f5222d',
} as const;

// 类型自动推导为精确的字面量类型
type ThemeColor = typeof THEME_COLORS[keyof typeof THEME_COLORS];
// ThemeColor = '#1890ff' | '#52c41a' | '#faad14' | '#f5222d'

function setThemeColor(color: ThemeColor): void {
  document.documentElement.style.setProperty('--color', color);
}

setThemeColor(THEME_COLORS.primary); // ✅
setThemeColor('#1890ff');            // ✅
setThemeColor('#000000');            // ❌ 不是合法的主题色
```

#### 应用3: Redux/状态管理的 Action 类型

```typescript
// Redux action 创建器
const actions = {
  setUser: (user: { name: string }) => ({ type: 'SET_USER', payload: user }),
  clearUser: () => ({ type: 'CLEAR_USER' }),
  setLoading: (loading: boolean) => ({ type: 'SET_LOADING', payload: loading }),
} as const;

// actions.setUser().type 的类型是 'SET_USER'（字符串字面量）
// actions.clearUser().type 的类型是 'CLEAR_USER'
type ActionType = ReturnType<typeof actions[keyof typeof actions]>['type'];
// ActionType = 'SET_USER' | 'CLEAR_USER' | 'SET_LOADING'
```

#### 应用4: 路由配置

```typescript
const routes = {
  home: '/',
  about: '/about',
  users: '/users',
  userProfile: (id: number) => `/users/${id}`,
} as const;

// routes.home 的类型是 '/'（不是 string）
// 可以用来构建类型安全的路由系统
type RoutePath = typeof routes[keyof typeof routes]; // '/' | '/about' | '/users' | (id: number) => string
```

### 6.5 设计理念：为什么 as const 要做成递归 readonly？

这是因为 **字面量类型的语义本身就意味着"不可变"**：

```typescript
// 思考: 如果 as const 不加 readonly 会怎样？
const arr = [1, 2, 3] as /* 假设 */ const;
// 如果 arr 不是 readonly，我们可以执行 arr.push(4)
// 那么 arr 就变成了 [1, 2, 3, 4]
// 它还是 [1, 2, 3] 这个字面量类型吗？显然不是了！

// 所以 readonly 是字面量类型语义的必要组成部分
// 它保证了"类型即值，值即类型"的一致性
```

## 七、类型守卫 vs 断言——本质区别

这是一个非常重要的对比，理解它可以帮助你在两者之间做出正确的选择。

| 特性 | 类型断言 (`as`, `!`) | 类型守卫 (`typeof`, `instanceof`) |
|------|---------------------|----------------------------------|
| **发生时机** | 仅编译时 | 运行时 + 编译时 |
| **运行时影响** | 无（完全被移除） | 有（保留判断逻辑） |
| **安全性** | 取决于开发者 | 由运行时检查保障 |
| **适用场景** | 确定性的类型转换 | 不确定的类型分支 |

### 7.1 代码对比

```typescript
// ====== 断言方式 ======
function processValue1(value: string | number): number {
  return (value as string).length; // 如果 value 实际上是 number → 运行时崩溃！
}

// ====== 守卫方式 ======
function processValue2(value: string | number): number {
  if (typeof value === 'string') {
    return value.length; // 安全 — 运行时确认了类型
  }
  return String(value).length; // 处理 number 情况
}
```

### 7.2 选择原则

```
能用类型守卫解决的问题 → 优先使用类型守卫
TS 推断不足但你有把握   → 谨慎使用断言
外部数据来源             → 绝不用断言，用守卫或校验库
```

## 八、断言的安全使用原则

### 8.1 黄金法则

1. **优先使用类型守卫而非断言**：如果能在运行时检查，就不要用断言跳过
2. **缩小断言的作用范围**：只在必要的最小范围内使用断言
3. **添加注释说明为什么断言**：让后来者理解你的意图
4. **避免对用户输入/外部数据使用断言**：这些数据是不可信的

### 8.2 好的实践

```typescript
// ✅ 好的实践: 有明确理由 + 注释说明
class FormValidator {
  // 注意: 这些元素在 constructor 中通过 querySelector 初始化
  // 使用非空断言是因为 TS 无法追踪初始化顺序
  private formEl!: HTMLFormElement;
  private submitBtn!: HTMLButtonElement;

  constructor(formId: string, submitId: string) {
    this.formEl = document.querySelector(`#${formId}`) as HTMLFormElement;
    this.submitBtn = document.querySelector(`#${submitId}`) as HTMLButtonElement;

    if (!this.formEl || !this.submitBtn) {
      throw new Error('表单元素未找到');
    }
  }

  submit(): void {
    // 这里可以安全地使用 ! 因为 constructor 中已经做了验证
    this.formEl.dispatchEvent(new Event('submit'));
  }
}
```

### 8.3 不好的实践

```typescript
// ❌ 不好的实践: 无理由的断言
function processData(data: unknown): string {
  // 为什么断言是 User 类型？没有校验，没有注释，没有安全保障
  return (data as User).name;
}

// ❌ 不好的实践: 大面积使用非空断言
function badCode(): void {
  const el1 = document.querySelector('.a')!;
  const el2 = document.querySelector('.b')!;
  const el3 = document.querySelector('.c')!;
  const el4 = document.querySelector('.d')!;
  // 一旦任何一个元素不存在，全部崩溃
}
```

## 九、常见反模式和陷阱

### 9.1 反模式1: 过度使用断言代替正确的类型设计

```typescript
// ❌ 反模式: 用断言掩盖类型设计的问题
function fetchData(): any {
  return JSON.parse(response);
}
const data = fetchData() as User; // 用 any + 断言绕过一切类型检查

// ✅ 正确做法: 使用泛型和正确的类型定义
async function fetchUser(): Promise<User> {
  const response = await fetch('/api/user');
  return response.json() as Promise<User>; // 或者使用 zod/io-ts 等校验库
}
```

### 9.2 反模式2: 断言链条

```typescript
// ❌ 反模式: 连续断言，每一步都可能出错
const result = (externalData as any).data.items[0].name as string;

// ✅ 正确做法: 分步处理并加入校验
interface DataResponse {
  data: { items: Array<{ name: string }> };
}

function extractName(raw: unknown): string | null {
  if (
    raw &&
    typeof raw === 'object' &&
    'data' in raw &&
    raw.data &&
    typeof raw.data === 'object' &&
    'items' in raw.data &&
    Array.isArray(raw.data.items) &&
    raw.data.items.length > 0 &&
    raw.data.items[0] &&
    typeof raw.data.items[0] === 'object' &&
    'name' in raw.data.items[0]
  ) {
    return raw.data.items[0].name as string;
  }
  return null;
}
// （或者使用 zod 等 schema 校验库来简化这个过程）
```

### 9.3 陷阱: as const 与展开运算符

```typescript
const original = { x: 1, y: 2 } as const;
const spread = { ...original };

// spread 的类型不是 { readonly x: 1; readonly y: 2 }
// 而是 { x: number; y: number } — as const 的效果丢失了！

// 原因: 展开运算符创建了一个新的对象，类型推断重新开始
// 解决方案: 再次使用 as const
const spreadAgain = { ...original } as const;
```

### 9.4 陷阱: 非空断言与短路求值的微妙交互

```typescript
// 这个看起来没问题？
const result = possiblyUndefined && possiblyUndefined.someProperty;
// 但如果有人改成：
const result = possiblyUndefined!.someProperty; // 行为不同！

// 第一种: possiblyUndefined 为 falsy 时结果是 falsy 值本身
// 第二种: possiblyUndefined 为 undefined/null 时抛出 TypeError
```

### 9.5 陷阱: as const 不能用于表达式

```typescript
let x = 5;
const y = x as const; // ❌ Error: A 'const' assertion can only be applied to a reference to enum member, string, number, boolean, array, or object literal.

// 原因: as const 只能作用于字面量值（literal），不能作用于变量
// 因为变量的值可能在运行时改变，无法确保"常量"
```

## 十、个人总结与心得

### 10.1 核心观点回顾

经过上面的详细探讨，我们来总结一下三种断言机制的定位：

| 特性 | `as` 类型断言 | `!` 非空断言 | `as const` 常量断言 |
|------|-------------|-------------|-------------------|
| **核心用途** | 告诉 TS "这是 X 类型" | 告诉 TS "这不是空值" | 让字面量保持最精确的类型 |
| **运行时影响** | 无 | 无 | 无 |
| **危险程度** | 中等（取决于使用方式） | 高（容易隐藏运行时错误） | 低（通常无害） |
| **推荐程度** | 必要时可用 | 尽量避免 | 推荐 |

### 10.2 心得体会

**1. 断言本质上是一种"权宜之计"**

TypeScript 的类型系统设计目标是提供尽可能好的类型安全。当你需要使用断言时，往往意味着某些地方的类型信息"断裂"了。这不一定是你做错了什么——DOM API 的限制、第三方库的类型缺陷等都是客观存在的——但每次使用断言都应该问自己：有没有更好的方式？

**2. 非空断言是"蜜糖砒霜"**

`!` 操作符非常方便，一行代码就能消除类型错误。但它也是静默运行时 bug 的头号元凶。我的个人经验是：**在一个大型项目中，80% 以上的 `!` 都可以通过更好的代码组织来避免**（比如提取公共的获取函数、使用异常处理模式等）。剩下的 20% 才是真正合理的使用场景。

**3. as const 是"免费午餐"**

与另外两种断言不同，`as const` 几乎只有好处没有坏处。它让类型更精确，同时还能防止意外修改（readonly）。唯一的"代价"是不能修改被断言的对象——但这通常是符合预期的行为。**建议在定义配置对象、常量映射等不变数据时，养成使用 `as const` 的习惯。**

**4. 断言 ≠ 类型转换**

这一点非常重要。很多从其他静态语言（如 Java、C#）转来的开发者会把类型断言当成"强制类型转换"。但 TypeScript 的断言**不会改变运行时的值**：

```typescript
let x = 'hello' as unknown as number;
console.log(typeof x); // "string" — 运行时仍然是字符串！
console.log(x + 1);    // "hello1" — 字符串拼接，不是数学运算
```

如果你需要真正的运行时类型转换，请使用显式的转换函数（如 `Number()`, `String()`, `parseInt()` 等）。

### 10.3 最终建议

```

│                                                     │
```
