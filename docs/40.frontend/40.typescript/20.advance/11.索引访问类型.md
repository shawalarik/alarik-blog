# 索引访问类型 —— T[K]、keyof、typeof 获取值类型

## 前言

索引访问类型（Indexed Access Types）是 TypeScript 类型系统的核心操作机制——**通过键名在编译期从对象类型中提取对应的值类型**。它与 JavaScript 运行时 `obj[key]` 的属性访问操作形成编译期等价，使得类型可以被查询、组合和变换，而非仅作为静态声明存在。

这一机制是 `Pick`、`Omit`、`Partial` 等内置工具类型的实现基础，也是编写泛型代码时的必备技能。

---

## 一、T[K] —— 索引访问类型的基础

### 1.1 核心概念

在 JavaScript 中，我们用 `obj['name']` 来获取对象属性的值。在 TypeScript 中，我们可以用完全相同的语法来**获取类型中某个属性的类型**：

```typescript
interface Person {
  name: string;
  age: number;
  email: string;
}

// 用属性名作为索引，取出对应值的类型
type Name = Person['name'];        // → string
type Age = Person['age'];          // → number
type Email = Person['email'];      // → string
```

**技术本质**：`T[K]` 在编译期的行为等价于运行时 `obj[key]` 的属性访问——键名决定取出的值类型。当 `K` 为字面量类型（如 `'name'`）时，返回该属性的确切类型；当 `K` 为联合类型时，返回所有匹配属性类型的联合。

> **为什么需要索引访问类型？**
>
> 在没有索引访问类型之前，如果你想"提取"一个类型的某个属性类型来复用，只能手动重复声明或使用 `typeof` 从值中推断：
>
> ```typescript
> // ❌ 旧方式：手动重复写类型——Person.name 改了这里也要跟着改
> type NameType = string;  // 和 Person['name'] 的定义耦合了
>
> // ✅ 索引访问方式：自动跟随 Person 定义变化
> type NameType2 = Person['name'];  // Person.name 改了这里自动同步
> ```
>
> 这就是**单一数据源（Single Source of Truth）原则在类型层面的体现**。

**底层原理**：TypeScript 编译器在处理 `T[K]` 时，会在内部执行以下步骤：

1. **解析 T**：获取类型 T 的完整结构信息（属性名、属性值类型）
2. **解析 K**：确定 K 是字面量类型还是联合类型
3. **分发匹配**：
   - 若 K 是单个字面量（如 `'name'`），直接查找 T 对应属性的值类型
   - 若 K 是联合类型（如 `'a'|'b'`），对联合中的每一项分别查找后合并为联合类型
4. **返回结果**：将匹配到的值类型作为结果

这个过程完全发生在编译期，不产生任何运行时代码。这也是 TypeScript 类型系统的核心优势之一——零运行时开销的类型计算。

**实际开发场景补充**：

```typescript
// 场景一：API 响应类型复用 —— 提取嵌套字段类型用于函数参数
interface ApiResponse<T> {
  code: number;
  data: T;
  message: string;
}

type UserResponse = ApiResponse<{
  id: number;
  name: string;
  avatar: string;
}>;

// 直接用索引访问提取内部数据类型
function renderUser(user: UserResponse['data']): string {
  return `${user.name} (ID: ${user.id})`;
}

// 场景二：事件系统 —— 从事件映射表提取事件载荷类型
interface EventMap {
  'user:login': { userId: string; timestamp: number };
  'user:logout': { userId: string };
  'post:created': { postId: string; authorId: string };
}

// 统一的事件处理器签名，通过索引访问保证载荷类型正确
function on<K extends keyof EventMap>(
  event: K,
  handler: (payload: EventMap[K]) => void
): void {
  // 实际注册逻辑...
}

on('user:login', ({ userId, timestamp }) => {
  console.log(`User ${userId} logged in at ${timestamp}`);
  // userId 自动推断为 string, timestamp 为 number
});

// 场景三：状态管理 —— 从全局状态提取子状态类型
interface RootState {
  user: { name: string; token: string; role: 'admin' | 'user' };
  theme: { mode: 'light' | 'dark'; primaryColor: string };
  app: { isLoading: boolean; error: string | null };
}

function useSelector<S>(selector: (state: RootState) => S): S {
  return null as S;
}

// 索引访问让选择器的返回类型精确对应子状态结构
const user = useSelector(state => state.user); // 推断为 RootState['user']
const themeMode = useSelector(state => state.theme.mode); // 推断为 'light' | 'dark'
```

**不同写法对比**：

| 写法 | 类型安全度 | 可维护性 | 适用场景 |
|------|-----------|---------|---------|
| `Person['name']` | 高（自动同步源类型） | 高（随源类型自动更新） | 需要引用已有类型的子类型时 |
| 手动写 `string` | 低（源类型改了不会报错） | 低（需要手动维护一致） | 独立的简单类型 |
| `Extract<typeof obj.key, ...>` | 中等 | 中等 | 值域和类型域混合使用的场景 |

### 1.2 同时获取多个属性的类型

最强大的地方在于：**索引可以是联合类型**，这样一次就能拿到多个属性类型的并集：

```typescript
interface Person {
  id: number;
  name: string;
  age: number;
  email: string;
}

// 用联合类型做索引，得到的是所有匹配属性类型的联合
type IdOrName = Person['id' | 'name'];     // → number | string
type BasicInfo = Person['name' | 'email']; // → string
type AllFields = Person['id' | 'name' | 'age' | 'email']; 
// → number | string
```

**设计理念**：TypeScript 的设计哲学是"类型即值"。既然运行时可以用 `obj[key]` 访问属性，那编译时也应该能用 `Type[Key]` 访问子类型。这种一致性让学习曲线变得平缓。

> **为什么联合索引返回的也是联合类型？**
>
> 这源于 TypeScript 编译器的**分布式索引访问（Distributed Indexed Access）**机制。当 K 为 `'a' | 'b'` 时，`T[K]` 等价于 `T['a'] | T['b']`——编译器会自动对联合中的每一项执行索引访问后再合并。这个行为和条件类型的分布式特性一脉相承，保证了类型操作的可预测性和一致性。

**更多实际场景示例**：

```typescript
// 场景一：表单校验 —— 提取可编辑字段的值类型联合
interface UserProfileForm {
  username: string;
  displayName: string;
  bio: string;
  avatarUrl: string;
  age: number;           // 数字输入
  isPublic: boolean;     // 开关
}

// 所有文本输入框共享同一种值处理逻辑
type TextFieldKeys = 'username' | 'displayName' | 'bio' | 'avatarUrl';
type TextFieldValues = UserProfileForm[TextFieldKeys]; // → string

function validateTextFields(value: TextFieldValues): string[] {
  const errors: string[] = [];
  if (typeof value !== 'string') errors.push('必须是字符串');
  if (value.length > 200) errors.push('长度不能超过200');
  return errors;
}

// 场景二：API 排序 —— 提取可用于排序的字段类型
interface Article {
  id: number;
  title: string;
  createdAt: Date;
  updatedAt: Date;
  viewCount: number;
  authorId: number;
}

type SortableField = 'createdAt' | 'updatedAt' | 'viewCount' | 'title';
type SortableValue = Article[SortableField]; // → Date | number | string

// 排序函数自动支持多种字段
function sortBy<T extends object, K extends SortableField>(
  items: T[],
  field: K,
  order: 'asc' | 'desc'
): T[] {
  return [...items].sort((a, b) => {
    const aVal = (a as any)[field] as SortableValue;
    const bVal = (b as any)[field] as SortableValue;
    if (aVal < bVal) return order === 'asc' ? -1 : 1;
    if (aVal > bVal) return order === 'asc' ? 1 : -1;
    return 0;
  });
}

// 场景三：数据库查询 —— 提取可筛选条件的字段类型
interface Product {
  id: number;
  name: string;
  price: number;
  category: string;
  inStock: boolean;
  createdAt: Date;
}

type FilterableKey = 'category' | 'inStock';
type FilterableValue = Product[FilterableKey]; // → string | boolean

const filters: Record<FilterableKey, FilterableValue> = {
  category: 'electronics',
  inStock: true,
};

// 类型安全：不能把数字赋给 filter 值
// @ts-expect-error
filters.category = 123;  // ❌ 不能将 number 赋给 string
```

**常见错误演示**：

```typescript
// ❌ 错误 1：用不存在的键做索引
type BadAccess = Person['salary'];  
// ❌ 错误：类型 "Person" 上不存在属性 "salary"

// ❌ 错误 2：用宽泛的类型做索引（某些场景下可能出问题）
type WideIndex = Person[string];  
// 在 TS 4.4+ 中这会报错，因为 string 太宽泛

// ✅ 正确做法：用 keyof 或明确的联合类型
type SafeIndex = Person[keyof Person];  // → string | number
```

### 1.3 用 `keyof` 一次性拿所有属性类型

当配合 `keyof` 使用时，可以一次性获取对象**所有属性值类型**的联合：

```typescript
interface Person {
  name: string;
  age: number;
  email: string;
}

// keyof Person 得到所有键的联合，再用它做索引
type AllValueTypes = Person[keyof Person];  
// 等价于 Person['name' | 'age' | 'email']
// → string | number
```

这个模式极其常见，后面会详细展开。

> **为什么 `T[keyof T]` 这个模式如此重要？**
>
> 它解决了"获取一个对象类型的**值域（value domain）**"这一通用需求。在很多场景中，我们并不关心具体的属性名，只关心这个对象的属性可能是什么**类型**——比如做运行时校验、做数据序列化、或者构建联合约束。
>
> ```typescript
> // 典型用途：泛型约束 —— 确保传入的值属于某个对象的合法值域
> function isValidPersonValue(value: Person[keyof Person]): boolean {
>   return value !== null && value !== undefined;
> }
>
> // 典型用途：默认值工厂 —— 为每种可能的值类型提供默认值
> const defaults: Record<keyof Person, Person[keyof Person]> = {
>   name: '',
>   age: 0,
>   email: '',
> };
> ```

**更多实际示例**：

```typescript
// 场景一：Redux action 的 payload 类型约束
interface UserActions {
  SET_USER: { id: number; name: string; token: string };
  UPDATE_PROFILE: { displayName: string; avatar?: string };
  LOGOUT: void;
}

// 提取所有 action 的 payload 类型
type ActionPayloads = UserActions[keyof UserActions];
// → { id: number; name: string; token: string } | { displayName: string; avatar?: string } | void

function dispatch<T extends keyof UserActions>(
  type: T,
  payload?: ActionPayloads & {}
): void {
  // payload 类型自动对应到具体 action 的载荷类型
}

dispatch('SET_USER', { id: 1, name: 'Alice', token: 'xxx' }); // ✅
dispatch('LOGOUT'); // ✅ (void 不需要 payload)
// @ts-expect-error
dispatch('SET_USER', { wrongField: 1 }); // ❌ payload 类型不匹配

// 场景二：数据库记录的值域提取
interface DbRecord {
  id: number;
  title: string;
  content: string;
  publishedAt: Date | null;
  viewCount: number;
  tags: string[];
  isDeleted: boolean;
}

type DbRecordValues = DbRecord[keyof DbRecord];
// → number | string | Date | null | boolean | string[]

// 用于运行时的值类型守卫
function isDbRecordValue(value: unknown): value is DbRecordValues {
  return (
    typeof value === 'number' ||
    typeof value === 'string' ||
    typeof value === 'boolean' ||
    value instanceof Date ||
    value === null ||
    Array.isArray(value)
  );
}

// 场景三：配置合并工具的类型安全实现
type ConfigValues = Record<string, any>[keyof Record<string, any>]; // → any

// 更实际的例子：确保 merge 的结果包含两个输入的所有值类型
function mergeConfigs<T, U>(base: T, override: U): T & U {
  return { ...base, ...override } as T & U;
}

const defaultConfig = { host: 'localhost', port: 3306, ssl: false };
const userConfig = { port: 5432, timeout: 5000 };

const merged = mergeConfigs(defaultConfig, userConfig);
// merged.port 的类型是 number（从两者都能推断）
```

## 二、数组与元组的索引访问

### 2.1 数组的数字索引

数组本质上是有数字索引签名的对象，所以也可以用索引访问类型：

```typescript
type ArrElement = Array<string>[0];    // → string
type NumArr = number[];                // 数字数组的类型
type NumArrElement = NumArr[number];   // → number

// 只读数组也一样
type ReadonlyArrElement = readonly string[]['0'];  // → string
```

**关键区别**：
- 用具体数字 `[0]` 取的是该位置的元素类型
- 用 `number` 类型做索引，拿到的是**所有位置元素类型的联合**

```typescript
type Tuple = [string, number, boolean];

type First = Tuple[0];           // → string （第一个元素）
type Second = Tuple[1];         // → number （第二个元素）
type AnyElement = Tuple[number]; // → string | number | boolean
```

**技术说明**：元组的数字索引访问遵循与对象属性索引相同的分发规则——字面量索引返回该位置元素的确切类型，`number` 类型索引触发联合类型分发，返回所有位置元素类型的并集。

> **底层原理：为什么元组可以用数字索引？**
>
> 在 TypeScript 内部，元组 `[string, number]` 被表示为一个具有数值属性签名的对象类型：
> ```
> {
>   0: string;
>   1: number;
>   length: 2;  // 元组自带 length 属性
> }
> ```
> 因此 `Tuple[0]` 实质上就是从上述结构中取出属性 `0` 的值类型 `string`。而 `Tuple[number]` 则是对所有数值键（`0 | 1`）做联合索引访问，得到 `string | number`。这也解释了为什么元组可以像数组一样用数字索引。

**更多实用场景示例**：

```typescript
// 场景一：提取 Promise resolve 的类型（利用元组解构）
async function fetchData(): Promise<[string, number, boolean]> {
  return ['data', 200, true];
}

// 用索引访问获取 Promise 返回的元组中各元素类型
type FetchResult = Awaited<ReturnType<typeof fetchData>>; // [string, number, boolean]
type DataType = FetchResult[0];    // string
type StatusCodeType = FetchResult[1]; // number
type SuccessType = FetchResult[2];   // boolean

// 场景二：函数参数列表的索引访问 —— 提取第 N 个参数的类型
declare function createUser(name: string, age: number, isAdmin: boolean): void;

type Params = Parameters<typeof createUser>; // [string, number, boolean]
type FirstParam = Params[0];  // string
type SecondParam = Params[1]; // number
type ThirdParam = Params[2];  // boolean

// 场景三：CSS 样式元组的类型安全处理
type CSSProperty = [property: string, value: string, priority?: 'important'];

const styles: CSSProperty[] = [
  ['color', 'red'],
  ['font-size', '14px'],
  ['margin', '0 auto'],
];

function getStyleValue(styles: CSSProperty[], index: number): CSSProperty[1] {
  return styles[index]?.[1]; // 返回值的类型是 string
}

// 场景四：路由参数的元组定义与提取
type RouteParams = [userId: string, postId: string];
type UserId = RouteParams[0]; // string
type PostId = RouteParams[1]; // string

function parseRoute(path: string): RouteParams {
  const match = path.match(/\/users\/([^/]+)\/posts\/([^/]+)/);
  return (match ? [match[1], match[2]] : ['', '']) as RouteParams;
}

const [userId, postId] = parseRoute('/users/123/posts/456');
// userId 和 postId 都自动推断为 string
```

### 2.2 元组支持 `length` 属性

元组还有一个特殊的可访问属性——`length`：

```typescript
type ThreeTuple = [string, number, boolean];
type Len = ThreeTuple['length'];  // → 3 （字面量类型）

type TwoTuple = [string, number];
type TwoLen = TwoTuple['length']; // → 2
```

这在泛型编程中非常有用，比如判断元组长度来做条件类型分支。

## 三、`keyof` 操作符 —— 拿到所有的"钥匙"

### 3.1 基本用法

`keyof` 操作符返回一个类型所有**公开属性键**的联合类型：

```typescript
interface User {
  id: number;
  name: string;
  email: string;
  isAdmin: boolean;
}

type UserKeys = keyof User;
// → 'id' | 'name' | 'email' | 'isAdmin'
```

**注意**：`keyof` 拿到的是**字面量联合类型**，不是 `string`！每个键都是精确的字面量。

> **为什么 `keyof` 返回的是字面量联合而不是 string？**
>
> 这是 TypeScript 类型系统设计中的核心决策之一。如果 `keyof { a: string }` 返回 `string`，那么 `T[keyof T]` 对任何对象类型都会返回 `string | number | ...` 的宽泛类型——完全失去了精确性。返回字面量联合使得 `keyof` 可以和索引访问 `T[K]`、泛型约束 `K extends keyof T` 等机制形成精密配合，实现精确的类型推导。
>
> 从编译器内部实现来看，`keyof` 本质上是遍历类型的属性声明列表，收集所有属性名字符串（或符号），然后构建成联合类型。这是一个 O(n) 操作，n 为属性的个数。对于大多数实际类型来说开销可以忽略不计。

**实际开发场景示例**：

```typescript
// 场景一：动态对象构建 —— 确保只添加合法的属性
function buildObject<T extends object>(
  template: T,
  entries: Array<{ key: keyof T; value: T[keyof T] }>
): T {
  const result = { ...template };
  for (const { key, value } of entries) {
    (result as any)[key] = value; // key 被约束为 T 的合法属性
  }
  return result;
}

interface Product {
  id?: number;
  name: string;
  price: number;
}

const product = buildObject({} as Product, [
  { key: 'name', value: '键盘' },       // ✅
  { key: 'price', value: 299 },         // ✅
  // @ts-expect-error
  { key: 'invalidKey', value: 'xxx' }, // ❌ "invalidKey" 不能赋给 keyof Product
]);

// 场景二：对象 diff —— 找出两个对象之间有差异的字段
function diffObjects<T extends object>(original: T, updated: T): Array<{
  field: keyof T;
  oldValue: T[keyof T];
  newValue: T[keyof T];
}> {
  const changes: Array<{ field: keyof T; oldValue: T[keyof T]; newValue: T[keyof T] }> = [];
  for (const key of Object.keys(original) as Array<keyof T>) {
    if (original[key] !== updated[key]) {
      changes.push({
        field: key,
        oldValue: original[key],
        newValue: updated[key],
      });
    }
  }
  return changes;
}

const oldConfig = { theme: 'light', fontSize: 14, lang: 'zh' };
const newConfig = { theme: 'dark', fontSize: 16, lang: 'zh' };

const changes = diffObjects(oldConfig, newConfig);
// changes[0].field → 'theme' | 'fontSize' | 'lang'
// changes[0].oldValue → string | number（自动推断）

// 场景三：ORM 查询构建器 —— 约束字段名和值类型的匹配
interface UserTable {
  id: number;
  username: string;
  email: string;
  created_at: Date;
}

class QueryBuilder<T extends object> {
  where<K extends keyof T>(field: K, value: T[K]): this {
    // 实现查询条件...
    return this;
  }
  
  select<K extends keyof T>(fields: K[]): Pick<T, K> {
    return {} as Pick<T, K>;
  }
  
  orderBy<K extends keyof T>(field: K, direction: 'asc' | 'desc'): this {
    return this;
  }
}

const query = new QueryBuilder<UserTable>()
  .where('username', 'alice')     // ✅ 值必须是 string（匹配 username 的类型）
  .where('created_at', new Date()) // ✅ 值必须是 Date
  // @ts-expect-error
  .where('id', 'not-a-number');   // ❌ 值应该是 number 不是 string
```

### 3.2 不同类型上的 `keyof`

`keyof` 对不同类型有不同的表现：

```typescript
// 1. 接口 / 类型别名
interface Point { x: number; y: number }
type PointKeys = keyof Point;  // → 'x' | 'y'

// 2. 对象字面量类型
type Config = { host: string; port: number };
type ConfigKeys = keyof Config;  // → 'host' | 'port'

// 3. 数组
type ArrKeys = typeof [];       // → (never[])[number] 的特殊处理
type ArrayKeys = keyof Array<any>; 
// → 'length' | 'toString' | 'toLocaleString' | 'pop' | 'push' | ... (很多方法)

// 4. 字符串/数字/布尔等原始类型
type StringKeys = keyof string;  // → Number | typeof IteratorSymbol | ...
type NumberKeys = keyof number;  // → toString | toFixed | ... 

// 5. 任何类型（top type）
type AnyKeys = keyof any;        // → string | number | symbol
```

**注意**：对原始类型如 `string`、`number` 使用 `keyof` 时，返回的是这些类型原型对象上的方法名与特殊符号，而非直觉预期的简单结果。日常开发中，`keyof` 主要应用于对象、接口或类类型。

### 3.3 映射类型的基石

`keyof` 是映射类型的灵魂。没有它就无法实现遍历对象属性的效果：

```typescript
// 把所有属性变成只读
type Readonly<T> = {
  readonly [P in keyof T]: T[P]
};

// 把所有属性变成可选
type Partial<T> = {
  [P in keyof T]?: T[P]
};
```

这里 `[P in keyof T]` 表示遍历 `T` 的每一个键 `P` 并创建对应属性。这种模式是 TypeScript 内置工具类型的实现基础。

## 四、`typeof` —— 从值到类型

### 4.1 基本概念

JavaScript 中有运行时的 `typeof` 运算符，TypeScript 在类型层面也有一个 `typeof`，但含义完全不同：

- **JS 的 `typeof`**：运行时检查值的类型，返回 `"string"`、`"number"` 等字符串
- **TS 的 `typeof`**：编译时推断表达式的**类型**，返回一个类型

```typescript
const myName = 'Alarik';
type MyNameType = typeof myName;  // → 'Alarik' （字面量类型！不是 string）

const config = {
  url: 'https://api.example.com',
  timeout: 5000,
  retries: 3,
};
type ConfigType = typeof config;
// → { url: string; timeout: number; retries: number }
```

**技术本质**：`typeof` 是 TypeScript 中从值域到类型域的唯一桥梁。它捕获变量的完整类型信息（包括字面量精度），使运行时定义的常量能在编译期参与类型运算。

> **为什么需要 typeof？**
>
> TypeScript 的类型系统是"可选的静态类型层"——你可以在值层面写代码（纯 JS），也可以在类型层面做约束。但两者之间需要一个桥梁来互通信息。`typeof` 就是这个桥梁的**单向通道**：从值到类型。
>
> ```typescript
> // 没有 typeof 时：你需要手动重复声明类型
> interface Config {
>   url: string;
>   timeout: number;
>   retries: number;
> }
> const config: Config = { url: '...', timeout: 5000, retries: 3 };
>
> // 有 typeof 时：让类型自动跟随值
> const config = { url: '...', timeout: 5000, retries: 3 };
> type Config = typeof config; // 类型从值自动推断
> ```
>
> 这在重构时尤其有价值——修改了值的结构后，类型会自动同步。

**底层原理——TypeScript 编译器如何处理 typeof**：

1. **标识符解析**：编译器找到 `typeof` 后面的表达式所绑定的变量
2. **类型推断**：根据变量的声明方式推断出完整类型：
   - `const` 声明 → 字面量类型（literal type）
   - `let/var` 声明 → 宽泛的基础类型
   - 函数声明 → 函数签名类型
   - 类声明 → 实例类型 + 静态成员类型
3. **类型输出**：将推断结果作为类型表达式使用

这个过程发生在类型检查阶段，不产生运行时代码。`typeof` 在编译后的 JS 中会被完全移除。

### 4.2 为什么 `typeof` 能得到精确的字面量类型？

这是因为 TypeScript 会根据变量的声明方式做**字面量类型推断**：

```typescript
// const 声明 → 推断为字面量类型
const str = 'hello';          // 类型是 'hello'
type StrType = typeof str;    // → 'hello'

// let 声明 → 扩展为基础类型
let num = 42;                 // 类型是 number
type NumType = typeof num;    // → number

// as const 断言 → 整个对象都变字面量
const settings = {
  theme: 'dark',
  fontSize: 14,
} as const;

type SettingsType = typeof settings;
// → { readonly theme: 'dark'; readonly fontSize: 14 }
```

### 4.3 `const` 对象 + `typeof` 的黄金组合

这是一个在实际项目中非常常见的模式：

```typescript
// 定义常量配置对象
const API_ENDPOINTS = {
  users: '/api/users',
  posts: '/api/posts',
  comments: '/api/comments',
} as const;

// 用 typeof 拿到精确的类型
type ApiEndpoints = typeof API_ENDPOINTS;
// → { readonly users: '/api/users'; readonly posts: '/api/posts'; readonly comments: '/api/comments' }

// 再用 keyof 拿到所有键
type EndpointKey = keyof typeof API_ENDPOINTS;
// → 'users' | 'posts' | 'comments'

// 最终实现类型安全的函数参数
function fetchApi(endpoint: EndpointKey) {
  return fetch(API_ENDPOINTS[endpoint]);
}

fetchApi('users');     // ✅ 正确
fetchApi('settings');  // ❌ 错误：不能将类型 '"settings"' 分配给类型 '"users" | "posts" | "comments"'
```

**实践要点**：这个组合模式（`const` 对象 + `as const` + `typeof` + `keyof`）是实际开发中高频使用的类型技巧。它以极低的标注成本获得完整的类型安全保证，且代码可读性良好。

> **为什么 `as const` 是这个模式的关键？**
>
> 没有 `as const` 时，TypeScript 对对象字面量的推断策略是"尽可能宽泛"：
> ```typescript
> const API_ENDPOINTS = {
>   users: '/api/users',    // 推断为 string（不是 '/api/users' 字面量）
>   posts: '/api/posts',    // 推断为 string
> };
> type Keys = keyof typeof API_ENDPOINTS; // → string！（不是 'users' | 'posts'）
> ```
> `as const` 触发了**顶层断言（top-level assertion）**，让编译器把每个属性值都收窄为字面量类型，整个对象变成只读的。这样 `keyof` 才能拿到精确的字面量联合。

**更多实际场景示例**：


## 五、`keyof` + `typeof` 组合使用

### 5.1 获取常量对象的键类型

这是上面模式的正式名称：

```typescript
const ROUTES = {
  home: '/',
  about: '/about',
  contact: '/contact',
} as const;

// keyof typeof 组合：先拿值类型，再拿键的联合
type RouteKey = keyof typeof ROUTES;
// → 'home' | 'about' | 'contact'

// 实际应用：路由守卫函数
function navigateTo(route: RouteKey): void {
  console.log(`Navigating to ${ROUTES[route]}`);
}
```

**执行顺序解释**：`keyof typeof ROUTES` 是从右往左读的：
1. `typeof ROUTES` → 拿到常量的类型 `{ readonly home: '/'; readonly about: '/about'; ... }`
2. `keyof ...` → 拿到这个类型的所有键 `'home' | 'about' | 'contact'`

### 5.2 枚举的替代方案

在不需要反向映射的场景下，`const` 对象 + `keyof typeof` 可以完美替代 `enum`：

```typescript
// 传统 enum 写法
enum Status {
  Pending = 'PENDING',
  Active = 'ACTIVE',
  Inactive = 'INACTIVE',
}

// const 对象写法（更推荐）
const STATUS = {
  Pending: 'PENDING',
  Active: 'ACTIVE',
  Inactive: 'INACTIVE',
} as const;

type StatusKey = keyof typeof STATUS;
// → 'Pending' | 'Active' | 'Inactive'

type StatusValue = (typeof STATUS)[StatusKey];  // 或 STATUS[keyof typeof STATUS]
// → 'PENDING' | 'ACTIVE' | 'INACTIVE'
```

**为什么推荐 `const` 对象？**
- `enum` 编译后会产生额外的 JS 代码（双向映射对象），增加包体积
- `const` 对象在编译后就是普通 JS 对象，零开销
- 配合 `as const` 能获得和 `enum` 同等的类型安全

## 六、`keyof` + 泛型约束 —— 经典模式

### 6.1 问题场景

假设我们要写一个通用的属性获取函数：

```typescript
function getProperty(obj: any, key: string) {
  return obj[key];
}

const user = { name: 'Alarik', age: 30 };

getProperty(user, 'name');  // 返回 any，丢失了类型信息
getProperty(user, 'xxx');   // 不存在的属性也不会报错
```

问题很明显：**完全没有类型安全**。我们想要的是——传什么对象、什么键，就返回什么类型的结果。

### 6.2 解决方案：K extends keyof T

```typescript
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Alarik', age: 30, email: 'alarik@example.com' };

const name = getProperty(user, 'name');   // → string ✅
const age = getProperty(user, 'age');     // → number ✅
const email = getProperty(user, 'email'); // → string ✅

// @ts-expect-error - 不能传入不存在的键
const invalid = getProperty(user, 'salary');  // ❌ 报错！
```

**逐步拆解这个签名**：
- `T`：对象本身的类型（由第一个参数自动推断）
- `K extends keyof T`：K 必须是 T 的合法键之一（这就是**泛型约束**！）
- `-> T[K]`：返回值类型是用 K 作为索引从 T 中取出的值类型

**设计理念**：这是 TypeScript 泛型约束的核心模式——通过 `K extends keyof T` 建立键名与对象类型的关联，使返回值类型 `T[K]` 完全由输入参数决定，无需手动标注，编译器完成全部类型推导。

> **底层原理：泛型约束如何工作？**
>
> 当你写 `K extends keyof T` 时，TypeScript 编译器在类型检查时执行以下逻辑：
>
> 1. **推断 T**：根据传入的 `obj` 参数推断出完整的对象类型
> 2. **提取 keyof T**：从 T 中提取所有键名的联合类型（如 `'name' | 'age' | 'email'`）
> 3. **约束 K**：`key` 参数的类型 K 必须是上述联合类型的子集——即只能传已存在的属性名
> 4. **解析 T[K]**：根据实际传入的 K 值，在 T 中查找对应位置的值类型作为返回值类型
>
> 这个过程的关键在于**延迟求值（deferred evaluation）**——T 和 K 的具体类型在调用点才被确定，而不是定义时就固定下来。这就是泛型的本质。

**更多实用场景示例**：

```typescript
// 场景一：类型安全的 lodash get —— 深度属性访问
function deepGet<T, K1 extends keyof T>(
  obj: T,
  key1: K1
): T[K1];

function deepGet<T, K1 extends keyof T, K2 extends keyof T[K1]>(
  obj: T,
  key1: K1,
  key2: K2
): T[K1][K2];

function deepGet<T, K1 extends keyof T, K2 extends keyof T[K1], K3 extends keyof T[K1][K2]>(
  obj: T,
  key1: K1,
  key2: K2,
  key3: K3
): T[K1][K2][K3];

function deepGet(obj: any, ...keys: string[]): any {
  return keys.reduce((acc, key) => acc?.[key], obj);
}

// API 响应数据
const apiResponse = {
  data: {
    user: {
      profile: { name: 'Alice', avatar: '/avatar.jpg' },
      settings: { theme: 'dark', notifications: true },
    },
  },
};

// 类型完全精确！
const userName = deepGet(apiResponse, 'data', 'user', 'profile', 'name'); // string
const theme = deepGet(apiResponse, 'data', 'user', 'settings', 'theme');   // string
// @ts-expect-error
const wrong = deepGet(apiResponse, 'data', 'user', 'nonexistent');          // ❌ 编译报错

// 场景二：类型安全的 setState —— React 组件中常见需求
interface ComponentState {
  isLoading: boolean;
  error: string | null;
  data: Array<{ id: number; title: string }>;
  page: number;
  filters: { keyword: string; category: string };
}

// 简化版 setState：只更新一个字段
function setField<T, K extends keyof T>(
  state: T,
  field: K,
  value: T[K]
): T {
  return { ...state, [field]: value };
}

let state: ComponentState = {
  isLoading: true,
  error: null,
  data: [],
  page: 1,
  filters: { keyword: '', category: '' },
};

// 每个字段赋值都有类型检查
state = setField(state, 'isLoading', false);         // ✅ boolean
state = setField(state, 'error', 'Network error');   // ✅ string | null
state = setField(state, 'page', 2);                  // ✅ number
state = setField(state, 'filters', {                 // ✅ 匹配 filters 的类型
  keyword: 'react',
  category: 'tutorial',
});
// @ts-expect-error
state = setField(state, 'page', 'not-a-number');     // ❌ 应该是 number

// 场景三：表单字段读写器 —— 自动处理不同字段的值类型
interface LoginForm {
  username: string;
  password: string;
  rememberMe: boolean;
  captcha?: string;
}

class FormStore<T extends object> {
  private data: T;

  constructor(initial: T) {
    this.data = initial;
  }

  // 类型安全的读取
  get<K extends keyof T>(key: K): T[K] {
    return this.data[key];
  }

  // 类型安全的写入
  set<K extends keyof T>(key: K, value: T[K]): void {
    this.data[key] = value;
  }

  // 批量更新
  update(changes: Partial<T>): void {
    Object.assign(this.data, changes);
  }
}

const loginForm = new FormStore<LoginForm>({
  username: '',
  password: '',
  rememberMe: false,
});

loginForm.set('username', 'alice');     // ✅ string
loginForm.set('rememberMe', true);     // ✅ boolean
const pwd = loginForm.get('password'); // ✅ string
// @ts-expect-error
loginForm.set('username', 123);        // ❌ 应该是 string
```

### 6.3 更复杂的例子：带默认值的属性获取

```typescript
function getOrDefault<T, K extends keyof T>(
  obj: T, 
  key: K, 
  defaultValue: T[K]
): T[K] {
  const value = obj[key];
  return value !== undefined ? value : defaultValue;
}

const config = { timeout: 5000, retries: 3, debug: false };

// 返回值类型自动推导为 number
const timeout = getOrDefault(config, 'timeout', 10000);     // → number
const retries = getOrDefault(config, 'retries', 5);         // → number
const debug = getOrDefault(config, 'debug', true);           // → boolean

// defaultValue 类型不匹配时直接报错
// @ts-expect-error
getOrDefault(config, 'debug', 'yes');  // ❌ boolean 不能赋值给 'yes'
```

### 6.4 另一个经典模式：Pick 工具类型

`keyof` + 映射类型构成了内置工具类型 `Pick` 的核心：

```typescript
/**
 * 从类型 T 中挑选一组属性 K，形成新的类型
 */
type Pick<T, K extends keyof T> = {
  [P in K]: T[P]
};

// 使用示例
interface UserInfo {
  id: number;
  name: string;
  email: string;
  phone: string;
  address: string;
  createdAt: Date;
}

// 公开 API 只需要部分字段
type PublicUser = Pick<UserInfo, 'id' | 'name'>;
// → { id: number; name: string }

// 用户自己能看到更多信息
type SelfViewUser = Pick<UserInfo, 'name' | 'email' | 'phone' | 'address'>
// → { name: string; email: string; phone: string; address: string }
```

## 七、嵌套索引访问 —— 深度类型导航

### 7.1 基本嵌套

索引访问可以链式嵌套，就像在 JavaScript 中连续访问深层属性一样：

```typescript
interface ApiResponse {
  code: number;
  message: string;
  data: {
    users: Array<{
      id: number;
      name: string;
      profile: {
        avatar: string;
        bio: string;
      };
    }>;
    total: number;
  };
}

// 逐层深入
type DataType = ApiResponse['data'];
// → { users: Array<{...}>; total: number }

type UsersType = ApiResponse['data']['users'];
// → Array<{ id: number; name: string; profile: {...} }>

type UserType = ApiResponse['data']['users'][0];
// → { id: number; name: string; profile: { avatar: string; bio: string } }

type AvatarType = ApiResponse['data']['users'][0]['profile']['avatar'];
// → string
```

**技术说明**：嵌套索引访问是单步索引访问的链式组合，每一步 `T[K]` 的输出作为下一步的输入类型。这与 JavaScript 运行时连续属性访问 `obj.a.b.c` 的求值路径在编译期形成精确对应。

### 7.2 嵌套访问 + 条件类型

结合条件类型，可以实现智能的深层路径提取：

```typescript
// 简化的 DeepPick 实现
type DeepPick<T, Path extends string> = 
  Path extends `${infer Key}.${infer Rest}`
    ? Key extends keyof T
      ? { [K in Key]: DeepPick<T[K], Rest> }
      : never
    : Path extends keyof T
      ? { [P in Path]: T[P] }
      : never;

interface Order {
  customer: {
    name: string;
    address: {
      city: string;
      street: string;
    };
  };
  items: Array<{ product: string; price: number }>;
}

type CustomerCity = DeepPick<Order, 'customer.address.city'>;
// → { customer: { address: { city: string } } }
```

> 注：上面的简化实现主要用于演示原理，完整的深度选取还需要处理数组索引等边缘情况。实际项目中建议使用 ts-toolbelt 等库提供的成熟实现。

## 八、实际应用案例

### 8.1 类型安全的 `getProperty` 函数

我们已经见过基本版本，这里给出增强版：

```typescript
/**
 * 安全地获取对象属性，支持嵌套路径
 */
function getDeepValue<T, K1 extends keyof T>(
  obj: T, 
  key1: K1
): T[K1];

function getDeepValue<T, K1 extends keyof T, K2 extends keyof T[K1]>(
  obj: T, 
  key1: K1, 
  key2: K2
): T[K1][K2];

function getDeepValue<T, K1 extends keyof T, K2 extends keyof T[K1], K3 extends keyof T[K1][K2]>(
  obj: T, 
  key1: K1, 
  key2: K2, 
  key3: K3
): T[K1][K2][K3];

function getDeepValue(obj: any, ...keys: string[]): any {
  return keys.reduce((acc, key) => acc?.[key], obj);
}

// 使用
const data = {
  user: {
    profile: {
      name: 'Alarik',
      preferences: { theme: 'dark' },
```

## 九、Record 类型背后的原理

### 9.1 Record 是什么？

`Record<K, V>` 是 TypeScript 内置的一个非常实用的工具类型，它的定义其实很简单：

```typescript
/**
 * Record<K, V> 的内部实现（简化版）
 *
 * 将 K 中的每个类型映射到 V，构造一个新的对象类型。
 */
type Record<K extends keyof any, V> = {
  [P in K]: V;
};
```

> **为什么 `K extends keyof any` 而不是 `K extends string`？**
>
> 因为 JavaScript 对象的键不仅限于字符串——还可以是数字和 Symbol：
>
> ```typescript
> const obj = {
>   1: 'number key',     // 数字键
>   [Symbol('id')]: 'symbol key', // Symbol 键
>   name: 'string key',  // 字符串键
> };
>
> type Keys = keyof typeof obj; // → string | number | symbol
> ```
>
> `keyof any` 正好等于 `string | number | symbol`，这是所有可能的对象键类型的联合。用 `keyof any` 作为约束可以确保 Record 同时支持这三种键类型。

**底层原理：Record 与索引签名的编译器等价性**

```typescript
// 方式一：使用 Record（推荐）
type StringToNumber = Record<string, number>;

// 方式二：使用索引签名
interface StringToNumber2 {
  [key: string]: number;
}

// 在 TypeScript 编译器内部，这两种写法被处理为完全相同的类型结构
// 它们之间是双向可赋值的
const a: StringToNumber = { a: 1, b: 2 };    // ✅
const b: StringToNumber2 = { c: 3, d: 4 };   // ✅

a = b;  // ✅ 完全兼容
b = a;  // ✅ 完全兼容
```

唯一的语义差异在于：`Record<'a'|'b', V>` 会产生确定属性的类型，而 `{[key: string]: V}` 是开放式的索引签名。前者允许额外的属性检查（excess property checking），后者不会。

### 9.2 逐行理解

```typescript
// K extends keyof any → K 必须是 string | number | symbol 的子集
// 因为 JavaScript 对象的键只能是这三种类型

// [P in K]: V → 对于 K 中的每一个 P，创建一个值为 V 类型的属性
```

所以 `Record<string, number>` 就等价于：

```typescript
{ [x: string]: number }  // 一个字符串索引签名，值必须是 number
```

而 `Record<'a' | 'b', boolean>` 等价于：

```typescript
{ a: boolean; b: boolean }  // 只有两个确定属性的对象
```

### 9.3 实际应用

```typescript
// 1. 字典/映射类型
type ScoreMap = Record<string, number>;
const scores: ScoreMap = {
  math: 95,
  english: 88,
  history: 92,
};

// 2. 角色权限映射
type Role = 'admin' | 'editor' | 'viewer';
type Permission = 'read' | 'write' | 'delete';

type RolePermissions = Record<Role, Permission[]>;

const permissions: RolePermissions = {
  admin: ['read', 'write', 'delete'],
  editor: ['read', 'write'],
  viewer: ['read'],
};

// 3. 状态机的状态定义

type StatusConfig = Record<Status, { label: string; color: string }>;

  idle: { label: '空闲', color: 'gray' },
  loading: { label: '加载中', color: 'blue' },
  success: { label: '成功', color: 'green' },
  error: { label: '错误', color: 'red' },
};

// 4. 与 keyof 结合使用
function createRecord<K extends string | number | symbol, V>(
  keys: K[],
  getValue: (key: K) => V
): Record<K, V> {
  const result = {} as Record<K, V>;
  for (const key of keys) {
    result[key] = getValue(key);
  }
  return result;
}

const flagMap = createRecord(['us', 'cn', 'jp'], (country) => ({
  name: country.toUpperCase(),
  continent: country === 'us' ? 'NA' : 'ASIA',
}));
// → Record<'us' | 'cn' | 'jp', { name: string; continent: string }>
```

> **实际项目中的使用建议**
>
> `Record` 最适合用于"键集合已知且有限"的场景。当键是开放式的（任意字符串都可以）时，使用索引签名更语义化。当需要精确控制每个属性的不同值类型时，使用手动定义的接口或交叉类型。
>
> **性能考量**：`Record<K, V>` 在编译期生成的类型结构是扁平的，对编译器来说处理成本很低。但当你用 `Record<string, ComplexType>` 然后大量使用时，每次属性访问都需要做一次索引查找。对于热路径代码（如渲染循环中的数据访问），考虑先用具体接口约束再赋值。

### 9.4 Record vs 索引签名

它们本质上是同一件事的不同写法：

```typescript
// 方式一：索引签名
interface IndexSignature {
  [key: string]: number;
}

// 方式二：Record（更语义化）
type UsingRecord = Record<string, number>;

// 两者完全等价
let a: IndexSignature = { x: 1, y: 2 };
let b: UsingRecord = { x: 1, y: 2 };

a = b; // ✅ 兼容
b = a; // ✅ 兼容
```

**何时选哪个？**
- 需要额外定义其他属性时 → **索引签名**（接口/类型别名中混用）
- 纯粹表示"键值映射"关系 → **Record**（更简洁、语义更清晰）

## 十、常见错误与陷阱

### 10.1 索引类型不是联合类型时报错

```typescript
interface Box<T> {
  value: T;
}

// ❌ 错误：这里的 T 不是联合类型，不能用 T 做索引
type Value = Box<string>['value'];  // ✅ 这个OK，因为 'value' 是字面量
type Bad = Box<string>[string];     // ⚠️ 这在某些版本可能有问题

// 正确做法：确保索引是字面量类型或其联合
type Keys = 'name' | 'age';
type Good = Person[Keys];  // ✅ Keys 是明确的字面量联合
```

### 10.2 `keyof` 只包含已知属性

```typescript
interface DynamicObj {
  name: string;
  [key: string]: unknown;  // 索引签名
}

type KeysOfDynamic = keyof DynamicObj;
// → 'name' | string （而不是只有 'name'！）

// 当有索引签名时，keyof 会包含 string（或 number）
// 这可能导致意外的行为
function printKey(obj: DynamicObj, key: keyof DynamicObj) {
  // key 的类型是 'name' | string，基本等于 string
  // 失去了精确约束的意义
  console.log(obj[key]);
}
```

**处理建议**：如果需要精确的键列表，避免在接口中同时声明具体属性和宽泛的索引签名。可改用 `Record` 类型或交叉类型来替代。

### 10.3 可选属性在索引访问中的表现

```typescript
interface OptionalProps {
  required: string;
  optional?: number;
  alsoOptional?: boolean;
}

// 用 keyof 访问可选属性时，值类型会加上 undefined
type RequiredVal = OptionalProps['required'];  // → string
type OptionalVal = OptionalProps['optional'];  // → number | undefined

// 所有值类型的联合也会包含 undefined
type AllValues = OptionalProps[keyof OptionalProps];
// → string | number | boolean | undefined
```

**记住**：可选属性 `prop?` 等价于 `prop | undefined`，这一点在索引访问中同样适用。

### 10.4 `as const` 断言的影响

```typescript
// 没有 as const
const colors = { primary: 'red', secondary: 'blue' };
type ColorKeys = keyof typeof colors;
// → string （因为 colors 的值被推断为 string，键也变成了 string）

// 有 as const
const strictColors = { primary: 'red', secondary: 'blue' } as const;
type StrictColorKeys = keyof typeof strictColors;
// → 'primary' | 'secondary' （精确的字面量联合！）
```

这是一个常见问题：`keyof typeof` 返回 `string` 而非预期的字面量联合类型，根本原因即在于缺少 `as const` 断言。

### 10.5 never 类型作为索引

```typescript
type Empty = {};
type Keys = keyof Empty;  // → never

type NeverIndex = Empty[never];  // → never

// 这个特性在条件类型中有重要用途：
type DistributiveUnion = 'a' | 'b' | 'c';
// 当用联合类型做索引时，TS 会分布式地处理每一项
// 但如果索引是 never，结果也是 never
```

## 十一、总结：知识体系全景图

本章知识体系总览：

```
索引访问类型生态系统

├── T[K] —— 基础索引访问
│   ├── 单个属性：Person['name'] → string
│   ├── 联合索引：Person['id'|'name'] → number|string
│   ├── 数字索引：Array<number>[0] → number
│   └── tuple 索引：[string,number][0] → string
│
├── keyof —— 键提取
│   ├── 对象键：keyof Person → 'name'|'age'|...
│   ├── 映射类型基础：[P in keyof T]
│   └── 泛型约束：K extends keyof T
│
├── typeof —— 值→类型转换
│   ├── 基本推断：typeof variable → Type
│   └── + as const：获得字面量类型
│
└── 组合模式
    ├── keyof typeof ConstObj → 常量对象的键联合
    ├── T[keyof T] → 所有值类型的联合
    ├── K extends keyof T → 泛型约束
    └── Record<K,V> ≡ {[P in K]: V}
```

### 总结

索引访问类型是 TypeScript 类型系统中连接值域与类型域的核心桥梁。它使类型成为可被查询、组合、变换的一等实体，而非孤立的静态声明。

`T[K]`、`keyof`、`typeof` 构成了索引访问类型的三个基本原语。它们是 `Pick`、`Omit`、`Partial` 等内置工具类型的实现基础，也是编写高质量泛型代码的必要前提。

**核心要点**：
> `T[K]` 按键取值类型，`keyof` 提取键名联合，`typeof` 从值推断类型。三者组合使用，覆盖了索引访问类型的全部基本操作。
