# 映射类型基础 —— `{ [P in K]: T }`、`readonly` 与 `?` 映射

> 映射类型（Mapped Types）是 TypeScript 中对已有类型的属性进行批量变换的机制。它通过遍历一个键的联合类型（通常由 `keyof` 获取），对每个属性应用统一的变换规则，从而生成一个新的类型。其设计思想与 `Array.prototype.map` 一脉相承——区别在于前者作用于运行时数组元素，后者作用于编译时类型属性。

## 一、什么是映射类型

### 1.1 本质理解

映射类型的核心行为是**遍历 + 变换**：以一个联合类型中的每个值为键，按相同的模式生成新属性。

与 `Array.map` 的对比：

```typescript
// 数组的 map：对每个元素做变换
const numbers = [1, 2, 3];
const doubled = numbers.map(n => n * 2); // [2, 4, 6]

// 映射类型：对每个属性做变换
interface Point {
  x: number;
  y: number;
}
type ReadonlyPoint = { readonly [K in keyof Point]: Point[K] };
// 结果：{ readonly x: number; readonly y: number; }
```

两者思路完全一致——遍历 → 变换 → 收集结果。映射类型可以理解为**类型层面的 `map` 操作**。

### 1.2 核心语法

映射类型的基本形式：

```typescript
type MappedType = {
  [P in K]: T
};
```

各部分含义：

| 部分 | 含义 |
|------|------|
| `[P in K]` | 遍历联合类型 K 中的每一个值，`in` 是映射类型专用的遍历操作符 |
| P | 当前遍历到的键名（类型变量） |
| T | 属性值的类型表达式 |

**关键注意**：`in` 操作符在此处不是 JavaScript 中检查属性是否存在的运算符，而是 TypeScript 映射类型专用的"遍历"操作符，语义上类似于 `for (const P of K)`。

## 二、基础语法详解

### 2.1 最简单的映射

```typescript
// 定义一组键名（联合类型）
type Keys = 'name' | 'age' | 'email';

// 用这些键名创建一个对象类型，所有属性都是 string
type User = {
  [K in Keys]: string
};

// 等价于：
// type User = {
//   name: string;
//   age: string;    // 注意：这里 age 也是 string，不是 number
//   email: string;
// }

const user: User = {
  name: '张三',
  age: '25',        // 字符串 "25"，不是数字 25
  email: 'zhangsan@example.com'
};
```

**用途**：当你拥有一组已知的键名时，可以用映射类型快速生成对应的对象结构，避免逐个手动定义。

### 2.2 使用 `keyof` 获取键

更常见的做法是结合 `keyof` 来获取某个类型的全部键：

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
  inStock: boolean;
}

// 提取 Product 的所有键，然后重新构造类型
type ProductCopy = {
  [K in keyof Product]: Product[K]
};

// ProductCopy 和 Product 完全等价！
// 这就是映射类型最基本的能力：基于一个类型创建"副本"
```

**要点**：`{ [K in keyof T]: T[K] }` 本质上就是对类型 T 做了一次浅层复制。虽然看起来没有变化，但它是所有高级映射的基础——一旦在遍历过程中引入修饰符或条件逻辑，就能产生各种有用的类型变换。

## 三、从接口到映射类型

### 3.1 场景引入

假设我们有这样一个人员信息接口：

```typescript
interface Person {
  name: string;
  age: number;
  email: string;
  address: string;
}
```

实际开发中，我们经常遇到以下需求：
- 表单编辑时，所有字段都应该是**可选的**（用户可以只填部分字段）
- 从服务器获取的数据应该是**只读的**（防止前端误修改）
- 提交数据时，某些字段是**必需的**

如果不用映射类型，你得为每种场景写一个新的接口：

```typescript
// 手动写的——繁琐且容易遗漏
interface PartialPerson {
  name?: string;
  age?: number;
  email?: string;
  address?: string;
}

interface ReadonlyPerson {
  readonly name: string;
  readonly age: number;
  readonly email: string;
  readonly address: string;
}
```

三个属性还好，如果有二十个呢？每次增删字段还要同步修改多个接口？这就是映射类型要解决的痛点——**用声明式的规则替代命令式的重复定义**。

### 3.2 用映射类型实现

```typescript
interface Person {
  name: string;
  age: number;
  email: string;
  address: string;
}

// 把每个属性变成可选 —— 加上 ? 修饰符
type OptionalPerson = {
  [K in keyof Person]?: Person[K]
};
// 等价于上面的 PartialPerson

// 把每个属性变成只读 —— 加上 readonly 修饰符
type ReadOnlyPerson = {
  readonly [K in keyof Person]: Person[K]
};
// 等价于上面的 ReadonlyPerson

// 使用示例
const partial: OptionalPerson = {
  name: '李四' // 只填一个也合法
};

const readOnly: ReadOnlyPerson = {
  name: '李四',
  age: 28,
  email: 'lisi@example.com',
  address: '北京市'
};

// readOnly.name = '王五'; // ❌ 错误！不能修改只读属性
```

**核心价值**：映射类型实现了"声明式地描述类型变换规则"，而不是命令式地逐个写出。规则写一次，任意大小的类型都能适用。

### 3.3 同时添加多个修饰符

```typescript
type ReadonlyOptional<T> = {
  readonly [K in keyof T]?: T[K]
};

type Result = ReadonlyOptional<Person>;
// 每个属性既是只读的，又是可选的
// { readonly name?: string; readonly age?: number; ... }
```

修饰符的位置有讲究：`readonly` 在 `[K in ...]` 前面，`?` 在 `T[K]` 后面。

## 四、内置映射类型工具解析

TypeScript 内置了几个常用的映射类型工具，它们本质上就是我们上面写的那些模式的封装。

### 4.1 `Readonly` —— 全部属性只读

**源码本质**：

```typescript
// TypeScript 内置实现（简化版）
type MyReadonly<T> = {
  readonly [P in keyof T]: T[P];
};
```

**使用示例**：

```typescript
interface Config {
  apiUrl: string;
  timeout: number;
  retries: number;
}

// 使用内置工具
type ReadonlyConfig = Readonly<Config>;
// 等价于：
// {
//   readonly apiUrl: string;
//   readonly timeout: number;
//   readonly retries: number;
// }

const config: ReadonlyConfig = {
  apiUrl: 'https://api.example.com',
  timeout: 5000,
  retries: 3
};

// config.apiUrl = 'https://new.api.com'; // ❌ 不能赋值，因为是只读的
```

**说明**：`Readonly` 将类型的每个属性标记为 `readonly`，禁止对这些属性进行重新赋值。编译器会在赋值操作处报错，从而在静态分析阶段拦截意外的数据修改。

**应用场景**：
- API 返回的配置对象
- 函数参数中的常量对象
- Redux store 中的 state（配合 immutable 更新模式）

**坑点**：`Readonly` 是**浅只读**！嵌套对象的内部属性仍然可以被修改：

```typescript
interface NestedConfig {
  database: {
    host: string;
    port: number;
  };
}

const cfg: Readonly<NestedConfig> = {
  database: {
    host: 'localhost',
    port: 3306
  }
};

// cfg.database = { host: '...', port: 5432 }; // ❌ 这行会报错
cfg.database.host = 'remotehost';             // ✅ 但这行不会报错！嵌套对象不受保护
```

**总结**：`Readonly` 只保证第一层属性不能被整体替换，不保证深层不可变。需要深度只读的话，需要自己实现递归映射（后面会讲）。

### 4.2 `Partial` —— 全部属性可选

**源码本质**：

```typescript
// TypeScript 内置实现
type MyPartial<T> = {
  [P in keyof T]?: T[P];
};
```

**使用示例**：

```typescript
interface UserProfile {
  username: string;
  avatar: string;
  bio: string;
  location: string;
  website: string;
}

function updateUser(id: string, fields: Partial<UserProfile>) {
  // 用户可以只提交想修改的字段
  console.log(`更新用户 ${id}`, fields);
}

// ✅ 只更新昵称
updateUser('123', { username: 'new_name' });

// ✅ 同时更新多个字段
updateUser('456', { bio: '我是开发者', location: '北京' });

// ✅ 甚至传空对象也可以（表示"什么都没改"）
updateUser('789', {});
}
```

**说明**：`Partial` 将类型的每个属性变为可选（添加 `?` 修饰符）。这是 HTTP PATCH 请求语义的类型级表达——客户端只需提交需要更新的字段子集，服务端进行合并处理。

**应用场景**：
- PATCH 请求的部分更新
- 表单的渐进式填写
- 组件的可选 props
- 合并默认配置与用户自定义配置

**坑点**：`Partial` 会把**所有**属性变成可选，包括那些逻辑上不应该省略的字段：

```typescript
interface LoginRequest {
  username: string;
  password: string;  // 密码怎么能可选呢？
  rememberMe: boolean;
}

// 如果不加区分地用 Partial
function login(credentials: Partial<LoginRequest>) {
  // credentials.password 可能是 undefined！
  // 这在登录场景中很危险
}
```

**解决方法**：对于这种场景，应该明确指定哪些字段可选，而不是一刀切用 `Partial`。

### 4.3 `Required` —— 全部属性必需

**源码本质**：

```typescript
// TypeScript 内置实现 —— 注意这里的 - 号！
type MyRequired<T> = {
  [P in keyof T]-?: T[P];  // -? 表示移除可选修饰符
};
```

**使用示例**：

```typescript
interface DraftArticle {
  title?: string;
  content?: string;
  tags?: string[];
  publishDate?: Date;
}

// 草稿状态下字段都是可选的
let draft: DraftArticle = {
  title: '我的第一篇文章'
};

// 发布时，要求所有字段都必须填写
function publish(article: Required<DraftArticle>) {
  console.log('发布文章:', article);
}

// publish(draft); // ❌ 错误！缺少 content、tags、publishDate

const completeArticle: Required<DraftArticle> = {
  title: '深入理解映射类型',
  content: '这是一篇详细的技术文章...',
  tags: ['TypeScript', '进阶'],
  publishDate: new Date()
};

publish(completeArticle); // ✅ 通过
```

**说明**：`Required` 移除所有属性的 `?` 可选修饰符，将宽松的草稿类型收严为完整的提交类型。典型应用是将"构建中"的数据结构转换为"已完成"状态时的类型约束。

**应用场景**：
- 从草稿状态转换到完成状态
- 表单最终提交前的校验
- 将宽松的类型约束收严

**设计理念**：`Partial` 和 `Required` 是一对互逆操作——前者加 `?`，后者减 `?`。它们代表了两种常见的数据生命周期状态："构建中"和"已完成"。

## 五、`?` 可选修饰符映射

### 5.1 添加可选修饰符

在属性值后面加上 `?`，就把该属性变为可选：

```typescript
interface StrictForm {
  firstName: string;
  lastName: string;
  phone: string;
  company: string;
}

type LooseForm = {
  [K in keyof StrictForm]?: StrictForm[K]
};

const form1: LooseForm = {
  firstName: '张'
}; // ✅ 其他字段都可以省略

const form2: LooseForm = {}; // ✅ 全部省略也可以
```

### 5.2 移除可选修饰符（减号 `-`）

这是 `Required` 工具的核心机制——用减号 `-` 移除 `?`：

```typescript
interface LooseConfig {
  host?: string;
  port?: number;
  ssl?: boolean;
}

type StrictConfig = {
  [K in keyof LooseConfig]-?: LooseConfig[K]
  //        ^^
  //   这个减号表示"移除 ? 修饰符"
};

// 现在 StrictConfig 的所有属性都是必需的
const cfg: StrictConfig = {
  host: 'localhost',
  port: 8080,
  ssl: true
  // 缺任何一个都会报错
};
```

**语法要点总结**：

| 写法 | 含义 |
|------|------|
| `[K in T]: U` | 保持原有的可选/必需状态不变 |
| `[K in T]?: U` | 强制设为可选（添加 `?`） |
| `[K in T]-?: U` | 强制设为必需（移除 `?`） |

**总结**：`+` 可以显式添加修饰符（但通常省略 `+` 就是隐式添加），`-` 用于移除。这个加减号的语法设计与正则表达式的 flag 操作类似，语义清晰直观。

## 六、`readonly` 映射

### 6.1 添加只读修饰符

```typescript
interface MutableSettings {
  theme: 'light' | 'dark';
  language: string;
  fontSize: number;
}

type ImmutableSettings = {
  readonly [K in keyof MutableSettings]: MutableSettings[K]
};

const settings: ImmutableSettings = {
  theme: 'dark',
  language: 'zh-CN',
  fontSize: 16
};

// settings.theme = 'light'; // ❌ 无法赋值，因为它是只读属性
```

### 6.2 移除只读修饰符

同样可以用减号 `-` 移除 `readonly`：

```typescript
interface FrozenConfig {
  readonly apiKey: string;
  readonly endpoint: string;
  readonly version: string;
}

type ThawedConfig = {
  -readonly [K in keyof FrozenConfig]: FrozenConfig[K]
  // ^^^^^^^^^
  // 移除 readonly，让属性可被重新赋值
};

const thawed: ThawedConfig = {
  apiKey: 'abc123',
  endpoint: '/api/v1',
  version: '2.0'
};

thawed.apiKey = 'new-key-456'; // ✅ 现在可以修改了
```

**语法要点总结**：

| 写法 | 含义 |
|------|------|
| `[K in T]: U` | 保持原有读写状态不变 |
| `readonly [K in T]: U` | 强制设为只读（添加 `readonly`） |
| `-readonly [K in T]: U` | 强制设为可写（移除 `readonly`） |

**说明**：`-readonly` 的实际用途是在接收到一个带有 `readonly` 约束的类型后，需要在其基础上进行定制修改的场景——例如将只读的默认配置模板转换为可编辑的用户配置副本。

### 6.3 实际应用案例

```typescript
// 场景：默认配置（只读）+ 用户覆盖（可写）
interface DefaultTheme {
  readonly primaryColor: '#1890ff';
  readonly borderRadius: '4px';
  readonly fontFamily: 'system-ui';
}

// 创建用户可定制的主题（移除 readonly）
type CustomizableTheme = {
  -readonly [K in keyof DefaultTheme]: DefaultTheme[K]
};

function createTheme(overrides: Partial<CustomizableTheme>): DefaultTheme {
  const defaults: DefaultTheme = {
    primaryColor: '#1890ff',
    borderRadius: '4px',
    fontFamily: 'system-ui'
  };

  return { ...defaults, ...overrides } as DefaultTheme;
}

const myTheme = createTheme({
  primaryColor: '#f5222d'  // 只覆盖颜色，其他保持默认
});
```

**设计理念**：通过控制 `readonly` 修饰符的增删，我们可以精确管理数据的"可变性边界"——哪些数据在哪个阶段允许修改，哪些必须保持不变。这在状态管理和数据流设计中非常重要。

## 七、映射类型 + 联合类型

### 7.1 用联合类型作为键

映射类型的键不一定非要从 `keyof` 某个类型来获取，可以直接用一个字面量联合类型：

```typescript
// 定义一组特征标志
type FeatureFlags = {
  [K in 'darkMode' | 'notifications' | 'autoSave' | 'betaFeatures']: boolean
};

// 等同于：
// interface FeatureFlags {
//   darkMode: boolean;
//   notifications: boolean;
//   autoSave: boolean;
//   betaFeatures: boolean;
// }

const flags: FeatureFlags = {
  darkMode: true,
  notifications: false,
  autoSave: true,
  betaFeatures: false
};
```

**适用场景**：当键名集合固定且已知时（如配置项、特征开关等），直接用字面量联合类型作为键来源比先定义接口再取 `keyof` 更简洁。

### 7.2 不同键对应不同类型

通过条件类型，可以让不同的键拥有不同类型的值：

```typescript
type FieldConfig = {
  // 不同字段有不同的校验规则
  username: { required: true; minLength: 3; maxLength: 20 };
  email:    { required: true; pattern: RegExp };
  age:      { required: false; min: 0; max: 150 };
  bio:      { required: false; maxLength: 500 };
};

type FieldValue<T> = {
  [K in keyof T]: T[K]['required'] extends true
    ? never          // 必填字段在"可选值"类型中不存在
    : T[K] extends { maxLength: infer L }
      ? string       // 有 maxLength 限制的是字符串
      : T[K] extends { min: infer _Min; max: infer _Max }
        ? number     // 有 min/max 限制的是数字
        : unknown
};

// 更实用的例子：根据键名推断值的类型
type HttpHeader = {
  'Content-Type': string;
  'Authorization': string;
  'X-Request-ID': string;
  'Accept': string;
};

// 为每个请求头设置初始值
type HeaderDefaults = {
  [K in keyof HttpHeader]: K extends 'Content-Type'
    ? 'application/json'
    : K extends 'Accept'
      ? '*/*'
      : string
};

const defaults: HeaderDefaults = {
  'Content-Type': 'application/json',  // 固定默认值
  'Authorization': '',                 // 需要后续填充
  'X-Request-ID': '',
  Accept: '*/*'                        // 固定默认值
};
```

### 7.3 动态键名映射

```typescript
// 根据事件名称自动生成事件处理器类型
type EventMap = {
  click: { x: number; y: number };
  keydown: { key: string; code: string };
  scroll: { scrollTop: number; scrollLeft: number };
};

type EventHandler = {
  [K in keyof EventMap]: (event: EventMap[K]) => void
};

// 等价于：
// interface EventHandler {
//   click: (event: { x: number; y: number }) => void;
//   keydown: (event: { key: string; code: string }) => void;
//   scroll: (event: { scrollTop: number; scrollLeft: number }) => void;
// }

const handlers: EventHandler = {
  click: ({ x, y }) => console.log(`点击位置: (${x}, ${y})`),
  keydown: ({ key }) => console.log(`按下按键: ${key}`),
  scroll: ({ scrollTop }) => console.log(`滚动位置: ${scrollTop}`)
};
```

**设计理念**：当键和值之间存在明确的对应关系时，映射类型能够保证它们的一致性——增加一个事件时，编译器会提醒你也添加对应的处理器。

## 八、嵌套映射 —— 深层变换

### 8.1 为什么需要嵌套映射

前面提到过，内置的 `Readonly` 和 `Partial` 都是**浅层**操作。如果我们需要对嵌套对象的所有层级做变换，就需要递归/嵌套映射。

### 8.2 实现 DeepReadonly

```typescript
type DeepReadonly<T> = {
  readonly [P in keyof T]: T[P] extends object
    ? DeepReadonly<T[P]>   // 如果是对象，递归处理
    : T[P]                 // 如果是基本类型，保持原样
};

// 测试
interface UserInfo {
  name: string;
  profile: {
    avatar: string;
    contacts: {
      email: string;
      phone: string;
    };
  };
  tags: string[];
}

type DeepUserInfo = DeepReadonly<UserInfo>;
// 结果：
// {
//   readonly name: string;
//   readonly profile: {
//     readonly avatar: string;
//     readonly contacts: {
//       readonly email: string;
//       readonly phone: string;
//     };
//   };
//   readonly tags: readonly string[];  // 数组也变成了只读
// }

const user: DeepUserInfo = {
  name: 'Alice',
  profile: {
    avatar: 'avatar.jpg',
    contacts: {
      email: 'alice@example.com',
      phone: '13800138000'
    }
  },
  tags: ['developer']
};

// user.name = 'Bob';                       // ❌ 第一层就拦截
// user.profile.avatar = 'new.jpg';         // ❌ 第二层也被拦截
// user.profile.contacts.email = 'a@b.com'; // ❌ 第三层同样拦截
// user.tags.push('designer');              // ❌ 数组也不能修改
```

**说明**：浅层 `Readonly` 仅约束顶层属性不可被整体替换；`DeepReadonly` 通过条件类型判断属性值是否为对象类型，若是则递归施加 `readonly` 约束，从而实现对所有嵌套层级的不变性保护。

**坑点**：要注意循环引用的问题！如果类型中存在互相引用，`DeepReadonly` 可能导致无限递归：

```typescript
// ⚠️ 危险！可能导致 TypeScript 编译器栈溢出
interface Node {
  value: string;
  next?: Node;  // 自引用
}

// type DeepNode = DeepReadonly<Node>;  // 可能出问题！

// 安全的做法是限制递归深度或排除特定情况
type SafeDeepReadonly<T, Depth extends number = 10> = {
  readonly [P in keyof T]: [Depth] extends [never]
    ? never
    : T[P] extends object
      ? SafeDeepReadonly<T[P], Depth extends 10 ? never : Depth>
      : T[P]
};
```

### 8.3 实现 DeepPartial

同理，我们也可以实现深层可选：

```typescript
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object
    ? DeepPartial<T[P]>
    : T[P]
};

interface Settings {
  ui: {
    theme: { light: LightColors; dark: DarkColors };
    sidebar: { width: number; collapsed: boolean };
  };
  api: {
    baseUrl: string;
    timeout: number;
  };
};

type PartialSettings = DeepPartial<Settings>;

const s: PartialSettings = {
  ui: {
    theme: {
      dark: { primary: '#fff' }  // 只需要写这一层
      // light、sidebar 都不需要
    }
    // api 整个都不需要
  }
}; // ✅ 合法！每一层的每个属性都是可选的
```

**应用场景**：
- 大型配置对象的渐进式构建
- 树形数据的部分更新
- 复杂表单的多步填写

### 8.4 实现DeepRequired

```typescript
type DeepRequired<T> = {
  [P in keyof T]-?: T[P] extends object
    ? DeepRequired<T[P]>
    : NonNullable<T[P]>  // 同时排除 null 和 undefined
};

interface MaybeData {
  user?: {
    name?: string;
    profile?: {
      avatar?: string | null;  // 既可能缺失，又可能是 null
    };
  } | null;
}

type CompleteData = DeepRequired<MaybeData>;
// 结果：所有层级的属性都变成了必需且非 null 的

const data: CompleteData = {
  user: {
    name: '必填',
    profile: {
      avatar: '必须有值，不能是 null'
    }
  }
  // 每一层都不能少，null 也不行
};
```

**总结**：嵌套映射的核心在于**条件类型 + 递归**的组合。判断当前属性是否为对象，如果是就递归处理，否则就返回本身。这种模式在类型编程中非常常见。

## 九、实际应用案例

### 9.1 API 响应类型转换

```typescript
// 服务端返回的数据格式（字段可能是 snake_case）
interface RawApiResponse {
  user_id: number;
  user_name: string;
  created_at: string;
  is_active: boolean;
  profile_image: string | null;
}

// 我们希望转成 camelCase 且类型安全
type CamelCase<S extends string> = S extends `${infer P}_${infer Q}`
  ? `${P}${Capitalize<CamelCase<Q>>}`
  : S;

// 映射类型：转换键名 + 处理 null
type ApiResponse<T> = {
  [K in keyof T as CamelCase<K & string>]:
    null extends T[K]           // 如果原始类型包含 null
      ? Exclude<T[K], null> | undefined  // 则转为可选（null → undefined）
      : T[K]
};

type CleanResponse = ApiResponse<RawApiResponse>;
// 结果：
// {
//   userId: number;
//   userName: string;
//   createdAt: string;
//   isActive: boolean;
//   profileImage?: string;  // 原 string | null → string | undefined（即 optional）
// }
```

### 9.2 表单数据校验类型

```typescript
// 定义表单字段的元信息
interface FormFieldMeta {
  type: 'text' | 'number' | 'email' | 'password';
  label: string;
  placeholder: string;
  required: boolean;
  validator?: (value: unknown) => string | null;  // 返回错误信息或 null
}

// 注册表单的字段定义
interface RegistrationFields {
  username: FormFieldMeta;
  password: FormFieldMeta;
  email: FormFieldMeta;
  confirmPassword: FormFieldMeta;
  inviteCode: FormFieldMeta;
}

// 从字段元信息提取值的类型
type FormValues<T> = {
  [K in keyof T]: T[K] extends { type: infer U }
    ? U extends 'number' ? number
      : U extends 'email' | 'password' | 'text'
        ? string
        : never
    : never
};

type RegistrationValues = FormValues<RegistrationFields>;
// { username: string; password: string; email: string; confirmPassword: string; inviteCode: string }

// 自动提取必填字段
type RequiredFieldNames<T> = {
  [K in keyof T]: T[K] extends { required: true } ? K : never
}[keyof T];

type RequiredFields = RequiredFieldNames<RegistrationFields>;
// "username" | "password" | "email" | "confirmPassword"
// （inviteCode 的 required 是 false，所以被过滤掉了）
```

### 9.3 对象选取（Pick）与 排除（Omit）

这两个也是基于映射类型实现的常用工具：

```typescript
// Pick —— 选取指定属性
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// Omit —— 排除指定属性
type MyOmit<T, K extends keyof any> = {
  [P in Exclude<keyof T, K>]: T[P]
};

interface Article {
  id: number;
  title: string;
  content: string;
  authorId: number;
  createdAt: Date;
  updatedAt: Date;
  isDeleted: boolean;
}

// 给前端展示时，不需要内部字段
type ArticleDTO = MyOmit<Article, 'authorId' | 'isDeleted'>;
// 只保留 id, title, content, createdAt, updatedAt

// 创建文章时，不允许传 id 和时间戳
type CreateArticleInput = MyPick<Article, 'title' | 'content'>;
// 只有 title 和 content
```

**说明**：
- **Pick**：从原始类型中选取指定的属性子集，构造一个新的子类型。
- **Omit**：从原始类型中排除指定的属性，保留剩余属性。内部实现依赖 `Exclude` 过滤键联合类型后再映射。

## 十、常见陷阱与注意事项

### 10.1 `never` 在映射中的作用

当映射的键联合类型中出现 `never` 时，整个映射结果为空对象：

```typescript
type Keys = 'a' | 'b' | never;  // 'a' | 'b' | never 简化为 'a' | 'b'

type Mapped = {
  [K in Keys]: boolean
};
// { a: boolean; b: boolean; } —— 正常

// 但如果只有 never：
type EmptyKeys = never;

type EmptyMapped = {
  [K in EmptyKeys]: boolean
};
// {} —— 空对象类型！
```

**为什么这很重要？** 因为在条件类型的过滤操作中，我们常常利用这个特性来"删除"不想保留的键：

```typescript
// 只保留函数类型的属性
type FunctionProperties<T> = {
  [K in keyof T as T[K] extends Function ? K : never]: T[K]
};

class MyClass {
  name = 'test';
  greet() { return 'hello'; }
  farewell() { return 'bye'; }
}

type Funcs = FunctionProperties<MyClass>;
// { greet: () => string; farewell: () => string }
// name 被过滤掉了，因为它的值不是函数
```

**原理**：当条件不满足时返回 `never` 作为新的键名，而 `never` 键会被自动忽略，从而实现"过滤"效果。这是一种非常巧妙的类型体操技巧。

### 10.2 symbol 键的处理

映射类型默认**不会**特殊处理 `symbol` 类型的键（除非显式包含或排除）：

```typescript
const sym = Symbol('mySymbol');

interface WithSymbol {
  name: string;
  [sym]: number;  // symbol 键
}

type Mapped = {
  [K in keyof WithSymbol]: WithSymbol[K]
};

// Mapped 包含 name 和 symbol 键
// 但在某些旧版本 TS 中可能会有差异

// 如果只想映射字符串键：
type StringKeysOnly<T> = {
  [K in Extract<keyof T, string>]: T[K]
};
```

**注意**：在使用 `keyof` 获取键时，返回的联合类型**同时包含 string、number 和 symbol** 三种类型的键。如果你只想处理字符串键，记得用 `Extract` 过滤。

### 10.3 数组/元组类型的映射

映射类型不仅可以作用于普通对象，还可以作用于数组/元组：

```typescript
// 对数组元素做映射
type ReadonlyArray<T> = readonly T[];

// 对元组做映射 —— 会改变元组的结构
type ReadonlyTuple<T extends readonly unknown[]> = readonly [...T];

type RT = ReadonlyTuple<[string, number, boolean]>;
// readonly [string, number, boolean]

// 让元组每个元素变为可选
type PartialTuple<T extends readonly unknown[]> = {
  [K in keyof T]?: T[K]
};

type PT = PartialTuple<[string, number, boolean]>;
// [string?, number?, boolean?]  —— 变成了可选元组
```

### 10.4 映射类型不会展开交叉类型

```typescript
type A = { a: string };
type B = { b: number };

type Cross = A & B;  // { a: string } & { b: number }

type MappedCross = {
  [K in keyof Cross]: Cross[K]
};
// { a: string; b: number }
// 注意：结果是展开后的，不是交叉形式
```

### 10.5 `as` 重映射（键名变换）

TypeScript 支持在映射类型中使用 `as` 子句对键进行重映射（re-mapping），这是一个非常强大的特性：

```typescript
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
};

interface Person {
  name: string;
  age: number;
}

type PersonGetters = Getters<Person>;
// {
//   getName: () => string;
//   getAge: () => number;
// }
```

**说明**：`as` 重映射允许在遍历过程中对键名进行变换。它接受一个模板字面量表达式作为新的键名，结合 `Capitalize`、`CamelCase` 等内置字符串类型操作，可以实现批量的、规则统一的键名转换。这在生成 getter/setter 类型、API 数据格式转换等场景中非常有用。

### 11.3 设计哲学总结

映射类型体现了 TypeScript 类型系统的几个核心理念：

1. **DRY（Don't Repeat Yourself）**：一次声明，处处生效。不需要为相似的结构重复编写类型定义。
2. **声明式思维**：描述"我要什么"，而不是"怎么做"。映射类型让你专注于变换规则本身。
3. **类型安全自动化**：当源类型发生变化时，映射出的类型自动同步更新，不会出现不一致。
4. **组合优于硬编码**：简单的映射类型可以组合成复杂的类型变换管道，灵活应对各种需求。

## 个人总结

映射类型是我认为 TypeScript 中**性价比最高**的高级特性之一。它的语法简洁直观（就是一个带 `for...of` 风格的花括号），但能力却极其强大——内置的 `Partial`、`Required`、`Readonly`、`Pick`、`Omit` 全部基于它实现。

学习建议：
1. 先从内置工具入手，理解它们各自的用途
2. 尝试手写一遍这些内置工具的实现（就像本文做的那样）
3. 在项目中主动寻找可以使用映射类型的地方（比如替代手动写的可选接口）
4. 逐步尝试嵌套映射和 `as` 重映射等进阶用法

记住一句话：**映射类型 = 类型世界的 `Array.prototype.map`**。如果你熟悉数组操作的 map/filter/reduce，那么映射类型及其组合对你来说就不会陌生——它们是同一套思想在不同维度的体现。
