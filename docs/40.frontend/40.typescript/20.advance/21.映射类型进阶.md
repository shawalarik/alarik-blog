# 映射类型进阶 —— 键重映射（`as` 子句）、过滤属性与"铁三角"组合

> 基础映射类型对每个属性执行统一的变换操作。进阶映射类型则在此基础上引入了**键重映射**和**条件过滤**能力：能够根据属性名称或值类型，有选择地对不同属性执行不同的变换策略——包括修改键名、筛选子集、动态决定变换逻辑等。

## 一、回顾：我们已有哪些基础

在进入进阶之前，先快速回顾一下基础篇的核心内容，确保地基稳固：

```typescript
// 基础映射：遍历键 → 生成新属性
type BasicMapping<T> = {
  [K in keyof T]: T[K]
};

// 添加修饰符
type Readonly<T> = {
  readonly [K in keyof T]: T[K]
};

type Partial<T> = {
  [K in keyof T]?: T[K]
};

// 移除修饰符
type Required<T> = {
  [K in keyof T]-?: T[K]
};
```

**这些操作的共同特点**：键名不变，只是变换了值的类型或添加/移除了修饰符。它们是"保名变换"。

而进阶篇要解决的核心问题是：**如果我想改变键名呢？如果我想只保留部分属性呢？如果我想根据条件动态决定每个属性怎么变呢？**

这就是 `as` 子句和条件类型要登场的地方。

## 二、`as` 子句 —— 键重映射（Key Remapping）

### 2.1 基本语法

TypeScript 4.1 引入了 **键重映射（Key Remapping）** 功能，允许在映射类型中用 `as` 子句修改键的名称：

```typescript
type MappedWithAs<T> = {
  [K in keyof T as NewKeyType]: T[K]
  //            ^^
  //   遍历 K 之后，用 as 把 K 转换成新的键名
};
```

**技术说明**：基础映射类型的键名在变换前后保持不变，仅对值类型或修饰符进行操作（即"保名变换"）。而 `as` 键重映射允许在遍历过程中动态生成新的键名——键和值的变换不再绑定，可以分别独立控制。

### 2.2 最简单的例子

```typescript
interface User {
  name: string;
  age: number;
  email: string;
}

// 把所有键变成大写
type UppercaseKeys<T> = {
  [K in keyof T as Uppercase<string & K>]: T[K]
};

type UpperUser = UppercaseKeys<User>;
// 等价于：
// {
//   NAME: string;
//   AGE: number;
//   EMAIL: string;
// }
```

注意这里的 `string & K` 写法——因为 `keyof T` 返回的类型可能是 `string | number | symbol`，而 `Uppercase` 工具类型只接受 `string` 类型参数。用交叉类型 `string & K` 收窄到 `string` 部分。

### 2.3 用模板字面量拼接新键名

这是实际开发中最常见的用法——基于原始键名通过模板字符串生成新的键名：

```typescript
interface State {
  loading: boolean;
  error: string | null;
  data: UserData[];
  page: number;
}

// 为每个状态字段自动生成 getter/setter 键
type GettersAndSetters<T> = {
  // getter
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
  // setter
  [K in keyof T as `set${Capitalize<string & K>}`]: (value: T[K]) => void;
};

type StateAccessors = GettersAndSetters<State>;

// 等价于：
// interface StateAccessors {
//   getLoading: () => boolean;
//   setLoading: (value: boolean) => void;
//   getError: () => string | null;
//   setError: (value: string | null) => void;
//   getData: () => UserData[];
//   setData: (value: UserData[]) => void;
//   getPage: () => number;
//   setPage: (value: number) => void;
// }
```

**设计理念**：这种模式在前端状态管理中非常常见（比如 Vuex/Pinia 的 getter 和 mutation 命名约定），通过映射类型 + `as` 重映射可以**自动化地保证命名一致性和类型安全**——你不需要手动为每个状态字段写对应的 getter/setter。

### 2.4 实际案例：事件系统

```typescript
// 定义事件的载荷类型
interface EventMap {
  'user:login': { userId: string; timestamp: number };
  'user:logout': { userId: string };
  'post:create': { postId: string; authorId: string };
  'post:delete': { postId: string; reason: string };
}

// 自动生成事件处理器的类型签名
type EventHandlers<T extends Record<string, unknown>> = {
  [K in keyof T as `on${Capitalize<string & K>}`]: (payload: T[K]) => void;
};

type Handlers = EventHandlers<EventMap>;

const handlers: Handlers = {
  onUserLogin: ({ userId, timestamp }) => {
    console.log(`用户 ${userId} 于 ${timestamp} 登录`);
  },
  onUserLogout: ({ userId }) => {
    console.log(`用户 ${userId} 已登出`);
  },
  onPostCreate: ({ postId }) => {
    console.log(`文章 ${postId} 已创建`);
  },
  onPostDelete: ({ postId, reason }) => {
    console.log(`文章 ${postId} 被删除，原因：${reason}`);
  }
};

// 类型完全匹配！少一个处理器或多一个都会报错
```

**个人总结**：`as` 重映射最强大的地方在于它能把**命名约定变成编译时约束**。如果你的团队规定所有事件处理器必须以 `on` 开头且首字母大写（如 `onUserLogin`），那这个类型就能强制执行这个规则——不按规范命名的函数根本无法赋值成功。

### 2.5 添加前缀和后缀

```typescript
interface ApiConfig {
  host: string;
  port: number;
  timeout: ssl: boolean;
}

// 统一添加 API_ 前缀（模拟环境变量命名）
type EnvVars<T> = {
  [K in keyof T as `API_${Uppercase<string & K>}`]: string
};

type ApiEnvVars = EnvVars<ApiConfig>;
// {
//   API_HOST: string;
//   API_PORT: string;      // 注意：值都变成了 string（环境变量都是字符串）
//   API_TIMEOUT: string;
//   API_SSL: string;
// }
```

### 2.6 snake_case ↔ camelCase 转换

这是一个经典需求——后端接口常用 snake_case，前端习惯用 camelCase：

```typescript
// snakeCase 转 camelCase
type SnakeToCamel<S extends string> =
  S extends `${infer Pre}_${infer Post}`
    ? `${Pre}${Capitalize<SnakeToCamel<Post>>}`
    : S;

// camelCase 转 snakeCase
type CamelToSnake<S extends string> =
  S extends `${infer First}${infer Rest}`
    ? Rest extends Capitalize<Rest>
      ? `${First}_${CamelToSnake<Rest>}`
      : `${First}${CamelToSnake<Rest>}`
    : S;

// 使用示例：将 API 返回的 snake_case 对象转为 camelCase
interface RawApiResponse {
  user_id: number;
  user_name: string;
  created_at: string;
  profile_image_url: string;
}

type CamelResponse<T> = {
  [K in keyof T as SnakeToCamel<K & string>]: T[K]
};

type CleanResponse = CamelResponse<RawApiResponse>;
// {
//   userId: number;
//   userName: string;
//   createdAt: string;
//   profileImageUrl: string;
// }
```

**设计理念**：数据格式转换是前后端协作中的高频痛点。通过类型层面的自动转换，我们可以让 TypeScript 编译器来确保转换后的对象拥有正确的结构，而不需要运行时的额外校验。

**坑点**：模板字面量类型的递归深度有限制。对于非常长的字段名或者嵌套极深的转换，可能会达到 TS 的类型实例化深度限制（通常上限约为 1000 层左右）。实际项目中很少会遇到这个问题，但值得了解。

## 三、条件过滤 —— 用 `never` 过滤属性

### 3.1 核心原理

这是映射类型进阶中最精妙的一个技巧：**利用 `never` 来"删除"不想保留的键**。

原理很简单：当 `as` 右侧的表达式结果为 `never` 时，该键会被直接从结果中排除。

```typescript
interface Person {
  id: number;
  name: string;
  age: number;
  password: string;
  ssn: string;          // 社会安全号码
  creditCard: string;   // 信用卡号
}

// 只保留"安全可展示"的字段（即排除敏感信息）
type SafeFields<T> = {
  [K in keyof T as K extends 'password' | 'ssn' | 'creditCard'
    ? never           // 敏感字段 → never → 被过滤掉
    : K               // 其他字段 → 保持原名
  ]: T[K]
};

type PublicPerson = SafeFields<Person>;
// 结果：
// {
//   id: number;
//   name: string;
//   age: number;
// }
// password, ssn, creditCard 全部消失！
```

**技术说明**：条件过滤的本质是利用 `as` 子句配合三元表达式，对每个键进行判断：匹配条件的键返回 `never`（被类型系统自动从联合类型中排除），不匹配的键保持原样返回。从而在映射过程中实现属性的子集筛选。

### 3.2 为什么 `never` 能实现"删除"

这是因为 TypeScript 中有一个特殊规则：**当映射类型的键联合类型中包含 `never` 时，`never` 会被自动忽略**。来看底层发生了什么：

```typescript
// 普通情况
type Keys1 = 'a' | 'b' | 'c';
type Obj1 = { [K in Keys1]: boolean };
// { a: boolean; b: boolean; c: boolean; }

// 包含 never 时
type Keys2 = 'a' | 'b' | never;   // 'a' | 'b' | never 简化为 'a' | 'b'
type Obj2 = { [K in Keys2]: boolean };
// { a: boolean; b: boolean; }  —— never 被"吸收"了

// 全部是 never
type Keys3 = never;
type Obj3 = { [K in Keys3]: boolean };
// {}  —— 空对象！
```

所以当我们写出 `K extends SomeCondition ? never : K` 时：
- 条件满足的键变成了 `never`
- `never` 在联合类型中被吸收
- 最终结果中这些键就"消失"了

**个人总结**：这是 TypeScript 类型编程中最经典的"以假乱真"技巧——不是真的有"删除"操作，而是巧妙利用了类型系统的数学特性。理解这一点之后，很多看似神奇的类型工具代码都会变得一目了然。

### 3.3 按值类型过滤

不仅可以按键名过滤，还可以按**值的类型**来过滤：

```typescript
interface MixedData {
  id: number;
  title: string;
  createdAt: Date;
  tags: string[];
  metadata: Record<string, unknown>;
  isActive: boolean;
  callback: () => void;
}

// 只提取函数类型的属性
type FunctionsOnly<T> = {
  [K in keyof T as T[K] extends Function ? K : never]: T[K]
};

type Funcs = FunctionsOnly<MixedData>;
// { callback: () => void; }

// 只提取数组类型的属性
type ArraysOnly<T> = {
  [K in keyof T as T[K] extends any[] ? K : never]: T[K]
};

type Arrays = ArraysOnly<MixedData>;
// { tags: string[]; }

// 只提取非函数、非数组的"普通"字段
type PlainFields<T> = {
  [K in keyof T as T[K] extends Function | any[]
    ? never
    : K
  ]: T[K]
};

type Plain = PlainFields<MixedData>;
// { id: number; title: string; createdAt: Date; metadata: Record<string, unknown>; isActive: boolean; }
```

**应用场景**：
- 从组件 props 中分离出事件回调（用于绑定事件）
- 从数据对象中分离出需要序列化的字段
- 从类定义中自动提取方法集合

## 四、Pick 与 Omit —— 手把手从零实现

这两个是最常用的内置工具类型，现在有了前面的知识，我们可以轻松还原它们的实现。

### 4.1 Pick —— 选取指定属性

**功能**：从一个类型中选取指定的若干属性，组成新类型。

**源码实现**：

```typescript
/**
 * 从 T 中选取 K 指定的属性，组成新类型
 * @example
 * type Result = Pick<{ a: string; b: number }, 'a'>  →  { a: string }
 */
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};
```

**逐行解读**：

| 部分 | 含义 |
|------|------|
| `<T, K extends keyof T>` | 两个泛型参数：T 是原类型，K 是要从 T 中选取的键 |
| `[P in K]` | 遍历 K 中的每一个键 |
| `: T[P]` | 取 T 中对应键的值类型 |

**使用示例**：

```typescript
interface Article {
  id: number;
  title: string;
  content: string;
  authorId: number;
  views: number;
  createdAt: Date;
  updatedAt: Date;
  isPublished: boolean;
  tags: string[];
}

// 文章列表页只需要这几个字段
type ArticleListItem = MyPick<Article, 'id' | 'title' | 'createdAt' | 'views'>;
// { id: number; title: string; createdAt: Date; views: number; }

// 编辑表单需要的字段
type ArticleForm = MyPick<Article, 'title' | 'content' | 'tags'>;
// { title: string; content: string; tags: string[]; }
```

**设计理念**：Pick 体现了"最小知识原则"——每个场景只暴露必要的信息，不多不少。列表页不需要文章正文，表单不需要创建时间和阅读量。

**坑点**：`K extends keyof T` 这个约束很重要！它保证了你不能选出不存在的键：

```typescript
// type Bad = Pick<Article, 'id' | 'nonExistent'>;
//                              ^^^^^^^^^^^^
// ❌ 错误！类型 "nonExistent" 不存在于类型 "Article" 中
```

这就是泛型约束的价值——在编译期就杜绝不可能的错误。

### 4.2 Omit —— 排除指定属性

**功能**：从一个类型中排除指定的属性，保留其余属性。

**源码实现（方式一：使用 Exclude）**：

```typescript
/**
 * 从 T 中排除 K 指定的属性，保留其余属性
 */
type MyOmit<T, K extends keyof any> = {
  [P in Exclude<keyof T, K>]: T[P]
};
```

**源码实现（方式二：使用 as + never）** —— 这就是上面学的条件过滤！

```typescript
/** 同样功能的另一种实现 */
type MyOmitV2<T, K extends keyof any> = {
  [P in keyof T as P extends K ? never : P]: T[P]
};
```

两种方式等价，但第二种更直观地展示了"过滤"的本质。

**逐行解读 V1**：

| 部分 | 含义 |
|------|------|
| `Exclude<keyof T, K>` | 从 T 的所有键中排除掉 K 里的键 |
| `[P in ...]` | 遍历排除后的剩余键 |
| `: T[P]` | 保持原有值类型 |

**使用示例**：

```typescript
// 创建文章时不需要这些字段（由后端生成）
type CreateArticleInput = MyOmit<Article, 'id' | 'createdAt' | 'updatedAt' | 'views'>;
// { title: string; content: string; authorId: number; isPublished: boolean; tags: string[]; }

// 给前端展示时隐藏内部字段
type ArticleDTO = MyOmit<Article, 'authorId' | 'isPublished'>;
// { id: number; title: string; content: string; views: number; createdAt: Date; updatedAt: Date; tags: string[]; }
```

**对比说明**：
- **Pick**：白名单模式，显式选取指定的属性子集
- **Omit**：黑名单模式，排除指定属性后保留其余部分

两者互为补集：`Pick<T, A>` ≈ `Omit<T, Exclude<keyof T, A>>`

### 4.3 OmitByValue —— 按值类型排除

内置的 Omit 只能按键名排除，如果我们想按键值的**类型**来排除呢？自己造一个：

```typescript
/**
 * 排除值为指定类型的属性
 * @example
 * OmitByValue<{ a: string; b: number; c: string }, string>
 * → { b: number }
 */
type OmitByValue<T, ValueType> = {
  [K in keyof T as T[K] extends ValueType ? never : K]: T[K]
};

interface ApiResponse {
  status: 'success' | 'error';
  message: string;
  data: unknown;
  errorDetail: string | null;
  timestamp: number;
  _internal: { traceId: string; requestId: string };
}

// 排除内部字段
type PublicApiResult = OmitByValue<ApiResponse, { traceId: string; requestId: string }>;
// 注意：这样不行，因为 _internal 的值是一个对象类型，不是那个对象字面量类型

// 正确做法 —— 用工具类型排除特定类型的值
type NonFunction<T> = OmitByValue<T, Function>;
type NonStringArray<T> = OmitByValue<T, string[]>;
```

## 五、"铁三角"组合：映射类型 + 条件类型 + 索引访问

这是 TypeScript 进阶类型编程的核心范式，我称之为"铁三角"。几乎所有的高级工具类型都是这三个基本能力组合而成的。

### 5.1 三角关系图解

```
        映射类型
       {[K in K]: T}
         ↗    ↖
        /      \
   索引访问   条件类型
     T[K]    A ? B : C
```

三者各司其职：
- **映射类型**提供遍历框架（for-each 循环）
- **条件类型**提供分支逻辑（if-else 判断）
- **索引访问**提供取值能力（变量取值）

单独使用任何一个都只能完成简单任务，但组合起来就能构建复杂的类型变换管道。

### 5.2 案例：CleanObject —— 移除 null 和 undefined

```typescript
/**
 * 将对象中所有可能为 null/undefined 的属性变为必需（移除 null 和 undefined）
 */
type NonNullableField<T> = {
  [K in keyof T]-?: NonNullable<T[K]>
};

// 测试
interface MaybeUser {
  name: string | null;
  age: number | undefined;
  email?: string | null;
  address: string;  // 本来就不是 nullable
}

type CleanUser = NonNullableField<MaybeUser>;
// {
//   name: string;       // string | null → string（去掉了 null）
//   age: number;        // number | undefined → number（去掉了 undefined）
//   email: string;      // 去掉了 ? 和 null，变为必需的 string
//   address: string;    // 不变
// }
```

这里同时使用了三个能力：
- **映射类型**：`[K in keyof T]` 遍历每个属性
- **修饰符操作**：`-?` 移除可选
- **内置工具**：`NonNullable` 包装值类型去除 null/undefined

### 5.3 案例：提取必填字段 / 可选字段

```typescript
/**
 * 提取所有可选属性
 */
type OptionalKeys<T> = {
  [K in keyof T]-?: {} extends Pick<T, K> ? K : never
}[keyof T];

/**
 * 提取所有必需属性
 */
type RequiredKeys<T> = {
  [K in keyof T]-?: {} extends Pick<T, K> ? never : K
}[keyof T];

interface Form {
  username: string;     // 必需
  password: string;     // 必需
  nickname?: string;    // 可选
  avatar?: string;      // 可选
  email: string;        // 必填
}

type Opt = OptionalKeys<Form>;  // "nickname" | "avatar"
type Req = RequiredKeys<Form>;  // "username" | "password" | "email"
```

**原理解析**（这段比较烧脑，仔细看）：

核心技巧是 `{}` extends Pick\<T, K\> 这个判断：
- `{}` 是空对象类型
- 如果属性 K 是可选的，那么 `Pick\<T, K\>` 得到的类型中 K 就是可选的
- 空对象类型 `{}` 可以赋值给"某个可选属性的对象类型"（因为可选意味着可以不存在）
- 所以 `{}` extends \`{ K?: T[K] }\` 成立 → 说明 K 是可选的
- 反之，如果 K 是必需的，空对象无法满足（缺少必需属性 K）→ 不成立 → K 是必需的

最后的 `[keyof T]` 是索引访问类型，用来把对象类型的所有值合并成联合类型。

**个人总结**：这个技巧被称为 "Optional-Check Idiom"，是 TypeScript 社区中广泛使用的判断属性是否可选的标准方法。虽然看起来很绕，但它解决了 TypeScript 类型系统中"判断一个属性是否可选"这一本原难题。

### 5.4 案例：ReadOnlyByKeys —— 对指定属性设为只读

```typescript
/**
 * 只将指定的键设为只读，其他不变
 * @example
 * ReadOnlyByKeys<{ a: string; b: number }, 'a'>
 * → { readonly a: string; b: number }
 */
type ReadOnlyByKeys<T, K extends keyof T> = {
  readonly [P in K]: T[P];       // 指定的键设为只读
} & {
  [P in Exclude<keyof T, K>]: T[P];  // 其余键保持原样
};

interface Config {
  apiUrl: string;
  apiKey: string;      // 这个不应该被改动
  timeout: number;
  retries: number;
}

type ProtectedConfig = ReadOnlyByKeys<Config, 'apiKey'>;
// {
//   readonly apiUrl: string;
//   readonly apiKey: string;   ← 只有这个被标记为 readonly？
// 不对... 上面的写法会让 K 中的所有键都变成 readonly
// }

// 让我们修正上面的理解：
// 实际上 readOnlyByKeys 会把 K 中的键变成 readonly
// 但注意第一个交叉成员用了 readonly，第二个没有

// ✅ 正确行为：apiKey 是 readonly，其他三个是可变的
const cfg: ProtectedConfig = {
  apiUrl: 'https://api.example.com',
  apiKey: 'sk-xxx',
  timeout: 5000,
  retries: 3
};

cfg.apiUrl = 'new-url';  // ✅ 可修改
cfg.timeout = 3000;      // ✅ 可修改
// cfg.apiKey = 'new-key'; // ❌ 不能修改，只读
```

**设计思路**：通过**交叉类型**将"需要只读化的属性"和"保持原样的属性"分成两组分别映射，再合并。这是一种"分治"思想在类型编程中的应用。

## 六、高级实战案例

### 6.1 DeepReadonly —— 深层只读（完整版）

基础篇介绍过简单的 DeepReadonly，现在我们来做一个**生产级**的版本：

```typescript
/**
 * 递归地将对象的所有层级设为只读
 * 特性：
 * - 处理对象和数组
 * - 处理 Map、Set 等内置类型
 * - 处理函数（函数不被展开）
 * - 防止无限循环（限制递归深度）
 */

// 原始类型，不做处理
type Primitive = string | number | bigint | boolean | undefined | symbol | null;
type Builtin = Primitive | Function | Date | Error | RegExp | Map<unknown, unknown>
  | Set<unknown> | WeakMap<object, unknown> | WeakSet<object>
  | Promise<unknown> | ((...args: any[]) => any);

// 带深度限制的 DeepReadonly
type DeepReadonly<T, Depth extends number = 10> =
  T extends Builtin
    ? T                                          // 内置类型直接返回，不递归
    : Depth extends never
      ? never                                    // 到达深度限制
      : {
          readonly [K in keyof T]:
            T[K] extends object                   // 如果值是对象
              ? DeepReadonly<T[K], Depth extends 10 ? 9 : Depth>  // 递归处理
              : T[K]                              // 原始类型直接返回
        };

// 测试
interface ComplexData {
  userInfo: {
    name: string;
    preferences: {
      theme: 'light' | 'dark';
      notifications: {
        email: boolean;
        push: boolean;
        sms: boolean;
      };
    };
  };
  tags: Array<{ id: string; label: string }>;
  metadata: Map<string, string>;
  createdAt: Date;
  callback: () => void;
}

type FrozenComplex = DeepReadonly<ComplexData>;

const data: FrozenComplex = {
  userInfo: {
    name: 'Alice',
    preferences: {
      theme: 'dark',
      notifications: {
        email: true,
        push: false,
        sms: false
      }
    }
  },
  tags: [{ id: '1', label: 'tech' }],
  metadata: new Map([['key', 'value']]),
  createdAt: new Date(),
  callback: () => {}
};

// 所有层级的所有属性都是只读的：
// data.userInfo.name = 'Bob';                    // ❌
// data.userInfo.preferences.theme = 'light';      // ❌
// data.userInfo.notifications.email = false;      // ❌
// data.tags.push({ id: '2', label: 'life' });    // ❌
// data.metadata.set('k', 'v');                   // ❌ （Map 也是只读的）
// data.createdAt = new Date();                   // ❌ （Date 也是只读的）
```

**关键设计决策**：

1. **为什么排除 `Function`**：函数也是对象（`typeof function === 'object'`），但我们通常不希望把函数也展开成只读形式。函数本身就是引用类型，"只读"对函数意义不大。
2. **为什么排除 `Date`、`RegExp` 等**：这些是特殊的包装对象，递归展开它们没有实际意义，还可能导致性能问题。
3. **为什么限制深度**：防止自引用类型导致的无限递归（比如树的节点包含子节点的引用）。
4. **如何处理数组**：`readonly [...T]` 让数组变成只读元组，阻止 push/pop/splice 等变异操作。

### 6.2 CleanObject —— 清理空值

```typescript
/**
 * 移除对象中所有值为 null/undefined/''
 */
type EmptyValues = null | undefined | '';

type CleanObject<T> = {
  [K in keyof T]-?: T[K] extends EmptyValues
    ? never                          // 值为空 → 删除整个属性
    : T[K]                           // 值非空 → 保留
};

interface RawInput {
  name: string;
  age: number | null;
  nickname: string | '';
  bio: string | undefined | null;
  email: string;
  website: '' | string;
}

type Cleaned = CleanObject<RawInput>;
// {
//   name: string;
//   age: number;        // number | null → number（非空时）
//   nickname: string;   // string | '' → string
//   bio: string;        // 去掉了 null 和 undefined
//   email: string;
//   website: string;    // '' | string → string
// }
```

**应用场景**：清理表单提交数据、过滤 API 无效字段、准备序列化数据。

### 6.3 API 类型转换管道

这是一个综合运用多种技术的实战案例：

```typescript
// ====== 原始 API 返回类型 ======
interface RawApiResponse {
  user_id: number;
  user_name: string;
  user_email: string | null;
  created_at: string;
  is_active: 0 | 1;          // 数据库风格布尔值
  profile_img: string | null;
  role: 'admin' | 'user' | 'guest' | null;
  last_login: string | null;
  preferences: {
    theme_light: 0 | 1;
    notify_email: 0 | 1;
    max_items: number | null;
  } | null;
}

// ====== 步骤 1：snake_case → camelCase ======
type SnakeToCamel<S extends string> =
  S extends `${infer Pre}_${infer Post}`
    ? `${Pre}${Capitalize<SnakeToCamel<Post>>}`
    : S;

type CamelKeys<T> = {
  [K in keyof T as SnakeToCamel<K & string>]: T[K]
};

// ====== 步骤 2：数据库布尔值(0|1) → TypeScript boolean ======
type DbBoolean = 0 | 1;
type ToBoolean<T> = T extends DbBoolean
  ? (0 extends T ? (1 extends T ? boolean : false) : true)
  : T;

type ConvertBooleans<T> = {
  [K in keyof T]: ToBoolean<T[K]>
};

// ====== 步骤 3：null → undefined（可选化）=====
type NullToOptional<T> = {
  [K in keyof T]: null extends T[K]
    ? Exclude<T[K], null> | undefined
    : T[K]
};

// ====== 组合：完整的转换管道 ======
type NormalizeApiResponse<T> =
  NullToOptional<ConvertBooleans<CamelKeys<T>>>;

type NormalizedUser = NormalizeApiResponse<RawApiResponse>;
// 结果：
// {
//   userId: number;
//   userName: string;
//   userEmail?: string;           // 原 string | null → string | undefined（可选）
//   createdAt: string;
//   isActive: boolean;            // 原 0 | 1 → boolean
//   profileImg?: string;          // 原 string | null → 可选
//   role?: 'admin' | 'user' | 'guest';  // 原 ... | null → 可选
//   lastLogin?: string;
//   preferences?: {               // 原 ... | null → 可选
//     themeLight: boolean;        // 原 0 | 1 → boolean
//     notifyEmail: boolean;       // 原 0 | 1 → boolean
//     maxItems?: number;          // 原 number | null → 可选
//   } | undefined;
// }

// ====== 使用 ======
async function fetchUser(id: string): Promise<NormalizedUser> {
  const response = await fetch(`/api/users/${id}`);
  const raw: RawApiResponse = await response.json();

  // 实际转换由运行时代码完成（这里只是类型层面）
  return raw as NormalizedUser;
}

// 现在 IDE 能给出完美的类型提示！
const user = await fetchUser('123');
console.log(user.userName);     // string ✅
console.log(user.isActive);     // boolean ✅
console.log(user.userEmail);    // string | undefined ✅
console.log(user.preferences?.themeLight);  // boolean | undefined ✅
```

**设计理念**：这个案例展示了类型系统的真正威力——它不仅仅是"给变量加个注解"，而是可以在**纯类型层面**构建完整的数据转换管道。每一层转换都是声明式的、可组合的、编译期安全的。运行时只需要做一个简单的断言（`as`），所有的正确性保证已经在类型推导中完成了。

### 6.4 表单验证器类型生成

```typescript
// 定义字段规则
interface FieldRule {
  type: 'text' | 'number' | 'email' | 'password' | 'tel';
  label: string;
  required: boolean;
  minLength?: number;
  maxLength?: number;
  pattern?: RegExp;
  min?: number;
  max?: number;
  validator?: (value: unknown) => string | null;  // 自定义校验，返回错误信息或 null
}

// 表单 schema 定义
interface RegisterFormSchema {
  username: FieldRule & { minLength: 3; maxLength: 20 };
  email: FieldRule & { type: 'email' };
  password: FieldRule & { type: 'password'; minLength: 8 };
  confirmPassword: FieldRule & { type: 'password'; minLength: 8 };
  phone: FieldRule & { type: 'tel'; required: false };  // 选填
  inviteCode: FieldRule & { required: false };           // 选填
}

// ====== 从 schema 生成值类型 ======
type FieldType<F extends FieldRule> = F['type'] extends 'number'
  ? number
  : F['type'] extends 'email' | 'password' | 'tel' | 'text'
    ? string
    : never;

type FormValues<T extends Record<string, FieldRule>> = {
  [K in keyof T]: T[K] extends infer R
    ? R extends FieldRule
      ? R['required'] extends true
        ? FieldType<R>
        : FieldType<R> | undefined
      : never
    : never
};

type RegisterFormValues = FormValues<RegisterFormSchema>;
// {
//   username: string;           // 必填 text
//   email: string;              // 必填 email
//   password: string;           // 必填 password
//   confirmPassword: string;    // 必填 password
//   phone?: string | undefined; // 选填 tel
//   inviteCode?: string | undefined; // 选填 text
// }

// ====== 从 schema 生成错误类型 ======
type FormErrors<T extends Record<string, FieldRule>> = {
  [K in keyof T]: string | null;  // 每个字段要么有错误消息，要么没有
};

// ====== 校验函数 ======
function validateForm<
  Schema extends Record<string, FieldRule>
>(schema: Schema, values: Partial<FormValues<Schema>>): FormErrors<Schema> {
  const errors = {} as FormErrors<Schema>;

  for (const key of Object.keys(schema) as Array<keyof Schema>) {
    const rule = schema[key];
    const value = values[key];

    // 检查必填
    if (rule.required && (value === undefined || value === null || value === '')) {
      errors[key] = `${rule.label}不能为空`;
      continue;
    }

    // 检查自定义 validator
    if (rule.validator) {
      const customError = rule.validator(value);
      if (customError) {
        errors[key] = customError;
        continue;
      }
    }

    errors[key] = null;  // 无错误
  }

  return errors;
}

// 使用
const schema: RegisterFormSchema = {
  username: { type: 'text', label: '用户名', required: true, minLength: 3, maxLength: 20 },
  email: { type: 'email', label: '邮箱', required: true },
  password: { type: 'password', label: '密码', required: true, minLength: 8 },
  confirmPassword: { type: 'password', label: '确认密码', required: true, minLength: 8 },
  phone: { type: 'tel', label: '手机号', required: false },
  inviteCode: { type: 'text', label: '邀请码', required: false }
};

const result = validateForm(schema, {
  username: 'alice',
  email: 'alice@example.com',
  password: '12345678',
  confirmPassword: '12345678',
  // phone 和 inviteCode 未填写（它们是可选的，不会报错）
});

result.username;    // string | null
result.email;      // string | null
result.phone;      // string | null
```

**个人总结**：这个案例展示了类型编程的实际价值——**schema 定义一次，值类型、错误类型全部自动派生**。任何字段规则的变更都会同步反映到所有相关的类型上，消除了大量手动维护的工作和出错的可能。

## 七、映射类型的设计模式总结

### 7.1 常见模式速查表

| 模式 | 语法 | 效果 | 典型用途 |
|------|------|------|----------|
| **身份映射** | `[K in keyof T]: T[K]` | 复制类型 | 类型拷贝、作为基础扩展 |
| **只读化** | `readonly [K in keyof T]: T[K]` | 全部只读 | 保护不可变数据 |
| **可选化** | `[K in keyof T]?: T[K]` | 全部可选 | PATCH 更新、表单草稿 |
| **必需化** | `[K in keyof T]-?: T[K]` | 全部必需 | 发布校验、完整性检查 |
| **键重映射** | `[K in keyof T as NewKey]: T[K]` | 改变键名 | 格式转换、getter/setter |
| **条件过滤** | `[K in keyof T as Cond ? K : never]` | 按条件保留 | 属性筛选、敏感信息过滤 |
| **值变换** | `[K in keyof T]: Transform<T[K]>` | 改变值类型 | 类型规范化、null 安全 |
| **递归映射** | `[K in keyof T]: Deep\<T[K]\>` | 深层变换 | DeepReadonly、DeepPartial |
| **交叉分割** | `{[K in A]} & {[K in B]}` | 分组处理不同属性 | 部分只读、差异化处理 |

### 7.2 组合策略

在实际项目中，很少只用单一模式。以下是几种常见的组合策略：

**策略一：先过滤再变换**
```typescript
// 先选出函数属性，再把返回类型包一层 Promise
type AsyncifyFunctions<T> = {
  [K in keyof T as T[K] extends Function ? K : never]:
    (...args: Parameters<T[K]>) => Promise<ReturnType<T[K]>>
};
```

**策略二：先变换再统一修饰**
```typescript
// 先把值转成特定类型，再加 readonly
type StrictConfig<T, TargetType> = {
  readonly [K in keyof T]: T[K] extends TargetType ? T[K] : never
};
```

**策略三：多层管道**
```typescript
// 像数据处理管道一样串联多个变换
type FullPipeline<T> =
  NullToOptional<
    BooleanConvert<
      SnakeToCamelKeys<
        DeepReadonly<T>
      >
    >
  >;
```

### 7.3 性能注意事项

映射类型虽然强大，但也需要注意性能影响：

1. **避免过深的递归**：每次递归都会创建新的类型实例化，深层递归可能导致编译变慢
2. **避免过于复杂的条件判断**：多重嵌套的条件类型会增加编译器推断时间
3. **善用类型别名缓存**：对于重复使用的中间类型，用 `type` 别名保存
4. **必要时拆分大类型**：与其对一个巨大的接口做复杂映射，不如先 Pick 出需要的子集再做映射

```typescript
// 可能较慢：直接处理大类型
type Slow<T> = ComplexTransform<BigInterface<T>>;

// 更快：先缩小范围再处理
type Fast<T> = ComplexTransform<Pick<BigInterface<T>, 'a' | 'b' | 'c'>>;
```

## 个人总结

如果说基础篇教会了我们映射类型的"语法"，那进阶篇就是教我们映射类型的"思维"。

**最重要的三个心智模型**：

1. **`never` 即删除**：在 `as` 子句中返回 `never` 就等同于"过滤掉这个属性"。这是映射类型中最核心的技巧，几乎所有的过滤操作都是建立在这个机制上的。

2. **铁三角思维**：遇到任何复杂的类型变换需求，先分解为三步——用什么遍历（映射）、用什么判断（条件）、怎么取值（索引访问）。大多数看似复杂的工具类型，本质上就是这三者的不同排列组合。

3. **管道式组合**：不要试图用一个映射类型解决所有问题。像写函数一样，每个映射类型只做一件事，然后用类型别名把它们串起来。这不仅更容易理解和调试，也能更好地复用。

**最后一句建议**：不要死记硬背这些高级用法。当你真正遇到"我需要一个能够 XXX 的类型"的需求时，回来看看这篇文章，找到对应的模式，然后根据自己的需求调整。类型编程和普通编程一样——**最好的学习方式是解决实际问题**。
