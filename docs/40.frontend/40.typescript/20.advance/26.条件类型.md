# 条件类型 —— T extends U ? X : Y、分布式条件类型

## 一、条件类型基础

### 1.1 语法形式

条件类型的语法看起来和三元运算符非常相似：

```typescript
// 三元表达式（值层面）
const value = condition ? trueValue : falseValue;

// 条件类型（类型层面）
type Result<T> = T extends SomeType ? YesType : NoType;
```

核心结构就是三部分：**条件判断（extends）→ 真分支 → 假分支**。

```typescript
type IsString<T> = T extends string ? "是字符串" : "不是字符串";

type A = IsString<"hello">;      // "是字符串"
type B = IsString<42>;           // "不是字符串"
type C = IsString<string>;       // "是字符串"
```

#### 为什么需要条件类型

在条件类型出现之前（TypeScript 2.8 之前），TypeScript 的类型系统缺乏"根据输入类型动态选择输出类型"的能力。开发者只能通过函数重载或手动声明大量变体类型来模拟这种行为——既冗长又容易出错。条件类型的引入标志着 TypeScript 类型系统从**静态描述**迈向**可编程变换**的关键一步，它让类型层面的分支逻辑成为可能，为后续所有高级类型特性奠定了基础。

#### 更多实际场景示例

```typescript
// 场景1: 提取函数参数中的可选参数类型
type OptionalKeys<T extends object> = {
  [K in keyof T]: undefined extends T[K] ? K : never
}[keyof T];

interface RequestOptions {
  url: string;
  method?: "GET" | "POST";
  headers?: Record<string, string>;
  timeout: number;
}

type Optional = OptionalKeys<RequestOptions>;
// "method" | "headers" — 自动识别出哪些属性是可选的

// 场景2: 区分 Promise 和非 Promise 类型来做不同处理
type UnwrapOrPass<T> = T extends Promise<infer U> ? U : T;

type A = UnwrapOrPass<string>;                  // string — 非Promise原样返回
type B = UnwrapOrPass<Promise<number>>;         // number  — 解包Promise
type C = UnwrapOrPass<Promise<{ data: string }>>; // { data: string }

// 场景3: 根据数组元素是否为元组决定返回类型
type IsTuple<T> = T extends readonly [any, ...any[]]
  ? { __tuple: true; length: T["length"] }
  : { __tuple: false; isArray: T extends any[] ? true : false };

type Tup1 = IsTuple<[string, number]>;     // { __tuple: true; length: 2 }
type Tup2 = IsTuple<string[]>;             // { __tuple: false; isArray: true }
type Tup3 = IsTuple<42>;                   // { __tuple: false; isArray: false }

// 场景4: 类型级别的四则运算结果推导（简化版）
type ArithmeticResult<T, U> =
  [T, U] extends [number, number]   ? "number"
  : [T, U] extends [string, string] ? "string"
  : [T, U] extends [bigint, bigint] ? "bigint"
  : "unknown";

type R1 = ArithmeticResult<number, number>;    // "number"
type R2 = ArithmeticResult<string, string>;    // "string"
type R3 = ArithmeticResult<number, string>;    // "unknown"
```

### 1.2 "类型层面的 if-else"

如果把普通代码里的 `if-else` 看作是"运行时的分支选择"，那么条件类型就是"编译时的分支选择"。TypeScript 编译器在类型检查阶段就会根据 `extends` 的判定结果，直接决定最终类型走哪个分支——这个过程完全发生在编译期，不会生成任何运行时代码。

```typescript
// 运行时：用值做判断，影响执行流程
function format(value: unknown) {
  if (typeof value === "string") {
    return value.toUpperCase(); // 走这个分支
  } else {
    return String(value);       // 走那个分支
  }
}

// 编译时：用类型做判断，影响最终得到的类型
type FormatReturn<T> = T extends string
  ? Uppercase<T>
  : string;

type R1 = FormatReturn<"hello">; // "HELLO"
type R2 = FormatReturn<123>;     // string
```

这种能力让 TypeScript 可以根据输入类型的不同，输出完全不同的结果类型。它是整个 TypeScript 类型体操的基石之一。

#### 编译器内部处理原理

TypeScript 编译器在处理条件类型时，执行的是一个称为**条件类型求值（Conditional Type Evaluation）**的内部算法。其核心流程如下：

1. **解析 extends 子句**：编译器对 `T extends U` 执行**赋值兼容性检查（Assignment Compatibility Check）**。这等价于问"如果有一个类型为 T 的值，能否把它赋值给一个类型为 U 的变量"。这个过程涉及子类型关系（Subtyping Relation）的判定——编译器会检查 T 的所有属性是否都存在于 U 中、T 的函数参数是否与 U 兼容等。
2. **选择分支**：根据兼容性检查的结果（true/false），编译器直接选取对应的分支类型作为结果。**未被选中的分支不会被求值**（延迟求值特性）。
3. **分布式展开检测**：如果被检测类型是裸类型参数且传入的是联合类型，编译器在进入上述流程前会先执行分布式拆分。

关键点在于，条件类型的求值发生在 TypeScript 编译器的**类型检查阶段（Type Checking Phase）**，早于 JavaScript 代码生成。这意味着最终的 `.js` 文件中不会包含任何条件类型的逻辑——它们纯粹是开发时的类型安全保障工具。

#### 对比：条件类型 vs 其他实现方式

| 方案 | 类型安全性 | 可维护性 | 表达能力 | 适用场景 |
|------|-----------|---------|---------|---------|
| 条件类型 | 完全静态 | 高（声明式） | 强（可组合嵌套） | 复杂的类型变换逻辑 |
| 函数重载 | 静态但冗长 | 低（每组合需手写） | 弱（线性增长） | 少量变体的 API |
| 联合类型 + 手动标注 | 依赖开发者自觉 | 中 | 弱 | 简单场景 |
| 类型断言 as | 无保障 | 高（但不安全） | 无（绕过系统） | 不推荐使用 |

## 二、extends 在条件类型中的行为

### 2.1 什么是"extends"

在条件类型中，`T extends U` 的含义是 **"类型 T 是否可赋值给类型 U"**。这和接口继承中的 `extends` 语义不同——这里更像是一个"兼容性检查"，而不是"继承关系声明"。

```typescript
// 基本兼容性判断
type Check1 = number extends number ? true : false;   // true
type Check2 = string extends string ? true : false;   // true
type Check3 = "hello" extends string ? true : false;  // true — 字面量类型属于其基类型
type Check4 = string extends "hello" ? true : false;  // false — 反过来不行
type Check5 = number extends string ? true : false;   // false — 完全不兼容
```

类之间同样遵循赋值兼容性：

```typescript
class Animal { name: string = ""; }
class Dog extends Animal { breed: string = ""; }

type Test1 = Dog extends Animal ? true : false;  // true — 子类可以赋值给父类
type Test2 = Animal extends Dog ? true : false;  // false — 父类不能赋值给子类
```

### 2.2 裸类型参数 vs 包装类型——关键区别！

这是条件类型中最重要、也最容易混淆的概念。

**裸类型参数（Naked Type Parameter）**：指的是在条件类型中直接使用泛型参数本身，没有被数组、元组、Promise 等任何类型"包装"过。

```typescript
// ✅ 裸类型参数 — T 直接出现，没有任何修饰
type Naked<T> = T extends string ? Yes : No;

// ❌ 非裸类型参数 — T 被数组、元组、Promise 等包裹了
type Wrapped1<T> = T[] extends string[] ? Yes : No;        // 数组包装
type Wrapped2<T> = [T] extends [string] ? Yes : No;         // 元组包装
type Wrapped3<T> = Promise<T> extends Promise<string> ? Yes : No; // Promise包装
type Wrapped4<T> = { x: T } extends { x: string } ? Yes : No; // 对象属性包装
```

为什么这个区别如此重要？因为**只有裸类型参数才会触发分布式行为**（下一节详细讲）。只要 T 被"包了一层"，分布式特性就消失了。

```typescript
type ToArray<T> = T extends any ? T[] : never;

// T 是裸类型参数 → 触发分布式条件类型
type Result1 = ToArray<string | number>;
// 相当于: (string extends any ? string[] : never) | (number extends any ? number[] : never)
// 结果: string[] | number[]

type ToArrayWrapped<T> = [T] extends [any] ? [T][] : never;

// T 在元组里 → 不触发分布式 → 整体作为条件判断
type Result2 = ToArrayWrapped<string | number>;
// 相当于: (string | number) extends any ? [(string | number)][] : never
// 结果: [(string | number)][]
```

同一个泛型参数，仅仅因为是否被"包装"，就产生了截然不同的结果。这是理解后续所有高级用法的前提。

## 三、分布式条件类型 —— 核心机制

### 3.1 自动展开联合类型

当条件类型中的被检测类型是一个**裸类型参数**，并且传入的是**联合类型**时，TypeScript 会自动将联合类型"分发"到条件类型的每一个成员上，然后将结果再次联合起来。

这就是所谓的**分布式条件类型（Distributive Conditional Types）**。

```typescript
type ToArray<T> = T extends any ? T[] : never;

// 当传入联合类型时：
type Distributed = ToArray<string | number | boolean>;

// 实际展开过程：
// Step 1: 提取联合成员 → string | number | boolean
// Step 2: 逐个代入:
//   string  extends any ? string[]  : never  → string[]
//   number  extends any ? number[]  : never  → number[]
//   boolean extends any ? boolean[] : never  → boolean[]
// Step 3: 合并结果 → string[] | number[] | boolean[]
```

从集合论的角度理解这一过程：联合类型 `A | B | C` 可视为一个有限集合 `{A, B, C}`，分布式条件类型的展开等价于对该集合做笛卡尔积映射——将条件类型函数 `f(T) = T extends U ? X : Y` 逐一应用于每个成员，再将所有结果取并集：

```
Distribute(f, A | B | C) = f(A) | f(B) | f(C)
```

这种"映射-归约"模式是分布式条件类型的数学本质。

### 3.2 分发的触发条件

触发分布式行为必须同时满足三个条件：

| 条件 | 说明 |
|------|------|
| 条件位置的被检测类型是**裸类型参数** | 不能有 `[]`、`Promise<>` 等包装 |
| 传入的实际类型是**联合类型** | 单个类型不触发分发 |
| 条件类型写在**泛型声明或别名中** | 直接写死的联合类型不触发 |

```typescript
// ✅ 满足所有条件 → 触发分发
type Distributive<T> = T extends string ? "str" : "other";
type Res1 = Distributive<string | number>; // "str" | "other"

// ❌ 条件1不满足 — T 被包装
type NonDistributive1<T> = [T] extends [string] ? "str" : "other";
type Res2 = NonDistributive1<string | number>; // "other" — 整体判断

// ❌ 条件2不满足 — 不是联合类型
type Res3 = Distributive<string>; // "str" — 无需分发

// ❌ 条件3不满足 — 直接使用联合类型字面量
type Literal = (string | number) extends string ? "str" : "other";
// 结果: "other" — 这里没有泛型参数，不触发分发
```

### 3.3 避免分发的技巧

如果不想让联合类型被分发（希望整体作为一个整体进行条件判断），可以用元组包装或交叉 `& unknown`：

```typescript
// 方法一：用元组包装
type NoDist1<T> = [T] extends [string] ? "yes" : "no";
type Test1 = NoDist1<string | number | boolean>; // "no" — 整体判断

// 方法二：用 & unknown 或其他交叉类型（注意：对某些场景可能不够）
type NoDist2<T> = (T & {}) extends string ? "yes" : "no";

// 方法三：将 T 先赋值给一个中间类型
type NoDist3<T> = (T extends string ? T : never) extends string ? "yes" : "no";
// 内层触发了分发，但外层拿到的是分发后的结果再判断
```

最常用也最可靠的就是**方法一——元组包装** `[T]`。

### 3.4 实际应用：过滤联合类型

分布式条件类型最常见的用途就是从联合类型中过滤出符合特定条件的成员。

#### Filter 基础模式

```typescript
// 从联合类型中只保留 string 类型的成员
type StringsOf<T> = T extends string ? T : never;

type Mixed = string | number | boolean | "hello" | 42;
type OnlyStrings = StringsOf<Mixed>;
// 展开过程：
//   string   extends string → string
//   number   extends string → never
//   boolean  extends string → never
//   "hello"  extends string → "hello"
//   42       extends string → never
// 联合: string | "hello"
// 注意：never 在联合类型中被自动忽略！
```

**为什么 never 会被忽略？**

`never` 表示"不可能存在的类型"。当 `never` 出现在联合类型中时，它相当于空集，与任何类型取并集都不会产生影响。这就像数学中的空集与任何集合的并集仍是原集合一样。

```typescript
type A = string | never;    // 等价于 string
type B = never | number;    // 等价于 number
type C = never;             // never 本身（没有其他成员）
```

#### 更复杂的过滤器

```typescript
// 只保留函数类型
type FunctionsOnly<T> = T extends (...args: any[]) => any ? T : never;

type Mix = string | ((x: number) => void) | number | (() => boolean);
type Funcs = FunctionsOnly<Mix>;
// ((x: number) => void) | (() => boolean)

// 只保留具有特定形状的对象类型
type WithName<T> = T extends { name: string } ? T : never;

type Entities = { name: "Alice" } | { id: 1 } | { name: "Bob", age: 30 };
type NamedEntities = WithName<Entities>;
// { name: "Alice" } | { name: "Bob"; age: 30 }
```

#### 实现 Exclude 和 Extract

有了上面的理解，TypeScript 内置的 `Exclude` 和 `Extract` 就非常好理解了：

```typescript
// Exclude: 从 T 中排除可赋值给 U 的类型
type MyExclude<T, U> = T extends U ? never : T;

// Extract: 从 T 中提取可赋值给 U 的类型
type MyExtract<T, U> = T extends U ? T : never;
```

```typescript
type T = "a" | "b" | "c" | "d";

type Excluded = MyExclude<T, "a" | "c">;
// 展开过程：
//   "a" extends "a"|"c" → never
//   "b" extends "a"|"c" → "b"
//   "c" extends "a"|"c" → never
//   "d" extends "a"|"c" → "d"
// 结果: "b" | "d"

type Extracted = MyExtract<T, "a" | "c">;
// 结果: "a" | "c"
```

这两个工具类型的实现竟然如此简洁——各只需要一行代码。这正是分布式条件类型威力的体现。

## 四、条件类型嵌套

条件类型可以在真分支或假分支中嵌套另一个条件类型，形成多层判断链。

### 4.1 基本嵌套

```typescript
// 多级类型判断
type TypeName<T> =
  T extends string ? "string" :
  T extends number ? "number" :
  T extends boolean ? "boolean" :
  T extends undefined ? "undefined" :
  T extends Function ? "function" :
  "object";

type N1 = TypeName<"hello">;     // "string"
type N2 = TypeName<42>;          // "number"
type N3 = TypeName<true>;        // "boolean"
type N4 = TypeName<() => void>;  // "function"
type N5 = TypeName<{ a: 1 }>;    // "object"
```

这种模式类似于编程语言中的 `if-else if-else` 链，从上往下依次匹配，命中第一个符合条件的就返回。

### 4.2 嵌套与分布式的交互

```typescript
// 判断类型是否为"原始类型"
type IsPrimitive<T> =
  T extends string ? true :
  T extends number ? true :
  T extends boolean ? true :
  T extends symbol ? true :
  T extends bigint ? true :
  T extends null ? true :
  T extends undefined ? true :
  false;

type P1 = IsPrimitive<string>;              // true
type P2 = IsPrimitive<{ x: number }>;       // false

// 配合分布式使用
type PrimitivesOnly<T> = IsPrimitive<T> extends true ? T : never;

type Mixed2 = string | number | { a: 1 } | boolean | Array<number>;
type Prim = PrimitivesOnly<Mixed2>;
// string | number | boolean
```

注意这里 `IsPrimitive<T>` 本身就是一个条件类型，外层又用它做了条件判断。内层的 `IsPrimitive` 因为 T 是裸参数所以会先触发分布式，然后每个分支的结果再参与外层判断。

## 五、infer 关键字 —— 类型推断

### 5.1 infer 基本语法

`infer` 关键字只能在条件类型的 `extends` 子句中使用，用于声明一个"待推断的类型变量"。编译器会自动从实际类型中推断出这个变量的具体类型。

```typescript
// 从数组类型中推断元素类型
type ElementOf<T> = T extends (infer E)[] ? E : never;

type El1 = ElementOf<string[]>;          // string
type El2 = ElementOf<Array<number>>;     // number
type El3 = ElementOf<[string, number]>;  // string | number — 元组的元素可能是多种类型
type El4 = ElementOf<never>;             // never
```

`infer` 的语义是在 `extends` 子句的类型模式中声明一个**类型变量占位符**。编译器在匹配过程中会通过**模式匹配（pattern matching）**机制，从实际传入的类型结构中推断并绑定该变量的具体类型。如果匹配成功，`infer` 声明的变量在真分支中可用；若匹配失败，则走入假分支。

### 5.2 从函数类型推断

`infer` 最经典的使用场景就是从函数类型中提取参数类型和返回值类型：

```typescript
// 获取返回值类型
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type R1 = MyReturnType<() => string>;           // string
type R2 = MyReturnType<(x: number) => boolean>; // boolean
type R3 = MyReturnType<(a: string, b: number) => { x: number }>; // { x: number }

// 获取参数类型元组
type MyParameters<T> = T extends (...args: infer P) => any ? P : never;

type P1 = MyParameters<(name: string, age: number) => void>;
// [name: string, age: number]

type P2 = MyParameters<() => void>;
// []

// 获取第一个参数类型
type FirstParam<T> = T extends (arg: infer F, ...rest: any[]) => any ? F : never;

type FP = FirstParam<(x: string, y: number, z: boolean) => void>;
// string
```

### 5.3 从 Promise 中推断

```typescript
// 解包 Promise，获取内部值的类型
type Unpromise<T> = T extends Promise<infer U> ? U : T;

type U1 = Unpromise<Promise<string>>;            // string
type U2 = Unpromise<Promise<{ data: number }>>;   // { data: number }
type U3 = Unpromise<string>;                      // string — 不是 Promise 则原样返回
type U4 = Unpromise<Promise<Promise<boolean>>>;   // Promise<boolean> — 只解一层
```

如果需要递归解包所有层级的 Promise：

```typescript
type DeepUnpromise<T> = T extends Promise<infer U>
  ? DeepUnpromise<U>  // 递归继续解包
  : T;                // 到达非 Promise 类型则停止

type DU = DeepUnpromise<Promise<Promise<Promise<string>>>>;
// string
```

### 5.4 从字符串模板推断

`infer` 还能配合模板字面量类型使用：

```typescript
// 解析 "prefix_value" 格式，提取前缀和值
type SplitPrefix<S extends string> =
  S extends `${infer Prefix}_${infer Suffix}` ? { prefix: Prefix; suffix: Suffix } : never;

type SP1 = SplitPrefix<"user_123">;   // { prefix: "user"; suffix: "123" }
type SP2 = SplitPrefix<"admin_alice">; // { prefix: "admin"; suffix: "alice" }

// 匹配邮箱格式（简化版）
type ParseEmail<E extends string> =
  E extends `${infer Name}@${infer Domain}` ? { name: Name; domain: Domain } : never;

type Email = ParseEmail<"test@example.com">;
// { name: "test"; domain: "example.com" }

// 提取 getter 方法名
type Getters<T> = T extends `get${infer Name}` ? Name : never;

type GetterNames = Getters<"getName" | "getAge" | "setEmail" | "removeItem">;
// "Name" | "Age"
```

### 5.5 多个 infer 的位置约束

在同一个条件类型中可以使用多个 `infer` 声明，但它们的位置关系会影响推断行为：

```typescript
// 协变位置 — 多个 infer 都在"产出"位置，推断为联合类型
type Args<T> = T extends (...args: infer A) => any ? A : never;
// 如果函数有重载，A 会是所有重载参数的联合

// 逆变位置 — infer 在"消费"位置（如回调参数），行为更复杂
type CallbackArg<T> = T extends (cb: (arg: infer A) => void) => void ? A : never;
```

关于协变和逆变的深入讨论超出了本文范围，只需记住：**同一位置的多个 infer 推断候选通常会被合并为联合类型**。

## 六、内置工具类型原理剖析

掌握了条件类型、分布式和 infer 之后，再来审视 TypeScript 的内置工具类型，会发现它们本质上都是这些基本机制的组合运用。

### 6.1 Exclude

```typescript
/**
 * 从 Type 中排除所有可赋值给 ExcludedUnion 的类型成员
 * 核心原理：利用分布式条件类型 + never 在联合中被忽略的特性
 */
type Exclude<Type, Union> = Type extends Union ? never : Type;
```

```typescript
// 示例
type E = Exclude<"a" | "b" | "c" | "d", "a" | "c">
// "b" | "d"
```

**工作原理图解**：

```
输入: "a" | "b" | "c" | "d"
         ↓ 分布式展开
"a" extends "a"|"c" → never   ← 被排除
"b" extends "a"|"c" → "b"     ← 保留
"c" extends "a"|"c" → never   ← 被排除
"d" extends "a"|"c" → "d"     ← 保留
         ↓ 联合合并
结果: "b" | "d"
```

### 6.2 Extract

```typescript
/**
 * 从 Type 中提取所有可赋值给 Union 的类型成员
 * 与 Exclude 互为补集操作
 */
type Extract<Type, Union> = Type extends Union ? Type : never;
```

```typescript
// 示例
type ET = Extract<"a" | "b" | "c" | "d", "a" | "c">
// "a" | "c"
```

### 6.3 NonNullable

```typescript
/**
 * 从 Type 中排除 null 和 undefined
 */
type NonNullable<Type> = Type extends null | undefined ? never : Type;
```

```typescript
// 示例
type NN = NonNullable<string | number | null | undefined>;
// string | number
```

### 6.4 ReturnType

```typescript
/**
 * 获取函数类型的返回值类型
 * 利用 infer 在条件类型中推断返回值
 */
type ReturnType<T extends (...args: any) => any> =
  T extends (...args: any) => infer R ? R : never;
```

```typescript
// 示例
type RT1 = ReturnType<() => string>;                    // string
type RT2 = ReturnType<(x: number) => Promise<boolean>>; // Promise<boolean>
type RT3 = ReturnType<typeof Math.random>;              // number
type RT4 = ReturnType<typeof Array.isArray>;             // boolean
```

### 6.5 Parameters

```typescript
/**
 * 获取函数类型的参数类型元组
 * 利用 infer 推断参数列表
 */
type Parameters<T extends (...args: any) => any> =
  T extends (...args: infer P) => any ? P : never;
```

```typescript
// 示例
declare function foo(x: string, y: number, z: boolean): void;
type ParamTypes = Parameters<typeof foo>;
// [x: string, y: number, z: boolean]
```

### 6.6 其他常用内置工具类型

```typescript
// Partial — 将所有属性变为可选（映射类型 + ? 修饰符）
type Partial<T> = {
  [P in keyof T]?: T[P];
};

// Required — 将所有属性变为必需（映射类型 + -? 修饰符）
type Required<T> = {
  [P in keyof T]-?: T[P];
};

// Pick — 选择指定属性组成新类型
type Pick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// Omit — 排除指定属性（基于 Exclude + Pick）
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

## 七、高级案例

### 7.1 深层 Partial

内置的 `Partial` 只处理对象的第一层属性。如果要递归地将所有层级的属性都变为可选，就需要结合条件类型：

```typescript
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object
    ? DeepPartial<T[P]>   // 如果属性值是对象，递归处理
    : T[P];               // 否则保持不变
};

// 使用示例
interface User {
  name: string;
  age: number;
  address: {
    city: string;
    street: string;
    geo: {
      lat: number;
      lng: number;
    };
  };
}

type PartialUser = DeepPartial<User>;
// 等价于：
// {
//   name?: string | undefined;
//   age?: number | undefined;
//   address?: {
//     city?: string | undefined;
//     street?: string | undefined;
//     geo?: {
//       lat?: number | undefined;
//       lng?: number | undefined;
//     } | undefined;
//   } | undefined;
// }
```

**原理说明**：`DeepPartial` 使用映射类型遍历对象的所有属性，对每个属性的值进行条件判断——如果是 `object` 类型（包括数组和嵌套对象），则递归调用 `DeepPartial`；否则直接保留原类型。同时，外层的 `?` 让当前层级属性都变为可选。

### 7.2 深层 Pick

类似地，可以实现支持路径选择的深层 Pick：

```typescript
// 辅助：获取对象某个属性的类型
type PathValue<T, K extends string> =
  K extends `${infer First}.${infer Rest}`
    ? First extends keyof T
      ? PathValue<T[First], Rest>   // 递归进入下一层
      : never                       // 路径不存在
    : K extends keyof T
      ? T[K]                        // 到达目标属性
      : never;

// 深层Pick
type DeepPick<T, Paths extends string> = {
  [K in Paths as PathValue<T, K> extends never ? never : K]: PathValue<T, K>;
};

interface Config {
  db: {
    host: string;
    port: number;
    auth: {
      user: string;
      pass: string;
    };
  };
  server: {
    name: string;
    port: number;
  };
}

// 只选取需要的深层字段
type Selected = DeepPick<Config, "db.host" | "db.auth.user" | "server.name">;
// {
//   db: {
//     host: string;
//     auth: {
//       user: string;
//     };
//   };
//   server: {
//     name: string;
//   };
// }
```

### 7.3 Promise 解包进阶

结合 infer 和递归，可以构建强大的异步工具类型：

```typescript
// 解包任意层级的 Promise
type Awaited<T> = T extends Promise<infer U>
  ? Awaited<U>  // 递归
  : T;

// 获取 async 函数的真正返回值（去掉 Promise 包装）
type AsyncReturnType<T extends (...args: any) => any> =
  Awaited<ReturnType<T>>;

async function fetchData(): Promise<{ id: number; name: string }> {
  return { id: 1, name: "test" };
}

type FetchResult = AsyncReturnType<typeof fetchData>;
// { id: number; name: string } — 不是 Promise<{ id: number; name: string }!

// 处理可能的错误情况
type SafeAwaited<T> = T extends Promise<infer U>
  ? U extends Promise<any>
    ? SafeAwaited<U>     // 继续解包
    : U                  // 到达底层
  : T;                   // 非 Promise 原样返回
```

### 7.4 函数重载提取

```typescript
// 提取构造函数的实例类型
type InstanceType<T extends new (...args: any) => any> =
  T extends new (...args: any) => infer I ? I : never;

class Person {
  constructor(name: string, age: number) {}
  greet() { return "hello"; }
}

type PersonInstance = InstanceType<typeof Person>;
// Person

// 结合 typeof 使用
function createInstance<Ctor extends new (...args: any) => any>(
  ctor: Ctor,
  ...args: ConstructorParameters<Ctor>
): InstanceType<Ctor> {
  return new ctor(...args);
}

const p = createInstance(Person, "Alice", 30);
// p 的类型是 Person，拥有 greet() 方法
```

## 八、常见陷阱与注意事项

### 8.1 意外的联合类型展开

分布式条件类型虽然强大，但有时会产生意外的行为。当你不希望联合类型被展开时，它却悄悄展开了：

```typescript
type WrapInArray<T> = T extends any ? T[] : never;

type W1 = WrapInArray<string>;           // string[] — 正常
type W2 = WrapInArray<string | number>;  // string[] | number[] — 被展开了！

// 如果你期望得到 (string | number)[]
// 就需要阻止分发：
type WrapInArrayNoDistribute<T> = [T] extends [any] ? T[] : never;
type W3 = WrapInArrayNoDistribute<string | number>;
// (string | number)[] — 符合预期
```

**经验法则**：当你写的条件类型接收联合类型后结果变得出乎意料地"分散"，首先考虑是不是分布式行为在作祟。

### 8.2 Never 的特殊行为

`never` 在条件类型中有两个特殊表现：

**表现一：作为被检测类型时，跳过分发**

```typescript
type ToArray<T> = T extends any ? T[] : never;

type N = ToArray<never>;
// 结果是 never，而不是 never[]！
```

原因：`never` 是"空联合类型"，没有成员可供分发，所以整体结果是 `never`。

**表现二：在联合类型中被自动忽略**

```typescript
type FilterString<T> = T extends string ? T : never;

type F = FilterString<string | number | never>;
// string — never 被静默忽略了
```

这在实际开发中通常是有利的行为——它让我们可以安全地在条件类型的假分支返回 `never` 来"过滤掉"不符合条件的类型成员。

**但如果你的逻辑依赖 never 不被忽略**（比如某些边界情况的精确控制），就要格外小心了。

### 8.3 交叉类型与条件类型的交互

```typescript
// 条件类型对交叉类型的处理可能不如直觉预期
type Test = (string & { x: number }) extends string ? true : false;
// true — 交叉类型 string & { x: number } 仍然 assignable to string

// 但反过来就不行了
type Test2 = string extends (string & { x: number }) ? true : false;
// false — string 不一定有 x 属性
```

### 8.4 条件类型的延迟求值

条件类型中的真假分支会被延迟求值，这意味着即使某个分支在当前情况下不会被选中，其中的类型引用也不需要立即可解析：

```typescript
type Deferred<T> = T extends string
  ? SomeTypeThatMightNotExist  // 即使未定义也不会报错（在这个分支未被选中的时候）
  : number;

type D = Deferred<number>; // number — 第一分支不会被求值，所以不会有类型错误

type ErrorCase = Deferred<string>; // 这里才会报错，因为第一分支被选中且需要求值
```

这种"惰性求值"特性使得条件类型非常适合用来处理一些可能存在循环引用或前置声明的复杂类型关系。

## 九、总结

条件类型是 TypeScript 类型系统中最具表达力的特性之一。回顾一下核心知识点：

| 特性 | 关键点 |
|------|--------|
| 基本语法 | `T extends U ? X : Y` |
| extends 含义 | 类型兼容性检查，不是继承 |
| 裸类型参数 | 直接出现的泛型参数，无任何包装 |
| 分布式条件类型 | 裸参数 + 联合类型 → 自动逐成员展开 |
| 避免分发 | 用 `[T]` 元组包装或其他方式 |
| infer 关键字 | 在条件类型中声明待推断的类型变量 |
| never 在联合中 | 自动被忽略，可用于过滤 |
| 内置工具类型 | 大多是条件类型 + infer 的组合应用 |

掌握条件类型，意味着你已经跨过了 TypeScript 类型编程的一道重要门槛。接下来可以尝试将这些知识组合运用，去理解和编写更复杂的工具类型，甚至探索模板字面量类型与条件类型的联动——那将是另一片广阔天地。
