# 类型兼容性 —— 结构化类型系统、协变与逆变

> 类型兼容性（Type Compatibility）是 TypeScript 编译器判断一个值能否赋给某个目标类型的核心机制。它决定了哪些赋值操作合法、哪些会报错，是理解 TypeScript 错误信息的基础。与许多主流语言的名义类型系统不同，TypeScript 采用**结构化类型系统（Structural Typing）**——类型的兼容性由其内部结构决定，而非名称。这一选择深刻影响了函数参数、类、泛型等各个层面的行为。

## 一、结构化类型系统 vs 名义类型系统

### 1.1 核心区别

在编程语言理论中，类型系统按"身份判定方式"分为两大阵营：

| 特征 | 结构化类型（Structural Typing） | 名义类型（Nominal Typing） |
|------|-------------------------------|--------------------------|
| 兼容性依据 | 类型的**成员结构**是否匹配 | 类型的**声明名称**是否相同 |
| 代表语言 | TypeScript, Go, OCaml | Java, C#, Rust (部分), C++ |
| 鸭子类型支持 | 编译期自动识别 | 需要显式实现/继承 |

### 1.2 结构化类型的基本规则

TypeScript 的核心兼容规则可以概括为：

> **如果类型 Y 至少拥有类型 X 的所有必需成员，则 Y 兼容 X（Y 可以赋给 X 类型的位置）。**

这本质上就是"鸭子类型"的编译期体现——编译器不关心你叫什么名字，只关心你有什么属性和方法。

> **为什么需要结构化类型？** JavaScript 作为动态语言，其运行时对象系统本身就是基于结构的——任何两个对象只要拥有相同形状的属性就可以互相替换。TypeScript 采用结构化类型，使得 JS 代码迁移到 TS 时无需修改运行时行为，同时获得了编译期的类型安全保障。名义类型系统（如 Java、Rust）要求显式声明继承/实现关系，这在以 JSON 为核心数据交换格式的前端开发中会产生大量适配代码。

### 1.2.1 结构化类型在真实项目中的典型场景

```typescript
// 场景一：API 响应与前端类型的自然对接
// 后端返回的 JSON 对象天然满足前端定义的接口形状
interface UserProfile {
  id: number;
  name: string;
  email: string;
}

// fetch API 返回的对象自动兼容 UserProfile，无需额外转换
async function getUser(id: number): Promise<UserProfile> {
  const res = await fetch(`/api/users/${id}`);
  return res.json(); // ✅ 返回值自动匹配 UserProfile 结构
}

// 场景二：第三方库的类型适配
// 假设你使用了一个 UI 库期望特定形状的 props
interface TableProps<T> {
  data: T[];
  columns: { key: keyof T; title: string }[];
  onRowClick?: (row: T) => void;
}

// 你的业务数据不需要"实现"任何接口，只要形状对就行
interface Order { orderId: string; amount: number; status: string; }

const orderTableProps: TableProps<Order> = {
  data: [{ orderId: 'ORD-001', amount: 99, status: 'paid' }],
  columns: [
    { key: 'orderId', title: '订单号' },
    { key: 'amount', title: '金额' },
    { key: 'status', title: '状态' },
  ],
  onRowClick(order) {
    // order 的类型被正确推断为 Order
    console.log(`点击订单: ${order.orderId}`);
  },
};

// 场景三：测试中的 mock 对象
interface CacheService {
  get(key: string): Promise<string | null>;
  set(key: string, value: string, ttl?: number): Promise<void>;
}

// 测试时直接用普通对象 mock，无需实现类
const mockCache: CacheService = {
  async get(key) {
    console.log(`Mock get: ${key}`);
    return null;
  },
  async set(key, value, ttl) {
    console.log(`Mock set: ${key} = ${value}, TTL=${ttl}s`);
  },
};
```

### 1.2.2 常见错误演示

```typescript
// 错误 1：混淆了"有属性"和"属性类型匹配"
interface IdProvider {
  getId(): string;  // 返回 string
}

class NumericId {
  getId(): number {  // 返回 number，不是 string！
    return 42;
  }
}

let provider: IdProvider = new NumericId();
// ❌ Error: Type 'NumericId' is not assignable to type 'IdProvider'.
// 原因：getId 的返回类型 number 不兼容 string

// 错误 2：可选属性的位置放错
interface RequiredName {
  firstName: string;   // 必需
  lastName?: string;   // 可选
}

class BothRequired {
  firstName: string = '';
  lastName: string = '';  // 这里 lastName 是必需的
}

let rn: RequiredName = new BothRequired();  // ✅ 兼容（多属性没关系）
// 但反过来就不行：
let br: BothRequired = { firstName: 'Alice' };
// ❌ Error: Property 'lastName' is missing in type...
// 原因：BothRequired 需要 lastName 作为必需属性

// 错误 3：方法签名的细微差异
interface Comparator {
  compare(a: string, b: string): number;
}

// 参数名不同但类型相同 —— 这其实是 OK 的
let cmp1: Comparator = {
  compare(x: string, y: string) { return x.localeCompare(y); }  // ✅
};

// 但参数数量不同就不行
let cmp2: Comparator = {
  compare(a: string) { return 0; }  // ❌ 缺少第二个参数
  // 注意：这里说的是接口方法声明，不受"少参数函数可赋给多参数位置"规则影响
};

// 正确理解：接口方法声明的参数比较是严格的一对一检查
// "少参数函数可赋给多参数"规则仅适用于函数类型的赋值场景
```

### 1.3 对象类型的完整兼容性判断流程

当 TypeScript 判断源类型 S 是否兼容目标类型 T 时，对于对象类型遵循以下流程：

1. **检查必需属性**：S 必须包含 T 的所有必需（non-optional）属性
2. **检查属性类型**：每个对应属性的值的类型必须兼容
3. **忽略多余属性**：S 中存在但 T 中未声明的属性不影响兼容性（有例外，见 Freshness 规则）

```typescript
interface Target {
  id: number;
  label: string;
  active?: boolean;  // 可选属性
}

const source = {
  id: 42,
  label: 'test',
  active: true,
  extraData: 'ignored',  // 多余属性，被忽略
  count: 100            // 同样被忽略
};

let t: Target = source; // ✅ 完全兼容
```

> **编译器内部处理机制**：TypeScript 编译器（tsc）在检查对象类型兼容时，会递归地遍历目标类型的每个属性，然后在源类型中查找同名属性并进行子类型关系判断。这一过程发生在类型检查阶段（Type Checker），不产生任何运行时代码。编译器使用**结构化比较算法**——对每个属性执行 `isTypeAssignableTo(sourceProp, targetProp)` 递归检查。

## 二、基本类型的兼容性

### 2.1 原始类型的兼容关系

原始类型之间存在明确的层级关系，子类型可以赋给父类型位置：

```typescript
// 基本层级：具体类型 ← 宽泛类型
let str: string = 'hello';       // 精确匹配
let numOrStr: string | number = str;  // string → string | number ✅

let specific: 'hello' = 'hello';
let general: string = specific;      // 字面量类型 → 其父类型 ✅

// ❌ 反方向不行
// let narrow: 'hello' = general;     // string 不能赋值给 'hello'
```

**原始类型的兼容层次图**：

```
        string | number | boolean | ... （最宽泛）
         ↙    ↓     ↓          ↘
     string   number  boolean    null | undefined（严格模式下）
     ↙  ↓       ↓
'hello'   42    true
（最精确的字面量类型）
```

### 2.2 字面量类型与联合类型

```typescript
type Direction = 'north' | 'south' | 'east' | 'west';

let d1: Direction = 'north';  // ✅ 字面量是其所在联合类型的子类型

// 联合类型与其构成元素的关系
let d2: 'north' | 'south' = 'north'; // ✅ 单个字面量 → 包含它的联合类型
```

### 2.3 null 与 undefined 的兼容性

这是 `strictNullChecks` 编译选项影响最大的区域之一：

```typescript
// === strictNullChecks: false（宽松模式）===
let s: string = null;     // ✅ null 可赋给 string
let n: number = undefined;  // ✅ undefined 可赋给 number

// === strictNullChecks: true（严格模式）===
let s2: string = null;     // ❌ null 不可赋给 string
let s3: string | null = null;  // ✅ 显式包含 null 才行
let s4: string | undefined = undefined; // ✅ 显式包含 undefined 才行
let s5: string | null | undefined = null; // ✅ 都包含就没问题

// 非空断言
let maybeStr: string | null = 'hello';
let definiteStr: string = maybeStr!;  // 用 ! 断言移除 null/undefined
```

**设计考量**：`strictNullChecks` 默认关闭是为了向后兼容 JavaScript 的宽松语义；开启后能捕获大量运行时可能出现的空值错误，建议始终开启。

### 2.4 枚举类型的兼容性

枚举类型的兼容性规则比较特殊，分三种情况：

```typescript
// ===== 数字枚举 =====
enum Status {
  Pending = 0,
  Active = 1,
  Inactive = 2
}

let num: number = Status.Active;  // ✅ 数字枚举 ↔ number 双向兼容
let status: Status = 1;           // ✅ 数字可以赋给数字枚举变量

// ===== 字符串枚举 =====
enum Color {
  Red = 'red',
  Green = 'green',
  Blue = 'blue'
}

let color: Color = Color.Red;
// let str: string = Color.Red;  // ❌ 字符串枚举不能隐式转为 string
// let c: Color = 'red';         // ❌ string 不能赋给字符串枚举

// ===== const enum（常量枚举）=====
const enum Size {
  Small = 'S',
  Large = 'L'
}

let sz: Size = Size.Small;
// const enum 在编译后被内联为字面量，行为类似字面量类型
```

**关键差异总结**：

| 枚举类型 | 与 number 的兼容性 | 与 string 的兼容性 | 原因 |
|---------|-------------------|-------------------|------|
| 数字枚举 | 双向兼容 | 不适用 | 基于数字，与 JS 数值体系一致 |
| 字符串枚举 | 不兼容 | 不兼容 | 设计上更严格，防止意外混用 |
| const enum | 编译后内联为字面量 | 取决于底层类型 | 编译期常量，无运行时表示 |

### 2.5 联合类型的兼容性规则深入

联合类型的兼容性遵循"分配律"——一个类型与联合类型兼容当且仅当它与联合中的至少一个成员兼容：

```typescript
// 基本规则：T 与 A | B | C 兼容 ⟺ T 与 A 兼容 或 T 与 B 兼容 或 T 与 C 兼容
type StringOrNumber = string | number;

let sn: StringOrNumber;
sn = 'hello';    // ✅ 'hello' 是 string 的子类型，string ∈ StringOrNumber
sn = 42;         // ✅ 42 是 number 的子类型，number ∈ StringOrNumber
// sn = true;     // ❌ boolean 与 string 和 number 都不兼容

// 反向：联合类型赋值给具体类型 —— 需要所有成员都兼容
let s: string = sn;  // ❌ StringOrNumber 中包含 number，number 不兼容 string

// 更复杂的例子：对象联合类型
interface Cat { type: 'cat'; meow(): void }
interface Dog { type: 'dog'; bark(): void }
type Pet = Cat | Dog;

function handlePet(pet: Pet) {
  // pet.type 在此处是 'cat' | 'dog'
}

let cat: Cat = { type: 'cat', meow() {} };
let pet: Pet = cat;  // ✅ Cat 是 Pet 的子类型（Cat ∈ Pet）
```

> **实际项目建议**：在定义 API 参数或组件 props 时，优先使用联合类型而非宽泛的 `any` 或基础类型。这样既能获得精确的类型推导，又能保持赋值的灵活性。例如 `status: 'loading' | 'success' | 'error'` 比 `status: string` 安全得多。

## 三、函数参数的兼容性（重点难点）

### 3.1 参数数量：少参数函数可赋给多参数位置

这是一个反直觉但经过深思熟虑的设计决策：

```typescript
// 少参数的函数可以赋给需要更多参数的位置
function logName(name: string): void {
  console.log(name);
}

function processUser(id: number, name: string, email: string): void {
  console.log(id, name, email);
}

let fn: typeof processUser = logName;
// ✅ 合法！logName 只有 1 个参数，但可以赋给期望 3 个参数的位置

// 为什么这样设计？考虑以下场景：
const users = ['Alice', 'Bob', 'Charlie'];
users.forEach(logName); // forEach 期望 (value, index, array) => void
                        // 但我们传了只有 1 个参数的函数也没问题
```

**原理**：`Array.prototype.forEach` 的回调签名是 `(element: T, index: number, array: T[]) => void`。如果 TypeScript 强制要求参数数量完全匹配，那么所有只用到 `element` 的简单回调都需要写全 `(item) => logName(item)` 这种冗余包装——这在工程实践中极其繁琐。

> **注意**：反过来不行——多参数函数不能赋给少参数位置：
> ```typescript
> let shortFn: (name: string) => void = processUser;
> // ❌ processUser 需要 3 个参数，shortFn 只接受 1 个
> ```

### 3.1.1 参数数量规则的更多实际场景

```typescript
// 场景一：事件处理器 —— 最常见的应用
// DOM addEventListener 的回调签名是 (event: Event) => void
button.addEventListener('click', (event: MouseEvent) => {
  // 我们只用到了 MouseEvent 的属性，忽略了 Event 中不关心的字段
  console.log(`Clicked at (${event.clientX}, ${event.clientY})`);
});
// ✅ (event: MouseEvent) => void 可以赋给 (event: Event) => void

// 场景二：Promise.then 链式调用
function parseData(raw: string): { data: any } {
  return JSON.parse(raw);
}

// Promise.then 期望 (value: T) => U，但我们只关心 value 的一部分
const result = fetch('/api/data')
  .then(res => res.json())
  .then(obj => {
    // obj 的类型推断为任意 JSON 值，我们只取需要的字段
    console.log(obj.name);
    return obj; // 返回值可能比 then 期望的更宽泛
  });

// 场景三：数组高阶方法的回调
const numbers = [1, 2, 3, 4, 5];

// filter 只需要 (value) => boolean
const evens = numbers.filter(n => n % 2 === 0);  // ✅

// map 只需要 (value) => U
const doubled = numbers.map(n => n * 2);  // ✅

// reduce 签名是 (prev, curr, index, arr) => T
// 但通常只用到前两个参数
const sum = numbers.reduce((acc, val) => acc + val, 0);  // ✅

// 圆满的错误示例：多参数赋给少参数位置
type Logger = (msg: string) => void;
type VerboseLogger = (msg: string, level: 'info' | 'warn' | 'error', timestamp: number) => void;

const verboseLog: VerboseLogger = (msg, level, ts) =>
  console.log(`[${level}] [${ts}] ${msg}`);

let simpleLog: Logger = verboseLog;
// ❌ Error: Type 'VerboseLogger' is not assignable to type 'Logger'
// 原因：调用 simpleLog('hello') 时不会传 level 和 timestamp，
//       verboseLog 内部如果依赖这些参数就会出问题
```

### 3.2 函数参数的双向协变（Bivariance）

这是 TypeScript 最具争议性的设计之一。

#### 什么是双向协变？

在标准的类型理论中，函数参数应该是**逆变的（Contravariant）**——即参数类型应该向"更宽泛"的方向兼容。但 TypeScript 出于实用主义考量，在大多数场景下允许**双向协变（Bivariance）**：

```typescript
interface Animal {
  species: string;
}
interface Dog extends Animal {
  breed: string;
}
interface Cat extends Animal {
  meow(): void;
}

let animalHandler = (animal: Animal): void => {};
let dogHandler = (dog: Dog): void => {};

// 协变方向：Dog 是 Animal 的子类型
// 正常情况下（返回值位置），Dog → Animal 是合法的（协变）

// ===== TypeScript 的默认行为：双向协变 =====
let handler1: (arg: Animal) => void = dogHandler;  // ✅ 协变方向：窄→宽
let handler2: (arg: Dog) => void = animalHandler;  // ✅ 逆变方向：宽→窄 也允许！

// 第二行在严格的类型理论中是不安全的，
// 但 TypeScript 为了实用性选择了放行。
```

**为什么 TS 选择双向协变？**

核心原因是 **DOM API 的现实约束**：

```typescript
// Array.prototype.sort 的真实签名
declare function sort<T>(compareFn?: (a: T, b: T) => number): T[];

// 开发者经常这样使用
const numbers = [1, 3, 2];
numbers.sort((a, b) => a - b); // 参数类型推断为 number

// 如果 sort 内部将这个回调存储起来并传递更具体的子类型呢？
// 或者事件监听器的模式：
element.addEventListener('click', (event: MouseEvent) => {
  // 这里用的是 MouseEvent（Event 的子类型）
});

// 如果严格要求逆变，addEventListener 的签名必须是：
// addEventListener(type: string, handler: (e: Event) => void)
// 那么 (event: MouseEvent) => {} 就不能赋给它了！
// 这会导致大量现有代码报错。
```

#### 双向协变的底层类型理论

从类型论角度理解，函数参数的逆变性源于**函数类型的正确性保证**。假设有函数 `f: (Dog) => void` 被赋给 `g: (Animal) => void` 类型的变量：

```typescript
// 逆变不安全的完整演示
let handleDog: (d: Dog) => void = (dog) => {
  console.log(dog.breed); // 使用了 Dog 特有的属性
};

// 如果允许逆变（宽→窄），以下代码在运行时会崩溃：
let handleAnimal: (a: Animal) => void = handleDog; // ⚠️ 假设这被允许

handleAnimal({ species: 'cat' }); // 运行时错误！cat 没有 breed 属性
```

这就是为什么严格类型系统要求参数逆变的根本原因：调用方传入的参数范围比声明更广，而函数体可能依赖窄类型的特定属性。

TypeScript 的双向协变本质上是在说"我们相信开发者不会做危险的事"，用便利性换取了理论上的一致性。

#### 实际项目中如何应对双向协变

```typescript
// 策略一：开启 strictFunctionTypes（推荐）
// 在 tsconfig.json 中设置 "strictFunctionTypes": true
// 这样可以捕获大部分危险的逆变赋值

// 策略二：使用泛型约束替代具体的回调签名
type EventListener<E extends Event = Event> = (event: E) => void;

const clickHandler: EventListener<MouseEvent> = (e) => {
  console.log(e.clientX, e.clientY);
};
// 此时 clickHandler 的类型精确为 (MouseEvent) => void，
// 避免了与通用 Event 处理器混淆

// 策略三：使用重载签名明确表达意图
interface SafeEventTarget {
  addEventListener(type: 'click', handler: (e: MouseEvent) => void): void;
  addEventListener(type: 'input', handler: (e: InputEvent) => void);
  addEventListener(type: string, handler: (e: Event) => void): void;
}

// 每种事件类型都有对应的精确处理器签名，编译器能做出最严格的检查
```

### 3.2.1 strictFunctionTypes 的实际影响对比

TypeScript 提供了 `strictFunctionTypes` 编译选项来控制这一行为。**注意：它只影响函数类型的显式声明，不影响方法简写形式**：

```typescript
// 开启 strictFunctionTypes 后：

// ===== 函数类型声明（受影响）=====
type CompareFn = (a: Animal) => void;

let f1: CompareFn = dogHandler;  // ✅ 协变仍然允许
let f2: (arg: Dog) => void = animalHandler;
// ❌ 逆变不再允许！strictFunctionTypes 下报错

// ===== 接口中的方法声明（受影响）=====
interface Comparer {
  compare: (a: Animal) => void;
}
let comparer: Comparer = { compare: dogHandler };  // ✅
// let comparer2: Comparer = { compare: animalHandler };
// ❌ strictFunctionTypes 下报错

// ===== 对象方法简写（不受影响！）=====
interface ObjectMethod {
  compare(a: Animal): void;  // 方法简写语法
}
// 即使开启了 strictFunctionTypes，这里仍然是双向协变！
let om: ObjectMethod = {
  compare(dog: Dog) {}  // ✅ 方法简写不受限制
};
```

**为什么方法简写不受限制？** 因为大量现有的类和接口使用了这种风格，强制改变会导致生态系统的广泛破坏。这是一个历史遗留的妥协。

### 3.3 可选参数与剩余参数的兼容性

```typescript
// 可选参数的兼容性规则
function optional(x?: number): void {}
function required(x: number): void {}

let f1: typeof required = optional;  // ✅ 可选→必需：合法
// let f2: typeof optional = required; // ❌ 必需→可选：不合法
// （因为调用 f2() 时不传参会出问题）

// 剩余参数
function withRest(...args: string[]): void {}
function withFixed(s: string): void {}

let f3: typeof withFixed = withRest;  // ✅ 剩余参数函数可以赋给固定参数
// 剩余参数等价于"接受任意数量的参数"，当然能满足"接受1个参数"

// 剩余参数之间的兼容
function restAny(...args: any[]): void {}
function restString(...args: string[]): void {}
let f4: typeof restString = restAny;  // ✅ any 更宽泛
```

### 3.4 重载签名的兼容性判断

```typescript
function overloaded(x: string): string;
function overloaded(x: number): number;
function overloaded(x: string | number): string | number {
  return typeof x === 'string' ? x.toUpperCase() : x * 2;
}

// 重载函数只能赋给与之兼容的重载目标
// 目标签名的每个重载都必须有源函数的对应兼容版本
function target(s: string): string;
function target(n: number): number;
function target(sn: string | number): string | number {
  return sn as never;
}

let assign: typeof target = overloaded;  // ✅ 所有签名都兼容
```

**规则**：重载函数的兼容性要求——源函数的**每一个**重载签名都必须与目标函数的**某一个**重载签名兼容（不是一一对应，而是覆盖关系）。

### 3.4.1 重载兼容的复杂场景与错误演示

```typescript
// 场景一：部分重载不兼容 —— 整体赋值失败
function flexible(x: string): string;
function flexible(x: number): boolean;
function flexible(x: string | number): string | boolean {
  return typeof x === 'string' ? x.toUpperCase() : x > 0;
}

function strictOnly(s: string): string;
function strictOnly(s: string | number): string | boolean {
  return typeof x === 'string' ? x : String(x);
}

// ❌ flexible 不能赋给 strictOnly
// 原因：flexible 有 (x: number) => boolean 的重载，
//       但 strictOnly 没有对应的接受 number 的重载可以"容纳"它

// 场景二：重载顺序影响兼容性判断
function lenient(x: string | number): void;
function lenient(x: string): void { /* impl */ }
// 第一个签名最宽泛，覆盖所有情况

function specific(x: string): void { /* impl */ }

let assign: typeof specific = lenient; // ✅ lenient 的宽泛签名兼容具体签名

// 场景三：实际开发中的典型用法 —— 库的类型声明
declare function parse(input: string): Result;
declare function parse(input: Buffer, encoding?: string): Result;

// 用户实现时只需要匹配至少一个重载
const myParse: typeof parse = (input, encoding?) => {
  if (typeof input === 'string') {
    return JSON.parse(input);
  }
  return input.toString(encoding as BufferEncoding);
};
```

## 四、返回值类型的协变

与普通类型的位置一样，返回值位置遵循标准的**协变（Covariance）**规则：

```typescript
class Base { baseMethod() {} }
class Derived extends Base { derivedMethod() {} }

function getBase(): Base { return new Base(); }
function getDerived(): Derived { return new Derived(); }

let f1: () => Base = getDerived;  // ✅ 协变：Derived → Base（子→父）
// let f2: () => Derived = getBase; // ❌ 逆变不成立：Base 不能替代 Derived
```

**包含方法的对象的兼容性**：

```typescript
interface HasMethod {
  process(data: string): number;
}

interface HasMoreMethods {
  process(data: string): number;
  extra(data: number): string;
}

let obj1: HasMethod = {
  process(data: string): number { return data.length; }
};

let obj2: HasMoreMethods = {
  process(data: string): number { return data.length; },
  extra(data: number): string { return String(data); }
};

obj1 = obj2;  // ✅ HasMoreMethods 拥有 HasMethod 的全部成员 → 兼容
// obj2 = obj1; // ❌ 反过来缺 extra 方法 → 不兼容
```

## 五、协变、逆变与不变的形式化定义

### 5.1 用集合包含关系理解方差（Variance）

假设存在类型继承链 `Dog extends Animal`（即 `Dog ⊆ Animal`，Dog 的值集合是 Animal 的值集合的子集）。现在考察复合类型构造器（如数组、函数、泛型容器）如何保持或翻转这种子类型关系：

**设类型关系**：`Dog ≤ Animal`（Dog 是 Animal 的子类型）

| 方差类型 | 复合类型上的关系 | 含义 | 示例 |
|---------|----------------|------|------|
| **协变 Covariant** | `Container<Dog> ≤ Container<Animal>` | 方向保持一致 | 返回值类型、数组元素类型 |
| **逆变 Contravariant** | `Container<Dog> ≥ Container<Animal>` | 方向相反 | 严格模式下的函数参数 |
| **双向协变 Bivariant** | `Container<Dog>` 和 `Container<Animal>` 互相兼容 | 两个方向都允许 | TS 默认的函数参数行为 |
| **不变 Invariant** | 无任何方向兼容 | 必须完全相同 | 不可变引用容器 |

### 5.2 数学视角的解释

从集合论角度理解：

- **协变**：若 \( A \subseteq B \)，则 \( F(A) \subseteq F(B) \)。构造器 F 保持包含关系。
- **逆变**：若 \( A \subseteq B \)，则 \( F(A) \supseteq F(B) \)。构造器 F 翻转包含关系。
- **不变**：\( F(A) \) 与 \( F(B) \) 之间不存在子类型关系，除非 \( A = B \)。

### 5.3 函数类型中方差的分布

一个完整的函数类型 `(param: P) => R` 中存在两个方差维度：

```typescript
// 函数类型：(param: P) => R
//
// - 参数位置 P：理论上应该是逆变的
//   如果 Dog ≤ Animal，则：
//   (param: Animal) => R  ≤  (param: Dog) => R
//   （接受 Animal 的函数比接受 Dog 的函数"更通用"，因而是"更小的子类型"）
//
// - 返回值位置 R：是协变的
//   如果 Dog ≤ Animal，则：
//   () => Dog  ≤  () => Animal
//   （返回 Dog 的函数可以用在任何需要返回 Animal 的地方）

// 综合示例
type Fn1 = (x: Animal) => Dog;
type Fn2 = (x: Dog) => Animal;

// 在严格函数类型下：
// Fn1 的参数更宽（Animal > Dog），返回值更窄（Dog < Animal）
// Fn2 的参数更窄（Dog < Animal），返回值更宽（Animal > Dog）
// 两者之间没有直接的子类型关系
```

### 5.4 实际代码演示

```typescript
class Entity { id: number; }
class User extends Entity { name: string; }
class Admin extends User { permissions: string[]; }

// ---- 卐变的实际例子：数组和 Promise ----

// 数组是协变的（TS 中）
let users: User[] = [{ id: 1, name: 'alice' }];
let entities: Entity[] = users;  // ✅ User[] → Entity[] 卧变
// 注意：这在运行时其实不安全！entities.push(new Entity()) 会污染 users
// 这是 TS 为便利性做出的妥协

// Promise 也是协变的
let userPromise: Promise<User> = Promise.resolve({ id: 1, name: 'bob' });
let entityPromise: Promise<Entity> = userPromise; // ✅ 协变

// ---- 不变的实际例子 ----

// 以下示意"不变"的场景（某些严格的语言如 Scala 会这样处理）
// 假设有一个不可变的容器类型 ImmutableBox<T>
// ImmutableBox<Dog> 和 ImmutableBox<Animal> 之间不能互相赋值
// （除非 DTS 有特殊的方差标注）

// ---- 实际应用：事件的协变性 ----
type EventHandler<T> = (event: T) => void;

// 由于 TS 默认双向协变，以下两种赋值都通过：
let animalEvent: EventHandler<Animal> = (dog: Dog) => {};  // ✅ 协变方向
let dogEvent: EventHandler<Dog> = (animal: Animal) => {};   // ✅ 逆变方向也放行

// 开启 strictFunctionTypes 后：
// 第一行仍然 ✅
// 第二行变为 ❌（因为参数位置的逆变不再被允许）
```

## 六、类的兼容性

类的兼容性结合了结构化比较和名义化因素，规则较为复杂：

### 6.1 实例成员的结构化比较

类的实例类型兼容性基于**实例成员**进行结构化比较：

```typescript
class Point2D {
  x: number = 0;
  y: number = 0;
}

class Point3D {
  x: number = 0;
  y: number = 0;
  z: number = 0;
}

// ✅ Point3D 拥有 Point2D 的全部实例成员 → 兼容
let p2d: Point2D = new Point3D();

// ❌ Point2D 缺少 z → 不兼容
// let p3d: Point3D = new Point2D();
```

### 6.2 静态成员和构造函数不参与比较

```typescript
class WithStatic {
  static id: string = 'static-id';
  instanceField: number = 42;
}

class WithoutStatic {
  instanceField: number = 42;
}

// ✅ 静态成员不影响实例类型的兼容性
let ws: WithoutStatic = new WithStatic();
let wsWithout: WithStatic = new WithoutStatic();
```

**原理**：TypeScript 将**实例类型**（instance type）和**静态类型**（constructor type / static side）分开处理。赋值兼容性只考察实例类型，静态成员属于构造函数本身的类型。

### 6.3 private / protected 成员导致名义化比较

当类中出现 `private` 或 `protected` 成员时，兼容性规则发生根本变化——从结构化比较切换为**名义化比较（nominal comparison）**：

```typescript
class A {
  private secret: string = 'a-secret';
  public visible: number = 1;
}

class B {
  private secret: string = 'b-secret';  // 同名私有字段
  public visible: number = 1;
}

// ❌ 即使结构完全相同，也不兼容！
// 因为 private 成员使得比较变成"同源"检查
let a: A = new B();  // Error!
let b: B = new A();  // Error!

// 但是，继承自同一基类的 private 成员是可以跨子类兼容的：
class Base {
  private secret: string = 'base';
  public value: number = 0;
}

class Child1 extends Base {
  public extra: string = 'c1';
}

class Child2 extends Base {
  public extra: string = 'c2';
}

// ✅ 继承自同一个基类的 private 成员，子类之间兼容
let c1: Child1 = new Child2();

// protected 成员同理
class ProtectedBase {
  protected shared: number;
}

class PA extends ProtectedBase { public pa = 1; }
class PB extends ProtectedBase { public pb = 2; }

let pa: PA = new PB();  // ✅ protected 来自同一个声明
```

**设计意图**：`private`/`protected` 成员通常承载着类的内部不变量（invariant），两个独立声明同名私有字段的类虽然字段名相同，但其语义和约束可能截然不同。强行允许兼容会破坏封装性。

### 6.3.1 private/protected 兼容性的深层机制与实际影响

```typescript
// 场景一：private 字段导致的意外不兼容（最常见的坑）
// 在使用 ORM 或 DI 框架时经常遇到

class Repository<T> {
  private items: T[] = [];
  findAll(): T[] { return this.items; }
}

class UserService extends Repository<User> {
  // 隐式继承 items 的 private 声明
  findAdmins(): User[] {
    return this.items.filter(u => u.role === 'admin');
  }
}

class ProductService extends Repository<Product> {
  findExpensive(): Product[] {
    return this.items.filter(p => p.price > 100);
  }
}

// ❌ 即使两个类结构完全相同，也不兼容！
let userService: UserService = new ProductService();
// Error: Type 'ProductService' is not assignable to type 'UserService'
// 原因：两个类各自有独立的 private items 声明，来源不同

// 解决方案一：改用 protected
class BetterRepository<T> {
  protected items: T[] = [];
  findAll(): T[] { return this.items; }
}
// 如果继承自同一个基类，protected 可以跨子类兼容

// 场景二：class 表达式的每次调用都产生不同的 private 身份
const createCounter = class {
  private count = 0;
  increment() { return ++this.count; }
};

let c1 = new createCounter();
let c2 = new createCounter();
let cRef: typeof c1 = c2;  // ❌ 不兼容！每次 class 表达式都是独立的类型声明

// 场景三：正确利用 private 名义化来保证类型安全
class UserId { private __brand!: unique symbol; constructor(public id: string) {} }
class OrderId { private __brand!: unique symbol; constructor(public id: string) {} }

function processUser(userId: UserId) { /* ... */ }

processUser(new UserId('user-123'));  // ✅
// processUser(new OrderId('order-456')); // ❌ 编译期拦截！这就是名义类型的优势
```

> **实际项目建议**：当你需要"同名但不同语义"的类型区分时（如 ID 类型安全），可以利用 `private` 的名义化特性来实现**品牌类型（Nominal Branding）**模式。这比单纯依赖结构化类型能捕获更多逻辑错误。

### 6.4 泛型类的兼容性

```typescript
// 泛型参数未被用于任何成员时
class Empty<T> {}

let e1: Empty<number> = new Empty<string>();  // ✅ 完全兼容
let e2: Empty<string> = new Empty<boolean>();  // ✅ 完全兼容
// 因为 T 没有影响任何实例成员的结构

// 泛型参数被用于成员时
class Box<T> {
  value: T;
  constructor(value: T) { this.value = value; }
}

let box1: Box<number> = new Box(42);
let box2: Box<string> = new Box('hello');
// let cross: Box<number> = box2;  // ❌ T 影响了 value 的类型，不再无条件兼容
```

**规则总结**：泛型类 `Generic<T>` 的兼容性取决于 T 是否出现在实例成员的类型声明中。如果 T 仅作为运行时的临时计算中间值而不体现在任何公开属性上，则不同 T 实例化的类互相兼容。

### 6.4.1 泛型类兼容性的实际场景

```typescript
// 场景一：类型擦除后的兼容 —— EventEmiiter 模式
class EventEmitter<Events extends Record<string, any>> {
  private listeners = new Map<string, Function[]>();

  on<EventName extends keyof Events>(
    event: EventName,
    handler: (data: Events[EventName]) => void
  ): void { /* ... */ }
}

// 如果 Events 泌型参数不影响实例的"公共形状"
let ee1: EventEmitter<{ click: MouseEvent }>;
let ee2: EventEmitter<{ change: ChangeEvent }>;
// 两者是否兼容取决于 Events 是否参与公共属性的类型声明

// 场景二：泛型约束对兼容性的影响
interface Comparable<T> {
  compareTo(other: T): number;
}

class NumberBox implements Comparable<number> {
  constructor(public value: number) {}
  compareTo(other: number): number { return this.value - other; }
}

class StringBox implements Comparable<string> {
  constructor(public value: string) {}
  compareTo(other: string): number { return this.value.localeCompare(other); }
}

let cb: Comparable<number> = new NumberBox(42);     // ✅
// let cb2: Comparable<number> = new StringBox('hi'); // ❌ 类型参数不同且被使用

// 场景三：泛型类的协变使用
// 虽然 Box<Box<Dog>> 不能赋给 Box<Box<Animal>>
// 但在只读场景下可以手动声明协变接口
interface ReadOnlyContainer<out T> {   // 协变标注（TS 不支持此语法，仅为概念示意
  readonly value: T;
}
```

## 七、泛型类型的兼容性

### 7.1 未使用泛型参数的情况

当一个泛型接口或类型的类型参数没有在成员中被使用时，其兼容性与具体化无关：

```typescript
interface EmptyHolder<T> {
  // T 没有出现
}

let eh1: EmptyHolder<number>;
let eh2: EmptyHolder<string>;

eh1 = eh2;  // ✅ 兼容
eh2 = eh1;  // ✅ 双向兼容
```

### 7.2 使用了泛型参数时的关系推导

当类型参数被使用时，兼容性根据参数位置的具体类型关系递归推导：

```typescript
interface Container<T> {
  value: T;
  getValue(): T;
  setValue(value: T): void;
}

let numContainer: Container<number> = { value: 42, getValue: () => 42, setValue: v => {} };
let strContainer: Container<string> = { value: 'hi', getValue: () => 'hi', setValue: v => {} };

// numContainer = strContainer; // ❌ 不兼容
// strContainer = numContainer; // ❌ 也不兼容
// number 和 string 之间没有子类型关系
```

### 7.3 泛型接口的实现兼容性

实现泛型接口时，具体类型必须满足接口的所有约束：

```typescript
interface Repository<T, ID extends number | string> {
  findById(id: ID): T | undefined;
  save(entity: T): T;
  delete(id: ID): boolean;
}

class UserRepository implements Repository<User, number> {
  findById(id: number): User | undefined { /* ... */ return undefined; }
  save(entity: User): User { /* ... */ return entity; }
  delete(id: number): boolean { /* ... */ return false; }
}

// ✅ UserRepository 正确实现了 Repository<User, number>

// 如果尝试用不兼容的类型实现：
// class BadRepo implements Repository<string, number> { ... }
// save 方法的参数类型 string 无法满足 User 的要求（如果 User 不是 string 子类型的话）
```

### 7.3.1 泛型接口兼容性的进阶场景

```typescript
// 场景一：泛型函数类型的兼容性 —— 协变/逆变在泛型中的体现
type Transformer<T, U> = (input: T) => U;

// 对于 Transformer<Dog, Animal> 和 Transformer<Animal, Dog>：
type T1 = Transformer<Dog, Animal>;
type T2 = Transformer<Animal, Dog>;

// T1 的参数更窄（Dog < Animal），返回值更窄（Animal > Dog 不成立...）
// 实际上：Dog 是 Animal 的子类型，所以：
// - 参数位置：Dog（窄）vs Animal（宽）→ 逆变关系，T1 参数"更大"
// - 返回值位置：Animal（宽）vs Dog（窄）→ 协变关系，T1 返回值"更宽"
// 综合判断取决于 strictFunctionTypes

// 场景二：条件类型中的兼容性推导
type IsSubType<A, B> = A extends B ? true : false;

type R1 = IsSubType<{ a: number }, { a: number; b: string }>; // false
type R2 = IsSubType<{ a: number; b: string }, { a: number }>;  // true

// 场景三：高阶泛型的兼容性 —— 难点
interface Mapper<T> {
  map<U>(fn: (item: T) => U): Mapper<U>;
}

let numberMapper: Mapper<number>;
let anyMapper: Mapper<any>;

numberMapper = anyMapper;   // ✅ Mapper<any> → Mapper<number>
// anyMapper = numberMapper; // ❌ 反向不成立

// 原因：any 可以赋给任何类型，但反过来不行
```

## 八、赋值兼容性的实际应用场景

### 8.1 回调函数传参时的类型放宽

```typescript
// 库代码声明了一个通用的事件处理器
type EventCallback<E> = (event: E) => void;

// 我们只需要用到 event 的一部分属性
interface MouseEvent {
  type: string;
  x: number;
  y: number;
  button: number;
  timestamp: number;
  // ... 很多其他属性
}

// 使用者只需关心坐标
function handleClick(event: MouseEvent) {
  console.log(`Clicked at (${event.x}, ${event.y})`);
}

// 由于双向协变，即使库期望的是更宽泛的处理器签名，
// 我们的 narrower handler 也能正常工作
let cb: EventCallback<MouseEvent> = handleClick;  // ✅

// 甚至可以接受更宽泛的参数类型（如果 strictFunctionTypes 未开启）
interface Event {
  type: string;
  timestamp: number;
}

function handleAnyEvent(event: Event) {
  console.log(`Event: ${event.type}`);
}

let cb2: EventCallback<MouseEvent> = handleAnyEvent; // ⚠️ 默认模式允许
```

### 8.1.1 回调函数类型放宽的实际应用

```typescript
// 场景一：React 组件的事件处理
// React 事件系统中的典型用法
function Button({ onClick }: { onClick: (e: React.MouseEvent) => void }) {
  return <button onClick={onClick}>Click me</button>;
}

// 使用者可以传入更具体的处理器
<Button
  onClick={(e: React.MouseEvent<HTMLButtonElement>) => {
    // e 的类型是更精确的 HTMLButtonElement 的 MouseEvent
    console.log(`Button clicked at (${e.clientX}, ${e.clientY})`);
    // 同时也能访问 HTMLButtonElement 特有的属性
    const button = e.currentTarget; // 类型为 HTMLButtonElement
  }}
/>;

// 场景二：数组方法的回调签名
interface User { id: string; name: string; role: 'admin' | 'user' }
const users: User[] = [
  { id: '1', name: 'Alice', role: 'admin' },
  { id: '2', name: 'Bob', role: 'user' },
];

// Array.find 的签名为 (predicate: (value: T, index: number, array: T[]) => unknown, thisArg?: any): T | undefined
const admin = users.find(u => u.role === 'admin');
// 我们只用了第一个参数，忽略了 index 和 array —— 完全合法

// 场景三：Promise 链中的类型收窄
fetch('/api/data')
  .then(res => res.json())
  .then((data: ApiResponse<User>) => {
    // data 被我们标注为具体类型，虽然 then 期望的是更宽泛的类型
    return data.payload;
  });
```

### 8.2 对象字面量的多余属性检查（Freshness）

Freshness（新鲜度）是 TypeScript 中针对对象字面量的一种特殊检查机制：

```typescript
interface Config {
  url: string;
  timeout: number;
}

// ✅ 直接赋值给变量 —— Freshness 生效，多余属性会被检查
let config: Config = {
  url: '/api',
  timeout: 5000,
  debug: true  // ❌ Error: 对象字面量只能指定已知属性，'debug' 不存在
};

// ✅ 但如果是先赋给变量再传递 —— Freshness 消失，多余属性被忽略
const rawConfig = {
  url: '/api',
  timeout: 5000,
  debug: true  // 这里的多余属性不会被检查
};
config = rawConfig;  // ✅ rawConfig 的类型被推断为 { url: string; timeout: number; debug: boolean }
                     // 而 { url: string; timeout: number; debug: boolean } 兼容 Config

// 另一种绕过方式：类型断言
config = {
  url: '/api',
  timeout: 5000,
  debug: true
} as Config;  // ✅ 断言跳过 Freshness 检查
```

**Freshness 的设计意图**：防止开发者因拼写错误而意外传入多余属性（通常是 bug 的信号），同时不破坏结构化类型系统的灵活性。它只在对象字面量**首次出现**时触发，之后该值就不再是"新鲜的"了。

### 8.2.1 Freshness 的更多细节与边界情况

```typescript
// 边界 1：嵌套对象中的 Freshness 检查
interface Address {
  city: string;
  zip: string;
}

interface User {
  name: string;
  address: Address;  // 嵌套对象类型
}

// 嵌套的对象字面量也享受 Freshness 保护
let user: User = {
  name: 'Alice',
  address: {
    city: 'Beijing',
    zip: '100000',
    district: 'Haidian'  // ❌ Error: 'district' 不存在于 Address 类型中
    // 嵌套层级的对象字面量同样触发 Freshness 检查
  },
};

// 边界 2：函数返回值的 Freshness
function createConfig() {
  return {
    url: '/api',
    timeout: 5000,
    debug: true,   // 不报错 —— 函数返回值不是"新鲜"的
  };
}

const config: Config = createConfig(); // ✅ 多余属性被忽略

// 边界 3：展开运算符的影响
const baseConfig = { url: '/api', timeout: 5000 };

// 展开后的字面量仍然是新鲜的
let config2: Config = {
  ...baseConfig,
  debug: true  // ❌ 仍然会报错！展开后整体被视为新鲜字面量
};

// 正确做法
let config3: Config = { ...baseConfig };  // ✅

// 边界 4：数组元素不受 Freshness 影响（数组不是对象字面量）
interface Point { x: number; y: number }
const points: Point[] = [
  { x: 1, y: 2, label: 'A' },  // ⚠️ TS 4.x+ 中可能会警告，但通常不报错
  { x: 3, y: 4, label: 'B' },  // 数组元素在较新版本中也受 Freshness 约束
];

// 绕过数组元素的 Freshness
const rawPoints = [
  { x: 1, y: 2, label: 'A' },
  { x: 3, y: 4, label: 'B' },
];
const safePoints: Point[] = rawPoints;  // ✅ 先赋变量再使用
```

> **实际项目建议**：Freshness 检查是 TypeScript 防御拼写错误的最佳工具之一。当遇到"多余属性"报错时，首先检查是否是拼写错误而非急于用 `as` 断言绕过。

### 8.3 类型的断言与强制转换

```typescript
// 当你确定某个值具有编译器无法推断出的类型时
const data: unknown = JSON.parse('{"name":"test","age":25}');

// 方式一：类型断言
let user = data as { name: string; age: number };

// 方式二：双重断言（当两个类型完全不兼容时）
interface StrictType {
  readonly id: number;
  name: string;
  greet(): string;
}

const roughObject = { id: 1, name: 'test' };

// let strict: StrictType = roughObject;  // ❌ 缺少 greet 方法
// let strict2: StrictType = roughObject as StrictType;  // ❌ 直接断言也可能失败

// 双重断言：先断言为 unknown（顶层类型），再断言为目标类型
let strict: StrictType = roughObject as unknown as StrictType;  // ✅ 强制成功

// ⚠️ 双重断言完全绕过了类型检查，运行时可能出错！仅在你确信安全时使用。
```

## 九、类型断言 as 与兼容性的关系

### 9.1 类型断言的本质

类型断言（`as`）告诉编译器："相信我，我知道自己在做什么"。它**绕过正常的兼容性检查**，但不产生任何运行时代码：

```typescript
let someValue: unknown = 'this is a string';

// 正常方式：类型守卫
let strLength: number;
if (typeof someValue === 'string') {
  strLength = someValue.length;
}

// 断言方式：直接告诉编译器类型
let len = (someValue as string).length;  // ✅ 无需类型守卫
```

**关键区别**：

| 特性 | 类型断言 `as` | 类型转换（运行时） |
|------|-------------|------------------|
| 发生时机 | 编译期 | 运行时 |
| 性能开销 | 零 | 取决于转换逻辑 |
| 安全保证 | 无 | 可能抛异常 |
| 适用场景 | 开发者确知类型时 | 需要运行时验证时 |

### 9.2 双重断言的使用场景与风险

双重断言 `as unknown as T` 用于两个类型之间没有任何重叠的情况：

```typescript
// 典型场景：来自不可信源的JSON数据
const apiResponse = fetchSomeData(); // 返回 any/unknown

// 你知道这个响应实际上符合你的接口形状
interface DetailedUser {
  id: number;
  name: string;
  email: string;
  role: 'admin' | 'user' | 'guest';
  preferences: {
    theme: 'light' | 'dark';
    notifications: boolean;
  };
}

// 直接断言可能会失败（因为 any/unknown 到复杂类型的路径受限）
const user: DetailedUser = apiResponse as unknown as DetailedUser;

// ⚠️ 风险：如果 apiResponse 实际上不符合 DetailedUser 的结构，
//     运行时会得到 undefined 或其他意外行为
console.log(user.preferences.theme);  // 可能是 undefined！
```

**推荐的安全实践**：配合运行时校验库（如 zod、io-ts、class-validator）使用：

```typescript
import { z } from 'zod';

const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string().email(),
  role: z.enum(['admin', 'user', 'guest']),
  preferences: z.object({
    theme: z.enum(['light', 'dark']),
    notifications: z.boolean()
  })
});

// 先运行时校验，再类型收窄
const parsed = UserSchema.safeParse(apiResponse);
if (parsed.success) {
  const user: DetailedUser = parsed.data;  // 类型安全！无需断言
}
```

### 9.3 `as const` 对字面量类型的影响

`as const` 是一个特殊的断言形式，它不是"绕过检查"，而是**将类型尽可能收窄到最具体的字面量类型**：

```typescript
// 普通 const 声明
const normal = {
  name: 'Alice',
  age: 30,
  roles: ['admin', 'editor']
};
// 推断类型：
// {
//   name: string;       // string（ widened from 'Alice'）
//   age: number;        // number（widened from 30）
//   roles: string[];    // string[]（widened from string literal array）
// }

// as const 断言
const narrowed = {
  name: 'Alice',
  age: 30,
  roles: ['admin', 'editor']
} as const;
// 推断类型：
// {
//   readonly name: 'Alice';              // 字面量类型 'Alice'
//   readonly age: 30;                    // 字面量类型 30
//   readonly roles: readonly ['admin', 'editor'];  // 只读元组 + 字面量
// }

// 实际用途：让类型系统精确表达配置/常量
type Config = typeof narrowed;
// 等价于：
// {
//   readonly name: 'Alice';
//   readonly age: 30;
//   readonly roles: readonly ['admin', 'editor'];
// }
```

**`as const` 对类型兼容性的影响**：由于类型被大幅收窄，原本兼容的赋值可能变得不兼容：

```typescript
let s: string = normal.name;  // ✅ string ← string
let s2: string = narrowed.name;  // ✅ string ← 'Alice'（字面量类型可赋给其父类型）

let literal: 'Alice' = normal.name;    // ❌ string 不能赋给 'Alice'
let literal2: 'Alice' = narrowed.name; // ✅ 'Alice' ← 'Alice'（精确匹配）
```

### 9.3.1 as const 在实际项目中的高级用法

```typescript
// 用法一：构建类型安全的路由映射
const ROUTES = {
  home: '/',
  users: '/users',
  userId: '/users/:id',
  settings: '/settings',
} as const;

type RouteKey = keyof typeof ROUTES;
// type RouteKey = 'home' | 'users' | 'userId' | 'settings'

type RoutePath = typeof ROUTES[RouteKey];
// type RoutePath = '/' | '/users' | '/users/:id' | '/settings'

function navigate(route: RouteKey, params?: Record<string, string>) {
  let path = ROUTES[route];
  if (params) {
    for (const [k, v] of Object.entries(params)) {
      path = path.replace(`:${k}`, v);
    }
  }
  window.history.pushState(null, '', path);
}

navigate('home');          // ✅
navigate('userId', { id: '42' });  // ✅
// navigate('profile');    // ❌ 不存在的路由

// 用法二：构建类型安全的 API 端点定义
const API_ENDPOINTS = {
  getUser: '/api/users/:id',
  createUser: '/api/users',
  updateUser: '/api/users/:id',
  deleteUser: '/api/users/:id',
} as const;

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';

const API_CONFIG = {
  getUser:   { method: 'GET' as const, endpoint: API_ENDPOINTS.getUser },
  createUser:{ method: 'POST' as const, endpoint: API_ENDPOINTS.createUser },
  updateUser:{ method: 'PUT' as const, endpoint: API_ENDPOINTS.updateUser },
  deleteUser:{ method: 'DELETE' as const, endpoint: API_ENDPOINTS.deleteUser },
} as const;

// 用法三：构建不可变的配置对象（防止运行时意外修改）
const APP_CONFIG = {
  apiUrl: import.meta.env.VITE_API_URL ?? 'https://api.example.com',
  maxRetryCount: 3,
  timeoutMs: 30000,
  supportedLocales: ['zh-CN', 'en-US', 'ja-JP'],
} as const;

// APP_CONFIG.apiUrl = 'hacked';  // ❌ 只读属性不能修改

type AppConfig = typeof APP_CONFIG;
// 所有值都是字面量类型，可以在编译期被完整推导
```

## 十、常见陷阱与调试技巧

### 10.1 解读 "不能将类型 X 赋值给类型 Y"

这是最常见的 TypeScript 错误。系统化的排查步骤：

```typescript
// 典型错误信息：
// Type '{ id: number; name: string; }' is not assignable to parameter of
// type '{ id: number; name: string; email: string; }'.
```

**排查清单**：

| # | 检查项 | 常见原因 |
|---|--------|---------|
| 1 | 是否缺少必需属性？ | 目标类型的某个 non-optional 属性未提供 |
| 2 | 属性类型是否兼容？ | 如 `number` vs `string`、`Dog` vs `Animal` 的方向问题 |
| 3 | 是否有多余属性？ | 对象字面量触发了 Freshness 检查 |
| 4 | 函数参数数量/类型？ | 参数过多或类型方差方向错误 |
| 5 | private/protected 成员来源？ | 不同起源的私有成员导致名义化比较失败 |
| 6 | null/undefined？ | `strictNullChecks` 下未处理的可能空值 |

### 10.2 利用条件类型测试兼容关系

TypeScript 的条件类型提供了一个强大的调试工具——利用 `extends` 关键字在编译期测试任意两个类型的兼容关系：

```typescript
// 通用兼容性测试工具类型
type IsAssignable<A, B> = A extends B ? true : false;

// 测试基本类型
type T1 = IsAssignable<string, string | number>;  // true
type T2 = IsAssignable<string | number, string>;   // false
type T3 = IsAssignable<'hello', string>;            // true
type T4 = IsAssignable<string, 'hello'>;            // false

// 测试对象类型
interface Source { id: number; name: string; extra: boolean; }
interface Target { id: number; name: string; }

type T5 = IsAssignable<Source, Target>;  // true —— Source 拥有 Target 的全部成员
type T6 = IsAssignable<Target, Source>;  // false —— Target 缺少 extra

// 测试函数类型的方差
type HandlerDog = (d: Dog) => void;
type HandlerAnimal = (a: Animal) => void;
type T7 = IsAssignable<HandlerDog, HandlerAnimal>;  // 取决于 strictFunctionTypes

// 测试类兼容性
type T8 = IsAssignable<Point3D, Point2D>;  // true
type T9 = IsAssignable<Point2D, Point3D>;  // false

// 测试 private 成员的影响
type T10 = IsAssignable<B, A>;  // false —— private 导致名义化比较
```

**进阶用法**：构建一个完整的类型级别调试工具集：

```typescript
// 更详细的兼容性诊断工具
type CompatibilityCheck<A, B> =
  A extends B
    ? B extends A
      ? '[双向兼容] A ≡ B（或至少互相可赋值）'
      : '[单向兼容] A → B（A 可赋给 B）'
    : B extends A
      ? '[单向兼容] B → A（B 可赋给 A）'
      : '[不兼容] A 与 B 互不可赋值';

type Result1 = CompatibilityCheck<string, string | number>;
// "[单向兼容] A → B（A 可赋给 B）"

type Result2 = CompatibilityCheck<{ a: number }, { a: number; b: string }>;
// "[不兼容] A 与 B 互不可赋值"
```

### 10.2.1 条件类型调试的更多实用模式

```typescript
// 模式一：提取两个类型的差异属性
type DiffKeys<T, U> =
  Exclude<keyof T, keyof U> | Exclude<keyof U, keyof T>;

type D1 = DiffKeys<{ a: number; b: string }, { a: number; c: boolean }>;
// type D1 = 'b' | 'c' —— 快速找出不匹配的属性

// 模式二：检查某个类型是否为"空类型"（never）
type IsNever<T> = [T] extends [never] ? true : false;

type N1 = IsNever<never>;    // true
type N2 = IsNever<string>;   // false
type N3 = IsNever<string & number>; // true（string & number = never）

// 模式三：检查联合类型的所有成员是否都满足某条件
type AllMembersExtends<U, Base> = U extends Base ? true : false;

type A1 = AllMembersExtends<'a' | 'b', string>;     // true —— 所有成员都是 string 的子类型
type A2 = AllMembersExtends<string | number, string>; // false —— number 不是 string

// 模式四：获取类型在赋值时会丢失的信息（用于诊断）
type AssignmentLoss<A, B> =
  A extends B ? never :
  {
    source: A;
    target: B;
    reason: 'incompatible';
    missingFromSource: Exclude<keyof B, keyof A>;
    extraInSource: Exclude<keyof A, keyof B>;
  };

// 模式五：完整的兼容性报告生成器
type CompatibilityReport<S, T> = {
  assignable: S extends T;
  reverseAssignable: T extends S;
  missingProperties: Exclude<keyof T, keyof S>;
  extraProperties: Exclude<keyof S, keyof T>;
};

type Report = CompatibilityReport<
  { id: number; name: string },
  { id: number; name: string; email: string }
>;
// type Report = {
//   assignable: true;
//   reverseAssignable: false;
//   missingProperties: never;        // 源不缺目标任何属性
//   extraProperties: never;          // 等等... 这不对
// }
```

### 10.3 常见错误模式速查

```typescript
// ==== 模式 1：解构丢失了可选性 ====
interface Request {
  method: string;
  headers?: Record<string, string>;  // 可选
}

function handle(req: Request) {
  const { headers } = req;  // headers 的类型变成了 Record<string, string> | undefined
  // 如果后续把 headers 传给期望 Record<string, string> 的地方，就会报错
}

// 解决方案
function handleFixed(req: Request) {
  const { headers = {} } = req;  // 提供默认值
  // 现在 headers 是 Record<string, string>，不会出现 undefined
}

// ==== 模式 2：回调函数的 this 丢失 ====
class Counter {
  count = 0;
  increment() { this.count++; }
}

const counter = new Counter();
// setTimeout(counter.increment, 100);
// ❌ this 在回调中丢失，类型系统无法保证 this.count 存在

// 解决方案
setTimeout(() => counter.increment(), 100);  // 箭头函数保留 this

// ==== 模式 3：Promise resolve 的类型过宽 ====
async function fetchData(): Promise<string> {
  return 'data';  // 推断为 string
}

async function fetchDataBad(): Promise<string> {
  return Promise.resolve('data');  // 可能推断为更宽泛的类型
}

// 解决方案：显式注解
async function fetchDataGood(): Promise<string> {
  return Promise.resolve<string>('data');
}

// ==== 模式 4：交叉类型的属性合并陷阱 ====
type A = { x: number };
type B = { x: string };  // 同名属性，类型不同！

type AB = A & B;  // x 的类型是 number & string = never！

// let val: AB = { x: 42 };  // ❌ 42 不能赋值给 never
// let val2: AB = { x: 'hello' };  // ❌ 同理
```

### 11.3 核心原则总结

TypeScript 类型兼容性的设计哲学可以归纳为以下几点：

1. **结构性优先**：类型兼容性由成员决定而非名称，这使得鸭子类型在编译期成为现实，大大提升了灵活性。

2. **实用性优于纯粹性**：双向协变、数组协变等设计虽然在类型理论上不够严谨，但它们解决了真实的工程问题（DOM API 兼容、回调函数便利性等）。

3. **渐进式的严格度**：通过 `strictNullChecks`、`strictFunctionTypes` 等开关，开发者可以根据项目的成熟度和团队偏好逐步提升类型严格程度。

4. **Freshness 平衡**：对象字面量的多余属性检查在安全性和便利性之间取得平衡——既防止拼写错误又不破坏结构化类型的核心优势。

## 个人总结

类型兼容性是 TypeScript 类型系统中**最容易被误解、但又最重要**的部分之一。很多初学者面对"不能将类型 X 赋值给类型 Y"的错误感到困惑，本质上是因为不理解 TypeScript 结构化类型系统的运作机制。

几个关键要点值得反复思考：

- **结构化 vs 名义化**：TypeScript 默认按结构判断兼容性，但 `private`/`protected` 成员会让它退回到名义化模式。这个转折点常常让人措手不及。

- **双向协变的取舍**：TypeScript 放宽了函数参数的逆变要求以适配现实的 JS 生态，这是务实的表现，但也意味着你需要了解 `strictFunctionTypes` 来控制严格程度。

- **用条件类型做实验**：`X extends Y ? true : false` 这个简单的模式是你探索类型兼容性的最好工具。遇到不确定的关系时，用它来验证直觉。

- **类型断言是最后手段**：双重断言虽然能消除编译错误，但也意味着你放弃了类型安全的保护。优先考虑重构类型定义或使用运行时校验库。

掌握这些规则后，你会发现 TypeScript 的错误信息不再是晦涩的天书，而是指向明确问题的精确诊断。
