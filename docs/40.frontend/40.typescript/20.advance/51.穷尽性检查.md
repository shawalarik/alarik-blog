# 穷尽性检查 —— 利用 never 类型实现完整的分支覆盖

在使用联合类型和可辨识联合时，一个常见的隐患是：当新增了联合类型的成员后，忘记在所有 switch/case 或 if-else 分支中添加对应的处理逻辑。TypeScript 的 never 类型结合控制流分析，可以在编译期检测这种遗漏——这就是穷尽性检查（Exhaustiveness Checking）。

## 问题背景

考虑一个典型的状态机场景：

```typescript
type Status = 'pending' | 'running' | 'success' | 'failure';

function getStatusLabel(status: Status): string {
  switch (status) {
    case 'pending': return '等待中';
    case 'running':  return '运行中';
    case 'success':  return '成功';
    case 'failure':  return '失败';
  }
}
```

代码看起来没有问题。但两周后，需求变更，`Status` 新增了 `'cancelled'` 成员：

```typescript
type Status = 'pending' | 'running' | 'success' | 'failure' | 'cancelled';

function getStatusLabel(status: Status): string {
  switch (status) {
    case 'pending': return '等待中';
    case 'running':  return '运行中';
    case 'success':  return '成功';
    case 'failure':  return '失败';
    // cancelled 被遗漏了——函数对 cancelled 返回 undefined，可能引发运行时错误
  }
}
```

TypeScript 编译器**不会报错**。`getStatusLabel('cancelled')` 返回 `undefined`，下游代码如果期望 `string` 类型，就会产生难以排查的运行时 bug。

穷尽性检查的核心目标就是：**让这类遗漏在编译期就被捕获**。

## never 类型的核心特性

理解穷尽性检查的前提是深入理解 `never` 类型。

### never 是空类型

`never` 是 TypeScript 类型系统中的"底部类型"（bottom type），表示**永远不存在**的值：

```typescript
let x: never;
x = 1;        // Error: Type 'number' is not assignable to type 'never'
x = 'hello';   // Error: Type 'string' is not assignable to type 'never'
x = {};        // Error: Type '{}' is not assignable to type 'never'
```

没有任何值可以赋给 `never` 类型的变量——除了 `never` 自身：

```typescript
function throwError(msg: string): never {
  throw new Error(msg);
}

let x: never;
x = throwError('oops');  // OK: throw 表达式的返回类型为 never
```

### never 是所有类型的子类型

`never` 可以赋值给任意类型：

```typescript
let num: number = throwError('oops');   // OK
let str: string = throwError('oops');    // OK
let obj: object = throwError('oops');    // OK
```

这一特性使得 `never` 在函数返回值位置具有特殊意义。

### 控制流中的 never 收窄

TypeScript 的控制流分析会在某些代码路径上推断出 `never` 类型。当所有可能的类型变体都经过处理后，剩余变量的类型会被收窄为 `never`：

```typescript
type Direction = 'up' | 'down' | 'left' | 'right';

function move(dir: Direction) {
  if (dir === 'up') {
    // dir 在此处的类型被收窄为 'up'
  } else if (dir === 'down') {
    // dir 在此处的类型被收窄为 'down'
  } else if (dir === 'left') {
    // dir 在此处的类型被收窄为 'left'
  } else {
    // dir 在此处的类型被收窄为 'right'——唯一的剩余可能性
    // 如果 Direction 有更多成员且未被处理，这里就不是 'right' 而是 union 类型
    dir; // 类型为 'right'
  }
}
```

当所有分支都被覆盖时，最后一个 else 分支中的变量类型就是 **never**。穷尽性检查正是利用这一机制实现的。

## 基本 exhaustive 函数

### 实现原理

最经典的 exhaustive 函数实现如下：

```typescript
function exhaustive(value: never): never {
  throw new Error(`[Exhaustive check failed] Unexpected value: ${value}`);
}
```

工作流程：

1. 函数参数声明为 `never` 类型
2. 当调用处传入的变量类型**不是** `never` 时，TypeScript 报错
3. 只有当变量已被完全收窄为 `never`（即所有分支都已处理）时，调用才合法

### 在 switch 语句中使用

```typescript
type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'rectangle'; width: number; height: number }
  | { kind: 'triangle'; base: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':
      return Math.PI * shape.radius ** 2;
    case 'rectangle':
      return shape.width * shape.height;
    case 'triangle':
      return (shape.base * shape.height) / 2;
    default:
      // 此时 shape.kind 的类型为 never（三种 kind 都已处理）
      // 如果 Shape 新增了 { kind: 'polygon' } 成员，
      // 此处 shape 的类型将包含 'polygon'，不再是 never，触发编译错误
      return exhaustive(shape);
  }
}
```

### 在 if-else 链中使用

```typescript
type Result<T, E> =
  | { status: 'ok'; data: T }
  | { status: 'error'; error: E };

function handleResult<T, E>(result: Result<T, E>): void {
  if (result.status === 'ok') {
    console.log(result.data);
  } else if (result.status === 'error') {
    console.error(result.error);
  } else {
    // result 的类型在此处为 never
    exhaustive(result);
  }
}
```

## 与可辨识联合配合

可辨识联合（Discriminated Union）是穷尽性检查最常见的应用场景。

### Action Reducer 模式完整示例

在 Redux 风格的状态管理中，reducer 函数需要处理所有 action 类型：

```typescript
// 定义 State 和 Action
interface TodoState {
  items: TodoItem[];
  filter: FilterType;
  loading: boolean;
}

type TodoAction =
  | { type: 'ADD_TODO'; payload: { text: string } }
  | { type: 'TOGGLE_TODO'; payload: { id: string } }
  | { type: 'DELETE_TODO'; payload: { id: string } }
  | { type: 'SET_FILTER'; payload: FilterType }
  | { type: 'FETCH_TODOS_START' }
  | { type: 'FETCH_TODOS_SUCCESS'; payload: { items: TodoItem[] } }
  | { type: 'FETCH_TODOS_FAILURE'; payload: { error: string } };

function todoReducer(state: TodoState, action: TodoAction): TodoState {
  switch (action.type) {
    case 'ADD_TODO':
      return {
        ...state,
        items: [...state.items, createTodo(action.payload.text)],
      };
    case 'TOGGLE_TODO':
      return {
        ...state,
        items: state.items.map(item =>
          item.id === action.payload.id ? { ...item, done: !item.done } : item
        ),
      };
    case 'DELETE_TODO':
      return {
        ...state,
        items: state.items.filter(item => item.id !== action.payload.id),
      };
    case 'SET_FILTER':
      return { ...state, filter: action.payload };
    case 'FETCH_TODOS_START':
      return { ...state, loading: true };
    case 'FETCH_TODOS_SUCCESS':
      return { ...state, loading: false, items: action.payload.items };
    case 'FETCH_TODOS_FAILURE':
      return { ...state, loading: false };
    default:
      // 新增 action type 后此处自动报错
      return exhaustive(action);
  }
}
```

假设团队新增了一个 `ARCHIVE_TODO` action：

```typescript
type TodoAction =
  | /* ... existing actions ... */
  | { type: 'ARCHIVE_TODO'; payload: { id: string } };  // 新增
```

此时 `exhaustive(action)` 处立即产生编译错误：

```
Argument of type 'TodoAction' is not assignable to parameter of type 'never'.
  Type '{ type: "ARCHIVE_todo"; payload: { id: string; }; }' is not assignable to type 'never'.
```

开发者收到明确的提示，知道需要在 switch 中添加新的 case 分支。

### API 结果处理的完整覆盖

```typescript
type ApiResponse<T> =
  | { status: 200; data: T }
  | { status: 400; error: ValidationError[] }
  | { status: 401; error: AuthError }
  | { status: 403; error: ForbiddenError }
  | { status: 404; error: NotFoundError }
  | { status: 500; error: InternalServerError };

async function handleResponse<T>(response: ApiResponse<T>): Promise<void> {
  switch (response.status) {
    case 200:
      renderData(response.data);
      break;
    case 400:
      showValidationErrors(response.error);
      break;
    case 401:
      redirectToLogin();
      break;
    case 403:
      showForbiddenMessage();
      break;
    case 404:
      showNotFound();
      break;
    case 500:
      showErrorPage(response.error.message);
      break;
    default:
      exhaustive(response); // 确保 HTTP 状态码全覆盖
  }
}
```

## 与枚举配合

### 数字枚举

```typescript
enum HttpMethod {
  GET = 'GET',
  POST = 'POST',
  PUT = 'PUT',
  DELETE = 'DELETE',
  PATCH = 'PATCH',
}

function getHttpMethodLabel(method: HttpMethod): string {
  switch (method) {
    case HttpMethod.GET:
      return '查询';
    case HttpMethod.POST:
      return '创建';
    case HttpMethod.PUT:
      return '更新（全量）';
    case HttpMethod.DELETE:
      return '删除';
    case HttpMethod.PATCH:
      return '更新（部分）';
    default:
      return exhaustive(method);
  }
}
```

### const 对象枚举（推荐方式）

使用 `as const` 断言的对象替代传统 enum，可以获得更精确的字面量类型推导：

```typescript
const UserRole = {
  ADMIN: 'admin',
  EDITOR: 'editor',
  VIEWER: 'viewer',
  GUEST: 'guest',
} as const;

// 推导出联合类型
type UserRole = typeof UserRole[keyof typeof UserRole];
// 等价于: 'admin' | 'editor' | 'viewer' | 'guest'

function getUserPermissions(role: UserRole): Permission[] {
  switch (role) {
    case 'admin':  return [Permission.ALL];
    case 'editor': return [Permission.READ, Permission.WRITE, Permission.DELETE];
    case 'viewer': return [Permission.READ];
    case 'guest':  return [Permission.READ_PUBLIC];
    default:
      return exhaustive(role);
  }
}
```

### 字符串枚举与数字枚举的差异

字符串枚举和数字枚举在穷尽性检查中行为一致，但需要注意数字枚举的反向映射问题：

```typescript
enum NumericStatus {
  Idle = 0,
  Active = 1,
  Done = 2,
}

// 数字枚举会产生反向映射，switch 时需确保覆盖所有正向值
// 字符串枚举则无此问题
enum StringStatus {
  Idle = 'idle',
  Active = 'active',
  Done = 'done',
}
```

对于新项目，推荐优先使用 `const as const` 对象或字符串枚举，避免数字枚举的反向映射带来的复杂性。

## 进阶 exhaustive 变体

### assertNever：保留输入值的类型信息

基础版 `exhaustive` 参数和返回值都是 `never`，在某些场景下无法获取到具体遗漏的类型信息。`assertNever` 变体通过泛型参数保留输入类型：

```typescript
function assertNever<T>(value: never & T): never {
  throw new Error(`[Exhaustive check failed] Unexpected value: ${JSON.stringify(value)}`);
}

// 使用方式相同，但错误消息能序列化出实际值
default: return assertNever(action);
```

`never & T` 的交叉类型在 T 不为 never 时等价于 T，因此保留了输入的具体类型用于调试输出。

### exhaustiveCheck：带自定义上下文信息

在实际项目中，多个地方使用 exhaustive 时，仅凭错误消息难以定位问题来源：

```typescript
function exhaustiveCheck(
  value: never,
  context?: { file?: string; function?: string; message?: string },
): never {
  const location = context?.function || context?.file || 'unknown location';
  const hint = context?.message || '';
  throw new Error(
    `[Exhaustive check failed at ${location}] ${hint}` +
    `\nReceived value: ${JSON.stringify(value)}`
  );
}

// 带上下文使用
default:
  return exhaustiveCheck(action, {
    function: 'todoReducer',
    message: 'Unhandled TodoAction type in reducer',
  });
```

### typedExhaustive：表达式上下文兼容

有时 exhaustive 需要在期望特定返回值的表达式中使用：

```typescript
function typedExhaustive<T>(value: never): T {
  throw new Error(`[Exhaustive check failed] Unexpected value: ${value}`);
}

function getColor(status: Status): Color {
  switch (status) {
    case 'active':  return Color.Green;
    case 'inactive': return Color.Gray;
    case 'archived': return Color.Blue;
    default:
      // 直接返回 Color 类型，无需额外类型断言
      return typedExhaustive<Color>(status);
  }
}
```

### 案例 2：错误码到用户友好消息的映射

```typescript
enum AppErrorCode {
  NETWORK_ERROR = 'NETWORK_ERROR',
  AUTH_EXPIRED = 'AUTH_EXPIRED',
  PERMISSION_DENIED = 'PERMISSION_DENIED',
  RESOURCE_NOT_FOUND = 'RESOURCE_NOT_FOUND',
  RATE_LIMITED = 'RATE_LIMITED',
  VALIDATION_FAILED = 'VALIDATION_FAILED',
  SERVER_ERROR = 'SERVER_ERROR',
}

const ERROR_MESSAGES: Record<AppErrorCode, string> = {
  [AppErrorCode.NETWORK_ERROR]:     '网络连接异常，请检查网络设置',
  [AppErrorCode.AUTH_EXPIRED]:      '登录已过期，请重新登录',
  [AppErrorCode.PERMISSION_DENIED]: '您没有权限执行此操作',
  [AppErrorCode.RESOURCE_NOT_FOUND]: '请求的资源不存在',
  [AppErrorCode.RATE_LIMITED]:      '操作过于频繁，请稍后再试',
  [AppErrorCode.VALIDATION_FAILED]: '输入数据验证失败',
  [AppErrorCode.SERVER_ERROR]:      '服务器内部错误',
};

function getErrorMessage(code: AppErrorCode): string {
  const message = ERROR_MESSAGES[code];
  if (!message) {
    // Record 映射不保证穷尽性，用 exhaustive 作为兜底检查
    exhaustive(code);
    return '未知错误';
  }
  return message;
}
```

注意：`Record<K, V>` 本身**不会强制穷尽性**。即使 `ERROR_MESSAGES` 遗漏了某个 key，TypeScript 也不会报错。上面的 `exhaustive` 调用提供了额外的安全保障。若要更强的约束，可以使用满足（Satisfies）操作符：

```typescript
const ERROR_MESSAGES = {
  [AppErrorCode.NETWORK_ERROR]:     '网络连接异常...',
  // ... 所有 key 必须存在
} satisfies Record<AppErrorCode, string>;
```

`satisfies` 会校验字面量类型是否匹配 `Record<AppErrorCode, string>`，遗漏任何 key 都会报错。

### 案例 3：AST 访问器模式

在编译器、代码生成工具或 lint 规则开发中，AST 节点遍历需要覆盖所有节点类型：

```typescript
type AstNode =
  | { nodeType: 'Program'; body: Statement[] }
  | { nodeType: 'FunctionDeclaration'; name: string; params: Param[]; body: BlockStatement }
  | { nodeType: 'VariableDeclaration'; declarations: VariableDeclarator[]; kind: 'let' | 'const' | 'var' }
  | { nodeType: 'ExpressionStatement'; expression: Expression }
  | { nodeType: 'ReturnStatement'; argument?: Expression }
  | { nodeType: 'IfStatement'; test: Expression; consequent: Statement; alternate?: Statement }
  | { nodeType: 'BinaryExpression'; operator: BinaryOp; left: Expression; right: Expression }
  | { nodeType: 'Identifier'; name: string }
  | { nodeType: 'Literal'; value: string | number | boolean | null }
  | { nodeType: 'CallExpression'; callee: Expression; arguments: Expression[] };

interface Visitor {
  visitProgram(node: Extract<AstNode, { nodeType: 'Program' }>): void;
  visitFunctionDeclaration(node: Extract<AstNode, { nodeType: 'FunctionDeclaration' }>): void;
  visitVariableDeclaration(node: Extract<AstNode, { nodeType: 'VariableDeclaration' }>): void;
  visitExpressionStatement(node: Extract<AstNode, { nodeType: 'ExpressionStatement' }>): void;
  visitReturnStatement(node: Extract<AstNode, { nodeType: 'ReturnStatement' }>): void;
  visitIfStatement(node: Extract<AstNode, { nodeType: 'IfStatement' }>): void;
  visitBinaryExpression(node: Extract<AstNode, { nodeType: 'BinaryExpression' }>): void;
  visitIdentifier(node: Extract<AstNode, { nodeType: 'Identifier' }>): void;
  visitLiteral(node: Extract<AstNode, { nodeType: 'Literal' }>): void;
  visitCallExpression(node: Extract<AstNode, { nodeType: 'CallExpression' }>): void;
}

function walk(node: AstNode, visitor: Visitor): void {
  switch (node.nodeType) {
    case 'Program':
      visitor.visitProgram(node);
      node.body.forEach(child => walk(child, visitor));
      break;
    case 'FunctionDeclaration':
      visitor.visitFunctionDeclaration(node);
      node.params.forEach(p => walkExpression(p.init, visitor));
      walk(node.body, visitor);
      break;
    case 'VariableDeclaration':
      visitor.visitVariableDeclaration(node);
      node.declarations.forEach(d => {
        if (d.init) walkExpression(d.init, visitor);
      });
      break;
    case 'ExpressionStatement':
      visitor.visitExpressionStatement(node);
      walkExpression(node.expression, visitor);
      break;
    case 'ReturnStatement':
      visitor.visitReturnStatement(node);
      if (node.argument) walkExpression(node.argument, visitor);
      break;
    case 'IfStatement':
      visitor.visitIfStatement(node);
      walkExpression(node.test, visitor);
      walk(node.consequent, visitor);
      if (node.alternate) walk(node.alternate, visitor);
      break;
    case 'BinaryExpression':
      visitor.visitBinaryExpression(node);
      walkExpression(node.left, visitor);
      walkExpression(node.right, visitor);
      break;
    case 'Identifier':
      visitor.visitIdentifier(node);
      break;
    case 'Literal':
      visitor.visitLiteral(node);
      break;
    case 'CallExpression':
      visitor.visitCallExpression(node);
      walkExpression(node.callee, visitor);
      node.arguments.forEach(arg => walkExpression(arg, visitor));
      break;
    default:
      // 新增 AST 节点类型后，walk 函数必须更新
      exhaustive(node);
  }
}
```

## 常见陷阱与注意事项

### any 类型绕过检查

`any` 是穷尽性检查的头号敌人：

```typescript
function brokenHandler(input: any): void {
  switch (input.type) {
    case 'a': handleA(input); break;
    case 'b': handleB(input); break;
    default:
      // input 的类型为 any，any 可以赋值给 never，不会报错！
      exhaustive(input); // 静默通过，检查失效
  }
}
```

**解决方案**：确保参与穷尽性检查的变量具有具体的联合类型标注，杜绝 `any` 泄入。

### 类型断言破坏检查

```typescript
function alsoBroken(input: SomeUnion): void {
  // ...
  default:
    // 强制断言绕过了类型检查
    exhaustive(input as never); // 永远不会报错，即使有遗漏
}
```

`as never` 将任何类型强制转为 never，使 exhaustive 形同虚设。这是**绝对禁止**的用法。

### 返回值类型声明不当

```typescript
function implicitReturn(value: SomeUnion) {
  // 函数没有声明返回值类型，隐式返回 undefined
  switch (value) {
    case 'a': return 'A';
    case 'b': return 'B';
    // 没有 default 分支，函数隐式返回 undefined
    // 但因为返回类型推断为 string | undefined，不触发错误
  }
}
```

建议：始终为涉及穷尽性检查的函数显式声明返回值类型，并在 default 中调用 exhaustive。

### 多层嵌套条件的穷尽性保证

多层嵌套的 if-else 或 switch 中，每一层的穷尽性需要独立保证：

```typescript
function complexHandler(data: ComplexType): void {
  if (data.category === 'A') {
    // 第一层：category 为 'A'
    if (data.subType === 'a1') {
      // 处理 a1
    } else if (data.subType === 'a2') {
      // 处理 a2
    } else {
      // 内层穷尽性：subType 的所有可能已覆盖
      exhaustive(data.subType);
    }
  } else if (data.category === 'B') {
    // 第二层独立保证穷尽性
    // ...
  } else {
    // 外层穷尽性：category 的所有可能已覆盖
    exhaustive(data.category);
  }
}
```

### 回调函数中的行为差异

将 exhaustive 放入回调函数时，类型收窄可能不如预期：

```typescript
function withCallback(union: A | B | C): void {
  const handler = () => {
    // 回调闭包内无法获得外部的控制流收窄信息
    // union 在这里的类型仍然是 A | B | C，而非 never
    exhaustive(union); // 可能不会按预期工作
  };
  handler();
}
```

回调函数形成独立的类型分析作用域，外部控制流收窄结果不会自动传播进去。解决方法是将变量作为参数传入：

```typescript
function withCallback(union: A | B | C): void {
  const handler = (remaining: never) => {
    exhaustive(remaining); // 正确工作
  };
  // 在外层完成收窄后再调用
  handler(union as never); // 仅在外部确信穷尽时使用
}
```

更好的做法是在回调之前就完成完整的 switch/if 处理，避免将穷尽性检查延迟到回调内部。

## 与其他语言/工具的对比

穷尽性检查并非 TypeScript 独有的概念。许多语言在语言层面原生支持这一能力：

| 语言/工具 | 机制 | 强制级别 | 特点 |
|-----------|------|----------|------|
| **Rust** | `match` 表达式 | **编译器强制**（未覆盖则编译失败） | 最严格的穷尽性保证；必须显式处理所有变体 |
| **Scala** / **Haskell** | Pattern Match | 可配置 warning/error | 模式匹配表达式天然支持穷尽性检测 |
| **Swift** | `switch` 语句 | **编译器强制** | switch 必须 exhaustive，否则编译错误 |
| **Kotlin** | `when` 表达式 | 编译器警告（可提升为错误） | `when` 用作表达式时要求 exhaustive |
| **OCaml** | Pattern Match | 编译器警告（`-match-exhaustive`） | 警告模式，可通过 CI 配置升级 |
| **TypeScript** | `never` + `exhaustive` 函数 | **手动配置** | 库级方案，需要开发者主动编写和调用 exhaustive |
| **Flow** | `$Exact<>` 类型 | 内置死代码消除 | Flow 的类型系统内置了类似的能力 |

TypeScript 的方案属于**约定优于强制**：语言本身不在语法层面强制穷尽性，而是提供 `never` 类型的底层能力，由开发者构建上层工具（exhaustive 函数）。这带来了灵活性——可以选择性地启用——但也意味着团队需要有统一的编码规范来确保一致性。

## ESLint / 工具链集成

### @typescript-eslint/switch-exhaustiveness-check

`@typescript-eslint` 提供了一条专用规则，可以在 switch 语句层面自动检测穷尽性：

```javascript
// .eslintrc.js
module.exports = {
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended',
  ],
  rules: {
    '@typescript-eslint/switch-exhaustiveness-check': 'error',
  },
};
```

该规则的工作方式：

- 检查 switch 语句是否覆盖了判别联合的所有成员
- 对于非判别联合，默认不做强制要求
- 支持 `requireDefaultForNonUnion` 选项：对非联合类型的 switch 也要求 default 分支

```javascript
{
  '@typescript-eslint/switch-exhaustiveness-check': ['error', {
    requireDefaultForNonUnion: true, // 非 union 的 switch 也必须有 default
  }]
}
```

### ESLint 规则 vs exhaustive 函数

两者并非互斥关系，而是互补：

| 维度 | ESLint 规则 | exhaustive 函数 |
|------|-------------|-----------------|
| 适用范围 | 仅 switch 语句 | switch + if-else + 其他条件结构 |
| 检测时机 | Lint 阶段 | 类型检查阶段（tsc --noEmit） |
| 运行时保护 | 无 | 有（抛出运行时异常） |
| 错误信息定制 | 固定格式 | 可自由定制 |
| if-else 兼容 | 不支持 | 支持 |

**推荐策略**：同时启用两者。ESLint 规则在编辑器中即时反馈，exhaustive 函数在类型检查阶段做二次保障，并为生产环境提供运行时的最后防线。

 * 穷尽性检查工具函数

  throw new Error(

}

## 最佳实践总结

### 什么时候应该用穷尽性检查

以下场景强烈建议引入穷尽性检查：

1. **联合类型 / 可辨识联合的 switch 或 if-else 分支分发**——尤其是那些会被频繁扩展的类型定义
2. **枚举值到其他值的映射**——如错误码到消息、状态码到颜色等转换逻辑
3. **reducer 函数**——Redux/Vuex/Pinia 等状态管理中的 action 处理
4. **编译器 / AST 工具**——节点访问器和遍历器
5. **协议 / 格式解析器**——需要处理所有可能的 token 或 tag 类型
6. **公共 API 的响应处理**——需要覆盖所有可能的响应变体

以下场景通常**不需要**穷尽性检查：

1. 只有两三个固定不变的可能性的简单分支
2. 分支逻辑本身就是临时的、一次性的脚本代码
3. 使用 `Record<K, V>` + `satisfies` 已经保证了键的完整性

### 团队协作规范建议

1. **统一 exhaustive 函数入口**：项目中只维护一份 exhaustive 实现，放在共享工具包中，禁止各模块自行复制
2. **代码审查 Checklist**：新增联合类型成员时，审查者应确认所有相关 switch/if-else 已补充对应分支
3. **CI 配置**：`tsc --noEmit` 作为 CI 必检步骤，确保穷尽性检查不会被绕过
4. **commit message 规范**：修改联合类型定义时，建议在 commit message 中注明受影响的处理函数

### 大型项目的组织方式

在大型项目中，穷尽性检查可以按照领域边界组织：

```
src/
├── utils/
│   └── exhaustive.ts          # 统一的 exhaustive 实现
├── features/
│   ├── auth/
│   │   └── types.ts           # auth 领域的联合类型 + 内联 exhaustive
│   ├── order/
│   │   └── types.ts           # order 领域的联合类型
│   └── payment/
│       └── types.ts           # payment 领域的联合类型
└── shared/
    └── error-codes.ts         # 全局错误码枚举 + 消息映射
```

每个领域的类型定义和对应的处理函数放在一起，便于维护和审计。全局共用的 exhaustive 函数从统一路径导入，保持一致的行为。

## 总结

穷尽性检查是 TypeScript 类型系统中一项强大而实用的技术。它利用 `never` 类型的底层特性和控制流分析能力，让编译器帮助开发者捕获"遗漏分支"类的缺陷。

核心要点回顾：

- **`never` 是穷尽性检查的基础**：它是空类型，只有当所有分支都处理后，剩余变量才会被收窄为 never
- **exhaustive 函数是标准写法**：接受 never 参数并抛出异常，在 default/final else 分支中调用
- **可辨识联合是最常用场景**：action reducer、状态机、API 响应处理都是典型应用
- **ESLint 规则提供额外保障**：`@typescript-eslint/switch-exhaustiveness-check` 在 lint 层面增加一道防线
- **`any` 和 `as never` 是主要风险点**：它们会无声地破坏穷尽性检查的有效性

穷尽性检查的价值不仅在于发现 bug，更在于建立一种工程文化：**类型变更时，编译器主动告知你所有需要同步更新的位置**。在团队协作和长期维护的大型项目中，这种能力带来的收益是巨大的。
