## 概述 —— TypeScript 工具类型生态

### 为什么需要工具类型

在 TypeScript 的日常开发中，存在大量**基于已有类型生成新类型**的需求：将某个接口的所有属性变为可选、从联合类型中剔除某些成员、提取函数的返回值类型等等。这些操作遵循着固定的模式，如果每次都手写实现，代码冗余且容易出错。

TypeScript 将这些常见的类型变换模式封装为**工具类型（Utility Types）**，作为全局可用的类型工具提供。它们本质上是利用条件类型、映射类型、`keyof`、`infer` 等类型运算能力构建的泛型别名，开发者只需传入源类型即可获得变换后的结果。

使用方式统一为以下形式：

```typescript
type ResultType = UtilityName<SourceType, /* 可选的其他参数 */>;
```

例如，将 `User` 类型的所有属性变为可选：

```typescript
type PartialUser = Partial<User>;
```

### 内置工具类型一览表

TypeScript 内置的工具类型按功能可分为以下几类：

| 分类 | 工具类型 | 功能 |
|------|----------|------|
| 属性修饰 | `Partial<T>` | 所有属性变为 optional |
| 属性修饰 | `Required<T>` | 所有 optional 属性变为 required |
| 属性修饰 | `Readonly<T>` | 所有属性变为 readonly |
| 属性选取/排除 | `Pick<T, K>` | 选取指定键组成新类型 |
| 属性选取/排除 | `Omit<T, K>` | 排除指定键后得到新类型 |
| 联合类型操作 | `Exclude<T, U>` | 从 T 中排除可分配给 U 的成员 |
| 联合类型操作 | `Extract<T, U>` | 从 T 中提取可分配给 U 的成员 |
| 联合类型操作 | `NonNullable<T>` | 排除 null 和 undefined |
| 函数类型推断 | `ReturnType<T>` | 提取函数返回值类型 |
| 函数类型推断 | `Parameters<T>` | 提取函数参数元组类型 |
| 映射构造 | `Record<K, V>` | 构造键值映射类型 |

下面逐一深入分析每个工具类型的定义、原理和使用场景。

## Partial\<T\>

### 定义与效果

`Partial<T>` 将类型参数T的所有属性变为**可选属性（optional）**，即在每个属性后面加上 `?` 标记。

```typescript
interface User {
  id: number;
  name: string;
  email: string;
  age: number;
}

// 所有属性都变成了可选的
type PartialUser = Partial<User>;
// 等价于：
// interface PartialUser {
//   id?: number;
//   name?: string;
//   email?: string;
//   age?: number;
// }
```

### 底层实现源码解析

`Partial` 的实现非常简洁，核心是一个**映射类型（Mapped Type）**：

```typescript
/**
 * Make all properties in T optional
 */
type Partial<T> = {
  [P in keyof T]?: T[P];
};
```

逐行解析：

- `[P in keyof T]`：遍历 T 的所有属性名，P 依次绑定每个属性名的字面量类型。
- `?`：在属性名后添加可选标记，使该属性可以省略。
- `T[P]`：通过索引访问语法获取属性 P 在原始类型中的类型，保持不变。

这个实现的关键在于映射类型的 `?` 修饰符——它对每个属性执行"可选化"操作，而不改变属性的类型本身。

### 典型场景

#### 1. PATCH 请求的部分更新

RESTful API 的 PATCH 方法通常只接收需要更新的字段，而非完整对象。`Partial` 天然适合描述这种场景：

```typescript
interface UserProfile {
  displayName: string;
  avatarUrl: string;
  bio: string;
  location: string;
}

async function updateProfile(
  userId: string,
  updates: Partial<UserProfile>
): Promise<UserProfile> {
  // 只发送有值的字段到后端
  const response = await fetch(`/api/users/${userId}`, {
    method: 'PATCH',
    body: JSON.stringify(updates),
  });
  return response.json();
}

// 调用方可以只传部分字段
await updateProfile('u123', { displayName: '新名称' });
await updateProfile('u123', { bio: '新的个人简介', location: '北京' });
```

没有 `Partial` 的话，调用方必须构造一个完整的 `UserProfile` 对象，即使大部分字段并未改变。

#### 2. 表单草稿状态

表单编辑过程中，用户可能尚未填写所有字段，此时对象状态天然是"部分填充"的：

```typescript
interface ArticleForm {
  title: string;
  content: string;
  tags: string[];
  categoryId: number;
}

// 草稿状态下所有字段都是可选的
const draftRef = ref<Partial<ArticleForm>>({});

function handleFieldChange(field: keyof ArticleForm, value: unknown) {
  // 可以安全地逐个字段赋值
  draftRef.value[field] = value as any;
}
```

#### 3. 渐进式对象构建

当对象的初始化需要多个步骤完成时，可以用 `Partial` 作为中间态类型：

```typescript
function buildConfig(): AppConfig {
  const partial: Partial<AppConfig> = {};

  partial.theme = loadTheme();
  partial.language = detectLanguage();
  partial.apiEndpoint = getApiUrl();

  // 类型收窄为完整类型后返回
  return partial as AppConfig;
}
```

### 与 Required 的对应关系

`Partial` 和 `Required` 是一对互逆操作：`Partial` 添加 `?`，`Required` 移除 `?`。但需要注意，这种互逆性只在原始类型的属性本身具有明确的 optional/required 状态时才成立——对于原本就是 optional 的属性，`Required` 会将其变为 required；对于原本就是 required 的属性，`Partial` 会将其变为 optional。

### 局限性：浅层变换

`Partial` 只处理一层属性，不会递归作用于嵌套对象：

```typescript
interface Company {
  name: string;
  address: {
    city: string;
    street: string;  // 这个不会变成可选
  };
}

type PartialCompany = Partial<Company>;
// address 本身变成可选了，但 address.city 和 address.street 仍然是 required
// { name?: string; address?: { city: string; street: string }; }
```

如果需要深层的 Partial 效果，需要自行编写递归版本（详见后文"常见陷阱"章节）。

### 编译器内部处理原理

TypeScript 编译器在处理 `Partial<T>` 时，内部经历以下阶段：

1. **类型解析**：识别 `Partial` 为内置工具类型别名，解析类型参数 T。
2. **keyof 提取**：对 T 执行 `keyof` 操作，获取所有属性名的联合类型。
3. **映射展开**：遍历属性名联合类型，为每个属性生成带有 `?` 修饰符的新属性签名。
4. **类型缓存**：结果类型被缓存在编译器的类型表中，同一输入不会重复计算。

关键点在于映射类型的展开发生在**类型检查阶段**而非运行时——这意味着 `Partial` 零运行时开销，纯编译时变换。

### 更多实战示例

#### 数据库查询条件的动态构建

ORM 查询通常支持动态条件组合，`Partial` 天然适配这种模式：

```typescript
interface QueryCondition {
  field: string;
  operator: '=' | '>' | '<' | 'like' | 'in';
  value: unknown;
  logic?: 'and' | 'or';
}

function buildWhere(conditions: Partial<QueryCondition>[]): string {
  return conditions
    .filter(c => c.field != null && c.value != null)
    .map(c => `${c.field} ${c.operator ?? '='} ${formatValue(c.value)}`)
    .join(' ');
}

// 调用方可以只传必要字段
buildWhere([
  { field: 'age', operator: '>', value: 18 },
  { field: 'status', operator: '=', value: 'active', logic: 'and' },
]);
```

#### 组件 Props 的默认值合并

React/Vue 组件中常用 `Partial` 处理默认 props 的合并逻辑：

```typescript
interface ModalProps {
  title: string;
  width: number;
  closable: boolean;
  maskClosable: boolean;
  footer: ReactNode;
}

const DEFAULT_PROPS: Partial<ModalProps> = {
  width: 520,
  closable: true,
  maskClosable: true,
};

function useModal(userProps: ModalProps): Required<ModalProps> {
  // 将用户传入的 props 与默认值合并
  const merged = { ...DEFAULT_PROPS, ...userProps } as Required<ModalProps>;
  return merged;
}
```

#### 状态机转换的类型安全定义

有限状态机的部分状态转换可以用 `Partial` 表达：

```typescript
type StateTransition<S> = Partial<Record<S, S[]>>;

type TrafficLightState = 'red' | 'yellow' | 'green';

// 定义合法的状态转换（未定义的键表示该状态下不允许任何转换）
const transitions: StateTransition<TrafficLightState> = {
  red: ['green'],
  yellow: ['red'],
  green: ['yellow'],
};
```

### 常见错误与纠正

**错误 1：误以为 Partial 会递归处理**

```typescript
// 错误假设：DeepPartial 可以直接用 Partial 实现
interface Config {
  db: {
    host: string;
    port: number;
  };
}

const cfg: Partial<Config> = {};
cfg.db.host = 'localhost';  // 运行时可能报错！db 可能是 undefined

// 正确做法：使用 DeepPartial 或手动检查
if (cfg.db) {
  cfg.db.host = 'localhost';
}
```

**错误 2：忽略 Partial 后的 undefined 类型扩散**

```typescript
interface User {
  id: number;
  name: string;
}

function process(u: Partial<User>) {
  console.log(u.name.toUpperCase());  // 编译错误！u.name 可能是 undefined
  // 正确写法：
  console.log(u.name?.toUpperCase());
}
```

**错误 3：在需要完整对象的地方误用 Partial**

```typescript
interface ValidationRule {
  validator: (value: any) => boolean;
  message: string;
}

// 错误：Partial 使得所有字段都可选，失去了约束力
function addRule(rule: Partial<ValidationRule>) {
  // rule.validator 和 rule.message 都可能不存在
}

// 正确：如果确实需要灵活性，应使用更精确的联合类型
function addRule(rule:
  | { validator: (value: any) => boolean; message?: string }
  | { validator?: never; message: string }
) {}
```

## Required\<T\>

### 定义与效果

`Required<T>` 与 `Partial<T>` 相反：它将类型参数 T 中所有带 `?` 标记的可选属性移除可选标记，使其变为**必填属性（required）**。

```typescript
interface Config {
  host?: string;
  port?: number;
  ssl?: boolean;
  timeout?: number;
}

type StrictConfig = Required<Config>;
// 等价于：
// interface StrictConfig {
//   host: string;
//   port: number;
//   ssl: boolean;
//   timeout: number;
// }
```

### 底层实现源码解析

```typescript
/**
 * Make all properties in T required
 */
type Required<T> = {
  [P in keyof T]-?: T[P];
};
```

关键点在于 `-?` 语法：这是映射类型中的**减号修饰符**，表示移除 `?` 可选标记。对应的还有 `-readonly` 用于移除 readonly 修饰符。

对比 `Partial` 的实现：

| 工具类型 | 修饰符 | 含义 |
|----------|--------|------|
| `Partial` | `?` | 添加可选标记 |
| `Required` | `-?` | 移除可选标记 |

### 典型场景

#### 将宽松配置收严为完整定义

开发中常定义宽松的配置接口用于逐步组装，最终确认时再转为严格版本：

```typescript
// 宽松配置——允许缺省
interface LooseConfig {
  apiUrl?: string;
  retryCount?: number;
  timeout?: number;
  enableCache?: boolean;
}

function normalizeConfig(loose: LooseConfig): Required<LooseConfig> {
  return {
    apiUrl: loose.apiUrl ?? 'https://api.example.com',
    retryCount: loose.retryCount ?? 3,
    timeout: loose.timeout ?? 5000,
    enableCache: loose.enableCache ?? true,
  };
}

// 返回值保证每个字段都有值，下游使用无需再做判空
const config = normalizeConfig({ timeout: 10000 });
config.apiUrl;       // 类型为 string（非 undefined）
config.retryCount;   // 类型为 number（非 undefined）
```

#### 确保函数参数完整性

某些函数要求传入的对象必须包含所有字段，可以使用 `Required` 强制约束：

```typescript
function submitOrder(order: Required<OrderDraft>): OrderId {
  // 这里可以放心使用 order 的所有属性，无需判空
  return createOrder({
    items: order.items,
    shippingAddress: order.shippingAddress,
    paymentMethod: order.paymentMethod,
    couponCode: order.couponCode,
  });
}
```

### 与 Partial 的互逆关系

对于任意类型 T：

- `Required<Partial<T>>` ≈ T（恢复为所有属性 required，前提是 T 的属性原本都是 required）
- `Partial<Required<T>>` ≈ T（恢复为所有属性 optional，前提是 T 的属性原本都是 optional）

但这种互逆并非完美对称。若 T 中混合了 optional 和 required 属性，两次变换后结果与原 T 不同：

```typescript
interface Mixed {
  a: string;      // 原本 required
  b?: number;     // 原本 optional
}

type Round1 = Required<Partial<Mixed>>;
// { a: string; b: number } — b 变成了 required，与原 Mixed 不同
```

### `-?` 修饰符的编译器实现细节

映射类型中的 `+?` 和 `-?` 语法在 TypeScript 编译器内部被处理为**可选性标志位**的设置和清除。编译器为每个属性签名维护一个可选性标记（optionalFlag），`+?` 将该位置为 true，`-?` 将其置为 false。默认情况下，源类型的 optionalFlag 会被保留，除非显式使用 `+?` 或 `-?` 覆盖。

这一机制也解释了为什么 `Readonly<T>` 不需要类似 `-readonly` 的操作来移除 readonly——因为 `Readonly` 是添加修饰符而非移除。

### 更多实战示例

#### 表单提交前的完整性校验

```typescript
interface LoginForm {
  username: string;
  password: string;
  captcha: string;
  rememberMe: boolean;
}

// 校验函数：返回完整的必填对象或错误信息
function validateForm(
  data: Partial<LoginForm>
): { success: true; data: Required<Pick<LoginForm, 'username' | 'password'>> }
| { success: true; data: Required<LoginForm> }
| { success: false; errors: Record<keyof LoginForm, string> } {
  const errors: Record<string, string> = {};

  if (!data.username) errors.username = '用户名不能为空';
  if (!data.password) errors.password = '密码不能为空';

  if (Object.keys(errors).length > 0) {
    return { success: false, errors: errors as any };
  }

  return {
    success: true,
    data: {
      username: data.username!,
      password: data.password!,
      captcha: data.captcha ?? '',
      rememberMe: data.rememberMe ?? false,
    },
  };
}
```

#### 环境变量的类型安全加载

```typescript
interface EnvConfig {
  API_BASE_URL: string;
  DATABASE_URL: string;
  REDIS_HOST?: string;
  REDIS_PORT?: number;
  LOG_LEVEL: 'debug' | 'info' | 'warn' | 'error';
  NODE_ENV: 'development' | 'production' | 'test';
}

function loadEnv(): Required<Omit<EnvConfig, 'REDIS_HOST' | 'REDIS_PORT'>> &
  Pick<EnvConfig, 'REDIS_HOST' | 'REDIS_PORT'> {
  const raw = process.env as Partial<EnvConfig>;

  // 必填字段缺失时抛出明确错误
  if (!raw.API_BASE_URL) throw new Error('Missing API_BASE_URL');
  if (!raw.DATABASE_URL) throw new Error('Missing DATABASE_URL');
  if (!raw.LOG_LEVEL) throw new Error('Missing LOG_LEVEL');
  if (!raw.NODE_ENV) throw new Error('Missing NODE_ENV');

  return {
    API_BASE_URL: raw.API_BASE_URL,
    DATABASE_URL: raw.DATABASE_URL,
    LOG_LEVEL: raw.LOG_LEVEL,
    NODE_ENV: raw.NODE_ENV,
    REDIS_HOST: raw.REDIS_HOST ?? 'localhost',
    REDIS_PORT: parseInt(raw.REDIS_PORT ?? '6379', 10),
  };
}
```

#### 类型守卫辅助：从 Partial 到 Required 的安全转换

```typescript
function hasAllRequiredKeys<T extends object>(
  obj: Partial<T>,
  keys: (keyof T)[]
): obj is Required<Pick<T, typeof keys[number]>> {
  return keys.every(key => key in obj && obj[key] !== undefined && obj[key] !== null);
}

interface OrderItem {
  productId: string;
  quantity: number;
  unitPrice: number;
  discount?: number;
}

const item: Partial<OrderItem> = { productId: 'p1', quantity: 2 };

if (hasAllRequiredKeys(item, ['productId', 'quantity', 'unitPrice'])) {
  // item 在此分支中被收窄为 Required<Pick<OrderItem, 'productId' | 'quantity' | 'unitPrice'>>
  const total = item.quantity * item.unitPrice;
}
```

### 实际项目中的使用建议

1. **配置对象标准化**：在模块入口处用 `Required` 将外部输入的宽松配置转换为内部使用的严格配置，避免下游代码到处做判空。
2. **表单校验链**：`Partial` 收集输入 → 校验逻辑填充默认值 → `Required` 输出完整结果，形成清晰的类型流水线。
3. **慎用于接口定义**：如果某个字段本身就是可选的语义（如 `nickname`），不要用 `Required` 强制它变成必填——这会破坏领域模型的准确性。
4. **配合 Pick 使用**：`Required<Pick<T, K>>` 可以只对特定子集字段做必填要求，比全局 `Required` 更精确。

## Readonly\<T\>

### 定义与效果

`Readonly<T>` 将类型参数 T 的所有属性加上 **readonly** 修饰符，表示这些属性在赋值后不可被修改。

```typescript
interface Point {
  x: number;
  y: number;
}

type ReadonlyPoint = Readonly<Point>;
// 等价于：
// interface ReadonlyPoint {
//   readonly x: number;
//   readonly y: number;
// }

const p: ReadonlyPoint = { x: 1, y: 2 };
p.x = 10;  // 编译错误：无法为“x”赋值，因为它是只读属性
```

### 底层实现源码解析

```typescript
/**
 * Make all properties in T readonly
 */
type Readonly<T> = {
  readonly [P in keyof T]: T[P];
};
```

在映射类型的属性名前加上 `readonly` 关键字即可。这与 `as const` 断言的效果不同：`as const` 让值本身变为字面量类型且所有层级都是 readonly，而 `Readonly<T>` 仅做**浅层** readonly 处理。

### 典型场景

#### 不可变状态管理

在 Redux 或类似的状态管理模式中，state 应当是不可变的。`Readonly` 可以在类型层面强制这一点：

```typescript
interface AppState {
  user: UserInfo;
  theme: 'light' | 'dark';
  notifications: Notification[];
}

// store 中的 state 不允许直接修改
let state: Readonly<AppState>;

// 正确做法：通过 reducer 产生新 state
state = reducer(state, action);

// 错误尝试：直接修改会被编译器拦截
state.user.name = 'new';  // 编译错误
```

#### 函数参数保护

当函数不应修改传入的对象时，可以用 `Readonly` 参数类型来防止意外修改：

```typescript
function logUserInfo(user: Readonly<User>) {
  console.log(user.name, user.email);
  user.name = 'hacked';  // 编译错误：防止函数内部修改外部数据
}
```

#### const 对象的浅层版本

`const` 声明仅保证变量引用不可重新赋值，不保证对象内部属性不可变。`Readonly` 补足了这一层保护：

```typescript
const config = { host: 'localhost', port: 3000 } as const;
// as const 使所有层级变为 readonly + 字面量类型

// 如果只需要浅层 readonly，且保留宽泛类型
const config2: Readonly<{ host: string; port: number }> = {
  host: 'localhost',
  port: 3000,
};
```

### 注意：只做浅层 readonly

与 `Partial` 类似，`Readonly` 也只处理顶层属性：

```typescript
interface Team {
  name: string;
  members: Member[];
}

type ReadonlyTeam = Readonly<Team>;
// name 是 readonly，但 members 数组内部的修改不受限制
const team: ReadonlyTeam = { name: 'Alpha', members: [] };
team.members.push({ name: 'Bob' });  // 编译通过，未受 Readonly 保护
```

### 编译器层面的 readonly 语义

TypeScript 的 `readonly` 修饰符在编译器内部被建模为**赋值限制**而非真正的不可变性。具体来说：

1. **类型系统层面**：标记为 `readonly` 的属性不允许通过赋值语句修改其值。
2. **运行时层面**：JavaScript 无 readonly 概念——`Readonly<T>` 的输出与 `T` 完全一致（编译后无差异）。
3. **方法调用不受限**：数组的 `push`、`pop`、`sort` 等变异方法不受 `readonly` 限制，因为它们不是直接的属性赋值。

这也是为什么需要 `ReadonlyArray<T>` 这种专门的不可变数组类型——它从方法层面禁用了所有变异操作。

### 更多实战示例

#### Redux store 的不可变快照

#### 事件系统的不可变事件对象

```typescript
  type: string;
  timestamp: number;
  bubbles: boolean;
}

  stopPropagation(): void;
};

  type: E['type']
```

### Readonly vs as const vs Object.freeze 对比

| 维度 | `Readonly<T>` | `as const` | `Object.freeze()` |
|------|--------------|-----------|-------------------|
| 作用阶段 | 类型检查时 | 类型推断时 | 运行行时 |
| 影响范围 | 浅层，仅顶层 | 深层，所有层级 | 深层，运行时冻结 |
| 类型变化 | 属性加 readonly | 字面量类型 + readonly | 类型不变 |
| 运行时保护 | 无 | 无 | 有（严格模式下） |
| 可逆性 | 可通过类型断言移除 | 需要显式拓宽类型 | 无法解冻 |

选择建议：
- 需要**纯类型约束**且只需浅层保护 → `Readonly<T>`
- 需要字面量类型推断 + 深层只读 → `as const`
- 需要运行时不可变性 → `Object.freeze()`
- 需要两者兼顾 → `Readonly<T>` + `Object.freeze()` 组合使用

## Pick\<T, K\>

### 定义与效果

`Pick<T, K>` 从类型 T 中**选取**由键字面量联合类型 K 指定的属性，组成一个新的对象类型。

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
  description: string;
  stock: number;
  createdAt: Date;
}

// 只选取需要的三个字段
type ProductSummary = Pick<Product, 'id' | 'name' | 'price'>;
// 等价于：
// interface ProductSummary {
//   id: number;
//   name: string;
//   price: number;
// }
```

### 底层实现源码解析

```typescript
/**
 * From T, pick a set of properties whose keys are in the union K
 */
type Pick<T, K extends keyof T> = {
  [P in K]: T[P];
};
```

关键细节：

- `K extends keyof T`：这是**泛型约束**，确保 K 只能是 T 的属性名的子集。如果传入了 T 中不存在的键，会在编译时报错。
- `[P in K]`：只遍历 K 中指定的属性名，而非 T 的全部属性名。
- `T[P]`：保持原属性类型不变。

约束的作用体现在以下报错行为：

```typescript
type BadPick = Pick<Product, 'id' | 'nonexistent'>;
// 编译错误：类型 ""nonexistent"" 不能赋值类型 "keyof Product"
```

### 典型场景

#### API 响应字段选取

前端列表页通常只需要后端返回数据的部分字段，可以用 `Pick` 定义精简类型：

```typescript

  email: string;
  phone: string;
  passwordHash: string;
  createdAt: Date;
  updatedAt: Date;
  lastLoginAt: Date;
  ipHistory: string[];
}

// 列表页只需展示这些字段

  | 'id'
  | 'username'
  | 'email'
  | 'createdAt'
>;

function renderUserList(users: UserListItem[]) {
  users.forEach(u => console.log(u.username));
  // u.passwordHash 在此作用域内不存在
}
```

#### 公开接口暴露子集

库或模块对外暴露类型时，通常隐藏内部字段，只暴露必要的子集：

```typescript
// 内部完整类型
interface InternalConnection {
  id: string;
  url: string;
  socket: WebSocket;
  reconnectTimer: number;
  messageQueue: Message[];
  _internalState: unknown;
}

// 对外暴露的安全子集

  | 'id'
  | 'url'
>;
```

### 与 Omit 的互补关系

`Pick` 和 `Omit` 是同一枚硬币的两面：一个按需"取"，另一个按需"舍"。具体选择取决于哪种方式表达更简洁——要保留的字段少就用 `Pick`，要排除的字段少就用 `Omit`。

### 泛型约束 `K extends keyof T` 的深层意义

`Pick` 中的 `K extends keyof T` 约束不仅是编译时的安全网，它还体现了**类型级编程中的子集关系**。从集合论角度看：

- `keyof T` 是属性名全集
- K 必须是全集的子集
- 映射类型的遍历范围由 K 决定，而非 T 本身

这一约束使得 `Pick` 在泛型上下文中特别强大——当 K 也是一个类型参数时（而非固定的字面量联合），编译器会自动推断 K 的合法范围：

```typescript
function pluck<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K>[K][] {
  return keys.map(key => obj[key]);
}

const user = { id: 1, name: 'Alice', email: 'alice@example.com' };
const values = pluck(user, ['name', 'email']);  // K 被推断为 'name' | 'email'
// 返回值类型：(string | string)[]
```

```typescript
// 如果需要将可选变为必填：
type PickedRequired = Required<Pick<Config, 'optional'>>;
```

## Omit\<T, K\>

### 定义与效果

`Omit<T, K>` 从类型 T 中**排除**由 K 指定的属性，保留剩余属性形成新类型。

```typescript
interface Article {
  id: number;
  title: string;
  content: string;
  authorId: number;
  viewCount: number;
  isDeleted: boolean;
  createdAt: Date;
}

// 排除内部/敏感字段
type PublicArticle = Omit<Article, 'authorId' | 'isDeleted'>;
// 等价于：
// interface PublicArticle {
//   id: number;
//   title: string;
//   content: string;
//   viewCount: number;
//   createdAt: Date;
// }
```

### 底层实现

`Omit` 并非原语级别的工具类型，而是由 `Pick` 和 `Exclude` 组合而成：

```typescript
/**
 * Construct a type with the properties of T except for those in type K.
 */
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

拆解其工作流程：

1. `keyof T` 获取 T 的所有属性名组成的联合类型。
2. `Exclude<keyof T, K>` 从中排除 K 指定的属性名。
3. `Pick<T, ...>` 用排除后的属性名集合从 T 中选取属性。

以 `Omit<Article, 'authorId' | 'isDeleted'>` 为例：

```
keyof Article = 'id' | 'title' | 'content' | 'authorId' | 'viewCount' | 'isDeleted' | 'createdAt'

Exclude<keyof Article, 'authorId' | 'isDeleted'>
= 'id' | 'title' | 'content' | 'viewCount' | 'createdAt'

Pick<Article, 'id' | 'title' | 'content' | 'viewCount' | 'createdAt'>
= { id: number; title: string; content: string; viewCount: number; createdAt: Date; }
```

### 典型场景

#### 排除敏感字段

从包含内部信息的类型中派生出安全的公开类型：

```typescript
type PublicUser = Omit<User,
  | 'password'
  | 'passwordHash'
  | 'securityQuestion'
  | 'securityAnswer'
  >;
```

#### 移除内部字段后导出类型

组件库常从 props 类型中排除仅供内部使用的属性：

```typescript
import { ButtonHTMLAttributes } from 'react';

// 排除原生 button 的 size 属性，使用自定义的
type CustomButtonProps = Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'size'> & {
  size: 'sm' | 'md' | 'lg';
  variant: 'primary' | 'secondary';
};
```

### Pick vs Omit 选择策略

| 场景 | 推荐 | 原因 |
|------|------|------|
| 需要保留的属性少 | `Pick` | 直接列出少数目标属性更直观 |
| 需要排除的属性少 | `Omit` | 直接列出少数排除项更简洁 |
| 原始类型的属性未来会增加 | `Omit` 更稳健 | 新增属性自动被保留；而 `Pick` 需要手动追加 |
| 需要明确"白名单"语义 | `Pick` | 表达"我只认这几个"的意图更清晰 |

实际项目中，`Omit` 的使用频率通常高于 `Pick`，因为它在面对类型演化时更加健壮。

### Omit 的组合威力：排除 + 变换

`Omit` 最强大的场景是与其他工具类型组合，实现"排除某些字段后做进一步变换"：

```typescript
interface User {
  id: number;
  username: string;
  password: string;
  email: string;
  createdAt: Date;
  updatedAt: Date;
}

// 场景1：排除敏感字段 + 部分更新
type UserUpdatePayload = Partial<Omit<User, 'id' | 'createdAt' | 'updatedAt'>>;
// { username?: string; password?: string; email?: string; }

// 场景2：排除内部字段 + 只读暴露
type PublicUserView = Readonly<Omit<User, 'password'>>;
// 所有字段只读，且不包含 password

// 场景3：排除系统字段 + 选取特定子集
type UserProfileResponse = Pick<
  Omit<User, 'password' | 'id' | 'createdAt' | 'updatedAt'>,
  'username' | 'email'
>;
```

### 实际项目中的使用建议

3. **注意 Omit 的静默行为**：传入不存在的键名不会报错，建议配合 ESLint 的 `@typescript-eslint/consistent-type-imports` 规则减少拼写错误。
4. **链式组合表达复杂意图**：`Partial<Omit<T, K>>` 比 `Pick<...>` 在表达"排除部分字段后的可编辑视图"时更清晰。

## Exclude\<T, U\>

### 定义与效果

`Exclude<T, U>` 从联合类型 T 中**排除**所有可赋值给 U 的类型成员。这是针对联合类型的集合差集操作。

```typescript
type T1 = Exclude<string | number | boolean, number>;
// 结果：string | boolean

type T2 = Exclude<'click' | 'focus' | 'scroll' | 'resize', 'scroll' | 'resize'>;
// 结果：'click' | 'focus'

type T3 = Exclude<string | number | null, null>;
// 结果：string | number
```

### 底层实现源码解析

```typescript
/**
 * Exclude from T those types that are assignable to U
 */
type Exclude<T, U> = T extends U ? never : T;
```

这里涉及条件类型的**分布式条件类型（Distributive Conditional Type）**机制：

- 当 T 是一个**裸类型参数**（即没有被数组、元组、Promise 等包裹）且是联合类型时，条件类型会自动**分发**到联合类型的每一个成员上。
- 对于 `Exclude<string | number | boolean, number>`，实际展开为：
  ```
  (string extends number ? never : string)
  | (number extends number ? never : number)
  | (boolean extends number ? never : boolean)
  = string | never | boolean
  = string | boolean  （never 在联合类型中被自动吸收）
  ```

`never` 是 TypeScript 的**空类型（Bottom Type）**，它在联合类型中被吸收（`A | never` 等于 A），这正是 `Exclude` 能实现"排除"效果的底层原因——被排除的成员变成了 `never`，然后在联合类型中消失。

### 分布式行为的重要性

分布式行为是有条件的——只有**裸类型参数**才会触发：

```typescript
// 场景 1：裸类型参数 → 触发分发 ✓
type Dist<T> = T extends string ? 'yes' : 'no';
type R1 = Dist<string | number>;  // 'yes' | 'no' — 分发了

// 场景 2：被包裹 → 不触发分发 ✗
type NoDist<T> = [T] extends [string] ? 'yes' : 'no';
type R2 = NoDist<string | number>;  // 'no' — 整体判断
```

`Exclude` 正是依赖这一特性实现对联合类型成员的逐一过滤。

### 典型场景

#### 从事件类型中过滤掉特定事件

```typescript
type UIEvent =
  | { type: 'click'; x: number; y: number }
  | { type: 'focus'; target: HTMLElement }
  | { type: 'scroll'; deltaY: number }
  | { type: 'resize'; width: number; height: number };

type StaticEvent = Exclude<UIEvent,
  { type: 'scroll' } | { type: 'resize' }
>;
// StaticEvent = { type: 'click'; x: number; y: number } | { type: 'focus'; target: HTMLElement }
```

#### 去除 null / undefined

虽然 `NonNullable` 是专门的工具，但其底层正是 `Exclude` 的特例：

```typescript
type WithoutNull = Exclude<string | number | null, null>;
// string | number

type WithoutNullAndUndefined = Exclude<string | number | null | undefined, null | undefined>;
// string | number
```

### 分布式条件类型的完整机制

`Exclude` 依赖的分布式条件类型（Distributive Conditional Types）是 TypeScript 类型系统的核心特性之一，值得深入理解：

**触发条件**：
1. 条件类型中的待检查类型必须是**裸类型参数**（naked type parameter）——直接引用泛型参数 T 本身
2. T 在当前上下文中解析为联合类型时才触发分发

**不触发分发的情况**：

```typescript
// 情况1：T 被数组包裹
type Wrapped<T> = [T] extends [string] ? 'yes' : 'no';
type W1 = Wrapped<string | number>;  // 'no' — 不分发

// 情况2：T 被元组包裹
type Tupled<T> = [T] extends [string | number] ? 'yes' : 'no';
type W2 = Tupled<string>;  // 'yes' — 整体判断

// 情况3：使用非裸形式的类型
type NotNaked<T> = { x: T } extends { x: string } ? 'yes' : 'no';
type W3 = NotNaked<string | number>;  // 'no' — 不分发

// 情况4：在函数签名中使用（不涉及条件类型分发）
// 函数参数中的联合类型不会触发分发——这是不同的语言特性
```

1. **配合 discriminated union 使用**：`Exclude` 和 `Extract` 与可辨识联合（tagged union）搭配时效果最佳——通过 `type` 字符串字面量字段精确筛选。
2. **用于类型守卫的返回值**：自定义 `is()` 函数的返回值类型通常用 `Extract` 来表达收窄后的类型。
3. **注意 `never` 的吸收行为**：如果 `Exclude` 结果为 `never`，说明目标类型中没有任何成员匹配排除条件。

## Extract\<T, U\>

### 定义与效果

`Extract<T, U>` 与 `Exclude` 相反：它从联合类型 T 中**提取**所有可赋值给 U 的类型成员。这是联合类型的集合交集操作。

```typescript
type E1 = Extract<string | number | boolean, number | string>;
// 结果：string | number

type E2 = Extract<'click' | 'focus' | 'scroll', 'click' | 'scroll'>;
// 结果：'click' | 'scroll'
```

### 底层实现

```typescript
/**
 * Extract from T those types that are assignable to U
 */
type Extract<T, U> = T extends U ? T : never;
```

与 `Exclude` 的唯一区别是条件分支的返回值互换：匹配时返回 T 自身（保留），不匹配时返回 `never`（丢弃）。展开过程如下：

```
Extract<string | number | boolean, number | string>
= (string extends number | string ? string : never)
| (number extends number | string ? number : never)
| (boolean extends number | string ? boolean : never)
= string | number | never
= string | number
```

### 典型场景

#### 提取特定类型的成员

从混合类型中筛选出特定类别的值：

```typescript
type MixedValue = string | number | boolean | (() => void);
type Callable = Extract<MixedValue, Function>;
// 结果：() => void

type StringOrNum = Extract<MixedValue, string | number>;
// 结果：string | number
```

#### 配合 typeof 使用

```typescript
const COLORS = { red: '#f00', green: '#0f0', blue: '#00f', white: '#fff' };
const SIZES = { sm: 12, md: 16, lg: 20 };

type ColorKeys = Extract<keyof typeof COLORS, keyof typeof SIZES>;
// 结果：never（两者无交集）

// 更实用的场景：从路由配置中提取特定类型的路由
type PageRoutes = Extract<
  keyof RouteConfig,
  '/home' | '/about' | '/settings' | '/api/' | string
>;
```

### Exclude vs Extract 对比

| 特性 | Exclude | Extract |
|------|---------|---------|
| 操作 | 差集（T − U） | 交集（T ∩ U） |
| 条件分支 | 匹配→never，不匹配→保留 | 匹配→保留，不匹配→never |
| 语义 | "去除不需要的" | "提取需要的" |

### `T & {}` 实现方式的深层原理

TypeScript 选择 `T & {}` 作为 `NonNullable` 的实现，而非更直觉的 `Exclude<T, null | undefined>`，有其深层次的考量：

1. **性能优势**：交叉类型的计算比条件类型的分发更快，尤其在处理大型联合类型时。
2. **语义精确性**：`{}` 在 TypeScript 类型系统中代表"非 null/undefined 的任何值"，这恰好就是 NonNullable 想要表达的含义。
3. **与 JavaScript 行为一致**：JavaScript 中 `{} + null` 是非法操作，而 `{}` 可以接收任何非空值，这种语义映射到类型系统层面就是 `T & {}`。

```typescript
// 验证：{} 确实只接受非 null/undefined
type A = string & {};      // string ✓
type B = number & {};      // number ✓
type C = null & {};        // never ✗（null 不能赋值给 {}）
type D = undefined & {};   // never ✗
type E = void & {};        // never ✗（void 也不能赋值给 {}）
```

**错误 2：在可能包含 void 时使用**


## NonNullable\<T\>

### 定义与效果

`NonNullable<T>` 从类型 T 中排除 `null` 和 `undefined`，确保结果类型不包含这两种空值类型。

```typescript
type N1 = NonNullable<string | number | null>;
// string | number

type N2 = NonNullable<string | undefined | null | boolean>;
// string | boolean

type N3 = NonNullable<null | undefined>;
// never（全部被排除后为空集合）
```

### 底层实现

```typescript
/**
 * Exclude null and undefined from T
 */
type NonNullable<T> = T & {};
```

或者等价的另一种写法：

```typescript
type NonNullable<T> = Exclude<T, null | undefined>;
```

TypeScript 实际采用的是 `T & {}` 形式。其原理是：`{}` 类型（空对象类型）被视为**非空类型**的约束——任何非 `null` 且非 `undefined` 的类型都可以赋值给 `{}`，而 `null` 和 `undefined` 不行。因此 `T & {}` 通过交叉类型实现了"过滤掉 null 和 undefined"的效果。

### 典型场景

#### API 参数类型安全

当前端需要确保传递给后端的参数不包含空值时：

```typescript
function queryUsers(params: NonNullable<QueryParams>): Promise<User[]> {
  return fetch('/api/users?' + new URLSearchParams(params as any)).then(r => r.json());
}

// 如果 params 可能含有 null/undefined 值，先做过滤
const safeParams: NonNullable<QueryParams> = Object.fromEntries(
  Object.entries(rawParams).filter(([, v]) => v != null)
);
queryUsers(safeParams);
```

#### 泛型约束

约束泛型参数不接受空值：

```typescript
function processValue<T>(value: NonNullable<T>): string {
  return String(value);
  // 此处 value 保证不是 null/undefined，无需判空
}

processValue(null);     // 编译错误
processValue(undefined); // 编译错误
processValue('hello');  // 正确
```

## ReturnType\<T\>

### 定义与效果

`ReturnType<T>` 提取函数类型 T 的**返回值类型**。

```typescript
function getUser(id: number): { name: string; email: string } {
  return { name: 'Alice', email: 'alice@example.com' };
}

type Userinfo = ReturnType<typeof getUser>;
// { name: string; email: string }
```

注意这里用的是 `typeof getUser`（值的类型），因为 `ReturnType` 接收的是**类型**，而不是值。

### 底层实现（infer 的使用）

```typescript
/**
 * Obtain the return type of a function type
 */
type ReturnType<T extends (...args: any) => any> = T extends (...args: any) => infer R ? R : any;
```

核心机制是条件类型中的 **`infer` 关键字**：

- `infer R` 表示在条件类型的位置声明一个**待推断的类型变量**。
- 当 T 能够匹配函数类型结构 `(...args: any) => ...` 时，TypeScript 会将实际的返回值类型**推断并绑定**到 R 上。
- 匹配成功则返回 R，否则回退到 `any`。

`infer` 只能出现在条件类型的 `extends` 子句中，且用于"从已知结构中提取未知部分"的场景。

### 函数重载时的行为

当函数存在多个重载签名时，`ReturnType` 取的是**最后一个重载签名**的返回值类型：

```typescript
declare function example(x: string): string;
declare function example(x: number): number;
declare function example(x: boolean): boolean;

type R = ReturnType<typeof example>;
// 取最后一个重载的返回值：boolean
```

这是一个需要注意的行为——如果重载签名的排列顺序改变，`ReturnType` 的结果也会随之变化。

### 典型场景

#### 高阶函数返回值推导

编写高阶函数时，`ReturnType` 可以自动推导包装函数的返回类型：

```typescript
function withLogging<T extends (...args: any[]) => any>(fn: T): (...args: Parameters<T>) => ReturnType<T> {
  return (...args: Parameters<T>) => {
    console.log(`calling ${fn.name} with`, args);
    const result = fn(...args);
    console.log(`result:`, result);
    return result;
  };
}

function add(a: number, b: number): number {
  return a + b;
}

const loggedAdd = withLogging(add);
// loggedAdd 的类型：(a: number, b: number) => number
```

#### 异步函数返回值解包

结合其他工具类型，可以解包 Promise 内部的类型：

```typescript
async function fetchData(): Promise<{ data: string; status: number }> {
  const resp = await fetch('/api/data');
  return resp.json();
}

type RawReturn = ReturnType<typeof fetchData>;
// Promise<{ data: string; status: number }>

// 解包 Promise 得到真正的数据类型
type Unpacked<T> = T extends Promise<infer U> ? U : T;
type DataType = Unpacked<RawReturn>;
// { data: string; status: number }
```

### infer 的推断优先级与多位置推断

当条件类型的同一分支中出现多个 `infer` 声明时，它们是**同时被推断**的——编译器会尝试从目标结构中同时提取所有位置的类型信息：

```typescript
// 同时推断参数和返回值
type FunctionSignature<T> = T extends (arg: infer A) => infer R
  ? { argType: A; returnType: R }
  : never;

type Sig = FunctionSignature<(x: string) => number>;
// { argType: string; returnType: number }

// 推断数组元素和长度
type ArrayInfo<T> = T extends Array<infer E>
  ? { elementType: E; length: number extends T['length'] ? 'dynamic' : T['length'] }
  : never;

type Info = ArrayInfo<[string, number, boolean]>;
// { elementType: string | number | boolean; length: 3 }
```

## Parameters\<T\>

### 定义与效果

`Parameters<T>` 提取函数类型 T 的**参数类型元组**，返回一个元组类型，其中每个元素依次对应函数的一个参数类型。

```typescript
function createUser(name: string, age: number, active?: boolean): User {
  return { name, age, active: active ?? true };
}

type CreateUserParams = Parameters<typeof createUser>;
// [string, number, boolean | undefined]
```

返回的是一个**元组类型（Tuple）**，保留了参数顺序和可选性信息。

### 底层实现

```typescript
/**
 * Obtain the parameters of a function type in a tuple
 */
type Parameters<T extends (...args: any) => any> = T extends (...args: infer P) => any ? P : never;
```

与 `ReturnType` 类似，这里也使用了 `infer`，只是推断位置换到了参数列表部分：

- `infer P` 在参数位置声明类型变量 P。
- 当 T 匹配函数类型时，P 被推断为**参数类型的元组**。
- 匹配失败返回 `never`（注意与 `ReturnType` 回退为 `any` 不同）。

### 典型场景

#### 函数包装器

`Parameters` 最经典的用途是在不改变函数签名的前提下包装已有函数：

```typescript
function debounce<T extends (...args: any[]) => any>(
  fn: T,
  delay: number
): (...args: Parameters<T>) => void {
  let timer: ReturnType<typeof setTimeout>;
  return (...args: Parameters<T>) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

function saveData(text: string, autoBackup: boolean): void {
  // ...
}

const debouncedSave = debounce(saveData, 300);
// debouncedSave 类型：(text: string, autoBackup: boolean) => void
debouncedSave('hello', true);  // 参数类型完全一致
```

#### 参数转发

在事件处理、中间件等场景中将参数转发给原始函数：

```typescript
type EventHandler<T> = (...args: Parameters<T>) => void;

function createListener<T extends (...args: any[]) => any>(
  handler: EventHandler<T>,
  context?: object
): EventHandler<T> {
  if (context) {
    return (...args) => handler.apply(context, args);
  }
  return handler;
}
```

### Parameters 与元组类型的精确映射

`Parameters` 返回的不仅仅是参数类型的集合，而是**保留了可选性和 rest 参数信息**的精确元组类型：

```typescript
// 可选参数被保留
function optional(a: string, b?: number, c?: boolean): void {}
type P1 = Parameters<typeof optional>;
// [string, (number | undefined)?, (boolean | undefined)?]

// Rest 参数被保留为数组
function variadic(first: string, ...rest: number[]): void {}
type P2 = Parameters<typeof variadic>;
// [string, ...number[]]

// this 参数不被包含在 Parameters 中（它是伪参数）
function withThis(this: GlobalAPI, key: string): void {}
type P3 = Parameters<typeof withThis>;
// [string] — this 参数被自动排除
```

#### 函数参数的柯里化工具

```typescript
// 柯里化：将多参数函数转换为一系列单参数函数
function curry<Fn extends (...args: any[]) => any>(fn: Fn):
  Parameters<Fn> extends [infer First, ...infer Rest]
    ? Rest extends []
      ? (arg: First) => ReturnType<Fn>
      : (arg: First) => curry<(...args: Rest) => ReturnType<Fn>>
    : never {

  return ((first: First) =>
    (Rest.length === 0
      ? fn(first)
      : curry((...rest: Rest) => fn(first, ...rest))
    )
  ) as any;
}

function add(a: number, b: number, c: number): number {
  return a + b + c;
}

const curriedAdd = curry(add);
// curriedAdd 类型：(a: number) => (b: number) => (c: number) => number

const result = curriedAdd(1)(2)(3);  // 6，全程类型安全
```

### 实际项目中的使用建议

1. **高阶函数的标准模式**：任何需要包装/装饰函数的工具函数，都应使用 `Parameters<T>` 和 `ReturnType<T>` 来保持签名的完整传递。
2. **注意 this 排除**：`Parameters` 会自动排除 `this` 参数，如果需要保留 `this` 信息应使用 `ThisParameterType`（TS 5.4+）。
3. **配合 rest 展开**：`Parameters<T>` 可以用 `...args: Parameters<T>` 直接展开到另一个函数的参数列表中。

## Record\<K, V\>

### 定义与效果

`Record<K, V>` 构造一个对象类型，其**键来自类型 K**，**所有值的类型均为 V**。它本质上创建了一个键值映射类型。

```typescript
type RoleMap = Record<string, 'admin' | 'editor' | 'viewer'>;
// 等价于：{ [key: string]: 'admin' | 'editor' | 'viewer' }

type HttpStatusCode = Record<number, string>;
// 等价于：{ [key: number]: string }

type WeekdaySchedule = Record<'Mon' | 'Tue' | 'Wed' | 'Thu' | 'Fri' | 'Sat' | 'Sun', Task[]>;
// 键必须是星期几，值是任务数组
```

### 底层实现（映射类型 + 索引签名）

```typescript
/**
 * Construct a type with a set of properties K of type T
 */
type Record<K extends keyof any, T> = {
  [P in K]: T;
};
```

要点解析：

- `K extends keyof any`：约束 K 必须可作为对象键的类型。`keyof any` 等价于 `string | number | symbol`——这是 JavaScript 中合法对象键的类型全集。
- `[P in K]: T`：遍历 K 中的每一个可能的键，将其映射到统一的值类型 T。

### 典型场景

#### 字典/映射表类型定义

最直接的用途是定义字典或映射表：

```typescript
// 国际化文本字典
type I18nDict = Record<Locale, Record<string, string>>;

const zhDict: I18nDict['zh-CN'] = {
  welcome: '欢迎',
  logout: '退出登录',
};

// 角色权限矩阵
type PermissionMatrix = Record<Role, Permission[]>;

const permissions: PermissionMatrix = {
  admin: ['read', 'write', 'delete', 'manage_users'],
  editor: ['read', 'write'],
  viewer: ['read'],
};
```

#### 配置表类型

```typescript
// 功能开关配置
type FeatureFlags = Record<string, boolean>;

const flags: FeatureFlags = {
  darkMode: true,
  newDashboard: false,
  betaAPI: true,
};

// 状态码映射
type HttpStatusMessages = Record<200 | 201 | 400 | 401 | 404 | 500, string>;

const messages: HttpStatusMessages = {
  200: 'OK',
  201: 'Created',
  400: 'Bad Request',
  401: 'Unauthorized',
  404: 'Not Found',
  500: 'Internal Server Error',
};
```

### 与普通索引签名的区别

`Record<string, V>` 与直接写索引签名 `[key: string]: V` 在大多数情况下效果相同，但有以下细微差异：

| 特性 | `Record<K, V>` | 索引签名 |
|------|----------------|----------|
| 键的类型灵活性 | K 可以是字面量联合类型 | 通常只能是 string / number / symbol |
| 语义表达 | 明确表达"映射/记录"意图 | 表达"动态属性"意图 |
| 与其他工具组合 | 可作为泛型参数参与推导 | 需要额外类型声明 |

特别地，当 K 为字面量联合类型时，`Record` 的优势明显——它会精确限定键的取值范围：

```typescript
// 精确的键集合
type ExactKeys = Record<'a' | 'b' | 'c', number>;
// { a: number; b: number; c: number }
// 只允许 a、b、c 三个键，不允许其他字符串键

// 对比普通索引签名
type LooseKeys = { [key: string]: number };
// 允许任意字符串键
```

### Record 的索引签名等价性与差异

虽然 `Record<string, V>` 与 `{ [key: string]: V }` 在大多数场景下可以互换，但在 TypeScript 编译器内部，它们的处理路径不同：

1. **`Record<K, V>`** 走的是泛型实例化路径：先解析 K 和 V 类型参数，再构建映射类型。
2. **索引签名 `{ [key: string]: V }`** 是对象类型的字面量声明，直接在类型检查器中创建索引签名。

这种差异在某些边缘场景下会体现出来：

```typescript
// Record 可以参与更复杂的类型运算
type MappedRecord = Record<`_${string}`, Handler>;
// 键必须以 _ 开头的字符串

// 索引签名无法表达这种模式
type MappedIndex = { [key: `_${string}`]: Handler };
// 语法错误！索引签名的 key 不能使用模板字面量

// 但 Record 也有局限——不能与显式声明的属性共存（除非属性是 Record 键的子集）
type Mixed = Record<string, number> & { special?: string };
// 需要用交叉类型来实现混合
```

#### 事件发射器的类型安全实现

```typescript
type EventMap = Record<string, unknown[]>;

class TypedEmitter<Events extends EventMap> {
  private listeners = new Map<keyof Events, Set<Function>>();

  on<E extends keyof Events>(event: E, handler: (...args: Events[E]) => void): () => void {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(handler);
    return () => this.listeners.get(event)?.delete(handler);
  }

  emit<E extends keyof Events>(event: E, ...args: Events[E]): void {
    this.listeners.get(event)?.forEach(handler => handler(...args));
  }
}

// 定义事件映射
type AppEvents = {
  'user:login': [userId: string, timestamp: number];
  'user:logout': [userId: string];
  'notification:receive': [title: string, body: string, type: 'info' | 'warning' | 'error'];
  ['data:update']: [entity: string, id: string, changes: Partial<object>];
};

// 使用——完全类型安全的事件系统
const emitter = new TypedEmitter<AppEvents>();

emitter.on('user:login', (userId, timestamp) => {
  // userId: string, timestamp: number — 自动推断正确
  console.log(`User ${userId} logged in at ${timestamp}`);
});

emitter.emit('notification:receive', '新消息', '您有一条未读消息', 'info');
// 参数类型和数量完全匹配
```

### 常见错误与纠正

**错误 1：用 Record 表达异构值类型**

```typescript
// 错误尝试：让每个键对应不同的值类型
type BadConfig = Record<'host' | 'port' | 'timeout', string | number>;
// 所有值都是 string | number，无法区分 host 必须是 string

// 正确做法：用普通接口或交叉类型
interface GoodConfig {
  host: string;
  port: number;
  timeout: number;
}

// 或者用 Record + Pick 的组合
type StrictConfig = Record<string, unknown> & {
  host: string;
  port: number;
  timeout: number;
};
```

**错误 2：忽略 number 作为键的运行时行为**

```typescript
type NumKey = Record<number, string>;
const data: NumKey = { 0: 'a', 1: 'b' };

console.log(data[0]);   // 'a'
console.log(data['0']); // 'a' —— 运行时数字键被转为字符串！

// 如果需要区分数字和字符串键：
type HybridKeys = Record<number, string> & {
  [key: string]?: never;  // 排除字符串键
};
```

## 工具类型的组合使用

TypeScript 的内置工具类型设计时就考虑了可组合性。多个工具类型可以像管道一样串联使用，实现复杂的类型变换。

### 多个工具类型串联

```typescript
interface User {
  id: number;
  username: string;
  email: string;
  password: string;
  createdAt: Date;
  updatedAt: Date;
}

// 串联示例：选取部分字段 → 变为可选 → 变为只读
type UserPatchRequest = Readonly<Partial<Pick<User, 'username' | 'email'>>>;
// 等价于：
// {
//   readonly username?: string;
//   readonly email?: string;
// }
```

从内向外求值：

```
Step 1: Pick<User, 'username' | 'email'>
      → { username: string; email: string; }

Step 2: Partial<{ username: string; email: string; }>
      → { username?: string; email?: string; }

Step 3: Readonly<{ username?: string; email?: string; }>
      → { readonly username?: string; readonly email?: string; }
```

### 实战案例：API 请求/响应的完整类型管道

以下是一个模拟真实项目的类型管道，展示如何通过组合工具类型构建前后端交互的类型体系：

```typescript
// ========== 后端领域模型（完整定义）==========

interface ArticleEntity {
  id: number;
  title: string;
  content: string;
  summary: string;
  authorId: number;
  author: AuthorEntity;
  category: CategoryEntity;
  tags: TagEntity[];
  viewCount: number;
  likeCount: number;
  commentCount: number;
  status: 'draft' | 'review' | 'published' | 'archived';
  isTop: boolean;
  publishedAt: Date | null;
  createdAt: Date;
  updatedAt: Date;
  deletedAt: Date | null;
}


// ========== 列表响应：排除大字段和内部字段 ==========

type ArticleListItem = Omit<ArticleEntity,
  | 'content'        // 正文太长，列表不需要
  | 'author'         // 作者详情单独请求
  | 'category'       // 分类详情单独请求
  | 'tags'           // 标签详情单独请求
  | 'deletedAt'      // 内部字段
>;


// ========== 详情响应：排除内部字段 ==========

type ArticleDetail = Omit<ArticleEntity,
  | 'deletedAt'
>;


// ========== 创建请求：仅需用户填写的字段，全部可选（草稿） ==========

type CreateArticleDraft = Partial<Pick<ArticleEntity,
  | 'title'
  | 'content'
  | 'summary'
  | 'categoryId'    // 注意：这里假设已将 category 改为 categoryId
  | 'tagIds'
  | 'status'
  | 'isTop'
>>;


// ========== 更新请求：基于 ID + 部分更新 ==========

type UpdateArticleBody = Partial<Pick<ArticleEntity,
  | 'title'
  | 'content'
  | 'summary'
  | 'status'
  | 'isTop'
>>;


// ========== 导出类型 ==========

export type {
  ArticleListItem,
  ArticleDetail,
  CreateArticleDraft,
  UpdateArticleBody,
};
```

### 组合顺序的影响

工具类型的组合顺序有时会影响最终结果，尤其是 `Partial` 和 `Readonly` 的顺序：

```typescript
interface Data {
  name: string;
  count: number;
}

// 方案 A：先 Partial 再 Readonly
type A = Readonly<Partial<Data>>;
// { readonly name?: string; readonly count?: number; }
// 属性既可选又只读

// 方案 B：先 Readonly 再 Partial
type B = Partial<Readonly<Data>>;
// { readonly name?: string; readonly count?: number; }
// 结果相同！因为 ? 和 readonly 修饰不同的维度

// 但在某些情况下顺序确实有影响
interface Config {
  requiredField: string;
  optionalField?: number;
}

type C = Partial<Required<Config>>;
// { requiredField?: string; optionalField?: number }
// 先把 optionalField 变成 required，再把所有变 optional

type D = Required<Partial<Config>>;
// { requiredField: string; optionalField: number }
// 先把 requiredField 变 optional，再把所有变 required
// C ≠ D，optionalField 在 C 中仍可选，在 D 中必填
```

一般原则：`Partial` ↔ `Required` 这对操作会互相抵消，而 `Readonly` 是独立维度上的修饰。跨维度组合时顺序往往不影响结果；同维度组合时，后操作的会覆盖前面的效果。

## 常见陷阱与注意事项

### 1. 只做浅层变换（不递归处理嵌套对象）

除了 `Record`，前面介绍的多数工具类型（`Partial`、`Required`、`Readonly`、`Pick`、`Omit`）都只处理**顶层属性**。嵌套对象内部的属性不会被变换。

```typescript
interface Nested {
  outer: {
    inner: string;
  };
}

type ShallowPartial = Partial<Nested>;
// { outer?: { inner: string } }
// outer 变可选了，但 inner 仍然是 required
```

如需深层变换，可以自定义递归版本：

```typescript
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object ? DeepPartial<T[P]> : T[P];
};

type DeepNested = DeepPartial<Nested>;
// { outer?: { inner?: string } }
```

类似地，也可以定义 `DeepReadonly`、`DeepRequired` 等递归变体。不过要注意递归过深可能导致编译性能问题，TypeScript 默认对递归深度有一定限制。

### 2. never 在联合类型中的特殊行为影响 Exclude 结果

`never` 作为空类型，在任何联合类型中都会被"吸收"：

```typescript
type A = string | never;      // string
type B = never | number;      // number
type C = string | never | number; // string | number
```

这意味着 `Exclude` 的底层机制依赖于这一行为。但也意味着，如果输入联合类型本身就包含 `never`，结果可能不符合直觉：

```typescript
type Weird = Exclude<never | string | number, boolean>;
// string | number（正常）

type AllNever = Exclude<never, string>;
// still never
```

此外，`Exclude<T, T>` 永远返回 `never`，因为所有成员都能赋值给自身从而被排除：

```typescript
type Empty = Exclude<string | number, string | number>;
// never
```

这可以用来判断两个类型是否完全相同（结果为 never 则说明 T 的成员全都被排除了，即 T 是 U 的子集）。

### 3. Pick/Omit 键不存在时的静默行为

`Pick` 有 `K extends keyof T` 约束，传入不存在的键会直接报编译错误。但 `Omit` 的约束是 `K extends keyof any`（即只要 K 是合法的键类型即可），因此：

```typescript
// Pick：不存在的键 → 报错
type BadPick = Pick<User, 'nonexistent' | 'name'>
//          ^^^^^^^^^^^^^^^^ 编译错误

// Omit：不存在的键 → 静默忽略（不会报错）
type BadOmit = Omit<User, 'nonexistent' | 'password'>
// 结果等同于 Omit<User, 'password'>， nonexistent 被静默忽略
```

这是因为 `Exclude` 在处理不存在的键时返回该键本身（因为该键不在 `keyof T` 中，自然不会被"排除"），随后 `Pick` 收到的键集中包含了一个 T 中不存在的键——但由于 `Pick` 内部是映射类型而非索引签名，多出的键实际上不会出现在最终结果中。

这一行为可能导致隐蔽的错误：拼写错误的键名在 `Omit` 中不会触发警告。建议配合 ESLint 规则或在开发中优先使用 `Pick` 以获得更好的类型校验。

### 4. Record 的 key 类型限制

`Record<K, V>` 要求 K 必须是 `string | number | symbol` 的子集（即满足 `extends keyof any`）。以下是合法和不合法的用法：

```typescript
// 合法
type R1 = Record<string, number>;
type R2 = Record<'a' | 'b', string>;
type R3 = Record<number, boolean>;
type R4 = Record<`${string}_id`, Object>;

// 不合法
type R5 = Record<boolean, string>;
//          ^^^^^^^^ 编译错误：boolean 不是有效的对象键类型

type R6 = Record<{} | null, string>;
//          ^^^^^^^^^^ 编译错误
```

JavaScript 中对象键会被隐式转为字符串（除非使用 Symbol），所以 `Record<number, V>` 实际运行时键也是字符串。TypeScript 在类型层面允许 `number` 作为键是为了方便某些场景的类型表达（如数字索引），但开发者应意识到这一运行时行为。

另外，`Record` 创建的类型的键是"开放的"——当 K 为 `string` 时，允许任意字符串键，而不仅仅是特定的字面量。如果需要限定为固定的键集合，应使用字面量联合类型作为 K：

```typescript
// 开放键：允许任意字符串
type OpenMap = Record<string, number>;
const open: OpenMap = { a: 1, b: 2, anything: 3 };  // 全部合法

// 封闭键：只允许指定的几个
type ClosedMap = Record<'x' | 'y', number>;
const closed: ClosedMap = { x: 1, y: 2 };
// const bad: ClosedMap = { x: 1, z: 3 };  // 编译错误，z 不是合法的键
```

## 总结速查表

下表汇总了所有内置工具类型的核心信息，便于快速查阅。

| 工具类型 | 一行实现 | 输入 | 输出 | 典型用途 |
|----------|----------|------|------|----------|
| `Partial<T>` | `{[P in keyof T]?: T[P]}` | 对象类型 | 所有属性变可选 | PATCH 请求、草稿状态、渐进构建 |
| `Required<T>` | `{[P in keyof T]-?: T[P]}` | 对象类型 | 所有属性变必填 | 配置规范化、完整性校验 |
| `Readonly<T>` | `{readonly [P in keyof T]: T[P]}` | 对象类型 | 所有属性变只读 | 不可变状态、参数保护 |
| `Pick<T, K>` | `{[P in K]: T[P]}` | 对象类型 + 键子集 | 仅含指定键的新类型 | 字段选取、接口子集暴露 |
| `Omit<T, K>` | `Pick<T, Exclude<keyof T, K>>` | 对象类型 + 排除键集 | 不含指定键的新类型 | 敏感字段排除、Props 继承裁剪 |
| `Exclude<T, U>` | `T extends U ? never : T` | 联合类型 + 排除目标 | 差集 | 过滤联合类型成员 |
| `Extract<T, U>` | `T extends U ? T : never` | 联合类型 + 提取目标 | 交集 | 提取特定类别成员 |
| `NonNullable<T>` | `T & {}` | 任意类型 | 去除 null 和 undefined | 空值安全、泛型约束 |
| `ReturnType<T>` | `T extends (...args: any) => infer R ? R : any` | 函数类型 | 返回值类型 | 高阶函数类型推导 |
| `Parameters<T>` | `T extends (...args: infer P) => any ? P : never` | 函数类型 | 参数元组类型 | 函数包装、参数转发 |
| `Record<K, V>` | `{[P in K]: V}` | 键类型 + 值类型 | 键值映射类型 | 字典、映射表、配置定义 |

### 组合模式速查

| 目标 | 组合方式 | 说明 |
|------|----------|------|
| 可选 + 只读 | `Readonly<Partial<T>>` | 草稿状态的不可变快照 |
| 选取 + 可选 + 只读 | `Readonly<Partial<Pick<T, K>>>` | 安全的部分更新请求体 |
| 排除 + 可选 | `Partial<Omit<T, K>>>` | 排除敏感字段后的部分更新 |
| 解包 Promise | `T extends Promise<infer U> ? U : T` | 获取异步函数的真实返回类型 |
| 深层 Partial | 自定义递归映射类型 | 嵌套对象的完全可选化 |
