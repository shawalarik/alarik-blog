## 为什么需要自定义工具类型

TypeScript 提供了一组内置工具类型——`Partial`、`Required`、`Readonly`、`Pick`、`Omit`、`Record` 等。它们解决了最常见的类型变换需求，但在实际工程中，这些内置工具往往不够用。

### 内置工具的局限性

内置工具类型的操作都是**浅层**（shallow）的：

```ts
interface Config {
  db: {
    host: string;
    port: number;
  };
  cache: {
    enabled: boolean;
    ttl: number;
  };
}

// Partial 只让第一层属性变为可选，嵌套对象不受影响
type PartialConfig = Partial<Config>;
// 等价于：
// {
//   db?: { host: string; port: number };
//   cache?: { enabled: boolean; ttl: number };
// }
// db.host 和 db.port 仍然是必填！
```

如果业务场景要求**深层嵌套可选**，内置 `Partial` 无能为力。类似地，`Readonly` 只冻结第一层，内部对象仍然可变；`Required` 也只作用于顶层。

另一个局限是**缺乏组合能力**。内置工具各自独立，无法表达"把某些字段设为 optional、某些字段设为 readonly、再合并另一个类型"这样的复合变换。

### 类型编程的价值

自定义工具类型的本质是**类型级别的函数**：输入一个或多个类型，输出经过计算的新类型。其价值体现在三个方面：

1. **消除重复声明**：从核心模型派生 CRUD 操作类型，避免手写多个相似接口
2. **提升可维护性**：修改源类型时，所有派生类型自动同步更新
3. **编译期保证正确性**：类型变换逻辑在编译期执行，运行时零开销

### 设计原则

设计自定义工具类型时应遵循以下原则：

| 原则 | 说明 |
|------|------|
| 组合优于重复 | 尽量用已有工具类型组合，而非从头实现 |
| 单一职责 | 每个工具解决一个明确的类型变换问题 |
| 边界完备 | 处理 Array、Tuple、Map、Set、Function、null、undefined 等边界 |
| 可测试 | 用 `type Test = Expect<Actual>` 模式编写编译期单测 |

## DeepPartial\<T\> —— 深度可选

### 问题背景

`Partial<T>` 将 T 的所有属性变为可选，但仅处理一层。对于深层嵌套的对象结构，我们常常需要递归地将每一层都变为可选。

### 实现原理

核心思路是**递归映射 + 条件类型判断**：

```ts
type Primitive =
  | string
  | number
  | boolean
  | bigint
  | symbol
  | undefined
  | null;

type DeepPartial<T> = T extends Primitive
  ? T
  : T extends (...args: any[]) => any // 排除函数类型
  ? T
  : T extends Map<infer K, infer V>
  ? Map<DeepPartial<K>, DeepPartial<V>>
  : T extends Set<infer U>
  ? Set<DeepPartial<U>>
  : T extends ReadonlyMap<infer K, infer V>
  ? ReadonlyMap<DeepPartial<K>, DeepPartial<V>>
  : T extends ReadonlySet<infer U>
  ? ReadonlySet<DeepPartial<U>>
  : T extends Array<infer U>
  ? Array<DeepPartial<U>>
  : T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;
```

逐层分析这个实现：

1. **Primitive 基础类型直接返回**：string、number 等不需要展开
2. **Function 直接返回**：函数不应被拆解为 `{ apply?: ...; call?: ... }`
3. **Map/Set 特殊处理**：对键值类型分别递归
4. **Array/Tuple 处理**：数组元素递归
5. **object 递归**：对每个属性值递归调用 DeepPartial，并用 `?` 标记可选

### 使用示例

```ts
interface ServerConfig {
  name: string;
  database: {
    host: string;
    port: number;
    credentials: {
      username: string;
      password: string;
    };
  };
  features: {
    logging: boolean;
    caching: { maxSize: number };
  }[];
}

// PATCH API 的请求体类型：所有层级字段均可选
type PatchConfig = DeepPartial<ServerConfig>;

const patch: PatchConfig = {
  // 只修改数据库密码这一处深层嵌套字段
  database: {
    credentials: {
      password: "new-secret",
    },
  },
}; // ✓ 合法
```

### 性能考量

TypeScript 对条件类型的递归深度有限制（通常在 50-100 层左右）。对于极端深层的嵌套结构，可能触发"Type instantiation is excessively deep and possibly infinite"编译错误。实际业务中，配置对象的嵌套深度极少超过 10 层，因此一般不会遇到此问题。

如果确实需要处理超深结构，可以限制递归深度：

```ts
type DeepPartialN<
  T,
  Depth extends number = 5,
  _Current extends any[] = [],
> = _Current["length"] extends Depth
  ? T
  : T extends Primitive
  ? T
  : T extends object
  ? { [K in keyof T]?: DeepPartialN<T[K], Depth, [..._Current, any]> }
  : T;

// 限制最多递归 3 层
type SafePartial = DeepPartialN<SomeVeryDeepType, 3>;
```

## DeepRequired\<T\> —— 深度必选

### 与 DeepPartial 的逆操作

`DeepRequired` 是 `DeepPartial` 的反向操作：将嵌套对象中所有层级的可选属性全部恢复为必填。

```ts
type DeepRequired<T> = T extends Primitive
  ? T
  : T extends (...args: any[]) => any
  ? T
  : T extends Map<any, any>
  | Set<any>
  | ReadonlyMap<any, any>
  | ReadonlySet<any>
  ? T
  : T extends Array<infer U>
  ? Array<DeepRequired<U>> & {}
  : T extends object
  ? { [K in keyof T]-?: DeepRequired<T[K]> }
  : T;
```

关键点：

1. 使用 `-?` 修饰符移除可选标记（与 `?` 相反）
2. 对于 Array，使用 `& {}` 触发交叉类型展开，确保元组元素也被处理
3. 同样排除 Function、Map/Set 等不需要展开的类型

### 典型场景

```ts
// 用户填写的草稿表单（宽松）
interface DraftUser {
  name?: string;
  profile?: {
    avatar?: string;
    bio?: string;
    contact?: {
      email?: string;
      phone?: string;
    };
  };
}

// 收紧为完整定义，所有字段必须填写
type CompleteUser = DeepRequired<DraftUser>;
// 等价于：
// {
//   name: string;
//   profile: {
//     avatar: string;
//     bio: string;
//     contact: {
//       email: string;
//       phone: string;
//     };
//   };
// }
```

## DeepReadonly\<T\> —— 深度只读

### Readonly 浅层问题

`Readonly<T>` 仅在顶层添加 `readonly` 修饰符，内部对象仍然可以被修改：

```ts
const config = {
  server: { host: "localhost", port: 3000 },
} as Readonly<{ server: { host: string; port: number }>;

config.server.host = "example.com"; // TypeScript 不报错！
```

### 完整实现

```ts
type DeepReadonly<T> = T extends ((...args: any[]) => any)
  | Date
  | RegExp
  | Error
  ? T
  : T extends Map<infer K, infer V>
  ? ReadonlyMap<DeepReadonly<K>, DeepReadonly<V>>
  : T extends ReadonlyMap<infer K, infer V>
  ? ReadonlyMap<DeepReadonly<K>, DeepReadonly<V>>
  : T extends WeakMap<any, any>
  ? T // WeakMap 键必须是对象，且本身不支持迭代
  : T extends Set<infer U>
  ? ReadonlySet<DeepReadonly<U>>
  : T extends ReadonlySet<infer U>
  ? ReadonlySet<DeepReadonly<U>>
  : T extends WeakSet<any>
  ? T
  : T extends Promise<any>
  ? T // Promise 内部状态由 JS 引擎管理
  : T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;
```

需要特别处理的不可变内置类型：

| 类型 | 处理方式 | 原因 |
|------|----------|------|
| Function | 不递归 | 函数不是数据容器 |
| Date | 不递归 | 通过方法修改，非属性赋值 |
| RegExp | 不递归 | 通过方法修改 |
| Error | 不递归 | 特殊内置对象 |
| Promise | 不递归 | 内部状态不由用户管理 |
| WeakMap/WeakSet | 不递归 | 弱引用集合，不可枚举 |

### 使用示例 —— 不可变状态管理

```ts
type ImmutableState<T> = DeepReadonly<T>;

interface AppState {
  user: { id: string; name: string; roles: string[] };
  ui: { theme: "light" | "dark"; sidebarOpen: boolean };
  entities: Map<string, { data: any; version: number }>;
}

function createStore<S>(initialState: S): {
  state: ImmutableState<S>;
  update: (fn: (draft: S) => S) => void;
} {
  let state = initialState;
  return {
    get state(): ImmutableState<S> {
      return state as ImmutableState<S>;
    },
    update(fn) {
      state = fn(structuredClone(state));
    },
  };
}

const store = createStore<AppState>({
  user: { id: "1", name: "Alice", roles: ["admin"] },
  ui: { theme: "light", sidebarOpen: false },
  entities: new Map(),
});

store.state.user.name = "Bob"; // ❌ Cannot assign to 'name' because it is read-only
store.state.ui.theme = "dark"; // ❌ Cannot assign to 'theme' because it is read-only
```

## Mutable\<T\> —— 移除只读

### 作为 DeepReadonly 的逆操作

当从外部接收到 `readonly` 数据后，有时需要对其进行本地修改。`Mutable` 移除所有层级的 readonly 修饰符。

```ts
type Mutable<T> = {
  -readonly [K in keyof T]: T[K] extends object ? Mutable<T[K]> : T[K];
};
```

核心是 `-readonly` 映射修饰符（TypeScript 2.8+ 支持）。

```ts
type FrozenUser = DeepReadonly<{
  id: string;
  profile: { name: string; email: string };
}>;

type ThawedUser = Mutable<FrozenUser>;
// {
//   id: string;
//   profile: { name: string; email: string };  // 所有层级都可写
// }

function thaw<T>(data: DeepReadonly<T>): Mutable<T> {
  return structuredClone(data) as Mutable<T>;
}
```

## AsyncReturnType\<T\>

### 问题：ReturnType 的局限

`ReturnType` 获取函数返回值的类型，但对于 async 函数，它返回的是 `Promise<T>` 而非实际的 `T`：

```ts
async function fetchUser() {
  return { id: "1", name: "Alice" };
}

type R = ReturnType<typeof fetchUser>;
// Promise<{ id: string; name: string }> — 不是我们要的
```

### 实现方式

```ts
// 基础版：解包一层 Promise
type AsyncReturnType<T extends (...args: any[]) => any> =
  T extends (...args: any[]) => Promise<infer U> ? U
  : T extends (...args: any[]) => infer U
  ? U
  : never;

// 递归版：处理 Promise<Promise<T>> 嵌套
type UnwrapAsync<T> = T extends Promise<infer U> ? UnwrapAsync<U> : T;

type DeepAsyncReturnType<T extends (...args: any[]) => any> = UnwrapAsync<
  ReturnType<T>
>;
```

### 与 Awaited 内置类型对比

TypeScript 4.5 引入了内置的 `Awaited<T>` 工具类型，功能等价于上述 `UnwrapAsync`：

```ts
type A = Awaited<Promise<Promise<string>>>; // string

// 因此可以这样简写：
type MyAsyncReturn<T extends (...args: any[]) => any> = Awaited<ReturnType<T>>;
```

`Awaited` 还额外处理了 `thenable` 对象（具有 `.then()` 方法的非 Promise 对象），比手动实现更完善。

```ts
// Awaited 能处理的 thenable 场景
const thenable = {
  then(
    resolve: (value: string) => void,
    _reject: (err: Error) => void,
  ) {
    resolve("hello");
  },
};

type T = Awaited<typeof thenable>; // string — 手动版 UnwrapAsync 无法处理
```

## NonNeverKeys\<T\> / OptionalKeys\<T\> / RequiredKeys\<T\>

### 提取属性的"可选性"信息

这三个工具用于提取对象类型中不同性质的属性键名：

```ts
// 提取值为 never 以外的属性键名
type NonNeverKeys<T> = {
  [K in keyof T]: [T[K]] extends [never] ? never : K;
}[keyof T];

// 提取可选属性的键名
type OptionalKeys<T> = {
  [K in keyof T]: {} extends Pick<T, K> ? K : never;
}[keyof T];

// 提取必填属性的键名
type RequiredKeys<T> = {
  [K in keyof T]: {} extends Pick<T, K> ? never : K;
}[keyof T];
```

### 底层原理

这里利用了**分配条件类型的一个微妙行为**：`{} extends Pick<T, K>` 在 `K` 为可选属性时为 `true`，因为可选属性允许缺失，而空对象 `{}` 恰好不包含任何属性，所以是合法的子类型。

```ts
interface User {
  id: string;
  name: string;
  age?: number;
  email?: string;
}

type Opt = OptionalKeys<User>; // "age" | "email"
type Req = RequiredKeys<User>; // "id" | "name"
```

### 实际应用：表单验证器自动生成

```ts
interface LoginForm {
  username: string;
  password: string;
  rememberMe?: boolean;
  captcha?: string;
}

// 自动区分必填和可选字段
function createValidator<T extends object>(schema: {
  [K in RequiredKeys<T>]: (val: unknown) => boolean;
  [K in OptionalKeys<T>]?: (val: unknown) => boolean;
}) {
  return (data: Partial<T>): { valid: boolean; errors: string[] } => {
    const errors: string[] = [];
    for (const key of Object.keys(schema) as (keyof typeof schema)[]) {
      const validator = schema[key];
      if (validator && !validator((data as any)[key])) {
        errors.push(`${String(key)} validation failed`);
      }
    }
    return { valid: errors.length === 0, errors };
  };
}

const validateLogin = createValidator<LoginForm>({
  username: (v) => typeof v === "string" && v.length > 0, // 必填
  password: (v) => typeof v === "string" && v.length >= 6, // 必填
  rememberMe: (v) => typeof v === "boolean", // 可选
  captcha: (v) => !v || /^\d{4}$/.test(v), // 可选
});
```

## Merge\<A, B\> —— 合并两个类型

### 问题：交叉类型不能覆盖同名属性

使用 `&` 合并两个类型时，同名属性的类型会做**交叉**而非**覆盖**：

```ts
type A = { x: number; y: string };
type B = { x: string; z: boolean };

type Cross = A & B;
// {
//   x: number & string  ← never！number 和 string 的交集是 never
//   y: string;
//   z: boolean;
// }
```

这通常不是我们想要的结果。我们需要的是 B 的属性**覆盖** A 的同名属性。

### 实现

```ts
type Merge<A, B> = Omit<A, keyof B> & B;
```

原理：先从 A 中剔除与 B 同名的属性，再做交叉。这样 B 中同名字段自然成为最终类型。

```ts
type Merged = Merge<A, B>;
// {
//   y: string;   // 来自 A
//   x: string;   // 被 B 覆盖
//   z: boolean;  // 来自 B
// }

// 实际应用：默认配置 + 用户覆盖
type DefaultConfig = {
  apiUrl: string;
  timeout: number;
  retries: number;
  debug: boolean;
  headers: Record<string, string>;
};

type UserOverrides = Partial<DefaultConfig> & {
  // 用户只覆盖部分字段
};

function buildConfig(
  defaults: DefaultConfig,
  overrides?: UserOverrides,
): Merge<DefaultConfig, UserOverrides> {
  return { ...defaults, ...(overrides ?? {}) } as any;
}
```

## MarkOptional\<T, K\> / MarkRequired\<T, K\>

### 更精确的控制粒度

`Partial<T>` 让所有属性可选，`Pick<T, K>` 只保留指定属性。但很多时候我们需要的是：**保持大部分不变，仅将某些属性改为 optional 或 required**。

```ts
// 将指定属性设为可选
type MarkOptional<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;

// 将指定属性设为必填
type MarkRequired<T, K extends keyof T> = Omit<T, K> & Required<Pick<T, K>>;
```

### 使用示例

```ts
interface Article {
  id: string;
  title: string; // 必填
  content: string; // 必填
  summary: string; // 创建时可省略
  tags: string[]; // 创建时可省略
  createdAt: Date; // 服务端生成
  updatedAt: Date; // 服务端生成
}

// 创建文章时：summary 和 tags 可选，createdAt/updatedAt 不需要提交
type CreateArticleInput = Omit<Article, "id" | "createdAt" | "updatedAt"> &
  MarkOptional<Article, "summary" | "tags">;

// 更新文章时：title/content 至少填一个，其余全部可选
type UpdateArticleInput = MarkOptional<
  Article,
  Exclude<keyof Article, "id">
> & {
  id: string; // id 仍为必填
};

// 或者用更简洁的方式：先全量可选，再把 id 收回来
type UpdateInput = Partial<Omit<Article, "id">> & Pick<Article, "id">;
```

对比三种方式的适用场景：

| 方式 | 效果 | 适用场景 |
|------|------|----------|
| `Partial<T>` | 全部可选 | 创建资源时的宽松输入 |
| `MarkOptional<T, K>` | 部分可选 | 大部分必填、少数可选 |
| `Omit<T, K> & Partial<Pick<T, K>>` | 排除+可选组合 | 最灵活的手动控制 |

## TypeGuard\<T\> —— 类型守卫工具

### 封装断言函数的类型签名

TypeScript 的**类型守卫**（type guard）通过 `x is T` 语法在运行时收窄类型。我们可以封装一个通用工具来简化断言函数的定义：

```ts
type TypeGuard<T> = (value: unknown) => value is T;

// 基础用法
const isString: TypeGuard<string> = (value): value is string =>
  typeof value === "string";

const isNumber: TypeGuard<number> = (value): value is number =>
  typeof value === "number";

// 复合守卫
interface User {
  id: string;
  name: string;
}

const isUser: TypeGuard<User> = (value): value is User =>
  !!value &&
  typeof value === "object" &&
  "id" in value &&
  "name" in value &&
  typeof (value as any).id === "string" &&
  typeof (value as any).name === "string";
```

### 进阶：带错误信息的守卫

```ts
type TypedGuard<T> = (
  value: unknown,
) => value is T | { valid: false; reason: string };

function createGuard<T>(
  check: (value: unknown) => check is T,
  typeName: string,
): TypedGuard<T> {
  return (value) => {
    if (check(value)) return true;
    return { valid: false, reason: `Expected ${typeName}, got ${typeof value}` };
  };
}

const guardedIsUser = createGuard<User>(isUser, "User");

function processUser(input: unknown) {
  if (guardedIsUser(input)) {
    // input 类型被收窄为 User
    console.log(input.name);
  } else {
    console.error(guardedIsUser(input).reason);
  }
}
```

## StringKeyOf\<T\> —— 提取字符串键名

### 为什么需要

`keyof T` 返回所有键名的联合类型，包括 `symbol` 类型的键名。在某些场景下（如动态属性访问），只需要字符串键名：

```ts
type StringKeyOf<T> = Extract<keyof T, string>;

interface Mixed {
  foo: string;
  bar: number;
  [Symbol.toStringTag]: "Mixed";
  [sym: unique symbol]: boolean;
}

type Keys = keyof Mixed; // "foo" | "bar" | typeof Symbol.toStringTag | symbol
type StrKeys = StringKeyOf<Mixed>; // "foo" | "bar"
```

### 应用场景

```ts
// 动态属性访问的安全类型
function getProp<T extends object, K extends StringKeyOf<T>>(
  obj: T,
  key: K,
): T[K] {
  return obj[key];
}

// JSON 序列化时只处理字符串键
function stringifyObject<T extends object>(obj: T): Record<StringKeyOf<T>, any> {
  return obj as any;
}

// 路由参数提取
type RouteParams = { userId: string; postId: string; [meta: string]: string };
type ParamNames = StringKeyOf<RouteParams>; // "userId" | "postId"
```

## 实战案例：完整的 CRUD 类型工具集

在实际项目中，一个数据模型通常需要对应四种操作类型：创建、读取列表、读取详情、更新、删除。手工维护这些类型既繁琐又容易出错。下面展示如何从一个 Model 类型派生出全套 CRUD 类型。

### 定义基础模型

```ts
interface BaseModel {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

interface ArticleModel extends BaseModel {
  title: string;
  content: string;
  summary?: string;
  tags: string[];
  authorId: string;
  status: "draft" | "published" | "archived";
}
```

### CRUD 类型工具集

```ts
/**
 * 创建操作的输入类型
 * - 排除服务端生成的字段（id, createdAt, updatedAt）
 * - 其余字段中原本可选的仍然可选
 */
type CreateType<T extends BaseModel> = Omit<T, keyof BaseModel>;

/**
 * 更新操作的输入类型（PATCH 语义）
 * - id 为必填（定位目标记录）
 * - 其余所有字段（含 BaseModel 字段如 updatedAt）均为可选
 * - 支持深层嵌套可选（如更新嵌套配置）
 */
type UpdateType<T extends BaseModel> = DeepPartial<Omit<T, "id">> &
  Pick<T, "id">;

/**
 * 读取详情的响应类型
 * - 所有字段必填（即使原模型中有可选字段也补齐）
 * - 所有字段只读
 */
type ReadType<T extends BaseModel> = DeepReadonly<DeepRequired<T>>;

/**
 * 列表查询的响应类型（不含完整内容）
 * - 只包含摘要字段
 * - 所有字段只读
 */
type ListItemType<T extends BaseModel, SummaryFields extends keyof T = "id" | "createdAt" | "updatedAt"> = DeepReadonly<Pick<T, SummaryFields>>;
```

### 应用到具体模型

```ts
// ====== 创建文章 ======
type CreateArticle = CreateType<ArticleModel>;
// {
//   title: string;
//   content: string;
//   summary?: string;
//   tags: string[];
//   authorId: string;
//   status: "draft" | "published" | "archived";
// }

// ====== 更新文章（PATCH） ======

// {
//   id: string;  // 必填
//   title?: string | undefined;
//   content?: string | undefined;
//   summary?: string | undefined;
//   tags?: string[] | undefined;
//   authorId?: string | undefined;
//   status?: "draft" | "published" | "archived" | undefined;
//   createdAt?: Date | undefined;
//   updatedAt?: Date | undefined;
// }

// ====== 文章详情 ======
type ArticleDetail = ReadType<ArticleModel>;
// 所有字段 readonly + required

// ====== 文章列表项 ======
type ArticleListItem = ListItemType<ArticleModel, "id" | "title" | "status" | "createdAt">;
// { readonly id: string; readonly title: string; readonly status: ...; readonly createdAt: Date }
```

## 实战案例：API 层类型管道

真实的前端应用中，数据流经多个阶段，每一步都可能涉及类型变换。下面的例子展示了一条完整的 API 数据处理管道。

### 场景描述

1. 后端返回 snake_case JSON
2. 前端转为 camelCase
3. 过滤掉不需要的字段
4. 补充前端特有的计算字段
5. 最终交给组件使用的类型

### 类型定义

```ts
// ====== 后端原始响应（snake_case） ======
interface RawArticleResponse {
  article_id: string;
  article_title: string;
  article_content: string;
  created_at: string; // ISO 字符串
  updated_at: string;
  author_name: string;
  view_count: number;
  is_published: boolean;
  internal_notes: string; // 前端不应看到
}

// ====== 步骤1：snake_case → camelCase ======
type SnakeToCamel<S extends string> = S extends `${infer P}_${infer Rest}`
  ? `${P}${Capitalize<SnakeToCamel<Rest>>}`
  : S;

type CamelizeKeys<T> = {
  [K in keyof T as K extends string ? SnakeToCamel<K> : K]: T[K]
};

type CamelizedArticle = CamelizeKeys<RawArticleResponse>;
// {
//   articleId: string;
//   articleTitle: string;
//   articleContent: string;
//   createdAt: string;
//   updatedAt: string;
//   authorName: string;
//   viewCount: number;
//   isPublished: boolean;
//   internalNotes: string;
// }

// ====== 步骤2：过滤敏感字段 ======
type FilterFields<T, Excluded extends keyof T> = Omit<T, Excluded>;

type PublicArticle = FilterFields<CamelizedArticle, "internalNotes">;

// ====== 步骤3：类型转换 + 计算字段补充 ======
type ProcessedArticle = Omit<PublicArticle, "createdAt" | "updatedAt"> & {
  createdAt: Date;
  updatedAt: Date;
  // 前端计算字段
  readingTime: number; // 分钟数，基于内容长度估算
  excerpt: string; // 从 content 截取前 200 字
};
```

### 运行时实现配合类型管道

```ts
// snake_case → camelCase 转换器
function camelizeKeys<T extends object>(obj: T): CamelizeKeys<T> {
  const result: Record<string, unknown> = {};
  for (const [key, value] of Object.entries(obj)) {
    const camelKey = key.replace(/_([a-z])/g, (_, c) => c.toUpperCase());
    result[camelKey] = value;
  }
  return result as CamelizeKeys<T>;
}

// 完整的数据处理管道
async function fetchArticle(id: string): Promise<ProcessedArticle> {
  // 1. 获取原始响应
  const raw = await api.get<RawArticleResponse>(`/articles/${id}`);

  // 2. 键名转换
  const camelized = camelizeKeys(raw);

  // 3. 过滤 + 转换 + 补充计算字段
  const { internalNotes: _, createdAt, updatedAt, content, ...rest } = camelized;

  return {
    ...rest,
    content,
    createdAt: new Date(createdAt),
    updatedAt: new Date(updatedAt),
    readingTime: Math.ceil(content.split(/\s+/).length / 200),
    excerpt: content.slice(0, 200) + (content.length > 200 ? "..." : ""),
  };
}

// 使用时拥有完整类型提示
const article = await fetchArticle("123");
article.readingTime; // number
article.excerpt; // string
article.createdAt; // Date
article.internalNotes; // ❌ Property does not exist
```

这条管道展示了多个工具类型如何串联协作：`CamelizeKeys` 做键名重映射、`Omit` 做字段过滤、交叉类型 `&` 做字段增强。每个步骤都有独立的类型变换，组合起来形成一条完整的类型安全数据处理链路。

## 设计原则与最佳实践

### 命名规范

自定义工具类型应遵循一致的命名约定：

| 命名模式 | 示例 | 含义 |
|----------|------|------|
| 形容词 + 名词 | `DeepPartial`, `DeepReadonly` | 变换后的特征 |
| 动词开头 | `CamelizeKeys`, `FilterFields` | 执行的操作 |
| 前缀区分 | `NonNullable`, `NonNullish` | 区分变体 |
| 后缀区分 | `KeyType`, `ValueType`, `KeyTypeOf` | 提取的内容 |

推荐使用 PascalCase（与内置工具类型一致）。如果工具属于某个领域，可以用命名空间组织：

```ts
namespace TypeUtils {
  export type DeepPartial<T> = /* ... */;
  export type DeepRequired<T> = /* ... */;
  export type Mutable<T> = /* ... */;

  export namespace String {
    export type Camelize<S> = /* ... */;
    export type Snakelize<S> = /* ... */;
    export type Capitalize<S> = /* ... */;
  }
}

// 使用
type C = TypeUtils.DeepPartial<Config>;
type S = TypeUtils.String.Camelize<"foo_bar">;
```

### 文档和注释

工具类型的代码本身就是文档，但适当的注释能够显著降低理解成本：

```ts
/**
 * 递归地将 T 的所有层级的属性变为可选。
 *
 * @example
 * type Result = Deep<{ a: { b: string } }>
 * // => { a?: { b?: string } }
 *
 * @remarks
 * - 不处理 Function、Date、RegExp 等内置类型
 * - 递归深度受 TS 编译器限制（约 50-100 层）
 */
export type DeepPartial<T> = /* ... */;
```

关键要说明的是：**边界行为**（什么不做、为什么）、**使用示例**（一眼看懂效果）、**注意事项**（已知限制）。

### 何时应该封装

不是所有的类型表达式都需要封装成命名工具类型。判断标准：

| 应该封装 | 不需要封装 |
|-----------|-----------|
| 在多处复用 | 只用一次 |
| 逻辑复杂（超过 3 行） | 简单的 Pick/Omit 组合 |
| 团队成员可能用到 | 个人项目中的临时需求 |
| 边界情况复杂（需处理多种类型） | 语义清晰的内联类型 |

```ts
// ✅ 值得封装：复杂逻辑、多出复用
export type DeepPartial<T> = { /* ... */ };

// ❌ 不需要封装：只用一次的简单变换
// type MyType = Omit<User, "password"> & { maskedPassword: string };
// 直接内联即可：
type SecureUser = Omit<User, "password"> & { maskedPassword: string };
```

### 编译期测试策略

工具类型最有效的测试方式是**编译期类型检查**——利用 TypeScript 类型系统自身的推导能力来验证正确性：

```ts
// ====== 测试辅助工具 ======

// 期望两个类型相等
type Equal<X, Y> =
  (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2)
    ? true
    : false;

// 期望类型匹配
type Expect<T extends true> = T;

// ====== 测试用例 ======

// DeepPartial 测试
namespace DeepPartialTests {
  interface Nested {
    a: { b: { c: string } };
    arr: number[];
    fn: () => void;
  }

  type Test1 = Expect<
    Equal<
      DeepPartial<Nested>,
      {
        a?: { b?: { c?: string } };
        arr?: number[];
        fn: () => void; // 函数不被展开
      }
    >
  >;

  type Test2 = Expect<Equal<DeepPartial<string>, string>>;
  type Test3 = Expect<Equal<DeepPartial<number>, number>>;
}

// Merge 测试
namespace MergeTests {
  type M = Merge<{ a: number; b: string }, { b: boolean; c: number }>;
  type Test1 = Expect<Equal<M["b"], boolean>>; // 被覆盖
  type Test2 = Expect<Equal<M["a"], number>>; // 保留
  type Test3 = Expect<Equal<M["c"], number>>; // 新增
}

// 如果类型不等，Expect 会报错，编译失败即测试失败
```

这种测试方式的特点：

1. **零运行时开销**：纯类型检查，不会出现在产物中
2. **即时反馈**：保存文件即可看到是否通过
3. **精确**：不仅检查结构兼容，还检查字面量类型的精确匹配

对于更复杂的场景，可以使用 [tsd](https://github.com/SamVerschueren/tsd) 或 [@type-challenges/utils](https://github.com/type-challenges/utils) 等专门的类型测试框架。

### 常见陷阱

**陷阱一：交叉类型导致 never**

```ts
type Bad = { x: string } & { x: number };
// x 的类型是 string & number = never
// 应该用 Merge 替代 &
```

**陷阱二：递归无限展开**

```ts
// 缺少终止条件的递归会导致 TS 报错
type Infinite<T> = { [K in keyof T]: Infinite<T[K]> }; // ⚠️ 可能超限
// 应加入 Primitive 终止条件
```

**陷阱三：as 断言绕过检查**

```ts
// 用 as 强行赋值虽然能过编译，但失去了类型安全保障
const config = someData as DeepPartial<MyConfig>; // 危险
// 应该用真正的类型变换或运行时校验
```

**陷阱四：忽略数组/元组差异**

```ts
type Arr = DeepPartial<string[]>;       // (string | undefined)[]
type Tuple = DeepPartial<[string, number]>;  // [string?, number?] — 保持元组结构
// 注意两者行为的区别
```

## 小结

自定义工具类型是 TypeScript 类型编程的核心实践。从本文涵盖的内容来看，几个关键的思维模型值得记住：

1. **递归 + 条件类型**是实现深度变换的基本范式，几乎所有 Deep* 工具都遵循此模式
2. **映射修饰符**（`?`、`-?`、`readonly`、`-readonly`）提供精细的可选性和可变性控制
3. **Omit + & 组合**是实现"选择性修改"的通用技巧，比直接用 `&` 更安全
4. **infer 关键字**是提取类型内部结构的唯一手段，常用于解包 Promise、提取函数参数等
5. **编译期测试**用 `Equal` + `Expect` 模式就能构建可靠的类型回归测试

掌握这些模式后，面对新的类型变换需求时，不再是从零开始摸索，而是选择合适的范式进行组合和适配。这正是类型编程从"魔法"走向"工程"的关键。
