# 命名空间与模块

TypeScript 的模块系统是其类型安全体系的核心支柱之一。理解命名空间（Namespace）与模块（Module）的区别、演进脉络和最佳实践，是编写可维护、可扩展 TypeScript 项目的基础能力。

## JavaScript 模块系统的演进

在深入 TypeScript 的模块机制之前，需要回顾 JavaScript 模块化思想的演进历程。TypeScript 作为 JavaScript 的超集，其设计目标之一就是兼容各个历史阶段的模块规范。

### 无模块时代

最早的 JavaScript 没有任何模块化机制。所有脚本共享全局作用域：

```js
// app.js
var config = { apiEndpoint: '/api' };
var utils = {
  formatDate: function(d) { /* ... */ }
};

// 另一个文件可能覆盖同名变量
```

这种模式的致命问题是命名冲突和依赖管理缺失。开发者通过 IIFE（Immediately Invoked Function Expression）来模拟局部作用域：

```js
var MyLib = (function() {
  var privateVar = 42;

  function privateHelper() {
    return privateVar * 2;
  }

  return {
    publicMethod: function() {
      return privateHelper();
    }
  });
})();
```

IIFE 通过闭包实现了信息隐藏和封装，但无法解决跨文件的依赖关系——脚本的加载顺序完全依赖 HTML 中的 script 标签排列。

### CommonJS

Node.js 推出的 CommonJS 规范是第一个被广泛采用的模块系统：

```js
// 导出
module.exports = { foo: 'bar' };

// 或逐个导出
exports.baz = function() {};

// 导入
const lib = require('./lib');
const { baz } = require('./lib');
```

CommonJS 采用同步加载模型，天然适配服务端文件系统环境。它的 `require` 是一个运行时函数调用，意味着导入的路径可以是动态表达式。

### AMD

AMD（Asynchronous Module Definition）由 RequireJS 社区推动，专为浏览器异步加载场景设计：

```js
// 定义模块
define(['dependency1', 'dependency2'], function(dep1, dep2) {
  return {
    method: function() {}
  };
});

// 使用模块
require(['myModule'], function(myModule) {
  myModule.method();
});
```

AMD 在浏览器环境中曾有一定影响力，但随着打包工具链的成熟，逐渐退出主流。

### ES Modules

ES2015（ES6）正式引入了语言层面的模块系统，即 ES Modules（ESM）：

```ts
// 具名导出
export const PI = 3.14159;
export function add(a: number, b: number): number {
  return a + b;
}

// 默认导出
export default class Calculator {}

// 导入
import Calculator, { PI, add } from './math';
```

ESM 的关键特性是**静态结构**：import 和 export 语句必须在顶层，编译器可以在不执行代码的情况下分析模块依赖图。这为 tree-shaking、静态分析和 IDE 智能提示提供了基础。

### TypeScript 在演进中的定位

TypeScript 的独特之处在于它同时支持上述所有模块格式，并额外提供了 namespace 语法：

| 格式 | 编译器支持 | tsconfig 配置 | 适用场景 |
|------|-----------|---------------|---------|
| CommonJS | 完整 | module: commonjs | Node.js 后端项目 |
| AMD | 完整 | module: amd | 遗留浏览器项目 |
| ES Modules | 完整 | module: esnext/es2020+ | 现代前端项目 |
| SystemJS | 完整 | module: system | 特殊运行时需求 |
| Namespace | 完整 | 默认可用 | 类型声明、全局扩展 |

## ES Modules：现代推荐的模块方案

ES Modules 应作为新项目的默认选择。TypeScript 对 ESM 提供了全面的类型安全和增强支持。

### 默认导出与具名导出

```ts
// ===== utils.ts =====

// 具名导出 — 推荐，支持 tree-shaking 且语义明确
export const VERSION = '1.0.0';
export interface Config {
  debug: boolean;
  timeout: number;
}
export function normalize(input: string): string {
  return input.trim().toLowerCase();
}

// 默认导出 — 适用于单职责模块的主输出
export default class Logger {
  constructor(private prefix: string) {}
  log(msg: string): void {
    console.log(`[${this.prefix}] ${msg}`);
  }
}
```

```ts
// ===== consumer.ts =====

// 具名导入
import { VERSION, normalize, type Config } from './utils';

// 默认导入 — 名称可以任意指定
import AppLogger from './utils';

// 混合使用
import Logger, { VERSION, normalize } from './utils';
```

**实践建议**：优先使用具名导出。默认导出虽然灵活，但在重构时会增加追踪成本——IDE 无法像具名导入那样精确地跳转到定义位置。

### 重导出（Re-export）

重导出用于构建统一出口文件（barrel file），对外暴露精心设计的 API 边界：

```ts
// ===== index.ts (barrel file) =====

// 逐一重导出
export { Config, normalize } from './config';
export { Logger } from './logger';
export { parse, stringify } from './serializer';

// 全部重导出（谨慎使用，会暴露内部细节）
export * from './internal-utils';

// 重导出并改名
export { format as formatDate } from './date-utils';

// 重导出默认导出为具名
export { default as HttpService } from './http';
```

Barrel file 是库项目组织公共 API 的标准模式，但需要注意它可能阻碍某些 bundler 的 tree-shaking 优化。

### 动态 import()

动态 import 是 ESM 规范中唯一的运行时加载机制，返回 Promise：

```ts
async function loadAdminPanel(): Promise<void> {
  // 代码分割：AdminPanel 及其依赖会被打包为独立 chunk
  const { AdminPanel } = await import('./admin/AdminPanel');

  const panel = new AdminPanel(document.getElementById('root'));
  panel.render();
}

// 结合 React.lazy 使用
const Chart = React.lazy(() =>
  import('./charts/Chart').then(m => ({ default: m.Chart }))
);
```

动态 import 的核心价值在于**按需加载**：只有在函数实际执行时才会触发网络请求和代码解析，这对大型应用的性能至关重要。

### 类型专用导入导出

TypeScript 提供了纯类型的导入导出语法，确保这些声明在编译后被完全擦除，不产生任何 JavaScript 运行时代码：

```ts
// ===== types.ts =====

// 仅导出类型
export type Result<T> =
  | { success: true; data: T }
  | { success: false; error: string };

export interface RequestOptions {
  method?: string;
  headers?: Record<string, string>;
}

export type { Result, RequestOptions };

// ===== consumer.ts =====

// import type — 纯类型导入，编译后消失
import type { Result, RequestOptions } from './types';

// export type — 纯类型导出
export type { Result };

// inline type import — 在同一语句中混合值与类型导入
import { fetchData, type RequestConfig } from './api';
```

启用 `isolatedModules` 和 `verbatimModuleSyntax` 后，TypeScript 会强制要求对仅涉及类型的导入使用 `import type` 语法，这是保证与 Babel/swc 等单文件编译器兼容的关键配置。

### 模块解析策略

`tsconfig.json` 中的 `moduleResolution` 决定编译器如何定位模块文件：

```json
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler"
  }
}
```

三种主要解析策略的差异：

**node**：经典 Node.js 解析规则。查找 `index.ts/index.js`，处理 `.tsx` 扩展名时自动映射到 `.js`，但不支持 ESM 的 `exports` 字段条件导出。适合纯 CommonJS 项目或向后兼容场景。

**nodenext / node16**：完整实现 Node.js ESM 支持。区分 ESM 和 CJS 边界，严格遵循 `package.json` 中 `"type": "module"` 声明。最严格但也最容易因配置不当报错。

**bundler**：为 Vite、Webpack、esbuild 等打包工具优化。允许 ESM 语法导入 CJS 包（如 `import _ from 'lodash'`），支持 `exports` 条件解析但放宽部分限制。**大多数现代前端项目的最佳选择**。

### 路径映射（Path Mapping）

当项目目录层级较深时，相对路径导入会变得冗长且脆弱：

```ts
// 不推荐
import { UserService } from '../../../../../../core/services/UserService';
```

通过 `tsconfig.json` 的 paths 配置创建路径别名：

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@core/*": ["packages/core/src/*"],
      "@shared/*": ["src/shared/*"],
      "@/types/*": ["src/types/*"]
    }
  }
}
```

```ts
// 清晰且稳定
import { UserService } from '@core/services/UserService';
import type { ApiResponse } from '@/types/api';
```

注意：paths 只是 TypeScript 编译时的映射，不影响运行时。打包工具需要额外配置（Vite 的 resolve.alias，Webpack 的 resolve.alias）来同步这一映射。

## Namespace：历史遗留但有特定价值

Namespace 是 TypeScript 早期（ES Modules 尚未普及之前）引入的代码组织机制。虽然在绝大多数新项目中应优先使用 ESM，但它在特定场景下仍有不可替代的作用。

### 基本语法

```ts
namespace Geometry {
  // 未导出的成员仅在 namespace 内部可见
  const EPSILON = 0.000001;

  // 导出的成员可通过 Geometry.xxx 访问
  export interface Point {
    x: number;
    y: number;
  }

  export class Vector implements Point {
    constructor(public x: number, public y: number) {}

    magnitude(): number {
      return Math.sqrt(this.x ** 2 + this.y ** 2);
    }

    normalize(): Vector {
      const m = this.magnitude();
      if (m < EPSILON) return new Vector(0, 0);
      return new Vector(this.x / m, this.y / m);
    }

    static fromPoints(a: Point, b: Point): Vector {
      return new Vector(b.x - a.x, b.y - a.y);
    }
  }

  export function distance(a: Point, b: Point): number {
    const v = Vector.fromPoints(a, b);
    return v.magnitude();
  }

  // 嵌套 namespace
  export namespace Transform {
    export function translate(point: Point, dx: number, dy: number): Point {
      return { x: point.x + dx, y: point.y + dy };
    }

    export function rotate(
      point: Point,
      origin: Point,
      radians: number
    ): Point {
      const cos = Math.cos(radians);
      const sin = Math.sin(radians);
      const px = point.x - origin.x;
      const py = point.y - origin.y;
      return {
        x: origin.x + px * cos - py * sin,
        y: origin.y + px * sin + py * cos
      };
    }
  }
}

// 使用
const p1: Geometry.Point = { x: 0, y: 0 };
const p2: Geometry.Point = { x: 3, y: 4 };
console.log(Geometry.distance(p1, p2)); // 5

const shifted = Geometry.Transform.translate(p1, 10, 20);
```

### 嵌套命名空间与点号访问

嵌套 namespace 支持通过点号路径直接引用，也可以用简写语法一次性声明：

```ts
// 层级声明
namespace A {
  export namespace B {
    export namespace C {
      export const value = 42;
    }
  }
}

// 简写语法 —— 等价于上面的嵌套声明
namespace A.B.C {
  export const value = 42;
}

console.log(A.B.C.value); // 42
```

### 编译输出：Namespace 与 IIFE

Namespace 的本质是一个立即执行的函数表达式（IIFE），将所有内容包裹在闭包中以隔离作用域：

```ts
// TypeScript 源码
namespace Utils {
  const secret = 'internal';

  export function publicFn(): string {
    return secret;
  }
}
```

编译为 JavaScript 后（假设 target 为 ES5）：

```js
var Utils;
(function(Utils) {
  var secret = 'internal';
  function publicFn() { return secret; }
  Utils.publicFn = publicFn;
})(Utils || (Utils = {}));
```

未导出的变量（如 `secret`）成为闭包内的局部变量，外部无法直接访问；导出的成员则挂载到命名空间对象上。这与手动编写 IIFE 的效果一致，但由编译器自动化完成。

### 何时仍然需要 Namespace

尽管 ESM 已成为绝对主流，以下场景中 Namespace 仍是合理选择：

#### 定义全局类型（.d.ts 声明文件）

```ts
// global-types.d.ts
declare namespace MyApp {
  interface User {
    id: string;
    name: string;
    email: string;
  }

  interface ApiError {
    code: number;
    message: string;
    details?: unknown[];
  }

  type Role = 'admin' | 'editor' | 'viewer';
}
```

#### 与旧版 JS 库交互

当对接未提供类型声明的全局变量库时：

```ts
// legacy-lib.d.ts
declare namespace LegacyChart {
  interface Options {
    width: number;
    height: number;
    theme?: 'light' | 'dark';
  }

  function init(selector: string, options?: Options): void;
  function destroy(selector: string): void;

  // 声明该全局变量存在
}

declare var LegacyChart: typeof LegacyChart;
```

#### 组织相关类型和常量

当一组类型和常量逻辑上紧密关联，但不需要独立的运行时模块时：

```ts
namespace HttpStatus {
  export const OK = 200;
  export const Created = 201;
  export const BadRequest = 400;
  export const Unauthorized = 401;
  export const NotFound = 404;
  export const InternalError = 500;

  export function isSuccess(code: number): boolean {
    return code >= 200 && code < 300;
  }

  export function isClientError(code: number): boolean {
    return code >= 400 && code < 500;
  }

  export type Code = typeof OK | typeof Created | typeof NotFound; // ...
}
```

#### DOM 操作库的全局扩展

```ts
// jquery-extensions.d.ts
declare namespace JQuery {
  interface TooltipOptions {
    content: string;
    position?: 'top' | 'bottom' | 'left' | 'right';
  }

  interface AjaxSetup {
    csrfToken?: string;
    retryCount?: number;
  }

  function tooltip(options: TooltipSettings): JQuery;
}
```

### 何时不应使用 Namespace

以下情况应坚决选择 ESM 而非 Namespace：

- **任何新业务代码**：应用逻辑、组件、工具函数等全部使用 ESM
- **库的公共 API**：发布给消费者使用的接口应采用 ESM 格式
- **需要 tree-shaking 的场景**：Namespace 编译为 IIFE 后，bundler 无法安全地消除未使用的导出
- **需要动态加载的模块**：Namespace 不支持按需加载

简单判断准则：如果代码需要在运行时被独立加载或排除，使用 Module；如果代码仅存在于编译期（类型声明），Namespace 是可选方案之一。

## Module 与 Namespace 核心对比

| 维度 | Module (ESM) | Namespace |
|------|-------------|-----------|
| **作用域边界** | 文件级别，每个文件即一个模块 | 代码块级别，可在单个文件内定义多个 |
| **加载方式** | 静态分析确定依赖；支持动态 import() 运行时加载 | 编译为 IIFE 或合并到全局对象，无独立加载能力 |
| **依赖管理** | 显式 import 声明，缺少依赖会导致编译错误 | 隐式依赖全局上下文，无编译期依赖检查 |
| **Tree-shaking** | 静态结构使 bundler 可安全消除未使用导出 | IIFE 包裹导致跨模块内联困难，优化受限 |
| **适用场景** | 绝大多数业务代码和库开发 | d.ts 类型声明、全局增强、遗留代码适配 |
| **编译输出** | 保持模块化结构（import/export 或 require） | 合并为闭包或挂载到全局对象 |
| **循环依赖** | 可检测（取决于解析策略），允许有限形式的循环引用 | 同一 namespace 内无此问题；跨 namespace 合并时行为复杂 |
| **类型擦除** | `import type` 可确保纯类型导入编译后消失 | 整个 namespace 可能因包含值而被保留 |

从架构视角看，Module 强调的是**物理隔离**——每个文件有清晰的输入输出契约；Namespace 强调的是**逻辑分组**——相关符号聚合在同一名称下。两者解决的问题域不同，并非简单的替代关系。

## 声明文件中的 Namespace 用法

`.d.ts` 文件是 Namespace 最活跃的应用舞台。掌握其模式对于阅读和理解第三方类型声明至关重要。

### .d.ts 文件基本结构

声明文件只包含类型信息，不含实现代码：

```ts
// my-library.d.ts

// 声明一个全局变量及其类型
declare var version: string;

// 声明一个全局函数
declare function init(config?: InitConfig): void;

// 声明一个全局类
declare class Factory<T> {
  create(): T;
  static getInstance(): Factory<any>;
}

// 声明一个 namespace（通常对应一个全局对象）
declare namespace MyLibrary {
  interface Options {
    debug?: boolean;
    locale?: string;
  }

  const DEFAULT_OPTIONS: Options;

  function configure(opts: Options): void;
  function getVersion(): string;
}
```

### declare global + namespace 扩展全局对象

当需要向已有的全局对象添加属性时，结合 `declare global` 与 namespace 合并：

```ts
// extensions.d.ts

// 扩展 Window 接口
declare global {
  interface Window {
    __APP_CONFIG__: AppConfig;
    __INITIAL_STATE__: Record<string, unknown>;

    // 自定义全局方法
    notify(message: string, level?: 'info' | 'warn' | 'error'): void;
  }

  interface NodeJS {
    ProcessEnv: ProcessEnv & {
      CUSTOM_API_KEY: string;
      FEATURE_FLAGS: string;
    };
  }
}

// 使当前文件成为全局脚本（非模块）
export {};
```

关键点：文件末尾的 `export {}` 将文件标记为模块，从而激活 `declare global` 的增强作用域。若文件中没有任何 import 或 export，整个文件被视为全局脚本，此时 `interface Window {}` 直接生效无需 `declare global` 包裹。

### 为 jQuery 插件写类型声明

jQuery 生态系统大量使用 namespace 来扩展原型方法：

```ts
// jquery-plugins.d.ts

/// <reference types="jquery" />

interface JQuery {
  // 插件方法 1：模态框
  modal(options?: ModalOptions): JQuery;
  modal(command: 'show' | 'hide' | 'toggle'): JQuery;

  // 插件方法 2：表单验证
  validate(rules: ValidationRule[]): JQuery;
  validate(command: 'isValid'): boolean;

  // 插件方法 3：数据表格
  dataTable(settings?: DataTableSettings): DataTableApi;
}

// 相关的类型定义放在对应的 namespace 中
namespace ModalOptions {
  export interface Base {
    title: string;
    closable?: boolean;
  }

  export interface AlertModal extends Base {
    message: string;
    onConfirm?(): void;
  }

  export interface ConfirmModal extends Base {
    message: string;
    onOk(): void;
    onCancel?(): void;
  }
}
```

这种声明利用了 TypeScript 的**声明合并**（Declaration Merging）机制：同名的 interface 声明会被合并为一个整体。jQuery 类型声明本身已定义基础 `JQuery` 接口，插件只需再次声明同名接口并添加新方法即可扩展。

### Ambient Module Declaration

为没有类型信息的第三方模块创建 ambient 声明：

```ts
// declarations.d.ts

// 声明一个模块及其导出
declare module 'some-untyped-library' {
  export function main(input: string): Promise<Result[]>;

  export namespace Helpers {
    function sanitize(s: string): string;
    function parseJSON<T>(raw: string): T;
  }
}

// 通配符模块声明 — 匹配所有 .svg 文件的导入
declare module '*.svg' {
  const content: string;
  export default content;
}

// CSS 模块声明
declare module '*.module.css' {
  const classes: Record<string, string>;
  export default classes;
}

// 模板声明
declare module '*.hbs' {
  export default function template(context: object): string;
}
```

## 命名空间的进阶用法

### 跨文件合并 Namespace

多个文件中的同名 namespace 会在编译时自动合并：

```ts
// models/User.ts
namespace Models {
  export interface User {
    id: string;
    name: string;
  }
}

// models/Product.ts
namespace Models {
  export interface Product {
    sku: string;
    price: number;
  }
}

// consumer.ts —— 可以同时访问两个文件中的成员
import './models/User';
import './models/Product';

const u: Models.User = { id: '1', name: 'Alice' };
const p: Models.Product = { sku: 'A100', price: 99.9 };
```

注意：要使跨文件 namespace 合并生效，必须确保这些文件被包含在编译范围内（通过 import 引用或在 tsconfig.json 的 include 中列出）。否则每个文件中的 namespace 是独立的，不会发生合并。

### export 与不 export 的区别

namespace 内部的可见性规则类似于类的 public/private：

```ts
namespace InternalAPI {
  // 私有 —— 外部不可见
  const BASE_URL = 'https://api.example.com';
  const CACHE_TTL = 3600000;

  // 私有辅助函数
  function buildHeaders(authToken: string): HeadersInit {
    return {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${authToken}`
    };
  }

  // 公共接口
  export async function fetchUser(id: string, token: string): Promise<User> {
    const response = await fetch(`${BASE_URL}/users/${id}`, {
      headers: buildHeaders(token)
    });
    return response.json();
  }

  export async function fetchProducts(
    category?: string
  ): Promise<Product[]> {
    const url = category ? `${BASE_URL}/products?cat=${category}` : `${BASE_URL}/products`;
    const response = await fetch(url);
    return response.json();
  }
}
```

这种封装模式在 namespace 中很自然，但在 ESM 中可以通过不 export 相应绑定来实现相同效果。区别在于 namespace 将私有和公共成员集中在同一个代码块中，而 ESM 的私有性体现在文件层面。

### Namespace 与枚举的配合

Enum 与 namespace 可以组合使用，为枚举附加方法和元数据：

```ts
enum Direction {
  Up,
  Down,
  Left,
  Right
}

namespace Direction {
  // 为枚举添加反向查找
  const _labels: Record<Direction, string> = {
    [Direction.Up]: '向上',
    [Direction.Down]: '向下',
    [Direction.Left]: '向左',
    [Direction.Right]: '向右'
  };

  export function label(dir: Direction): string {
    return _labels[dir];
  }

  export function opposite(dir: Direction): Direction {
    switch (dir) {
      case Direction.Up: return Direction.Down;
      case Direction.Down: return Direction.Up;
      case Direction.Left: return Direction.Right;
      case Direction.Right: return Direction.Left;
    }
  }

  export function* allDirections(): Generator<Direction> {
    yield Direction.Up;
    yield Direction.Down;
    yield Direction.Left;
    yield Direction.Right;
  }

  export const vectors: Record<Direction, [number, number]> = {
    [Direction.Up]: [0, -1],
    [Direction.Down]: [0, 1],
    [Direction.Left]: [-1, 0],
    [Direction.Right]: [1, 0]
  };
}

// 使用
const dir = Direction.Up;
console.log(Direction.label(dir));       // '向上'
console.log(Direction.opposite(dir));     // Direction.Down (1)
console.log(Direction.vectors[dir]);      // [0, -1]
```

这种 enum + namespace 组合是 TypeScript 中常见的"富枚举"模式，编译后会生成一个完整的方向操作工具集。

### Namespace 作为类型组织容器

在大型项目中，可以用 namespace 对类型进行逻辑分组，避免过多顶层类型污染：

```ts
namespace Schema {
  // 用户相关
  export namespace User {
    export interface CreateInput {
      name: string;
      email: string;
      password: string;
    }
    export interface Output {
      id: string;
      name: string;
      email: string;
      createdAt: Date;
    }
  }

  // 订单相关
  export namespace Order {
    export interface Item {
      productId: string;
      quantity: number;
      unitPrice: number;
    }
    export interface CreateInput {
      items: Item[];
      shippingAddressId: string;
    }
    export interface Output extends CreateInput {
      id: string;
      status: OrderStatus;
      total: number;
    }
  }

  export type OrderStatus =
    | 'pending'
    | 'confirmed'
    | 'shipped'
    | 'delivered'
    | 'cancelled';
}

// 使用时路径清晰
type UserInput = Schema.User.CreateInput;
type OrderOutput = Schema.Order.Output;
```

## 三斜线指令（Triple-Slash Directives）

三斜线指令是 TypeScript 特有的编译器指令，以 `///` 开头，出现在文件最顶部（仅在 `/// <reference types="...">` 时可出现在其他声明之后）。

### reference path

指示编译器在处理当前文件前先包含另一个文件，主要用于非模块化脚本之间的依赖声明：

```ts
/// <reference path="./types.ts" />
/// <reference path="./constants.ts" />

// 现在可以使用 types.ts 和 constants.ts 中的声明
```

在现代 ESM 项目中，`reference path` 几乎已被 `import` 语句完全取代。它仅在处理纯 `.d.ts` 声明文件链时偶有出现。

### reference types

声明对某个 `@types` 包的依赖，等同于在 tsconfig.json 的 `types` 字段中添加对应条目：

```ts
/// <reference types="node" />
/// <reference types="jest" />

// 现在可以使用 node 和 jest 的全局类型
import { readFileSync } from 'fs';          // 来自 @types/node
describe('suite', () => {                   // 来自 @types/jest
  it('test', () => {});
});
```

当项目使用了 `skipLibCheck: true` 或 `types: []` （空数组禁用自动包含）时，`reference types` 成为选择性引入特定类型包的唯一方式。

### reference lib

注入内置的 lib 文件（如 ES 特性、DOM API）：

```ts
/// <reference lib="es2022" />
/// <reference lib="dom" />
/// <reference lib="dom.iterable" />

// 现在可以使用 ES2022 新特性和完整 DOM API
const controller = new AbortController();        // DOM
const weakRef = new WeakRef({});                 // es2021+
for (const entry of document.querySelectorAll('div')) { // dom.iterable
  // ...
}
```

这在编写通用库的声明文件时很有用——可以精确控制需要的内置 API 范围，而不依赖 tsconfig.json 的 lib 设置。

### 现代项目中的使用时机

| 场景 | 是否仍需三斜线指令 | 替代方案 |
|------|------------------|---------|
| .ts/.tsx 源文件间的依赖 | 否 | `import` 语句 |
| .d.ts 声明文件间的前后顺序 | 有时需要 | `reference path` 或整理为 barrel file |
| 选择性引入 @types 包 | 是 | `reference types` 或 tsconfig types 字段 |
| 声明文件指定 lib 范围 | 是 | `reference lib` |
| npm 包的类型声明 | 否 | package.json 的 types/typings 字段 |

## 模块的常见陷阱与调试

### Cannot find module 错误排查清单

这是 TypeScript 开发中最常见的错误之一。系统化排查步骤：

1. **确认文件确实存在**：检查路径大小写和拼写。Windows 文件系统不区分大小写，但 TypeScript 模块解析区分。
2. **确认文件扩展名**：`.ts` 导入 `.tsx` 时需显式写出扩展名（除非使用 bundler 解析）；`.d.ts` 通常不需要显式扩展名。
3. **检查 moduleResolution 设置**：
   - `node` 模式下不支持 `package.json` 的 `exports` 字段
   - `nodenext` 要求严格的 ESM/CJS 边界
   - 大多数情况下 `bundler` 最宽容
4. **验证 include/exclude 配置**：目标文件是否在 tsconfig.json 的扫描范围内？
5. **检查 paths 映射**：如果使用了路径别名，确认 tsconfig 和打包工具的配置同步。
6. **查看 package.json**：目标包是否有 `types` / `typings` 字段指向正确的声明文件？

### moduleResolution 设置不当的影响

错误的 moduleResolution 选项可能导致一系列隐蔽问题：

```jsonc
// 问题配置：moduleResolution: "node" 但 module: "esnext"
// 结果：无法正确解析 ESM-only 包的 exports 字段
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "node",  // ⚠️ 不匹配
  }
}
```

推荐的组合方式：

```jsonc
// 方案 A：Node.js 后端
{ "module": "nodenext", "moduleResolution": "nodenext" }

// 方案 B：现代前端（使用 Vite/Webpack/Rollup）
{ "module": "esnext", "moduleResolution": "bundler" }

// 方案 C：向后兼容 CJS 库
{ "module": "commonjs", "moduleResolution": "node" }
```

### 不同文件类型的模块解析差异

| 文件类型 | 是否被视为模块 | 导出方式 | 导入方式 |
|---------|--------------|---------|---------|
| `.ts` | 有 import/export 则是 | export / export default | import |
| `.tsx` | 同上，且支持 JSX | 同上 | 同上 |
| `.d.ts` | 同上，仅含类型 | declare export | import type |
| `.js` / `.jsx` | 取决于 allowJs | 同上 | 同上 |
| `.mts` / `.cts` | 始终是 ESM / CJS | 标准 ESM / CJS | 标准 ESM / CJS |

一个常见混淆点：即使 `.d.ts` 文件中没有实际的 `import` 语句，只要包含 `export` 声明，它就是一个环境模块声明（ambient module declaration），而非全局脚本。

### 循环依赖的检测和处理

TypeScript 本身不会阻止循环依赖，但某些 moduleResolution 模式下会产生警告。循环依赖的危害在于运行时行为的不确定性：

```ts
// a.ts
import { funcB } from './b';
export function funcA(): string {
  return funcB(); // b 中的 funcB 可能尚未初始化完毕
}

// b.ts
import { funcA } from './a';
export function funcB(): string {
  return funcA();
}
```

应对策略：

1. **提取共享层**：将循环依赖的部分抽取到第三个模块 c.ts，a 和 b 都依赖 c
2. **延迟引用**：将其中一个依赖改为动态 import()
3. **依赖注入**：通过参数传递而非直接 import
4. **重构为单向依赖**：审视架构设计，真正的循环依赖往往是设计问题的信号

### any 类型污染模块边界的风险

当一个模块的导出包含 `any` 类型时，它会像病毒一样传播到所有消费方：

```ts
// untyped-dep.ts
// 第三方库缺少完善类型
export function process(data: any): any {
  return JSON.parse(data);
}

// consumer.ts —— 类型安全荡然无存
import { process } from './untyped-dep';

const result = process(someInput);         // result 的类型是 any
result.nonExistentMethod().prop.foo.bar;    // 不报错！
```

防护措施：

```ts
// 方案 1：包装函数收窄类型
function safeProcess(input: string): ProcessedData {
  return process(input) as ProcessedData;
}

// 方案 2：为第三方库补充类型声明
// third-party.d.ts
declare module 'untyped-dep' {
  interface ProcessedData {
    status: string;
    payload: Record<string, unknown>;
  }
  function process(data: string): ProcessedData;
  export { process };
}

// 方案 3：开启 noImplicitAny 并配合 eslint 的 @typescript-eslint/no-explicit-any
```

│   └── events.ts              # 事件总线

│   ├── auth/
│   │   ├── index.ts           # auth 模块的公共 API
│   │   ├── types.ts           # auth 专属类型
│   │   ├── services/
│   │   └── components/        # UI 组件（如果是前端）
│   ├── dashboard/
│   │   ├── index.ts
│   │   └── ...
│   └── settings/
├── shared/                    # 跨功能共享代码

关键原则：

- **入口点最小化**：main.ts 只负责组装和启动

## 总结与迁移指南

### 从 Namespace 到 ESM 的迁移步骤

对于仍在使用 namespace 的存量代码，迁移路径清晰：

1. **识别所有 namespace 声明**：全局搜索 `namespace` 关键字
2. **评估每个 namespace 的用途**：
   - 若位于 `.d.ts` 文件中用于类型声明 → **保留**
   - 若位于 `.ts` 文件中包含运行时逻辑 → **迁移**
3. **拆分迁移**：将每个 namespace 的内容移至独立文件，改用 export/import
4. **更新所有引用点**：将 `Namespace.Member` 形式的访问改为 import 后的直接使用
5. **调整 tsconfig**：确保 moduleResolution 与新的模块格式匹配
6. **逐步验证**：每次迁移一个 namespace 后运行测试套件

示例：

```ts
// 迁移前
namespace ValidationRules {
  const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

  export function isEmail(value: string): boolean {
    return EMAIL_REGEX.test(value);
  }

  export function isRequired(value: unknown): value is string {
    return typeof value === 'string' && value.trim().length > 0;
  }
}

// 使用
ValidationRules.isEmail(user.email);

// ===== 迁移后 =====
// validation-rules.ts
const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

export function isEmail(value: string): boolean {
  return EMAIL_REGEX.test(value);
}

export function isRequired(value: unknown): value is string {
  return typeof value === 'string' && value.trim().length > 0;
}

// 使用
import { isEmail } from './validation-rules';
isEmail(user.email);
```

### 新项目的模块策略建议

决策流程如下：

```
开始
 │
 ├─ 编写运行时代码？
 │   ├─ 是 → 使用 ES Modules (import/export)
 │   │       ├─ 需要按需加载？ → dynamic import()
 │   │       ├─ 仅涉及类型？ → import type / export type
 │   │       └─ 组织公共 API？ → barrel file (index.ts)
 │   │
 │   └─ 否（仅类型声明）
 │       ├─ 扩展全局对象？ → declare global + interface 合并
 │       ├─ 为第三方库补类型？ → declare module / declare namespace
 │       ├─ 组织相关类型？ → namespace 或独立 type 文件
 │       └─ 写 .d.ts 声明？ → 三斜线指令 + declare 系列
 │
 └─ 结束
```

核心原则总结：

1. **ESM 优先**：一切运行时代码都应使用 ES Modules
2. **Namespace 定位明确**：它是类型声明和全局增强的工具，不是日常编码的组织手段
3. **声明文件是 Namespace 的主战场**：`.d.ts` 之外尽量不用
4. **配置决定行为**：`module`、`moduleResolution`、`verbatimModuleSyntax` 三者协同影响模块处理方式
5. **保持一致性**：项目内统一使用一种主要的模块风格，避免 ESM 和 namespace 混用造成认知负担
