## 什么是声明合并

声明合并（Declaration Merging）是 TypeScript 编译器的一项核心机制：**当编译器遇到多个同名的声明时，会将它们合并为一个定义**。这与 JavaScript 中"重复声明会报错"的行为截然不同——TypeScript 有意设计了这个机制，使其成为扩展类型、组织代码的强大工具。

```typescript
interface Box {
  width: number;
}

// 同名接口不会报错，而是与上面的接口合并
interface Box {
  height: number;
}

// 合并后的结果等同于：
// interface Box {
//   width: number;
//   height: number;
// }

const box: Box = { width: 100, height: 200 }; // ✅
```

### 核心价值

- **扩展已有类型**：无需修改原始源码即可为类型添加新成员
- **为第三方库补充类型**：为缺少完整类型声明的库编写补丁
- **组织大型代码库**：将一个大的类型拆分到多个文件中按功能维护

### 与普通重复声明报错的区别

TypeScript 中并非所有同名声明都会触发合并。只有以下几种声明支持合并：

| 支持合并的声明 | 不支持合并的声明 |
|---|---|
| interface | let / const / var |
| namespace (module) | class |
| enum | function |
| class + 同名 namespace | type alias |
| function + 同名 namespace | |
| enum + 同名 namespace | |

```typescript
let x = 1;
let x = 2; // ❌ 无法重新声明块范围变量 "x"

function foo() {}
function foo() {} // ❌ 无法重新声明函数 "x"
```

## 接口合并

接口合并是声明合并中使用频率最高的形式。TypeScript 允许在同一个作用域内定义多个同名的接口，编译器自动将其成员合并。

### 基本语法

```typescript
interface User {
  id: string;
  name: string;
}

interface User {
  email: string;
  age?: number; // 可选属性可以新增
}

const user: User = {
  id: 'u1',
  name: '张三',
  email: 'zhangsan@example.com',
}; // ✅ 完整包含两个接口的所有成员
```

### 非函数成员合并规则

非函数成员按**字段名称**进行合并。当多个接口声明了同名字段时，字段的类型必须兼容：

```typescript
interface Config {
  host: string;
  port: number;
}

interface Config {
  timeout: number;
  // host: number; // ❌ 后续属性的类型必须与其初始声明一致或为其超类型
}

// ✅ 正确做法：使用更宽泛的超类型
interface Config {
  host: string | number; // string 是 string | number 的子类型，兼容
}
```

**关键规则**：后出现的声明中的同名字段类型必须是先出现类型的**超类型**。这是因为第一个声明被视为"基础契约"，后续声明只能放宽约束、不能收紧约束。

### 函数成员合并为重载

当多个接口声明了同名函数时，这些签名会被合并为一个**重载组**。这里有一个重要的特殊规则：

```typescript
interface Document {
  createElement(tagName: 'div'): HTMLDivElement;
  createElement(tagName: 'span'): HTMLSpanElement;
  createElement(tagName: string): HTMLElement;
}
// 合并后的重载顺序就是上面代码的书写顺序
```

**特殊规则——重载顺序反转**：

当函数签名分布在多个接口声明中时，**后声明的接口中的重载会出现在最终重载列表的前面**。这个设计是为了让后续的声明能够提供更具体的类型推断优先级：

```typescript
interface Responder {
  respond(): void;
  respond(x: string): void;
  respond(x: number): void;
}

interface Responder {
  respond(x: boolean): void;     // 这个重载会在最前面
  respond(x: { msg: string }): void; // 然后是这一个
}
```

最终的重载顺序为：

```typescript
// 编译器实际生成的重载列表：
respond(x: { msg: string }): void;   // 来自第二个接口
respond(x: boolean): void;           // 来自第二个接口
respond(): void;                     // 来自第一个接口
respond(x: string): void;            // 来自第一个接口
respond(x: number): void;            // 来自第一个接口
```

这意味着**后声明的接口有机会"插队"到重载列表前面**，在实际调用时会优先匹配这些更精确的签名。这是有意为之的设计，使得补丁声明能够覆盖默认行为。

### 跨文件接口合并

只要处于相同的命名空间或模块作用域下，不同文件中的同名接口也会自动合并：

```typescript
// types/base.ts
export interface ApiResponse<T> {
  code: number;
  data: T;
}

// types/pagination.ts —— 在同一模块系统中
export interface ApiResponse<T> {
  page?: number;
  pageSize?: number;
  total?: number;
}

// 使用时，ApiResponse 同时具备基础和分页字段
const response: ApiResponse<User[]> = {
  code: 200,
  data: [],
  page: 1,
  total: 100,
};
```

### 实际应用场景

#### 为第三方库的类型做增量补丁

当第三方库的类型声明不完整时，可以用接口合并在不修改 node_modules 的前提下补充缺失的字段：

```typescript
// types/third-party-patch.d.ts
import 'some-library';

declare module 'some-library' {
  interface LibraryOptions {
    // 补充官方遗漏的自定义配置项
    customRetryCount?: number;
    enableDebugLog?: boolean;
  }
}
```

#### 按功能拆分大型接口定义

```typescript
// user/core.ts
export interface User {
  id: string;
  name: string;
  email: string;
}

// user/auth.ts
export interface User {
  passwordHash: string;
  lastLoginAt: Date;
  role: 'admin' | 'member';
}

// user/profile.ts
export interface User {
  avatarUrl?: string;
  bio?: string;
  socialLinks?: SocialLink[];
}
```

每个文件只关注自己负责的功能域，最终使用时获得完整的 User 类型。

#### 插件系统中的类型扩展

插件架构的核心需求之一是允许插件向核心类型注入新的能力：

```typescript
// core/types.ts
export interface PluginContext {
  app: Application;
  config: Record<string, unknown>;
}

// plugin-a/types.ts —— plugin-a 扩展上下文
export interface PluginContext {
  featureAConfig: FeatureAOptions;
  invokeFeatureA(): Promise<Result>;
}
```

## 命名空间合并

命名空间（namespace）也支持同名合并。与接口合并不同的是，namespace 合并的是其**导出的成员**。

### 基本 namespace 合并

```typescript
namespace ValidationRules {
  export const required = (v: unknown) => v != null;
  export const minLength = (n: number) => (v: string) => v.length >= n;
}

namespace ValidationRules {
  export const maxLength = (n: number) => (v: string) => v.length <= n;
  export const pattern = (re: RegExp) => (v: string) => re.test(v);
}

// 合并后同时拥有四个导出
ValidationRules.required('');
ValidationRules.minLength(3)('abc');
ValidationRules.maxLength(10)('abc');
ValidationRules.pattern(/^\d+$/)('123');
```

### namespace 与其他声明的合并

这是命名空间合并中最强大的模式——namespace 可以与 class、function、enum 进行合并，从而为这些值添加额外的静态成员。

#### class + 同名 namespace

这种模式常用于将类的**内部类型和辅助方法**从类定义本身分离出去，保持类体的简洁性：

```typescript
class Album {
  label: Album.AlbumInfo;

  constructor(info: Album.AlbumInfo) {
    this.label = info;
  }

  display() {
    return `${this.label.title} - ${this.label.artist}`;
  }
}

namespace Album {
  export interface AlbumInfo {
    title: string;
    artist: string;
    year: number;
    genre: string;
  }

  export const GENRES = ['Rock', 'Jazz', 'Classical', 'Pop'] as const;

  export function create(title: string, artist: string, year: number, genre: string): Album {
    return new Album({ title, artist, year, genre });
  }

  export function isClassic(album: Album): boolean {
    return album.label.year < 1990;
  }
}

// 使用
const album = Album.create('Abbey Road', 'The Beatles', 1969, 'Rock');
console.log(Album.isClassic(album)); // true

// 类型也可以通过命名空间访问
const info: Album.AlbumInfo = {
  title: 'Kind of Blue',
  artist: 'Miles Davis',
  year: 1959,
  genre: 'Jazz',
};
```

`Album.AlbumInfo` 这种嵌套写法清晰表达了"AlbumInfo 属于 Album 语义域"的关系，比顶层单独定义一个 `AlbumInfo` 接口更具可读性和组织性。

#### function + 同名 namespace

这种模式是 jQuery 等经典库的核心实现方式——让函数同时作为可调用对象和属性容器：

```typescript
function $(selector: string): ElementList;
function $(el: Element): ElementList;
function $(fn: () => void): void;

// 重载实现
function $(arg: string | Element | (() => void)): any {
  if (typeof arg === 'function') {
    document.addEventListener('DOMContentLoaded', arg);
    return;
  }
  if (typeof arg === 'string') {
    return document.querySelectorAll(arg);
  }
  return [arg];
}

namespace $ {
  export function ajax(url: string, options?: AjaxOptions): Promise<Response> {
    return fetch(url, options as RequestInit);
  }

  export function get(url: string): Promise<Response> {
    return fetch(url);
  }

  export function post(url: string, data: unknown): Promise<Response> {
    return fetch(url, {
      method: 'POST',
      body: JSON.stringify(data),
      headers: { 'Content-Type': 'application/json' },
    });
  }

  export const version = '4.0.0';

  // 内部工具类型
  export interface AjaxOptions {
    method?: string;
    headers?: Record<string, string>;
    timeout?: number;
  }
}
```

这样 `$('div')` 作为函数调用，而 `$.ajax('/api/data')` 则通过命名空间附加的属性访问。两者共用同一个名称 `$`，形成统一 API 入口。

#### enum + 同名 namespace

枚举本身只能包含数值/字符串成员。通过与同名 namespace 合并，可以为枚举附加方法、映射表等：

```typescript
enum HttpStatus {
  Ok = 200,
  Created = 201,
  BadRequest = 400,
  Unauthorized = 401,
  NotFound = 404,
  InternalError = 500,
}

namespace HttpStatus {
  export const isSuccess = (code: HttpStatus): boolean =>
    code >= 200 && code < 300;

  export const isClientError = (code: HttpStatus): boolean =>
    code >= 400 && code < 500;

  export const isServerError = (code: HttpStatus): boolean =>
    code >= 500;

  // 枚举值到描述信息的映射
  const descriptions: Record<HttpStatus, string> = {
    [HttpStatus.Ok]: '请求成功',
    [HttpStatus.Created]: '资源创建成功',
    [HttpStatus.BadRequest]: '请求参数错误',
    [HttpStatus.Unauthorized]: '未授权',
    [HttpStatus.NotFound]: '资源不存在',
    [HttpStatus.InternalError]: '服务器内部错误',
  };

  export const describe = (code: HttpStatus): string =>
    descriptions[code] ?? '未知状态';

  // 分组信息
  export const SUCCESS_CODES = [HttpStatus.Ok, HttpStatus.Created];
  export const CLIENT_ERROR_CODES = [
    HttpStatus.BadRequest,
    HttpStatus.Unauthorized,
    HttpStatus.NotFound,
  ];
}

// 使用
if (HttpStatus.isSuccess(response.status)) {
  console.log(HttpStatus.describe(response.status));
}
```

### 内部模块与外部模块的差异

在非模块文件（没有 import/export 的脚本文件）中，声明合并的作用域是全局的；而在外部模块文件中，声明受限于当前模块：

```typescript
// 全局脚本文件 global-utils.ts （无 import/export）
interface GlobalSettings {
  theme: string;
}

// 同一脚本文件的另一处
interface GlobalSettings {
  language: string;
} // ✅ 自动合并到全局 GlobalSettings
```

```typescript
// 模块文件 my-module.ts （有 import 或 export）
import { something } from './other';

interface LocalInterface {
  a: number;
}

// 另一个模块文件 other.ts 中即使定义同名 LocalInterface
// 也不会发生合并 —— 它们属于不同的模块作用域
```

若要在跨模块场景中进行合并，需要使用后面介绍的 Module Augmentation 机制。

## 用 declare merge 扩展全局类型

利用声明合并扩展全局内置类型是最直观的应用之一。通过在 `.d.ts` 文件中声明与全局类型同名的接口，可以向 Array、String、Window 等注入自定义成员。

### 扩展 Array 接口

```typescript
// types/global.d.ts

interface Array<T> {
  /**
   * 返回最后一个元素，不存在则返回 undefined
   */
  last(): T | undefined;

  /**
   * 按指定字段去重
   */
  distinctBy<K extends keyof T>(key: K): T[];

  /**
   * 将数组按指定大小分块
   */
  chunk(size: number): T[][];
}

// 对应的实现文件 utils/array-extensions.ts
if (!Array.prototype.last) {
  Array.prototype.last = function<T>(this: T[]): T | undefined {
    return this[this.length - 1];
  };
}

if (!Array.prototype.distinctBy) {
  Array.prototype.distinctBy = function<T, K extends keyof T>(
    this: T[],
    key: K
  ): T[] {
    const seen = new Set();
    return this.filter(item => {
      const val = item[key];
      if (seen.has(val)) return false;
      seen.add(val);
      return true;
    });
  };
}
```

使用效果：

```typescript
const nums = [1, 2, 3, 4, 5];
console.log(nums.last()); // 5

const users = [
  { id: 1, name: 'Alice', dept: 'Engineering' },
  { id: 2, name: 'Bob', dept: 'Design' },
  { id: 3, name: 'Alice', dept: 'Marketing' },
];
console.log(users.distinctBy('name')); // 按 name 去重
```

### 扩展 Window 接口

为 Web 项目添加全局运行时属性的类型声明：

```typescript
// types/global.d.ts

interface Window {
  // 全局应用实例
  __APP_CONFIG__: {
    apiBaseUrl: string;
    env: 'development' | 'production' | 'staging';
    version: string;
  };

  // 第三方 SDK 注入的全局对象
  __grecaptcha: {
    execute(siteKey: string, action: { action: string }): Promise<string>;
    render(container: string, params: object): string;
  };

  // 自定义事件总线
  __eventBus: {
    on(event: string, handler: (...args: any[]) => void): void;
    emit(event: string, ...args: any[]): void;
    off(event: string, handler: (...args: any[]) => void): void;
  };

  // 初始化钩子
  onAppReady(callback: () => void): void;
}
```

### 扩展 String 和 Number 等内置类型

```typescript
interface String {
  /** 首字母大写 */
  capitalize(): string;

  /** 转换为 kebab-case */
  kebabCase(): string;

  /** 判断是否为空或仅含空白字符 */
  isBlank(): boolean;
}

interface Number {
  /** 四舍五入到指定小数位 */
  toFixedSafe(digits?: number): string;

  /** 限制在指定范围内 */
  clamp(min: number, max: number): number;
}
```

### 全局扩展的利弊权衡

**优势**：
- 无需修改每个使用处的类型导入，随处可用
- 与 JavaScript 运行时原型扩展配合自然
- 适合项目级的通用工具方法

**风险**：
- **全局类型空间污染**：所有 `.ts` 文件都能看到这些扩展，可能造成命名冲突
- **隐式依赖**：开发者可能不清楚某个方法来自原型扩展而非原生 API
- **与其他库冲突**：如果引入的第三方库也扩展了同一个接口且使用了相同的方法名，类型会发生意外合并

### 更安全的替代方案：Module Augmentation

当需要避免污染全局空间时，可以使用模块增强来限定扩展的作用域。详见下一节。

## Module Augmentation —— 模块增强

Module Augmentation 是一种在**模块外部**扩展该模块已导出声明的能力。它是编写第三方库类型补丁的核心手段。

### 核心概念

普通情况下，一个模块内部定义的类型对外部是不可修改的。但通过 `declare module "模块名"` 语法，可以在不触碰原模块源码的前提下为其添加类型成员：

```typescript
// node_modules/some-lib/index.d.ts （原始声明）
export interface Options {
  url: string;
  method: 'GET' | 'POST';
}

export function request(options: Options): Promise<Response>;

// types/some-lib-patch.d.ts （我们的补丁）
declare module 'some-lib' {
  interface Options {
    // 新增可选属性
    headers?: Record<string, string>;
    timeout?: number;
    retry?: number;
    interceptor?: RequestInterceptor;
  }

  // 还可以为该模块新增导出的接口
  export interface RequestInterceptor {
    onRequest(config: Options): Options;
    onResponse(response: Response): Response;
  }
}
```

### 典型用途

#### 为 npm 包补充缺失的类型声明

许多 npm 包要么完全没有类型，要么类型声明不完整。Module Augmentation 是解决此问题的标准方式：

```typescript
// types/vuex-patch.d.ts
import 'vuex';

declare module 'vuex' {
  // 补充 Store 类型上的自定义插件方法
  interface Store<S> {
    $reset(): void;
    $hydrate(state: Partial<S>): void;
  }
}

// types/express-patch.d.ts
import 'express';

declare module 'express' {
  interface Request {
    // 自定义中间件附加的属性
    user?: AuthUser;
    sessionId?: string;
    requestTime: number;
  }

  interface Response {
    standardSuccess(data: unknown): void;
    standardError(status: number, message: string): void;
  }
}
```

#### 与直接修改源文件的区别

| 维度 | Module Augmentation | 直接修改源码 |
|------|-------------------|-------------|
| 是否改动 node_modules | 否 | 是（不推荐） |
| 升级安全性 | 升级后需检查补丁是否仍适用 | 丢失修改 |
| 团队协作 | 通过共享 .d.ts 文件同步 | 需要额外同步机制 |
| 版本控制 | 可纳入 Git 管理 | 无法纳入 |

### 三方库类型补全工作流

实际项目中推荐的工作流程如下：

1. **识别缺失类型**：通过 IDE 报错或 `any` 类型的使用发现类型缺口
2. **创建补丁文件**：在 `src/types/` 或项目根目录 `types/` 下创建对应的 `.d.ts` 文件
3. **编写增强声明**：使用 `declare module` 语法补全缺失成员
4. **更新 tsconfig.json**：确保 `typeRoots` 或 `include` 能发现补丁文件
5. **测试验证**：确认原有功能和新增类型都正确工作

```json
// tsconfig.json 配置示例
{
  "compilerOptions": {
    "typeRoots": ["./node_modules/@types", "./types"],
    "baseUrl": ".",
    "paths": {
      "@types/*": ["types/*"]
    }
  },
  "include": ["src/**/*.ts", "types/**/*.d.ts"]
}
```

## 合并的限制与冲突解决

理解声明合并的限制有助于在遇到问题时快速定位原因。

### 类型不兼容时的错误解读

当同名接口的非函数成员类型不兼容时，TypeScript 会给出明确的编译错误：

```typescript
interface Point {
  x: number;
}

interface Point {
  // x: string; // 错误 TS2717: 后续属性的类型必须与其初始声明一致或为其超类型
  // y: string; // 如果 Point.y 不存在，新增任何类型都可以
}
```

错误信息的含义是：后续声明的同名字段类型必须能**包容**初始声明的类型。这是因为 TypeScript 将接口视为结构化合约，后续声明应当是对合约的扩展而非破坏性变更。

**正确的扩展方式**：

```typescript
interface Point {
  x: number;
}

interface Point {
  x: number & { __brand: 'PointX' }; // 交叉类型，number 的子类型，兼容 ✅
  y: number;                          // 新增字段 ✅
}
```

### 基本类型无法合并

基本类型关键字不能参与声明合并：

```typescript
let count: number = 1;
// interface number { toHex(): string; } // ❌ 接口 'number' 不能对基本类型 'number' 进行扩展

type ID = string;
// type ID = number; // ❌ 重复标识符 'ID'
```

但可以通过**包装类型**间接实现类似效果：

```typescript
interface StringConstructor {
  fromCamelCase(s: string): string;
}

// 或者用 namespace 包装
declare global {
  namespace StringHelpers {
    function slugify(s: string): string;
    function truncate(s: string, len: number): string;
  }
}
```

### 合并顺序的影响

对于非函数成员，合并顺序通常不影响结果（只要类型兼容）。但**函数重载的顺序高度依赖声明顺序**：

```typescript
interface Converter {
  convert(value: string): number;
  convert(value: number): string;
  convert(value: boolean): boolean;
}

interface Converter {
  convert(value: Date): string;       // 最终排第 1 位
  convert(value: RegExp): string[];   // 最终排第 2 位
}
```

由于后声明的重载排在前面，调用 `converter.convert(new Date())` 时会优先匹配 `Date` 签名。如果重载顺序不当，可能导致不符合预期的类型推导：

```typescript
const c: Converter = {
  convert: (value: any): any => value,
};

const result = c.convert('2024-01-01'); // 可能被错误地匹配为 Date 签名
```

**最佳实践**：将最具体的重载放在后面的接口声明中，确保它们在最终重载列表中位于前列。

### 如何查看编译器的最终合并结果

有几种方式可以验证声明合并的结果是否符合预期：

1. **IDE 跳转（Go to Definition）**：在 IDE 中对类型名称执行跳转，可以看到合并后的全部成员
2. **鼠标悬停查看类型提示**：IDE 会展示完整的合并后类型信息
3. **编译输出检查**：使用 `tsc --declaration --emitDeclarationOnly` 只生成声明文件，然后检查输出的 `.d.ts`
4. **tsc --traceResolution**：开启详细日志观察模块解析过程

```bash
# 仅生成声明文件用于审查
npx tsc --declaration --emitDeclarationOnly --outDir dist-types

# 开启详细模式排查合并问题
npx tsc --traceResolution 2>&1 | grep -i "merge"
```

## 常见实战模式

### Mixin 模式

Mixin 模式利用接口合并实现类的组合式能力扩展。核心思路是通过接口声明"标记"，再通过混入函数将对应的能力注入到类中：

```typescript
// 定义能力标记接口
interface Serializable {
  serialize(): string;
  deserialize(data: string): void;
}

interface Loggable {
  setLogLevel(level: 'debug' | 'info' | 'warn' | 'error'): void;
  getLogs(): LogEntry[];
}

interface Validatable {
  validate(): ValidationResult;
}

// Mixin 工厂函数
function withSerializable<TBase extends new (...args: any[]) => any>(Base: TBase) {
  return class extends Base implements Serializable {
    serialize(): string {
      return JSON.stringify(this);
    }
    deserialize(data: string): void {
      Object.assign(this, JSON.parse(data));
    }
  };
}

function withValidatable<TBase extends new (...args: any[]) => any>(Base: TBase) {
  return class extends Base implements Validatable {
    validate(): ValidationResult {
      const errors: string[] = [];
      for (const [key, value] of Object.entries(this)) {
        if (value == null) errors.push(`${key} is required`);
      }
      return { valid: errors.length === 0, errors };
    }
  };
}

// 组合使用
class BaseModel {
  id!: string;
  createdAt!: Date;
}

const EnhancedModel = withSerializable(withValidatable(BaseModel));

const model = new EnhancedModel();
model.id = 'm1';
model.createdAt = new Date();

model.validate();        // 来自 Validatable 接口
model.serialize();       // 来自 Serializable 接口
```

### Plugin 架构中的动态类型扩展

插件系统需要在注册时动态扩展核心类型。声明合并为此提供了静态类型保障：

```typescript
// core/plugin-system.ts
export interface PluginDefinition {
  name: string;
  version: string;
  init(context: PluginContext): void;
}

// 核心 PluginContext 接口 —— 插件可以通过声明合并来扩展它
export interface PluginContext {
  app: AppInstance;
  registerCommand(name: string, handler: CommandHandler): void;
}

// core/app.ts
export class AppInstance {
  private plugins = new Map<string, PluginDefinition>();

  async loadPlugin(plugin: PluginDefinition) {
    plugin.init({
      app: this,
      registerCommand: (name, handler) => this.commands.set(name, handler),
    });
    this.plugins.set(plugin.name, plugin);
  }
}
```

```typescript
// plugins/database-plugin.ts
import { PluginContext } from '../core/plugin-system';

// 通过声明合并扩展 PluginContext
export interface PluginContext {
  getDatabase(): DatabaseConnection;
  registerModel(name: string, model: ModelDefinition): void;
}

export const databasePlugin: PluginDefinition = {
  name: 'database',
  version: '1.0.0',

  init(context: PluginContext) {
    // context.getDatabase 现在有类型提示了！
    const db = context.getDatabase();
    context.registerModel('User', userModel);
  },
};
```

### Declaration file 编写规范

`@types/xxx` 类型的包本质上是一组精心组织的声明合并产物。理解其结构有助于编写高质量的声明文件：

```
@types/my-library/
├── index.d.ts          # 主入口声明
├── globals.d.ts        # 全局类型扩展（如有）
└── v2/                  # 多版本支持
    └── index.d.ts
```

```typescript
// @types/my-library/index.d.ts
export = MyLib;
declare namespace MyLib {
  // 核心接口
  interface Options {
    baseUrl?: string;
    timeout?: number;
  }

  // 导出的函数
  function init(options?: Options): MyLib.Instance;
  function create(config: MyLib.Config): MyLib.Instance;

  // 命名空间嵌套
  namespace Utils {
    function formatPath(...parts: string[]): string;
    function deepMerge<T>(target: T, source: Partial<T>): T;
  }

  // 类声明
  class Instance {
    request<T = any>(path: string, options?: RequestOptions): Promise<MyLib.Response<T>>;
    use(middleware: Middleware): this;
  }
}
```

## 声明合并 vs 继承 vs 交叉类型

这三种机制都能达到"组合类型"的目的，但语义和使用场景各不相同。

### 对比总览

| 维度 | 声明合并 | extends (class 继承) | and (交叉类型) |
|------|---------|---------------------|---------------|
| 适用对象 | interface、namespace、enum、class+ns | class、interface | 所有类型 |
| 合并时机 | 编译期 | 编译期 | 编译期 |
| 运行时影响 | 无（纯类型层面） | 有（原型链继承） | 无（纯类型层面） |
| 可否拆分到多文件 | 可以 | 不行 | 表达式级别 |
| 成员来源 | 同名声明自动合并 | 显式继承声明 | 显式组合 |
| 循环引用 | 支持（有限制） | 受原型链限制 | 无限制 |
| 主要场景 | 扩展现有类型、类型补丁 | OOP 继承体系 | 临时组合类型 |

### 各自的最佳适用场景

**选择声明合并**当：
- 需要为已有的 interface / namespace 添加新成员而不修改原定义
- 编写 `.d.ts` 类型声明文件
- 实现插件式的类型扩展系统
- 组织分散在多文件中的大型类型定义

**选择 class extends**当：
- 构建 OOP 继承层次结构
- 需要运行时的原型链关系（instanceof 检查等）
- 子类需要复用父类的逻辑实现

**选择交叉类型 (&)**当：
- 临时将多个类型组合成一个匿名类型
- 组合一次性的工具类型
- 需要精确控制最终类型结构（不依赖自动合并）

```typescript
// 声明合并的场景
interface BaseRequest {
  url: string;
}
interface BaseRequest {
  headers?: Record<string, string>; // 合并到 BaseRequest
}

// 继承的场景
class HttpError extends Error {
  constructor(public status: number, message: string) {
    super(message);
  }
}
new HttpError(404, 'Not Found') instanceof Error; // true —— 运行时有意义

// 交叉类型的场景
type WithTimestamp<T> = T & { _createdAt: Date; _updatedAt: Date };
const timedUser: WithTimestamp<User> = { ...userData, _createdAt: now, _updatedAt: now };
```

## 调试与最佳实践

### 确认合并结果的实用技巧

**1. 利用 IDE 的 Type Hierarchy 功能**

大多数现代 IDE（VS Code、WebStorm）支持查看类型的层级结构和完整定义。右键类型名称 → Go to Definition 即可看到合并后的全部成员。

**2. 断言辅助调试**

```typescript
// 用于验证合并结果是否符合预期
const _assertMerged: Assert<
  // 如果合并成功，以下条件应该满足
  Array<string> extends { last(): string | undefined } ? true : false
> = true;

type Assert<T extends true> = T;
type Assert<T extends false> = never; // 如果合并失败会产生 never 类型错误
```

**3. 使用 tsc --noEmit 快速校验**

```bash
# 不生成输出文件，仅做类型检查 —— 最快的验证方式
npx tsc --noEmit
```

### 避免过度使用

声明合并虽然强大，但过度使用会带来维护负担：

- **类型追踪困难**：当同一类型散落在十几个文件中时，理解完整类型定义变得困难
- **隐式耦合**：A 文件的接口合并可能影响 B 文件中的行为，但这种关系并不明显
- **编译性能**：大量的跨文件合并会增加编译器的工作量

**推荐原则**：
- 单个接口的合并声明控制在 3-5 个以内
- 相关的合并声明尽量集中在同一目录下
- 对于超过 10 个成员的大型类型，考虑是否应该拆分为独立的类型而非持续合并

## 总结

声明合并是 TypeScript 区别于普通类型系统的独特特性。它打破了"类型定义必须在单一位置完成"的约束，使得类型可以像代码一样被增量式地组织和扩展。掌握这一机制的关键点包括：

1. **接口合并**是最高频的使用形式，注意非函数成员的兼容性规则和函数重载的反序特性
2. **命名空间与值类型的合并**（class/ns、function/ns、enum/ns）是实现内部类型封装的经典模式
3. **Module Augmentation** 是为第三方库补充类型的标准方式，优于直接修改 node_modules
4. **全局类型扩展**方便但存在污染风险，应在收益和代价间做好评估
5. **声明合并、继承、交叉类型**三者各有适用场景，根据实际需求合理选用

在实际工程中，声明合并的价值主要体现在：为不可修改的外部代码补充类型、构建可扩展的插件架构、以及在大规模代码库中按维度拆分类型定义。适度使用这一特性，能在保持类型安全的同时显著提升代码的可维护性。
