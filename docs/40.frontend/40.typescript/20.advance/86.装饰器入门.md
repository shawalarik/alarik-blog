# 装饰器入门 —— 从原理到实战的完整指南

> 装饰器（Decorator）是 TypeScript 中最强大的元编程特性之一。它允许你在不改变原有代码结构的前提下，通过声明式语法为类、方法、属性和参数附加额外行为。本文从基础概念出发，系统讲解五种装饰器的用法、执行机制、元数据系统以及实际工程案例。

这段代码中出现了三种不同的装饰器：`@sealed` 是**类装饰器**，`@log` 是**方法装饰器**，`@required` 是**参数装饰器**。

### 1.1.1 装饰器的编译输出原理

理解装饰器的关键在于明白 **TypeScript 编译器将 `@decorator` 语法糖编译成了什么 JavaScript 代码**。以 Legacy 标准为例，以下 TypeScript 代码：

```typescript
@sealed
class Greeter {
  @log
  greet(@required name: string): void {
    console.log(`Hello, ${name}`)
  }
}
```

会被 TypeScript 编译器大致转换为如下等价的 JavaScript 代码（简化后）：

```javascript
// 装饰器编译输出的核心逻辑（Legacy 模式）

// 1. 类装饰器：__decorate 包装整个类定义
let Greeter = class Greeter {
  greet(name) {
    console.log(`Hello, ${name}`)
  }
};
Greeter = __decorate([
  sealed          // ← 类装饰器函数作为数组元素传入
], Greeter);

// 2. 方法和参数装饰器：在 __decorate 内部通过 descriptor 应用
// __decorate 的核心逻辑（简化版）：
var __decorate = (this && this.__decorate) || function (decorators, target, key, desc) {
  var c = arguments.length, r = c < 3 ? target : desc === null ? desc = Object.getOwnPropertyDescriptor(target, key) : desc;
  for (var i = decorators.length - 1; i >= 0; i--)
    if (d = decorators[i]) r = (c < 3 ? d(r) : c > 3 ? d(target, key, r) : d(target, key)) || r;
  if (c > 3 && r) Object.defineProperty(target, key, r);
  return r;
};

// 3. 参数装饰器通过 __param（本质是 __decorate 的封装）
var __param = (this && this.__param) || function (paramIndex, decorator) {
  return function (target, key) { decorator(target, key, paramIndex); }
};
```

**核心要点**：

1. **`__decorate` 是装饰器机制的心脏**：它接收一个装饰器函数数组和目标对象，从右到左遍历调用每个装饰器
2. **类装饰器**最终返回的是经过所有装饰器处理后的构造函数（可能已被替换）
3. **方法/属性/参数装饰器**在类定义过程中被逐一应用到对应的成员上
4. **装饰器在模块加载时即执行**——不是在实例化时，而是在类定义被求值时。这意味着即使从未 `new` 过某个类，其装饰器代码也会运行

```typescript
// 验证：装饰器在定义时而非使用时执行
function tracker(target: Function) {
  console.log(`${target.name} 类的装饰器已执行`)
}

@tracker   // ← 这行就会立即触发 console.log
class NeverInstantiated {}

// 输出：NeverInstantiated 类的装饰器已执行
// （即使从未 new NeverInstantiated()）
```

### 1.1.2 常见错误演示

```typescript
// ❌ 错误 1：在非类成员上使用装饰器
@log                          // 编译错误！独立函数不能使用装饰器
function standalone(): void {}

// ✅ 正确写法：将需要装饰的逻辑包裹到类的静态方法中
class Utils {
  @log
  static standalone(): void {}
}

// ❌ 错误 2：箭头函数表达式上使用装饰器
const fn = @log (): void => {}  // 编译错误！

// ❌ 错误 3：装饰器函数忘记导出或未定义
@undefinedDecorator              // 运行时错误：undefinedDecorator is not a function
class BadClass {}

// ✅ 正确写法：确保装饰器在使用前已定义并正确导出
function definedDecorator(target: Function) { /* ... */ }
@definedDecorator
class GoodClass {}
```

## 一、装饰器概述

### 1.1 什么是装饰器

**装饰器（Decorator）是一种特殊的声明，可以附加到类、方法、访问器、属性和参数上，用于修改其行为或附加元数据。**

### 1.2 设计灵感与渊源

装饰器的概念并非 TypeScript 原创：

- **Python 的装饰器**：Python 最早引入了函数/类装饰器的概念（PEP 318），使用 `@decorator` 语法糖将一个函数作为参数传递给另一个函数。
- **Java 注解（Annotation）**：Java 通过 `@Override`、`@Deprecated` 等注解为编译器和运行时提供元信息，配合反射 API 实现框架级功能。
- **设计模式中的装饰者模式（Decorator Pattern）**：GoF 设计模式中的装饰者模式动态地将责任附加到对象上，通过组合而非继承扩展功能。

TypeScript 装饰器与经典设计模式的**关键区别**在于：

| 维度 | GoF 装饰者模式 | TS 装饰器 |
|------|--------------|----------|
| 应用层级 | 运行时对象包装 | 编译时声明转换 |
| 作用目标 | 实例对象 | 类、方法、属性、参数 |
| 实现方式 | 手动创建包装类 | 编译器自动生成包装逻辑（`__decorate`） |
| 元数据能力 | 无 | 支持反射元数据（reflect-metadata） |
| 组合方式 | 显式嵌套构造 | 声明式叠加（`@a @b @c`） |
| 代码侵入性 | 高（需修改实例化代码） | 低（零侵入，声明即生效） |

### 1.2.1 为什么需要装饰器——问题导向

在引入装饰器之前，要为类或方法附加横切关注点（如日志、验证、权限），通常采用以下几种方案，每种都有明显的不足：

**方案一：手动包装（高重复代码）**

```typescript
// ❌ 每个需要日志的方法都要手动包裹
class UserService {
  createUser(data: UserData): User {
    console.log(`[LOG] createUser 被调用, 参数: ${JSON.stringify(data)}`)
    const start = Date.now()
    try {
      const result = this._doCreateUser(data)
      console.log(`[LOG] createUser 返回: ${JSON.stringify(result)}, 耗时: ${Date.now() - start}ms`)
      return result
    } catch (err) {
      console.error(`[ERROR] createUser 异常:`, err)
      throw err
    }
  }

  deleteUser(id: number): boolean {
    console.log(`[LOG] deleteUser 被调用, 参数: ${id}`)
    // ... 又是一套完全相同的样板代码
  }

  updateUser(id: number, data: Partial<UserData>): User {
    console.log(`[LOG] updateUser 被调用, 参数: ${JSON.stringify({ id, ...data })}`)
    // ... 还是同样的样板代码
  }
}
```

**方案二：继承/混入（类爆炸问题）**

```typescript
// ❌ 每种横切关注点都需要一个基类或 Mixin
class Loggable { /* 日志相关 */ }
class Validatable { /* 验证相关 */ }
class Authorizable { /* 权限相关 */ }
class Cacheable { /* 缓存相关 */ }

// 组合需求多时，继承链或 Mixin 数量失控
class UserService extends LoggableMixin(
  ValidatableMixin(
    AuthorizableMixin(
      CacheableMixin(BaseService)
    )
  )
) {}
```

**方案三：使用装饰器（声明式、零侵入）**

```typescript
// ✅ 装饰器将横切逻辑与业务逻辑彻底分离
class UserService {
  @log({ includeArgs: true, includeResult: true })
  createUser(data: UserData): User {
    return this._doCreateUser(data)   // 纯业务逻辑
  }

  @log
  @validate(CreateUserSchema)
  @requireRole('admin')
  deleteUser(id: number): boolean {
    return this._doDeleteUser(id)     // 纯业务逻辑
  }
}
```

**核心价值总结**：

| 维度 | 传统方案 | 装饰器方案 |
|------|---------|-----------|
| 代码复用性 | 剪贴板式复制 | 声明式复用 |
| 业务代码纯净度 | 被横切逻辑污染 | 只包含核心业务 |
| 可组合性 | 继承链限制 | 自由叠加多个装饰器 |
| 可维护性 | 分散在各处 | 集中定义、统一管理 |

### 1.2.2 装饰器在主流框架中的实际应用速览

在动手写装饰器之前，先看看业界成熟框架是如何使用装饰器的，建立直观认知：

```typescript
// ====== NestJS：控制器 + 依赖注入 ======
@Controller('users')                          // 类装饰器：注册路由前缀
export class UsersController {
  constructor(private userService: UserService) {} // 参数装饰器实现 DI

  @Get()                                       // 方法装饰器：定义 HTTP GET 路由
  @UseGuards(JwtAuthGuard)                     // 方法装饰器：附加守卫中间件
  findAll(): User[] {
    return this.userService.findAll()
  }
}

// ====== TypeORM：实体定义 ======
@Entity('products')                            // 类装饰器：映射数据库表
class Product {
  @PrimaryGeneratedColumn()                    // 属性装饰器：主键
  id: number

  @Column({ type: 'varchar', length: 100 })   // 属性装饰器：列定义
  name: string

  @ManyToMany(type => Category)                // 属性装饰器：关联关系
  @JoinTable()
  categories: Category[]
}

// ====== class-validator：声明式验证 ======
class LoginDto {
  @IsEmail()                                   // 属性装饰器：邮箱格式校验
  email: string

  @MinLength(8)                                // 属性装饰器：最小长度
  @Matches(/^(?=.*[A-Za-z])(?=.*\d)/)          // 属性装饰器：正则匹配
  password: string

  @IsOptional()
  @IsInt()
  @Min(0)
  @Max(120)
  age?: number                                 // 组合多个装饰器
}
```

这些框架的共同特点是：**通过装饰器将配置信息（路由、表结构、验证规则）与代码逻辑声明式地绑定在一起**，使代码既可读又具备运行时可编程能力。

### 1.3 两套标准

TypeScript 存在两套装饰器标准，这是学习前必须厘清的事实：

**TC39 Stage 3 Decorators（新标准）**

- TS 5.0+ 推荐使用
- 对齐 ECMAScript 标准提案
- 使用 `"decorators": true` 配置启用
- 装饰器函数签名略有不同（接收 context 对象）
- 目前仍标记为实验性特性

**Legacy Decorators（旧标准）**

- TS 5.0 之前唯一的选择
- 广泛应用于 Angular、NestJS、TypeORM 等生态
- 使用 `"experimentalDecorators": true` 配置启用
- 社区生态最为成熟
- 同样是实验性特性

```jsonc
// tsconfig.json —— 新标准（TC39 Stage 3）
{
  "compilerOptions": {
    "decorators": true,
    "experimentalDecorators": false
  }
}

// tsconfig.json —— 旧标准（Legacy）
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "decorators": false
  }
}
```

**本文主要基于 Legacy 标准进行讲解**，原因有二：其一，当前主流框架（NestJS、TypeORM、class-validator）均基于此标准；其二，理解 Legacy 标准后迁移到新标准并不困难。文中会在适当位置标注新旧差异。

### 1.3.1 新旧标准详细语法对比表

以下是对两套装饰器标准在各个维度上的完整对照，供迁移时参考：

| 对比维度 | Legacy Decorators | TC39 Stage 3 Decorators |
|---------|-------------------|------------------------|
| **tsconfig 配置** | `"experimentalDecorators": true` | `"decorators": true` |
| **类装饰器签名** | `(target: Function) => void \| Function` | `(value: Function, context: ClassDecoratorContext) => void \| Function` |
| **方法装饰器签名** | `(target, key, descriptor) => PropertyDescriptor \| void` | `(value: Function, context: ClassMethodDecoratorContext) => void \| Function` |
| **属性装饰器签名** | `(target, key) => void`（无 descriptor） | `(value: undefined, context: ClassFieldDecoratorContext) => void \| (initialValue) => void \| undefined` |
| **访问器装饰器签名** | 与方法装饰器相同 | `(value: { get: Function, set: Function }, context: ClassAccessorDecoratorContext)` |
| **参数装饰器签名** | `(target, key, parameterIndex) => void` | 不再单独存在，归入 `context.addInitializer` |
| **context 对象** | 无 | 提供 `kind`、`name`、`addInitializer()`、`access` 等 |
| **私有字段 `#field`** | 有限支持（需 hack） | 原生完整支持 |
| **自动访问器 auto-accessor** | 不支持 | 支持 `accessor` 关键字 |
| **返回值语义** | 返回 descriptor 替换原描述符 | 返回函数替换原方法/初始化器 |
| **元数据发射** | 通过 `emitDecoratorMetadata` + reflect-metadata | 需配合独立提案或社区方案 |

**关键差异解读**：

```typescript
// ====== Legacy 写法 ======
function logLegacy(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value
  descriptor.value = function (...args: any[]) {
    console.log(`[CALL] ${propertyKey}`)
    return original.apply(this, args)
  }
  return descriptor
}

// ====== Stage 3 写法 ======
// 注意：context 是一个包含丰富信息的对象
const logStandard: MethodDecorator = (value, context) => {
  // context.kind === 'method'
  // context.name === 'greet'（方法名的 symbol 或 string）
  if (context.kind === 'method' && typeof context.name === 'string') {
    return function (...args: any[]) {
      console.log(`[CALL] ${context.name}`)
      return value.call(this, ...args)
    }
  }
}

// 使用方式完全一致：
class Example {
  @logLegacy
  greet1() {}

  @logStandard
  greet2() {}
}
```

### 1.3.2 如何选择

| 项目场景 | 推荐选择 | 原因 |
|---------|---------|------|
| NestJS / TypeORM / Angular 项目 | Legacy | 框架核心依赖此标准 |
| 全新项目，无遗留依赖 | Stage 3 | 更符合 ECMAScript 标准演进方向 |
| 需要使用私有字段装饰器 | Stage 3 | Legacy 对 `#private` 字段支持极差 |
| 需要大量 `emitDecoratorMetadata` | Legacy | 元数据发射与旧标准绑定更深 |
| 库/框架开发，面向广泛用户 | 同时兼容两者 | 提供双模式适配层 |

> **版本提示**：TS 5.0 同时支持两套标准但不能同时启用。如果项目需要使用基于 Legacy 标准的第三方库，必须选择 `experimentalDecorators`。纯新项目可考虑直接采用新标准。

## 二、类装饰器（Class Decorator）

### 2.1 函数签名

```typescript
type ClassDecorator = (
  target: Function   // 被装饰类的构造函数
) => void | Function // 可选返回值
```

类装饰器的参数 `target` 就是**被装饰类本身的构造函数**。它可以选择性地返回一个新的构造函数来替换原类。

### 2.1.1 底层原理：target 到底是什么

`target` 参数的本质是被装饰类的**构造函数引用**，而非实例。这意味着：

```typescript
function inspect(target: Function) {
  console.log(target.name)              // → 类名（如 'Greeter'）
  console.log(target.prototype)         // → 类的原型对象
  console.log(typeof target)            // → 'function'
  // target === Greeter（在 @inspect(Greeter) 中）
}

@inspect
class Greeter {
  greet() {}
}
```

关键点：**类装饰器接收的是类本身（即构造函数），不是 `prototype`，也不是实例**。这是与方法/属性装饰器最大的区别——后两者操作的是原型或属性描述符。

### 2.1.2 为什么需要类装饰器——前置引导

在 JavaScript/TypeScript 中，如果要在不修改源码的情况下为类添加行为，传统方式有以下几种局限：

- **修改 prototype**：直接污染原型链，不够声明式
- **继承包装**：需要手动创建子类，使用方代码要改变
- **高阶函数包装**：每次都要写 `wrapClass(OriginalClass)`

类装饰器通过编译器的语法糖支持，将"对类本身的转换"以声明式的方式表达出来。当你看到 `@singleton class Database {}` 时，一眼就能知道这个类有特殊的行为约束，无需翻阅使用代码。

### 2.1.3 常见错误与陷阱

### 2.1.3 常见错误与陷阱

```typescript
// ❌ 错误 1：返回值破坏原型链
function broken(constructor: Function) {
  // 直接返回一个全新的、不继承原类的构造函数
  return function NewClass() {
    console.log('broken')
  }
  // 原类的所有方法和属性全部丢失！
}

@broken
class Greeter {
  greet() { console.log('hello') }
}
const g = new Greeter()
g.greet()  // → TypeError: g.greet is not a function

// ✅ 正确写法：通过 extends 继承原类
function correct<T extends new (...args: any[]) => any>(constructor: T) {
  return class extends constructor {
    // 新增行为
    extraMethod() { console.log('extra') }
    // 原有方法保持不变
  }
}

// ❌ 错误 2：在类装饰器中修改 prototype 后又返回新类（修改丢失）
function wastedWork<T extends new (...args: any[]) => any>(constructor: T) {
  constructor.prototype.added = 'hi'   // 这行白做了
  return class extends constructor {}   // 返回的新类没有这个属性！
}

// ✅ 正确：要么只改 prototype 不返回，要么在新类中重新添加
function fixed<T extends new (...args: any[]) => any>(constructor: T) {
  return class extends constructor {
    constructor(...args: any[]) {
      super(...args)
      ;(this as any).added = 'hi'
    }
  }
}

// ❌ 错误 3：忘记处理泛型约束，导致类型信息丢失
function badSingleton(constructor: any) {  // 使用 any 丢失类型
  let instance: any = null
  return class extends constructor { /* ... */ } as any
  // 调用方完全失去类型提示
}

// ✅ 正确：保留完整的泛型信息
function goodSingleton<T extends new (...args: any[]) => any>(constructor: T): T & { getInstance(): InstanceType<T> } {
  let instance: InstanceType<T> | null = null
  const NewClass = class extends constructor {
    static getInstance(): InstanceType<T> {
      if (!instance) instance = new NewClass()
      return instance
    }
  }
  return NewClass as T & typeof NewClass
}
```

### 2.2 三种返回值行为

**行为一：不返回值（void）——保留原类不变**

```typescript
function addTimestamp<T extends new (...args: any[]) => any>(constructor: T) {
  constructor.prototype.createdAt = new Date()
}

@addTimestamp
class Article {
  title!: string
}

const article = new Article()
article.title = '深入装饰器'
console.log((article as any).createdAt)
// → 当前时间戳
```

**行为二：返回函数——继承原类后扩展**

```typescript
function singleton<T extends new (...args: any[]) => any>(constructor: T) {
  let instance: InstanceType<T> | null = null

  return new class extends constructor {
    constructor(...args: any[]) {
      if (instance) return instance
      super(...args)
      instance = this as InstanceType<T>
    }
  } as T
}

@singleton
class Database {
  connection: string

  constructor() {
    this.connection = `db_${Date.now()}`
    console.log('新建数据库连接')
  }
}

const db1 = new Database()  // 输出：新建数据库连接
const db2 = new Database()  // 无输出，返回同一实例
console.log(db1 === db2)    // → true
```

**行为三：返回全新构造函数——完全替代原类**

```typescript
function sealed(constructor: Function) {
  // 封闭整个类，阻止后续修改
  Object.seal(constructor)
  Object.seal(constructor.prototype)
}

@sealed
class ImmutableConfig {
  readonly version: string = '1.0.0'
}
```

### 2.3 典型应用场景

#### 场景一：全局注册表（类似 NestJS 的 Controller）

```typescript
// 全局控制器注册表
const controllerRegistry: Map<string, Function> = new Map()

function Controller(path: string) {
  return function <T extends new (...args: any[]) => any>(constructor: T) {
    controllerRegistry.set(path, constructor)
    return constructor
  }
}

@Controller('/api/users')
class UserController {
  list(): void { /* ... */ }
  create(): void { /* ... */ }
}
```

#### 场景四：Mixin 组合（多继承模拟）

**为什么需要 Mixin**：TypeScript 只支持单继承，但实际项目中经常需要将多个可复用的能力（如事件发射、序列化、日志）组合到同一个类上。装饰器 + Mixin 是实现这一目标的优雅方式。

```typescript
// ====== 定义可复用的 Mixin 能力 ======

// 能力 1：事件发射器
function EventEmitter<T extends new (...args: any[]) => any>(Base: T) {
  return class extends Base {
    private __handlers: Record<string, Array<(...args: any[]) => void>> = {}

    on(event: string, handler: (...args: any[]) => void): this {
      ;(this.__handlers[event] ??= []).push(handler)
      return this
    }

    emit(event: string, ...args: any[]): void {
      this.__handlers[event]?.forEach(h => h(...args))
    }

    off(event: string, handler?: (...args: any[]) => void): void {
      if (!handler) {
        delete this.__handlers[event]
      } else {
        this.__handlers[event] = this.__handlers[event]?.filter(h => h !== handler)
      }
    }
  }
}

// 能力 2：序列化支持
function Serializable<T extends new (...args: any[]) => any>(Base: T) {
  return class extends Base {
    toJSON(): Record<string, any> {
      const obj: Record<string, any> = {}
      for (const key of Object.getOwnPropertyNames(this)) {
        if (key.startsWith('__')) continue // 跳过私有属性
        obj[key] = (this as any)[key]
      }
      return obj
    }

    static fromJSON<T>(this: new (...args: any[]) => T, json: string): T {
      const data = JSON.parse(json)
      const instance = new this()
      Object.assign(instance, data)
      return instance
    }
  }
}

// 能力 3：变更追踪
function Trackable<T extends new (...args: any[]) => any>(Base: T) {
  return class extends Base {
    private __snapshot: Record<string, any> = {}
    private __dirty = false

    saveSnapshot(): void {
      this.__snapshot = { ...(this as any) }
      this.__dirty = false
    }

    get isDirty(): boolean {
      for (const key of Object.keys(this.__snapshot)) {
        if ((this as any)[key] !== this.__snapshot[key]) return true
      }
      return this.__dirty
    }

    get changedFields(): string[] {
      const changed: string[] = []
      for (const key of Object.keys(this.__snapshot)) {
        if ((this as any)[key] !== this.__snapshot[key]) changed.push(key)
      }
      return changed
    }
  }
}

// ====== 通过类装饰器组合多个 Mixin ======
type Constructor<T = object> = new (...args: any[]) => T

function applyMixins(...mixins: Array<(c: Constructor<any>) => Constructor<any>>) {
  return function <T extends Constructor<any>>(constructor: T): T {
    let result: Constructor<any> = constructor
    for (const mixin of mixins) {
      result = mixin(result)
    }
    return result as unknown as T
  }
}

// ====== 使用：自由组合多种能力 ======

@applyMixins(EventEmitter, Serializable, Trackable)
class Task {
  id: number
  title: string
  status: 'pending' | 'done' = 'pending'

  constructor(id: number, title: string) {
    this.id = id
    this.title = title
  }

  complete(): void {
    this.status = 'done'
    this.emit('statusChanged', this.status)
  }
}

// 验证所有 Mixin 能力都生效了
const task = new Task(1, '学习装饰器')

// EventEmitter 能力
task.on('statusChanged', (newStatus) => console.log(`状态变为 ${newStatus}`))
task.complete()
// → 状态变为 done

// Trackable 能力
task.saveSnapshot()
task.title = '精通装饰器'
console.log(task.isDirty)       // → true
console.log(task.changedFields) // → ['title']

// Serializable 能力
console.log(task.toJSON())
// → { id: 1, title: '精通装饰器', status: 'done' }
```

#### 场景五：自动绑定 `this`（解决 React 类组件常见问题）

```typescript
// 为什么需要这个？React 类组件中，事件回调的 this 容易丢失
// 传统做法需要在构造函数中手动 bind，或使用箭头函数属性
// 装饰器可以自动完成这件事

function autobind<T extends new (...args: any[]) => any>(constructor: T) {
  const prototype = constructor.prototype

  for (const propertyName of Object.getOwnPropertyNames(prototype)) {
    const descriptor = Object.getOwnPropertyDescriptor(prototype, propertyName)

    // 只处理方法，跳过构造函数和 getter/setter
    if (typeof descriptor?.value === 'function' && propertyName !== 'constructor') {
      const original = descriptor.value

      // 使用 defineProperty 重新定义方法，自动绑定 this
      Object.defineProperty(prototype, propertyName, {
        configurable: true,
        get() {
          // 创建一个永久绑定的函数，并覆盖 getter 使后续访问不再重复绑定
          const bound = original.bind(this)
          Object.defineProperty(this, propertyName, {
            value: bound,
            writable: true,
            configurable: true,
          })
          return bound
        },
      })
    }
  }

  return constructor
}

@autobind
class ReactComponent {
  name: string

  constructor(name: string) {
    this.name = name
  }

  handleClick(): void {
    console.log(`Clicked by ${this.name}`)
  }
}

const comp = new ReactComponent('App')
const fn = comp.handleClick   // 提取方法引用
fn()                           // → Clicked by App（this 自动绑定！）
```

### 2.4 类装饰器的实际项目使用建议

| 场景 | 推荐返回值模式 | 原因 |
|------|---------------|------|
| 注册/标记类 | 返回原 constructor | 不改变类行为，仅附加元数据 |
| 单例/工厂 | 返回继承后的新类 | 需要拦截或控制实例化过程 |
| 混入能力 | 返回链式继承的新类 | 需要在原型链上添加新方法 |
| 封闭/冻结类 | 不返回值（直接操作） | Object.seal/freeze 后无需替换 |
| 版本控制/审计 | 返回继承后的新类 | 需要添加额外字段和方法 |

## 三、方法装饰器（Method Decorator）

### 3.1 函数签名

```typescript
type MethodDecorator = (
  target: Object,                    // 类的原型对象（对于静态方法是构造函数本身）
  propertyKey: string | symbol,       // 方法名称
  descriptor: PropertyDescriptor       // 属性描述符
) => PropertyDescriptor | void         // 可选返回新的描述符
```

这是五种装饰器中最灵活的一种，因为它拿到了完整的 `PropertyDescriptor`，可以自由修改方法的实现。

### 3.2 参数详解

```typescript
function log(
  target: Object,           // 对于实例方法：Greeter.prototype
                            // 对于静态方法：Greeter（构造函数）
  propertyKey: string,      // 'greet' —— 方法名
  descriptor: PropertyDescriptor
  // {
  //   value: [Function: greet],   ← 原始方法引用
  //   writable: true,             ← 是否可写
  //   enumerable: false,          ← 是否可枚举
  //   configurable: true          ← 是否可配置
  // }
) {
  // 在这里操作 descriptor
}
```

### 3.3 核心操作：劫持方法执行

方法装饰器的核心能力在于**替换原始方法的实现**：

```typescript
function measure(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value

  descriptor.value = function (...args: any[]) {
    const start = performance.now()
    const result = originalMethod.apply(this, args)
    const duration = performance.now() - start
    console.log(`[PERF] ${propertyKey} 耗时 ${duration.toFixed(2)}ms`)
    return result
  }

  return descriptor
}

class Calculator {
  @measure
  fibonacci(n: number): number {
    if (n <= 1) return n
    return this.fibonacci(n - 1) + this.fibonacci(n - 2)
  }
}

const calc = new Calculator()
calc.fibonacci(35)
// → [PERF] fibonacci 耗时 XX.XXms
```

```typescript
enum LogLevel {
  DEBUG = 'DEBUG',
  INFO = 'INFO',
  WARN = 'WARN',
  ERROR = 'ERROR',
}

interface LogOptions {
  level?: LogLevel
  includeArgs?: boolean
  includeResult?: boolean
}

function log(options: LogOptions = {}) {
  const { level = LogLevel.DEBUG, includeArgs = true, includeResult = false } = options

  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value

    descriptor.value = function (...args: any[]) {
      const prefix = `[${level}]`
      console.log(`${prefix} 调用 ${String(propertyKey)}${includeArgs ? `(${JSON.stringify(args)})` : ''}`)

      try {
        const result = original.apply(this, args)
        if (includeResult !== false && result !== undefined) {
          console.log(`${prefix} ${String(propertyKey)} 返回:`, result)
        }
        return result
      } catch (error) {
        console.error(`${prefix} ${String(propertyKey)} 抛出异常:`, error)
        throw error
      }
    }

    return descriptor
  }
}
```

```typescript
function debounce(delayMs: number) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value
    let timer: ReturnType<typeof setTimeout> | null = null

    descriptor.value = function (...args: any[]) {
      if (timer) clearTimeout(timer)
      timer = setTimeout(() => {
        original.apply(this, args)
        timer = null
      }, delayMs)
    }

    return descriptor
  }
}

function throttle(intervalMs: number) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value
    let lastCall = 0

    descriptor.value = function (...args: any[]) {
      const now = Date.now()
      if (now - lastCall >= intervalMs) {
        lastCall = now
        original.apply(this, args)
      }
    }

    return descriptor
  }
}

class SearchBox {
  @debounce(300)
  onInput(query: string): void {
    console.log('搜索:', query)
  }

  @throttle(1000)
  onScroll(position: number): void {
    console.log('滚动位置:', position)
  }
}
```

#### 应用四：自动重试

```typescript
function retry(maxAttempts: number, delayMs: number = 1000) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value

    descriptor.value = async function (...args: any[]) {
      let lastError: Error | undefined

      for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
          return await original.apply(this, args)
        } catch (error) {
          lastError = error as Error
          console.warn(`[RETRY] ${String(propertyKey)} 第 ${attempt}/${maxAttempts} 次尝试失败`)

          if (attempt < maxAttempts) {
            await new Promise(resolve => setTimeout(resolve, delayMs))
          }
        }
      }

      throw lastError!
    }

    return descriptor
  }
}

class ApiService {
  @retry(3, 2000)
  async fetchData(): Promise<string> {
    if (Math.random() > 0.7) {
      throw new Error('网络请求失败')
    }
    return '数据获取成功'
  }
}
```

```typescript
function memoize(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value
  const cache = new Map<string, any>()

  descriptor.value = function (...args: any[]) {

    if (cache.has(key)) {

    const result = original.apply(this, args)
    cache.set(key, result)
    return result
  }

  return descriptor
}
```

## 四、属性装饰器（Property Decorator）

### 4.1 函数签名与关键限制

```typescript
type PropertyDecorator = (
  target: Object,              // 类的原型对象
  propertyKey: string | symbol // 属性名称
) => void                      // 注意：没有 descriptor！没有返回值！
```

**属性装饰器与方法装饰器的根本区别**：属性装饰器**拿不到 PropertyDescriptor**，也**不能返回任何值来修改属性的行为**。它只能"标记"该属性，为后续的验证或处理做准备。

为什么？因为 TypeScript 编译器在处理属性装饰器时，还没有初始化属性的描述符（实例属性在构造函数执行后才存在）。

### 4.2 访问器装饰器（Accessor Decorator）

访问器装饰器（用于 getter/setter）的签名与方法装饰器相同，**拥有 descriptor**：

```typescript
type AccessorDecorator = (
  target: Object,
  propertyKey: string | symbol,
  descriptor: PropertyDescriptor
) => PropertyDescriptor | void
```

这意味着访问器装饰器可以修改 getter/setter 的行为：

```typescript
function uppercase(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalGetter = descriptor.get!

  descriptor.get = function (): string {
    const value = originalGetter.call(this)
    return typeof value === 'string' ? value.toUpperCase() : value
  }
}

class User {
  private _name: string = ''

  @uppercase
  get name(): string {
    return this._name
  }

  set name(value: string) {
    this._name = value
  }
}

const user = new User()
user.name = 'alarik'
console.log(user.name)  // → 'ALARIK'
```

### 4.3 属性装饰器的典型用法：标记 + 验证引擎

由于属性装饰器本身无法修改行为，实际开发中通常采用**标记+后处理**的模式：

```typescript
// ====== 第一步：定义标记装饰器 ======

const requiredProperties = new Set<string>()

function required(target: any, propertyKey: string) {
  requiredProperties.add(propertyKey)
}

function minLength(n: number) {
  return function (_target: any, propertyKey: string) {
    const metadata = Reflect.getOwnMetadata('validation', _target.constructor) || {}
    metadata[propertyKey] = { ...(metadata[propertyKey] || {}), minLength: n }
    Reflect.defineMetadata('validation', metadata, _target.constructor)
  }
}

function maxLength(n: number) {
  return function (_target: any, propertyKey: string) {
    const metadata = Reflect.getOwnMetadata('validation', _target.constructor) || {}
    metadata[propertyKey] = { ...(metadata[propertyKey] || {}), maxLength: n }
    Reflect.defineMetadata('validation', metadata, _target.constructor)
  }
}

// ====== 第二步：定义验证引擎 ======

function validate(instance: object): string[] {
  const errors: string[] = []
  const ctor = instance.constructor

  // 检查必填字段
  for (const prop of requiredProperties) {
    if ((instance as any)[prop] === undefined || (instance as any)[prop] === null || (instance as any)[prop] === '') {
      errors.push(`${prop} 为必填项`)
    }
  }

  // 检查长度约束
  const validationMeta = Reflect.getOwnMetadata('validation', ctor) || {}
  for (const [prop, rules] of Object.entries(validationMeta)) {
    const value = (instance as any)[prop]
    if (typeof value === 'string') {
      const r = rules as { minLength?: number; maxLength?: number }
      if (r.minLength && value.length < r.minLength) {
        errors.push(`${prop} 长度不能小于 ${r.minLength}`)
      }
      if (r.maxLength && value.length > r.maxLength) {
        errors.push(`${prop} 长度不能超过 ${r.maxLength}`)
      }
    }
  }

  return errors
}

// ====== 第三步：使用 ======

class RegistrationForm {
  @required
  @minLength(2)
  @maxLength(50)
  username!: string

  @required
  email!: string

  age?: number
}

const form1 = new RegistrationForm()
form1.username = ''
form1.email = 'test@example.com'

console.log(validate(form1))
// → ['username 为必填项', 'username 长度不能小于 2']

const form2 = new RegistrationForm()
form2.username = 'a'.repeat(100)
form2.email = 'test@example.com'

console.log(validate(form2))
// → ['username 长度不能超过 50']
```

这个模式正是 class-validator 库的核心设计思路。

## 五、参数装饰器（Parameter Decorator）

### 5.1 函数签名

```typescript
type ParameterDecorator = (
  target: Object,                // 类原型或构造函数
  propertyKey: string | symbol | undefined,  // 方法名（构造函数参数时为 undefined）
  parameterIndex: number          // 参数索引（从 0 开始）
) => void                         // 无返回值
```

### 5.2 关键特征

参数装饰器是最"被动"的一种：
- **无法修改参数值**
- **无法拦截参数传递**
- **只能标记某个位置的参数**，供其他机制读取

因此参数装饰器几乎总是与**反射元数据（reflect-metadata）**配合使用。

### 5.3 典型应用：依赖注入中的类型标记

这是 NestJS 等 DI 框架的核心机制之一：

```typescript
import 'reflect-metadata'

// 自定义 Token 用于标识依赖
const PARAM_TYPES = Symbol('design:paramtypes')

function Inject(token: string) {
  return function (target: any, _propertyKey: string | symbol, parameterIndex: number) {
    // 获取现有的参数类型元数据，或初始化空数组
    const existingTokens: Array<string | undefined> =
      Reflect.getMetadata(PARAM_TYPES, target) || []
    
    existingTokens[parameterIndex] = token
    Reflect.defineMetadata(PARAM_TYPES, existingTokens, target)
  }
}

// ====== 依赖容器 ======

class Container {
  private providers = new Map<string, any>()

  register(token: string, provider: any): void {
    this.providers.set(token, provider)
  }

  resolve<T>(ctor: new (...args: any[]) => T): T {
    // 获取构造函数参数的类型
    const paramTypes: Function[] = Reflect.getMetadata('design:paramtypes', ctor) || []
    const injectedTokens: (string | undefined)[] =
      Reflect.getMetadata(PARAM_TYPES, ctor) || []

    const injections = paramTypes.map((paramType, index) => {
      const token = injectedTokens[index]
      if (token && this.providers.has(token)) {
        return this.providers.get(token)
      }
      // 尝试按类型自动解析
      if (this.providers.has(paramType.name)) {
        return this.providers.get(paramType.name)
      }
      throw new Error(`无法解析参数 #${index} 的依赖`)
    })

    return new ctor(...injections)
  }
}

// ====== 使用示例 ======

class LoggerService {
  log(msg: string): void {
    console.log(`[LOG] ${msg}`)
  }
}

class ConfigService {
  get(key: string): string {
    return `config_value_for_${key}`
  }
}
```

### 5.4 参数验证标记

```typescript
import 'reflect-metadata'

interface ValidationRule {
  min?: number
  max?: number
  pattern?: RegExp
  custom?: (value: any) => boolean | string
}

function Min(min: number) {
  return function (_target: any, _propertyKey: string, parameterIndex: number) {
    const rules: ValidationRule[] =
      Reflect.getMetadata('paramValidation', _target, String(_propertyKey)) || []
    rules[parameterIndex] = { ...(rules[parameterIndex] || {}), min }
    Reflect.defineMetadata('paramValidation', rules, _target, String(_propertyKey))
  }
}

function Max(max: number) {
  return function (_target: any, _propertyKey: string, parameterIndex: number) {
    const rules: ValidationRule[] =
      Reflect.getMetadata('paramValidation', _target, String(_propertyKey)) || []
    rules[parameterIndex] = { ...(rules[parameterIndex] || {}), max }
    Reflect.defineMetadata('paramValidation', rules, _target, String(_propertyKey))
  }
}

function validateParams(target: any, propertyKey: string, args: any[]): string[] {
  const rules: (ValidationRule | undefined)[] =
    Reflect.getMetadata('paramValidation', target, propertyKey) || []
  const errors: string[] = []

  for (let i = 0; i < args.length; i++) {
    const rule = rules[i]
    if (!rule) continue
    const value = args[i]

    if (rule.min !== undefined && typeof value === 'number' && value < rule.min) {
      errors.push(`参数 #${i}: 值 ${value} 不能小于最小值 ${rule.min}`)
    }
    if (rule.max !== undefined && typeof value === 'number' && value > rule.max) {
      errors.push(`参数 #${i}: 值 ${value} 不能大于最大值 ${rule.max}`)
    }
  }

  return errors
}

class OrderService {
  placeOrder(
    @Min(1) quantity: number,
    @Max(10000) amount: number,
    note?: string
  ): void {
    console.log(`下单: 数量=${quantity}, 金额=${amount}, 备注=${note}`)
  }
}

// 手动验证调用
const orderService = new OrderService()
const errors = validateParams(OrderService.prototype, 'placeOrder', [-1, 50000])
console.log(errors)
// → ['参数 #0: 值 -1 不能小于最小值 1', '参数 #1: 值 50000 不能大于最大值 10000']
```

## 六、装饰器工厂（Decorator Factory）

### 6.1 为什么需要工厂

前面的例子中已经大量使用了装饰器工厂。简单总结一下：

**普通装饰器**是无参的固定行为：

```typescript
function log(target: any, key: string, desc: PropertyDescriptor) {
  // 固定逻辑，无法定制
}
```

**装饰器工厂**是一个高阶函数，返回装饰器函数，从而支持传入配置参数：

```typescript
function log(level: string) {
  // 工厂函数：接收配置参数
  return function (target: any, key: string, desc: PropertyDescriptor) {
    // 装饰器函数：可以使用闭包中的 level 变量
  }
}

// 使用时传参：
@log('info')
myMethod() {}
```

### 6.2 五种装饰器的工厂模式

所有类型的装饰器都可以写成工厂形式：

```typescript
// ====== 1. 类装饰器工厂 ======
function entity(tableName: string) {
  return function <T extends new (...args: any[]) => any>(constructor: T) {
    ;(constructor as any).__table = tableName
    return constructor
  }
}

// ====== 2. 方法装饰器工厂 ======
function retry(times: number, delay: number = 1000) {
  return function (target: any, key: string, desc: PropertyDescriptor) {
    const original = desc.value
    desc.value = async function (...args: any[]) {
      for (let i = 1; i <= times; i++) {
        try { return await original.apply(this, args) }
        catch (e) { if (i === times) throw e; await new Promise(r => setTimeout(r, delay)) }
      }
    }
    return desc
  }
}

// ====== 3. 属性装饰器工厂 ======
function defaultVal(value: any) {
  return function (target: any, key: string) {
    const meta = Reflect.getOwnMetadata('defaults', target.constructor) || {}
    meta[key] = value
    Reflect.defineMetadata('defaults', meta, target.constructor)
  }
}

// ====== 4. 访问器装饰器工厂（与方法相同） ======
function transform(fn: (value: any) => any) {
  return function (target: any, key: string, desc: PropertyDescriptor) {
    const getter = desc.get!
    desc.get = function () { return fn(getter.call(this)) }
    return desc
  }
}

// ====== 5. 参数装饰器工厂 ======
function inject(token: string) {
  return function (target: any, key: string, index: number) {
    // 使用 token 标记参数
  }
}

// ====== 综合使用示例 ======

@Entity('products')
class Product {
  @defaultVal(0)
  @Column({ type: 'integer' })
  price!: number

  @transform((v: string) => v.toUpperCase())
  get name(): string { return this._name }
  set name(v: string) { this._name = v }
  private _name: string = ''

  constructor(
    @inject('DatabaseService') private db: any
  ) {}

  @retry(3, 2000)
  async save(): Promise<void> {
    // 可能失败的网络操作
  }
}
```

### 6.3 可配置的缓存 TTL 示例

```typescript
function cacheable(ttlMs: number = 60000) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value
    const cache = new Map<string, { value: any; expiresAt: number }>()

    descriptor.value = function (...args: any[]) {
      const key = JSON.stringify(args)
      const cached = cache.get(key)

      if (cached && Date.now() < cached.expiresAt) {
        return cached.value
      }

      const result = original.apply(this, args)
      cache.set(key, { value: result, expiresAt: Date.now() + ttlMs })
      return result
    }

    return descriptor
  }
}

class WeatherApi {
  @cacheable(300000)  // 缓存 5 分钟
  async getWeather(city: string): Promise<string> {
    console.log(`请求天气API: ${city}`)
    return `${city}: 晴朗, 25°C`
  }
}
```

## 七、多个装饰器的组合与执行顺序

### 7.1 执行顺序规则

当同一个声明上应用多个装饰器时，它们的求值和执行遵循特定顺序：

```
@f
@g
@h
class C {}
```

**求值顺序（编译时）**：类似于函数嵌套调用，**从下到上、从外到内**：

```
f(g(h(C)))  → 先计算 h，再 g，最后 f
```

**执行顺序（运行时）**：求值的结果作为高阶函数，**从上到下**执行：

```
先执行 f 的返回值，再执行 g 的返回值，最后执行 h 的返回值
```

### 7.2 完整演示

```typescript
function first() {
  console.log('[first]: 被求值（工厂函数执行）')
  return function (
    target: any,
    propertyKey?: string,
    descriptor?: PropertyDescriptor
  ) {
    console.log('[first]: 被执行（装饰器生效）')
  }
}

function second() {
  console.log('[second]: 被求值（工厂函数执行）')
  return function (
    target: any,
    propertyKey?: string,
    descriptor?: PropertyDescriptor
  ) {
    console.log('[second]: 被执行（装饰器生效）')
  }
}

function third() {
  console.log('[third]: 被求值（工厂函数执行）')
  return function (
    target: any,
    propertyKey?: string,
    descriptor?: PropertyDescriptor
  ) {
    console.log('[third]: 被执行（装饰器生效）')
  }
}

// ====== 应用于类 ======

console.log('=== 类装饰器执行流程 ===')

@first()
@second()
@third()
class ExampleClass {
  // ====== 应用于方法 ======

  @first()
  @second()
  @third()
  method(): void {}
}
```

**输出结果**：

```
=== 类装饰器执行流程 ===
[third]: 被求值（工厂函数执行）     ← 先求值第三个（最靠近类声明）
[second]: 被求值（工厂函数执行）    ← 再求值第二个
[first]: 被求值（工厂函数执行）     ← 最后求值第一个
[first]: 被执行（装饰器生效）       ← 执行顺序反过来：先第一个
[second]: 被执行（装饰器生效）      ← 再第二个
[third]: 被执行（装饰器生效）       ← 最后第三个
```

### 7.3 类装饰器 vs 成员装饰器的时机差异

类装饰器和成员装饰器的求值和执行时机有所不同：

```typescript
function classDec(name: string) {
  console.log(`[工厂] 类装饰器 ${name}`)
  return function (target: Function) {
    console.log(`[执行] 类装饰器 ${name}`, target.name)
  }
}

function propDec(name: string) {
  console.log(`[工厂] 属性装饰器 ${name}`)
  return function (_target: any, _key: string) {
    console.log(`[执行] 属性装饰器 ${name}`)
  }
}

function methodDec(name: string) {
  console.log(`[工厂] 方法装饰器 ${name}`)
  return function (_target: any, _key: string, _desc: PropertyDescriptor) {
    console.log(`[执行] 方法装饰器 ${name}`)
  }
}

@classDec('A')
@classDec('B')
class Demo {
  @propDec('x')
  x!: string

  @methodDec('foo')
  foo(): void {}
}
```

**输出结果**：

```
[工厂] 属性装饰器 x        ← 成员装饰器先求值
[工厂] 方法装饰器 foo
[工厂] 类装饰器 B           ← 最后求值类装饰器
[工厂] 类装饰器 A
[执行] 类装饰器 A            ← 类装饰器先执行
[执行] 类装饰器 B
[执行] 属性装饰器 x          ← 成员装饰器后执行
[执行] 方法装饰器 foo
```

**规律总结**：

| 阶段 | 顺序 |
|------|------|
| 成员装饰器求值 | 先于类装饰器 |
| 类装饰器求值 | 后于成员装饰器 |
| 类装饰器执行 | 先于成员装饰器 |
| 成员装饰器执行 | 后于类装饰器 |
| 同类型多个装饰器 | 下→上求值，上→下执行 |

### 7.4 实际意义

理解执行顺序对于编写组合装饰器至关重要。例如：

```typescript
// 外层先执行：设置日志级别上下文
// 内层后执行：在日志上下文中计时
@logWithLevel('info')    // 先执行
@measurePerformance()     // 后执行
async fetchUserData(userId: number): Promise<User> {
  // ...
}
```

## 八、装饰器元数据（reflect-metadata）

### 8.1 为什么需要 reflect-metadata

前面多次提到 `Reflect.getMetadata` 和 `Reflect.defineMetadata`。这些 API 来自 **reflect-metadata** 库——它是连接 TypeScript 类型系统和运行时的桥梁。

**核心问题**：TypeScript 的类型信息在编译后被擦除。运行时无法知道某个属性是什么类型、某个方法的参数有哪些类型。而许多高级功能（如依赖注入、ORM 映射、序列化）恰恰需要这些信息。

**解决方案**：利用 TypeScript 的**发射元数据（emitDecoratorMetadata）**功能，结合 reflect-metadata 库，在编译阶段将类型信息嵌入到输出代码中，运行时即可读取。

### 8.2 安装与配置

```bash
npm install reflect-metadata
# 或
yarn add reflect-metadata
# 或
pnpm add reflect-metadata
```

**tsconfig.json 需要添加两项配置**：

```jsonc
{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,    // ← 关键：发射类型元数据
    // "moduleResolution": "node"      // 推荐配置
  }
}
```

**入口文件顶部必须导入一次**：

```typescript
import 'reflect-metadata'
```

这行代码会 polyfill 全局 `Reflect` 对象，添加元数据相关的方法。

### 8.3 核心 API

```typescript
// 定义元数据

Reflect.defineMetadata(metadataKey: any, metadataValue: any, target: Object, propertyKey: string | symbol)

// 读取元数据（沿原型链查找）
Reflect.getMetadata(metadataKey: any, target: Object): any
Reflect.getMetadata(metadataKey: any, target: Object, propertyKey: string | symbol): any

// 只读取自身定义的元数据（不沿原型链查找）
Reflect.getOwnMetadata(metadataKey: any, target: Object): any
Reflect.getOwnMetadata(metadataKey: any, target: Object, propertyKey: string | symbol): any

// 检查是否存在
Reflect.hasMetadata(metadataKey: any, target: Object): boolean
Reflect.hasMetadata(metadataKey: any, target: Object, propertyKey: string | symbol): boolean

Reflect.hasOwnMetadata(metadataKey: any, target: Object): boolean
Reflect.hasOwnMetadata(metadataKey: any, target: Object, propertyKey: string | symbol): boolean

// 删除元数据

Reflect.deleteMetadata(metadataKey: any, target: Object, propertyKey: string | symbol): boolean

// 获取所有元数据的键
Reflect.getMetadataKeys(target: Object): any[]
Reflect.getMetadataKeys(target: Object, propertyKey: string | symbol): any[]
```

### 8.4 设计类型元数据键（Design-time Metadata Keys）

当启用 `emitDecoratorMetadata` 时，TypeScript 编译器会自动注入三类元数据：

| 元数据键 | 含义 | 用途 |
|---------|------|------|
| `design:type` | 属性/参数的类型构造函数 | ORM 字段映射 |
| `design:paramtypes` | 方法/构造函数的所有参数类型数组 | 依赖注入 |
| `design:returntype` | 方法的返回值类型 | 序列化策略 |

**示例**：

```typescript
import 'reflect-metadata'

class Sample {
  // design:type → String
  name!: string

  // design:type → Number
  age!: number

  // design:type → Boolean
  active!: boolean

  // design:paramtypes → [String, Number]
  // design:returntype → Boolean
  isValid(name: string, threshold: number): boolean {
    return name.length > threshold
  }

  // design:paramtypes → [Number, String]
  constructor(id: number, label: string) {}
}
```

**验证自动生成的元数据**：

```typescript
// 属性类型
console.log(Reflect.getMetadata('design:type', Sample.prototype, 'name'))
// → [Function: String]

console.log(Reflect.getMetadata('design:type', Sample.prototype, 'age'))
// → [Function: Number]

// 构造函数参数类型
console.log(Reflect.getMetadata('design:paramtypes', Sample))
// → [ [Function: Number], [Function: String] ]

// 方法参数类型
console.log(Reflect.getMetadata('design:paramtypes', Sample.prototype, 'isValid'))
// → [ [Function: String], [Function: Number] ]

// 方法返回类型
console.log(Reflect.getMetadata('design:returntype', Sample.prototype, 'isValid'))
// → [Function: Boolean]
```

## 九、装饰器的实际应用案例集

### 案例 1：简易 ORM 模型定义

模仿 TypeORM 的风格，构建一套基于装饰器的模型定义系统：

```typescript
import 'reflect-metadata'

// ====== 元数据存储 ======
const ENTITY_TABLE = Symbol('entity_table')
const ENTITY_COLUMNS = Symbol('entity_columns')

// ====== 装饰器定义 ======

function Entity(tableName: string) {
  return function <T extends new (...args: any[]) => any>(constructor: T) {
    Reflect.defineMetadata(ENTITY_TABLE, tableName, constructor)
    return constructor
  }
}

type ColumnOptions = {
  type?: string
  primary?: boolean
  nullable?: boolean
  default?: any
  unique?: boolean
}

function Column(options: ColumnOptions = {}) {
  return function (_target: any, propertyKey: string) {
    const designType = Reflect.getMetadata('design:type', _target, propertyKey)
    const columns: Array<{
      name: string
      type: string
      primary?: boolean
      nullable?: boolean
      default?: any
      unique?: boolean
    }> = Reflect.getOwnMetadata(ENTITY_COLUMNS, _target.constructor) || []

    columns.push({
      name: propertyKey,
      type: options.type ?? designType.name.toLowerCase(),
      ...options,
    })

    Reflect.defineMetadata(ENTITY_COLUMNS, columns, _target.constructor)
  }
}

// ====== SQL 生成器 ======

function generateCreateTableSQL(EntityClass: new (...args: any[]) => any): string {
  const tableName = Reflect.getMetadata(ENTITY_TABLE, EntityClass)
  const columns = Reflect.getOwnMetadata(ENTITY_COLUMNS, EntityClass) || []

  const colDefs = columns
    .map(col => {
      let def = `  ${col.name} ${col.type}`
      if (col.primary) def += ' PRIMARY KEY'
      if (!col.nullable && !col.primary) def += ' NOT NULL'
      if (col.unique) def += ' UNIQUE'
      if (col.default !== undefined) def += ` DEFAULT '${col.default}'`
      return def
    })
    .join(',\n')

  return `CREATE TABLE IF NOT EXISTS ${tableName} (\n${colDefs}\n);`
}

// ====== 使用 ======

@Entity('users')
class User {
  @Column({ primary: true })
  id!: number

  @Column({ type: 'varchar', nullable: false })
  username!: string

  @Column({ type: 'varchar', unique: true })
  email!: string

  @Column({ nullable: true, default: 0 })
  score!: number

  @Column()
  createdAt!: Date
}

console.log(generateCreateTableSQL(User))
```

**输出 SQL**：

```sql
CREATE TABLE IF NOT EXISTS users (
  id integer PRIMARY KEY,
  username varchar NOT NULL,
  email varchar UNIQUE,
  score integer DEFAULT '0',
  createdat date
);
```

### 案例 2：API 路由定义

模仿 Express/NestJS 的路由装饰器体系：

```typescript
import 'reflect-metadata'

// ====== 元数据常量 ======
const ROUTES_KEY = Symbol('routes')
const MIDDLEWARES_KEY = Symbol('middlewares')

// ====== HTTP 方法装饰器工厂 ======

type HttpMethod = 'get' | 'post' | 'put' | 'patch' | 'delete'

function httpMethod(method: HttpMethod, path: string) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const routes: Array<{ method: string; path: string; handler: string }> =
      Reflect.getOwnMetadata(ROUTES_KEY, target.constructor) || []

    routes.push({
      method: method.toUpperCase(),
      path,
      handler: propertyKey,
    })

    Reflect.defineMetadata(ROUTES_KEY, routes, target.constructor)
  }
}

const Get = (path: string) => httpMethod('get', path)
const Post = (path: string) => httpMethod('post', path)
const Put = (path: string) => httpMethod('put', path)
const Delete = (path: string) => httpMethod('delete', path)

// ====== 控制器基类装饰器 ======

function Controller(prefix: string) {
  return function <T extends new (...args: any[]) => any>(constructor: T) {
    Reflect.defineMetadata('prefix', prefix, constructor)
    return constructor
  }
}

// ====== 中间件装饰器 ======

function Use(middleware: Function) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const middlewares: Function[] =
      Reflect.getOwnMetadata(MIDDLEWARES_KEY, target, propertyKey) || []
    middlewares.push(middleware)
    Reflect.defineMetadata(MIDDLEWARES_KEY, middlewares, target, propertyKey)
    return descriptor
  }
}

// ====== 路由注册器 ======

function registerRoutes(app: any, controllers: any[]): void {
  for (const controller of controllers) {
    const prefix = Reflect.getMetadata('prefix', controller)
    const routes: Array<{ method: string; path: string; handler: string }> =
      Reflect.getOwnMetadata(ROUTES_KEY, controller) || []

    for (const route of routes) {
      const fullPath = `${prefix}${route.path}`
      const middlewares: Function[] =
        Reflect.getOwnMetadata(MIDDLEWARES_KEY, controller.prototype, route.handler) || []

      const handler = controller.prototype[route.handler]

      app[route.method.toLowerCase()](
        fullPath,
        ...middlewares.map(m => m()),
        handler.bind(new controller())
      )

      console.log(`注册路由: ${route.method} ${fullPath}`)
    }
  }
}

// ====== 使用示例 ======

// 模拟 Express app
const expressApp: Record<string, Function> = {
  get: function (path: string, ...handlers: Function[]) {
    console.log(`[Express] GET ${path} → 已挂载 ${handlers.length} 个处理器`)
  },
  post: function (path: string, ...handlers: Function[]) {
    console.log(`[Express] POST ${path} → 已挂载 ${handlers.length} 个处理器`)
  },
}

@Controller('/api/users')
class UserController {
  private users: Array<{ id: number; name: string }> = [
    { id: 1, name: 'Alice' },
    { id: 2, name: 'Bob' },
  ]

  @Get('/')
  getAll() {
    return this.users
  }

  @Get('/:id')
  getById(req: any, res: any) {
    const user = this.users.find(u => u.id === Number(req.params.id))
    res.json(user || null)
  }

  @Use(() => function auth(req: any, res: any, next: Function) {
    console.log('[中间件] 认证检查')
    next()
  })
  @Post('/')
  create(body: any) {
    const newUser = { id: this.users.length + 1, ...body }
    this.users.push(newUser)
    return newUser
  }

  @Delete('/:id')
  remove(req: any) {
    this.users = this.users.filter(u => u.id !== Number(req.params.id))
    return { success: true }
  }
}

registerRoutes(expressApp, [UserController])
```

### 案例 3：表单验证系统

构建一套类似 class-validator 的声明式验证框架：

```typescript
import 'reflect-metadata'

// ====== 错误收集器 ======

interface ValidationError {
  property: string
  constraints: string[]
}

// ====== 验证规则存储 ======

const VALIDATION_RULES = Symbol('validation_rules')

interface RuleSet {
  isRequired?: boolean
  isEmail?: boolean
  minLength?: number
  maxLength?: number
  min?: number
  max?: number
  pattern?: RegExp
  customFn?: (value: any) => boolean | string
}

// ====== 装饰器集合 ======

function IsRequired(_target: any, propertyKey: string) {
  addRule(_target, propertyKey, { isRequired: true })
}

function IsEmail(_target: any, propertyKey: string) {
  addRule(_target, propertyKey, { isEmail: true })
}

function MinLength(n: number) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { minLength: n })
}

function MaxLength(n: number) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { maxLength: n })
}

function Min(n: number) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { min: n })
}

function Max(n: number) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { max: n })
}

function Matches(pattern: RegExp, message?: string) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { pattern, message })
}

function Validate(customFn: (value: any) => boolean | string) {
  return (_target: any, propertyKey: string) =>
    addRule(_target, propertyKey, { customFn })
}

function addRule(_target: any, propertyKey: string, partial: Partial<RuleSet>) {
  const allRules: Record<string, RuleSet> =
    Reflect.getOwnMetadata(VALIDATION_RULES, _target.constructor) || {}
  allRules[propertyKey] = { ...(allRules[propertyKey] || {}), ...partial }
  Reflect.defineMetadata(VALIDATION_RULES, allRules, _target.constructor)
}

// ====== 验证执行引擎 ======

function validate<T>(instance: T): ValidationError[] {
  const errors: ValidationError[] = []
  const ctor = (instance as any).constructor
  const allRules: Record<string, RuleSet> =
    Reflect.getOwnMetadata(VALIDATION_RULES, ctor) || {}

  for (const [propertyName, rules] of Object.entries(allRules)) {
    const value = (instance as any)[propertyName]
    const constraints: string[] = []

    if (rules.isRequired && (value === undefined || value === null || value === '')) {
      constraints.push(`${propertyName} 为必填项`)
    }

    if (value !== undefined && value !== null && value !== '') {
      if (rules.isEmail && !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value)) {
        constraints.push(`${propertyName} 格式必须是有效的邮箱地址`)
      }
      if (rules.minLength !== undefined && String(value).length < rules.minLength) {
        constraints.push(`${propertyName} 长度不能小于 ${rules.minLength}`)
      }
      if (rules.maxLength !== undefined && String(value).length > rules.maxLength) {
        constraints.push(`${propertyName} 长度不能超过 ${rules.maxLength}`)
      }
      if (rules.min !== undefined && Number(value) < rules.min) {
        constraints.push(`${propertyName} 不能小于 ${rules.min}`)
      }
      if (rules.max !== undefined && Number(value) > rules.max) {
        constraints.push(`${propertyName} 不能大于 ${rules.max}`)
      }
      if (rules.pattern && !rules.pattern.test(String(value))) {
        constraints.push(`${propertyName} 格式不符合要求`)
      }
      if (rules.customFn) {
        const result = rules.customFn(value)
        if (result !== true) {
          constraints.push(typeof result === 'string' ? result : `${propertyName} 校验未通过`)
        }
      }
    }

    if (constraints.length > 0) {
      errors.push({ property: propertyName, constraints })
    }
  }

  return errors
}

// ====== 类装饰器：自动验证 ======

function ValidateClass<T extends new (...args: any[]) => any>(constructor: T) {
  return class extends constructor {
    constructor(...args: any[]) {
      super(...args)
    }

    validate(): ValidationError[] {
      return validate(this)
    }

    isValid(): boolean {
      return validate(this).length === 0
    }
  }
}

// ====== 使用示例 ======

@ValidateClass
class LoginForm {
  @IsRequired
  @IsEmail
  @MaxLength(100)
  email!: string

  @IsRequired
  @MinLength(8)
  @Matches(/^(?=.*[A-Za-z])(?=.*\d)/, '密码必须包含字母和数字')
  password!: string

  @Min(0)
  @Max(120)
  age?: number

  @Validate(v => v.startsWith('+86'), '手机号必须以 +86 开头')
  phone?: string
}

// 测试
const form = new LoginForm()
form.email = 'invalid-email'
form.password = '123'
form.age = 150
form.phone = '13800138000'

const validationErrors = form.validate()
console.log(validationErrors)
// [
//   { property: 'email', constraints: ['email 格式必须是有效的邮箱地址'] },
//   { property: 'password', constraints: ['password 长度不能小于 8', '密码必须包含字母和数字'] },
//   { property: 'age', constraints: ['age 不能大于 120'] },
//   { property: 'phone', constraints: ['手机号必须以 +86 开头'] }
// ]

console.log(form.isValid())  // → false

// 修正后的数据
form.email = 'user@example.com'
form.password = 'abc12345'
form.age = 25
form.phone = '+8613800138000'

console.log(form.validate())  // → [] （无错误）
console.log(form.isValid())   // → true
```

### 案例 4：权限控制系统

基于角色和资源的细粒度权限控制系统：

```typescript
import 'reflect-metadata'

// ====== 权限元数据 ======

const PERMISSIONS_KEY = Symbol('permissions')

interface PermissionRequirement {
  resource: string
  actions: string[]
  roles?: string[]
  conditions?: string[]
}

// ====== 权限装饰器 ======

function RequiresPermission(resource: string, actions: string | string[]) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const perms: PermissionRequirement[] =
      Reflect.getOwnMetadata(PERMISSIONS_KEY, target, propertyKey) || []

    perms.push({
      resource,
      actions: Array.isArray(actions) ? actions : [actions],
    })

    Reflect.defineMetadata(PERMISSIONS_KEY, perms, target, propertyKey)

    const original = descriptor.value

    descriptor.value = function (...args: any[]) {
      const ctx = (this as any)._context
      if (!checkPermission(ctx, perms)) {
        throw new Error(`权限不足：需要 ${resource}:${actions.join(',')} 权限`)
      }
      return original.apply(this, args)
    }

    return descriptor
  }
}

function RequiresRole(...roles: string[]) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const perms: PermissionRequirement[] =
      Reflect.getOwnMetadata(PERMISSIONS_KEY, target, propertyKey) || []

    if (perms.length > 0) {
      perms[perms.length - 1].roles = roles
    } else {
      perms.push({ resource: '*', actions: ['*'], roles })
    }

    Reflect.defineMetadata(PERMISSIONS_KEY, perms, target, propertyKey)

    const original = descriptor.value

    descriptor.value = function (...args: any[]) {
      const ctx = (this as any)._context
      if (!roles.some(r => ctx.user.roles.includes(r))) {
        throw new Error(`权限不足：需要角色 ${roles.join(' 或 ')}`)
      }
      return original.apply(this, args)
    }

    return descriptor
  }
}

// ====== 权限检查函数 ======

interface SecurityContext {
  user: {
    id: number
    roles: string[]
    permissions: string[]
  }
  resource?: {
    ownerId: number
  }
}

function checkPermission(ctx: SecurityContext, requirements: PermissionRequirement[]): boolean {
  return requirements.every(req => {
    const hasRole = !req.roles || req.roles.some(r => ctx.user.roles.includes(r))

    const hasPermission = req.actions.some(action => {
      return ctx.user.permissions.includes(`${req.resource}:${action}`) ||
             ctx.user.permissions.includes('*:*') ||
             ctx.user.permissions.includes(`${req.resource}:*`)
    })

    return hasRole && hasPermission
  })
}

// ====== 使用示例 ======

class AdminService {
  _context: SecurityContext

  constructor(context: SecurityContext) {
    this._context = context
  }

  @RequiresPermission('user', 'read')
  getUserList(): string[] {
    return ['Alice', 'Bob']
  }

  @RequiresPermission('user', 'write')
  @RequiresRole('admin', 'moderator')
  createUser(data: any): any {
    return { id: 1, ...data }
  }

  @RequiresPermission('user', 'delete')
  deleteUser(id: number): boolean {
    console.log(`删除用户 ${id}`)
    return true
  }

  @RequiresPermission(['user', 'read'], ['user', 'write'])
  manageUsers(): void {
    console.log('管理用户')
  }
}

// 测试场景
const adminContext: SecurityContext = {
  user: { id: 1, roles: ['admin'], permissions: ['*', '*'] },
}

const normalContext: SecurityContext = {
  user: { id: 2, roles: ['user'], permissions: ['user:read'] },
}

const adminService = new AdminService(adminContext)

console.log(adminService.getUserList())     // ✅ 成功
console.log(adminService.createUser({}))    // ✅ 成功
console.log(adminService.deleteUser(99))    // ✅ 成功

const userService = new AdminService(normalContext)

console.log(userService.getUserList())      // ✅ 有读权限

try {
  userService.createUser({})
} catch (e) {
  console.error(e.message)
  // → 权限不足：需要 user:write 权限
}

try {
  userService.deleteUser(1)
} catch (e) {
  console.error(e.message)
  // → 权限不足：需要 user:delete 权限
}
```

## 十、装饰器的局限性与注意事项

### 10.1 实验性特性状态

截至 TypeScript 5.x，装饰器（无论新旧标准）仍属于**实验性特性**：

- TC39 Decorator 提案处于 **Stage 3**（候选阶段），尚未进入最终规范
- 旧版 Legacy 装饰器已被 TypeScript 团队明确标注为遗留方案
- 新版标准装饰器仍在持续演进中

**影响**：未来可能存在破坏性变更。生产环境使用需评估升级成本。

### 10.2 版本间的语法差异

新旧标准之间存在显著差异，以下是关键对照：

| 特性 | Legacy（旧） | Standard（新，Stage 3） |
|------|-------------|----------------------|
| 配置项 | `experimentalDecorators` | `decorators` |
| 类装饰器参数 | `(target: Function)` | `(value: Class, context: ClassDecoratorContext)` |
| 方法装饰器参数 | `(target, key, descriptor)` | `(value: Function, context: ClassMethodDecoratorContext)` |
| 属性装饰器参数 | `(target, key)` | `(value: undefined, context: ClassFieldDecoratorContext)` |
| 自动填充 access | 不支持 | 支持 `context.access` |
| 私有字段支持 | 有限 | 完整支持 `#private` 字段 |
| 返回值语义 | 替换 descriptor/value | 替换 initializer/value |

**新标准示例（仅供参考）**：

```typescript
// 新标准写法（TS 5.0+ decorators: true）
const logged: MethodDecorator = (value, context) => {
  if (context.kind === 'method') {
    return function (...args: any[]) {
      console.log(`calling ${String(context.name)}`)
      return value.apply(this, args)
    }
  }
}

class Example {
  @logged
  method() {}
}
```

### 10.3 性能影响

装饰器在以下环节产生额外开销：

**编译时开销**：装饰器表达式会被求值并转换为函数调用，增加编译产物体积。

**运行时开销**：
- 每次实例化时，类装饰器可能执行额外的构造逻辑
- 方法装饰器会创建闭包，增加内存占用
- 反射元数据的读取涉及 Map 查找

**优化建议**：

```typescript
// ❌ 每次调用都创建新的正则表达式
function match(pattern: string) {
  return function (target: any, key: string, desc: PropertyDescriptor) {
    const regex = new RegExp(pattern)  // 每次装饰都创建
    // ...
  }
}

// ✅ 提取为外部变量或模块常量
const PATTERN_CACHE = new Map<string, RegExp>()
function matchOptimized(pattern: string) {
  return function (target: any, key: string, desc: PropertyDescriptor) {
    let regex = PATTERN_CACHE.get(pattern)
    if (!regex) {
      regex = new RegExp(pattern)
      PATTERN_CACHE.set(pattern, regex)
    }
    // ...
  }
}
```

### 10.4 使用范围限制

装饰器**只能用于类及其成员**，不能用于：

```typescript
// ❌ 不能用于独立函数
@log
function standaloneFunction(): void {}  // 编译错误！

// ❌ 不能用于箭头函数
@log
const arrowFunc = (): void => {}       // 编译错误！

// ✅ 只能用于类内部
class ValidCase {
  @log
  validMethod(): void {}               // 正确

  @log
  validProperty: string = ''           // 正确
}
```

### 10.5 调试困难

装饰器改变了原始代码结构，可能带来调试挑战：

- **堆栈信息不直观**：被包装的方法在堆栈中显示的是包装函数名，而非原始方法名
- **断点失效**：IDE 断点可能打在被装饰后的包装函数上而非原始方法体
- **源映射问题**：经过多层包装后，source-map 可能无法准确映射

**缓解策略**：

```typescript
function debuggable(target: any, key: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value
  const className = target.constructor.name

  descriptor.value = function (...args: any[]) {
    // 保留原始方法名以便调试
    const fnName = `${className}.${key}`
    console.debug(`[${fnName}] 进入方法`)
    const result = original.apply(this, args)
    console.debug(`[${fnName}] 离开方法`)
    return result
  }

  // 设置 displayName 以改善调试体验
  descriptor.value.displayName = `${className}.${key}(wrapped)`

  return descriptor
}
```

## 十一、总结与学习路线

### 11.1 各类装饰器速查表

| 装饰器类型 | 目标 | 签名要点 | 能否修改行为 | 典型场景 |
|-----------|------|---------|------------|---------|
| 类装饰器 | `class` | `(target: Function)` | 可替换构造函数 | 单例、注册、Mixin |
| 方法装饰器 | 方法 | `(target, key, descriptor)` | 可替换方法实现 | 日志、缓存、鉴权、重试 |
| 访问器装饰器 | getter/setter | `(target, key, descriptor)` | 可替换 getter/setter | 数据变换、懒加载 |
| 属性装饰器 | 属性 | `(target, key)` | 仅能标记（无返回值） | 必填校验、序列化标记 |
| 参数装饰器 | 参数 | `(target, key, index)` | 仅能标记（无返回值） | 依赖注入、参数验证 |
