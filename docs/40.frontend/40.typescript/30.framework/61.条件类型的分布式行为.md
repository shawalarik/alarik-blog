# 条件类型的分布式行为 —— 联合类型分发、never 的过滤作用

> **核心问题**：为什么 `string | number` 传入 `T extends string ? X : Y` 会得到两个结果的联合？为什么 `T extends never ? X : Y` 会返回 `never`？这些看似"魔法"的行为背后，是 TypeScript 条件类型的**分布式条件类型（Distributed Conditional Types）**机制在起作用。理解它，你才能驾驭 `Exclude`、`Extract`、`NonNullable` 等内置工具类型的本质。

---

## 一、什么是分布式条件类型？

### 1.1 先看一个令人困惑的现象

在正式解释之前，先让你感受一下分布式行为的"魔力"：

```typescript
type ToArray<T> = T[]

// 当 T 是联合类型时，普通泛型的行为：
type A = ToArray<string | number>
// 结果： (string | number)[]
// 
// 解释：整个联合类型被当作一个整体，套上了一层数组
// 就像把一袋混合糖果（糖+巧克力）装进一个盒子 → 一盒混合糖果


// 但条件类型完全不同！
type ToArrayDist<T> = T extends any ? T[] : never

type B = ToArrayDist<string | number>
// 结果： string[] | number[]
//
// 解释：联合类型被"拆开"了！每个成员分别处理后再合并回来
// 就像把混合糖果拆成糖和巧克力，分别装盒 → 一盒糖 OR 一盒巧克力
```

**这就是分布式条件类型的核心**——当条件类型中的"被检查类型"是一个**裸类型参数**（naked type parameter），且该参数被推断为联合类型时，TypeScript 会自动把联合类型**分发（distribute）**到条件类型的每一个分支。

### 1.2 生活类比：分拣中心的工作方式

想象你经营一个快递分拣中心：

```
═══════════════════════════════════════════════════
         快递分拣中心的两种工作模式
═══════════════════════════════════════════════════

【模式 A：整箱处理（非分布式）】
───────────────────────────────────────

输入：一个大箱子，里面混着 文件、食品、电子产品
规则：如果箱子能通过安检，就贴上"已安检"标签

处理过程：
  ┌──────────────────┐
  │ 整个箱子一起过检 │ → 通过 ✓ → 贴标签 → 输出：【已安检的大箱子】
  └──────────────────┘

结果：还是一个箱子，里面什么都有


【模式 B：逐件分拣（分布式）】
───────────────────────────────────────

输入：同样的大箱子，里面混着 文件、食品、电子产品
规则：对每一件物品单独检查：
      如果是文件 → 放入文件柜
      如果是食品 → 放入冷藏柜
      如果是电子产品 → 放入防静电柜

处理过程：
  ┌─────────┐   ┌─────────┐   ┌──────────┐
  │  文件   │   │  食品   │   │ 电子产品  │
  │  单独过检│   │  单独过检│   │  单独过检 │
  └────┬────┘   └────┬────┘   └─────┬────┘
       │             │              │
       ▼             ▼              ▼
  ┌─────────┐  ┌─────────┐  ┌──────────┐
  │ 文件柜  │  │ 冷藏柜  │  │防静电柜  │
  └─────────┘  └─────────┘  └──────────┘

结果：三个独立的柜子（联合类型）
     文件柜 | 冷藏柜 | 防静电柜
```

**TypeScript 的分布式条件类型就是"模式 B"**——它不会把联合类型当成一坨东西整体处理，而是拆开来，每一份单独跑一遍条件逻辑，最后把所有结果合并回去。

### 1.3 触发分布式的严格条件

不是所有的条件类型都会触发分布式行为！只有同时满足以下**两个条件**时才会分发：

```
╔══════════════════════════════════════════════════════════╗
║                                                          ║
║  分布式触发的两大必要条件                                  ║
║                                                          ║
║  ① "被检查类型"必须是一个裸类型参数                        ║
║     （naked type parameter）                              ║
║     即 extends 左边直接写的是 T 本身                      ║
║                                                          ║
║  ② 该类型参数在调用时被推断/指定为联合类型                  ║
║                                                          ║
║  缺少任何一个条件都不会触发分发！                           ║
║                                                          ║
╚══════════════════════════════════════════════════════════╝
```

#### 什么是"裸类型参数"？

**裸（Naked）**指的是类型参数 `T` 直接出现在 `extends` 的左边，没有被数组、元组、Promise 等任何外层包装：

```typescript
// ✅ 裸的 —— 会触发分布式
type Dist1<T> = T extends U ? X : Y        // T 直接出现
type Dist2<T> = [T] extends [U] ? X : Y    // T 在元组中也是裸的
type Dist3<T> = T extends any ? X : Y      // T 直接出现

// ❌ 不裸的 —— 不会触发分布式
type NonDist1<T> = T[] extends U ? X : Y   // T 被 [] 包装了
type NonDist2<T> = Promise<T> extends U ? X : Y  // T 被 Promise 包装了
type NonDist3<T> = { a: T } extends U ? X : Y  // T 被对象包装了
type NonDist4<T> = () => T extends U ? X : Y  // T 被函数包装了
```

**生活类比再深化**：

- **裸类型参数** = 你直接拿到一份原始名单（张三|李四|王五），你可以逐一处理每个人
- **非裸类型参数** = 你拿到的名单被封在一个信封里（`[T]`）或锁在一个保险箱里（`Promise<T>`）。你只能看到信封或保险箱本身，无法接触到里面的名单，所以无法逐一分发

#### 实际对比验证

```typescript
// ====== 案例 1: 裸 vs 不裸 =======

// 裸的：会分发
type Naked<T> = T extends string ? '是字符串' : '不是字符串'

type Test1 = Naked<string | number | boolean>
// 分发过程：
//   Naked<string>   → '是字符串'
//   Naked<number>   → '不是字符串'
//   Naked<boolean>  → '不是字符串'
// 最终结果：'是字符串' | '不是字符串'


// 不裸的：不分发
type Wrapped<T> = T[] extends string[] ? '是字符串数组' : '不是字符串数组'

type Test2 = Wrapped<string | number>
// T 被推断为 string | number
// 但 T[] 变成了 (string | number)[]
// 这是作为一个整体去匹配 string[] 的
// (string | number)[] ≠ string[]（因为元素可能是 number）
// 最终结果：'不是字符串数组'  （没有分发！）


// ====== 案例 2: 更隐蔽的不裸情况 ======

interface Box<T> {
  value: T
}

// 看起来 T 是裸的？不！T 出现在对象属性的位置，不是 extends 的左边
type BoxCheck<T> = Box<T> extends Box<string> ? '是字符串盒子' : '不是'

type Test3 = BoxCheck<string | number>
// 推断过程：
//   Box<string | number> extends Box<string> ?
//   { value: string | number } extends { value: string } ?
//   → value 类型不匹配（string|number ⊄ string）
//   → '不是'
// 最终结果：'不是'  （不分发，整体判断）
```

### 1.4 分布式的完整执行流程

让我们用最详细的方式追踪一次分发的完整过程：

```typescript
type MyExclude<T, U> = T extends U ? never : T

type Result = MyExclude<'a' | 'b' | 'c', 'a'>
// 期望结果：'b' | 'c'
```

TypeScript 编译器内部发生了什么？

```
═══════════════════════════════════════════════════
           分布式条件类型的内部执行流程
═══════════════════════════════════════════════════

【步骤 1】识别条件
────────────────
  type MyExclude<T, U> = T extends U ? never : T
  
  检查：extends 左边的 T 是否是裸类型参数？
        → 是！T 直接出现，没有任何包装
        → 标记：此条件类型具有分布式特性


【步骤 2】获取实际类型参数
────────────────
  Result = MyExclude<'a' | 'b' | 'c', 'a'>
  
  绑定：T = 'a' | 'b' | 'c'
         U = 'a'
  
  检查：T 是否为联合类型？
        → 是！'a'|'b'|'c' 是联合类型
        → 触发分布式处理！


【步骤 3】拆分联合类型
────────────────
  将 T = 'a' | 'b' | 'c' 拆分为三个独立分支：
  
  分支 1：T = 'a'
  分支 2：T = 'b'
  分支 3：T = 'c'


【步骤 4】逐分支求值
────────────────
  分支 1: 'a' extends 'a' ? never : 'a'
          → 'a' 确实可以赋值给 'a' ✓
          → 取 true 分支：never
          → 结果：never

  分支 2: 'b' extends 'a' ? never : 'b'
          → 'b' 不能赋值给 'a' ✗
          → 取 false 分支：'b'
          → 结果：'b'

  分支 3: 'c' extends 'a' ? never : 'c'
          → 'c' 不能赋值给 'a' ✗
          → 取 false 分支：'c'
          → 结果：'c'


【步骤 5】合并结果
────────────────
  所有分支的结果组成新的联合类型：
  
  never | 'b' | 'c'
  
  在 TypeScript 中，never | X = X（never 是吸收元/空集）
  所以最终结果：'b' | 'c'


【步骤 6】返回最终类型
────────────────
  type Result = 'b' | 'c'  ✓

═══════════════════════════════════════════════════
```

这个流程揭示了 TypeScript 内部的一个关键设计决策：**分布式条件类型本质上是一种隐式的 map-reduce 操作**——map（对每个成员应用条件）+ reduce（将结果联合）。

## 二、内置工具类型的本质都是分布式

### 2.1 Exclude、Extract、NonNullable 的实现原理

TypeScript 内置的这些工具类型，底层全都是分布式条件类型：

```typescript
/**
 * Exclude<T, U> —— 从 T 中排除可分配给 U 的类型
 * 
 * 直觉：筛子！把不需要的过滤掉
 */
type Exclude<T, U> = T extends U ? never : T

// 使用示例
type T1 = Exclude<string | number | boolean, number | boolean>
// 过程：
//   string extends (number|boolean)?  no  → string
//   number extends (number|boolean)?  yes → never
//   boolean extends (number|boolean)? yes → never
// 结果：string

/**
 * Extract<T, U> —— 从 T 中提取可分配给 U 的类型
 * 
 * 直觉：磁铁！只吸引需要的
 */
type Extract<T, U> = T extends U ? T : never

// 使用示例
type T2 = Extract<string | number | (() => void), Function>
// 过程：
//   string extends Function?   no  → never
//   number extends Function?   no  → never
//   (()=>void) extends Function? yes → ()=>void
// 结果：() => void

/**
 * NonNullable<T> —— 从 T 中排除 null 和 undefined
 * 
 * 直觉：真空泵！抽走空值
 */
type NonNullable<T> = T extends null | undefined ? never : T

// 使用示例
type T3 = NonNullable<string | null | undefined | number>
// 过程：
//   string extends null|undefined?     no  → string
//   null extends null|undefined?       yes → never
//   undefined extends null|undefined?  yes → never
//   number extends null|undefined?     no  → number
// 结果：string | number
```

### 2.2 用生活场景理解这三个工具

想象你在整理书架：

```
你的书架上现在有：
┌──────────────────────────────────────┐
│ 📕 小说    📗 教材    📙 漫画         │
│ 📕 科幻    📗 词典    📙 四格漫画     │
│ 📘 杂志    🗑️ 废纸    ❓ 空位(undef)  │
└──────────────────────────────────────┘


【Exclude —— 扔掉不要的】
────────────────────────
指令："把教材和废纸扔掉"

处理：
  小说 → 保留（不是教材也不是废纸）
  教材 → 扔掉！（匹配"教材"）
  漫画 → 保留
  科幻 → 保留
  词典 → 扔掉！（匹配"教材"类）
  四格漫画 → 保留
  杂志 → 保留
  废纸 → 扔掉！（匹配"废纸"）
  空位 → 保留（不在排除列表中）

结果：小说 | 漫画 | 科幻 | 四格漫画 | 杂志 | 空位


【Extract —— 只要特定的】
────────────────────────
指令："只要教材类的"

处理：
  小说 → 不要
  教材 → 要！
  漫画 → 不要
  科幻 → 不要
  词典 → 要！（属于教材类）
  四格漫画 → 不要
  杂志 → 不要
  废纸 → 不要
  空位 → 不要

结果：教材 | 词典


【NonNullable —— 去掉空位和垃圾】
────────────────────────
指令："去掉废纸和空位"

结果：小说 | 教材 | 漫画 | 科幻 | 词典 | 四格漫画 | 杂志
```

### 2.3 手动实现更多实用工具

基于分布式特性，我们可以构建自己的工具类型库：

```typescript
/**
 * 工具 1：UnionToIntersection —— 将联合类型转为交叉类型
 *
 * 这是一个经典的"反直觉"技巧
 * 利用函数参数位置的逆变性来实现转换
 */
type UnionToIntersection<U> =
  (U extends any ? (arg: U) => void : never) extends (arg: infer I) => void
    ? I
    : never

// 测试
type UI = UnionToIntersection<{ a: string } | { b: number }>
// 结果：{ a: string } & { b: number}
// 
// 解释：这个技巧利用了函数参数的逆变性质
// 先用分布式把联合变成函数联合，再用逆变变成交叉


/**
 * 工具 2：LastOf —— 获取联合类型的最后一个成员
 */
type LastOf<T> = 
  UnionToIntersection<
    T extends any ? () => T : never
  > extends () => infer R
    ? R
    : never

// 测试
type L = LastOf<'a' | 'b' | 'c' | 'd'>
// 结果：'d'（联合类型的最后一个成员）


/**
 * 工具 3：UnionToArray —— 将联合类型转为元组
 *
 * 利用递归 + 分布式 + Exclude 逐步提取成员
 */
type UnionToArray<T, R extends unknown[] = []> =
  // 如果 T 已经是 never（空联合），说明提取完毕，返回累积的结果 R
  [T] extends [never]
    ? R
    // 否则，取出当前 T 的第一个成员，追加到 R，然后从 T 中移除它继续递归
    : UnionToArray<Exclude<T, LastOf<T>>, [...R, LastOf<T>]>

// 测试
type Arr = UnionToArray<'a' | 'b' | 'c'>
// 结果：['a', 'b', 'c']
// 
// 这个操作非常重要！因为联合类型的成员是无序的，
// 转成元组后就有了固定的顺序，可以做更多操作


/**
 * 工具 4：IsUnion —— 判断一个类型是否是联合类型
 *
 * 利用分布式和非分布式的行为差异来检测
 */
type IsUnion<T, B = T> =
  T extends B
    ? [B] extends [T]
      ? false   // 不是联合类型（B 和 T 完全相同）
      : true    // 是联合类型（分发后产生了不同的结果）
    : never

// 测试
type IsStr = IsUnion<string>               // false（单一类型）
type IsUN = IsUnion<string | number>       // true（联合类型）
type IsNever = IsUnion<never>              // false（never 是特殊情况）
```

**`IsUnion` 的原理解析**——这是一个非常巧妙的技巧：

```typescript
// 当 T = string（单一类型）时：
IsUnion<string>
= string extends string                    // T extends B，B 默认等于 T
  ? [string] extends [string]              // [B] extends [T]，两者相同
    ? false                               // → 不是联合类型 ✓
    : true
  : never

// 当 T = string | number（联合类型）时：
IsUnion<string | number>
// 因为 T 是裸类型参数且是联合类型 → 触发分布式！
= (string extends string|number ? ... ) | (number extends string|number ? ...)
// 分支 1：string extends string|number
  ? [string|number] extends [string]       // [B]=[string|number], [T]=string（分发后T变为string）
    // 注意：这里的 T 在 [T] 中已经变成了单个成员 string
    // 而 B 还是完整的 string|number
    // [string|number] 不是 [string] 的子集
    ? false
    : true                                // → true！是联合类型 ✓
```

## 三、never 的特殊行为

### 3.1 为什么 never 在分布式中被跳过？

这是分布式条件类型中最反直觉的一个特性：

```typescript
type TestNever<T> = T extends string ? 'yes' : 'no'

type R1 = TestNever<never>
// 结果：never  （既不是 'yes' 也不是 'no'！）

type R2 = TestNever<string | never>
// 结果：'yes'  （never 成员被静默跳过了）
```

**为什么会这样？**

这要从 `never` 的本质说起：

```
═══════════════════════════════════════════════════
              never 的双重身份
═══════════════════════════════════════════════════

【身份 1：底部类型（Bottom Type）】
────────────────────────
  never 是所有类型的子类型。
  这意味着 never 可以赋值给任何类型。
  
  let x: never
  x = 1        // ✓ never 可以是 number
  x = 'hello'  // ✓ never 可以是 string
  x = {}       // ✓ never 可以是 object
  
  类比：never 像"空集合 ∅"
       空集合是任何集合的子集


【身份 2：空的联合类型】
────────────────────────
  从另一个角度，never 相当于"什么都不包含的联合"
  就像一个没有元素的列表：[]
  
  当分布式条件类型尝试"遍历" never 时：
  它就像在对空列表做 for-each 循环 ——
  根本没有元素可以迭代！
  
  for (const item of []) {
    // 这里的代码永远不会执行
  }
  
  同理：
  never distributed over (T => ...) = never
  （空联合分发后还是空联合 / 空集映射后还是空集）

═══════════════════════════════════════════════════
```

**数学类比**：

```
在集合论中：
  ∅（空集）∪ A = A        → never | T = T
  f(∅) = ∅                → 对 never 应用条件类型 = never

在 TypeScript 中：
  never | string = string                          → 空集的并集
  (never extends X ? Y : Z) = never                → 空集的映射
```

### 3.2 利用 never 的过滤能力

正因为 `never | T = T`，我们可以利用分布式条件类型来实现**过滤**：

```typescript
/**
 * 只保留 T 中满足条件 P 的成员
 * 不满足的被替换为 never，然后在联合中被自然消除
 */
type Filter<T, Condition> = T extends Condition ? T : never

// 示例：只保留函数类型
type OnlyFunctions<T> = Filter<T, (...args: any[]) => any>

type F1 = OnlyFunctions<string | number | (() => void) | { x: number }>
// 过程：
//   string    extends Function?  no  → never
//   number    extends Function?  no  → never
//   ()=>void  extends Function?  yes → ()=>void
//   {x:number}extends Function?  no  → never
// 结果：() => void  （其他都被 never 吸收了）


// 示例：只保留带有 name 属性的对象
type WithName<T> = T extends { name: any } ? T : never

type W = WithName<
  { name: string } 
  | { age: number } 
  | { name: string; age: number }
  | boolean
>
// 结果：{ name: string } | { name: string; age: number }


/**
 * 反向过滤：移除 T 中满足条件的成员
 */
type Remove<T, Condition> = T extends Condition ? never : T

type NoStrings<T> = Remove<T, string>

type NS = NoStrings<'a' | 1 | true | 'b' | 2 | false>
// 结果：1 | true | 2 | false  （字符串全部被过滤）
```

### 3.3 实战案例：基于属性值的类型过滤

```typescript
/**
 * 场景：你有一个用户列表的类型定义，
 * 你想筛选出所有"管理员"用户的类型
 */

type User =
  | { id: 1;  name: 'Alice';   role: 'admin' }
  | { id: 2;  name: 'Bob';     role: 'user' }
  | { id: 3;  name: 'Charlie'; role: 'admin' }
  | { id: 4;  name: 'Diana';   role: 'moderator' }

/**
 * 提取角色为特定值的用户类型
 */
type UsersByRole<U, Role extends string> = 
  U extends { role: Role } ? U : never

type Admins = UsersByRole<User, 'admin'>
// 结果：
// | { id: 1; name: 'Alice'; role: 'admin' }
// | { id: 3; name: 'Charlie'; role: 'admin' }

/**
 * 更通用的版本：按任意属性的值来过滤
 */
type ByProperty<T, K extends keyof T, V> =
  T extends Record<K, V> ? T : never

type NamedAlice = ByProperty<User, 'name', 'Alice'>
// 结果：{ id: 1; name: 'Alice'; role: 'admin' }
```

### 3.4 never 与 Avoid 模式

有时候你不想要分布式行为，但又不得不使用条件类型。这时候需要避免 `never` 的干扰：

```typescript
/**
 * 问题：当你想对 never 本身做条件判断时...
 */
type Check<T> = T extends string ? '是字符串' : '不是'

type C1 = Check<never>
// 期望：'不是'（因为 never 不是 string 子集...等等，actually never 是所有类型子集）
// 实际：never ← 分发导致被跳过！

/**
 * 解决方案：用一个元组包裹 T 来阻止分布式
 *
 * 原理：T 出现在元组内部时不再是"裸类型参数"，所以不会触发分发
 */
type SafeCheck<T> = [T] extends [string] ? '是字符串' : '不是'

type SC1 = SafeCheck<never>
// [never] extends [string]?
// → never 不是 string 的子集...不对，never 是所有类型子集
// → 实际上 never extends string 为 true
// 结果：'是字符串'

type SC2 = SafeCheck<number>
// [number] extends [string]? → false → '不是字符串' ✓


/**
 * 通用的"禁止分发"包装器
 */
type NoDistribute<T> = [T] extends [never] ? never : [T][0]

// 使用场景：确保即使传入联合类型也不会分发
type ND = NoDistribute<string | number>
// 结果：string | number（保持不变，但没有被分发处理）
```

## 四、高级分发模式

### 4.1 多层嵌套分发

当有多个裸类型参数时，分发会发生在多个维度：

```typescript
/**
 * 双重分发：T 和 U 都是裸参数且都是联合类型时
 * 会产生笛卡尔积式的组合
 */
type DoubleDistribute<T, U> = T extends U ? '[match]' : '[mismatch]'

type DD = DoubleDistribute<'a' | 'b', 'a' | 'c'>

// T 有 2 个成员，U 有 2 个成员 → 2 × 2 = 4 种组合
//
// 组合 1：T='a', U='a' → 'a' extends 'a'? → '[match]'
// 组合 2：T='a', U='c' → 'a' extends 'c'? → '[mismatch]'
// 组合 3：T='b', U='a' → 'b' extends 'a'? → '[mismatch]'
// 组合 4：T='b', U='c' → 'b' extends 'c'? → '[mismatch]'
//
// 最终结果：'[match]' | '[mismatch]'
// （注意：相同的值在联合类型中会被去重）
```

**生活类比**：

```
想象你有两副扑克牌：

牌堆 T（花色）：♠ ♥ ♦ ♣
牌堆 U（点数）：A K Q J

双重分发就像是：
  把每一张花色牌，和每一张点数牌都配对一次
  
  ♠A  ♠K  ♠Q  ♠J
  ♥A  ♥K  ♥Q  ♥J
  ♦A  ♦K  ♦Q  ♦J
  ♣A  ♣K  ♣Q  ♣J

总共 4 × 4 = 16 种组合
每种组合独立地经过"条件判断"的筛选
```

### 4.2 分发与递归的结合

分布式条件类型和递归类型结合后，威力大增：

```typescript
/**
 * DeepPartial —— 递归地将所有属性变为可选
 * 
 * 结合了：
 * - 映射类型（遍历属性）
 * - 条件类型（判断是否为对象）
 * - 递归（深入嵌套结构）
 * - 分布式（处理可选标记）
 */
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object
    ? DeepPartial<T[P]>      // 如果是对象，递归处理
    : T[P]                   // 否则保持不变
}

// 测试
type Config = {
  database: {
    host: string
    port: number
    credentials: {
      username: string
      password: string
    }
  }
  cache: {
    enabled: boolean
    ttl: number
  }
  debug: boolean
}

type PartialConfig = DeepPartial<Config>
// 所有层级都可以省略：
// {
//   database?: {
//     host?: string
//     port?: number
//     credentials?: {
//       username?: string
//       password?: string
//     }
//   }
//   cache?: {
//     enabled?: boolean
//     ttl?: number
//   }
//   debug?: boolean
// }


/**
 * DeepRequired —— 反过来，递归地将所有属性变为必需
 */
type DeepRequired<T> = {
  [P in keyof T]-?: Required<T[P] extends object
    ? DeepRequired<Required<T[P]>>
    : Required<T[P]>
}


/**
 * DeepReadonly —— 递归地将所有属性设为 readonly
 */
type DeepReadonly<T> = {
  readonly [P in keyof T]: T[P] extends object
    ? DeepReadonly<T[P]>
    : T[P]
}
```

### 4.3 分发用于类型守卫工厂

分布式条件类型在运行时的对应物就是**类型守卫**。结合使用可以实现非常强大的类型收窄：

```typescript
/**
 * 创建一个类型守卫函数，用于在运行时区分联合类型的成员
 */
function isType<T>(
  value: unknown,
  checkFn: (v: unknown) => v is T
): value is T {
  return checkFn(value)
}

// 更实用的：自动化的联合类型守卫生成器
type Guard<T> = (value: unknown) => value is T

function createGuard<T>(checkFn: (v: unknown) => v is T): Guard<T> {
  return checkFn
}

// 实际用法
const isString = createGuard((v): v is string => typeof v === 'string')
const isNumber = createGuard((v): v is number => typeof v === 'number')

function process(value: string | number | boolean) {
  if (isString(value)) {
    // value 在这里被收窄为 string
    console.log(value.toUpperCase())
  } else if (isNumber(value)) {
    // value 在这里被收窄为 number
    console.log(value.toFixed(2))
  } else {
    // value 在这里被收窄为 boolean
    console.log(value ? 'TRUE' : 'FALSE')
  }
}
```

### 4.4 分发用于路由匹配系统

这是一个更接近真实项目的实战案例——利用分布式条件类型实现类型安全的路由匹配：

```typescript
/**
 * 定义路由配置的类型
 */
type RouteConfig =
  | { path: '/home'; query: never }
  | { path: '/users/:id'; query: { id: string } }
  | { path: '/posts/:postId/comments/:commentId'; query: { postId: string; commentId: string } }
  | { path: '/search'; query: { q: string; page?: number } }

/**
 * 从路径中提取参数
 * 
 * 这里利用分布式来匹配每一条路由
 */
type MatchRoute<Path extends string, Routes> = 
  Routes extends { path: Path; query: infer Q }
    ? Q
    : Routes extends { path: infer P; query: infer Q }
      ? Path extends P
        ? ExtractParams<Path, P>
        : never
      : never

type ExtractParams<Template, Actual> = 
  Template extends `${infer _}:${infer Param}/${infer Rest}`
    ? Actual extends `${infer _}:${infer Value}/${infer Rest2}`
      ? { [K in Param | ExtractParams<Rest, Rest2>]: string }
      : never
    : Template extends `${infer _}:${infer Param}`
      ? Actual extends `${infer _}:${infer Value}`
        ? { [K in Param]: string }
        : never
      : {}

// 使用
type HomeQuery = MatchRoute<'/home', RouteConfig>
// 结果：never（/home 没有参数）

type UserQuery = MatchRoute<'/users/:id', RouteConfig>
// 结果：{ id: string }
```

## 五、常见陷阱与调试技巧

### 5.1 陷阱一：意外的分发导致意外结果

```typescript
/**
 * 问题：你想检查 T 是否是某个类型的子类型
 * 但 T 可能是联合类型，导致意外分发
 */

// 你的本意：
type IsString<T> = T extends string ? true : false

type Test = IsString<'hello' | 42>
// 你可能期望：false（因为 'hello'|42 整体不是 string 子类型）
// 实际结果：true | false  （分发了！'hello'→true, 42→false）

// 解决方法：用元组包裹防止分发
type IsStringStrict<T> = [T] extends [string] ? true : false

type TestStrict = IsStringStrict<'hello' | 42>
// ['hello' | 42] extends [string]？
// → 联合类型不能直接赋值给单一类型 → false ✓
```

### 5.2 陷阱二：never 导致的条件短路

```typescript
/**
 * 问题：当 T 可能为 never 时，整个条件类型可能返回 never
 */
type Process<T> = T extends object ? 'object' : 'primitive'

type P1 = Process<never>
// 期望：'primitive'（never 不是 object...嗯实际上 never 是所有类型子集...）
// 实际：never ← 被分发跳过了

// 如果你确实想处理 never 的情况：
type ProcessSafe<T> = 
  [T] extends [never]
    ? 'this-is-never'     // 特殊处理 never
    : T extends object
      ? 'object'
      : 'primitive'

type PS1 = ProcessSafe<never>    // 'this-is-never' ✓
type PS2 = ProcessSafe<{x: 1}>  // 'object' ✓
type PS3 = ProcessSafe<42>       // 'primitive' ✓
```

### 5.3 陷阱三：交叉类型中的 never 消失

```typescript
/**
 * 问题：never 在交叉类型中会被"吸收"
 */
type Cross1 = never & string
// 结果：never（∩ anything = ∅）

type Cross2 = { a: never }
// 结果：{ a: never }  （作为属性值可以保留）

type Cross3 = never & { a: string } & { b: number }
// 结果：never

// 但在接口/对象中，never 属性有特殊用途：
type ImpossibleKeys = {
  a: string
  b: never  // 表示 b 属性不能存在（不能赋值除 never 外的任何值）
}

let obj: ImpossibleKeys = { a: 'hello' }       // ✓
let obj2: ImpossibleKeys = { a: 'hello', b: 1 } // ✗ 1 不能赋值给 never
```

### 5.4 调试技巧：可视化分发过程

当你不确定一个复杂条件类型是如何被分发的时，可以使用以下调试手段：

```typescript
/**
 * 技巧 1：中间类型变量法
 * 把每一步的结果输出为一个命名类型
 */
type DebugStep1<T> = T extends string ? `[${T}是字符串]` : `[${T}不是字符串]`

type D1 = DebugStep1<'a' | 1 | true>
// 查看 IDE 提示：['a'是字符串] | [1不是字符串] | [true不是字符串]

/**
 * 技巧 2：计数法 —— 计算联合类型有多少个成员
 */
type CountUnion<T, R extends any[] =[]> = 
  T extends any
    ? CountUnion<Exclude<T, T>, [unknown, ...R]>
    : R['length']

// 注意：上面的写法有问题，正确的方式更复杂
// 简单版本：
type TupleLength<T extends any[]> = T['length']


/**
 * 技巧 3：条件式错误报告
 * 让类型告诉你它"看到了什么"
 */
type ShowType<T> = T extends infer S ? { __debug__: S } : never

type ST = ShowType<string | number>
// IDE 显示：{ __debug__: string } | { __debug__: number }
// 这样你能清楚地看到分发后的每个分支"看到"的 T 是什么
```

## 六、总结

分布式条件类型是 TypeScript 类型系统中最为精妙的设计之一。它的核心思想可以用以下层次来概括：

**第一层：现象认知**——知道 `T extends X ? Y : Z` 在 T 为联合时会自动分发到每个成员。这是最基本的观察。

**第二层：触发条件**——理解"裸类型参数"的含义和重要性，知道如何用 `[T]` 包裹来阻止分发，知道 `never` 作为空联合的特殊行为。

**第三层：工程实践**——能够利用分发实现 `Exclude`、`Extract`、`Filter` 等实用工具类型；能够在路由匹配、状态管理、API 层等场景中应用分发模式。

**第四层：创造性运用**——将分发与递归、映射类型、模板字面量等特性组合，构建出 `DeepPartial`、`UnionToArray`、`IsUnion` 等高级类型工具。

> **一句话带走**：分布式条件类型就像一台**自动分拣机**——你往里面倒一袋混合原料（联合类型），它会自动把每一种原料分开，送到各自的加工流水线上处理（条件分支），最后再把所有产品打包在一起（联合结果）。理解这台机器的工作原理，你就掌握了 TypeScript 类型体操中最强大的自动化工具之一。
