# infer 的协变与逆变位置 —— 在不同位置的推导行为

> **核心问题**：为什么 `Promise<string>` 能用 `infer T` 推导出 `string`，但 `((x: string) => void)` 推导出的参数类型却变成了 `unknown`？为什么数组中的 `infer` 和函数参数中的 `infer` 行为截然不同？这一切都与**型变（Variance）**有关——而 `infer` 关键字在不同型变位置的表现，决定了它能"记住"什么、"遗忘"什么。

---

## 一、infer 基础回顾

### 1.1 infer 是什么？

在深入协变和逆变的细节之前，先确保我们对 `infer` 有一个稳固的基础认知：

```
╔══════════════════════════════════════════════════════════╗
║                                                          ║
║  infer = inference（推断/推导）                            ║
║                                                          ║
║  它只能在条件类型的 extends 子句中使用                     ║
║  用于"反向提取"类型中的某一部分                             ║
║                                                          ║
║  语法：type X = SomeType<infer U> ? U : never            ║
║                                                          ║
║  含义：如果 SomeType 匹配成功，则将其类型参数提取为 U      ║
║                                                          ║
╚══════════════════════════════════════════════════════════╝
```

**生活类比：拆礼物**

```typescript
// 想象 Promise<T> 就像一个包装好的礼物盒
// 你知道它是 Promise 类型的（知道盒子的形状）
// 但不知道里面的 T 具体是什么（不知道礼物是什么）

type UnwrapPromise<T> = T extends Promise<infer Inner> ? Inner : T

// 这就像：
// "如果这个盒子是 Promise 形状的，
//  那就把里面的东西拿出来给我"
//
type P1 = UnwrapPromise<Promise<string>>  // string —— 盒子里是字符串
type P2 = UnwrapPromise<Promise<number>>  // number —— 盒子里是数字
type P3 = UnwrapPromise<string>           // string —— 不是盒子，原样返回
```

### 1.2 infer 可以出现的所有位置

`infer` 可以在多种上下文中使用，每种上下文的"型变性质"不同：

```typescript
// ═══════════════════════════════════════
// 位置 1：泛型参数位置（协变位置）
// ═══════════════════════════════════════

type GetPromiseValue<T> = T extends Promise<infer V> ? V : never
//                                    ^^^^^^^^
//                                    infer 在 Promise 的类型参数位置
//                                    这是一个"产出"位置（返回值的类型）

type GP1 = GetPromiseValue<Promise<string>>  // string
type GP2 = GetPromiseValue<Promise<number>>  // number
type GP3 = GetPromiseValue<Promise<boolean>> // boolean


// ═══════════════════════════════════════
// 位置 2：函数返回值位置（协变位置）
// ═══════════════════════════════════════

type GetReturnType<T> = T extends (...args: any[]) => infer R ? R : never
//                                                  ^^^^^^^^
//                                                  infer 在返回值位置
//                                                  函数"产出"返回值

type GR1 = GetReturnType<() => string>     // string
type GR2 = GetReturnType<(x: number) => boolean>  // boolean
type GR3 = GetReturnType<(a: string, b: number) => { x: number }>
// { x: number }


// ═══════════════════════════════════════
// 位置 3：函数参数位置（逆变位置）
// ═══════════════════════════════════════

type GetFirstArg<T> = T extends (arg: infer A, ...rest: any[]) => any ? A : never
//                                       ^^^^^^^^
//                                       infer 在第一个参数位置
//                                       函数"消费"参数

type GA1 = GetFirstArg<(x: string) => void>    // string
type GA2 = GetFirstArg<(x: number) => void>    // number
type GA3 = GetFirstArg<(x: { a: string }) => void>  // { a: string }


// ═══════════════════════════════════════
// 位置 4：数组的元素位置（协变位置）
// ═══════════════════════════════════════

type ArrayElement<T> = T extends (infer E)[] ? E : never
//                                   ^^^^^^
//                                   infer 在数组元素位置
//                                   数组"包含"元素

type AE1 = ArrayElement<string[]>       // string
type AE2 = ArrayElement<number[]>       // number
type AE3 = ArrayElement<Array<{x: number}>>  // { x: number }


// ═══════════════════════════════════════
// 位置 5：对象属性位置（协变位置，如果是读取的话）
// ═══════════════════════════════════════

type GetValueType<T, K extends keyof T> = T extends { [key in K]: infer V } ? V : never
//                                                        ^^^^^^^^
//                                                        infer 在属性值位置

type GV1 = GetValueType<{ name: string; age: number }, 'name'>  // string
type GV2 = GetValueType<{ name: string; age: number }, 'age'>   // number


// ═══════════════════════════════════════
// 位置 6：元组的固定位置
// ═══════════════════════════════════════

type First<T extends any[]> = T extends [infer F, ...any[]] ? F : never
type Second<T extends any[]> = T extends [any, infer S, ...any[]] ? S : never
type Last<T extends any[]> = T extends [...any[], infer L] ? L : never

type F1 = First<[string, number, boolean]>   // string
type S1 = Second<[string, number, boolean]>  // number
type L1 = Last<[string, number, boolean]>    // boolean
```

## 二、协变位置 vs 逆变位置

### 2.1 什么是协变和逆变？

在开始讨论 `infer` 在不同位置的行为差异之前，我们需要先搞清楚**协变**和**逆变**这两个概念：

```
═══════════════════════════════════════════════════
           型变（Variance）的本质
═══════════════════════════════════════════════════

假设类型继承关系：Dog extends Animal（狗是动物的子类型）

【协变 Covariant】方向一致 ↑
────────────────
  Dog ⊆ Animal
  → Array<Dog> ⊆ Array<Animal>    方向相同 → 协变
  → Promise<Dog> ⊆ Promise<Animal>
  → 返回值位置也如此
  
  直觉："产出"的位置是协变的
       函数返回一个 Dog，当然也可以说返回了一个 Animal
       （具体的东西可以当一般的用）


【逆变 Contravariant】方向相反 ↓
────────────────
  Dog ⊆ Animal
  → ((x: Dog) => void) ⊇ ((x: Animal) => void)  方向相反 → 逆变
  → 函数参数位置是逆变的
  
  直觉："消费"的位置是逆变的
       一个接受 Animal 的函数，不一定能接受 Dog（因为它可能调用 Animal 专有的方法）
       反过来，一个接受 Dog 的函数，一定可以接受 Animal（Dog 就是 Animal）
       
       等等...让我重新理清：
       
       参数要求 Dog → 只接收 Dog（ stricter / narrower ）
       参数要求 Animal → 接收一切动物（ more lenient / wider ）
       
       ((x: Dog) => void) 能否赋值给 ((x: Animal) => void)？
       不能！因为前者只能处理 Dog，后者可能收到 Cat
       
       ((x: Animal) => void) 能否赋值给 ((x: Dog) => void)？
       能！前者能处理所有动物，包括 Dog
       
       所以：(Dog→void) 是 (Animal→void) 的子类型？不对...
       实际上是反过来的：(Animal→void) ⊆ (Dog→void)
       参数类型越宽泛，函数类型越"具体"


【不变 Invariant】不允许变化
────────────────
  Dog ⊆ Animal
  → { x: Dog } 和 { x: Animal} 不可互相赋值（对于可写属性）
  
  直觉："读写"双重要求 → 必须精确匹配

═══════════════════════════════════════════════════
```

### 2.2 用水管的类比理解型变

```
想象数据流经一根管道（函数），从入口流向出口：

  入口（参数位置）──→ [ 处理逻辑 ] ──→ 出口（返回值位置）
  
  【出口 = 协变位置】
  ┌────────────────────────────────────────┐
  │                                        │
  │   出来的水是"纯净水"(Dog)              │
  │   那么说出来的水是"饮用水"(Animal)也对  │
  │   （纯净水当然是饮用水的一种）           │
  │                                        │
  │   具体 → 一般：✓ 允许（协变）           │
  │                                        │
  └────────────────────────────────────────┘
  
  
  【入口 = 逆变位置】
  ┌────────────────────────────────────────┐
  │                                        │
  │   管道声明"我只接受纯净水"(Dog)         │
  │   你往里倒"饮用水"(Animal)行不行？       │
  │   不行！万一里面有杂质呢！              │
  │                                        │
  │   但反过来：                            │
  │   管道声明"我接受任何饮用水"(Animal)     │
  │   你往里倒"纯净水"(Dog)行不行？          │
  │   当然行！（纯净水是最好的饮用水）        │
  │                                        │
  │   具体(Dog)的要求 比 一般(Animal)的要求 更严格  │
  │   更严格的函数 是 更宽松函数 的"升级版"      │
  │                                        │
  │   所以参数位置的继承关系是反过来的（逆变）  │
  │                                        │
  └────────────────────────────────────────┘
```

### 2.3 各位置的型变分类表

```
╔═══════════════════════════════════════════════════════════╗
║                                                           ║
║  位置                    型变        数据流向            ║
║  ─────────────────────────────────────────────────────── ║
║  泛型参数（如 Promise<T>）  协变       产出（output）     ║
║  函数返回值                协变       产出（output）     ║
║  数组元素                  协变       包含（contain）    ║
║  对象属性值（读）          协变       提供（provide）    ║
║  元组成员                  协变       包含（contain）    ║
║  ─────────────────────────────────────────────────────── ║
║  函数参数                  逆变       消费（consume）    ║
║  方法参数                  逆变       消费（consume）    ║
║  ═══════════════════════════════════════════════════════ ║
║  对象属性值（写）          不变       双向（bidirectional）║
║  可变数组 push 的参数      不变       双向                 ║
║                                                           ║
╚═══════════════════════════════════════════════════════════╝
```

## 三、infer 在协变位置的行为

### 3.1 协变位置 infer 的基本表现

在**协变位置**（如返回值、泛型参数、数组元素），`infer` 表现得非常直观——它推导出的是**最宽的合理类型**（即联合类型中的所有可能性都会被保留）：

```typescript
/**
 * 场景：从联合类型的 Promise 中提取值
 */
type ExtractPromise<T> = T extends Promise<infer V> ? V : never

// 单一类型的情况
type E1 = ExtractPromise<Promise<string>>  // string ✓

// 联合类型的情况
type E2 = ExtractPromise<Promise<string> | Promise<number>>
// 结果：string | number
//
// 解释：
// Promise<string> 匹配成功 → V = string
// Promise<number> 匹配成功 → V = number
// 联合在一起 → string | number
//
// 协变位置的 infer 保留了所有可能的类型信息


/**
 * 场景：从函数返回值中提取
 */
type ReturnTypes<T> = T extends (...args: any[]) => infer R ? R : never

type RT1 = ReturnTypes<() => string | (() => number) | (() => boolean)>
// 结果：string | number | boolean
//
// 每个函数的返回值被分别提取，然后联合
```

### 3.2 协变位置的"扩展"倾向

协变位置的 `infer` 有一种**扩展（widening）**倾向——它倾向于推导出更宽泛的类型，而不是更具体的：

```typescript
/**
 * 即使实际传入的字面量很具体，
 * 协变位置的 infer 也可能会"放宽"
 */
type GetArrayItem<T> = T extends Array<infer Item> ? Item : never

type G1 = GetArrayItem<['a', 'b', 'c']>
// 结果：string（而不是 'a' | 'b' | 'c'）
//
// 原因：['a','b','c'] 的类型被推断为 string[]
// 而不是 ('a'|'b'|'c')[]
// 数组字面量的默认推断就是 widen 的


// 如果你想保留字面量类型，需要用 as const
type G2 = GetArrayItem<readonly ['a', 'b', 'c']>
// 结果：'a' | 'b' | 'c'（readonly 元组保留了字面量）
```

### 3.3 协变 infer 实战：解构嵌套容器

```typescript
/**
 * 实战 1：多层 Promise 解包
 */
type Unwrap<T> =
  T extends Promise<infer Inner>
    ? Unwrap<Inner>      // 如果还是 Promise，继续解
    : T                  // 直到不是 Promise 了

type U1 = Unwrap<Promise<Promise<Promise<string>>>>
// 结果：string（三层 Promise 全部剥去）

type U2 = Unwrap<Promise<Promise<number>>>
// 结果：number（两层）

type U3 = Unwrap<string>
// 结果：string（本来就不是 Promise）


/**
 * 实战 2：从 React 组件中提取 Props 类型
 */
import { ComponentType } from 'react'

type GetComponentProps<C extends ComponentType<any>> = 
  C extends ComponentType<infer P> ? P : never

// 假设有一个组件
// function Button(props: { label: string; onClick: () => void }) { ... }
//
// type ButtonProps = GetComponentProps<typeof Button>
// 结果：{ label: string; onClick: () => void }


/**
 * 实战 3：从元组中提取所有类型（利用协变位置的多次 infer）
 */
type TupleElements<T extends any[]> = 
  T extends [infer First, ...infer Rest]
    ? [First, ...TupleElements<Rest>]
    : []

type TE = TupleElements<[string, number, boolean, { x: string }]>
// 结果：[string, number, boolean, { x: string }]
```

### 3.4 协变 infer 与条件类型的配合

协变位置的 `infer` 可以与条件类型产生强大的化学反应：

```typescript
/**
 * 提取所有 Promise 成功值的类型（忽略非 Promise）
 */
type AwaitedValues<T> = T extends Promise<infer V> ? V : never

type AV = AwaitedValues<
  | Promise<string>
  | number
  | Promise<{ code: number; msg: string }>
  | boolean
  | Promise<number[]>
>
// 过程：
// Promise<string>           → string
// number                    → never（不是 Promise）
// Promise<{code,msg}>       → { code: number; msg: string }
// boolean                   → never（不是 Promise）
// Promise<number[]>         → number[]
//
// 最终：string | { code: number; msg: string } | number[]


/**
 * 只提取某种特定形状的 Promise 值
 */
type StringPromises<T> = T extends Promise<infer V extends string> ? V : never

type SP = StringPromises<
  Promise<string> | Promise<number> | Promise<boolean>
>
// 结果：string
// 只有 V extends string 的才被保留
```

## 四、infer 在逆变位置的行为

### 4.1 逆变位置 infer 的"收缩"倾向

这是 `infer` 最令人困惑的地方。在**逆变位置**（主要是函数参数），`infer` 的行为与协变位置截然不同：

```typescript
/**
 * ⚠️ 注意这里的反直觉行为！
 */

// 协变位置（正常行为）
type Return<T> = T extends (...args: any[]) => infer R ? R : never
type RN = Return<(x: string) => void | (x: number) => void>
// 结果：void | void = void（两个都是 void）


// 逆变位置（特殊行为！）
type FirstArg<T> = T extends (x: infer A) => any ? A : never
type FA = FirstArg<(x: string) => void | (x: number) => void>
//
// 你可能期望：string | number（像协变位置一样）
// 实际结果：string & number = never !!!
//
// 为什么？？？
```

**为什么会这样？这背后的深层原因是：**

```
═══════════════════════════════════════════════════
       逆变位置 infer 的推导逻辑
═══════════════════════════════════════════════════

考虑两个函数类型：
  F1: (x: string) => void
  F2: (x: number) => void

它们的联合类型是：F1 | F2

当我们写：
  type A = (F1 | F2) extends (x: infer A) => any ? A : never

TypeScript 问自己一个问题：
  "什么样的类型 A，使得 (x:A)=>any 同时兼容 F1 和 F2？"

由于参数位置是逆变的：
  F1 要求参数是 string（或者其父类型）
  F2 要求参数是 number（或者其父类型）
  
  要同时满足两个函数的参数要求，
  A 必须既是 string 的父类型，又是 number 的父类型。
  
  也就是说：A ⊇ string 且 A ⊇ number
  → A 必须是 string 和 number 的**最小公共父类型**
  
  但 string 和 number 没有共同的子类型关系...
  
  实际上 TypeScript 的做法更严格：
  逆变位置的 infer 在面对联合类型时，
  推导出的是**交叉类型（intersection）**
  
  string & number = never（没有值既是 string 又是 number）
═══════════════════════════════════════════════════
```

### 4.2 用生活场景理解逆变 infer

```
想象你在组织一场招聘面试：

有两个面试官，他们对候选人有不同的要求：

面试官 Alice：（候选人 must be 前端工程师）→ 通过
面试官 Bob：  （候选人 must be 后端工程师）→ 通过

现在问：什么样的候选人能同时让 Alice 和 Bob 都满意？

候选人必须：
  ✓ 是前端工程师（满足 Alice）
  ✓ 是后端工程师（满足 Bob）

→ 候选人必须是 全栈工程师！（前端 AND 后端的交集）

但在 TypeScript 类型世界中：
  string 和 number 没有交集
  → string & number = never（不存在这样的值）

这就是逆变位置 infer 推导出 never 的原因——
它在寻找能同时满足所有函数的"最小上界"，
但有时候这个界根本不存在。
```

### 4.3 什么时候逆变 infer 有用？

虽然逆变 infer 在联合类型上的行为看似"没用"（总是得到 `never` 或极窄的交叉类型），但它在某些特定场景下非常有价值：

```typescript
/**
 * 用途 1：提取回调参数的类型（单一类型场景）
 */
type CallbackParam<T> = T extends (cb: (arg: infer P) => void) => void ? P : never

// 注册事件的典型模式
function onEvent(handler: (event: MouseEvent) => void): void { /* ... */ }
function onData(handler: (data: string) => void): void { /* ... */ }

type EP1 = CallbackParam<typeof onEvent>   // MouseEvent ✓
type EP2 = CallbackParam<typeof onData>    // string ✓
// 单一函数类型时，逆变 infer 正常工作！


/**
 * 用途 2：构造函数参数提取
 */
type ConstructorParams<T> = T extends new (...args: infer A) => any ? A : never

class Person {
  constructor(name: string, age: number) {}
}
class Car {
  constructor(model: string, year: number, color: string) {}
}

type PP = ConstructorParams<typeof Person>  // [name: string, age: number]
type CP = ConstructorParams<typeof Car>     // [model: string, year: number, color: string]


/**
 * 用途 3：检测函数是否有特定签名的参数
 */
type HasStringParam<T> = T extends (x: string) => any ? true : false

type HSP1 = HasStringParam<(s: string) => void>    // true ✓
type HSP2 = HasStringParam<(n: number) => void>    // false ✓
type HSP3 = HasStringParam<(x: any) => void>       // true (any 包含 string)


/**
 * 用途 4：高阶函数的类型传递
 */
function apply<F extends (x: infer A) => any>(fn: F, arg: A): ReturnType<F> {
  return fn(arg)
}

// A 被推断为 fn 的参数类型
const r1 = apply((x: number) => x * 2, 10)        // r1: number
const r2 = apply((s: string) => s.toUpperCase(), 'hi')  // r2: string
```

### 4.4 如何绕过逆变 infer 的限制

当你想在函数参数位置进行类似协变的推导时，有几个技巧：

```typescript
/**
 * 技巧 1：翻转函数 —— 把参数变成返回值
 *
 * 原理：如果我们控制函数的定义方式，
 *       可以把需要推导的信息放到返回值位置（协变位置）
 */
type Flip<Func extends (...args: any[]) => any> = 
  (...args: Parameters<Func>) => { args: Parameters<Func>; return: ReturnType<Func> }

// 这样参数信息就"流"到了返回值位置


/**
 * 技巧 2：用元组收集参数
 */
type AllParams<T> = T extends (...args: infer A) => any ? A : never

// 元组类型是协变的（整体来看），所以可以正常推导
type AP = AllParams<(a: string, b: number, c: boolean) => void>
// 结果：[a: string, b: number, c: boolean]


/**
 * 技巧 3：使用变体注解强制指定型变
 *
 * TypeScript 4.7+ 支持 in/out 关键字
 */
type Contravariant<in out T> = T

// 在自定义泛型中明确标注型变
type Mapper<in T, out U> = (input: T) => U
// T 是逆变的（in），U 是协变的（out）
```

## 五、多位置 infer 的协同

### 5.1 同时提取函数的输入和输出

在实际编程中，我们经常需要同时了解一个函数"吃什么"和"吐什么"：

```typescript
/**
 * 完整的函数签名分解
 */
type FunctionSignature<T> = T extends (...args: infer Args) => infer Return
  ? { args: Args; returnType: Return }
  : never

type FS = FunctionSignature<(name: string, age: number) => boolean>
// 结果：{
//   args: [name: string, age: number];
//   returnType: boolean
// }


/**
 * 更精细的版本：分离每个参数
 */
type DetailedSignature<T> = T extends (
  firstArg: infer First,
  ...restArgs: infer Rest
) => infer Ret
  ? { first: First; rest: Rest; return: Ret }
  : never

type DS = DetailedSignature<(x: string, y: number, z: boolean) => void>
// 结果：{
//   first: string;
//   rest: [y: number, z: boolean];
//   return: void
// }
```

### 5.2 从事件系统中提取类型

```typescript
/**
 * 实战：类型安全的事件系统
 * 
 * 利用多位置 infer 从事件处理器中提取事件类型和处理器的参数类型
 */

type EventMap = {
  'click': { x: number; y: number; target: HTMLElement }
  'keydown': { key: string; code: string; ctrlKey: boolean }
  'resize': { width: number; height: number }
}

/**
 * 从 EventMap 提取事件名称和事件对象类型
 */
type EventHandler<E> = E extends {
  [K in keyof EventMap]: (event: infer Event) => void
}[keyof EventMap]
  ? Event
  : never

// 或者更好的写法：
type EventType<Map, Key extends keyof Map> = 
  Map[Key] extends (event: infer E) => any ? E : never

type ClickEvent = EventType<EventMap, 'click'>
// { x: number; y: number; target: HTMLElement }

type KeydownEvent = EventType<EventMap, 'keydown'>
// { key: string; code: string; ctrlKey: boolean }
```

### 5.3 从 Promise 链中提取中间类型

```typescript
/**
 * 分析一个 .then() 链中每一步的类型变换
 */
type ThenChain<T> = 
  T extends Promise<infer Current>
    ? Current extends (arg: infer Input) => Promise<infer Output>
      ? { input: Input; output: Output; next: ThenChain<Promise<Output>> }
      : { current: Current }
    : never

// 对于链：fetch(url).then(r => r.json()).then(data => processData(data))
// 可以分析每一步的输入输出类型
```

## 六、常见陷阱与解决方案

### 6.1 陷阱：联合类型在逆变位置消失

```typescript
/**
 * 问题代码
 */
type GetCallbackArg<T> = T extends (cb: (arg: infer A) => void) => void ? A : never

type Bad = GetCallbackArg<
  ((cb: (x: string) => void) => void) |
  ((cb: (x: number) => void) => void)
>
// 期望：string | number
// 实际：string & number = never  💥

/**
 * 解决方案：用元组包裹后处理
 */
type GetCallbackArgFixed<T> = 
  T extends (cb: (arg: infer A) => void) => void 
    ? [A]        // 先放进元组（协变位置！）
    : never

type FixedResult = GetCallbackArgFixed<
  ((cb: (x: string) => void) => void) |
  ((cb: (x: number) => void) => void)
>
// 结果：[string] | [number]
// 再取 [number] 就能得到 string | number

type Final = GetCallbackArgFixed<
  ((cb: (x: string) => void) => void) |
  ((cb: (x: number) => void) => void)
>[number]
// 结果：string | number ✓
```

### 6.2 陷阱：条件类型嵌套导致的 infer 丢失

```typescript
/**
 * 问题：多层条件类型嵌套时，内层的 infer 可能无法正确绑定
 */
type ComplexExtract<T> = 
  T extends Promise<infer Inner>
    ? Inner extends (arg: infer A) => infer R
      ? { arg: A; ret: R }
      : never
    : never

// 这种嵌套通常是 OK 的
type CE = ComplexExtract<Promise<(s: string) => number>>
// 结果：{ arg: string; ret: number } ✓

// 但如果结构不匹配：
type CE2 = ComplexExtract<Promise<string>>
// Inner = string
// string extends (arg: infer A) => infer R ？ → false
// 结果：never ✓（正确的行为）
```

### 6.3 陷阱：infer 与 distributive 的交互

```typescript
/**
 * 当 infer 出现在分布式条件类型中时
 */
type DistributedInfer<T> = T extends { a: infer A } ? A : never

type DI = DistributedInfer<{ a: string } | { a: number } | { b: boolean }>
// T 是裸类型参数 → 触发分布式
// 
// {a:string} matches → A=string
// {a:number} matches → A=number  
// {b:boolean} doesn't match → never
//
// 结果：string | number ✓
```

## 七、总结

`infer` 在不同位置的型变行为是 TypeScript 类型系统中最精妙的细节之一。掌握它，意味着你真正理解了类型如何在复合结构中流动。

**核心要点速查表**：

```
╔═══════════════════════════════════════════════════════╗
║                                                       ║
║  【协变位置 infer】（推荐优先使用）                     ║
║  · 位置：返回值、泛型参数、数组/元组元素、属性值        ║
║  · 行为：推导联合类型时保留所有可能性                   ║
║  · 倾向：扩展（widening）                              ║
║  · 适用：大部分类型提取场景                            ║
║                                                       ║
║  【逆变位置 infer】（谨慎使用）                         ║
║  · 位置：函数参数、方法参数                            ║
║  · 行为：推导联合类型时产生交叉类型（常为 never）       ║
║  · 倾向：收缩（narrowing）                             ║
║  · 适用：单一类型场景、构造函数参数提取                 ║
║                                                       ║
║  【黄金法则】                                          ║
║  尽量把需要推导的信息放在协变位置                       ║
║  如果必须在逆变位置推导，注意联合类型可能导致 never     ║
║  用 [T] 包裹可以把逆变位置的信息"搬运"到协变位置       ║
║                                                       ║
╚═══════════════════════════════════════════════════════╝
```

> **一句话带走**：`infer` 在协变位置像一个**慷慨的收集者**——不管进来多少种类型，它都照单全收；而在逆变位置它却像一个**严格的守门员**——只有所有人都同意的类型才能通过。选择正确的位置放置 `infer`，就是选择让你的类型推导是"宽容的"还是"严格的"。
