# 类型级 DSL 设计 —— 构建类型安全的查询构建器、状态机描述

> **核心问题**：如何设计一套**领域特定语言（DSL）**，让开发者能用声明式、接近自然语言的方式编写代码，同时在编译期获得完整的类型安全保障？本章将从零开始设计两套完整的类型级 DSL：一个是数据库查询构建器（Query Builder DSL），另一个是有限状态机描述语言（State Machine DSL）。通过这两个案例，你将学会如何在 TypeScript 中构建工业级的类型安全 DSL 系统。

---

## 一、什么是 DSL？为什么需要类型级 DSL？

### 1.1 从通用语言到专用语言

```
═══════════════════════════════════════════════════
             通用语言 vs 领域特定语言
═══════════════════════════════════════════════════

【通用编程语言 General-Purpose Language】
──────────────────────────────────
  如 TypeScript、Python、Java...
  特点：什么都能做，但对特定问题不够简洁

  例：用原生 TS 查询数据库
  ┌────────────────────────────────────────┐
  │ const result = await db.query(          │
  │   `SELECT u.name, p.title               │
  │    FROM users u                         │
  │    JOIN posts p ON p.user_id = u.id     │
  │    WHERE u.age > ? AND p.published = 1  │
  │    ORDER BY u.name ASC LIMIT ?`,        │
  │   [18, 10]                              │
  │ )                                       │
  └────────────────────────────────────────┘
  
  问题：
  • 字符串中的 SQL 无法被类型检查
  • 参数数量靠人工保证（多了少了都不知道）
  • 列名拼写错误要到运行才发现


【领域特定语言 Domain-Specific Language】
──────────────────────────────────
  为特定问题量身定制的迷你语言
  特点：表达能力受限但在该领域极度简洁和安全

  例：用 DSL 查询数据库
  ┌────────────────────────────────────────┐
  │ const result = await db                │
  │   .from('users')                       │
  │   .join('posts').on('user_id', 'id')   │
  │   .where('age', '>', 18)               │
  │   .and('published', '=', true)         │
  │   .orderBy('name', 'asc')              │
  │   .limit(10)                           │
  │   .selectMany<{                        │
  │     name: string;                      │
  │     title: string                      │
  │   }>()                                 │
  └────────────────────────────────────────┘
  
  优势：
  • 每一步都有类型提示
  • 列名自动补全
  • 参数类型自动校验
  • 整体结构在编译期验证
═══════════════════════════════════════════════════
```

### 1.2 生活类比：乐高 vs 3D 打印

| 维度 | 通用语言（3D 打印） | DSL（乐高积木） |
|------|---------------------|----------------|
| **自由度** | 几乎无限，可以做出任何形状 | 受限于已有零件的种类 |
| **上手难度** | 需要专业技能 | 拼搭即可，直觉性强 |
| **出错概率** | 高（自由带来风险） | 低（形状决定了能否拼接） |
| **效率** | 从零开始慢 | 快速组装标准部件 |
| **典型场景** | 全新发明 | 组装标准产品 |

**类型级 DSL** 就是给开发者提供一套"乐高积木"——你不需要知道每个积木内部是怎么制造的，只需要知道哪些积木可以拼在一起、拼出来是什么样子。而**类型系统**就是那个确保你不会把圆头插进方孔的"防呆机制"。

### 1.3 设计 DSL 的核心原则

在设计类型级 DSL 时，我们需要遵循几个关键原则：

```
╔══════════════════════════════════════════════════════════╗
║                                                          ║
║  类型级 DSL 设计原则                                      ║
║                                                          ║
║  1. 渐进式可推导（Progressive Typability）                 ║
║     每一步操作的返回类型都携带足够的上下文信息，           ║
║     使得下一步的操作能够自动获得类型提示                   ║
║                                                          ║
║  2. 非法状态不可表示（Illegal States Unrepresentable）    ║
║     类型层面排除所有非法的操作序列                        ║
║     如果编译通过了，运行时就不可能出现这类错误             ║
║                                                          ║
║  3. 自文档化（Self-documenting）                          ║
║     类型签名本身就是最好的文档                            ║
║     IDE 的自动补全就是交互式文档                          ║
║                                                          ║
║  4. 最小惊讶原则（Least Surprise）                        ║
║     API 行为符合直觉，边缘情况有明确的类型反馈             ║
║                                                          ║
╚══════════════════════════════════════════════════════════╝
```

## 二、案例一：类型安全查询构建器

### 2.1 需求分析

我们要构建一个数据库查询 DSL，支持以下操作链：

```
from(表名)
  → where(列名, 操作符, 值)
  → and(列名, 操作符, 值) | or(列名, 操作符, 值)
  → join(表名).on(左列, 右列)
  → orderBy(列名, 方向)
  → limit(数量)
  → offset(数量)
  → selectOne<T>() | selectMany<T>()
```

**类型安全目标**：
- `from()` 后只能跟该表中存在的列名
- `where()` 的值类型必须匹配列的类型
- `selectOne/selectMany` 的泛型参数必须包含所选列
- 操作顺序合理（如 `limit` 后不能再接 `where`）

### 2.2 定义数据模型

首先，我们需要描述数据库的 schema：

```typescript
/**
 * 数据库 Schema 定义
 *
 * 这是整个 DSL 的"真相来源"（Single Source of Truth）
 * 所有的类型推导都基于这个定义
 */

interface DBSchema {
  // ====== 用户表 ======
  users: {
    id: number           // 主键，自增
    name: string         // 姓名
    email: string        // 邮箱（唯一）
    age: number          // 年龄
    role: 'admin' | 'user' | 'guest'  // 角色
    active: boolean      // 是否激活
    createdAt: Date      // 创建时间
  }

  // ====== 文章表 ======
  posts: {
    id: number
    authorId: number     // 外键 → users.id
    title: string
    content: string
    status: 'draft' | 'published' | 'archived'
    publishedAt: Date | null
    viewCount: number
  }

  // ====== 评论表 ======
  comments: {
    id: number
    postId: number       // 外键 → posts.id
    authorId: number     // 外键 → users.id
    body: string
    createdAt: Date
  }
}

// 类型别名
type TableNames = keyof DBSchema
type ColumnsOf<T extends TableNames> = keyof DBSchema[T]
typeColumnType<T extends TableNames, C extends ColumnsOf<T>> = DBSchema[T][C]
```

### 2.3 构建器的状态机模型

查询构建器的本质是一个**有限状态机**——每个方法将状态从一个阶段推进到下一个阶段：

```
═══════════════════════════════════════════════════
        查询构建器的状态流转图
═══════════════════════════════════════════════════

  [Init] ──from()──→ [FromSet] ──where()──→ [WhereSet]     ↑
  (初始)             (表已选)          (条件已设)     │
                                           │              │
                                    and()/or()          join()
                                           │              │
                                           ↓              ↓
                                   [WhereSet+Join] ◄── [JoinSet]
                                   (条件和连接都有)

  [FromSet] / [WhereSet] / [WhereSet+Join]
      │
      ├── orderBy() ──→ [Ordered]
      ├── limit()    ──→ [Limited]
      │                    │
      │                offset() ──→ [Offset]
      │                                  │
      │                         selectOne/selectMany
      │                                  │
      │                                  ↓
      │                            [Complete] (终态)
      │
      └── selectMany() ──→ [Complete] (跳过 order/limit)


  关键：每个状态对应一个不同的 TypeScript 接口，
        该接口只暴露该状态下"合法"的方法！
        
═══════════════════════════════════════════════════
```

### 2.4 核心类型定义

```typescript
/**
 * 查询条件的类型表示
 */
interface WhereCondition<T extends TableNames, C extends ColumnsOf<T>> {
  column: C
  operator: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'LIKE' | 'IN' | 'IS NULL' | 'IS NOT NULL'
  value: ColumnType<T, C>
}

/**
 * JOIN 配置的类型
 */
interface JoinConfig<
  Primary extends TableNames,
  Joined extends TableNames
> {
  table: Joined
  leftColumn: ColumnsOf<Primary> | ColumnsOf<Joined>
  rightColumn: ColumnsOf<Primary> | ColumnsOf<Joined>
}

/**
 * 各阶段的查询接口
 */

/** 阶段 1：初始状态 —— 只能 from() */
interface QueryInit {
  from<T extends TableNames>(table: T): QueryFromSet<T>
}

/** 阶段 2：表已选择 —— 可以 where/join/order/limit/select */
interface QueryFromSet<T extends TableNames> {
  /** 添加 WHERE 条件 */
  where<C extends ColumnsOf<T>>(
    column: C,
    operator: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'LIKE',
    value: ColumnType<T, C>
  ): QueryWhereSet<T>

  /** 添加 JOIN */
  join<J extends TableNames>(
    table: J
  ): QueryJoinOn<T, J>

  /** 排序 */
  orderBy<C extends ColumnsOf<T>>(
    column: C,
    direction?: 'ASC' | 'DESC'
  ): QueryOrdered<T>

  /** 限制数量 */
  limit(n: number): QueryLimited<T>

  /** 直接选择（无条件） */
  selectOne<R>(): Promise<R | null>
  selectMany<R>(): Promise<R[]>
}

/** 阶段 3：条件已添加 —— 可以 and/or/join/order/limit */
interface QueryWhereSet<T extends TableNames> {
  and<C extends ColumnsOf<T>>(
    column: C,
    operator: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'LIKE',
    value: ColumnType<T, C>
  ): QueryWhereSet<T>

  or<C extends ColumnsOf<T>>(
    column: C,
    operator: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'LIKE',
    value: ColumnType<T, C>
  ): QueryWhereSet<T>

  join<J extends TableNames>(
    table: J
  ): QueryJoinOn<T, J>

  orderBy<C extends ColumnsOf<T>>(
    column: C,
    direction?: 'ASC' | 'DESC'
  ): QueryOrdered<T>

  limit(n: number): QueryLimited<T>

  selectOne<R>(): Promise<R | null>
  selectMany<R>(): Promise<R[]>
}

/** 阶段 4：等待 ON 条件 */
interface QueryJoinOn<P extends TableNames, J extends TableNames> {
  on(
    leftCol: ColumnsOf<P> | ColumnsOf<J>,
    rightCol: ColumnsOf<P> | ColumnsOf<J>
  ): QueryWhereSet<P | J>
}

/** 阶段 5：已排序 */
interface QueryOrdered<T extends TableNames> {
  limit(n: number): QueryLimited<T>
  selectOne<R>(): Promise<R | null>
  selectMany<R>(): Promise<R[]>
}

/** 阶段 6：已限制 */
interface QueryLimited<T extends TableNames> {
  offset(n: number): QueryReady<T>
  selectOne<R>(): Promise<R | null>
  selectMany<R>(): Promise<R[]>
}

/** 阶段 7：准备执行 */
interface QueryReady<T extends TableNames> {
  selectOne<R>(): Promise<R | null>
  selectMany<R>(): Promise<R[]>
}
```

### 2.5 实现查询构建器类

```typescript
class QueryBuilder implements QueryInit {
  private queryState: {
    from?: string
    wheres: string[]
    joins: string[]
    orderBys: string[]
    limitCount?: number
    offsetCount?: number
  } = {
    wheres: [],
    joins: [],
    orderBys: [],
  }

  /**
   * 开始一个新查询 —— 选择表
   */
  from<T extends TableNames>(table: T): QueryFromSet<T> {
    this.queryState.from = table
    return this as unknown as QueryFromSet<T>
  }

  /**
   * 添加过滤条件
   */
  private addCondition<T extends TableNames, C extends ColumnsOf<T>>(
    connector: 'WHERE' | 'AND' | 'OR',
    column: C,
    operator: string,
    value: ColumnType<T, C>
  ): QueryWhereSet<T> {
    const prefix = this.queryState.wheres.length === 0 ? 'WHERE' : connector
    this.queryState.wheres.push(`${prefix} ${String(column)} ${operator} ${JSON.stringify(value)}`)
    return this as unknown as QueryWhereSet<T>
  }

  // 实现 QueryFromSet 的方法
  where<T extends TableNames, C extends ColumnsOf<T>>(
    this: QueryFromSet<T>,
    column: C,
    operator: '=' | '!=' | '>' | '<' | '>=' | '<=' | 'LIKE',
    value: ColumnType<T, C>
  ): QueryWhereSet<T> {
    return this.addCondition('WHERE', column, operator, value)
  }

  // ... 其他方法的实现类似
}

// 工厂函数
export function createQuery(): QueryInit {
  return new QueryBuilder()
}
```

## 三、案例二：有限状态机 DSL

### 3.1 什么是有限状态机？

**有限状态机（Finite State Machine, FSM）** 是一种计算模型，它在任意时刻都处于一组有限状态中的一个状态，并且可以根据输入事件在这些状态之间转换。

```
═══════════════════════════════════════════════════
         生活中的状态机无处不在
═══════════════════════════════════════════════════

【红绿灯】── 最经典的状态机
────────────
  状态：红灯 → 绿灯 → 黄灯 → 红灯 → ...
  事件：定时器到期（Timer Tick）
  
  ┌──────┐  tick   ┌──────┐  tick   ┌──────┐
  │ RED  │ ──────→ │GREEN │ ──────→ │YELLOW│
  └──────┘         └──────┘         └──────┘
    ▲                               │
    └───────────────────────────────┘ tick


【订单系统】── 电商核心业务逻辑
────────────
  状态流转：
  
  待支付(Pending)
     ↓ 支付成功
  已 Paid(Paid)
     ↓ 发货
  已 Shipped(Shipped)
     ↓ 确认收货
  完成(Delivered)
     ↓ 申请退款
  退款中(Refunding)
     ↓ 退款成功/失败
  已退款(Refunded) | 退款失败(回到 Delivered)
     
  每个状态只能接收特定的事件！
  比如"已发货"状态下不能再"取消订单"


【TCP 连接】── 网络协议的基础
────────────
  CLOSED → SYN_SENT → ESTABLISHED → FIN_WAIT → CLOSE
  (关闭)   (发送SYN)  (建立连接)    (等待FIN)   (关闭)
  
  各种异常路径也有明确定义
═══════════════════════════════════════════════════
```

### 3.2 为什么要在类型层面建模状态机？

```typescript
/**
 * 问题：普通的枚举 + switch 无法阻止非法的状态转换
 */

enum OrderStatus {
  Pending = 'PENDING',
  Paid = 'PAID',
  Shipped = 'SHIPPED',
  Delivered = 'DELIVERED',
  Cancelled = 'CANCELLED',
}

// 处理事件的普通函数
function handleEvent(status: OrderStatus, event: string): OrderStatus {
  switch (event) {
    case 'pay':
      if (status === OrderStatus.Pending) {
        return OrderStatus.Paid
      }
      break
    case 'ship':
      if (status === OrderStatus.Paid) {
        return OrderStatus.Shipped
      }
      break
    case 'deliver':
      if (status === OrderStatus.Shipped) {
        return OrderStatus.Delivered
      }
      break
    case 'cancel':
      // ⚠️ 这里有个 bug：应该只能在 Pending 时取消
      //     但代码中没有强制约束！
      return OrderStatus.Cancelled
    default:
      return status
  }
  return status  // 静默忽略了非法转换！
}

// 这些调用在运行时才会发现问题：
handleEvent(OrderStatus.Delivered, 'cancel')  // 应该被禁止！
handleEvent(OrderStatus.Pending, 'ship')       // 还没付款就能发货？！

/**
 * 我们的目标：让非法转换在编译期就被拦截
 * 
 * handleEvent(OrderStatus.Delivered, 'cancel')
 * → 💥 Compile Error: Event 'cancel' is not valid for state 'DELIVERED'
 */
```

### 3.3 类型安全状态机的核心设计

我们的目标是：**让每个状态的类型只暴露该状态下合法的事件处理方法**。

```typescript
/**
 * 核心思路：每个状态都是一个独立的类型，
 * 只包含从该状态出发的合法转换方法
 */

// ====== 第一步：定义状态和事件 ======

type OrderState = 
  | { status: 'pending'; context: PendingContext }
  | { status: 'paid'; context: PaidContext }
  | { status: 'shipped'; context: ShippedContext }
  | { status: 'delivered'; context: DeliveredContext }
  | { status: 'cancelled'; context: CancelledContext }

// 各状态的上下文数据
interface PendingContext {
  orderId: string
  items: OrderItem[]
  totalAmount: number
  createdAt: Date
}

interface PaidContext extends PendingContext {
  paidAt: Date
  paymentMethod: 'alipay' | 'wechat' | 'card'
}

interface ShippedContext extends PaidContext {
  shippedAt: Date
  trackingNumber: string
  carrier: 'sf' | 'yt' | 'zt'
}

interface DeliveredContext extends ShippedContext {
  deliveredAt: Date
}

interface CancelledContext {
  orderId: string
  reason: string
  cancelledAt: Date
}

interface OrderItem {
  productId: string
  quantity: number
  unitPrice: number
}


// ====== 第二步：为每个状态定义可用的转换 ======

/**
 * Pending 状态的可用操作
 */
interface PendingOrder {
  readonly state: 'pending'
  readonly data: PendingContext

  /** 支付订单 */
  pay(method: 'alipay' | 'wechat' | 'card'): PaidOrder

  /** 取消订单 */
  cancel(reason: string): CancelledOrder
}

/**
 * Paid 状态的可用操作
 */
interface PaidOrder {
  readonly state: 'paid'
  readonly data: PaidContext

  /** 发货 */
  ship(params: {
    trackingNumber: string
    carrier: 'sf' | 'yt' | 'zt'
  }): ShippedOrder

  /** 取消订单并退款 */
  refund(reason: string): RefundingOrder
}

/**
 * Shipped 状态的可用操作
 */
interface ShippedOrder {
  readonly state: 'shipped'
  readonly data: ShippedContext

  /** 确认收货 */
  confirmDelivery(): DeliveredOrder
}

/**
 * Delivered 状态 —— 终态，没有更多转换
 */
interface DeliveredOrder {
  readonly state: 'delivered'
  readonly data: DeliveredContext
  // 没有任何方法返回非 Delivered 类型
  // 这意味着一旦到达 Delivered，就无法再转换
}

/**
 * Cancelled 状态 —— 终态
 */
interface CancelledOrder {
  readonly state: 'cancelled'
  readonly data: CancelledContext
}

/**
 * Refunding 状态
 */
interface RefundingOrder {
  readonly state: 'refunding'
  readonly data: PaidContext & { refundReason: string }

  approveRefund(): CancelledOrder
  rejectRefund(): PaidOrder
}


// ====== 第三步：联合类型作为"任意状态" ======

type Order = 
  | PendingOrder 
  | PaidOrder 
  | ShippedOrder 
  | DeliveredOrder 
  | CancelledOrder
  | RefundingOrder
```

### 3.4 实现状态机类

```typescript
class OrderStateMachine {
  private constructor(private state: Order) {}

  /**
   * 创建新订单（工厂方法）
   */
  static create(orderId: string, items: OrderItem[]): PendingOrder {
    const pendingData: PendingContext = {
      orderId,
      items,
      totalAmount: items.reduce((sum, item) => sum + item.quantity * item.unitPrice, 0),
      createdAt: new Date(),
    }
    return new OrderStateMachine({ status: 'pending', context: pendingData }) as unknown as PendingOrder
  }

  get currentState(): Order {
    return this.state
  }

  // ====== 状态转换方法 ======

  pay(method: 'alipay' | 'wechat' | 'card'): PaidOrder {
    if (this.state.status !== 'pending') {
      throw new Error(`Cannot pay in state: ${this.state.status}`)
    }
    const paidData: PaidContext = {
      ...this.state.context,
      paidAt: new Date(),
      paymentMethod: method,
    }
    this.state = { status: 'paid', context: paidData }
    return this as unknown as PaidOrder
  }

  cancel(reason: string): CancelledOrder {
    if (this.state.status !== 'pending') {
      throw new Error(`Cannot cancel in state: ${this.state.status}`)
    }
    const cancelledData: CancelledContext = {
      orderId: this.state.context.orderId,
      reason,
      cancelledAt: new Date(),
    }
    this.state = { status: 'cancelled', context: cancelledData }
    return this as unknown as CancelledOrder
  }

  ship(params: { trackingNumber: string; carrier: 'sf' | 'yt' | 'zt' }): ShippedOrder {
    if (this.state.status !== 'paid') {
      throw new Error(`Cannot ship in state: ${this.state.status}`)
    }
    const shippedData: ShippedContext = {
      ...this.state.context,
      shippedAt: new Date(),
      trackingNumber: params.trackingNumber,
      carrier: params.carrier,
    }
    this.state = { status: 'shipped', context: shippedData }
    return this as unknown as ShippedOrder
  }

  confirmDelivery(): DeliveredOrder {
    if (this.state.status !== 'shipped') {
      throw new Error(`Cannot confirm delivery in state: ${this.state.status}`)
    }
    const deliveredData: DeliveredContext = {
      ...this.state.context,
      deliveredAt: new Date(),
    }
    this.state = { status: 'delivered', context: deliveredData }
    return this as unknown as DeliveredOrder
  }

  refund(reason: string): RefundingOrder {
    if (this.state.status !== 'paid') {
      throw new Error(`Cannot refund in state: ${this.state.status}`)
    }
    this.state = {
      status: 'refunding',
      context: { ...this.state.context, refundReason: reason },
    }
    return this as unknown as RefundingOrder
  }

  approveRefund(): CancelledOrder {
    if (this.state.status !== 'refunding') {
      throw new Error(`Cannot approve refund in state: ${this.state.status}`)
    }
    const cancelledData: CancelledContext = {
      orderId: this.state.context.orderId,
      reason: this.state.context.refundReason,
      cancelledAt: new Date(),
    }
    this.state = { status: 'cancelled', context: cancelledData }
    return this as unknown as CancelledOrder
  }

  rejectRefund(): PaidOrder {
    if (this.state.status !== 'refunding') {
      throw new Error(`Cannot reject refund in state: ${this.state.status}`)
    }
    this.state = { status: 'paid', context: this.state.context }
    return this as unknown as PaidOrder
  }
}
```

### 3.5 使用示例

```typescript
// ========== 正常流程 ==========

async function normalFlow() {
  // 创建订单 → Pending 状态
  const order = OrderStateMachine.create('ORD-001', [
    { productId: 'P001', quantity: 2, unitPrice: 99.9 },
    { productId: 'P002', quantity: 1, unitPrice: 199.9 },
  ])
  // order 的类型是 PendingOrder
  // 可用的方法：.pay(), .cancel()


  // 支付 → 进入 Paid 状态
  const paid = order.pay('wechat')
  // paid 的类型是 PaidOrder
  // 可用的方法：.ship(), .refund()
  // ⚠️ .pay() 和 .cancel() 已经不存在了！IDE 不会提示这些方法


  // 发货 → 进入 Shipped 状态
  const shipped = paid.ship({ trackingNumber: 'SF1234567890', carrier: 'sf' })
  // shipped 的类型是 ShippedOrder
  // 可用的方法：.confirmDelivery()


  // 确认收货 → 进入 Delivered（终态）
  const delivered = shipped.confirmDelivery()
  // delivered 的类型是 DeliveredOrder
  // 没有任何转换方法 —— 流程结束
}


// ========== 含退款的流程 ==========

async function refundFlow() {
  const order = OrderStateMachine.create('ORD-002', [
    { productId: 'P003', quantity: 1, unitPrice: 50 },
  ])

  const paid = order.pay('alipay')

  // 申请退款 → Refunding 状态
  const refunding = paid.refund('不想要了')

  // 退款审核
  if (Math.random() > 0.5) {
    // 通过退款 → Cancelled
    const cancelled = refunding.approveRefund()
    console.log('退款成功', cancelled.data.reason)
  } else {
    // 驳回退款 → 回到 Paid（可以重新发货）
    const backToPaid = refunding.rejectRefund()
    const shipped = backToPaid.ship({
      trackingNumber: 'YT9876543210',
      carrier: 'yt',
    })
    console.log('重新发货', shipped.data.trackingNumber)
  }
}
```

### 3.6 通用的状态机框架

上面的订单状态机是硬编码的。我们可以进一步抽象出一个**通用的状态机 DSL**：

```typescript
/**
 * 通用状态机类型定义框架
 *
 * 允许用户用声明式的方式定义状态机，
 * 然后自动生成完全类型安全的代码
 */

// ====== 状态机定义语言（Configuration DSL）=====

interface StateMachineDefinition<
  States extends string,
  Events extends string
> {
  /** 初始状态 */
  initial: States

  /** 每个状态的上下文类型 */
  contexts: {
    [S in States]?: object
  }

  /** 状态转换规则 */
  transitions: {
    [S in States]?: {
      [E in Events]?: {
        target: States       // 目标状态
        guard?: (ctx: any, event: any) => boolean  // 守卫条件
        action?: (ctx: any, event: any) => any     // 转换动作
      }
    }
  }
}

// ====== 订单状态机的声明式定义 ======

const orderMachineDef: StateMachineDefinition<
  'pending' | 'paid' | 'shipped' | 'delivered' | 'cancelled' | 'refunding',
  'PAY' | 'SHIP' | 'CONFIRM_DELIVERY' | 'CANCEL' | 'REFUND' | 'APPROVE_REFUND' | 'REJECT_REFUND'
> = {
  initial: 'pending',

  transitions: {
    pending: {
      PAY: { target: 'paid' },
      CANCEL: { target: 'cancelled' },
    },
    paid: {
      SHIP: { target: 'shipped' },
      REFUND: { target: 'refunding' },
    },
    shipped: {
      CONFIRM_DELIVERY: { target: 'delivered' },
    },
    refunding: {
      APPROVE_REFUND: { target: 'cancelled' },
      REJECT_REFUND: { target: 'paid' },
    },
    // delivered 和 cancelled 没有定义任何转换 → 终态
  },
}

// 基于这个定义，可以用代码生成器自动创建类型安全的
// 状态机类（类似于上面的 OrderStateMachine）
```

## 四、DSL 设计的高级技巧

### 4.1 方法链（Fluent Interface）的类型传递

方法链的关键在于：**每个方法返回的正确类型取决于之前的调用历史**。

```typescript
/**
 * 技巧：用泛型参数编码"调用历史"
 */

interface ValidatedBuilder<T extends string = ''> {
  /** 必须先设置用户名 */
  username(name: string): ValidatedBuilder<'hasUsername'>

  /** 必须设置了 username 才能调用 */
  password(pwd: string): ValidatedBuilder<'hasUsername' | 'hasPassword'>

  /** 必须同时有 username 和 password 才能调用 */
  email(e: string): ValidatedBuilder<'hasUsername' | 'hasPassword' | 'hasEmail'>

  /** 所有必填字段都有了才能提交 */
  submit(): ValidatedBuilder<'hasUsername' | 'hasPassword' | 'hasEmail'>
}

// 使用
const builder = {} as ValidatedBuilder
builder
  .username('alice')     // ✓ 返回 hasUsername
  // .submit()            // ❌ 缺少 password
  .password('secret123') // ✓ 返回 hasUsername|hasPassword
  // .submit()            // ❌ 缺少 email（如果 email 必填的话）
  .email('alice@example.com')
  .submit()              // ✓ 所有条件满足
```

### 4.2 重载方法实现条件性方法可用

有时候同一个方法在不同状态下有不同的行为或签名：

```typescript
interface FlexibleSearch {
  /** 无关键词时，不能搜索 */
  search(query: string): SearchWithQuery

  /** 有查询结果后，可以翻页或筛选 */
  page(n: number): SearchWithQuery
  filter(tags: string[]): SearchWithQuery
}

interface SearchWithQuery extends FlexibleSearch {
  /** 有查询结果后才能导出 */
  export(format: 'csv' | 'json' | 'excel'): void
}

// export() 只在有 query 之后才出现
const s1 = {} as FlexibleSearch
// s1.export(...)  // ❌ 不存在

const s2 = s1.search('TypeScript') as SearchWithQuery
s2.export('csv')  // ✓ 存在
```

### 4.3 使用 branded types 防止值混淆

```typescript
/**
 * Branded Types —— 给原始类型打上"品牌标签"
 * 
 * 防止不同含义但相同底层类型的值被混淆
 * 例如：UserId 和 ProductId 都是 string，但不应该混用
 */

declare const brand: unique symbol

type Branded<T, B extends string> = T & { [brand]: B }

type UserId = Branded<string, 'UserId'>
type ProductId = Branded<string, 'ProductId'>
type OrderId = Branded<string, 'OrderId'>

// 创建函数
function createUserId(id: string): UserId {
  return id as UserId
}

function createProductId(id: string): ProductId {
  return id as ProductId
}

// 使用
const uid = createUserId('user-123')
const pid = createProductId('prod-456')

function getUser(id: UserId) { /* ... */ }
function getProduct(id: ProductId) { /* ... */ }

getUser(uid)       // ✓
getProduct(pid)    // ✓
getUser(pid)       // ❌ ProductId 不能赋值给 UserId！
getProduct(uid)    // ❌ UserId 不能赋值给 ProductId！
```

## 五、总结

类型级 DSL 设计是 TypeScript 高阶应用的巅峰之一。它将类型系统从"被动检查"提升到了"主动引导"的角色。

**设计层次总结**：

```
╔══════════════════════════════════════════════════════════╗
║                                                          ║
║  类型级 DSL 设计成熟度等级                                ║
║                                                          ║
║  Level 1: 类型标注                                        ║
║    给已有的值加上类型注解                                  ║
║    例：function add(a: number, b: number): number          ║
║                                                          ║
║  Level 2: 泛型抽象                                        ║
║    用泛型参数化类型，复用类型逻辑                          ║
║    例：type Result<T> = { data: T; ok: boolean }          ║
║                                                          ║
║  Level 3: 条件类型 + 映射类型                              ║
║    根据条件动态构造类型                                    ║
║    例：type Partial<T> = { [K in keyof T]?: T[K] }       ║
║                                                          ║
║  Level 4: 类型级 DSL（本章重点）                           ║
║    用类型系统构建完整的领域特定语言                        ║
║    例：QueryBuilder、StateMachine、Validator              ║
║    特点：非法状态不可表示、渐进式可推导、自文档化          ║
║                                                          ║
╚══════════════════════════════════════════════════════════╝
```

> **一句话带走**：类型级 DSL 的最高境界不是"让代码通过类型检查"，而是**让类型系统引导你写出正确的代码**。当你的 IDE 自动补全告诉你"此时此刻只有这三个操作是合法的"，当编译器在你试图进行非法状态转换时立刻拦住你——你就真正体会到了类型级 DSL 的威力。它不只是工具，更是你的**编程副驾驶**。
