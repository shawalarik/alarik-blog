# 变量声明 —— var、let、const 的完整行为（暂时性死区、重复声明、全局属性）

> **核心内容**：深入理解 JavaScript 中三种变量声明方式的底层机制、行为差异与最佳实践。本文将从**编译原理**的视角，逐层剖析 `var`、`let`、`const` 在作用域、提升、暂时性死区、重复声明和全局对象绑定等方面的完整行为。

## 一、从编译原理看变量声明

### 1.1 JavaScript 是一门编译语言

尽管 JavaScript 常被归类为"动态"或"解释执行"语言，但它实际上是一门**编译语言**。与传统编译语言不同的是，JavaScript 的编译过程发生在代码执行前的几微秒内——这被称为 **JIT（Just-In-Time）编译**。

当 JavaScript 引擎处理一行代码时，它经历了三个经典阶段（参考《你不知道的JavaScript》）：

```
源代码 → 分词/词法分析 → 解析/语法分析 → 代码生成 → 可执行指令
```

以 `var a = 2;` 为例：

| 阶段 | 过程 | 说明 |
|------|------|------|
| 分词 | 将字符流拆解为词法单元 | `var`、`a`、`=`、`2`、`;` |
| 解析 | 生成抽象语法树（AST） | VariableDeclaration → Identifier(a) → NumericLiteral(2) |
| 代码生成 | AST 转为机器指令 | 创建名为 a 的变量，分配内存并存储值 2 |

**关键认知转变**：当我们写下一行 `var a = 2;` 时，引擎看到的并不是"一条语句"，而是**两个完全独立的操作**：

```javascript
var a = 2;
// 实际被引擎理解为：
// ① 编译阶段：var a;          （声明 —— 编译器负责）
// ② 执行阶段：a = 2;          （赋值 —— 引擎在运行时负责）
```

这个"声明"与"赋值"分离的认知，是理解后续所有行为（提升、暂时性死区等）的基石。

### 1.2 编译器 vs 引擎 vs 作用域

理解变量声明需要认识三个角色的协作关系（《你不知道的JavaScript》第1章）：

| 角色 | 职责 | 类比 |
|------|------|------|
| **引擎** | 负责整个程序的编译与执行 | 施工队 |
| **编译器** | 词法分析与代码生成 | 设计师 |
| **作用域** | 收集维护所有标识符的查询规则 | 物业管理（决定谁有权访问哪个房间） |

**对话流程**（以 `var a = 2;` 为例）：

1. **编译器**遇到 `var a`，先问**作用域**："当前作用域是否已有叫 `a` 的变量？"
   - 如果有 → 忽略该声明
   - 如果没有 → 在当前作用域中创建一个新变量 `a`
2. 随后，**引擎**执行 `a = 2` 时，会再次查询**作用域**："找到变量 `a`，我要对它进行赋值"
3. **作用域**按照规则查找（LHS 查询），确认位置后引擎完成赋值

::: tip 核心要点
**声明是编译时的工作，赋值是运行时的工作**。这一分离机制直接导致了"提升"现象的产生。
:::

## 二、var —— 古老而特殊的声明方式

### 2.1 var 的本质特性

`var` 是 JavaScript 最古老的变量声明关键字（ES1, 1997年），它的设计带有明显的历史局限性。理解 `var` 是理解为什么 ES6 引入 `let`/`const` 的前提。

#### 特性一：函数作用域（而非块级作用域）

`var` 声明的变量只认**函数边界**，不认 `{}` 块边界：

```javascript
function example() {
  if (true) {
    var x = 10;    // 虽然 in if-block...
  }
  console.log(x);  // ...但这里依然可以访问！输出 10
}
example();
```

**通俗类比**：想象一个公司大楼，`var` 声明的变量就像是贴在整个楼层（函数）上的便签纸，无论你在会议室（if 块）、茶水间（for 块）还是走廊写的便签，整层楼的人都能看到。

```javascript
// 经典的 for 循环陷阱
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 输出：3, 3, 3  （而不是 0, 1, 2！）
// 原因：三个回调共享同一个 i，循环结束时 i 已经变成 3
```

这个问题在 `let` 出现之前，只能通过闭包（IIFE）来绕过：

```javascript
// 旧式解决方案 —— IIFE（立即调用函数表达式）
for (var i = 0; i < 3; i++) {
  (function(j) {        // 用函数作用域"捕获"每次迭代的 j
    setTimeout(() => console.log(j), 100);
  })(i);                // 立即传入当前的 i 值
}
// 输出：0, 1,2
```

#### 特性二：变量提升（Hoisting）

`var` 的声明会被**提升到所在作用域的最顶部**，而赋值保留在原处：

```javascript
console.log(name);     // 输出 undefined（不是 ReferenceError！）
var name = "Alarik";

// 引擎实际理解为：
var name;               // ← 声明提升到作用域顶部
console.log(name);      // undefined（已声明但未赋值）
name = "Alarik";        // ← 赋值留在原位
```

**为什么不是报错？** 因为 `var name` 的声明已经在编译阶段完成了，只是还没走到赋值那一步，所以变量存在但值为 `undefined`。

**提升的真正顺序**（《你不知道的JavaScript》第4章）：
- 函数声明优先于变量声明
- 同名时，函数声明"覆盖"变量声明

```javascript
foo();                  // 输出 1（不是 TypeError！）
var foo;                // 这行被忽略（因为下面有同名函数声明）
function foo() {
  console.log(1);
}

// 引擎实际理解为：
function foo() { console.log(1); }   // 函数声明先提升
foo();                                // 正常调用
```

#### 特性三：允许重复声明

`var` 允许在同一作用域内多次声明同一个名称，后者会静默覆盖前者：

```javascript
var user = "Pete";
var user = "John";       // 不报错！静默覆盖
console.log(user);       // "John"

// 更隐蔽的情况：
var count = 1;
if (true) {
  var count = 2;        // 不是新变量！是同一个 count 被重新赋值
}
console.log(count);     // 2（可能出乎意料）
```

**这种"宽容"恰恰是 bug 的温床**——在大型项目中，不同开发者可能在同一作用域内无意中使用了相同的变量名，导致难以排查的问题。

#### 特性四：成为全局对象的属性

在全局作用域中使用 `var` 声明变量时，它会自动成为**全局对象的属性**：

```javascript
var globalVar = "hello";
console.log(window.globalVar);         // "hello"（浏览器环境）
console.log(this.globalVar);           // "hello"
console.log(globalThis.globalVar);     // "hello"（标准全局对象）
```

这意味着全局 `var` 声明的变量可以被**任何代码访问和修改**，包括第三方库，增加了命名冲突的风险。

### 2.2 var 的历史地位

| 时期 | 状况 |
|------|------|
| 1997-2015 | `var` 是唯一的选择，开发者用 IIFE 模拟块级作用域 |
| 2015 (ES6) | `let` 和 `const` 正式引入 |
| 至今 | `var` 已不推荐在新代码中使用，仅用于维护旧项目 |

> 《Effective JavaScript》第 1 条建议就明确指出：**了解你使用的 JavaScript 版本**，在现代环境中应优先使用 `let` 和 `const`。

## 三、let —— 块级作用域的现代方案

### 3.1 let 解决了 var 的哪些问题

ES6（2015）引入的 `let` 关键字专门用于解决 `var` 的历史遗留问题：

| 问题 | var 的表现 | let 的改进 |
|------|-----------|------------|
| 作用域 | 函数作用域，无视 `{}` | **块级作用域**，`{}` 内有效 |
| 提升 | 提升为 `undefined`，可提前使用 | **暂时性死区（TDZ）**，提前使用报错 |
| 重复声明 | 允许，静默覆盖 | **禁止**，直接抛出 SyntaxError |
| 全局属性 | 成为 `window` 的属性 | **不会**成为全局对象属性 |

```javascript
// let 的块级作用域
{
  let blockScoped = "我在块内";
  console.log(blockScoped);  // ✅ 正常访问
}
// console.log(blockScoped); // ❌ ReferenceError: blockScoped is not defined

// let 在循环中的正确表现
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 输出：0, 1, 2  （每次迭代都有独立的 i）
```

**为什么循环中的 `let` 能正确工作？**

这是因为 `let` 在 `for` 循环头部的声明有一种特殊行为——它**不仅为循环体创建了新的块级作用域，而且每次迭代都会重新绑定一个新的变量实例**。这在技术上被称为 **per-iteration binding**（每次迭代绑定）。

### 3.2 let 与暂时性死区（Temporal Dead Zone, TDZ）

这是 `let`（以及 `const`）最重要的概念之一，也是区分现代 JavaScript 开发者的关键知识点。

#### 什么是 TDZ

**暂时性死区（TDZ）**指的是：从代码块的开始直到变量声明语句之间的区域，在这个区域内，变量虽然已经被引擎"知晓"（处于作用域中），但还**不能被访问或使用**。

```javascript
{
  // ========== TDZ 开始 ==========
  console.log(value);          // ❌ ReferenceError: Cannot access 'value' before initialization

  let value = 42;              // ========== TDZ 结束 ==========
  console.log(value);          // ✅ 42
}
```

**关键理解**：TDZ 并不是说变量"不存在"，而是说变量处于一种"已声明但未初始化"的状态。这与 `var` 的"声明即初始化为 `undefined`"完全不同。

#### TDZ 的实际意义

TDZ 是一项**安全保护机制**，它强制开发者在变量完成初始化之前不能使用它，从而避免了许多隐式 bug：

```javascript
// 反面案例（如果用 var 就不会有错误提示）
var data = fetchFromAPI();     // 可能返回 undefined
process(data);                 // 对 undefined 进行操作 → 运行时才暴露 bug

// 正面案例（用 let 会更早暴露问题）
let data = fetchFromAPI();     // 如果在声明前误用了 data...
// process(data);              // ...会在编译阶段就直接报错！
data = fetchFromAPI();         // 必须先完成声明
```

#### TDZ 存在于各种场景

TDZ 不仅存在于显式的 `let`/`const` 声明中，还隐藏在很多地方：

```javascript
// 场景1：函数默认参数
// let x = x + 1;              // ❌ ReferenceError! x 在右侧处于 TDZ

function f(x = x) {}           // ❌ 参数 x 的默认值表达式中，x 处于 TDZ
// f();                        // 抛出 ReferenceError

// 场景2：解构赋值
let { a, b = a } = {};         // ❌ b 的默认值引用 a，但 a 还未初始化
                               // ReferenceError: Cannot access 'a' before initialization

// 场景3：class 声明
class A extends B {}           // ❌ 如果 B 还未定义
// class B {}                  // 必须先定义 B

// 场景4：typeof 的特殊行为
console.log(typeof undeclaredVar);  // "undefined"（未声明的变量，typeof 安全）
// console.log(typeof valueInTDZ);  // ❌ 但对于处于 TDZ 的变量...ReferenceError!
```

::: warning 重要细节
`typeof` 操作符通常可以安全地检测未声明变量，但对于**处于 TDZ 中的变量**，`typeof` 同样会抛出 `ReferenceError`！这是很多开发者容易忽略的陷阱。
:::

### 3.3 let 不允许重复声明

```javascript
let name = "Alice";
// let name = "Bob";            // ❌ SyntaxError: Identifier 'name' has already been declared

// 即使一个是 var 一个是 let 也不行
var age = 25;
// let age = 26;                // ❌ 同样报错！

// 但在不同作用域中可以同名
let x = 1;
{
  let x = 2;                   // ✅ 新的作用域，新的变量
  console.log(x);              // 2
}
console.log(x);                // 1
```

**这种严格性看似不便，实则是好事**——它能帮助你在编码阶段就发现变量命名冲突，而不是等到运行时才发现诡异的 bug。

### 3.4 let 也会提升吗？

这是一个常见的误解。答案是：**是的，`let` 也会被提升，但是不会被初始化为 `undefined`**。

```javascript
let x = 10;

{
  // 此时 x 已经被提升了（否则外层的 x 应该可见），但处于 TDZ
  // console.log(x);           // ReferenceError（不是 undefined！）
  let x = 20;
  console.log(x);              // 20（遮蔽了外层的 x）
}
console.log(x);                // 10
```

三者在提升方面的对比：

| 声明方式 | 是否提升 | 提升后的初始状态 | 能否提前使用 |
|---------|---------|-----------------|-------------|
| `var` | 是 | `undefined` | 可以（得到 `undefined`） |
| `let` | 是 | 未初始化（TDZ） | **不可以**（ReferenceError） |
| `const` | 是 | 未初始化（TDZ） | **不可以**（ReferenceError） |
| `function` | 是 | 函数本身 | 可以（正常调用） |

## 四、const —— 不可变绑定的最佳实践

### 4.1 const 的基本语义

`const` 声明的是一个**常量绑定**（constant binding）——注意关键词是"**绑定**"而非"**值**"：

```javascript
const PI = 3.14159;
// PI = 3.14;                  // ❌ TypeError: Assignment to constant variable

const API_URL = "https://api.example.com";
// API_URL = "https://new.api.com";  // ❌ 同样报错
```

**必须同时初始化**：`const` 声明时必须立即赋值，否则语法错误：

```javascript
const name;                    // ❌ SyntaxError: Missing initializer in const declaration
const greeting = "Hello";     // ✅ 正确
```

### 4.2 const 的本质：不可变的是"绑定"而非"值"

这是理解 `const` 最重要的概念：

```javascript
const person = { name: "Alice", age: 25 };
person.name = "Bob";           // ✅ 完全合法！修改的是对象的内容
person.age = 26;               // ✅ 合法

person = { name: "Charlie" };  // ❌ 非法！试图改变绑定本身
```

**通俗类比**：把 `const` 想象成一个**固定在墙上的标签**。标签上写着"这是 person 盒子"。你可以打开盒子、修改盒子里的东西，但你不能把标签撕下来贴到另一个盒子上。

```
const person = { name: "Alice" };

┌─────────────────────────────────────┐
│  const 绑定（不可变）                │
│  ┌─────────────────────────────┐    │
│  │  person ──→ { name:"Alice"}│    │
│  └─────────────────────────────┘    │
│                                     │
│  ✅ 可以修改对象内部的数据             │
│  ❌ 不能让 person 指向另一个对象       │
└─────────────────────────────────────┘
```

如果要真正冻结一个对象（防止任何修改），需要使用 `Object.freeze()`：

```javascript
const config = Object.freeze({
  host: "localhost",
  port: 3000,
});

config.port = 8080;            // 静默失败（非严格模式）或 TypeError（严格模式）
config.newProp = "hi";         // 同上
```

### 4.3 为什么推荐优先使用 const

现代 JavaScript 社区普遍遵循的原则是：

> **默认使用 const，只在确定需要重新赋值时改用 let。**

这样做的好处：

1. **意图明确**：`const` 告诉读者"这个变量不会被重新赋值"，降低了阅读代码时的心理负担
2. **防止意外修改**：编译器帮你 enforce 这个约束，减少因意外赋值导致的 bug
3. **优化潜力**：引擎可以对 `const` 声明进行更好的优化（因为它知道绑定不会变）

```javascript
// 推荐写法
function processData(items) {
  const result = [];          // 不需要重新赋值 → const
  const len = items.length;   // 固定值 → const

  for (let i = 0; i < len; i++) {  // 循环计数器需要变化 → let
    const item = items[i];   // 每次迭代都是新的绑定 → const
    result.push(transform(item));
  }

  return result;             // result 本身不需要重新赋值
}
```

## 五、三种声明方式的完整对比

### 5.1 行为总览表

| 特性 | `var` | `let` | `const` |
|------|-------|-------|---------|
| 作用域 | 函数作用域 / 全局作用域 | **块级作用域** | **块级作用域** |
| 提升 | 是（值为 `undefined`） | 是（进入 TDZ） | 是（进入 TDZ） |
| 暂时性死区（TDZ） | 无 | **有** | **有** |
| 重复声明 | **允许** | **禁止** | **禁止** |
| 全局声明时成为 window 属性 | **是** | 否 | 否 |
| 是否必须初始化 | 否 | 否 | **是** |
| 能否重新赋值 | 能 | 能 | **不能** |

### 5.2 代码行为对比

```javascript
// ====== 作用域对比 ======
function scopeDemo() {
  var a = 1;
  let b = 2;
  const c = 3;

  if (true) {
    var a = 10;      // 同一个 a，覆盖外部值
    let b = 20;      // 新的 b，遮蔽外部值
    // const c = 30;  // 可以，也是新的 c
  }

  console.log(a);    // 10（var 无块级作用域！）
  console.log(b);    // 2（let 有块级作用域）
  console.log(c);    // 3（const 有块级作用域）
}
scopeDemo();

// ====== 提升与 TDZ 对比 ======
console.log(varX);     // undefined（var 提升并初始化为 undefined）
// console.log(letY);  // ReferenceError（let 进入 TDZ）
// console.log(constZ); // ReferenceError（const 进入 TDZ）

var varX = 1;
let letY = 2;
const constZ = 3;

// ====== 重复声明对比 ======
var v = 1;  var v = 2;      // ✅ 允许
// let l = 1; let l = 2;     // ❌ SyntaxError
// const c = 1; const c = 2; // ❌ SyntaxError

// ====== 全局属性对比 ======
var gVar = "global var";
let gLet = "global let";
const gConst = "global const";

console.log(window.gVar);     // "global var"（是 window 属性）
console.log(window.gLet);     // undefined（不是 window 属性）
console.log(window.gConst);   // undefined（不是 window 属性）
```

### 5.3 决策流程图

```
需要声明变量？
    │
    ▼
┌─────────────────┐
│ 需要重新赋值吗？ │
└────────┬────────┘
         │
    ┌────┴────┐
    │ 是      │ 否
    ▼         ▼
  使用 let   使用 const
```

## 六、进阶主题：隐藏的细节

### 6.1 全局对象属性问题

在浏览器环境中，全局作用域的 `var` 声明会成为 `window` 对象的属性，而 `let`/`const` 不会：

```javascript
var aVar = "var 声明";
let aLet = "let 声明";
const aConst = "const 声明";

console.log(window.aVar);     // "var 声明"
console.log(window.aLet);     // undefined
console.log(window.aConst);   // undefined
```

**为什么这很重要？**

1. **安全性**：`let`/`const` 不会被 `for...in` 遍历到，也不会意外地被其他脚本覆盖
2. **一致性**：Node.js 环境中 `var` 不会成为 `global` 的属性（模块作用域），而浏览器中会——这种不一致性本身就是问题
3. **Web Worker**：在 Worker 中没有 `window` 对象，`var` 的行为又有所不同

```javascript
// window 上的属性可以被随意删除
var config = { debug: true };
delete window.config;          // true（成功删除！）
console.log(config);           // ReferenceError

// 但 let/const 不在 window 上，不存在此风险
let settings = { debug: true };
// delete window.settings;     // 无效（settings 从来不在 window 上）
```

### 6.2 类似块作用域的历史替代方案

在 ES6 之前，开发者如何模拟块级作用域？主要有以下几种模式：

**IIFE（立即执行函数表达式）**：

```javascript
// 旧时代写法
(function() {
  var privateVar = "只有这里面能用";
  console.log(privateVar);
})();
// console.log(privateVar);  // ReferenceError
```

**try/catch 块**（鲜为人知）：

```javascript
// catch 子句具有块级作用域！（ES3 规范）
try {
  throw "secret";
} catch (e) {
  console.log(e);             // "secret"
}
// console.log(e);            // ReferenceError!
```

**with 语句（已被废弃，切勿使用）**：

```javascript
// with 可以创建临时作用域，但有严重的性能和安全问题
// 现代严格模式下已禁用
```

这些 workaround 在 ES6 之后都已成为历史。`let` 和 `const` 提供了原生、清晰、高效的块级作用域支持。

### 6.3 死区与 typeof 的交互

前面提到 `typeof` 对 TDZ 内的变量会抛出异常。这是一个非常微妙的点：

```javascript
console.log(typeof neverDeclared);   // "undefined"（安全）

{
  console.log(typeof inTDZ);         // ❌ ReferenceError!
  let inTDZ = 42;
}
```

**为什么会这样？** 因为 TDZ 中的变量确实已经存在于作用域中了（只是还不能被访问），所以 `typeof` 无法将其当作"从未声明"来处理。ECMAScript 规范明确规定了对这类情况的 `ReferenceError` 行为。

### 6.4 循环中的闭包与 let

这是面试高频题，也最能体现 `let` 相对于 `var` 的价值：

```javascript
// 问题代码（var）
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(`var: ${i}`), 100);
}
// 输出：var: 3, var: 3, var: 3

// 正确代码（let）
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(`let: ${i}`), 100);
}
// 输出：let: 0, let: 1, let: 2

// 等价的手动实现（理解 let 的原理）
for (var _i = 0; _i < 3; _i++) {
  let i = _i;                     // 每次迭代创建一个新的 i
  setTimeout(() => console.log(`manual: ${i}`), 100);
}
// 输出：manual: 0, manual: 1, manual: 2
```

**底层原理**：`let` 在 `for` 循环头部时，不仅仅是简单的块级作用域声明。规范规定，每次循环迭代都会**创建一个新的绑定实例**，并将当前迭代的值赋给它。这使得闭包能捕获到每次迭代的独立值。

### 6.5 script 标签与 module 模式的差异

在浏览器中，脚本的运行模式也会影响变量声明的行为：

```html
<!-- 普通 script（非 module） -->
<script>
  var topVar = "I'm on window";
  // topVar 会泄漏到全局作用域
</script>

<!-- ES Module -->
<script type="module">
  var modVar = "I'm NOT on window";
  // 即使是 var，也不会成为 window 属性！
  // 且顶层作用域本身就是模块作用域
</script>
```

在 **Module 模式**下，即使是 `var` 也具有类似块级作用域的行为——它不会成为全局对象的属性。这也是推荐使用 `<script type="module">` 的原因之一。

## 七、最佳实践总结

### 7.1 声明风格指南

根据《Effective JavaScript》、《JavaScript 语言精粹》以及现代社区共识：

| 场景 | 推荐做法 | 示例 |
|------|---------|------|
| 普通变量（需重赋值） | `let` | `let counter = 0;` |
| 常量 / 不变量 | `const` | `const MAX_SIZE = 100;` |
| 配置对象 | `const` + `Object.freeze()` | `const CONFIG = Object.freeze({...});` |
| 循环计数器 | `let`（for 循环） | `for (let i = 0; ...) { ... }` |
| 循环内的固定值 | `const` | `for (...) { const item = arr[i]; }` |
| 函数参数 | N/A（无需声明） | `function fn(arg) { ... }` |

### 7.2 命名约定

```javascript
// 常量：全大写 + 下划线分隔（传统惯例）
const MAX_CONNECTIONS = 10;
const DEFAULT_TIMEOUT = 5000;
const API_BASE_URL = "https://api.example.com";

// 普通变量：camelCase
let currentUser = null;
let isLoading = false;

// 私有变量（约定）：前缀 _
let _internalCache = new Map();

// 布尔值：前缀 is/has/should/can
let isActive = true;
let hasPermission = false;
let shouldRetry = false;
let canEdit = true;
```

### 7.3 需要避免的反模式

```javascript
// ❌ 反模式 1：链式 var 声明（易出错）
var a = 1, b = 2, c = 3;       // 其中一个遗漏分号可能导致连锁问题

// ✅ 推荐：每行单独声明
let a = 1;
let b = 2;
let c = 3;

// ❌ 反模式 2：先使用后声明（依赖提升）
function bad() {
  console.log(x);              // 依赖提升行为
  var x = 10;
}

// ✅ 推荐：在使用前声明
function good() {
  const x = 10;
  console.log(x);
}

// ❌ 反模式 3：条件中声明函数（不可靠）
if (condition) {
  function doSomething() { ... }  // 不同引擎行为不一致
}

// ✅ 推荐：使用函数表达式
const doSomething = condition
  ? () => { /* ... */ }
  : () => { /* ... */ };
```

## 八、知识图谱

```
变量声明体系
├── var（ES1，1997）
│   ├── 函数作用域
│   ├── 变量提升（初始化为 undefined）
│   ├── 允许重复声明
│   ├── 成为全局对象属性
│   └── 已不推荐使用（遗留兼容）
│
├── let（ES6，2015）
│   ├── 块级作用域 {}
│   ├── 变量提升 + TDZ（暂时性死区）
│   ├── 禁止重复声明
│   ├── 不成为全局对象属性
│   └── 用于需要重新赋值的场景
│
├── const（ES6，2015）
│   ├── 块级作用域 {}
│   ├── 变量提升 + TDZ
│   ├── 禁止重复声明
│   ├── 声明时必须初始化
│   ├── 绑定不可变（值可变）
│   └── 默认首选的声明方式
│
└── 相关核心概念
    ├── 编译原理（词法分析 → AST → 代码生成）
    ├── 作用域（词法作用域、作用域链、LHS/RHS 查询）
    ├── 提升（Hoisting）—— 声明提升 vs 赋值保留
    ├── TDZ（Temporal Dead Zone）—— 暂时性死区
    ├── 闭包（Closure）—— 与循环 + let 的交互
    └── IIFE（历史替代方案，现已不需要）
```
