# 作用域链与执行上下文 —— 全局、函数、块级作用域，词法环境与变量环境

> **核心内容**：深入 JavaScript 引擎的内部运作机制——词法环境的结构、变量查找的作用域链、执行上下文的创建与销毁、`var`/`let`/`const` 在底层的行为差异、暂时性死区（TDZ）的本质，以及闭包如何通过 `[[Environment]]` 保持外部变量的存活。

---

## 一、为什么需要理解作用域与执行上下文？

在 JavaScript 的世界里，每一段代码的运行都不是孤立的。当你声明一个变量、调用一个函数、或者写下一对花括号 `{}` 时，引擎背后都在默默地构建和维护一套精密的系统——这套系统决定了"这个变量从哪里来""那个函数能访问什么数据""代码执行完后哪些内存可以被回收"。这套系统就是**作用域（Scope）和执行上下文（Execution Context）**。

打个比方：如果你把一个 JavaScript 程序想象成一栋**多层办公楼**——全局代码是大堂，每个函数是一个独立办公室，每个代码块 `{}` 是办公室里的小隔间。那么作用域就是这栋楼的**房间布局图**（谁能在哪个房间里看到什么东西），而执行上下文就是每次有人进入某个房间时的**工作记录卡**（记录当前正在做什么、手头有哪些工具可用）。不理解这两套机制，就像在一栋陌生的大楼里瞎逛——你可能随时撞上墙（报错），或者找不到你需要的东西（`ReferenceError`）。

更重要的是，作用域和执行上下文是理解后续所有高级概念的基础：闭包、模块化、异步编程模式、性能优化……几乎所有进阶话题都建立在这两个概念之上。

## 二、三种基本作用域类型

JavaScript 中有三种基本的作用域级别，它们决定了变量在代码中的可见范围。

### 2.1 全局作用域（Global Scope）

全局作用域是所有作用域的最外层，就像办公楼的**大堂**——任何人、任何地方都能看到大堂里的东西。在浏览器环境中，全局作用域对应的是 `window` 对象（在严格模式下不完全等同）；在 Node.js 中则是 `global` 对象。

```javascript
// 这些变量在全局作用域中声明——任何地方都可以访问
let globalVar = "我是全局的";
const PI = 3.14159;

function globalFunction() {
  console.log(globalVar); // 可以访问 ✓
}

console.log(globalVar);     // 可以访问 ✓
globalFunction();           // 可以访问 ✓
```

全局作用域的特点是：
- **生命周期最长**——从脚本开始运行到页面关闭（或进程结束）
- **任何内层作用域都可以访问**——但反过来不行（内层的变量外层看不到）
- **容易被污染**——如果在全局作用域中不小心声明了太多变量，可能与其他脚本产生命名冲突

### 2.2 函数作用域（Function Scope）

每当一个函数被调用时，都会创建一个新的**函数作用域**。这个作用域就像是给这次函数调用分配了一个**独立的临时办公室**——只有进入这个办公室的人（函数内部的代码）才能使用里面的设施（局部变量），外面的人完全看不到里面有什么。

```javascript
function createWorkspace() {
  let localVariable = "我是局部的";
  const secret = "这是秘密";

  console.log(localVariable); // 可以访问 ✓
  console.log(globalVar);     // 也可以访问外层的全局变量 ✓
}

createWorkspace();

// console.log(localVariable); // ReferenceError！外部无法访问 ✓（正确地报错了）
```

函数作用域的核心意义在于**封装（Encapsulation）**——它让每个函数都拥有自己的私有空间，不会与外面的世界互相干扰。这就像每个人在自己的办公室里可以自由地整理桌面、贴便签、放文件，这些都不会影响到隔壁办公室的人。

### 2.3 块级作用域（Block Scope）

ES6 引入的 `let` 和 `const` 带来了块级作用域的概念——**任何一对花括号 `{}` 都可以创建一个独立的作用域**。这包括 `if` 语句、`for`/`while` 循环、单独的 `{}` 块等：

```javascript
// if 块创建块级作用域
if (true) {
  let blockScoped = "只在 if 块内有效";
  const alsoBlock = "也是块级的";
  console.log(blockScoped); // 可以访问 ✓
}
// console.log(blockScoped); // ReferenceError ✗

// for 循环也创建块级作用域
for (let i = 0; i < 3; i++) {
  const iterationValue = i * 10;
  console.log(`第${i}次迭代: ${iterationValue}`);
}
// console.log(i);              // ReferenceError ✗
// console.log(iterationValue); // ReferenceError ✗

// 甚至单独的花括号也可以
{
  let standalone = "独立块中的变量";
}
// console.log(standalone); // ReferenceError ✗
```

块级作用域就像是办公室里的**更小的隔间或储物柜**——它比函数作用域更加精细，让你可以在函数内部的任意位置划出一片临时的私密区域。这在循环和条件分支中特别有用，因为你可以确保每次迭代的变量都是独立的。

### 2.4 变量遮蔽（Shadowing）

当内外层作用域中有同名变量时，内层的变量会"遮蔽"外层的同名变量——这种现象叫做**变量遮蔽（Shadowing）**：

```javascript
let name = "全局的 Alice"; // 外层变量

function showName() {
  let name = "函数内的 Bob"; // 内层同名变量——遮蔽了外层的 name
  console.log(name);         // "Bob" —— 使用的是内层的
  
  if (true) {
    let name = "块内的 Carol"; // 再次遮蔽
    console.log(name);          // "Carol"
  }
  
  console.log(name); // "Bob" —— 回到函数层的 name
}

showName();
console.log(name); // "Alice" —— 最外层的始终不变
```

变量遮蔽可以这样理解：假设你在大厅（全局作用域）挂了一个写着"Alice"的名牌。然后你进了自己的办公室（函数作用域），也在门上挂了一个写着"Bob"的同名牌子。当你在办公室里问"谁是 Alice？"时，你首先看到的肯定是自己门口的那个牌子——Bob。只有出了办公室回到大厅，才能再次看到原来的 Alice 名牌。**内层永远优先于外层**，这是变量查找的基本规则。

## 三、词法环境——引擎的内部地图

前面讲的都是"表面现象"——你能观察到的行为规则。那么 JavaScript 引擎内部到底是如何实现这些作用域规则的？答案就在**词法环境（Lexical Environment）** 这个概念中。它是 ECMAScript 规范定义的理论模型，虽然不同引擎的实现细节可能有所优化，但其外在行为都遵循这一模型。

### 3.1 词法环境的两个组成部分

每一个正在运行的代码单元（脚本、函数、代码块）都有一个关联的**词法环境对象**。这个对象由两部分组成：

1. **环境记录（Environment Record）**—— 一个存储容器，保存了当前作用域内所有的**局部变量**及其值。可以把环境记录理解为一张**变量清单**，上面列出了这个作用域里有哪些"物品"以及它们当前的"状态"。本质上，所谓的"读取变量"就是查这张清单；"修改变量"就是在清单上更新状态。
2. **对外部词法环境的引用（outer）**—— 一个指针，指向**包围当前代码的外层词法环境**。这就是连接各个作用域形成"链"的关键纽带。

用图形来表示词法环境的结构：

```
┌──────────────────────────────────────┐
│        词法环境 (Lexical Env)          │
├──────────────────────────────────────┤
│                                      │
│  ┌─ 环境记录 (Environment Record) ─┐ │
│  │                                 │ │
│  │   变量A : value1                │ │
│  │   变量B : value2                │ │
│  │   变量C : value3                │ │
│  │   ...                           │ │
│  └─────────────────────────────────┘ │
│                                      │
│  outer ───────────────────────────► [外层词法环境] 或 null（如果是全局）
│                                      │
└──────────────────────────────────────┘
```

### 3.2 全局词法环境

当 JavaScript 脚本开始执行之前，引擎会首先创建**全局词法环境**。它是整个作用域链的终点，其 `outer` 引用为 `null`（因为再往外就没有了）：

```javascript
// 脚本开始时，全局词法环境被创建

let phrase;

phrase = "Hello";

phrase = "Bye";
```

这段简单代码背后的词法环境变化过程如下：

```
步骤 0 — 脚本启动前（预编译阶段）:
┌──────────────────────┐
│   全局词法环境        │
├──────────────────────┤
│ phrase: <未初始化>    │ ← let 变量进入 TDZ 状态
│ outer: null          │
└──────────────────────┘

步骤 1 — 执行 let phrase 后:
┌──────────────────────┐
│   全局词法环境        │
├──────────────────────┤
│ phrase: undefined    │ ← 初始化完成，值为 undefined
│ outer: null          │
└──────────────────────┘

步骤 2 — 执行 phrase = "Hello":
┌──────────────────────┐
│   全局词法环境        │
├──────────────────────┤
│ phrase: "Hello"      │ ← 赋值操作
│ outer: null          │
└──────────────────────┘
```

### 3.3 函数调用的词法环境

当一个函数被调用时，引擎会为这一次调用**创建一个全新的词法环境**。这个新环境的环境记录中会填入函数的形参和内部声明的变量，而它的 `outer` 指向的是函数**被定义时**所在的外部环境：

```javascript
let phrase = "Hello";

function say(name) {
  // 当 say("John") 被调用时：
  // 创建新的词法环境
  console.log(`${phrase}, ${name}`);
}

say("John"); // 输出: "Hello, John"
```

当 `say("John")` 执行时，内存中形成的词法环境链如下：

```
┌─────────────────────────┐         ┌─────────────────────────┐
│   say() 的词法环境       │         │   全局词法环境            │
├─────────────────────────┤         ├─────────────────────────┤
│                         │  outer  │                         │
│  环境记录:               │◄────────│  环境记录:               │
│    name: "John"         │         │    phrase: "Hello"       │
│                         │         │    say: <function>       │
│  outer ─────────────────┼────────►│                         │
└─────────────────────────┘         │  outer: null             │
                                    └─────────────────────────┘
```

当函数内部需要访问 `phrase` 这个变量时，查找过程是这样的：

1. 先在**当前的** `say()` 词法环境中找 → 没找到 `phrase`
2. 通过 `outer` 指针跳到**外部的**全局词法环境中找 → 找到了 `"Hello"` ✓

而访问 `name` 时：
1. 直接在**当前的** `say()` 词法环境中就找到了 `"John"` ✓ —— 不需要向外查找

这个过程就像是在一串连在一起的房间里找东西：先在自己房间里翻箱倒柜，找不到就去隔壁房间（外层作用域）找，还找不到就去再外面一层找……直到找到为止，或者确认整栋楼都没有这个东西（抛出 `ReferenceError`）。这条由 `outer` 指针串联起来的路径，就是**作用域链（Scope Chain）**。

### 3.4 块级作用域的词法环境

对于使用 `let`/`const` 的代码块，引擎同样会为其创建一个独立的词法环境。这个环境是临时的——当代码块执行完毕后就会被销毁（除非有闭包引用它）：

```javascript
let x = 10; // 全局

{
  let y = 20; // 块级
  let z = x + y; // 可以访问外层的 x
  console.log(z); // 30
}

// console.log(y); // ReferenceError! 块级环境的 y 已被销毁
```

块级作用域的词法环境链：

```
┌─────────────────────────┐         ┌─────────────────────────┐
│   { } 块的词法环境       │         │   全局词法环境            │
├─────────────────────────┤         ├─────────────────────────┤
│                         │  outer  │                         │
│  环境记录:               │◄────────│  环境记录:               │
│    y: 20                │         │    x: 10                 │
│    z: 30                │         │                         │
│  outer ─────────────────┼────────►│  outer: null             │
└─────────────────────────┘         └─────────────────────────┘
（块执行完毕后被销毁）
```

## 四、执行上下文——代码执行的"工作台"

如果说词法环境是静态的"地图"，那**执行上下文（Execution Context）**就是动态的"工作台"。每当 JavaScript 引擎开始执行一段可执行代码时，就会创建一个对应的执行上下文。

### 4.1 什么是执行上下文？

执行上下文是一个抽象概念，它代表了代码执行时的**完整上下文信息**。你可以把它想象成每次进入一个房间时发的**工作证**——上面记录了你是谁（`this` 绑定）、你的工位在哪（词法环境）、你的参考资料在哪里（变量环境）等信息。

JavaScript 中有三种类型的执行上下文：

| 类型 | 触发时机 | 说明 |
|------|---------|------|
| **全局执行上下文** | 脚本开始执行时 | 整个程序只有一个 |
| **函数执行上下文** | 每次调用函数时 | 可同时存在多个（递归时） |
| **Eval 执行上下文** | `eval()` 内的代码 | 不推荐使用 |

### 4.2 执行上下文的组成成分

每个执行上下文包含以下关键组件：

```
┌──────────────────────────────────────────┐
│            执行上下文 (EC)                 │
├──────────────────────────────────────────┤
│                                          │
│  thisBinding: <this 的值>                │ ← 当前 this 指向谁
│                                          │
│  LexicalEnvironment: { ... }             ← 词法环境（存储 let/const）
│  VariableEnvironment: { ... }            ← 变量环境（存储 var / function）
│                                          │
└──────────────────────────────────────────┘
```

注意这里有两个看似相似但实际上不同的环境：
- **词法环境（LexicalEnvironment）**：主要存储通过 `let` 和 `const` 声明的变量，以及 `function` 声明
- **变量环境（VariableEnvironment）**：主要存储通过 `var` 声明的的变量和 `function` 声明

为什么要分成两套？这是因为 `var` 和 `let/const` 在初始化时机上有本质差异（后面会详细解释），规范层面需要区分它们。在实际执行中，大多数情况下这两个环境指向同一个底层结构或非常相似的结构，但在某些边界场景下它们的行为确实不同。

### 4.3 执行上下文栈（Call Stack）

JavaScript 是单线程语言，同一时间只能做一件事。当多个函数嵌套调用时，引擎使用**执行上下文栈（也叫调用栈 Call Stack）**来管理它们的执行顺序：

```javascript
function third() {
  console.log("第三层");
}

function second() {
  third();
  console.log("第二层");
}

function first() {
  second();
  console.log("第一层");
}

first();
```

执行过程中的栈变化过程：

```
第一步: first() 被调用
┌──────────────┐
│  first()     │  ← 栈顶（正在执行）
│  [全局 EC]   │
└──────────────┘

第二步: first() 内部调用 second()
┌──────────────┐
│  second()    │  ← 栈顶
│  first()     │
│  [全局 EC]   │
└──────────────┘

第三步: second() 内部调用 third()
┌──────────────┐
│  third()     │  ← 栈顶
│  second()    │
│  first()     │
│  [全局 EC]   │
└──────────────┘

第四步: third() 执行完毕 → 出栈
┌──────────────┐
│  second()    │  ← 恢复执行
│  first()     │
│  [全局 EC]   │
└──────────────┘

第五步: second() 执行完毕 → 出栈
┌──────────────┐
│  first()     │  ← 恢复执行
│  [全局 EC]   │
└──────────────┘

第六步: first() 执行完毕 → 出栈
┌──────────────┐
│  [全局 EC]   │  ← 只剩全局
└──────────────┘
```

这个栈的工作方式就像是一叠盘子——最后放上去的盘子最先被拿走（LIFO，后进先出）。每次函数调用就是往栈顶压入一个新盘子（新的执行上下文），函数返回就是把栈顶的盘子拿走。如果递归调用太深（盘子叠得太高），就会出现著名的**栈溢出（Stack Overflow）**错误。

## 五、var vs let/const——两种截然不同的初始化策略

这是本章最关键的实战知识点之一。`var` 和 `let/const` 虽然都是用来声明变量的关键字，但它们在词法环境和变量环境中的行为差异巨大，这种差异直接导致了大量令人困惑的现象和 bug。

### 5.1 let/const 的三阶段生命周期

使用 `let` 或 `const` 声明的变量，其生命周期经历了三个明确的阶段：

**阶段一：进入作用域——处于"未初始化"状态**

当 JavaScript 引擎进入一个作用域（比如函数体或代码块）的那一刻，所有使用 `let/const` 声明的变量就已经被"注册"到了词法环境中。但此时它们处于一种特殊的**未初始化（Uninitialized）**状态——引擎知道它们存在，但禁止任何代码访问它们：

```javascript
{
  // 此时变量 x 已经存在于词法环境中
  // 但处于 Uninitialized 状态
  // console.log(x); 
  // ❌ ReferenceError: Cannot access 'x' before initialization
  // 这就是"暂时性死区"（Temporal Dead Zone, TDZ）
  
  let x = 10; // 到了这一行，x 才完成初始化
  console.log(x); // 10 ✓
}
```

**阶段二：执行声明语句——完成初始化**

当执行流走到 `let x` 或 `const x` 这一具体行时，变量才正式完成初始化。如果没有赋初始值，默认为 `undefined`（`const` 必须赋值，否则语法错误）。

**阶段三：正常使用——读写自由**

初始化之后，变量就可以被正常读取和修改了。

这三个阶段可以用一个生动的类比来说明：**TDZ 就像是一家餐厅的"预订等待期"**。你在电话里订了一张桌子（变量被注册到词法环境中），餐厅知道你要来（变量名已被识别），但在约定的到达时间之前（执行到 `let` 那一行），你不能进去用餐（不能访问变量）。提前去的话会被礼貌地请出去（抛出 `ReferenceError`）。

### 5.2 var 的行为：没有"等待期"

与 `let/const` 形成鲜明对比的是，`var` 声明的变量**不存在"未初始化"状态**。当引擎进入函数作用域（注意不是块级作用域，因为 `var` 不认块级作用域！）时，`var` 变量会被立即初始化为 `undefined`：

```javascript
function example() {
  // var 变量在这里已经被初始化为 undefined 了
  console.log(myVar); // undefined —— 不会报错！（只是值为空）
  
  var myVar = 42;
  console.log(myVar); // 42
}

example();
```

`var` 的这种行为就像是餐厅的**散客入场**——不需要预约，推门就能进来（虽然一开始座位还没准备好，只能给你一把钥匙形状的占位符 `undefined`），等到真正安排好位置（执行到赋值语句）才能坐下享用美食。

### 5.3 为什么 var 没有块级作用域？

这是一个历史遗留的设计决策。在 ES6 之前，JavaScript 只有函数作用域和全局作用域两种级别，`var` 声明的变量会被提升到**整个函数体的顶部**（或全局顶部），完全忽略中间的 `{}` 代码块：

```javascript
function test() {
  // 所有 var 变量实际上都被"提升"到这里
  var i; // 实际发生的位置
  
  for (var i = 0; i < 3; i++) { // var 不受 {} 限制
    // 这里的 i 就是上面的那个 i
  }
  
  console.log(i); // 3 —— i 泄漏到了整个函数范围！
}

test();
```

而同样的代码使用 `let` 则完全不同：

```javascript
function test2() {
  for (let i = 0; i < 3; i++) {
    // i 只在这个 for 块内有效
  }
  
  console.log(i); // ReferenceError: i is not defined ✓
}
```

`var` 的这种"穿透"行为可以用一个比喻：`var` 像是在函数的**大门处**登记访客信息，不管这个人后来去了哪个小房间（代码块），他的登记信息都在大门口；而 `let/const` 则像是在**每个小房间的门口**分别登记——出了这个小房间，登记就失效了。

### 5.4 函数声明的特殊处理

函数声明（`function name(){}`）在初始化时机上有自己独特的规则：**它在词法环境创建时就完成了完整的初始化**（不仅仅是"已知"或"undefined"，而是可以直接使用的完整函数对象）。这也是为什么函数声明可以在定义之前就被调用的原因：

```javascript
sayHi("World"); // "Hi, World!" ✓ —— 提前调用完全合法

function sayHi(name) {
  console.log(`Hi, ${name}!`);
}
```

而函数表达式则遵循普通变量/表达式的规则——不会被特殊对待：

```javascript
sayBye(); // TypeError: sayBye is not a function ❌

var sayBye = function() {
  console.log("Bye!");
};
```

函数声明的这种"特权待遇"可以这样理解：**函数声明就像是 VIP 客户**——在餐厅开门营业之前（代码执行之前），他们的位置就已经预留好了并且布置完毕；而函数表达式（无论匿名还是具名）则像是普通顾客，必须按流程排队等候（等到赋值语句执行）。

### 5.5 综合对比表

| 特性 | `var` | `let` | `const` |
|------|-------|-------|---------|
| **作用域** | 函数级（或全局） | 块级 `{}` | 块级 `{}` |
| **进入作用域时** | 初始化为 `undefined` | 进入 TDZ（不可访问） | 进入 TDZ（不可访问） |
| **声明前访问** | `undefined`（不报错） | `ReferenceError` | `ReferenceError` |
| **重复声明** | 允许（静默覆盖） | 不允许（SyntaxError） | 不允许（SyntaxError） |
| **重新赋值** | 允许 | 允许 | **不允许** |
| **是否提升** | 是（带 `undefined` 值） | 是（进入 TDZ） | 是（进入 TDZ） |
| **作为全局变量时** | 成为 `window` 的属性 | 不成为 `window` 属性 | 不成为 `window` 属性 |

## 六、[[Environment]]——闭包的秘密属性

理解作用域链和词法环境后，我们就可以揭开 JavaScript 中最神秘也最强大的特性之一——**闭包（Closure）**的面纱了。而闭包的核心秘密，就藏在一个名为 `[[Environment]]` 的隐藏属性中。

### 6.1 [[Environment]] 是什么？

每一个函数在被创建时（注意，是创建时，不是调用时），引擎会给它添加一个隐藏的内部属性 `[[Environment]]`。这个属性的值是一个**引用**，指向**创建该函数的那一瞬间所在的词法环境**。

换句话说：**函数记得它出生在哪里**。

```javascript
function makeCounter() {
  let count = 0;
  
  // 这个函数在 makeCounter 的词法环境中被创建
  // 所以它的 [[Environment]] 指向 makeCounter 的词法环境
  return function() {
    return count++;
  };
}
```

当 `makeCounter()` 执行时发生的完整过程：

```
步骤 1: makeCounter() 被调用，创建其词法环境
┌──────────────────────────────────┐
│  makeCounter() 的词法环境          │
├──────────────────────────────────┤
│  count: 0                        │
│  outer: ──→ 全局词法环境            │
└──────────────────────────────────┘
         ▲
         │ [[Environment]]
         │
步骤 2: 返回的匿名函数被创建，
       其 [[Environment]] 自动指向当前环境
┌──────────────────────────────────┐
│  匿名函数对象                      │
│  code: return count++             │
│  [[Environment]] ────────────────┼──► makeCounter 的词法环境
└──────────────────────────────────┘

步骤 3: makeCounter() 执行结束，
       但返回的函数仍持有 [[Environment]] 引用！
       所以 count 所在的词法环境不会被垃圾回收！
```

### 6.2 为什么闭包能保持变量存活？

正常情况下，当一个函数执行完毕后，其词法环境中的局部变量就应该被销毁——毕竟没人再用它们了。但闭包打破了这个规则。

当 `makeCounter()` 返回的匿名函数被赋给外部变量 `counter` 后，即使 `makeCounter()` 本身早已执行结束，但由于 `counter.[[Environment]]` 仍然引用着 `makeCounter()` 的词法环境（其中包含了 `count` 变量），**垃圾回收器（Garbage Collector）不敢回收这片内存**——因为它发现还有人在用！

```javascript
let counter = makeCounter(); // makeCounter() 执行完了，但...

console.log(counter()); // 0 —— count 从外部环境中读取并 +1
console.log(counter()); // 1 —— 同一个 count，继续累加
console.log(counter()); // 2
```

闭包保持变量存活的机制可以这样类比：**`makeCounter()` 就像是一个工厂车间**，生产完产品（匿名函数）后就关门了。但这个产品的说明书（`[[Environment]]`）上写着"原料仓库地址：某某房间"（指向 `count` 所在的词法环境）。只要你手里拿着这个产品（`counter` 变量还在引用这个函数），那个原料仓库就必须保持开放——因为你随时可能回去取材料。

### 6.3 多个闭包实例各自独立

每次调用 `makeCounter()` 都会创建一个全新的词法环境和一个新的函数实例，因此不同的计数器之间完全独立：

```javascript
let counterA = makeCounter();
let counterB = makeCounter(); // 新的词法环境，新的 count = 0

console.log(counterA()); // 0
console.log(counterA()); // 1
console.log(counterB()); // 0 —— 独立的计数器！
console.log(counterB()); // 1
console.log(counterA()); // 2 —— 不影响 A
```

这就像是同一个工厂的两条生产线——它们生产的产品看起来一模一样（相同的函数代码），但每条线都有自己的独立原料仓库（各自的 `count`），互不干扰。

### 6.4 同一次函数调用中的闭包共享环境

在同一次函数调用中创建的所有嵌套函数，共享同一个外部词法环境：

```javascript
function createToggle() {
  let state = false; // 所有闭包共享这一个 state
  
  return {
    toggle() { state = !state; return state; },    // 修改 state
    isOn() { return state; },                        // 读取 state
    isOff() { return !state; },                      // 间接读取
  };
}

const switcher = createToggle();

console.log(switcher.isOn());   // false
console.log(switcher.toggle()); // true  —— toggle 改了 state
console.log(switcher.isOn());   // true  —— isOn 读到了变化后的值
console.log(switcher.toggle()); // false
```

这里的三个方法（`toggle`、`isOn`、`isOff`）都通过各自的 `[[Environment]]` 指向同一个 `createToggle()` 调用的词法环境，所以它们操作的 `state` 是同一个变量——就像三个人手里都有同一间仓库的钥匙，谁都可以进去改变库存，其他人下次进去时看到的就是更新后的状态。

### 6.5 闭包与垃圾回收

闭包虽然强大，但也意味着额外的内存开销。如果一个闭包不再被使用，应该主动解除引用以允许垃圾回收释放内存：

```javascript
function heavyProcess() {
  let hugeData = new Array(1000000).fill('data');
  
  return function useData() {
    return hugeData.length; // 引用了 hugeData
  };
}

let processor = heavyProcess();
// 现在 hugeData（约 8MB+）一直保存在内存中

// 用完后解除引用
processor = null; // 现在 hugeData 可以被回收了
```

现代 JavaScript 引擎（如 V8）还会进行优化分析——如果闭包中没有实际使用某些外部变量，引擎可能会将这些变量从词法环境中移除以节省内存。但这可能导致调试时的一些困惑：你在调试器中可能看不到某些理论上应该存在的变量。

## 七、经典陷阱深度解析

### 7.1 循环中的闭包问题——最经典的面试题

这是 JavaScript 中最著名也最容易踩坑的问题之一：

```javascript
// ❌ 错误写法 —— 使用 var
for (var i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, 100);
}
// 输出: 3, 3, 3（而不是 0, 1, 2）
```

为什么会这样？让我们追踪一下发生了什么：

1. `var i` 被**提升到函数（或全局）作用域的顶部**，只创建了**一个** `i` 变量
2. 三次循环创建了三个回调函数，它们**共享同一个 `i`**
3. 当 `setTimeout` 的回调在 100ms 后执行时，循环早就结束了，此时 `i` 的值已经是 `3`
4. 所有回调打印的都是同一个最终的 `i`

用词法环境的视角来看：

```
循环结束后（回调尚未执行时）:
┌──────────────────────────────┐
│  全局/函数词法环境             │
├──────────────────────────────┤
│  i: 3                         │ ← 三个回调都通过闭包引用这个 i
│  (三个回调函数对象)             │
│    callback1.[[Env]] ────────┼┐
│    callback2.[[Env]] ────────┼┼── 都指向同一个环境
│    callback3.[[Env]] ────────┼┘
└──────────────────────────────┘
```

**解决方案一：使用 `let`（推荐）**

```javascript
// ✅ 正确写法 —— 使用 let
for (let i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, 100);
}
// 输出: 0, 1, 2
```

`for (let i)` 有一个特殊的魔法：**每一次循环迭代都会创建一个全新的、独立的 `i` 变量绑定到一个新的块级词法环境**。这意味着每次迭代的回调函数捕获的是属于那一次迭代的特定 `i` 值：

```
每次迭代的独立环境:
迭代 0: { i: 0 } ◄── callback0.[[Env]] 指向这里
迭代 1: { i: 1 } ◄── callback1.[[Env]] 指向这里
迭代 2: { i: 2 } ◄── callback2.[[Env]] 指向这里
```

**解决方案二：使用 IIFE 创建额外的作用域（旧时代方案）**

```javascript
// ✅ 也正确 —— 但不如 let 简洁
for (var i = 0; i < 3; i++) {
  (function(j) {  // j 是每次 IIFE 调用的参数，每次都是新的
    setTimeout(function() {
      console.log(j);
    }, 100);
  })(i); // 把当前的 i 值传进去
}
// 输出: 0, 1, 2
```

IIFE 方案的原理是为每次迭代手动创建一个新的函数作用域，把当前的 `i` 值复制到参数 `j` 中。每个回调函数闭包引用的是各自 IIFE 中的 `j`，而不是共享的全局 `i`。

### 7.2 函数获取的是最新值而非快照

闭包引用的是**变量本身**（引用），而不是变量在某时刻的**快照（副本）**：

```javascript
let value = "初始值";

function showValue() {
  console.log(value); // 不是创建时刻的值，而是调用时刻的最新值
}

value = "修改后";
showValue(); // "修改后"

value = "再次修改";
showValue(); // "再次修改"
```

这就像是你有一张写着"去仓库 A 取货"的单据（闭包引用变量），而不是"取 5 个苹果"的具体订单。每次你去仓库，拿到的是仓库里**当前存放的东西**，而不是单据开出那一刻仓库里有什么。

### 7.3 创建位置决定词法环境，而非调用位置

函数的 `[[Environment]]` 在**创建时**确定，指向**创建位置**的词法环境，而不是**调用位置**的环境：

```javascript
let name = "全局的 John";

function makeWorker() {
  let name = "内部的 Pete"; // 局部变量
  
  return function() {
    return name; // 记住的是 makeWorker 内部的 name
  };
}

let work = makeWorker(); // 函数在 makeWorker 内部创建

console.log(work()); // "Pete"（不是 "John"！）
```

即使我们在全局环境中调用 `work()`，它访问到的仍然是 `"Pete"`。因为 `work` 函数诞生于 `makeCounter()` 的词法环境之中——它的 `[[Environment]]` 指向那里，不管后来它被带到了哪里去执行。

这就好比一个人在他的家乡学会了说方言（在 `makeWorker` 中创建了函数），后来搬到了另一个城市（在外部调用），他说的依然是家乡话（访问的还是创建时的环境中的变量）。

## 八、最佳实践与设计模式

### 8.1 作用域设计原则

**原则一：最小暴露原则**

变量的作用域应该尽可能小。能用 `const` 就不用 `let`，能用 `let` 就不用 `var`，能用块级就不扩大到函数级：

```javascript
// ❌ 作用域过大
let result;
if (condition) {
  result = computeA();
} else {
  result = computeB();
}

// ✅ 作用域最小化
const result = condition ? computeA() : computeB();

// 或者使用即时使用的块级作用域
{
  const temp = expensiveCalculation();
  process(temp);
  // temp 在此块结束后即不可见
}
```

**原则二：避免全局污染**

尽量减少全局变量的数量。使用 IIFE（旧项目）或 ES Modules（现代项目）来实现作用域隔离：

```javascript
// ❌ 全局污染
let counter = 0;
function increment() { counter++; }

// ✅ 模块化隔离
// module.js
let counter = 0;
export function increment() { counter++; }
export function getCount() { return counter; }
```

**原则三：优先使用 const**

如果变量不需要重新赋值，使用 `const`。这不仅防止意外修改，还能帮助引擎进行优化（常量的值是不变的，可以做更多假设）：

```javascript
// ❌ 本应是常量但用了 let
let config = { url: "/api", timeout: 5000 };

// ✅ 明确表示不会变
const config = Object.freeze({ url: "/api", timeout: 5000 });
```

### 8.2 利用闭包实现数据私有化

闭包最常见的应用之一是模拟"私有变量"——利用闭包的特性让某些数据只能在特定的函数接口中被访问和修改：

```javascript
function createBankAccount(initialBalance) {
  // 这些变量被闭包保护，外部无法直接访问
  let balance = initialBalance;
  let transactions = [];

  return {
    deposit(amount) {
      balance += amount;
      transactions.push({ type: 'deposit', amount });
      return balance;
    },
    
    withdraw(amount) {
      if (amount > balance) throw new Error('余额不足');
      balance -= amount;
      transactions.push({ type: 'withdraw', amount });
      return balance;
    },
    
    getBalance() {
      return balance; // 只读接口
    },
    
    getHistory() {
      return [...transactions]; // 返回副本，防止外部篡改原数组
    },
  };
}

const account = createBankAccount(100);

account.deposit(50);   // 150
account.withdraw(30);  // 120
account.getBalance();   // 120

// account.balance = 9999999; // 无法直接修改！balance 不暴露给外部
// account.transactions = [];  // 同样无法直接访问！
```

这种模式在 JavaScript 没有 `private` 关键字的年代（ES2020 的 class private fields 之前）是唯一的"真正的私有数据"实现方式，至今仍然广泛使用。

### 8.3 闭包与内存管理注意事项

闭包虽然强大，但需要注意避免不必要的内存占用：

```javascript
// ⚠️ 潜在内存泄漏
function setupHandler(element) {
  let hugeData = /* 大型数据集 */;
  
  element.addEventListener('click', function() {
    // 这个闭包引用了 hugeData
    console.log('clicked');
    // 但其实并没有用到 hugeData！
  });
}

// ✅ 如果不需要 hugeData，不要让它被闭包捕获
function setupHandler(element) {
  let hugeData = /* 大型数据集 */; // 处理完
  
  let processedResult = processData(hugeData);
  hugeData = null; // 主动释放引用
  
  element.addEventListener('click', function() {
    // 闭包现在只引用 processedResult
    console.log(processedResult);
  });
}
```
