# 错误处理

> **核心内容**：JavaScript 错误处理机制的完整体系——`try...catch...finally` 的执行流程与底层原理、Error 对象的三大核心属性（name/message/stack）、内建错误类型体系（7 大类 + 子类型）、`throw` 的使用场景与最佳实践、重新抛出（rethrow）的选择性错误处理模式、自定义 Error 继承链与包装异常（exception wrapping）、异步错误的特殊行为，以及生产环境的全局错误监控方案。

---

## 一、程序中的错误——为什么需要处理它们？

在理想的世界里，代码永远按照我们写下的逻辑精确执行：输入合法的数据，网络请求永不失败，用户永远不会做奇怪的操作。但现实是残酷的——**错误是编程中不可避免的一部分**。

JavaScript 中的"错误"可以分为两个完全不同的层次：

**第一层：语法错误（Parse-time Errors）**

这是在代码被 JavaScript 引擎**解析（读取）阶段**就发现的问题。比如括号不匹配、关键字拼写错误、缺少分号等。这种错误就像是**一封地址写错的信件**——邮递员连信封都还没打开就发现寄不出去。对于这类错误，引擎直接拒绝执行整个脚本，`try...catch` 也无法挽救它：

```javascript
try {
  {{{{{{{{{{{{
} catch (err) {
  // 这里的 catch 永远不会执行！
  // 因为语法错误在解析时就已报错，根本没进入运行阶段
}
```

**第二层：运行时错误（Runtime Errors）**

这是代码语法正确，但在**执行过程中**出现的问题。比如访问未定义的变量、调用不存在的方法、除以零、JSON 解析失败等。这类错误就像是一封**内容有问题的正常信件**——信封本身没问题（代码能运行），但拆开后发现里面的信息不对。这正是 `try...catch` 能够捕获和处理的错误类型：

```javascript
try {
  console.log(undefinedVariable.name); // 运行时才暴露的问题
} catch (err) {
  console.log("捕获到错误:", err.message);
}
```

理解这个区分至关重要。很多初学者试图用 `try...catch` 来包裹明显有语法错误的代码段，结果困惑为什么不起作用。记住：**`try...catch` 只能处理运行时错误**。

## 二、try...catch...finally 的完整机制

### 2.1 基本结构与执行流程

`try...catch...finally` 是 JavaScript 处理运行时错误的唯一正式语法结构。它的完整形式包含三个可选的子句：

```javascript
try {
  // 尝试执行的代码 —— "危险区"
} catch (error) {
  // 当 try 中抛出错误时执行的代码 —— "安全网"
} finally {
  // 无论是否出错都会执行的代码 —— "收尾工作"
}
```

完整的执行流程可以用一个流程图来表示：

```
进入 try 块
    │
    ├── 执行 try 内部的代码
    │
    ├── 如果没有发生任何错误 ─────────────┐
    │   ↓                                  │
    │   跳过 catch 块                        │
    │   进入 finally 块                      │
    │   ↓                                  │
    │   继续执行后续代码 ◄─────────────────┘
    │
    └── 如果发生了错误（throw 或运行时异常）
        ↓
    try 块中剩余代码不再执行（立即跳出）
        ↓
    进入 catch 块（error 对象自动传入）
        │
        ├── 在 catch 中处理 / 记录 / 转换错误
        │
        ├── 进入 finally 块
        │   ↓
        │   根据 catch 的情况：
        │   ├── catch 中无 return/throw → 继续执行后续代码 ✓
        │   └── catch 中有 return/throw → 以该值为准
        │
        └── （如果没有 catch）→ 直接进入 finally → 然后向外传播错误
```

### 2.2 三种子句的使用场景

**场景一：只有 try 和 catch（最常见的用法）**

```javascript
function parseUserData(jsonString) {
  let user;
  
  try {
    user = JSON.parse(jsonString); // 可能抛出 SyntaxError
    console.log('解析成功:', user.name);
    
    if (!user.age) {
      throw new Error('数据缺少 age 字段'); // 业务层面的校验失败
    }
    
    return user;
    
  } catch (err) {
    console.error('数据处理失败:', err.message);
    return { name: '默认用户', age: 0 }; // 提供降级方案
  }
}

parseUserData('{ "name": "Alice", "age": 30 }');
// "解析成功: Alice"
// 返回 { name: "Alice", age: 30 }

parseUserData('{ bad json }');
// "数据处理失败: Unexpected token b in JSON at position 2"
// 返回 { name: "默认用户", age: 0 }（降级方案生效）

parseUserData('{ "name": "Bob" }'); // 缺少 age
// "数据处理失败: 数据缺少 age 字段"
// 返回 { name: "默认用户", age: 0 }
```

这里 `catch` 就像是给一段可能有风险的代码买了一份**保险**——如果出事了（解析失败或校验不过），保险就会赔付一个安全的默认值（fallback），让程序不至于崩溃。

**场景二：try...catch...finally（需要清理资源时）**

```javascript
let startTime;

function measurePerformance(taskName, taskFn) {
  startTime = Date.now();
  
  try {
    const result = taskFn();
    console.log(`[${taskName}] 成功完成，耗时 ${Date.now() - startTime}ms`);
    return result;
    
  } catch (err) {
    console.warn(`[${taskName}] 失败: ${err.message}`);
    return null; // 出错时返回 null
    
  } finally {
    // 无论成功还是失败，都要记录耗时！
    // finally 是计时器的必然归宿
    const duration = Date.now() - startTime;
    console.log(`[${taskName}] 总耗时: ${duration}ms`);
  }
}

measurePerformance('计算斐波那契', () => {
  function fib(n) {
    if (n < 0) throw new Error('不接受负数');
    return n <= 1 ? n : fib(n - 1) + fib(n - 2);
  }
  return fib(35);
});

// 输出：
// "[计算斐波那契] 成功完成，耗时 xxxms"
// "[计算斐波那契] 总耗时: xxxms"
```

**`finally` 的存在理由可以这样类比：**不管你做饭成功了还是把厨房烧了（`try` 正常结束 vs 抛出异常），最后都要关火（`finally` 清理操作）。关火这个动作不受做饭成败的影响——它是必须执行的收尾工作。常见的 `finally` 使用场景包括：释放文件句柄、关闭数据库连接、清除定时器、恢复 UI 状态等。

**场景三：try...finally（不需要 catch 但需要确保清理）**

有时候你不打算就地处理错误，但你必须确保某些清理逻辑一定会执行：

```javascript
function connectToDatabase(config) {
  let connection = null;
  
  try {
    connection = database.createConnection(config);
    // ... 一系列可能出错的数据库操作 ...
    return connection; // 成功则返回连接对象
    
  } finally {
    // 注意：没有 catch！如果出错，错误会继续向外传播
    // 但无论如何，连接都要关闭
    if (connection) {
      connection.close(); // 必须执行的清理
      console.log('数据库连接已关闭');
    }
  }
}
```

### 2.3 可选的 catch 绑定（ES2019）

如果你不关心具体的错误信息，可以省略 `catch` 的参数：

```javascript
// ES2019 之前的写法
try {
  riskyOperation();
} catch (err) {  // err 参数声明了但不使用
  console.log('出了点问题');
}

// ES2019+ 可以省略参数
try {
  riskyOperation();
} catch {  // 干净利落
  console.log('出了点问题');
}
```

### 2.4 finally 与 return 的交互

这是一个非常微妙且重要的知识点：**即使 `try` 或 `catch` 中包含了 `return` 语句，`finally` 中的代码仍然会在 `return` 之前执行**：

```javascript
function testFinallyWithReturn() {
  try {
    console.log(1);     // ① 先执行
    return '来自 try';
  } finally {
    console.log(2);     // ② 在 return 之前执行！
  }
  // 不可能有输出 3 了
}

console.log(testFinallyWithReturn());
// 输出顺序: 1 → 2 → "来自 try"
```

这看起来违反直觉——`return` 不是应该立刻终止函数吗？实际上是的，但规范规定 `finally` 的优先级更高。你可以这样理解：当引擎遇到 `return` 时，它会先"暂存"返回值，然后跳去执行 `finally`，`finally` 执行完毕后，再取回之前暂存的值作为真正的返回值。

但如果 `finally` 自身也有 `return`，那么它就会**覆盖**之前暂存的值：

```javascript
function testFinallyOverridesReturn() {
  try {
    return '来自 try';
  } finally {
    return '来自 finally'; // 这个 return 会胜出！
  }
}

console.log(testFinallyOverridesReturn()); // "来自 finally"
```

这种行为在实际开发中通常应该避免——不要在 `finally` 中写 `return`，因为这让代码的控制流变得难以理解和预测。`finally` 的职责应该是纯粹的清理工作，不应该参与值的传递决策。

## 三、Error 对象深度解析

当 JavaScript 引擎检测到一个运行时错误时，它会自动创建一个 **Error 对象**并沿着调用栈向上抛出。这个对象携带了关于错误的丰富信息，是我们诊断问题的关键工具。

### 3.1 三大标准属性

| 属性 | 类型 | 说明 | 示例值 |
|------|------|------|--------|
| `name` | String | 错误的类型名称（对应构造器名） | `"ReferenceError"` |
| `message` | String | 人类可读的错误描述 | `"x is not defined"` |
| `stack` | String | 完整的函数调用堆栈（非标准但广泛支持） | 多行字符串含行号 |

```javascript
try {
  undefinedVariable.someMethod();
} catch (err) {
  console.log('=== toString ===');
  console.log(err.toString());       // "TypeError: Cannot read properties of undefined (reading 'someMethod')"
  
  console.log('\n=== 各属性 ===');
  console.log('name:', err.name);         // "TypeError"
  console.log('message:', err.message);     // "Cannot read properties of undefined (reading 'someMethod')"
  
  console.log('\n=== 完整堆栈 ===');
  console.log(err.stack);
  // TypeError: Cannot read properties of undefined (reading 'someMethod')
  //     at <anonymous>:2:19
  //     at ...（更多堆栈帧）
}
```

**`stack` 属性的价值**在于它能告诉你**错误发生在哪里、经过哪些函数调用路径到达那里**。这在调试复杂应用时极其有用——你不需要靠猜来定位 bug，`stack` 会给你一张精确的"路线图"。每一条堆栈帧通常包含：函数名、文件路径、行号和列号。

### 3.2 JavaScript 内建错误类型体系

JavaScript 定义了 7 种标准的内置错误类型，每种对应一类特定的错误场景：

```
Error（所有错误类型的基类）
│
├── SyntaxError          —— 语法错误（代码本身有问题）
│   ├── 少了括号、逗号、分号
│   ├── 非法标识符
│   └── JSON.parse 解析失败
│
├── ReferenceError      —— 引用错误（变量/函数找不到）
│   ├── 访问未声明的变量（严格模式下）
│   ├── 访问不存在的属性
│   └── 调用 undefined/null 作为函数
│
├── TypeError           —— 类型错误（值不是期望的类型）
│   ├── 对非函数值使用 ()
│   ├── 修改只读属性
│   ├── null/undefined 上读取属性
│   └── this 绑定错误
│
├── RangeError          —— 范围越界
│   ├── 数组索引超出范围
│   ├── 栈溢出（递归过深）
│   └── 重复声明 Symbol
│
├── URIError             —— URI 编码错误
│   └── encodeURI / decodeURI 参数非法
│
├── EvalError            —— eval() 执行失败
│   └── 严格模式下使用 eval
│
└── AggregateError       —— 多个错误聚合（ES2021）
    └── Promise.allSettled 中的批量错误
```

```javascript
// 各种错误类型的触发示例
console.log('--- SyntaxError ---');
try { JSON.parse('{bad}'); } catch(e) { console.log(e.name, ':', e.message); }

console.log('--- ReferenceError ---');
try { console.log(notDefinedVar); } catch(e) { console.log(e.name, ':', e.message); }

console.log('--- TypeError ---');
try { null.method(); } catch(e) { console.log(e.name, ':', e.message); }

console.log('--- RangeError ---');
try { new Array(-1); } catch(e) { console.log(e.name, ':', e.message); }

console.log('--- EvalError ---');
try { new Function('"use strict"; eval"); } catch(e) { console.log(e.name, ':', e.message); }
```

这些内置错误类型之间也存在继承关系——它们都继承自 `Error` 类，所以 `instanceof` 检查具有传递性：

```javascript
const err = new TypeError('wrong type');
console.log(err instanceof Error);       // true
console.log(err instanceof TypeError);   // true
console.log(err instanceof RangeError);  // false
```

### 3.3 Error 对象的隐式创建

需要注意的是，大多数情况下你不需要手动 `new Error()`——JavaScript 引擎在很多场景下会**自动创建** Error 对象：

```javascript
// 以下情况引擎会自动抛出 Error 对象：
// 1. 访问未定义变量
x; // 自动抛出 ReferenceError

// 2. 调用非函数
null(); // 自动抛出 TypeError

// 3. 解析非法 JSON
JSON.parse('bad'); // 自动抛出 SyntaxError

// 4. 数组越界
[1,2][5]; // 自动抛出 undefined（不抛错，但某些环境会警告）
new Array(Number.MAX_VALUE); // RangeError
```

## 四、throw——主动出击的错误触发器

到目前为止我们看到的都是引擎被动抛出的错误。但 JavaScript 也允许你**主动**使用 `throw` 关键字来抛出错误——这就是所谓的"异常抛出"。

### 4.1 throw 的基本语法

```javascript
throw expression;
```

`throw` 后面可以跟任何表达式。虽然从技术上你可以 `throw` 任何值（数字、字符串、对象甚至 `undefined`），但**最佳实践是始终抛出一个 Error 对象（或其子类的实例）**：

```javascript
// ❌ 不推荐的写法
throw '出错了';              // 只是一个普通字符串
throw 404;                   // 只是一个数字
throw { code: 404, msg: 'Not Found' }; // 没有 stack 信息！

// ✅ 推荐的写法
throw new Error('出错了');                    // 标准 Error 对象
throw new ValidationError('数据验证失败');       // 自定义 Error（后面详述）
throw new HttpError('请求超时', { status: 504 }); // 带额外信息的自定义 Error
```

为什么要坚持使用 Error 对象？因为它自带三个关键属性（`name`、`message`、`stack`）。如果你 `throw` 一个普通字符串，你就丢失了堆栈信息和结构化的错误分类能力，这对调试来说是巨大的损失。

### 4.2 throw 的典型使用场景

**场景一：输入验证失败时主动抛错**

```javascript
function createOrder(orderData) {
  // 验证必填字段
  if (!orderData.productId) {
    throw new Error('订单必须包含 productId');
  }
  
  if (typeof orderData.quantity !== 'number' || orderData.quantity <= 0) {
    throw new TypeError('quantity 必须为正数');
  }
  
  if (orderData.quantity > 999) {
    throw new RangeError('单次下单数量不能超过 999');
  }
  
  // 所有验证通过，继续业务逻辑
  return { id: generateId(), ...orderData, status: 'pending' };
}
```

这里的 `throw` 就像是一道**安检门上的警报器**——当检查到不符合规定的物品（无效数据）时，立即触发警报（抛出错误），阻止其继续往下流动。与其带着脏数据进入后续的业务流程导致更难追踪的 bug，不如在入口处就直接拦截。

**场景二：根据条件选择不同的错误分支**

```javascript
class ApiClient {
  async fetchUser(id) {
    const response = await fetch(`/api/users/${id}`);
    
    if (!response.ok) {
      if (response.status === 404) {
        throw new NotFoundError(`用户 ${id} 不存在`, { userId: id });
      } else if (response.status >= 500) {
        throw new ServerError('服务器内部错误', { statusCode: response.status });
      } else if (response.status === 401) {
        throw new AuthError('认证失效，请重新登录');
      } else {
        throw new HttpError(`HTTP ${response.status}: ${response.statusText}`, { 
          statusCode: response.status 
        });
      }
    }
    
    return response.json();
  }
}
```

这种模式被称为**提前失败（Fail Fast）**原则：一旦发现问题就立即抛出错误，而不是带着无效状态继续执行后续代码。这能让错误发生的地点尽可能地接近其根源，便于定位和修复。

## 五、重新抛出（Rethrow）——选择性错误处理

这是错误处理中最重要的策略之一。它的核心理念是：**`catch` 块不应该是一个什么都处理的"黑洞"，而应该是一个智能的分拣中心——认识的处理，不认识的转交上级**。

### 5.1 为什么不能简单地吞掉所有错误？

```javascript
// ❌ 反模式：吞掉所有错误
function parseConfig(configJson) {
  try {
    const config = JSON.parse(configJson);
    validateConfig(config); // 假设这个函数内部也会抛错
    applyConfig(config);     // 这里也可能出错
    return config;
  } catch (e) {
    return getDefaultConfig(); // 不管什么错误都用默认配置？
  }
}
```

这段代码的问题是：它对**所有错误一视同仁**——无论是 JSON 格式错误（SyntaxError）、配置校验失败（ValidationError），还是一个意外的编程错误（ReferenceError 因为拼写错了变量名），全部静默地返回默认配置。结果是：真正严重的 bug 被掩盖了，调试变得极其困难。

### 5.2 选择性处理 + 重新抛出的正确模式

```javascript
function parseConfig(configJson) {
  try {
    const config = JSON.parse(configJson);
    validateConfig(config);
    applyConfig(config);
    return config;
    
  } catch (e) {
    // ====== 分拣中心 ======
    
    // 我认识的错误 → 我来处理
    if (e instanceof SyntaxError) {
      console.warn('JSON 格式错误，使用默认配置:', e.message);
      return getDefaultConfig();
    }
    
    // 我认识的错误 → 我来处理
    if (e instanceof ValidationError) {
      console.warn('配置校验未通过:', e.message);
      return getDefaultConfig();
    }
    
    // 我不认识的错误 → 交给上层处理！
    throw e; // ← rethrow！让外层的 try-catch 来处理
  }
}

// 外层兜底
try {
  const config = parseConfig(userInput);
} catch (e) {
  // 这里能收到 rethrow 过来的未知错误
  sendErrorToMonitoringService(e);
  showUserErrorMessage('系统暂时不可用，请联系管理员');
}
```

这种模式的执行逻辑就像是一个**公司客服分级制度**：

- **一级客服（内层 catch）**：处理常见问题（JSON 格式错误、校验失败等），这些问题他们有标准答案。
- **二级主管（外层 catch）**：处理一级客服无法解决的疑难杂症（未知错误），他们会升级处理——记录日志、通知技术团队等。
- **rethrow 就是"升级工单"**——一级客服知道自己解决不了，于是把问题原封不动地往上提交。

### 5.3 多层嵌套的 rethrow 协作

在大型应用中，错误可能会经过多层 catch 的过滤和包装：

```javascript
// 第三层：最底层的具体业务逻辑
function processPayment(paymentData) {
  try {
    validateCardNumber(paymentData.cardNo);
    chargeAmount(paymentData.amount);
    sendConfirmation(paymentData.email);
  } catch (e) {
    if (e instanceof CardError) {
      throw new PaymentError('支付卡片验证失败', { cause: e }); // 包装后 rethrow
    }
    throw e; // 其他错误直接 rethrow
  }
}

// 第二层：API 调用层
function handlePaymentRequest(request) {
  try {
    const result = processPayment(request.body);
    return { success: true, data: result };
  } catch (e) {
    if (e instanceof PaymentError) {
      throw new ApiError('支付处理失败', { statusCode: 400, cause: e }); // 再次包装
    }
    throw e;
  }
}

// 第一层：路由/控制器层
app.post('/pay', async (req, res) => {
  try {
    const response = handlePaymentRequest(req.body);
    res.json(response);
  } catch (e) {
    // 最终兜底
    logError(e);
    
    if (e instanceof ApiError) {
      res.status(e.statusCode).json({ error: e.message });
    } else {
      res.status(500).json({ error: 'Internal Server Error' });
    }
  }
});
```

这种多层包装后的错误对象形成了一条**错误链条（Error Chain）**——每一层都添加了自己的上下文信息，同时保留了原始错误的完整信息。这就好比是事故报告层层上报：现场员工填写第一层报告 → 部门经理补充管理上下文 → 公司高层添加战略影响。每一层都在前一层的基础上增值，最终形成一个完整的错误全景图。

## 六、自定义错误类型

虽然内置的 7 种错误类型覆盖了大部分通用场景，但在实际项目中，你几乎总是需要定义自己的错误类型——因为你的业务领域中有自己特有的"错误语言"。

### 6.1 为什么要继承 Error？

你可能会想："我为什么不直接 `throw` 一个字符串或者一个普通对象？"原因有三：

1. **类型识别**：继承 Error 后可以使用 `instanceof` 来判断错误类型（`if (err instanceof MyCustomError)`），这比检查字符串属性更可靠、更具扩展性
2. **属性支持**：自动获得 `name`、`message`、`stack` 三个标准属性，无需手动维护
3. **工具兼容性**：错误监控服务、日志框架、调试工具都能正确识别和处理 Error 对象

```javascript
class CustomError extends Error {
  constructor(message) {
    super(message); // ⭐ 必须先调 super 设置 message
    this.name = 'CustomError'; // 然后重置 name 为自定义名称
  }
}

const err = new CustomError('出问题了');

console.log(err instanceof Error);    // true ✓
console.log(err instanceof CustomError); // true ✓
console.log(err.name);                 // "CustomError"
console.log(err.message);               // "出问题了"
console.log(err.stack);                  // 包含完整堆栈 ✓
```

### 6.2 构建自定义错误层级体系

在大型项目中，通常会构建一棵自定义错误的**继承树**：

```javascript
// ========== 第一层：基础错误类 ==========
class AppError extends Error {
  constructor(message, options = {}) {
    super(message);
    this.name = this.constructor.name; // 自动设为当前类名
    this.code = options.code || 'APP_ERROR';
    this.statusCode = options.statusCode || 500;
    this.cause = options.cause || null; // 存储原始错误（用于错误链）
    this.timestamp = new Date().toISOString();
    this.context = options.context || {};
  }
  
  // 方便地转为可序列化格式
  toJSON() {
    return {
      name: this.name,
      message: this.message,
      code: this.code,
      statusCode: this.statusCode,
      timestamp: this.timestamp,
      context: this.context,
      ...(this.cause ? { cause: { name: this.cause.name, message: this.cause.message } } : {})
    };
  }
}

// ========== 第二层：领域错误类 ==========
class ValidationError extends AppError {
  constructor(message, fields = {}) {
    super(message, { code: 'VALIDATION_ERROR', statusCode: 400 });
    this.fields = fields; // 哪些字段校验失败了
  }
}

class NetworkError extends AppError {
  constructor(message, options = {}) {
    super(message, { code: 'NETWORK_ERROR', statusCode: 503, ...options });
  }
}

class AuthError extends AppError {
  constructor(message, options = {}) {
    super(message, { code: 'AUTH_ERROR', statusCode: 401, ...options });
  }
}

// ========== 第三层：更具体的错误 ==========
class RequiredFieldError extends ValidationError {
  constructor(field) {
    super(`缺少必填字段: ${field}`, { [field]: 'required' });
    this.missingField = field;
  }
}

class TimeoutError extends NetworkError {
  constructor(url, timeout) {
    super(`${url} 请求超时 (${timeout}ms)`, { url, timeout });
  }
}

class InvalidTokenError extends AuthError {
  constructor(details) {
    super(`Token 无效: ${details}`, { details });
  }
}
```

### 6.3 使用自定义错误：实战案例

```javascript
async function registerUser(userData) {
  // 第一层验证：基本格式
  try {
    validateBasic(userData);
  } catch (e) {
    throw new RequiredFieldError(e.field); // 包装为领域错误
  }
  
  // 第二层：网络请求
  try {
    const response = await fetch('/api/users', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${userData.token}` },
      body: JSON.stringify(userData)
    });
    
    if (!response.ok) {
      if (response.status === 401) {
        throw new InvalidTokenError('token 已过期');
      }
      if (response.status === 409) {
        throw new AppError('用户已存在', { code: 'USER_EXISTS', statusCode: 409 });
      }
      throw new NetworkError(`注册失败: HTTP ${response.status}`);
    }
    
    return await response.json();
    
  } catch (e) {
    // 网络层面的错误保持不变，直接向上传播
    if (e instanceof NetworkError || e instanceof AuthError) throw e;
    
    // 其他意外错误也包装一下
    throw new AppError('注册流程异常', { cause: e });
  }
}

// 控制器中使用
router.post('/register', async (req, res) => {
  try {
    const user = await registerUser(req.body);
    res.status(201).json({ success: true, data: user });
    
  } catch (e) {
    // 统一的错误处理中间件
    console.error('[Register]', e.toJSON());
    
    if (e instanceof ValidationError) {
      return res.status(400).json({ error: e.message, fields: e.fields });
    }
    
    if (e instanceof AuthError) {
      return res.status(401).json({ error: e.message, code: 'NEED_LOGIN' });
    }
    
    if (e instanceof NetworkError) {
      return res.status(503).json({ error: e.message, code: 'SERVICE_UNAVAILABLE' });
    }
    
    // 兜底
    res.status(500).json({ error: e.message || '服务器内部错误' });
  }
});
```

### 6.4 错误包装（Exception Wrapping）模式详解

上面代码中反复出现的"捕获→包装→重抛"模式有一个正式的名字——**异常包装（Exception Wrapping）**。这是一种将低层错误转换为高层错误的设计模式，它的核心价值在于**抽象层次隔离**：

```javascript
// 低层函数：关心的是 JSON 能否解析、HTTP 状态码是什么
function lowLevelReadUser(json) {
  try {
    return JSON.parse(json);
  } catch (e) {
    // 低层只知道"JSON 解析失败了"
    throw new AppError('读取用户数据失败', { cause: e });
  }
}

// 高层函数：关心的是"能不能拿到有效的用户数据"
function highLevelGetUser(input) {
  let user;
  try {
    user = lowLevelReadUser(input); // 可能抛出 ReadError
    validateUser(user);            // 可能抛出 ValidationError
    sanitizeUser(user);             // 可能抛出 SanitizationError
    return user;
  } catch (e) {
    // 高层统一包装为一个"获取用户数据失败"的错误
    throw new AppError('获取用户数据失败', { cause: e });
  }
}

// 更高层的调用者：完全不关心底层细节
try {
  const user = highLevelGetUser(someInput);
  showUserProfile(user);
} catch (e) {
  // 只需要知道"拿用户数据失败了"，不需要知道
  // 是 JSON 错了、校验错了、还是清洗出了问题
  showGenericErrorPage(e);
}
```

这种分层包装的好处是：**每一层只需要关心自己那一层的事情**。低层函数负责处理低级的具体错误；高层函数负责把它们统一成一个语义清晰的业务错误；UI 层只需展示友好的错误信息给用户。每一层都适当地隐藏了下层的实现细节，使得代码的关注点清晰分离。

## 七、异步错误处理的特殊性

前面讨论的所有 `try...catch` 规则都是针对**同步代码**的。当代码涉及异步操作（如 `setTimeout`、Promise、事件监听器）时，错误的捕获方式会有所不同。

### 7.1 setTimeout/setInterval 中的错误

```javascript
// ❌ 这种写法无法捕获异步回调中的错误
try {
  setTimeout(function() {
    undefinedVar.doSomething(); // 1000ms 后才执行的错误
  }, 1000);
} catch (e) {
  console.log('永远不会执行到这里'); // 因为 setTimeout 的回调在 try 块结束后才执行
}

// ✅ 正确做法：将 try...catch 放到异步函数内部
setTimeout(function() {
  try {
    undefinedVar.doSomething();
  } catch (e) {
    console.log('异步错误被捕获了:', e.message);
  }
}, 1000);
```

为什么会这样？因为 `setTimeout(fn, delay)` 只是告诉引擎"请在 `delay` 毫秒后执行 `fn`"——这个注册动作本身是同步完成的，所以 `try` 块正常结束。但当 `fn` 在未来某个时刻真正执行时，原来的 `try...catch` 结构早就已经不在调用栈上了。此时的错误只能由 `fn` 自己内部的 `try...catch` 来处理。

### 7.2 Promise 中的 .catch()

Promise 提供了一种专门为异步设计的错误处理机制——`.then()` / `.catch()` 链：

```javascript
fetch('/api/data')
  .then(response => {
    if (!response.ok) {
      throw new HttpError(`HTTP ${response.status}`); // Promise 链中的 throw
    }
    return response.json();
  })
  .then(data => {
    console.log('拿到数据:', data);
  })
  .catch(error => {
    // 捕获 then 中抛出的任何错误（包括 reject 和显式 throw）
    console.error('数据获取失败:', error.message);
  });
```

`.catch()` 与 `try...catch` 的区别在于：`.catch()` 是**时间解耦**的——你在声明 `.catch()` 回调的那一刻并不需要错误真的发生，只要在 Promise 链的将来某一点上出现了 reject 或 throw，这个 `.catch()` 就会被激活。

### 7.3 全局异步错误：unhandledrejection

对于 Promise 中未被任何 `.catch()` 处理的错误（即 unhandled rejection），浏览器和 Node.js 都提供了全局的兜底机制：

```javascript
// 浏览器和 Node.js 都支持
window.addEventListener('unhandledrejection', event => {
  console.error('未处理的 Promise 拒绝:', event.reason);
  
  // 可以在这里做统一的错误收集
  reportToErrorService({
    type: 'unhandled_promise_rejection',
    error: event.reason,
    timestamp: new Date().toISOString(),
  });
  
  // preventDefault() 可以防止控制台显示红色错误
  // event.preventDefault();
});

// 故意产生一个未处理的 Promise 拒绝
Promise.reject(new Error('测试未处理错误'));
```

这相当于是在整栋大楼的**屋顶上装了一个最终的安全网**——即使所有的窗户（局部 `try...catch`）都没接住掉下来的人（未处理的错误），这个屋顶网也能兜住他。

## 八、全局错误捕获——最后一道防线

无论你的代码写得多么小心谨慎，总有一些意料之外的错误会漏过所有的局部 `try...catch`。全局错误处理器就是用来捕获这些"漏网之鱼"的。

### 8.1 window.onerror（浏览器环境）

```javascript
window.onerror = function(message, source, lineno, colno, error) {
  // message: 错误消息字符串（如 "Uncaught TypeError: ..."）
  // source: 发生错误的脚本 URL
  // lineno: 行号
  // colno: 列号
  // error: Error 对象（部分浏览器可能不提供）
  
  console.error('全局错误捕获:');
  console.error(`  消息: ${message}`);
  console.error(`  位置: ${source}:${lineno}:${colno}`);
  console.error(`  堆栈: ${error?.stack?.substring(0, 200)}`);
  
  // 发送到远程错误监控服务
  sendToLogService({
    message,
    source,
    line: lineno,
    column: colno,
    stack: error?.stack,
    url: location.href,
    userAgent: navigator.userAgent,
  });
  
  // 通常返回 true 表示"错误已被处理"，浏览器不会再显示默认错误
  return true; 
};

// 测试
function buggyFunction() {
  oopsThisVariableDoesNotExist;
}

buggyFunction(); // 触发 window.onerror
```

### 8.2 process.on('uncaughtException')（Node.js 环境）

```javascript
process.on('uncaughtException', (err) => {
  console.error('进程级未捕获异常:', err.message);
  console.error('堆栈:', err.stack);
  
  // 在 Node.js 服务中，你可能想要优雅地关闭
  // 而不是让进程崩溃
  gracefulShutdown(err);
  
  // 注意：如果在 uncaughtException 中再次抛出错误，
  // 进程将会崩溃退出
});
```

### 8.3 生产环境的完整错误监控方案

在实际的生产环境中，通常会集成专业的前端错误监控服务（如 Sentry、LogRocket、Fundebug 等）。以下是集成的核心思路：

```javascript
// lib/error-monitor.js —— 错误监控模块

class ErrorMonitor {
  constructor(options = {}) {
    this.endpoint = options.endpoint || '/api/errors';
    this.appVersion = options.appVersion || '1.0.0';
    this.environment = options.environment || 'production';
    this.sampleRate = options.sampleRate || 1.0; // 采样率
    this.user = options.user; // 当前登录用户信息
  }
  
  init() {
    // 注册全局错误处理器
    window.onerror = (msg, src, line, col, err) => {
      this.capture({
        type: 'javascript_error',
        message: msg,
        source: src,
        line,
        column: col,
        stack: err?.stack,
        isTrusted: false, // 来自第三方脚本的错误可能不可信
      });
      return true; // 已处理，不显示默认弹窗
    };
    
    // 注册未处理 Promise 拒决
    window.addEventListener('unhandledrejection', (event) => {
      this.capture({
        type: 'unhandled_promise_rejection',
        message: event.reason?.message || String(event.reason),
        stack: event.reason?.stack,
      });
    });
    
    // 注册资源错误（图片加载失败等）
    window.addEventListener('error', (event) => {
      if (event.target instanceof HTMLImageElement ||
          event.target instanceof HTMLScriptElement) {
        this.capture({
          type: 'resource_error',
          message: `加载资源失败: ${event.target.src || event.target.href}`,
          element: event.target.tagName,
        });
      }
    });
  }
  
  capture(errorInfo) {
    // 采样控制：避免在高流量下发送过多错误
    if (Math.random() > this.sampleRate) return;
    
    const payload = {
      ...errorInfo,
      appVersion: this.appVersion,
      environment: this.environment,
      url: location.href,
      userAgent: navigator.userAgent,
      screenResolution: `${screen.width}x${screen.height}`,
      timestamp: new Date().toISOString(),
      user: this.user ? { id: this.user.id, name: this.user.name } : null,
    };
    
    // 使用 navigator.sendBeacon 保证页面关闭时也能发送
    if (navigator.sendBeacon) {
      navigator.sendBeacon(this.endpoint, JSON.stringify(payload));
    } else {
      fetch(this.endpoint, {
        method: 'POST',
        body: JSON.stringify(payload),
        keepalive: true,
        headers: { 'Content-Type': 'application/json' },
      }).catch(() => {}); // 静默失败
    }
  }
}

// 初始化
const monitor = new ErrorMonitor({
  endpoint: '/api/log-error',
  appVersion: '2.1.0',
  environment: 'production',
}).init();

export default monitor;
```

这套监控系统的设计遵循了一个重要原则：**错误收集应该是"静默"且"不影响用户体验"的**——使用 `sendBeacon`（而非普通的 `fetch`）确保即使页面正在关闭也能发出请求；设置采样率避免性能开销过大；返回 `true` 阻止浏览器弹出默认的错误提示框。

## 九、常见陷阱与最佳实践

### 9.1 陷阱速查表

| 陷阱 | 问题表现 | 正确做法 |
|------|---------|---------|
| **吞掉错误**（空 catch 体） | 错误悄无声息地消失，难以排查 | 至少记录日志，必要时 rethrow |
| **catch 中不 rethrow 未知错误** | 严重 bug 被掩盖 | 用 `instanceof` 分类处理后 rethrow 其余 |
| **try 包裹异步回调外部** | 异步错误无法被捕获 | 将 try...catch 放入异步函数内部 |
| **finally 中修改返回值** | 行为难以预期 | finally 只做清理，不参与值决策 |
| **throw 非 Error 对象** | 丢失 stack 信息 | 始终 `throw new Error(...)` 或其子类 |
| **依赖 window.onerror 做主要错误处理** | 它只是最后的兜底 | 应该在代码层面用 try-catch 主动处理 |
| **混淆 SyntaxError 与其他错误** | 认为 try-catch 能修复语法错误 | 语法错误必须在编写阶段修正 |

### 9.2 最佳实践清单

**原则一：Fail Fast（尽早失败）**

```javascript
// ✅ 一旦发现问题就立即抛出
function divide(a, b) {
  if (b === 0) throw new Error('除数不能为零');
  return a / b;
}

// ❌ 带着 invalid state 继续执行
function divideBad(a, b) {
  if (b === 0) { b = 1; console.warn('修正为零的除数'); } // 隐蔽问题
  return a / b; // 结果可能是错误的，且没人知道
}
```

**原则二：错误应该有意义（Informative）**

```javascript
// ❌ 含糊的错误
throw new Error('出错了');

// ✅ 有明确指导意义的错误
throw new ValidationError('邮箱格式不正确', { 
  field: 'email', 
  value: userInput,
  expectedFormat: 'xxx@yyy.com'
});
```

**原则三：每一层只处理自己认识的错误**

```javascript
// ✅ 选择性处理
catch (e) {
  if (e instanceof KnownErrorTypeA) { /* 处理 A */ }
  else if (e instanceof KnownErrorTypeB) { /* 处理 B */ }
  else throw e; // 不认识的交给上层
}
```

**原则四：finally 只做清理不做决策**

```javascript
// ✅ finally 的职责单一
try {
  db.beginTransaction();
  doSomethingRisky();
  db.commitTransaction();
} catch (e) {
  db.rollbackTransaction();
  throw e; // 决策：回滚并重新抛出
} finally {
  db.releaseConnection(); // 清理：释放连接（始终执行）
}
```

**原则五：异步错误用异步方式处理**

```javascript
// ✅ Promise 链式处理
async function fetchData() {
  try {
    const response = await fetch(url);
    return await response.json();
  } catch (e) {
    logger.error('Fetch failed', e);
    return fallbackData;
  }
}

// ✅ async/await 配合 try-catch（推荐）
// ❌ 不要用同步 try-catch 包裹异步回调的外部
```

## 十、知识图谱

```
JavaScript 错误处理完整体系
│
├── 错误的两层分类
│   ├── 语法错误（Parse-time）—— try-catch 无法捕获
│   │   └── 括号不匹配、非法字符、保留字误用
│   └── 运行时错误（Runtime）—— try-catch 的目标
│       └── 变量未定义/类型不对/值越界/API 调用失败
│
├── try...catch...finally 结构
│   ├── try —— "危险区"：尝试执行可能出错的代码
│   ├── catch(err) —— "安全网"：捕获并处理错误
│   │   ├── err.name —— 错误类型名
│   │   ├── err.message —— 人类可读描述
│   │   └── err.stack —— 完整调用堆栈
│   └── finally —— "收尾工作"：必定执行的清理逻辑
│       ├── 即使 try/catch 中有 return 也会先于 return 执行
│       └── 无 catch 时 finally 后错误继续向外传播
│
├── throw —— 主动抛出错误
│   ├── 推荐：始终 throw Error 对象（保留 stack 信息）
│   └── 场景：输入验证、Fail Fast、状态机切换
│
├── 内建错误类型（7 种）
│   ├── Error（基类）
│   ├── SyntaxError —— 语法/解析错误
│   ├── ReferenceError —— 未定义引用
│   ├── TypeError —— 类型不匹配
│   ├── RangeError —— 越出有效范围
│   ├── URIError —— URL 编解码错误
│   ├── EvalError —— eval 执行错误
│   └── AggregateError（ES2021）—— 多错误聚合
│
├── 重新抛出（Rethrow）模式
│   └── 分拣中心：认识的错误处理，不认识的 rethrow
│       └── 形成错误链：每层包装增加上下文
│
├── 自定义错误类型
│   ├── 继承 Error 的好处（instanceof / stack / 属性）
│   ├── 基础类：super(msg) + 重置 name
│   ├── 继承树：AppError → DomainError → SpecificError
│   └── Exception Wrapping（异常包装/错误链）
│       ├── 底层错误 → 高层错误
│       └── cause 属性保存原始错误
│
├── 异步错误处理
│   ├── setTimeout/setInterval：try 放进回调内部
│   ├── Promise: .then().catch()
│   └── 全局兜底: unhandledrejection / uncaughtException
│
├── 全局错误捕获
│   ├── 浏览器: window.onerror(msg, src, line, col, error)
│   ├── 浏览器: addEventListener('error')
│   ├── Node.js: process.on('uncaughtException')
│   └── 生产方案: sendBeacon + 采样率 + Sentry/自建服务
│
└── 设计原则
    ├── Fail Fast（尽早失败）
    ├── Informative Error（有意义的错误信息）
    ├── Selective Handling（选择性处理）
    ├── Finally Only Cleanup（finally 只做清理）
    └── Async Error Async Handle（异步错误异步处理）
```
