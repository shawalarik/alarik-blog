# 严格模式 —— "use strict" 的完整行为变化、与宽松模式的逐项对比

> **核心内容**：JavaScript 严格模式的完整解析——启用方式（全局/函数级/模块自动）、9 项核心行为改变（`this` 指向、变量未定义行为、删除限制、保留字保护、eval 安全性、arguments 不可变、八进制语法、重复声明/参数、with 禁用）、TDZ（暂时性死区）的底层原理、var 与 let/const 的作用域差异，以及为什么现代开发应该始终使用严格模式。

---

## 一、什么是严格模式——JavaScript 的"安全驾驶模式"

在 JavaScript 诞生的早期阶段（1995-2009 年），语言的设计者为了让这门语言对初学者"友好"，做出了许多宽容甚至可以说是"纵容"的决定：未声明的变量不会报错而是静默创建全局变量、`this` 在错误的地方也不会抛异常而是指向全局对象、重复声明被悄悄忽略……这些设计在当时看来是善意的帮助新手避免报错，但随着项目规模的增长，它们变成了**隐藏 bug 的温床**。

2009 年发布的 ES5 标准引入了**严格模式（Strict Mode）**——一个可选的、向后兼容的"安全增强包"。你可以把它想象成 JavaScript 的**"安全驾驶模式"**：

- **默认模式（Sloppy Mode）**就像是在一条没有交通规则的路上开车——你可以随意变道、闯红灯也没人拦你。看起来很自由，但随时可能撞车。
- **严格模式（Strict Mode）**则像是在有完善交通规则的高速公路上行驶——虽然规则更多更严，但你和所有人都能更快更安全地到达目的地。

严格模式的核心设计哲学可以概括为一句话：**让错误尽早暴露出来，而不是在沉默中蔓延到不可控的地步。**

### 1.1 为什么要使用严格模式？

在实际开发中，严格模式带来的好处远大于它带来的"麻烦"：

| 好处 | 说明 |
|------|------|
| **消除隐式全局变量** | ` undeclaredVar = 'hello'` 直接报错而不是污染全局 |
| **防止意外的 this 绑失** | 函数调用时 `this` 为 undefined 而非 window |
| **消除静默失败的操作** | 删除不可配置属性会抛出错误而非静默失败 |
| **为未来标准铺路** | 很多新特性只在严格模式下可用（class、模块、箭头函数等） |

```javascript
// 宽松模式下这段代码能"运行"，但结果完全错误
function createUser() {
  userName = "Alice"; // 本意声明局部变量
}

createUser();
console.log(userName); // "Alice" —— 但它是全局变量！任何代码都能访问
// 如果其他地方也用了 userName 就会被覆盖或覆盖别人
```

```javascript
// 严格模式下同样代码立即暴露问题
'use strict';

function createUser() {
  userName = "Alice"; // 💥 ReferenceError: userName is not defined
}
```

这就是严格模式的价值——**与其让一个错误的程序带着隐含的 bug 长期运行，不如让它在一开始就大声报警**。

### 1.2 严格模式不是新语言，而是同一语言的"严格版本"

这是一个非常重要的认知：严格模式并没有创造新的 JavaScript 语法或特性。它只是**改变了已有特性的行为规则**——同样的代码在不同的模式下可能产生不同的执行结果。这就像是同一个人穿休闲装还是穿正装——本质上是同一个人，但在不同场合下行为规范不同：

```javascript
// 同样的代码，在不同模式下表现不同
function testThis() {
  console.log(this);
}

testThis();           // 宽松模式: Window { ... } （可能不是你想要的）
'use strict';
testThis();          // 严格模式: undefined （明确告诉你这里有问题）
```

## 二、如何开启严格模式

JavaScript 提供了三种方式来激活严格模式，每种方式的作用范围不同：

### 2.1 全局严格模式（脚本级别）

将 `'use strict';` 放置在整个脚本文件的最顶部：

```javascript
'use strict'; // ⭐ 必须在所有代码之前

// 整个文件中的代码都处于严格模式
const app = {
  name: "MyApp",
  
  init() {
    // 这里的代码也是严格模式
    console.log('初始化中...');
  }
};

app.init();
```

**关键要求**：
- `'use strict'` 必须出现在**最顶部**
- 它前面只能有注释，不能有任何实际代码语句
- 如果它后面还有其他语句，那严格模式不会被激活（相当于被"淹没"了）

```javascript
// ❌ 错误：use strict 被忽略了
console.log('这行代码先执行');
'use strict'; // 太晚了！上面的代码已经在宽松模式下跑过了
```

### 2.2 函数级严格模式（局部模式）

将 `'use strict'` 放在函数体的最内部，只有该函数内的代码受影响：

```javascript
function strictFunction(x, y) {
  'use strict'; // 只在这个函数内生效
  
  // 这里的代码是严格模式
  console.log(this); // undefined
  undeclaredVar = 10;   // ReferenceError
}
  
  return x + y;
}

function sloppyFunction(a, b) {
  // 这里不受上面那个 'use strict' 影响
  // 仍然是宽松模式
  console.log(this); // window
  globalVar = 20;     // 全局变量被创建 ✓（但不应该这样做）
  
  return a * b;
}

strictFunction(3, 5);
sloppyFunction(4, 6); // 宽松模式下 globalVar 被创建
```

函数级严格模式适用于以下场景：
- 你只想让某个特定函数更严格地运行
- 你正在维护一个大型旧代码库，不想一次性全部改为严格模式
- 你需要把某个第三方库包裹起来，隔离它的宽松模式行为

### 2.3 类与模块——自动严格模式

这是最重要也最常见的方式：**在现代 JavaScript 开发中，你几乎不需要手动写 `'use strict'`**：

```javascript
// ====== Class 自动严格模式 ======
class MyClass {
  constructor(name) {
    this.name = name;  // 内部已经是严格模式
  }
  
  method() {
    undeclared = 1;     // ReferenceError! 不需要手动 use strict
  }
}

const obj = new MyClass('Test');

// ====== Module (.mjs 文件) 自动严格模式 ======
// export {};
// import {} from './file.js';

// 模块中的所有代码自动处于严格模式
undeclaredInModule = 'hi';  // ReferenceError!
```

ES2015 引入的 `class` 和 ES2015 Modules（`.mjs` 文件）**自动启用了严格模式**，不需要也不允许你在其中再写 `'use strict'`。这意味着如果你全程使用 class 和 module 来组织代码（这正是现代前端项目的标配），你的整个项目天然就是严格模式下的——这是推荐的做法。

### 2.4 控制台中的严格模式

在浏览器开发者工具的控制台中运行代码时，默认不启动严格模式。有两种方式解决：

**方法一：多行输入 + Shift+Enter**

大多数现代浏览器的控制台支持 Shift+Enter 来换行输入，确保第一行是 `'use strict';`：

```javascript
// 在 Chrome/Firefox 控制台中:
'use strict';       // 第一行
Shift+Enter 换行      // 输入其余代码...
alert('严格模式生效');
// 按 Enter 执行
```

**方法二：IIFE 包装器**

```javascript
(function() {
  'use strict';
  yourCodeHere();
})();
```

## 三、9 项核心行为变化详解

以下是严格模式相对于宽松模式的所有重要行为改变。每一项都是面试中的高频考点，也是日常开发中容易踩坑的地方。

### 3.1 变量必须先声明后使用（消除隐式全局创建）

**宽松模式**：访问未声明的变量不会报错，而是在全局对象上创建一个同名属性。这被称为**意外全局变量（Accidental Global Variable）**——是 JS 中最常见的 bug 来源之一。

**严格模式**：访问未声明的变量直接抛出 `ReferenceError`。

```javascript
// ========== 宽松模式 ==========
userName = 'Alice'; // 没有 var/let/const —— 不报错！
console.log(userName);   // "Alice"
// 但实际上 userName 成了 window.userName —— 全局污染！

// ========== 严格模式 ==========
'use strict';
userAge = 25;            // 💥 ReferenceError: userAge is not defined
// 错误立刻暴露，不会偷偷创建全局变量
```

**为什么宽松模式要这样设计？** 这是历史遗留的"善意"。早期 JS 的设计者认为：如果程序员忘了写 `var`，引擎帮他创建一个全局变量是一种"帮忙"。但这种"帮忙"在实践中导致了无数难以追踪的 bug——因为拼写错误产生的意外全局变量不会报错，只是静默地创建了某个属性，后续代码可能在完全不知情的情况下读取到这个错误值。

**类比**：宽松模式像是**没有门禁的门卫系统的大楼**——谁都能进，包括小偷和推销员（意外全局变量），虽然方便但也混乱。严格模式则是**每扇门都有门禁系统的写字楼**——没带工牌的人（未声明变量）直接被拦在外面，虽然麻烦但安全有序。

### 3.2 函数调用时的 this 指向

这是严格模式和宽松模式之间**影响最广泛**的一个差异，因为它影响了几乎所有涉及函数调用的场景。

**宽松模式**：独立调用的函数（即不是作为对象的方法调用），其内部的 `this` 指向**全局对象**（浏览器中是 `window`）。

**严格模式**：独立调用的函数，其内部的 `this` 为 **`undefined`**。

```javascript
'use strict';

function showThis() {
  console.log(`this: ${String(this)}`);
}

showThis();        // "this: undefined" ← 严格模式：独立调用 this 为 undefined
window.showThis(); // "this: [object Window]" ← 方法调用：this 为 window
```

这个变化的深层意义在于：**严格模式让你更容易发现 `this` 相关的错误**。在宽松模式下，当 `this` 意外地指向全局对象时，你可能给全局对象添加了一些属性而不自知——这些属性永远不会报错，但会导致难以排查的逻辑错误。而在严格模式下，尝试访问 `undefined.xxx` 会直接抛出 `TypeError`——问题立刻暴露。

```javascript
'use strict';

const obj = {
  name: 'Test',
  
  introduce() {
    // 宽松模式：如果这里是普通函数，this 可能指向 window
    console.log(`你好，我是 ${this.name}`); 
  },
  
  badExample() {
    // 用箭头函数确保 this 总是指向 obj
    const print = () => {
      console.log(`你好，我是 ${this.name}`);
    };
    print();
  }
};

obj.introduce();   // ✓ this === obj
obj.badExample(); // ✓ 箭头函数的 this 词法绑定正确
```

### 3.3 删除不可配置属性时报错

**宽松模式**：使用 `delete` 操作符删除对象的属性时，即使操作失败（比如属性不可删除），也只是静默返回 `false`，不会报错。

**严格模式**：试图删除不可配置（non-configurable）的属性会抛出 `TypeError`：

```javascript
'use strict';

const immutable = {};

Object.defineProperty(immutable, 'frozen', {
  value: 'cannot delete me',
  writable: true,
  configurable: false  // 关键：设为 false 表示不可配置
});

// 尝试删除
delete immutable.frozen; // 💥 TypeError: Cannot delete property 'frozen'
```

宽松模式下同样的操作只会返回 `false`（静默失败），你可能以为删除成功了但实际上属性还在那里。严格模式通过抛出错误强制你必须正视这个问题。

### 3.4 禁止使用保留字作为变量名

ECMAScript 规范定义了一系列**保留字（Reserved Words）**——这些词在未来版本的 JavaScript 中可能被用作关键字（如 `class`、`let`、`const`、`yield`、`import`、`export`、`static`、`extends` 等）。在宽松模式下使用这些词作为变量名虽然不推荐，但不会报错。严格模式则会直接抛出 `SyntaxError`：

```javascript
'use strict';

// 这些词现在是关键字或保留字
let class = 10;         // SyntaxError: Unexpected strict mode reserved word
let import = 'test';    // SyntaxError: Unexpected strict mode reserved word
let yield = function() {}; // SyntaxError: Unexpected strict mode reserved word
let static = true;        // SyntaxError: Unexpected strict mode word (in some contexts)
```

注意：即使在宽松模式下，使用 `class` 和 `function*`（生成器函数）等已经会在某些环境中报错。严格模式只是把这个检查做得更加彻底和一致。

### 3.5 eval 的安全性限制

`eval()` 函数可以动态执行字符串形式的 JavaScript 代码。这在宽松模式下非常危险——因为 `eval` 内部代码可以访问外部作用域的变量，存在安全隐患（如 XSS 攻击向量）。严格模式对此做了两件事：

**第一：eval 内部的变量不会泄漏到外部**

```javascript
// 宽松模式
(function() {
  eval('var leaked = "I escape!"');
  console.log(leaked); // "I escape!" —— 变量泄露到了外部！
})();

// 严格模式
'use strict';
(function() {
  eval('var leaked = "I try to escape";');
  console.log(typeof leaked); // "undefined" —— 变量被关在 eval 自己的作用域内
})();
```

**第二：不能通过 eval 声明变量**

```javascript
'use strict';
eval('var x = 1;'); // SyntaxError: Strict mode eval cannot declare variables
eval('let y = 2;'); // 同样报错
eval('z = 3');        // 同样报错

// 正确做法：只能执行表达式
eval('2 + 3'); // 返回 5 —— 表达式求值是被允许的
```

### 3.6 arguments 对象不可修改

每个非箭头函数内部都有一个类数组对象 `arguments`，包含了函数被调用时传入的所有实参。在宽松模式下，你可以修改 `arguments` 或通过它来"欺骗"形参列表：

```javascript
// 宽松模式
function flexible(first) {
  arguments[0] = 'changed';
  console.log(first);       // 仍然是原始值（按位置绑定）
  console.log(arguments[0]); // 'changed' —— 但 arguments 可以单独修改！
}

flexible('original');
```

**严格模式下**：`arguments` 对象变成了"只读快照"——你不能修改它也不能重新赋值给它，而且它与形参之间的"神奇链接"也被切断了：

```javascript
'use strict';
function rigid(first) {
  arguments[0] = 'hacked';  // TypeError: 'assign' on read-only arguments
  arguments = [];             // TypeError: Invalid assignment to 'arguments'
  console.log(first, arguments[0]);
}

rigid('test');
// TypeError: 'assign' on read-only arguments
```

这种限制的原因在于：优化器需要对 `arguments` 进行特殊处理才能实现"形参-arguments 同步"的特性，而这种优化在严格模式下被禁用了。从实践角度看，这其实是一件好事——修改 `arguments` 本身就是一种反模式，它会让代码的行为变得极其难以理解。

### 3.7 禁止八进制字面量和转义字符前缀 `\0`

这是一个比较冷门的特性，但在严格模式中有明确的规则：

```javascript
'use strict';

// 八进制数字（以 0o 或 0O 开头的字面量）
var octal = 010;        // SyntaxError: Octal literals are not allowed in strict mode
var alsoOctal = 0o10;     // 同样报错

// 但十进制和十六进制正常
var decimal = 10;
var hex = 0x10;

// 转义字符 \0 和 \u0000
var str1 = '\010';       // SyntaxError: \010 octal escape sequences are not allowed in strict mode
var str2 = '\u000a';     // 正常：\u000a 是换行符
var str3 = '\x41';       // 正常：\x41 是 'A'
```

为什么禁止？因为 `010` 这种八进制写法在宽松模式下很容易与普通的十进制数字 `10` 混淆——特别是在字符串拼接的场景中，`'001' + '002'` 到底是三个字符相加还是数字一加二？严格模式干脆禁止了这种歧义写法，强迫开发者使用更清晰的替代方案（如 `0o8` 或 `parseInt(str, 8)`）。

### 3.8 禁止重复声明同一个变量

```javascript
// 宽松模式：后面的声明覆盖前面的，不报错
var x = 1;
var x = 2;
console.log(x); // 2 —— 静默覆盖

// 严格模式：重复声明直接报错
'use strict';
var a = 1;
var a = 2;              // SyntaxError: Identifier 'a' has already been declared

// let/const 无论是否严格模式都不允许重复声明
let b = 1;
let b = 2;              // SyntaxError: Identifier 'b' has already been declared
```

### 3.9 函数声明不在块级作用域内创建（ES2015+）

这是一个经常让人困惑的点。ES2015 之前，函数声明在 `{}` 块内的行为取决于是否处于严格模式：

```javascript
{
  // 宽松模式（ES2015之前）：函数声明会被"提升"到当前函数或全局作用域
  if (false) {
    function deprecated() { /* ... */ }  // 这个函数居然能在 if 外面调用！
  }
  deprecated(); // 居然 if(false)，但它存在！
}

// 严格模式下：函数声明被限制在块级作用域内
{
  'use strict';
  if (false) {
    function modern() { /* ... */ }  // 只在这个 if 块内有效
  }
  modern(); // ReferenceError: modern is not defined
}
```

在 ES2015 之后，无论是否严格模式，块级函数声明都被限制在块级作用域内（这是 `let`/`const` 的时代了，没人再这么写函数了）。但了解这个历史遗留问题有助于理解为什么 `class` 和 `let`/`const` 更受推荐。

### 3.10 禁止 with 语句

`with` 语句曾经是用来简化对象属性访问的（类似 Python 的 `with obj as:`），但它严重破坏了作用域的可预测性：

```javascript
'use strict';

const user = { name: 'Alice', age: 30 };

// 宽松模式：with 创建了一个临时作用域，user 的属性可以直接访问
with (user) {
  console.log(name);    // "Alice" —— 从 user 对象上找到
  console.log(age);     // 30
}

// 严格模式：禁止使用 with
with ({ x: 1 }) {  // SyntaxError: Strict mode may not use 'with' statement
  console.log(x);
}
```

`with` 被禁止的原因很简单：**性能灾难**——引擎无法对 `with` 块内的变量做任何静态分析优化（因为不知道哪些是来自 with 对象、哪些是外部变量），而且它让代码的作用域变得极难预测。在现代 JavaScript 中，**解构赋值（`const { name } = obj`）完全可以替代 `with` 的功能，而且更清晰高效**。

## 四、暂时性死区（TDZ）——let/const 的"等待区"

虽然 TDZ 不是严格模式独有的概念，但由于它与 `let`/`const` 密切相关且经常被放在一起讨论，这里做一个完整的梳理。

### 4.1 什么是 TDZ？

**TDZ（Temporal Dead Zone，暂时性死区）**指的是：从代码进入某个作用域开始，到变量声明被执行之前的这段时间窗口。在这个窗口期内，变量**已经被引擎"注册"了（知道它的存在），但它处于一种特殊的"未初始化"状态——任何对它的读写操作都会触发 `ReferenceError`**。

```javascript
{
  // 进入块作用域的那一刻
  // ↓
  // 此时 let x 已经被"感知"，但还不能使用
  // 这段区域就是 x 的 TDZ
  
  console.log(x);  // 💥 ReferenceError: Cannot access 'x' before initialization
  
  let x = 10;     // ← 到了这一行，TDZ 结束，x 变得可用了
  console.log(x);  // 10 ✓
}
```

### 4.2 TDZ 的三阶段生命周期

每个 `let` / `const` 变量都会经历三个阶段：

| 阶段 | 时间点 | 状态 | 可访问？ |
|------|--------|------|--------|
| **① 注册（进入作用域）** | 引擎扫描到 `let x` 时 | 已注册，但**未初始化** | ❌ 访问报 ReferenceError |
| **② 初始化（执行声明行）** | 引擎执行到 `let x = value` 时 | 已初始化为指定值（无则为 `undefined`） | ✅ 可正常访问 |
| **③ 使用（声明行之后）** | 之后任意时刻 | 保持已初始化状态 | ✅ 正常访问 |

### 4.3 为什么需要 TDZ？

TDZ 存在的根本原因是**防止"先使用后声明"的时序错误**。考虑以下场景：

```javascript
// 假设没有 TDZ，变量在声明前值为 undefined
let value = myVariable; // 如果 myVariable 还没声明，value 就是 undefined

myVariable = 'important data';
let myVariable; // 此时 value 已经拿到了 "important data"

// 上面的代码逻辑是错的！我们想用 myVariable 的最终值，
// 但却拿到了初始的 undefined（或者旧的值）
```

有了 TDZ，这种"在声明前就使用"的错误模式会被直接拦截——因为根本不允许你在声明前访问。这是一种**预防性的安全机制**，类似于**安检口在登机前的身份验证**——你不能在还没通过安检的时候就说"我已经在飞机上了"。

### 4.4 var 没有真正意义上的 TDZ

这也是 `var` 和 `let/const` 的核心区别之一：

```javascript
// var 的"伪 TDZ" —— 声明时就被初始化为 undefined
function testVar() {
  console.log(x);  // undefined —— 不报错！（但值不对）
  var x = 10;
  console.log(x);  // 10
}
testVar();

// let/const 的真 TDZ —— 声明时处于不可用状态
function testLet() {
  console.log(y);  // ReferenceError! 直接拦截
  let y = 10;
  console.log(y);  // 10
}
testLet();
```

`var` 在提升时就被赋予了 `undefined`（虽然此时还没有执行赋值语句）。所以技术上它也有一个短暂的"未定义→undefined"的过程，但这不算真正的 TDZ——因为你**可以读取它**，只是读到的值是 `undefined`。而 `let/const` 在 TDZ 中是**连读取都被禁止的**——这才是真正的"死区"。

### 4.5 typeof 的特殊行为

有一个有趣的边缘情况：`typeof` 操作符在 TDZ 中是安全的——它不会触发 ReferenceError：

```javascript
{
  console.log(typeof x); // "undefined" ← 不报错！
  let x = 10;
  console.log(typeof x); // "number"
}
```

这是因为 `typeof` 操作符被特殊对待——它在引擎内部做了特殊的安全检查。`typeof` 的设计目标之一就是用来检测变量的类型，如果连它都不能在 TDZ 中工作，那就失去了存在的意义。所以 `typeof` 是唯一可以在 TDZ 中"存活"的操作符。

## 五、var vs let/const——完整对比

基于以上所有知识点，我们可以对 `var` 和 `let/const` 做一次最终的总结对比：

### 5.1 作用域差异（最关键的区别）

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│  var: 函数级作用域（穿透 if/for/{} 块）                │
│                                                      │
│  let/const: 块级作用域（仅限于最近的 { } 内）          │
│                                                      │
│  示意图图：                                            │
│                                                      │
│  var: 像一间大办公室的门禁系统                          │
│     ┌─────────────────────────────────────┐              │
│     │  函数内部任何地方都可以看到 var 变量          │              │
│     │  即使隔了 if 块、for 循环、嵌套的 {}          │              │
│     └─────────────────────────────────────┘              │
│                                                      │
│  let: 每个小房间都有独立的门禁                              │
│     ┌─────┐ ┌─────┐ ┌─────┐                        │
│     │ if{} │ for{} │ {}   │  ← 每个块有自己的变量      │
│     └─────┘ └─────┘ └─────┘                        │
│       （出了房间就看不到了）                                  │
│                                                      │
└──────────────────────────────────────────────────────┘
```

```javascript
function testScope() {
  // var 版本
  if (true) {
    var aVar = 'if 内的 var';
  }
  console.log(aVar); // "if 内的 var" —— 穿透了 if 块
  
  for (var i = 0; i < 3; i++) {
    var loopVar = `第${i}次`;
  }
  console.log(loopVar); // "第3次" —— 穿透了 for 块
  
  // let/const 版本
  if (true) {
    let aLet = 'if 内的 let';
  }
  // console.log(aLet); // ReferenceError! 出了 if 就看不到了
  
  for (let j = 0; j < 3; j++) {
    let loopLet = `第${j}次`;
  }
  // console.log(loopLet); // ReferenceError! 出了 for 就看不到了
}
```

### 5.2 其他维度完整对比表

| 特性 | `var` | `let` | `const` |
|------|-----|-----|-------|
| **作用域** | 函数级（穿透块） | 块级（不穿透） | 块级（不穿透） |
| **提升** | 提升（值为 `undefined`） | 提升（进入 TDZ，不可用） | 提升（进入 TDZ，不可用） |
| **重复声明** | 允许（静默覆盖） | **SyntaxError** | **SyntaxError** |
| **全局副作用** | 创建 `window` 属性 | 不创建全局属性 | 不创建全局属性 |
| **严格模式** | 行为不变（本身就很"宽松"） | **TDZ 保护** | **TDZ 保护** |
| **重新赋值** | ✅ 可以 | ✅ 可以 | ❌ **SyntaxError** |
| **适用场景** | 维护旧代码 | **推荐用于变量** | **推荐用于常量** |

### 5.3 最佳实践建议

```
优先级排序（从高到低）:

1. const → 定义后不再改变的值（大部分情况）
2. let  → 需要重新赋值的变量（循环计数器等）
3. var   → 基本不推荐使用（除非维护旧代码）

另外：
✅ 始终在文件/模块/Class 顶层加上 'use strict'
✅ 或者直接使用 Class / Module（自动严格模式）
❌ 不要用 with / eval / 八进制 / arguments 修改
❌ 不要依赖隐式全局创建（即使是 var）
```
