# 对象内部方法 —— [[Get]]、[[Set]]、[[Delete]]、属性描述符与访问器属性

> **核心内容**：JavaScript 对象属性操作的底层机制——四大内部方法（[[Get]]、[[Set]]、[[HasProperty]]、[[Delete]]）的工作原理、属性描述符（writable/enumerable/configurable）的完整控制、数据属性 vs 访问器属性的本质区别、Getter/Setter 的智能属性模式、对象锁定三级机制（preventExtensions/seal/freeze），以及标志感知式克隆等高级技巧。

---

## 一、为什么需要理解对象内部方法？

在 JavaScript 的日常开发中，我们几乎每时每刻都在和对象打交道——`obj.name = 'Alice'`、`delete obj.age`、`for (let key in obj)`……这些操作看似简单直接，但你有没有想过：**当你写下 `obj.name` 这行代码时，JavaScript 引擎内部到底发生了什么？** 它是如何"找到"这个值的？它是如何"决定"能不能修改的？又是如何"判断"要不要删除的？

这些问题的答案，都隐藏在 JavaScript 引擎的**对象内部方法（Internal Methods）**之中。

### 1.1 从日常操作到引擎内部

让我们用一个简单的类比来建立直觉：

想象你走进一家**自助餐厅**。你看到的只是：拿盘子、夹菜、结账离开。但餐厅背后有一整套运作系统：

| 你的操作 | 餐厅内部发生的事情 |
|---------|-------------------|
| 拿盘子取菜 | 厨房根据菜单编号查找对应菜品（**属性读取**） |
| 往盘子里放菜 | 服务员检查这道菜是否允许添加（**属性写入**） |
| 把不想要的菜退回去 | 收银台检查是否可以退换（**属性删除**） |

JavaScript 对象也是如此。每一次 `obj.prop`、`obj.prop = value`、`delete obj.prop` 的操作，背后都有对应的**内部方法**在工作。理解这些内部方法，就是从"食客视角"升级到"餐厅经理视角"——你不再只知道"菜好不好吃"，而是知道"整个厨房是怎么运转的"。

### 1.2 四大核心内部方法

ECMAScript 规范定义了多个对象内部方法，其中最常用的有四个：

| 内部方法 | 触发时机 | 核心职责 |
|---------|---------|---------|
| **[[Get]](propertyKey, receiver)** | 读取属性 `obj.key` 或 `obj[key]` | 沿原型链查找属性值 |
| **[[Set]](propertyKey, value, receiver)** | 写入属性 `obj.key = value` | 决定值如何存储或是否触发 setter |
| **[[HasProperty]](propertyKey)** | 检查属性存在性 `'key' in obj` | 判断自身+原型链上是否存在该属性 |
| **[[Delete]](propertyKey)** | 删除属性 `delete obj.key` | 判断是否允许删除并执行移除 |

这四个方法是所有对象属性操作的**底层基础设施**。接下来我们将逐一深入每个方法的内部工作机制，并揭示它们与属性描述符之间的紧密联系。

## 二、[[Get]]—— 属性读取的完整链路

### 2.1 什么是 [[Get]]？

当你在代码中写 `obj.name` 来读取一个属性的值时，JavaScript 引擎会自动调用对象的 `[[Get]]` 内部方法。这个过程远比表面看起来复杂——它涉及**多层查找、类型检查、原型链遍历**等多个环节。

### 2.2 [[Get]] 的算法流程

以下是规范层面简化后的 `[[Get]]` 执行流程：

```
┌─────────────────────────────────────────────────────┐
│              [[Get]](P) 执行流程                      │
│                                                     │
│  Step 1: 在对象自身的属性中查找 P                     │
│    ├─ 找到 → 返回属性值                              │
│    └─ 未找到 → 进入 Step 2                          │
│                                                     │
│  Step 2: 获取对象的原型 (O.[[Prototype]])            │
│    ├─ 原型为 null → 返回 undefined（链的尽头）       │
│    └─ 原型不为 null → 在原型上递归调用 [[Get]]      │
│        （这就是"沿原型链向上查找"）                    │
│                                                     │
│  特殊情况：                                          │
│  如果找到的是 Accessor Property → 调用 getter 函数   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 2.3 逐步追踪示例

让我们通过一个具体例子来追踪 `[[Get]]` 的完整过程：

```javascript
// 定义一个原型对象
const animal = {
  species: "unknown",
  eats: true,
  
  get info() {
    return `${this.species} - eats: ${this.eats}`;
  }
};

// 创建一个继承自 animal 的对象
const rabbit = {
  __proto__: animal,
  species: "Rabbit",   // 自身属性，覆盖原型的
  jumps: true           // 自身独有属性
};
```

当我们执行以下读取操作时，`[[Get]]` 内部经历了什么？

```javascript
// ====== 操作 1：读取 rabbit.species ======
console.log(rabbit.species); // "Rabbit"
// [[Get]]("species") 流程：
// Step 1: 在 rabbit 自身属性中查找 "species"
//         → 找到了！值是 "Rabbit"
//         → 直接返回 "Rabbit"，不去原型链了

// ====== 操作 2：读取 rabbit.eats ======
console.log(rabbit.eats); // true
// [[Get]]("eats") 流程：
// Step 1: 在 rabbit 自身属性中查找 "eats"
//         → rabbit 只有 species 和 jumps，没找到 "eats"
// Step 2: 获取 rabbit.[[Prototype]] → animal
//         → 在 animal 中递归调用 [[Get]]("eats")
//         → animal 有 eats 属性，值为 true
//         → 返回 true

// ====== 操作 3：读取 rabbit.info ======
console.log(rabbit.info); // "Rabbit - eats: true"
// [[Get]]("info") 流程：
// Step 1: rabbit 自身没有 info
// Step 2: 沿原型链找到 animal.info
//         → 发现这是一个 Accessor Property（有 getter）
//         → 调用 getter 函数，this 绑定为 rabbit
//         → getter 返回 `${this.species} ${this.eats}`
//         → this.species 在 rabbit 上找到 "Rabbit"
//         → this.eats 沿原型链找到 true
//         → 最终返回 "Rabbit - eats: true"

// ====== 操作 4：读取不存在的属性 ======
console.log(rabbit.fly); // undefined
// [[Get]]("fly") 流程：
// Step 1: rabbit 没有 fly
// Step 2: animal 也没有 fly
// Step 3: animal.[[Prototype]] 是 Object.prototype
//         → Object.prototype 也没有 fly
// Step 4: Object.prototype.[[Prototype]] 是 null
//         → 链的尽头！返回 undefined
```

### 2.4 [[Get]] 的关键特征

**特征一：只读不写**

这是初学者最容易混淆的点：`[[Get]]` 只负责**读取**属性，它**永远不会修改对象本身**。即使你在原型链上找到了某个属性，这个查找过程也是纯读操作——不会把那个属性"复制"到当前对象上。

**类比**：就像你去图书馆查书，`[[Get]]` 就是去目录柜里翻卡片。你找到了书的位置信息（返回了结果），但并没有把那本书搬回你的办公室（不会改变任何东西）。

**特征二：访问器属性触发函数调用**

如果找到的属性是一个访问器属性（有 getter 函数），`[[Get]]` 不会直接返回一个存储的值，而是**立即调用 getter 函数**，并将 getter 的返回值作为最终结果。这意味着每次读取都可能得到不同的值——因为它实际上是**动态计算的**。

```javascript
const counter = {
  _count: 0,
  
  get count() {
    console.log('getter 被调用了！');
    this._count++;
    return this._count;
  }
};

console.log(counter.count); // "getter 被调用了！" 然后 1
console.log(counter.count); // "getter 被调用了！" 然后 2
console.log(counter.count); // "getter 被调用了！" 然后 3
// 每次读取都会重新执行 getter 函数
```

**特征三：`this` 绑定规则**

当 getter 函数被调用时，`this` 的绑定遵循一个重要规则：**`this` 始终指向最初触发属性访问的那个对象**，而不是 getter 所在的原型对象。

```javascript
const parent = {
  _name: "Parent",
  
  get displayName() {
    // 这里的 this 不是 parent，而是触发访问的对象
    return this._name || "(未设置)";
  }
};

const child = { __proto__: parent, _name: "Child" };
const orphan = { __proto__: parent }; // 没有 _name

child.displayName;  // "Child"     ← this === child
orphan.displayName; // "(未设置)"  ← this === orphan
```

这个设计极其重要——它保证了**方法共享但状态独立**：同一个 getter 函数可以被无数个对象共用（存在于原型中节省内存），但每次调用时 `this` 都正确地指向各自的实例，从而访问到各自的数据。

## 三、[[Set]]—— 属性写入的两条路径

### 3.1 什么是 [[Set]]？

当你在代码中写 `obj.name = value` 来写入/创建一个属性时，JavaScript 引擎会调用对象的 `[[Set]]` 内部方法。与 `[[Get]]` 不同的是，`[[Set]]` 的逻辑更加微妙——它存在**两条完全不同的执行路径**，取决于属性的类型（数据属性还是访问器属性）。

### 3.2 [[Set]] 的算法流程

```
┌──────────────────────────────────────────────────────┐
│              [[Set]](P, V) 执行流程                   │
│                                                      │
│  Step 1: 在自身属性中查找 P                           │
│    ├─ 找到且是 Data Property                          │
│    │   ├─ writable 为 true → 直接赋值，成功返回        │
│    │   └─ writable 为 false → 严格模式报 TypeError     │
│    │                       非严格模式静默失败          │
│    │                                                  │
│    ├─ 找到且是 Accessor Property（有 setter）          │
│    │   └─ 调用 setter(V)，将控制权交给 setter          │
│    │                                                  │
│    └─ 未找到 → 进入 Step 2                           │
│                                                      │
│  Step 2: 沿原型链查找                                 │
│    ├─ 原型上有同名 Accessor Property（有 setter）      │
│    │   └─ 调用原型的 setter(V)，this 绑定当前对象      │
│    │                                                  │
│    ├─ 原型上是 Data Property（只读）                   │
│    │   └─ 严格模式报 TypeError                        │
│    │      非严格模式静默失败（不创建新属性！）          │
│    │                                                  │
│    ├─ 原型上不存在                                   │
│    │   └─ 在当前对象自身上创建新属性，赋值为 V          │
│    │                                                  │
│    └─ 到达 null（链的尽头）                           │
│        → 在当前对象自身上创建新属性，赋值为 V           │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 3.3 关键区别：读取 vs 写入的不对称性

这是理解对象行为的核心要点之一：

| 操作 | 是否使用原型链？ | 效果 |
|------|----------------|------|
| **读取** ([[Get]]) | ✅ 会沿原型链查找 | 可能从原型获取值 |
| **写入** ([[Set]]) | ⚠️ **通常不使用原型链** | **几乎总是在自身创建/修改属性** |

**唯一例外**：当原型上存在同名的 **Accessor Property 且有 setter** 时，写入操作会被拦截并路由到 setter。

### 3.4 经典案例追踪

让我们通过几个关键场景来深入理解 `[[Set]]` 的行为：

#### 场景一：普通写入——在自身创建属性

```javascript
const animal = { eats: true };
const rabbit = { __proto__: animal };

rabbit.jumps = true;
// [[Set]]("jumps", true) 流程：
// Step 1: rabbit 自身没有 "jumps"
// Step 2: 沿原型链找 → animal 也没有
// Step 3: 到达 null → 在 rabbit 自身上创建 jumps = true

console.log(rabbit);     // { jumps: true, __proto__: { eats: true } }
console.log(animal.eats); // true（不受影响）
console.log(animal.jumps); // undefined（animal 完全不知道 jumps 的存在）
```

#### 场景二：覆盖原型上的可写属性

```javascript
const base = { version: "1.0" };
const derived = { __proto__: base };

derived.version = "2.0";
// [[Set]]("version", "2.0") 流程：
// Step 1: derived 自身没有 "version"
// Step 2: 沿原型链找 → base 有 "version"，是 Data Property
//         但注意：这里不会修改 base.version！
// Step 3: 在 derived 自身上创建新的 "version" = "2.0"
//         （属性遮蔽/Shadowing）

console.log(base.version);    // "1.0" ← 没变！
console.log(derived.version); // "2.0" ← 自身的值遮蔽了原型
```

这就是著名的**属性遮蔽（Property Shadowing）**现象。写入操作不会修改原型上的属性，而是在当前对象上创建一个同名的新属性来"挡住"原型的那个。

**类比**：就像你 inherited 了父亲的一本旧书（原型上的属性）。后来你自己买了一本同名的新版书放在自己的书架上（自身属性）。以后你拿这本书时，总是先拿到自己买的那本（属性遮蔽），父亲的那本依然完好地在原处。

#### 场景三：Setter 拦截——唯一的"写入走原型"场景

```javascript
const userProto = {
  _firstName: "",
  _lastName: "",

  set fullName(value) {
    // 这个 setter 会在子类写入时被触发！
    [this._firstName, this._lastName] = value.split(" ");
  },

  get fullName() {
    return `${this._firstName} ${this._lastName}`;
  }
};

const admin = { __proto__: userProto, isAdmin: true };

admin.fullName = "Alice Cooper";
// [[Set]]("fullName", "Alice Cooper") 流程：
// Step 1: admin 自身没有 "fullName"
// Step 2: 沿原型链找 → userProto 有 "fullName"
//         → 它是 Accessor Property 且有 set！
//         → 调用 userProto 的 setter("Alice Cooper")
//         → setter 中 this 绑定为 admin（不是 userProto！）
//         → this._firstName = "Alice" → 创建在 admin 身上
//         → this._lastName = "Cooper"  → 创建在 admin 身上

console.log(admin.fullName);    // "Alice Cooper"
console.log(admin._firstName);  // "Alice"
console.log(admin._lastName);   // "Cooper"

// 注意：userProto 上的 _firstName 和 _lastName 并没有被修改
console.log(userProto._firstName); // ""（仍然是空字符串）
```

这个场景展示了 setter 的强大之处——它可以**拦截对属性的写入**，并将值分散存储到其他地方。更重要的是，setter 中的 `this` 始终指向**最初发起写入操作的对象**，确保数据存储在正确的位置。

#### 场景四：原型上的只读属性阻止写入

```javascript
'use strict';

const config = {};
Object.defineProperty(config, 'MAX_ITEMS', {
  value: 100,
  writable: false,       // 只读！
  configurable: false,
  enumerable: true
});

const myObj = { __proto__: config };

myObj.MAX_ITEMS = 999;
// [[Set]]("MAX_ITEMS", 999) 流程（严格模式）：
// Step 1: myObj 自身没有 "MAX_ITEMS"
// Step 2: 沿原型链找 → config 有 "MAX_ITEMS"
//         → 它是 Data Property，但 writable 为 false
//         → 💥 TypeError: Cannot assign to read only property
//
// 注意：即使是非严格模式，也不会在 myObj 上创建新属性！
// 这是与场景二的关键差异！

console.log(myObj.MAX_ITEMS); // 100（仍然是原型的值）
```

**为什么不能像场景二那样创建遮蔽属性？**

这是 ECMAScript 规范的设计决策。当原型链上找到一个**不可写的**数据属性时，为了防止继承层次中的意外破坏（比如子类意外覆盖了一个本应是常量的配置项），`[[Set]]` 选择拒绝操作而非创建遮蔽属性。这是一种**保护性设计**——类似于图书馆里某些珍贵的参考书只能阅览不能借走，即使你试图用自己的复印本来替代也不允许。

## 四、[[HasProperty]] 与 in 操作符

### 4.1 什么是 [[HasProperty]]？

`'key' in obj` 这个操作符的背后，就是 `[[HasProperty]]` 内部方法。它的职责是判断**给定的属性键是否在对象自身或其原型链上存在**。

### 4.2 算法流程

```
┌──────────────────────────────────────────┐
│    [[HasProperty]](P) 执行流程             │
│                                           │
│  Step 1: 检查对象自身是否有属性 P          │
│    ├─ 有 → 返回 true                      │
│    └─ 无 → 进入 Step 2                    │
│                                           │
│  Step 2: 获取原型                         │
│    ├─ 原型为 null → 返回 false            │
│    └─ 原型不为 null → 在原型上递归调用     │
│        [[HasProperty]](P)                 │
│                                           │
│  注意：                                    │
│  即使属性值为 undefined，也返回 true       │
│  （因为属性确实存在，只是值为 undefined）    │
│                                           │
└──────────────────────────────────────────┘
```

### 4.3 `in` vs `hasOwnProperty` vs `=== undefined`

三种检测方式的行为对比：

```javascript
const proto = { inherited: "来自原型" };
const obj = { 
  __proto__: proto,
  own: "自身属性",
  undefinedVal: undefined  // 存在，但值为 undefined
};

// ====== 方法一：in 操作符 ======
console.log('own' in obj);           // true  ← 自身有
console.log('inherited' in obj);     // true  ← 原型链上有
console.log('undefinedVal' in obj);  // true  ← 属性存在，虽然值是 undefined
console.log('nonExist' in obj);      // false ← 真的不存在

// ====== 方法二：hasOwnProperty ======
console.log(obj.hasOwnProperty('own'));           // true  ← 仅检查自身
console.log(obj.hasOwnProperty('inherited'));     // false ← 不看原型链
console.log(obj.hasOwnProperty('undefinedVal'));  // true  ← 自身有，尽管值是 undefined
console.log(obj.hasOwnProperty('nonExist'));      // false ← 不存在

// ====== 方法三：=== undefined ======
console.log(obj.own === undefined);          // false ← 有值
console.log(obj.inherited === undefined);    // false ← 有值
console.log(obj.undefinedVal === undefined); // true  ← 但这可能误判！
console.log(obj.nonExist === undefined);     // true  ← 这个是真的不存在
```

**关键陷阱**：用 `=== undefined` 检测属性存在性时，无法区分"属性不存在"和"属性存在但值为 undefined"。如果你需要精确区分这两种情况，必须使用 `in` 操作符或 `hasOwnProperty()`。

**类比**：
- `in` 操作符像是问："这本书在图书馆的**整个馆藏体系**中吗？"（包括分馆/总馆）
- `hasOwnProperty` 像是问："这本书在**当前这家分馆**的书架上吗？"
- `=== undefined` 像是问："我能**读到内容**吗？"（可能书不在，也可能书在但是空白页）

### 4.4 hasOwnProperty 的安全性问题

有一个非常微妙的坑需要注意：`hasOwnProperty` 本身是从 `Object.prototype` 继承来的方法。如果你的对象恰好有一个名为 `hasOwnProperty` 的自有属性，就会把它"遮蔽"掉：

```javascript
const evilObj = {
  hasOwnProperty: "我是冒牌货！"  // 遮蔽了原型上的方法
};

// evilObj.hasOwnProperty('name') 会报错！
// 因为 evilObj.hasOwnProperty 是字符串，不是函数
// TypeError: evilObj.hasOwnProperty is not a function
```

**安全的解决方案**：

```javascript
// 方案一：使用 Object.prototype.hasOwnProperty.call()
Object.prototype.hasOwnProperty.call(evilObj, 'name'); // 安全

// 方案二：使用 ES2022 的 Object.hasOwn()（推荐）
Object.hasOwn(evilObj, 'name'); // 最安全、最简洁

// 方案三：使用 Object.create(null) 创建纯净对象（没有原型）
const safeDict = Object.create(null);
safeDict['hasOwnProperty'] = "随便设"; // 不影响任何事
safeDict['key'] = "value";

// 但注意：safeDict 没有 hasOwnProperty 方法
// 必须用 Object.hasOwn(safeDict, 'key')
```

## 五、[[Delete]] 与 delete 操作符

### 5.1 什么是 [[Delete]]？

`delete obj.property` 操作符触发的就是 `[[Delete]]` 内部方法。它的职责是**从对象上移除指定的属性**——但这并不总是能成功。

### 5.2 算法流程

```
┌──────────────────────────────────────────┐
│    [[Delete]](P) 执行流程                 │
│                                           │
│  Step 1: 检查对象自身是否有属性 P          │
│    ├─ 没有属性 P → 返回 true              │
│    │   （"反正也没有，算你删成功了"）        │
│    └─ 有属性 P → 进入 Step 2              │
│                                           │
│  Step 2: 检查属性的 configurable 标志     │
│    ├─ configurable 为 true               │
│    │   → 移除该属性，返回 true             │
│    │                                      │
│    └─ configurable 为 false              │
│        ├─ 严格模式 → 抛出 TypeError       │
│        └─ 非严格模式 → 返回 false         │
│            （静默失败，不报错也不删除）      │
│                                           │
└──────────────────────────────────────────┘
```

### 5.3 各种删除场景

```javascript
'use strict';

// 场景一：正常删除
const user = { name: "Alice", age: 30 };
delete user.name;
console.log(user); // { age: 30 } ✓ 成功删除

// 场景二：删除不存在的属性（不算错）
delete user.salary;
// 返回 true —— "本来就没有，算你成功"
console.log(user); // { age: 30 }

// 场景三：删除不可配置属性
const config = {};
Object.defineProperty(config, 'API_KEY', {
  value: 'sk-xxx',
  configurable: false  // 不可删除！
});

delete config.API_KEY;
// 💥 TypeError: Cannot delete property 'API_KEY'

// 场景四：delete 只能删除自有属性，不能删除原型链上的属性
const base = { shared: "共享" };
const derived = { __proto__: base, own: "私有" };

delete derived.shared;
// 返回 true —— 但实际上什么都没删！
// 因为 derived 自身没有 "shared"，delete 对原型无能为力
console.log(derived.shared); // "共享" —— 还在！

// 场景五：delete 不能删除 var 声明的全局变量
var globalVar = "我是全局变量";
delete globalVar;
// 💥 严格模式: TypeError
// 非严格模式: 静默返回 false
// 原因：用 var 声明的全局变量的 configurable 为 false

// 但 delete 可以删除隐式创建的全局属性
implicitGlobal = "我没有声明就直接赋值了";
delete implicitGlobal; // ✓ 成功（非严格模式下）

// 场景六：delete 不能删除 const/let
const constant = "常量";
delete constant; // ❌ SyntaxError（编译阶段就报错了）
```

### 5.4 delete 的限制总结

| 目标类型 | 能否 delete？ | 原因 |
|---------|-------------|------|
| 普通自有属性 | ✅ 可以 | 默认 `configurable: true` |
| `configurable: false` 的属性 | ❌ 不行 | 被 `defineProperty` 锁定 |
| 原型链上的属性 | ❌ 不行 | delete 只作用于自身 |
| `var` 声明的全局变量 | ❌ 不行 | `configurable: false` |
| `const` / `let` 变量 | ❌ 不行 | 语法层面禁止 |
| 隐式全局属性（宽松模式） | ✅ 可以 | `configurable: true` |
| 不存在的属性 | 返回 true | "本来就没有" |

**重要提醒**：`delete` 返回 `true` **不代表真的删除了什么东西**——对于不存在的属性，它也会返回 `true`。所以不要用返回值来判断是否"真正发生了删除"。

## 六、属性描述符（Property Descriptor）—— 属性的"身份证"

### 6.1 超越键值对

在日常编程中，我们习惯于把对象属性看作简单的"键值对"——就像一张便利贴，一面写着名字，另一面写着值。但实际上，JavaScript 中的每一个属性都携带了一份更丰富的信息——**属性描述符（Property Descriptor）**。

如果把属性看作一个人，那么：
- **键名（key）**是他的名字
- **值（value）**是他的年龄
- **属性描述符**则是他的**完整档案**：是否允许改名？是否可以被公开列出？是否可以从系统中彻底注销？

```javascript
const user = { name: "John" };

// 查看属性的完整"档案"
const descriptor = Object.getOwnPropertyDescriptor(user, 'name');
console.log(JSON.stringify(descriptor, null, 2));
```

输出：

```json
{
  "value": "John",
  "writable": true,
  "enumerable": true,
  "configurable": true
}
```

看到了吗？一个看似简单的 `name: "John"` 属性，实际上携带了 **4 个字段的信息**。

### 6.2 数据属性的四个标志位

数据属性（Data Property）是最常见的属性类型，它的描述符包含以下四个字段：

| 字段 | 类型 | 默认值 | 含义 |
|------|------|--------|------|
| `value` | 任意类型 | `undefined` | 属性的值 |
| `writable` | 布尔值 | `false*` | 是否允许修改值 |
| `enumerable` | 布尔值 | `false*` | 是否能在循环中被枚举 |
| `configurable` | 布尔值 | `false*` | 是否可删除、能否修改标志 |

> \***注意**：这里的默认值指的是通过 `Object.defineProperty` 创建时的默认值。通过常规方式（如字面量 `{ name: "John" }`）创建的属性，这三个标志位的默认值都是 **`true`**。

### 6.3 Writable（可写性）详解

`writable` 控制着属性值**能否被修改**。

```javascript
'use strict';

const product = { price: 99 };

// 将价格设为只读
Object.defineProperty(product, 'price', {
  writable: false  // 价格一旦设定就不能改
});

product.price = 199;
// 💥 TypeError: Cannot assign to read only property 'price'
// 严格模式下直接抛出错误

// 非 strict 模式下：静默失败（不报错，但值不变）
console.log(product.price); // 仍然 99
```

**实际应用场景——防止意外修改**：

```javascript
function createImmutableConfig(settings) {
  const config = {};
  
  for (const key of Object.keys(settings)) {
    Object.defineProperty(config, key, {
      value: settings[key],
      writable: false,
      enumerable: true,
      configurable: false
    });
  }
  
  return config;
}

const appConfig = createImmutableConfig({
  API_BASE_URL: 'https://api.example.com',
  MAX_RETRY_COUNT: 3,
  TIMEOUT_MS: 5000
});

appConfig.API_BASE_URL = 'https://evil.com';
// 无法修改——配置被锁定了
```

### 6.4 Enumerable（可枚举性）详解

`enumable` 控制着属性**是否会在遍历操作中被枚举出来**。这是最容易被忽视但影响最深远的标志之一。

```javascript
const user = {
  name: "Alice",
  age: 30,
  
  // 内部属性——不想被外部看到
  _internalId: "xYz-123",
  
  toString() {
    return `[User: ${this.name}]`;
  }
};

// 将内部方法和属性隐藏起来
Object.defineProperty(user, '_internalId', {
  enumerable: false  // 不可枚举
});
Object.defineProperty(user, 'toString', {
  enumerable: false  // 不可枚举
});
```

隐藏之后的效果：

```javascript
// for...in 循环——看不到不可枚举属性
for (let key in user) {
  console.log(key);
  // 输出：name, age
  // _internalId 和 toString 不会出现
}

// Object.keys——同样看不到
console.log(Object.keys(user));       // ["name", "age"]

// JSON.stringify——也会忽略不可枚举属性！
console.log(JSON.stringify(user));    
// {"name":"Alice","age":30"}
// _internalId 不会被序列化——这对安全很有意义！

// 但显式访问仍然可以
console.log(user._internalId);        // "xYz-123" ← 还是可以读到
console.log(user.toString());         // "[User: Alice]" ← 还是可以调用
```

**哪些内置方法是不可枚举的？**

JavaScript 大量的内置原型方法都被标记为 `enumerable: false`，这样它们就不会污染你的 `for...in` 循环：

```javascript
const arr = [1, 2, 3];

// Array.prototype 上有很多方法：map/filter/reduce/find...
// 但 for...in 不会遍历到它们
for (let key in arr) {
  console.log(key); // 只输出 "0", "1", "2"（数组索引）
  // map, filter, reduce 等全部被跳过
}
```

**这就是为什么你可以放心地对数组使用 `for...in` 而不会被一堆内置方法淹没的原因**——因为这些方法全部被设置为不可枚举。

### 6.5 Configurable（可配置性）详解

`configurable` 是三个标志中最强大的一个——它同时控制着**两个维度**的操作：

1. **能否删除属性**（`delete` 操作）
2. **能否修改属性的其他标志**（能否再次调用 `defineProperty` 改变标志）

```javascript
'use strict';

const sensitiveData = {};

Object.defineProperty(sensitiveData, 'token', {
  value: 'secret-key-abc123',
  writable: true,      // 值还可以改
  enumerable: true,    // 可以被看到
  configurable: false  // 🔒 但不能删除、不能改标志
});

sensitiveData.token = 'new-key';  // ✓ 允许（writable 还是 true）
delete sensitiveData.token;       // ❌ TypeError!（configurable: false）

// 试图改变其他标志——也不行
Object.defineProperty(sensitiveData, 'token', {
  configurable: true  // 试图解锁
});  // ❌ TypeError! 一旦 configurable 设为 false 就回不了头
```

**configurable 的单向特性**

`configurable: false` 是一条**单行道**——一旦设为 false，就**永远无法再改为 true**。这是 ECMAScript 规范层面的硬性限制。

**唯一的例外**：即使 `configurable` 为 false，只要 `writable` 当前为 true，你仍然可以**将 `writable` 从 true 改为 false**（加一层保护），但不能反向操作（从 false 改回 true）。

```javascript
const obj = {};
Object.defineProperty(obj, 'data', {
  value: 'hello',
  writable: true,
  configurable: false
});

// ✓ 允许：true → false（增加保护层）
Object.defineProperty(obj, 'data', { writable: false });

// ✗ 禁止：false → true（去掉保护层）
Object.defineProperty(obj, 'data', { writable: true });
// TypeError: Cannot redefine property
```

**类比**：`configurable: false` 就像是在文件上盖了一个"永久密封"章。一旦盖章，你不能撕掉这个章（改回 `configurable: true`），也不能更改文件的分类等级（改其他标志）。但如果文件原本标记为"可编辑"，你还可以把它降级为"只读"（`writable: true → false`）——但不能反过来提升权限。

### 6.6 defineProperty 的默认值陷阱

这是新手最容易踩的一个大坑：

**通过常规赋值创建属性时**（如 `obj.name = 'John'`），三个标志默认都是 `true`。

**通过 `Object.defineProperty` 创建属性时**，如果不显式指定标志，它们的默认值都是 **`false`**！

```javascript
const obj = {};

// 方式一：常规赋值（标志默认 true）
obj.a = 'hello';
console.log(Object.getOwnPropertyDescriptor(obj, 'a'));
// { value: 'hello', writable: true, enumerable: true, configurable: true }

// 方式二：defineProperty（标志默认 false！！）
Object.defineProperty(obj, 'b', { value: 'world' });
console.log(Object.getOwnPropertyDescriptor(obj, 'b'));
// { value: 'world', writable: false, enumerable: false, configurable: false }
// ⚠️ 全是 false！b 变成了一个"只读、不可枚举、不可删除、不可配置"的属性！
```

**为什么这样设计？**

这是因为 `Object.defineProperty` 主要用于**精细控制**属性行为的使用场景。在这种场景下，开发者通常是想要**明确限制**属性的某种能力（如设为只读），所以默认给出最严格的配置（全 false），让开发者按需开启需要的权限。这与"默认开放，需要时再加锁"的常规思路正好相反——它是"默认锁定，需要时再开锁"的安全优先策略。

**类比**：
- 常规赋值像是**开放式办公区**——默认谁都能进出、谁都能改动（标志全 true）
- `defineProperty` 像**银行金库**——默认所有门都锁着，你需要明确说明开哪扇门、给什么权限（标志默认 false）

## 七、访问器属性（Accessor Properties）—— Getter/Setter

### 7.1 数据属性 vs 访问器的本质区别

到目前为止，我们讨论的都是**数据属性（Data Property）**——它们存储一个具体的值（`value`），并通过 `writable` 控制能否修改这个值。

但 JavaScript 还提供了另一种属性类型——**访问器属性（Accessor Property）**。它**不存储值本身**，而是由一对**getter 函数**和 **setter 函数**组成：

| 特性 | 数据属性 | 访问器属性 |
|------|---------|-----------|
| **本质** | 存储一个静态值 | 由函数组成（get/set） |
| **描述符关键字段** | `value`, `writable` | `get`, `set` |
| **读取时** | 直接返回 `value` | **调用 getter 函数**，返回其结果 |
| **写入时** | 直接替换 `value` | **调用 setter 函数**，传入新值 |
| **外部表现** | 看起来像普通变量 | 看起来也像普通变量（无需括号！） |
| **同一属性能否两者兼有** | ❌ 不可能 | ❌ 不可能 |

**核心思想**：访问器属性让你可以在**属性的读写操作中注入自定义逻辑**，而外部使用者完全不需要知道这一点——他们仍然像使用普通属性一样用点号来读写。

### 7.2 字面量语法定义

在对象字面量中使用 `get` 和 `set` 关键字来定义访问器属性：

```javascript
const user = {
  firstName: "John",
  lastName: "Smith",

  // 定义 getter——读取 fullName 时自动调用
  get fullName() {
    console.log('getter 被触发了');
    return `${this.firstName} ${this.lastName}`;
  },

  // 定义 setter——写入 fullName 时自动调用
  set fullName(value) {
    console.log('setter 被触发了，收到值:', value);
    [this.firstName, this.lastName] = value.split(" ");
  }
};
```

**使用方式——看起来跟普通属性一模一样**：

```javascript
// 读取——触发 getter（不需要加括号！）
console.log(user.fullName);
// 输出：
// "getter 被触发了"
// "John Smith"

// 写入——触发 setter（不需要调用函数！）
user.fullName = "Alice Cooper";
// 输出：
// "setter 被触发了，收到值: Alice Cooper"

// 验证：值已经被拆分存储到 firstName 和 lastName
console.log(user.firstName); // "Alice"
console.log(user.lastName);  // "Cooper"
```

### 7.3 只读属性——只有 getter 没有 setter

如果你只定义了 getter 而不定义 setter，这个属性就会变成**只读**的：

```javascript
const circle = {
  radius: 5,

  // 只定义 getter，不定义 setter
  get area() {
    return Math.PI * this.radius * this.radius;
  },
  
  get diameter() {
    return this.radius * 2;
  }
};

console.log(circle.area);     // 78.5398... ✓ 正常读取
console.log(circle.diameter); // 10 ✓ 正常读取

circle.area = 100;
// 💥 TypeError: Cannot set property area which has only a getter
// （严格模式下报错，非严格模式静默失败）
```

这种模式非常适合用于**派生属性**——那些可以根据其他属性计算得出、不需要单独存储的属性。

### 7.4 用 defineProperty 定义访问器

除了字面量语法，你也可以用 `Object.defineProperty` 来创建访问器属性：

```javascript
const user = {
  firstName: "John",
  lastName: "Smith"
};

Object.defineProperty(user, 'fullName', {
  // 注意：没有 value 和 writable
  // 取而代之的是 get 和 set
  
  get() {
    return `${this.firstName} ${this.lastName}`;
  },
  
  set(value) {
    [this.firstName, this.lastName] = value.split(" ");
  },
  
  enumerable: true,     // 可枚举（默认 false！）
  configurable: true    // 可配置（默认 false！）
});

console.log(user.fullName); // "John Smith"
user.fullName = "Jane Doe";
console.log(user.firstName); // "Jane"
```

**重要细节**：通过 `defineProperty` 创建的访问器属性，`enumerable` 和 `configurable` 的默认值同样是 **`false`**——如果你希望它能被遍历和修改，必须显式设为 `true`。

### 7.5 智能属性模式（Smart Properties）

Getter/Setter 最实用的场景之一是**对属性进行包装**，在不改变外部接口的前提下增加验证、日志、缓存等额外逻辑：

#### 模式一：值验证

```javascript
const account = {
  _balance: 0,

  get balance() {
    return this._balance;
  },

  set balance(amount) {
    if (typeof amount !== 'number' || isNaN(amount)) {
      console.error(`❌ 金额必须是数字: ${amount}`);
      return;
    }
    if (amount < 0) {
      console.error(`❌ 余额不能为负数: ${amount}`);
      return;
    }
    this._balance = amount;
    console.log(`✅ 余额已更新为: ¥${amount.toFixed(2)}`);
  }
};

account.balance = 1000;   // ✅ 余额已更新为: ¥1000.00
account.balance = -500;   // ❌ 余额不能为负数: -500
account.balance = "很多";  // ❌ 金额必须是数字: 很多
console.log(account.balance); // 1000（最后一次有效值）
```

**下划线约定**：以 `_` 开头的属性名（如 `_balance`）是一种广泛使用的**命名约定**，表示"这是一个内部实现细节，请勿直接访问"。当然这只是一种约定，并非真正的语言级私有（ES2022 的私有字段 `#` 才是语言级的）。

#### 模式二：向后兼容重构

假设你的项目中有大量代码在使用 `user.age`，但现在你想改为基于生日计算年龄以提高准确性：

```javascript
function User(name, birthday) {
  this.name = name;
  this.birthday = birthday;

  // 将 age 改为访问器属性——旧代码不用改！
  Object.defineProperty(this, 'age', {
    get() {
      const today = new Date();
      let age = today.getFullYear() - this.birthday.getFullYear();
      const m = today.getMonth() - this.birthday.getMonth();
      if (m < 0 || (m === 0 && today.getDate() < this.birthday.getDate())) {
        age--;
      }
      return age;
    },
    
    // 可选：禁止直接设置 age（因为应该通过 birthday 间接修改）
    set(value) {
      console.warn('⚠️ 请通过 birthday 属性来设置出生日期');
    }
  });
}

const john = new User("John", new Date(1992, 6, 1));

// 所有旧的代码都不需要修改！
console.log(john.age); // 根据当前日期自动计算出的年龄
// 旧代码继续工作，但底层数据源已经变了
```

**这就是访问器属性的威力**：你可以在完全不破坏现有 API 的前提下，彻底改变数据的存储方式和计算逻辑。这在大型项目的渐进式重构中非常有价值。

#### 模式三：懒加载/延迟计算

```javascript
const heavyResource = {
  _cachedData: null,
  _isLoaded: false,

  get data() {
    if (!this._isLoaded) {
      console.log('⏳ 正在加载重型资源...');
      // 模拟耗时操作
      this._cachedData = Array.from({ length: 1000000 }, (_, i) => i);
      this._isLoaded = true;
      console.log('✅ 加载完成');
    }
    return this._cachedData;
  }
};

console.log(heavyResource.data.length); // 第一次：触发加载
console.log(heavyResource.data.length); // 第二次：直接返回缓存
// 只有第一次读取会触发加载，后续都是从缓存读取
```

### 7.6 数据属性与访问器属性的互斥性

一个属性**不可能同时既是数据属性又是访问器属性**。如果你尝试这样做，会报错：

```javascript
Object.defineProperty({}, 'prop', {
  value: 42,        // 尝试定义为数据属性
  get() { return 1 } // 同时尝试定义为访问器
});
// 💥 TypeError: Invalid property descriptor.
// Cannot both specify accessors and a value or writable attribute
```

但你可以**将一种类型转换为另一种类型**（前提是 `configurable` 为 `true`）：

```javascript
const obj = { name: "John" }; // 数据属性

// 转换为访问器属性
Object.defineProperty(obj, 'name', {
  get() { return "Mr. " + this._name; },
  set(val) { this._name = val; },
  configurable: true
});

console.log(obj.name); // "undefined"（因为 _name 还没设）
obj.name = "Alice";
console.log(obj.name); // "Mr. Alice"
```

## 八、对象锁定三级机制

除了针对单个属性的细粒度控制，JavaScript 还提供了三个**对象级别**的方法来批量限制对象的行为。这三个方法形成了由弱到强的三级锁定机制：

### 8.1 三级锁定的完整对比

| 级别 | 方法 | 能否添加新属性？ | 能否删除已有属性？ | 能否修改已有属性值？ | 类比 |
|------|------|:-:|:-:|:-:|------|
| **Level 1** | `Object.preventExtensions(obj)` | ❌ 禁止 | ✅ 可以 | ✅ 可以 | 门上贴了"禁止入内" |
| **Level 2** | `Object.seal(obj)` | ❌ 禁止 | ❌ 禁止 | ⚠️ 仅限已有属性 | 门封死了 + 窗户钉死 |
| **Level 3** | `Object.freeze(obj)` | ❌ 禁止 | ❌ 禁止 | ❌ 全部冻结 | 整个房间变成水晶展品 |

对应的检测方法：

- `Object.isExtensible(obj)` —— 是否还能扩展？
- `Object.isSealed(obj)` —— 是否已封闭？
- `Object.isFrozen(obj)` —— 是否已冻结？

### 8.2 Level 1：preventExtensions（禁止扩展）

```javascript
const room = { desk: 1, chair: 2 };

Object.preventExtensions(room);

// ❌ 不能添加新属性
room.lamp = 1;
// 严格模式: TypeError: Cannot add property
// 非严格模式: 静默失败（不会真的加上）

// ✅ 可以修改已有属性
room.desk = 2;
console.log(room.desk); // 2

// ✅ 可以删除已有属性
delete room.chair;
console.log(room.chair); // undefined

console.log(Object.isExtensible(room)); // false
```

**类比**：`preventExtensions` 就像是给你的房间贴了一张"禁止搬入新家具"的告示。原有的家具可以移动位置（修改）、可以搬出去（删除），但不能再往里面带新东西了。

### 8.3 Level 2：seal（封闭对象）

```javascript
'use strict';
const box = { itemA: "apple", itemB: "banana" };

Object.seal(box);

// ❌ 不能添加新属性
box.itemC = "cherry";
// TypeError: Cannot add property itemC

// ❌ 不能删除已有属性
delete box.itemA;
// TypeError: Cannot delete property itemA

// ✅ 可以修改已有属性的值
box.itemB = "blueberry";
console.log(box.itemB); // "blueberry"

// 但不能修改属性的特性（因为 seal 把所有属性的 configurable 都设为 false）
Object.defineProperty(box, 'itemA', { enumerable: false });
// TypeError: Cannot redefine property

console.log(Object.isSealed(box)); // true
```

**seal 的底层原理**：调用 `Object.seal(obj)` 相当于将对象上**所有现有属性**的 `configurable` 标志统一设为 `false`，同时调用 `Object.preventExtensions`。也就是说，seal = preventExtensions + 所有属性 configurable:false。

**类比**：seal 就像是用保鲜膜把盒子密封起来了。你不能往里面塞新东西（禁止扩展），也不能把里面的东西拿出来（禁止删除），但可以通过挤压保鲜膜改变里面的物品形状（修改值）。而且一旦封上了，你就不能再调整盒子的结构（修改标志）。

### 8.4 Level 4：freeze（冻结对象）

```javascript
'use strict';
const constants = {
  APP_NAME: "MyApp",
  VERSION: "1.0.0",
  MAX_USERS: 1000
};

Object.freeze(constants);

// ❌ 不能添加
constants.DEBUG = true;       // TypeError

// ❌ 不能删除
delete constants.APP_NAME;    // TypeError

// ❌ 不能修改值
constants.VERSION = "2.0.0";  // TypeError

console.log(Object.isFrozen(constants)); // true
```

**freeze 的底层原理**：`Object.freeze(obj)` 相当于在 `Object.seal(obj)` 的基础上，再将**所有现有属性**的 `writable` 标志统一设为 `false`。也就是说，freeze = seal + 所有属性 writable:false。

### 8.5 ⚠️ 浅冻结——嵌套对象的陷阱

`Object.freeze` 是**浅冻结（Shallow Freeze）**——它只会冻结对象的第一层属性。如果属性值本身又是一个对象，那个内部对象并不会被冻结：

```javascript
const config = {
  db: {
    host: "localhost",
    port: 3306
  },
  api: {
    timeout: 5000
  }
};

Object.freeze(config);

// 第一层确实被冻结了
config.db = { host: "evil.com" }; // ❌ TypeError（第一层的引用不能改）

// 但是！内部的 db 对象没有被冻结！
config.db.host = "evil.com";      // ✅ 这竟然成功了！
console.log(config.db.host);      // "evil.com" —— 安全漏洞！

config.api.timeout = 1;           // ✅ 也成功了
console.log(config.api.timeout);  // 1
```

**解决方案：深冻结（Deep Freeze）**

```javascript
function deepFreeze(obj) {
  // 先冻结当前对象
  Object.freeze(obj);

  // 遍历所有属性
  for (const key of Object.getOwnPropertyNames(obj)) {
    const value = obj[key];
    
    // 如果属性值是对象且还没被冻结
    if (typeof value === 'object' && value !== null && !Object.isFrozen(value)) {
      deepFreeze(value); // 递归冻结
    }
  }
  
  return obj;
}

deepFreeze(config);

config.db.host = "hacker.com";   // ❌ TypeError（现在也被保护了）
config.api.timeout = 0;          // ❌ TypeError
```

### 8.6 Math.PI——天然冻结的常量

JavaScript 内置的一些常量就是通过 freeze 机制实现的：

```javascript
const piDescriptor = Object.getOwnPropertyDescriptor(Math, 'PI');
console.log(piDescriptor);
// {
//   value: 3.141592653589793,
//   writable: false,      ← 不可写
//   enumerable: false,    ← 不可枚举
//   configurable: false   ← 不可删除、不可修改标志
// }

Math.PI = 3;           // 静默失败
Math.PI;               // 仍然是 3.141592653589793
delete Math.PI;        // 静默失败
Math.PI;               // 仍然是 3.141592653589793
```

`Math.PI` 就是一个完美的"常量"范例——`writable: false` 保证值不被修改，`configurable: false` 保证属性本身不被删除或重新定义。如果你想在自己的代码中创建类似的常量，可以用同样的方式：

```javascript
// 创建一个类似 Math.PI 的常量
const MY_APP = {};
Object.defineProperty(MY_APP, 'VERSION', {
  value: '1.0.0',
  writable: false,
  enumerable: true,
  configurable: false
});

MY_APP.VERSION = '9.9.9'; // 改不了
delete MY_APP.VERSION;    // 删不掉
```

## 九、高级工具与方法速查

### 9.1 描述符相关 API 速查表

| 方法 | 功能 | 返回值 |
|------|------|--------|
| `Object.getOwnPropertyDescriptor(obj, key)` | 获取**单个**自身属性的描述符 | 描述符对象或 `undefined` |
| `Object.getOwnPropertyDescriptors(obj)` | 获取**所有**自身属性的描述符（含 Symbol） | 描述符对象的对象 |
| `Object.defineProperty(obj, key, desc)` | 定义/修改**单个**属性及其描述符 | 被操作的对象 |
| `Object.defineProperties(obj, descs)` | 批量定义/修改**多个**属性 | 被操作的对象 |
| `Object.getPrototypeOf(obj)` | 获取对象的原型（推荐替代 `__proto__`） | 原型对象或 `null` |
| `Object.setPrototypeOf(obj, proto)` | 设置对象的原型（性能警告！） | 被操作的对象 |
| `Object.create(proto, descs)` | 创建新对象并可指定原型和描述符 | 新对象 |
| `Object.isExtensible(obj)` | 检查是否可扩展 | boolean |
| `Object.preventExtensions(obj)` | 禁止扩展 | 被操作的对象 |
| `Object.isSealed(obj)` | 检查是否已封闭 | boolean |
| `Object.seal(obj)` | 封闭对象 | 被操作的对象 |
| `Object.isFrozen(obj)` | 检查是否已冻结 | boolean |
| `Object.freeze(obj)` | 冻结对象 | 被操作的对象 |

### 9.2 标志感知式克隆（Flag-Aware Cloning）

普通的对象复制方式（展开运算符、`Object.assign`）**只会复制属性的值**，会丢失所有的属性描述符信息：

```javascript
const original = {};

Object.defineProperty(original, 'readOnlyProp', {
  value: '不可改变的值',
  writable: false,
  enumerable: true,
  configurable: false
});

original.normalProp = '普通属性';

// ❌ 普通克隆——丢失描述符
const shallowClone = { ...original };
// shallowClone.readOnlyProp 现在变成了 writable: true！
shallowClone.readOnlyProp = "被改掉了！"; // 竟然成功了！
console.log(shallowClone.readOnlyProp); // "被改掉了！"

// ✅ 标志感知克隆——保留所有描述符
const perfectClone = Object.defineProperties(
  {},
  Object.getOwnPropertyDescriptors(original)
);

perfectClone.readOnlyProp = "还想改？";
// 💥 TypeError: Cannot assign to read only property
// 描述符被完美保留了！
```

**`Object.defineProperties` + `Object.getOwnPropertyDescriptors` 的组合**是目前 JavaScript 中唯一能够完整复制对象属性元数据的方式。这在需要深度克隆带有特殊属性描述符的对象时非常有用。

### 9.3 属性检测方法完整对比

| 方法 | 检测范围 | 包含不可枚举属性？ | 包含 Symbol 属性？ | 包含原型链？ | 返回类型 |
|------|---------|:-:|:-:|:-:|------|
| `'key' in obj` | 自身 + 原型链 | ✅ | ✅ | ✅ | boolean |
| `obj.hasOwnProperty(key)` | 仅自身 | ✅ | ✅ | ❌ | boolean |
| `Object.hasOwn(obj, key)` | 仅自身 | ✅ | ✅ | ❌ | boolean |
| `Object.keys(obj)` | 仅自身 | ❌ | ❌ | ❌ | string[] |
| `Object.values(obj)` | 仅自身 | ❌ | ❌ | ❌ | any[] |
| `Object.entries(obj)` | 仅自身 | ❌ | ❌ | ❌ | [string, any][] |
| `Object.getOwnPropertyNames(obj)` | 仅自身 | ✅ | ❌ | ❌ | string[] |
| `Object.getOwnPropertySymbols(obj)` | 仅自身 | ✅ | ✅ | ❌ | symbol[] |
| `Reflect.ownKeys(obj)` | 仅自身 | ✅ | ✅ | ❌ | (string\|symbol)[] |
| `for...in` | 自身 + 原型链 | ❌ | ❌ | ✅ | 循环遍历 |

## 十、经典陷阱与最佳实践

### 10.1 五大常见陷阱速查

| # | 陷阱 | 现象 | 解决方案 |
|---|------|------|---------|
| 1 | **defineProperty 默认标志为 false** | 创建的属性突然变得"只读+不可枚举+不可删除" | 显式指定所有需要的标志为 `true` |
| 2 | **freeze 是浅冻结** | 内部嵌套对象仍可被修改 | 使用 `deepFreeze()` 递归冻结 |
| 3 | **hasOwnProperty 被遮蔽** | 对象有同名属性导致方法调用报错 | 使用 `Object.hasOwn()` 或 `.call()` |
| 4 | **for...in 遍历到原型属性** | 意外遍历到继承来的属性 | 配合 `hasOwnProperty` 过滤 |
| 5 | **JSON.stringify 忽略不可枚举属性** | 序列化时丢失数据 | 确保需要序列化的属性 `enumerable: true` |

### 10.2 最佳实践清单

```javascript
// ✅ 最佳实践 1：创建常量对象
const CONSTANTS = Object.freeze({
  API_URL: 'https://api.example.com',
  VERSION: '1.0.0'
});

// ✅ 最佳实践 2：使用访问器做数据校验
class User {
  #_email;  // 私有字段（ES2022+）
  
  get email() { return this.#_email; }
  
  set email(value) {
    if (!value.includes('@')) {
      throw new Error('Invalid email format');
    }
    this.#_email = value;
  }
}

// ✅ 最佳实践 3：安全地检测属性
if (Object.hasOwn(obj, 'key')) {  // 比 hasOwnProperty 更安全
  // ...
}

// ✅ 最佳实践 4：完整克隆时保留描述符
const clone = Object.defineProperties(
  {},
  Object.getOwnPropertyDescriptors(source)
);

// ✅ 最佳实践 5：需要不可变数据时优先用 freeze
const state = deepFreeze({
  user: { name: "Alice" },
  items: [1, 2, 3]
});

// ❌ 反模式 1：不要用 __proto__ 代替 Object.create
// bad: obj.__proto__ = proto;
// good: const obj = Object.create(proto);

// ❌ 反模式 2：不要频繁使用 setPrototypeOf（性能杀手）
// 它会破坏引擎的优化，尽量在创建时就确定好原型

// ❌ 反模式 3：不要依赖 delete 的返回值来判断是否成功
// delete 不存在的属性也返回 true
```

## 十一、知识图谱

```
JavaScript 对象内部方法完整体系
│
├── 四大内部方法（Internal Methods）
│   │
│   ├── [[Get]](propertyKey, receiver) —— 属性读取
│   │   ├── 优先查找自身属性
│   │   ├── 找到 Data Property → 返回 value
│   │   ├── 找到 Accessor Property → 调用 getter(this=receiver)
│   │   └── 自身找不到 → 沿原型链递归查找 → null 则返回 undefined
│   │
│   ├── [[Set]](propertyKey, value, receiver) —— 属性写入
│   │   ├── 自身找到 Data Property(writable:true) → 直接赋值
│   │   ├── 自身找到 Data Property(writable:false) → 报错/静默失败
│   │   ├── 自身找到 Accessor Property(setter) → 调用 setter
│   │   ├── 原型找到 Accessor(setter) → 调用原型 setter(this=receiver) ★
│   │   ├── 原型找到 Data(writable:false) → 报错/静默失败 ★
│   │   └── 都找不到 → 在自身创建新属性
│   │
│   ├── [[HasProperty]](propertyKey) —— 属性存在性检测 ('in')
│   │   ├── 检查自身 + 递归检查整条原型链
│   │   └── 属性存在但值为 undefined 也返回 true
│   │
│   └── [[Delete]](propertyKey) —— 属性删除 (delete)
│       ├── 自身没有该属性 → 返回 true（"本来就没"）
│       ├── 有且 configurable:true → 删除并返回 true
│       ├── 有但 configurable:false → 报错/返回 false
│       └── 只能删除自有属性，不影响原型链
│
├── 属性描述符（Property Descriptor）
│   │
│   ├── 数据属性（Data Property）
│   │   ├── value: 属性的实际值
│   │   ├── writable: 能否修改值（默认 true / defineProperty 默认 false）
│   │   ├── enumerable: 能否被 for...in 枚举
│   │   └── configurable: 能否删除 + 能否修改标志
│   │
│   ├── 访问器属性（Accessor Property）
│   │   ├── get(): 读取时调用的函数
│   │   ├── set(value): 写入时传入新值
│   │   ├── enumerable: 同上
│   │   └── configurable: 同上
│   │   └── ⚠️ 与 data property 互斥（不能同时存在）
│   │
│   └── Object.defineProperty 的重要细节
│       ├── 常规赋值：默认标志全为 true
│       └── defineProperty：默认标志全为 false！（大陷阱）
│
├── 对象锁定三级机制
│   │
│   ├── Level 1: preventExtensions（禁止新增）
│   │   ├── ❌ 不能添加新属性
│   │   ├── ✅ 可以修改/删除已有属性
│   │   └── 检测：isExtensible()
│   │
│   ├── Level 2: seal（禁止新增 + 禁止删除）
│   │   ├── = preventExtensions + 所有属性 configurable:false
│   │   ├── ❌ 不能增/删，✅ 只能改已有属性值
│   │   └── 检测：isSealed()
│   │
│   └── Level 3: freeze（完全冻结）
│       ├── = seal + 所有属性 writable:false
│       ├── ❌ 不能增/删/改
│       ├── ⚠️ 浅冻结：嵌套对象需递归 deepFreeze
│       └── 检测：isFrozen()
│
├── 高级应用模式
│   │
│   ├── 智能属性（Smart Properties）
│   │   ├── 值验证模式（set 中校验后存储）
│   │   ├── 向后兼容重构（数据属性→访问器无缝切换）
│   │   ├── 懒加载/延迟计算（首次读取才初始化）
│   │   └── 只读计算属性（仅 get，无 set）
│   │
│   ├── 标志感知式克隆
│   │   └── defineProperties + getOwnPropertyDescriptors
│   │
│   └── 深冻结（Deep Freeze）
│       └── 递归遍历 + typeof === 'object' 判断 + Object.freeze
│
└── 设计原则
    ├── Fail Fast：严格模式下尽早暴露错误
    ├── 最小暴露：不必要的属性设为 enumerable:false
    ├── 不可变性优先：能用 freeze/seal 就不用手动管理
    ├── 访问器封装：用 getter/setter 保护内部数据
    └── 向后兼容：通过访问器平滑迁移 API
```
