# 属性访问器 —— Getter/Setter、defineProperty、defineProperties 与智能属性设计模式

> **核心内容**：JavaScript 访问器属性的完整解析——数据属性与访问器属性的本质区别、getter/setter 的两种语法定义（字面量/defineProperty）、只读属性与计算属性、四大智能属性设计模式（值验证/懒加载/兼容性重构/通知机制）、defineProperty 默认标志陷阱、defineProperties 批量操作、访问器在类中的高级应用，以及 Vue/React 等框架中响应式原理的底层基础。

## 一、从"存储值"到"控制行为"——为什么需要访问器？

### 1.1 数据属性的局限性

在日常编程中，我们最常接触的是**数据属性（Data Property）**——它就是一个简单的键值对：`obj.name = "Alice"`。这就像是把一张写着"Alice"的便利贴贴在一个叫"name"的位置上。简单直接。

但现实世界中的需求远比"存一个值"复杂。考虑以下场景：

- **用户名至少需要 3 个字符**——但 `obj.name = "A"` 这样的赋值完全合法
- **年龄应该是从生日自动计算出来的**——而不是一个可以随意篡改的数字
- **旧代码都在用 `obj.age`**，但新架构想改为基于生日计算——不能让所有调用方都改一遍
- **每次修改某个属性时需要自动触发某些操作**（如发送事件、更新 UI）

这些问题，数据属性都无法优雅地解决。因为数据属性的本质是**被动存储**——你给它什么值它就存什么，没有任何判断、拦截或副作用的余地。

### 1.2 访问器的本质

**访问器属性（Accessor Property）** 提供了一种全新的思路：**属性不再直接存储值，而是由一对函数来控制读写行为**。

让我们用一个生活中的类比来理解这个概念：

想象一家**银行的金库柜台**：

- **数据属性**就像是一个**敞开的自助储物柜**——谁都能往里放东西、取东西，没有检查、没有记录。
- **访问器属性**就像是一个**有柜员的柜台窗口**：
  - 你说"我想知道余额多少" → 柜员去查账本后告诉你（**getter**）
  - 你说"我要存入 100 元" → 柜员先验钞、记账、然后才完成操作（**setter**）

对于外部的人来说，两种方式的体验看起来差不多——都是问一下或者给个指令。但内部的处理流程却天差地别。访问器属性就是这样一种**对外伪装成普通属性、内部却执行自定义逻辑的属性**。

### 1.3 两种属性类型的完整对比

| 特性维度 | 数据属性 | 访问器属性 |
|---------|---------|-----------|
| **本质** | 存储一个静态值 | 由函数（get/set）组成 |
| **描述符关键字段** | `value` + `writable` | `get()` + `set(value)` |
| **读取行为** | 直接返回 `value` | **调用 getter 函数**，返回其结果 |
| **写入行为** | 直接替换 `value` | **调用 setter 函数**，传入新值 |
| **是否占用内存存储值** | ✅ 是（存储 value） | ❌ 否（不存储值，由 get/set 动态决定） |
| **能否做验证/日志等** | ❌ 不能 | ✅ 可以（在 set 中添加任意逻辑） |
| **能否实现计算属性** | ❌ 不能（值是静态的） | ✅ 可以（每次读取都重新计算） |
| **共同拥有的标志** | `enumerable`, `configurable` | `enumerable`, `configurable` |

### 1.4 互斥规则——同一属性只能二选一

这是 ECMAScript 规范层面的硬性约束：**一个属性要么是数据属性（有 `value`），要么是访问器属性（有 `get`/`set`），不可能同时拥有两者**：

```javascript
// ❌ 错误：同时指定 value 和 getter —— 规范禁止！
Object.defineProperty({}, 'confused', {
  value: 42,
  get() { return 100; }
});
// 💥 TypeError: Invalid property descriptor.
// Cannot both specify accessors and a value or writable attribute
```

为什么不允许？原因很直观：如果既有存储的值又有 getter 函数，那读取时应该返回哪个？如果既有 setter 又有 `writable: true`，写入时应该走哪条路径？这种歧义会导致不可预测的行为，所以规范干脆禁止了这种情况。

## 二、Getter 和 Setter 的基本语法

### 2.1 对象字面量语法（推荐用于定义时）

在现代 JavaScript 中，最常用的方式是在对象字面量中直接使用 `get` 和 `set` 关键字：

```javascript
const user = {
  firstName: "John",
  lastName: "Smith",

  // ====== Getter 定义 ======
  // 语法：get 属性名() { ... }
  // 作用：当有人读取 user.fullName 时，这个函数会被自动调用
  get fullName() {
    console.log('📖 getter 被调用了');
    return `${this.firstName} ${this.lastName}`;
  },

  // ====== Setter 定义 ======
  // 语法：set 属性名(参数) { ... }
  // 作用：当有人写 user.fullName = xxx 时，这个函数会被自动调用
  set fullName(value) {
    console.log('✏️ setter 被调用了，收到:', value);
    [this.firstName, this.lastName] = value.split(" ");
  }
};
```

**使用方式——跟普通属性一模一样，不需要加括号**：

```javascript
// 读取 → 自动触发 getter
console.log(user.fullName);
// 控制台输出：
// 📖 getter 被调用了
// John Smith  ← 这是 getter 的返回值

// 写入 → 自动触发 setter
user.fullName = "Alice Cooper";
// 控制台输出：
// ✏️ setter 被调用了，收到: Alice Cooper

// 验证拆分结果
console.log(user.firstName); // "Alice"
console.log(user.lastName);  // "Cooper"
```

**关键细节**：注意使用时是 `user.fullName` 而不是 `user.fullName()`。这就是访问器的魔力——**外表像普通属性一样简洁，内部却有函数的全部能力**。

### 2.2 Object.defineProperty 语法（推荐用于运行时动态创建）

除了字面量语法，你也可以在任何时候通过 `Object.defineProperty` 来创建或转换访问器属性。这在以下场景特别有用：

- 需要在对象创建之后**追加**访问器属性
- 需要**将已有的数据属性转换为访问器属性**（向后兼容重构）
- 需要精确控制 `enumerable` / `configurable` 标志

```javascript
const product = {
  _price: 0,       // 内部存储变量（下划线约定）
  discount: 0      // 折扣百分比（0-100）
};

Object.defineProperty(product, 'finalPrice', {
  // 注意：这里没有 value 和 writable
  // 取而代之的是 get 和 set 函数

  get() {
    const discounted = this._price * (1 - this.discount / 100);
    return Math.round(discounted * 100) / 100; // 保留两位小数
  },

  set(value) {
    if (typeof value !== 'number' || value < 0) {
      throw new Error(`价格必须是非负数字，收到: ${value}`);
    }
    if (this.discount > 0) {
      // 如果有折扣，反算原价
      this._price = value / (1 - this.discount / 100);
    } else {
      this._price = value;
    }
  },

  enumerable: true,     // 允许被枚举（默认 false！）
  configurable: true    // 允许后续修改（默认 false！）
});
```

使用效果：

```javascript
product._price = 100;
product.discount = 20;

console.log(product.finalPrice); // 80 ← getter 自动计算折扣后价格

product.finalPrice = 90;
// setter 被触发：因为有 20% 折扣，反算原价 = 90 / 0.8 = 112.5
console.log(product._price);    // 112.5
```

### 2.3 两种语法的对比

| 特性 | 字面量语法 `{ get x(){} }` | defineProperty 语法 |
|------|:-:|:-:|
| **使用时机** | 创建对象的同时定义 | 对象创建后的任何时候 |
| **代码位置** | 必须在对象字面量内部 | 可以在任何地方调用 |
| **灵活性** | 较固定 | 可根据条件动态决定 |
| **标志控制** | 默认 `enumerable: true, configurable: true` | **默认 `enumerable: false, configurable: false`** ⚠️ |
| **适用场景** | 大部分日常开发 | 运行时修改、向后兼容重构 |

## 三、只读属性——只有 getter 没有 setter

### 3.1 基本概念

如果你只定义了 getter 而省略了 setter，那么这个属性就变成了**只读属性**——可以读取但不能写入：

```javascript
const circle = {
  radius: 5,

  // 只定义 getter，不定义 setter → 只读
  get area() {
    return Math.PI * this.radius * this.radius;
  },
  
  get circumference() {
    return 2 * Math.PI * this.radius;
  },

  get diameter() {
    return this.radius * 2;
  }
};
```

```javascript
console.log(circle.area);          // 78.54... ✓ 正常读取
console.log(circle.circumference); // 31.42... ✓ 正常读取
console.log(circle.diameter);      // 10 ✓ 正常读取

circle.area = 100;
// 💥 严格模式：TypeError: Cannot set property area which has only a getter
// 非严格模式：静默失败（值不变）

circle.radius = 10;
console.log(circle.area);          // 314.15... ← 改变 radius 后 area 自动更新
```

### 3.2 为什么只读属性如此有用？

**场景一：派生/计算属性**

很多值并不需要独立存储，它们可以从其他属性实时计算得出。面积就是典型的例子——它永远等于 πr²，没必要单独存一份。如果用普通属性来存，就会出现 radius 改了但 area 没更新的不一致问题：

```javascript
// ❌ 用普通属性的糟糕做法
const badCircle = {
  radius: 5,
  area: Math.PI * 5 * 5  // 初始化时计算的
};

badCircle.radius = 10;
console.log(badCircle.area); // 78.54... ← 还是旧的！radius 变了但 area 没跟着变！

// ✅ 用只读访问器的正确做法
const goodCircle = {
  radius: 5,
  get area() { return Math.PI * this.radius * this.radius; }
};

goodCircle.radius = 10;
console.log(goodCircle.area); // 314.15... ← 自动重新计算！
```

**类比**：普通属性像是拍了一张照片挂在墙上——即使本人已经长高了，照片上的身高还是老的。只读访问器则像是每次看一眼真人再报出身高——永远是实时的准确值。

**场景二：暴露 API 但隐藏实现**

```javascript
class DatabaseConnection {
  #poolSize = 10;

  // 外部代码可以"查看"连接池大小
  get poolSize() {
    return this.#poolSize;
  }

  // 但不能从外部修改它
  // （没有定义 setter）
}
```

**场景三：常量保护**

```javascript
const AppConfig = Object.create(null);

Object.defineProperty(AppConfig, 'VERSION', {
  get() { return '1.2.0'; },   // 只能读到固定值
  enumerable: true
});

AppConfig.VERSION = '9.9.9';
console.log(AppConfig.VERSION); // 仍然是 '1.2.0' — 无法篡改
```

## 四、四大智能属性设计模式

访问器属性的真正威力在于它可以实现各种**智能属性（Smart Properties）**模式——在属性的读写操作中注入业务逻辑。

### 4.1 模式一：值验证（Validation Gatekeeper）

**问题**：如何确保赋给对象的值总是合法的？

**方案**：在 setter 中加入验证逻辑，只有通过验证的值才能被实际存储：

```javascript
class UserAccount {
  #email;
  #age;
  #password;

  get email() { return this.#email; }
  
  set email(value) {
    // 验证 1：必须包含 @ 符号
    if (!value.includes('@')) {
      throw new Error(`无效的邮箱格式: "${value}"，必须包含 @`);
    }
    
    // 验证 2：长度限制
    if (value.length > 254) {
      throw new Error('邮箱地址过长（最大254字符）');
    }
    
    // 验证 3：不能有空格
    if (value.includes(' ')) {
      throw new Error('邮箱地址不能包含空格');
    }
    
    this.#email = value.toLowerCase(); // 统一转为小写
  }

  get age() { return this.#age; }
  
  set age(value) {
    if (!Number.isInteger(value)) {
      throw new Error('年龄必须是整数');
    }
    if (value < 0 || value > 150) {
      throw new Error('年龄必须在 0-150 之间');
    }
    this.#age = value;
  }

  get password() { return '******'; } // 永远不暴露真实密码
  
  set password(value) {
    if (value.length < 8) {
      throw new Error('密码至少8个字符');
    }
    // 实际存储哈希值而非明文
    this.#password = hashPassword(value);
  }
}

function hashPassword(pwd) {
  return Array.from(pwd).reduce((hash, ch) => 
    ((hash << 5) - hash + ch.charCodeAt(0)) | 0, 0
  ).toString(16);
}

const user = new UserAccount();
user.email = "Alice@Example.COM";  // ✓ 通过验证，存储为小写
console.log(user.email);            // "alice@example.com"

user.age = 25;                     // ✓ 通过验证
user.age = -5;                     // 💥 Error: 年龄必须在 0-150 之间

user.password = "mySecret123";     // ✓ 存储的是哈希值
console.log(user.password);         // "******" — 明文永远不会泄露
```

**设计哲学**：setter 就像一个**安检门**——所有进入的数据都必须经过检查。不合格的被拦在外面（抛出异常），合格的才能进入（存到内部变量）。而 getter 则像是**经过过滤的水龙头**——流出的水（数据）已经被处理过（如脱敏、格式化），不会泄露原始信息。

### 4.2 模式二：懒加载与缓存（Lazy Loading & Caching）

**问题**：某些属性的初始化非常耗时（如解析大文件、网络请求、复杂数学运算），但如果最终没有被用到，这些开销就被浪费了。

**方案**：只在第一次读取时执行昂贵操作，之后将结果缓存起来：

```javascript
class HeavyResourceLoader {
  #cachedData = null;
  #isLoaded = false;

  get data() {
    if (!this.#isLoaded) {
      console.log('⏳ 开始加载重型资源...');
      
      // 模拟耗时的初始化操作
      // 可能是：解析大型 JSON、建立数据库连接、编译正则表达式...
      const startTime = performance.now();
      
      this.#cachedData = Array.from({ length: 500000 }, (_, i) => ({
        id: i,
        name: `Item-${i}`,
        computed: Math.sqrt(i) * Math.PI
      }));
      
      const elapsed = (performance.now() - startTime).toFixed(2);
      console.log(`✅ 加载完成，耗时 ${elapsed}ms`);
      
      this.#isLoaded = true;
    }
    
    return this.#cachedData;
  }
}

const loader = new HeavyResourceLoader();

// 第一次读取 → 触发加载
console.log(loader.data.length);
// ⏳ 开始加载重型资源...
// ✅ 加载完成，耗时 xx ms
// 500000

// 第二次及之后的读取 → 直接返回缓存
console.log(loader.data.length);
console.log(loader.data[0].name);
// 不再有 "开始加载" 的日志——直接从缓存返回
```

**更进阶的带过期时间的缓存**：

```javascript
class CachedAPIResponse {
  #cache = null;
  #timestamp = 0;
  #ttl = 60000; // 缓存有效期 60 秒

  async get userData() {
    const now = Date.now();
    
    // 缓存未过期 → 直接返回
    if (this.#cache && (now - this.#timestamp) < this.#ttl) {
      console.log('📦 使用缓存数据');
      return this.#cache;
    }
    
    // 缓存过期或不存在 → 重新获取
    console.log('🔄 请求最新数据...');
    this.#cache = await fetch('/api/user').then(r => r.json());
    this.#timestamp = now;
    return this.#cache;
  }
}
```

### 4.3 模式三：向后兼容重构（Backward Compatible Refactoring）

**问题**：你的项目中大量代码在使用 `user.age` 属性。但现在你想改为基于生日计算年龄以提高准确性（因为人的年龄每天都会变化）。如果直接删除 `age` 并改用 `birthday`，所有旧代码都会崩溃。

**方案**：将 `age` 从数据属性转换为访问器属性——外部接口不变，内部实现彻底改变：

```javascript
// ========== 旧版本（数据属性）==========
function OldUser(name, age) {
  this.name = name;
  this.age = age;  // 直接存的数字
}

const oldUser = new OldUser("John", 30);
console.log(oldUser.age); // 30 —— 但一年后还是 30，不对了


// ========== 新版本（访问器属性——接口完全不变！）==========
function NewUser(name, birthday) {
  this.name = name;
  this.birthday = birthday; // 改为存储 Date 对象

  // 将 age 定义为访问器属性
  Object.defineProperty(this, 'age', {
    get() {
      const today = new Date();
      let age = today.getFullYear() - this.birthday.getFullYear();
      
      // 处理今年还没过生日的情况
      const m = today.getMonth() - this.birthday.getMonth();
      if (m < 0 || (m === 0 && today.getDate() < this.birthday.getDate())) {
        age--;
      }
      
      return age;
    },

    set(value) {
      console.warn(
        '⚠️ 建议设置 birthday 而不是直接设置 age。' +
        '已自动推算出生年份（可能不准确）。'
      );
      
      // 为了兼容性，仍然允许写入（只是给出警告）
      // 反推生日：假设生日是今年的今天
      const estimatedBirthday = new Date();
      estimatedBirthday.setFullYear(estimatedBirthday.getFullYear() - value);
      this.birthday = estimatedBirthday;
    },

    enumerable: true,
    configurable: true
  });
}


// ========== 旧代码完全不用改！==========
const newUser = NewUser("Alice", new Date(1992, 6, 1)); // 1992年7月1日

// 这些代码无论在新版还是旧版中都正常工作：
console.log(newUser.name);           // "Alice"
console.log(newUser.age);            // 动态计算出的真实年龄
console.log(newUser.birthday);       // 新增的功能也可以用

newUser.age = 30;                    // 旧代码中的写入也能工作（只是警告一下）
```

**这就是访问器属性最大的工程价值之一**：它让你可以在**零破坏迁移**的前提下改变数据的底层实现。在大规模项目的渐进式重构中，这种能力极其珍贵。

**类比**：这就像是把一家商店的收银台换成了自动结账机——顾客（外部代码）的操作流程没变（扫码→付款→拿走商品），但后台的结算系统已经完全不同了（人工记账→电子系统）。过渡期间两边都能正常运作。

### 4.4 模式四：变更通知与副作用（Change Notification & Side Effects）

**问题**：当一个属性发生变化时，需要自动触发其他操作（如更新 DOM、发送网络请求、触发事件、维护其他相关属性的一致性）。

**方案**：在 setter 中注入副作用逻辑：

```javascript
class ReactiveComponent {
  #state = {};

  constructor(initialState) {
    this.#state = { ...initialState };
  }

  // 通用的响应式属性工厂
  createReactiveProp(key) {
    Object.defineProperty(this, key, {
      get() {
        return this.#state[key];
      },
      
      set(newValue) {
        const oldValue = this.#state[key];
        
        // 只有值真正改变了才触发更新
        if (oldValue === newValue) return;
        
        // 1. 更新状态
        this.#state[key] = newValue;
        
        // 2. 触发副作用
        this.onPropertyChanged(key, oldValue, newValue);
      },
      
      enumerable: true,
      configurable: true
    });
  }

  onPropertyChanged(key, oldValue, newValue) {
    console.log(`📣 属性 "${key}" 变化: ${oldValue} → ${newValue}`);
    
    // 这里可以扩展为：
    // - 重新渲染组件
    // - 发送 WebSocket 消息
    // - 写入 localStorage
    // - 触发自定义事件
    
    if (key === 'theme') {
      document.documentElement.setAttribute('data-theme', newValue);
      // 切换主题色
    }
    
    if (key === 'language') {
      this.loadTranslations(newValue);
    }
  }

  loadTranslations(lang) {
    console.log(`🌍 加载 ${lang} 语言包...`);
    // fetch(`/i18n/${lang}.json`)...
  }
}

const component = new ReactiveComponent({
  theme: 'dark',
  language: 'zh-CN',
  title: 'Hello'
});

component.createReactiveProp('theme');
component.createReactiveProp('language');
component.createReactiveProp('title');

component.theme = 'light';    // 📣 属性 "theme" 变化: dark → light
component.language = 'en-US'; // 📣 属性 "language" 变化: zh-CN → en-US
component.title = 'World';    // 📣 属性 "title" 变化: Hello → World

component.title = 'World';    // （无输出——值相同，不触发）
```

这个模式正是现代前端框架（Vue.js 的 `reactive`、MobX 的 `observable`、Solid.js 的信号系统）的核心原理。虽然框架的实现使用了更底层的 Proxy 技术，但其**思想源头都是一样的——拦截属性的读写操作并注入额外逻辑**。

## 五、defineProperties——批量定义多个属性

### 5.1 为什么需要批量操作？

当你需要一次性为一个对象定义多个带有特殊描述符的属性时，反复调用 `Object.defineProperty` 既冗长又低效。`Object.defineProperties` 就是为此设计的批量操作方法：

```javascript
const user = {
  firstName: "John",
  lastName: "Smith",
  email: "john@example.com"
};

// 一次调用定义多个访问器属性
Object.defineProperties(user, {

  // 访问器 1：fullName
  fullName: {
    get() { return `${this.firstName} ${this.lastName}`; },
    set(value) { [this.firstName, this.lastName] = value.split(" "); },
    enumerable: true,
    configurable: true
  },

  // 访问器 2：domain（从邮箱提取域名）
  domain: {
    get() { return this.email.split('@')[1]; },
    enumerable: true,
    configurable: true
  },

  // 数据属性 3：createdAt（设为不可配置的只读时间戳）
  createdAt: {
    value: new Date().toISOString(),
    writable: false,
    enumerable: true,
    configurable: false
  },

  // 数据属性 4：internalId（内部标识，不可枚举）
  internalId: {
    value: crypto.randomUUID?.() ?? Math.random().toString(36).slice(2),
    enumerable: false,  // 外部遍历看不到
    writable: false,
    configurable: false
  }
});
```

使用效果：

```javascript
console.log(user.fullName); // "John Smith"
console.log(user.domain);  // "example.com"
console.log(user.createdAt); // "2026-04-17T08:30:00.000Z"

user.fullName = "Jane Doe";
console.log(user.firstName); // "Jane"

for (let key in user) {
  console.log(key);
  // 输出：firstName, lastName, email, fullName, domain, createdAt
  // 注意：internalId 不会出现（enumerable: false）
}
```

### 5.2 与 defineProperty 的关系

`Object.defineProperties(obj, descriptors)` 本质上就是对每个属性依次调用 `Object.defineProperty(obj, prop, descriptor)` 的语法糖。两者在功能上完全等价，区别仅在于：

| 维度 | `defineProperty`（单数） | `defineProperties`（复数） |
|------|:-:|:-:|
| **每次调用定义几个属性** | 1 个 | N 个 |
| **适合的场景** | 单个属性动态添加/修改 | 初始化时批量配置 |
| **原子性** | 每次独立 | 一次调用完成全部（语义上更清晰） |

## 六、访问器在 Class 中的应用

### 6.1 类中的访问器语法

ES2015 引入的 class 语法原生支持访问器属性的定义，而且比对象字面量更强大——因为它可以配合私有字段（`#`）实现真正的封装：

```javascript
class BankAccount {
  // 私有字段（ES2022+，真正的语言级私有）
  #balance;
  owner;
  #transactionLog = [];

  constructor(ownerName, initialBalance = 0) {
    this.owner = ownerName;
    this.#balance = initialBalance;
  }

  // ====== 只读计算属性 ======
  get balance() {
    return this.#balance;
  }

  // balance 没有 setter → 外部无法直接修改余额！

  get isOverdrawn() {
    return this.#balance < 0;
  }

  get status() {
    if (this.isOverdraft) return '⚠️ 透支';
    if (this.#balance === 0) return '💸 空账户';
    return '✅ 正常';
  }

  // ====== 有完整读写控制的属性 ======
  get overdraftLimit() {
    return this.#overdraftLimit ?? 0;
  }

  set overdraftLimit(amount) {
    if (amount < 0) throw new Error('透支额度不能为负');
    if (amount > 10000) throw new Error('透支额度上限为 10000');
    this.#overdraftLimit = amount;
  }

  // ====== 方法（真正的业务操作）=====
  deposit(amount) {
    if (amount <= 0) throw new Error('存款金额必须大于0');
    this.#balance += amount;
    this.#logTransaction('存款', amount);
  }

  withdraw(amount) {
    if (amount <= 0) throw new Error('取款金额必须大于0');
    if (amount > this.#balance + this.overdraftLimit) {
      throw new Error('超出可用余额（含透支额度）');
    }
    this.#balance -= amount;
    this.#logTransaction('取款', -amount);
  }

  #logTransaction(type, amount) {
    this.#transactionLog.push({
      type,
      amount,
      timestamp: new Date().toISOString(),
      balanceAfter: this.#balance
    });
  }

  get history() {
    return [...this.#transactionLog]; // 返回副本防止外部修改
  }
}
```

使用示例：

```javascript
const account = new BankAccount("Alice", 1000);

console.log(account.balance);    // 1000 ✓ 只读
account.balance = 999999;        // ❌ 无效（没有 setter）

console.log(account.status);     // "✅ 正常"

account.deposit(500);
console.log(account.balance);    // 1500

account.withdraw(2000);
console.log(account.balance);    // -500
console.log(account.isOverdrawn); // true
console.log(account.status);     // "⚠️ 透支"

account.overdraftLimit = 5000;
console.log(account.history);    // 完整的交易记录数组
```

### 6.2 静态访问器属性

类也支持**静态（static）访问器属性**——属于类本身而不属于实例：

```javascript
class TemperatureConverter {
  static get absoluteZeroCelsius() {
    return -273.15;
  }

  static get boilingPointCelsius() {
    return 100;
  }

  static get freezingPointFahrenheit() {
    return 32;
  }
}

// 通过类名访问（不是实例）
console.log(TemperatureConverter.absoluteZeroCelsius); // -273.15
console.log(TemperatureConverter.boilingPointCelsius);  // 100
```

### 6.3 继承中的访问器覆盖

子类可以覆盖父类的 getter 或 setter，甚至只覆盖其中一个：

```javascript
class Animal {
  constructor(name, speed) {
    this.name = name;
    this._speed = speed;
  }

  get info() {
    return `${this.name}: speed ${this._speed} km/h`;
  }
}

class Bird extends Animal {
  constructor(name, speed, canFly) {
    super(name, speed);
    this.canFly = canFly;
  }

  // 只覆盖 getter（保留父类的 setter 行为——如果有的话）
  get info() {
    const baseInfo = super.info; // 调用父类的 getter
    return `${baseInfo}, ${this.canFly ? '会飞' : '不会飞'}`;
  }

  // 也可以新增自己的访问器
  get type() {
    return 'Bird';
  }
}

const eagle = new Bird("Eagle", 320, true);
console.log(eagle.info); // "Eagle: speed 320 km/h, 会飞"
```

## 七、陷阱与注意事项

### 7.1 五大常见陷阱速查

| # | 陷阱 | 现象 | 解决方案 |
|---|------|------|---------|
| 1 | **defineProperty 创建的访问器默认不可枚举** | `for...in` 和 `Object.keys()` 遍历不到新属性 | 显式设置 `enumerable: true` |
| 2 | **递归调用导致栈溢出** | getter 内部又读取同名属性 | 确保读取的是内部存储变量（`_name`）而非自身 |
| 3 | **setter 中再次触发 setter 导致无限循环** | setter 内部对同名属性赋值 | 同上，赋值给内部存储变量 |
| 4 | **下划线约定并非真正的私有** | 外部代码可以直接访问 `_name` | 使用 ES2022 私有字段 `#name` 或 WeakMap |
| 5 | **JSON.stringify 忽略访问器属性** | 序列化时丢失数据 | 实现 `toJSON()` 方法或在序列化前手动提取值 |

### 7.2 陷阱详解：递归无限循环

这是一个新手最容易犯的错误：

```javascript
const obj = {
  // ❌ 错误示范：递归调用自己！
  get value() {
    return this.value; // 这里又触发了 getter → 无限循环！
  },
  
  set value(v) {
    this.value = v;   // 这里又触发了 setter → 无限循环！
  }
};

obj.value = 10;
// 💥 Maximum call stack size exceeded（栈溢出）
```

正确的做法——使用不同的名称来存储实际值：

```javascript
// ✅ 正确：使用 _value 作为内部存储
const obj = {
  _value: undefined,

  get value() {
    return this._value; // 读取的是 _value，不是 value → 不会递归
  },
  
  set value(v) {
    this._value = v;    // 赋值给 _value，不是 value → 不会递归
  }
};

obj.value = 10;
console.log(obj.value); // 10 ✓ 正常工作
```

**为什么会出现这个问题？** 因为 getter/setter 中的 `this.value` 也会触发 getter/setter——就像一个人站在镜子前，镜子里的人也在照镜子，形成了无限反射。解决方法就是打破这个反射链——用一个不同的名字来存储真实值。

### 7.3 JSON 序列化的问题

`JSON.stringify()` 在序列化对象时会忽略访问器属性（因为它只序列化可枚举的数据属性）。如果你的对象主要依赖访问器来提供数据，序列化结果可能是空的或缺失重要字段：

```javascript
const user = {
  firstName: "John",
  lastName: "Smith",

  get fullName() {
    return `${this.firstName} ${this.lastName}`;
  },

  // 即使设为 enumerable: true 也可能不如预期
  get displayName() {
    return `Mr. ${this.fullName}`;
  }
};

console.log(JSON.stringify(user));
// {"firstName":"John","lastName":"Smith"}
// fullName 和displayName 都不在其中！

// 解决方案：实现 toJSON 方法
user.toJSON = function() {
  return {
    firstName: this.firstName,
    lastName: this.lastName,
    fullName: this.fullName,      // 手动提取访问器的值
    displayName: this.displayName
  };
};

console.log(JSON.stringify(user));
// {"firstName":"John","lastName":"Smith","fullName":"John Smith","displayName":"Mr. John Smith"}
```

## 八、最佳实践指南

### 8.1 何时使用访问器属性？

| 场景 | 推荐 | 说明 |
|------|------|------|
| 需要在赋值时验证数据合法性 | ✅ 强烈推荐 | setter 天然适合做校验门卫 |
| 属性值由其他属性计算而来 | ✅ 强烈推荐 | getter 实现计算属性，避免数据冗余 |
| 需要在属性变化时触发副作用 | ✅ 推荐 | 如通知系统、更新关联状态 |
| 需要保持 API 向后兼容 | ✅ 推荐 | 数据属性→访问器的无缝切换 |
| 只是简单的数据存取 | ❌ 不需要 | 普通数据属性就够了 |
| 高频读取的性能敏感路径 | ⚠️ 谨慎 | 每次 getter 调用都有函数调用开销 |

### 8.2 设计原则清单

```javascript
// ✅ 原则 1：单一职责
// 每个 getter/setter 只做一件事（验证/计算/通知/存储）
// 不要在 setter 里同时做验证、发请求、写日志……

// ✅ 原则 2：保持幂等性
// 多次读取同一个 getter 应该得到相同的结果（除非依赖的状态确实变了）

// ✅ 原则 3：快速失败（Fail Fast）
// setter 中发现非法值应立即抛异常，不要静默接受错误数据

// ✅ 原则 4：内部存储命名规范
// 用 _前缀（约定）或 #前缀（ES2022 私有字段）标记内部变量

// ✅ 原则 5：不要在 getter 中产生副作用
// getter 应该是纯计算/读取操作，不应修改任何状态

// ❌ 反模式：getter 中修改状态
get dangerous() {
  this._counter++; // ❌ getter 不应该有副作用！
  return this._counter;
}
```

### 8.3 下划线约定的真相

以 `_` 开头的属性名（如 `_name`, `_balance`）是一种广泛使用的**命名约定**，用来表示"这是内部实现细节，请不要直接使用"。但它仅仅是一个**约定**——语言层面完全不阻止任何人访问和修改它：

```javascript
const obj = {
  _secret: "内部数据",

  get secret() { return this._secret; },
  set secret(v) { this._secret = v; }
};

// 约定可以被绕过
obj._secret = "被外部篡改了";  // 完全合法，没有任何警告
console.log(obj.secret);        // "被外部篡改了" —— 保护失效
```

如果你需要真正的私有性（连名字都看不到、无法从外部访问），请使用 ES2022 引入的**私有字段（Private Fields）**：

```javascript
class SecureBox {
  #realSecret; // 真正的私有——外部完全不可见

  constructor(value) {
    this.#realSecret = value;
  }

  get secret() { return this.#realSecret; }
  set secret(v) { this.#realSecret = v; }
}

const box = new SecureBox("绝密");
box.#realSecret = "试试"; // 💥 SyntaxError: Private field '#realSecret'
                          // 必须在类内部声明的方法中才能访问
```

## 九、知识图谱

```
JavaScript 属性访问器（Getter/Setter）完整体系
│
├── 核心概念
│   │
│   ├── 数据属性 vs 访问器属性
│   │   ├── 数据属性：存储静态值（value + writable）
│   │   ├── 访问器属性：由函数控制（get + set）
│   │   ├── 外表一致：都用 obj.prop 方式访问
│   │   └── 互斥规则：同一属性不能既是数据又是访问器
│   │
│   ├── 为什么需要访问器？
│   │   ├── 数据属性无法做验证/计算/通知
│   │   ├── 访问器 = "伪装成属性的函数"
│   │   └── 类比：自助储物柜 vs 有柜员的柜台窗口
│   │
│   └── 只读属性
│       └── 仅 getter 无 setter → 写入时报错
│       └── 适用：计算属性/常量/API 隐藏
│
├── 语法定义（两种方式）
│   │
│   ├── 方式一：对象字面量语法
│   │   └── { get propName() {} , set propName(v) {} }
│   │   └── 默认 enumerable:true, configurable:true
│   │
│   └── 方式二：Object.defineProperty
│       └── Object.defineProperty(obj, key, { get(){}, set(v){} })
│       └── ⚠️ 默认 enumerable:false, configurable:false（大陷阱！）
│
├── 四大智能属性设计模式
│   │
│   ├── 模式一：值验证（Validation Gatekeeper）
│   │   ├── setter 中校验合法性
│   │   ├── 不合格 → 抛异常拒绝
│   │   └── 类比：安检门
│   │
│   ├── 模式二：懒加载与缓存（Lazy Loading）
│   │   ├── 首次读取才初始化
│   │   ├── 后续读取返回缓存
│   │   └── 进阶：带 TTL 的过期缓存
│   │
│   ├── 模式三：向后兼容重构（Backward Compatibility）
│   │   ├── 数据属性 → 访问器无缝切换
│   │   ├── 外部代码零修改
│   │   └── 类比：收银台换成自动结账机
│   │
│   └── 模式四：变更通知（Change Notification）
│       ├── setter 中触发副作用
│       ├── 应用：DOM更新/事件/持久化
│       └── 框架响应式的思想源头（Vue/MobX/Solid）
│
├── 批量操作
│   └── Object.defineProperties(obj, { prop1: desc1, prop2: desc2 })
│   └── 一次定义多个属性及其描述符
│
├── Class 中的访问器
│   ├── 配合私有字段 # 实现真封装
│   ├── 静态访问器 static get/set
│   └── 继承中的覆盖 super.get()
│
├── 陷阱与注意事项
│   ├── defineProperty 默认 enumerable:false
│   ├── 递归调用栈溢出（getter 内读自身）
│   ├── 下划线约定 ≠ 真正私有（用 # 解决）
│   ├── JSON.stringify 忽略访问器（用 toJSON 解决）
│   └── getter 不应有副作用
│
└── 最佳实践
    ├── 验证/计算/兼容/通知 → 用访问器
    ├── 简单数据存取 → 用数据属性
    ├── getter 纯读取、setter 快速失败
    ├── 内部存储用 _ 或 # 命名
    └── 性能敏感路径慎用 getter
```
