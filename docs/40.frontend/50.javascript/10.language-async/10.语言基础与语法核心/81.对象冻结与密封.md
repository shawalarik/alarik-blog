# 对象冻结与密封 —— freeze、seal、preventExtensions 的三级锁定机制

> **核心内容**：JavaScript 对象不可变性（Immutability）的三级锁定机制完整解析——`Object.preventExtensions`/`Object.seal`/`Object.freeze` 的精确行为差异与底层实现原理、每个方法对属性描述符的具体影响、对应的检测方法、浅冻结陷阱与深递归冻结方案（含循环引用处理）、实际工程应用场景（常量定义/配置保护/状态快照/纯函数优化）、性能影响分析以及与 Proxy/Immutable.js 等方案的对比。

## 一、为什么需要对象锁定？

### 1.1 JavaScript 对象的"过于自由"

在 JavaScript 中，对象是极其灵活的数据结构。你可以随时给它添加新属性、删除已有属性、修改任何属性的值——甚至修改从原型继承来的东西。这种灵活性在开发初期非常方便，但随着项目规模的增长，它也变成了**意外数据损坏的温床**：

```javascript
// 一个简单的配置对象
const config = {
  API_URL: 'https://api.example.com',
  TIMEOUT: 5000,
  MAX_RETRIES: 3
};

// 三个月后，某个新同事写的代码不小心改了它：
config.TIMEOUT = 99999999;     // 调试时忘了改回来
config.DEBUG_MODE = true;      // 加了个调试开关，上线时也没删
delete config.MAX_RETRIES;     // 某次重构时不小心删了

// 结果：生产环境出现超长超时 + 调试信息泄露 + 无限重试
// 这种 bug 极难排查——因为问题出在"有人改了不该改的东西"
```

这类问题的本质在于：**JavaScript 默认假设所有对象都是"可变的公共资源"，没有任何内置的保护机制**。就像一个没有门锁的房间——任何人都能进去搬家具、扔垃圾或者把重要的文件拿走。

### 1.2 三级锁定的设计哲学

ECMAScript 规范提供了三个层级的方法来限制对象的"可变程度"。它们的设计遵循了一个**渐进增强**的原则：每一级都在上一级的基础上增加更多的限制。

让我们用一栋建筑的安保系统来类比这三个级别：

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   Level 3: 🧊 冻结 (freeze)                          │
│   ─────────────────────────────                      │
│   整个房间变成博物馆展品                               │
│   ❌ 不能搬进新家具                                    │
│   ❌ 不能搬走现有物品                                  │
│   ❌ 不能移动/修改任何物品的位置                       │
│   一切都固定在原位，只能看不能动                        │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   Level 2: 🔒 密封 (seal)                             │
│   ─────────────────────                              │
│   房间被封起来了                                      │
│   ❌ 不能搬进新家具                                    │
│   ❌ 不能搬走现有物品                                  │
│   ✅ 但可以调整已有家具的位置（修改值）                 │
│   门和窗户都钉死了，但室内还能活动                     │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   Level 1: 🚫 阻止扩展 (preventExtensions)            │
│   ────────────────────────────────────               │
│   门上贴了"禁止入内"的告示                            │
│   ❌ 不能搬进新家具                                    │
│   ✅ 可以搬走现有物品                                  │
│   ✅ 可以移动/修改已有物品                             │
│   只是不能再往里加东西了                               │
│                                                      │
├──────────────────────────────────────────────────────┤
│                                                      │
│   Level 0: 🔓 普通对象                                │
│   ──────────────                                     │
│   完全开放的仓库                                       │
│   ✅ 随意添加新物品                                    │
│   ✅ 随意移除物品                                      │
│   ✅ 随意修改任何物品                                  │
│   JavaScript 对象的默认状态                           │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 1.3 三级方法的快速总览

| 维度 | `preventExtensions` | `seal` | `freeze` |
|------|:-:|:-:|:-:|
| **能否添加新属性？** | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |
| **能否删除已有属性？** | ✅ 可以 | ❌ **禁止** | ❌ **禁止** |
| **能否修改属性值？** | ✅ 可以 | ✅ **可以** | ❌ **禁止** |
| **对 configurable 的影响** | 不改变 | 全部 → `false` | 全部 → `false` |
| **对 writable 的影响** | 不改变 | **不改变** | 全部 → `false` |
| **检测方法** | `isExtensible()` | `isSealed()` | `isFrozen()` |
| **严格模式违规后果** | `TypeError` | `TypeError` | `TypeError` |

> **记忆口诀**："**扩密冻**"——扩展被阻止、密封不能删、冻结全不行。

## 二、Level 1 —— preventExtensions（阻止扩展）

### 2.1 基本行为

`Object.preventExtensions(obj)` 是最基础的锁定操作。它的作用只有一个：**让对象永远无法再添加新的属性**。已有的属性不受任何影响。

```javascript
const room = {
  desk: "办公桌",
  chair: "椅子",
  lamp: "台灯"
};

console.log(Object.isExtensible(room)); // true ← 初始状态下可扩展

Object.preventExtensions(room);

console.log(Object.isExtensible(room)); // false ← 已经不可扩展了
```

### 2.2 具体效果演示

```javascript
'use strict';

const room = { desk: 1, chair: 2 };

Object.preventExtensions(room);

// ====== 效果 1：无法添加新属性 ======
room.lamp = 3;
// 💥 TypeError: Cannot add property lamp, object is not extensible
//
// 非 strict 模式下：静默失败（不会报错，但属性也不会被添加）
// room.lamp === undefined

// ====== 效果 2：可以修改已有属性 ======
room.desk = 2;           // ✓ 成功
room.chair = "转椅";     // ✓ 成功
console.log(room);       // { desk: 2, chair: "转椅" }

// ====== 效果 3：可以删除已有属性 ======
delete room.desk;        // ✓ 成功
console.log(room);       // { chair: "转椅" }

// ====== 效果 4：Object.defineProperty 也不能添加新属性 ======
Object.defineProperty(room, 'window', {
  value: '落地窗',
  enumerable: true,
  writable: true,
  configurable: true
});
// 💥 TypeError: Cannot define property window,
//    object is not extensible
//
// 注意！即使是 defineProperty 也被拦住了
// 因为 preventExtensions 在最底层拦截了一切"新增属性"的尝试
```

### 2.3 底层原理

`Object.preventExtensions(obj)` 做的事情其实非常简单——它在对象内部设置了一个标记 `[[Extensible]] = false`。之后每当引擎尝试给这个对象添加新属性时，都会先检查这个标记，如果是 false 就拒绝操作。

```javascript
// 等价的底层伪代码：
function preventExtensions(obj) {
  obj.[[Extensible]] = false;  // 设置内部标记
  return obj;
}
```

**重要细节**：`preventExtensions` 只影响**对象自身**，不影响其原型链上的对象。你仍然可以通过修改原型来间接地"添加"可访问的属性（虽然不是添加到当前对象上）：

```javascript
const proto = { inherited: "来自原型" };
const obj = { own: "自有" };
Object.setPrototypeOf(obj, proto);
Object.preventExtensions(obj);

obj.newProp = "试试";        // ❌ 自身不能添加
proto.shared = "共享";        // ✓ 但原型可以改！
console.log(obj.shared);      // "共享" ← 通过原型链访问到了
console.log(obj.hasOwnProperty('shared')); // false ← 但不是自身的属性
```

### 2.4 使用场景

`preventExtensions` 最典型的使用场景是**在初始化完成后"封死"对象的结构**：

```javascript
function createFixedStructure(data) {
  const obj = { ...data };  // 先完成所有属性的初始化
  
  // 初始化完成后，锁定结构
  Object.preventExtensions(obj);
  
  return obj;
}

const user = createFixedStructure({ name: "Alice", age: 30 });

user.name = "Bob";     // ✓ 修改已有属性 OK
user.email = "...";    // ❌ 添加新属性被拒
// 这确保了 user 对象的结构永远不会偏离预期的形状
```

## 三、Level 2 —— seal（密封）

### 3.1 基本行为

`Object.seal(obj)` 是第二级锁定。它在 `preventExtensions` 的基础上增加了**禁止删除已有属性**的能力，并且会将所有现有属性的 `configurable` 标志统一设为 `false`。

换句话说：sealed 的对象是一个**结构完全固定的容器**——里面的东西不能增、不能减，但内容本身还可以变化。

```javascript
'use strict';

const box = {
  apple: "🍎",
  banana: "🍌",
  cherry: "🍒"
};

Object.seal(box);

console.log(Object.isSealed(box)); // true
```

### 3.2 具体效果演示

```javascript
'use strict';

const box = {
  itemA: "apple",
  itemB: "banana"
};

Object.seal(box);

// ====== 效果 1：不能添加新属性（同 preventExtensions）=====
box.itemC = "cherry";
// 💥 TypeError: Cannot add property itemC, object is not extensible

// ====== 效果 2：不能删除已有属性（新增能力！）======
delete box.itemA;
// 💥 TypeError: Cannot delete property 'itemA' of #[object Object]

// ====== 效果 3：可以修改已有属性的值（这是关键区别）======
box.itemA = "apricot";          // ✓ 成功
box.itemB = "blueberry";        // ✓ 成功
console.log(box.itemA);         // "apricot"

// ====== 效果 4：不能改变属性的特性标志 ======
// 因为 seal 把所有属性的 configurable 都设为了 false
Object.defineProperty(box, 'itemA', {
  writable: false               // 试图将 itemA 变为只读
});
// 💥 TypeError: Cannot redefine property: itemA
//
// 原因：configurable 为 false 时，几乎不能修改任何标志
// （唯一允许的操作是 writable: true → false）

// ====== 效果 5：writable 仍为 true 时可以继续赋值 ======
// seal 并不修改 writable 标志！
const descA = Object.getOwnPropertyDescriptor(box, 'itemA');
console.log(descA.writable);      // true ← 还是可写的
console.log(descA.configurable);  // false ← 但已不可配置
```

### 3.3 seal 的精确等价操作

`Object.seal(obj)` 实际上等价于以下两步操作的组合：

```javascript
// seal 的内部逻辑（简化版）：
function mySeal(obj) {
  // Step 1: 阻止扩展（禁止添加新属性）
  Object.preventExtensions(obj);
  
  // Step 2: 将所有自身属性的 configurable 设为 false
  for (const key of Object.getOwnPropertyNames(obj)) {
    const desc = Object.getOwnPropertyDescriptor(obj, key);
    
    if (desc.configurable) {
      Object.defineProperty(obj, key, {
        ...desc,
        configurable: false  // 锁住这个属性
      });
    }
  }
  
  return obj;
}
```

理解了这个等价关系后，你就明白为什么 sealed 对象**不能删除属性**了——因为删除操作（`[[Delete]]` 内部方法）会检查 `configurable` 标志，如果为 false 就拒绝执行。

### 3.4 seal 与 preventExtensions 的关键差异

很多人容易混淆这两个方法。它们的核心差异只有一点，但这一点的影响很大：

| 操作 | preventExtensions | seal |
|------|:-:|:-:|
| 添加新属性 | ❌ | ❌ |
| 删除已有属性 | ✅ **可以** | ❌ **不可以** |
| 修改属性值 | ✅ | ✅ |
| 修改属性标志 | ✅（如果 configurable 为 true） | ❌（全部 configurable 已为 false） |

**为什么 seal 要额外禁止删除？**

因为"删除属性"本质上是在**改变对象的结构**（shape）。如果你希望一个对象的"骨架"（有哪些属性）是完全固定的，那么既不允许新增也不允许删除才是合理的——这就是 seal 的设计意图。

**类比**：`preventExtensions` 像是贴了一张"满员"的告示——房间里的人不能再进来了，但里面的人还是可以出去的。`seal` 则像是把门焊死了——人既进不来也出不去，但屋里的人还是可以换座位（修改值）的。

## 四、Level 3 —— freeze（冻结）

### 4.1 基本行为

`Object.freeze(obj)` 是最高级别的锁定。它在 `seal` 的基础上进一步**禁止修改所有属性的值**（将 `writable` 也设为 `false`）。经过冻结的对象变成了一个**真正意义上的只读快照**——不能增、不能删、不能改。

```javascript
'use strict';

const constants = {
  APP_NAME: "MyApp",
  VERSION: "1.0.0",
  AUTHOR: "Alarik",
  MAX_CONNECTIONS: 100
};

Object.freeze(constants);

console.log(Object.isFrozen(constants)); // true
```

### 4.2 具体效果演示

```javascript
'use strict';

const frozenObj = {
  name: "Alice",
  score: 95,
  tags: ["js", "ts"]
};

Object.freeze(frozenObj);

// ====== 效果 1：不能添加新属性 ======
frozenObj.age = 30;
// 💥 TypeError: Cannot add property age,
//    object is not extensible

// ====== 效果 2：不能删除已有属性 ======
delete frozenObj.name;
// 💥 TypeError: Cannot delete property 'name'

// ====== 效果 3：不能修改属性值 ======
frozenObj.name = "Bob";
// 💥 TypeError: Cannot assign to read only property 'name'

frozenObj.score = 100;
// 💥 TypeError: Cannot assign to read only property 'score'

// ====== 效果 4：freeze 后的属性描述符 ======
const desc = Object.getOwnPropertyDescriptor(frozenObj, 'name');
console.log(JSON.stringify(desc, null, 2));
/*
{
  "value": "Alice",        ← 值被锁定了
  "writable": false,       ← 不可写
  "enumerable": true,      ← 可枚举（不变）
  "configurable": false    ← 不可配置
}
*/

// 所有属性都同时具有 writable:false 和 configurable:false
```

### 4.3 freeze 的精确等价操作

`Object.freeze(obj)` 等价于以下三步的组合：

```javascript
// freeze 的内部逻辑（简化版）：
function myFreeze(obj) {
  // Step 1: 阻止扩展
  Object.preventExtensions(obj);
  
  // Step 2: 将所有自身属性的 configurable 设为 false
  // Step 3: 将所有自身属性的 writable 设为 false
  for (const key of Object.getOwnPropertyNames(obj)) {
    const desc = Object.getOwnPropertyDescriptor(obj, key);
    
    Object.defineProperty(obj, key, {
      value: desc.value,
      enumerable: desc.enumerable,  // 保持原样
      writable: false,             // ← 新增：设为不可写
      configurable: false          // ← 设为不可配置
    });
  }
  
  // 注意：对于访问器属性（有 getter/setter 的），freeze 不会添加 writable
  // 因为访问器根本没有 writable 标志
  // freeze 只是将它们的 configurable 设为 false
  
  return obj;
}
```

### 4.4 访问器属性的冻结行为

这是一个容易被忽略的细微差别：`freeze` 对数据属性和访问器属性的处理方式略有不同：

```javascript
const mixed = {
  // 数据属性
  dataVal: 42,
  
  // 访问器属性
  get computed() { return this.dataVal * 2; },
  set computed(v) { this.dataVal = v / 2; }
};

Object.freeze(mixed);

// 数据属性：writable 变为 false，不能改值
mixed.dataVal = 999;
// 💥 TypeError: Cannot assign to read only property

// 访问器属性：configurable 变为 false，但 getter/setter 仍然工作！
console.log(mixed.computed);  // 84 ← getter 正常调用
mixed.computed = 200;         // setter 正常调用！
console.log(mixed.dataVal);   // 100 ← 被 setter 修改了！

// 但是你不能重新定义这个访问器属性
Object.defineProperty(mixed, 'computed', {
  get() { return 0; }         // 试图替换 getter
});
// 💥 TypeError: Cannot redefine property
// 因为 configurable 已经是 false 了
```

**关键结论**：freeze 会阻止你对访问器属性**重新定义或删除**，但**不会阻止 getter/setter 本身的正常工作**。这意味着如果一个访问器属性的 setter 会修改其他数据属性的值，那么即使对象已被冻结，通过写入这个访问器属性仍然可能间接地改变对象的状态。

### 4.5 Math.PI —— 天然冻结的范例

JavaScript 引擎中的一些内置常量就是通过 freeze 机制的原理实现的：

```javascript
const piDesc = Object.getOwnPropertyDescriptor(Math, 'PI');

console.log(piDesc);
// {
//   value: 3.141592653589793,
//   writable: false,      ← 不可写
//   enumerable: false,    ← 不可枚举
//   configurable: false   ← 不可删除、不可重定义
// }

Math.PI = 3;              // 静默失败（非严格模式）
Math.PI;                  // 仍然是 3.141592653589793

delete Math.PI;           // 静默失败
Math.PI;                  // 仍然是原来的值

Object.defineProperty(Math, 'PI', { value: 4 });  // TypeError
```

`Math.PI` 就是一个完美的**冻结式常量**——它的值不可变、不可删、不可重新定义。如果你想在自己的代码中创建类似的常量，可以用同样的方式：

```javascript
// 创建一个类似 Math.PI 的常量对象
const AppConstants = Object.freeze({
  VERSION: '2.0.0',
  API_BASE_URL: 'https://api.example.com',
  DEFAULT_TIMEOUT: 5000,
  ENVIRONMENT: process.env.NODE_ENV || 'development'
});

AppConstants.VERSION = '9.9.9';  // 改不了
delete AppConstants.API_BASE_URL; // 删不了
AppConstants.DEBUG = true;        // 加不了

// 常量对象本身也是不可变的
console.log(AppConstants.VERSION);  // '2.0.0' — 安全可靠
```

## 五、⚠️ 浅冻结（Shallow Freeze）陷阱

### 5.1 什么是浅冻结？

`Object.freeze()` 是一个**浅操作（Shallow Operation）**——它只会冻结对象的第一层属性。如果某个属性值本身又是一个对象或数组，那个内部的嵌套对象**不会被自动冻结**。

这是一个极其常见且危险的陷阱：

```javascript
const config = Object.freeze({
  database: {
    host: "localhost",
    port: 3306,
    credentials: {
      username: "admin",
      password: "secret123"
    }
  },
  
  features: ["auth", "logging", "caching"]
});

// 第一层确实被冻结了
config.database = { host: "evil.com" };  // ❌ TypeError ✓ 保护有效
config.features = [];                     // ❌ TypeError ✓ 保护有效

// ⚠️ 但是！嵌套的对象并没有被保护！！
config.database.host = "evil.com";       // ✅ 居然成功了！！！
config.database.port = 9999;             // ✅ 也成功了！！！
config.database.credentials.username = "hacker"; // ✅ 还能成功！！！
config.features.push("malicious");       // ✅ 数组也被修改了！！！

console.log(config.database.host);       // "evil.com"     ← 😱 被篡改
console.log(config.database.port);       // 9999            ← 😱 被篡改
console.log(config.credentials.username); // "hacker"        ← 😱 被篡改
console.log(config.features);            // ["auth","logging","caching","malicious"] ← 😱
```

**为什么会这样？**

因为 `freeze` 只遍历对象自身的直接属性并设置它们的描述符标志。当它遇到 `database` 这个属性时，它做的是：

```javascript
// freeze 对 database 这个属性做的事情：
Object.defineProperty(config, 'database', {
  value: config.database,       // 值保持不变（还是指向同一个对象引用）
  writable: false,              // 不能替换整个 database 对象
  configurable: false           // 不能删除 database 属性
});
```

注意：它只是**锁住了 `database` 这个槽位**——让你不能用另一个对象来替换它。但 `database` 所指向的那个**内部对象本身**并没有被冻结。这就像是把你家门锁上了（不能换门），但门里面的房间还是可以随便进出。

### 5.2 深冻结（Deep Freeze）的实现

要彻底解决浅冻结的问题，我们需要递归地冻结所有层级的嵌套对象：

```javascript
/**
 * 深度冻结对象——递归冻结所有层级的嵌套对象和数组
 * 
 * @param {object} obj - 要冻结的对象
 * @param {WeakSet} [visited] - 用于检测循环引用（内部使用）
 * @returns {object} 冻结后的同一对象引用
 */
function deepFreeze(obj, visited = new WeakSet()) {
  // 第一步：基本类型和非对象直接返回
  if (obj === null || typeof obj !== 'object') {
    return obj;
  }
  
  // 第二步：防止循环引用导致的无限递归
  if (visited.has(obj)) {
    return obj; // 已经处理过了，跳过
  }
  visited.add(obj);
  
  // 第三步：获取所有属性名（包括不可枚举的 Symbol 属性）
  const allKeys = [
    ...Object.getOwnPropertyNames(obj),
    ...Object.getOwnPropertySymbols(obj)
  ];
  
  // 第四步：递归冻结每个属性值
  for (const key of allKeys) {
    const value = obj[key];
    
    // 如果属性值是对象（包括数组和普通对象）且还没冻结
    if (value !== null && typeof value === 'object' && !Object.isFrozen(value)) {
      deepFreeze(value, visited); // 递归！
    }
  }
  
  // 第五步：冻结当前对象本身
  return Object.freeze(obj);
}
```

**使用效果对比**：

```javascript
// 用 deepFreeze 替代 Object.freeze
const secureConfig = deepFreeze({
  database: {
    host: "localhost",
    port: 3306,
    credentials: { username: "admin", password: "secret123" }
  },
  features: ["auth", "logging", "caching"]
});

// 现在——所有层级都被保护了
secureConfig.database.host = "evil.com";       // ❌ TypeError ✅
secureConfig.database.port = 9999;             // ❌ TypeError ✅
secureConfig.credentials.password = "hacked";  // ❌ TypeError ✅
secureConfig.features.push("bad");             // ❌ TypeError ✅

// 彻底安全！
```

### 5.3 深冻结的关键技术细节

#### 细节一：循环引用的处理

如果对象中存在循环引用（A 引用 B，B 又引用 A），普通的递归会陷入死循环导致栈溢出。`deepFreeze` 使用 `WeakSet` 来记录已经访问过的对象，从而安全地处理循环引用：

```javascript
// 循环引用的场景
const a = { name: "A" };
const b = { name: "B" };
a.ref = b;  // a 引用 b
b.ref = a;  // b 又引用 a —— 循环！

deepFreeze(a);  // 有了 WeakSet 追踪，不会死循环

a.name = "changed";   // ❌ TypeError ✓
b.name = "changed";   // ❌ TypeError ✓
a.ref.name = "hack";  // ❌ TypeError ✓
```

#### 细节二：Symbol 属性也不放过

`Object.getOwnPropertySymbols()` 确保以 Symbol 为键的属性也会被递归冻结：

```javascript
const sym = Symbol('secret');
const obj = {
  normal: { nested: true },
  [sym]: { hidden: true }
};

deepFreeze(obj);
obj[sym].hidden = false; // ❌ TypeError ✓
```

#### 细节三：数组的特殊处理

数组在 JavaScript 中本质上也是对象，所以 `deepFreeze` 同样适用。但要注意冻结后的数组不能再用 `push`/`pop`/`splice` 等方法修改：

```javascript
const list = deepFreeze([1, 2, 3, { inner: "value" }]);
list.push(4);          // ❌ TypeError
list.pop();             // ❌ TypeError
list[0] = 999;          // ❌ TypeError
list[3].inner = "hacked"; // ❌ TypeError（深层也被冻结）
```

#### 细节四：Date、RegExp、Map、Set 等特殊对象

这些特殊类型的"内部状态"无法通过 `Object.freeze` 来保护：

```javascript
const frozenDate = Object.freeze(new Date('2024-01-01'));
frozenDate.setFullYear(2099);  // ✅ 竟然成功了！
console.log(frozenDate.getFullYear()); // 2099 —— Date 的内部值变了

// 原因：Date 的内部 [[DateValue]] 不是普通的属性，
// freeze 只能冻结对象的自有属性，管不到内部插槽
```

对于这类特殊对象，如果需要真正的不可变性，通常需要在更高层面进行处理（如封装成类并提供只读接口）。

## 六、三种方法的完整行为矩阵

### 6.1 操作 × 方法的结果表

下表展示了每种操作在每个锁定级别下的结果（假设处于**严格模式**）：

| 操作 | 普通对象 | preventExtensions | seal | freeze |
|------|:-:|:-:|:-:|:-:|
| `obj.newProp = v` | ✅ 添加成功 | ❌ **TypeError** | ❌ **TypeError** | ❌ **TypeError** |
| `delete obj.prop` | ✅ 删除成功 | ✅ **成功** | ❌ **TypeError** | ❌ **TypeError** |
| `obj.prop = newValue` | ✅ 修改成功 | ✅ **成功** | ✅ **成功** | ❌ **TypeError** |
| `Object.defineProperty(...)` 添加 | ✅ 成功 | ❌ **TypeError** | ❌ **TypeError** | ❌ **TypeError** |
| `defineProperty` 修改标志 | ⚠️ 取决于 configurable | ⚠️ 取决于 configurable | ❌ **TypeError** | ❌ **TypeError** |
| `defineProperty` writable:true→false | ✅ 成功 | ✅ 成功 | ✅ **成功** | ❌ **TypeError** |
| `__proto__` 赋值 | ✅ 成功 | ⚠️ 可能失败 | ❌ 失败 | ❌ 失败 |
| `isExtensible()` | `true` | `false` | `false` | `false` |
| `isSealed()` | `false` | `false` | `true` | `true` |
| `isFrozen()` | `false` | `false` | `false*` | `true` |

\*注：如果 seal 后的所有属性恰好都是 `writable: false`（比如全是访问器属性），则 `isFrozen()` 也会返回 `true`。

### 6.2 检测方法的精确定义

#### `Object.isExtensible(obj)`

判断对象是否还可以添加新属性。等价于检查内部标记 `[[Extensible]]` 是否为 `true`。

```javascript
const obj = {};
console.log(Object.isExtensible(obj)); // true

Object.preventExtensions(obj);
console.log(Object.isExtensible(obj)); // false

// 注意：seal 和 freeze 都会让 isExtensible 返回 false
Object.seal(obj);  // 或 Object.freeze(obj)
console.log(Object.isExtensible(obj)); // false
```

#### `Object.isSealed(obj)`

判断对象是否被密封。判断条件有两个：
1. `isExtensible(obj) === false`
2. **所有自身属性**的 `configurable` 都是 `false`

```javascript
const obj = { a: 1, b: 2 };

Object.preventExtensions(obj);
console.log(Object.isSealed(obj)); 
// false ← 虽然 isExtensible 为 false，但属性的 configurable 还是 true

Object.seal(obj);
console.log(Object.isSealed(obj));
// true ← isExtensible 为 false 且所有属性 configurable 为 false

// 特殊情况：空对象
const empty = {};
Object.preventExtensions(empty);
console.log(Object.isSealed(empty));
// true ← 没有任何属性 → "所有属性的 configurable 都是 false" 自动成立
```

#### `Object.isFrozen(obj)`

判断对象是否被冻结。判断条件有三个：
1. `isExtensible(obj) === false`
2. **所有自身属性**的 `configurable` 都是 `false`
3. **所有自身数据属性**的 `writable` 都是 `false`（访问器属性不参与此条件）

```javascript
const obj = { a: 1, get computed() { return this.a * 2; } };

Object.seal(obj);
console.log(Object.isFrozen(obj));
// false ← a 的 writable 还是 true

Object.freeze(obj);
console.log(Object.isFrozen(obj));
// true ← 所有条件满足

// 特殊情况：全是访问器属性的对象 seal 后就等于 frozen
const accessorOnly = {
  get x() { return 1; },
  get y() { return 2; }
};
Object.seal(accessorOnly);
console.log(Object.isFrozen(accessorOnly));
// true ← 没有 writable 的数据属性 → frozen 条件自动满足
```

## 七、实际应用场景

### 7.1 场景一：应用常量配置

```javascript
// config/constants.js
export const CONFIG = Object.freeze({
  // 环境相关
  ENVIRONMENT: import.meta.env.MODE,
  API_BASE_URL: import.meta.env.VITE_API_URL,
  
  // 业务常量
  ITEMS_PER_PAGE: 20,
  MAX_UPLOAD_SIZE_MB: 50,
  SESSION_TIMEOUT_MIN: 30,
  
  // 功能开关
  FEATURES: Object.freeze({
    DARK_MODE: true,
    NOTIFICATIONS: true,
    ANALYTICS: false
  }),
  
  // 错误码映射
  ERROR_CODES: Object.freeze({
    UNAUTHORIZED: 401,
    FORBIDDEN: 403,
    NOT_FOUND: 404,
    SERVER_ERROR: 500
  })
});

// 任何地方都可以安全地导入使用
import { CONFIG } from './constants';

// 不用担心被意外修改
CONFIG.MAX_UPLOAD_SIZE_MB = 999999; // 无效
CONFIG.FEATURES.ANALYTICS = true;   // 无效（嵌套也被 freeze 了）
```

**为什么不用 `const`？** `const` 只能保证变量引用不被重新赋值（`CONFIG = somethingElse` 会报错），但不能防止 `CONFIG.someProp = newValue` 这样的属性修改。`Object.freeze` 则是从**对象本身**层面进行保护。

### 7.2 场景二：Redux/Vuex Store 的状态快照

在现代前端框架中，状态的不可变性是非常重要的原则。`freeze` 可以帮助你在开发阶段检测意外的状态变更：

```javascript
// Redux 开发工具中的典型用法（简化版）
const devToolsMiddleware = store => next => action => {
  
  // 在 dispatch 之前，冻结当前状态用于比较
  const prevState = deepFreeze(
    JSON.parse(JSON.stringify(store.getState()))
  );
  
  const result = next(action);
  
  const nextState = store.getState();
  
  // 如果 reducer 中直接修改了 prevState（而不是返回新状态）
  // 这里就会抛出错误——帮助我们尽早发现 bug
  console.assert(
    prevState !== nextState && 
    !Object.is(prevState, nextState),
    '⚠️ Reducer 不应该直接修改状态！请返回新的状态对象。'
  );
  
  return result;
};
```

### 7.3 场景三：纯函数参数保护

当你编写一个不应该有副作用的纯函数时，可以用 `freeze` 来确保调用者不会意外传入被修改的对象：

```javascript
function calculateTotal(items) {
  // 防御性编程：冻结参数以确保函数内外的隔离
  // （生产环境中可能只在 development 模式下启用）
  if (process.env.NODE_ENV === 'development') {
    Object.freeze(items);
  }
  
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

const shoppingCart = [
  { name: "Book", price: 30, quantity: 2 },
  { name: "Pen", price: 5, quantity: 5 }
];

calculateTotal(shoppingCart);

// 如果 calculateTotal 内部不小心做了 items[0].price = 0
// 开发模式下这里会报错，帮助我们定位问题
```

### 7.4 场景四：防御性复制（Defensive Copy）

当你的库需要对外暴露一些内部数据，但你不想让外部代码修改它们时：

```javascript
class SecureVault {
  #secrets = new Map();

  setSecret(key, value) {
    this.#secrets.set(key, value);
  }

  // 返回一个冻结的副本——外部拿到的是只读视图
  getSecretsSnapshot() {
    const snapshot = Object.fromEntries(this.#secrets);
    return Object.freeze(snapshot);
  }

  // 或者返回深冻结版本
  getDeepSecretsSnapshot() {
    const snapshot = JSON.parse(JSON.stringify([...this.#secrets]));
    return deepFreeze(snapshot);
  }
}

const vault = new SecureVault();
vault.setSecret('apiKey', 'sk-abc123');
vault.setSecret('dbPassword', 'p@ssw0rd');

const publicView = vault.getSecretsSnapshot();
publicView.apiKey = "stolen";  // ❌ 无效
publicView.dbPassword = "hacked"; // ❌ 无效
// 外部代码无法修改返回的数据
```

### 7.5 场景五：switch/case 和查找表的不可变性

```javascript
  '/home': () => import('./pages/Home.vue'),

// HTTP 状态码消息映射

});

// 这些映射表在整个应用生命周期中都应该是只读的
```

## 八、性能影响分析

### 8.1 V8 引擎中的优化

你可能担心频繁使用 `freeze`/`seal`/`preventExtensions` 会对性能产生负面影响。实际上情况恰恰相反——**告诉引擎"这个对象不会再变了"，反而能让引擎做出更好的优化**。

V8 引擎（Chrome/Node.js 使用的 JS 引擎）有几个关键的优化依赖于对象的"不变性"假设：

| 优化类型 | 说明 | 需要的条件 |
|---------|------|-----------|
| **Hidden Class 稳定** | 对象的"形状"不再变化，V8 可以用更高效的属性访问路径 | `preventExtensions` 或更高级别 |
| **内联缓存（IC）稳定** | 属性查找可以被缓存，不需要每次都查原型链 | `seal`（属性数量和类型固定） |
| **去虚拟化** | 如果确定对象的结构不变，某些操作可以跳过额外的检查 | `freeze`（完全不可变） |

### 8.2 基准测试参考

以下是一些粗略的性能特征（具体数字取决于引擎版本和硬件）：

```javascript
// Object.freeze 本身的开销
const obj = { x: 1, y: 2, z: 3 };
console.time('freeze');
for (let i = 0; i < 100000; i++) {
  Object.freeze({ x: 1, y: 2, z: 3 });
}
console.timeEnd('freeze'); // 通常几十毫秒级别（10万次）

// freeze 后的属性访问 vs 普通对象
const frozen = Object.freeze({ a: 1, b: 2, c: 3 });
const normal = { a: 1, b: 2, c: 3 };

console.time('frozen access');
for (let i = 0; i < 10000000; i++) { frozen.a; }
console.timeEnd('frozen access'); // 通常比 normal 更快或持平

console.time('normal access');
for (let i = 0; i < 10000000; i++) { normal.a; }
console.timeEnd('normal access');
```

### 8.3 deepFreeze 的性能注意事项

`deepFreeze` 由于需要递归遍历所有嵌套对象，其时间复杂度取决于对象的总属性数量。对于特别大或特别深的对象，可能会带来明显的性能开销：

```javascript
// 建议：仅在初始化时调用一次 deepFreeze
// 不要在热路径（高频执行的代码）中反复调用

// ✅ 好的做法：应用启动时一次性冻结配置
const APP_CONFIG = deepFreeze(loadConfiguration());

// ❌ 不好的做法：每次渲染前都重新冻结
function render(data) {
  const frozen = deepFreeze(data); // 每次都递归冻结——太慢了
  // ...
}

// ✅ 更好的做法：在数据进入框架之前就冻结
const initialState = deepFreeze(reducer(undefined, {}));
// 之后确保 reducer 总是返回新的冻结对象
```

### 9.2 Proxy 方案示例

如果你需要比 `freeze` 更灵活的控制（如自定义错误消息、部分属性例外等），Proxy 是一个强大的替代方案：

```javascript
function createReadOnlyProxy(target) {
  return new Proxy(target, {
    set(obj, prop, value) {
      console.warn(`⚠️ 尝试修改只读属性 "${String(prop)}"`);
      return false; // 拦截写入
    },

    deleteProperty(obj, prop) {
      console.warn(`⚠️ 尝试删除只读属性 "${String(prop)}"`);
      return false; // 拦截删除
    },

    defineProperty(obj, prop, desc) {
      console.warn(`⚠️ 尝试定义属性 "${String(prop)}"`);
      return false; // 拦截 defineProperty
    },

    // 但允许读取
    get(obj, prop) {
      return Reflect.get(obj, prop);
    }
  });
}

const config = createReadOnlyProxy({
  api: 'https://api.example.com',
  timeout: 5000
});

config.timeout = 99999;
// 控制台：⚠️ 尝试修改只读属性 "timeout"
// 不会报错，只是静默拦截 + 警告

console.log(config.timeout); // 5000（值没变）
```

Proxy 的优势是可以**精细化控制**哪些操作被允许、哪些被拦截，甚至可以为不同的属性设置不同的规则。缺点是需要更多的运行时代码，且在极端性能敏感场景下可能有额外的间接调用开销。

## 十、最佳实践总结

### 10.1 选择指南

```
你需要什么程度的保护？
│
├── 只是防止意外添加新属性
│   └──→ Object.preventExtensions()
│
├── 需要固定的"属性列表"（不能增不能删）
│   └──→ Object.seal()
│
├── 需要完全只读的对象
│   ├── 只有第一层需要保护
│   │   └──→ Object.freeze()
│   └── 有嵌套对象需要一起保护
│       └──→ deepFreeze()（自定义递归实现）
│
├── 需要在拦截时做自定义逻辑（如日志/警告/白名单）
│   └──→ Proxy
│
└── 大型应用的复杂状态管理
    └──→ Immutable.js 或 Immer
```

### 10.2 最佳实践清单

```javascript
// ✅ 1. 应用启动时一次性冻结全局配置
const CONFIG = deepFreeze(readConfigFile());

// ✅ 2. 导出的常量对象始终 freeze
export const CONSTANTS = Object.freeze({ ... });

// ✅ 3. 开发环境下用 freeze 辅助调试纯函数
if (process.env.NODE_ENV === 'dev') {
  Object.freeze(inputData);
}

// ✅ 4. 公开 API 返回冻结副本防止外部篡改
getPublicState() {
  return Object.freeze({ ...this.#privateState });
}

// ✅ 5. 构造函数完成后立即 seal/freeze 类实例的不变部分
class User {
  constructor(id, name) {
    this.id = id;       // ID 一旦设定就不应该变
    this.name = name;
    Object.seal(this);  // 锁定结构，name 还能改但 id 不能被删除
  }
}

// ❌ 1. 不要在热路径上重复调用 deepFreeze
// ❌ 2. 不要指望 freeze 能保护 Date/RegExp/Map 等特殊对象的内部状态
// ❌ 3. 不要混淆 const（变量引用保护）和 freeze（对象属性保护）
// ❌ 4. 忘记处理循环引用的 deepFreeze 会在循环引用时栈溢出
// ❌ 5. freeze 后的数组不能用 push/pop/splice——要用展开运算符创建新数组
```

## 十一、知识图谱

```
JavaScript 对象冻结与密封完整体系
│
├── 为什么需要锁定？
│   ├── JS 对象默认"过于自由"——任何人随时可增删改
│   ├── 意外数据损坏的温床（配置被篡改、常量被覆盖）
│   └── 三级渐进式锁定：每级在上层基础上加强限制
│
├── Level 1: preventExtensions（阻止扩展）
│   ├── 行为：仅禁止添加新属性
│   ├── 底层：设置 [[Extensible]] = false
│   ├── 已有属性：✅ 可修改、可删除
│   ├── detect: Object.isExtensible() → false
│   └── 场景：初始化完成后固定对象结构
│
├── Level 2: seal（密封）
│   ├── 行为 = preventExtensions + 所有属性 configurable:false
│   ├── 已有属性：✅ 可修改值、❌ 不可删除、❌ 不可改标志
│   ├── 底层等价：
│   │   ① Object.preventExtensions(obj)
│   │   ② 每个 prop: { configurable: false }
│   ├── detect: Object.isSealed() → true
│   └── 类比：门焊死了（不能进出），但室内可活动（可改值）
│
├── Level 3: freeze（冻结）
│   ├── 行为 = seal + 所有数据属性 writable:false
│   ├── 已有属性：❌ 不可修改、❌ 不可删除、❌ 不可新增
│   ├── 底层等价：
│   │   ① Object.preventExtensions(obj)
│   │   ② 每个 prop: { configurable: false, writable: false }
│   ├── 访问器属性的特殊性：
│   │   └── configurable:false 但 getter/setter 仍正常工作
│   ├── detect: Object.isFrozen() → true
│   └── 类比：博物馆展品（只能看不能动）
│
├── ⚠️ 浅冻结陷阱
│   ├── Object.freeze 只冻结第一层
│   ├── 嵌套对象/数组内部仍可被修改
│   ├── 解决方案：deepFreeze() 递归实现
│   │   ├── WeakSet 防止循环引用
│   │   ├── 包含 Symbol 属性
│   │   └── 数组同样生效
│   └── 特殊对象限制：Date/RegExp/Map/Set 的内部状态不受保护
│
├── 检测方法精确定义
│   ├── isExtensible: [[Extensible]] === true ?
│   ├── isSealed: !extensible && 所有属性 configurable === false
│   └── isFrozen: !extensible && 所有 configurable === false
│                && 所有数据属性 writable === false
│
├── 实际应用场景
│   ├── 应用常量配置（API_URL、VERSION 等）
│   ├── Redux/Vuex 状态快照与纯函数检测
│   ├── 纯函数参数防御性保护
│   ├── 防御性复制（公开 API 返回只读副本）
│   └── switch/case 路由映射表、HTTP 状态码表
│
├── 性能分析
│   ├── V8 引擎优化依赖不变性假设
│   ├── Hidden Class / IC / 去虚拟化
│   ├── freeze 本身开销小（~10万次/数十ms）
│   └── deepFreeze 仅应在初始化时调用一次
│
└── 方案对比
    ├── Object.freeze: 浅层、原生、高性能
    ├── deepFreeze: 深层、自实现、中等性能
    ├── Proxy: 高度可定制、灵活拦截
    ├── Immutable.js: 深层不可变、持久化数据结构
    └── Immer: 按需不可变、写时复制
```
