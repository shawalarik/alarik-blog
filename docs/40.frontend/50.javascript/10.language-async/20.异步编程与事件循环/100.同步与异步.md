# 同步与异步 —— 阻塞、非阻塞、单线程模型与事件循环机制

> **核心内容**：JavaScript 同步与异步编程的完整解析——为什么 JavaScript 是单线程的（历史原因与浏览器安全考量）、同步代码的阻塞问题与非阻塞的必要性、回调函数基础（同步回调 vs 异步回调）与回调地狱、Promise 三种状态生命周期、**Promise 链式调用机制与值传递规则**、async/await 语法糖原理与执行顺序、**事件循环（Event Loop）的完整运行算法**——宏任务队列与微任务队列的本质差异与优先级规则、渲染时机的精确定位，以及 setTimeout(0)/queueMicrotask/requestAnimationFrame 的行为差异。

## 一、为什么需要理解同步与异步？

### 1.1 一个令人困惑的现象

如果你写过一段时间的 JavaScript，你一定遇到过这样的困惑：

```javascript
console.log("第一步");

setTimeout(() => {
  console.log("第二步");
}, 0);

console.log("第三步");
```

直觉上你会期望输出顺序是：`第一步 → 第二步 → 第三步`。但实际输出却是：

```
第一步
第三步
第二步
```

明明 `setTimeout` 的延迟是 **0 毫秒**——字面意思就是"不要等待"，为什么"第二步"还是跑到了"第三步"的后面？这个反直觉的结果背后隐藏着 JavaScript 最核心也最容易被误解的概念之一：**同步与异步，以及驱动它们的事件循环机制**。

### 1.2 同步与异步的本质差异

让我们用一个最直观的生活场景来建立初步认知。

#### 场景：去餐厅点餐

**同步（Synchronous）模式——排队等餐**：

你走到柜台前点了一份牛排。厨师说："好的，请在这里等着。"于是你就站在柜台前面**死等**——不能玩手机，不能跟朋友聊天，不能做任何其他事情，直到厨师把牛排递到你手里。在此期间，整个队伍都在等你一个人。如果厨师做菜要花 10 分钟，那这 10 分钟里你什么也干不了。

```javascript
// 同步代码——"死等"模式
console.log("开始点餐");
const result = cookSteak(); // ⏳ 这里会卡住！程序停在这行不动了
                          //    直到 cookSteak 函数执行完毕
console.log("拿到牛排了:", result);
// 在 cookSteak 执行完之前，这行永远不会执行
```

**异步（Asynchronous）模式——叫号取餐**：

你走到柜台前点了牛排。厨师给了你一张小票说："好了会叫号。"然后你可以**去做其他事情了**——刷手机、和朋友聊天、甚至再点一杯饮料。当厨师做好后，他会喊你的号码（触发回调），你再过去取餐。

```javascript
// 异步代码——"叫号"模式
console.log("开始点餐");
cookSteakAsync((result) => {
  console.log("拿到牛排了:", result); // 牛排好了才执行这里
});
console.log("先去干别的"); // 不用等！这行立刻执行
```

#### 核心区别总结

| 维度 | 同步（Synchronous） | 异步（Asynchronous） |
|------|---------------------|----------------------|
| **等待方式** | 死等（阻塞 Blocking） | 先去忙别的（非阻塞 Non-blocking） |
| **控制权** | 调用者被挂起，无法做别的事 | 调用者立刻拿回控制权 |
| **执行顺序** | 一条道走到黑，必须等完才能继续 | 发起请求后继续往下走 |
| **时间效率** | 低（等待期间 CPU/线程资源浪费） | 高（等待期间可以做别的事） |
| **代码可读性** | 直观（执行顺序 = 书写顺序） | 稍复杂（执行顺序 ≠ 书写顺序） |
| **适用场景** | 快速完成的简单计算任务 | 耗时的 I/O 操作（网络、文件、定时器）|
| **生活类比** | 排队等餐（死等） | 叫号取餐（先去忙别的） |

**关键认知**：JavaScript 中的"异步"并不意味着多线程并行——它只是意味着**发起一个操作后不需要立即等待它完成**，而是通过某种机制（回调/Promise/事件循环）在操作完成后回来处理结果。这是单线程环境下的协作式多任务策略。

## 二、JavaScript 的单线程模型

### 2.1 为什么 JavaScript 是单线程的？

这是一个历史遗留的设计决策，但它并非没有道理。JavaScript 诞生于 1995 年（Brendan Eich 用 10 天设计出来的），当时的首要任务是**在网页中处理用户交互和 DOM 操作**——让按钮能点击、表单能提交、页面能动态变化。

想象一下这个场景：

如果 JavaScript 有多个线程同时操作同一个 DOM：
- **线程 A** 说："把这个元素的文字改成 'Hello'"
- **线程 B 同时说："把这个元素删除掉"**
- **线程 C 又说："给这个元素加个红色背景"**

三个指令同时发出，谁先谁后？DOM 应该变成什么样？结果完全取决于哪个线程最后执行——这就是典型的**竞态条件（Race Condition）**。就像三个人同时在同一张白纸上画画，最终画面会是混乱不堪的涂鸦。

所以 Brendan Eich 做出了那个影响深远的决定：**JavaScript 只有一个主线程来执行代码**。这意味着同一时间只能做一件事——从根本上杜绝了多线程操作 DOM 可能导致的混乱。

> **注意**：现代浏览器确实有多个线程（渲染线程、网络线程、GPU 线程等），但**执行 JavaScript 代码的永远只有一个线程**。Web Workers 可以创建额外的 JS 线程，但它们无法访问 DOM。

### 2.2 单线程的直接后果——阻塞

单线程虽然保证了安全性（不会有两个地方同时改同一个 DOM），但也带来了一个严重问题：**如果某个操作耗时很长，整个程序都会被"卡住"**。

```javascript
// 这是一个"灾难性"的同步阻塞示例
console.log("页面开始加载...");

// 模拟一个耗时3秒的网络请求（同步阻塞）
function syncFetchData() {
  const start = Date.now();
  while (Date.now() - start < 3000) {
    // 忙等待（busy-wait）——CPU 空转但什么都不做
    // 这相当于一个同步的 XMLHttpRequest 或巨大的计算任务
  }
  return "数据拿到了";
}

const data = syncFetchData(); // 💀 整个程序在这里卡住了3秒！
                              //    用户点击没反应、动画停止、页面冻结
console.log("数据:", data);

// 这3秒内发生的事情：
// ❌ 用户点击任何按钮 — 完全无反应
// ❌ CSS 动画 — 停止播放（卡在某一帧）
// ❌ 键盘输入 — 无法响应
// ❌ 浏览器可能弹出 "页面未响应" 警告对话框
// ❌ 用户可能会直接强制关闭标签页
```

**这就是"阻塞（Blocking）"的危害**——当一个耗时的同步操作占据着唯一的线程时，一切都得停下来等它完成。在浏览器环境中，这意味着 UI 完全冻结；在 Node.js 中，这意味着无法处理新的客户端请求（服务器对所有请求都无响应了）。

为什么会这样？因为 JavaScript 引擎只有一双手（一个线程）。当它的手正忙着做一个长达 3 秒的计算时，它没办法分出手来处理用户点击或绘制动画帧——就像一个餐厅只有一个服务员，当他被缠住给一张桌子算账时，新进来的客人就没人招呼了。

### 2.3 解决方案——异步非阻塞与事件循环

既然单线程不能真正"并行"做两件事（那是多线程做的事），那 JavaScript 怎么解决阻塞问题？答案是：**通过事件循环（Event Loop）实现"伪并行"——把耗时的操作委托给浏览器/Web API 在后台进行，主线程注册好回调后立刻继续处理其他事情，等后台完成了再把回调放入队列，由事件循环安排执行时机**。

```javascript
console.log("页面开始加载...");

// 异步非阻塞的数据获取
fetchDataAsync((data) => {     // 发起请求后立刻返回！不等待！
  console.log("数据:", data);   // 数据准备好了再执行这里（未来某个时刻）
});

console.log("页面可以继续响应了！"); // ← 这行立刻执行！不用等 fetchDataAsync
```

这段代码中，`fetchDataAsync` 做的事情是：告诉浏览器的网络模块"帮我去请求这个数据"，然后立刻返回。主线程不需要等网络模块工作完——它可以继续往下执行后面的代码。等网络数据真的回来了，浏览器会把回调函数放到任务队列里，事件循环会在适当的时机取出并执行。

**关键洞察**：JavaScript 并不是真的让两个任务同时运行（那是多线程做的事）。它做的是**在等待耗时操作的同时，切换去处理其他任务**——这就是所谓的**协作式多任务（Cooperative Multitasking）**。

回到餐厅的类比——这就像只有一个服务员的餐厅，但服务员很聪明：他接了单之后不会傻站在厨房门口等菜，而是先把小票贴在出菜口，然后转身去招呼新进来的客人、收拾桌子、倒水。等厨房喊"3号桌的菜好了"，他再去把菜端过去。这样虽然只有一个服务员，但整个餐厅的运转效率大大提高了。

## 三、回调函数 —— 异步编程的基础

### 3.1 什么是回调？

**回调函数（Callback Function）** 是一种将函数作为参数传递给另一个函数的模式。被传入的函数会在适当的时机被"回来调用（call back）"——通常是某个异步操作完成之后，或者满足某个条件的时候。

```javascript
// 最基本的回调示例
function greet(name, callback) {
  console.log(`你好, ${name}!`);
  callback(); // 在主逻辑完成后调用传入的函数
}

greet("Alice", function() {
  console.log("回调被执行了！");
});

// 输出：
// 你好, Alice!
// 回调被执行了！
```

**类比**：回调就像是**留下联系电话**——你告诉对方："事情办完了给我打电话。"对方在事情做完后拨通那个电话号码（调用你的回调函数传递结果）。你没有在那儿傻等（非阻塞），而是继续做自己的事，直到电话响了（回调被触发），你去接电话处理结果。

回调之所以能在异步场景下工作，是因为**函数在 JavaScript 中是一等公民（First-class Citizen）**——它可以像数字、字符串一样被赋值给变量、作为参数传递、作为返回值返回。这意味着你可以把"将来要做的事"打包成一个函数对象，交给别人保管，让他们在合适的时机帮你执行。

### 3.2 同步回调 vs 异步回调 —— 初学者最大的混淆点

这是初学者最容易混淆的概念之一。**回调本身不一定是异步的**——回调只是一种"把函数传进去让别人调用"的模式。关键是这个函数**什么时候被调用**：

```javascript
// ====== 同步回调 ======
// 回调在当前代码执行过程中就被调用了（没有任何延迟）
[1, 2, 3].forEach(function(item) {
  console.log(item); // forEach 内部同步地逐个调用每个回调
});
console.log("forEach 结束了");
// 输出顺序：1 → 2 → 3 → forEach 结束了
// 回调和后面的代码是"顺序执行"的，没有任何"跳跃"


// ====== 异步回调 ======
// 回调在未来某个时刻才被调用（由定时器、事件系统或 I/O 触发）
console.log("准备发请求");
setTimeout(function() {
  console.log("1秒后才执行的回调");
}, 1000);
console.log("不用等，我先走了");
// 输出顺序：
// 准备发请求          ← 立即执行
// 不用等，我先走了      ← 立刻执行！（不等 setTimeout）
// （约1秒后）1秒后才执行的回调  ← 延迟执行
```

**区分标准很简单**：看回调是在**当前执行栈清空之前**就被调用了（同步），还是在**之后的某个事件循环回合**才被调用（异步）。同步回调节奏紧凑——调用者还没返回呢，回调就已经跑完了；异步回调节奏有间隔——调用者早就返回了，回调还在队列里排队等着呢。

#### 为什么区分两者很重要？

因为它们对**执行顺序和性能**的影响截然不同：

```javascript
let arr = [1, 2, 3, 4, 5];

// forEach 是同步回调 —— 会阻塞后续代码
arr.forEach(item => {
  // 即使这里做了很重的操作
  heavyProcessing(item);  // 后面的代码必须等 forEach 完全结束
});
console.log("forEach 之后");  // 肯定在 forEach 全部完成后才执行

// setTimeout 是异步回调 —— 不阻塞
arr.forEach(item => {
  setTimeout(() => {
    heavyProcessing(item);  // 每个 item 的处理都是独立安排的
  }, 0);
});
console.log("所有 setTimeout 注册完毕");  // 立刻执行！不等内部回调
```

### 3.3 Error-first 回调风格 —— Node.js 的传统约定

Node.js 社区早期广泛使用的一种约定——回调的第一个参数专门用来传递错误信息：

```javascript
/**
 * Error-first Callback 规范（错误优先回调）：
 *
 * 设计哲学：
 * - 第一个参数：error（出错时有值，成功时为 null）
 * - 第二个及之后的参数：正常的结果数据
 *
 * 为什么这样设计？
 * 因为异步操作的失败不像同步代码那样可以用 try/catch 捕获。
 * 统一把 error 放第一个位置，让开发者每次都养成"先检查错误"的习惯。
 */

function readFile(path, callback) {
  // 模拟文件读取（有概率失败）
  const success = Math.random() > 0.3; // 70%概率成功

  if (success) {
    callback(null, "文件内容: Hello World!");
    // 成功时：第一个参数为 null（表示没有错误）
    //       第二个参数是实际数据
  } else {
    callback(new Error("文件不存在: " + path));
    // 失败时：第一个参数是 Error 对象
    //       第二个参数通常不存在（undefined）
  }
}

// 使用方式：每次都必须先检查第一个参数
readFile("/data.txt", function(error, data) {
  if (error) {                    // 第一步：检查是否有错
    console.error("出错了:", error.message);
    return;                       // 有错就处理，不继续
  }
  // 只有确认没错了才使用数据
  console.log(data);
});
```

这种风格的好处是统一的错误处理接口——无论什么异步操作，第一件事都是 `if (error)`。缺点是每次都要写样板化的错误检查代码，而且容易忘记处理错误。

### 3.4 回调地狱（Callback Hell） —— 厄运金字塔

当多个异步操作需要按顺序执行时（前一个的结果是后一个的输入），回调嵌套会变得越来越深，形成著名的"厄运金字塔"（也叫"毁灭三角洲"）：

```javascript
// 典型场景：获取用户信息 → 获取用户的朋友列表 → 获取朋友的最新动态
getUserInfo(userId, function(err, user) {
  if (err) {
    handleError(err);
  } else {
    getFriends(user.id, function(err, friends) {        // 第二层嵌套
      if (err) {
        handleError(err);
      } else {
        getPosts(friends[0].id, function(err, posts) {  // 第三层嵌套
          if (err) {
            handleError(err);
          } else {
            renderPosts(posts);
            // 如果还有更多步骤……继续往右缩进……
            // 第四层、第五层、第六层……
            // 每一层都要重复 if (err) 的错误处理
          }
        });
      }
    });
  }
});
```

这段代码的问题一目了然：

| 问题 | 说明 |
|------|------|
| **金字塔形状** | 代码不断向右缩进，很快就会超出编辑器的可视范围 |
| **错误处理重复** | 每一层都要写相同的 `if (err) { handleError(err); }` 样板代码 |
| **难以维护** | 要修改任何一个步骤的逻辑，需要深入到嵌套的最内部 |
| **调试困难** | 错误堆栈变得极其复杂，难以追踪问题的源头 |
| **流程不直观** | 代码从上到下的阅读顺序 ≠ 实际执行的时间顺序 |

有人尝试过用**拆分命名函数**的方式来缓解：

```javascript
loadScript('1.js', step1);

function step1(error, script) {
  if (error) { handleError(error); return; }
  loadScript('2.js', step2);
}

function step2(error, script) {
  if (error) { handleError(error); return; }
  loadScript('3.js', step3);
}

function step3(error, script) {
  if (error) { handleError(error); return; }
  // 所有脚本加载完毕
}
```

这样做消除了缩进金字塔，但带来了新的问题：**代码阅读体验断裂**——你需要在不同函数之间来回跳转才能理解完整的执行流程；而且这些一次性函数污染了全局作用域。

**这就是 Promise 和 async/await 登场的原因**——它们用更优雅的方式彻底解决了回调地狱问题。

## 四、Promise —— 异步操作的契约

### 4.1 什么是 Promise？

**Promise** 是 JavaScript 中用于表示一个**尚未完成但将来会完成（或失败）的操作结果**的对象。你可以把它理解为一份**"承诺书"或"订单小票"**——你现在拿到的不是最终的商品（结果），而是一张凭证（Promise 对象），凭这张凭证你可以在商品准备好之后取货（或者得知商品缺货了）。

**类比：歌手与粉丝的订阅模式**

| 角色 | 编程中的对应 | 生活类比 |
|------|-------------|---------|
| **生产者**（Executor）| 执行耗时任务的代码（网络请求、读文件、定时器） | 正在录音的歌手 |
| **消费者**（Handler）| 需要获取任务结果的代码（`.then()` 中的回调） | 等待新歌的粉丝 |
| **订阅名单**（Promise 对象）| 连接生产者和消费者的特殊对象 | 粉丝俱乐部的订阅清单 |

流程是这样的：
1. **粉丝订阅**（创建 Promise）：你说"出新歌了告诉我"
2. **歌手表演**（Executor 执行）：生产者代码开始工作（如发送 HTTP 请求）
3. **通知结果**（resolve/reject）：歌手完成后通知——成功了（resolve 新歌链接）或失败了（reject 录音设备坏了）
4. **粉丝收到消息**（.then/.catch）：根据结果做后续处理（听歌或显示错误提示）

### 4.2 Promise 的三种状态与生命周期

Promise 在其生命周期中只会处于以下三种状态之一，且状态转换遵循严格的单向规则：

```
┌─────────────────────────────────────────────┐
│           Promise 生命周期状态机               │
│                                             │
│   ┌───────────┐                             │
│   │  pending   │ ← 初始状态（等待中）         │
│   │  (待定)    │   结果尚未确定               │
│   └─────┬─────┘                             │
│         │                                   │
│     ┌───┴───┐  Executor 函数执行完毕后      │
│     │       │                               │
│     ▼       ▼                               │
│ ┌────────┐  ┌────────┐                      │
│ │fulfilled│  │rejected│                     │
│ │ 已兑现  │  │ 已拒绝  │                     │
│ │ 结果:value│  │ 原因:error│                   │
│ └────────┘  └────────┘                      │
│                                             │
│  ⚠️ 状态一旦改变就不可逆！（单向性）          │
│  ⚠️ resolve/reject 只有第一次有效！（幂等性）  │
│  ⚠️ fulfilled ↔ rejected 之间不能互转        │
└─────────────────────────────────────────────┘
```

三种状态的详细说明：

| 状态 | 含义 | 是否终态 | 结果值 |
|------|------|---------|--------|
| **pending（待定）** | 初始状态，异步操作正在进行中 | 否 | `undefined` |
| **fulfilled（已兑现）** | 操作成功完成 | ✅ 是 | `value`（任意值）|
| **rejected（已拒绝）** | 操作失败 | ✅ 是 | `reason`（通常是 Error）|

**状态的单向不可逆特性**非常重要——就像水结成冰后就再也变不回液态水一样（至少在这个 Promise 的上下文中如此）。这保证了消费者代码的行为是可以预测的——不会出现"一会儿成功一会儿失败"的反复横跳。

```javascript
// 状态单向性演示
const promise = new Promise(function(resolve, reject) {
  resolve("第一次成功!");     // ✅ 有效 — 状态变为 fulfilled
  reject(new Error("失败"));   // ❌ 被忽略 — 状态已定，不可更改
  resolve("第二次成功!");      // ❌ 被忽略 — 同上
  // 后续的所有 resolve/reject 调用都会被静默忽略
});

promise.then(console.log); // 只输出: "第一次成功!"
```

### 4.3 创建 Promise 与消费 Promise

**创建端（生产者角色）—— 使用 `new Promise()` 构造函数**：

```javascript
/**
 * new Promise(executor) 构造函数说明：
 *
 * executor 是一个函数，签名为：(resolve, reject) => void
 * - resolve(value): 将 Promise 状态改为 fulfilled，结果为 value
 * - reject(reason): 将 Promise 状态改为 rejected，原因为 reason
 *
 * 重要：executor 会在 new Promise() 被调用时【立即同步执行】！
 * 这不是异步的——异步的是 resolve/reject 的调用时机。
 */

function fetchUserData(userId) {
  return new Promise(function(resolve, reject) {
    // executor 函数体 —— 此时已经进入同步执行！

    // 模拟网络请求（实际中可能是 fetch/XMLHttpRequest）
    setTimeout(() => {
      if (userId > 0) {
        // 成功：调用 resolve，传入结果
        resolve({ id: userId, name: "Alice", role: "admin" });
        // resolve 后，Promise 状态变为 fulfilled
        // 所有 .then() 处理器将在微任务中被调度执行
      } else {
        // 失败：调用 reject，传入错误
        reject(new Error("无效的用户 ID"));
        // reject 后，Promise 状态变为 rejected
        // 所有 .catch() 处理器将在微任务中被调度执行
      }
    }, 1000);  // 模拟1秒的网络延迟
  });
}

const userPromise = fetchUserData(42);
// 此时 Promise 处于 pending 状态
// 内部的 setTimeout 还没到时间，resolve 还没被调用
```

**消费端（消费者角色）—— 使用 `.then()` / `.catch()` / `.finally()`**：

```javascript
userPromise
  .then(function(user) {
    // onFulfilled 处理器
    // 仅当 Promise 被 resolve 时才会执行
    // 参数 user 就是 resolve() 传入的值
    console.log("获取到用户:", user.name);
    return user;  // 返回值将传递给下一个 .then()
  })
  .catch(function(error) {
    // onRejected 处理器
    // 仅当 Promise 被 reject 时才会执行
    // 参数 error 就是 reject() 传入的错误对象
    console.error("出错了:", error.message);
    // 如果这里返回一个值，可以"恢复"链的执行（变成 fulfilled）
  })
  .finally(function() {
    // onFinally 处理器
    // 无论成功还是失败【都会】执行
    // 通常用于清理操作（隐藏 loading 动画、关闭连接等）
    // 注意：finally 不接收参数（不知道结果是成功还是失败）
    console.log("请求结束了（不管成败）");
  });
```

### 4.4 已 settle 的 Promise —— 延迟订阅依然生效

一个非常重要的特性：**即使 Promise 已经完成（fulfilled 或 rejected），之后再给它添加 `.then()` / `.catch()` 处理器仍然会立即（以微任务形式）执行**：

```javascript
// 这个 Promise 创建时就已经是 fulfilled 状态
let promise = Promise.resolve("立即成功!");

// 过了一会儿才添加处理器
setTimeout(() => {
  promise.then(console.log);  // 依然输出 "立即成功!" —— 不会遗漏
}, 2000);

// 同样适用于 rejected
let failed = Promise.reject(new Error("早已失败"));

setTimeout(() => {
  failed.catch(e => console.log("捕获到:", e.message));  // "早已失败"
}, 2000);
```

**类比**：这就像是歌手已经唱完了演唱会（Promise 已 settle），但你后来才加入粉丝群（附加 `.then()`）。你依然能听到现场录音回放（处理器被执行），或者知道演出取消了（收到错误信息）。比现实生活中"错过了就无法弥补"更加灵活——**Promise 会记住它的最终结果**，等待所有感兴趣的消费者来领取。

### 4.5 Promise 链式调用 —— 值传递与 Promise 穿透机制

Promise 最强大的能力之一是**链式调用（Chaining）**——每一个 `.then()` 都会返回一个新的 Promise，使得异步操作可以被串联起来，形成一条扁平的处理流水线。

#### 核心规则：.then(handler) 的返回值决定下一个 Promise 的状态

```javascript
new Promise((resolve) => resolve(1))
  .then(result => {
    console.log(result);  // 1
    return result * 2;     // 返回普通值 2
  })
  .then(result => {
    console.log(result);  // 2 ← 收到的是上一个 then 的返回值！
    return result * 2;     // 返回普通值 4
  })
  .then(result => {
    console.log(result);  // 4 ← 值像流水线一样一级级传递下去
  });
```

`.then()` 内部 handler 的返回值有三种情况：

| handler 返回值 | 下一个 Promise 的状态 | 传递给下一级的值 |
|---------------|-------------------|----------------|
| **普通值**（数字/字符串/对象等）| 自动包装为 `fulfilled` | 该普通值本身 |
| **新的 Promise** | 等待该 Promise 的结果 | 该 Promise resolve 的值 |
| **抛出异常 `throw err`** | 变为 `rejected` | 该异常对象 |

#### 返回新 Promise —— 链中的"暂停"

当 `.then()` 的 handler 返回一个新的 Promise 时，整个链会**暂停**等待这个新 Promise 完成，然后才继续：

```javascript
fetch('/api/user.json')              // Promise A: 发起网络请求
  .then(response => response.json())  // 解析 JSON → 得到用户数据
  .then(user => fetch(`https://api.github.com/users/${user.name}`))  // Promise B: 用用户名查 GitHub
  .then(response => response.json())  // 解析 GitHub 数据
  .then(githubUser => {
    console.log(githubUser.avatar_url);
    // 到这里，两个串行的网络请求都已完成
  });
```

每一步都可能涉及网络 I/O（耗时几百毫秒），但因为链式调用，代码看起来像是**顺序执行的同步代码**——从上到下阅读，逻辑一目了然。

#### Thenable 对象 —— 兼容第三方库

handler 返回的不一定是原生 Promise，只要是一个带有 `.then()` 方法的对象（称为 **Thenable**），就会被自动当作 Promise 处理：

```javascript
class CustomThenable {
  constructor(value) { this.value = value; }

  then(resolve, reject) {
    // 第三方库可以实现自己的 thenable 协议
    setTimeout(() => resolve(this.value * 2), 500);
  }
}

Promise.resolve(1)
  .then(result => new CustomThenable(result))
  .then(console.log);  // 约 500ms 后输出 2
```

这让不同库之间的 Promise 互操作成为可能——你可以在自己的 Promise 链中使用 jQuery Deferred、Bluebird 等第三方库返回的对象，它们会被自动适配。

#### 错误在链中的传播

```javascript
fetch('/api/data')
  .then(response => {
    if (!response.ok) {
      throw new Error("HTTP 错误: " + response.status);
      // 这里 throw 等价于 return Promise.reject(new Error(...))
    }
    return response.json();
  })
  .then(data => {
    console.log(data);
  })
  .catch(error => {
    // ⭐ 关键：.catch() 可以捕获链中【任何一步】产生的错误
    // 不管是网络错误、JSON 解析错误还是上面手动 throw 的错误
    console.error("某处出错了:", error.message);
  });
```

## 五、async/await —— 让异步代码看起来像同步

### 5.1 核心概念

`async/await` 是 ES2017（ES8）引入的语法糖，建立在 Promise 之上。它的目标是让**异步代码的书写方式和阅读体验尽可能接近同步代码**——不再需要 `.then()` 链，不再需要嵌套回调，用 `try/catch` 就能处理错误。

如果说 Promise 把"回调地狱"拉平成了"流水线"；那么 `async/await` 则是把这条流水线重新折叠成了**一本从头读到尾的故事书**。

### 5.2 async 函数 —— 自动返回 Promise

在一个普通函数前面加上 `async` 关键字，它会自动变成一个返回 Promise 的函数：

```javascript
// 普通函数 —— 返回普通值
function normalFunction() {
  return 42;
}

// async 函数 —— 返回值自动包装在 Promise 中
async function asyncFunction() {
  return 42;  // 等价于：return Promise.resolve(42)
}

console.log(normalFunction());  // 42（普通值）
console.log(asyncFunction());   // Promise {<fulfilled>: 42}（Promise 对象）

// 所以你可以直接 .then()
asyncFunction().then(v => console.log(v));  // 42
```

`async` 关键字做了两件事：
1. **让函数始终返回 Promise**——即使你 return 一个普通值，也会被自动包装
2. **允许你在函数体内使用 `await` 关键字**

### 5.3 await 表达式 —— 暂停并等待结果

`await` 只能在 `async` 函数内部使用。它会让 JavaScript 引擎**暂停**当前 async 函数的执行，等待右边的 Promise 完成，然后将结果（或抛出异常）返回：

```javascript
async function fetchUser() {
  console.log("开始...");

  // await 暂停执行，等 fetch 完成后恢复
  let response = await fetch('/api/user.json');  // ⏸ 在此暂停

  console.log("拿到响应了");  // fetch 完成后才执行到这里

  let user = await response.json();  // ⏸ 再次暂停，等 JSON 解析完成

  console.log("拿到数据了:", user.name);
  return user;
}

fetchUser().then(u => console.log("全部完成:", u.name));

/* 输出顺序：
开始...
（等待网络...）
拿到响应了
（等待解析...）
拿到数据了: Alice
全部完成: Alice
*/
```

**`await` 的行为细节**：

| 行为 | 说明 |
|------|------|
| **暂停的是什么？** | 只是暂停当前的 **async 函数**的执行，不是整个主线程！ |
| **是否阻塞？** | **不阻塞！** 主线程可以去处理其他任务（事件循环继续运转）|
| **返回什么？** | Promise fulfilled → 返回 resolve 的值；rejected → 抛出异常 |
| **能否在普通函数中使用？** | ❌ 不能！必须在 `async` 函数内 |

**重要认知**：`await` 不是 `sleep()` 或 `Thread.sleep()`——它不会让 CPU 空转等待，也不会阻塞整个程序。它更像是**把当前函数的执行权暂时交还给事件循环**，等 Promise 完成了再回来继续。这和生成器（Generator）中的 `yield` 有异曲同工之妙。

### 5.4 async/await 的错误处理 —— try/catch 回归

由于 `await` 在 Promise rejected 时会**抛出异常**，我们可以用熟悉的 `try/catch` 来处理异步错误——就像处理同步代码的错误一样自然：

```javascript
async function loadAndShowUser() {
  try {
    // try 块内的任何一个 await 失败都会跳转到 catch
    let response = await fetch('/api/user.json');
    let user = await response.json();

    // 显示用户头像
    let img = document.createElement('img');
    img.src = user.avatar;
    document.body.appendChild(img);

  } catch (error) {
    // 统一捕获所有可能的错误：
    // - 网络断开（fetch reject）
    // - 404/500 等 HTTP 错误（需自行判断 response.ok）
    // - JSON 格式错误（json() reject）
    // - DOM 操作错误（如果有）
    console.error("加载失败:", error.message);
    showErrorMessage("用户信息加载失败，请重试");

  } finally {
    hideLoadingSpinner();  // 无论成败都执行
  }
}
```

对比 Promise 链式的 `.catch()`：

```javascript
// Promise 方式的错误处理 —— 也行，但不够直观
fetch('/api/user.json')
  .then(response => response.json())
  .then(user => { /* ... */ })
  .catch(error => {
    console.error("加载失败:", error.message);
    showErrorMessage("...");
  })
  .finally(() => hideLoadingSpinner());
```

两种方式的区别在于：`try/catch` 能让你**在同一片代码区域内看到完整的业务逻辑和错误处理**，而不需要跳到链的末尾去看 catch 块。

### 5.5 并行执行 —— 避免"瀑布式"等待

默认情况下，`await` 会**串行**等待——必须等上一个 Promise 完成才启动下一个。但如果多个异步操作之间**没有依赖关系**，串行等待就是浪费时间的：

```javascript
// ❌ 串行 —— 总耗时 = 时间1 + 时间2 + 时间3
async function sequential() {
  const user = await fetch('/api/user');      // 等待 300ms
  const posts = await fetch('/api/posts');    // 再等 400ms（与上面无关！）
  const comments = await fetch('/api/comments');// 再等 200ms（也与上面无关！）
  // 总共等待约 900ms 😢
}

// ✅ 并行 —— 总耗时 = max(时间1, 时间2, 时间3)
async function parallel() {
  // 同时发起所有请求，不等待！
  const [userRes, postsRes, commentsRes] = await Promise.all([
    fetch('/api/user'),      // ~300ms
    fetch('/api/posts'),     // ~400ms
    fetch('/api/comments')   // ~200ms
  ]);
  // 总共只需等待约 400ms（最慢的那个）🎉

  // 然后再分别解析
  const user = await userRes.json();
  const posts = await postsRes.json();
  const comments = await commentsRes.json();
}
```

`Promise.all([...])` 会同时启动所有 Promise，然后用数组的形式统一返回结果。其中任何一个失败则整体失败。如果你希望某些失败不影响其他的，可以用 `Promise.allSettled([...])`。

### 5.6 async/await 底层原理 —— 它就是 Generator + Promise 的语法糖

理解 `async/await` 的本质有助于你写出更好的异步代码。实际上，编译器（或引擎）会将 async 函数大致转换为如下等价形式：

```javascript
// 你写的 async/await 代码
async function example() {
  const a = await fetch('/api/a');
  const b = await fetch('/api/b');
  return a + b;
}

// 大致等价的底层实现（简化版）
function example() {
  // 自动返回 Promise
  return Promise.resolve().then(function() {
    return fetch('/api/a').then(function(a) {
      return fetch('/api/b').then(function(b) {
        return a + b;  // 最终值
      });
    });
  });
}
```

每一次 `await` 都对应着一次 `.then()` 链式调用。所以 async/await 的执行顺序完全受事件循环和微任务规则的约束——这一点我们接下来详细讨论。

## 六、事件循环（Event Loop） —— JavaScript 的心跳

### 6.1 核心概念

现在我们终于来到了本章最重要的部分：**事件循环（Event Loop）**。它是理解 JavaScript 一切异步行为的基石。

还记得开头那个 `setTimeout(() => {}, 0)` 为什么不立即执行吗？答案就在事件循环的运行机制中。

**事件循环**是 JavaScript 运行时（无论是浏览器的 V8 还是 Node.js）用来协调以下几件事的核心机制：

1. **执行同步代码**（调用栈中的任务）
2. **处理异步操作完成后的回调**
3. **执行页面渲染**（DOM 更新、样式重计算、绘制）
4. **等待新的任务到来**

它的名字来源于其工作机制：**一个不断重复的循环过程——从队列中取出任务并执行，执行完后再去取下一个**。就像心脏跳动一样——泵血（执行任务）、回流（收集新任务）、再泵血、再回流……周而复始，永不停止（除非进程退出）。

### 6.2 三个核心组件

要理解事件循环，你需要认识它的三个核心组成部分：

```
┌──────────────────────────────────────────────────────────┐
│                   JavaScript 运行时                        │
│                                                          │
│  ┌──────────────────────┐                                │
│  │     调用栈             │                                │
│  │   (Call Stack)        │  ← 当前正在执行的函数/代码      │
│  │                        │     后进先出 LIFO 结构          │
│  │   ┌────────────────┐  │                                │
│  │   │  main()        │  │  ← 栈底：主脚本                │
│  │   ├────────────────┤  │                                │
│  │   │  foo()         │  │  ← main 调用了 foo             │
│  │   ├────────────────┤  │                                │
│  │   │  bar()         │  │  ← foo 调用了 bar              │
│  │   └────────────────┘  │  ← 栈顶：正在执行 bar          │
│  └──────────┬───────────┘                                │
│             │                                            │
│             ▼  同步代码执行完毕                            │
│  ┌──────────────────────────────────────────────────┐   │
│  │            事件循环 (Event Loop)                  │   │
│  │                                                  │   │
│  │  ┌────────────┐  ┌─────────────────────────┐     │   │
│  │  │ 微任务队列   │  │  宏任务队列              │     │   │
│  │  │(Microtask)  │  │  (Macrotask)            │     │   │
│  │  │            │  │                         │     │   │
│  │  │ • then()   │  │ • script (整体脚本)      │     │   │
│  │  │ • catch()  │  │ • setTimeout()          │     │   │
│  │  │ • finally  │  │ • setInterval()         │     │   │
│  │  │ • await后  │  │ • UI Events (click...)  │     │   │
│  │  │ • queue..  │  │ • I/O callbacks         │     │   │
│  │  │ • MutatObs │  │ • postMessage           │     │   │
│  │  └────────────┘  └─────────────────────────┘     │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │        Web APIs (浏览器/Node.js 提供)             │   │
│  │  setTimeout / setInterval / fetch / DOM Events    │   │
│  │  这些不在 JS 引擎的主线程中运行                    │   │
│  └──────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

**三个组件的角色类比**：

| 组件 | 类比 | 职责 | 关键特性 |
|------|------|------|---------|
| **调用栈（Call Stack）** | 你的办公桌 | 正在处理的任务——一次只能做一件事 | LIFO（后进先出）|
| **Web APIs** | 外包服务商（快递公司/厨房/银行）| 处理异步操作的地方——**不在主线程上运行** | 定时器、网络请求、DOM 事件 |
| **任务队列（Task Queues）** | 待办事项箱 | 异步操作完成后，回调函数被放到这里排队等候 | 分为微任务和宏任务两种 |

**调用栈的工作方式**：当你调用一个函数时，它被压入栈顶；函数执行完毕后，从栈顶弹出。如果函数 A 中调用了函数 B，B 会压在 A 上面——A 必须等 B 完成后才能继续。这就解释了为什么递归太深会导致"栈溢出（Stack Overflow）"——栈的空间是有限的。

**Web APIs 的独立性**：当你调用 `setTimeout(fn, 1000)` 时，定时器的倒计时**不是由 JavaScript 引擎做的**——而是由浏览器的定时器模块（一个独立的 C++ 线程）负责。同样，`fetch()` 发起的网络请求也是由浏览器的网络线程处理的。JS 引擎只管把任务交给 Web API，然后继续做自己的事。等 Web API 完成了，它会**把回调函数放入任务队列**——注意，此时回调还没有被执行，只是在排队而已。

### 6.3 事件循环的完整算法 —— 5 步精确流程

以下是事件循环每一次迭代（one tick）所做的事情——这是理解一切异步行为的关键：

```
╔══════════════════════════════════════════════════════════╗
║          事件循环的一次迭代（One Tick of Event Loop）       ║
║                                                           ║
║  Step 1: 从【宏任务队列】中取出最早的一个任务               ║
║         ──→ 推入调用栈，开始执行                           ║
║                                                           ║
║  Step 2: 执行当前宏任务中的所有同步代码                     ║
║         （执行过程中可能产生新的微任务/宏任务）              ║
║                                                           ║
║  Step 3: 🔑 清空【微任务队列】                             ║
║         while (微任务队列不为空) {                         ║
║           取出一个微任务 → 执行                           ║
║         }                                                 ║
║         （执行微任务过程中产生的新微任务也在本轮清空）      ║
║                                                           ║
║  Step 4: 🎨 渲染更新（如果需要且时机合适）                 ║
║         浏览器执行：样式计算 → 布局 → 绘制 → 合成           ║
║                                                           ║
║  Step 5: 回到 Step 1（循环继续...）                        ║
╚══════════════════════════════════════════════════════════╝
```

**最核心的规则（背诵级别重要）**：

> **每次执行完一个宏任务后，事件循环一定会先把当前所有的微任务全部执行完毕，然后才考虑渲染和下一个宏任务。**

这意味着微任务的优先级**远高于**宏任务——它们总是插队到两个宏任务之间批量执行。

### 6.4 经典面试题逐步追踪

让我们用上面的算法来追踪一段经典代码的完整执行过程。这是前端面试中最常见的题目类型之一：

```javascript
console.log("1");                    // 同步代码

setTimeout(() => {                   // 宏任务 A
  console.log("2");
}, 0);

Promise.resolve().then(() => {      // 微任务 ①
  console.log("3");
});

Promise.resolve().then(() => {      // 微任务 ②
  console.log("4");
  setTimeout(() => {                // 微任务内注册的新宏任务 B
    console.log("5");
  }, 0);
});

Promise.resolve().then(() => {      // 微任务 ③
  console.log("6");
});

setTimeout(() => {                   // 宏任务 C
  console.log("7");
}, 0);

console.log("8");                    // 同步代码
```

**预期输出**：`1 → 8 → 3 → 4 → 6 → 2 → 7 → 5`

现在让我们用事件循环算法一步步追踪：

---

**阶段一：执行主脚本（这是一个宏任务）**

```
调用栈: [主脚本]

执行 console.log("1")     → 输出: 1 ✓
执行 setTimeout(cb_A)     → cb_A 加入【宏任务队列】尾部
                              （cb_A = () => { console.log("2") }）
执行 Promise.then(cb_①)   → cb_① 加入【微任务队列】尾部
执行 Promise.then(cb_②)   → cb_② 加入【微任务队列】尾部
  （注意：cb_② 内部的 setTimeout 暂时不入队——还没执行到这里）
执行 Promise.then(cb_③)   → cb_③ 加入【微任务队列】尾部
执行 setTimeout(cb_C)     → cb_C 加入【宏任务队列】尾部
执行 console.log("8")     → 输出: 8 ✓

主脚本执行完毕！（当前宏任务完成）

当前各队列状态：
  微任务队列: [ cb_①, cb_②, cb_③ ]    ← 3 个微任务排队
  宏任务队列: [ cb_A, cb_C ]            ← 2 个宏任务排队
```

---

**阶段二：清空微任务队列（Step 3！）**

```
  取出 cb_① → 推入调用栈 → 执行 → 输出: 3 ✓  → 弹出
  取出 cb_② → 推入调用栈 → 执行 → 输出: 4 ✓  → 弹出
             → cb_② 内部执行 setTimeout → cb_B 加入【宏任务队列】尾部
  取出 cb_③ → 推入调用栈 → 执行 → 输出: 6 ✓  → 弹出

  微任务队列空了！✅（cb_② 产生的 setTimeout 不是微任务）

当前各队列状态更新：
  微任务队列: [ 空 ]
  宏任务队列: [ cb_A, cb_C, cb_B ]    ← 新增了 cb_B
```

---

**阶段三：进入下一个宏任务（回到 Step 1）**

```
  取出 cb_A → 推入调用栈 → 执行 → 输出: 2 ✓
  （执行完后检查微任务队列 → 空 → 继续下一步）

  取出 cb_C → 推入调用栈 → 执行 → 输出: 7 ✓
  （执行完后检查微任务队列 → 空 → 继续下一步）

  取出 cb_B → 推入调用栈 → 执行 → 输出: 5 ✓
  （执行完后检查微任务队列 → 空 → 继续）

  宏任务队列也空了！全部完成！✅
```

---

**最终输出顺序**：`1 8 3 4 6 2 7 5`

现在你应该彻底明白了为什么 `setTimeout(fn, 0)` 中的回调总是排在所有同步代码和所有微任务之后执行——因为它是一个**宏任务**，必须等到当前的宏任务（主脚本）执行完毕 + **所有**微任务清空后才有机会轮到它。即使延迟设为 0，也要等这一轮"清空微任务"的过程完全结束后才能执行。

### 6.5 宏任务 vs 微任务 —— 完整对比

| 特性维度 | **宏任务（Macrotask）** | **微任务（Microtask）** |
|----------|:-:|:-:|
| **常见来源** | `script`(整体脚本)、`setTimeout`、`setInterval`、UI 事件（click/input/scroll）、I/O callbacks、`postMessage`、`setImmediate`(Node.js) | `Promise.then/catch/finally`、`queueMicrotask()`、`MutationObserver`、`await`（本质上是微任务）|
| **每次执行几个？** | 每次**取 1 个**，执行完后检查微任务 | 每次**全部清空**（一个不留）|
| **执行时机** | 在微任务全部清空**之后** | 在每个宏任务**之后**、**之前**（高优先级插入）|
| **优先级** | 低 | **高** |
| **典型最小延迟** | `setTimeout(0)` 嵌套 ≥5 层时最少约 **4ms** | 几乎 **0ms**（同步代码之后紧接着）|
| **渲染关系** | **两次宏任务之间**可能发生渲染 | **微任务执行期间绝不渲染**|
| **设计目的** | I/O 操作、定时器、用户交互 | 状态更新后的快速响应 |

**为什么要有两种队列而不是一种？**

这是因为不同的异步操作有不同的**紧急程度（Urgency）**：

- `Promise.then`（微任务）通常代表**数据状态的变更**——比如"Vue/React 更新了虚拟 DOM，应该尽快反映到界面上"。这类操作需要在当前任务结束后**立即**处理，否则界面会出现不一致的中间状态。
- `setTimeout`（宏任务）通常代表**"过一段时间再做"的非紧急操作**——比如"3 秒后弹出一个提示"、"100ms 后检测一下滚动位置"。这类操作不需要那么紧急。

微任务的高优先级保证了**状态变更的原子性和一致性**——在一轮微任务执行期间，不会有任何宏任务（比如用户的鼠标点击）插进来打断你。这对于框架（Vue、React）的状态更新机制至关重要。

### 6.6 渲染时机 —— 页面何时更新？

浏览器在事件循环中有特定的时机进行页面渲染：

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│  [执行宏任务] → [清空微任务] → 🎨 [渲染] → [下一个宏任务] │
│                                     ↑                │
│                              渲染发生在这里！          │
│                              （如果有 DOM 变更的话）     │
│                                                      │
│  渲染管线（Rendering Pipeline）：                     │
│  1. Style → 样式重新计算 (Recalculate Style)          │
│  2. Layout → 布局计算 (Reflow/Layout)                 │
│  3. Paint → 绘制 (Paint)                              │
│  4. Composite → 合成 (Composite)                       │
│                                                      │
│  ⚠️ 渲染的两个限制条件：                               │
│  1. 微任务执行期间【不渲染】                            │
│  2. 如果一个宏任务太久，渲染也会被推迟                  │
│  3. 浏览器可能会智能合并多次 DOM 变更为一次渲染          │
└──────────────────────────────────────────────────────┘
```

**实际影响举例**：

```javascript
// 修改 DOM 10 次 —— 但用户可能只看到一次渲染！
for (let i = 0; i < 10; i++) {
  element.style.left = i * 10 + 'px';
  element.style.top = i * 10 + 'px';
}
// 整个 for 循环是一个同步代码块（在同一个宏任务中）
// 循环期间不会渲染！用户看到的元素是直接出现在最终位置
// 而不是一步一步挪过去的动画效果

// 如果你想要看到中间状态（动画效果），需要拆分为多个宏任务：
let i = 0;
function move() {
  element.style.left = i * 10 + 'px';
  element.style.top = i * 10 + 'px';
  i++;
  if (i < 10) {
    requestAnimationFrame(move);  // 每次渲染帧前执行一次
    // 或者用 setTimeout(move, 16)
  }
}
move();
```

## 七、各种"延迟执行"方式的深度对比

### 7.1 setTimeout(fn, 0)

```javascript
console.log("start");
setTimeout(() => {
  console.log("setTimeout(0)");
}, 0);
console.log("end");

// 输出：start → end → setTimeout(0)
```

`setTimeout(callback, 0)` 的含义是**"将 callback 尽快放入宏任务队列，但不早于当前宏任务和所有微任务"**。

关键细节：
- **不是真正的 0ms**——浏览器规范规定嵌套层级 ≥ 5 的 `setTimeout` 有**最小 4ms 延迟限制**（防止恶性循环消耗 CPU）
- 它创建的是**宏任务**
- 常见用途：拆分大任务、在事件冒泡完成后执行操作、兼容旧浏览器

### 7.2 queueMicrotask(fn) / Promise.resolve().then(fn)

```javascript
console.log("start");
queueMicrotask(() => {
  console.log("microtask");
});
console.log("end");

// 输出：start → end → microtask
```

`queueMicrotask` 创建的是**微任务**——它会在当前宏任务结束后**立即**执行，排在任何 `setTimeout(0)` 之前。几乎没有延迟——它是同步代码之后最早的异步操作。

`Promise.resolve().then(fn)` 行为与 `queueMicrotask(fn)` 完全相同（后者只是语义更明确的前者语法糖）。

### 7.3 requestAnimationFrame(fn)

```javascript
function animate() {
  console.log("raf frame");
  box.style.transform = `translateX(${x}px)`;
  x += 5;
  if (x < 300) {
    requestAnimationFrame(animate);  // 注册下一帧
  }
}
requestAnimationFrame(animate);
```

`requestAnimationFrame`（简称 rAF）与浏览器的**渲染帧率**同步——它在每次页面即将重绘之前被调用（通常是每秒 60 次，即约 16.67ms 一次）。它是做动画的最佳选择：

| 特性 | `setTimeout` 做 rAF | `requestAnimationFrame` |
|------|:-:|:-:|
| **与刷新率同步** | ❌ 固定间隔，可能与刷新不同步 | ✅ 自动匹配显示器刷新率（60/120/144Hz）|
| **标签页不可见时** | ❌ 继续运行（浪费 CPU）| ✅ 自动暂停（节省资源）|
| **流畅度** | 可能丢帧或重复帧 | ✅ 保证每帧最多执行一次 |
| **精度** | 受 4ms 最小延迟影响 | 亚像素级精准 |

### 7.4 四种方式决策速查表

| 方式 | 任务类型 | 典型延迟 | 适用场景 |
|------|---------|---------|---------|
| `setTimeout(fn, 0)` | **宏任务** | ~4ms（嵌套时）| 拆分大任务、事件冒泡后执行、跨浏览器兼容 |
| `queueMicrotask(fn)` | **微任务** | ~0ms | 需要在当前同步代码之后**立即**观察副作用/状态变更 |
| `Promise.resolve().then(fn)` | **微任务** | ~0ms | 同上（兼容性更好，IE 不支持 queueMicrotask）|
| `requestAnimationFrame(fn)` | **宏任务**（渲染相关）| ~16.67ms（60fps）| 平滑动画、视觉更新 |

## 八、长任务拆分 —— 防止 UI 卡死的实战方案

### 8.1 问题：长任务冻结界面

如果一个同步的计算任务耗时太长（超过约 50ms），浏览器就来不及响应用户输入和渲染画面，用户就会感受到明显的"卡顿"：

```javascript
// 危险：长时间运行的同步计算
function heavyCalculation() {
  let result = 0;
  for (let i = 0; i < 10_000_000_000; i++) {  // 100亿次循环
    result += Math.sqrt(i);
  }
  return result;
}

heavyCalculation();
// 在这大概 10+ 秒钟内：
// ❌ 页面完全冻结（白屏或最后一帧静止）
// ❌ 点击任何按钮 —— 无反应
// ❌ CSS 动画 —— 停在当前帧
// ❌ 滚动 —— 无法滚动
// ❌ 键盘输入 —— 无法输入
// ❌ 浏览器很可能弹出 "页面未响应" 警告对话框
// ❌ 用户可能直接强制关闭标签页 —— 体验灾难
```

为什么会这样？因为这个 `for` 循环占用了唯一的主线程，事件循环根本没机会去执行其他任务（包括处理点击事件和执行渲染）。调用栈里一直压着一个庞大的循环函数，弹都弹不出来。

### 8.2 解决方案：利用 setTimeout(0) 进行任务分片（Yielding）

利用事件循环的特性，我们可以把一个大任务拆分成多个小块，每块之间插入一个 `setTimeout(0)`，让控制权暂时归还给事件循环：

```javascript
let i = 0;
const TOTAL = 10_000_000_000;  // 总共需要处理 100 亿次
const CHUNK = 1_000_000;        // 每次只处理 100 万次（约几毫秒）
const progressBar = document.getElementById('progress');

function processChunk() {
  // 计算一小块
  const start = i;
  const end = Math.min(i + CHUNK, TOTAL);

  for (; i < end; i++) {
    // 做一部分计算...
    Math.sqrt(i);
  }

  // 更新进度指示器
  const percent = Math.round((i / TOTAL) * 100);
  progressBar.textContent = `进度: ${percent}%`;
  progressBar.style.width = `${percent}%`;

  // 如果还没做完，安排下一块（放入宏任务队列）
  if (i < TOTAL) {
    setTimeout(processChunk, 0);  // 🔑 关键：让出主线程
                                    // 这样浏览器有机会：
                                    // 1. 处理用户的点击事件
                                    // 2. 执行渲染更新（用户能看到进度条增长！）
                                    // 3. 处理其他宏任务
  } else {
    console.log("全部完成！");
    progressBar.textContent = "完成！";
  }
}

processChunk();  // 开始第一块
```

**原理图解对比**：

```
❌ 未分片（阻塞）：
  [████████████████████████████████████████]  ← 连续执行 10 秒
                                              UI 完全冻结

✅ 分片后（非阻塞）：
  [████] ──→ 渲染+事件 ──→ [████] ──→ 渲染+事件 ──→ [████] ──→ ...
   ~5ms/块     ↑           ~5ms/块      ↑
             浏览器有机会呼吸（处理点击、渲染进度条...）
```

每执行一小块后主动"让路"（yield），让浏览器有机会处理用户的鼠标点击、键盘输入以及渲染最新的进度指示器。用户看到的是一个**逐渐增长的进度条**和一个**可以交互的页面**，而不是一个死寂的冻结窗口。

### 8.3 更优雅的分片方案 —— requestIdleCallback 与 scheduler.yield()

现代浏览器提供了更专业的 API 来做这件事：

```javascript
// 使用 requestIdleCallback（在浏览器空闲时执行）
function yieldToMain() {
  return new Promise(resolve => {
    requestIdleCallback(resolve);  // 浏览器空闲时 resolve
  });
}

async function splitWork() {
  for (let i = 0; i < TOTAL; i += CHUNK) {
    // 做一块工作...
    doChunk(i, Math.min(i + CHUNK, TOTAL));

    // 让出主线程，等待浏览器空闲
    await yieldToMain();
  }
}

// 更现代的方案：scheduler.yield()（实验性 API）
// import { scheduler } from 'node:timers/promises'; // Node.js
// await scheduler.yield();  // 比 rIC 更可控
```

对于极端繁重的计算，终极方案是 **Web Worker**——它开辟了一个完全独立的线程来做计算，完全不占用主线程。但 Worker 无法访问 DOM，所以适合纯计算密集型任务。

## 九、陷阱与注意事项

| # | 陷阱 | 说明 | 解决方案 |
|---|------|------|---------|
| 1 | **`setTimeout(fn, 0)` 不是立即执行** | 至少要等当前宏任务 + 所有微任务完成 | 如需"几乎立即"，用 `queueMicrotask` 或 `Promise.resolve().then` |
| 2 | **`async` 函数返回 Promise** | `let x = asyncFn()` 拿到的是 Promise 不是值 | 需要 `let x = await asyncFn()` 或 `asyncFn().then(x => ...)` |
| 3 | **`await` 只能在 `async` 内使用** | 普通 function 里写 await 会 SyntaxError | 包裹在 async 函数中，或用顶层 await（ES2022 Module）|
| 4 | **`for...of` 忽略最后的 `return` 值** | Generator/AsyncGenerator 的 return 值不出现在 for/of 循环中 | 用 `.next().value` 手动获取最后一个值 |
| 5 | **微任务中修改 DOM 不会立即渲染** | 渲染只在微任务清空后才可能发生 | 需要即时视觉反馈时考虑用 `requestAnimationFrame` |
| 6 | **`unhandledrejection`** | Promise 被 reject 但没有 `.catch()` 处理 | 始终在链尾加 `.catch()` 或在 async 函数外捕获 |
| 7 | **`await` 串行导致不必要的等待** | 多个独立的 await 会串行执行 | 用 `Promise.all([...])` 并行化 |
| 8 | **`try/catch` 只捕获最近的 await** | 上面的 await 出错会跳到 catch，后面的 await 不执行 | 合理划分 try/catch 的范围 |

### 陷阱详解：async 函数中的"隐形 Promise"

```javascript
async function problematic() {
  try {
    let data = await fetch(url);       // 如果这里失败了
    let user = await data.json();      // 这行永远不会执行
    console.log(user.name);            // 这行也不会
  } catch (e) {
    console.error("出错:", e);         // 直接跳到这里
  }
}

// ✅ 如果需要部分容错，分开 try/catch
async function robust() {
  let response;
  try {
    response = await fetch(url);       // 只包裹可能出错的部分
  } catch (e) {
    console.error("请求失败:", e);
    return null;                       // 给调用方一个 fallback
  }
  // 即使 fetch 失败了，这里的代码仍可执行（如果上面 return 了就不会）
  let user = await response?.json();
  console.log(user?.name);
}
```

## 十、最佳实践与设计原则

### 何时用什么？

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 简单的一次性异步操作 | `async/await` | 代码最接近同步风格，易读 |
| 多个独立的并行异步操作 | `Promise.all([await a(), await b()])` | 并行化减少总耗时 |
| 需要精确控制执行顺序 | `Promise` 链或 `async/await` | 两者都可以表达顺序依赖 |
| 状态变更后立即响应 | `queueMicrotask` | 最高优先级，在渲染前执行 |
| 平滑动画 | `requestAnimationFrame` | 与渲染帧同步 |
| CPU 密集型长任务 | 分片 (`setTimeout(0)`) 或 Web Worker | 避免阻塞主线程 |
| 兼容旧浏览器 | `Promise` + polyfill | async/await 需要转译 |
| 跨浏览器的一致延迟 | `setTimeout(fn, 0)` | 最广泛支持的"延后执行"方式 |

### 设计原则

1. **不要阻塞主线程**：任何超过 50ms 的同步操作都应该警惕——用户能感知到 100ms 以内的延迟
2. **用微任务处理"需要尽快反映状态变更"的逻辑**：比如 Vue/React 响应式系统的批处理更新
3. **用宏任务处理"可以稍后"的非紧急操作**：比如日志上报、统计埋点
4. **优先 `async/await`，必要时退回 Promise**：大多数场景下 async/await 更清晰；但在动态组合 Promise 数组时，原生 Promise API 更灵活
5. **始终处理错误的 Promise**：未捕获的 rejection 会导致 `unhandledrejection` 事件——在生产环境中可能导致难以排查的 bug
6. **理解你的工具**：知道 `await` 底层是微任务，知道 `setTimeout` 底层是宏任务——这决定了它们的执行顺序

```
JavaScript 同步与异步完整体系
│
├── 单线程模型
│   ├── 为什么单线程？（1995年历史 + DOM 安全）
│   ├── 阻塞的危害（长任务冻结 UI）

├── 同步 vs 异步
│   ├── 同步（Synchronous）
│   │   ├── "死等" / "排队"模式
│   │   ├── 优点：直观（执行顺序 = 书写顺序）
│   │   └── 缺点：耗时操作阻塞整个线程
│   │
│   └── 异步（Asynchronous）
│       ├── "叫号" / "回调通知"模式
│       ├── 优点：不阻塞，高效利用单线程
│       └── 缺点：执行顺序 ≠ 书写顺序
│
├── 回调函数（Callback）—— 异步基础
│   ├── 本质：函数作为一等公民传入另一函数
│   ├── 同步回调：forEach/map/filter（立即执行）
│   ├── 异步回调：setTimeout/fetch/event（延迟执行）
│   ├── Error-first 风格：callback(err, data)
│   └── 回调地狱：深层嵌套 → 可读性崩溃
│
├── Promise —— 异步契约
│   ├── 三种状态：pending → fulfilled / rejected（单向不可逆）
│   ├── 创建：new Promise(executor)，executor 立即同步执行
│   ├── 消费：.then() / .catch() / .finally()
│   ├── 链式调用：
│   │   ├── 返回普通值 → 下一个 then 立即收到
│   │   ├── 返回新 Promise → 链暂停等待
│   │   ├── throw → 跳转到最近 catch
│   │   └── Thenable 对象兼容
│   └── 已 settle Promise 可延迟订阅
│
├── async/await —— 语法糖
│   ├── async 函数自动返回 Promise
│   ├── await 暂停当前 async 函数（不阻塞主线程！）
│   ├── try/catch 替代 .catch()
│   ├── 串行 await vs 并行 Promise.all()
│   └── 本质：Generator + Promise 的语法糖
│
├── 事件循环（Event Loop）⭐ 核心
│   │
│   ├── 三个组件
│   │   ├── 调用栈（Call Stack）— LIFO，当前执行上下文

│   │   └── 任务队列 — 回调排队等候
│   │
│   ├── 两类任务
```
