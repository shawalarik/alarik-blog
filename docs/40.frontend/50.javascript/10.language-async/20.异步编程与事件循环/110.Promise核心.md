# Promise 核心 —— 状态机、then 链式调用、错误冒泡机制与 finally

> **核心内容**：Promise 的本质（异步操作的契约/状态容器）、三种状态的完整生命周期与单向不可逆特性、Executor 执行器函数（resolve/reject 的精确行为规则）、消费者方法（.then/.catch/.finally）的完整语义、**then 链式调用的三大返回值规则**（普通值传递/Promise 穿越/throw 转换）、Thenable 对象协议、**错误冒泡机制与隐式 try-catch**、错误恢复模式（处理/恢复/再抛出）、unhandledrejection 全局事件、六大静态方法（all/allSettled/race/any/resolve/reject）完整用法与对比、从回调到 Promise 的架构升级

## 一、为什么需要 Promise？

### 1.1 回调模式的根本缺陷回顾

在深入 Promise 之前，我们需要先理解它要解决什么问题。回调函数（Callback）虽然是 JavaScript 异步编程的基础，但它有一个**无法在自身框架内修复的根本性缺陷**——**控制反转带来的信任危机（Inversion of Control & Trust Issues）**。

当你使用回调时，你把一部分逻辑的控制权交给了别人：

```javascript
// 回调模式的问题：你不知道对方会怎么对待你的回调
doSomething(function(result) {
  // 这个函数什么时候被调用？
  // 被调用几次？
  // 传进来的参数对不对？
  // 出错了怎么办？
  // 这些全由 doSomething 内部决定——你失去了控制！
});
```

而 **Promise 正是为解决这些信任问题而设计的**。它不是一个简单的"语法糖"或"写法变体"，而是一种全新的**异步操作管理范式**——它把不可控的"回调通知"变成了可控的**"状态机查询"**。

### 1.2 Promise 是什么？—— 三种视角的理解

#### 视角一：状态容器（State Container）

Promise 本质上是一个**带有内部状态的对象**，这个状态记录了一个异步操作的进展情况。你可以随时查看它的状态，但**不能直接从外部改变状态**——只有内部的执行逻辑才能改变状态。

这就像一个**快递包裹的状态追踪系统**：

```
包裹状态追踪：
┌──────────┐   运输中    ┌──────────┐   已签收    ┌──────────┐
│ Pending  │ ─────────→ │ Delivered │ ─────────→ │ Archived  │
│ (待处理) │           │ (已送达) │           │ (已归档)  │
└──────────┘           └──────────┘           └──────────┘

你（消费者）可以：
- 查看当前状态
- 注册"到达每个状态时的通知"
但你不能：
- 手动把状态改成"已签收"
```

#### 视角二：异步操作的契约（Contract）

如果把异步操作比作一份**施工合同**：

| 角色 | 回调模式下 | Promise 模式下 |
|------|-----------|---------------|
| **甲方（你）** | 留下电话号码等通知 | 拿到合同书（Promise 对象），上面写着条款 |
| **乙方（执行者）** | 做完了打电话 | 完成后在合同上盖章（改变 Promise 状态）|
| **保障** | 无书面保证——全凭信任 | 白纸黑字写明条款——可查验、可追溯 |

Promise 就是这份**白纸黑字的合同**。它规定了：

1. 操作只会有**三种结果**：进行中、成功、失败——不可能有第四种
2. 结果一旦确定就**不可更改**——不会反复横跳
3. 你可以**随时查阅**当前状态和最终结果
4. 你可以在合同上**附加后续条款**（.then 链式调用）

#### 角角三：歌手与粉丝的订阅模式（经典类比）

这是现代 JavaScript 教程中非常精准的类比：

| 现实世界 | 编程世界 |
|---------|---------|
| **歌手**（录制歌曲的人）| **生产者代码**（执行耗时任务的代码）|
| **新歌发布** | 异步操作完成（数据准备好了）|
| **订阅名单**（谁想听新歌） | **Promise 对象**（连接生产者和消费者的桥梁）|
| **粉丝**（等待新歌的听众）| **消费者代码**（.then() 中的回调）|

流程：
1. **粉丝订阅**（创建 Promise）：你说"出新歌了告诉我"
2. **歌手录音**（Executor 执行）：开始工作
3. **发行通知**（resolve/reject）：歌发出来了（或录音设备坏了）
4. **粉丝收到**（.then/.catch）：根据结果听歌或看错误信息

**关键区别于回调**：即使你在"歌手已经发完歌"之后才加入粉丝群，你依然能听到这首歌。这就是 Promise 的**延迟订阅能力**。

## 二、Promise 的三种状态与生命周期

### 2.1 三种状态定义

一个 Promise 在其整个生命周期中，**始终且只能处于以下三种状态之一**：

```
┌─────────────────────────────────────────────┐
│         Promise 状态机 (State Machine)          │
│                                             │
│   ┌─────────┐                               │
│   │ pending  │ ← 初始状态                    │
│   │ 待定     │   操作正在进行中                │
│   │         │   result = undefined            │
│   └────┬────┘                               │
│        │                                     │
│   Executor 函数执行完毕                      │
│   (resolve 或 reject 被调用)                 │
│        │                                     │
│   ┌────┴────┐    ┌────────────────────┐       │
│   │         │    │                    │       │
│   ▼         ▼    ▼                    ▼       │
│ ┌────────┐  ┌────────┐                  │
│ │fulfilled│  │rejected │                  │
│ │已兑现  │  │已拒绝   │                  │
│ │成功 ✓  │  │失败 ✗  │                  │
│ └────────┘  └────────┘                  │
│ result=value result=error               │
│                                             │
│  ⚠️ 状态改变是单向且不可逆的！              │
│  ⚠️ resolve/reject 只有第一次有效！          │
│  ⚠️ fulfilled ↔ rejected 不能互转！          │
└─────────────────────────────────────────────┘
```

| 状态 | 英文 | 含义 | result 值 | 是否终态（settled）|
|------|------|------|-----------|:---:|
| **pending** | 待定 | `undefined` | 否 |
| **fulfilled** | 已兑现/成功 | resolve 传入的值 | ✅ 是 |
| **rejected** | 已拒绝/失败 | reject 传入的原因（通常为 Error）| ✅ 是 |

> **术语说明**：`fulfilled` 和 `rejected` 统称为 **settled（已敲定）**——表示状态已经确定，不会再变了。

### 2.2 状态的单向不可逆性 —— 为什么如此设计？

这是 Promise 最关键的设计决策之一。状态一旦改变就不能回头，原因如下：

**第一：保证一致性**

如果 Promise 可以在 fulfilled 和 rejected 之间反复切换，消费者代码就会陷入混乱——同一份数据一会儿说"成功了"一会儿说"失败了"。就像法庭判决不能朝令夕改一样，Promise 的状态必须是最终的。

```javascript
let promise = new Promise((resolve, reject) => {
  resolve("成功了!");      // ✅ 状态变为 fulfilled
  reject(new Error("失败")); // ❌ 被忽略！状态不变！
  resolve("又成功了!");   // ❌ 同样被忽略！
});

promise.then(console.log);  // 只输出 "成功了!" —— 第一次的结果被永久锁定
```

**第二：支持多次消费**

因为状态是确定的、不变的，所以**多个消费者可以安全地在不同时间点订阅同一个 Promise**，而且都能拿到正确的最终结果。这是回调做不到的。

```javascript
let promise = Promise.resolve("数据来了");

// 消费者 A：立即订阅
promise.then(data => console.log("A:", data));  // "A: 数据来了"

// 过了一会儿...
// 消费者 B：延迟订阅
setTimeout(() => {
  promise.then(data => console.log("B:", data));  // "B: 数据来了" ← 依然能拿到！
}, 2000);

// 两个人都拿到了正确的结果，因为 Promise 记住了最终状态
```

**第三：简化推理模型**

开发者不需要考虑"这个 Promise 可能会被修改"、"状态可能已经变了"这类复杂情况。看到 `fulfilled` 就知道它成功了，看到 `rejected`就知道它失败了——**所见即所得**。

### 2.3 Executor 执行器函数 —— Promise 的"发动机"

`new Promise()` 构造函数接收一个**函数参数**，这个函数被称为 **executor（执行器）**。它是 Promise 中唯一一段**立即同步执行的代码**。

```javascript
/**
 * new Promise(executor) 的执行流程：
 *
 * 1. 创建一个新的 Promise 对象（初始状态: pending）
 * 2. 【同步】调用 executor 函数，传入两个预定义好的回调：
 *    - resolve(value): 将状态改为 fulfilled，结果为 value
 *    - reject(reason): 将状态改为 rejected，结果为 reason
 * 3. 返回 Promise 对象
 *
 * 关键：executor 在 new Promise() 时就运行了！不是异步的！
 */

let promise = new Promise(function(resolve, reject) {
  console.log("① executor 开始执行");  // 这行立刻执行！

  // 通常这里会有异步操作（网络请求、定时器等）
  setTimeout(() => {
    const success = Math.random() > 0.5;

    if (success) {
      resolve("✅ 操作成功！");   // 改变状态 → fulfilled
    } else {
      reject(new Error("❌ 操作失败")); // 改变状态 → rejected
    }
  }, 1000);

  console.log("② executor 结束（但异步任务还在进行中）");
});

console.log("③ Promise 对象已创建");
// 输出顺序：① → ② → ③ （约1秒后）→ resolve/reject 生效
```

**Executor 的四条铁律**：

| # | 规则 | 说明 |
|---|------|------|
| 1 | **立即执行** | `new Promise()` 时就开始跑 executor，不等任何东西 |
| 2 | **必须调用一次且仅一次 resolve/reject** | 第一个有效调用决定最终状态；后续调用全部被静默忽略 |
| 3 | **建议用 Error 对象 reject** | `reject(new Error("msg"))` 比 `reject("msg")` 更好调试（保留堆栈）|
| 4 | **异常自动转为 rejection** | 如果 executor 内部 throw 了错误，等同于调用了 `reject(error)` |

```javascript
// 规则4演示：throw 自动触发 reject
new Promise(function(resolve, reject) {
  throw new Error("executor 里出错了！");
  // 等价于: reject(new Error("executor 里出错了!"))
}).catch(e => console.log(e.message));
// 输出: "executor 里出错了！"
```

> **重要认知**：Promise 只能捕获 **executor 函数同步执行期间**发生的错误。如果错误发生在 executor 内部的**异步回调**中（比如 `setTimeout` 里面 throw），Promise 无法感知——因为它早就执行完毕并退出了。

## 三、消费者方法 —— then、catch、finally

当 Promise 的状态确定后（或之前），你需要通过**消费者方法**来获取结果或处理错误。这三个方法是 Promise API 的核心接口。

### 3.1 .then(onFulfilled, onRejected?) —— 最基础的消费者方法

`.then()` 可以接收一个或两个函数参数：

```javascript
promise.then(
  function(value) {
    // onFulfilled 处理器：仅在 Promise 变为 fulfilled 时调用
    // 参数 value = resolve() 传入的值
  },
  function(error) {
    // onRejected 处理器：仅在 Promise 变为 rejected 时调用
    // 参数 error = reject() 传入的错误对象
  }
);
```

**两种写法**：

```javascript
// 写法A：两个参数（同时处理成功和失败）
promise.then(
  successCallback,
  failureCallback
);

// 写法B：只传一个参数（只关心成功）
promise.then(successCallback);
// 如果 Promise rejected 且没有第二个参数，错误会穿透到后面的 .catch()

// 写法C：只处理失败（不常见）
promise.then(null, failureCallback);
// 等价于 promise.catch(failureCallback)
```

### 3.2 .catch(onRejected) —— 专门处理错误的语法糖

`.catch(f)` **完全等价于** `.then(null, f)`——它是 `.then(null, errorCallback)` 的简写形式：

```javascript
// 以下两行完全等价
promise.catch(errorHandler);
promise.then(null, errorHandler);
```

`.catch()` 存在的意义是**语义更清晰**——当你读到 `.catch` 时，一眼就知道这里是专门处理错误的。而在 `.then(null, fn)` 中，那个 `null` 很容易被忽略或误解。

### 3.3 .finally(onFinally) —— 清理操作专用

无论 Promise 最终是成功还是失败，`.finally()` 中的代码**都会执行**。它就像是 `try...catch...finally` 中的 `finally` 块——用于做清理工作。

```javascript
function fetchData() {
  showLoadingSpinner();  // 显示加载动画

  return fetch("/api/data")
    .then(response => response.json())
    .then(data => {
      hideLoadingSpinner();
      return data;
    })
    .catch(error => {
      hideLoadingSpinner();  // 即使出错也要隐藏加载动画
      throw error;            // 继续传播错误
    })
    .finally(() => {
      console.log("请求结束——不管成败都会执行");
      // 这里适合放：日志上报、性能统计等
      // 注意：finally 不接收参数！不知道结果是成功还是失败
    });
}
```

**`.finally()` 的三个特殊规则**：

| 特性 | 说明 |
|------|------|
| **无参数** | 回调函数不接收任何参数（不知道结果是啥）|
| **透传性** | 它会把上游的 value 或 error 原样传递给下一个 handler |
| **返回值被忽略** | 如果 finally 返回了一个值，会被丢弃（除非抛出异常）|
| **不影响状态** | finally 不能把 rejected 变回 fulfilled，也不能反过来 |

**透传性详解**：

```javascript
Promise.resolve(42)
  .finally(() => {
    console.log("清理中...");
    return 100;  // 返回值被忽略！
  })
  .then(value => {
    console.log(value);  // 42 ← 不是 100！finally 的返回值被忽略了
    // 收到的是原始的 fulfilled 值
  });

Promise.reject(new Error("出错了"))
  .finally(() => {
    console.log("清理中...");
    // 即使这里 return 了也不会阻止错误传播
  })
  .catch(err => {
    console.log(err.message);  // "出错了！" ← 错误正常传播
  });
```

### 3.4 已 settle 的 Promise —— 延迟订阅依然生效

这是 Promise 相对于回调的一个巨大优势：**即使 Promise 在你添加处理器之前就已经完成了（settled），之后添加的处理器仍然会被调用**。

```javascript
// 这个 Promise 创建时就直接 resolve 了（没有异步操作）
let promise = Promise.resolve("立即成功!");

// 模拟"过一会儿"才来订阅
setTimeout(() => {
  promise.then(value => {
    console.log(value);  // "立即成功！" ← 依然能拿到结果！
  });
}, 2000);

// 对比：如果用回调实现同样的功能，
// "2秒后才注册的回调"将永远不会被执行（事件早已过去）
```

**原理**：Promise 会**记住自己的最终状态和结果**。当你调用 `.then()` 时，引擎会检查 Promise 当前的状态——如果是 pending 就把回调注册进去等待；如果是 fulfilled/rejected 则**立刻安排一个微任务来回调该处理器**。

## 四、then 链式调用 —— Promise 的灵魂功能

### 4.1 核心原理：每个 .then() 都返回一个新的 Promise

这是 Promise 最强大的能力——**链式调用（Chaining）**的基础。它的核心机制非常简单却又极其强大：

> **每一个 `.then()` 或 `.catch()` 调用都会返回一个全新的 Promise 对象。**

这意味着你可以在上一个 `.then()` 后面继续接 `.then()`，形成一条**处理流水线**：

```javascript
Promise.resolve(1)
  .then(x => {             // 第一个 .then()
    console.log(x);       // 1
    return x * 2;           // 返回 2
  })
  .then(x => {             // 第二个 .then() —— 接收上一个的返回值
    console.log(x);       // 2
    return x * 2;           // 返回 4
  })
  .then(x => {             // 第三个 .then()
    console.log(x);       // 4
    return "完成";
  })
  .then(msg => {
    console.log(msg);      // "完成"
  });

// 输出：1 → 2 → 4 → "完成"
// 值像流水线一样一级级传递下去
```

### 4.2 ⭐ Handler 返回值的三大规则 —— 链式调用的完整机制

`.then()` 内部的 handler 函数返回值决定了**下一个 Promise 的状态**。这里有三种情况：

#### 规则一：返回普通值 → 下一个 Promise 立即 fulfilled

```javascript
Promise.resolve(10)
  .then(x => {
    return x + 1;   // 返回普通值 11
  })
  .then(x => {
    console.log(x);  // 11
    // 上面的 .then() 返回 11 后，引擎自动做了：
    // Promise.resolve(11) → 新的 fulfilled Promise
    // 所以这里的 x = 11
  });
```

**引擎内部的等价操作**：
```javascript
// handler 返回 value 后，引擎实际上执行了：
Promise.resolve(handlerReturnValue).then(nextHandler)
// 这就是为什么值能自动传递到下一个 .then()
```

#### 规则二：返回 Promise → 链**暂停等待**直到该 Promise 完成

```javascript
Promise.resolve(1)
  .then(x => {
    console.log("收到:", x);  // "收到: 1"

    // 返回一个新的 Promise！（不是普通值）
    return new Promise(resolve => {
      setTimeout(() => resolve(x * 2), 1000);  // 1秒后 resolve 为 2
    });
  })
  .then(x => {
    console.log("结果:", x);  // "结果: 2" —— 等了 1 秒才出现！
    // 因为上面的 .then() 返回了一个未完成的 Promise
    // 引擎暂停了整条链，直到这个 Promise settled
  });
```

**时间线**：
```
T=0ms:   第一个 .then() 执行 → 输出 "收到: 1" → 返回新 Promise（pending）
         整个链暂停等待...

T=1000ms: 新 Promise resolve(2) → 第二个 .then() 被触发 → 输出 "结果: 2"
```

这就是 Promise 链能够**替代回调嵌套**的根本原因——每一步都可以等待异步操作完成后再继续下一步，而不需要层层缩进。

#### 规则三：抛出异常 / 返回 rejected Promise → 下一个 Promise 变为 rejected

```javascript
Promise.resolve(1)
  .then(x => {
    if (x > 0) throw new Error("不允许正数！");
    return x;
  })
  .then(x => {
    console.log("这里不会执行");
  })
  .catch(err => {
    console.log("捕获到:", err.message);  // "捕获到: 不允许正数！"
    // throw 让 .then() 返回 rejected Promise
    // 控制权跳到了 .catch()
  });
```

**三大规则汇总表**：

| handler 返回值 | 下一个 Promise 状态 | 传递给下一级的值 | 链的行为 |
|:--:|:--:|:--:|:--:|
| **普通值**（数字/字符串/对象/undefined） | `fulfilled` | 该普通值本身 | **继续执行**（不暂停）|
| **新的 Promise**（pending） | 取决于该 Promise | 该 Promise resolve 的值 | **暂停等待**（直到 settle）|
| **throw error** 或返回 **rejected Promise** | `rejected` | Error 对象 | **跳转到最近的 .catch()**|

### 4.3 Thenable 对象 —— 兼容第三方库的协议

handler 不一定非要返回原生的 `Promise` 对象。只要返回的对象**具有 `.then()` 方法**，JavaScript 引擎就会将其当作 Promise 来对待。这种对象叫做 **Thenable**（可 then 化的）：

```javascript
class CustomThenable {
  constructor(num) {
    this.num = num;
  }

  // 只要实现了 .then() 方法，就是 Thenable 对象
  then(resolve, reject) {
    // 引擎会把原生的 resolve/reject 作为参数传进来
    setTimeout(() => resolve(this.num * 2), 500);
  }
}

Promise.resolve(10)
  .then(result => {
    return new CustomThenable(result);  // 返回 Thenable 对象！
  })
  .then(value => {
    console.log(value);  // 约 500ms 后输出 20 (10*2)
  });
```

**引擎的处理过程**：
1. 发现 handler 返回的对象有 `.then()` 方法
2. 把自己原生的 `resolve`/`reject` 交给这个 `.then()`
3. 等待该 Thenable 对象调用 `resolve` 或 `reject`
4. 用结果继续链的执行

这使得第三方库（如 jQuery 的 Deferred、Bluebird 等）创建的对象可以无缝融入原生 Promise 生态系统中。

### 4.4 ⚠️ 常见陷阱：多监听 vs 真正的链

新手常犯的错误是把多个 `.then()` 添加到**同一个** Promise 对象上，以为这是"链式调用"：

```javascript
let promise = Promise.resolve(1);

// ❌ 这不是链！这是"多监听器"模式
promise.then(x => {
  console.log(x);   // 1
  return x * 2;
});
promise.then(x => {
  console.log(x);   // 还是 1！！不是 2！
  // 因为这是在原始 promise 上注册的另一个独立处理器
  // 它收到的永远是原始 promise 的结果
});

// ✅ 这才是真正的链式调用！
promise
  .then(x => {
    console.log(x);   // 1
    return x * 2;     // 返回值成为新 promise 的结果
  })
  .then(x => {
    console.log(x);   // 2 ← 来自上一步的返回值
  });
```

**区分要点**：
- **多监听**：`p.then(f1); p.then(f2);` —— f1 和 f2 都收到**同一个**原始结果，互不影响
- **真链式**：`p.then(f1).then(f2)` —— f2 收到的是 **f1 的返回值**，形成流水线

## 五、错误冒泡机制与隐式 try-catch

### 5.1 错误沿链向下传播

Promise 链中的错误处理遵循一个简单而强大的原则：**当一个步骤产生错误（rejected Promise 或 throw）时，控制权会跳转到链中最近的 `.catch()`（或 `.then()` 的第二个参数）**。

```javascript
fetch('/api/user')                     // 步骤 1：发送请求
  .then(response => {
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);  // 可能在这里抛错
    }
    return response.json();
  })                                    // 步骤 2：解析 JSON
  .then(user => {
    console.log(user.name);                // 可能 JSON 格式不对 → 抛错
    return user;
  })                                    // 步骤 3：使用数据
  .catch(error => {
    // ⭐ 无论上面哪一步出错，都会流到这里
    console.error("某处出错了:", error.message);
    // 步骤 1 的网络错误 / 步骤 2 的 HTTP 错误 / 步骤 3 的 JSON 错误
    // 全部都能被这一个 .catch() 捕获！
  });
```

这就像同步代码里的 `try...catch`——只要在任何一层出了问题，控制权就会跳到 `catch` 块。但 Promise 版本的优势在于它可以**跨越多个异步步骤**生效。

### 5.2 隐式 try-catch 机制

Promise 的 executor 和 handler 内部都有一个**隐式的 `try...catch` 包裹**。这意味着在这些代码块中抛出的异常会**自动**被捕获并转换为 rejected Promise：

```javascript
// === Executor 中的隐式 try-catch ===
new Promise((resolve, reject) => {
  // 引擎隐式地用 try{ ... } 包裹了这段代码
  throw new Error("executor 抛错了");
  // 等价于：try { throw ... } catch(e) { reject(e); }
})
.catch(err => console.log(err.message));
// 输出: "executor 抛错了"


// === Handler (.then 回调) 中的隐式 try-catch ===
Promise.resolve("data")
  .then(str => {
    // 这里也有隐式 try-catch
    console.log(undefinedVar.name);  // ReferenceError!
    // 等价于：try { ... } catch(e) { reject(e); }
  })
  .catch(err => console.log(err instanceof ReferenceError);  // true
```

这种机制让 Promise 的错误处理变得**自然且一致**——不需要在每个 handler 内部手动写 `try/catch`，异常会自动沿着链传播下去。

### 5.3 错误的三种处理模式

#### 模式一：处理并恢复（Handle and Resume）

如果在 `.catch()` 中正常结束（**没有再次抛出错误**），Promise 链会**恢复为 fulfilled 状态**，继续执行后续的 `.then()`：

```javascript
Promise.reject(new Error("出错了"))
  .catch(error => {
    console.log("错误已处理:", error.message);  // 处理错误
    // 正常返回 → 没有 throw → 错误被视为"已修复"
    return "默认值";  // 这个返回值会让链恢复正常
  })
  .then(value => {
    console.log("恢复后的值:", value);  // "默认值" ← 链恢复了！
  });
```

**执行流**：`rejected` → catch（处理）→ **fulfilled**（恢复！）→ then（正常执行）

#### 模式二：处理后再次抛出（Rethrow）

如果 `.catch()` 遇到了它无法处理的错误，可以用 `throw` 将其**再次抛出**。此时控制权会跳转到下一个 `.catch()`（如果有的话）：

```javascript
Promise.reject(new Error("原始错误"))
  .catch(error => {
    console.log("第一个 catch:", error.message);

    if (error instanceof TypeError) {
      return "修复了";  // 能处理的就处理
    }

    // 不能处理的 → 再次抛出
    console.log("转发给下一个 catch");
    throw error;  // rethrow！
  })
  .then(() => {
    console.log("不会到这里");  // 因为上面的 catch rethrow 了
  })
  .catch(error => {
    console.log("第二个 catch 捕获到:", error.message);  // "原始错误"
  });
```

**执行流**：`rejected` → catch(A)（rethrow）→ **rejected** → catch(B)

#### 模式三：选择性处理

利用 `instanceof` 或 `error.code` 等属性对不同类型的错误进行差异化处理：

```javascript
fetch('/api/data')
  .then(response => response.json())
  .catch(error => {
    // 根据错误类型选择不同的恢复策略
    if (error instanceof TypeError) {
      return { fallback: "默认数据" };  // JSON 解析错误 → 给个默认值
    }
    if (error.message.includes('404')) {
      return { notFound: true };          // 404 → 返回空结果
    }
    if (error.message.includes('network')) {
      return { cached: getFromCache() };   // 网络错误 → 用缓存
    }
    // 其他无法处理的 → 继续抛出让全局 handler 处理
    throw error;
  })
  .then(data => {
    console.log(data);
  });
```

### 5.4 .then(f1, f2) vs .then(f1).catch(f2) —— 一个关键差异

这是一个经典的面试题。这两种写法**看起来相似但行为不同**：

```javascript
// 写法 A：推荐 ✅
promise
  .then(f1)    // f1 成功时的处理
  .catch(f2);  // f1 **或者** 原始 promise 失败时的处理

// 写法 B：有缺陷 ⚠️
promise
  .then(f1, f2); // f1 成功处理，f2 是**原始 promise**失败时的处理
```

**差异在哪里？**

当 **f1 内部抛出异常**（或在 f1 中返回了 rejected Promise）时：

| 写法 | f1 抛错时的行为 |
|------|:--:|
| **A: `.then(f1).catch(f2)`** | f1 的错误让当前 Promise 变为 rejected → **f2 能够捕获到** ✅ |
| **B: `.then(f1, f2)`** | f2 只负责处理**原始 promise** 的 rejection → f1 内部的错误**可能导致 unhandled rejection** ⚠️ |

```javascript
// 具体示例
Promise.resolve("hello")
  .then(data => {
    undefinedVar.foo;  // ReferenceError！f1 内部出错
    return data.toUpperCase();
  })
  .catch(err => {
    console.log("A 方式能抓到:", err.message);  // ✅ "Cannot read properties of undefined"
  });

Promise.resolve("hello")
  .then(data => {
    undefinedVar.foo;  // ReferenceError！f1 内部出错
    return data.toUpperCase();
  }, err => {
    console.log("B 方式不一定能抓到:", err.message);  // ⚠️ 可能抓不到！
  });
// B 方式中 f2 只处理原始 promise 被 reject 的情况
// 但 f1 内部的 throw 导致的是一个新 rejected promise
// 这个新 rejected promise 没有 catch 来处理它 → unhandledrejection
```

**结论**：**始终推荐使用 `.then().catch()` 模式**——它能捕获链条中**任意环节**产生的错误。

### 5.5 unhandledrejection —— 未捕获错误的兜底机制

如果一个 Promise 变成了 rejected 但没有任何地方去 `.catch()` 它，这个错误就会"卡住"——既不被处理也不消失。浏览器提供了全局事件来监控这种情况：

```javascript
// 全局监控所有未被捕获的 Promise 错误
window.addEventListener('unhandledrejection', function(event) {
  console.warn("⚠️ 未捕获的 Promise 错误!");
  console.error("Promise:", event.promise);
  console.error("原因:", event.reason);

  // 可以在这里做统一的错误上报
  logErrorToServer(event.reason);
});

// 测试：创建一个 rejected 但不 catch 的 Promise
Promise.reject(new Error("忘记处理了这个错误"));
// 触发 unhandledrejection 事件
```

在生产环境中，强烈建议至少注册一个 `unhandledrejection` 监听器来做最后的兜底——防止错误"静默消失"导致难以排查的 bug。

## 六、静态方法 —— Promise 工具箱

除了通过 `new Promise()` 创建实例外，Promise 构造函数本身还提供了几个实用的**静态方法**用于常见的组合场景。

### 6.1 Promise.all(iterable) —— 并行执行，全部成功才算成功

**行为**：并行启动所有 Promise，**全部 fulfilled** 才算成功。**任一 rejected** 则整体立刻 rejected（短路失败）。

```javascript
// 基本用法
Promise.all([
  fetch("/api/user"),         // ~300ms
  fetch("/api/posts"),        // ~500ms
  fetch("/api/comments")      // ~200ms
])
  .then(([userRes, postsRes, commentsRes]) => {
    console.log("全部请求成功！");
    // results 数组的顺序与输入数组的顺序一致
    // 不管谁先完成，userRes 始终是第一个元素
  })
  .catch(error => {
    console.error("至少一个请求失败:", error.message);
    // 一旦任何一个 fail，立刻进入 catch（其他的可能还在跑）
  });
```

**特点**：
- 结果数组保持输入顺序（按索引对应）
- **快速失败（Fail-Fast）**：第一个 reject 就触发整体 reject
- 支持 Promise 与普通值混合（非 Promise 值会原样传递）

**适用场景**：多个独立的异步操作**全部成功**后才能进行下一步**

### 6.2 Promise.allSettled(iterable) —— 并行执行，全部结束才算结束（ES2020）

**行为**：等待**所有 Promise 都 settles**（无论是 fulfilled 还是 rejected），**永远不会 reject**。结果是一个包含每个 Promise 状态的对象数组。

```javascript
Promise.allSettled([
  fetch("/api/a"),  // 假设成功
  fetch("/api/b"),  // 假设 404 失败
  fetch("/api/c")   // 假设超时失败
])
  .then(results => {
    results.forEach((result, index) => {
      switch (result.status) {
        case "fulfilled":
          console.log(`[${index}] 成功:`, result.value.status);
          break;
        case "rejected":
          console.log(`[${index}] 失败:`, result.reason.message);
          break;
      }
    });
  });
// 输出：
// [0] 成功: 200
// [1] 失败: Not Found
// [2] 失败: Network timeout
// 所有结果都被保留了！
```

**与 `all` 的关键区别**：

| 维度 | `Promise.all` | `Promise.allSettled` |
|------|:-:|:-:|
| **触发条件** | **全部 fulfilled** | **全部 settled**（任一即可）|
| **有失败时** | 立刻 reject（短路）| **不 reject**，等全部完成 |
| **结果格式** | `[value, value, ...]` | `[{status,value}, {status,reason}, ...]`|
| **用途** | "全部成功才继续" | "我要知道每个人的结果" |

**典型场景**：批量操作后需要知道**哪些成功哪些失败**（如批量上传文件后的结果汇总）

### 6.3 Promise.race(iterable) —— 谁先完成谁赢

**行为**：返回**第一个 settle 的 Promise 的结果**（不管是 fulfilled 还是 rejected）。后面的 Promise 直接被忽略。

```javascript
Promise.race([
  new Promise(r => setTimeout(() => r("A 完成"), 3000)),   // 3秒
  new Promise(r => setTimeout(() => r("B 完成"), 2000)),   // 2秒 ← 最快
  new Promise(r => setTimeout(() => r("C 完成"), 1000)),   // 1秒 ← 最快
])
  .then(result => {
    console.log("赢家:", result);  // "C 完成" —— 第一个完成的！
  });
```

**类比**：赛跑比赛——谁先冲线谁就赢，后面的人的成绩不再重要。

**适用场景**：
- 多个镜像服务器取**最快响应**
- 设置**超时竞争**：`Promise.race([fetch(url), timeout(5000)])`
- 取消令牌（见下文的 `any`）

### 6.4 Promise.any(iterable) —— 谁先成功谁赢（ES2021）

**行为**：返回**第一个 fulfilled 的 Promise 的结果**。rejected 的 Promise 会被**忽略**——除非**全部**都 rejected。

```javascript
Promise.any([
  new Promise((_, r) => setTimeout(() => r(Error("A 失败")), 1000)),
  new Promise(r => setTimeout(() => r("B 成功")), 2000),    // ✅ 第一个成功
  new Promise(r => setTimeout(() => r("C 成功")), 3000),
])
  .then(result => {
    console.log("首个成功:", result);  // "B 成功"
  });
```

**全部失败的特例**：

```javascript
Promise.any([
  new Promise((_, r) => setTimeout(() => r(Error("X")), 1000)),
  new Promise((_, r) => setTimeout(() => r(Error("Y")), 2000)),
])
).catch(aggregateError => {
  console.log(aggregateError.constructor.name);  // "AggregateError"
  console.log(aggregateError.errors);         // [Error("X"), Error("Y")]
  // 全部失败时返回 AggregateError，.errors 包含所有错误
});
```

### 6.5 Promise.resolve / Promise.reject —— 快速创建

```javascript
// Promise.resolve(value) —— 创建一个已 fulfilled 的 Promise
let p1 = Promise.resolve("立即成功");
let p2 = Promise.resolve(42);
let p3 = Promise.resolve({ name: "Alice" });  // 对象也会包装

// Promise.reject(reason) —— 创建一个已 rejected 的 Promise
let e1 = Promise.reject(new Error("立即失败"));

// 主要用途：统一接口
function getData(source) {
  if (cache.has(source)) {
    return Promise.resolve(cache.get(source));  // 从缓存取也返回 Promise
  }
  return fetch(source);                        // 从网络取
}

// 调用方不需要关心数据来自哪里
getData("/api/user").then(handleData);
```

### 6.6 六大静态方法速查表

| 方法 | 参数 | 成功条件 | 失败条件 | 返回值（成功）| 返回值（失败）|
|------|------|---------|---------|------------|------------|
| **`all`** | 可迭代 | **全部** fulfilled | 任一 rejected | `[v1,v2,...]` | （第一个 error）|
| **`allSettled`** | 可迭代 | **全部** settled | 永不 reject | `[{status,value},...]` | —（永不为 reject）|
| **`race`** | 可迭代 | 第一个 **settled** | 同左（第一个） | 第一个 value/error | 同左 |
| **`any`** | 可迭代 | 第一个 **fulfilled** | **全部** rejected | 第一个 value | `AggregateError` |
| **`resolve`** | 任意值 | — | — | 包装后的值 | — |
| **`reject`** | 任意值 | — | — | — | 包装后的 error |

### 案例 1：带超时控制的请求

```javascript
/**
 * 发起一个带超时的 fetch 请求
 * 使用 Promise.race 实现"竞速"模式
 */
function fetchWithTimeout(url, ms = 5000) {
  const fetchPromise = fetch(url);
  const timeoutPromise = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("请求超时")), ms)
  );

  return Promise.race([fetchPromise, timeoutPromise]);
}

// 使用
fetchWithTimeout("/api/slow-endpoint", 3000)
  .then(res => res.json())
  .then(data => console.log("数据:", data))
  .catch(err => {
    if (err.message === "请求超时") {
      console.warn("⏰ 请求超时，请稍后重试");
    } else {
      console.error("其他错误:", err.message);
    }
  });
```

### 案例 2：带重试机制的健壮请求

```javascript
/**
 * 最大重试 N 次的 fetch 封装
 */
function robustFetch(url, options = {}, maxRetries = 3) {
  return new Promise((resolve, reject) => {
    let attempt = 0;

    function attemptFetch() {
      fetch(url, options)
        .then(resolve)                          // 成功 → 直接 resolve
        .catch(error => {
          attempt++;
          if (attempt < maxRetries) {
            console.warn(`第 ${attempt} 次重试...`);
            setTimeout(attemptFetch, 1000 * attempt);  // 指数退避
          } else {
            reject(error);  // 重试次数用完 → 放弃
          }
        });
    }

    attemptFetch();
  });
}

robustGet("/api/flaky", {}, 5)
  .then(data => console.log("终于成功了:", data))
  .catch(err => console.error("彻底失败:", err));
```

### 案例 3：图片渐进式加载

```javascript
/**
 * 加载图片并在 DOM 中显示，完成后移除加载占位图
 * 展示 Promise 链中混合同步和异步操作
 */
function loadAndDisplay(imgUrl, containerId) {
  const container = document.getElementById(containerId);

  // 显示占位图
  showPlaceholder(container);

  return new Promise((resolve, reject) => {
    const img = new Image();
    img.src = imgUrl;

    img.onload = () => {
      removePlaceholder(container);
      container.appendChild(img);
      resolve(img);  // 图片加载成功
    };

    img.onerror = () => {
      showError(container);
      reject(new Error("图片加载失败: " + imgUrl));
    };
  })
  .then(img => {
    console.log("图片显示成功:", img.src);
    img.classList.add("fade-in");
    return img;
  })
  .catch(err => {
    console.error(err.message);
  });
}
```

## 八、陷阱速查

| # | 陷阱 | 现象 | 解决方案 |
|---|------|------|---------|
| 1 | **executor 内的异步 throw 无法 catch** | `setTimeout` 内 throw 不会被 Promise 捕获 | 不要在 executor 的异步回调中 throw；改用 `reject` |
| 2 | **.then(f1, f2) 漏掉 f1 内部错误** | f1 的 throw 可能导致 unhandled rejection | 始终用 `.then(f1).catch(f2)` |
| 3 | **忘记在链尾加 .catch()** | rejected Promise 变成 unhandledrejection | 链的末尾始终要有 `.catch()` |
| 4 | **.finally 返回值被忽略** | `return xxx` 在 finally 里不起作用 | finally 用于清理，不用于返回值 |
| 5 | **Promise.all 的短路失败** | 一个失败导致整体 reject，其他结果丢失 | 用 `allSettled` 如果需要知道每个的结果 |
| 6 | **混淆 race 和 any** | `race` 任一 settle 即返回，`any` 要全部 reject 才失败 | 需要成功选 `any`，需要"最快响应"选 `race` |
| 7 | **循环中创建的 Promise 不在 all 中** | `for` 循环内的异步操作没有被 `await` | 用 `.map()` 先收集所有 Promise 再 `Promise.all` |

### 陷阱详解：executor 中的异步 throw

```javascript
// ❌ 危险：executor 内的异步 throw
new Promise((resolve, reject) => {
  setTimeout(() => {
    throw new Error("异步错误");  // 这个 throw 发生在 executor 已经退出后
                                      // Promise 无法感知到！
  }, 1000);
}).catch(e => {
  console.log("这里永远执行不到");  // 因为 Promise 一直是 pending
});

// ✅ 正确：在异步回调中使用 reject
new Promise((resolve, reject) => {
  setTimeout(() => {
    reject(new Error("异步错误"));  // 通过 reject 正确报告错误
  }, 1000);
}).catch(e => {
  console.log("正确捕获到:", e.message);  // "异步错误" ✅
});
```

## 九、最佳实践总结

### Promise 使用决策树

```
需要处理异步操作？
│
├── 单次简单操作？
│   ├── 是 → Promise + .then/.catch 或 async/await
│   └── 否 → 见下方
│
├── 多个独立操作需要并行？
│   ├── 全部成功才继续？ → Promise.all()
│   ├── 需要知道每个的成败？ → Promise.allSettled()
│   ├── 只要第一个成功？ → Promise.any()
│   └── 只要第一个完成？  → Promise.race()
│
├── 有现成的回调风格 API？
│   └── 需要转成 Promise？（Promisify）
│
└── 需要多次重试/超时控制？
    └── 用 Promise + .race / 循环重试封装
```

### 设计原则

1. **每个链都以 .catch() 结尾**：防止 unhandled rejection 泄漏到全局
2. **优先 .then().catch() 而非 .then(f1, f2)**：前者能捕获更多类型的错误
3. **用 .finally() 做清理**：loading 动画、资源释放、日志记录
4. **合理使用静态方法**：`all`/`allSettled`/`race`/`any` 各有适用场景
5. **Executor 保持简洁**：只做初始化和启动异步任务，不要在里面写复杂的业务逻辑
6. **全局 unhandledrejection 监控**：作为最后一道防线

## 十、知识图谱

```
Promise 核心完整体系
│
├── 本质定位
│   ├── 状态容器：记录异步操作的进展（pending → fulfilled/rejected）
│   ├── 异步操作的契约：白纸黑字的状态约定，可延迟订阅
│   └── 回调问题的根治方案：从"被动通知"变为"主动查询"
│
├── 三种状态生命周期
│   ├── pending（待定）→ result=undefined
│   ├── fulfilled（已兑现）→ result=value
│   ├── rejected（已拒绝）→ reason=error
│   └── 状态单向不可逆 + settled 概念
│
├── 创建：new Promise(executor)
│   ├── executor 立即同步执行
│   ├── resolve(value) → fulfilled
│   ├── reject(reason) → rejected
│   ├── throw 等价于 reject
│   └── 只能调用一次 resolve/reject
│
├── 消费者方法
│   ├── .then(onFulfilled, onRejected?)
│   │   ├── 两个参数：成功回调和失败回调
│   │   └── 可只传一个（忽略失败或成功）
│   │
│   ├── .catch(onRejected)
│   │   └── .then(null, f) 的语法糖，语义更清晰
│   │
│   └── .finally(onFinally)
│       ├── 无参数（不知道结果是什么）
│       ├── 透传 value/error 到下一环
│       ├── 返回值被忽略
│       └── 专用于清理操作
│
│   └── 已 settle Promise 可延迟订阅
│       └── 后续 .then() 仍然能获取最终结果
│
├── then 链式调用 ⭐ 核心
│   ├── 每个 .then()/.catch() 返回全新 Promise
│   │
│   ├── 规则一：返回普通值 → 下一 Promise fulfilled（继续）
│   ├── 规则二：返回 Promise → 暂停等待（关键能力！）
│   └── 规则三：throw / rejected Promise → 下一 Promise rejected
│   │
│   ├── Thenable 对象协议（.thenable 兼容）
│   │   └── 有 .then() 方法的对象被当作 Promise
│   │
│   └── 真正的链 vs 多监听（同一个 Promise 上加多个 .then）
│
├── 错误处理机制
│   ├── 冒泡：错误沿链向下传播到最近的 .catch()
│   ├── 隐式 try-catch：executor 和 handler 内部的自动包裹
│   ├── 三种处理模式
│   │   ├── 处理并恢复（正常返回 → 链恢复 fulfilled）
│   │   ├── 处理后 rethrow（throw → 传递给下一个 catch）
│   │   └── 选择性处理（instanceof 分发）
│   │
│   ├── .then(f1,f2) vs .then(f1).catch(f2) 差异
│   │   └── 推荐后者（捕获范围更大）
│   │
│   └── unhandledrejection 全局事件（兜底监控）
│
│
├── 静态方法
│   ├── Promise.resolve(value) → 快速创建 fulfilled Promise
│   ├── Promise.reject(reason) → 快速创建 rejected Promise
│   ├── Promise.all([...]) → 全部成功才算成功（短路失败）
│   ├── Promise.allSettled([...]) → 全部结束才算结束（保留所有结果）
│   ├── Promise.race([...]) → 第一个 settle 的结果（竞速）
│   └── Promise.any([...]) → 第一个 fulfilled 的结果
│
├── 从回调到 Promise 的升级
│   ├── 回调：控制反转 + 信任危机 + 回调地狱
│   └── Promise：状态机 + 链式调用 + 错误冒泡
│       ↓
│   └── async/await：同步风格的异步代码（下一篇主题）
│
└── 最佳实践
    ├── 每个链末尾都有 .catch()
    ├── .then().catch() 优于 .then(f1, f2)
    ├── .finally() 用于清理（loading / 日志 / 资源释放）
    ├── 合理选择 all/allSettled/race/any
    ├── 全局 unhandledrejection 监控
    └── Executor 保持简洁
```
