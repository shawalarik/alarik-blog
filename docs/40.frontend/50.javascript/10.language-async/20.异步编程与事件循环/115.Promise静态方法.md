# Promise 静态方法 —— resolve、reject、all、race、allSettled、any

> **核心内容**：Promise 的六个静态方法是异步编程的"工具箱"——`resolve/reject` 是工厂，`all/allSettled/race/any` 是组合器。本文逐一拆解每个方法的内部机制、行为差异和实战场景。

## 一、为什么需要静态方法？

在深入每个 API 之前，我们先回答一个根本问题：**为什么 Promise 需要这些静态方法？**

### 从实例方法到静态方法：能力边界的扩展

你已经熟悉了 Promise 的实例方法（`.then()`、`.catch()`、`.finally()`），它们是"消费者"工具——用来消费一个已经存在的 Promise 的结果。但现实开发中，我们经常面临以下需求：

1. **我手里没有 Promise，但需要一个已完成的 Promise**——比如写单元测试时想 mock 一个成功/失败的异步操作。
2. **我有多个 Promise，想同时处理它们**——比如并行下载 5 张图片。
3. **我想让多个 Promise 竞速，取最快的结果**——比如请求多个 CDN 镜像源，谁快用谁。
4. **我想知道所有 Promise 的最终状态**——比如批量上传文件，即使部分失败也要展示完整结果。

这些需求都无法用实例方法解决。**静态方法正是为了填补这个空白而设计的**——它们不依赖于某个具体的 Promise 实例，而是作为"工厂"或"组合器"，从无到有地创建或组合 Promise。

**通俗类比**：如果把 Promise 实例比作一辆已经出厂的汽车（你可以驾驶它、给它加油、检查它的状态），那么静态方法就是汽车制造厂——`resolve/reject` 是两台不同的生产流水线，分别生产新车和故障车；而 `all/allSettled/race/any` 则是四条不同的组装线，把多辆车按不同规则组合成一支车队。没有这个制造厂，你就永远只能使用别人给你的现成的车，无法自己创造或组合。

### 六个方法的角色分工

可以把这六个静态方法分为两大阵营：

| 类别 | 方法 | 角色定位 | 一句话类比 |
|------|------|---------|-----------|
| **工厂方法** | `Promise.resolve()` | 创建一个已成功的 Promise | 印钞机——直接印出一张面值确定的钞票 |
| **工厂方法** | `Promise.reject()` | 创建一个已失败的 Promise | 开具罚单——直接开出一张确定金额的罚单 |
| **组合器** | `Promise.all()` | 全部成功才算成功 | 拼图游戏——缺一块都不算完成 |
| **组合器** | `Promise.allSettled()` | 收集所有最终结果 | 考试成绩单——不管及格不及格都记录下来 |
| **组合器** | `Promise.race()` | 取第一个结束的结果 | 赛跑——谁先撞线谁赢（哪怕爬过终点的也算）|
| **组合器** | `Promise.any()` | 取第一个成功的结果 | 面试录用——只要有一个通过就录用，全挂才报错 |

### 学习路线建议

推荐按以下顺序学习，因为后面的方法会引用前面的概念：

```
工厂方法 → resolve / reject（理解 Thenable 协议）
    ↓
组合器基础 → all（最常用的并行模式）
    ↓
容错变体 → allSettled（all 的容错版）
    ↓
竞速模式 → race / any（理解 settled vs fulfilled 的关键区别）
```

## 二、工厂方法 —— Promise.resolve() 与 Promise.reject()

### 2.1 Promise.resolve(value) —— 快速创建成功 Promise

#### 基本用法

`Promise.resolve()` 是创建一个**已处于 fulfilled 状态**的 Promise 的最简方式。它接受一个参数作为这个 Promise 的结果值：

```javascript
// 创建一个结果为 42 的已完成 Promise
let p1 = Promise.resolve(42);
p1.then(console.log); // 42

// 创建一个结果为字符串的已完成 Promise
let p2 = Promise.resolve('Hello');
p2.then(console.log); // 'Hello'

// 甚至可以包装 null 和 undefined
let p3 = Promise.resolve(null);
p3.then(v => console.log(v));     // null
let p4 = Promise.resolve(undefined);
p4.then(v => console.log(v));     // undefined

// 特殊值也原样保留
let p5 = Promise.resolve(0);
p5.then(v => console.log(v));     // 0（不是 falsy 被过滤！）
let p6 = Promise.resolve(false);
p6.then(v => console.log(v));     // false（同样原样保留）
```

等价于以下写法，但更简洁：

```javascript
// 手动写法（冗长）
let p = new Promise(resolve => {
  resolve(42);
});

// resolve 写法（简洁）
let p = Promise.resolve(42);
```

#### 为什么需要它？——三大核心场景

你可能会问："既然可以直接用 `new Promise()`，为什么要多此一举？" 答案在于**场景**——`Promise.resolve()` 的价值不在于它能做什么（毕竟 `new Promise()` 也能做），而在于它在特定场景下能做得**更优雅**：

##### 场景一：统一同步/异步接口（最重要的用途）

这是 `Promise.resolve()` 最经典的使用场景。想象你正在编写一个数据加载函数，它有两种获取数据的方式：如果缓存中有数据就直接返回（同步），否则发起网络请求（异步）。问题来了——调用者该怎么用你的函数？

```javascript
// ❌ 不好的设计：调用者需要判断返回类型
function getDataBad(useCache) {
  if (useCache && cache.has('key')) {
    return cache.get('key');        // 返回普通值！
  }
  return fetch('/api/data').then(r => r.json());  // 返回 Promise！
}

// 调用者的噩梦：
const result = getDataBad(true);
if (result instanceof Promise) {      // 还要做类型判断？！
  result.then(data => console.log(data));
} else {
  console.log(result);                // 分支处理...
}
```

这种设计迫使调用者去判断返回值的类型——这违反了**接口一致性原则**，让代码变得复杂脆弱。而 `Promise.resolve()` 提供了一个优雅的解决方案：

```javascript
// ✅ 好的设计：始终返回 Promise
function getDataGood(useCache) {
  if (useCache && cache.has('key')) {
    // 即使是同步数据，也包装成 Promise 返回
    return Promise.resolve(cache.get('key'));
  }
  // 异步情况本来就已经返回 Promise
  return fetch('/api/data').then(r => r.json());
}

// 调用者永远可以用同一种方式处理
getDataGood(true).then(data => console.log(data));
getDataGood(false).then(data => console.log(data));
// 无论走哪个分支，调用代码完全一样！
```

**这就是 "接口一致性"原则的威力**——无论底层实现是同步还是异步，对外暴露的都是同一个 Promise 接口。调用者可以用完全相同的方式处理结果，不需要做任何类型判断。这种模式在库和框架开发中被广泛使用，因为库的作者不知道使用者会在什么上下文中调用他们的 API。

**通俗类比**：这就像快递服务。无论你寄的东西是在本地仓库（同步可取）还是需要从远方运过来（异步等待），快递公司都会给你一张统一的运单号（Promise）。你只需要拿着运单号等包裹就好，不需要关心包裹是从隔壁仓库还是从南极运来的。

##### 场景二：测试中 mock 异步结果

```javascript
// 在单元测试中模拟一个成功的 API 调用
const mockApiResponse = Promise.resolve({
  id: 1,
  name: 'Test User',
  email: 'test@example.com',
  role: 'admin'
});

// 被测试的代码无需修改就能处理这个 mock 数据
async function displayUser(userPromise) {
  const user = await userPromise;  // 真实代码
  console.log(`欢迎, ${user.name}`);
}

displayUser(mockApiResponse); // 正常工作，无需真实 API
```

测试的价值在于隔离——你只想验证"当拿到用户数据后显示逻辑是否正确"，而不想依赖真实的网络请求。`Promise.resolve()` 让你能用一个普通的对象冒充一个"已经完成的网络请求"，被测代码完全感知不到区别。

##### 场景三：链式调用中的快速值传递

在 Promise 链的中间环节，有时你需要根据条件提前返回一个固定值，然后继续后续的处理流程：

```javascript
fetchUser()
  .then(user => {
    if (!user) {
      // 用户不存在时，快速返回一个"空用户"对象作为默认值
      // 这样后续的 .then() 就不会因为 undefined 而报错
      return Promise.resolve({ id: null, name: 'Guest', preferences: {} });
    }
    // 用户存在则正常获取偏好设置
    return fetchUserPreferences(user.id);
  })
  .then(preferences => {
    // 无论上面走了哪个分支，这里都能安全执行
    console.log(`主题色: ${preferences.theme || 'light'}`);
  });
```

注意这里也可以直接 `return { id: null, ... }` 而不用 `Promise.resolve()` 包装，因为 `.then()` 的 handler 本身就会自动将返回值包装成 Promise。但在某些情况下显式使用 `Promise.resolve()` 能让代码意图更明确——告诉阅读者："我这里故意返回的是一个已解决的 Promise"。

#### ⭐ 核心机制：Thenable 对象的"拆包"

这是 `Promise.resolve()` 最重要但也最容易被忽视的特性：**当传入的对象带有 `.then()` 方法时，它会将这个对象"拆包"为一个真正的 Promise。这种对象被称为 Thenable。**

##### 什么是 Thenable？

任何拥有 `.then()` 方法的对象都是 Thenable。这个名字来自 "then-able"（有 `then` 的能力）。它不一定是一个真正的原生 Promise，可能是一个自定义类实例、一个来自其他库的类 Promise 对象，甚至就是一个普普通通的 JavaScript 字面对象：

```javascript
// 形式一：字面对象 Thenable
let thenable1 = {
  then: function(resolve, reject) {
    resolve(99);
  }
};

// 形式二：自定义类的实例
class MyWrapper {
  constructor(value) {
    this._value = value;
  }
  then(resolve) {
    resolve(this._value);
  }
}
let thenable2 = new MyWrapper(88);

// 形式三：第三方库的类 Promise 对象（如 jQuery Deferred）
// jQuery.ajax() 返回的就是一个 Thenable（不是原生 Promise）
```

##### 拆包过程演示

```javascript
// 这是一个 Thenable——不是真正的 Promise，但有 then 方法
let thenable = {
  then: function(resolve, reject) {
    console.log('then 方法被调用了！');
    resolve(99);
  }
};

// Promise.resolve 会自动识别并拆包
let p = Promise.resolve(thenable);

console.log('创建完成');
p.then(console.log);

// 输出顺序：
// 1. 'then 方法被调用了！'  ← 拆包发生在 resolve 调用时，是同步的！
// 2. '创建完成'
// 3. 99                      ← 微任务队列中的回调
```

**逐步拆解执行过程**：

1. `Promise.resolve(thenable)` 被调用
2. 引擎检测到 `thenable` 有 `.then()` 属性且值为函数
3. 引擎**立即（同步）**调用 `thenable.then(resolve, reject)`——这里的 resolve 和 reject 是引擎为新创建的 Promise 准备的两个回调函数
4. `thenable` 的 `then` 方法内部调用 `resolve(99)`——这个 resolve 就是步骤 3 传进去的那个
5. 于是新创建的 Promise p 变为 fulfilled 状态，值为 99
6. `p.then(console.log)` 注册的回调进入微任务队列，在当前宏任务结束后执行

**关键细节**：Thenable 的 `then` 方法是**同步调用**的，不是异步的！这是很多开发者误解的地方。`Promise.resolve()` 对 Thenable 的处理过程本身是同步的，只是最终结果的传递是通过微任务机制异步的。

##### 为什么需要 Thenable 拆包？

这是**跨库互操作性**的关键设计。让我们回到历史背景来理解这个问题：

在 ES2015（ES6）引入原生 Promise 之前，JavaScript 世界中已经存在多种异步方案：
- jQuery 的 `$.Deferred` 和 `$.ajax` 返回的对象
- Q.js 库的 Promise 实现
- Bluebird 库的高性能 Promise
- 当时的各种 polyfill

每种实现都有自己的构造函数和原型链。如果 `Promise.resolve()` 只接受原生 Promise，那么当你拿到一个 jQuery Deferred 对象时就没办法把它融入原生 Promise 体系了。

**Thenable 协议解决了这个问题**——它是一种"鸭子类型"（duck typing）设计：只要一个对象有 `.then()` 方法，不管它是哪个库创造的、继承自哪个类，都能被当作 Promise 来处理。这让 JavaScript 社会的不同"部落"能够和平共处、互通有无。

```javascript
// jQuery 的 $.ajax 返回的是 jqXHR 对象（不是原生 Promise）
// 但 jqXHR 有 .then() 方法，所以它是 Thenable！

// 可以直接混入原生 Promise 体系
let data = await Promise.resolve($.ajax('/api/data')); // ✅ 完美工作
```

**通俗类比**：想象你在机场行李提取处。原生 Promise 就像机场自己的标准行李箱，有统一的大小和标签格式；而 Thenable 就像一个被塑料膜包裹的各种形状的箱子——可能是圆形的桶、长方形的盒子，甚至是三角形的手提袋。它们看起来各不相同，但都有一个共同的特征：有一个把手（`then` 方法）可以让传送带系统抓取。`Promise.resolve()` 的作用就是识别这个把手，帮你把这些形状各异的包裹拆开，取出里面的真正内容，放到标准的机场手推车上（变成原生 Promise）。这样无论乘客用的是哪种行李箱，提取流程都是一样的。

##### Thenable 导致的陷阱

理解 Thenable 对于调试非常重要，因为它可能导致一些令人困惑的行为：

```javascript
// ⚠️ 陷阱一：非函数的 then 属性
let weirdObj = { then: 'hello' };
let p = Promise.resolve(weirdObj);
// TypeError: then is not a function！
// 因为 Promise.resolve 发现 obj 有 then 属性，
// 尝试将其作为函数调用，但它是个字符串

// ✅ 安全：then 属性为 undefined 或不存在
let normalObj = { name: 'Alice' };
let p2 = Promise.resolve(normalObj); // 正常，不会被当作 Thenable

// ⚠️ 陷阱二：原型链上的 then
class Base {
  then() { console.log('Base then'); }
}
class Child extends Child {}
let child = new Child();
Promise.resolve(child); // 会触发 Base.prototype.then！
// 因为 then 在原型链上也能被发现

// ⚠️ 陷阱三：Thenable 中抛出异常
let throwingThenable = {
  then() {
    throw new Error('Thenable 内部出错');
  }
};
Promise.resolve(throwingThenable).catch(err => {
  console.log(err.message); // 'Thenable 内部出错'
  // Thenable 内部的 throw 会被捕获并转化为 rejected Promise
});
```

**特别值得注意的是第三个陷阱**：Thenable 的 `then` 方法内部抛出的异常不会导致程序崩溃，而是会被自动捕获并转化成一个 rejected 的 Promise。这是因为 `Promise.resolve()` 在调用 `thenable.then(resolve, reject)` 时，内部相当于给 `then` 方法的执行包裹了一层隐式的 try-catch。这与原生 Promise executor 的行为是一致的。

##### 嵌套 Thenable 的递归展开

`Promise.resolve()` 不仅会展开一层 Thenable，还会**递归展开嵌套的 Thenable**：

```javascript
// 嵌套 Thenable
let nestedThenable = {
  then(resolve) {
    // 这里又返回了一个 Thenable
    resolve({
      then(innerResolve) {
        innerResolve(42);  // 最终值
      }
    });
  }
};

Promise.resolve(nestedThenable).then(v => console.log(v));
// 输出: 42 —— 经过两层拆包后得到最终值
```

更常见的情况是嵌套的 Promise：

```javascript
// 嵌套的 Promise 会被"展平"
let p1 = Promise.resolve(1);           // Promise<1>
let p2 = Promise.resolve(p1);          // Promise<Promise<1>>？
p2.then(v => console.log(v));          // 输出: 1，不是 [object Promise]！

// 无论嵌套多少层都会展平
let p3 = Promise.resolve(Promise.resolve(Promise.resolve('deep')));
p3.then(v => console.log(v));          // 输出: 'deep'
```

这种行为被称为 **Promise 展平**（Promise Flattening）或 **一致化**（Consistency）。它的好处是你永远不用担心得到 `Promise<Promise<T>>` 这种"俄罗斯套娃"式的结构——`Promise.resolve()` 保证输出的一定是一个普通的 `Promise<T>`。

### 2.2 Promise.reject(reason) —— 快速创建失败 Promise

#### 基本用法

与 `resolve()` 对称，`Promise.reject()` 创建一个**已处于 rejected 状态**的 Promise：

```javascript
let p = Promise.reject(new Error('出错了'));
p.catch(err => console.log(err.message)); // '出错了'
```

等价于：

```javascript
let p = new Promise((resolve, reject) => {
  reject(new Error('出错了'));
});
```

与 `resolve()` 类似，`reject()` 接受任意类型的参数作为拒绝原因（reason），但最佳实践是**始终传入 Error 对象**，这样可以保留错误堆栈信息便于调试：

```javascript
// ✅ 推荐：传入 Error 对象
Promise.reject(new Error('数据库连接超时'))
  .catch(err => console.error(err.stack)); // 完整堆栈

// ❌ 不推荐：传入字符串（丢失堆栈信息）
Promise.reject('出错了')
  .catch(msg => console.error(msg)); // 只有字符串，不知道哪里出的错
```

#### 使用场景

##### 场景一：提前校验与快速失败（Guard Clause）

在进入复杂的异步逻辑前先检查前置条件，不满足条件则立即拒绝，避免无意义的资源消耗：

```javascript
function fetchUserById(id) {
  // Guard Clause：防御性校验
  if (!id) {
    return Promise.reject(new Error('用户 ID 不能为空'));
  }
  if (typeof id !== 'number' || id < 0) {
    return Promise.reject(new Error(`无效的用户 ID: ${id}`，期望正整数));
  }
  // 校验通过后才发请求
  return fetch(`/api/users/${id}`).then(r => r.json());
}

fetchUserById(-1).catch(err => console.error(err.message));
// '无效的用户 ID: -1，期望正整数'
// 不会浪费网络请求！
```

这种"快速失败"（Fail Fast）模式的好处是：**错误在入口处就被拦截**，不会传播到深层逻辑中去产生更难追踪的问题。同时节省了不必要的计算和网络资源。

##### 场景二：测试中模拟错误

```javascript
// 模拟各种类型的错误
const networkError = Promise.reject(
  Object.assign(new Error('Network request failed'), { code: 'NETWORK_ERROR', status: 0 })
);

const authError = Promise.reject(
  Object.assign(new Error('Unauthorized'), { code: 'AUTH_ERROR', status: 401 })
);

const serverError = Promise.reject(
  Object.assign(new Error('Internal Server Error'), { code: 'SERVER_ERROR', status: 500 })
);
```

##### 场景三：状态机中的非法状态

```javascript
/**
 * 订单状态机：只有特定状态转换才是合法的
 * PENDING -> PAID -> SHIPPED -> DELIVERED
 */
async function transitionOrder(orderId, newState) {
  const order = await getOrder(orderId);

  const validTransitions = {
    PENDING: ['PAID', 'CANCELLED'],
    PAID: ['SHIPPED', 'REFUNDED'],
    SHIPPED: ['DELIVERED'],
    DELIVERED: [],
    CANCELLED: []
  };

  const allowed = validTransitions[order.state] || [];
  if (!allowed.includes(newState)) {
    return Promise.reject(
      new Error(`非法状态转换: ${order.state} -> ${newState}`)
    );
  }

  return updateOrderState(orderId, newState);
}
```

#### ⚠️ 关键差异：reject 不会拆包 Thenable！

这是一个**极其重要**的区别，也是最常见的混淆来源之一：

```javascript
// ====== resolve 会拆包 Thenable ======
let thenable = {
  then: function(resolve) {
    console.log('Thenable.then 被调用');
    resolve(100);
  }
};
Promise.resolve(thenable).then(v => console.log('resolve 结果:', v));
// 输出：
// 'Thenable.then 被调用'   ← then 方法被执行了
// 'resolve 结果: 100'       ← 得到拆包后的值 100

// ====== 但 reject 不会拆包！ ======
Promise.reject(thenable).catch(e => {
  console.log('reject 结果 === thenable?', e === thenable);
  // 输出: true —— 原样传入，未被拆包！
  // Thenable.then 从未被调用
});
```

**为什么会有这种不对称设计？** 让我们从语义层面思考：

- `Promise.resolve(thenable)` 的意思是"请把这个值解析为一个 Promise"。既然它有 `then` 方法说明它可能携带某种异步逻辑，那我就应该调用它的 `then` 来获取最终值——这是一种**"信任并委托"**的态度。

- `Promise.reject(thenable)` 的意思是以这个东西为理由拒绝。reason 是对"为什么失败"的回答——它应该是**错误本身**而不是某种需要进一步解析的容器。如果 `reject` 也去调用 `then` 方法，那么一个内部会 `resolve()` 的 Thenable 反而会导致整个操作变成成功——这在语义上完全不合理。想象一下：你对老板说"这个项目失败了"，然后拿出一份报告。老板应该看这份报告的内容来判断失败原因，而不是去执行报告上写的"下一步操作"。`reject` 就是交出原始报告，不做任何加工。

**类比**：`Promise.resolve()` 像快递员收到包裹后会拆开检查里面的物品（即使里面还有一个小包裹也会继续拆）；而 `Promise.reject()` 更像拒收信件——信件本身被退回给寄件人，但邮局的人不会打开去看里面写了什么，更不会按照信件里的"指示"去行动。

### 2.3 resolve vs reject 速查表

| 特性 | `Promise.resolve(value)` | `Promise.reject(reason)` |
|------|--------------------------|--------------------------|
| 返回状态 | fulfilled | rejected |
| 结果值 | value（可以是任意类型）| reason（**强烈建议**用 Error 实例）|
| Thenable 处理 | **自动拆包**（递归解包到最内层）| **不拆包**（原样包装，then 不被调用）|
| 嵌套 Promise | **展平**（`Promise<Promise<T>>` → `Promise<T>`）| 不展平 |
| then 内部 throw | 自动转为 rejected Promise | N/A（then 根本不被调用）|
| 典型使用场景 | 统一接口、mock 成功、链式传值 | 提前校验（Guard Clause）、mock 错误、非法状态拒绝 |

## 三、组合器 —— Promise.all() 并行全部

### 3.1 核心概念

`Promise.all()` 是最常用、最重要的组合器，它的行为可以用一句话概括：**"全部成功才算成功，一个失败全盘皆输。"**

```javascript
Promise.all([
  Promise.resolve(1),
  Promise.resolve(2),
  Promise.resolve(3)
]).then(results => console.log(results)); // [1, 2, 3]
```

语法格式：

```javascript
let promise = Promise.all(iterable);
```

- **参数**：一个可迭代对象（通常是数组），元素可以是 Promise 也可以是普通值
- **返回值**：一个新的 Promise

**通俗类比**：`all()` 就像拼图游戏——你必须集齐最后一块碎片才能看到完整的画面。哪怕你完成了 999 块，只差最后一块，这幅画仍然是不完整的。这种"全有或全无"的策略在某些场景下非常合适（比如加载网页需要的 CSS、JS、字体文件缺一不可），但在另一些场景下又过于严格了（后面会介绍 `allSettled()` 作为替代）。

### 3.2 行为详解 —— "全有或全无"契约

#### 成功路径：顺序保证机制

当数组中的**所有** Promise 都变为 fulfilled 时，`Promise.all()` 返回的 Promise 也变为 fulfilled，结果是一个数组。**最重要的是：元素的顺序与原始数组的顺序一致**，而不是按照完成先后排序：

```javascript
// 注意：虽然完成时间不同，但结果顺序不变
Promise.all([
  new Promise(resolve => setTimeout(() => resolve('A'), 3000)), // 最慢：3 秒
  new Promise(resolve => setTimeout(() => resolve('B'), 2000)), // 中等：2 秒
  new Promise(resolve => setTimeout(() => resolve('C'), 1000))  // 最快：1 秒
]).then(results => console.log(results));
// 3 秒后（最慢的那个完成后）才输出: ['A', 'B', 'C']
// 不是 ['C', 'B', 'A']！
```

**顺序保证是 `all()` 的核心承诺之一**，也是它最有价值的设计决策之一。无论各个 Promise 以什么顺序完成，结果数组始终与输入数组保持一一对应关系。这意味着你可以安全地用索引来访问特定位置的结果：

```javascript
const [userResp, postsResp, friendsResp] = await Promise.all([
  fetch('/api/user'),
  fetch('/api/posts'),
  fetch('/api/friends')
]);
// userResp 一定是 /api/user 的响应
// postsResp 一定是 /api/posts 的响应
// friendsResp 一定是 /api/friends 的响应
// 无需额外的标识字段来区分！
```

**为什么顺序保证如此重要？** 试想如果没有这个保证，你拿到结果数组后将无法确定哪个结果对应哪个请求。你不得不在每个 Promise 里手动添加标识信息，或者改用对象而非数组来收集结果——这大大增加了使用的复杂性。

**通俗类比**：就像餐厅同时做多道菜。虽然有的菜炒得快（只需 1 分钟的凉菜），有的慢（需要 3 小时的慢炖汤），但上菜时服务员会按照点餐菜单的顺序依次摆盘——第一道永远是点的第一个菜，第二道是第二个。顾客拿到的不仅是一整套完整的菜肴，而且每道菜的位置是可以预期的。如果服务员按做好就上的顺序摆盘，顾客就得自己回忆哪道菜是什么了。

**内部实现原理**：`all()` 内部维护一个与输入数组等长的结果数组和一个计数器。每当一个 Promise fulfill 时，就把结果存入对应索引位置，计数器加一。当计数器等于数组长度时，返回结果数组。这就解释了为什么顺序总是正确的——结果是根据索引存放的，而不是根据完成顺序。

#### 非 Promise 值的处理

`all()` 数组中可以混入非 Promise 的普通值。它们会被**原样传递**到结果数组的对应位置，就像它们是"瞬间完成"的 Promise 一样：

```javascript
Promise.all([
  42,                          // 普通值 → 瞬间"完成"
  'Hello',                     // 普通值 → 瞬间"完成"
  Promise.resolve('World'),    // Promise → 正常等待
  new Promise(r => setTimeout(() => r('!'), 1000)) // Promise → 等 1 秒
]).then(results => console.log(results));
// 约 1 秒后输出: [42, 'Hello', 'World', '!']
```

**这个特性的实用价值远比看起来大**：它允许你把一些**同步计算的配置参数、常量值、缓存命中数据和异步获取的数据混合在一起处理**，无需额外的包装步骤。比如你可以在请求参数里同时放入已知的配置和需要异步获取的数据：

```javascript
function loadPageData(pageId) {
  return Promise.all([
    pageId,                              // 同步：页面 ID（用于后续渲染）
    getConfig(),                         // 可能同步也可能异步
    fetchPageContent(pageId),            // 异步：页面内容
    pageId > 0 ? fetchPrevPage(pageId - 1) : null  // 条件性的异步
  ]).then(([id, config, content, prevPage]) => {
    render({ id, config, content, prevPage });
  });
}
```

#### 失败路径 —— "短路效应"

这是 `all()` 最需要小心对待的行为：**只要有一个 Promise 被 reject，整个 `all()` 立即 reject，忽略其他尚未完成的 Promise**：

```javascript
Promise.all([
  new Promise(resolve => setTimeout(() => resolve('OK'), 1000)),  // 1秒后成功
  new Promise((_, reject) => setTimeout(() => reject(new Error('失败了!')), 2000)), // 2秒后失败
  new Promise(resolve => setTimeout(() => resolve('也会被忽略'), 3000))  // 3秒后成功
]).catch(err => console.log(err.message));
// 2 秒后输出: '失败了!'
// 第三个 Promise 即使 3 秒后成功也不会触发任何回调
```

**短路的精确行为分解**：

1. `all()` 开始监听数组中的所有 Promise
2. 第 1 个 Promise 在 1 秒后 fulfill——结果被记录，计数器 +1
3. 第 2 个 Promise 在 2 秒后 reject——**`all()` 立即以同样的 reason reject**
4. 第 3 个 Promise 的监听器被移除（不再关注它的结果）
5. `.catch()` 收到错误

**关于"取消"的重要澄清**：`all()` 的短路只是**不再监听后续结果**，并不会真正取消正在进行的底层任务。那些仍在运行的 Promise（如网络请求、定时器、文件读写）会继续执行完毕，只不过它们的 settle 结果变成了无人关心的"孤儿"。这在网络请求的场景下意味着服务器仍然会处理请求并发送响应，只是客户端已经不在意了。

**类比**：就像接力赛跑，一名选手摔倒后比赛立刻终止——裁判宣布比赛结束，停止计时。但其他选手不会凭空消失，他们只是在另一个维度继续跑完了而已，只是成绩不被记录。如果你希望选手真的停下来（取消网络请求），需要配合 `AbortController` 使用（后面章节会详细讲解）。

### 3.3 实战案例：并行加载多个资源

这是 `all()` 最经典、最高频的使用模式——并行发起多个独立请求，等待全部完成后统一处理：

```javascript
/**
 * 加载用户的完整资料页
 * 同时发起三个独立请求，全部成功后合并数据
 */
function loadUserProfile(userId) {
  return Promise.all([
    fetch(`/api/users/${userId}`).then(r => r.json()),           // ① 基本信息
    fetch(`/api/users/${userId}/posts`).then(r => r.json()),    // ② 文章列表
    fetch(`/api/users/${userId}/followers`).then(r => r.json()) // ③ 粉丝列表
  ]).then(([user, posts, followers]) => {
    // 解构赋值——结果按 [①②③] 的顺序对应
    return {
      ...user,
      posts,
      followersCount: followers.length,
      loadedAt: Date.now()
    };
  });
}

// 调用
loadUserProfile(123).then(profile => {
  console.log(`用户 ${profile.name} 有 ${profile.posts.length} 篇文章`);
});
```

**性能优势量化分析**：假设三个请求各自需要的时间分别为 150ms、200ms、180ms。

- **串行执行**：总时间 = 150 + 200 + 180 = **530ms**
- **all() 并行执行**：总时间 ≈ max(150, 200, 180) = **200ms**（取最长的那一个）

加速比达到 **2.65 倍**！而且随着请求数量增加，理论上加速比可以无限接近于请求数量（当然受限于浏览器的最大并发连接数限制，通常同一域名约 6 个）。

### 3.4 进阶模式：两阶段加载

在实际项目中，经常遇到一种更细粒度的并行模式：先并行发送所有 HTTP 请求拿到 Response 头（此时已确认 HTTP 状态码），再并行解析所有的 JSON body：

```javascript
let urls = [
  'https://api.github.com/users/alarik',
  'https://api.github.com/users/taylorotwell',
  'https://api.github.com/users/sindresorhus'
];

// ========== 第一阶段：并行发送所有请求 ==========
// 此时只拿到 Response 对象（HTTP 请求已完成）
// 但 body 流还没有读取
Promise.all(urls.map(url => fetch(url)))
  .then(responses => {
    // ✅ 此处可以做快速的 HTTP 状态码检查
    const failed = responses.filter(r => !r.ok);
    if (failed.length > 0) {
      console.warn(`${failed.length} 个请求返回了非 200 状态码`);
    }

    // ========== 第二阶段：并行解析所有 JSON body ==========
    // body 解析通常是 CPU 密集型的（JSON.parse）
    // 并行解析可以利用多核 CPU（取决于浏览器实现）
    return Promise.all(responses.map(r => r.json()));
  })
  .then(users => {
    // users 是完全解析后的 JavaScript 对象数组
    users.forEach(u => console.log(`${u.login}: ${u.name}`));
  });
```

**这种两阶段模式的优势不仅仅是"分了两步"那么简单**：

1. **更早的错误发现**：第一阶段完成后你就知道哪些请求返回了 404/500，不必等到昂贵的 JSON 解析之后才发现问题
2. **更好的进度反馈**：你可以在 UI 上显示"N 个请求已接收响应，正在解析..."
3. **内存效率**：Response body 默认是流式读取的，分段解析比分批一次性解析所有大响应更节省内存
4. **可插拔的中间处理**：你可以在两个阶段之间插入日志、缓存、压缩等中间件逻辑

### 3.5 all() 与 async/await 的结合

现代 JavaScript 开发中，`all()` 几乎总是和 `async/await` 配合使用，代码更加清晰易读：

```javascript
// ✅ 现代写法：async/await + 解构
async function loadDashboard(userId) {
  const [user, notifications, messages] = await Promise.all([
    fetchUser(userId),                    // 用户信息
    fetchNotifications(userId),           // 通知列表
    fetchUnreadCount(userId)              // 未读消息数
  ]);

  return {
    user,
    notificationCount: notifications.length,
    unreadCount: messages.unread,
    lastActive: user.lastLogin
  };
}
```

对比传统的 `.then()` 链式写法，`await` 版本的优势在于：
- **变量命名自由**：不需要依赖数组索引或解构位置来推断含义
- **错误处理自然**：可以用外层的 `try/catch` 包裹所有逻辑
- **中间操作方便**：可以在 `await` 之后、下一个 `await` 之前插入任意同步逻辑

## 四、组合器 —— Promise.allSettled() 全量收集

### 4.1 核心概念与动机

`Promise.all()` 的"短路失败"策略在某些场景下过于严格了。考虑以下实际场景：

批量上传 10 个文件到服务器。如果第 3 个文件因为文件名包含非法字符而失败，`all()` 会立即 reject——你连其余 7 个文件是否成功都不知道。但业务上你可能希望：**即使部分文件上传失败也要知道每一個的上传结果**，这样前端才能正确地显示"8/10 上传成功"这样的进度信息，并且只重试那 2 个失败的文件。

**`Promise.allSettled()` 正是为了解决这类需求而生**。它的行为哲学完全不同：**我不做价值判断，我只做客观记录。不管你是成功还是失败，把最终状态如实汇报给我。**

```javascript
Promise.allSettled([
  Promise.resolve(33),
  Promise.reject(new Error('出错啦')),
  Promise.resolve(66)
]).then(results => console.log(JSON.stringify(results, null, 2)));
```

输出结果：

```json
[
  { "status": "fulfilled", "value": 33 },
  { "status": "rejected",  "reason": {} },
  { "status": "fulfilled", "value": 66 }
]
```

注意返回值的结构与 `all()` 截然不同：**不是简单的值数组 `[v1, v2, v3]`，而是状态描述对象数组 `[{status, value}, {status, reason}, ...]`**。每个对象都有固定的两个字段：

| 当 Promise 被 fulfill 时 | 当 Promise 被 reject 时 |
|--------------------------|------------------------|
| `{ status: "fulfilled", value: <结果值> }` | `{ status: "rejected", reason: <拒绝原因> }` |

**为什么需要两个不同的字段名？** 这是因为成功时的"产出"和失败时的"理由"本质上是不同性质的信息——成功时我们关心的是**结果值**（value），失败时我们关心的是**错误原因**（reason）。用不同的名字能让你在使用时一目了然。

**类比**：如果说 `all()` 是拼图游戏——缺一块就不算完成；那么 `allSettled()` 更像是**期末考试的成绩单**。老师不会因为某一科不及格就把整张成绩单撕毁——相反，所有科目的成绩都会被如实记录在上面，让你一目了然哪些通过了（fulfilled）、哪些没通过（rejected）、具体分数是多少（value）、挂科原因是什麼（reason）。

### 4.2 结果处理实用工具函数

`allSettled()` 返回的结构比 `all()` 稍微复杂一点，通常我们会封装几个辅助函数来简化日常使用：

```javascript
/**
 * 从 allSettled 的结果中筛选出所有成功的结果
 * @param {Array<{status: string, value: any}>} settledResults
 * @returns {Array<any>}
 */
function getFulfilledValues(settledResults) {
  return settledResults
    .filter(r => r.status === 'fulfilled')
    .map(r => r.value);
}

/**
 * 从 allSettled 的结果中筛选出所有失败的原因
 * @param {Array<{status: string, reason: any}>} settledResults
 * @returns {Array<any>}
 */
function getRejectedReasons(settledResults) {
  return settledResults
    .filter(r => r.status === 'rejected')
    .map(r => r.reason);
}

/**
 * 检查是否全部成功
 */
function isAllFulfilled(settledResults) {
  return settledResults.every(r => r.status === 'fulfilled');
}

/**
 * 检查是否至少有一个成功
 */
function isAnyFulfilled(settledResults) {
  return settledResults.some(r => r.status === 'fulfilled');
}

// 使用示例
const results = await Promise.allSettled([
  upload(file1),
  upload(file2),
  upload(file3)
]);

if (isAllFulfilled(results)) {
  console.log('全部上传成功！');
} else {
  const ok = getFulfilledValues(results);
  const errs = getRejectedReasons(results);
  console.log(`${ok.length}/${results.length} 上传成功`);
  errs.forEach(e => console.error('失败:', e.message));
}
```

### 4.3 实战案例：批量操作结果汇总

```javascript
/**
 * 批量上传文件并返回详细的上传报告
 * @param {File[]} files 要上传的文件数组
 * @returns {Promise<{succeeded: Array, failed: Array}>}
 */
async function batchUploadFiles(files) {
  // 将每个文件包装为上传任务
  const uploadPromises = files.map(file =>
    uploadToServer(file).then(
      url => ({ file: file.name, status: 'success', url }),
      error => ({ file: file.name, status: 'failed', error: error.message })
    )
  );

  // 使用 allSettled 等待所有任务结束（不管成败）
  const results = await Promise.allSettled(uploadPromises);

  // 分类汇总
  const succeeded = results
    .filter(r => r.status === 'fulfilled')
    .map(r => r.value)
    .filter(r => r.status === 'success');

  const failed = results
    .filter(r => r.status === 'rejected')
    .map(r => r.reason);

  console.log(`✅ 上传完成：${succeeded.length} 成功，${failed.length} 失败`);
  return { succeeded, failed };
}
```

另一个常见的实战场景是**批量表单字段校验**：

```javascript
/**
 * 并行校验表单的所有字段，返回每个字段的校验结果
 * 不会因为一个字段校验失败就中断其他字段的校验
 */
async function validateFormAllFields(formData) {
  const validators = [
    validateEmail(formData.email),         // 返回 Promise<string | null>，null 表示通过
    validatePassword(formData.password),    // 返回 Promise
    validatePhone(formData.phone),          // 返回 Promise
    validateUsername(formData.username)     // 返回 Promise
  ];

  const fieldNames = ['email', 'password', 'phone', 'username'];

  const results = await Promise.allSettled(validators);

  const errors = {};
  results.forEach((result, index) => {
    const field = fieldNames[index];
    if (result.status === 'fulfilled' && result.value !== null) {
      errors[field] = result.value;  // 字段校验失败的具体原因
    } else if (result.status === 'rejected') {
      errors[field] = '校验程序异常';  // 校验器本身抛出了异常
    }
    // fulfilled 且 value 为 null → 该字段校验通过，不加到 errors 中
  });

  return {
    isValid: Object.keys(errors).length === 0,
    errors
  };
}
```

### 4.4 all vs allSettled 选择指南

| 维度 | `Promise.all()` | `Promise.allSettled()` |
|------|-----------------|------------------------|
| **等待条件** | 所有 **resolve**（成功）| 所有 **settled**（结束即可）|
| **失败策略** | **短路**：任一 reject 则整体 reject | **容错**：收集所有结果，永不分胜负 |
| **结果格式** | 纯值数组 `[v1, v2, v3]` | 状态对象数组 `[{status,value}...]` |
| **返回的 Promise 会 reject 吗？** | ✅ 会（任一子项失败时）| ❌ **永远不会**（总是 fulfilled）|
| **适用场景** | 所有数据都必须成功才能继续渲染 | 批量操作，允许部分失败，需知全貌 |
| **典型例子** | 页面初始化时同时加载 Header 导航 + Body 内容 + Footer 信息 | 批量上传文件、批量发送通知邮件、批量校验表单字段 |
| **错误信息完整性**| 只知道**第一个**错误（其余丢失）| 保留**所有**错误信息 |
| **性能** | 失败时可提前终止后续处理 | 必须等待所有 Promise 结束 |

选择口诀：**"必须全对才往下走 → 用 all；想知道谁对谁错 → 用 allSettled"；"要速度 → all；要完整 → allSettled"**

### 4.5 Polyfill：自己实现 allSettled

如果你的运行环境不支持 `allSettled`（它是 ES2020 才加入标准的新特性），可以用 `all()` + 包装函数来实现一个功能完整的 polyfill：

```javascript
if (!Promise.allSettled) {
  Promise.allSettled = function(promises) {
    // 核心思想：把每个 Promise 包装成"永远成功"的形式
    //
    // 如果原始 Promise fulfill → 包装为 { status: 'fulfilled', value: ... }
    // 如果原始 Promise reject  → 包装为 { status: 'rejected', reason: ... }
    //
    // 这样包装后，所有的 Promise 都会 fulfill
    // 外层的 Promise.all() 就永远不会触发短路由

    const wrappedPromises = Array.from(promises).map(p =>
      Promise.resolve(p).then(
        value   => ({ status: 'fulfilled', value }),   // 成功路径
        reason  => ({ status: 'rejected', reason })     // 失败路径
      )
    );

    // 用 all() 来等待所有包装后的 Promise（它们现在永远不会 reject）
    return Promise.all(wrappedPromises);
  };
}
```

**原理深度剖析**：

这个 polyfill 巧妙地利用了 `all()` 的"短路失败"特性来实现它的反面——**"永不失败"**。具体来说：

1. **第一步**：`Promise.resolve(p)` 确保数组中的每个元素都被规范化为原生 Promise（包括处理可能的 Thenable 值）
2. **第二步**：`.then(onFulfilled, onRejected)` 为每个 Promise 注册了两个 handler
   - 如果 Promise fulfill → `onFulfilled` 被调用，返回 `{ status: 'fulfilled', value }`
   - 如果 Promise reject → `onRejected` 被调用，返回 `{ status: 'rejected', reason }`
3. **关键点**：这两个 handler 都**返回一个普通对象**（不是 throw），所以包装后的 Promise **总是会 fulfill**！
4. **第三步**：`Promise.all(wrappedPromises)` 等待所有包装后的 Promise——由于它们永远不会 reject，`all()` 永远不会短路，从而实现了"收集所有结果"的效果

**类比**：这就像给每个参赛选手都发了一件"参与奖"马甲。不管选手是跑到了终点还是中途退赛，只要他穿上了马甲就算"完成任务"了。`all()` 看到的只是一群穿着马甲、全部"完成"了的选手——至于马甲里面的故事，要看马甲上绣的字（status 字段）才能知道。

## 五、组合器 —— Promise.race() 竞速

### 5.1 核心概念

`Promise.race()` 的行为同样可以用一句话概括：**"谁先结束就用谁的结果——不管是成功还是失败。"**

```javascript
let promise = Promise.race(iterable);
```

它返回一个 Promise，其状态取决于**第一个 settle（结束）的 Promise**——注意是 **settled**（包含 fulfilled 和 rejected 两种），而不只是 fulfilled：

```javascript
// ====== 最快的是成功的情况 ======
Promise.race([
  new Promise(resolve => setTimeout(() => resolve('我是冠军!'), 1000)),
  new Promise(resolve => setTimeout(() => resolve('我也完成了'), 2000)),
  new Promise(resolve => setTimeout(() => resolve('我也是'), 3000))
]).then(result => console.log(result));
// 1 秒后输出: '我是冠军!' —— 第一个 settle 的是 fulfilled

// ====== 最快的是失败的情况 ======
Promise.race([
  new Promise((_, reject) => setTimeout(() => reject(new Error('我摔倒了!')), 500)),
  new Promise(resolve => setTimeout(() => resolve('我到了'), 2000))
]).catch(err => console.log(err.message));
// 0.5 秒后输出: '我摔倒了!' —— 第一个 settle 的是 rejected
// 注意：第二个 Promise 即使在 2 秒后成功了也没用，比赛早已结束
```

**类比**：`race()` 就像一场正规的赛跑比赛——规则规定**谁第一个冲过终点线（或者摔倒在终点线上），比赛就结束了**。裁判不会等所有人都跑到终点才宣布结果，第一名撞线的瞬间比赛即止。这与后面要讲的 `any()` 有本质区别——`any()` 更像是"面试录用"模式，摔倒在终点的选手不算录用，面试官会继续看下一位候选人。

### 5.2 实战案例：超时控制（最经典用法）

这是 `race()` 在实际开发中使用频率最高的应用模式——给任意异步操作加上时间上限：

```javascript
/**
 * 带超时的 fetch 封装
 *
 * @param {string} url 请求地址
 * @param {number} timeoutMs 超时毫秒数（默认 5 秒）
 * @returns {Promise<Response>}
 *
 * @example
 *   fetchWithTimeout('https://example.com/api', 3000)
 *     .then(r => r.json())
 *     .catch(err => {
 *       if (err.message.includes('超时')) { /* 处理超时 */ }
 *     });
 */
function fetchWithTimeout(url, timeoutMs = 5000) {
  // 创建两个"竞争者"：
  // 竞争者 A：真正的网络请求
  let fetchPromise = fetch(url);

  // 竞争者 B：定时器（到达指定时间后自动 reject）
  let timeoutPromise = new Promise((_, reject) => {
    setTimeout(() => reject(new Error(`请求超时 (${timeoutMs}ms): ${url}`)), timeoutMs);
  });

  // 让两者竞速——谁先 settle 就用谁的结果
  return Promise.race([fetchPromise, timeoutPromise]);
}

// ====== 使用示例 ======
fetchWithTimeout('https://example.com/slow-api', 3000)
  .then(response => response.json())
  .then(data => console.log('数据:', data))
  .catch(err => {
    if (err.message.includes('超时')) {
      showUserMessage('网络较慢，请稍后重试', 'warning');
      // 可以引导用户点击"重试"按钮
    } else {
      showErrorDialog(err.message);
    }
  });
```

**工作原理图解**：

```
时间轴 →

fetchWithTimeout(url, 3000) 被调用
│
├─→ fetchPromise ────────────────── [等待服务器响应...]
│                                    │
│                                    ├── 若 3秒内收到响应 → race 返回 Response ✅
│                                    └── 若 3秒内无响应 → 继续等...
│
└─→ timeoutPromise ─── [等待 3000ms]
                           │
                           └── 300ms 到了 → reject(Error('超时')) ❌
                               → race 立即以该错误 reject
```

**两个竞争者各自的命运**：

| 结果 | fetchPromise 的命运 | timeoutPromise 的命运 |
|------|---------------------|----------------------|
| fetch 先完成 | ✅ 结果被采用 | 定时器仍会到期但不影响结果（但占内存）|
| 超时先发生 | ⚠️ 仍在运行（未取消！）| ❌ 错误被采用 |

### 5.3 ⚠️ race() 的资源泄漏风险

上面的表格揭示了一个重要问题：**当 `race()` 因超时而结束时，被"淘汰"的那个 Promise（如 fetch 请求）并不会自动取消**。底层的网络请求仍然在后台运行，消耗带宽和服务器资源。

```javascript
function riskyFetchWithTimeout(url) {
  return Promise.race([
    fetch(url),                              // 这个请求会一直跑到完
    new Promise((_, rej) => setTimeout(() => rej(new Error('超时')), 5000))
  ]);
}

// 问题演示
riskyFetchWithTimeout('https://example.com/huge-file.zip')
  .catch(err => console.log(err.message));

// 5 秒后输出: '超时'
// 但是！huge-file.zip 的下载仍在后台进行中！
// 如果用户频繁触发这个操作，会产生大量"僵尸"网络请求
// 浏览器的并发连接数会被耗尽，导致其他正常的请求也被拖慢
```

#### 解决方案：配合 AbortController 真正取消请求

`AbortController` 是浏览器提供的标准取消 API，它可以真正中止 `fetch` 请求：

```javascript
/**
 * 带超时且支持真正取消的 fetch 封装（生产级版本）
 */
function fetchWithTimeout(url, ms = 5000) {
  const controller = new AbortController();

  // 创建一个"会在指定时间后中止请求"的超时 Promise
  const timeoutId = setTimeout(() => controller.abort(), ms);

  // 将 abort signal 传给 fetch
  // fetch 会在 controller.abort() 调用时真正取消网络请求
  return fetch(url, { signal: controller.signal })
    .finally(() => {
      clearTimeout(timeoutId); // 清理定时器（无论成功失败都清理）
    });
}

// 使用
fetchWithTimeout('https://example.com/slow-api', 3000)
  .then(r => r.json())
  .catch(err => {
    if (err.name === 'AbortError') {
      console.log('请求因超时被取消');
    } else {
      console.log('其他错误:', err.message);
    }
  });

// 这次超时时，底层的网络请求会真正被中止！
// 不会产生僵尸请求 ✅
```

**AbortController 的工作原理**：

`controller.abort()` 做了两件事：
1. 将 `signal.aborted` 设为 `true`
2. 触发 `signal` 上的 `abort` 事件
3. 正在监听此 `signal` 的 `fetch` 请求会收到中止信号，**真正关闭 TCP 连接**，停止接收数据

### 5.4 实战案例：竞速请求多个镜像源

除了超时控制，`race()` 另一个高频应用场景是多源竞速——向多个数据源同时请求相同的数据，谁先返回就用谁的：

```javascript
/**
 * 多镜像源竞速加载
 * 向多个 CDN 地址同时请求同一资源，最快返回的被使用
 *
 * @param {string[]} urls 镜像 URL 列表（优先级从高到低）
 * @returns {Promise<any>}
 */
function fastestMirrorLoad(urls) {
  if (urls.length === 0) {
    return Promise.reject(new Error('镜像源列表不能为空'));
  }

  // 将每个 URL 映射为一个 fetch 请求
  const requests = urls.map(url =>
    fetch(url)
      .then(res => {
        if (!res.ok) throw new Error(`${url}: HTTP ${res.status}`);
        return res.json();
      })
  );

  // 竞速：谁最先成功返回就用谁
  return Promise.race(requests);
}

// 使用
const mirrors = [
  'https://cdn-primary.example.com/data.json',
  'https://cdn-backup.example.com/data.json',
  'https://cdn-fallback.example.com/data.json'
];

fastestMirrorLoad(mirrors)
  .then(data => console.log('最快的数据源返回了:', data))
  .catch(error => console.error('所有数据源均不可用:', error));
```

**注意**：对于镜像源竞速场景，实际上 `Promise.any()` 往往更适合——因为如果一个镜像源返回了 404（失败），你不一定想把这当作最终结果。`any()` 会跳过失败的继续等下一个成功的。但如果你的需求确实是"谁先响应就用谁，哪怕是错误响应"，那就用 `race()`。

## 六、组合器 —— Promise.any() 首个成功

### 6.1 核心概念 —— 与 race 的本质区别

`Promise.any()` 在 ES2021 中引入。它与 `race()` 表面相似——都是"多个 Promise 竞速"的模式，但有一个**根本性的态度差异**：

| 对比维度 | `Promise.race()` | `Promise.any()` |
|---------|------------------|-----------------|
| 关注的目标 | 第一个 **settled**（结束）| 第一个 **fulfilled**（**成功**）|
| 对 reject 的态度 | **第一个 reject 就算输**（比赛结束）| **忽略单个 reject**（继续等待下一个）|
| 全部都 reject 时 | 返回遇到的**第一个错误** | 返回 `AggregateError`（聚合所有错误的特殊对象）|
| 适用心态 | "我要最快的答案，不管好坏" | "我要一个好的答案，越快越好" |

**类比**：如果说 `race()` 是正规赛跑——谁先到终点谁赢（哪怕是爬着到的，哪怕是摔倒后被担架抬过终点的）；那么 `any()` 更像是**企业招聘面试**——面试官有一份候选人名单，他会逐个面试，只要有一个人通过了面试（fulfilled）就立即发出录取通知，停止后续面试。只有当所有人都面试失败（rejected）时，招聘才宣告失败——这时 HR 会整理一份包含所有人失败原因的报告（AggregateError）交给老板。

### 6.2 行为演示：失败被忽略

```javascript
// 第一个最快但是失败了 → 被 any() 忽略，继续等
Promise.any([
  new Promise((_, reject) => setTimeout(() => reject(new Error('源A超时')), 1000)),  // 最快但失败
  new Promise(resolve => setTimeout(() => resolve('从源B获取的数据'), 2000)),          // 第二个成功
  new Promise(resolve => setTimeout(() => resolve('从源C获取的数据'), 3000))           // 第三个也成功（但不会被用到）
]).then(result => console.log(result));
// 2 秒后输出: '从源B获取的数据'
// 注意：源A 的错误被静默忽略了！
```

**逐帧追踪执行过程**：

```
时间线 →

T=0ms:    any() 开始监听 3 个 Promise

T=1000ms: 源A reject(Error('源A超时'))
          │
          └─→ any() 的反应：忽略！继续等待
             （就像面试官看了第一份简历说"不行，下一个"）

T=2000ms: 源B resolve('从源B获取的数据')
          │
          └─→ any() 的反应：找到了！立即 fulfill
             （就像面试官找到合格的候选人，立即录用）
             → 输出: '从源B获取的数据'

T=3000ms: 源C resolve('从源C获取的数据')
          │
          └─→ 已经没人听了（比赛早已结束）
```

### 6.3 AggregateError —— 当所有人都失败时

当**所有** Promise 都被 reject 时，`Promise.any()` 不会返回普通的 `Error` 对象，而是返回一个特殊的 `AggregateError`（聚合错误）对象。

#### AggregateError 的结构

```javascript
// AggregateError 继承自 Error，拥有 Error 的所有属性
// 同时新增了一个 errors 属性

class AggregateError extends Error {
  constructor(errors, message) {
    super(message);               // 标准 message 属性
    this.errors = errors;         // ⭐ 新增：存储所有错误原因的数组
    this.name = 'AggregateError'; // 固定的 name
  }
}
```

#### 完整演示

```javascript
Promise.any([
  Promise.reject(new Error('源 A 不可达 (DNS lookup failed)')),
  Promise.reject(new Error('源 B 连接超时 (connection timed out)')),
  Promise.reject(new Error('源 C 返回 503 (Service Unavailable)'))
]).catch(err => {
  console.log('错误名称:', err.constructor.name);   // 'AggregateError'
  console.log('通用消息:', err.message);            // 'All promises were rejected'

  console.log('\n--- 所有失败原因 ---');
  err.errors.forEach((e, i) => {
    console.log(`[${i}] ${e.message}`);
  });
  // [0] 源 A 不可达 (DNS lookup failed)
  // [1] 源 B 连接超时 (connection timed out)
  // [2] 源 C 返回 503 (Service Unavailable)
});
```

**为什么需要 AggregateError 而不是一个普通 Error？**

当使用 `any()` 时，你通常是在尝试多种备选方案（fallback strategy）。比如你有 3 个 CDN 镜像源、2 个备用 API 服务器、1 个本地缓存——你尝试了所有方案但全都失败了。这时候一个简单的 `"所有请求都失败了"` 错误信息对你毫无帮助。你需要知道的是：

- 源 A 为什么失败？（DNS 解析失败 → 可能是网络配置问题）
- 源 B 为什么失败？（连接超时 → 可能是防火墙问题）
- 源 C 为什么失败？（503 服务不可用 → 服务器端问题）

有了这些详细信息，你才能做出合理的降级决策——比如"源 A 和 B 是网络问题，建议用户检查网络；源 C 是服务器问题，可以先展示缓存的旧版本数据"。

### 6.4 实战案例：多源容错请求

```javascript
/**
 * 多源容错数据加载器
 * 依次尝试多个数据源，任何一个成功即可
 * 全部失败时返回详细的错误报告
 */
async function resilientFetch(endpoints) {
  if (endpoints.length === 0) {
    throw new Error('至少需要一个端点');
  }

  try {
    const data = await Promise.any(
      endpoints.map(url =>
        fetch(url)
          .then(res => {
            if (!res.ok) throw new Error(`${url}: HTTP ${res.status}`);
            return res.json();  // 只有真正成功才 fulfill
          })
          .catch(err => {
            // 把 URL 信息附加到错误上，方便后续诊断
            err.url = url;
            throw err;  // 重新抛出让 any() 捕获
          })
      )
    );
    return { success: true, data, source: 'ok' };

  } catch (aggregatedErr) {
    // 所有端点都失败了
    if (aggregatedErr instanceof AggregateError) {
      console.error('=== 所有数据源均不可用 ===');
      aggregatedErr.errors.forEach((err, i) => {
        console.error(`  源 ${i + 1} (${err.url}): ${err.message}`);
      });

      // 降级决策：根据错误类型决定下一步
      const hasNetworkErrors = aggregatedErr.errors.some(
        e => e.message.includes('Failed to fetch') || e.message.includes('NetworkError')
      );
      const hasServerErrors = aggregatedErr.errors.some(
        e => e.message.includes('HTTP 5') || e.message.includes('HTTP 4')
      );

      return {
        success: false,
        error: 'ALL_SOURCES_FAILED',
        details: aggregatedErr.errors.map(e => ({ url: e.url, message: e.message })),
        suggestion: hasNetworkErrors ? 'check_network' : hasServerErrors ? 'try_later' : 'unknown'
      };
    }
    throw aggregatedErr; // 不是 AggregateError，重新抛出
  }
}

// 使用
const endpoints = [
  'https://primary-api.example.com/data',
  'https://backup-api.example.com/data',
  'https://cache.example.com/data'
];

const result = await resilientFetch(endpoints);
if (result.success) {
  renderData(result.data);
} else {
  showFallbackUI(result.suggestion);
}
```

## 七、六大方法全景对比

### 7.1 行为矩阵

下表展示了六个方法在面对不同输入组合时的完整行为。这是最实用的速查参考：

| 输入场景 | `all()` | `allSettled()` | `race()` | `any()` |
|----------|---------|---------------|----------|---------|
| **全部成功** | ✅ 返回 `[v1,v2,v3]` | ✅ 返回 `[{fulfilled}]×3` | ✅ 返回最快的一个值 | ✅ 返回最快的一个值 |
| **部分成功部分失败** | ❌ **短路 reject**（取第一个错误）| ✅ 返回混合状态数组（成功+失败都有）| 取决于**哪个最快结束**（不区分成败）| ✅ **忽略失败**，取第一个成功 |
| **全部失败** | ❌ 返回**第一个**错误 | ✅ 返回 `[{rejected}]×3`（所有错误都在）| 取决于**哪个最快失败**（返回那个错误）| ❌ 返回 **AggregateError**（**所有**错误的聚合）|
| **空数组** | ✅ `[]`（**立即** resolve）| ✅ `[]`（**立即** resolve）| ⚠️ **永远 pending**（永远不会 settle）| ⚠️ **永远 pending**（永远不会 settle）|
| **含非 Promise 值** | 原样传递到结果数组 | 原样传递（包装为 fulfilled）| 当作即时 fulfilled 处理 | 当作即时 fulfilled 处理 |

> **关于空数组的特殊行为**：这是一个非常重要的边界情况！`all([])` 和 `allSettled([])` 会**立即 resolve** 为空数组——这是合理的，因为"零个 Promise 全部成功"在逻辑上是成立的（空真）。但 `race([])` 和 `any([])` 会返回一个**永远不 settle 的 Promise**——因为没有竞争者，比赛永远不会开始，也没有人触发结束。**这几乎总是 bug 的来源**。使用时请务必确保数组不为空。

### 7.2 决策流程图

```
你需要处理多个 Promise？
│
├─→ 你需要【所有】的结果？
│   │
│   ├─→ 【必须全部成功】，一个失败就不能继续？
│   │   └──→ 用 Promise.all()
│   │       例：同时加载 CSS + JS + 字体，缺一不可
│   │
│   └─→ 【允许部分失败】，需要知道每一个的成败？
│       └──→ 用 Promise.allSettled()
│           例：批量上传 10 个文件，要知道哪些成功哪些失败
│
└─→ 你只需要【最快的一个】结果？
    │
    ├─→ 【失败也算结果】？
    │   └──→ 用 Promise.race()
    │       例：超时控制（setTimeout 竞速）
    │       例：请求取消（AbortController 竞速）
    │
    └─→ 【只要成功的】，失败的要跳过？
        └──→ 用 Promise.any()
            例：多 CDN 镜像源取最快的一个
            例：多备用 API 端点容错
```

### 7.3 一句话记忆法

| 方法 | 一句话记忆 |
|------|-----------|
| `all` | **拼图**——缺一块都不算完成 |
| `allSettled` | **成绩单**——对错都记下来 |
| `race` | **赛跑**——谁先到终点谁赢（含爬过去的）|
| `any` | **面试**——谁先通过就录用谁（全挂才报错）|
| `resolve` | **印钞**——直接印出确定金额的钞票 |
| `reject` | **罚单**——直接开出确定金额的罚单 |

## 八、高级应用模式

### 8.1 并发限制器（Concurrency Pool）

当你需要并行大量请求但又不想一次性打垮服务器（或浏览器）时，并发限制模式是最常用的解决方案：

```javascript
/**
 * 通用的并发 Promise 执行器
 *
 * 控制同时运行的 Promise 数量不超过 concurrency 上限
 * 类似于 p-pool 或 p-limit 库的核心功能
 *
 * @param {Function[]} tasks 任务数组（每个元素是返回 Promise 的函数）
 * @param {number} concurrency 最大并发数（默认 3）
 * @returns {Promise<Array>} 所有任务的执行结果（保持输入顺序）
 *
 * @example
 *   const tasks = [
 *     () => fetch('/api/1'),
 *     () => fetch('/api/2'),
 *     // ... 共 100 个任务
 *   ];
 *   const results = await concurrentPool(tasks, 5); // 最多同时 5 个
 */
async function concurrentPool(tasks, concurrency = 3) {
  const results = [];
  const executing = new Set(); // 存储正在执行的 Promise

  for (const task of tasks) {
    // 创建一个"带标记"的 Promise
    // 当它完成时，自动从 executing 集合中移除自己
    const promise = task().then(result => {
      executing.delete(promise); // 完成 → 释放一个槽位
      return result;
    }, error => {
      executing.delete(promise); // 失败 → 也释放槽位
      throw error;               // 但错误继续传播
    });

    executing.add(promise);   // 加入执行池
    results.push(promise);    // 记录到结果数组（保序）

    // 如果已达并发上限，等待任意一个完成后再继续
    if (executing.size >= concurrency) {
      await Promise.race(executing); // 等待最快完成的那个
      // 完成后 executing.size 减少，有空位了
      // 下一次循环就可以塞入新任务
    }
  }

  // 所有任务都已加入，等待剩余的全部完成
  return Promise.all(results);
}

// ====== 使用示例 ======
// 模拟 10 个任务，最多 3 个同时运行
const tasks = Array.from({ length: 10 }, (_, i) => () =>
  new Promise(resolve =>
    setTimeout(() => {
      console.log(`任务 ${i} 完成`);
      resolve(`结果_${i}`);
    }, Math.random() * 2000 + 500) // 500~2500ms 随机延迟
  )
);

concurrentPool(tasks, 3).then(allResults => {
  console.log(`\n全部 ${allResults.length} 个任务完成`);
  console.log('结果:', allResults);
});

/* 输出示例（每次运行顺序可能不同）：
任务 2 完成
任务 5 完成
任务 1 完成      ← 任何时候最多 3 个在跑
任务 8 完成
任务 3 完成
任务 7 完成
任务 0 完成
任务 4 完成
任务 6 完成
任务 9 完成

全部 10 个任务完成
*/
```

**原理深度剖析**：

这个并发池的核心思想是用一个 Set 来跟踪"正在执行"的 Promise 数量：

1. **入队**：遍历任务数组，依次创建 Promise 并加入 `executing` Set
2. **限流**：当 `executing.size >= concurrency` 时，调用 `await Promise.race(executing)`——这会让当前函数**暂停**（yield），直到执行中最快的那个 Promise 完成
3. **释放**：完成的 Promise 通过 `.then()` 回调从 Set 中删除自己，腾出一个空位
4. **续行**：`race()` resolve 后，for 循环继续，创建新的 Promise 填补空位
5. **收尾**：所有任务都已加入后，`Promise.all(results)` 等待剩余的全部完成

**类比**：这就像一家理发店有 3 把椅子（concurrency = 3）。顾客排队进来（tasks 数组），有空椅子就直接坐（创建 Promise），满了就在门口等（`await race`）。某位顾客剪完离开（Promise complete → delete from Set），门口的第一位顾客就可以进去了（循环继续）。最终所有顾客都理完发了（`Promise.all` 等待剩余）。

### 8.2 重试包装器（Retry Wrapper）

结合 Promise 的基本概念构建一个带指数退避的重试机制：

```javascript
/**
 * 带指数退避重试的异步操作封装
 *
 * @param {Function} fn 返回 Promise 的异步操作函数
 * @param {Object} options 配置选项
 * @param {number} options.maxRetries 最大重试次数（默认 3）
 * @param {number} options.initialDelay 初始延迟毫秒数（默认 1000）
 * @param {number} options.backoff 退避倍数（默认 2，每次延迟翻倍）
 * @param {Function} options.shouldRetry 判断是否值得重试的函数（可选）
 * @returns {Promise<any>} 操作结果
 *
 * @example
 *   retry(() => fetch('/api/unstable'), { maxRetries: 5, initialDelay: 500 })
 *     .then(console.log);
 */
function retry(fn, options = {}) {
  const {
    maxRetries = 3,
    initialDelay = 1000,
    backoff = 2,
    shouldRetry = () => true
  } = options;

  return new Promise((resolve, reject) => {
    let attempt = 0;
    let delay = initialDelay;

    function attemptOperation() {
      attempt++;
      fn()
        .then(resolve)                    // 成功 → 直接 resolve，不再重试
        .catch(error => {
          // 检查自定义的重试条件（如 429 Too Many Requests 可重试，400 Bad Request 不可重试）
          if (attempt < maxRetries && shouldRetry(error)) {
            console.warn(
              `[retry] 第 ${attempt}/${maxRetries} 次尝试失败: ${error.message}. ` +
              `${delay}ms 后重试...`
            );
            setTimeout(attemptOperation, delay);
            delay *= backoff;  // 指数退避：1s → 2s → 4s → 8s ...
          } else {
            // 重试次数耗尽或不满足重试条件
            reject(new Error(
              `经过 ${attempt} 次尝试后仍失败 (最后错误: ${error.message})`
            ));
          }
        });
    }

    attemptOperation();
  });
}

// ====== 使用示例 ======

// 场景一：请求不稳定的外部 API
retry(
  () => fetch('https://unstable-api.example.com/data').then(r => r.json()),
  { maxRetries: 5, initialDelay: 1000, backoff: 2 }
)
  .then(data => console.log('终于拿到数据:', data))
  .catch(err => console.error('彻底失败:', err.message));

// 场景二：只在特定错误下重试（429 限流、503 服务不可用、网络错误）
retry(
  () => fetch('/api/rate-limited'),
  {
    maxRetries: 3,
    shouldRetry: err =>
      err.message?.includes('429') ||
      err.message?.includes('503') ||
      err.message?.includes('Failed to fetch')
  }
);
```

**指数退避（Exponential Backoff）的意义**：如果你的 API 因为流量过大返回了 429（Too Many Requests），立即重试只会让问题更糟。指数退避让重试间隔逐渐增大（1s → 2s → 4s → 8s），给服务端恢复的时间，同时避免加重服务端压力。这是分布式系统中经过实践检验的标准策略。

### 8.3 Map + All 两阶段加载模式

先并行获取 ID 列表，再根据 ID 批量获取详情——这是数据加载中最经典的瀑布流模式：

```javascript
/**
 * 分页 + 并行的数据预加载模式
 * 适用于"先获取摘要列表，再并行加载详情"的场景
 */
async function loadArticleFeed(page = 1) {
  // ===== 第一阶段：获取文章 ID 列表 =====
  const listResponse = await fetch(`/api/articles?page=${page}&size=20`);
  const { items: articleIds, total } = await listResponse.json();

  if (articleIds.length === 0) {
    return { articles: [], total, hasMore: false };
  }

  // ===== 第二阶段：并行获取每篇文章的详情 =====
  const detailPromises = articleIds.map(id =>
    fetch(`/api/articles/${id}`)
      .then(res => res.json())
      .catch(err => ({
        id,
        title: '(加载失败)',
        error: err.message
      }))
  );

  // 单独处理每个请求的错误，不让一个失败阻断其他
  const articles = await Promise.all(detailPromises);

  return { articles, total, hasMore: articles.length === articleIds.length };
}

// 使用：先显示骨架屏，数据到位后渲染
showSkeleton();
loadArticleFeed(1).then(({ articles }) => {
  hideSkeleton();
  renderArticles(articles);
});
```

### 8.4 allSettled + 过滤恢复模式

当部分操作失败时，自动过滤掉失败的项目并对失败项进行二次处理：

```javascript
/**
 * 带失败恢复的批量操作
 * 先尝试全部并行，失败的自动降级处理
 */
async function robustBatchGet(urls, fallbackUrl) {
  // 第一轮：尝试所有主数据源
  const primaryResults = await Promise.allSettled(
    urls.map(url => fetch(url).then(r => r.json()))
  );

  const successes = [];    // 成功的结果
  const failures = [];     // 失败的 URL 列表

  primaryResults.forEach((result, index) => {
    if (result.status === 'fulfilled') {
      successes.push({ index, data: result.value });
    } else {
      failures.push({ index, url: urls[index], error: result.reason });
    }
  });

  // 如果有失败项，使用备用数据源补充
  if (failures.length > 0 && fallbackUrl) {
    console.warn(`${failures.length} 个主源失败，启用备用源`);

    const fallbackResults = await Promise.allSettled(
      failures.map(f => fetch(fallbackUrl).then(r => r.json()))
    );

    fallbackResults.forEach((result, i) => {
      if (result.status === 'fulfilled') {
        successes.push({ index: failures[i].index, data: result.value });
      }
    });
  }

  // 按 index 排序恢复原始顺序
  successes.sort((a, b) => a.index - b.index);
  return successes.map(s => s.data);
}
```

## 九、常见陷阱与注意事项

### 9.1 陷阱速查表

| # | 陷阱 | 现象 | 解决方案 |
|---|------|------|----------|
| 1 | **`all()` 吞掉后续错误** | 第一个 reject 后，后续 Promise 的 rejection 变成 unhandledrejection | 用 `allSettled()` 替代，或在每个 Promise 单独加 `.catch()` |
| 2 | **空数组传给 race/any** | 返回**永远 pending** 的 Promise，`.then()` 永远不执行 | 始终检查数组非空，或设置兜底 Promise（如 `Promise.resolve(null)`）|
| 3 | **混淆 race 与 any** | 想要"首个成功"却用了 race，导致超时 reject 或 404 被误当作最终结果 | 口诀：**race=谁快谁赢（含失败）；any=谁先成功谁赢** |
| 4 | **`all()` 不保证"全部完成"** | 误以为 `all()` 一定会等所有 Promise 结束 | 明确区分"全部完成"和"一个失败就停止"两种需求 |
| 5 | **忘记 `all()` 保持输入顺序** | 误认为结果数组按完成顺序排列 | 结果**始终**与输入数组顺序对应，与完成顺序无关 |
| 6 | **`reject()` 不拆包 Thenable** | 传入带 `then` 属性的对象，期望它被解析但实际原样传入 | 如需解析先用 `Promise.resolve()` 再 `.then()` |
| 7 | **`AggregateError` 被普通 catch 吞掉** | `any()` 全部失败时只用 `console.log(error)` 看不到具体原因 | 检查 `error instanceof AggregateError`，访问 `error.errors` 数组 |

### 9.2 陷阱深度解析

#### 陷阱 1：all() 的"静默失败"问题（最危险）

这是一个非常隐蔽且危害性极高的问题：

```javascript
// ❌ 危险代码
Promise.all([
  fetch('/api/a'),   // 假设这个成功
  fetch('/api/b'),   // 假设这个 404 失败
  fetch('/api/c')    // 假设这个也 500 失败
])
  .then(responses => {
    // 永远不会到这里
    renderResponses(responses);
  })
  .catch(err => {
    // 你只能看到一个错误（第一个 reject 的那个）
    console.error('出错:', err.message);  // '404' 或类似的
  });

// fetch('/api/b') 和 fetch('/api/c') 的错误去哪了？
// 它们变成了 unhandledrejection（未处理的 Promise 拒绝）
// 浏览器控制台会有黄色警告：
//   "Uncaught (in promise) TypeError: Failed to fetch"
//
// 这些"孤儿错误"可能导致：
// - 监控系统漏报（错误采集 SDK 无法捕获）
// - 内存泄漏（某些情况下）
// - 调试困难（你以为只有一个地方出错）
```

**为什么会这样？** 当 `/api/b` 的 Promise 在 `all()` 已经 reject 后才完成 reject 时，它的 rejection 没有 catch handler 来处理——因为 `all()` 返回的 Promise 已经被 `.catch()` 捕获过了，而这个 `.catch()` 只对应第一个错误。后续的错误就成了"孤儿"。

**解决方案 A —— 使用 allSettled（推荐）**：

```javascript
Promise.allSettled([
  fetch('/api/a'),
  fetch('/api/b'),
  fetch('/api/c')
]).then(results => {
  results.forEach((r, i) => {
    if (r.status === 'fulfilled') {
      console.log(`请求 ${i}: OK (${r.value.status})`);
    } else {
      console.error(`请求 ${i} 失败:`, r.reason);
    }
  });
});
// 所有结果都能看到 ✅
```

**解决方案 B —— 每个 Promise 独立 catch**：

```javascript
Promise.all([
  fetch('/api/a').catch(e => { logError('a', e); throw e; }),
  fetch('/api/b').catch(e => { logError('b', e); throw e; }),
  fetch('/api/c').catch(e => { logError('c', e); throw e; })
]).then(/* ... */).catch(err => {
  console.log('仍有错误（但每个都已被记录）:', err.message);
});
// 每个 Promise 的错误都被独立记录了 ✅
// 然后 throw e 让错误继续传播给 all() 的 catch
```

#### 陷阱 2：空数组的永远 pending

```javascript
// ⚠️ 隐藏的 bug
function getFastestResult(urls) {
  // 如果 urls 为空数组...
  return Promise.race(urls.map(url => fetch(url)));  // 永远 pending！
}

getFastestResult([])
  .then(data => console.log('数据:', data))    // 永远不执行
  .catch(err => console.error('错误:', err));   // 永远不执行

// UI 永久显示 loading 状态，用户永远看不到结果或错误提示
```

**防御性编程**：

```javascript
// ✅ 安全版本
function safeRace(promises, fallbackValue = null) {
  if (promises.length === 0) {
    return Promise.resolve(fallbackValue); // 空数组立即返回默认值
  }
  return Promise.race(promises);
}

function safeAny(promises) {
  if (promises.length === 0) {
    return Promise.reject(new Error('不能传入空数组'));
  }
  return Promise.any(promises);
}
```

#### 陷阱 3：race() 与 AbortController 的配合缺失

前面已经提到过，`race()` 做超时时如果不配合 `AbortController` 会造成资源泄漏。这里是另一个角度的分析：

```javascript
// ⚠️ 有问题的代码
function pollWithTimeout(pollFn, intervalMs, timeoutMs) {
  return Promise.race([
    // 轮询：每隔 intervalMs 检查一次
    new Promise(async resolve => {
      while (true) {
        const result = await pollFn();
        if (result) return resolve(result);
        await new Promise(r => setTimeout(r, intervalMs));
      }
    }),
    // 超时
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error('轮询超时')), timeoutMs)
    )
  ]);
}

// 问题：即使超时了，while(true) 循环还在不断执行 pollFn()！
// 每次 pollFn() 的结果都被丢弃，白白浪费 CPU 和网络
```

**修复方案：使用标志位 + AbortController**：

```javascript
function pollWithTimeout(pollFn, intervalMs, timeoutMs) {
  const controller = new AbortController();

  const polling = (async () => {
    while (!controller.signal.aborted) {
      try {
        const result = await pollFn();
        if (result) return result;
      } catch (e) {
        if (controller.signal.aborted) throw e; // 是超时导致的错误，继续抛出
      }
      // 等待下一次或超时信号
      await new Promise((resolve, reject) => {
        const timer = setTimeout(resolve, intervalMs);
        controller.signal.addEventListener('abort', () => {
          clearTimeout(timer);
          reject(new Error('轮询被中止'));
        }, { once: true });
      });
    }
  })();

  const timeout = new Promise((_, reject) => {
    const timer = setTimeout(() => {
      controller.abort();  // ← 通知轮循停止
      reject(new Error('轮询超时'));
    }, timeoutMs);
    controller.signal.addEventListener('abort', () => clearTimeout(timer), { once: true });
  });

  return Promise.race([polling, timeout]);
}
```

## 十、最佳实践

### 10.1 场景决策表

| 你的具体需求 | 推荐方法 | 理由 |
|--------------|---------|------|
| 并行下载页面必需的资源（CSS/JS/字体），缺一不可 | `all()` | 缺少任一资源都无法正确渲染 |
| 批量上传 20 张照片，要知道每张的上传结果 | `allSettled()` | 允许部分失败，需要完整报告 |
| 给 fetch 请求加 5 秒超时限制 | `race()` | 与 `setTimeout` + `AbortController` 竞速 |
| 多个 CDN 镜像源，取最快返回的有效数据 | `any()` | 只要一个有效响应即可，失败的要跳过 |
| 将缓存中已有的同步数据包装为 Promise 接口 | `resolve()` | 统一异步接口签名 |
| 参数校验不通过时立即返回错误 | `reject()` | Guard Clause 快速失败 |
| 同时发起 100 个请求但不能打垮服务器 | 自定义**并发限制器** | 控制 `concurrency` 上限 |
| 请求不稳定的外部 API 需要自动重试 | 自定义**重试包装器** | 指数退避 + 最大重试次数 |

### 10.2 设计原则

#### 原则 1：优先用 async/await 代替链式调用

静态方法与 `async/await` 结合时代码的可读性和可维护性显著提升：

```javascript
// ✅ 推荐：async/await 版本
async function loadDashboard(userId) {
  const [user, posts, notifications] = await Promise.all([
    fetchUser(userId),
    fetchPosts(userId),
    fetchNotifications(userId)
  ]);

  // 中间可以插入任意同步逻辑
  const isAdmin = user.role === 'admin';
  const filteredPosts = isAdmin ? posts : posts.filter(p => p.published);

  return { user, posts: filteredPosts, notifications, isAdmin };
}

// ❌ 不推荐：.then() 链式版本
function loadDashboard(userId) {
  return Promise.all([fetchUser(userId), fetchPosts(userId), fetchNotifications(userId)])
    .then(([user, posts, notifications]) => {
      const isAdmin = user.role === 'admin';
      const filteredPosts = isAdmin ? posts : posts.filter(p => p.published);
      return { user, posts: filteredPosts, notifications, isAdmin };
    });
}
```

`async/await` 版本的优势：变量命名自由、错误处理可以用外层 `try/catch` 统一管理、中间逻辑插入更自然。

#### 原则 2：用 allSettled() 替代手动错误追踪

不要试图在 `all()` 的 `.catch()` 中做复杂的恢复逻辑来模拟 `allSettled()`——那样既复杂又容易遗漏边缘情况：

```javascript
// ❌ 不推荐：试图在 all() 中手动追踪所有错误
let errors = [];
Promise.all([
  fetch('/a').catch(e => { errors.push(e); throw e; }),
  fetch('/b').catch(e => { errors.push(e); throw e; }),
  fetch('/c').catch(e => { errors.push(e); throw e; })
])
  .then(/* ... */)
  .catch(e => {
    // 这里你只知道最后一个被 throw 的错误
    // errors 数组虽然收集了之前的错误，但逻辑很脆弱
  });

// ✅ 推荐：直接用 allSettled()
const results = await Promise.allSettled([fetch('/a'), fetch('/b'), fetch('/c')]);
results.filter(r => r.status === 'rejected').forEach(r => handleFailure(r.reason));
```

#### 原则 3：始终处理 any() 的 AggregateError

不要用通用的 `.catch()` 直接吞掉 `any()` 的 AggregateError——其中包含了所有备选方案的失败原因，对调试和降级决策非常有价值：

```javascript
// ❌ 不推荐
Promise.any(sources).catch(err => showToast('加载失败')); // 丢掉了所有错误详情

// ✅ 推荐
try {
  const data = await Promise.any(sources);
  render(data);
} catch (err) {
  if (err instanceof AggregateError) {
    // 分析每个源的失败原因来做精准的降级决策
    const networkErrors = err.errors.filter(e => isNetworkError(e));
    const serverErrors = err.errors.filter(e => isServerError(e));

    if (networkErrors.length > 0) {
      showOfflineMode();
    } else if (serverErrors.length === err.errors.length) {
      showMaintenancePage();
    } else {
      showPartialData();
    }
  }
}
```

#### 原则 4：race() 要配合清理逻辑

使用 `race()` 做超时或竞速时，被淘汰的 Promise 可能还在占用系统资源。**始终配合 `AbortController` 或 `.finally()` 进行清理**：

```javascript
// ✅ 完整模式：race + AbortController + finally 清理
function robustFetchWithTimeout(url, timeoutMs) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);

  return fetch(url, { signal: controller.signal }).finally(() => {
    clearTimeout(timer); // 无论成功失败都清理定时器
  });
}
```

#### 原则 5：空数组防御

`race()` 和 `any()` 对空数组的行为是"永远 pending"——这几乎总是 bug。**始终在调用前做空数组检查**：

```javascript
function safeAny(promises) {
  const arr = Array.isArray(promises) ? promises : [...promises];
  if (arr.length === 0) {
    return Promise.reject(new Error('safeAny: 不能传入空的可迭代对象'));
  }
  return Promise.any(arr);
}
```

#### 原则 6：错误信息要携带上下文

在批量操作中，让每个 Promise 的 reject 原因携带足够的信息（URL、ID、索引、时间戳等），方便 `allSettled()` 或 `AggregateError` 后的分类统计和根因分析：

```javascript
// ✅ 好：错误信息丰富
Promise.allSettled(
  urls.map((url, i) =>
    fetch(url).catch(err => {
      err.url = url;
      err.index = i;
      err.timestamp = Date.now();
      throw err;  // 附加信息后重新抛出
    })
  )
);

// ❌ 不好：错误信息空洞
Promise.allSettled(
  urls.map(url => fetch(url))  // 失败时只知道 "Failed to fetch"
);
```

## 十一、性能考量与基准

### 11.1 各方法的相对性能

| 方法 | 时间复杂度 | 空间开销 | 备注 |
|------|-----------|---------|------|
| `resolve/reject` | O(1) | O(1) | 极快，几乎无开销 |
| `all` | O(n) | O(n) | 需要存储 n 个结果 |
| `allSettled` | O(n) | O(n) | 比 `all` 稍慢（每个都要包装）|
| `race` | O(n) | O(1) | 只需跟踪最快的一个 |
| `any` | O(n) | O(n) | 最坏情况需要等到最后一个 reject |

### 11.2 all() 的并行度限制

`Promise.all()` 虽然是"并行"的，但并不意味着所有 Promise 真正的同时执行。实际并行度受到以下因素限制：

1. **浏览器 HTTP 并发限制**：同一域名通常最多 6 个 TCP 连接（HTTP/1.1），HTTP/2 支持多路复用但仍有上限
2. **操作系统文件描述符限制**：Node.js 环境下尤其需要注意
3. **服务器限流**（Rate Limiting）：API 服务器可能限制同一客户端的并发请求数

当需要大量并行请求时，**使用并发限制器（见 8.1 节）而非直接传给 `all()`** 是更好的做法。

### 11.3 resolve() 与 new Promise() 性能对比

在绝大多数场景下，两者的性能差异可以忽略不计（微秒级别）。但在极高性能敏感的循环中（如每秒调用百万次），`Promise.resolve()` 通常略快于 `new Promise()`：

```javascript
// 微基准测试（仅供理解，实际项目中不要做这种优化）
const N = 1000000;

// new Promise 版本
console.time('new Promise');
for (let i = 0; i < N; i++) {
  new Promise(r => r(i));
}
console.timeEnd('new Promise'); // 约 200-400ms（因引擎而异）

// Promise.resolve 版本
console.time('Promise.resolve');
for (let i = 0; i < N; i++) {
  Promise.resolve(i);
}
console.timeEnd('Promise.resolve'); // 约 150-300ms（略快）
```

**但这不应该成为选择依据**。代码可读性和正确性永远优于微秒级的性能差异。只有在经过性能分析（profiling）确认此处为热点路径后，才应考虑这种级别的优化。

## 十二、知识图谱

```
Promise 静态方法体系
│
├── 工厂方法（Factory Methods）
│   ├── Promise.resolve(value)
│   │   ├── 基础：创建已 fulfilled 的 Promise（O(1) 时间）
│   │   ├── ⭐ Thenable 自动拆包协议
│   │   │   ├── 定义：有 .then() 方法的对象即为 Thenable
│   │   │   ├── 过程：同步调用 then(resolve, reject)，递归展开
│   │   │   ├── 目的：跨库互操作性（jQuery/Q.js/Bluebird ↔ 原生 Promise）
│   │   │   └── 陷阱：非函数的 then / 原型链上的 then / then 内 throw
│   │   ├── 嵌套 Promise 展开：Promise<Promise<T>> → Promise<T>
│   │   └── 应用：统一同步/异步接口 / mock 测试 / 链式传值
│   │
│   └── Promise.reject(reason)
│       ├── 基础：创建已 rejected 的 Promise
│       ├── ⚠️ 关键差异：不拆包 Thenable！（语义：reason 是证据不是线索）
│       ├── 最佳实践：始终传入 Error 实例（保留堆栈）
│       └── 应用：Guard Clause 前置校验 / mock 错误 / 状态机非法转换
│
├── 组合器（Combinators）—— 并行与竞速
│   ├── Promise.all(iterable)
│   │   ├── 策略：全有或全无（AND 逻辑）
│   │   ├── 成功路径：[v1,v2,...vn]，保持输入顺序 ⭐
│   │   ├── 失败路径：⚡ 短路效应（首个 reject 立即终止）
│   │   ├── 非 Promise 值：原样传递（视为瞬时 fulfilled）
│   │   ├── ⚠️ 陷阱：吞掉后续错误 → unhandledrejection
│   │   ├── 经典模式：并行加载多资源 / 两阶段加载（Response → JSON）
│   │   └── 适用：所有数据必须成功才能继续的场景
│   │
│   ├── Promise.allSettled(iterable)  [ES2020]
│   │   ├── 策略：容错全收集（永不 reject）
│   │   ├── 结果结构：[{status:'fulfilled',value}, {status:'rejected',reason}]
│   │   ├── Polyfill：all() + 双 handler 包装（失败→成功对象）
│   │   ├── 工具函数：getFulfilledValues / getRejectedReasons / isAllFulfilled
│   │   └── 适用：批量上传 / 表单校验 / 部分失败可接受的场景
│   │
│   ├── Promise.race(iterable)
│   │   ├── 策略：首个 settled 者胜（OR 逻辑，含失败）
│   │   ├── 经典应用：超时控制（race vs setTimeout）
│   │   ├── ⚠️ 资源泄漏：被淘汰的 Promise 未取消
│   │   ├── 解决：AbortController 真正取消 fetch
│   │   └── 适用：超时 / 取消 / 多镜像源竞速（含失败也算）
│   │
│   └── Promise.any(iterable)  [ES2021]
│       ├── 策略：首个 fulfilled 者胜（忽略失败）
│       ├── 全败结局：AggregateError（.errors 包含所有原因）
│       └── 适用：多源容错 / CDN 镜像加速 / 备用 API 端点
│
└── 高级模式（Advanced Patterns）
    ├── 并发限制器（Set + race + 循环）—— 控制 N 个同时执行
    ├── 重试包装器（递归 + setTimeout + 指数退避）
    ├── Map + All 两阶段加载（先 IDs 后详情）
    ├── allSettled + 过滤恢复（失败项自动降级）
    └── race + AbortController（超时 + 真正取消）
```

## 十三、总结

Promise 的六个静态方法构成了异步编程的**完整工具箱**。掌握它们意味着你能够在任何异步场景下选择最合适的工具：

| 维度 | 核心要点 |
|------|---------|
| **角色分工** | `resolve/reject` 是**工厂**（创建单个 Promise）；`all/allSettled/race/any` 是**组合器**（组合多个 Promise）|
| **成败哲学** | `all`=全对才算对；`allSettled`=对错都要记录；`race`=谁快谁赢（含失败）；`any`=谁先对谁赢 |
| **Thenable 协议** | `resolve` **会递归拆包**（跨库互操作的关键），`reject` **不会拆包**（语义保证）——这是最常见的混淆点 |
| **短路 vs 容错** | `all()` 的短路行为既是优势（快速失败 Fail Fast）也是隐患（丢失后续错误信息）|
| **settled vs fulfilled** | 这是区分 `race()` 和 `any()` 的关键词：settled 含失败，fulfilled 仅指成功 |
| **空数组边界** | `all/allSettled` 空数组立即 resolve；`race/any` 空数组**永远 pending**（几乎总是 bug）|
| **实战频率排行** | `all()` > `resolve()` > `race()` > `allSettled()` > `reject()` > `any()` |
| **ES 版本** | `resolve/reject/all/race` = ES2015（广泛支持）；`finally` = ES2018；`allSettled/any` = ES2021（较新）|
| **最佳搭档** | 静态方法 + **async/await** + **AbortController** = 现代 JS 异步编程的三剑客 |
