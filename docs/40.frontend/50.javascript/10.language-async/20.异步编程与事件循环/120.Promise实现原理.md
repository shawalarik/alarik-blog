# Promise 实现原理 —— 从状态机到微任务队列，手写符合规范的 Promise

> **核心内容**：Promise 不只是 API，更是一套精巧的状态机 + 异步调度系统。本文从零开始拆解 Promise 的内部构造——状态机模型、executor 同步执行机制、then 链式调用原理、Thenable 拆包算法、微任务队列调度、错误传播机制，最终手写一个通过 Promises/A+ 测试套件的完整实现。

## 一、为什么需要理解实现原理？

你已经会使用 `Promise` 了——`new Promise()`、`.then()`. `.catch()`、`async/await` 都能熟练运用。但你是否想过以下问题：

1. **为什么 `.then()` 的回调是异步的？** 即使 `Promise.resolve(42)` 已经是完成状态了，`.then(v => console.log(v))` 里的代码也不会立即运行。
2. **`new Promise()` 里面的代码到底什么时候执行？** 是创建时还是 `.then()` 注册后？
3. **`.then()` 怎么做到链式调用的？** 为什么每次 `.then()` 都返回一个新的 Promise？
4. **Promise.resolve(thenable)` 是如何"拆包"的？** 引擎内部做了什么操作？
5. **`unhandledrejection` 事件是什么时候触发的？** 为什么延迟用 `setTimeout` 去捕获错误来不及？

这些问题都指向 Promise 内部的实现机制。**理解这些机制的价值在于：**

- **调试能力提升**：当遇到奇怪的异步问题时（比如 `.then()` 不执行、错误被吞掉），你能准确推断出原因而不是盲目试错
- **面试竞争力**：手写 Promise 是前端高频面试题，但真正拉开差距的不是"能写出来"，而是理解每一步设计决策背后的原因
- **架构设计能力**：Promise 的状态机模式和观察者模式可以应用到很多其他场景中
- **阅读源码基础**：V8 引擎中 Promise 的 C++ 实现、各种 polyfill 库的实现，都基于相同的原理

### 本文的学习路线

```
内部状态机 → 理解 Promise 的核心数据结构
    ↓
Executor 机制 → 理解同步执行的"生产者"
    ↓
then 链式调用 → 理解新 Promise 的创建与值传递
    ↓
Thenable 拆包 → 理解 resolve 的递归展开算法
    ↓
微任务队列 → 理解异步调度的时机
    ↓
错误处理机制 → 理解隐式 try-catch 和 unhandledrejection
    ↓
手写完整实现 → 将理论转化为可运行的代码
```

## 二、内部状态机 —— Promise 的心脏

### 2.1 三种状态的精确定义

每个 Promise 对象在内部维护两个关键属性：

| 属性名 | 初始值 | 说明 |
|--------|--------|------|
| `state` | `"pending"` | 当前状态：pending / fulfilled / rejected |
| `result` | `undefined` | 最终结果：resolve 的值或 reject 的原因 |

**状态转换图**：

```
                    resolve(value)
   ┌─────────┐    ───────────────────────>   ┌──────────────┐
   │         │                               │              │
   │ pending ├─────────────────────────────→│  fulfilled   │
   │  (待定) │                               │  (已兑现)     │
   │         │                               │ result=value │
   └─────────┘                               └──────────────┘
        │
        │     reject(reason)
        │    ────────────────────────
        │
        ▼
   ┌──────────────┐
   │              │
   │  rejected    │
   │  (已拒绝)     │
   │ result=reason│
   └──────────────┘

   ⚠️ 关键规则：状态只能 pending → fulfilled 或 pending → rejected
      一旦变更，不可逆！不可回退！不可再次改变！
```

**这个"单向不可逆"特性是整个 Promise 体系最根本的设计约束**。它保证了：
- 一个 Promise 的最终结果是确定的——你不会看到它一会儿成功一会儿失败
- 多个消费者（`.then()` handler）看到的都是同一个确定的结果
- 链式调用中的每个环节都有明确的输入和输出

**通俗类比**：Promise 就像一封已经寄出的信件。信一旦寄出，它的状态就确定了——要么送达（fulfilled），要么丢失/退回（rejected）。你不能说"等等，我改主意了，把信撤回来改成另一封"。信的状态是终局的。

### 2.2 状态不可逆的实际影响

```javascript
let p = new Promise((resolve, reject) => {
  resolve('第一次调用');       // ✅ 生效：pending → fulfilled
  reject(new Error('第二次')); // ❌ 忽略！已经是 fulfilled 了
});

p.then(console.log);            // '第一次调用'
p.catch(err => console.log(err)); // 永远不会执行
```

**为什么后续调用会被忽略？** 因为在引擎内部的 `resolve()` 函数中，第一件事就是检查当前状态是否仍为 `pending`。如果不是（说明已经被 settle 过了），直接返回，什么都不做。这是一种**幂等性保证**——无论你调用多少次 `resolve/reject`，效果只相当于调用一次。

```javascript
// 更极端的例子：多次 resolve 和 reject 全部忽略
let p = new Promise((resolve, reject) => {
  resolve(1);                  // ✅ 生效
  resolve(2);                  // ❌ 忽略
  resolve(3);                  // ❌ 忽略
  reject('a');                 // ❌ 忽略
  reject('b');                 // ❌ 忽略

  setTimeout(() => {
    resolve(4);                // ❌ 忽略（即使过了很久）
  }, 5000);
});

p.then(v => console.log(v));   // 输出: 1
// 5 秒后没有任何变化
```

这种设计消除了竞态条件的不确定性。想象一下如果允许多次状态切换，那么多个 `.then()` 可能在不同时间看到不同的结果——这会导致完全不可预测的行为。

### 2.3 内部属性的外部不可访问性

你可能想问："既然有 `state` 和 `result` 属性，能不能直接访问它们？"

答案是**不能**。这两个属性是 JavaScript 引擎的内部实现细节（ECMAScript 规范中称为 Internal Slots，用 `[[]]` 表示为 `[[PromiseState]]` 和 `[[PromiseResult]]`），不暴露给 JavaScript 层面。

```javascript
let p = Promise.resolve(42);

console.log(p.state);     // undefined！不存在这个属性
console.log(p.result);     // undefined！也不存在
console.log(p);            // Promise {<fulfilled>: 42}
                          // 只能看到浏览器 DevTools 的友好显示

// 你唯一能获取结果的方式是通过 .then()
p.then(v => console.log(v)); // 42
```

**为什么要隐藏内部状态？**

这是**封装原则**的体现。如果把 `state` 和 `result` 暴露出去，开发者就可以随意修改它们——这会破坏 Promise 的不变量（invariant）。强制通过 `.then()` 访问结果，确保了：

1. 结果只能在正确的时机获取（异步的）
2. 无法从外部篡改已 settled 的 Promise
3. 引擎可以在内部做优化（如缓存策略）而不影响外部接口

## 三、Executor 机制 —— 同步执行的"生产者"

### 3.1 核心事实：Executor 立即同步执行

这是 Promise 最容易误解的地方之一。很多人以为 executor 中的代码是"异步延迟执行"的——**大错特错！**

```javascript
console.log('① 开始');

let p = new Promise((resolve, reject) => {
  console.log('② Executor 执行中');  // 这行什么时候运行？
  resolve('Hello');
  console.log('③ Executor 继续');
});

console.log('④ Promise 创建完毕');

p.then(v => console.log('⑤', v));

// 实际输出顺序：
// ① 开始
// ② Executor 执行中    ← 立即同步执行！
// ③ Executor 继续      ← 还没退出 executor
// ④ Promise 创建完毕
// ⑤ Hello               ← 这是 .then() 的回调，才是异步的
```

**注意输出顺序**：② 和 ③ 在 ④ 之前！这意味着 `new Promise()` 构造函数在返回之前就已经**完整地**执行完了 executor 函数。executor 不是"注册以后再执行"，而是**立刻、马上、同步地**执行。

### 3.2 为什么必须是同步执行？—— 设计理由

你可能会问：让 executor 异步执行不是更合理吗？这样就不会阻塞后面的代码了。

答案涉及一个关键的架构决策：**Promise 的职责分离**。

**通俗类比**：Promise 就像一家快递公司的服务流程：

1. **下单（new Promise）**：你填写运单信息——这个过程是**同步的**（你必须现在就填好地址和物品描述）
2. **包裹运输（executor 内部操作）**：快递员取货并运输——这可能需要很长时间（网络请求、定时器等）
3. **签收通知（.then() 回调）**：包裹送达后通知你来签收——这个通知是**异步的**（你不需要一直等在门口）

executor 就是那个"填单"的过程。它必须在 `new Promise()` 返回前完成，因为：
- 它负责**启动异步任务**（如发起 fetch 请求、设置 setTimeout）。如果不立即执行，异步任务永远不会开始
- 它决定了 Promise 的初始行为（是立即 resolve 还是等待异步操作）

```javascript
// 如果 executor 是异步的，下面的代码就会出问题：
let p = new Promise(resolve => {
  // 假设这里不是立即执行，而是"稍后执行"
  fetch('/api/data').then(r => r.json()).then(resolve);
  // 如果 executor 被推迟执行，fetch 请求也就会被推迟发出！
});
// 我们希望的是：创建 Promise 时就立即发起请求
// 只是请求的结果（resolve）是异步到达的
```

### 3.3 Executor 中 throw 的自动捕获

另一个重要的机制：**executor 内部抛出的异常会自动转化为 rejection**。这是因为引擎在执行 executor 时，内部给它包裹了一层隐式的 try-catch：

```javascript
let p = new Promise((resolve, reject) => {
  throw new Error('Executor 里抛错了！');
  // 上面的 throw 相当于自动调用了：
  // reject(new Error('Executor 里抛错了！'));
});

p.catch(err => console.log(err.message)); // 'Executor 里抛错了！'
```

等价于以下手动写法：

```javascript
let p = new Promise((resolve, reject) => {
  try {
    throw new Error('Executor 里抛错了！');
  } catch (err) {
    reject(err); // 自动将异常转为 rejection
  }
});
```

**这个机制的存在意义**：如果 executor 中的异常不能自动捕获，它就会变成一个未处理的异常导致程序崩溃。但有了这个机制，executor 中的任何错误都会优雅地变成 Promise 的 rejection，可以通过 `.catch()` 来统一处理。这就是 Promise "让异步错误的处理方式与同步错误一致"的设计目标之一。

### 3.4 resolve/reject 函数的本质

传递给 executor 的 `resolve` 和 `reject` 并不是普通函数——它们是**引擎提供的特殊函数**，具有以下内置行为：

#### resolve 的行为

```javascript
function builtInResolve(value) {
  // 步骤 1：检查当前状态
  if (this.state !== 'pending') return; // 已 settle，忽略

  // 步骤 2：更新状态和结果
  this.state = 'fulfilled';
  this.result = value; // 注意：value 可能是一个 Thenable 或 Promise！

  // 步骤 3：触发所有 onFulfilled 回调（放入微任务队列）
  this.triggerQueue();
}
```

#### reject 的行为

```javascript
function builtInReject(reason) {
  // 步骤 1：检查当前状态
  if (this.state !== 'pending') return;

  // 步骤 2：更新状态和结果
  this.state = 'rejected';
  this.result = reason;

  // 步骤 3：触发所有 onRejected 回调（放入微任务队列）
  // 如果没有处理器，触发 unhandledrejection
  this.triggerQueue();
}
```

注意两者的对称性：唯一的区别是状态名称和结果字段名不同。但有一个**关键差异**后面会详细讲：`resolve(value)` 在 `value` 是 Thenable/Promise 时不会立即存储 value，而是会进入**解析过程**（Resolution Procedure）。

## 四、then 方法 —— 链式调用的秘密

### 4.1 then 的核心契约

`.then(onFulfilled, onRejected)` 是 Promise 最核心的方法。根据 Promises/A+ 规范，它必须满足：

1. **返回一个新的 Promise**——永远不是原来的那个
2. **两个参数都是可选的**——如果传入的不是函数，会被忽略/替换
3. **handler 必须异步执行**——即使 Promise 已经 settled

```javascript
let original = Promise.resolve(42);
let derived = original.then(v => v * 2);

console.log(original === derived); // false！是全新的 Promise
original.then(v => console.log('原:', v));   // 42
derived.then(v => console.log('新:', v));     // 84
```

**为什么必须返回新的 Promise？** 这是链式调用的基础：

```javascript
Promise.resolve(1)
  .then(v => v + 1)  // 返回 Promise A
  .then(v => v * 2)  // 返回 Promise B
  .then(v => console.log(v)); // 返回 Promise C

// 如果 .then() 返回原始 Promise：
// 那么 .then().then() 就没有意义了，
// 因为你无法区分"第一个 then 的结果"和"第二个 then 的结果"
// 每一步都需要自己的 Promise 来承载自己的结果
```

### 4.2 then 的内部执行流程

当你调用 `promise.then(onFulfilled, onRejected)` 时，内部发生了以下过程：

```
promise.then(onFulfilled, onRejected) 被调用
│
├─→ 创建一个新的 Promise（称为 promise2）← 这是返回值！
│
├─→ 检查 promise 当前的 state：
│   │
│   ├─→ state === 'pending'？
│   │   └─→ 把 { promise2, onFulfilled, onRejected } 存入 promise 的队列
│   │       （等 promise settle 后再处理）
│   │
│   ├─→ state === 'fulfilled'？
│   │   └─→ 把 onFulfilled(promise.result) 包装为微任务
│   │       （微任务执行时：用结果来 resolve/reject promise2）
│   │
│   └─→ state === 'rejected'？
│       └─→ 把 onRejected(promise.result) 包装为微任务
│           （同上）
│
└─→ 立即返回 promise2 ← 此时 handler 还没执行！
```

### 4.3 参数规范化

Promises/A+ 规范要求对 `onFulfilled` 和 `onRejected` 进行**参数校验和规范化**：

```javascript
// 规范原文：
// If onFulfilled is not a function, it must be ignored
// If onRejected is not a function, it must be ignored

// 具体来说：

// 1. onFulfilled 不是函数 → 用默认的恒等函数替代
promise.then(null, onRejected)
  // 等价于：
promise.then(value => value, onRejected)

// 2. onRejected 不是函数 → 用默认的透传函数替代
promise.then(onFulfilled, null)
  // 等价于：
promise.then(onFulfilled, reason => { throw reason })

// 3. 两个都不是函数 → 值/错误直接透传到下一个
promise.then(null, null)
  // 等价于：
promise.then(value => value, reason => { throw reason })
```

**为什么需要这个规范？** 因为实际使用中经常出现只传一个参数的情况：

```javascript
// 只关心成功，不处理错误
fetchData().then(data => render(data));
// 等价于：fetchData().then(data => render(data), undefined)
// undefined 不是函数 → 错误会透传下去

// 只关心错误
initApp().catch(err => showError(err));
// .catch(f) 就是 .then(undefined, f) 的语法糖
```

### 4.4 Handler 三种返回值的处理

当 `.then()` 的 handler 执行完成后，它的返回值决定了**返回的新 Promise（promise2）** 如何 settle。这是链式调用中最核心的逻辑：

#### 情况一：返回普通值 → promise2 以该值 fulfill

```javascript
Promise.resolve(1)
  .then(v => v + 1)   // 返回 2（普通值）
  .then(console.log);  // 2

// 内部过程：
// handler(v=1) 返回 2
// → resolvePromise(promise2, 2)
// → 2 不是 Thenable
// → promise2 以值 2 fulfill
```

#### 情况二：返回 Promise → promise2 等待该 Promise 后 adopt 其状态

```javascript
Promise.resolve(1)
  .then(v => fetch('/api/' + v))  // 返回一个 Promise
  .then(response => console.log(response.status));

// 内部过程：
// handler(v=1) 返回 fetchPromise（一个 Promise 对象）
// → resolvePromise(promise2, fetchPromise)
// → fetchPromise 是 Thenable（因为 Promise 有 .then 方法）
// → 进入 Thenable 解析过程（详见第六节）
// → promise2 adopt fetchPromise 的最终状态和结果
```

#### 情况三：throw 错误 → promise2 以该错误 reject

```javascript
Promise.resolve(1)
  .then(v => {
    throw new Error('Handler 里出错');
  })
  .catch(err => console.log(err.message));

// 内部过程：
// handler 抛出了 Error
// → 这个 throw 被 .then() 内部的隐式 try-catch 捕获
// → 相当于 rejectPromise(promise2, error)
// → promise2 被 reject
```

**这三个情况覆盖了 handler 所有可能的行为**，使得链式调用中的数据流动完全可控且可预测。

## 五、Thenable 解析算法 —— Promise 的递归展开

### 5.1 什么是 Thenable 解析？

前面多次提到 `Promise.resolve(value)` 在 value 是 Thenable 时会"拆包"。这个拆包过程的正式名称叫 **Promise Resolution Procedure**（Promise 解析过程），是 Promises/A+ 规范的核心算法之一。

**触发条件**：当 `resolve(x)` 被调用且 x 是一个对象或函数时，引擎会检查 x 是否有 `then` 方法。如果有，就进入 Thenable 解析过程。

### 5.2 解析算法的伪代码

以下是 Promises/A+ 规范中 `[[Resolve]](promise, x)` 算法的简化版：

```javascript
function resolvePromise(promise, x) {
  // 规则 1：如果 x 和 promise 是同一个对象 → 循环引用错误
  if (promise === x) {
    return reject(promise, new TypeError('循环引用'));
  }

  // 规则 2：如果 x 是 Promise（有明确的状态）
  // 直接 adopt x 的状态
  if (x instanceof MyPromise) {
    x.then(
      y => resolvePromise(promise, y),   // x fulfill → 递归解析 y
      r => reject(promise, r)             // x reject → 直接 reject
    );
    return;
  }

  // 规则 3：如果 x 是对象或函数（可能是 Thenable）
  if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
    let called = false;  // 防止多次调用

    try {
      let then = x.then;  // 读取 then 属性

      if (typeof then === 'function') {
        // ✅ 确认是 Thenable！以 x 为 this 调用 then 方法
        then.call(
          x,
          // then 的 resolve 参数
          y => {
            if (called) return; called = true;  // 防重入
            resolvePromise(promise, y);          // 递归！
          },
          // then 的 reject 参数
          r => {
            if (called) return; called = true;
            reject(promise, r);
          }
        );
      } else {
        // x 没有 then 方法（或 then 不是函数）→ 当作普通值
        fulfill(promise, x);
      }

    } catch (e) {
      // 读取 x.then 或调用 then 时抛出异常
      if (called) return; called = true;
      reject(promise, e);
    }

    return;
  }

  // 规则 4：其他情况 → x 是普通值，直接 fulfill
  fulfill(promise, x);
}
```

### 5.3 逐条解读算法的关键点

#### 规则 1：防止循环引用

```javascript
let p = {};
p.then = p;  // p 的 then 指向自己

let promise = Promise.resolve(p);
// TypeError: 循环引用！
```

如果没有这个检查，`then.call(p, ...)` 会无限递归调用自身，导致栈溢出。这是一个安全阀——**如果一个 Promise 要解析的值就是它自己或包含自身的链条，直接报错比无限递归要好得多**。

**类比**：就像你在照两面相对的镜子——如果你试图追踪"镜子里面的镜子里面..."的影像，你会陷入无限递归。循环引用检查就是在说："如果发现自己在看自己的倒影，停下来。"

#### 规则 2：直接 adopt 已有 Promise 的状态

```javascript
let inner = Promise.resolve('inner value');

// Promise.resolve(inner) 会直接 adopt inner 的状态
let outer = Promise.resolve(inner);

outer === inner;  // false（是不同的对象）
// 但 outer 的状态和结果与 inner 完全相同
outer.then(v => console.log(v)); // 'inner value'

// 即使 inner 后来改变了（实际上不可能，因为状态不可逆），
// outer 也已经在那一刻 adopt 了 inner 当时状态
```

**为什么不直接 `outer = inner`？** 因为 `Promise.resolve()` 的语义是"创建一个新 Promise"，所以总是返回新对象。但如果参数本身就是一个 Promise，复制其状态比重新包装更有意义。

#### 规则 3：Thenable 的递归解析

这是最复杂的部分。核心逻辑是：

1. 读取 `x.then`（可能抛出异常——如果 getter 有副作用的话）
2. 如果 `then` 是函数，把它当作"解析函数"来调用
3. 传入两个回调（resolveHandler 和 rejectHandler）
4. **防重入标志 called**：确保 resolve 或 reject 只调用一次

**防重入的重要性**：某些恶意的或写得不好的 Thenable 可能会在同一个 `then` 调用中同时调用 resolve 和 reject：

```javascript
let weird = {
  then(resolve, reject) {
    resolve(1);  // 第一次调用
    reject(2);   // 第二次调用 ← 应该被忽略
    resolve(3);   // 第三次调用 ← 也应该被忽略
  }
};

Promise.resolve(weird).then(console.log); // 1（只有第一次生效）
```

`called` 标志保证了只有第一次调用有效，后续全部静默忽略。

#### 规则 4：普通值直接 fulfill

```javascript
Promise.resolve(42).then(v => console.log(v));  // 42
Promise.resolve('hello').then(v => console.log(v)); // 'hello'
Promise.resolve(null).then(v => console.log(v));  // null
Promise.resolve(undefined).then(v => console.log(v)); // undefined
```

### 5.4 嵌套 Thenable 的多层展开

解析算法是**递归的**，这意味着嵌套的 Thenable 会被一层层剥开：

```javascript
// 三层嵌套
let level3 = {
  then(resolve) { resolve('最终值'); }
};

let level2 = {
  then(resolve) { resolve(level3); }  // resolve 了一个 Thenable
};

let level1 = {
  then(resolve) { resolve(level2); }  // resolve 了一个 Thenable
};

Promise.resolve(level1).then(v => console.log(v));
// '最终值'

// 解析过程：
// resolvePromise(promise, level1)
//   → level1 是 Thenable → 调用 level1.then(resolveHandler)
//     → resolveHandler 收到 level2 → resolvePromise(promise, level2)
//       → level2 是 Thenable → 调用 level2.then(resolveHandler)
//         → resolveHandler 收到 level3 → resolvePromise(promise, level3)
//           → level3 是 Thenable → 调用 level3.then(resolveHandler)
//             → resolveHandler 收到 '最终值' → fulfill(promise, '最终值')
```

每一层都是一次完整的 `resolvePromise` 递归调用。这就是为什么 `Promise.resolve(Promise.resolve(Promise.resolve(42)))` 最终得到的只是一个值为 42 的普通 Promise——所有嵌套都被展平了。

## 六、微任务队列 —— 异步调度的引擎

### 6.1 什么是微任务？

微任务（Microtask）是 JavaScript 引擎内部的一种**高优先级异步任务队列**。它与宏任务（Macrotask，如 setTimeout、事件回调、UI 渲染等）共同构成了事件循环的两个层级。

**Promise 的 `.then()/.catch()/.finally()` 回调都被放入微任务队列中执行。**

### 6.2 微任务的执行时机

微任务队列的处理遵循严格的时机规则：

```
事件循环的一个完整轮回：

1. 执行一个宏任务（如一段 <script> 代码、setTimeout 回调等）
   │
2. 【关键步骤】宏任务执行完后，立即清空微任务队列
   │  ├── 取出队首的微任务并执行
   │  ├── 该微任务可能产生新的微任务 → 加入队尾
   │  ├── 继续取出下一个微任务...
   │  └── 直到微任务队列为空
   │
3. 浏览器渲染（如果需要）
   │
4. 回到步骤 1，取下一个宏任务
```

**核心特征：微任务在每个宏任务结束后、下一个宏任务开始前被集中处理。而且微任务执行过程中产生的新的微任务也会在同一批中被处理掉（不会等到下一轮）。**

```javascript
console.log('① script start');

Promise.resolve()
  .then(() => console.log('② promise1'))
  .then(() => console.log('③ promise2'));

Promise.resolve()
  .then(() => console.log('④ promise3'));

console.log('⑤ script end');

// 执行顺序：
// ① script start     ← 同步代码
// ⑤ script end       ← 同步代码结束
// ② promise1          ← 微任务队列第一轮
// ④ promise3          ← 微任务队列第二轮（同一批处理）
// ③ promise2          ← promise1 执行后又产生了新微任务，继续处理
```

**为什么 ② 在 ④ 前面？** 因为先注册的微任务先入队（FIFO）。而 ③ 在最后是因为它是 ② 的 handler 执行后才注册的新微任务——但微任务队列的处理是一直到空为止，所以 ③ 也在同一批中被执行了。

### 6.3 为什么 then 的回调必须是异步的？

这是一个经典面试问题。假设 `.then()` 的 handler 是**同步执行**的：

```javascript
// 假设：then 是同步的
let data;
Promise.resolve(1).then(v => { data = v; });
console.log(data); // 期望输出 1

// 但考虑这种情况：
let promise = Promise.resolve();
promise.then(() => console.log('then 1'));
promise.then(() => console.log('then 2'));

// 如果同步执行，输出：then 1, then 2
// 这看起来没问题...但是：
```

问题出在**链式调用**上：

```javascript
// 假设：then 是同步的
let p1 = Promise.resolve(1);
let p2 = p1.then(v => {
  console.log('handler 1:', v);
  return v + 1;
});
// 如果 handler 同步执行了，那 p2 现在就已经是 fulfilled 状态了

let p3 = p2.then(v => {
  console.log('handler 2:', v);
  return v * 2;
});
// p2 已经 fulfilled → handler 2 也同步执行了
// p3 也 fulfilled...

// 这意味着整个 Promise 链变成了同步执行！
// 失去了异步的所有优势：
// 1. 不能在 handler 之间插入其他操作
// 2. 如果 handler 中有大量计算，会阻塞主线程
// 3. 与 async/await 的语义冲突
```

**更深层的理由——一致性**：如果 Promise 已 settle 时 then 同步执行、未 settle 时异步执行，那么同一段代码在不同时机会有不同的行为——这是灾难性的不一致。**统一为异步执行消除了这个不确定性。**

### 6.4 unhandledrejection 的检测时机

这是一个非常精妙的机制。**`unhandledrejection` 事件的触发不是在 Promise 被 reject 的时刻，而是在一轮微任务队列清空后检测到的**：

```javascript
// 场景 A：正常处理 → 不触发
let p = Promise.reject(new Error('oops'));
p.catch(err => console.log('caught:', err.message)); // caught: oops
// 微任务队列：[catch handler]
// 清空后发现 p 的 rejection 已被处理 → OK

// 场景 B：未处理 → 触发
let p2 = Promise.reject(new Error('oops2'));
// 微任务队列：（空的，没有 catch handler）
// 清空后检测到 p2 是 rejected 且无处理器
// → 触发 unhandledrejection 事件！

// 场景 C：延迟处理（用 setTimeout）→ 仍然触发
let p3 = Promise.reject(new Error('oops3'));
setTimeout(() => {
  p3.catch(err => console.log('delayed catch:', err.message));
}, 0);
// 微任务队列清空时 → p3 无处理器 → 触发 unhandledrejection!
// setTimeout 是宏任务，在微任务之后才执行
// 到那时 unhandledrejection 已经触发了
```

**这个设计的意义**：它允许你在"本轮微任务处理完"这个时间窗口内去附加 catch handler。如果在窗口期内添加了 catch，就不算"unhandled"；超出了这个窗口，就算你后来加了 catch（通过 setTimeout 等），也已经太晚了——因为引擎认为你"忘记了"处理它。

**类比**：这就像餐厅结账。服务员在你用餐结束时过来问"有人买单吗？"（微任务队列清空时的检测）。如果你当时就说"我来付"（同步注册了 catch），那就没问题。但你如果说"我一会回来付"然后离开了（打算用 setTimeout 延迟处理），餐厅可能会把你列入黑名单（触发 unhandledrejection）——因为你离开的那一刻起，他们就没有义务等你回来了。

## 七、错误处理机制 —— 隐式 try-catch 网络

### 7.1 Executor 的隐式 try-catch

前面提到过，executor 内部的 throw 会被自动捕获。这在底层是通过**隐式 try-catch 包裹**实现的：

```javascript
// V8 引擎中的概念性代码（简化版）
class MyPromise {
  constructor(executor) {
    this.state = 'pending';
    this.result = undefined;
    this.onFulfilledCallbacks = [];
    this.onRejectedCallbacks = [];

    // 核心包裹
    const resolve = (value) => { /* ... */ };
    const reject = (reason) => { /* ... */ };

    try {
      executor(resolve, reject);  // ← 立即同步执行
    } catch (err) {
      reject(err);  // executor 中的 throw 自动转为 reject
    }
  }
}
```

这意味着：

```javascript
// 这些写法完全等价：
new Promise((resolve, reject) => {
  throw new Error('boom');
});

new Promise((resolve, reject) => {
  reject(new Error('boom'));
});

new Promise((resolve, reject) => {
  try {
    throw new Error('boom');
  } catch (e) {
    reject(e);
  }
});
```

### 7.2 Handler 的隐式 try-catch

同样地，`.then()` 的 handler 执行时也被隐式 try-catch 包裹：

```javascript
// then 方法的概念性实现片段
then(onFulfilled, onRejected) {
  const promise2 = new MyPromise((resolve, reject) => {
    const handler = (callback, value) => {
      // 隐式 try-catch 包裹每一个 handler
      try {
        const result = callback(value);
        resolvePromise(promise2, result);  // 用返回值 resolve promise2
      } catch (err) {
        reject(promise2, err);  // handler 抛错则 reject promise2
      }
    };
    // ... 根据 state 决定何时调用 handler
  });

  return promise2;
}
```

这就是为什么 `.then()` 中的 throw 能被下游的 `.catch()` 捕获的原因：

```javascript
Promise.resolve(1)
  .then(v => {
    console.log(v); // 1
    throw new Error('handler error'); // 这个 throw 被 then 内部的 try-catch 捕获
  })
  .then(v => {
    console.log('不会到这里'); // 因为上一个 then 返回的 Promise 被 reject 了
  })
  .catch(err => {
    console.log(err.message); // 'handler error' — 成功捕获！
  });
```

**完整的错误传播链路图**：

```
then handler 执行
    │
    ├─→ 正常返回值 x
    │   └─→ resolvePromise(promise2, x) → promise2 fulfill
    │
    └─→ throw error e
        └─→ reject(promise2, e) → promise2 reject
            │
            └─→ 下游的 .catch() 或 .then(null, onError) 接收
```

### 7.3 错误沿链传播的过程

当一个 Promise 被 reject 且当前 `.then()` 没有 onRejected handler 时，错误会**自动向下游传播**：

```javascript
Promise.reject(new Error('原始错误'))
  .then(v => v)           // 只有 onFulfilled，没有 onRejected
                           // → 错误透传（等价于 .then(v=>v, r=>{throw r})）
  .then(v => v * 2)       // 同样没有 onRejected
                           // → 错误继续透传
  .then(v => console.log(v)) // 仍然没有 onRejected
                              // → 错误继续透传
  .catch(err => console.log('终于捕获:', err.message));
  // '终于捕获: 原始错误'
```

**传播机制的实现原理**：当 `.then(onFulfilled, undefined)` 接收到一个 rejected Promise 时，由于 `onRejected` 是 undefined（不是函数），它会使用默认的错误透传函数——即 `reason => { throw reason }`。这使得 rejection 顺着链条一路向下传递，直到遇到一个真正的 `.catch()` 或带有 onRejected 的 `.then()`。

## 八、手写完整实现

### 8.1 第一版：基本状态机 + then

我们先实现最核心的功能——三种状态、executor、then 方法：

```javascript
/**
 * MyPromise - 第一版：基本功能
 *
 * 实现：状态管理、executor 执行、then 方法（基本版）
 */
const PENDING = 'pending';
const FULFILLED = 'fulfilled';
const REJECTED = 'rejected';

class MyPromise {
  constructor(executor) {
    // 内部状态
    this.state = PENDING;
    this.result = undefined;

    // 回调队列（用于处理 pending 状态下注册的 handler）
    this.onFulfilledCallbacks = [];
    this.onRejectedCallbacks = [];

    // resolve 函数
    const resolve = (value) => {
      // 只能在 pending 状态下转换
      if (this.state !== PENDING) return;

      this.state = FULFILLED;
      this.result = value;

      // 触发所有已注册的成功回调
      this.onFulfilledCallbacks.forEach(cb => cb());
    };

    // reject 函数
    const reject = (reason) => {
      if (this.state !== PENDING) return;

      this.state = REJECTED;
      this.result = reason;

      // 触发所有已注册的失败回调
      this.onRejectedCallbacks.forEach(cb => cb());
    };

    // 立即执行 executor，并用 try-catch 包裹
    try {
      executor(resolve, reject);
    } catch (err) {
      reject(err);
    }
  }

  then(onFulfilled, onRejected) {
    // 参数规范化：非函数则替换为默认函数
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : value => value;
    onRejected = typeof onRejected === 'function' ? onRejected : reason => { throw reason };

    // 创建新 Promise（链式调用的关键）
    const promise2 = new MyPromise((resolve, reject) => {
      // 封装通用的 handler 执行逻辑
      const fulfillHandler = () => {
        queueMicrotask(() => {
          try {
            const x = onFulfilled(this.result);
            resolvePromise(promise2, x, resolve, reject);
          } catch (e) {
            reject(e);
          }
        });
      };

      const rejectHandler = () => {
        queueMicrotask(() => {
          try {
            const x = onRejected(this.result);
            resolvePromise(promise2, x, resolve, reject);
          } catch (e) {
            reject(e);
          }
        });
      };

      if (this.state === FULFILLED) {
        fulfillHandler(); // 已 fulfill → 排队执行
      } else if (this.state === REJECTED) {
        rejectHandler(); // 已 reject → 排队执行
      } else {
        // pending → 存入队列，等 settle 后执行
        this.onFulfilledCallbacks.push(fulfillHandler);
        this.onRejectedCallbacks.push(rejectHandler);
      }
    });

    return promise2;
  }
}
```

**代码要点解释**：

1. **常量定义**：用三个字符串常量代替魔法值，提高可读性和减少拼写错误风险
2. **回调队列**：`onFulfilledCallbacks` 数组用于保存 pending 状态下注册的 handler——因为 Promise 还没 settles，handler 不能立即执行，必须排队等候
3. **queueMicrotask**：使用浏览器的原生微任务 API 确保 handler 异步执行（兼容性问题后面解决）
4. **promise2 的创建位置**：在 `then()` 方法内部、return 之前创建——这保证了每次调用 `then()` 都得到一个全新的 Promise

### 8.2 第二版：加入 resolvePromise 算法

上面的代码引用了 `resolvePromise` 函数，现在来实现它：

```javascript
/**
 * Promises/A+ 核心算法：Promise Resolution Procedure
 *
 * @param {MyPromise} promise - 需要被 resolve 的 promise（即 promise2）
 * @param {*} x - handler 的返回值
 * @param {Function} resolve - promise2 的 resolve
 * @param {Function} reject - promise2 的 reject
 */
function resolvePromise(promise, x, resolve, reject) {
  // 规则 1：防止循环引用
  if (promise === x) {
    return reject(new TypeError('Chaining cycle detected for promise'));
  }

  // 规则 2：x 是 MyPromise 实例
  if (x instanceof MyPromise) {
    // adopt x 的状态
    x.then(
      y => resolvePromise(promise, y, resolve, reject),
      reject
    );
    return;
  }

  // 规则 3：x 是对象或函数（可能是 Thenable）
  if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
    let called = false; // 防重入标志

    try {
      const then = x.then; // 读取 then 属性

      if (typeof then === 'function') {
        // Thenable：调用 then 方法
        then.call(
          x,
          // then 的成功回调
          (y) => {
            if (called) return;
            called = true;
            resolvePromise(promise, y, resolve, reject); // 递归！
          },
          // then 的失败回调
          (r) => {
            if (called) return;
            called = true;
            reject(r);
          }
        );
      } else {
        // 有 then 属性但不是函数 → 当作普通值
        resolve(x);
      }
    } catch (e) {
      // 读取 then 或调用 then 时抛出异常
      if (called) return;
      called = true;
      reject(e);
    }

    return;
  }

  // 规则 4：普通值 → 直接 fulfill
  resolve(x);
}
```

**这段代码是 Promises/A+ 规范的灵魂所在**。它实现了：

- **循环引用检测**：防止 `promise.then(() => promise)` 这种自指导致的无限递归
- **Promise 身份识别**：如果是 MyPromise 实例，直接 adopt 其状态
- **Thenable 互操作**：支持任何有 `.then()` 方法的第三方库的对象
- **递归解析**：嵌套的 Thenable 会被层层展开
- **防重入保护**：`called` 标志确保 resolve/reject 只生效一次
- **异常安全**：读取 `then` 或调用 `then` 时的异常都会正确捕获

### 8.3 第三版：补全 catch/finally/resolve/reject

```javascript
// ========== catch 方法 ==========
MyPromise.prototype.catch = function(onRejected) {
  return this.then(null, onRejected); // 语法糖：then(null, onRejected)
};

// ========== finally 方法 ==========
MyPromise.prototype.finally = function(onFinally) {
  return this.then(
    value => {
      // 执行清理回调，但不改变传递的值
      return MyPromise.resolve(onFinalize()).then(() => value);
    },
    reason => {
      // 同样执行清理回调，但保持错误传递
      return MyPromise.resolve(onFinalize()).then(() => { throw reason; });
    }
  );

  function onFinalize() {
    return typeof onFinally === 'function'
      ? onFinally()
      : void 0;
  }
};

// ========== 静态方法：resolve ==========
MyPromise.resolve = function(value) {
  // 如果 value 本身就是 MyPromise 实例，直接返回
  if (value instanceof MyPromise) {
    return value;
  }
  // 否则创建一个新的 fulfilled Promise
  // （value 会经过 resolvePromise 处理，包括 Thenable 拆包）
  return new MyPromise(resolve => resolve(value));
};

// ========== 静态方法：reject ==========
MyPromise.reject = function(reason) {
  // 注意：reject 不会像 resolve 那样拆包 Thenable！
  return new MyPromise((_, reject) => reject(reason));
};
```

### 8.4 第四版：兼容性与测试适配

为了在不支持 `queueMicrotask` 的环境中也能工作，我们需要一个降级方案：

```javascript
// 微任务调度器的跨平台实现
const isBrowser = typeof window !== 'undefined';
const hasQueueMicrotask = typeof queueMicrotask === 'function';

function runMicroTask(fn) {
  if (hasQueueMicrotask) {
    queueMicrotask(fn); // 最佳方案
  } else if (isBrowser && typeof MutationObserver !== 'function') {
    // 旧版浏览器：利用 MutationObserver
    const observer = new MutationObserver(fn);
    const node = document.createTextNode('');
    observer.observe(node, { characterData: true });
    node.data = '1'; // 触发 mutation → 执行 fn
  } else {
    // 最终降级：setTimeout(fn, 0)（不是真正的微任务，但可用）
    setTimeout(fn, 0);
  }
}

// 使用 runMicroTask 替换前面的 queueMicrotask 调用即可
```

**各方案的优先级对比**：

| 方案 | 类型 | 准确性 | 兼容性 |
|------|------|--------|--------|
| `queueMicrotask()` | 原生微任务 API | ✅ 完美 | Chrome 69+, Firefox 69+, Safari 13+, Node.js 11+ |
| `MutationObserver` | hack（DOM 变化触发）| ≈✅ 接近 | 旧版浏览器 |
| `setTimeout(fn, 0)` | 宏任务降级 | ❌ 不精确（会延后到下一轮）| 所有环境 |
| `process.nextTick()` | Node.js 微任务 | ✅ Node.js | 仅 Node.js |

### 8.5 第五版：静态组合器

```javascript
// ========== all ==========
MyPromise.all = function(promises) {
  return new MyPromise((resolve, reject) => {
    const results = [];
    let completedCount = 0;
    const total = promises.length;

    if (total === 0) {
      return resolve([]); // 空数组立即 resolve
    }

    promises.forEach((p, index) => {
      // 先用 resolve() 包装，确保非 Promise 值也能正常处理
      MyPromise.resolve(p).then(
        value => {
          results[index] = value;  // 按索引存放（保序）
          completedCount++;
          if (completedCount === total) {
            resolve(results); // 全部完成
          }
        },
        reject // 任一失败 → 整体 reject（短路）
      );
    });
  });
};

// ========== race ==========
MyPromise.race = function(promises) {
  return new MyPromise((resolve, reject) => {
    promises.forEach(p => {
      MyPromise.resolve(p).then(resolve, reject); // 第一个 settle 的决定结果
    });
  });
};

// ========== allSettled ==========
MyPromise.allSettled = function(promises) {
  return new MyPromise(resolve => {
    const results = [];
    let completedCount = 0;
    const total = promises.length;

    if (total === 0) return resolve([]);

    promises.forEach((p, index) => {
      MyPromise.resolve(p).then(
        value => {
          results[index] = { status: 'fulfilled', value };
          completedCount++;
          if (completedCount === total) resolve(results);
        },
        reason => {
          results[index] = { status: 'rejected', reason };
          completedCount++;
          if (completedCount === total) resolve(results);
        }
      );
    });
  }); // 永远 fulfill（因为包装后的 handler 总是返回对象）
};

// ========== any ==========
MyPromise.any = function(promises) {
  return new MyPromise((resolve, reject) => {
    const errors = [];
    let rejectedCount = 0;
    const total = promises.length;

    if (total === 0) {
      return reject(new AggregateError([], 'All promises were rejected'));
    }

    promises.forEach(p => {
      MyPromise.resolve(p).then(
        resolve, // 第一个成功 → 立即 resolve
        reason => {
          errors.push(reason);
          rejectedCount++;
          if (rejectedCount === total) {
            reject(new AggregateError(errors, 'All promises were rejected'));
          }
        }
      );
    });
  });
};
```

## 十、V8 引擎中的真实实现概览

我们手写的实现是教学用的简化版本。V8 引擎（Chrome/Node.js 使用的 JS 引擎）中的真实实现有以下优化：

### 10.1 对象布局优化

V8 中的 Promise 对象使用了优化的内存布局：

```
V8 内部 Promise 对象结构（简化）：
┌─────────────────────────────────┐
│  Map（隐藏类/Shape）            │  8 bytes - 共享的形状信息
├─────────────────────────────────┤
│  properties（属性指针）         │  8 bytes - 指向属性存储区
├─────────────────────────────────┤
│  elements（元素指针）           │  8 bytes - 指向元素存储区
├─────────────────────────────────┤
│  [[PromiseState]]               │  1 byte  - 状态枚举
│  [[PromiseResult]]              │  8 bytes - 结果值或原因
│  [[PromiseFulfillReactions]]    │  8 bytes - 待执行的 fulfill 反应列表
│  [[PromiseRejectReactions]]     │  8 bytes - 待执行的 reject 反应列表
│  [[IsHandled]]                  │  1 bit   - 是否已有 handler（用于 unhandledrejection 检测）
└─────────────────────────────────┘
```

### 10.2 微任务队列的实现

V8 中的微任务队列是一个**单向链表**结构：

```
Microtask Queue（微任务队列）:

  head → [microtask1] → [microtask2] → [microtask3] → tail
            │                │                │
            ▼                ▼                ▼
       execute()       execute()        execute()
       (then handler)  (then handler)   (then handler)

每次宏任务结束后：
  while (head !== null) {
    task = head;
    head = head.next;
    task.execute();  // 执行微任务
    // 执行过程中可能 push 新的 microtask 到 tail
  }
```

### 10.3 性能优化：快速路径

V8 为常见场景做了大量优化：

1. **已 resolved Promise 的快速路径**：如果 Promise 在创建时就 resolved（如 `Promise.resolve(42)`），then handler 可以更快地入队
2. **单一 reaction 优化**：如果一个 Promise 只有一个 then handler（最常见的情况），就不需要分配反应列表数组
3. **惰性求值**：`[[PromiseResult]]` 在某些情况下可以延迟计算

## 十一、陷阱速查

| # | 陷阱 | 现象 | 原因 | 解决方案 |
|---|------|------|------|----------|
| 1 | **忘记 then 是异步的** | 期望 `.then()` 中的代码立即执行 | then handler 始终通过微任务异步执行 | 如需同步执行，不要放在 then 里 |
| 2 | **循环引用 Thenable** | `TypeError: Chaining cycle` | `{then(){resolve(this)}}` 导致无限递归 | 不要让 Thenable 解析指向自身 |
| 3 | **多次 resolve/reject** | 后续调用被忽略 | 状态一旦变更就不可逆 | 检查逻辑确保只调用一次 |
| 4 | **executor 中忘记 try-catch** | throw 导致未捕获异常 | 虽然 Promise 内部会自动捕获，但自定义实现需手动包裹 | 始终用 try-catch 包裹 executor |
| 5 | **then 返回同一个 Promise** | 链式调用失效 | 每次 then 必须返回**新的** Promise | `const p2 = new Promise(...)` |
| 6 | **thenable 的 then 抛异常** | 错误被吞掉 | 需要在 resolvePromise 中 catch then.call | `try { then.call(...) } catch(e) { reject(e) }` |
| 7 | **微任务 vs setTimeout 混淆** | 顺序不符合预期 | 微任务优先于宏任务 | 记住：微任务 > DOM渲染 > 宏任务 |

## 十二、最佳实践（针对库/框架开发者）

### 12.1 如果你需要实现类 Promise 功能

1. **尽量复用原生 Promise**：除非有充分的性能理由，否则不要自己实现
2. **如果必须实现**，严格遵循 Promises/A+ 规范并通过官方测试套件
3. **提供 Thenable 接口**：让你的类拥有 `.then()` 方法以便与生态集成
4. **文档化你的异步行为**：明确哪些操作是同步的、哪些是异步的

### 12.2 如果你需要调试 Promise 问题

1. **使用 `async stacks`**：Chrome DevTools 的 "Async" 面板可以看到跨异步边界的完整堆栈
2. **监听 `unhandledrejection`**：全局添加监听器捕获遗漏的错误
3. **利用 `Promise.prototype.finally`**：在链尾添加日志便于跟踪完整流程
4. **使用 Chrome DevTools 的 Promise Inspector**：在 Console 中可以直接查看 Promise 的内部状态
