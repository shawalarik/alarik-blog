# async/await 语法糖 —— 转换规则、错误处理与 try/catch、顶层 await

> **核心内容**：async/await 是 JavaScript 异步编程的终极形态——它不是魔法，而是 Promise 的语法糖。本文从底层转换规则讲起，深入 await 的暂停恢复机制、错误处理策略（try/catch vs .catch）、并行执行陷阱、顶层 await，以及 async/await 与 Generator + Promise 运行时的等价性证明。

## 一、为什么需要 async/await？

### 从 Promise 链到 async/await

你已经掌握了 Promise——`.then()` 链式调用、`.catch()` 错误处理、`Promise.all()` 并行组合。但在实际使用中，你可能会遇到以下"痛点"：

```javascript
// 用 Promise 链写一段稍微复杂的逻辑：
function loadAndRenderUser(userId) {
  return fetch(`/api/users/${userId}`)
    .then(response => {
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return response.json();
    })
    .then(user => {
      // 在这里想用 user 变量做一些同步计算...
      const displayName = user.name || user.email.split('@')[0];
      return fetch(`/api/users/${user.id}/posts`);
    })  // ⚠️ 问题：user 变量在这里的作用域里已经不能直接访问了！
    .then(response => response.json())
    .then(posts => {
      // 如果我想同时用到 user 和 posts...
      // 我做不到！因为 user 只在第二个 then 里可用！
      console.log(posts); // 只有 posts，没有 user
    });
}
```

这段代码暴露了 Promise `.then()` 链的几个结构性缺陷：

1. **变量作用域断裂**：每个 `.then()` 是一个独立的作用域，前面步骤的结果变量无法自然地传递到后面的步骤。你需要通过返回值来"手动传递"，但一旦中间步骤需要同时使用多个前置结果，代码就会变得很别扭。
2. **条件分支复杂**：如果某个步骤需要根据前一步的结果决定是否继续、走哪条分支，`.then()` 链会迅速退化为嵌套回调或需要提前返回。
3. **错误处理割裂**：每个 `.then()` 可以有自己的错误处理，但如果你想统一处理多个步骤的错误，就需要把 `.catch()` 放在最后——而中间某一步的错误可能需要特殊处理。

### async/await 的核心价值

`async/await` 并没有引入任何新的异步能力（它底层完全基于 Promise），但它解决了上述所有问题：

```javascript
// 同样的逻辑，用 async/await 重写：
async function loadAndRenderUser(userId) {
  try {
    const response = await fetch(`/api/users/${userId}`);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);

    const user = await response.json();
    // ✅ user 在整个函数范围内都可用！
    const displayName = user.name || user.email.split('@')[0];

    const postsResponse = await fetch(`/api/users/${user.id}/posts`);
    const posts = await postsResponse.json();

    // ✅ 同时访问 user 和 posts —— 完全自然
    return { user, displayName, posts };

  } catch (err) {
    // ✅ 所有步骤的错误统一在这里处理
    console.error('加载失败:', err.message);
    throw err; // 可选择重新抛出
  }
}
```

**对比一下两种写法的本质区别**：

| 维度 | `.then()` 链 | `async/await` |
|------|-------------|---------------|
| **控制流** | 水平展开（链式）| 垂直展开（顺序书写）|
| **变量作用域** | 每个 then 独立 | 整个函数共享 |
| **条件分支** | 需要 early return 或嵌套 | 天然的 `if/else` |
| **错误处理** | 分散在各 then 中或末尾 catch | 统一的 `try/catch` |
| **可读性** | 需要理解链式模型 | 就像读同步代码一样直观 |
| **调试体验** | 断点在异步边界处不连续 | 断点按代码行号顺序触发 |

**通俗类比**：如果说 Promise 的 `.then()` 链就像**写一首每行只有一个字的竖排诗**——你需要从上到下、再从下到上反复跳跃才能读懂完整意思；那么 `async/await` 就像**正常的横排文章**——从左到右、从上到下一口气读完。

### async/await 的定位

准确地说，`async/await` 是 **Promise API 的语法糖**（Syntactic Sugar）。这意味着：

1. **它不创造新的能力**：任何能用 async/await 写的逻辑都可以用纯 Promise 重写
2. **它改变的是表达方式**：让异步代码看起来和 behave 得像同步代码
3. **它编译后就是 Promise**：现代 JS 引擎和构建工具会将 async/await 转换为 Generator + Promise 的运行时（Babel/TSC 都是这样做的）

## 二、async 关键字 —— 函数的"异步化"

### 2.1 核心效果：函数自动返回 Promise

在一个普通函数前面加上 `async` 关键字会发生两件事：

**效果一：函数的返回值自动被包装成 Promise**

```javascript
// 普通 function → 加了 async 之后
async function f1() {
  return 42;
}
// 等价于：
function f1() {
  return Promise.resolve(42);
}

f1().then(v => console.log(v)); // 42

// 即使返回的是 undefined
async function f2() {
  // 没有 return → 相当于 return undefined
}
f2().then(v => console.log(v)); // undefined

// 即使抛出异常
async function f3() {
  throw new Error('oops');
}
f3().catch(err => console.log(err.message)); // 'oops'
// 等价于：Promise.reject(new Error('oops'))
```

**关键细节**：不管你在 `async` 函数内部写了什么——return 一个数字、return 一个对象、throw 一个错误、或者什么都不 return（隐式 return undefined）——最终调用者拿到的总是一个 Promise。这是 `async` 最基础也是最重要的保证。

**效果二：允许在函数体内使用 `await`**

```javascript
// ❌ 没有 async → 不能用 await
function bad() {
  await Promise.resolve(1); // SyntaxError: await is only valid in async functions
}

// ✅ 有 async → 可以用 await
async function good() {
  const result = await Promise.resolve(1); // 正常工作
  return result;
}
```

这两个效果是绑定在一起的：`async` 标记告诉引擎"这是一个异步函数"，所以 (1) 它的返回值需要被包装；(2) 它的内部可以使用暂停/恢复能力（即 `await`）。

### 2.2 async 的各种形式

`async` 可以用在各种函数声明形式上：

```javascript
// 形式一：函数声明
async function fetchData() { /* ... */ }

// 形式二：函数表达式
const fetchData = async function() { /* ... */ };

// 形式三：箭头函数
const fetchData = async () => { /* ... */ };

// 形式四：对象方法
const obj = {
  async getData() { /* ... */ }
};

// 形式五：类方法
class UserService {
  async fetchUser(id) { /* ... */ }
  static async findAll() { /* ... */ }  // 静态方法也可以
}

// 形式六：立即执行的异步函数（IIFE）
(async () => {
  const data = await fetch('/api/data');
  console.log(await data.json());
})();
```

**注意**：`async` 不能用在以下位置（会报语法错误）：

```javascript
// ❌ 不能用在普通对象的 getter 上
const obj = {
  get async value() { }  // SyntaxError
};

// ❌ 不能用在 generator 函数上（需要用 async function*）
async function* gen() {}  // 这是异步生成器，不是 async + generator 的简单叠加
```

### 2.3 async 函数内部的 this 绑定

`async` 不会影响函数的 `this` 绑定行为。它遵循和普通函数一样的规则：

```javascript
const obj = {
  name: 'Alice',
  async getName() {
    return this.name; // ✓ this 正确指向 obj
  },
  async getNestedName() {
    const inner = {
      name: 'Bob',
      getName: () => this.name  // 箭头函数 → this 来自外层
    };
    return inner.getName(); // 'Alice'（箭头函数的 this）
  }
};

obj.getName().then(console.log);       // 'Alice'
obj.getNestedName().then(console.log);  // 'Alice'
```

## 三、await 表达式 —— 暂停与恢复的魔法

### 3.1 基本行为：等待 Promise 结束

`await` 只能在 `async` 函数内部使用。它的语义是：**暂停当前 async 函数的执行，等待右边的表达式 settle，然后用结果恢复执行**。

```javascript
async function example() {
  console.log('① 开始');

  const promise = new Promise(resolve => {
    setTimeout(() => resolve('数据到了'), 2000);
  });

  console.log('② 发起了请求');

  const result = await promise; // ⏸️ 暂停！等 promise settle

  console.log('③ 收到:', result); // 2 秒后才执行这行

  return result.toUpperCase();
}

example().then(v => console.log('④ 最终结果:', v));

// 执行时间线：
// T=0ms:   ① 开始
//          ② 发起了请求
//          （await 暂停，函数执行被挂起）
//          （主线程空闲，可以做其他事情）
//
// T=2000ms: promise resolve
//          （example 函数恢复执行）
//          ③ 收到: 数据到了
//          函数 return → 自动包装为 Promise
//
// T=2000ms: ④ 最终结果: 数据到了
```

### 3.2 "暂停"的精确含义

**最重要的概念澄清：`await` 不是 sleep！它不会阻塞线程！**

很多初学者会把 `await` 理解为"等待期间什么都做不了"。这是完全错误的。

```javascript
async function slowOperation() {
  console.log('slowOperation: 开始');
  await new Promise(r => setTimeout(r, 3000));
  console.log('slowOperation: 结束'); // 3 秒后
}

async function fastOperation() {
  console.log('fastOperation: 开始');
  await new Promise(r => setTimeout(r, 100));
  console.log('fastOperation: 结束'); // 0.1 秒后
}

console.log('=== 启动 ===');
slowOperation();  // 注意：这里没有 await！
fastOperation(); // 两个操作并行运行！

console.log('=== 两者都已启动，主线程没有被阻塞 ===');

// 输出：
// === 启动 ===
// slowOperation: 开始
// fastOperation: 开始     ← fastOperation 不需要等 slowOperation！
// === 两者都已启动，主线程没有被阻塞 === ← 主线程继续执行
// fastOperation: 结束     ← 0.1秒后
// slowOperation: 结束     ← 3秒后
```

**这个例子揭示了 `await` 的真实含义**：它暂停的是**当前 async 函数的执行**，而不是整个 JavaScript 线程。当 `slowOperation` 在第一个 `await` 处暂停时，引擎完全可以去执行其他代码（如 `fastOperation` 的开始部分、事件监听器等）。只有当被等待的那个 Promise settle 时，`slowOperation` 才会被"唤醒"继续执行。

**类比**：想象你正在厨房做饭（async 函数），你把一锅汤放在炉子上炖（await Promise），然后你不会傻站在灶台前盯着锅看——你可以去切菜、洗碗、接电话（其他任务）。只有定时器响了（Promise settle）你才回到灶台前继续下一步操作（恢复执行）。厨房（JavaScript 线程）始终是忙碌而有条理的。

### 3.3 await 后面跟不同类型的值

`await` 后面的表达式可以是任意类型，行为各不相同：

#### 情况一：await 一个已 fulfill 的 Promise

```javascript
async function f() {
  const v = await Promise.resolve(42); // 已经 fulfilled
  console.log(v);                      // 42（微任务延迟后执行）
}
f();
```

注意：即使 Promise 已经完成了，`await` 仍然会产生一次**微任务调度**。下面的代码证明了这一点：

```javascript
async function f() {
  console.log('② inside async');
  await Promise.resolve(1); // 已完成的 Promise
  console.log('④ after await');
}

console.log('① before');
f();
console.log('③ after call');

// 输出：
// ① before
// ② inside async        ← executor 同步执行完毕
// ③ after call          ← f() 返回了（但 f 内部还没执行完）
// ④ after await         ← 微任务队列中的回调
```

#### 情况二：await 一个非 Promise 的普通值

```javascript
async function f() {
  const a = await 42;            // 数字
  const b = await 'hello';       // 字符串
  const c = await null;          // null
  const d = await undefined;     // undefined
  const e = await { x: 1 };      // 对象（无 then 方法）

  console.log(a, b, c, d, e);
}
f(); // 42 'hello' null undefined {x: 1}
```

**普通值的行为**：`await 42` 实际上等价于 `await Promise.resolve(42)`。引擎会在内部先把普通值包装成一个已 fulfill 的 Promise，然后再等待它。所以即使是普通值，也会产生微任务延迟。

**但这在实际中几乎不影响你的代码逻辑**——唯一需要注意的是不要依赖 `await` 来做同步的"下一步"操作。

#### 情况三：await 一个 Thenable 对象

```javascript
class MyThenable {
  constructor(value) {
    this.value = value;
  }
  then(resolve) {
    // Thenable 的 then 会被 await 调用
    setTimeout(() => resolve(this.value * 2), 1000);
  }
}

async function useThenable() {
  console.log('等待 Thenable...');
  const result = await new MyThenable(21);
  console.log('结果:', result); // 42（1 秒后）
}
useThenable();
```

这与 `Promise.resolve(thenable)` 的拆包机制是一致的——`await` 底层就是调用 `PromiseResolve(x)` 然后注册回调。

#### 情况四：await 一个 reject 的 Promise —— 抛出异常！

这是最需要注意的情况：

```javascript
async function f() {
  try {
    const v = await Promise.reject(new Error('失败'));
    console.log('永远不会到这里', v);
  } catch (e) {
    console.log('捕获到:', e.message); // '捕获到: 失败'
  }
}
f();

// await Promise.reject(...) 等价于 throw ...
// 所以必须用 try/catch 来捕获
```

### 3.4 多个 await 的串行执行

当一个 async 函数中有多个 `await` 时，它们是**严格串行的**——第一个 await 恢复后才开始第二个：

```javascript
async function sequential() {
  console.log('开始');

  const start = Date.now();

  const r1 = await new Promise(resolve => setTimeout(() => resolve('A'), 1000));
  console.log(`拿到 A，耗时 ${Date.now() - start}ms`);

  const r2 = await new Promise(resolve => setTimeout(() => resolve('B'), 1000));
  console.log(`拿到 B，耗时 ${Date.now() - start}ms`);

  const r3 = await new Promise(resolve => setTimeout(() => resolve('C'), 1000));
  console.log(`拿到 C，耗时 ${Date.now() - start}ms`);

  return [r1, r2, r3];
}

sequential().then(arr => console.log('全部完成:', arr));

// 时间线：
// 开始
// 拿到 A，耗时 ~1000ms
// 拿到 B，耗时 ~2000ms
// 拿到 C，耗时 ~3000ms    ← 总时间 = 各 await 之和！
// 全部完成: ['A','B','C']
```

**三个 await 串行，总耗时 = 1s + 1s + 1s = 3s**。这在需要依赖前一步结果的场景下是合理的（比如先获取 userId，再用 userId 获取用户详情，再用详情获取文章列表）。但如果这些请求之间没有依赖关系，串行 await 就是**严重的性能浪费**——后面会讲如何优化。

## 四、底层原理 —— async/await 到底是什么？

### 4.1 编译转换：async/await ≈ Generator + Promise 运行时

这是理解 async/await 最关键的视角。现代 JavaScript 工具链（Babel、TypeScript）将 async/await 编译为 **Generator 函数 + 一个自动驱动 Generator 的运行时函数**。

来看一段 async/await 代码及其等价的 Generator 转换：

```javascript
// ====== 原始 async/await 代码 ======
async function getUserData(userId) {
  const resp = await fetch(`/api/users/${userId}`);
  const user = await resp.json();
  return user.name;
}

// ====== 等价的 Generator 版本 ======
function* genGetUserData(userId) {
  const resp = yield fetch(`/api/users/${userId}`);   // yield 代替 await
  const user = yield resp.json();                       // yield 代替 await
  return user.name;                                    // return 保持不变
}
```

两者的结构几乎一模一样——唯一的区别是 `await` 变成了 `yield`。那谁来驱动这个 Generator 呢？需要一个**运行时函数**（通常叫 `asyncToGenerator` 或类似的名称）：

```javascript
/**
 * 简化版的 async/await 运行时
 * 将 Generator 函数变为自动执行的 async 函数
 */
function asyncToGenerator(generatorFn) {
  return function(...args) {
    const gen = generatorFn.apply(this, args);

    return new Promise((resolve, reject) => {
      function step(nextFn) {
        let result;
        try {
          result = nextFn(); // 调用 gen.next() 或 gen.throw()
        } catch (e) {
          return reject(e);  // 同步异常 → 直接 reject
        }

        if (result.done) {
          return resolve(result.value); // Generator 完成 → resolve
        }

        // result.value 可能是 Promise 也可能是普通值
        // 统一包装为 Promise 以便 .then()
        Promise.resolve(result.value).then(
          val => step(() => gen.next(val)),   // yield 出去的值回来 → 作为 next 参数传入
          err => step(() => gen.throw(err))   // 错误 → 注入到 generator 内部
        );
      }

      step(() => gen.next()); // 启动 Generator
    });
  };
}

// 使用转换器
const getUserData = asyncToGenerator(genGetUserData);

// 现在 getUserData 的表现和 async 版本完全一致！
getUserData(123).then(name => console.log(name));
```

**逐步追踪这个运行时的工作流程**：

```
调用 getUserData(123)
│
├─→ 创建 gen = genGetUserData(123)
├─→ 返回 new Promise(...)
├─→ 调用 step(() => gen.next())
│   │
│   ├─→ gen.next() 执行到第一个 yield
│   │   └─→ result = { value: fetch('/api/users/123'), done: false }
│   │
│   ├─→ Promise.resolve(fetchPromise).then(...)
│   │   │
│   │   ├─→ fetch 请求完成后 resolve
│   │   └─→ step(() => gen.next(response))
│   │       │
│   │       ├─→ gen.next(response) 恢复执行
│   │       │   → response 赋给 resp
│   │       │   → 执行到第二个 yield (resp.json())
│   │       │   └─→ result = { value: jsonPromise, done: false }
│   │       │
│   │       ├─→ Promise.resolve(jsonPromise).then(...)
│   │       │   │
│   │       │   ├─→ json 解析完成后 resolve
│   │       │   └─→ step(() => gen.next(userData))
│   │       │       │
│   │       │       ├─→ gen.next(userData)
│   │       │       │   → userData 赋给 user
│   │       │       │   → return user.name
│   │       │       │   └─→ result = { value: 'Alice', done: true }
│   │       │       │
│   │       │       └─→ done === true → resolve('Alice')
│   │       │           └─→ 外部 .then(name => console.log(name)) 执行
```

**这就是 async/await 的全部秘密**：它就是一个自动化的 Generator 驱动器。每次 `await`（编译后变成 `yield`）都会暂停 Generator，等 Promise settle 后自动调用 `gen.next(result)` 把结果送回去并恢复执行。如果 Promise reject 了，就调用 `gen.throw(error)` 把错误注入进去——这就解释了为什么 `await` 被 reject 时可以 `try/catch` 捕获（`gen.throw` 会触发 Generator 内部的 `catch` 块）。

### 4.2 为什么说它是"语法糖"？

有了上面的转换图，你就能理解为什么说 async/await 是语法糖了：

| async/await 写法 | 编译后的等价写法 |
|-----------------|-----------------|
| `async function f(){}` | `function f(){ return asyncToGenerator(function*(){})}`|
| `await promise` | `yield promise` （由运行时自动驱动 next）|
| `try { await p } catch(e){}` | Generator 内部 `try { yield p } catch(e){}` + `gen.throw(e)` |
| `return value` | `return value`（Generator 的 return）|

**但请注意**："语法糖"并不意味着它不重要。好的语法糖能极大地改善代码的可维护性和可读性——正如 `for...of` 循环是迭代器的语法糖、类是原型继承的语法糖、模板字符串是字符串拼接的语法糖一样。async/await 让异步编程的门槛大大降低了。

## 五、错误处理 —— try/catch vs .catch()

### 5.1 await 的错误传播机制

当 `await` 右边的 Promise 被 reject 时，`await` 表达式的行为等同于 `throw`：

```javascript
// 这两种写法完全等价：
async function versionA() {
  await Promise.reject(new Error('boom'));
}

async function versionB() {
  throw new Error('boom');
}
```

这意味着你可以用最熟悉的 `try/catch` 来捕获 `await` 的错误：

```javascript
async function safeFetch(url) {
  try {
    const response = await fetch(url);          // 可能 reject（网络错误）
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`); // 手动 throw
    }
    const data = await response.json();         // 可能 reject（JSON 解析错误）
    return data;

  } catch (error) {
    // ✅ 一个 catch 能捕获上面所有可能的错误！
    console.error(`${url} 请求失败:`, error.message);

    // 你可以选择：
    // 1. 返回默认值（降级处理）
    return { error: true, message: error.message };

    // 2. 重新抛出（让调用者处理）
    // throw error;

    // 3. 返回缓存的数据
    // return getCachedData(url);
  }
}
```

### 5.2 try/catch vs 外部 .catch()

除了在 async 函数内部使用 `try/catch`，你也可以在外部使用 `.catch()` —— 因为 async 函数本身返回的就是一个 Promise：

```javascript
// 方式一：内部 try/catch
async function approachA() {
  try {
    const data = await riskyOperation();
    return data;
  } catch (err) {
    console.log('内部捕获:', err.message);
    return null;
  }
}

// 方式二：外部 .catch()
async function approachB() {
  const data = await riskyOperation(); // 如果出错，整个函数 reject
  return data;
}
approachB().catch(err => console.log('外部捕获:', err.message));
```

**如何选择？** 一般来说：

| 场景 | 推荐 | 理由 |
|------|------|------|
| 函数内部需要**根据错误类型做不同的降级处理** | `try/catch` | 可以在 catch 里做精细判断和 fallback |
| 函数只是**传递错误给调用者** | 外部 `.catch()` | 更简洁，不增加缩进层级 |
| 需要**统一处理多个 await 的错误** | 外层 `try/catch` 包裹多个 await | 一个 catch 覆盖所有步骤 |
| **顶层代码**（不在任何 async 函数内）| `.catch()` 或 IIFE 包裹 | 顶层不能用 await |

### 5.3 精细的错误处理模式

实际项目中，你可能需要对不同来源的错误做不同处理：

```javascript
async function robustFetchWithRetry(url, maxRetries = 3) {
  let lastError;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url);

      if (!response.ok) {
        // HTTP 错误 → 通常不需要重试（4xx 是客户端错误）
        if (response.status >= 400 && response.status < 500) {
          throw new Error(`客户端错误: HTTP ${response.status}`);
        }
        // 5xx 服务端错误 → 可以重试
        throw new Error(`服务端错误: HTTP ${response.status} (第${attempt}次尝试)`);
      }

      const data = await response.json();
      return data; // 成功 → 返回

    } catch (error) {
      lastError = error;

      // 网络错误 → 可重试
      const isNetworkError = error.message.includes('Failed to fetch') ||
                            error.message.includes('NetworkError');

      // 4xx 客户端错误 → 不要重试（重试也没用）
      const isClientError = error.message.includes('客户端错误');

      if (isClientError) {
        break; // 直接跳出循环，不需要重试
      }

      if (attempt < maxRetries && isNetworkError) {
        console.warn(`第 ${attempt} 次失败，准备重试...`);
        await new Promise(r => setTimeout(r, 1000 * attempt)); // 指数退避等待
      }
    }
  }

  // 所有重试都失败了
  throw lastError;
}
```

### 5.4 不用 try/catch 的危险

如果你在 async 函数中使用了 `await` 但没有 `try/catch`，也没有外部 `.catch()`，错误就会变成**未处理的 rejection**：

```javascript
async function dangerous() {
  const data = await fetch('/api/that-does-not-exist');
  return data.json();
}

dangerous(); // ⚠️ 没有 .catch()，也没有 try/catch
// 控制台会出现黄色警告：Uncaught (in promise) TypeError: Failed to fetch
```

**防御性编程建议**：对于可能对外暴露的 async 函数，至少在最外层加一个兜底：

```javascript
// 开发环境下的全局兜底
if (typeof window !== 'undefined') {
  window.addEventListener('unhandledrejection', event => {
    console.warn('[未处理的 Promise 拒绝]', event.reason);
    // event.preventDefault(); // 可选：阻止默认的控制台警告
  });
}
```

## 六、并行执行 —— 避免 await 陷阱

### 6.1 经典性能陷阱：不必要的串行

这是 async/await 新手最容易犯的性能错误：

```javascript
// ❌ 串行 await —— 慢！
async function getUsersSlowly(ids) {
  const results = [];
  for (const id of ids) {
    const user = await fetch(`/api/users/${id}`).then(r => r.json());
    results.push(user); // 等 1 个完成才发起下一个
  }
  return results;
}

// 假设有 10 个 ID，每个请求 200ms
// 总时间 = 10 × 200ms = 2000ms 😱
```

**为什么慢？** 因为 `for` 循环里的 `await` 会让每次迭代都等待上一个完成才开始下一个。这就像你去餐厅点菜，每次只点一道菜、吃完再点下一道——明明可以一次性把菜单上的菜都点了。

### 6.2 解决方案：Promise.all + 解构

```javascript
// ✅ 并行 await —— 快！
async function getUsersFast(ids) {
  // 先把所有请求都发出去（并行）
  const promises = ids.map(id =>
    fetch(`/api/users/${id}`).then(r => r.json())
  );

  // 然后一起等待它们全部完成
  const results = await Promise.all(promises);

  return results;
}

// 10 个请求同时发出，总时间 ≈ 200ms（取最长的那一个）🚀
```

**更优雅的写法——直接在 await 里 map**：

```javascript
async function getUsersElegant(ids) {
  // Promise.all + await + map + 解构 一气呵成
  const users = await Promise.all(
    ids.map(async (id) => {
      const resp = await fetch(`/api/users/${id}`);
      return resp.json();
    })
  );

  return users;
}
```

### 6.3 进阶：allSettled 处理部分失败

```javascript
async function fetchMultipleUrls(urls) {
  // 使用 allSettled 允许部分失败
  const results = await Promise.allSettled(
    urls.map(url =>
      fetch(url).then(res => res.json())
    )
  );

  // 分类汇总
  const successful = results
    .filter(r => r.status === 'fulfilled')
    .map(r => r.value);

  const failed = results
    .filter(r => r.status === 'rejected')
    .map(r => ({ url: urls[results.indexOf(r)], error: r.reason }));

  return { successful, failed };
}
```

### 6.4 决策指南：何时串行、何时并行

```
多个异步操作？
│
├─→ 后面的操作依赖前面的结果？（如：先拿 userId 再获取详情）
│   └─→ ✅ 必须串行 await（有依赖关系）
│
└─→ 操作之间互相独立？
    ├─→ 需要全部成功？
    │   └─→ ✅ Promise.all([...]).then(await ...) 并行
    │
    └─→ 允许部分失败？
        └─→ ✅ Promise.allSettled([...]).then(await ...) 并行容错
```

## 七、顶层 await（Top-Level Await）

### 7.1 背景：模块系统的痛点

在 ES2022 之前，你不能在模块的顶层使用 `await`——只能在 async 函数内部用。这意味着如果你想在模块加载时执行一些异步初始化操作（比如读取配置文件、建立数据库连接），就必须用一个 IIFE（立即执行函数表达式）来包裹：

```javascript
// ES2022 之前的方式（IIFE 包裹）
let config;

(async () => {
  const resp = await fetch('/config.json');
  config = await resp.json();
  console.log('配置加载完成:', config);
})();

// 导出的变量可能在配置还没加载完就被其他模块使用了
export { config }; // ⚠️ 其他模块 import 时 config 还是 undefined
```

### 7.2 顶层 await 的用法

ES2022 引入了**顶层 await（Top-Level Await）**，允许在 ECMAScript 模块的顶级作用域中直接使用 `await`：

```javascript
// config.mjs（必须是 ES Module —— type="module" 或者 .mjs 扩展名）
const resp = await fetch('/config.json');
const config = await resp.json();

// ✅ config 在这里一定是已经加载好的了
export default config;

// 其他模块 import 时一定能拿到完整的数据
// import config from './config.mjs'; // config 一定存在
```

**顶层 await 的行为特点**：

1. **它会阻塞当前模块的求值**——后续的 import 语句会等到 await 完成
2. **它会阻塞导入该模块的其他模块**——形成依赖链阻塞
3. **它不会阻塞整个应用**——不相关的模块不受影响（浏览器可以并行加载其他无依赖的模块）

```javascript
// module-a.mjs
console.log('module-a: 开始');
export const a = await new Promise(r => setTimeout(() => r('A 的值'), 1000));
console.log('module-a: 结束');

// module-b.mjs（不依赖 module-a）
console.log('module-b: 开始');
export const b = 'B 的值';
console.log('module-b: 结束');

// main.mjs
import { a } from './module-a.mjs';
import { b } from './module-b.mjs';
console.log('main:', a, b);

// 执行顺序：
// module-b: 开始    ← 无 await 阻塞，立即执行完
// module-b: 结束
// module-a: 开始    ← 开始执行但有 await
// （1 秒等待）
// module-a: 结束    ← await 完成
// main: A 的值 B 的值
```

注意 `module-b` 完全不受 `module-a` 的顶层 await 影响——因为它不依赖 `module-a`。这就是顶层 await 的**局部阻塞**特性。

### 7.3 使用注意事项

1. **必须是在 ESM 模块中**——CommonJS（Node.js 的 require）不支持
2. **避免死锁**：如果两个模块互相 import 且都有顶层 await，可能导致循环依赖死锁
3. **谨慎用于关键路径**：顶层 await 会推迟模块的"准备好"的时间点，可能影响应用的首次渲染速度

```javascript
// ⚠️ 潜在的死锁场景
// db.mjs
import { initApp } from './app.mjs';  // 依赖 app
export const db = await connectDB();   // 顶层 await

// app.mjs
import { db } from './db.mjs';        // 依赖 db
export const app = await initApp(db);  // 顶层 await

// 死锁：db 等待自己被 app 初始化，app 等待 db 连接成功
// 两个模块互相等待对方先准备好 → 永远不会发生
```

## 八、async/await 与微任务队列的关系

### 8.1 await 产生微任务的精确时机

`await` 不仅会暂停执行，还会产生至少一个微任务。理解这一点对面试和调试非常重要：

```javascript
async function test() {
  console.log('② async 函数体开始');
  await Promise.resolve();  // await 一个已完成的 Promise
  console.log('④ await 之后');
}

console.log('① script start');
test();
console.log('③ script end');

// 输出：
// ① script start
// ② async 函数体开始
// ③ script end
// ④ await 之后
```

**为什么 ④ 在 ③ 之后？** 因为 `await Promise.resolve()` 产生了一个微任务——虽然 Promise 已经完成了，但 `await` 后面的代码还是被放入微任务队列中等待当前宏任务结束后执行。这保证了 `await` 始终是异步的。

### 8.2 经典面试题解析

这是一道非常经典的面试题，考验你对 async/await 和微任务的理解深度：

```javascript
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}

async function async2() {
  console.log('async2');
}

console.log('script start');

setTimeout(() => {
  console.log('timeout');
}, 0);

async1();

new Promise(resolve => {
  console.log('promise1');
  resolve();
}).then(() => {
  console.log('promise2');
});

console.log('script end');
```

**请先思考输出顺序，再看下面的解析。**

.

.

.

**逐帧解析**：

```
T=0: 执行同步代码
│
├─→ console.log('script start')                    输出: script start
│
├─→ 调用 async1()
│   │
│   ├─→ console.log('async1 start')                 输出: async1 start
│   │
│   ├─→ await async2()
│   │   │
│   │   ├─→ 调用 async2()
│   │   │   ├─→ console.log('async2')               输出: async2
│   │   │   └─→ async2() 返回 Promise{<fulfilled>:undefined}
│   │   │
│   │   ├─→ await 收到一个 Promise → 暂停 async1
│   │   │   将「console.log('async1 end')」加入微任务队列
│   │   │   当前微任务队列: [async1-end-task]
│   │   │
│   │   └─→ async1() 返回 Promise（pending 状态）
│   │
│   ├─→ new Promise(executor)
│   │   ├─→ executor 同步执行
│   │   ├─→ console.log('promise1')                输出: promise1
│   │   ├─→ resolve() 调用
│   │   └─→ 将 .then 回调加入微任务队列
│   │       当前微任务队列: [async1-end-task, promise2-task]
│   │
│   └─→ console.log('script end')                   输出: script end
│
├─→ setTimeout 注册（宏任务队列）
│
T=0结束: 同步代码执行完毕

T≈0: 清空微任务队列
│
├─→ 取出 async1-end-task → 执行
│   └─→ console.log('async1 end')                  输出: async1 end
│
├─→ 取出 promise2-task → 执行
│   └─→ console.log('promise2')                     输出: promise2
│
└─→ 微任务队列清空

T≈0+: 渲染（如果有变化的话）

T≈0++: 取出一个宏任务
│
└─→ setTimeout 回调执行
    └─→ console.log('timeout')                     输出: timeout
```

**最终输出**：
```
script start
async1 start
async2
promise1
script end
async1 end      ← 微任务
promise2         ← 微任务
timeout          ← 宏任务
```

**最容易错的地方**：很多人以为 `await async2()` 会等 `async2` 完全执行完（包括它的所有微任务）后才继续。但实际上 `await` 只是等 `async2()` 返回的 Promise settle——而 `async2` 内部没有 `await`，它的 Promise 在 executor 结束时就立即 fulfill 了。`async1` 中 `await` 之后的代码被作为**独立的微任务**排队，排在 `new Promise().then()` 的微任务**之前**（因为在代码中先遇到的）。

## 九、实战案例

### 9.1 带超时和重试的健壮请求封装

```javascript
/**
 * 生产级的 async fetch 封装
 * @param {string} url
 * @param {Object} options
 * @param {number} options.timeout 超时毫秒数
 * @param {number} options.retries 最大重试次数
 * @returns {Promise<any>}
 */
async function robustFetch(url, { timeout = 5000, retries = 3 } = {}) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);

  for (let i = 1; i <= retries; i++) {
    try {
      const response = await fetch(url, { signal: controller.signal });

      if (!response.ok) {
        throw new FetchError(`HTTP ${response.status}`, response.status);
      }

      clearTimeout(timer);
      return await response.json();

    } catch (error) {
      clearTimeout(timer);

      // 取消导致的错误不需要重试
      if (error.name === 'AbortError' && i === 1) {
        throw new TimeoutError(`请求超时 (${timeout}ms): ${url}`);
      }

      // 最后一次不再重试
      if (i === retries) {
        throw error;
      }

      // 指数退避
      const delay = Math.min(1000 * Math.pow(2, i - 1), 10000);
      console.warn(`[robustFetch] 第 ${i}/${retries} 次 ${url} 失败: ${error.message}，${delay}ms 后重试`);
      await sleep(delay);
    }
  }
}

class FetchError extends Error {
  constructor(message, status) {
    super(message);
    this.status = status;
  }
}
class TimeoutError extends Error {}

function sleep(ms) {
  return new Promise(r => setTimeout(r, ms));
}
```

### 9.2 异步资源清理模式

```javascript
/**
 * 使用 async/await 的资源管理模式
 * 类似于 Python 的 async with 或 C# 的 using
 */
async function withResource(resourceFactory, usageFn) {
  const resource = await resourceFactory();
  try {
    return await usageFn(resource);
  } finally {
    await resource.dispose?.(); // 不管成功失败都要释放
  }
}

// 使用示例
async function processFile(filePath) {
  return withResource(
    () => openFile(filePath),           // 资源创建
    async (file) => {                   // 资源使用
      const content = await file.read();
      const result = transform(content);
      return result;
    }
  ); // finally 自动关闭 file
}
```

### 9.3 并发控制池（async/await 版本）

```javascript
/**
 * 带并发限制的异步任务池（async/await 实现）
 *
 * @param {Function[]} tasks 任务数组（返回 Promise 的函数）
 * @param {number} concurrency 最大并发数
 */
async function asyncPool(tasks, concurrency = 5) {
  const results = [];
  const executing = new Set();

  for (const task of tasks) {
    const promise = task().then(result => {
      executing.delete(promise);
      return result;
    });

    executing.add(promise);
    results.push(promise);

    if (executing.size >= concurrency) {
      await Promise.race(executing); // 等待最快完成的
    }
  }

  return Promise.all(results);
}

// 使用
const tasks = Array.from({ length: 20 }, (_, i) => ()
  fetch(`/api/item/${i}`).then(r => r.json())
);

const results = await asyncPool(tasks, 5); // 最多 5 个并发
```

## 十、常见陷阱速查

| # | 陷阱 | 现象 | 解决方案 |
|---|------|------|----------|
| 1 | **for 循环中串行 await** | N 个独立操作耗时 N 倍 | 用 `Promise.all(ids.map(id => fetch(id)))` 并行 |
| 2 | **forEach 中 await 无效** | forEach 的回调不是 async 函数，await 不生效 | 改用 `for...of` 循环或 `Promise.all` + map |
| 3 | **忘记 try/catch 导致 unhandledrejection** | 控制台出现黄色警告 | 始终用 try/catch 包裹 await，或外层 .catch() |
| 4 | **在构造函数/getter 中使用 async** | `SyntaxError` 或返回值不符合预期 | 构造函数不能用 async；getter 不能用 async；改用工厂函数 |
| 5 | **混用 await 和回调风格** | 回调中的错误无法被 try/catch 捕获 | 统一使用 async/await 或 Promise |
| 6 | **async 函数中多余的 await** | `return await x` 多余的一层 Promise 包装 | 直接 `return x`（除非在 try/finally 中）|
| 7 | **顶层 await 在非 ESM 中使用** | `SyntaxError` | 确保 `<script type="module">` 或 .mjs 扩展名 |

### 陷阱 2 详解：forEach 中的 await

这是一个极其常见的坑：

```javascript
// 错误：forEach 的回调中的 await 不起作用
['a', 'b', 'c'].forEach(async (item) => {
  await new Promise(r => setTimeout(r, 1000));
  console.log(item); // 几乎同时打印 a,b,c（不是间隔 1 秒）
});

// 正确：使用 for...of 循环
for (const item of ['a', 'b', 'c']) {
  await new Promise(r => setTimeout(r, 1000));
  console.log(item); // 依次打印 a（1秒后）b（2秒后）c（3秒后）
}

// 正确：使用 Promise.all 并行
await Promise.all(
  ['a', 'b', 'c'].map(async (item) => {
    await new Promise(r => setTimeout(r, 1000));
    console.log(item); // 约 1 秒后几乎同时打印
  })
);
```

**原因**：`Array.prototype.forEach` 的 callback 返回值（包括 Promise）会被忽略。它不会等待 callback 中的 async 函数完成就继续下一次迭代。`forEach` 本身不是 async-aware 的。

### 陷阱 6 详解：多余的 `return await`

```javascript
// 多余的 await
async function redundant() {
  try {
    return await fetchData(); // 多了一层 unwrap + re-wrap
  } finally {
    cleanup();
  }
}

// 直接 return（大多数情况）
async function clean() {
  try {
    return fetchData();
  } finally {
    cleanup();
  }
}
```

`return await x` 和 `return x` 在大多数情况下行为相同，但 `return await` 多了一次微任务开销和一个额外的 Promise 层。**唯一的例外是在 `try/finally` 中**——如果你需要在 `finally` 中做清理且希望 finally 在 `x` settle 之后再执行，就需要 `return await`。

## 十一、最佳实践总结

### 11.1 代码风格建议

```javascript
// 推荐的风格
async function loadData(userId) {
  // 1. 单个 try/catch 包裹所有 await
  try {
    const [user, posts, comments] = await Promise.all([
      fetchUser(userId),
      fetchPosts(userId),
      fetchComments(userId)
    ]);

    // 2. 用 const 声明，充分利用块级作用域
    const enrichedUser = enrichUser(user, posts.length);

    // 3. 返回明确的结构化数据
    return { user: enrichedUser, posts, comments };

  } catch (error) {
    // 4. catch 中记录日志
    logger.error('loadData failed', { userId, error: error.message });
    // 5. 根据错误类型决定是降级还是重新抛出
    if (isRecoverable(error)) {
      return getCachedData(userId);
    }
    throw error;
  }
}
```

### 11.2 设计原则

| 原则 | 说明 |
|------|------|
| **优先 async/await** | 新代码一律使用 async/await，只在需要 `.all()` `.race()` `.allSettled()` 时才显式用 Promise API |
| **并行优于串行** | 独立操作用 `Promise.all()`，只在有依赖关系时才串行 await |
| **统一错误入口** | 每个 async 函数要么内部 `try/catch`，要么确保调用者有 `.catch()` |
| **避免顶层副作用** | async 函数应该是纯操作+返回值，不要在里面直接操作 DOM（除非它本身就是 UI 函数）|
| **命名约定** | async 函数名不加前缀也能接受，但 `fetch` `load` `get` `query` 等动词天然暗示异步 |
| **JSDoc 注释** | 标注 `@returns {Promise<T>}` 让调用者知道返回类型 |

## 十二、知识图谱

```
async/await 体系
│
├── async 关键字
│   ├── 效果一：返回值自动包装为 Promise（resolve/reject/undefined）
│   ├── 效果二：解锁 await 使用权限
│   ├── 六种声明形式（声明/表达式/箭头/对象方法/类方法/IIFE）
│   └── 不影响 this 绑定
│
├── await 表达式
│   ├── 核心：暂停 async 函数，等 Promise settle 后恢复
│   ├── 不是 sleep！不阻塞线程！（交还执行权）
│   ├── 四种输入类型：
│   │   ├── fulfill 的 Promise -> 返回结果
│   │   ├── reject 的 Promise -> throw 异常
│   │   ├── 普通值 -> 自动包装为 Promise（仍有微任务延迟）
│   │   └── Thenable -> 调用 .then() 拆包
│   ├── 多个 await 默认串行（总时间 = 各项之和）
│   └── 产生微任务（即使在已 settled 的 Promise 上）
│
├── 底层原理
│   ├── 编译目标：Generator + 自动驱动运行时
│   ├── await -> yield（由运行时的 gen.next() 驱动）
│   ├── try/catch -> Generator 内部 try/catch + gen.throw()
│   └── "语法糖" != 不重要（大幅降低认知负担）
│
├── 错误处理
│   ├── await reject -> 等价 throw -> try/catch 捕获
│   ├── 内部 try/catch（精细化处理）vs 外部 .catch（简洁传递）
│   ├── 多层 catch（网络错误重试 / 客户端错误不重试）
│   └── unhandledrejection 危险（必须有 catch 或 try）
│
├── 性能优化
│   ├── 陷阱：for 循环串行 await -> O(N) 延迟
│   ├── 解决：Promise.all(map(...)).then(await) 并行
│   ├── forEach 中 await 无效 -> 改 for...of
│   └── return await 多余（除 try/finally 场景外）
│
├── 顶层 await [ES2022]
│   ├── 仅限 ESM 模块（type="module" / .mjs）
│   ├── 局部阻塞（仅阻塞依赖该模块的其他模块）
│   ├── 循环依赖死锁风险
│   └── 应用场景：模块级配置加载 / DB 连接初始化
│
├── 微任务行为
│   ├── await 始终产生微任务（即使 Promise 已 settle）
│   ├── 经典面试题：async1/async2/promise/setTimeout 执行顺序
│   └-> 规律：同步代码 -> 微任务（FIFO + 产消）-> 渲染 -> 宏任务
│
└── 实战模式
    ├── robustFetch（超时 + AbortController + 指数退避重试）
    ├── withResource（async 资源管理器模式）
    ├── asyncPool（并发控制池）
    └── 错误分类处理（网络/HTTP/业务错误的差异化策略）
```

## 十三、总结

| 维度 | 核心要点 |
|------|---------|
| **本质** | async/await = **Generator + 自动驱动运行时**的语法糖，底层 100% 基于 Promise |
| **async** | 两件事：返回值自动 Promise 化 + 允许使用 await |
| **await** | 暂停当前函数（**不阻塞线程**），等 Promise settle 后恢复；reject 时等同 throw |
| **错误处理** | `try/catch` 回归——可以用熟悉的同步方式处理异步错误 |
| **最大陷阱** | `for` 循环中 `await` 导致不必要的**串行化**，独立操作应使用 `Promise.all()` 并行 |
| **微任务** | `await` 始终产生微任务（即使 Promise 已完成）；执行顺序：同步 > 微任务 > 渲染 > 宏任务 |
| **顶层 await** | ES2022 新特性，仅在 ESM 模块中有效，**局部阻塞**依赖者模块 |
| **性能** | 与原生 Promise 性能等价（V8 有专门的优化通道）；主要优势在于**开发效率**而非运行效率 |
| **适用场景** | 任何涉及多步异步操作的逻辑——API 调用链、数据库操作、文件读写、动画序列 |
