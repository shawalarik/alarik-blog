# 事件循环（浏览器）—— 宏任务、微任务、渲染管线与调用栈协作机制

> **核心内容**：事件循环是 JavaScript 异步世界的"总指挥官"。本文从浏览器架构的宏观视角出发，逐步拆解调用栈（Call Stack）、宏任务队列（Macrotask Queue）、微任务队列（Microtask Queue）三者的协作关系，深入事件循环的完整算法流程、渲染时机与 rAF 的精确行为、经典面试题的逐帧追踪，最终构建出完整的事件循环心智模型。

## 一、为什么需要理解事件循环？

### 从一个"简单"问题开始

你写过无数次这样的代码：

```javascript
console.log('开始');

setTimeout(() => {
  console.log('定时器到了');
}, 0);

Promise.resolve().then(() => {
  console.log('微任务');
});

console.log('结束');
```

在看到答案之前，请先思考一下输出顺序。

.

.

.

答案是：`开始` → `结束` → `微任务` → `定时器到了`

如果你答对了，恭喜。但如果有人问你**为什么是这个顺序**？`setTimeout(fn, 0)` 不是"立即执行"吗？为什么它排在 Promise `.then()` 后面？这两个"异步操作"之间到底有什么区别？浏览器内部是怎么决定"谁先谁后"的？

要回答这些问题，就必须理解 **事件循环（Event Loop）**——JavaScript 运行时的核心调度机制。它是理解所有异步行为的根基：回调函数、Promise、async/await、requestAnimationFrame、DOM 事件……一切都建立在事件循环之上。

### 事件循环解决的核心矛盾

JavaScript 是**单线程**的——同一时间只能做一件事。但浏览器需要同时处理成千上万种事情：

- 执行你的 JavaScript 代码
- 响应鼠标点击、键盘输入、滚动
- 渲染页面（HTML → 样式计算 → 布局 → 绘制）
- 网络请求完成后的回调
- 定时器到期触发
- `<img>` / `<script>` 资源加载完成

**单线程 vs 多任务** —— 这就是事件循环要解决的根本矛盾。

**类比**：想象一家只有**一个厨师**（JavaScript 主线程）的小餐厅，但同时有：
- 点菜订单不断进来（用户交互事件）
- 外卖订单需要处理（网络回调）
- 菜品需要摆盘上桌（DOM 渲染）
- 定时提醒要响（setTimeout）

如果厨师一次只处理一件事且必须做完一件才开始下一件，那点菜的客人会等很久、外卖会超时、菜品会凉掉。事件循环就是这位厨师的**工作调度系统**——它让厨师能够合理地安排各种任务的执行优先级和切换时机，让餐厅看起来像是有很多厨师在工作一样流畅。

### 学习路线

```
单线程模型 → 理解为什么需要调度系统
    ↓
调用栈 → 同步代码如何被组织
    ↓
宏任务队列 → "大块工作"的排队机制
    ↓
微任务队列 → "精细工作"的高优先级插队
    ↓
事件循环算法 → 三者如何协作
    ↓
渲染时机 → DOM 更新何时变为像素
    ↓
完整案例追踪 → 把理论应用到真实代码分析
```

## 二、调用栈（Call Stack）—— 同步代码的执行轨迹

### 2.1 什么是调用栈？

当你写下一行行 JavaScript 代码时，引擎并不是"随便乱跑"的。它严格按照**调用栈（Call Stack）**的后进先出（LIFO）规则来管理函数的执行上下文：

```javascript
function third() {
  console.log('③ 第三层');   // 当前栈: [main → first → second → third]
}

function second() {
  console.log('② 第二层');   // 当前栈: [main → first → second]
  third();
  // third 返回后，third 出栈
  // 回到这里继续
  console.log('② second 恢复');
}

function first() {
  console.log('① 第一层');    // 当前栈: [main → first]
  second();
  // second 返回后，second 出栈
}

first();                       // 初始入栈: [main]
// first 返回后，first 出栈，main 也结束
// 栈空了

// 输出：
// ① 第一层
// ② 第二层
// ③ 第三层
// ② second 恢复
```

**调用栈的可视化过程**：

```
执行 first()
│
├─→ main 入栈          栈: [main]
│
├─→ first 入栈         栈: [main, first]
│   │ console.log('①')
│   │
│   ├─→ second 入栈     栈: [main, first, second]
│   │   │ console.log('②')
│   │   │
│   │   ├─→ third 入栈  栈: [main, first, second, third]
│   │   │   │ console.log('③')
│   │   │   │ third return → third 出栈
│   │   │   │           栈: [main, first, second]
│   │   │   │ console.log('② second 恢复')
│   │   │   │ second return → second 出栈
│   │   │   │           栈: [main, first]
│   │   │   │ first return → first 出栈
│   │   │   │           栈: [main]
│   │   │   │ main 结束 → main 出栈
│   │   │   │           栈: [] （空！）
```

### 2.2 调用栈的关键特征

| 特征 | 说明 |
|------|------|
| **LIFO（后进先出）** | 最后调用的函数最先返回 |
| **同步阻塞** | 一个函数不返回，下面的代码不会执行 |
| **大小有限** | 栈深度过大（如无限递归）会导致 **Maximum call stack size exceeded** 错误 |
| **每个栈帧包含** | 局部变量、参数、返回地址、this 引用 |

### 2.3 调用栈与"阻塞"

当调用栈中有一个函数长时间不返回时，整个 JavaScript 线程就被**阻塞**了：

```javascript
// 这个函数会在调用栈上待很久
function heavyComputation() {
  let sum = 0;
  for (let i = 0; i < 10000000000; i++) {  // 100亿次循环
    sum += i;
  }
  return sum;
}

console.log('开始计算');
heavyComputation();  // 调用栈: [main → heavyComputation] — 卡在这里！
console.log('算完了');     // 这行要等 heavyComputation 完全返回才执行
// 在等待期间：
// - 点击按钮没反应
// - 动画停止
// - 输入框无法打字
// - 浏览器可能弹出 "页面无响应" 警告
```

**这就是单线程 + 同步调用的代价**：一个耗时操作就能冻结整个页面。事件循环的存在正是为了解决这个问题——通过将耗时操作"拆出去"，让主线程有机会去处理其他事情。

## 三、任务队列 —— 异步操作的"等候室"

既然调用栈一次只能做一件事，那么那些不需要立即做的事情该放哪里呢？答案是：**任务队列（Task Queue）**。

### 3.1 浏览器中的两种队列

浏览器维护着**两类**不同优先级的任务队列：

| | 宏任务队列（Macrotask Queue）| 微任务队列（Microtask Queue）|
|--|------|--------|
| **别名** | Task Queue / Callback Queue | Microtask Queue |
| **存储什么** | "大块"的异步任务 | "精细"的异步回调 |
| **典型来源** | `setTimeout` / `setInterval`、I/O 回调、UI 事件（click/input/scroll）、`<script>` 整体加载、`MessageChannel`、`postMessage`、`setImmediate`(Node) | `Promise.then/catch/finally`、`await` 后面的代码、`queueMicrotask()`、`MutationObserver` 回调、`Object.observe`（已废弃）|
| **执行时机** | 每次**取一个**执行 | 每次清空**全部** |
| **优先级** | 低（在微任务之后）| 高（在每个宏任务之后立即执行）|

### 3.2 宏任务队列 —— 先进先出的长队

宏任务队列就像银行柜台前的排队队伍。每个顾客（任务）按照到达顺序排队，柜员（主线程）每次服务一个顾客：

```javascript
// 注册三个宏任务（按顺序加入队列）
setTimeout(() => console.log('A'), 0);   // 第 1 个进入队列
setTimeout(() => console.log('B'), 0);   // 第 2 个进入队列
setTimeout(() => console.log('C'), 0);   // 第 3 个进入队列

// 队列状态: [A, B, C]

// 事件循环每次从队首取出一个执行：
// 第 1 轮: 取出 A → 执行 → 输出 'A'
// 第 2 轮: 取出 B → 执行 → 输出 'B'
// 第 3 轮: 取出 C → 执行 → 输出 'C'
```

**注意 FIFO 顺序**：即使 B 的实际工作量比 A 小得多，A 也必须先完成。这是公平性保证——先来先服务。

### 3.3 微任务队列 —— 高优先级的插队者

微任务队列的行为完全不同。它更像是一个"紧急事项箱"——每当柜员（主线程）处理完一个大客户（一个宏任务）后，**必须先检查这个箱子并处理里面的全部事项**，才能继续服务下一个大客户：

```javascript
// 注册三个微任务
Promise.resolve().then(() => console.log(1));
Promise.resolve().then(() => console.log(2));
Promise.resolve().then(() => console.log(3));

// 微任务队列: [1, 2, 3]

// 当某个宏任务完成后：
// → 清空微任务队列 → 全部依次执行
// 输出: 1 2 3（一次性全做完）
```

**关键区别**：微任务是"批量处理"的——一旦开始处理微任务，就会一直做到队列空为止（即使过程中又产生了新的微任务）。这保证了微任务的高优先级不被打断。

### 3.4 两类队列的对比总结

```
事件循环的一个完整轮回：

┌──────────────────────────────────────────────┐
│  第 N 个宏任务                               │
│  （如：<script> 整体、setTimeout 回调、      │
│        click 事件处理器、网络请求回调）       │
│                                              │
│  执行期间产生的微任务 → 进入微任务队列等待     │
└──────────────────────────────────────────────┘
                      │
                      ▼
┌──────────────────────────────────────────────┐
│  🔄 清空微任务队列                            │
│                                              │
│  取出微任务1 → 执行                          │
│  取出微任务2 → 执行                          │
│  取出微任务3 → 执行                          │
│  ...                                         │
│  直到队列为空                                 │
│                                              │
│  ⚠️ 执行期间产生的新微任务也在这轮处理！        │
└──────────────────────────────────────────────┘
                      │
                      ▼
              ┌──────────────┐
              │  渲染（可选）  │ ← 如果需要更新画面
              └──────────────┘
                      │
                      ▼
            回到顶部，取第 N+1 个宏任务
```

## 四、事件循环 —— 完整算法

### 4.1 标准定义的事件循环算法

以下是 HTML 规范中定义的事件循环简化版算法：

```
while (true) {                                    // 无限循环——只要页面存在就持续运行
  ┌── 步骤 1: 从宏任务队列中取出队首的任务 task     │
  │   if (task === undefined) {                    │
  │     等待新任务到来（休眠/挂起状态）             │  ← 几乎零 CPU 消耗
  │     continue;                                  │
  │   }                                           │
  │                                               │
  ├── 步骤 2: 执行 task                           │
  │   此时调用栈: [task 的执行上下文]               │
  │   task 内部的同步代码全部运行                   │
  │   task 中注册的新异步任务进入各自队列           │
  │   task 执行完毕，调用栈回到初始状态             │
  │                                               │
  ├── 步骤 3: 清空微任务队列                     │  ← 关键步骤！
  │   while (microtaskQueue 不为空) {              │
  │     取出 microtask → 执行                      │
  │     // 如果执行过程中产生了新的 microtask       │
  │     // → 加入队尾，本轮继续处理                │
  │   }                                           │
  │   // 此时微任务队列一定为空                     │
  │                                               │
  ├── 步骤 4: 判断是否需要渲染                     │
  │   if (需要更新画面 && 符合渲染条件) {           │
  │     执行 rendering（样式→布局→绘制）          │
  │   }                                           │
  │                                               │
  └── 回到步骤 1                                  │
}
```

### 4.2 各步骤详解

#### 步骤 1&2：执行宏任务

最常见的"宏任务"是 `<script>` 标签中的整体代码。当浏览器解析 HTML 遇到 `<script>` 时，会把脚本执行作为一个宏任务来处理：

```html
<!DOCTYPE html>
<html>
<body>
  <script>
    // 这是一个宏任务
    console.log('script 开始');

    setTimeout(() => console.log('setTimeout'));  // 注册宏任务
    Promise.resolve().then(() => console.log('then')); // 注册微任务

    console.log('script 结束');
    // script 宏任务执行完毕 → 进入步骤 3（清微任务）
  </script>
</body>
</html>

// 输出：
// script 开始
// script 结束
// then            ← 微任务在 script 之后立即执行
// setTimeout      ← 宏任务在微任务之后执行
```

**其他常见的宏任务来源**：

| 来源 | 何时产生宏任务 | 示例 |
|------|---------------|------|
| `setTimeout(fn, delay)` | delay 毫秒后 | `setTimeout(cb, 100)` → 100ms 后 cb 入队 |
| `setInterval(fn, interval)` | 每 interval 毫秒 | `setInterval(cb, 1000)` → 每 1 秒 cb 入队 |
| UI 事件 | 用户操作时 | click、input、scroll、keydown |
| I/O 完成 | 网络/文件操作完成时 | fetch 回调、WebSocket onmessage |
| `postMessage` | 收到消息时 | iframe/Worker 间通信 |

#### 步骤 3：清空微任务队列（最关键的步骤）

这一步是区分宏任务和微任务行为差异的核心：

```javascript
console.log('start');

// 注册 3 个微任务
Promise.resolve().then(() => {
  console.log('micro 1');
  // 在微任务中又产生新的微任务
  Promise.resolve().then(() => console.log('micro 1.5 (嵌套)'));
});

Promise.resolve().then(() => console.log('micro 2'));

Promise.resolve().then(() => {
  console.log('micro 3 (内含 setTimeout)');
  setTimeout(() => console.log('来自微任务的 setTimeout'));
});

// 注册 1 个宏任务
setTimeout(() => console.log('macro'), 0);

console.log('end');

// ====== 完整执行过程 ======
//
// 【宏任务 1】<script> 整体执行:
//   start → end（同步代码）
//   注册: micro[1,2,3], macro[timeout]
//
// 【步骤 3】清空微任务队列:
//   micro 1 → 执行 → 产生 micro 1.5（追加到队尾）
//   micro 2 → 执行
//   micro 3 → 执行 → 注册新 macro
//   micro 1.5 → 执行（嵌套的那个也被本轮处理！）
//   队列空 ✅
//
// 【步骤 4】判断渲染（本例无需渲染）
//
// 【回到步骤 1】下一个宏任务:
//   macro (setTimeout) → 执行 → 输出 'macro'
//
// 【步骤 3】清空微任务:
//   来自微任务的 setTimeout → 执行 → 输出 '来自微任务的 setTimeout'
//   队列空 ✅
//
// 最终输出:
// start
// end
// micro 1
// micro 2
// micro 3 (内含 setTimeout)
// micro 1.5 (嵌套)
// macro
// 来自微任务的 setTimeout
```

**特别注意"微任务产消模式"**：微任务 1 执行时产生了微任务 1.5，它没有被留到"下一轮"，而是在当前这轮清空中就被处理掉了。这就是为什么说微任务有**更高的优先级和更快的响应速度**——它们不会被宏任务"插队"。

#### 步骤 4：渲染（Rendering）

渲染是浏览器的独立子系统，它有自己的节奏。事件循环不会每次都触发渲染——只有在**满足特定条件**时才会：

```javascript
// 条件 1: 有 DOM 变更
document.body.style.backgroundColor = 'red';

// 条件 2: 浏览器认为"是时候更新画面了"
// 通常受限于显示刷新率（60Hz = 约 16.7ms 一帧）
// 但不会比 1fps 更慢（约 1000ms 一帧的上限）

// 所以连续修改 DOM 100 次：
for (let i = 0; i < 100; i++) {
  document.getElementById('counter').textContent = i;
}
// 用户只看到最后一次的结果！中间 99 次修改不会渲染
```

**渲染的精确时机**（根据 HTML 规范和现代浏览器实现）：

1. 宏任务执行完毕 ✓
2. 微任务队列已清空 ✓
3. **满足以下任一条件则触发渲染**：
   - 距上次渲染超过浏览器的帧预算时间（通常 ~16.7ms @60Hz）
   - 有 `requestAnimationFrame` 回调待执行
   - 有用户输入事件待处理（某些浏览器优化）
   - 页面可见性发生变化

### 4.3 完整的时间线图解

把所有概念整合到一张图中：

```
时间 →

┌─ <script> 宏任务 ──────────────────────────────────────┐
│  sync code...                                      │
│  setTimeout → [M1] 入宏任务队列                    │
│  Promise.then → [u1] 入微任务队列                  │
└──────────────────────────────────────────────────────┘
                        │
                        ▼
┌─ 微任务清空 ──────┐
│  执行 u1           │  ← 可能在此过程中产生 u1.1, u1.2...
│  执行 u1.1         │     （也在本轮处理）
│  执行 u1.2         │
│  ...直到队列空       │
└────────────────────┘
                        │
                   ┌────┴────┐
                   │  渲染？   │ ← 检查是否需要更新画面
                   │ (可选)    │
                   └────┬────┘
                        │
                        ▼
┌─ 下一个宏任务 ──→ [M1] setTimeout 回调
│  sync code...                                │
│  新的 .then → [u2] 入微任务队列                 │
└──────────────────────────────────────────────────┘
                        │
                        ▼
                   (重复以上过程...)
```

## 五、requestAnimationFrame 与渲染的关系

### 5.1 rAF 是什么？

`requestAnimationFrame(callback)`（简称 rAF）是一个特殊的 API。它的回调**不是普通宏任务也不是微任务**，而是与浏览器的**渲染步骤紧密绑定**：

```javascript
let frameCount = 0;

function animate(timestamp) {
  frameCount++;
  console.log(`第 ${frameCount} 帧, timestamp=${timestamp}`);

  box.style.transform = `translateX(${frameCount * 5}px)`;

  if (frameCount < 60) {
    requestAnimationFrame(animate);  // 注册下一帧
  }
}

requestAnimationFrame(animate);

// 输出示例（@60Hz 显示器）:
// 第 1 帧, timestamp=1438.200
// 第 2 帧, timestamp=1454.867  (~16.7ms 后)
// 第 3 帧, timestamp=1471.534  (~16.7ms 后)
// ...
// 每两次调用间隔 ≈ 16.7ms（= 1000ms / 60帧）
```

### 5.2 rAF 与 setTimeout 的本质区别

这是一个经典的比较：

```javascript
// 方式一：用 setTimeout 做动画
const start1 = performance.now();
function animateWithTimeout() {
  const elapsed = performance.now() - start1;
  box.style.left = elapsed * 0.1 + 'px';
  if (elapsed < 3000) {
    setTimeout(animateWithTimeout, 16); // 人为指定 16ms 间隔
  }
}
setTimeout(animateWithTimeout, 16);

// 方式二：用 rAF 做动画
function animaterAF(timestamp) {
  box.style.left = timestamp * 0.1 + 'px';
  if (timestamp < 3000) {
    requestAnimationFrame(animaterAF);
  }
}
requestAnimationFrame(animaterAF);
```

| 维度 | `setTimeout(fn, 16)` | `requestAnimationFrame(fn)` |
|------|---------------------|----------------------------|
| **执行时机** | 宏任务队列（最低优先级）| **与渲染步骤绑定** |
| **精度** | 受事件循环延迟影响（可能 4ms+ 或更多）| **与显示器刷新同步**（精确到帧）|
| **后台标签页** | 继续执行（浪费 CPU）| **自动暂停**（省电）|
| **帧率适配** | 固定 16ms（不管屏幕是 60Hz 还是 144Hz）| **自适应屏幕刷新率** |
| **CPU 使用** | 即使页面不可见也在跑 | 页面不可见时自动停止 |
| **典型用途** | 不适合动画 | **动画的标准选择** |

**为什么 rAF 更适合动画？**

因为 rAF 的回调是在**渲染之前**执行的（更准确地说，是在"渲染机会"的检查阶段），所以你在 rAF 回调中对 DOM 的修改能**赶上最近的一次渲染**。而 setTimeout 的回调只是普通宏任务，它可能在渲染之后才执行，导致丢帧。

### 5.3 rAF 在事件循环中的位置

rAF 回调在事件循环中的位置可以概括为：

```
事件循环的一轮:

1. 执行宏任务
2. 清空微任务队列
3. 【渲染相关】↓
   ├─ 判断是否需要渲染
   │   ├─ 是 → 执行 rAF 回调（如果有注册的话）
   │   → Style 计算 → Layout → Paint
   │   └─ 否 → 跳过
   └─ （注意：rAF 不是每轮都执行，
      只有浏览器决定"这次要渲染"时才执行）
4. 下一个宏任务
```

**重要细节**：rAF 并不是"每 16ms 必定执行一次"。如果上一帧的计算太复杂导致事件循环忙于执行其他任务，rAF 就会被推迟。这也是为什么性能优化的目标通常是**让事件循环的每一帧都有空闲**——这样 rAF 才能按时触发，动画才流畅。

│
└─ script 结束

│

├─ u:p2    → console.log('p2')       输出: p2

**最容易错的地方**：很多人以为 `await async2()` 会等 `async2` **包括其后续微任务**全部完成才继续。但实际上 `await` 只等 `async2()` 返回的 Promise settle——`async2` 内部没有 `await`，它的 Promise 在 executor 结束时就 fulfill 了。`async1` 中 `await` 之后的代码（`console.log('a1-end')`）被作为**独立的微任务**排队，排在后面注册的 `p2` **之前**（因为在源码位置上更早遇到）。

## 七、实际应用场景与性能影响

### 7.1 长任务拆分 —— 避免 UI 冻结

当一个 JavaScript 任务执行超过 **50ms** 时，用户就能感知到卡顿（因为 60Hz 下每帧只有 16.7ms 的预算）。解决方案是将长任务拆分为多个小宏任务：

```javascript
/**
 * 分片处理大量数据
 * 每次只处理一小部分，然后用 setTimeout(0) 让出主线程
 */
function processLargeArray(items, processor, chunkSize = 1000) {
  let i = 0;

  function processChunk() {
    const end = Math.min(i + chunkSize, items.length);

    for (; i < end; i++) {
      processor(items[i]); // 处理一小批
    }

    // 更新进度 UI
    progressEl.textContent = `处理中: ${i}/${items.length} (${Math.round(i/items.length*100)}%)`;

    if (i < items.length) {
      // 关键：将剩余工作放入新的宏任务
      // 这样事件循环有机会在两次处理之间响应用户操作
      setTimeout(processChunk, 0);
    } else {
      console.log('全部完成！');
    }
  }

  processChunk();
}

// 使用：处理 100 万条数据
processLargeArray(
  Array.from({ length: 1000000 }, (_, i) => ({ id: i })),
  item => { /* 处理逻辑 */ },
  50000  // 每批 5 万条
);
```

**原理**：每次 `processChunk` 只执行一小部分，然后 `setTimeout(processChunk, 0)` 将剩余工作放入新的宏任务。两次宏任务之间有一段"空隙"，事件循环利用这段空隙去处理 UI 事件和渲染——用户看到的进度条会实时更新，按钮也能点击。

### 7.2 用 queueMicrotask 进行高优先级调度

如果你需要在当前代码执行完后、但在渲染之前做一些事情（比如批量 DOM 修改后的统一通知），`queueMicrotask` 是最佳选择：

```javascript
class BatchDOMUpdater {
  #dirty = false;
  #updates = [];

  markDirty(updateFn) {
    this.#updates.push(updateFn);
    this.#dirty = true;

    if (!this.#scheduled) {
      this.#scheduled = true;
      // 用微任务确保在当前同步代码结束后、
      // 但在渲染之前批量执行所有 DOM 更新
      queueMicrotask(() => this.flush());
    }
  }

  flush() {
    this.#scheduled = false;
    this.#dirty = false;
    const updates = this.#updates;
    this.#updates = [];

    // 所有更新在一个微任务中批量执行
    updates.forEach(fn => fn());

    // 通知观察者（也是在渲染前）
    this.notifyObservers();
  }

  notifyObservers() {
    // ...
  }
}
```

**为什么不用 `setTimeout(fn, 0)`？** 因为 `setTimeout` 会等到下一次宏任务才执行——中间可能会多一轮渲染（如果距离上次渲染已经超过了 16ms），导致用户看到一个"中间态"。微任务保证在当前宏任务结束后**立即**执行，赶在同一次渲染之前。

### 7.3 事件委托中的延迟派发

有时你需要确保某个自定义事件在当前所有事件处理器（及其冒泡链）都完成后才触发：

```javascript
menu.addEventListener('click', function handler(e) {
  // ... 一些同步处理 ...

  // 我们希望 customEvent 在所有 click 的冒泡处理器完成后才派发
  // 因为冒泡过程中的处理器可能是同步的

  // ❌ 直接派发：可能在其他 click 处理器之前执行
  // menu.dispatchEvent(new CustomEvent('menu-open'));

  // ✅ 延迟到下一个宏任务：确保所有同步 click 处理已完成
  setTimeout(() => {
    menu.dispatchEvent(new CustomEvent('menu-open', { bubbles: true }));
  }, 0);
});
```

## 八、Node.js 事件循环的差异

虽然本文聚焦于浏览器环境，但你可能也需要了解 Node.js 事件循环的关键区别（避免混淆）：

| 维度 | 浏览器 | Node.js |
|------|--------|---------|
| **宏任务来源** | setTimeout/UI/I/O/script | timers / poll/check/close callbacks |
| **微任务** | Promise.then / MutationObserver / queueMicrotask | **process.nextTick** (优先级最高!) / Promise.then / _tickCallback |
| **微任务清空时机** | 每个宏任务之后 | **每个阶段（phase）之后**（timers → I/O callbacks → **idle → prepare → check → close callbacks）|
| **nextTick 特殊性** | 不存在 | nextTick 微任务在**同一阶段内**执行，早于其他微任务 |
| **I/O 密集型** | 单线程（主线程）| libuv 线程池（部分 I/O 不占用主线程）|

**Node.js 的特殊之处——process.nextTick**：

```javascript
// Node.js 环境
console.log('start');

process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('then'));
setTimeout(() => console.log('timeout'), 0);

console.log('end');

// 输出（Node.js）:
// start
// end
// nextTick     ← 比 then 更早！
// then
// timeout
```

在 Node.js 中，`process.nextTick` 的优先级高于 Promise `.then()`。这是因为 Node.js 的事件循环在每个阶段（phase）结束后都会先检查 `nextTickQueue`，然后才是 `microtaskQueue`（Promise 属于后者）。这是 Node.js 和浏览器的一个重要实现差异。

## 九、陷阱速查

| # | 陷阱 | 现象 | 原因 | 解决方案 |
|---|------|------|------|----------|
| 1 | **setTimeout(fn, 0) 不立即执行** | 总是在同步代码和微任务之后 | 它是宏任务，最低优先级 | 需要"几乎立即"用 `queueMicrotask` |
| 2 | **for 循环修改 DOM 不实时渲染** | 循环结束时才看到最终结果 | 渲染只在宏任务+微任务全部完成后 | 用 rAF 或 setTimeout(0) 拆分循环 |
| 3 | **微任务死循环** | 页面完全冻结（连 DevTools 都难打开） | 微任务产消模式：无限产生新微任务 | 确保微任务有终止条件 |
| 4 | **rAF 动画不如 CSS animation 流畅** | 偶尔掉帧 | rAF 回调本身也是宏任务级别 | 纯动画首选 CSS transition/animation |
| 5 | **混淆浏览器和 Node.js 事件循环** | nextTick vs then 的顺序不同 | 实现差异 | 明确目标环境再分析 |
| 6 | **忽略 requestIdleCallback** | 不知道何时有空闲时间 | 利用不了浏览器空闲期 | 用于低优先级后台任务 |
| 7 | **以为所有异步都是微任务** | setTimeout 也是"异步"但它很慢 | 混淆了两类队列的概念 | 记住分类表 |

### 陷阱 3 详解：微任务死循环

```javascript
// ⚠️ 危险！微任务死循环
function infiniteMicrotasks() {
  Promise.resolve().then(() => {
    console.log('还在跑...');
    infiniteMicrotasks(); // 递归产生新微任务
  });
}

infiniteMicrotasks();

// 结果：
// 还在跑...
// 还在跑...
// 还在跑...
// ...无限下去
// 页面完全冻结！
// 因为事件循环永远卡在"清空微任务"步骤中
// 无法执行下一个宏任务 → 无法渲染 → 无法响应点击
```

这与普通的 `while(true){}` 不同——普通的无限循环至少会被浏览器检测到并提示"页面无响应"。而微任务死循环更加隐蔽和危险。

## 十、最佳实践与调试技巧

### 10.1 性能优化原则

| 原则 | 说明 | 目标值 |
|------|------|-------|
| **保持帧预算 50ms** | 长任务拆分，每段不超过 50ms | Long Task < 50ms |

| **Web Workers 跑重计算** | 不阻塞主线程事件循环 | 复杂数据处理 |

## 十二、总结

| 维度 | 核心要点 |
|------|---------|
| **本质** | 事件循环 = **单线程的协作式调度系统**，让 JS 能同时处理大量异步任务而不阻塞 |
| **三大组件** | 调用栈（同步执行）+ 宏任务队列（FIFO，每次取一个）+ 微任务队列（产消模式，每次清空全部）|
| **核心规则** | **每个宏任务结束后，立即清空所有微任务，然后才考虑渲染或下一个宏任务** |
| **优先级** | 同步代码 > **微任务** > **渲染** > **宏任务** |
| **微任务特性** | 产消模式（本轮产生的新微任务同轮处理）、高优先级、适合状态批量同步 |
| **宏任务特性** | FIFO、低优先级、适合非紧急操作、`setTimeout(fn,0)` 不是"立即执行" |
| **渲染时机** | 宏任务+微任务全部完成 + 满足帧 budget（~16.7ms @60Hz）+ 有 rAF/DOM 变更 |
| **rAF vs setTimeout** | rAF 与渲染绑定、自动适应刷新率、后台暂停；setTimeout 固定间隔、后台继续跑 |
| **长任务危害** | 超 50ms → 用户感知卡顿；解决方案：拆分/Web Workers/requestIdleCallback |
| **调试工具** | Chrome Performance 面板（火焰图）/ Long Task API / Console 异步栈 |
| **Node.js 差异** | `process.nextTick` 优先于 `Promise.then`；分阶段模型而非简单的两队列 |
