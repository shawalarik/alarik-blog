# 事件循环（Node.js）—— process.nextTick、timers、poll、check、close 阶段与 libuv

> **核心内容**：Node.js 的事件循环并非浏览器那套简单的"宏任务+微任务"双队列模型，而是一个基于 **libuv 库的六阶段循环系统**。本文从 Node.js 的架构设计动机出发，深入剖析 libuv 的角色、六个阶段的精确行为、`process.nextTick` 的特殊优先级、微任务在 Node.js 中的两套队列机制、I/O 轮询的核心原理、与浏览器事件循环的完整对比，最终构建出 Node.js 异步世界的完整心智模型。

## 一、为什么需要理解 Node.js 事件循环？

### 从一个"简单"问题开始

你在写 Node.js 服务端代码时可能遇到过这样的困惑：

```javascript
console.log('start');

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));

console.log('end');
```

在浏览器中你已知道答案是 `start → end → promise → timeout/immediate`。但在 Node.js 中呢？

```
可能的输出 A：start, end, nextTick, promise, immediate/timeout
可能的输出 B：start, end, nextTick, promise, timeout/immediate（顺序不确定！）
```

更让人困惑的是：**同样的代码在不同执行上下文下会有不同的输出顺序**：

```javascript
// 在主模块中直接运行：
// → setTimeout 和 setImmediate 的顺序不确定！

// 但如果在 I/O 回调内部运行：
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate')); // ← 这个总是先于 timeout！
});
```

为什么会这样？Node.js 的事件循环和浏览器有什么不同？`process.nextTick` 到底是什么？`setImmediate` 又是什么？这些问题的答案都藏在 Node.js 事件循环的**六阶段模型**中。

### Node.js 与浏览器事件循环的根本差异

虽然两者都叫"事件循环"，但它们的实现哲学完全不同：

| 维度 | 浏览器事件循环 | Node.js 事件循环 |
|------|----------------|---------------|
| **底层引擎** | V8/SpiderMonkey 等 JS 引擎内置 | **libuv**（C 语言跨平台库）|
| **任务模型** | 双队列（宏任务 + 微任务）| **六阶段循环** + **两套微任务队列** |
| **I/O 处理方式** | 主线程阻塞等待 | **线程池异步处理**（不阻塞主线程）|
| **渲染** | 有（Style → Layout → Paint） | 无（纯后端环境）|
| **API 丰富度** | 较少（setTimeout/UI/DOM）| 更多（nextTick/setImmediate/file I/O/stream/crypto）|
| **设计目标** | 驱动 UI 交互 + 执行脚本 | 高效处理 I/O 密集型任务 |

**通俗类比**：如果浏览器的事件循环像一个**小型诊所**——一个医生（主线程）兼顾挂号、诊断和开药，用"叫号排队"（宏任务）和"加急通道"（微任务）来管理；那么 Node.js 的事件循环就像一座**大型综合医院**——它有专门的挂号处（timers）、急诊科（pending callbacks）、检验科（check）、住院部（poll/I/O）、出院处（close），还有一套特殊的"院长特批"通道（process.nextTick）。医院的规模越大，调度规则就越复杂精细。

### 学习路线

```
libuv 架构 → 理解 C 层抽象和线程池的作用
    ↓
六阶段模型 → timers/pending/idle&prepare/poll/check/close
    ↓
两套微任务队列 → nextTickQueue vs microtaskQueue（优先级差异）
    ↓
各阶段详解 → 每个阶段的触发条件、典型 API 和行为特征
    ↓
实际应用 → I/O 回调中的顺序确定性 / 饥饿风险 / 性能优化策略
    ↓
与浏览器的完整对比 → 差异速查表
```

## 二、libuv —— Node.js 事件循环的引擎

### 2.1 什么是 libuv？

**libuv** 是一个用 C 语言编写的跨平台异步 I/O 库，它是 Node.js 最核心的依赖之一。当你安装 Node.js 时，libuv 也被一起打包了进来。它的职责可以用一句话概括：

**将不同操作系统的异步 I/O 能力抽象为统一的接口，让 Node.js 能够以一致的方式处理文件系统操作、网络通信、DNS 查询、子进程管理等所有 I/O 操作。**

```javascript
// 你写的 Node.js 代码
const fs = require('fs');

fs.readFile('/etc/hostname', 'utf8', (err, data) => {
  console.log(data); // 文件读取完成后的回调
});

console.log('这行先执行');
```

这段代码背后发生了什么？libuv 在默默地工作：

```
你的 JavaScript 代码
    │
    ▼
┌─────────────────────────────────┐
│  V8 引擎 (JS 执行)             │
│  - 执行同步代码               │
│  - 遇到 fs.readFile()           │
│    └→ 这不是普通的函数调用！     │
│       它是 C++ 绑定的方法          │
│       最终调用 libuv 的 API      │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────────────┐
│  libuv (C 语言层)                      │
│                                         │
│   readFile() 内部流程：                  │
│   1. 检查是否有线程池可用线程        │
│   2. 将读取任务提交给线程池中的工作线程   │
│   3. 工作线程调用 OS 原生的 read() 系统调用  │
│   4. read() 是非阻塞的（OS 支持）      │
│   5. 数据就绪后，将回调推入 poll 队列      │
│   6. 事件循环在 poll 阶段取出回调执行     │
└─────────────────────────────────────────┘
```

### 2.2 libuv 线程池 —— 为什么 Node.js I/O 不阻塞主线程？

这是理解 Node.js 性能优势的关键。当你的代码调用 `fs.readFile()` 时，实际的磁盘读取并不是由 JavaScript 主线程完成的：

```
Node.js 进程内存布局（简化）:

┌──────────────────────────────────────────┐
│  主线程 (JS Engine / Event Loop)         │
│  ├── 执行你的 .js 代码                    │
│  ├── 运行事件循环的各个阶段              │
│  └── 执行 I/O 回调（数据已经准备好了！）     │
│                                          │
│  ⚠️ 注意：主线程从不直接做 I/O 操作！     │
├──────────────────────────────────────────┤
│  libuv 线程池 (4 个默认工作线程)            │
│                                          │
│  Thread #1: ┌────────────┐                 │
│            │  read() from disk  │  ← OS 调用     │
│            │  (阻塞的是这个线程)  │                │
│            └────────────────┘                 │
│                                          │
│  Thread #2: ┌────────────┐                 │
│            │  DNS lookup()      │  ← 可能阻塞     │
│            └────────────────┘                 │
│                                          │
│  Thread #3: [空闲]                           │
│  Thread #4: [空闲]                           │
└──────────────────────────────────────────┘
```

**关键点**：`read()` 系统调用虽然是阻塞的（操作系统层面），但它**阻塞的是工作线程而不是主线程**。主线程始终是空闲的，可以继续执行其他 JavaScript 代码或处理其他回调。这就是为什么 Node.js 在处理大量并发 I/O 时仍然能保持高性能的原因——**真正的 I/O 重活被外包给了线程池**。

### 2.3 libuv 的其他职责

除了线程池和事件循环，libuv 还负责：

| 功能 | 说明 |
|------|------|
| **平台适配** | Linux 用 epoll、Windows 用 IOCP（I/O 完成端口）、macOS 用 kqueue |
| **DNS 解析** | c-ares 库集成，异步 DNS 查询 |
| **文件系统 watcher** | inotify/kqueue/FSEvents |
| **子进程管理** | spawn/exec 的底层实现 |
| **信号处理** | Unix signal 到事件循环的桥接 |
| **定时器** | 精确的定时器管理（不是粗糙的 setTimeout）|

## 三、六阶段模型 —— Node.js 事件循环的核心

### 3.1 六个阶段的全景图

Node.js 的事件循环不是一个简单的 "取任务→执行→取任务→执行" 循环。它是一个**分阶段（phase-based）**的系统，每次循环都会按顺序经过以下六个阶段：

```
Node.js 事件循环的一次完整轮回（简化版算法）

while (event_loop_alive) {
  ══════════ 阶段 1: timers ══════════
  │  执行 setTimeout / setInterval 到期的回调
  │  （注意：不到时间的不执行）
  └──────────────────────┬──────────────┘
                         │
                         ▼
  ══════════ 阶段 2: pending callbacks ══════════
  │  执行延迟到下一轮的 I/O 错误回调
  │  （如 ECONNREFUSED、EPIPE）
  └──────────────────────┬──────────────┘
                         │
                         ▼
  ══════════ 阶段 3: idle, prepare ══════════
  │  仅内部使用（libuv 自身的事务）
  │  开发者通常不需要关心
  └──────────────────────┬──────────────┘
                         │
                         ▼
  ══════════ 阶段 4: poll ⭐ 核心 ══════════
  │  执行 I/O 相关回调（fs/net/dns 等）
  │  如果没有 I/O 事件 → 在此等待（不消耗 CPU）
  │  如果有新 I/O → 取出并执行对应回调
  └──────────────────────┬──────────────┘
                         │
                         ▼
  ══════════ 阶段 5: check ══════════
  │  执行 setImmediate() 的回调
  └──────────────────────┬──────────────┘
                         │
                         ▼
  ══════════ 阶段 6: close callbacks ════════
  │  执行 socket.on('close') 等关闭回调
  └──────────────────────┬──────────────┘
                         │
                         ▼
              ┌──────────────────────┐
              │  微任务处理（每个阶段之间）  │  ← 重要！
              │  ├─ 清空 nextTickQueue       │
              │  └─ 清空 microtaskQueue       │
              └──────────────────────┘
                         │
                   (回到阶段 1)
}
```

### 3.2 各阶段逐一详解

#### 阶段 1：timers（定时器）

```javascript
// 这些回调会在 timers 阶段被执行
setTimeout(callback, 1000);   // 1000ms 后到期
setInterval(callback, 500);    // 每 500ms 重复
```

**关键细节**：

1. **"最早可执行时机"而非"准时执行"**：如果上一个阶段（close callbacks）花了 200ms 才完成，而一个 `setTimeout(fn, 100)` 本该在 100ms 后到期，那它实际上会延迟到 ~300ms 才执行（因为事件循环还在忙于 close 阶段）。timers 阶段只检查"有没有到期的"，不管"晚了多久"。
2. **顺序保证**：同一次到期的多个回调按注册顺序执行。
3. **最小粒度**：Node.js 的计时器精度通常是 **1ms**（受操作系统调度粒度限制），所以 `setTimeout(fn, 0)` 实际上至少要等 1ms。

#### 阶段 2：pending callbacks（待定回调）

这个阶段处理的是**上一轮 I/O 操作中推迟的错误回调**：

```javascript
const net = require('net');

const req = net.connect(8080, 'localhost', () => {
  console.log('连接成功！');
});

req.on('error', (err) => {
  // 这个错误回调不会立即执行
  // 而是"延迟"到下一轮事件循环的 pending callbacks 阶段才执行
  console.error('连接失败:', err.message);
});
```

为什么需要单独的一个阶段来处理这些错误？因为在某些情况下（如 TCP RST 包导致连接重置），错误回调需要在下一个事件循环迭代中安全地执行——不能在当前迭代的中间状态中处理。

#### 阶段 3：idle, prepare

这两个阶段**仅供 libuv 内部使用**，开发者通常无需关心。简而言之：
- **prepare**：做一些循环每轮开始前的准备工作（如检查是否需要退出进程）
- **idle**：libuv 在没有事情可做时可能会在这里进行一些内部清理（V8 的垃圾回收有时在这个时间点被触发）

#### 阶段 4：poll（轮询）⭐ 核心阶段

这是 Node.js 事件循环**最重要、最忙碌的阶段**。大部分 I/O 回调都在这里执行：

```javascript
const fs = require('fs');

// readFile 的回调将在 poll 阶段执行
fs.readFile('/path/to/file.txt', 'utf8', (err, data) => {
  if (err) throw err;
  console.log('文件内容:', data.substring(0, 50));
});

console.log('这行先执行'); // 同步代码先跑完
// 然后进入事件循环
// poll 阶段：发现文件读取完成 → 执行回调 → 输出文件内容
```

**poll 阶段的行为逻辑**：

```
poll 阶段开始:
│
├─→ 检查 I/O 队列（由 libuv 线程池填充）
│   │
│   ├─→ 队列不为空？
│   │   └─→ YES → 取出一个 I/O 回调并执行
│   │       → 继续检查直到队列为空 或 达到最大数量上限
│   │
│   └─→ 队列为空？
│       └─→ 检查是否有 timers 即将到期
│           ├─→ 有且很快 → 等一小会儿（不超过最近 timer 的时间）
│           └─→ 没有 → 进入休眠等待新 I/O 事件
│
└─→ poll 阶段结束 → 进入下一阶段（check）
```

**这就是为什么 Node.js 适合 I/O 密集型应用的原因**：poll 阶段的本质是一个**高效的事件多路复用器**（类似 Linux 的 epoll 或 Windows 的 IOCP），它可以同时监控成千上万个文件描述符（file descriptor），任何一个有事件到来都能立即唤醒事件循环去处理对应的回调。

#### 阶段 5：check（检查）

```javascript
// setImmediate 的回调在这里执行
setImmediate(() => {
  console.log('我在 check 阶段！');
});
```

**check 阶段的存在理由**：`setImmediate()` 被专门分配了一个独立的阶段，这意味着它在事件循环中的位置是**固定的、确定的**——总是在 poll 之后、close 之前。这与 `setTimeout(fn, 0)` 形成了鲜明对比。

#### 阶段 6：close callbacks（关闭回调）

```javascript
const net = require('net');

const server = net.createServer((socket) => {
  socket.end('Hello!');
  // 当客户端断开连接时
  socket.on('close', () => {
    console.log('客户端断开了'); // 这个回调在 close callbacks 阶段执行
  });
});

server.listen(3000);
```

当 TCP 连接关闭、管道关闭、IPC 通道断开时，相关的 `close` 事件会被收集并在 close callbacks 阶段统一处理。这保证了资源的正确清理。

## 四、两套微任务队列 —— nextTick vs Promise

### 4.1 Node.js 的微任务特殊性

在浏览器中，只有一套微任务队列（Microtask Queue）。但 Node.js 有**两套**：

| | **nextTick Queue** | **microtaskQueue** |
|--|---|---|
| **来源** | `process.nextTick(cb)` | `Promise.then/catch/finally` / `await` |
| **清空时机** | **每个阶段之后**（6 个阶段每个都检查）| **每个阶段之后且 nextTick 为空之后** |
| **优先级** | **更高** | 较低 |

**执行伪代码**（每个阶段结束后的微任务处理）：

```javascript
function runMicrotasks() {
  // 第一优先级：nextTick
  while (nextTickQueue.length > 0) {
    const cb = nextTickQueue.shift();
    cb(); // 执行 nextTick 回调
  }

  // 第二优先级：Promise（仅当 nextTick 为空时才执行）
  while (microtaskQueue.length > 0 && nextTickQueue.length === 0) {
    const cb = microtaskQueue.shift();
    cb(); // 执行 Promise then/catch/finally 回调
  }
}

// 事件循环在每个阶段结束后都调用 runMicrotasks()
```

**这就是 `process.nextTick` 比 `Promise.then()` 先执行的根本原因**——它有自己专属的高优先级队列，而且每个阶段结束时都是先清 nextTick 再清 Promise。

### 4.2 经典演示：优先级差异

```javascript
console.log('1:start');

process.nextTick(() => console.log('2:nextTick'));

Promise.resolve().then(() => console.log('3:promise'));

console.log('4:end');
```

**输出**：`1:start` → `4:end` → `2:nextTick` → `3:promise`

追踪过程：

```
【初始】<script> 作为第一个宏任务执行:
│
├─ console.log('1:start')     → 输出: 1:start
│
├─ process.nextTick(cb)      → nextTickQueue: [cb]
│
├─ Promise.resolve().then(cb)  → microtaskQueue: [cb]
│   （注意：此时 Promise 已 fulfill，
│     但 .then 回调还没执行！只是入了队）
│
├─ console.log('4:end')       → 输出: 4:end
│
└─ <script> 执行完毕
   【每个阶段后都要清微任务】

【微任务处理】(script 结束后的第一次):
│
├─ nextTickQueue 不为空 → 取出 cb → 执行
│   → 输出: 2:nextTick
│   nextTickQueue 空 ✅
│
├─ nextTickQueue 空 → 检查 microtaskQueue
│   不为空 → 取出 cb → 执行
│   → 输出: 3:promise
│   microtaskQueue 空 ✅
│
└─ 微任务全部清空 → 进入下一阶段(timers)
```

### 4.3 setImmediate vs setTimeout(fn, 0)

这是一个非常容易混淆的点。两者看起来都是"尽快执行回调"，但行为有重要差异：

#### 在主模块中调用时（I/O 循环外）

```javascript
// 直接在脚本顶层运行（不属于任何 I/O 回调）
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// 输出顺序：不一定！
// 大多数情况：timeout 先（因为只有 1ms 延迟）
// 但偶尔：immediate 先（取决于系统调度）
```

**原因**：`setTimeout(fn, 0)` 的回调在 **timers 阶段**执行，而 `setImmediate(fn)` 的回调在 **check 阶段**执行。由于 timers 阶段在 check 之前，理论上 `setTimeout` 更早。但实际上 Node.js 为了性能会对定时器做**截断优化**（通常最小精度为 1ms），所以在某些边界条件下两者的顺序可能互换。

#### 在 I/O 循环内调用时（I/O 回调内）

```javascript
const fs = require('fs');

// 在文件读取的回调（属于 poll 阶段的结果）
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

// 输出顺序：一定是 immediate → timeout
// （100% 确定！）
```

**为什么这次顺序确定了？** 因为 I/O 回调是在 **poll 阶段**执行的。poll 结束后的下一个阶段是 **check**（`setImmediate` 所在地），再下一个才是 **timers**（`setTimeout` 所在地）。所以只要在 I/O 循环内部，`setImmediate` 就一定比 `setTimeout(fn, 0)` 早执行。

### 4.4 完整优先级总结

把所有"异步操作"放在一起看：

```
Node.js 中各类操作的执行优先级（从高到低）:

1. 同步代码（调用栈中立即执行）
   └─ console.log() / 变量赋值 / 函数调用

2. process.nextTick() ← 最高优先级的异步
   └─ 在当前操作完成后、下一阶段之前执行

3. Promise.then() / await 后面的代码
   └─ 在 nextTick 清空后才执行

4. setImmediate()
   └─ check 阶段（poll 之后）

5. setTimeout(fn, 0)
   └─ timers 阶段（最早也要 1ms）

6. setTimeout(fn, N)  N > 0
   └ timers 阶段（等待指定毫秒数）

7. I/O 回调 (fs.read / net.request / dns.resolve)
   └ poll 阶段（I/O 完成时）
```

## 五、深入 I/O 回调与 Poll 阶段

### 5.1 I/O 回调是如何进入 poll 阶段的？

这是理解 Node.js 异步模型最核心的部分。让我们跟踪一个网络请求的完整生命周期：

```javascript
const http = require('http');

http.get('https://api.example.com/data', (res) => {
  console.log(`状态码: ${res.statusCode}`);
  // 这个回调何时执行？
});

console.log('请求已发出');
```

**完整的时间线追踪**：

```
T=0ms: 你的代码开始执行（<script> 宏任务）
│
├─ http.get() 被 V8 引擎调用
│   │
│   └─→ V8 发现这是 HTTP 请求
│       │
│       ▼
│   ┌──────────────────────────────────────┐
│   │  libuv 层面                            │
│   │                                        │
│   │   1. 创建 TCP socket                  │
│   │   2. 发送 HTTP GET 请求              │
│   │   3. socket 注册到 epoll/kqueue 监控     │
│   │   4. 返回 control 给 JS（不阻塞！）     │
│   │                                        │
│   │  ┌─ Thread Pool ──────────────┐   │
│   │  │  Worker Thread #1           │   │
│   │  │  ...OS 处理...            │   │
│   │  │  收到 HTTP Response        │   │
│   │  │  将回调推入 I/O 队列         │   │
│   │  └───────────────────────────────┘   │
│   └──────────────────────────────────────┘
│
├─ console.log('请求已发出')  → 输出: '请求已发出'
│
└─ script 宏任务执行完毕
   （事件循环开始第一轮）

=== 事件循环第 1 轮 ===
│
[阶段 1] timers: 无到期定时器 → 跳过
[阶段 2] pending: 无待定回调 → 跳过
[阶段 3] idle/prepare: 内部事务 → 跳过
[阶段 4] poll: ★ 核心！
  │
  ├─→ 检查 I/O 队列 → 发现 HTTP Response 回调
  ├─→ 取出回调 → 执行
  │   └─→ console.log(`状态码: ${res.statusCode}`)
  │
[阶段 5] check: 无 setImmediate → 跳过
[阶段 6] close: 无关闭事件 → 跳过

→ 清空微任务（如果有）
→ 回到阶段 1（等待下一轮）
```

**关键洞察**：从发起请求到收到响应的这段时间里，JavaScript 主线程完全没有闲着——它在执行你的其他代码（或者如果没有其他事做的话就在事件循环中"空转"等待）。真正耗时的 I/O 操作（DNS 查询、TCP 握手、HTTP 传输、接收响应体）全都是由**工作线程在线程池中完成的**，主线程只在最后一步"摘果子"——取出已经准备好的结果来执行回调。

### 5.2 poll 阶段的阻塞与非阻塞

当 I/O 队列为空且没有即将到期的定时器时，poll 阶段会让事件循环**进入阻塞（sleep）状态**：

```javascript
// 假设此时没有任何 I/O 正在进行
const start = Date.now();

// 1 秒后的定时器
setTimeout(() => {
  console.log(`${Date.now() - start} ms 后的定时器`);
}, 1000);

// 此时事件循环会做什么？
// → timers 阶段：检查 → 定时器未到期（还需 999ms）
// → poll 阶段：I/O 队列为空 → **阻塞等待**
// → 操作系统挂起 Node.js 进程（几乎零 CPU）
// → 999ms 后：OS 唤醒进程 → 定时器到期
// → 下一轮循环：timers 阶段执行回调
```

**这种阻塞是高效的**：不像 `while(true){}` 那样消耗 CPU，poll 的阻塞是通过操作系统的 `epoll_wait()` 实现的——内核会将进程挂起，直到有事件到来才唤醒。这对于服务器长时间运行时的能耗控制非常重要。

## 六、经典面试题深度解析

### 6.1 基础题：四大异步 API 对决

```javascript
console.log('1');

setTimeout(() => console.log('2'), 0);

setImmediate(() => console.log('3'));

process.nextTick(() => console.log('4'));

Promise.resolve().then(() => console.log('5'));

console.log('6');
```

**逐步追踪**：

```
【<script> 同步执行】:
  log('1')    → 输出: 1
  setTimeout → 宏任务队列 [M:timer]
  setImm    → check 队列   [C:imm]
  nextTick   → nT 队列    [N:cb]
  Promise   → mT 队列    [P:cb]
  log('6')    → 输出: 6
  script 结束

【阶段间微任务处理】(script 后):
  nT: [cb] → 执行 → 输出: 4    (nextTick 先!)
  mT: [cb] → 执行 → 输出: 5    (Promise 后)

【事件循环第 1 轮】:
  [timers]: timer 未到 → 跳过
  [pending]: 空 → 跳过
  [idle/prep]: 跳过
  [poll]: 空 → 跳过
  [check]: imm → 执行 → 输出: 3
  [close]: 空 → 跳过

  [阶段间微任务]: 无

【事件循环第 2 轮】:
  [timers]: timer 到了! → 执行 → 输出: 2
  ...

最终输出: 1, 6, 4, 5, 3, 2
```

### 6.2 I/O 循环内的顺序确定性

```javascript
const fs = require('fs');

fs.readFile(__filename, () => {
  process.nextTick(() => console.log('A:nextTick'));
  Promise.resolve().then(() => console.log('B:promise'));
  setTimeout(() => console.log('C:timeout'), 0);
  setImmediate(() => console.log('D:immediate'));
});

console.log('E:sync end');
```

**输出**：`E:sync end → A:nextTick → B:promise → D:immediate → C:timeout`

**解析**：这段代码在 `readFile` 的 I/O 回调（poll 阶段产物）中运行。poll 阶段结束后依次经历 check → close → timers → (回到 poll)。每个阶段间隙都有微任务处理。`setImmediate` 在 check 阶段执行（固定位置），`setTimeout` 在 timers 阶段执行（下一轮循环）。

### 6.3 递归 nextTick 的饥饿风险

```javascript
// ⚠️ 危险代码！
function infiniteNextTicks() {
  process.nextTick(infiniteNextTicks); // 递归产生新的 nextTick
}

infiniteNextTicks();

// 同时注册的其他回调：
setTimeout(() => console.log('我永远不会执行！'), 100);

// 结果：
// 无限打印 nextTick...
// setTimeout 的回调永远无法执行！
// 因为事件循环永远卡在 nextTick 的无限循环中
// 无法进入 poll 阶段 → 无法处理 I/O → 无法检查定时器
```

**这就是所谓的"微任务饥饿（starvation）"问题**：如果 nextTick 队列永远不空（不断有新的 nextTick 加入），事件循环就永远卡在"清空 nextTick → 清空 Promise → 下一阶段"的循环中，永远不会到达 timers、poll、check 等后续阶段。I/O 回调和定时器全部被"饿死"了。

### 7.3 同一段代码在不同环境的执行差异

```javascript
// 相同的代码
console.log('start');

setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
process.nextTick?.(() => console.log('nextTick')); // Node.js only

console.log('end');
```

**浏览器环境输出**：
```
start
end
promise
timeout
(nextTick 不存在，报错或跳过)
```

**Node.js 环境**：
```
start
end
nextTick      ← 比 promise 先!
promise
timeout
```

**关键区别就是 `process.nextTick` 的存在及其高于 Promise 的优先级**。如果你在写同时支持浏览器和 Node.js 的库/框架，这一点必须特别注意——不要假设 `Promise.then` 一定是"最快的异步操作"。

## 八、实战应用模式

### 8.1 用 nextTick 让错误处理跑在 Promise 之前

```javascript
/**
 * 确保 error handler 在 Promise 之前执行
 * 用于一些必须在微任务阶段早期运行的初始化操作
 */
function ensureInitialized() {
  if (!initialized) {
    initialized = true;

    // nextTick 中的代码会在当前同步代码之后、
    // 所有 Promise 之前执行
    process.nextTick(() => {
      setupErrorHandling();
      setupGracefulShutdown();
    });
  }
}
```

### 8.2 用 setImmediate 分割长任务

```javascript
/**
 * 使用 setImmediate 进行长任务分割
 * 类似于浏览器的 setTimeout(0)，但不受 1ms 限制
 */
function processInChunks(items, processor, chunkSize = 1000) {
  let i = 0;
  
  function processChunk() {
    const end = Math.min(i + chunkSize, items.length);
    
    for (; i < end; i++) {
      processor(items[i]);
    }
    
    if (i < items.length) {
      // 使用 setImmediate 而非 setTimeout
      // 原因：在 I/O 循环内 setImmediate 总是先于 setTimeout
      setImmediate(processChunk);
    } else {
        console.log('全部处理完毕');
      onDone();
    }
  }

  processChunk();
}
```

### 8.3 用 nextTick 实现 run-after-current

```javascript
/**
 * 让某个函数在当前同步代码执行完后、但在任何 Promise 之前执行
 * 类似 Vue 的 $nextTick() 的实现原理
 */
function afterCurrentSync(fn) {
  process.nextTick(fn);
}

// 使用示例：确保 DOM 更新在数据变化之后
state.data = newData;
afterCurrentSync(() => syncDOMWith(state));
// 这里的 DOM 更新会比 Promise.then 中的更新更早执行
```

### 8.4 避免 nextTick 饥饿

```javascript
// ✅ 安全的批量 nextTick 模式
const tasks = [];

function safeNextTickBatch(task) {
  tasks.push(task);
  
  if (tasks.length === 1) {
    // 只有第一个任务时才注册 nextTick
    process.nextTick(runAllTasks);
  }
  // 后续的任务会被同一个 nextTick 批量处理
}

function runAllTasks() {
  const batch = tasks.splice(0); // 取出全部
  batch.forEach(task => task());
  // 本次 nextTick 结束后，事件循环才能继续
}
```

## 九、陷阱速查

| # | 陷阱 | 现象 | 原因 | 解决方案 |
|---|------|------|------|----------|
| 1 | **nextTick > Promise 顺序记混** | 误以为 Promise 先执行 | Node.js 有两套微任务队列，nextTick 优先级更高 | 记住："**Node 中 nextTick 跑在 Promise 前**" |
| 2 | **setImmediate vs setTimeout(0) 不确定** | 主模块中两者顺序随机 | timers 阶段受 1ms 截断优化影响 | 需要**确定顺序时在 I/O 回调内使用** |
| 3 | **递归 nextTick 饿死** | I/O 永远不执行、页面/服务无响应 | nextTick 无限递归填满队列，事件循环卡死 | 控制递归深度 / 使用 `setImmediate` 替代 |
| 4 | **浏览器代码 copy 到 Node 报错** | nextTick 不存在报 ReferenceError | Node.js 特有 API | 用条件判断 `typeof process !== 'undefined'` |
| 5 | **以为 poll 会阻塞** | 其实 I/O 由线程池处理不阻塞主线程 | libuv 线程池让主线程始终可用 | 只有**无 I/O 且无定时器**时才真正阻塞 |
| 6 | **忽略 prepare/idle 阶段** | 试图在这些阶段注册回调 | 它们仅供 libuv 内部使用 | 不要直接操作（除非你在写 Node.js C++ addon）|

## 十、最佳实践与调试技巧

### 10.1 场景决策表

| 你的需求 | 推荐 API | 理由 |
|---------|---------|------|
| **让代码在当前操作后尽快执行但不阻塞 I/O** | `process.nextTick()` | 最高优先级的微任务，比 Promise 快 |
| **确保在 I/O 回调之后、定时器之前执行** | `setImmediate()` | 固定在 check 阶段（poll 之后）|
| **需要精确延迟（>=1ms）** | `setTimeout(fn, ms)` | timers 阶段，有最低 1ms 限制 |
| **需要"尽快"但不关心确切时机** | `queueMicrotask()` 或 `Promise.resolve().then()` | 微任务，比宏任务快 |
| **分割长任务避免事件循环饥饿** | `setImmediate()` 递归 | 不受 1ms 限制，且不在 timers 阻塞 |
| **需要兼容浏览器和 Node.js** | `Promise.resolve().then()` | 两者都支持的标准 API |

### 10.2 Node.js 性能监控

```javascript
const { performance, PerformanceObserver } = require('perf_hooks');

// 监控事件循环的延迟
if (performance.eventLoopUtilization) {
  // Node.js 12+
  const histogram = performance.eventLoopUtilization();
  
  setInterval(() => {
    const summary = histogram;
    // summary.sum: 累积的阻塞时间占比
    console.log(`事件循环利用率: ${(summary.sum * 100).toFixed(1)}%`);
  }, 5000);
}

// 监控长任务
if ('PerformanceObserver' in globalThis) {
  const obs = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      if (entry.entryType === 'longtask' && entry.duration > 50) {
        console.warn(`⚠️ 长任务: ${entry.name} (${entry.duration.toFixed(1)}ms)`);
      }
    }
  });
  obs.observe({ entryTypes: ['longtask'] });
}
```

```
│   │   └─ GC 触发点之一
│   │
│   ├── ④ poll ⭐ 核心：I/O 回调（fs/net/dns 等）
│   │   ├── 队列不空 → 执行回调
│   │   ├── 队列空 + 无 timer → **阻塞等待**（OS 挂起进程）
│   │   └─ I/O 密集型的性能根基
│   │
│   ├── ⑤ check：setImmediate() 专用阶段
│   │   └─ 固定位置：poll 之后、timers 之前
│   │
│   └── ⑥ close：socket.on('close') 等关闭回调
│
├── 两套微任务队列（每个阶段间隙执行）
│   ├── nextTickQueue（最高优先级）
│   │   ├── 来源：process.nextTick()
│   │   └── 每个阶段后首先清空
│   │   └── ⚠️ 递归可能导致饥饿
│   │
│   └── microtaskQueue（次优先级）
│       ├── 来源：Promise.then/catch/finally / await
│       └── 仅在 nextTick 为空时才清空
│
├── API 优先级总览（从高到低）
│   1. 同步代码（调用栈）
│   2. process.nextTick()
│   3. Promise.then() / await
│   4. setImmediate()
│   5. setTimeout(fn, 0)
│   6. setTimeout(fn, N)  N>0
│   7. I/O 回调（poll 阶段）
│
├── 与浏览器的关键差异
│   ├── 底层：libuv vs V8 引擎内置
│   ├── 模型：六阶段 vs 双队列
│   ├── 额外 API：setImmediate / nextTick / 无 rAF
│   ├── I/O：线程池异步 vs 主线程处理
│   └── 微任务：两套队列 vs 一套队列
│
└── 实战
    ├── 避免递归 nextTick 饥饿
    ├── setImmediate 长任务拆分
    ├── nextTick 初始化模式
    └── 性能监控（eventLoopUtilization / Long Task Observer）
```

## 十二、总结

| 维度 | 核心要点 |
|------|---------|
| **架构** | Node.js 事件循环基于 **libuv**（C 语言跨平台库），不是 JS 引擎内置 |
| **模型** | **六阶段循环**（timers → pending → idle&prepare → **poll** → check → close），每个阶段间隙处理微任务 |
| **微任务** | **两套队列**：`nextTickQueue`（最高优先级，每个阶段后清空）> `microtaskQueue`（Promise，nextTick 为空时才清空）|
| **I/O 核心** | **poll 阶段**：I/O 由 **线程池异步执行**，主线程只取结果（不阻塞）；队列空时**阻塞挂起**（OS 级程挂起，~0 CPU）|
| **setImmediate** | 固定在 **check 阶段**（poll 之后）；在 I/O 回调内总是先于 `setTimeout(fn,0)` |
| **setTimeout(0)** | 在 **timers 阶段**；受 1ms 最小精度限制；在 I/O 外顺序不确定 |
| **nextTick** | 最高优先级异步 API；**危险**：递归可导致事件循环饥饿（I/O 全部饿死）|
| **与浏览器对比** | 无渲染 / 有 nextTick & setImmediate / I/O 线程池 / 六阶段 vs 双队列 |
| **性能利器** | 适合 I/O 密集型应用（服务器/CLI/网络代理）；长任务用 `setImmediate` 或 Workers |
