# 异步模式设计 —— 防抖（debounce）、节流（throttle）、重试（retry）、超时（timeout）

> **核心内容**：在异步编程中，仅仅"让代码跑通"远远不够。真实世界中充满了不可控因素：网络延迟波动、API 偶发失败、用户高频操作、资源竞争条件……这些都需要**经过验证的设计模式**来应对。防抖解决的是"频繁触发但只需响应一次"的问题；节流解决的是"频繁触发需要限速响应"的问题；重试解决的是"操作可能失败但值得再试"的问题；超时解决的是"等待不能无限期持续"的问题。这四大模式是每一个前端开发者工具箱中的必备利器——它们看似简单，但其背后的原理、变体和陷阱足以写满整章。

---

## 一、防抖（Debounce）—— 等用户"消停"后再行动

### 1.1 什么是防抖？

**防抖（Debounce）** 的核心思想是：**当事件被连续触发时，不要立即执行回调函数，而是等待一段"静默期"。如果在这段等待期间又触发了事件，就重新计时。只有当用户真正停下来、不再触发新的事件之后，过了指定的等待时间才执行一次回调。**

名字的来源是电子工程中的"去抖动开关"（debounce switch）：机械开关在按下或释放的瞬间会产生多次电信号的抖动（bounce），电路设计中会用一个电容来"吸收"这些抖动信号，只输出一个稳定的开关状态。

### 1.2 为什么需要防抖？

想象一个搜索框的实时搜索功能：

```javascript
// ❌ 没有防抖 —— 用户每输入一个字符就发起请求
const searchInput = document.getElementById('search');
searchInput.addEventListener('input', (e) => {
  const query = e.target.value;
  // 每输入一个字符就发送一个请求！
  fetch(`/api/search?q=${query}`)
    .then(r => r.json())
    .then(results => renderResults(results));
});
```

问题显而易见：当用户输入 "javascript" 这个词时，会依次发起 **10 个请求**（`j`, `ja`, `jav`, ... `javascript`）。不仅浪费带宽和服务器资源，而且由于网络延迟的不确定性，后发出的请求可能比先发出的更早返回，导致结果顺序错乱。

### 1.3 防抖的基本实现

```javascript
/**
 * 防抖函数
 * @param {Function} fn      需要防抖的函数
 * @param {number}   delay   等待时间（毫秒）
 * @returns {Function}       防抖后的函数
 */
function debounce(fn, delay) {
  // 使用闭包保存定时器 ID
  let timerId = null;
  
  return function(...args) {
    // 每次触发时，先清除上一次的定时器
    if (timerId) {
      clearTimeout(timerId);
    }
    
    // 设置新的定时器，delay 毫秒后才真正执行
    timerId = setTimeout(() => {
      fn.apply(this, args);  // 保持 this 指向和参数传递
    }, delay);
  };
}

// ==================== 使用示例 ====================

// 搜索框 —— 用户停止输入 300ms 后才发起搜索
const debouncedSearch = debounce((query) => {
  console.log(`🔍 发起搜索: ${query}`);
  fetch(`/api/search?q=${query}`)
    .then(r => r.json())
    .then(results => console.log('✅ 收到', results.length, '条结果'));
}, 300);

searchInput.addEventListener('input', (e) => {
  debouncedSearch(e.target.value);
});

// 窗口 resize —— 用户停止调整大小后才重新计算布局
const debouncedResize = debounce(() => {
  console.log(`窗口尺寸: ${window.innerWidth}x${window.innerHeight}`);
  recalculateLayout();
}, 200);

window.addEventListener('resize', debouncedResize);

// 按钮 click 防重复提交 —— 快速连击只处理最后一次
const submitBtn = document.getElementById('submit');
const debouncedSubmit = debounce((event) => {
  event.preventDefault();
  console.log('💾 提交表单...');
  submitForm();
}, 500);

submitBtn.addEventListener('click', debouncedSubmit);
```

### 1.4 防抖的执行时序图

```
用户输入:  j  a  v  a  s  c  r  i  p  t
时间轴:  |  |  |  |  |  |  |  |  |  |  |
           ↓  ↓  ↓  ↓  ↓  ↓  ↓  ↓  ↓  ↓
         [清除][清除]...[清除]     [等待300ms] → ✅ 执行!

每次按键都清除前一个定时器并重新设置。
只有最后一次按键后的 300ms 内没有新按键，
定时器才会到期，最终执行回调。
```

### 1.5 立即执行版防抖（Leading Edge）

上面的实现是**尾部防抖（trailing edge）**：等待期结束才执行。还有一种变体是**首部防抖（leading edge / immediate）**：第一次触发时立即执行，然后在等待期内忽略后续触发：

```javascript
/**
 * 支持立即执行的防抖函数
 * @param {Function}  fn        需要防抖的函数
 * @param {number}    delay     等待时间
 * @param {boolean}   immediate 是否首次立即执行
 */
function debounce(fn, delay, immediate = false) {
  let timerId = null;
  
  return function(...args) {
    const callNow = immediate && !timerId;
    
    if (timerId) clearTimeout(timerId);
    
    if (callNow) {
      fn.apply(this, args);
    }
    
    timerId = setTimeout(() => {
      timerId = null;  // 重置，使下次 leading 可以生效
      if (!immediate) {
        fn.apply(this, args);
      }
    }, delay);
  };
}

// 对比两种模式的区别:

// trailing 模式（默认）—— "等用户打完字再搜"
const trailingSearch = debounce(performSearch, 500);
// 输入: a---b---c---d（每个间隔200ms）
// 执行:                     performSearch("abcd")

// immediate 模式 —— "用户一开始输入就立刻搜"
const leadingSearch = debounce(performSearch, 500, true);
// 输入: a---b---c---d（每个间隔200ms）
// 执行: performSearch("a")
// 后续的 b,c,d 都被忽略（因为还在 500ms 冷却期内）
```

**适用场景对比**：

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 搜索框实时搜索 | **Trailing** | 应该用最终的关键词搜索 |
| 按钮防止重复点击 | **Immediate + Trailing** | 第一次立即响应，后续忽略 |
| 窗口 resize 重算 | **Trailing** | 应该用最终的尺寸计算 |
| 自动保存草稿 | **Trailing** | 用最终内容保存 |
| 防止表单重复提交 | **Immediate** | 第一次就提交，后续忽略 |

### 1.6 取消防抖

有时候需要在等待期间取消即将执行的回调（比如组件卸载时）：

```javascript
function debounceWithCancel(fn, delay) {
  let timerId = null;
  
  const debounced = function(...args) {
    if (timerId) clearTimeout(timerId);
    timerId = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
  
  // 添加取消方法
  debounced.cancel = function() {
    if (timerId) {
      clearTimeout(timerId);
      timerId = null;
    }
  };
  
  return debounced;
}

// React 组件中使用示例:
class SearchComponent extends React.Component {
  constructor(props) {
    super(props);
    this.debouncedSearch = debounceWithCancel(
      (q) => this.props.onSearch(q), 
      300
    );
  }
  
  handleChange = (e) => {
    this.debouncedSearch(e.target.value);
  };
  
  componentWillUnmount() {
    // 组件卸载时取消防抖，避免内存泄漏和无效调用
    this.debouncedSearch.cancel();
  }
  
  render() {
    return <input onChange={this.handleChange} />;
  }
}
```

### 1.7 结果刷新版防抖（Flush）

Lodash 的 `_.debounce` 还提供了 `flush()` 方法，可以立即执行当前挂起的调用：

```javascript
function debounceWithFlush(fn, delay) {
  let timerId = null;
  let lastArgs = null;
  let lastThis = null;
  
  const debounced = function(...args) {
    lastArgs = args;
    lastThis = this;
    
    if (timerId) clearTimeout(timerId);
    
    timerId = setTimeout(() => {
      timerId = null;
      fn.apply(lastThis, lastArgs);
    }, delay);
  };
  
  // 强制立即执行当前挂起的调用
  debounced.flush = function() {
    if (timerId !== null) {
      clearTimeout(timerId);
      timerId = null;
      fn.apply(lastThis, lastArgs);
    }
  };
  
  return debounced;
}

// 场景: 用户正在输入搜索关键词，
// 但突然按下了回车键 —— 此时应该立即执行搜索
const smartSearch = debounceWithFlush(performSearch, 300);

searchInput.addEventListener('input', (e) => smartSearch(e.target.value));
searchInput.addEventListener('keydown', (e) => {
  if (e.key === 'Enter') {
    e.preventDefault();
    smartSearch.flush();  // 回车时不等待，立即搜索！
  }
});
```

### 1.8 通俗类比：电梯门 vs 公交车关门

**防抖 = 电梯门的关闭机制**：
- 有人按了关门键（触发事件），但门不会立刻关上
- 如果又有人进来或者按了开门键（再次触发），关门倒计时**重新开始**
- 只有当所有人都安静下来、没有人再进出时，门才开始关闭
- 最终只发生**一次**关门动作（执行一次回调）

这就是为什么叫"防抖"——就像消除电信号的抖动一样，把连续的多次触发"压缩"成一次稳定的输出。

## 二、节流（Throttle）—— 有节奏地响应，不快也不慢

### 2.1 什么是节流？

**节流（Throttle）** 的核心思想是：**无论事件触发多么频繁，回调函数都按照固定的时间间隔规律地执行。** 就像水龙头的水流——不管上游压力多大，出口的水流速度都是恒定的。

与防抖不同：防抖是把多次触发合并为**一次**执行；节流是把多次触发均匀地分散为**多次**执行（只是限制了频率）。

### 2.2 为什么需要节流？

想象一个页面滚动时的动画效果：

```javascript
// ❌ 没有节流 —— 浏览器一秒可能触发 60+ 次 scroll 事件！
window.addEventListener('scroll', () => {
  const scrollTop = window.pageYOffset;
  updateParallaxBackground(scrollTop);  // 每次滚动都更新背景位置
  updateProgressBar(scrollTop);        // 更新进度条
  lazyLoadImages(scrollTop);            // 懒加载图片
  trackReadingProgress(scrollTop);       // 上报阅读进度
});

// 问题：现代显示器刷新率 60Hz~144Hz，
// 意味着每秒可能触发 60~144 次 scroll 回调！
// 大量的 DOM 操作和计算会导致页面卡顿、掉帧。
```

### 2.3 时间戳版本（Timestamp-based Throttle）

这是最常见的节流实现方式，使用两个时间戳来判断是否到了执行时机：

```javascript
/**
 * 节流函数（时间戳版本）
 * @param {Function} fn      需要节流的函数
 * @param {number}   interval 最小执行间隔（毫秒）
 * @returns {Function}       节流后的函数
 */
function throttle(fn, interval) {
  let lastTime = 0;  // 上次执行的时间戳
  
  return function(...args) {
    const now = Date.now();  // 当前时间
    
    // 如果距离上次执行已经超过了 interval，就执行
    if (now - lastTime >= interval) {
      lastTime = now;  // 更新上次执行时间
      fn.apply(this, args);
    }
    // 否则，忽略本次触发（静默丢弃）
  };
}
```

**执行时序图**：

```
scroll 事件: ● ● ● ● ● ● ● ● ● ● ● ● （非常密集）
时间(ms):   0 20 40 60 80 100 120 140 160 180 200

节流(interval=100ms):
             ↓                    ↓
           执行!               执行!
           
第0ms: 触发，距离上次>=100ms → 执行 ✓
第20ms: 触发，距离上次<100ms  → 忽略 ✗
第40ms: 触发，距离上次<100ms  → 忽略 ✗
...
第100ms: 触发，距离上次=100ms → 执行 ✓
```

### 2.4 定时器版本（Timer-based Throttle）

另一种实现使用 `setTimeout` 来控制执行节奏：

```javascript
/**
 * 节流函数（定时器版本）
 * 特点: 保证第一次触发一定执行，后续按固定间隔执行
 */
function throttleTimer(fn, interval) {
  let canRun = true;  // 锁标志
  
  return function(...args) {
    if (!canRun) return;  // 正在冷却中，直接返回
    
    canRun = false;  // 上锁
    
    fn.apply(this, args);  // 先执行
    
    setTimeout(() => {
      canRun = true;  // interval 毫秒后解锁
    }, interval);
  };
}
```

### 2.5 两种版本的细微差异

```javascript
// 对比两种实现的边界行为:

const throttledA = throttle(fn, 100);      // 时间戳版
const throttledB = throttleTimer(fn, 100);   // 定时器版

// 场景1: 连续密集触发，然后突然停止
// 时间戳版: 最后一个间隔内的触发会被完全丢失
// 定时器版: 最后一次执行后会有一个延迟锁定期

// 场景2: 第一次触发
// 时间戳版: 立即执行 ✓
// 定时器版: 也立即执行 ✓

// 场景3: 最后一次触发（停止后是否补执行？）
// 时间戳版: 不补执行（最后一次触发如果在间隔内就被忽略了）
// 定时器版: 也不补执行（两者在这个场景下行为类似）
```

### 2.6 更完善的实现（结合两者优势）

```javascript
/**
 * 完善版节流函数
 * 支持:
 *   - leading: 是否允许首次立即执行
 *   - trailing: 是否在结束后执行最后一次
 *   - cancel(): 取消
 */
function advancedThrottle(fn, interval, options = {}) {
  const { leading = true, trailing = true } = options;
  
  let lastTime = 0;
  let timerId = null;
  let lastArgs = null;
  let lastThis = null;
  
  const throttled = function(...args) {
    const now = Date.now();
    
    // 计算距离上次执行经过了多久
    const elapsed = now - lastTime;
    
    // 首次执行且允许 leading
    if (elapsed >= interval) {
      if (leading) {
        executeCall(args);
      } else if (trailing) {
        scheduleTrailing(args);
      }
    } else if (trailing) {
      // 在冷却期内，如果允许 trailing，则安排末尾执行
      lastArgs = args;
      lastThis = this;
      
      if (!timerId) {
        timerId = setTimeout(() => {
          timerId = null;
          if (lastArgs) {
            executeCall(lastArgs);
            lastArgs = null;
          }
        }, elapsed > 0 ? interval - elapsed : interval);
      } else {
        // 已经有待执行的定时器，更新参数
      }
    }
  };
  
  function executeCall(args) {
    lastTime = Date.now();
    fn.apply(this, args);
  }
  
  function scheduleTrailing(args) {
    lastArgs = args;
    lastThis = this;
    
    if (!timerId) {
      timerId = setTimeout(() => {
        timerId = null;
        executeCall(lastArgs);
        lastArgs = null;
      }, interval);
    }
  }
  
  throttled.cancel = function() {
    if (timerId) {
      clearTimeout(timerId);
      timerId = null;
    }
    lastArgs = null;
    lastTime = 0;
  };
  
  return throttled;
}
```

### 2.7 实际应用场景

#### 场景1：滚动事件的性能优化

```javascript
// 页面滚动时的高频事件优化
const throttledScrollHandler = throttle((scrollTop) => {
  // 这些操作不需要每次 scroll 都做
  requestAnimationFrame(() => {
    updateNavbarStyle(scrollTop);     // 导航栏样式变化
    updateActiveSection(scrollTop);   // 高亮当前章节
    saveScrollPosition(scrollTop);     // 保存阅读位置到 localStorage
  });
}, 100);  // 每 100ms 最多执行一次

window.addEventListener('scroll', () => {
  throttledScrollHandler(window.pageYOffset);
});
```

#### 场景2：鼠标移动追踪

```javascript
// 绘制画布应用 —— 鼠标移动时绘制轨迹
const canvas = document.getElementById('canvas');
const ctx = canvas.getContext('2d');

const throttledDraw = throttle((x, y) => {
  ctx.lineTo(x, y);
  ctx.stroke();
}, 16);  // 约 60fps (1000/16 ≈ 62)

canvas.addEventListener('mousemove', (e) => {
  const rect = canvas.getBoundingClientRect();
  const x = e.clientX - rect.left;
  const y = e.clientY - rect.top;
  ctx.beginPath();

```

```javascript
// 点赞按钮 —— 限制每秒最多点赞 1 次
const likeBtn = document.getElementById('like-btn');

const throttledLike = throttle(async () => {
  likeBtn.disabled = true;  // 防止并发
  
  await fetch('/api/like', { method: 'POST' })
    .then(r => r.json())
    .then(data => {
```

#### 场景4：自动保存（带节流的防抖混合策略）

```javascript
// 编辑器的智能自动保存:
// - 输入过程中每 2 秒保存一次（throttle）
// - 停止编辑后也确保最后内容被保存（debounce flush）
class AutoSaver {
  constructor(saveFn, throttleInterval = 2000) {
    this.saveFn = saveFn;
    this.lastSaveContent = '';
    this.throttledSave = throttle(() => this.performSave(), throttleInterval);
    this.debounceSave = debounce(() => this.performSave(), 1000);
  }
  
  onContentChange(content) {
    this.lastSaveContent = content;
    this.throttledSave(content);   // 节流保存（保证频率上限）
  }
  
  onEditorBlur() {
    this.throttledSave.cancel();
    this.debounceSave(this.lastSaveContent);  // 失焦时确保保存
  }
  
  async performSave() {
    console.log('💾 自动保存...', new Date().toLocaleTimeString());
    await this.saveFn(this.lastSaveContent);
  }
}

const saver = new AutoSaver(async (content) => {
  await fetch('/api/save', {
    method: 'POST',
    body: JSON.stringify({ content }),
    headers: { 'Content-Type': 'application/json' }
  });
});

editor.on('change', (content) => saver.onContentChange(content));
editor.on('blur', () => saver.onEditorBlur());
```

### 2.8 通俗类比：公交车 vs 出租车

**节流 = 公交车的固定班次时刻表**：
- 不管站台上挤了多少乘客（事件触发多频繁），公交车每隔 **10 分钟**准时发一班
- 提早到的乘客（提前触发的事件）要等到下一班车
- 迟到的乘客（错过本次触发的事件）也要等下一班
- 关键是**有规律的、可预期的**执行节奏，而不是像防抖那样"等人齐了再走"

## 三、重试（Retry）—— 失败了不要紧，再试一次

### 3.1 为什么需要重试？

在分布式系统中，**失败是常态而非异常**。网络超时、临时性服务过载、DNS 解析瞬态失败……这些错误往往不需要人工干预，简单地重试几次就能成功。重试模式就是将这种"失败了再试"的策略标准化、自动化。

**理论依据**：很多分布式系统的故障模型符合**指数衰减**特征——大多数瞬态错误会在短时间内自行恢复。因此，合理的重试策略能大幅提升系统的整体成功率。

### 3.2 基础重试实现

```javascript
/**
 * 带固定次数的重试函数
 * @param {Function} fn       可能失败的异步操作（应返回 Promise）
 * @param {number}   retries  最大重试次数
 * @returns {Promise}          操作成功的结果或最后的错误
 */
async function retry(fn, retries = 3) {
  let lastError;
  
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn();  // 尝试执行
    } catch (error) {
      lastError = error;
      console.warn(`⚠️ 第 ${attempt + 1}/${retries + 1} 次尝试失败: ${error.message}`);
    }
  }
  
  // 所有尝试都失败了，抛出最后一个错误
  throw lastError;
}

// ==================== 使用示例 ====================

async function fetchData(url) {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

retry(() => fetchData('/api/users'), 3)
  .then(data => console.log('✅ 成功:', data))
  .catch(err => console.error('❌ 最终失败:', err.message));
```

### 3.3 指数退避重试（Exponential Backoff）

这是工业界最广泛使用的重试策略。核心思想是：**每次重试之间的等待时间逐渐增加**（通常是指数增长），给系统更多恢复时间，同时避免雪崩效应（大量客户端同时重试导致系统进一步过载）。

```javascript
/**
 * 带指数退避的重试函数
 * @param {Function}  fn              异步操作
 * @param {Object}    options         配置选项
 * @param {number}    options.retries 最大重试次数（默认3）
 * @param {number}    options.baseDelay 初始延迟毫秒数（默认200）
 * @param {number}    options.maxDelay 最大延迟毫秒数（默认5000）
 * @param {Function}  options.shouldRetry 自定义判断是否应该重试
 */
async function retryWithBackoff(fn, options = {}) {
  const {
    retries = 3,
    baseDelay = 200,
    maxDelay = 5000,
    shouldRetry = (err) => true  // 默认所有错误都重试
  } = options;
  
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      // 检查是否应该继续重试
      const isLastAttempt = attempt === retries;
      
      if (isLastAttempt || !shouldRetry(error)) {
        throw error;  // 最后一次或不应重试，直接抛出
      }
      
      // 计算延迟时间: baseDelay * 2^attempt（指数增长）
      const delay = Math.min(baseDelay * Math.pow(2, attempt), maxDelay);
      
      console.warn(
        `⚠️ 第 ${attempt + 1} 次失败 (${error.message})，${delay}ms 后重试...`
      );
      
      // 等待指定时间后重试
      await sleep(delay);
    }
  }
}

// 工具函数: sleep
function sleep(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

// ==================== 使用示例 ====================

// 只对网络类错误进行重试
await retryWithBackoff(
  () => fetch('/api/data').then(r => r.json()),
  {
    retries: 4,
    baseDelay: 300,
    shouldRetry: (err) => {
      // 4xx 客户端错误通常不应该重试（改参数也没用）
      if (err.message.includes('400') || err.message.includes('404')) {
        return false;
      }
      // 5xx 服务端错误和网络错误应该重试
      return true;
    }
  }
);
```

**指数退避的时序示意**：

```
尝试1: 失败 → 等 200ms (baseDelay × 2^0)
尝试2: 失败 → 等 400ms (baseDelay × 2^1)
尝试3: 失败 → 等 800ms (baseDelay × 2^2)
尝试4: 失败 → 等 1600ms (baseDelay × 2^3)
...

总等待时间: 200 + 400 + 800 + 1600 = 3000ms（约3秒）
相比固定等待（如每次都等1秒），总等待时间更短且更合理
```

### 3.4 抖动（Jitter）

在分布式系统中，如果所有客户端都采用相同的退避时间，可能出现"惊群效应"——大量客户端在同一时刻重试，造成新的拥塞峰值。**抖动（Jitter）** 是通过在退避时间中加入随机偏移量来解决这个问题的技术：

```javascript
/**
 * 带抖动的指数退避重试
 */
async function retryWithJitter(fn, options = {}) {
  const {
    retries = 3,
    baseDelay = 200,
    maxDelay = 5000
  } = options;
  
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt === retries) throw error;
      
      // 指数退避
      const exponentialDelay = baseDelay * Math.pow(2, attempt);
      // 加入随机抖动: ±25% 的随机偏移
      const jitter = exponentialDelay * (0.75 + Math.random() * 0.5);
      const delay = Math.min(jitter, maxDelay);
      
      console.warn(`⚠️ 第 ${attempt + 1} 次，等待 ${Math.round(delay)}ms`);
      await sleep(delay);
    }
  }
}
```

**抖动的价值**：

```
没有抖动（10个客户端同时重试）:
时间轴:  |----200ms----|----400ms----|----800ms----|
         [10个请求同时到达] [10个请求同时到达] ...

有抖动（10个客户端同时重试）:
时间轴:  |--180ms--|--350ms|--720ms|--950ms|--210ms|--430ms|...
         [请求分布在不同时刻] [负载平滑]
```

### 3.5 断路器模式（Circuit Breaker）

当服务持续失败时，盲目重试只会浪费资源。断路器模式在重试的基础上增加了一个**熔断机制**：如果失败率超过阈值，就直接拒绝后续请求（快速失败），而不是反复重试。

```javascript
/**
 * 简易断路器实现
 */
class CircuitBreaker {
  constructor(fn, options = {}) {
    this.fn = fn;
    this.failureThreshold = options.failureThreshold || 5;  // 连续失败多少次后熔断
    this.resetTimeout = options.resetTimeout || 30000;     // 熔断后多久尝试恢复（毫秒）
    this.halfOpenMaxAttempts = 1;                           // 半开状态允许的最大尝试数
    
    this.state = 'CLOSED';    // CLOSED(正常) / OPEN(熔断) / HALF_OPEN(半开)
    this.failureCount = 0;
    this.nextAttemptTime = 0;
  }
  
  async execute(...args) {
    // 检查是否处于熔断状态
    if (this.state === 'OPEN') {
      if (Date.now() >= this.nextAttemptTime) {
        this.state = 'HALF_OPEN';  // 进入半开状态，允许试探性请求
        console.log('🔄 断路器进入半开状态，允许试探性请求...');
      } else {
        throw new Error('⛔ 断路器已开启，请求被拒绝（服务可能不可用）');
      }
    }
    
    try {
      const result = await this.fn(...args);
      
      // 成功了！
      if (this.state === 'HALF_OPEN') {
        console.log('✅ 半开状态下请求成功，恢复正常');
        this.state = 'CLOSED';
      }
      this.failureCount = 0;
      return result;
      
    } catch (error) {
      this.failureCount++;
      
      if (this.state === 'HALF_OPEN') {
        console.log('❌ 半开状态下请求失败，重新开启断路器');
        this.state = 'OPEN';
        this.nextAttemptTime = Date.now() + this.resetTimeout;
        throw error;
      }
      
      if (this.failureCount >= this.failureThreshold) {
        console.warn(
          `⚠️ 连续失败 ${this.failureCount} 次，开启断路器 ${this.resetTimeout/1000}s`
        );
        this.state = 'OPEN';
        this.nextAttemptTime = Date.now() + this.resetTimeout;
      }
      
      throw error;
    }
  }
}

// ==================== 使用示例 ====================

const apiBreaker = new CircuitBreaker(
  () => fetch('/api/expensive-operation').then(r => r.json()),
  { failureThreshold: 3, resetTimeout: 15000 }
);

// 正常使用 —— 断路器内部管理重试逻辑
try {
  const data = await apiBreaker.execute();
  console.log('数据:', data);
} catch (err) {
  if (err.message.includes('断路器')) {
    showFallbackUI();  // 显示降级 UI
  } else {
    showError(err);
  }
}
```

### 3.6 通俗类比：打电话 vs 门铃

**重试 = 打电话没人接时的应对策略**：
- 你拨了一个电话号码，对方没接（第一次失败）
- 你等一会儿再打（重试 + 固定延迟）
- 还是没接，你等更长时间再打（**指数退避**：也许对方在忙别的事）
- 为了不打扰别人太频繁，你在等待时间中加入一些**随机性**（**抖动**）
- 如果你打了 5 次都没人接，你可能决定今天不再打了（**断路器**：暂时放弃，明天再说）

这种从"坚持"到"放弃"的渐进式策略，正是重试模式的核心智慧。

## 四、超时（Timeout）—— 别让我无限等待下去

### 4.1 为什么需要超时？

在异步操作中，最令人焦虑的情况之一就是**无限期的等待**。网络请求可能因为服务端死锁而永远不响应；数据库查询可能因为锁竞争而一直阻塞；WebSocket 连接可能因为网络中断而既不断开也不发数据。如果没有超时机制，整个程序可能会陷入一种"僵尸态"——不死也不活。

**理论要点**：超时本质上是一种**资源保护策略**。它承认了分布式系统中"不确定性"的存在，并为每种操作设置了合理的时间边界。超过这个边界就意味着"情况不对劲"，应该采取行动（取消、降级、报错）而不是继续空等。

### 4.2 Promise.race 实现超时

最基本的超时模式利用 `Promise.race` 将原 Promise 与一个定时器 Promise 竞争：

```javascript
/**
 * 为 Promise 添加超时
 * @param {Promise} promise 需要设置超时的 Promise
 * @param {number}   ms      超时时间（毫秒）
 * @param {string}   message 超时错误信息
 * @returns {Promise}         原始结果或超时错误
 */
function withTimeout(promise, ms, message = 'Operation timed out') {
  // 创建一个会在 ms 毫秒后 reject 的 Promise
  const timeoutPromise = new Promise((_, reject) => {
    setTimeout(() => reject(new Error(message)), ms);
  });
  
  // 让原始 Promise 和超时 Promise 竞赛
  // 谁先 resolve/reject，结果就是谁
  return Promise.race([promise, timeoutPromise]);
}

// ==================== 使用示例 ====================

// 示例1: API 请求超时
try {
  const data = await withTimeout(
    fetch('/api/slow-endpoint').then(r => r.json()),
    5000,  // 5 秒超时
    'API 请求超过 5 秒未响应'
  );
  console.log('收到数据:', data);
} catch (error) {
  if (error.message.includes('timed out')) {
    console.error('⏰ 请求超时，显示缓存数据或提示用户');
    showCachedData();
  } else {
    console.error('其他错误:', error.message);
  }
}

// 示例2: 数据库查询超时
async function queryWithTimeout(sql, timeoutMs = 3000) {
  return withTimeout(
    database.query(sql),
    timeoutMs,
    `数据库查询超过 ${timeoutMs}ms 未完成`
  );
}
```

**`Promise.race` 的工作原理**：

```
时间轴:
  ┌─ 原始 Promise ───────────────────────┐
  │                                      │ resolved (成功)
  └──────────────────────────────────────┘
  
  ┌─ 超时 Promise ───────┐
  │                      │ rejected (超时!)
  └──────────────────────┘

  ┌─ Promise.race 结果 ─┐
  │  取决于谁先完成      │ ← 超时 Promise 先完成了！
  └─────────────────────┘  所以结果是超时错误
```

### 4.3 AbortController 方案（推荐）

现代浏览器和 Node.js（v15+）支持 `AbortController`，这是更优雅的超时（和取消）方案：

```javascript
/**
 * 使用 AbortController 实现可取消的超时
 */
function withAbortTimeout(promise, ms, signal) {
  // 如果外部没提供 signal，创建内部的
  const controller = new AbortController();
  const targetSignal = signal || controller.signal;
  
  // 设置超时自动 abort
  const timer = setTimeout(() => controller.abort(), ms);
  
  // 包装 promise 以支持 abort
  const wrappedPromise = new Promise((resolve, reject) => {
    targetSignal.addEventListener('abort', () => {
      clearTimeout(timer);
      reject(new DOMException(`Aborted after ${ms}ms`, 'AbortError'));
    });
    
    promise.then(resolve).catch(reject);
  });
  
  return wrappedPromise.finally(() => clearTimeout(timer));
}

// ==================== 使用示例 ====================

// 配合 fetch 使用（fetch 原生支持 AbortSignal!）
async function fetchWithTimeout(url, options = {}, timeoutMs = 5000) {
  const controller = new AbortController();
  
  const timer = setTimeout(() => controller.abort(), timeoutMs);
  
  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal  // 将 abort 信号传给 fetch
    });
    
    clearTimeout(timer);
    return response;
    
  } catch (error) {
    clearTimeout(timer);
    
    if (error.name === 'AbortError') {
      throw new Error(`请求在 ${timeoutMs}ms 内未完成`);
    }
    throw error;
  }
}

// 使用
try {
  const data = await fetchWithTimeout('/api/heavy-computation', {}, 10000);
  console.log(data);
} catch (error) {
  if (error.name === 'AbortError' || error.message.includes('未完成')) {
    console.error('⏰ 请求超时');
  }
}
```

**AbortController 相比 Promise.race 的优势**：

| 特性 | Promise.race | AbortController |
|------|-------------|----------------|
| 超时时能否真正取消请求 | ❌ 不能（请求仍在后台运行） | **✅ 能**（实际终止 HTTP 连接） |
| 可否手动提前取消 | ❌ 不能 | **✅ 可以**（随时调用 `controller.abort()`） |
| 是否支持级联取消 | ❌ | **✅**（signal 可传递给子操作） |
| 错误类型区分 | 普通 Error | 专门的 **AbortError** |
| 浏览器兼容性 | 所有浏览器 | 现代浏览器均支持 |

### 4.4 组合模式：超时 + 重试

超时和重试常常配合使用：每次尝试都有独立的超时限制，而总体又有最大尝试次数：

```javascript
/**
 * 带超时的重试函数
 * 每次尝试都有独立超时，总共最多重试 N 次
 */
async function retryWithTimeout(fn, options = {}) {
  const {
    retries = 3,
    timeoutMs = 5000,
    baseDelay = 200,
    shouldRetry = () => true
  } = options;
  
  let lastError;
  
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      // 每次尝试都加上超时保护
      return await withTimeout(fn(), timeoutMs, 
        `第 ${attempt + 1} 次尝试超时 (${timeoutMs}ms)`
      );
    } catch (error) {
      lastError = error;
      const isLast = attempt === retries;
      
      if (isLast || !shouldRetry(error)) throw error;
      
      // 指数退避等待
      const delay = Math.min(baseDelay * Math.pow(2, attempt), 5000);
      console.warn(`${error.message}，${delay}ms 后重试...`);
      await sleep(delay);
    }
  }
  
  throw lastError;
}

// ==================== 使用示例 ====================

async function robustApiCall(endpoint) {
  return retryWithTimeout(
    () => fetch(endpoint).then(r => {
      if (!r.ok) throw new Error(`HTTP ${r.status}`);
      return r.json();
    }),
    {
      retries: 4,       // 最多尝试 5 次（初始 + 4 次重试）
      timeoutMs: 3000,  // 每次尝试 3 秒超时
      baseDelay: 300,   // 初始退避 300ms
      shouldRetry: (err) => !err.message.includes('400')
    }
  );
}

robustApiCall('/api/critical-data')
  .then(data => console.log('✅', data))
  .catch(err => console.error('❌ 最终失败:', err.message));
```

### 4.5 并发请求的整体超时

有时候需要对一组并发请求设置整体超时（而不是单个请求的超时）：

```javascript
/**
 * 并发请求的整体超时
 * 无论单个请求如何，所有请求必须在 totalTimeout 内全部完成
 */
async function allWithTimeout(promises, totalTimeoutMs) {
  // 整体超时 Promise
  const timeoutPromise = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('整体操作超时')), totalTimeoutMs)
  );
  
  try {
    // 等待所有 Promise 完成 或 超时
    const results = await Promise.race([
      Promise.allSettled(promises),  // 即使部分失败也继续
      timeoutPromise
    ]);
    
    return results;
    
  } catch (error) {
    if (error.message.includes('整体操作超时')) {
      // 超时时，记录已完成的部分结果
      const settled = await Promise.allSettled(
        promises.map(p => p.catch(e => ({ error: e.message })))
      );
      
      const succeeded = settled.filter(s => s.status === 'fulfilled').length;
      const failed = settled.filter(s => s.status === 'rejected').length;
      
      console.warn(`⏰ 整体超时: 已完成 ${succeeded}/${promises.length}, 失败 ${failed}`);
      
      // 可以选择返回部分结果或抛出错误
      throw error;
    }
    throw error;
  }
}

// 使用: 并行获取多个数据源，但最多等 5 秒
const sources = [
  fetch('/api/source-a'),
  fetch('/api/source-b'), 
  fetch('/api/source-c'),
  fetch('/api/source-d')
];

const results = await allWithTimeout(sources, 5000);
```

### 4.6 Node.js 特有超时方案

Node.js 中还有一些特有的超时技巧：

```javascript
// Node.js: socket/connect 超时
const net = require('net');

function connectWithTimeout(host, port, timeoutMs = 5000) {
  return new Promise((resolve, reject) => {
    const socket = net.createConnection({ host, port }, () => resolve(socket));
    
    // connect 超时
    socket.setTimeout(timeoutMs);
    socket.on('timeout', () => {
      socket.destroy();
      reject(new Error(`连接 ${host}:${port} 超时 (${timeoutMs}ms)`));
    });
    
    socket.on('error', reject);
  });
}

// Node.js: child_process 超时
const { exec } = require('child_process');

function execWithTimeout(command, timeoutMs = 10000) {
  return new Promise((resolve, reject) => {
    const child = exec(command, (error, stdout, stderr) => {
      if (error) reject(error);
      else resolve(stdout.trim());
    });
    
    // 进程级别的超时 kill
    const timer = setTimeout(() => {
      child.kill('SIGTERM');  // 先温和终止
      setTimeout(() => child.kill('SIGKILL'), 2000);  // 强制杀死
      reject(new Error(`命令执行超时 (${timeoutMs}ms): ${command}`));
    }, timeoutMs);
    
    child.on('close', () => clearTimeout(timer));
  });
}
```

### 4.7 通俗类比：约会守时规则

**超时 = 约会的守时规则**：
- 你约朋友下午 3 点见面（发起异步操作）
- 你设定了一个底线：如果 3 点 15 分还没出现，你就走了（设置超时）
- 这不是你不耐心，而是你需要为后续计划预留时间（**资源保护**）
- 如果你的朋友经常迟到，你可以给他更多机会（**重试**），但每次还是要有时间底线
- 如果他连续放了 5 次鸽子，你可能决定这段时间不再约他了（**断路器**）

这套从"耐心等待"到"果断放弃"的完整策略，正是超时模式在日常生活中的体现。

## 五、四大模式的组合实战

### 5.1 一个健壮的网络请求函数

让我们把四种模式组合起来，构建一个**生产级别**的网络请求封装：

```javascript
/**
 * 生产级的健壮请求函数
 * 结合了: 超时 + 重试(指数退避+抖动) + 防抖(防止重复请求)
 */
function createRobustRequest(defaultOptions = {}) {
  const pendingRequests = new Map();  // 用于防重复
  
  return async function robustRequest(url, options = {}) {
    const {
      timeout = 8000,           // 单次请求超时
      retries = 3,              // 重试次数
      baseDelay = 300,          // 退避基础延迟
      dedupeKey = null,         // 去重键（相同 key 的请求会合并）
      ...requestOptions
    } = { ...defaultOptions, ...options };
    
    // ===== 防抖/去重: 相同的请求只发一个 =====
    if (dedupeKey) {
      if (pendingRequests.has(dedupeKey)) {
        console.log(`♻️ 复用已有请求: ${dedupeKey}`);
        return pendingRequests.get(dupeKey);
      }
      
      const promise = _doRobustRequest(url, requestOptions, { timeout, retries, baseDelay })
        .finally(() => pendingRequests.delete(dedupeKey));
      
      pendingRequests.set(dedupeKey, promise);
      return promise;
    }
    
    return _doRobustRequest(url, requestOptions, { timeout, retries, baseDelay });
  };
  
  /**
   * 核心请求逻辑（含超时和重试）
   */
  async function _doRobustRequest(url, opts, { timeout, retries, baseDelay }) {
    let lastError;
    
    for (let attempt = 0; attempt <= retries; attempt++) {
      try {
        // ===== 超时保护 =====
        const controller = new AbortController();
        const timer = setTimeout(() => controller.abort(), timeout);
        
        const response = await fetch(url, {
          ...opts,
          signal: controller.signal
        });
        
        clearTimeout(timer);
        
        if (!response.ok) {
          // 根据状态码决定是否重试
          if (response.status >= 400 && response.status < 500) {
            throw new Error(`客户端错误 ${response.status}: 不应重试`);
          }
          throw new Error(`服务端错误 ${response.status}`);
        }
        
        console.log(`✅ 请求成功 (第 ${attempt + 1} 次)`);
        return await response.json();
        
      } catch (error) {
        clearTimeout(timer);
        lastError = error;
        
        const isLast = attempt === retries;
        
        // AbortError 不重试
        if (error.name === 'AbortError') {
          throw new Error(`请求超时 (${timeout}ms)`);
        }
        
        // 4xx 不重试
        if (error.message.includes('客户端错误')) {
          throw error;
        }
        
        if (isLast) {
          console.error(`❌ 全部 ${retries + 1} 次尝试均失败`);
          throw error;
        }
        
        // ===== 指数退避 + 抖动 =====
        const exponentialDelay = baseDelay * Math.pow(2, attempt);
        const jitter = exponentialDelay * (0.75 + Math.random() * 0.5);
        const finalDelay = Math.min(jitter, 5000);
        
        console.warn(
          `⚠️ 第 ${attempt + 1} 次失败: ${error.message}，${Math.round(finalDelay)}ms 后重试`
        );
        
        await new Promise(r => setTimeout(r, finalDelay));
      }
    }
    
    throw lastError;
  }
}

// ==================== 使用示例 ====================

const api = createRobustRequest({
  headers: { 'Authorization': 'Bearer token123' }
});

// 场景1: 普通请求（自动获得超时+重试能力）
const users = await api('/api/users');

// 场景2: 带去重的请求（快速连击只发一次）
button.addEventListener('click', async () => {
  button.disabled = true;

  } catch (error) {
    showToast(`操作失败: ${error.message}`);
  } finally {

  }

  timeout: 15000,   // 这个慢接口给更长超时
  retries: 5,       // 允许更多重试
  baseDelay: 500    // 更长的退避间隔
});
```

### 5.2 模式选择决策树

```
遇到异步问题时，如何选择合适的模式？

你的问题是关于"频率控制"吗？
├── 是 → 事件触发很频繁？
│   ├── 只需响应最后一次？→ 🎯 防抖 (Debounce)
│   │   搜索框、窗口resize、自动保存
│   │
│   └── 需要持续响应但限速？→ 🎯 节流 (Throttle)
│       滚动事件、鼠标追踪、按钮限速
│
└── 否 → 关于"可靠性"的问题？
    ├── 操作可能失败？→ 🎯 重试 (Retry)
    │   网络请求、数据库操作、第三方 API
    │
    ├── 操作可能卡住？→ 🎯 超时 (Timeout)
    │   任何 I/O 操作都应该有超时
    │
    └── 以上都有？→ 🎯 组合使用！
        超时 + 重试 + 防抖/节流
        构建生产级的健壮异步代码
```

### 5.3 性能影响与注意事项

#### 注意事项1: 内存泄漏风险

```javascript
// ⚠️ 危险: 事件监听器中的防抖/节流如果不清理可能导致内存泄漏
class Component {
  constructor(element) {
    this.element = element;
    // 每次 new Component 都创建新的闭包引用
    this.handler = throttle(this.handleScroll.bind(this), 100);
    window.addEventListener('scroll', this.handler);
  }
  
  destroy() {
    // ⚠️ 必须移除监听器！否则 component 实例无法被 GC
    window.removeEventListener('scroll', this.handler);
    // 同时取消挂起的定时器
    this.handler?.cancel?.();
  }
}
```

#### 注意事项2: this 指向问题

```javascript
// ⚠️ 注意箭头函数和普通函数在防抖/节流中的 this 表现不同
const obj = {
  name: 'MyObject',
  value: 42,
  
  // 箭头函数版本: this 继承自定义时的作用域
  handlerArrow: debounce(() => {
    console.log(this.name);  // 可能不是 obj！（取决于调用方式）
  }, 100),
  
  // 普通函数版本: 通过 .apply(this, args) 保持 this
  handlerNormal: debounce(function() {
    console.log(this.name);  // ✅ 总是 obj
  }, 100)
};
```

#### 注意事项3: React 中的正确用法

```jsx
// ⚠️ React 中常见的错误做法:
function BadComponent() {
  // ⚠️ 每次渲染都会创建新的防抖函数！
  const debouncedFn = debounce((value) => {
    api.save(value);
  }, 300);
  
  return <input onChange={(e) => debouncedFn(e.target.value)} />;
}

// ✅ 正确做法: 用 useRef 保持防抖函数的稳定引用
function GoodComponent() {
  const debouncedFnRef = useRef(null);
  
  if (!debouncedFnRef.current) {
    debouncedFnRef.current = debounce((value) => {
      api.save(value);
    }, 300);
  }
  
  // 或者使用 useCallback + useRef 组合
  const debouncedSave = useMemo(
    () => debounce((value) => api.save(value), 300),
    []  // 空依赖数组，只在首次渲染时创建
  );
  
  return <input onChange={(e) => debouncedSave(e.target.value)} />;
}
```

## 六、总结

### 6.1 四大模式速查表

| 模式 | 核心思想 | 解决的问题 | 典型场景 | 关键参数 |
|------|---------|-----------|---------|---------|
| **防抖 Debounce** | "等你消停了我再做" | 高频触发只需响应一次 | 搜索框、resize、防止重复提交 | `delay`(等待时间)、`immediate`(是否首次执行) |
| **节流 Throttle** | "不管多快，我只按这个节奏来" | 高频触发需要限速响应 | scroll、mousemove、按钮限速 | `interval`(最小间隔)、`leading/trailing` |
| **重试 Retry** | "失败了？再来！" | 操作可能临时失败 | 网络请求、数据库查询、第三方 API | `retries`(次数)、`backoff`(退避策略) |
| **超时 Timeout** | "等不了那么久" | 操作可能无限期挂起 | 任何 I/O 操作 | `ms`(超时时间)、取消机制 |

### 6.2 模式组合矩阵

```
                防抖      节流      重试      超时
              ──────  ──────  ──────  ──────
防抖           ✓        ○       ○       ○
节流           ○        ✓       ○       ○
重试           ○        ○       ✓       ✓ ★
超时           ○        ○       ✓ ★     ✓

★ = 强烈推荐的组合
○ = 可根据场景选择的组合
```

### 6.3 一句话总结

> **四大异步模式是前端工程师面对"不确定世界"的四件武器**：防抖帮你过滤噪音（用户的急躁手指），节流帮你保持节奏（系统的承载极限），重试给你第二次机会（网络的偶发抽风），超时为你守住底线（资源的有限生命）。它们单独使用时各有所长，组合起来时威力倍增——掌握它们，意味着你的代码不再是"碰运气能跑"，而是"有底气能扛"。
