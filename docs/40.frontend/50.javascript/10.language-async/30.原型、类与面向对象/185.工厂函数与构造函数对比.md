# 工厂函数与构造函数对比

## 两种对象创建范式的相遇

在 JavaScript 的世界里，当你需要创建一个新对象时，摆在面前的从来都不只有一条路。最广为人知的方式是使用**构造函数配合 `new` 操作符**——`new User()`、`new Date()`、`new Promise()`，这是从语言诞生之初就存在的经典模式。但在另一种同样流行甚至越来越受青睐的方式中，你不需要 `new`，也不需要 `this`，只需要一个普通的**函数返回一个对象**——这就是**工厂函数（Factory Function）**。

这两种方式看似都能达到"创建对象"的目的，但它们背后的设计哲学、适用场景、优缺点却截然不同。选择哪种方式，往往取决于你的具体需求、团队的技术偏好、以及对代码风格的价值取向。本章将对这两种范式进行全方位的深度对比和分析，帮助你在实际项目中做出明智的选择。

### 为什么需要对比？

很多开发者在整个职业生涯中可能只使用过其中一种方式，对另一种要么一无所知，要么存在误解。这种"单一视角"会限制你的技术视野：

- 如果你只用构造函数/`class`，你可能会错过工厂函数在**封装性**和**灵活性**方面的独特优势
- 如果你只用工厂函数，你可能会错过原型继承带来的**内存效率**和**类型标识**能力
- 如果你能同时理解并熟练运用两者，你就拥有了更丰富的工具箱，能在不同的场景中选出最优解

这就好比一个木工既会用锯子也会用刨子——虽然两者都能"处理木材"，但各有各的最佳用途。高手不是只会用一种工具的人，而是知道每种工具什么时候该出场的人。

## 工厂函数 —— 不需要 new 的对象创建者

### 什么是工厂函数？

定义非常简单：**工厂函数就是任何返回对象的普通函数**。它不需要 `new` 关键字来调用，不依赖原型链来共享方法，也不强制要求某种命名规范。它的本质就是一个函数，恰好做了"创建并返回对象"这件事。

```javascript
// 最简单的工厂函数
function createUser(name, age) {
  // 直接返回一个对象字面量
  return {
    name: name,           // 姓名：每个用户的值不同
    age: age,             // 年龄：每个用户的值不同
    greet() {            // 方法：所有用户共用同一份逻辑
      return `你好，我是 ${this.name}，今年 ${this.age} 岁`;
    },
    isAdult() {
      return this.age >= 18;
    }
  };
}

// 使用 —— 注意：没有 new！
let u1 = createUser("张三", 25);
let u2 = createUser("李四", 15);

u1.greet();           // "你好，我是 张三，今年 25 岁"
u2.greet();           // "你好，我是 李四，今年 15 岁"
console.log(u1.isAdult()); // true
console.log(u2.isAdult()); // false
```

看到这里你可能会问：这跟用对象字面量直接写 `{ name: "张三", ... }` 有什么区别？区别在于——**工厂函数把"如何创建这类对象"的逻辑封装了起来**。如果你需要创建 100 个结构相同的用户对象，每次都手写字面量不仅繁琐而且容易出错；而工厂函数让你只需写一次"模板"，然后通过传入不同参数批量生成。

### 工厂函数的理论基础

从计算机科学的角度来看，工厂函数体现了**工厂方法模式（Factory Method Pattern）**的核心思想。这个模式的目的是：**将对象的创建过程与使用过程解耦**。调用者不需要关心对象是怎么创建的（是新的？是从缓存中取的？还是经过特殊处理的？），它只关心拿到手的对象是否满足自己的需求。

工厂函数在 JavaScript 中之所以特别自然和受欢迎，是因为 JavaScript 的**一等函数（First-Class Function）**特性——函数可以像值一样被传递、存储、返回。这意味着工厂函数可以被赋给变量、作为参数传给其他函数、从其他函数中返回、甚至动态生成。这种灵活性是许多静态类型语言所不具备的。

从内存模型的角度来看，工厂函数创建的每个对象都是**完全独立的个体**。每个对象都有自己的属性副本（包括方法）。这意味着如果工厂函数内部定义了方法，那么每创建一个实例，就会在内存中新产生一份该方法的拷贝。对于少量对象来说这不是问题，但如果需要创建成千上万个实例，就需要考虑内存效率了（后面我们会详细讨论这一点）。

### 通俗类比：定制礼品店 vs 流水线工厂

让我们用一个生活化的场景来建立对工厂函数的直觉：

想象有一家**定制礼品包装店（Factory Function）**。顾客走进店里，告诉店员："我要一份礼物，收件人是张三，主题是生日。"店员根据这些要求，现场为你打包一份独一无二的礼物——挑选合适的包装纸、写上个性化的贺卡、系上漂亮的丝带。每一份礼物都是根据顾客的要求**当场定制**出来的，彼此之间可能完全不同，也可能有相似之处（都用同样的包装纸品牌）。

这家店的运作方式就是**工厂函数**：
- 顾客 = 调用者（调用 `createUser()`）
- 顾客的需求 = 传入的参数（`name`, `age`）
- 店员的打包工作 = 函数体内部的逻辑
- 打包好的礼物 = 返回的对象

注意几个关键特征：**顾客不需要自己动手包礼物**（不需要 `new`），**不需要了解打包的具体流程**（不需要理解 `this` 和原型链），**每份礼物都是独立定制的**（每个返回的对象都是独立的）。

## 构造函数 + new —— 基于原型的对象创建者

### 什么是构造函数？

构造函数在技术上也是一个普通的 JavaScript 函数，但按照社区的约定，我们用**首字母大写的 PascalCase** 来命名它（如 `User`、`Animal`、`HttpRequest`），并且**总是配合 `new` 关键字来调用**。当函数被 `new` 调用时，JavaScript 引擎会在幕后执行一系列特殊的操作——创建空对象、链接原型、绑定 `this`、处理返回值——我们在《构造函数与 new》和《手动实现 new 运算符》两章中已经深入分析过了。

```javascript
// 构造函数 + new 的方式
function User(name, age) {
  // this 在这里指向 new 创建的新对象
  this.name = name;      // 每个用户的姓名不同 → 放在实例上
  this.age = age;        // 每个用户的年龄不同 → 放在实例上
}

// 方法放在 prototype 上 → 所有实例共享同一份
User.prototype.greet = function () {
  return `你好，我是 ${this.name}，今年 ${this.age} 岁`;
};

User.prototype.isAdult = function () {
  return this.age >= 18;
};

// 使用 —— 必须用 new！
let u1 = new User("张三", 25);
let u2 = new User("李四", 15);

u1.greet();           // "你好，我是 张三，今年 25 岁"
u2.greet();           // "你好，我是 李四，今年 15 岁"
console.log(u1 instanceof User); // true ← 构造函数特有的能力！
```

### 构造函数的理论基础

构造函数体现的是基于**原型链（Prototype Chain）**的对象组织模式。在这种模式下，对象分为两个层次：

- **实例层（Instance Level）**：通过 `this.xxx` 定义在每个对象自身上的属性，通常是数据（如 `name`、`age`），每个实例的值不同
- **原型层（Prototype Level）**：通过 `Constructor.prototype.xxx` 定义在原型对象上的属性，通常是方法（如 `greet()`、`isAdult()`），所有实例共享同一份

这种分层设计的核心优势在于**内存效率和方法一致性**。无论你创建多少个 `User` 实例，`greet` 方法在内存中始终只有一份——所有实例通过 `[[Prototype]]` 链找到同一个函数对象。这与工厂函数形成鲜明对比：工厂函数创建 1000 个实例就意味着 1000 份 `greet` 方法的内存拷贝。

此外，构造函数还天然支持 **`instanceof` 运算符**进行运行时类型检查，支持**原型继承**实现类型层级关系（`Dog extends Animal`），这些都是工厂函数不具备的能力（除非手动模拟）。

### 通俗类比：标准化流水线工厂

如果说工厂函数像是定制礼品店，那**构造函数 + new 就像是一条标准化的工业生产流水线**：

这条流水线有严格的设计图纸（构造函数的定义），规定了每个产品必须有哪些零件（`this.name`、`this.age`）。更重要的是，流水线上有一个**中央公共配件库（prototype）**——里面存放着所有产品共用的部件（如操作手册 `greet()`、检验标准 `isAdult()`）。

每当一个新产品被制造出来时（`new User()`），它会自动获得一本公共配件库的查阅手册（`[[Prototype]]` 链接）。当产品需要执行某个操作时（调用 `greet()`），先检查自己身上有没有这个功能；如果没有，就去查手册（沿原型链查找）——找到了就直接按手册操作。

关键特点：**手册只有一本（存在 prototype 上），但所有产品都可以查阅它**。当手册更新了操作流程（修改了 `prototype.greet`），所有后续使用该功能的产品都会自动获得最新版本——不需要逐一通知每个产品。

这就是构造函数 + 原型的核心价值所在：**数据的独立性 + 行为的共享性**。

## 全面对比：11 个维度的差异分析

为了让你能够系统地理解和权衡两种方式的优劣，我们从以下 11 个维度进行逐项对比：

### 维度 1：调用方式

| | 工厂函数 | 构造函数 (+ new) |
|--|---------|----------------|
| **语法** | `createUser("张三", 25)` | `new User("张三", 25)` |
| **关键字** | 无需特殊关键字 | **必须使用 `new`** |
| **遗忘后果** | ✅ 无任何副作用 | ⚠️ 非严格模式下 `this` 指向全局对象，导致污染 |

```javascript
// 工厂函数：怎么调用都安全
function safeFactory(name) { return { name }; }
let a = safeFactory("A");   // 正常
let b = new safeFactory("B"); // 虽然用了 new，也只是 this 被忽略，返回对象正常

// 构造函数：忘记 new 就出问题
function UnsafeConstructor(name) { this.name = name; }
let c = UnsafeConstructor("C");   // 💥 全局污染! window.name = "C"
let d = new UnsafeConstructor("D"); // 正常
```

**理论补充**：构造函数必须配合 `new` 使用这一约束，在 ES6 的 `class` 语法中被强化为**语法层面上的强制**——如果你对一个 class 使用不带 `new` 的普通调用，引擎会直接抛出 `TypeError: Class constructor XXX cannot be invoked without 'new'`。这是一种"严格模式优先"的设计哲学：与其让错误的用法静默地产生难以排查的 bug，不如直接报错让开发者立刻意识到问题。

### 维度 2：this 的行为

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| **this 指向** | 取决于调用上下文（通常不使用 this） | **始终指向新创建的实例对象** |
| **灵活性** | 高（可以用箭头函数、bind 等） | 低（被 new 强制绑定） |

```javascript
// 工厂函数中的 this —— 通常不依赖它
function factoryWithThis(name) {
  return {
    name,
    // 如果这里用了 this... 它的值取决于 factoryWithThis 是怎么被调用的
    // 但由于我们返回的是新对象字面量，这里的 this 通常不是我们想要的
    getContext: () => this  // 箭等一下，这是谁？
  };
}
let obj1 = factoryWithThis("test");
// obj1.getContext() 返回的是什么？
// 取决于 strict mode 和调用环境，通常不是 obj1 本身！

// 构造函数中的 this —— 明确且可靠
function ConstructorWithThis(name) {
  this.name = name;  // this 100% 是即将返回的新对象
  this.getThis = function () { return this; };
}
let obj2 = new ConstructorWithThis("test");
console.log(obj2.getThis() === obj2); // true ✅ this 就是 obj2
```

**通俗类比**：工厂函数中的 `this` 就像一个**自由人**——他可以去任何地方，他的身份取决于他在哪里被召唤。而构造函数中的 `this` 就像一个**被分配到固定岗位的员工**——他的职责范围被 `new` 明确定义了，不会乱跑。

### 维度 3：方法共享机制

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| **方法存放位置** | 每个对象内部（闭包或属性） | 原型对象（`Constructor.prototype`）|
| **内存占用** | N 个实例 = N 份方法 | N 个实例 = **1 份方法** |
| **方法一致性** | 创建后各自独立，互不影响 | 修改 prototype 立即影响所有实例 |

```javascript
// ====== 工厂函数：每个实例有自己的方法副本 ======
function FactoryUser(name) {
  return {
    name,
    greet() { return `我是 ${this.name}`; }  // 每次创建都会产生一个新的函数对象
  };
}

let f1 = FactoryUser("A");
let f2 = FactoryUser("B");
console.log(f1.greet === f2.greet); // false ❌ 两个不同的函数！

// ====== 构造函数：所有实例共享同一个方法 ======
function ConstructorUser(name) {
  this.name = name;
}
ConstructorUser.prototype.greet = function () {
  return `我是 ${this.name}`;
};

let c1 = new ConstructorUser("A");
let c2 = new ConstructorUser("B");
console.log(c1.greet === c2.greet); // true ✅ 同一个函数！

// 动态更新能力对比：
// 修改工厂函数已创建对象的方法 —— 不影响已有对象
f1.greet = () => "我被修改了";
console.log(f1.greet()); // "我被修改了" （只有 f1 变了）
console.log(f2.greet()); // "我是 B" （f2 不受影响）

// 修改构造函数原型上的方法 —— 所有实例立即生效
ConstructorUser.prototype.greet = () => "统一修改";
console.log(c1.greet()); // "统一修改" （c1 也变了！）
console.log(c2.greet()); // "统一修改" （c2 也变了！）
```

**性能量化分析**：假设一个 `greet` 方法占用约 200 字节的内存（包含函数代码、作用域链引用等元数据），创建 1000 个实例时：

- **工厂函数**：`200 × 1000 = 200,000 字节`（约 195KB）仅用于存储重复的方法
- **构造函数**：`200 × 1 = 200 字节`（所有实例共享）

差距约为 **1000 倍**。当然，现代浏览器的垃圾回收器（GC）很智能，对于短生命周期的对象能快速回收，但这种无谓的内存浪费在创建大量长生命周期对象或嵌入式设备（内存受限）的场景下仍需认真对待。

### 维度 4：instanceof 支持

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| `instanceof` | ❌ 不支持（始终返回 `false`）| ✅ 支持（检查原型链）|

```javascript
function factoryFn() { return { x: 1 }; }
function ConstructorFn() { this.x = 1; }

let fObj = factoryFn();
let cObj = new ConstructorFn();

console.log(fObj instanceof factoryFn);     // false ❌
console.log(cObj instanceof ConstructorFn);  // true  ✅
console.log(cObj instanceof Object);        // true  ✅（继承链顶端）
```

**为什么工厂函数不支持 instanceof？** 因为 `instanceof` 的工作原理是沿着对象的原型链向上查找，看能否找到指定构造函数的 `prototype` 属性。而工厂函数创建的对象的 `[[Prototype]]` 默认指向 `Object.prototype`（或者你指定的某个对象），它与工厂函数本身没有任何注册关系。引擎无法知道"这个对象是由哪个函数创建的"，因为工厂函数只是普通地返回了一个对象，没有留下任何"血缘标记"。

**instanceof 不支持的影响**：在某些场景下确实会造成不便：
- 无法做运行时类型检查（如 `if (obj instanceof User) { ... }`）
- 框架或库无法自动识别对象类型来做特殊处理（如 ORM 框架判断实体类型）
- 单元测试中无法方便地验证对象"出身"

但也有变通方案——后面我们会介绍 `Symbol.hasInstance` 可以手动实现自定义的 `instanceof` 行为。

### 维度 5：私有变量 / 封装能力

| | 工厂函数 | 构造函数（ES6 前）| 构造函数（ES6+）|
|--|---------|------------------|---------------|
| **真正的私有变量** | ✅ 通过闭包轻松实现 | ❌ 只能用约定（`_前缀`）| ✅ **私有字段（#）** |
| **外部可访问性** | 完全可控 | 属性公开可修改 | 编译器强制私有 |

```javascript
// ====== 工厂函数：真正的私有变量（闭包）======
function createBankAccount(initialBalance) {
  // 这些变量在外部绝对无法访问！
  let balance = initialBalance;     // 私有：余额
  let transactionCount = 0;         // 私有：交易次数
  let pin = "0000";                  // 私有：密码

  return {
    deposit(amount) {
      balance += amount;
      transactionCount++;
      console.log(`存入 ${amount}，余额: ${balance}`);
    },
    withdraw(amount, inputPin) {
      if (inputPin !== pin) {
        console.error("密码错误！");
        return;
      }
      if (amount > balance) {
        console.error("余额不足！");
        return;
      }
      balance -= amount;
      transactionCount++;
      console.log(`取出 ${amount}，余额: ${balance}`);
    },
    getBalance() {
      return balance;
    },
    getTransactionCount() {
      return transactionCount;
    }
  };
}

let account = createBankAccount(1000);
account.deposit(500);              // 存入 500，余额: 1500
account.withdraw(200, "0000");     // 取出 200，余额: 1300
account.withdraw(9999, "1234");     // 密码错误！

console.log(account.balance);          // undefined ← 无法访问！
console.log(account.transactionCount);// undefined ← 无法访问！
account.balance = 9999999;            // 静默无效！只是在 account 上创建了一个无用属性
console.log(account.getBalance());     // 1300 ← 真正的 balance 未受影响


// ====== 构造函数 ES6 前：只能模拟私有 ======
function LegacyAccount(initialBalance) {
  this._balance = initialBalance;     // _ 前缀约定："请勿直接访问"
  this._transactionCount = 0;

  // 但这只是一种"君子协定"，没有任何强制性
}
LegacyAccount.prototype.deposit = function (amount) {
  this._balance += amount;
};
LegacyAccount.prototype.withdraw = function (amount) {
  if (amount > this._balance) throw new Error("余额不足");
  this._balance -= amount;
};

let legacy = new LegacyAccount(1000);
legacy._balance = -9999999;  // 😱 直接篡改！没有任何阻止！
console.log(legacy._balance);    // -9999999 —— "私有"数据被破坏了


// ====== 构造函数 ES6+：真正的私有字段 ======
class ModernAccount {
  #balance;          // # 前缀表示私有字段（ES2022 标准）
  #transactionCount;
  #pin;

  constructor(initialBalance) {
    this.#balance = initialBalance;
    this.#transactionCount = 0;
    this.#pin = "0000";
  }

  deposit(amount) {
    this.#balance += amount;
    this.#transactionCount++;
  }
  getBalance() {
    return this.#balance;
  }
}

let modern = new ModernAccount(1000);
modern.#balance = 0;  // SyntaxError! 编译器直接阻止你在外部访问私有字段
modern.getBalance();  // 1000 ← 安全
```

**理论深挖：为什么闭包能实现真正的私有？**

这是因为 JavaScript 的作用域规则：**函数内部声明的变量对外部代码是不可见的**（词法作用域/Lexical Scoping）。当工厂函数内部声明了 `let balance` 后，这个变量存在于工厂函数的作用域中。返回对象上的方法（如 `deposit`、`withdraw`）是在工厂函数内部定义的——它们形成了**闭包（Closure）**，捕获了对 `balance` 等变量的引用。但这些引用只在闭包内部可用，外部的代码完全看不到也摸不着这些变量。

这是一种**语言层面的硬性保护**——不是靠约定，不是靠文档提醒，而是靠作用域规则在物理上隔绝了访问路径。相比之下，构造函数的 `_` 前缀约定则完全是软性的——就像门上贴了一张"闲人免进"的纸条，但门并没有锁。

### 维度 6：组合 vs 继承

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| **复用策略** | 组合（Composition）优于继承 | 继承（Inheritance）为主 |
| **灵活性** | ★★★★★ 可自由组合任意能力模块 | ★★☆☆☆ 受限于单原型链 |
| **复杂度** | 低（简单直观）| 中到高（需理解原型链、super 等）|

```javascript
// ====== 工厂函数：自由的组合（Mixin 模式）======

// 定义一组可复用的"能力模块"
const canFly = {
  fly() { console.log(`${this.name} 🦅 飞向蓝天!`); },
  altitude: 10000
};

const canSwim = {
  swim() { console.log(`${this.name} 🏊 潜入水中!`); },
  maxDepth: 100
};

const canWalk = {
  walk() { console.log(`${this.name} 🚶 在路上行走!`); },
  speed: 5
};

const canMakeSound = {
  makeSound(noise) { console.log(`${this.name}: "${noise}"`); }
};

// 工厂函数可以随意组合这些能力
function createCreature(name, ...abilities) {
  let creature = { name };
  abilities.forEach(ability => {
    Object.assign(creature, ability);  // 把能力"混入"对象
  });
  return creature;
}

// 根据需求灵活组合
let duck = createCreature("鸭子", canWalk, canSwim, canFly, canMakeSound);
let fish = createCreature("鱼", canSwim, canMakeSound);
let human = createCreature("人类", canWalk, canSwim, canMakeSound);
let eagle = createCreature("老鹰", canFly, canWalk, canMakeSound);

duck.walk();   // "鸭子 🚶 在路上行走!"
duck.swim();   // "鸭子 🏊 潜入水中!"
duck.fly();    // "鸭子 🦅 飞向蓝天!"
duck.makeSound("嘎嘎嘎");

fish.swim();   // "鱼 🏊 潜入水中!"
human.walk();  // "人类 🚶 在路上行走!"
human.swim();  // "人类 🏊 潜入水中!"

// ====== 构造函数：基于继承的类型层次 ======

class Animal {
  constructor(name) {
    this.name = name;
  }
  makeSound(noise) { console.log(`${this.name}: "${noise}"`); }
}

class Bird extends Animal {        // 只能继承自一个父类
  constructor(name) {
    super(name);
    this.canFly = true;
  }
  fly() { console.log(`${this.name} 🦅 飞起来!`); }
}

class Fish extends Animal {        // 继承链是线性的
  constructor(name) {
    super(name);
    this.canSwim = true;
  }
  swim() { console.log(`${this.name} 🏊 游起来了!`); }
}

// 要让 Penguin 既会"飞"又会"游"又要会"走"？
// 必须精心设计多层继承或使用 mixin 工具...
class Penguin extends Animal { /* 复杂的多重继承模拟 */ }
```

**理论补充：组合优于继承（Composition over Inheritance）**

这是面向对象设计中一条著名的**设计原则**（由 GoF《设计模式》一书推广）。它的核心观点是：**通过将多个小的、独立的功能单元组合在一起来构建复杂行为，比通过建立深层继承层级来实现同样的功能更加灵活、更容易维护。**

工厂函数天然适合这种"组合式"思维——因为它创建的就是普通对象，你可以用 `Object.assign()` 或展开运算符 `({...a, ...b})` 自由地将任意多的能力模块"混入"到一个对象中。而构造函数的原型继承则是"继承式"思维的典型代表——你需要预先规划好类型层级（Animal → Bird → Penguin），一旦层级确立就很难改变。

Go 语言甚至完全去掉了类的继承语法，只保留了接口的组合（embedding），其官方博客标题就是 **"Less type-oriented, more Go-style"**（少一些类型导向，多一些 Go 风格——即组合风格）。

### 维度 7：调试体验

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| **控制台输出** | `{ name: "张三", age: 25, greet: [Function] }` | `User { name: "张三", age: 25 }` |
| **方法可见性** | 方法直接显示在对象属性列表中 | 方法在原型中（`[[Prototype]]`），需要展开查看 |

function FactoryDemo(x) {

}

  this.x = x;
}

### 维度 8：与 JSON 的兼容性

| | 工厂函数 | 构造函数 |
|--|---------|---------|
| `JSON.stringify()` | ✅ 所有自有属性都被序列化 | ✅ 只序列化自有属性（同左） |
| `JSON.parse()` | 得到普通对象（丢失方法）| 得到普通对象（丢失方法和原型关联）|

```javascript
let fData = JSON.stringify(createUser("张三", 25));
// '{"name":"张三","age":25}' — 方法不能被序列化（函数被忽略）

let cData = JSON.stringify(new User("张三", 25));
// '{"name":"张三","age":25}' — 结果相同

// 反序列化后都变成了普通对象，没有方法
let fRestored = JSON.parse(fData);
let cRestored = JSON.parse(cData);
// fRestored.greet → undefined（方法丢了）
// cRestored.greet → undefined（方法也在原型上，丢了）
```

在这个维度上两者的表现是一致的——JSON 序列化只关心对象的自有可枚举属性，方法（无论在哪里定义的）都不会被序列化。反序列化得到的永远是纯数据对象，需要额外的步骤才能恢复方法。

## 各自的最佳适用场景

### 选择工厂函数的场景

#### 场景 1：需要真正的私有封装

如果你的对象包含不应该被外部直接访问的内部状态（如银行账户余额、加密密钥、内部缓存等），工厂函数的闭包机制是最简单可靠的私有化方案：

```javascript
function createSecureToken(secret) {
  const hmacKey = crypto.createHash('sha256').update(secret).digest();
  let usageCount = 0;
  const MAX_USAGE = 1000;

  return {
    generate(payload) {
      if (usageCount >= MAX_USAGE) throw new Error("Token 已过期");
      usageCount++;
      // 使用 hmacKey 进行签名（hmacKey 对外界不可见）
      const signature = crypto
        .createHmac('sha256', hmacKey)
        .update(payload)
        .digest('hex');
      return { payload, signature, remaining: MAX_USAGE - usageCount };
    },
    getUsageInfo() {
      return { used: usageCount, remaining: MAX_USAGE - usageCount };
    }
  };
}
```

#### 场景 2：对象结构多变或不定型

当需要创建的对象在不同条件下具有显著不同的结构时，工厂函数的条件分支比构造函数的继承体系更加自然：

```javascript
function createDataAdapter(source) {
  // 根据数据源类型返回不同结构的适配器
  if (source.type === 'database') {
    return {
      source,
      async query(sql) { return source.execute(sql); },
      async close() { return source.disconnect(); }
    };
  } else if (source.type === 'api') {
    return {
      source,
      async query(endpoint) { return fetch(source.baseUrl + endpoint).then(r => r.json()); },
      async close() { /* API 无需关闭 */ }
    };
  } else if (source.type === 'file') {
    return {
      source,
      async query(key) { return source.data[key]; },
      async close() { return source.fileHandle.close(); }
    };
  }
  throw new Error(`未知的数据源类型: ${source.type}`);
}
```

#### 场景 3：偏好函数式/组合式编程风格

如果你的项目或团队倾向于函数式编程（Functional Programming）风格，强调不可变性（Immutability）、纯函数（Pure Function）、组合（Composition）而非继承，那么工厂函数是更自然的选择：

```javascript
// 函数式风格：通过组合小函数来构建复杂对象
const withId = (obj) => ({ ...obj, id: Math.random().toString(36).slice(2, 8) });

const withTimestamp = (obj) => ({ ...obj, createdAt: Date.now(), updatedAt: Date.now() });

const withValidation = (schema) => (obj) => {
  const { error, value } = schema.validate(obj);
  if (error) throw new Error(`验证失败: ${error.message}`);
  return value;
};

// 组合使用
const createValidatedEntity = (data) =>
  pipe(
    withId,
    withTimestamp,
    withValidation(userSchema)
  )(data);

let entity = createValidatedEntity({ name: "测试", email: "test@example.com" });
```

#### 场景 4：对象数量少，内存不敏感

如果你创建的对象数量不多（比如配置对象、一次性使用的工具对象等），工厂函数带来的内存开销完全可以忽略不计。此时选择工厂函数可以获得更好的封装性和更简洁的代码。

### 选择构造函数 / class 的场景

#### 场景 1：需要大量同类对象

游戏引擎中的粒子系统、电商系统中的商品对象、社交网络中的用户实体——当需要创建成千上万个结构相同的实例时，构造函数 + 原型方法的内存优势是不可替代的：

```javascript
// 游戏中的粒子系统：可能有数万个粒子对象
class Particle {
  constructor(x, y, vx, vy) {
    this.x = x;
    this.y = y;
    this.vx = vx;
    this.vy = vy;
    this.life = 1.0;
  }
  // update 和 render 在原型上 —— 数万个粒子只共享一份！
  update(dt) { /* ... */ }
  render(ctx) { /* ... */ }
}

const PARTICLE_COUNT = 50000;
for (let i = 0; i < PARTICLE_COUNT; i++) {
  particles.push(new Particle(
    Math.random() * canvasWidth,
    Math.random() * canvasHeight,
    (Math.random() - 0.5) * 4,

// 如果用工厂函数：50000 份 update/render 方法 ≈ 额外数十 MB 内存
```

#### 场景 2：需要 instanceof 类型检查

在多态分发、参数校验、序列化/反序列化等需要运行时类型信息的场景中，构造函数（或 class）的 `instanceof` 能力至关重要：

```javascript
// 路由处理器：根据请求对象的类型走不同逻辑
function handleRequest(req) {
  if (req instanceof UserRequest) {
    return userService.handle(req);
  } else if (req instanceof AdminRequest) {
    return adminService.handle(req);
  } else if (req instanceof ApiRequest) {
    return apiProxy.forward(req);
  }
  throw new Error(`未知的请求类型`);
}
```

#### 场景 3：需要清晰的类型层级关系

当领域模型中有明确的"is-a"（是一个）泛化-特化关系时——如 `Employee` is-a `Person`、`Dog` is-an `Animal`、`SavingAccount` is-an `Account`——基于原型的继承是最自然的表达方式：

```javascript
class Account {
  constructor(owner, balance) {
    this.owner = owner;
    this.balance = balance;
    this.createdAt = new Date();
    this.#transactions = [];
  }
  deposit(amount) { this.balance += amount; this.#logTransaction('deposit', amount); }
  withdraw(amount) { /* ... */ }
  getStatement() { return { owner: this.owner, balance: this.balance }; }
}

class SavingsAccount extends Account {
  constructor(owner, balance, interestRate) {
    super(owner, balance);
    this.interestRate = interestRate;
  }
  applyInterest() { this.balance *= (1 + this.interestRate); }
  // 继承了 Account 的所有方法，同时扩展了自己的行为
}

class CheckingAccount extends Account {
  constructor(owner, balance, overdraftLimit) {
    super(owner, balance);
    this.overdraftLimit = overdraftLimit;
    this.overdraftUsed = 0;
  }
  withdraw(amount) { /* 重写：增加透支逻辑 */ }
}

let savings = new SavingsAccount("张三", 10000, 0.03);
let checking = new CheckingAccount("李四", 5000, 1000);
savings.deposit(1000);       // 来自 Account

savings.getStatement();     // 来自 Account

console.log(savings instanceof SavingsAccount); // true
```

#### 团队熟悉面向对象编程范式

如果你的团队成员大多来自 Java、C#、Python 等强 OOP 语言背景，他们对 class、继承、多态、interface 等概念已经非常熟悉。在这种情况下，使用构造函数/class 可以降低团队的认知成本，让代码风格与他们的经验相吻合。

## 第三条路：混合使用与进阶技巧

在实际项目中，你不必非此即彼——两种范式可以根据需要在同一个项目中混合使用。此外，还有一些进阶技巧可以让工厂函数弥补自身的短板。

### 技巧 1：Symbol.hasInstance —— 让工厂函数支持 instanceof

ES6 引入了 `Symbol.hasInstance` 这个知名符号，允许对象自定义 `instanceof` 的行为。我们可以用它来让工厂函数创建的对象也能通过 `instanceof` 检查：

```javascript
function UserFactory(name, age) {
  return { name, age, greet() { return \`我是 ${this.name}\`; } };
}

// 定义 Symbol.hasInstance
Object.defineProperty(UserFactory, Symbol.hasInstance, {
  value: function(instance) {
    // 检查 instance 是否拥有工厂函数产物应有的特征
    return instance != null &&
           typeof instance.name === 'string' &&
           typeof instance.greet === 'function' &&
           typeof instance.age === 'number';
  }
});

let user = UserFactory("张三", 25);
console.log(user instanceof UserFactory);  // true ✅！
console.log({} instanceof UserFactory);     // false ✅（普通对象通不过检查）
```

这让工厂函数在一定程度上弥补了不支持 `instanceof` 的缺陷。不过需要注意的是：`Symbol.hasInstance` 不能让 `instanceof` 右侧的表达式变成任意的——它仍然是左边对象对右边构造函数的检查，只是检查逻辑由你自己定义了。

### 技巧 2：结合 Object.create 共享方法

如果你喜欢工厂函数的简洁但又不想牺牲方法共享的内存效率，可以将两者结合起来：

```javascript
// 定义共享的方法集合（相当于"原型"）
const userMethods = {
  greet() { return \`你好，我是 ${this.name}\`; },
  isAdult() { return this.age >= 18; },
  toString() { return \`[User: ${this.name}, ${this.age}岁]\`; }
};

function createUser(name, age) {
  // 以 userMethods 为原型创建对象 → 方法只存一份！
  let user = Object.create(userMethods);
  // 数据属性放在对象自身
  user.name = name;
  user.age = age;
  return user;
}

let u1 = createUser("张三", 25);
let u2 = createUser("李四", 30);

console.log(u1.greet === u2.greet); // true ✅ 方法共享了！
console.log(u1.name);               // "张三"
console.log(u1 instanceof Object);    // true（userMethods 继承自 Object.prototype）
```

这种方式兼具了两者的优点：工厂函数式的简洁调用（不用 `new`）、接近构造函数的方法共享效率（通过 `Object.create`）、以及闭包私有化的可能性（在 `createUser` 内部用 `let` 声明的变量对返回的对象来说是私有的）。

### 技巧 3：类工厂方法（Class + Static Factory）

在 ES6+ 项目中最常见的"混合模式"可能是这样的：用 `class` 定义类型和行为，同时提供**静态工厂方法**来封装创建逻辑：

```javascript
class Color {
  #r; #g; #b;

  constructor(r, g, b) {
    this.#r = r;
    this.#g = g;
    this.#b = b;
  }

  // 实例方法
  toHex() {
    const toHex = (n) => n.toString(16).padStart(2, '0');
    return \`#${toHex(this.#r)}${toHex(this.#g)}${toHex(this.#b)}\`;
  }

  toRgb() {
    return \`rgb(${this.#r}, ${this.#g}, ${this.#b})\`;
  }

  // ====== 静态工厂方法 ======
  static fromHex(hex) {
    const result = /^#?([a-f\d]{2})([a-f\d]{2})([a-f\d]{2})$/i.exec(hex);
    if (!result) throw new Error(`无效的颜色值: ${hex}`);
    return new Color(
      parseInt(result[1], 16),
      parseInt(result[2], 16),
      parseInt(result[3], 16)
    );
  }

  static fromName(name) {
    const colors = {
      red: [255, 0, 0],
      green: [0, 255, 0],
      blue: [0, 0, 255],
      white: [255, 255, 255],
      black: [0, 0, 0]
    };
    if (!(name in colors)) throw new Error(`未知的颜色名: ${name}`);
    return new Color(...colors[name]);
  }

  static random() {
    return new Color(
      Math.floor(Math.random() * 256),
      Math.floor(Math.random() * 256),
      Math.floor(Math.random() * 256)
    );
  }
}

// 使用方式多样且清晰
let red = new Color(255, 0, 0);                    // 传统 new
let blue = Color.fromHex("#0000ff");               // 工厂方法：从十六进制
let green = Color.fromName("green");                 // 工厂方法：从名字
let randomColor = Color.random();                   // 工厂方法：随机颜色

console.log(red.toHex());      // "#ff0000"
console.log(blue.toRgb());     // "rgb(0, 0, 255)"
console.log(green.toHex());    // "#00ff00"
```

这种模式在实际工程中被广泛采用——它让类的使用者可以选择最适合自己的创建方式：传统的 `new`、语义明确的工厂方法、或是带参数解析的便捷方法。jQuery 的 `$(selector)` 本质上也是类似的思路——一个工厂函数根据参数的不同类型返回不同包装后的对象。

## 总结：如何做出选择

### 决策流程图

面对一个具体的对象创建需求时，你可以参照以下决策流程：

```
需要创建对象吗？
│
├─→ 是否需要大量（数百以上）同类对象？
│   │
│   ├─→ 是 → 优先考虑构造函数/class（内存效率优势）
│   │        ↓
│   │   是否需要 instanceof 类型检查？
│   │   ├─→ 是 → class（最佳选择）
│   │   └─→ 否 → 构造函数 + prototype
│   │
│   └─→ 否（少量对象或单个对象）→ 继续 ↓
│
├─→ 是否需要真正的私有封装？
│   │
│   ├─→ 是（且不能用 class #私有字段） → 工厂函数（闭包私有）
│   │
│   └─→ 否或可用 class → 继续 ↓
│
├─→ 对象的结构是否高度一致（同一"类型"）？
│   │
│   ├─→ 是 → 构造函数/class（类型语义清晰）
│   │
│   └─→ 否（不同条件返回不同结构）→ 工厂函数（灵活组合）
│
└─→ 团队/项目的现有风格是什么？
    │
    ├─→ OOP 主导 → class
    ├─→ FP 主导 → 工厂函数
    └─→ 混合 → 根据具体场景选择
```

### 最终建议

**没有绝对的"更好"——只有"更适合"。** 工厂函数和构造函数（class）都是 JavaScript 对象创建工具箱中的利器，各有各的光芒和阴影：

- 当你需要**简洁、灵活、强封装**的对象创建方式，且不关心 `instanceof` 和大规模创建的性能问题时 → **工厂函数是你的好帮手**
- 当你需要**高效、类型安全、可继承**的对象体系，且需要创建大量同类实例时 → **构造函数 / class 是你不二之选**
- 最强大的开发者**两者皆通**，能够在正确的时候选择正确的工具

> **记住：工具没有高低之分，只有合适与否之别。真正的精通不在于只会用一种方式解决所有问题，而在于理解每种方式的本质和边界，在最恰当的时刻拿出最合适的武器。**
