# 原型链查找机制与属性遮蔽

## 属性访问的"幕后推手"

在 JavaScript 中，每当你写下 `obj.propertyName` 来获取一个值，或者执行 `obj.methodName()` 来调用一个方法时，你实际上触发了一个远比表面看起来复杂得多的过程。这个过程的学名叫做 **"属性查找"（Property Lookup）**——它是 JavaScript 原型继承系统的核心运作机制，也是理解整门语言的关键钥匙。

很多开发者对属性查找的理解停留在模糊的"如果自己没有就去原型上找"这一层面。但这个描述太过简化了——它没有回答以下关键问题：

- 查找的精确算法步骤是什么？每一步做了什么判断？
- "找到"和"没找到"分别意味着什么？返回值的类型有何不同？
- 查找过程中 `this` 的绑定是如何确定的？
- 为什么读取和写入的行为截然不同？什么是"属性遮蔽（Shadowing）"？
- 如果原型链形成了环怎么办？引擎会陷入死循环吗？
- 访问器属性（getter/setter）如何影响查找过程？

本章将对这些问题的每一个都给出精确、深入且配有丰富示例的回答。掌握这些内容后，你对 JavaScript 对象系统的理解将达到一个新的深度。

### 通俗类比：公司内部的信息查询系统

为了建立直觉，让我们先用一个生活化的场景来模拟属性查找的全过程。

想象一家**大型跨国公司**（这就是我们的对象 `obj`）。这家公司的每个部门都有自己的文件柜（自有属性），但有些文件可能不在本部门。当员工需要查询某份信息时：

1. **先查自己的部门（自身属性）**：翻开自己部门的文件柜，看看有没有这份资料。有？直接取走使用。
2. **如果没有，查总部的公共资料室（[[Prototype]] / 原型）**：拿着申请单去总部资料室查阅。资料室里存放着全公司通用的《操作手册》《标准流程》《政策文档》等。找到了？复印一份拿回来用。
3. **如果总部也没有，继续往上查集团层面的资料库（原型的原型）**……
4. **一直查到最高层（`null` = 公司不存在更上层级了）**，返回"未找到"。

关键细节：
- 当员工从总部**查阅并复印**了一份资料时（读取），他并没有把资料从总部移走——原始文件还在那里，其他部门的人仍然可以查阅
- 但如果员工决定**修改/重写**某份资料（写入），他会把它放在**自己部门的文件柜里**（在自身创建新属性），而不是去涂改总部的原件。以后他自己再查这份资料时，优先看到的是自己部门的那份（被涂改过的版本），而不是总部的原始版本——这就叫"遮蔽"

这个过程就是 JavaScript 属性查找的完美类比。接下来我们用精确的技术语言来拆解每一个环节。

## 一、读取操作：沿原型链向上查找

### [[Get]] 内部方法——规范层面的算法

ECMAScript 规范定义了一个名为 `[[Get]]`（Property Get）的内部方法来处理属性的读取操作。当我们写下 `obj.propName` 时，引擎内部会执行类似以下的算法（大幅简化但保留了核心逻辑）：

```
[[Get]] (P, propName) 的完整查找过程:

  让 currentObj = P（从目标对象开始）

  REPEAT（循环）:
    ┌─ 步骤 A: 在 currentObj 自身查找名为 "propName" 的属性
    │
    │  ├── 如果找到了（作为"自有属性" Own Property 存在）:
    │  │   ├── 如果是数据属性（Data Property）
    │  │   │   → 返回该属性的值 ✅ （查找结束）
    │  │   └── 如果是访问器属性（Accessor Property，有 getter）
    │  │       → 执行 getter 函数，返回其结果 ✅ （查找结束）
    │  │
    │  └── 如果没找到 ↓
    │
    ├─ 步骤 B: 获取 currentObj 的 [[Prototype]]
    │
    │  ├── 如果 [[Prototype]] === null:
    │  │   → 返回 undefined ⛔ （到达链条终点，属性不存在）
    │  │
    │  └── 否则 → 让 currentObj = [[Prototype]]，回到步骤 A 继续查找
```

### 用代码模拟整个查找过程

让我们用一个可运行的函数来直观展示这个算法：

```javascript
/**
 * 模拟 JavaScript 引擎的 [[Get]] 属性查找过程
 * @param {Object} obj - 要查询的对象
 * @param {string} propName - 要查找的属性名
 * @returns {*} 找到的值，或 undefined
 */
function simulateLookup(obj, propName) {
  let depth = 0;
  const MAX_DEPTH = 100; // 防止无限循环的安全阀
  let current = obj;

  while (current !== null && depth < MAX_DEPTH) {
    depth++;

    // 步骤 A：检查当前对象的自身属性
    if (current.hasOwnProperty(propName)) {
      // 获取属性描述符以区分数据和访问器
      const descriptor = Object.getOwnPropertyDescriptor(current, propName);

      console.log(`  [深度 ${depth}] ✅ 在 ${getLabel(current)} 上找到了 "${propName}"`);

      if (descriptor && 'get' in descriptor) {
        // 是访问器属性 —— 执行 getter
        return descriptor.get.call(obj);
      }
      // 是普通数据属性 —— 直接返回值
      return current[propName];
    }

    // 当前对象自身没有 → 输出调试信息并继续向上
    console.log(`  [深度 ${depth}] ⬜️ ${getLabel(current)} 上没有 "${propName}"，继续向上...`);

    // 步骤 B：沿 [[Prototype]] 向上移动
    current = Object.getPrototypeOf(current);
  }

  console.log(`  [深度 ${depth + 1}] ⛔ 到达原型链顶端 (null)，"${propName}" 不存在`);
  return undefined; // undefined
}

// 辅助工具：获取对象的标签
function getLabel(o) {
  if (o === null) return 'null';
  if (Array.isArray(o)) return `Array[${o.length}]`;
  try {
    if (o.constructor && o.constructor.name)
      return `(实例: ${o.constructor.name})`;
    return '(匿名对象)';
  } catch { return '(未知)'; }
}

// =============================================
// 测试：多层原型链上的属性查找
// =============================================

function GrandParent() {}
GrandParent.prototype.familyName = "王家";
GrandParent.prototype.ancestry = function () {
  return this.familyName || "未知";
};

function Parent() {}
// Parent 继承 GrandParent
Object.setPrototypeOf(Parent.prototype, GrandParent.prototype);
Parent.prototype.surname = "李";
Parent.prototype.getFullName = function () {
  return `${this.familyName || ""}${this.surname || ""}`;
};

function Child() {}
// Child 继承 Parent
Object.setPrototypeOf(Child.prototype, Parent.prototype);
Child.prototype.givenName = "小明";
Child.prototype.introduce = function () {
  return `我是 ${this.givenName}${this.surname ? this.surname : ''}${this.familyName ? this.familyName : ''}`;
};

let child = new Child();
child.personalHobby = "画画";  // 自身属性

console.log("=== 查找 personalHobby（自身属性）===");
simulateLookup(child, "personalHobby");
// 输出: [深度 1] ✅ 在 (实例: Child) 上找到了 "personalHobby"
// 返回: "画画"

console.log("\n=== 查找 givenName（自身属性）===");
simulateLookup(child, "givenName");
// 输出: [深度 1] ✅ 在 (实例: Child) 上找到了 "givenName"
// 返回: "小明"

console.log("\n=== 查找 surname（原型链第 2 层）===");
simulateLookup(child, "surname");
// 输出:
//   [深度 1] ⬜️ (实例: Child) 上没有 "surname"，继续向上...
//   [深度 2] ✅ 在 (实例: Parent) 上找到了 "surname"
// 返回: "李"

console.log("\n=== 查找 familyName（原型链第 3 层）===");
simulateLookup(child, "familyName");
// 输出:
//   [深度 1] ⬜️ (实例: Child) 上没有 "familyName"，继续向上...
//   [深度 2] ⬜️ (实例: Parent) 上没有 "familyName"，继续向上...
//   [深度 3] ✅ 在 (实例: GrandParent) 上找到了 "familyName"
// 返回: "王家"

console.log("\n=== 查找 nonExistent（不存在的属性）===");
simulateLookup(child, "nonExistent");
// 输出:
//   ... 经过 Child → Parent → GrandParent → Object ...
//   [深度 5] ⛔ 到达原型链顶端 (null)，"nonExistent" 不存在
// 返回: undefined
```

从这个输出可以清晰地看到属性查找是如何**一层一层地**向上进行的：先检查自身（深度 1），没有就去问"父亲"（深度 2），再没有就去问"祖父"（深度 3）……直到找到答案或者问到祖宗十八代都没有为止。

### `this` 在原型方法中的动态绑定

这是属性查找中一个极其重要但经常被忽视的细节：**无论方法是定义在对象自身还是继承自原型，方法内部的 `this` 始终指向调用该方法时点号 `.` 左边那个对象。**

```javascript
function Animal(name) {
  this.name = name;
  this.species = "动物";
}

Animal.prototype.sleep = function () {
  this.isSleeping = true;  // ← 注意这里的 this！
  return `${this.name || '某种生物'} 正在睡觉...`;
};

// 场景 A：通过 Dog 实例调用（继承的方法）
function Dog(name, breed) {
  Animal.call(this, name);  // 或者 super(name)
  this.breed = breed;
}
Object.setPrototypeOf(Dog.prototype, Animal.prototype);

let dog = new Dog("旺财", "柴犬");
dog.sleep();  // "旺财 正在睡觉..."
// sleep 方法中的 this === dog ✅
// 所以 isSleeping 属性被添加到了 dog 身上！
console.log(dog.isSleeping); // true
console.log(Animal.prototype.isSleeping); // undefined —— Animal 原型上没有被修改

// 场景 B：通过 Cat 实例调用（同一个原型方法！）
let cat = { __proto__: Animal.prototype, name: "喵喵", species: "猫" };
cat.sleep();  // "喵喵 正在睡觉..."
// sleep 方法中的 this === cat ✅
console.log(cat.isSleeping); // true —— isSleeping 加到了 cat 身上
```

**理论意义**：这意味着原型对象（如 `Animal.prototype`）扮演的是一个**"方法模板库"或"行为蓝图"**的角色——它定义了"怎么做某件事"的操作流程，而具体的数据（`this.name`、`this.isSleeping` 等）由调用者（实例）提供。这是一种优雅的**行为与数据分离**设计。

**通俗类比**：这就像一本《标准作业程序手册》放在公司前台（原型）。任何员工（实例）都可以去查阅这本手册。当员工按照手册上的步骤执行操作时，操作的対象是员工自己的工位（`this`），不是那本手册本身。所以不同员工执行同样的"组装产品"流程时，各自组装出来的产品各不相同——因为原材料（实例属性）不同。

## 二、写入操作：属性遮蔽（Shadowing）

### 写入与读取的根本性差异

如果说读取属性是一场"沿链条向上寻找"的旅程，那么**写入（赋值）属性就是一场"就地安家落户"的行动——它几乎不会改变链条上游的内容**。

JavaScript 对属性赋值的基本规则非常简洁：

| 操作 | 行为 |
|------|------|
| **读取 `obj.prop`** | 沿 `[[Prototype]]` 链**向上查找**，直到找到或到 null |
| **写入 `obj.prop = value`** | **直接在 `obj` 自身上创建或修改属性**，不影响原型链 |

```javascript
function Base() {}
Base.prototype.sharedValue = "来自 Base 的共享值";
Base.prototype.sharedMethod = function () {
  return `我的值是: ${this.sharedValue}`;
};

let obj = new Base();

// ====== 读取：沿原型链查找 ======
console.log(obj.sharedValue);     // "来自 Base 的共享值"
// obj 自身没有 sharedValue → 去 Base.prototype 上找到了 → 返回它

console.log(obj.sharedMethod());   // "我的值是: 来自 Base 的共享值"

// ====== 写入：直接作用于自身（遮蔽！）=====
obj.sharedValue = "我自己的值";

// 再次读取时：
console.log(obj.sharedValue);     // "我自己的值" ← 不是 "来自 Base 的共享值"！
// 因为 obj 自身现在有了 sharedValue，查找在深度 1 就结束了

console.log(Base.prototype.sharedValue); // "来自 Base 的共享值" ← 原型完全不受影响！✅
```

这种现象就叫做**属性遮蔽（Property Shadowing）**——对象自身的属性"挡住了"原型链上同名属性的视线"。就像太阳出来了，星星虽然还在天上但你看不到它们了；`obj.sharedValue` 这个"太阳"遮挡了原型上的同名"星星"。

### 为什么这样设计？——保护机制

试想一下，如果写入操作也会影响原型链，会发生什么灾难性的后果：

```javascript
// 假设的"混乱世界"：写入会修改原型
function Counter() {}
Counter.prototype.count = 0;  // 所有实例共享一个计数器？？！

let c1 = new Counter();
let c2 = new Counter();

c1.count++;  // 如果这修改了原型 → c2.count 也变成 1 了！！
c1.count++;  // c2.count 也变成 2 了！！

console.log(c1.count); // 2
console.log(c2.count); // 2 ← 等等！我明明只增加了 c1 的计数啊！
```

在这个"混乱世界"里，所有 `Counter` 实例会**共享同一个可变状态**——任何一个实例的修改都会波及所有其他实例。这对于计数器、配置对象、用户状态等场景来说是完全不可接受的。每个对象需要有自己独立的数据空间。

所以"写入只作用于自身"的设计是一种**保护机制**——确保实例之间的状态独立性。每个对象都是一座独立的岛屿，你在自己的岛上盖房子（添加属性）不会影响到隔壁岛屿的地形（原型上的属性）。

### 完整的遮蔽行为演示

```javascript
function Vehicle(type) {
  this.type = type || "未知载具";
}

Vehicle.prototype.description = "这是一辆交通工具";
Vehicle.prototype.getInfo = function () {
  return `[${this.type}] ${this.description}`;
};
Vehicle.prototype.honk = function () {
  return "叭！叭！";
};

// 创建两个实例
let car = new Vehicle("汽车");
let ship = new Vehicle("轮船");

// 初始状态：两者都从原型获取 description 和 honk
console.log(car.getInfo());  // "[汽车] 这是一辆交通工具"
console.log(ship.getInfo()); // "[轮船] 这是一辆交通工具"
console.log(car.honk());     // "叭！叭！"
console.log(ship.honk());    // "叭！叭！"
console.log(car.honk === ship.honk); // true ← 同一个函数！

// 现在 car 决定用自己的 description（遮蔽！）
car.description = "这是一辆超级跑车，百公里加速 3 秒";

// car 的 getInfo 行为改变了
console.log(car.getInfo());  // "[汽车] 这是一辆超级跑车，百公里加速 3 秒" ← 使用了自身的 description
// ship 的 getInfo 不受影响
console.log(ship.getInfo()); // "[轮船] 这是一辆交通工具" ← 仍然是原型的值

// honk 方法仍然共享（因为 car 没有遮蔽它）
console.log(car.honk === ship.honk); // true ✅

// 验证原型未被修改
console.log(Vehicle.prototype.description); // "这是一辆交通工具" ← 原型的原始值完好无损
```

## 三、特殊例外：Setter 拦截写入

前面说"写入只作用于自身"，但这有一个重要的**例外情况**——如果原型上的同名属性是一个 **Setter（写访问器）**，那么赋值操作会**触发 Setter 函数**而不是在自身创建新属性：

```javascript
class User {
  constructor(firstName, lastName) {
    this.firstName = firstName;
    this.lastName = lastName;
  }

  // 在原型上定义 fullName 的 getter/setter
  get fullName() {
    return `${this.firstName} ${this.lastName}`;
  }

  set fullName(value) {
    // ⭐ 关键：这是一个 setter！它会拦截对 fullName 的赋值操作
    const parts = value.trim().split(/\s+/);
    this.firstName = parts[0] || '';
    this.lastName = parts[1] || '';
  }
}

let admin = new User("张", "三");

// 读取：正常沿原型链查找 → 触发 getter
console.log(admin.fullName); // "张 三"

// 写入：触发了原型上的 setter！而不是在 admin 自身上创建 fullName 属性！
admin.fullName = "李 四";
// setter 内部执行：
//   this.firstName = "李"  → 修改了 admin 自身的 firstName
//   this.lastName = "四"   → 修改了 admin 自身的 lastName

console.log(admin.firstName); // "李" ← 被 setter 修改了
console.log(admin.lastName);  // "四" ← 被 setter 修改了
console.log(admin.fullName);   // "李 四" ← 再次通过 getter 获取

// 关键验证：admin 自身上有没有 fullName 属性？
console.log(admin.hasOwnProperty('fullName')); // false ❌
// fullName 并没有被写到 admin 自身上！
// 每次 admin.fullName 都是通过 getter 动态计算的
```

### 为什么 Setter 是例外？

这是因为 **Setter 本身就是一种"拦截并处理写入"的机制**。它的语义就是："当你试图给这个属性赋值时，请交给我来处理。"如果你连 Setter 都不让它生效，那 Setter 就失去了全部存在的意义。

从 ECMAScript 规范的角度来看，`[[Set]]`（属性设置内部方法的简化版）的逻辑大致如下：

```
[[Set]](obj, propName, value):

  1. 让 desc = 在 obj 自身查找 propName 的属性描述符
  2. 如果 desc 存在且 desc 有 set（是 Setter）:
       → 执行 desc.set.call(obj, value)  ← 触发 Setter！
       → 返回成功 ✅（不在自身创建属性）
  3. 否则（没有 Setter 或 属性不存在）:
       → 在 obj 自身创建/修改 propName 属性，值为 value
       → 返回成功 ✅（普通的属性遮蔽）
```

只有当原型上有 Setter 时才会走分支 2；其他所有情况都走分支 3（普通遮蔽）。

## 四、for...in 循环与原型链

不同的属性遍历方式对原型链的处理方式大相径庭。这是实际开发中容易踩坑的地方：

### `for...in` —— 会遍历到原型链上的可枚举属性

```javascript
function ProtoBase() {}
ProtoBase.prototype.baseProp = "基类属性";
ProtoBase.prototype.baseMethod = function () {};
ProtoBase.prototype.baseArr = [1, 2, 3];

let obj = new ProtoBase();
obj.ownProp = "自身属性";
obj.ownMethod = function () {};
obj.ownArr = ["a", "b"];

console.log("=== for...in 遍历结果 ===");
for (let key in obj) {
  let isOwn = obj.hasOwnProperty(key);
  console.log(`  ${isOwn ? "🏠️" : "🔗"} ${key}: ${typeof obj[key] === 'function' ? '[Function]' : JSON.stringify(obj[key])}`);
}
```

输出：

```
=== for...in 遍历结果 ===
  🏠 ownProp: "自身属性"
  🏠 ownMethod: [Function]
  🏠 ownArr: ["a","b"]
  🔗 baseProp: "基类属性"
  🔗 baseMethod: [Function]
  🔗 baseArr: [1,2,3]
```

可以看到 `for...in` 把**自身属性和原型链上所有可枚举属性**全都遍历到了。注意 `baseProp`、`baseMethod`、`baseArr` 这些定义在原型上的属性也出现了。

### `Object.keys()` / `Object.values()` —— 只遍历自身属性

```javascript
console.log("\n=== Object.keys() 结果 ===");
console.log(Object.keys(obj));
// ["ownProp", "ownMethod", "ownArr"] —— 干净！只有自身属性

console.log("\n=== Object.values() 结果 ===");
console.log(Object.values(obj));
// ["自身属性", [Function], ["a","b"]]
```

### 为什么内置方法不出现在 `for...in` 中？

你可能注意到，即使你的对象继承自 `Object.prototype`，`for...in` 也**不会**遍历到 `toString`、`valueOf`、`hasOwnProperty` 等内置方法。为什么？

因为这些方法在 `Object.prototype` 上的属性描述符中，`enumerable`（可枚举性）被设置为 **`false`**。`for...in` 只会遍历可枚举的属性，所以内置方法被自动过滤掉了。

```javascript
// 验证：toString 是不可枚举的
let desc = Object.getOwnPropertyDescriptor(Object.prototype, 'toString');
console.log(desc.enumerable); // false

// 你仍然可以通过 in 操作符检测到它
console.log('toString' in {}); // true
// 但 for...in 不会显示它
for (let key in {}) {
  if (key === 'toString') console.log("找到了 toString!"); // 永远不会执行
}
```

这种设计是非常明智的——否则每次 `for...in` 遍历一个对象都会输出几十个内置方法名，这对已有代码会造成破坏性的影响。

### 过滤掉继承属性的正确姿势

当你只想遍历自身属性时，有以下几种推荐做法：

```javascript
// 方式 1：for...in + hasOwnProperty 过滤
for (let key in obj) {
  if (obj.hasOwnProperty(key)) {
    console.log(`[自身] ${key}:`, obj[key]);
  }
}

// 方式 2：直接使用 Object.keys()（最简洁）
Object.keys(obj).forEach(key => {
  console.log(`[自身] ${key}:`, obj[key]);
});

// 方式 3：Object.entries() 同时获取键和值
Object.entries(obj).forEach(([key, value]) => {
  console.log(`[自身] ${key}:`, value);
});
```

## 五、经典陷阱：共享的可变状态（Hamster Problem）

这是一个极其经典的原型链面试题/实战陷阱，完美地展示了如果不正确理解属性查找和遮蔽机制，会产生多么诡异的结果。

### 问题代码

```javascript
function Hamster() {}
// ⚠️ 危险！把可变的引用类型放在了原型上
Hamster.prototype.stomach = [];

Hamster.prototype.eat = function (food) {
  // this.stomach 的查找过程：
  // 1. hamster 自身没有 stomach → 沿原型去 Hamster.prototype 上找
  // 2. 找到了！stomach 是一个数组
  // 3. push 操作修改了这个数组
  this.stomach.push(food);
};

let speedy = new Hamster();  // 仓鼠"快快"
let lazy = new Hamster();    // 仓鼠"懒懒"

speedy.eat("胡萝卜");
speedy.eat("苹果");
speedy.eat("坚果");

console.log(speedy.stomach);  // ["胡萝卜", "苹果", "坚果"] ✅ 正常
console.log(lazy.stomach);    // ["胡萝卜", "苹果", "坚果"] 😱 ！！！
// 等一下！！懒懒明明什么都没吃啊！
// 为什么它的胃里有食物？？
```

### 根因分析

问题出在 `eat` 方法中的 `this.stomach.push(food)` 这行代码。让我们追踪它的执行过程：

1. `speedy.eat("胡萝卜")` 开始执行
2. 进入 `eat` 函数体，`this` 绑定为 `speedy`
3. 遇到 `this.stomach` —— 读取属性！开始查找：
   - `speedy` 自身没有 `stomach` 属性
   - 沿 `[[Prototype]]` 到 `Hamster.prototype`
   - **找到了！** `stomoma` 数组在这里
4. `.push("胡萝卜")` —— **直接对这个数组进行了 push 操作**
5. 关键：**这个数组是所有 Hamster 实例共享的同一个对象！**
6. 后来 `lazy.eat(...)` 时，`lazy` 自身同样没有 `stomach`，也找到了同一个共享数组
7. `push` 操作继续往同一个数组里添加元素……

结果就是：**所有仓鼠共用同一个胃！** 快快吃的东西，懒懒也能"看到"。

### 三种解决方案

#### 方案 1：在构造函数中初始化每个实例的独立状态（推荐）

```javascript
function GoodHamster() {
  // 每个 Hamster 实例化时都在自身创建独立的 stomach
  // 这会在自身创建 stomach 属性，"遮蔽"原型上的那个
  this.stomach = [];
}

GoodHamster.prototype.eat = function (food) {
  this.stomach.push(food);
};

let speedy2 = new GoodHamster();
let lazy2 = new GoodHamster();

speedy2.eat("胡萝卜");
speedy2.eat("苹果");

console.log(speedy2.stomach);  // ["胡萝卜", "苹果"] ✅
console.log(lazy2.stomach);    // [] ← 空！正确！懒懒确实什么都没吃
```

**原理**：构造函数中的 `this.stomach = []` 是一个**写入操作**，它在 `speedy2` 和 `lazy2` 各自的身上创建了独立的 `stomach` 属性（遮蔽）。之后 `eat` 方法中的 `this.stomach.push(food)` 读取 `this.stomach` 时，在自身（深度 1）就能找到，不需要去原型上了。

#### 方案 2：在方法中使用赋值而非直接修改

```javascript
function AltHamster() {}

AltHamster.prototype.stomach = [];
AltHamster.prototype.eat = function (food) {
  // 先用 = 赋值（写入自身），然后对新数组进行操作
  this.stomach = this.stomach.slice(); // 复制一份到自身（如果有）或创建空数组
  this.stomach.push(food);
};

let a = new AltHamster();
let b = new AltHamster();
a.eat("X");
a.eat("Y");
console.log(a.stomach);  // ["X", "Y"]
console.log(b.stomach);  // [] ✅
```

#### 方案 3：根本不在原型上放可变状态

```javascript
// 最佳实践：只在原型上放不变的数据和方法
// 可变的状态永远在构造函数中初始化
function BestHamster(name) {
  this.name = name;          // 每个实例名字不同 → 构造函数参数
  this.stomach = [];         // 每个实例胃不同 → 构造函数初始化
  this.createdAt = Date.now(); // 每个实例创建时间不同
}

// 原型上只放不变的方法和行为
BestHamster.prototype.eat = function (food) {
  this.stomach.push(food);
  return this;
};
BestHamster.prototype.digest = function () {
  this.stomach = []; // 清空自己的胃
  return this;
};
```

**经验法则**：

> **永远不要在 `prototype` 上放置可变的引用类型数据（数组、普通对象）。** 原型上只应该存放：
> - **不变的数据常量**（如默认配置、版本号、类型名称）
> - **方法的定义**（函数引用本身是不可变的，虽然执行结果可能变）
> - **Symbol 类型的唯一标识符**（如 `Symbol.iterator`）

## 六、delete 操作与原型链

`delete` 操作用于删除对象自身的属性。它对原型链上的属性**无效**——你不能通过 `delete` 来删除原型上的东西：

```javascript
function Demo() {}
Demo.prototype.sharedProp = "共享值";
Demo.prototype.sharedFn = function () {};

let d = new Demo();
d.ownProp = "自身值";

// 删除自身属性
delete d.ownProp;
console.log(d.ownProp);           // undefined ✅ 已删除

// 尝试删除继承来的属性
delete d.sharedProp;
console.log(d.sharedProp);         // "共享值" ❌ 删除失败！
// delete 只能删除自身属性（Own Property）
// sharedProp 不在 d 自身上（它在 prototype 上）
// 所以 delete 无效

// 但你可以直接删除原型上的属性（不推荐！）
delete Demo.prototype.sharedProp;
let d2 = new Demo();
console.log(d2.sharedProp);         // undefined ← 这次真的没了（因为原型上的属性被删了）
```

**注意**：`delete` 只对**自有属性**有效。对于继承来的属性，`delete` 返回 `true`（不报错）但实际上什么都没发生——因为根本没有东西可删。

## 七、性能考量：原型链长度的影响

### 查找深度的性能含义

理论上，原型链越长（层级越深），属性查找就越慢——需要经过更多的 `[[Prototype]]` 跳转和更多的 `hasOwnProperty` 检查。

```javascript
// 测试不同深度下的属性查找性能
const DEPTH = 5000;

// 创建一条很深的原型链
let root = { value: "root", deepFunc() { return "from root"; } };
let current = root;
for (let i = 0; i < DEPTH; i++) {
  current = Object.create(current);
  current.value = `level-${DEPTH - i}`;
  current.deepFunc = function () { return `from level-${DEPTH - i}`; };
}
let deepObj = current;

// 性能测试
const ITERS = 100000;

console.time("deep property read");
for (let i = 0; i < ITERS; i++) {
  let v = deepObj.value;      // 每次都要沿 5000 层链查找！
  let f = deepObj.deepFunc(); // 同上
}
console.timeEnd("deep property read");

// 对比：浅层查找（1 层）
let shallow = { value: "shallow", shallowFunc() { return "shallow"; } };
console.time("shallow property read");
for (let i = 0; i < ITERS; i++) {
  shallow.value;
  shallow.shallowFunc();
}
console.timeEnd("shallow property read");
```

在 V8 等现代 JS 引擎中的典型结果：

| 原型链深度 | 10万次查找耗时 | 相对速度 |
|------------|-------------|---------|
| 1 层（浅层） | ~3~8ms | **1x**（基准） |
| 100 层 | ~10~20ms | ~2~3x |
| 1000 层 | ~50~150ms | ~15~25x |
| 5000 层 | ~300~800ms | ~50~100x |

深层原型链确实会带来显著的性能开销。但在实际项目中，正常的原型链深度通常只有 3~5 层（`Instance → Constructor.prototype → Parent.prototype → Object.prototype → null`），这种深度的查找开销在现代引擎中已经被优化得极小（纳秒级别），完全可以忽略不计。

### 现代引擎的优化技术

V8 等现代 JavaScript 引擎使用了多项技术来让原型链查找变得飞快：

**1. 内联缓存（Inline Cache, IC）**

```javascript
function getX(obj) {
  return obj.x;  // 反复访问 .x 属性
}
// 多次调用后，V8 可能记住：
// "哦，obj 的 Hidden Class 是 Map<x:num>，
//  偏移量 0 处就是 x 的值"
// 下次直接按偏移量读取，跳过完整的查找流程
```

**2. 隐藏类（Hidden Class）预测**

```javascript
// 引擎观察到同一类型的对象总是具有相同的原型结构
// 于是它将原型链的结构信息编码到对象中
// 后续查找可以利用这个预计算信息加速
```

**但这些优化的前提是：原型链结构保持稳定。** 如果你频繁地修改对象的 `[[Prototype]]`（通过 `setPrototypeOf`），这些优化假设会被打破，导致**去优化（Deoptimization）**，后续代码反而变得更慢。

## 八、总结：三大核心规则

### 原型链机制的三大支柱

| 规则 | 描述 | 通俗类比 |
|------|------|---------|
| **读取沿链向上** | `obj.prop` 从自身开始，沿 `[[Prototype]]` 逐层向上查找，直到找到或到达 `null` | 想在公司内部找不到文件→ 去公共资料室查 → 再去集团资料室查…… |
| **写入留在原地（遮蔽）** | `obj.prop = value` 直接在自身创建/修改属性，不影响原型链（Setter 除外） | 自己的文件柜里放一份资料，不再去翻总部的原件 |
| **this 始终指向调用者** | 无论方法在自身还是原型上，`this` 始终是调用 `obj.method()` 时的 `obj` | 按《操作手册》干活时，操作的对象是你自己的工位，不是那本手册 |

### 属性查找速查表

| 操作 | 查找路径 | 是否影响原型 | 是否受原型影响 |
|------|---------|------------|---------------|
| `obj.prop`（读取） | 自身 → 原型 → 原型的原型 … | 否 | ✅ 是（继承来的值） |
| `obj.prop = val`（写入） | 仅自身（创建或覆盖属性） | 否 | ❌ 否（Setter 除外） |
| `delete obj.prop`（删除） | 仅自身 | 否 | ❌ 否 |
| `for...in`（遍历） | 自身 + 原型链上所有可枚举属性 | 否 | ✅ 包含继承属性 |
| `Object.keys()` | 仅自身属性 | 否 | ❌ 不包含 |
| `in` 操作符 | 自身 + 原型链 | 否 | ✅ 包含继承属性 |

### 最佳实践建议

| 建议 | 说明 |
|------|------|
| **数据放实例，方法放原型** | 数据（每个实例不同）用 `this.x = x` 在构造函数中设置；方法（所有实例共享）放 `F.prototype` 上 |
| **不在原型上放可变状态** | 绝不在原型上放数组、普通对象等可变引用类型；避免 Hamster Problem |
| **善用 hasOwnProperty 过滤** | `for...in` 遍历时务必过滤，除非你确实需要包含继承属性 |
| **控制原型链深度在 3~5 层** | 过深的继承链会导致性能下降、代码复杂度增加、调试困难 |
| **理解 Setter 的拦截能力** | 如果原型上有 Setter，赋值操作会被它拦截，不会产生遮蔽 |
| **优先使用 class 语法** | `class` 自动处理好原型关系，减少手动出错的机会 |

> **一句话总结原型链查找的本质**：读取是一场"向上追寻"的旅程——当你在当前对象上找不到想要的答案时，就去问它的"父辈"（原型），父辈没有就去问"祖辈"（原型的原型）……一直问到家族最顶层的祖先（`null`）为止。而写入则是一次"就地定居"——不管祖先们有什么记录，你要么在自己的土地上盖房子（遮蔽原型属性），要么通过祖先留下的特殊渠道（Setter）来间接修改。这套"读上行、写留原地、this 指向调用者"的精密协作机制，构成了 JavaScript 原型继承的全部奥秘。
