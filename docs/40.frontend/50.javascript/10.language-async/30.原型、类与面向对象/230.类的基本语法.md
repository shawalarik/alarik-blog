# 类的基本语法 —— 声明、表达式、字段、方法、静态成员

## 从"配方"到"模具"：为什么需要 class

在 ES6 之前，JavaScript 创建对象的"标准流程"是通过构造函数和原型链的组合。你先写一个函数当作构造器，然后往它的 `prototype` 上挂载方法，最后用 `new` 关键字来实例化。这套机制能工作，但它更像是一种"约定俗成"的编程模式，而非语言层面的一等公民支持。开发者需要手动维护 `prototype`、记住不要在构造器里返回一个对象（否则 `new` 的行为会变）、小心处理 `this` 的指向……这些细节分散了注意力，让代码的意图变得不够直观。

ES6 引入的 `class` 语法并不是凭空创造了一套全新的面向对象体系——它本质上仍然是基于原型的继承机制，只是提供了一种更清晰、更结构化的语法糖。但这个"糖"非常关键：它把原本散落在各处的操作（定义构造函数、挂载原型方法、设置静态属性）收敛到了一个语法块内部，让代码的**声明性**大幅提升。你可以把 `class` 理解为一张"模具"或"蓝图"：它描述了一类对象应该具备什么样的结构和行为，而每一个通过 `new` 创建出来的实例，就是按照这张蓝图生产出来的"产品"。

## 类的基本声明

### 声明语法与基本结构

类的声明使用 `class` 关键字，后跟类名（通常采用 PascalCase 命名惯例），然后是一对花括号包裹的类体：

```javascript
class User {
  constructor(name) {
    this.name = name;
  }

  sayHi() {
    console.log(`你好，我是 ${this.name}`);
  }
}

const user = new User('张三');
user.sayHi(); // 你好，我是 张三
```

这段代码看起来很直观，但每一行背后都有值得深入理解的设计逻辑。

`constructor` 是一个特殊的方法——它是类的"初始化函数"。当你用 `new User('张三')` 创建实例时，引擎会自动执行 `constructor`，并把传入的参数原封不动地交给它。`constructor` 内部的 `this` 指向的就是新创建的那个实例对象，所以 `this.name = name` 实际上是在给这个新对象添加一个 `name` 属性。这和传统构造函数的行为完全一致，只不过现在它被显式地标记为"这是初始化代码"，阅读代码的人一眼就能识别出来。

`sayHi()` 则是一个普通的实例方法。注意这里有一个非常重要的细节：**类中定义的方法默认是不可枚举的**。这意味着如果你用 `for...in` 或 `Object.keys()` 遍历一个类实例，这些方法是不会出现的。这个设计是有意为之的——方法通常代表的是"行为"，而不是"数据"，遍历时应该只关注数据属性。相比之下，如果用传统的 `User.prototype.sayHi = function(){}` 方式定义方法，这个方法默认是可枚举的，这在某些场景下会导致意外的副作用。

### 类的本质：它仍然是一个函数

虽然 `class` 看起来像是一种全新的类型，但在 JavaScript 底层，**类实际上就是函数**：

```javascript
class User {}

console.log(typeof User); // 'function'
```

这不是比喻或近似，而是事实：`User` 本身就是一个函数对象。更准确地说，它就是那个 `constructor` 方法所对应的函数。当你写下一个类声明时，引擎做的事情大致等价于：

```javascript
// 引擎内部的简化模型
function User(...) { /* constructor 中的代码 */ }
User.prototype = {
  constructor: User,
  sayHi() { /* ... */ }
};
```

当然，实际实现远比这个简化模型复杂（后面会详细讨论），但核心思路是清晰的：**类的名称绑定到一个函数上，类中定义的方法被放置到该函数的 `prototype` 对象上**。

这意味着所有关于函数的特性都适用于类：它们可以被赋值给变量、作为参数传递、存储在数据结构中。同时，关于原型的一切知识也依然有效：实例通过 `__proto__`（或 `Object.getPrototypeOf`）链接到类的 `prototype`，属性查找沿着这条链向上进行。

### 类与普通函数的关键区别

尽管类本质上是函数，但它们之间存在几个重要的差异，这些差异是 JavaScript 引擎为了提供更安全的面向对象编程体验而刻意设置的"护栏"。

第一个也是最明显的差异是：**类不能像普通函数那样直接调用**。尝试不使用 `new` 来调用一个类会抛出错误：

```javascript
class User {
  constructor(name) {
    this.name = name;
  }
}

User('张三'); // TypeError: Class constructor User cannot be invoked without 'new'
```

这是因为类函数内部带有一个特殊的标记 `[[IsClassConstructor]]`，当引擎检测到调用的是一个带有此标记的函数且没有使用 `new` 时，会直接拒绝执行。这是一个非常实用的安全特性——在 ES5 时代，忘记写 `new` 是一种常见的 bug，它会导致 `this` 指向全局对象（非严格模式）或者抛出错误（严格模式），而这种错误的排查往往需要不少时间。类从根本上杜绝了这种可能性。

第二个差异是：**类体自动运行在严格模式之下**。即使你没有在文件顶部写 `"use strict"`，类内部的所有代码都会被当作严格模式来处理。这意味着你不能使用未声明的变量、`this` 在普通函数中不会自动指向全局对象、`arguments.callee` 不可用等等。这个设计减少了"意外行为"的发生空间，让代码的可预测性更强。

第三个差异前面已经提到：**类中定义的方法是不可枚举的**。这一点可以通过以下代码验证：

```javascript
class User {
  sayHi() {}
}

console.log(
  Object.getOwnPropertyDescriptor(User.prototype, 'sayHi').enumerable
); // false
```

而在传统的原型写法中：

```javascript
function User() {}
User.prototype.sayHi = function() {};

console.log(
  Object.getOwnPropertyDescriptor(User.prototype, 'sayHi').enumerable
); // true
```

这种差异在大多数日常开发中不会造成明显影响，但在需要对对象进行序列化或属性遍历的场景下就变得至关重要。

第四个差异涉及一个不太常被讨论的细节：**类的方法没有 `prototype` 属性**（或者说它们的 `prototype` 是 `undefined`）。在 ES5 中，每个函数都有一个 `prototype` 对象，即使你不打算用它来做继承。但对于类的方法来说，它们被设计为不可被用作构造器，所以不需要 `prototype`。这也是为什么你不能用 `new` 调用一个类的方法——它根本就没有构建新对象所需的原型信息。

```javascript
class User {
  sayHi() {}
}

console.log(User.prototype.hasOwnProperty('sayHi'));     // true
console.log(typeof User.prototype.sayHi.prototype);      // undefined
new User.prototype.sayHi(); // TypeError: User.prototype.sayHi is not a constructor
```

## 类表达式：把类当作值来使用

除了使用 `class Name {...}` 这种声明形式，JavaScript 还允许你使用**类表达式**——即把类定义当作一个值，可以赋给变量、传给函数、从函数返回。这让类具备了"一等公民"的地位，极大地增强了编程灵活性。

### 基本类表达式

最简单的类表达式就是把一个匿名类赋值给变量：

```javascript
const User = class {
  constructor(name) {
    this.name = name;
  }

  introduce() {
    console.log(`我叫${this.name}`);
  }
};

const user = new User('李四');
user.introduce(); // 我叫李四
```

这里的 `class {...}` 和之前的 `class User{...}` 唯一的区别在于：后者会创建一个名为 `User` 的绑定（在当前作用域内），而前者只是产生了一个匿名的类对象并将其赋给了变量。两者创建出来的类在使用上没有任何区别。

### 命名类表达式

类表达式也可以拥有自己的名字，这被称为"命名类表达式"。这个名字只在类内部可见，类似于函数表达式中的作用域规则：

```javascript
const User = class MyClass {
  constructor(name) {
    this.name = name;
  }

  whoAmI() {
    // MyClass 在这里可以访问到
    console.log(MyClass);
    // 但在外部访问不到
  }
};

const user = new User('王五');
user.whoAmI();        // [class MyClass]

console.log(MyClass); // ReferenceError: MyClass is not defined
```

命名类表达式的主要用途有两个：一是用于递归引用（比如类内部某个方法需要引用自身），二是调试时在堆栈跟踪中显示更有意义的名称。在实际开发中，匿名类表达式更为常见，因为变量名本身就已经提供了足够的标识信息。

### 动态创建类：工厂模式

由于类表达式是一个值，你可以在运行时动态地生成类。这开启了一种称为"类工厂"的编程模式：

```javascript
function createUserClass(greeting) {
  return class {
    constructor(name) {
      this.name = name;
      this.greeting = greeting;
    }

    greet() {
      console.log(`${this.greeting}，${this.name}！`);
    }
  };
}

const ChineseUser = createUserClass('你好');
const EnglishUser = createUserClass('Hello');

const chinese = new ChineseUser('小明');
const english = new EnglishUser('Alice');

chinese.greet(); // 你好，小明！
english.greet(); // Hello，Alice！
```

这种模式在一些框架和库中被广泛使用。例如，某些 ORM（对象关系映射）库会根据数据库表的结构动态生成对应的 Model 类；React 的高阶组件模式本质上也是在动态地"包装"组件类。类表达式的存在让这类元编程变得更加自然和简洁。

可以把这个过程想象成一家"定制工厂"。普通的类声明就像是一个固定的模具，只能生产同一种规格的产品；而类表达式则像是可以根据客户需求随时调整参数的"柔性生产线"——你需要什么规格的模具，工厂就在现场为你制造一个。

## 构造器（Constructor）：对象的诞生时刻

### constructor 的基本用法与职责

`constructor` 是类中最特殊的一个方法。它在每次使用 `new` 创建实例时被自动调用，负责完成对象的初始化工作。"初始化"这个词听起来很简单，但实际上包含了几个层面的含义。

最基本的职责是为实例设置初始状态——也就是赋值各种属性：

```javascript
class Book {
  constructor(title, author, price) {
    this.title = title;
    this.author = author;
    this.price = price;
    this.createdAt = new Date();
  }
}
```

这里 `title`、`author`、`price` 是外部传入的数据，而 `createdAt` 是构造器自行计算的衍生数据。构造器的工作就是把这些信息整合到新对象身上，让它变成一个"有状态的、准备好被使用的"实体。

### constructor 不是必须的

如果一个类没有显式定义 `constructor`，引擎会自动提供一个空的构造器：

```javascript
class Animal {}

// 等价于：
// class Animal {
//   constructor() {}
// }

const animal = new Animal();
console.log(animal); // Animal {}
```

空构造器的存在保证了 `new Animal()` 这样的调用总是合法的。这对于那些不需要任何初始化逻辑的简单类来说非常方便——你只需要定义方法就够了。

### constructor 中 return 的特殊行为

构造器中可以使用 `return` 语句，但它的行为和普通函数有所不同。如果 `return` 返回的是一个对象，那么 `new` 表达式的结果就是这个对象而不是新创建的实例：

```javascript
class SpecialCase {
  constructor(name) {
    this.name = name;

    // 特殊情况：返回一个不同的对象
    if (name === 'singleton') {
      return { special: true, message: '这是一个特殊的单例' };
    }
  }
}

const normal = new SpecialCase('普通');
console.log(normal.name);         // 普通
console.log(normal.special);      // undefined

const special = new SpecialCase('singleton');
console.log(special.special);     // true
console.log(special.message);     // 这是一个特殊的单例
console.log(special.name);        // undefined —— this.name 被丢弃了
```

如果 `return` 返回的不是对象（或者说返回的是原始值如数字、字符串、`undefined`、`null`），则会被忽略，`new` 正常返回新创建的实例。这种行为是从 ES5 继承下来的，在某些高级设计模式（如单例模式、对象池）中有应用，但在日常开发中极少使用。

## 实例方法：对象的行为定义

### 定义与调用

类中最常见的成员就是实例方法。它们定义在类体内，通过类的实例来调用：

```javascript
class Calculator {
  add(a, b) {
    return a + b;
  }

  subtract(a, b) {
    return a - b;
  }

  multiply(a, b) {
    return a * b;
  }
}

const calc = new Calculator();
console.log(calc.add(3, 5));       // 8
console.log(calc.subtract(10, 4));  // 6
console.log(calc.multiply(7, 2));   // 14
```

实例方法的调用方式决定了 `this` 的指向：当你用 `calc.add(3, 5)` 调用时，`add` 内部的 `this` 就是 `calc` 这个实例。这是 JavaScript 中"方法调用"的标准行为——点号左边的对象成为 `this` 的绑定目标。

### 方法存储在哪里？

这是一个经常被误解的问题。很多人直觉上认为每个实例都有一份独立的方法副本，就像每个对象有自己的属性一样。但实际上：

```javascript
class Dog {
  bark() {
    console.log('汪汪！');
  }
}

const dog1 = new Dog();
const dog2 = new Dog();

console.log(dog1.bark === dog2.bark);          // true
console.log(dog1.bark === Dog.prototype.bark); // true
```

`dog1.bark` 和 `dog2.bark` 是同一个函数！它们都是 `Dog.prototype.bark` 这个方法的引用。当你在实例上调用方法时，引擎首先在实例自身查找该方法名，找不到时就顺着原型链向上找，最终在 `prototype` 上找到并执行它。

这种设计的优势在于**节省内存**。假设你创建了 1000 个 `Dog` 实例，如果每个实例都存一份 `bark` 函数的副本，那就是 1000 份相同的代码占用内存。而通过原型共享的方式，内存中只需要存一份方法，1000 个实例只是各自持有对这个方法的引用而已。

可以把原型想象成一本"公共手册"。每个员工（实例）办公桌上并没有各自放一本完整的手册，而是大家共享走廊里那一本。当某个员工需要查阅某条规则时，他走到走廊拿起手册翻到对应页码就行。这本手册就是 `prototype`，上面的每一条规则就是一个方法。

## Getter 与 Setter：属性的拦截门卫

### 基本语法

类支持 getter 和 setter，让你可以在读取或写入属性时插入自定义逻辑：

```javascript
class Circle {
  constructor(radius) {
    this._radius = radius; // 使用下划线前缀表示"内部属性"
  }

  get radius() {
    console.log('正在读取半径...');
    return this._radius;
  }

  set radius(value) {
    console.log(`正在设置半径为 ${value}...`);
    if (value < 0) {
      throw new Error('半径不能为负数');
    }
    this._radius = value;
  }

  get diameter() {
    return this._radius * 2;
  }

  set diameter(value) {
    this._radius = value / 2;
  }

  get area() {
    return Math.PI * this._radius ** 2;
  }
}

const circle = new Circle(5);
console.log(circle.radius);   // 正在读取半径... → 5
circle.radius = 10;           // 正在设置半径为 10...
console.log(circle.diameter); // 20
console.log(circle.area);     // 314.159...

circle.diameter = 30;         // 这会触发 setter，将 _radius 设为 15
console.log(circle.radius);   // 15
```

getter 和 setter 让你可以对外暴露一个"虚拟属性"，其值的计算或验证逻辑被封装在类的内部。对于使用者来说，他们只是在读写一个普通的属性，完全不需要知道背后发生了什么。

### 为什么需要下划线前缀？

你可能注意到了上面代码中使用了 `_radius` 而不是 `radius` 作为实际的存储属性。这是因为如果在 setter 中写成 `this.radius = value`，就会再次触发 setter 本身，导致无限递归直到栈溢出：

```javascript
class BadCircle {
  set radius(value) {
    this.radius = value; // 💥 无限递归！又调用了自己
  }
}
```

使用 `_radius`（或其他命名约定）来区分"对外接口"和"内部存储"是一种常见的做法。需要注意的是，这只是一种**约定**，并非语言强制规则——JavaScript 引擎并不会因为下划线而对属性做任何特殊处理。有些团队喜欢使用 `#radius`（私有字段语法）来实现真正的私有性，这会在后续章节详细介绍。

### 实际应用场景

Getter 和 setter 在实际开发中有多种用途。最常见的场景之一是**数据校验**：

```javascript
class User {
  constructor(name, age) {
    this.name = name;  // 会触发 setter
    this.age = age;    // 会触发 setter
  }

  set name(value) {
    if (typeof value !== 'string') {
      throw new Error('姓名必须是字符串');
    }
    if (value.trim().length === 0) {
      throw new Error('姓名不能为空');
    }
    this._name = value.trim();
  }

  get name() {
    return this._name;
  }

  set age(value) {
    if (!Number.isInteger(value)) {
      throw new Error('年龄必须是整数');
    }
    if (value < 0 || value > 150) {
      throw new Error('年龄必须在 0 到 150 之间');
    }
    this._age = value;
  }

  get age() {
    return this._age;
  }
}

const user = new User(' 小明 ', 25);
console.log(user.name); // 小明 （已自动去除首尾空白）
user.age = -5;          // Error: 年龄必须在 0 到 150 之间
```

另一个典型用途是**计算属性/派生属性**。像前面的 `Circle` 示例中，`area` 只有一个 getter 没有 setter——因为它是一个完全由 `radius` 派生出来的值，不应该被独立修改。这种"只读计算属性"的模式在表示具有内在关联关系的数据时非常有用。

可以把 getter/setter 想象成一家公司的"前台接待员"。外界想要见老板（获取属性值）或给老板送东西（设置属性值），都必须经过前台。前台可以检查访客身份（数据校验）、记录来访日志（副作用）、甚至婉拒不合理的请求（抛出异常），而老板本人（真正的数据存储）始终待在后台不被直接接触。

## 计算属性名称：动态的方法名

### 语法与示例

和对象字面量一样，类的方法名也支持使用方括号语法来进行动态计算：

```javascript
const methodName = 'greet';

class Greeter {
  [methodName]() {
    console.log('你好！');
  }

  ['say' + 'Hello']() {
    console.log('Hello!');
  }

  [Symbol.iterator]() {
    let step = 0;
    return {
      next() {
        step++;
        if (step <= 3) {
          return { value: step, done: false };
        }
        return { done: true };
      }
    };
  }
}

const greeter = new Greeter();
greeter.greet();    // 你好！

// 迭代器协议
for (const value of greeter) {
  console.log(value); // 1, 2, 3
}
```

计算属性名称让方法名不再局限于静态的标识符。你可以在运行时根据条件、配置或用户输入来决定方法叫什么名字。这在编写框架、库或者需要高度动态化的系统时特别有用。

### 实际应用场景

一个典型的使用场景是根据配置批量生成处理器方法：

```javascript
function createHandlerClass(events) {
  const handlers = {};
  for (const event of events) {
    handlers[`on${event.charAt(0).toUpperCase() + event.slice(1)}`] = function(data) {
      console.log(`[事件: ${event}]`, data);
    };
  }

  return class {
    constructor() {
      // 将所有方法挂载到 prototype 上
      Object.assign(this.constructor.prototype, handlers);
    }
  };
}

const EventHandler = createHandlerClass(['click', 'hover', 'focus']);
const handler = new EventHandler();

handler.onClick({ x: 100, y: 200 });   // [事件: click] { x: 100, y: 200 }
handler.onHover({ element: 'button' }); // [事件: hover] { element: 'button' }
handler.onFocus({ target: 'input' });   // [事件: focus] { target: 'input' }
```

计算属性名称的存在使得类可以更加灵活地适应变化的需求，而不需要在编码阶段就把一切固定下来。这是一种"以不变应万变"的策略——类的结构保持稳定，但具体的方法名和行为可以根据上下文动态确定。

## 类字段（Class Fields）：声明式的属性定义

### 什么是类字段

类字段（也称类属性）是 ES2022 正式纳入标准的特性，允许你在类体中直接声明属性及其初始值，而不必等到 `constructor` 中再赋值：

```javascript
class Person {
  species = '智人';           // 类字段，有默认值
  name;                        // 类字段，值为 undefined
  createdAt = new Date();      // 类字段，每次创建实例时求值

  constructor(name) {
    this.name = name;          // 这里覆盖了字段的默认值
  }
}

const person = new Person('赵六');
console.log(person.species);   // 智人
console.log(person.name);      // 赵六
console.log(person.createdAt); // 当前的日期时间
```

类字段的引入解决了一个长期困扰 JavaScript 开发者的问题：**属性定义的位置不一致**。在没有类字段的时代，一个类的属性一部分可能出现在 `constructor` 中（通过 `this.xxx = yyy`），另一部分可能在某个方法中被临时添加。这使得要了解一个类到底有哪些属性，你需要通读整个类体的全部代码。有了类字段之后，所有的属性声明都被集中到了类体的顶部，一目了然。

### 字段与 constructor 的执行顺序

类字段的初始化发生在 `constructor` 执行**之前**。更准确地说，执行顺序是：

1. 类字段的初始化（按声明顺序）
2. `constructor` 的执行

```javascript
class OrderDemo {
  first = console.log('① 字段 first 初始化');
  second = console.log('② 字段 second 初始化');

  constructor() {
    console.log('③ constructor 执行');
  }

  third = console.log('④ 字段 third 初始化');  // 注意：也在 constructor 之前！
}
// 输出顺序：① → ② → ④ → ③
new OrderDemo();
```

是的，无论字段写在类体的哪个位置（甚至在 `constructor` 之后），它们的初始化都优先于 `constructor`。这个规则可能会让初学者感到意外，但它确保了 `constructor` 执行时所有字段都已经有了初始值——哪怕只是 `undefined`。这意味着你永远不用担心"访问了一个从未被声明的属性"这种情况（虽然值可能是 `undefined`，但至少属性是存在的）。

### 字段存储在实例上，而不是原型上

这是一个至关重要的区分点。类方法和类字段的存储位置不同：

```javascript
class StorageTest {
  protoMethod() {}            // 存储在 prototype 上
  instanceField = 42;         // 存储在每个实例上
}

const a = new StorageTest();
const b = new StorageTest();

console.log(a.protoMethod === b.protoMethod);              // true —— 共享同一份
console.log(a.instanceField === 42 && b.instanceField === 42); // true —— 值相同
a.instanceField = 100;
console.log(b.instanceField);                               // 42 —— 各自独立
console.log(StorageTest.prototype.instanceField);           // undefined —— 不在原型上
```

方法存储在 `prototype` 上是因为方法是"行为"——所有实例的行为逻辑是一样的，没必要重复存储。而字段通常代表每个实例独有的"状态"——每个人的名字、年龄、账户余额都不一样，所以每个实例都需要自己的副本。

可以用"公寓楼"来类比：prototype 就像大楼里的"公共设施区"——健身房、会议室、花园，所有住户共享使用，只有一套；而每个住户（实例）自己的房间就是字段存储的地方，里面放的都是私人物品，互不影响。

## 用类字段绑定 this：解决回调地狱中的 this 丢失问题

### 问题根源：this 丢失现象

在 JavaScript 中，`this` 的值取决于函数的**调用方式**，而不是定义位置。当一个方法作为回调函数传递出去时，它通常会失去原来的 `this` 绑定：

```javascript
class Timer {
  constructor(seconds) {
    this.seconds = seconds;
  }

  tick() {
    this.seconds--;
    console.log(`剩余 ${this.seconds} 秒`);
    if (this.seconds <= 0) {
      console.log('时间到！');
      clearInterval(this.timer);
    }
  }

  start() {
    this.timer = setInterval(this.tick, 1000);
    //                ^^^^^^^^
    // 这里只是传递了 tick 方法的引用，没有保留 this 绑定！
  }
}

const timer = new Timer(3);
timer.start();
// 剩余 NaN 秒 ← this.seconds 变成了 undefined（因为 this 不再是 timer）
// 剩余 NaN 秒
// ...
```

问题的本质在于：`setInterval(this.tick, 1000)` 只是提取了 `tick` 这个函数的引用并交给定时器。当定时器在 1 秒后调用 `tick()` 时，调用方式是"裸调用"——没有点号，没有 `.call()`，没有 `.apply()`——此时 `this` 在严格模式下是 `undefined`，在非严格模式下是全局对象。无论是哪种情况，都不是我们期望的 `timer` 实例。

这种现象在很多地方都会出现：`setTimeout`、事件监听器、`Promise.then`、数组方法（`map`、`filter` 等）的回调……只要方法被当作"值"传递出去而不是直接调用，就有可能遇到这个问题。

### 解决方案一：箭头函数 + 类字段

利用箭头函数没有自己的 `this` 这一特性，结合类字段语法，可以得到一个非常优雅的解决方案：

```javascript
class Timer {
  constructor(seconds) {
    this.seconds = seconds;
  }

  tick = () => {             // 箭头函数定义为类字段
    this.seconds--;
    console.log(`剩余 ${this.seconds} 秒`);
    if (this.seconds <= 0) {
      console.log('时间到！');
      clearInterval(this.timer);
    }
  };

  start() {
    this.timer = setInterval(this.tick, 1000);
    // 现在 this.tick 已经是一个绑定了正确 this 的函数了
  }
}

const timer = new Timer(3);
timer.start();
// 剩余 2 秒 ✓
// 剩余 1 秒 ✓
// 时间到！✓
```

这段代码能正常工作的原因在于：**箭头函数定义在类字段中，而类字段在实例上创建**。箭头函数不会创建自己的 `this`，它会从外层作用域捕获 `this`——在这里外层就是正在构建的实例，所以 `this` 正确地指向了这个实例本身。更重要的是，因为 `tick` 现在是实例上的一个属性（而不是原型上的方法），`setInterval(this.tick, 1000)` 传递出去的这个函数已经永久性地绑定好了正确的 `this`。

### 解决方案对比

除了箭头函数字段之外，还有几种常见的替代方案：

```javascript
// 方案二：在 constructor 中 bind
class TimerV2 {
  constructor(seconds) {
    this.seconds = seconds;
    this.tick = this.tick.bind(this); // 手动绑定
  }

  tick() { /* ... */ }
  start() { this.timer = setInterval(this.tick, 1000); }
}

// 方案三：在调用处使用箭头函数包裹
class TimerV3 {
  tick() { /* ... */ }
  start() {
    this.timer = setInterval(() => this.tick(), 1000); // 箭头函数包裹
  }
}

// 方案四：在调用处使用 .bind()
class TimerV4 {
  tick() { /* ... */ }
  start() {
    this.timer = setInterval(this.tick.bind(this), 1000); // 每次 bind
  }
}
```

四种方案的对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 箭头函数字段 | 一次性绑定，语义清晰 | 每个实例都有独立的函数副本 |
| constructor 中 bind | 传统方案，兼容性好 | 需要在 constructor 中逐个绑定 |
| 调用处箭头函数 | 不改变方法定义方式 | 每次调用都创建新的箭头函数 |
| 调用处 bind | 显式表达意图 | 同上，且有性能开销 |

在实际项目中，**箭头函数字段**通常是最佳选择。它的代码最简洁、意图最明确，而且现代 JavaScript 引擎对这种模式做了大量优化。至于"每个实例有独立副本"带来的额外内存开销，在绝大多数应用场景下都可以忽略不计——除非你要创建数十万个实例（这种情况本身就说明设计可能有问题）。

### 内存代价的理性看待

很多开发者听到"每个实例一份函数副本"就会担心性能问题。让我们量化一下：

```javascript
class WithArrowMethod {
  handleClick = () => {};  // 每个实例一份副本
}

class WithPrototypeMethod {
  handleClick() {}         // 所有实例共享一份
}
```

假设一个函数对象大约占用几十到几百字节（包含闭包信息等）。即使按较大的估计 500 字节计算，创建 10,000 个实例也不过多占用约 5MB 内存。对于一个 Web 应用来说，这点内存消耗完全可以接受。真正需要警惕的是那种"无限制创建实例"的架构设计，而不是箭头函数字段本身。

## 静态成员（Static Members）：属于类本身的属性和方法

### 静态方法：不依赖实例的工具函数

使用 `static` 关键字定义的方法属于类本身，而不是类的实例。它们通过类名直接调用：

```javascript
class MathHelper {
  static add(a, b) {
    return a + b;
  }

  static multiply(a, b) {
    return a * b;
  }

  static factorial(n) {
    if (n < 0) return undefined;
    if (n === 0 || n === 1) return 1;
    let result = 1;
    for (let i = 2; i <= n; i++) {
      result *= i;
    }
    return result;
  }
}

// 通过类名直接调用，无需创建实例
console.log(MathHelper.add(3, 5));           // 8
console.log(MathHelper.factorial(5));         // 120

const helper = new MathHelper();
helper.add(1, 2); // 可以调用，但不推荐 —— 它不是一个"实例行为"
```

静态方法的核心特征是：**它们不依赖于任何特定实例的状态**。一个加法运算不需要知道"谁在加"、阶乘计算也不关心"谁在算"——输入参数确定了，输出就确定了。这正是静态方法适用的场景：纯工具函数、工厂方法、格式化工具等。

从技术角度看，静态方法是定义在**类构造函数本身**上的属性，而不是 `prototype` 上：

```javascript
class Example {
  static staticMethod() {}
  instanceMethod() {}
}

console.log(typeof Example.staticMethod);               // 'function'
console.log(typeof Example.prototype.instanceMethod);   // 'function'
console.log(typeof Example.staticMethod === 'function'); // true
```

### 静态方法的实际应用

#### 工厂方法模式

静态方法最常见的用途之一是作为"工厂"来创建实例。相比于直接使用 `new`，工厂方法可以有更具描述性的名称，还可以封装复杂的创建逻辑：

```javascript
class Color {
  constructor(r, g, b, a = 1) {
    this.r = r;
    this.g = g;
    this.b = b;
    this.a = a;
  }

  // 从十六进制字符串创建
  static fromHex(hex) {
    const result = /^#?([a-f\d]{2})([a-f\d]{2})([a-f\d]{2})$/i.exec(hex);
    if (!result) {
      throw new Error('无效的十六进制颜色值');
    }
    return new Color(
      parseInt(result[1], 16),
      parseInt(result[2], 16),
      parseInt(result[3], 16)
    );
  }

  // 从 RGB 整数值创建
  static fromRGB(r, g, b) {
    return new Color(r, g, b);
  }

  // 创建随机颜色
  static random() {
    return new Color(
      Math.floor(Math.random() * 256),
      Math.floor(Math.random() * 256),
      Math.floor(Math.random() * 256)
    );
  }

  toString() {
    return `rgba(${this.r}, ${this.g}, ${this.b}, ${this.a})`;
  }
}

const red = Color.fromHex('#ff0000');
const blue = Color.fromRGB(0, 0, 255);
const lucky = Color.random();

console.log(red.toString());   // rgba(255, 0, 0, 1)
console.log(blue.toString());  // rgba(0, 0, 255, 1)
```

`Color.fromHex('#ff0000')` 比 `new Color(255, 0, 0)` 更具可读性——调用者一眼就能看出"我正在从一个十六进制字符串创建颜色对象"。这就是工厂方法的价值所在：**让 API 更有表现力**。

#### 内置对象中的静态方法

JavaScript 的内置对象大量使用了静态方法。`Array.isArray()`、`Object.keys()`、`JSON.parse()`、`Math.random()`、`Number.parseInt()`……这些都是静态方法。它们之所以是"静态"的，是因为它们提供的功能是通用工具，不需要依附于某个特定的数组实例或对象实例才能使用：

```javascript
// Array.isArray 是静态方法 —— 判断任意值是否为数组
Array.isArray([1, 2, 3]);   // true
Array.isArray('hello');      // false

// Object.create 也是静态方法 —— 从原型创建新对象
const obj = Object.create(null);

// JSON.parse 也是静态方法 —— 解析 JSON 字符串
const data = JSON.parse('{"name": "张三"}');
```

理解了这一点，你就能明白为什么 `Array.from()` 是静态方法而 `Array.prototype.map()` 是实例方法：`from` 是从其他数据"制造"数组的工厂，不依赖现有数组；而 `map` 是对已有数组进行变换的操作，必须有源数据才行。

### 静态属性：类级别的共享数据

除了静态方法，类还可以拥有静态属性（也叫类字段）：

```javascript
class Counter {
  static count = 0;  // 静态属性，所有实例共享

  constructor() {
    Counter.count++;
    console.log(`当前已创建 ${Counter.count} 个实例`);
  }

  static getCount() {
    return Counter.count;
  }

  static reset() {
    Counter.count = 0;
  }
}

const c1 = new Counter(); // 当前已创建 1 个实例
const c2 = new Counter(); // 当前已创建 2 个实例
const c3 = new Counter(); // 当前已创建 3 个实例

console.log(Counter.getCount()); // 3

Counter.reset();
console.log(Counter.getCount()); // 0
```

静态属性存储在**类构造函数本身**上，所有实例共享同一份数据。这与实例字段形成了鲜明对比：每个实例的字段是独立的（你的名字和我的名字不一样），但静态属性是唯一的（计数器只有一个）。

### 静态方法中的 this

在静态方法中，`this` 指向的是**类本身**（也就是构造函数），而不是某个实例。这意味着你可以在静态方法中通过 `this` 访问其他静态成员：

```javascript
class AppConfig {
  static version = '1.0.0';
  static environment = 'development';

  static getInfo() {
    console.log(`版本: ${this.version}`);
    console.log(`环境: ${this.environment}`);
    // this 指向 AppConfig 这个构造函数本身
  }

  static setEnvironment(env) {
    this.environment = env;
  }
}

AppConfig.getInfo();
// 版本: 1.0.0
// 环境: development

AppConfig.setEnvironment('production');
AppConfig.getInfo();
// 版本: 1.0.0
// 环境: production
```

但也正因为 `this` 在静态方法中指向类本身，所以**静态方法中无法直接访问实例属性和实例方法**——因为 `this` 根本不是一个实例。如果需要在静态方法中使用实例相关的逻辑，你必须先获得一个实例（比如通过参数传入，或者在静态方法内部用 `new` 创建一个）。

### 静态成员的实际案例：数据库连接池

让我们看一个更贴近真实开发的例子——一个简化的数据库连接池：

```javascript
class ConnectionPool {
  static #pool = [];                          // 私有静态字段（存放连接）
  static maxSize = 10;                        // 最大连接数
  static currentSize = 0;                     // 当前连接数

  constructor(connectionString) {
    this.connectionString = connectionString;
    this.lastUsed = Date.now();
  }

  query(sql) {
    console.log(`[${this.connectionString}] 执行 SQL: ${sql}`);
    this.lastUsed = Date.now();
  }

  // 获取一个连接（静态工厂方法）
  static getConnection(connectionString) {
    // 先尝试从池中找一个空闲的
    const idle = ConnectionPool.#pool.find(c =>
      c.connectionString === connectionString &&
      Date.now() - c.lastUsed > 30000 // 30秒未使用视为空闲
    );

    if (idle) {
      console.log('从连接池复用连接');
      return idle;
    }

    // 池中没有空闲连接，创建新的
    if (ConnectionPool.currentSize < ConnectionPool.maxSize) {
      console.log('创建新连接');
      const conn = new ConnectionPool(connectionString);
      ConnectionPool.#pool.push(conn);
      ConnectionPool.currentSize++;
      return conn;
    }

    throw new Error('连接池已满，请稍后再试');
  }

  // 获取池状态（静态方法）
  static getStatus() {
    return {
      totalConnections: ConnectionPool.currentSize,
      maxSize: ConnectionPool.maxSize,
      available: ConnectionPool.#pool.filter(
        c => Date.now() - c.lastUsed > 30000
      ).length
    };
  }
}

// 使用连接池
const db1 = ConnectionPool.getConnection('mysql://localhost/db1');
db1.query('SELECT * FROM users');

const db2 = ConnectionPool.getConnection('mysql://localhost/db1');
// 如果距离上次使用超过30秒，会复用 db1；否则创建新连接

console.log(ConnectionPool.getStatus());
// { totalConnections: ..., maxSize: 10, available: ... }
```

这个例子展示了静态成员的典型应用模式：**管理跨实例共享的状态和行为**。连接池的大小限制、连接列表这些信息不属于任何一个单独的连接对象——它们属于整个"连接池概念"本身，因此用静态成员来表达是最自然的。

## 类的内部机制：[[HomeObject]] 与 super

### [[HomeObject]]：super 能够工作的秘密

在介绍继承细节之前，我们需要先理解一个支撑着 `super` 关键字工作的底层机制——`[[HomeObject]]`。

当一个函数作为类的方法（或对象的方法简写）被定义时，JavaScript 引擎会给这个函数添加一个内部属性 `[[HomeObject]]`，它的值就是**定义该方法的对象**。对于类方法来说，`[[HomeObject]]` 就是类的 `prototype` 对象：

```javascript
class Parent {
  getParentName() {
    return 'Parent';
  }
}

class Child extends Parent {
  getChildName() {
    return 'Child';
  }

  getNames() {
    // super.getParentName() 的工作原理：
    // 1. 引擎查找当前方法的 [[HomeObject]] → Child.prototype
    // 2. 取得 Child.prototype 的原型 → Parent.prototype
    // 3. 在 Parent.prototype 上查找 getParentName 方法
    return [
      super.getParentName(),  // 通过原型链向上查找
      this.getChildName()     // 直接在实例上查找
    ];
  }
}
```

`[[HomeObject]]` 的存在让 `super` 能够"知道自己来自哪里"，从而正确地沿着原型链定位父类方法。这是一个在类定义时就被确定的静态绑定，而不是在运行时动态查找的。

### 为什么 super 不能随意复制

正是因为 `[[HomeObject]]` 是在定义时绑定的，包含 `super` 的方法**不能被简单地复制到其他对象上使用**：

```javascript
class Animal {
  constructor(name) {
    this.name = name;
  }

  identify() {
    return `动物: ${this.name}`;
  }
}

class Dog extends Animal {
  identify() {
    // super.identify() 的 [[HomeObject]] 固定为 Dog.prototype
    return `${super.identify()}（犬科）`;
  }
}

const dog = new Dog('旺财');
console.log(dog.identify()); // 动物: 旺财（犬科）

// 尝试将方法复制到另一个对象
const cat = { name: '咪咪', identify: Dog.prototype.identify };
console.log(cat.identify());
// 动物: 咪咪（犬科）← 注意：super 仍然指向 Dog 的父类 Animal！
// 这可能不是你期望的行为
```

当你把 `Dog.prototype.identify` 复制给 `cat` 对象时，这个方法的 `[[HomeObject]]` 依然是 `Dog.prototype`，不会变成 `cat`。所以 `super.identify()` 还是去 `Animal.prototype` 上找方法。在某些情况下这可能恰好是你想要的，但更多时候这会导致难以追踪的 bug。

### 只有方法简写语法才有 [[HomeObject]]

还有一个重要的限制：**只有在方法简写语法定义的方法才会获得 `[[HomeObject]]`**。如果你用传统的函数表达式方式定义方法，是无法在其中使用 `super` 的：

```javascript
class Broken {
  // 这样定义的方法没有 [[HomeObject]]
  parentMethod = function() {
    // super.method() // ❌ SyntaxError: 'super' keyword unexpected here
  };

  // 必须用方法简写语法
  workingMethod() {
    // super.method() // ✅ 正常工作
  }
}
```

这是因为 `[[HomeObject]]` 的设置是方法简写语法特有的行为。引擎看到 `methodName() {...}` 这种形式时就知道"这是一个属于当前对象的方法"，从而设置 `[[HomeObject]]`；而看到 `propertyName = function() {...}` 时，引擎认为"这只是赋值一个函数表达式"，不做特殊处理。

## 类的注意事项与常见陷阱

### 不要使用逗号分隔成员

这是从其他语言转过来的开发者最容易犯的错误之一。在 JavaScript 的类语法中，**成员之间不需要也不能使用逗号**：

```javascript
// ❌ 错误 —— 类中不需要逗号
class Wrong {
  name = 'test',
  sayHi() {},
  goodbye() {},
}

// ✅ 正确 —— 成员之间直接换行即可
class Correct {
  name = 'test';
  sayHi() {}
  goodbye() {}
}
```

类的语法借鉴了对象字面量的风格（花括号、方法简写等），但在"是否使用逗号"这一点上选择了和对象字面量不同的规则。对象字面量要求属性之间用逗号分隔，而类的成员之间只用换行符分隔。这个设计选择是为了让类的语法更接近其他主流面向对象语言（Java、C#、Python 等）的风格，降低学习成本。

### 类声明不会被提升（Hoisting）

函数声明存在"提升"现象——你可以在函数定义之前调用它：

```javascript
sayHello(); // 正常工作 —— 函数声明被提升了

function sayHello() {
  console.log('Hello!');
}
```

但类声明不存在这样的提升。在类声明出现之前的代码中，类是不存在的：

```javascript
const p = new Pet(); // ReferenceError: Cannot access 'Pet' before initialization

class Pet {
  constructor() {
    console.log('一只宠物出生了');
  }
}
```

这是因为类可能存在继承关系（`extends`），而被继承的父类可能还没定义完。如果允许提升，就需要先解析完所有类声明才能确定继承链，这会增加实现的复杂度。为了保证一致性，JavaScript 选择不让类声明被提升。

不过，**类表达式**（因为是赋值语句的一部分）遵循变量声明的提升规则——`let` 和 `const` 存在"暂时性死区"，所以在赋值之前同样不能使用：

```javascript
const Expr = class {};  // 类表达式

const e = new Expr();   // 必须在这一行之后才能用
```

### 类体中的严格模式

正如前面提到的，类体自动运行在严格模式下。这意味着以下代码在类内部会报错，而在非严格的普通函数中可能不会：

```javascript
class SloppyCodeIsNotAllowed {
  method() {
    accidentalGlobal = 'oops'; // ReferenceError: accidentalGlobal is not defined
    // 在非严格模式下，这会意外创建一个全局变量

    delete this.property; // 严格模式下不能删除不可配置的属性

    var eval = 42;        // 严格模式下不能重命名 eval / arguments
    var arguments = 42;   // 同上
  }
}
```

严格模式的强制启用是一件好事。它消除了许多 JavaScript 语言历史遗留的"怪异行为"，让代码更加可预测、更不容易产生隐蔽的错误。如果你习惯了写非严格的 JavaScript 代码，刚开始可能会觉得有些限制很不习惯，但这些限制几乎都是在保护你免受常见错误的侵害。
