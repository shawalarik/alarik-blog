# `super` 的两种用法（函数调用与对象引用）+ 底层实现与 `this` 绑定

## 从"打电话给上级"说起：super 的本质

在理解 `super` 的具体语法之前，我们先从直觉层面建立对它的认知。想象一个公司的组织架构：基层员工（子类）遇到自己无法独立处理的问题时，需要向上级（父类）汇报并请求指示。`super` 就是这条"向上沟通的专用通道"——它让你能够在子类的方法或构造器内部，精确地访问和调用父类定义的功能。

但 `super` 不只是一个简单的"父类引用"。它是一个**语法关键字**，其行为取决于你使用它的上下文。它有两种截然不同的用法：一种是作为**函数调用** `super(...)`，另一种是作为**对象引用** `super.method(...)`。这两种在语义、执行时机、`this` 绑定规则等方面都有根本性的差异。混淆这两种用法是很多 JavaScript 开发者（包括有其他语言经验的人）常犯的错误。

本文将彻底拆解 `super` 的两种用法，深入引擎内部的实现机制（`[[HomeObject]]`），分析它在不同场景下的 `this` 绑定行为，并揭示箭头函数与 `super` 之间微妙的关系。读完之后，你将不再只是"知道怎么写 super"，而是真正理解"super 为什么这么工作"。

## 用法一：`super(...)` —— 作为函数调用父类构造器

### 基本语法与硬性规定

`super(...)` 的第一种用法是**在子类的构造器中调用父类的构造函数**。这是派生类初始化过程中最关键的一步：

```javascript
class Animal {
  #name;
  #age;

  constructor(name, age) {
    this.#name = name;
    this.#age = age;
    console.log(`Animal 构造完成: ${this.#name}, ${this.#age}岁`);
  }
}

class Dog extends Animal {
  #breed;

  constructor(name, age, breed) {
    super(name, age);  // ✅ 必须先调用父类构造器
    this.#breed = breed;
    console.log(`Dog 构造完成: ${breed}`);
  }
}

const dog = new Dog('旺财', 3, '柴犬');
// Animal 构造完成: 旺财, 3岁
// Dog 构造完成: 柴犬
```

这里有一条铁律：**在派生类的 constructor 中，必须在访问 `this` 之前调用 `super()`**。如果你尝试违反这条规则：

```javascript
class Broken extends Animal {
  constructor(name) {
    this.#temp = 'oops';  // ❌ ReferenceError: Must call super() before accessing this
    super(name);
  }
}
```

为什么会这样？让我们深入到 `new` 操作符的底层机制来理解。

### new 操作符的两种模式

当 JavaScript 引擎执行一个 `new` 表达式时，它会根据目标构造器的类型采取不同的策略。

对于**普通类**（没有 `extends` 的类），`new` 的执行过程如下：

```javascript
// 模拟 new 操作符对普通类的行为
function simulateNewNormal(Constructor, ...args) {
  // 1. 创建一个新的空对象
  const thisObj = {};

  // 2. 将对象的 [[Prototype]] 链接到 Constructor.prototype
  Object.setPrototypeOf(thisObj, Constructor.prototype);

  // 3. 将 thisObj 赋值给 this，然后执行 Constructor 函数体
  const result = Constructor.apply(thisObj, args);

  // 4. 如果构造器返回了对象，则使用该对象；否则返回 thisObj
  return (typeof result === 'object' && result !== null) ? result : thisObj;
}
```

注意第 1 步和第 2 步——**引擎自动创建了一个新对象并赋给了 `this`**。所以在普通类的构造器里，你一进来就能直接用 `this` 来添加属性。

但对于**派生类**（有 `extends` 的类），过程完全不同：

```javascript
// 模拟 new 操作符对派生类的行为
function simulateNewDerived(DerivedConstructor, ...args) {
  // 注意：此时不会创建新对象！不会赋值 this！

  // 直接执行派生类的构造函数体
  // 在这个函数体内，this 是 undefined（严格模式下）
  // 或者指向全局对象（非严格模式 —— 但类总是严格模式）

  // 只有当执行到 super() 时，才会触发父类构造器的执行
  // 父类构造器会创建对象并赋值给 this
  // 之后 this 才变得可用
}
```

派生类的构造器有一个特殊的内部标记 `[[ConstructorKind]]: "derived"`。当引擎看到这个标记时，它跳过了"创建新对象并赋值给 `this`"这一步。原因是：**如果父类的构造器需要做一些特殊的事情来初始化对象（比如设置内部的 `[[Prototype]]` 链、处理私有字段等），那么这些工作应该由父类来负责**。子类不应该擅自创建一个"半成品"的对象。

可以把这个过程比作一家汽车工厂的生产线。普通车型（普通类）可以直接在装配线上从头组装——底盘、发动机、车身一步步来。但如果是某种"改装版车型"（派生类），它必须先把基础车型送到总装车间去完成基础组装（调用 `super()`），然后才能回到自己的工位上安装特有的配件（比如赛车尾翼）。你不能在基础车还没成型的时候就去装尾翼——那时候连车身都没有呢。

### super() 创建并返回了什么？

当你在子类中调用 `super(...)` 时，实际上发生了以下事情：

1. **定位父类构造器**：通过当前类的 `[[Prototype]]` 链找到父类的构造函数
2. **以父类构造器的身份执行 `new` 行为**：
   - 创建一个新的空对象
   - 将该对象的 `[[Prototype]]` 设置为**父类的 prototype**
   - 将这个新对象赋值为 `this`
   - 执行父类构造器函数体（传入你传给 `super` 的参数）
3. **将同一个 `this` 对象返回给子类**

关键点是：**`super()` 返回的不是一个新的对象，而是把 `this` 本身初始化好了**。子类和父类操作的是**同一个 `this` 对象**：

```javascript
class Parent {
  constructor(x, y) {
    console.log('Parent 中:', this === obj); // true —— 就是同一个对象！
    this.x = x;       // 给 this 添加 x 属性
    this.y = y;       // 给 this 添加 y 属性
  }
}

class Child extends Parent {
  #z;

  constructor(x, y, z) {
    const result = super(x, y);  // super() 的返回值

    console.log('super() 返回值:', result);      // undefined （不是对象！）
    console.log('Child 中:', this === obj);        // true —— 同一个 this
    console.log('result === this:', result === this); // false

    this.#z = z;         // 继续给同一个 this 添加属性
  }
}

const obj = new Child(10, 20, 30);
console.log(obj); // { x: 10, y: 20 } + 私有 #z = 30
```

注意 `super()` 的返回值通常是 `undefined`（除非父类构造器显式返回了一个对象）。你不需要也不应该捕获这个返回值。`super()` 的工作是**副作用式的**——它的效果体现在 `this` 对象被初始化这件事上。

### super() 与 this 的绑定时机

`super()` 不仅创建了 `this`，还决定了 `this` 的初始状态。这包括：

1. **原型链的建立**：`this.__proto__` 指向子类的 `prototype`
2. **实例属性的初步设置**：父类构造器中所有 `this.xxx = yyy` 都会立即生效
3. **私有字段的注册**：父类的私有字段会被注册到 `this` 上

```javascript
class Machine {
  #serialNumber;

  constructor(id) {
    console.log('[Machine] super 开始执行...');
    console.log('[Machine] this 存在吗?', this !== undefined); // true
    console.log('[Machine] this 的原型:', Object.getPrototypeOf(this));
    // → Child.prototype （注意：是子类的 prototype，不是 Machine 的！）

    this.#serialNumber = id;
    console.log('[Machine] 序列号已设置');
  }

  get serialNumber() { return this.#serialNumber; }
}

class Robot extends Machine {
  #name;
  #mode = 'standby';

  constructor(id, name) {
    console.log('[Robot] 开始构造...');

    super(id);  // ← 这里 this 被创建并初始化

    console.log('[Robot] super 返回');
    console.log('[Robot] #serialNumber 可访问?', this.serialNumber !== undefined); // true

    this.#name = name;
    console.log('[Robot] 构造完成');
  }

  introduce() {
    return `${this.#name}(SN:${this.serialNumber}) [${this.#mode}]`;
  }
}

const robot = new Robot('R-2024-X', '瓦力');
// [Robot] 开始构造...
// [Machine] super 开始执行...
// [Machine] this 存在吗? true
// [Machine] this 的原型: Robot.prototype ← 关键！是子类的 prototype
// [Machine] 序列号已设置
// [Robot] super 返回
// [Robot] #serialNumber 可访问? true
// [Robot] 构造完成

console.log(robot.introduce()); // 瓦力(SN:R-2024-X) [standby]
```

有一个非常值得注意的点：**即使是在父类 `Machine` 的构造器中执行时，`this` 的原型已经是 `Robot.prototype` 而非 `Machine.prototype`**。这是因为 `new Robot(...)` 触发时，整个对象的原型链从一开始就被设定为以 `Robot.prototype` 为直接原型。这意味着如果在父类构造器中调用了某个方法，而该方法被子类重写了，那么执行的将是**子类的版本**（多态特性）：

```javascript
class Base {
  constructor() {
    this.identify();  // 多态调用！
  }

  identify() {
    console.log('我是 Base 实例');
  }
}

class Derived extends Base {
  identify() {
    console.log('我是 Derived 实例');  // ← 这个会被调用！
  }
}

const obj = new Derived();
// 输出: 我是 Derived 实例
```

这种设计确保了一致的多态行为——即使在对象的"出生阶段"，方法调用的分派规则也和在对象完全成熟后一样。

### 可以不写 super() 吗？

如果你的子类没有定义自己的 `constructor`，那么引擎会自动生成一个默认的构造器，其中包含了 `super()` 调用：

```javascript
class Parent {
  constructor(x) { this.x = x; }
}

class AutoChild extends Parent {
  // 没有写 constructor
  // 引擎自动生成:
  // constructor(...args) { super(...args); }
}

const child = new AutoChild(42);
console.log(child.x); // 42 ✅
```

但如果你的子类**确实定义了 constructor**，那么你必须手动写 `super()`（除非你的子类构造器明确返回了一个对象——这是一种极端罕见的边界情况）。

还有一种特殊情况：如果你的类继承自 `null`（即 `extends null`），那么不需要也不能调用 `super()`，但你必须在构造器中手动返回一个对象：

```javascript
class NullExtends extends null {
  constructor() {
    // 不能调用 super() —— 因为 "父类" 是 null，没有构造器可以调用
    // 但也必须返回一个对象，否则默认返回 undefined
    return {};
  }
}
```

## 用法二：`super.method(...)` —— 访问父类方法

### 基本语法与用途

`super` 的第二种用法是在子类的方法中以 `super.methodName(...)` 的形式**调用父类中被覆盖的方法**。这是实现"扩展而非替换"的核心手段：

```javascript
class Vehicle {
  #speed = 0;

  accelerate(delta) {
    this.#speed += delta;
    console.log(`加速后速度: ${this.#speed} km/h`);
  }

  brake(delta) {
    this.#speed = Math.max(0, this.#speed - delta);
    console.log(`减速后速度: ${this.#speed} km/h`);
  }

  get speedInfo() {
    return { current: this.#speed, unit: 'km/h' };
  }
}

class SportsCar extends Vehicle {
  #turboActive = false;
  #nitroRemaining = 3;

  accelerate(delta) {
    // 先执行父类的加速逻辑
    super.accelerate(delta);  // ← super 的第二种用法

    // 再加上跑车的额外逻辑
    if (this.#speed > 200 && !this.#turboActive) {
      this.#turboActive = true;
      console.log('🔥 涡轮增压已激活！');
    }
  }

  useNitro() {
    if (this.#nitroRemaining <= 0) {
      console.log('❌ 氮气已耗尽');
      return;
    }

    this.#nitroRemaining--;
    console.log(`💨 使用氮气加速! (剩余: ${this.#nitroRemaining})`);

    // 通过 super 调用父类的加速方法，传入额外的加成
    super.accelerate(50);  // ← 同样是 super 的第二种用法
  }

  brake(delta) {
    // 子类可以在 super 调用之前做额外的事
    if (this.#speed > 300 && delta > 50) {
      console.log('⚠️ 高速行驶中急刹车危险！启动 ABS...');
    }
    // 然后再调用父类的刹车逻辑
    super.brake(delta);
  }

  get speedInfo() {
    // super 对于 getter/setter 也有效
    const baseInfo = super.speedInfo;  // ← 调用父类的 getter
    return {
      ...baseInfo,
      turbo: this.#turboActive,
      nitro: this.#nitroRemaining
    };
  }
}

const car = new SportsCar();

car.accelerate(100);  // 加速后速度: 100 km/h
car.accelerate(120);  // 加速后速度: 220 km/h + 🔥 涡轮增压已激活！
car.useNitro();       // 💨 使用氮气加速! (剩余: 2) + 加速后速度: 270 km/h
car.brake(30);        // 减速后速度: 240 km/h

console.log(car.speedInfo);
// { current: 240, unit: 'km/h', turbo: true, nitro: 2 }
```

`super.method(...)` 和 `super(...)` 有本质区别：

| 特性 | `super(...)` | `super.method(...)` |
|------|-------------|-------------------|
| **出现位置** | 仅限子类 `constructor` | 子类的任何方法 |
| **调用目标** | 父类的**构造函数** | 父类的**实例方法/getter/setter** |
| **作用** | 初始化 `this` 对象 | 执行父类的特定逻辑 |
| **是否必须** | **必须**（在使用 `this` 前） | 可选 |
| **返回值** | 通常为 `undefined` | 取决于方法的返回值 |

### super.method() 中的 this 绑定

这是一个极其重要且容易误解的点：**当你在子类方法中通过 `super.parentMethod()` 调用父类方法时，父类方法内部的 `this` 指向的是什么？**

答案是：**`this` 仍然指向子类的实例对象**，而不是父类。

```javascript
class Parent {
  showThis() {
    console.log(`Parent.showThis 中的 this:`, this.constructor.name);
    // 输出的永远是实际实例所属的类名
    return this;
  }

  identify() {
    return `[Parent.identify] 我是 ${this.name || '(无名)'}`;
  }
}

class Child extends Parent {
  name = '子类实例';

  test() {
    console.log('Child.test 中的 this:', this.constructor.name);

    // 调用父类方法
    const returnedThis = super.showThis();  // this 没变！

    console.log('返回的 this 是否相同:', returnedThis === this); // true
    console.log(super.identify());
  }
}

const child = new Child();
child.test();
// Child.test 中的 this: Child
// Parent.showThis 中的 this: Child  ← 不是 Parent！
// 返回的 this 是否相同: true
// [Parent.identify] 我是 子类实例
```

这种行为的原因在于 `super.method()` 的底层实现方式。当引擎执行 `super.parentMethod()` 时，它大致做了以下几件事：

1. 根据当前方法的 `[[HomeObject]]` 找到父类原型
2. 在父类原型上找到 `parentMethod` 方法
3. 以**当前环境的 `this`** 为上下文调用该方法（相当于 `ParentMethod.call(this, ...)`）

所以 `this` 在整个调用链路中保持不变——它始终是最初触发方法调用的那个实例对象。这就是为什么父类的方法能够正确操作子类的属性（因为 `this` 上既有父类设置的属性，也有子类设置的属性）。

可以把这种情况比作一位 CEO 把一项任务委托给部门经理去办理。虽然任务的实际执行者是经理，但在办理过程中涉及到的"公司资源"（`this`）仍然是整个公司层面的——经理不能说"我只管我自己的部门"。这里的 `this` 就像是公司的整体资源池，无论谁在操作，操作的始终是同一个实体。

### super.prop：读取父类的属性

除了调用方法，`super` 还可以被用来**读取父类原型上的属性**：

```javascript
class Base {
  version = '1.0';
  static className = 'Base';

  get config() {
    return { theme: 'light', lang: 'zh-CN' };
  }
}

class Derived extends Base {
  version = '2.0';  // 覆盖了父类的同名字段

  showVersions() {
    console.log('子类版本:', this.version);     // 2.0 —— 来自自身
    console.log('父类版本:', super.version);    // 1.0 —— 来自 Base.prototype
  }

  showConfig() {
    const parentConfig = super.config;  // 读取父类的 getter
    console.log('父类配置:', parentConfig); // { theme: 'light', lang: 'zh-CN' }
  }
}

const obj = new Derived();
obj.showVersions();
// 子类版本: 2.0
// 父类版本: 1.0

obj.showConfig();
// 父类配置: { theme: 'light', lang: 'zh-CN' }
```

`super.prop` 的查找范围仅限于**父类的原型**（即 `[[HomeObject]].[[Prototype]]`），不会像 `this.prop` 那样沿整条原型链搜索到底。这使得你可以精确地获取被覆盖之前的原始值——在某些高级场景下非常有用。

### super 在静态方法和静态块中的行为

`super` 不仅能在实例方法中使用，也能在**静态方法**中使用。区别在于：静态方法中的 `super` 指向的是**父类的构造函数本身**（而非父类的 prototype）：

```javascript
class Animal {
  static kingdom = '动物界';

  static getInfo() {
    return `属于${Animal.kingdom}`;
  }
}

class Mammal extends Animal {
  static className = '哺乳纲';

  static getInfo() {
    // 这里的 super 指向 Animal（父类构造器）
    const parentInfo = super.getInfo();  // 调用 Animal.getInfo()
    return `${Mammal.className}, ${parentInfo.replace('属于', '')}`;
  }

  static describe() {
    console.log(this.getInfo());          // 多态 —— 取决于谁调用
    console.log(super.getInfo());         // 总是调用 Animal 的版本
  }
}

class Dog extends Mammal {
  static subClass = '犬科';

  static getInfo() {
    return `${Dog.subClass}, ${super.getInfo()}`;  // 调用 Mammal.getInfo()
  }
}

Dog.describe();
// 犬科, 哺乳纲, 动物界    ← this.getInfo() 多态调用到 Dog 版本
// 属于动物界              ← super.getInfo() 固定调用 Animal 版本
```

ES2022 还引入了**静态初始化块**（Static Initialization Blocks），在其中同样可以使用 `super`：

```javascript
class Configurable {
  static defaults = { theme: 'light', fontSize: 14 };

  static init() {
    console.log('基类初始化完成');
  }
}

class App extends Configurable {
  static customSettings = {};
  static initialized = false;

  // 静态初始化块 —— 在类定义求值时执行
  static {
    super.init();  // 调用父类的静态方法
    App.customSettings = { ...App.defaults, darkMode: false };
    App.initialized = true;
    console.log('App 类配置就绪');
  }
}

// 当 class App 的声明被执行时，静态块就会运行
console.log(App.customSettings); // { theme: 'light', fontSize: 14, darkMode: false }
console.log(App.initialized);    // true
```

## 底层机制：`[[HomeObject]]` —— super 能够工作的秘密

### 问题引入：为什么不直接用 this.proto?

在学习 `super` 的早期，很多人会有这样的直觉想法：`super.method()` 大概就是 `this.__proto__.method.call(this)` 吧？也就是说，沿着 `this` 的原型链往上找一层，然后调用那个方法？

对于单层继承来说，这个直觉恰好能 work：

```javascript
class Parent {
  sayHi() { console.log('Parent 说 Hi'); }
}

class Child extends Parent {
  sayHi() {
    // 直觉模拟：
    // this.__proto__.__proto__.sayHi.call(this); // 能找到 Parent.sayHi
    // 正确写法：
    super.sayHi();
    console.log('Child 补充的内容');
  }
}

new Child().sayHi();
// Parent 说 Hi
// Child 补充的内容
```

但当继承层次超过两层时，问题就暴露出来了：

```javascript
class A {
  sayHi() { console.log('A 层'); }
}

class B extends A {
  sayHi() {
    console.log('B 层开始');

    // 如果用 this.__proto__ 方式：
    // this.__proto__ 是 B.prototype
    // this.__proto__.__proto__ 是 A.prototype
    // 所以 this.__proto__.__proto__.sayHi.call(this) → A.sayHi() ✓
    // 目前没问题...

    super.sayHi(); // 正确地调用到 A.sayHi()
    console.log('B 层结束');
  }
}

class C extends B {
  sayHi() {
    console.log('C 层开始');

    // 问题来了！
    // C 的 sayHi 内部，this 指向 C 的实例
    // this.__proto__ 是 C.prototype
    // this.__proto__.__proto__ 是 B.prototype
    // 如果我们用 this.__proto__ 方式找"上一级"：
    //   找到的是 B.sayHi() ✓
    //
    // 但现在假设我们在 B.sayHi() 里也用同样的方式：
    //   B.sayHi() 内部的 this 还是 C 的实例！
    //   this.__proto__ 是 C.prototype
    //   this.__proto__.__proto__ 还是 B.prototype
    //   于是 B.sayHi() 又调用了自己 → 无限循环！💥

    super.sayHi(); // 正确：C→B→A，逐层递进
    console.log('C 层结束');
  }
}

new C().sayHi();
// C 层开始
// B 层开始
// A 层        ← 到达顶层，不再递归
// B 层结束
// C 层结束
```

核心问题是：**`this` 始终指向最初发起调用的那个实例**，它不会随着调用链的上升而改变。所以如果每一层都基于 `this.__proto__` 来找"上一级"，那每次找到的都是同一层——导致死循环或错误的方法被调用。

### [[HomeObject]] 如何解决这个问题

JavaScript 引擎通过在每个方法上附加一个隐藏属性 `[[HomeObject]]` 来解决这个困境。`[[HomeObject]]` 记录了这个方法**被定义时所归属的那个对象**：

```javascript
class A {
  // A.prototype.sayHi 的 [[HomeObject]] === A.prototype
  sayHi() { /* ... */ }
}

class B extends A {
  // B.prototype.sayHi 的 [[HomeObject]] === B.prototype
  sayHi() {
    super.sayHi(); // 引擎根据 [[HomeObject]]=B.prototype，去找 B.prototype 的原型
                    // 即 A.prototype，然后在上面找 sayHi → 找到了!
  }
}

class C extends B {
  // C.prototype.sayHi 的 [[HomeObject]] === C.prototype
  sayHi() {
    super.sayHi(); // [[HomeObject]]=C.prototype → 找 C.prototype 的原型
                    // 即 B.prototype，在上面找 sayHi → 找到 B.sayHi!
  }
}
```

每层方法的 `[[HomeObject]]` 都是不同的，它们各自"记住了自己来自哪里"。所以当 C.sayHi 执行 `super.sayHi()` 时，引擎走的是 C 的路线；当执行流进入 B.sayHi 后再遇到 `super.sayHi()` 时，引擎切换到 B 的路线。两条路线互不干扰，完美实现了逐级向上的方法调用链。

可以用"楼层指引牌"来类比：每层楼的方法都有一个内置的牌子写着"我在 X 层"。当你需要去上一层时，你不是看自己在哪个房间（`this` 可能到处都是），而是看你手里的牌子（`[[HomeObject]]`）——牌子说你在 3 楼，那上一层就是 4 楼；牌子说你在 5 楼，上一层就是 6 楼。不管你怎么移动，牌子上的信息永远不会错。

### [[HomeObject]] 的完整查找算法

当引擎遇到 `super.methodName(args...)` 时，完整的解析步骤如下：

```
输入: 当前环境中的 super 引用, 方法名 methodName, 参数列表 args

步骤 1: 获取当前函数的 [[HomeObject]]
       设 homeObj = 当前函数.[[HomeObject]]

步骤 2: 获取 homeObj 的原型（即"父级对象"）
       设 parentProto = homeObj.[[Prototype]]

步骤 3: 在 parentProto 及其原型链上查找名为 methodName 的属性
       从 parentProto 开始，沿着 [[Prototype]] 链向上搜索
       直到找到一个拥有 propertyName 的对象，或者到达 null 为止

步骤 4: 如果找到了
       设 parentMethod = 找到的属性值
       以当前环境的 this 为上下文调用 parentMethod
       即: parentMethod.call(this, ...args)

步骤 5: 如果没找到
       抛出 TypeError: super method not defined
```

注意步骤 3 中提到的一个细节：**`super.propertyName` 的查找是从 `[[HomeObject]].[[Prototype]]` 开始的，而不是从 `[[HomeObject]]` 自身开始的**。这一点确保了你通过 `super` 只能访问父类及更高层级祖先的成员，不会意外地访问到"兄弟层"或自身的成员。

### [[HomeObject]] 的不可变性

一旦方法被创建，它的 `[[HomeObject]]` 就被永久固定下来，无法在运行时修改。这带来一个重要的后果：**包含 `super` 的方法是"位置敏感"的——把它从一个对象搬到另一个对象上，`super` 的行为可能就不对了**：

```javascript
class Original {
  from() {
    console.log('Original.from() 被调用');
    // super.from() 会去 Original.prototype 的原型上找
    return this.value * 2;
  }
}

class Extended extends Original {
  value = 10;

  override() {
    // super.from() 会去 Extended.prototype 的原型上找
    // 也就是 Original.prototype
    console.log('结果:', super.from()); // 20
  }
}

// 危险：把 Original.from 复制到另一个完全无关的对象上
const stranger = {
  value: 100,
  from: Original.prototype.from  // [[HomeObject]] 仍然是 Original.prototype
};

stranger.from();
// Original.from() 被调用
// 返回: 200 （stranger.value * 2 = 100 * 2）
// super.from() 仍然基于 Original.prototype 解析 —— 也许这不是你期望的行为
```

在这个例子中，`stranger.from()` 能够正常工作（因为 `from` 内部只用了 `this.value`，而 `this` 正确指向 `stranger`）。但如果 `Original.from` 内部使用了 `super.otherMethod()`，那么这个 `super` 会去 `Original.prototype` 的原型上找 `otherMethod`，而不是去 `stranger` 的原型上找。这就可能导致难以预料的 bug。

因此，最佳实践是：**不要将包含 `super` 的方法从一个类复制到另一个不相关的对象上**。如果需要共享功能，应该通过组合（Composition）、Mixin 或工具函数来实现。

## 箭头函数与 super：借用外层的超能力

### 箭头函数没有自己的 super

和 `this` 一样，箭头函数**没有自己的 `super`**。当你在箭头函数中使用 `super` 时，它会从外层的第一个非箭头函数那里"借用" `super` 的值：

```javascript
class Parent {
  greet() {
    console.log('Parent says hello from', this.name);
  }
}

class Child extends Parent {
  name = 'Child';

  methodWithArrow() {
    // 这是一个普通方法，有自己的 super
    console.log('--- 进入 methodWithArrow ---');

    const arrow = () => {
      // 箭头函数没有自己的 super
      // 它借用了外层 methodWithArrow 的 super
      super.greet(); // ✅ 正确！借用成功
    };

    arrow(); // 执行箭头函数
    console.log('--- 退出 methodWithArrow ---');
  }
}

const child = new Child();
child.methodWithArrow();
// --- 进入 methodWithArrow ---
// Parent says hello from Child  ← super.greet() 正确执行
// --- 退出 methodWithArrow ---
```

这里的关键在于：箭头函数的 `super` 不是在**箭头函数被调用时**确定的，而是在**箭头函数被定义时**就从外层捕获的。这意味着即使箭头函数被传递到很远的地方去异步执行，它仍然能正确地使用 `super`：

```javascript
class TimerTask extends AsyncTask {
  start(delay) {
    // 普通方法有自己的 super
    setTimeout(() => {
      // 即使在这里延迟执行，super 仍然可用
      super.execute();  // ✅ 安全！super 从 methodWithArrow 借来的
    }, delay);
  }
}
```

### 为什么箭头函数 + super 特别适合异步回调

这是一个非常实用的模式。在传统的回调场景中，`super`（以及 `this`）经常会丢失：

```javascript
// ❌ 传统方式的问题
class Problematic extends Base {
  doAsyncWork() {
    fetch('/api/data')
      .then(function(response) {
        // 这个普通 function 没有 super！
        super.process(response);  // 💥 SyntaxError: 'super' keyword unexpected here
      });
  }
}

// ✅ 箭头函数解决方案
class Correct extends Base {
  doAsyncWork() {
    fetch('/api/data')
      .then((response) => {
        // 箭头函数借用了外层 doAsyncWork 的 super
        super.process(response);  // ✅ 正常工作
      });
  }
}
```

由于现代 JavaScript 开发中充满了异步操作（Promise、async/await、事件监听器、定时器），箭头函数+`super` 的组合几乎成了标准做法。它让你不必手动 bind 或保存 `super` 的引用就能安全地在回调中使用继承能力。

### 箭头函数嵌套时的 super 查找规则

当有多层箭头函数嵌套时，`super` 会一直向外查找，直到找到最近的拥有 `super` 的普通方法：

```javascript
class DeepNest extends Base {
  outerMethod() {
    // 第一层：普通方法 —— 有 super

    const level1 = () => {
      // 第二层：箭头函数 —— 借用 outerMethod 的 super

      const level2 = () => {
        // 第三层：箭头函数 —— 还是借用 outerMethod 的 super
        // （不是 level1 的 super，因为 level1 自己也没有 super）

        super.doSomething(); // ✅ 最终追溯到 outerMethod 的 super
      };

      level2();
    };

    level1();
  }
}
```

无论嵌套多深，只要最内层是箭头函数，`super` 就会一路向外穿透直到找到最近的非箭头函数上下文。

### 一个容易忽略的边界情况

如果箭头函数不在任何类方法内部（即在全局或模块顶层），那么其中使用 `super` 会报错：

```javascript
// 在全局/模块顶层
const orphanArrow = () => {
  super.anything(); // 💥 SyntaxError: 'super' keyword unexpected here
};
```

这是因为顶层作用域中没有 `super` 可供借用——`super` 只存在于类方法的词法环境中。

## super 的限制条件总结

了解了 `super` 的强大功能之后，我们还需要知道它的各种限制。这些限制大多源于 `[[HomeObject]]` 的设计约束。

### 限制一：只有简写方法才有 [[HomeObject]]

只有以下两种语法定义的方法才拥有 `[[HomeObject]]`，才能使用 `super`：

```javascript
class ValidSuperUsage {
  // ✅ 形式 1：类方法简写
  validMethod() {
    super.doStuff();
  }

  // ❌ 形式 2：属性形式的函数表达式
  brokenMethod = function () {
    super.doStuff(); // SyntaxError!
  };

  // ❌ 形式 3：属性形式的箭头函数
  alsoBroken = () => {
    super.doStuff(); // SyntaxError!
  };

  // ❌ 形式 4：传统方式在 constructor 中赋值
  constructor() {
    this.anotherBroken = function () {
      super.doStuff(); // SyntaxError!
    };
  }
}
```

原因很简单：只有方法简写语法（`methodName() {...}`）告诉引擎"这是一个方法，请给它设置 `[[HomeObject]]`"。其他的写法只是普通的赋值操作，引擎不做任何特殊处理。

### 限制二：super 不能在顶层代码中使用

`super` 只能在类的方法或构造器中出现。在全局代码、普通函数、模块顶层中使用 `super` 都会导致语法错误：

```javascript
// ❌ 全局代码
super.method();

function ordinaryFunction() {
  // ❌ 普通函数
  super.method();
}

// ✅ 类内部
class MyClass {
  method() {
    super.method(); // OK
  }

  static staticMethod() {
    super.staticMethod(); // OK
  }
}
```

### 限制三：super 不能被赋值、解构或用作变量名

`super` 是一个保留关键字，不能当作变量使用：

```javascript
class BadIdeas {
  method() {
    // let super = {};           // ❌ 语法错误
    // const { super: s } = {};  // ❌ 语法错误
    // super = something;        // ❌ 语法错误
    // function super() {}       // ❌ 语法错误
  }
}
```

### 限制四：动态属性名的 super 调用

`super` 支持动态（计算）属性名，这在某些元编程场景下很有用：

```javascript
class PluginHost {
  executePlugin(pluginName) {
    // 动态决定要调用哪个父类方法
    if (typeof this[`plugin_${pluginName}`] === 'function') {
      return super[`plugin_${pluginName}`]();  // ✅ 支持 computed property
    }
  }
}
```

但需要注意：动态 `super` 调用的性能通常略低于静态名称调用，因为引擎无法在编译期确定目标方法的位置。

## 实战案例：用 super 构建中间件系统

让我们用一个接近真实项目的案例——一个 HTTP 请求中间件系统——来综合展示 `super` 的两种用法以及各种相关技巧：

```javascript
// ========== 基础请求处理器 ==========
class BaseHandler {
  #requestCount = 0;
  #startTime;

  constructor(baseUrl) {
    this.baseUrl = baseUrl;
    this.#startTime = Date.now();
  }

  async handle(request) {
    this.#requestCount++;
    console.log(`[BaseHandler] 处理请求 #${this.#requestCount}: ${request.method} ${request.url}`);

    try {
      const response = await this.fetchFromServer(request);
      return this.formatResponse(response);
    } catch (error) {
      return this.handleError(error, request);
    }
  }

  async fetchFromServer(request) {
    const url = `${this.baseUrl}${request.url}`;
    console.log(`[BaseHandler] 发起请求: ${url}`);

    const controller = new AbortController();
    request.timeoutId = setTimeout(() => controller.abort(), request.timeout || 5000);

    const response = await fetch(url, {
      method: request.method,
      headers: request.headers,
      body: request.body ? JSON.stringify(request.body) : undefined,
      signal: controller.signal
    });

    clearTimeout(request.timeoutId);
    return response;
  }

  formatResponse(response) {
    return {
      status: response.status,
      ok: response.ok,
      data: null,
      headers: Object.fromEntries(response.headers.entries())
    };
  }

  handleError(error, request) {
    if (error.name === 'AbortError') {
      return { status: 408, ok: false, error: '请求超时', url: request.url };
    }
    return { status: 500, ok: false, error: error.message, url: request.url };
  }

  get stats() {
    return {
      uptime: Date.now() - this.#startTime,
      totalRequests: this.#requestCount
    };
  }
}

// ========== 缓存中间件 ==========
class CacheHandler extends BaseHandler {
  #cache = new Map();
  #maxCacheSize = 100;
  #defaultTTL = 60000; // 60秒

  constructor(baseUrl, cacheOptions = {}) {
    super(baseUrl);  // ← super 用法一：调用父类构造器

    if (cacheOptions.maxSize) this.#maxCacheSize = cacheOptions.maxSize;
    if (cacheOptions.defaultTTL) this.#defaultTTL = cacheOptions.defaultTTL;
  }

  async handle(request) {
    // 检查缓存
    const cacheKey = this.#buildCacheKey(request);
    const cached = this.#getFromCache(cacheKey);

    if (cached) {
      console.log(`[CacheHandler] 🎯 缓存命中: ${cacheKey}`);
      return cached;
    }

    // 缓存未命中 —— 调用父类的 handle 方法
    console.log(`[CacheHandler] 缓存未命中，转发给父类处理`);
    const response = await super.handle(request);  // ← super 用法二：调用父类方法

    // 将成功的 GET 请求响应存入缓存
    if (request.method === 'GET' && response.ok) {
      this.#setCache(cacheKey, response);
    }

    return response;
  }

  // 重写 fetchFromServer 以添加缓存相关日志
  async fetchFromServer(request) {
    console.log(
      `[CacheHandler] 请求缓存大小: ${this.#cache.size}/${this.#maxCacheSize}`
    );
    // 调用父类版本的 fetchFromServer
    return super.fetchFromServer(request);  // ← super 用法二
  }

  // 新增方法：清除缓存
  clearCache(pattern) {
    if (!pattern) {
      this.#cache.clear();
      console.log('[CacheHandler] 缓存已全部清除');
      return;
    }

    for (const key of this.#cache.keys()) {
      if (key.includes(pattern)) {
        this.#cache.delete(key);
      }
    }
    console.log(`[CacheHandler] 已清除匹配 "${pattern}" 的缓存条目`);
  }

  get stats() {
    // 扩展父类的 stats 信息
    const baseStats = super.stats;  // ← super 用于 getter
    return {
      ...baseStats,
      cacheSize: this.#cache.size,
      maxCacheSize: this.#maxCacheSize,
      hitRate: this.#requestCount > 0
        ? ((this.#cache.size / this.#requestCount) * 100).toFixed(1) + '%'
        : 'N/A'
    };
  }

  #buildCacheKey(request) {
    return `${request.method}:${request.url}:${JSON.stringify(request.params || {})}`;
  }

  #getFromCache(key) {
    const entry = this.#cache.get(key);
    if (!entry) return null;
    if (Date.now() > entry.expiry) {
      this.#cache.delete(key);
      return null;
    }
    return entry.data;
  }

  #setCache(key, data) {
    if (this.#cache.size >= this.#maxCacheSize) {
      // 简单淘汰策略：删除最早的条目
      const firstKey = this.#cache.keys().next().value;
      this.#cache.delete(firstKey);
    }

    this.#cache.set(key, {
      data,
      expiry: Date.now() + this.#defaultTTL
    });
  }
}

// ========== 日志记录中间件 ==========
class LoggingHandler extends CacheHandler {
  #logBuffer = [];
  #maxBufferSize = 50;

  constructor(baseUrl, options = {}) {
    super(baseUrl, options.cache);  // ← super 用法一：传递参数给父构造器
    this.#maxBufferSize = options.maxLogEntries || 50;
  }

  async handle(request) {
    const startTime = performance.now();
    const requestId = this.#generateRequestId();

    // 请求前日志
    this.#log({
      requestId,
      type: 'REQUEST',
      timestamp: new Date().toISOString(),
      method: request.method,
      url: request.url,
      params: request.params
    });

    try {
      // 调用父类（CacheHandler）的 handle —— 包含了缓存逻辑
      const response = await super.handle(request);  // ← super 用法二

      const duration = Math.round(performance.now() - startTime);

      // 响应后日志
      this.#log({
        requestId,
        type: 'RESPONSE',
        timestamp: new Date().toISOString(),
        status: response.status,
        duration: `${duration}ms`,
        cached: response._fromCache || false
      });

      return response;

    } catch (error) {
      this.#log({
        requestId,
        type: 'ERROR',
        timestamp: new Date().toISOString(),
        error: error.message,
        stack: error.stack?.substring(0, 200)
      });
      throw error;
    }
  }

  // 重写 handleError 以添加日志
  handleError(error, request) {
    this.#log({ type: 'ERROR_DETAIL', error: error.message, url: request.url });
    return super.handleError(error, request);  // ← 先日志，再交给父类处理
  }

  getLog() {
    return [...this.#logBuffer];
  }

  clearLog() {
    this.#logBuffer = [];
  }

  get stats() {
    const parentStats = super.stats;  // ← 三层继承链上的 super getter
    return {
      ...parentStats,
      logEntries: this.#logBuffer.length,
      maxLogEntries: this.#maxBufferSize
    };
  }

  #log(entry) {
    this.#logBuffer.push(entry);
    if (this.#logBuffer.length > this.#maxBufferSize) {
      this.#logBuffer.shift();
    }
  }

  #generateRequestId() {
    return `REQ-${Date.now().toString(36)}-${Math.random().toString(36).substring(2, 7)}`;
  }
}

// ========== 使用演示 ==========

const api = new LoggingHandler('https://api.example.com', {
  cache: { maxSize: 20, defaultTTL: 30000 },
  maxLogEntries: 100
});

// 模拟请求
api.handle({
  method: 'GET',
  url: '/users/1',
  params: { include: 'profile' },
  timeout: 3000
}).then(response => {
  console.log('响应:', response);
  console.log('统计:', api.stats);
});

// 一段时间后查看日志
setTimeout(() => {
  console.table(api.getLog());
}, 1000);
```

这个三层继承体系清晰地展示了 `super` 的两种用法如何在复杂系统中协作：

| 层级 | 类 | `super(...)` 用法 | `super.method()` 用法 |
|------|-----|------------------|---------------------|
| 第 1 层 | BaseHandler | —（基类无 super） | —（基类无 super） |
| 第 2 层 | CacheHandler | `super(baseUrl)` 调用 BaseHandler 构造器 | `super.handle()` / `super.fetchFromServer()` / `super.stats` |
| 第 3 层 | LoggingHandler | `super(baseUrl, options.cache)` 传递给 CacheHandler | `super.handle()` / `super.handleError()` / `super.stats` |

每一层都专注于自己的职责（基础通信 → 缓存 → 日志），同时通过 `super` 与上下游协作。这正是继承和 `super` 设计的精髓所在。
