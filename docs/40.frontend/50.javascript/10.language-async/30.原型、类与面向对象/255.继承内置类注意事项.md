# 继承内置类（`Array`、`Error`、`Map`）的注意事项 —— 为什么内置类不是普通的类

## 一个令人惊讶的事实：内置类"不普通"

当你写 `class Dog extends Animal {}` 时，你继承的是一个用 `class` 语法定义的普通自定义类。JavaScript 引擎处理这种继承的方式相对直观——设置原型链、传递 `this`、调用 `super()`。一切都在你的掌控之中。

但当你尝试继承 `Array`、`Error`、`Map`、`Promise` 这些**内置类**时，事情就变得复杂多了。这些类不是用普通的 JavaScript 类语法定义的——它们是引擎底层用 C++（或其他实现语言）编写的原生代码。它们的行为遵循着一些特殊的内部协议，这些协议在普通的类继承中根本不存在。

为什么这很重要？因为很多开发者会自然地想："既然我能继承自己的类，那我当然也能继承 `Array` 来创建一个增强版的数组。"这个想法完全合理，但实际操作中会遇到一系列意想不到的陷阱。本文将系统地揭示这些陷阱的成因、表现和解决方案。

## 继承 Array：最常见的场景与最多的坑

### 基本语法看起来很简单

让我们从最基础的例子开始。继承 `Array` 看起来非常直观：

```javascript
class PowerArray extends Array {
  isEmpty() {
    return this.length === 0;
  }

  first() {
    return this.length > 0 ? this[0] : undefined;
  }

  last() {
    return this.length > 0 ? this[this.length - 1] : undefined;
  }
}

const arr = new PowerArray(1, 2, 3, 4, 5);

console.log(arr instanceof Array);     // true
console.log(arr instanceof PowerArray); // true
console.log(arr.isEmpty());           // false
console.log(arr.first());             // 1
console.log(arr.last());              // 5

arr.push(6);
console.log(arr.last());              // 6

// 原生数组方法全部可用
const filtered = arr.filter(x => x > 3);
console.log(filtered);                // [4, 5, 6]
```

到目前为止一切正常。我们的 `PowerArray` 实例拥有原生的 `push`、`filter`、`map` 等所有方法，同时新增了 `isEmpty`、`first`、`last` 这些便利方法。看起来继承 `Array` 和继承一个普通类没什么区别——但这只是表面现象。

### 陷阱一：返回值类型丢失

第一个隐藏的问题出现在那些**返回新数组的方法**上。`filter`、`map`、`slice`、`concat`、`splice`、`flat`、`flatMap`……这些方法都会创建并返回一个新的数组。问题是：它们返回的是 `Array` 的实例还是 `PowerArray` 的实例？

```javascript
class PowerArray extends Array {
  isEmpty() { return this.length === 0; }
}

const powers = new PowerArray(1, 2, 3, 4, 5);

// 调用 filter —— 返回值是什么类型？
const even = powers.filter(x => x % 2 === 0);
console.log(even);                    // [2, 4]
console.log(even instanceof PowerArray); // ✅ true —— 还是 PowerArray！
console.log(even.isEmpty());          // ✅ 可以调用子类方法！
```

在这个例子中，`filter` 返回的竟然是一个 `PowerArray` 实例！这意味着你可以链式地使用自定义方法：

```javascript
powers
  .filter(x => x % 2 === 0)   // → PowerArray [2, 4]
  .map(x => x * 10)           // → PowerArray [20, 40]
  .isEmpty();                  // false
```

这看起来很棒——但这是如何实现的？当 `PowerArray` 的实例调用 `filter` 时，引擎内部的 `Array.prototype.filter` 方法需要创建一个新的数组来存放过滤结果。在普通的 `Array.filter` 中，它会用 `new Array()` 来创建这个新数组。但在派生类的上下文中，引擎使用了一个特殊的机制来确保返回的新数组也是派生类型的实例。

这个机制的核心是一个内部槽位 **`[[Species]]`**（物种）。默认情况下，一个派生自 `Array` 的类的 `[[Species]]` 就是它自己。所以 `Array.prototype.filter` 在执行时会检查 `this.constructor[Symbol.species]`（如果存在的话），然后用它来构造返回值的实例。

### 陷阱二：Symbol.species 与返回值控制

虽然默认行为很方便，但有时候你可能**不希望**方法返回子类实例。比如，如果你的子类有一些特殊的初始化要求或者昂贵的属性计算，那么每次 `filter` 或 `map` 都创建一个完整的子类实例可能是一种浪费甚至错误：

```javascript
class ExpensiveArray extends Array {
  #cache = new Map();
  #accessCount = 0;

  constructor(...items) {
    super(...items);
    // 模拟昂贵的初始化操作
    for (let i = 0; i < items.length; i++) {
      this.#cache.set(i, { value: items[i], computed: Math.pow(items[i], 2) });
    }
  }

  getCached(index) {
    this.#accessCount++;
    return this.#cache.get(index);
  }

  get accessCount() {
    return this.#accessCount;
  }
}

const expensive = new ExpensiveArray(1, 2, 3);
console.log(expensive.getCached(0)); // { value: 1, computed: 1 } ✓

const mapped = expensive.map(x => x * 10); // 返回 ExpensiveArray 实例
// 问题：mapped 也执行了昂贵的初始化！每个元素都创建了缓存条目
// 如果数据量大，这可能造成严重的性能问题

// 更严重的情况：某些操作可能依赖特定条件
const sliced = expensive.slice(1); // 只有一个元素的 ExpensiveArray
// 但它的缓存结构是为完整数组设计的，可能不一致
```

解决方案是通过静态 getter `Symbol.species` 来覆盖默认行为，告诉引擎："请用普通的 `Array` 作为返回值类型"：

```javascript
class CleanArray extends Array {
  isEmpty() { return this.length === 0; }
  first() { return this[0]; }
  last() { return this[this.length - 1]; }

  // 关键：指定"物种"为 Array
  static get [Symbol.species]() {
    return Array;
  }
}

const clean = new CleanArray(1, 2, 3, 4, 5);

const mapped = clean.map(x => x * 10);
console.log(mapped);                   // [10, 20, 30, 40, 50]
console.log(mapped instanceof Array);    // true
console.log(mapped instanceof CleanArray); // false ❌ —— 不再是 CleanArray！

// mapped 没有 first/last/isEmpty 方法
console.log(mapped.first);            // undefined
```

通过设置 `static get [Symbol.species]() { return Array; }`，所有返回新数组的原生方法都会改用 `Array` 构造器来创建结果对象。这在以下场景中特别有用：
- 子类有昂贵的初始化逻辑
- 子类有特定的不变量（invariant），而原生方法的输出无法保证这些不变量
- 你需要确保外部 API 接收到的是纯粹的 `Array` 对象，避免暴露子类的特殊能力

可以把 `Symbol.species` 想象成一家工厂的"产品标签"。默认情况下，`PowerArray` 工厂生产的所有产品（无论是通过工厂自己的生产线还是外包给 filter/map 车间生产的）都会贴上 "PowerArray" 标签。但如果你设置了 `Symbol.species` 为 `Array`，就相当于告诉外包车间："你们生产的产品请贴 'Array' 标签就行，别贴我们厂的标签了。"这样消费者拿到的就是标准的通用产品。

### 陷阱三：new.target 在内置类中的特殊行为

内置类的另一个特殊之处在于 `new.target` 的处理方式。对于普通类来说，`new.target` 总是指向被 `new` 直接调用的构造器。但对于内置类，情况更加微妙：

```javascript
class MyArray extends Array {
  constructor(...args) {
    super(...args);
    console.log(`MyArray: new.target.name = ${new.target.name}`);
  }
}

class SpecialArray extends MyArray {
  constructor(...args) {
    super(...args);
    console.log(`SpecialArray: new.target.name = ${new.target.name}`);
  }
}

const a = new MyArray(1, 2, 3);
// MyArray: new.target.name = MyArray

const b = new SpecialArray(1, 2, 3);
// MyArray: new.target.name = SpecialArray  ← super 中看到的 new.target 是最终调用的那个
// SpecialArray: new.target.name = SpecialArray

const c = b.filter(x => x > 1);
// MyArray: new.target.name = SpecialArray  ← filter 内部创建实例时也保留了 new.target！
// 这就是为什么 filter 返回的是 SpecialArray 而非 Array
```

`new.target` 会沿着继承链正确传播到最底层的调用者。这就是内置方法能够自动返回正确子类实例的根本原因——引擎内部在构造新实例时使用了 `new target()` 这种形式而非硬编码的 `new Array()`。

这就像一家连锁餐厅的订单系统：顾客（最终调用者）在 SpecialArray 门店点了餐，虽然订单经过了 MyArray 厨房（父类构造器）的处理，但厨房知道这道菜最终是给哪家门店的——因为 `new.target` 就像订单上的门店标识一样一路传递了下来。所以 filter 这道"菜"被打包时，包装上写的还是 SpecialArray 的名字。

### 陷阱四：Array 的 length 行为与子类属性冲突

`Array` 有一个非常特殊的行为：修改 `length` 属性可以截断数组。这个行为在子类中可能会导致问题：

```javascript
class LoggingArray extends Array {
  #logEntries = [];

  push(...items) {
    this.#logEntries.push({ action: 'push', items, time: Date.now() });
    return super.push(...items);
  }

  pop() {
    const value = super.pop();
    if (value !== undefined) {
      this.#logEntries.push({ action: 'pop', value, time: Date.now() });
    }
    return value;
  }

  getLog() {
    return [...this.#logEntries];
  }
}

const logArr = new LoggingArray(10, 20, 30);
logArr.push(40, 50);
logArr.pop();

console.log(logArr.getLog());
// [{ action:'push', items:[40,50], ... }, { action:'pop', value:30, ... }]

// 但截断操作不会经过我们重写的 pop
logArr.length = 2;
console.log(logArr);        // [10, 20] —— 两个元素被默默删除了
console.log(logArr.getLog()); // 之前的日志没有变化 —— 截断没有被记录！
```

`length` 赋值触发的截断是引擎层面的直接内存操作，它不会走 `pop()` 方法的逻辑。这是 `Array` 子类的一个固有限制——你无法拦截或自定义长度变化带来的副作用。如果你需要在长度变化时执行额外逻辑，必须使用 `Proxy` 来包装数组对象：

```javascript
function createLoggingArray(...initial) {
  let logs = [];

  const handler = {
    set(target, prop, value) {
      if (prop === 'length' && typeof value === 'number' && value < target.length) {
        const removed = target.length - value;
        logs.push({ action: 'truncate', removed, newLength: value });
      }
      target[prop] = value;
      return true;
    },

    get(target, prop) {
      if (prop === 'getLog') return () => [...logs];
      return target[prop];
    }
  };

  return new Proxy(new Array(...initial), handler);
}
```

## 继承 Error：又一个充满惊喜的领域

### Error 对象的特殊性

`Error` 对象可能是所有内置类中最特殊的一个。它不仅仅存储一条消息——现代 JavaScript 引擎还会自动捕获**堆栈跟踪信息（stack trace）**。而堆栈信息的捕获依赖于一个关键细节：`Error.captureStackTrace(this, this.constructor)` 必须在对象的早期阶段被调用。

```javascript
class AppError extends Error {
  #code;
  #httpStatus;

  constructor(message, code, httpStatus = 500) {
    super(message);  // ← 这行做了什么？

    this.#code = code;
    this.#httpStatus = httpStatus;
    this.name = 'AppError';

    // 捕获堆栈信息
    Error.captureStackTrace(this, this.constructor);
  }

  get code() { return this.#code; }
  get httpStatus() { return this.#httpStatus; }

  toJSON() {
    return {
      name: this.name,
      message: this.message,
      code: this.#code,
      httpStatus: this.#httpStatus,
      stack: this.stack
    };
  }
}

try {
  throw new AppError('用户不存在', 'USER_NOT_FOUND', 404);
} catch (error) {
  console.log(error.message);      // 用户不存在
  console.log(error.code);         // USER_NOT_FOUND
  console.log(error.httpStatus);   // 404
  console.log(error.toJSON());
  // {
  //   name: 'AppError',
  //   message: '用户不存在',
  //   code: 'USER_NOT_FOUND',
  //   httpStatus: 404,
  //   stack: 'Error: ...\n    at Object.<anonymous>...'
  // }
}
```

### 为什么必须在 super() 之后立即 captureStackTrace

`Error` 的构造器在执行时会做两件事：
1. 设置 `message` 属性
2. （在某些引擎中）尝试捕获当前的调用栈

但这里有一个微妙的时机问题：如果你在 `super(message)` 之后、在自己的代码之前添加了很多逻辑，那么堆栈中就会包含这些中间步骤的信息，导致堆栈变得冗长且不精确：

```javascript
class BadError extends Error {
  constructor(message) {
    super(message);

    // 假设这里有大量前置逻辑...
    this.validateMessage(message);
    this.setupMetadata();
    this.registerError();
    this.notifyMonitoring();

    // 最后才捕获堆栈 —— 太晚了！
    Error.captureStackTrace(this, this.constructor);
  }

  validateMessage(msg) { /* ... */ }
  setupMetadata() { /* ... */ }
  registerError() { /* ... */ }
  notifyMonitoring() { /* ... */ }
}
```

抛出这种 `BadError` 后查看堆栈信息，你会发现堆栈中包含了 `validateMessage`、`setupMetadata`、`registerError`、`notifyMonitoring` 这些内部方法的调用记录——这对调试来说是噪音。正确的做法是在 `super()` 之后**立即**调用 `captureStackTrace`：

```javascript
class GoodError extends Error {
  constructor(message, code) {
    super(message);
    this.code = code;
    this.name = 'GoodError';
    Error.captureStackTrace(this, this.constructor);  // 尽早！
    // 之后的任何操作都不会出现在堆栈中
  }
}
```

可以把堆栈信息想象成一张犯罪现场的照片。`captureStackTrace` 就像是在案发第一时间按下快门的动作——越早拍，照片中的干扰元素就越少。如果在拍照之前你已经让很多人在现场走动（执行了大量其他函数），照片里就会充满无关的脚印和痕迹，增加破案的难度。所以在 `super()` 之后立刻"拍照"，能确保堆栈干净且精准地指向真正的问题来源。

### Error 子类的 instanceOf 链

自定义的 Error 子类能正确地通过 `instanceof` 检测，这对于分层错误处理非常重要：

```javascript
class NetworkError extends Error {
  constructor(url, statusCode) {
    super(`网络请求失败: ${url} (${statusCode})`);
    this.name = 'NetworkError';
    this.url = url;
    this.statusCode = statusCode;
    Error.captureStackTrace(this, NetworkError);
  }

  isClientError() { return this.statusCode >= 400 && this.statusCode < 500; }
  isServerError() { return this.statusCode >= 500; }
}

class TimeoutError extends NetworkError {
  constructor(url, timeoutMs) {
    super(url, 408);
    this.name = 'TimeoutError';
    this.timeoutMs = timeoutMs;
    Error.captureStackTrace(this, TimeoutError);
  }
}

class ValidationError extends Error {
  #fields = [];

  constructor(message) {
    super(message);
    this.name = 'ValidationError';
    Error.captureStackTrace(this, ValidationError);
  }

  addField(field, reason) {
    this.#fields.push({ field, reason });
    return this;
  }

  get fields() { return [...this.#fields]; }
}

// ========== 错误处理 ==========

function handleApiCall(apiFunction) {
  try {
    return apiFunction();
  } catch (e) {
    if (e instanceof TimeoutError) {
      console.warn(`⏱️ 请求超时(${e.timeoutMs}ms): ${e.url}`);
      return { error: 'timeout', retryable: true };

    } else if (e instanceof NetworkError) {
      if (e.isClientError()) {
        console.error(`❌ 客户端请求错误: ${e.statusCode}`);
        return { error: 'client_error', statusCode: e.statusCode };
      } else {
        console.error(`💥 服务器错误: ${e.statusCode}`);
        return { error: 'server_error', statusCode: e.statusCode };
      }

    } else if (e instanceof ValidationError) {
      console.error(`📋 数据校验失败: ${e.fields}`);
      return { error: 'validation_failed', details: e.fields };

    } else if (e instanceof Error) {
      console.error(`⚠️ 未知错误: ${e.message}`);
      return { error: 'unknown', message: e.message };
    } else {
      throw e; // 非 Error 对象，重新抛出
    }
  }
}

// 测试各种错误类型
const r1 = handleApiCall(() => { throw new TimeoutError('/api/users', 3000); });
// ⏱️ 请求超时(3000ms): /api/users

const r2 = handleApiCall(() => { throw new NetworkError('/api/data', 500); });
// 💥 服务器错误: 500

const r3 = handleApiCall(() => {
  throw new ValidationError('表单数据无效').addField('email', '格式不正确').addField('age', '必须大于0');
});
// 📋 数据校验失败: [{field:'email',...}, {field:'age',...}]
```

这个例子展示了 `Error` 继承在实际项目中的巨大价值：你可以定义一套层次清晰的错误类型体系，然后在统一的地方用 `instanceof` 进行分类处理。每种错误类型携带自己特有的元数据（URL、状态码、校验字段等），让错误处理代码既简洁又信息丰富。

这种层次化的错误处理模式就像医院的分诊台：病人（错误对象）先经过初步检查（第一层 `instanceof Error`），然后根据具体症状分流到不同科室（`NetworkError` → 网络科、`ValidationError` → 校验科、`TimeoutError` → 超时科）。每个科室都有自己的处理方案，互不干扰但又协同工作。

## 继承 Map 和 Set：较少见但有价值的场景

### Map 子类：带过期时间的缓存

`Map` 是另一个值得继承的内置类。虽然比 `Array` 和 `Error` 少见，但在某些场景下非常有用：

```javascript
class TTLCache extends Map {
  #defaultTTL;
  #cleanupInterval;
  #cleanupTimer;

  constructor(defaultTTL = 60000, cleanupInterval = 300000) {
    super();  // ← Map 不接受构造参数（不像 Array 那样）
    this.#defaultTTL = defaultTTL;
    this.#cleanupInterval = cleanupInterval;
    this.#startCleanup();
  }

  set(key, value, ttl) {
    const expiry = Date.now() + (ttl || this.#defaultTTL);
    super.set(key, { value, expiry });  // 调用父类 Map.set()
    return this;                       // 支持链式调用
  }

  get(key) {
    const entry = super.get(key);
    if (!entry) return undefined;

    if (Date.now() > entry.expiry) {
      super.delete(key);  // 惰性删除
      return undefined;
    }

    return entry.value;
  }

  has(key) {
    return this.get(key) !== undefined;
  }

  delete(key) {
    const existed = super.has(key);
    super.delete(key);
    return existed;
  }

  get size() {
    this.#cleanupExpired();
    return super.size;
  }

  keys() {
    this.#cleanupExpired();
    return super.keys();
  }

  values() {
    this.#cleanupExpired();
    return super.values();
  }

  entries() {
    this.#cleanupExpired();
    return super.entries();
  }

  forEach(callback, thisArg) {
    this.#cleanupExpired();
    for (const [key, { value }] of super.entries()) {
      callback.call(thisArg, value, key, this);
    }
  }

  #startCleanup() {
    if (this.#cleanupTimer) clearInterval(this.#cleanupTimer);
    this.#cleanupTimer = setInterval(() => {
      this.#cleanupExpired();
    }, this.#cleanupInterval);
  }

  #cleanupExpired() {
    const now = Date.now();
    for (const [key, entry] of super.entries()) {
      if (now > entry.expiry) {
        super.delete(key);
      }
    }
  }

  clear() {
    super.clear();
  }

  destroy() {
    clearInterval(this.#cleanupTimer);
    this.clear();
  }

  get stats() {
    let total = 0;
    let expired = 0;
    const now = Date.now();
    for (const [, entry] of super.entries()) {
      total++;
      if (now > entry.expiry) expired++;
    }
    return { total, active: total - expired, expired, defaultTTL: this.#defaultTTL };
  }
}

// 使用示例
const sessionCache = new TTLCache(30 * 60 * 1000, 60 * 1000); // 30分钟TTL，每分钟清理

sessionCache.set('user_123', { name: '张三', role: 'admin' });
sessionCache.set('user_456', { name: '李四', role: 'user' });

console.log(sessionCache.get('user_123')); // { name: '张三', role: 'admin' } ✓
console.log(sessionCache.has('user_456'));  // true ✓
console.log(sessionCache.size);              // 2
```

注意几个关键点：
1. **`super()` 调用时不需要传参**——Map 的构造器不接受初始键值对
2. **所有对数据的操作都通过 `super.get()` / `super.set()` 委托给父类**
3. **重写了 `size`、`keys()`、`values()`、`entries()`、`forEach` 等多个方法**——因为它们都可能受到过期数据的影响
4. **清理定时器需要在销毁时手动停止**

可以把 `TTLCache` 比作一个带自动保洁系统的图书馆。普通的 `Map` 是一个书架——书放上去就在那里，永远不被动过。而 `TTLCache` 则是一个有借阅期限的书架：每本书上都贴着到期时间（expiry），每次取书时管理员会先检查是否过期（`get` 中的惰性删除），还有定时保洁员定期巡视把过期的书回收（`#cleanupExpired` 定时任务）。对外的借阅接口看起来和普通书架一模一样（`get/set/has/delete/size`），但内部多了整个生命周期管理机制。

### Set 子类：带容量限制的集合

```javascript
class BoundedSet extends Set {
  #maxSize;

  constructor(maxSize = 1000, iterable) {
    super();  // 先调用无参数的 super()

    this.#maxSize = maxSize;

    // 手动添加初始元素（如果有），并在超出限制时处理
    if (iterable) {
      for (const item of iterable) {
        if (this.size >= this.#maxSize) {
          break; // 静默忽略超出部分
        }
        super.add(item);
      }
    }
  }

  add(value) {
    if (super.has(value)) {
      return this; // 已存在，不做任何事
    }

    if (super.size >= this.#maxSize) {
      // 达到上限：移除最早的元素（FIFO 策略）
      // Set 保持插入顺序，所以第一个就是最早的
      const oldest = super.keys().next().value;
      super.delete(oldest);
    }

    return super.add(value);
  }

  get maxSize() { return this.#maxSize; }
  get remainingCapacity() { return this.#maxSize - super.size; }

  isFull() {
    return super.size >= this.#maxSize;
  }
}

// 使用：最近访问的页面缓存（最多保留 5 个）
const recentPages = new BoundedSet(5, ['home', 'about']);

recentPages.add('contact');
recentPages.add('products');  // size = 5，满了

recentPages.add('blog');       // 触发 FIFO 淘汰 → 'home' 被移除
console.log([...recentPages]);
// ['about', 'contact', 'products', 'blog'] + 还有一个初始元素

console.log(recentPages.remainingCapacity); // 1
console.log(recentPages.isFull());           // false
```

## 继承 Promise：异步世界的扩展

### Promise 子类的基本模式

`Promise` 也是可以被继承的，而且由于 `async/await` 语法的广泛使用，Promise 子类有其实际价值：

```javascript
class TimedPromise extends Promise {
  #timeoutMs;

  constructor(executor, timeoutMs = 5000) {
    this.#timeoutMs = timeoutMs;

    let rejectTimeout;
    const timer = setTimeout(() => {
      rejectTimeout(new Error(`操作超时 (${timeoutMs}ms)`));
    }, timeoutMs);

    super((resolve, reject) => {
      executor(
        (value) => {
          clearTimeout(timer);
          resolve(value);
        },
        (reason) => {
          clearTimeout(timer);
          reject(reason);
        }
      );
    });
  }

  // 静态工厂方法更符合习惯用法
  static withTimeout(executor, timeoutMs) {
    return new TimedPromise(executor, timeoutMs);
  }
}

// 使用方式一：直接构造
const timedFetch = new TimedPromise((resolve) => {
  fetch('https://api.example.com/slow-endpoint')
    .then(r => resolve(r))
    .catch(err => console.error('网络错误:', err.message));
}, 2000);  // 2秒超时

timedFetch
  .then(response => console.log('获取成功:', response.status))
  .catch(error => console.error('失败:', error.message));

// 使用方式二：静态工厂
TimedPromise.withTimeout((resolve) => {
  setTimeout(() => resolve('完成!'), 1000);
}).then(console.log);  // "完成!"
```

### Promise 子类的重要注意事项

Promise 子类有几个需要特别注意的地方：

**第一，`then` 和 `catch` 的返回值类型**：

```javascript
class TrackedPromise extends Promise {
  #startTime;
  #endTime;

  constructor(executor) {
    this.#startTime = performance.now();
    super(executor);
  }

  then(onFulfilled, onRejected) {
    const result = super.then(
      (value) => {
        this.#endTime = performance.now();
        console.log(`✅ Promise 在 ${this.#endTime - this.#startTime.toFixed(2)}ms 内完成`);
        return onFulfilled ? onFulfilled(value) : value;
      },
      (reason) => {
        this.#endTime = performance.now();
        console.log(`❌ Promise 在 ${this.#endTime - this.#startTime.toFixed(2)}ms 内拒绝`);
        return onRejected ? onRejected(reason) : Promise.reject(reason);
      }
    );

    return result;
  }
}

const tracked = new TrackedPromise(resolve => setTimeout(() => resolve('ok'), 1000));

const chained = tracked.then(val => val.toUpperCase());
console.log(chained instanceof TrackedPromise); // false ❌
// then() 返回的是普通 Promise，不是 TrackedPromise！
```

注意：和 `Array` 不同，`Promise.prototype.then` 默认**不会**返回子类实例。这是因为 Promise 的规范明确规定 `.then()` 应该返回一个标准的 `Promise` 对象。如果你想保持子类型，需要显式地在 `then` 中进行包装——但这会让代码变得相当繁琐，也是为什么大多数库选择组合而非继承来扩展 Promise 行为的原因之一。

## 内置类 vs 自定义类：核心差异总结

| 特性 | 自定义类 | 内置类 |
|------|---------|--------|
| **实现语言** | JavaScript（或编译成 JS） | C++ / Rust / 引擎原生代码 |
| **super() 行为** | 创建 `this` | 可能涉及额外的内部初始化 |
| **方法返回值** | 取决于你自己 | 通常遵循 `[[Species]]` 机制 |
| **内部槽位（Internal Slots）** | 无 | 可能有（如 Array 的 `[[ArrayLength]]`） |
| **引擎优化** | 标准 JIT | 可能享有专门的快路径 |
| **可继承性** | 完全可控 | 大多可继承，但有特殊规则 |

### 什么是"内部槽位"

这是理解内置类继承问题的关键概念。许多内置对象拥有**内部槽位**——一种只有引擎才能访问的隐藏属性，JavaScript 层面的代码无法直接触碰。

以 `Array` 为例，它有 `[[ArrayLength]]` 这个内部槽位。当你执行 `arr.length = 3` 时，引擎不只是设置一个普通的 `length` 属性——它在操作 `[[ArrayLength]]`，而这个操作会触发特殊行为（比如删除多余的索引属性）。如果你用一个普通对象去模仿 `Array`，无论怎么努力都无法完美复制这种行为——因为你无法访问 `[[ArrayLength]]`。

```javascript
// 普通对象无法真正成为 Array
const fakeArray = {
  0: 'a', 1: 'b', 2: 'c',
  length: 3,
  [Symbol.iterator]: function* () { yield* Object.values(this); },
  push(item) { this[this.length] = item; this.length++; },
  // ... 还要模拟 splice, slice, map, filter ...
};

// 它看起来像数组，但它不是真正的数组
console.log(Array.isArray(fakeArray)); // false
console.log(fakeArray instanceof Array);  // false
fakeArray.length = 0;  // 不会真的删除元素 —— 因为没有 [[ArrayLength]]
console.log(fakeArray[0]);  // "a" —— 还在！（真数组会变成 undefined）
```

而继承 `Array` 的好处就在于：子类实例**天然拥有**这些内部槽位。引擎会在创建对象时正确地初始化它们，所有的内置方法也能正确地和它们交互。这就是为什么要优先选择 `extends Array` 而不是"用普通对象模拟数组"的原因。

可以用"身份证芯片"来类比内部槽位。真正的 `Array` 对象就像持有合法身份证的公民——芯片里存储着官方认证的信息（`[[ArrayLength]]` 等），所有的公共服务机构（内置方法）都能读取并信任这些信息。而你用普通对象模拟的"假数组"就像一张伪造的身份证——虽然外观上可以做得惟妙惟肖，但没有真正的芯片，一旦遇到严格的核验（比如 `Array.isArray()` 或 `length` 截断行为）就会暴露原形。只有通过合法渠道出生（`extends Array`）的对象才能获得真正的芯片。

## 哪些内置类可以被安全继承

### 安全继承（推荐）

大多数内置类都可以安全地继承，只要遵循基本的规则（调用正确的 `super()`，必要时设置 `Symbol.species`）：

```javascript
// 数组相关
class EnhancedArray extends Array {}
class TypedCollection extends Array {}

// 错误相关
class AppError extends Error {}
class NetworkError extends Error {}
class ValidationError extends Error {}

// Map / Set / WeakMap / WeakSet
class CacheMap extends Map {}
class BoundedSet extends Set {}

// Promise（需要注意返回值类型）
class TrackedPromise extends Promise {}
```

### 需要特别注意

```javascript
// ArrayBuffer 及其视图类 —— 可以继承但不常见
class SecureBuffer extends ArrayBuffer {}

// DataView —— 同上
class CustomDataView extends DataView {}

// Date —— 可以继承但很少有必要（Date 的 API 设计不太适合扩展）
class SmartDate extends Date {}

// RegExp —— 可以继承
class PatternWithFlags extends RegExp {}

// Function —— 技术上可行但极其罕见
class LoggedFunction extends Function {}
```

### 不建议或不支持

```javascript
// Boolean, Number, String —— 原始包装类，继承几乎没意义
class MyBoolean extends Boolean {} // 能工作但没有实用价值

// Symbol —— 不能被继承
// class MySymbol extends Symbol {} // TypeError!

// null / undefined —— 不是构造器
// class ExtendsNull extends null {} // 特殊情况
```

## 最佳实践清单

在决定是否继承某个内置类之前，问自己以下几个问题：

1. **我是否真的需要继承？** 很多时候组合（Composition）比继承更灵活。如果你只是想让一个对象"表现得像数组"，不一定非要继承 `Array`——可以用迭代器协议来实现。

2. **目标内置类是否支持良好的继承语义？** `Array`、`Error`、`Map`、`Set` 的继承支持比较成熟；`Promise` 的继承则有一些边界情况需要注意。

3. **你是否理解了 `Symbol.species` 的影响？** 对于 `Array` 子类，一定要考虑是否需要覆盖 `[[Species]]` 来控制方法返回值类型。

4. **性能是否是关注点？** 继承内置类可能会影响引擎的优化能力（比如 V8 无法对内置类子类应用某些内联优化）。如果在热点路径中使用，最好进行基准测试。

5. **跨环境兼容性如何？** 某些内置类继承行为在不同浏览器或 Node.js 版本之间可能有细微差异。特别是在老版本环境中，`Symbol.species` 可能不被支持。
