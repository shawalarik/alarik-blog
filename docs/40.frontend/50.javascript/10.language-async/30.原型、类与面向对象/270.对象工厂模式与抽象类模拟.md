# 对象工厂模式与抽象类模拟

## 引言：当 `new` 不够用时

`class`、`extends`、`super` 这些面向对象编程的核心工具很强大，但并非万能。在实际开发中，你会遇到很多 `new` 和 `class` 无法优雅解决的问题：

- 如何根据运行时的参数（比如配置文件中的字符串）来决定创建哪种对象？
- 如何在不使用 TypeScript 的情况下，强制子类必须实现某个方法？
- 如何创建一个"不能直接实例化，只能被继承"的类？
- 如何在创建对象时隐藏一些内部细节，让调用者无需关心构造过程？

这些问题指向了两种重要的设计模式：**工厂模式（Factory Pattern）**和 **抽象类（Abstract Class）**。JavaScript 没有原生的 `abstract` 关键字，但我们可以用现有的语言特性完美地模拟它。同样地，工厂模式虽然不像某些语言那样有专门的语法糖，但用函数式的方式实现反而更加灵活。

本文将深入探讨这两种模式的原理、实现方式和最佳实践。它们是构建可维护、可扩展的 JavaScript 架构的基石。

---

## 第一部分：工厂模式

### 为什么需要工厂模式？

要理解工厂模式的价值，我们首先需要理解它的对立面——直接使用 `new` 创建对象的局限性。

#### 局限一：暴露了具体类型

```javascript
// 直接 new —— 调用者必须知道具体的类名
const db = new MySQLConnection({
  host: 'localhost',
  port: 3306,
});
```

这段代码有什么问题？问题在于：调用者必须知道 `MySQLConnection` 这个类的存在。如果明天你要切换到 PostgreSQL，所有创建连接的地方都需要改动。这违反了一个重要的设计原则——**依赖倒置原则（DIP）**：高层模块不应该依赖低层模块，两者都应该依赖抽象。

**通俗类比**：就像去餐厅点菜。如果顾客需要自己去后厨指定"用3号锅、2号灶台、王师傅炒菜"，那餐厅就乱套了。正确的做法是顾客只管看菜单点菜（依赖抽象），至于谁来做、用什么工具做（具体实现），那是厨房的事。

#### 局限二：创建逻辑复杂

有些对象的创建不是一行 `new` 就能搞定的。可能需要：

```javascript
// 复杂的创建流程
function createHttpClient() {
  const adapter = detectEnvironment();           // 检测环境
  const config = loadConfig();                    // 加载配置
  const interceptor = createAuthInterceptor();    // 创建拦截器
  const client = new HttpClient(adapter, config); // 组装
  client.setupRetryPolicy(config.retry);          // 设置重试策略
  client.registerInterceptor(interceptor);        // 注册拦截器
  return client;                                  // 返回
}
```

这种"准备材料 → 组装 → 配置 → 返回"的流程，如果散落在代码的各个地方，会造成大量重复且难以维护。工厂模式就是把这些复杂的创建逻辑封装到一个地方——**工厂**。

**通俗类比**：买一辆汽车。你不需要知道汽车的发动机是怎么组装的、喷漆经过几道工序、质检有哪些标准。你只需要去4S店（工厂），选好型号、颜色、配置，然后提车。工厂把所有的复杂制造过程都封装了起来。

#### 局限三：无法动态选择类型

```javascript
// 假设配置文件中指定了数据库类型
const dbType = config.database.type; // 可能是 'mysql' | 'postgres' | 'mongodb'

if (dbType === 'mysql') {
  return new MySQLConnection(config);
} else if (dbType === 'postgres') {
  return new PostgreSQLConnection(config);
} else if (dbType === 'mongodb') {
  return new MongoDBConnection(config);
}
```

这种 `if-else` 链如果出现在多个地方，每次新增一种数据库类型就需要修改所有地方。工厂模式可以把这个选择逻辑集中管理。

### 工厂函数基础

最简单的工厂就是一个返回新对象的函数：

```javascript
// 最基础的工厂函数
function createUser(name, email) {
  return {
    name,
    email,
    sayHi() {
      console.log(`Hi, I'm ${this.name}`);
    }
  };
}

const alice = createUser('Alice', 'alice@example.com');
const bob = createUser('Bob', 'bob@example.com');

alice.sayHi(); // Hi, I'm Alice
bob.sayHi();   // Hi, I'm Bob
```

这就是所谓的**工厂函数（Factory Function）**——一个专门用来创建并返回对象的函数。它与构造函数的区别在于：

| 特性 | 构造函数 (`new`) | 工厂函数 |
|------|------------------|----------|
| 调用方式 | `new User()` | `createUser()` |
| this 绑定 | 自动绑定到新对象 | 无需 this / 手动处理 |
| 首字母大写约定 | 必须 | 通常不遵守（小驼峰） |
| 原型链方法 | 在 prototype 上共享 | 每个对象独立拥有（或手动优化） |
| 忘记 new 会怎样 | this 指向全局（危险！） | 完全没问题 |

**核心优势**：工厂函数不会遇到"忘记写 `new` "的问题——因为它根本不需要 `new`。这是它相对于传统构造函数的一个显著优势。

> **历史背景**：在 ES6 的 `class` 出现之前，JavaScript 社区对"应该用构造函数还是工厂函数"有过长期的争论。Douglas Crockford（《JavaScript 语言精粹》作者）甚至曾公开表示："我不再使用 `new` 了。"他认为工厂函数更安全、更直观。不过随着 `class` 的普及，这场争论已经逐渐平息——两者各有适用场景。

### 工厂函数进阶：闭包封装私有状态

工厂函数真正强大的地方在于它可以利用闭包来创建**真正的私有变量**：

```javascript
function createBankAccount(owner, initialBalance = 0) {
  // 这些变量在外部完全不可访问
  let balance = initialBalance;
  const transactions = [];

  return {
    get owner() { return owner; },

    get balance() { return balance; },

    deposit(amount) {
      if (amount <= 0) {
        throw new Error('存款金额必须大于零');
      }
      balance += amount;
      transactions.push({ type: 'deposit', amount, date: new Date() });
      console.log(`存入 ${amount}，余额 ${balance}`);
      return balance;
    },

    withdraw(amount) {
      if (amount <= 0) {
        throw new Error('取款金额必须大于零');
      }
      if (amount > balance) {
        throw new Error('余额不足');
      }
      balance -= amount;
      transactions.push({ type: 'withdraw', amount, date: new Date() });
      console.log(`取出 ${amount}，余额 ${balance}`);
      return balance;
    },

    getHistory() {
      // 返回副本，防止外部篡改原始记录
      return [...transactions];
    }
  };
}

const account = createBankAccount('张三', 1000);

account.deposit(500);   // 存入 500，余额 1500
account.withdraw(200);  // 取出 200，余额 1300

console.log(account.balance);       // 1300 ✓ 可以读取

console.log(account.balance = 9999999);  // 试图篡改！
console.log(account.balance);       // 1300 ← 篡改无效！因为 getter 返回的是闭包变量
```

**为什么外部无法修改 `balance`？**

这里涉及到了闭包的核心机制。当我们调用 `createBankAccount` 时：

1. 函数内部的 `balance` 变量被创建
2. 返回的对象中的方法（`deposit`、`withdraw`、getter）**捕获了对 `balance` 的引用**
3. 外部只能通过这些方法间接操作 `balance`
4. 外部代码**没有任何方式**可以直接访问 `balance` 变量本身

这不是什么"约定"或者"命名规范"（像 `_balance` 下划线前缀那样），而是**语言层面的硬性保护**。就像银行的保险柜——你可以通过柜台办理业务（调用方法），但你不可能自己伸手进去拿钱。

对比一下用 `class` + `_约定` 的方式：

```javascript
class BankAccount {
  constructor(owner, initialBalance = 0) {
    this.owner = owner;
    this._balance = initialBalance;  // 只是约定！实际上可以随意修改
  }

  deposit(amount) { /* ... */ }
  withdraw(amount) { /* ... */ }

  get balance() { return this._balance; }
}

const account = new BankAccount('张三', 1000);
account._balance = 9999999;  // 没有任何东西阻止你这么做！
console.log(account.balance);  // 9999999 ← 篡改成功
```

下划线前缀只是一种"君子协定"，就像你在自家门上贴了一张"请勿入内"的纸条——守规矩的人会尊重它，但如果有人非要闯进来，这张纸条毫无阻挡能力。而闭包私有变量则相当于装了一扇铁门——物理层面上就不可能从外面进去。

当然，ES2022 引入了真正的私有字段 `#balance`，可以达到同样的效果：

```javascript
class BankAccount {
  #balance;

  constructor(owner, initialBalance = 0) {
    this.owner = owner;
    this.#balance = initialBalance;
  }
  // ...
}
```

所以现在的选择更加丰富了：
- **闭包工厂函数**：私有性最强，但不支持原型链共享（每个实例的方法都是独立的）
- **`#field` 私有字段**：兼顾私有性和原型共享，但语法较新
- **`_约定`**：兼容性最好，但没有实际保护能力

### 参数化工厂：运行时决定创建什么

参数化工厂是最常用的工厂形式——根据传入的参数来决定创建什么类型的对象：

```javascript
// ========== 数据库连接工厂 ==========

class MySQLConnection {
  constructor(config) {
    this.type = 'mysql';
    this.config = config;
  }
  connect() { console.log(`MySQL 连接到 ${this.config.host}:${this.config.port}`); }
  query(sql) { console.log(`[MySQL] 执行: ${sql}`); return []; }
}

class PostgreSQLConnection {
  constructor(config) {
    this.type = 'postgres';
    this.config = config;
  }
  connect() { console.log(`PostgreSQL 连接到 ${config.host}:${config.port}`); }
  query(sql) { console.log(`[Postgres] 执行: ${sql}`); return []; }
}

class MongoDBConnection {
  constructor(config) {
    this.type = 'mongodb';
    this.config = config;
  }
  connect() { console.log(`MongoDB 连接到 ${config.url}`); }
  query(filter) { console.log(`[MongoDB] 查询:`, filter); return []; }
}

// 工厂函数：统一入口
function createDatabaseConnection(type, config) {
  switch (type) {
    case 'mysql':
      return new MySQLConnection(config);
    case 'postgres':
      return new PostgreSQLConnection(config);
    case 'mongodb':
      return new MongoDBConnection(config);
    default:
      throw new Error(`不支持的数据库类型: ${type}`);
  }
}

// 使用
const config = { host: 'localhost', port: 3306 };

const mysqlDb = createDatabaseConnection('mysql', config);
mysqlDb.connect(); // MySQL 连接到 localhost:3306

const pgDb = createDatabaseConnection('postgres', { host: 'localhost', port: 5432 });
pgDb.connect();   // PostgreSQL 连接到 localhost:5432

const mongoDb = createDatabaseConnection('mongodb', { url: 'mongodb://localhost:27017' });
mongoDb.connect(); // MongoDB 连接到 mongodb://localhost:27017
```

**设计要点**：

1. **单一职责**：工厂只负责"根据类型创建对象"，不负责后续的使用
2. **统一接口**：所有产品类都应该实现相同的方法（如 `connect()`、`query()`），这样调用者不需要关心具体类型
3. **错误处理**：不认识的类型要抛出明确的错误，而不是静默失败

**通俗类比**：这就像汽车工厂的生产线。你告诉工厂"我要一辆SUV"、"我要一辆轿车"或"我要一辆跑车"，同一条生产线可以根据你的需求制造出不同类型的汽车。作为消费者，你只需要踩油门就能开走（统一接口），不需要关心发动机是V6还是V8。

### 注册表工厂：更灵活的类型注册

上面的 `switch-case` 方式有一个缺点：每增加一种新的数据库类型，就需要修改工厂函数本身。这违反了**开放-封闭原则（OCP）**——对扩展开放，对修改封闭。

更好的做法是用**注册表模式**：

```javascript
class DatabaseConnectionFactory {
  #registry = new Map();

  // 注册一种数据库类型
  register(type, ConnectionClass) {
    if (typeof ConnectionClass !== 'function') {
      throw new TypeError('ConnectionClass 必须是一个构造函数或类');
    }
    this.#registry.set(type, ConnectionClass);
    return this; // 支持链式调用
  }

  // 创建连接
  create(type, config) {
    const ConnectionClass = this.#registry.get(type);
    if (!ConnectionClass) {
      const supported = [...this.#registry.keys()].join(', ');
      throw new Error(
        `不支持的数据库类型: "${type}"。支持的类型: ${supported}`
      );
    }
    return new ConnectionClass(config);
  }

  // 查询已注册的类型
  getSupportedTypes() {
    return [...this.#registry.keys()];
  }
}

// ========== 注册各种数据库类型（可以在任何地方、任何时间）==========
const factory = new DatabaseConnectionFactory();

factory
  .register('mysql', MySQLConnection)
  .register('postgres', PostgreSQLConnection)
  .register('mongodb', MongoDBConnection);

// 将来可以轻松扩展，无需修改工厂源码
// factory.register('redis', RedisConnection);

// 使用 —— 与之前完全相同
const db = factory.create('mysql', { host: 'localhost', port: 3306 });
db.connect();

// 查看支持列表
console.log(factory.getSupportedTypes()); // ['mysql', 'postgres', 'mongodb']
```

**这种方式的优势是什么？**

1. **可扩展性强**：第三方库可以注册自己的类型，而不需要改工厂的代码
2. **解耦彻底**：工厂不知道也不关心有哪些具体类型——它只是一个注册表+查找表
3. **运行时动态**：可以在程序运行过程中随时注册新类型

**类比理解**：传统的 `switch-case` 工厂像一个固定的菜单——想加新菜品得重新印制菜单。而注册表工厂像是一个智能推荐系统——任何厨师（开发者）都可以把自己的特色菜注册进去，系统自动把它加到可选列表中。

### 抽象工厂模式：创建相关对象家族

有时候，我们需要一次性创建一组**相互关联的对象**。比如 UI 组件库，不同的主题（Windows风格、macOS风格）下，按钮、输入框、对话框等组件的外观和行为都不同，但同一主题下的组件必须协调一致。

这就是**抽象工厂（Abstract Factory）**的应用场景：

```javascript
// ========== Windows 风格组件族 ==========
const WindowsFactory = {
  createButton(label) {
    return {
      type: 'windows-button',
      label,
      render() {
        console.log(`[Windows] 渲染方形按钮: "${label}"`);
        console.log('  ┌─────────────────┐');
        console.log(`  │   ${label.padEnd(15)} │`);
        console.log('  └─────────────────┘');
      },
      click() { console.log('[Windows] 按钮点击效果: 边框高亮'); }
    };
  },

  createInput(placeholder) {
    return {
      type: 'windows-input',
      placeholder,
      render() {
        console.log(`[Windows] 渲染白色输入框: placeholder="${placeholder}"`);
      },
      focus() { console.log('[Windows] 输入框聚焦: 显示蓝色边框'); }
    };
  },

  createDialog(title, content) {
    return {
      type: 'windows-dialog',
      title,
      content,
      render() {
        console.log(`[Windows] 渲染对话框: "${title}"`);
        console.log('  内容:', content);
      },
      show() { console.log('[Windows] 弹出对话框: 居中显示'); },
      close() { console.log('[Windows] 关闭对话框: 点击 X 按钮'); }
    };
  }
};

// ========== macOS 风格组件族 ==========
const MacOSFactory = {
  createButton(label) {
    return {
      type: 'macos-button',
      label,
      render() {
        console.log(`[macOS] 渲染圆角按钮: "${label}"`);
        console.log('  ╭─────────────────╮');
        console.log(`  │   ${label.padEnd(15)} │`);
        console.log('  ╰─────────────────╯');
      },
      click() { console.log('[macOS] 按钮点击效果: 渐变下沉'); }
    };
  },

  createInput(placeholder) {
    return {
      type: 'macos-input',
      placeholder,
      render() {
        console.log(`[macOS] 渲染圆角输入框: placeholder="${placeholder}"`);
      },
      focus() { console.log('[macOS] 输入框聚焦: 显示金色光环'); }
    };
  },

  createDialog(title, content) {
    return {
      type: 'macos-dialog',
      title,
      content,
      render() {
        console.log(`[macOS] 渲染对话框: "${title}"`);
        console.log('  内容:', content);
      },
      show() { console.log('[macOS] 弹出对话框: 从底部滑出'); },
      close() { console.log('[macOS] 关闭对话框: 向下滑出消失'); }
    };
  }
};

// ========== 使用抽象工厂 ==========

function buildUI(factory) {
  console.log('\n--- 构建 UI ---');

  const btn = factory.createButton('确认');
  const input = factory.createInput('请输入用户名...');
  const dialog = factory.createDialog('提示', '操作成功完成');

  btn.render();
  input.render();
  dialog.render();
  
  btn.click();
  input.focus();
  dialog.show();
  dialog.close();
}

// 根据操作系统选择工厂
const os = process?.platform || 'windows';
const uiFactory = os === 'darwin' ? MacOSFactory : WindowsFactory;

buildUI(uiFactory);
```

输出结果（假设在 Windows 上运行）：

```
--- 构建 UI ---
[Windows] 渲染方形按钮: "确认"
  ┌─────────────────┐
  │   确认            │
  └─────────────────┘
[Windows] 渲染白色输入框: placeholder="请输入用户名..."
[Windows] 渲染对话框: "提示"
  内容: 操作成功完成
[Windows] 按钮点击效果: 边框高亮
[Windows] 输入框聚焦: 显示蓝色边框
[Windows] 弹出对话框: 居中显示
[Windows] 关闭对话框: 点击 X 按钮
```

**关键洞察**：`buildUI` 函数完全不关心用的是哪个工厂。它只知道工厂能提供 `createButton`、`createInput`、`createDialog` 这三个方法，而且创建出来的组件都有 `render()` 方法。只要换一个工厂，整个 UI 的风格就会全部改变——但 `buildUI` 的代码一行都不需要改。

**类比理解**：这就像装修公司。你说"我要中式风格"，装修公司就会给你配中式家具、中式窗帘、中式灯具；你说"我要北欧风格"，同样的房间就会变成北欧风家具、北欧风窗帘、北欧风灯具。你不需要告诉他们怎么搭配每一件物品，只需要选一个"风格"就行——剩下的交给工厂。

### 静态工厂方法

在 `class` 中，静态方法是实现工厂模式的常见方式。许多内置类都在使用这种模式：

```javascript
// 内置示例
Array.from([1, 2, 3]);            // 从类数组创建数组
Object.assign({}, source);         // 创建合并后的对象
Promise.resolve(value);            // 创建已完成的 Promise
Date.now();                        // 创建当前时间戳
URL.createObjectURL(blob);         // 从 Blob 创建 URL
```

我们在自己的类中也可以这样使用：

```javascript
class User {
  #name;
  #email;

  constructor(name, email) {
    this.#name = name;
    this.#email = email;
  }

  get name() { return this.#name; }
  get email() { return this.#email; }

  // 静态工厂方法：从 JSON 对象创建
  static fromJSON(json) {
    if (!json || typeof json.name !== 'string') {
      throw new Error('Invalid user JSON: missing name');
    }
    return new User(
      json.name,
      json.email || ''
    );
  }

  // 静态工厂方法：从数据库记录创建
  static fromDBRow(row) {
    return new User(
      row.user_name,    // 数据库列名映射
      row.user_email
    );
  }

  // 静态工厂方法：创建管理员
  static createAdmin(name, email) {
    const admin = new User(name, email);
    admin.#role = 'admin';  // 注意：这里需要特殊处理
    return admin;
  }

  toString() {
    return `User(${this.#name}, ${this.#email})`;
  }
}

// 不同来源，不同的创建方式
const fromJSON = User.fromJSON({ name: 'Alice', email: 'alice@x.com' });
const fromDB = User.fromDBRow({ user_name: 'Bob', user_email: 'bob@x.com' });

console.log(fromJSON.toString()); // User(Alice, alice@x.com)
console.log(fromDB.toString());   // User(Bob, bob@x.com)
```

**静态工厂方法的优势**：

1. **有意义的名称**：`User.fromJSON()` 比 `new User(json)` 更清楚地表达了意图
2. **可以缓存/复用**：可以实现单例、对象池等高级模式
3. **可以返回子类型**：不一定返回当前类的实例，也可以返回子类实例
4. **封装复杂逻辑**：把数据转换、验证等逻辑藏在工厂方法内部

**《Effective Java》作者 Joshua Bloch 的观点**：

> "静态工厂方法与构造器的第一优势：**它们有名字**"。当构造器的参数不能很好地描述返回的对象时，静态工厂方法可以通过名称来表达意图。例如 `BigInteger(int, int, Random)` 可能返回素数还是合数？不清楚。但 `BigInteger.probablePrime()` 就一目了然了。

### 单例工厂

单例模式确保一个类只有一个实例，并提供一个全局访问点。这在管理全局资源时特别有用：

```javascript
class DatabaseConnectionPool {
  static #instance = null;

  #connections = [];
  #maxSize;
  #currentConfig;

  constructor(config) {
    if (DatabaseConnectionPool.#instance) {
      return DatabaseConnectionPool.#instance;
    }

    this.#maxSize = config.maxSize || 10;
    this.#currentConfig = config;
    DatabaseConnectionPool.#instance = this;
  }

  // 静态工厂方法 —— 推荐的获取方式
  static getInstance(config) {
    if (!DatabaseConnectionPool.#instance) {
      DatabaseConnectionPool.#instance = new DatabaseConnectionPool(config);
    }
    return DatabaseConnectionPool.#instance;
  }

  getConnection() {
    if (this.#connections.length > 0) {
      return this.#connections.pop();
    }
    if (this.#maxSize > 0) {
      this.#maxSize--;
      return { id: Date.now(), config: this.#currentConfig }; // 模拟连接
    }
    throw new Error('连接池已耗尽');
  }

  releaseConnection(conn) {
    this.#connections.push(conn);
  }

  get size() {
    return this.#connections.length;
  }
}

// 无论在哪里获取，都是同一个实例
const pool1 = DatabaseConnectionPool.getInstance({ maxSize: 5 });
const pool2 = DatabaseConnectionPool.getInstance({ maxSize: 100 }); // 配置会被忽略！

console.log(pool1 === pool2); // true —— 始终是同一个实例

pool1.getConnection();
console.log(pool1.size);  // 0
console.log(pool2.size);  // 0 —— 共享同一个池子
```

**注意**：上面的实现有一个微妙之处——第一次调用 `getInstance` 时传入的 `config` 会被使用，之后的调用即使传入不同配置也会被忽略（因为实例已经创建了）。如果你希望配置可以被更新，需要额外处理。

**何时使用单例？**

| 适用场景 | 示例 |
|----------|------|
| 全局唯一的资源 | 数据库连接池、线程池 |
| 应用级别的配置 | 全局配置中心、环境变量管理 |
| 日志系统 | 全局 Logger 实例 |
| 缓存/状态存储 | Redux Store、应用状态管理器 |

**何时避免单例？**

- 需要多实例进行测试的时候（单例会让测试之间互相干扰）
- 需要多套配置并行运行的时候
- 当"全局唯一"只是当前的假设，未来可能会变化时

## 第二部分：抽象类模拟

### 什么是抽象类？

在 Java、C#、TypeScript 等语言中，**抽象类（Abstract Class）** 是一个特殊的类：

- 它**不能被直接实例化**——你不能 `new AbstractClass()`
- 它可以包含**抽象方法**——只有声明没有实现，子类必须实现
- 它也可以包含**具体方法**——已有实现，子类可以直接继承或覆盖
- 它的主要作用是**定义一套契约/模板**，让子类遵循统一的接口

```typescript
// TypeScript 中的抽象类（伪代码示意）
abstract class Animal {
  abstract makeSound(): void;  // 抽象方法 —— 子类必须实现
  
  move(): void {               // 具体方法 —— 已有实现
    console.log('正在移动...');
  }
}

class Dog extends Animal {
  makeSound(): void {          // 必须实现！
    console.log('汪！');
  }
}

const a = new Animal(); // 编译错误！不能实例化抽象类
const d = new Dog();     // 正常 ✓
d.makeSound();           // 汪！
d.move();                // 正在移动...（继承自父类）
```

**JavaScript 的问题**：原生 JavaScript 没有 `abstract` 关键字。但这不代表我们无法实现相同的效果——我们可以利用现有特性来模拟。

**通俗类比**：抽象类就像一份"合同模板"。模板上规定了哪些条款必须填写（抽象方法）、哪些条款已经预填好了（具体方法）。你不能直接拿空白模板去执行（不能实例化），而必须先填完所有必填项（实现抽象方法），得到一份完整的合同（子类实例）才能使用。

---

### 模拟方式一：手动抛出错误

最简单也最常见的抽象类模拟方式是在"抽象方法"中抛出错误：

```javascript
class Animal {
  constructor(name) {
    if (new.target === Animal) {
      throw new Error('Animal 是抽象类，不能直接实例化');
    }
    this.name = name;
  }

  // 抽象方法：子类必须覆盖
  makeSound() {
    throw new Error(
      `抽象方法 makeSound() 未被 ${this.constructor.name} 实现`
    );
  }

  // 具体方法：已提供默认实现
  move() {
    console.log(`${this.name} 正在移动...`);
  }
}

class Dog extends Animal {
  constructor(name) {
    super(name);
  }

  makeSound() {
    console.log(`${this.name}: 汪！汪！`);
  }
}

class Cat extends Animal {
  constructor(name) {
    super(name);
  }
  // 故意不实现 makeSound —— 运行时会报错
}

// 测试
const dog = new Dog('旺财');
dog.makeSound(); // 旺财: 汪！汪！
dog.move();      // 旺财 正在移动...

const cat = new Cat('咪咪');
cat.move();     // 咪咪 正在移动...
cat.makeSound(); // Error: 抽象方法 makeSound() 未被 Cat 实现

const animal = new Animal('未知'); 
// Error: Animal 是抽象类，不能直接实例化
```

**逐行解析关键技术点**：

**1. 阻止直接实例化 —— `new.target`**

```javascript
if (new.target === Animal) {
  throw new Error('Animal 是抽象类，不能直接实例化');
}
```

`new.target` 是一个特殊的属性，它在任何函数/构造器中都能访问。它的值取决于调用方式：
- 通过 `new Dog()` 调用时，Dog 内部的 `new.target` 是 `Dog`
- 通过 `new Animal()` 调用时，Animal 内部的 `new.target` 是 `Animal`
- 普通调用（不用 `new`）时，`new.target` 是 `undefined`

所以 `new.target === Animal` 的含义是：**当前类是被直接实例化的，而不是通过子类实例化的**。这正是我们想要检测的情况。

**2. 强制子类实现方法 —— 抛出错误**

```javascript
makeSound() {
  throw new Error(
    `抽象方法 makeSound() 未被 ${this.constructor.name} 实现`
  );
}
```

如果子类忘记覆盖这个方法，那么调用时会抛出一个清晰的错误信息，告诉你哪个类的哪个方法没有被实现。

注意这里用了 `this.constructor.name` 来获取实际的子类名——这让错误信息更有帮助。如果简单地写 `"未被子类实现"`，当你有深层继承链时（`Dog → Pet → Animal`），很难定位到底是谁漏实现了。

**这种方式的优缺点：**

| 优点 | 缺点 |
|------|------|
| 实现简单，零依赖 | 错误只在**运行时**触发，不是编译期 |
| 错误信息清晰明确 | IDE 无法给出提示"你需要实现这个方法" |
| 与普通类语法完全兼容 | 子类开发者需要阅读文档才知道要实现什么 |
| 支持多层继承 | — |

### 模板方法模式（Template Method Pattern）

模板方法模式是抽象类的经典应用场景。它的核心思想是：

> **在父类中定义算法的骨架（模板），将某些步骤延迟到子类中实现。**

```javascript
// ========== 抽象基类：数据处理管道 ==========
class DataProcessor {
  constructor(data) {
    if (new.target === DataProcessor) {
      throw new Error('DataProcessor 是抽象类');
    }
    this.rawData = data;
    this.processedData = null;
  }

  // 🔒 模板方法：定义了完整的处理流程（final，不应被覆盖）
  process() {
    console.log('===== 开始数据处理 =====');
    
    // 步骤 1：读取数据
    const raw = this.fetchData();
    console.log(`[1/4] 数据读取完毕，共 ${raw.length} 条记录`);

    // 步骤 2：校验数据
    const validated = this.validate(raw);
    console.log(`[2/4] 校验完成，${validated.validCount} 条有效，${validated.errorCount} 条无效`);

    // 步骤 3：转换数据（抽象方法 —— 子类决定如何转换）
    this.processedData = this.transform(validated.data);
    console.log(`[3/4] 转换完成`);

    // 步骤 4：保存结果
    const result = this.save(this.processedData);
    console.log(`[4/4] 保存完成`);
    
    console.log('===== 处理结束 =====\n');
    return result;
  }

  // ✅ 已实现的步骤（子类可以选择覆盖）
  fetchData() {
    return this.rawData;
  }

  validate(data) {
    let validCount = 0, errorCount = 0;
    const validData = [];

    for (const item of data) {
      if (item != null && typeof item === 'object') {
        validData.push(item);
        validCount++;
      } else {
        errorCount++;
      }
    }

    return { data: validData, validCount, errorCount };
  }

  save(data) {
    return { success: true, count: data.length };
  }

  // 🎨 抽象方法 —— 子类必须实现
  transform(data) {
    throw new Error(`transform() 未被 ${this.constructor.name} 实现`);
  }
}

// ========== 具体子类 A：CSV 导入处理器 ==========
class CSVImportProcessor extends DataProcessor {
  transform(data) {
    // CSV 特有的转换逻辑：扁平化对象、字段重命名
    return data.map(row => ({
      full_name: `${row.first_name || ''} ${row.last_name || ''}`.trim(),
      email: (row.email || '').toLowerCase(),
      age: parseInt(row.age) || 0,
      imported_at: new Date().toISOString()
    }));
  }

  validate(data) {
    // CSV 特有的校验：检查邮箱格式
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    let validCount = 0, errorCount = 0;
    const validData = [];

    for (const item of data) {
      if (item && typeof item.email === 'string' && emailRegex.test(item.email)) {
        validData.push(item);
        validCount++;
      } else {
        errorCount++;
      }
    }

    return { data: validData, validCount, errorCount };
  }
}

// ========== 具体子类 B：JSON API 同步处理器 ==========
class JSONSyncProcessor extends DataProcessor {
  transform(data) {
    // API 特有的转换逻辑：嵌套展开、日期格式化
    return data.map(item => ({
      ...item,
      created_at: item.created_at ? new Date(item.created_at).getTime() : null,
      metadata: {
        source: item.source || 'unknown',
        version: item.version || 1
      }
    }));
  }
}

// ========== 使用 ==========

const csvData = [
  { first_name: '张', last_name: '三', email: 'ZhangSan@example.com', age: '25' },
  { first_name: '李', last_name: '四', email: 'invalid-email', age: '30' },
  { first_name: '王', last_name: '五', email: 'WangWu@example.com', age: '28' },
];

const csvProcessor = new CSVImportProcessor(csvData);
const csvResult = csvProcessor.process();
console.log('CSV 结果:', csvResult.processedData);

const jsonData = [
  { id: 1, name: 'Product A', price: 100, created_at: '2025-01-15T10:30:00Z', source: 'erp' },
  { id: 2, name: 'Product B', price: 200, created_at: '2025-02-20T14:00:00Z', source: 'api' },
];

const jsonProcessor = new JSONSyncProcessor(jsonData);
const jsonResult = jsonProcessor.process();
console.log('JSON 结果:', jsonResult.processedData);
```

输出：

```
===== 开始数据处理 =====
[1/4] 数据读取完毕，共 3 条记录
[2/4] 校验完成，2 条有效，1 条无效
[3/4] 转换完成
[4/4] 保存完成
===== 处理结束 =====

CSV 结果: [
  { full_name: '张 三', email: 'zhangsan@example.com', age: 25, imported_at: '...' },
  { full_name: '王 五', email: 'wangwu@example.com', age: 28, imported_at: '...' }
]

===== 开始数据处理 =====
[1/4] 数据读取完毕，共 2 条记录
[2/4] 校验完成，2 条有效，0 条无效
[3/4] 转换完成
[4/4] 保存完成
===== 处理结束 =====

JSON 结果: [
  { id: 1, name: 'Product A', price: 100, created_at: 1705319400000, metadata: {...} },
  { id: 2, name: 'Product B', price: 200, created_count: 1740045600000, metadata: {...} }
]
```

**模板方法模式的价值**：

1. **流程固定，步骤可变**：`process()` 定义的四步流程永远不变，但每一步的具体行为可以由子类定制
2. **代码复用最大化**：通用的 `fetchData`、`validate`、`save` 只写一次，所有子类共享
3. **关注点分离**：父类管"什么时候做什么"，子类管"怎么做"
4. **易于扩展**：添加新的数据源只需新建一个子类，实现 `transform` 即可

**通俗类比**：这就像是烘焙食谱。食谱（抽象类）规定了步骤：1. 准备材料 2. 混合面团 3. 烘烤 4. 装饰。其中第1、2、4步已经有标准做法（具体方法）。但第3步"烘烤"——烤多少度、烤多长时间——取决于你做的是面包、蛋糕还是饼干（由子类决定）。无论做什么糕点，四个步骤的顺序永远不会变。

### 模拟方式二：抽象方法标记 + 自动检测

如果我们想在对象创建时就检测"是否所有抽象方法都已被实现"，而不是等到调用时才报错，可以用以下方式：

```javascript
// ========== 抽象工具函数 ==========

function defineAbstractClass(ClassDef, abstractMethods = []) {
  // 包装原始类
  return class extends ClassDef {
    constructor(...args) {
      super(...args);

      // 创建后立即检查所有抽象方法是否已被实现
      for (const methodName of abstractMethods) {
        const proto = Object.getPrototypeOf(this);
        const method = proto[methodName];

        // 如果方法的来源仍然是基类（未被覆盖），说明子类没实现
        if (
          method === ClassDef.prototype[methodName] ||
          // 或者方法体仍然是抛出错误的版本
          (method && method.toString().includes('abstract method'))
        ) {
          throw new Error(
            `${proto.constructor.name} 没有实现必需的抽象方法: ${methodName}()`
          );
        }
      }
    }
  };
}

// ========== 使用 ==========

class Shape {
  constructor(name) {
    if (new.target === Shape) {
      throw new Error('Shape 是抽象类，不能直接实例化');
    }
    this.name = name;
  }

  area() {
    throw new Error(`abstract method: area()`);
  }

  perimeter() {
    throw new Error(`abstract method: perimeter()`);
  }

  toString() {
    return `${this.name}[area=${this.area()}, perimeter=${this.perimeter()}]`;
  }
}

// 用工具函数包装 Shape，指定哪些方法是"抽象"的
const AbstractShape = defineAbstractClass(Shape, ['area', 'perimeter']);

// 现在子类继承包装后的类
class Circle extends AbstractShape {
  constructor(radius) {
    super('Circle');
    this.radius = radius;
  }

  area() {
    return Math.PI * this.radius * this.radius;
  }

  perimeter() {
    return 2 * Math.PI * this.radius;
  }
}

class Rectangle extends AbstractShape {
  constructor(width, height) {
    super('Rectangle');
    this.width = width;
    this.height = height;
  }

  area() {
    return this.width * this.height;
  }

  // 故意遗漏 perimeter()
}

const circle = new Circle(5);
console.log(circle.toString()); // Circle[area=78.54..., perimeter=31.42...]

const rect = new Rectangle(10, 20);
// Error: Rectangle 没有实现必需的抽象方法: perimeter()
```

这种方式比第一种更好，因为**错误发生在创建对象时**，而不是等到调用那个方法时才发现问题。越早发现 bug，修复成本越低。

**但这种方案也有局限性**：
- 依赖方法体的字符串匹配（`toString().includes(...)`）不够健壮
- 如果子类继承了中间层（`A extends B extends AbstractShape`），检测逻辑可能出错
- 对于更严格的需求，建议使用 TypeScript 或其他静态分析工具

### 模拟方式三：接口协议（Protocol/Interface）

有时候我们不需要完整的抽象类，只需要定义"一个对象必须具备哪些方法"——这就叫接口或协议：

```javascript
// ========== 接口定义工具 ==========

function implementsProtocol(obj, protocol) {
  const missingMethods = [];

  for (const [methodName, descriptor] of Object.entries(protocol)) {
    if (typeof obj[methodName] !== 'function') {
      missingMethods.push(methodName);
      continue;
    }

    // 可选：检查参数数量
    if (descriptor.params != null) {
      const actualParams = obj[methodName].length;
      if (actualParams < descriptor.params) {
        missingMethods.push(`${methodName}(需要至少 ${descriptor.params} 个参数)`);
      }
    }
  }

  return {
    valid: missingMethods.length === 0,
    missingMethods
  };
}

// ========== 定义协议 ==========

const Drawable = {
  draw(context): { params: 1 }  // 需要接受 1 个参数
};

const Serializable = {
  toJSON(): {},
  fromJSON(json): { params: 1 }
};

const Animatable {
  update(deltaTime): { params: 1 },
  start() {},
  stop() {}
}

// ========== 使用 ==========

class Sprite {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }

  draw(ctx) {
    ctx.fillRect(this.x, this.y, 32, 32);
  }

  update(dt) {
    this.x += dt * 60;
  }

  start() {
    console.log('动画开始');
  }

  stop() {
    console.log('动画停止');
  }
}

const sprite = new Sprite(100, 100);

// 检查是否实现了 Drawable 协议
const drawableCheck = implementsProtocol(sprite, Drawable);
console.log(drawableCheck.valid);        // true
console.log(drawableCheck.missingMethods); // []

// 检查是否同时实现了多个协议
function checkAllProtocols(obj, protocols) {
  const results = {};
  for (const [name, protocol] of Object.entries(protocols)) {
    results[name] = implementsProtocol(obj, protocol);
  }
  return results;
}

const checks = checkAllProtocols(sprite, { Drawable, Animatable });
console.log(checks);
// {
//   Drawable: { valid: true, missingMethods: [] },
//   Animatable: { valid: true, missingMethods: [] }
// }
```

**接口协议 vs 抽象类**：

| 维度 | 抽象类 | 接口协议 |
|------|--------|----------|
| 关注点 | **部分实现 + 部分待实现** | **纯契约，无实现** |
| 继承关系 | 单继承 | 可实现多个协议 |
| 实例化 | 不能直接实例化 | 不是类，不存在实例化问题 |
| 方法实现 | 可以提供默认实现 | 不提供任何实现 |
| 适用场景 | 多个相关类共享通用逻辑 | 不相关的类需要遵循相同的契约 |

**类比理解**：抽象类像是"半成品房子"——地基、框架已经建好了（具体方法），但厨房怎么装修、墙面刷什么颜色还需要你自己决定（抽象方法）。接口协议则是"建筑规范手册"——它规定房子必须有防火通道、通风系统、紧急出口，但不帮你建造任何东西。你可以按照规范建别墅、公寓或者办公楼。

## 第三部分：工厂 + 抽象类综合实战

让我们把前面学的所有知识整合起来，构建一个真实世界中有意义的案例。

### 案例：插件架构系统

目标：设计一个插件架构，允许第三方开发者编写插件来扩展系统的功能。插件必须遵循统一的接口规范。

```javascript
// ========================================
// 第一层：定义抽象基类（插件的"合同"）
// ========================================

class PluginBase {
  constructor(name, version = '1.0.0') {
    // 阻止直接实例化
    if (new.target === PluginBase) {
      throw new Error('PluginBase 是抽象类，请继承它来创建插件');
    }

    this.name = name;
    this.version = version;
    this.enabled = false;
    this.hooks = new Map();
  }

  // 🔒 抽象方法：插件必须实现
  install() {
    throw new Error(
      `[${this.name}] 抽象方法 install() 未被实现`
    );
  }

  uninstall() {
    throw new Error(
      `[${this.name}] 抽象方法 uninstall() 未被实现`
    );
  }

  // ✅ 已实现的方法：生命周期钩子的通用机制
  on(event, callback) {
    if (!this.hooks.has(event)) {
      this.hooks.set(event, []);
    }
    this.hooks.get(event).push(callback);
    return this; // 链式调用
  }

  emit(event, ...args) {
    const callbacks = this.hooks.get(event) || [];
    for (const cb of callbacks) {
      try {
        cb(...args);
      } catch (err) {
        console.error(`[${this.name}] Hook "${event}" 执行错误:`, err);
      }
    }
  }

  enable() {
    if (!this.enabled) {
      this.install();
      this.enabled = true;
      this.emit('enabled');
      console.log(`[PluginSystem] 插件 "${this.name}" v${this.version} 已启用`);
    }
    return this;
  }

  disable() {
    if (this.enabled) {
      this.emit('disabling');
      this.uninstall();
      this.enabled = false;
      console.log(`[PluginSystem] 插件 "${this.name}" 已禁用`);
    }
    return this;
  }

  getInfo() {
    return {
      name: this.name,
      version: this.version,
      enabled: this.enabled,
      hooks: [...this.hooks.keys()]
    };
  }
}

// 第二层：插件工厂
// ========================================

class PluginFactory {
  #plugins = new Map();

  // 注册插件类
  register(PluginClass) {
    // 验证 PluginClass 是否符合规范
    const requiredMethods = ['install', 'uninstall'];
    for (const method of requiredMethods) {
      if (typeof PluginClass.prototype[method] !== 'function') {
        throw new Error(
          `${PluginClass.name} 缺少必需的方法: ${method}()`
        );
      }
    }

    // 验证它是否继承自 PluginBase
    if (!(PluginClass.prototype instanceof PluginBase)) {
      throw new Error(
        `${PluginName} 必须继承自 PluginBase`
      );
    }

    this.#plugins.set(PluginClass.name, PluginClass);
    console.log(`[PluginFactory] 已注册插件: ${PluginClass.name}`);
    return this;
  }

  // 创建插件实例
  create(name, options = {}) {
    const PluginClass = this.#plugins.get(name);
    if (!PluginClass) {
      const available = [...this.#plugins.keys()].join(', ');
      throw new Error(
        `未找到插件 "${name}"。可用插件: ${available}`
      );
    }
    return new PluginClass(options);
  }

  listAvailable() {
    return [...this.#plugins.keys()];
  }
}

// --- 插件 A：日志插件 ---
class LoggerPlugin extends PluginBase {
  #level;
  #storage;

  constructor(options = {}) {
    super('logger-plugin', options.version || '2.1.0');
    this.#level = options.level || 'info';
    this.#storage = [];
  }

  install() {
    console.log(`[Logger] 安装完成，日志级别: ${this.#level}`);

    // 拦截 console 方法
    this._originalConsole = { ...console };
    const self = this;

    console.log = (...args) => self.#handleLog('log', args);
    console.warn = (...args) => self.#handleLog('warn', args);
    console.error = (...args) => self.#handleLog('error', args);
  }

  uninstall() {
    // 还原 console
    if (this._originalConsole) {
      Object.assign(console, this._originalConsole);
    }
    console.log('[Logger] 已卸载，console 已还原');
  }

  #handleLog(level, args) {
    const entry = {
      timestamp: new Date().toISOString(),
      level,
      message: args.map(a =>
        typeof a === 'object' ? JSON.stringify(a) : String(a)
      ).join(' ')
    };
    this.#storage.push(entry);

    // 同时输出到原始 console（防止递归）
    const original = this._originalConsole;
    if (level === 'error') original.error(entry.timestamp, entry.message);
    else if (level === 'warn') original.warn(entry.timestamp, entry.message);
    else original.log(entry.timestamp, entry.message);
  }

  getLogs() {
    return [...this.#storage];
  }

  clearLogs() {
    this.#storage = [];
  }
}

// --- 插件 B：性能监控插件 ---
class PerformancePlugin extends PluginBase {
  #metrics;
  #observer;

  constructor(options = {}) {
    super('performance-plugin', options.version || '1.5.0');
    this.#metrics = new Map();
    this.sampleRate = options.sampleRate || 1.0;
  }

  install() {
    console.log('[Performance] 性能监控已启动');

    // 使用 PerformanceObserver 监控性能指标
    if (typeof PerformanceObserver !== 'undefined') {
      this.#observer = new PerformanceObserver((list) => {
        for (const entry of list.getEntries()) {
          this.#recordMetric(entry.name, entry.duration);
        }
      });
      this.#observer.observe({ entryTypes: ['measure', 'navigation'] });
    }

    // 包装 fetch 和 XMLHttpRequest
    this._wrapNetworkAPIs();
  }

  uninstall() {
    if (this.#observer) {
      this.#observer.disconnect();
    }
    this._unwrapNetworkAPIs();
    console.log('[Performance] 性能监控已停止');
    console.log('[Performance] 收集到的指标:', Object.fromEntries(this.#metrics));
  }

  #recordMetric(name, value) {
    if (Math.random() > this.sampleRate) return;

    if (!this.#metrics.has(name)) {
      this.#metrics.set(name, { count: 0, total: 0, min: Infinity, max: 0 });
    }

    const m = this.#metrics.get(name);
    m.count++;
    m.total += value;
    m.min = Math.min(m.min, value);
    m.max = Math.max(m.max, value);
  }

  _wrapNetworkAPIs() {
    const self = this;
    const originalFetch = window.fetch;

    window.fetch = async function(...args) {
      const url = typeof args[0] === 'string' ? args[0] : args[0]?.url;
      const start = performance.now();

      try {
        const response = await originalFetch.apply(this, args);
        const duration = performance.now() - start;
        self.#recordMetric(`fetch:${url}`, duration);
        return response;
      } catch (error) {
        const duration = performance.now() - start;
        self.#recordMetric(`fetch:${url}:error`, duration);
        throw error;
      }
    };

    this._originalFetch = originalFetch;
  }

  _unwrapNetworkAPIs() {
    if (this._originalFetch) {
      window.fetch = this._originalFetch;
    }
  }

  getReport() {
    const report = {};
    for (const [name, m] of this.#metrics) {
      report[name] = {
        avg: (m.total / m.count).toFixed(2) + 'ms',
        min: m.min.toFixed(2) + 'ms',
        max: m.max.toFixed(2) + 'ms',
        count: m.count
      };
    }
    return report;
  }
}

// --- 插件 C：认证插件 ---
class AuthPlugin extends PluginBase {
  #tokens;
  #refreshInterval;

  constructor(options = {}) {
    super('auth-plugin', options.version || '3.0.0');
    this.#tokens = new Map();
    this.#refreshInterval = options.refreshInterval || 300000; // 5 分钟
  }

  install() {
    console.log('[Auth] 认证系统已初始化');

    // 设置 token 自动刷新定时器
    this._timer = setInterval(() => {
      this.emit('tokenRefresh');
      console.log('[Auth] Token 刷新事件已触发');
    }, this.#refreshInterval);
  }

  uninstall() {
    if (this._timer) {
      clearInterval(this._timer);
    }
    this.#tokens.clear();
    console.log('[Auth] 认证系统已关闭');
  }

  setToken(key, token, expiresIn) {
    this.#tokens.set(key, {
      value: token,
      expiresAt: Date.now() + expiresIn
    });
  }

  getToken(key) {
    const entry = this.#tokens.get(key);
    if (!entry) return null;

    if (Date.now() > entry.expiresAt) {
      this.#tokens.delete(key);
      this.emit('tokenExpired', { key });
      return null;
    }

    return entry.value;
  }
}
```

**架构解析**：

```
┌──────────────────────────────────────────────────────┐
│                   PluginBase (抽象类)                  │
│                                                      │
│  ○ install()      ○ uninstall()   ← 抽象方法（必须实现）│
│  ✓ enable()       ✓ disable()     ← 生命周期管理      │
│  ✓ on()/emit()                    ← 事件钩子系统       │
│  ✓ getInfo()                       ← 元信息查询        │
├──────────────────────────────────────────────────────┤
│              LoggerPlugin  (具体实现 A)                 │
│              PerformancePlugin  (具体实现 B)            │
│              AuthPlugin  (具体实现 C)                   │
├──────────────────────────────────────────────────────┤
│               PluginFactory (工厂)                     │
│                                                      │
│  register()  → 验证 → 存储                             │
│  create()    → 查找 → 实例化                            │
│  list()      → 查询可用插件                            │
└──────────────────────────────────────────────────────┘
```

这个案例展示了：

1. **抽象类**（`PluginBase`）：定义了所有插件必须遵循的契约——必须实现 `install` 和 `uninstall`，同时提供了通用的生命周期管理和事件系统
2. **工厂**（`PluginFactory`）：集中管理插件的注册和创建，并在注册时验证插件的合法性
3. **具体插件**：每个插件专注于自己的功能领域（日志、性能、认证），但都遵循统一的接口规范
4. **可扩展性**：想要添加新插件？只需要继承 `PluginBase` 并注册到工厂即可，现有代码零改动

## 设计决策指南

### 什么时候用工厂模式？

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| 创建逻辑复杂（多步骤、条件判断） | 工厂函数/静态工厂方法 | 封装复杂性 |
| 运行时决定创建什么类型 | 参数化工厂/注册表工厂 | 动态分派 |
| 隐藏具体类型（依赖倒置） | 工厂 + 接口 | 解耦 |
| 需要创建相关对象家族 | 抽象工厂 | 保证一致性 |
| 简单对象，无需特殊逻辑 | 直接 `new` 或字面量 | 不过度设计 |

### 什么时候用抽象类？

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| 多个子类共享通用逻辑和接口 | 抽象类（抛错法） | 代码复用 + 契约约束 |
| 固定流程，可变步骤 | 模板方法模式 | 算法骨架稳定 |
| 不相关的类需要统一契约 | 接口协议 | 灵活的多实现 |
| 需要"不能实例化"的保护 | `new.target` 检查 | 运行时安全 |
| 需要编译期检查 | 用 TypeScript 的 `abstract` | 严格的类型安全 |

### 工厂 vs 构造器 vs 类：终极对比

| 维度 | `new` / `class` | 工厂函数 | 抽象类 |
|------|-----------------|----------|--------|
| **创建方式** | `new ClassName()` | `createXxx()` | 不能直接实例化 |
| **this 绑定** | 自动 | 手动/不需要 | 由子类处理 |
| **原型链** | ✅ 原型共享 | ❌ 默认无 | ✅ 继承原型 |
| **内存效率** | 高（方法共享） | 低（每个实例独立方法） | 高 |
| **私有性** | `#field`（ES2022+） | 闭包（天然私有） | `#field` / 闭包 |
| **继承** | ✅ 原生支持 | ⚠️ 需额外处理 | 核心用途 |
| **动态类型选择** | ❌ 不支持 | ✅ 天然支持 | ❌ 不适用 |
| **调试友好度** | 好（类名清晰） | 一般（匿名对象） | 好 |
| **学习曲线** | 低 | 低 | 中等 |

## 总结

工厂模式和抽象类模拟是 JavaScript 面向对象编程的高级话题。它们解决的不是"能不能"的问题，而是"该不该"的设计问题：

- **工厂模式**回答的是"**谁来负责创建对象**"——把创建的复杂性封装起来，让调用者只关心"给我一个能用就行"
- **抽象类**回答的是"**什么行为是强制的**"——在编译/运行时层面保证子类履行契约

掌握这两种模式，你的代码将从"能用"进化到"好用"再到"优雅"。记住：好的设计不是炫技，而是在正确的地方使用正确的工具——不多不少，恰到好处。
