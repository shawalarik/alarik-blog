# 代理（Proxy）：13 种捕获器详解

> **核心内容**：Proxy 是 JavaScript 元编程（Metaprogramming）的核心工具，它允许你拦截并自定义对象上的基本操作。这里将逐一讲解全部 **13 种捕获器（Trap）** 的原理、用法和实战场景，配合大量理论分析和通俗类比，帮助你彻底掌握这门强大的技术。

## 什么是 Proxy？—— 对象的"数字代理人"

在深入 13 种捕获器之前，我们需要先理解一个根本性的问题：**Proxy 究竟是什么？它解决什么问题？**

### 从直觉出发：生活中的代理

想象一下你是一家大公司的 CEO。每天都有无数的人想要找你：员工要签字、媒体要采访、合作伙伴要谈判、推销员要推销产品。如果每个人都直接来找你，你将没有任何时间处理真正重要的事情。于是，你聘请了一位**秘书（Proxy）**。

这位秘书坐在你办公室门口，负责：

- **过滤请求**：不是所有人都能见到你，秘书会判断哪些事情需要你亲自处理，哪些她可以代劳或直接回绝
- **转发信息**：确实需要你的事情，她会整理后转达给你
- **记录日志**：谁来找过你、什么时候来的、谈了什么，她都一一记录
- **修改内容**：有时候她会把对方的话润色后再告诉你，或者把你的指示包装后再传达给对方

**你就是 target（目标对象），秘书就是 proxy（代理对象）。** 外界所有与你的交互都必须经过秘书这一层。秘书可以在中间做任何她想做的事情——拦截、修改、记录、拒绝……这就是 Proxy 的本质。

### 技术定义

从语言规范的角度来看，**Proxy 是 ES2015 引入的一种元编程机制**，它允许开发者拦截并重新定义对象的基本操作（fundamental operations）。所谓基本操作，就是 JavaScript 引擎在执行代码时对对象进行的底层行为，比如读取属性、写入属性、删除属性、检查属性是否存在、遍历属性等等。这些操作在规范中被称为**内部方法（Internal Methods）**，用双括号标记，如 `[[Get]]`、`[[Set]]`、`[[Delete]]` 等。

Proxy 的威力在于：**它让你有机会在这些内部方法被执行之前"插入"自己的逻辑**。你可以改变操作的行为、增加额外的功能、甚至完全阻止操作的进行。这就像是在 JavaScript 引擎和你的对象之间插入了一层可编程的"中间件"。

### 基本语法

```javascript
// 创建一个 Proxy 的基本形式
let proxy = new Proxy(target, handler);
```

- **`target`**：被代理的目标对象。这可以是任何 JavaScript 对象——普通对象、数组、函数、甚至是另一个 Proxy
- **`handler`**：一个普通对象，它的属性是"捕获器函数"（trap functions）。每个捕获器对应一种可以拦截的基本操作

当 `handler` 为空对象 `{}` 时，Proxy 是一个**透明代理**——所有操作都会原封不动地转发给 `target`，就像一个不干事的秘书：

```javascript
let target = { name: "张三", age: 25 };
let proxy = new Proxy(target, {});

// 透明的 —— 所有操作都直接透传到 target
console.log(proxy.name);     // "张三"  ← 相当于访问 target.name
proxy.age = 26;               //          ← 相当于设置 target.age = 26
console.log(target.age);      // 26       ← target 被修改了！
console.log(proxy.age);       // 26       ← proxy 读到的也是最新值
delete proxy.name;             //          ← 相当于 delete target.name
```

注意上面这个例子中一个关键细节：**通过 `proxy` 修改的属性，`target` 也会跟着变**。因为 `proxy` 并不是 `target` 的拷贝，它是 `target` 的一层"包装"。你对 `proxy` 做的操作最终都会落到 `target` 上（除非你在捕获器中阻止了这种转发）。

### 为什么叫"元编程"？

**元编程（Metaprogramming）** 是指"编写能够操作程序本身的程序"。普通的编程是你写代码来处理数据；而元编程是你写代码来改变代码/语言本身的行为。

打个比方：
- **普通编程** = 你按照菜谱做饭（数据是你的食材）
- **元编程** = 你在改写菜谱本身（你改变了烹饪规则）

当你使用 Proxy 时，你并不是在操作对象的属性值，而是在**定义"操作对象的属性"这个行为本身应该如何工作**。这就是为什么它被称为"元"编程——你在一个更高的抽象层次上运作。

## 属性读取：get 捕获器

### 触发时机与签名

`get` 捕获器是使用频率最高的捕获器之一，它在**读取属性值时被触发**。具体来说，以下任何一种情况都会触发 `get`：

```javascript
// 所有这些操作都会触发 get 捕获器
proxy.prop;           // 直接属性访问
proxy["prop"];        // 方括号语法
Object.create(proxy); // 创建以 proxy 为原型的对象（继承时的属性查找）
// ...以及 for...in 遍历中隐式的属性读取
```

`get` 捕获器的完整签名是：

```javascript
get(target, property, receiver)
// target   —— 被代理的目标对象
// property —— 被读取的属性名（字符串或 Symbol）
// receiver —— 接收者，通常是 proxy 本身或继承自 proxy 的对象
```

其中 `receiver` 参数需要特别关注——我们稍后会详细解释它的作用和重要性。

### 最简单的 get 示例

让我们从最基础的功能开始：**记录属性的读取行为**。

```javascript
let user = {
  name: "张三",
  age: 25,
  email: "zhangsan@example.com"
};

let loggedUser = new Proxy(user, {
  // get 捕获器：每次读取属性时触发
  get(target, prop, receiver) {
    console.log(`📖 [GET] 有人读取了 "${prop}" 属性`);
    // 将操作转发给原始对象，返回真正的值
    return Reflect.get(target, prop, receiver);
  }
});

loggedUser.name;    // 📖 [GET] 有人读取了 "name" 属性 → 返回 "张三"
loggedUser.age;     // 📖 [GET] 有人读取了 "age" 属性 → 返回 25
loggedUser.email;   // 📖 [GET] 有人读取了 "email" 属性 → 返回 "zhangsan@example.com"

// 注意：target 本身不受影响，直接访问不会触发日志
user.name;          // "张三" —— 无日志输出
```

这里我们首次使用了 `Reflect.get()` 方法。`Reflect` 是 ES2015 引入的内置对象，它提供了与 Proxy 捕获器一一对应的静态方法。在 Proxy handler 中使用 `Reflect` 方法来转发操作是一种**最佳实践**，原因有三：

1. **语义清晰**：`Reflect.get(target, prop, receiver)` 明确表达了"将 get 操作转发给目标对象"的意图
2. **简化代码**：不需要手动处理各种边界情况和返回值约定
3. **正确传递 receiver**：这是最重要的原因，后面会详细展开

### 实战场景一：默认值填充

在实际开发中，一个非常常见的需求是：**当访问的对象上不存在某个属性时，返回一个默认值而不是 `undefined`**。这在配置管理、字典翻译、表单数据处理等场景中都极为有用。

```javascript
// 场景：应用配置对象，未显式配置的项应返回合理的默认值
let defaults = {
  theme: "light",
  language: "zh-CN",
  fontSize: 14,
  notifications: true,
  autoSave: true,
  autoSaveInterval: 30000  // 毫秒
};

// 创建带默认值的配置对象
function withDefaults(config) {
  return new Proxy(config || {}, {
    get(target, prop) {
      if (prop in target) {
        // 属性存在 → 返回实际配置值
        return Reflect.get(target, prop);
      }
      // 属性不存在 → 返回默认值
      console.log(`⚙️ 配置 "${prop}" 未指定，使用默认值: ${defaults[prop]}`);
      return defaults[prop];
    }
  });
}

// 用户只配置了两项
let userConfig = {
  theme: "dark",           // 用户偏好深色主题
  fontSize: 18             // 用户喜欢更大的字体
};

let config = withDefaults(userConfig);

config.theme;            // "dark" ← 用户自定义的值
config.fontSize;         // 18    ← 用户自定义的值
// ⚙️ 配置 "language" 未指定，使用默认值: zh-CN
config.language;         // "zh-CN" ← 默认值自动补全
// ⚙️ 配置 "autoSaveInterval" 未指定，使用默认值: 30000
config.autoSaveInterval; // 30000 ← 默认值自动补全
```

这个模式的价值在于：调用者不需要关心某个配置是否已经被设置过，也不需要到处写 `config.xxx ?? defaultXxx` 这样的防御性代码。**Proxy 把"默认值填充"这个关注点封装在了代理层**，让业务代码更加干净。

### 实战场景二：负索引数组

Python 等语言支持负数索引（如 `arr[-1]` 表示最后一个元素），但 JavaScript 原生不支持。我们可以用 Proxy 轻松实现：

```javascript
function createNegativeIndexArray(arr) {
  return new Proxy(arr, {
    get(target, prop) {
      // 将属性名转为数字
      let index = Number(prop);

      // 如果是有效的整数索引且为负数
      if (Number.isInteger(index) && index < 0) {
        // 转换为正索引：-1 → 最后一个，-2 → 倒数第二个...
        index = target.length + index;
        if (index >= 0) {
          return Reflect.get(target, String(index));
        }
      }

      // 其他情况（正索引、非索引属性如 length、方法等）正常返回
      return Reflect.get(target, prop);
    }
  });
}

let arr = createNegativeIndexArray([10, 20, 30, 40, 50]);

arr[0];   // 10   ← 正常的正索引
arr[4];   // 50   ← 最后一个元素的正索引
arr[-1];  // 50   ← 最后一个元素！🎉
arr[-2];  // 40   ← 倒数第二个！
arr[-5];  // 10   ← 第一个元素
arr[-6];  // undefined ← 超出范围
arr.length; // 5    ← 非索引属性不受影响
```

**理论分析**：这个例子展示了 Proxy 的一个强大能力——**它可以改变语言的表面语法而不引入新的语法**。我们没有修改 JavaScript 引擎，也没有等待 TC39 委员会批准新提案，仅仅通过 Proxy 就让数组"学会"了负索引。这就是元编程的魅力：你可以在应用层面扩展语言的表达能力。

### 实战场景三：属性访问翻译 / 字典映射

另一个实用的场景是将属性名映射为其他值，实现类似"字典"或"国际化"的效果：

```javascript
// 中英文属性名双向映射
let dictionary = {
  name: "姓名",
  age: "年龄",
  email: "电子邮箱",
  phone: "电话号码",
  address: "地址"
};

// 创建支持双语访问的对象
function createI18nObject(data) {
  return new Proxy(data, {
    get(target, prop) {
      // 先尝试直接匹配
      if (prop in target) {
        return Reflect.get(target, prop);
      }

      // 尝试查找中文翻译对应的英文键名
      for (let [enKey, zhName] of Object.entries(dictionary)) {
        if (zhName === prop && enKey in target) {
          console.log(`🌐 "${prop}" → 映射到 "${enKey}"`);
          return Reflect.get(target, enKey);
        }
      }

      // 都找不到
      console.warn(`⚠️ 未找到属性: ${prop}`);
      return undefined;
    }
  });
}

let userProfile = createI18nObject({
  name: "李四",
  age: 30,
  email: "lisi@mail.com"
});

userProfile.name;    // "李四"    ← 英文属性名
userProfile["年龄"]; // 30       ← 中文属性名！自动映射
userProfile.email;   // "lisi@mail.com"
userProfile["电话号码"]; // undefined（原数据中没有 phone 字段）
```

### receiver 参数深度解析

现在我们来深入探讨 `get` 捕获器的第三个参数 `receiver`。这是一个经常被初学者忽略但至关重要的参数。

`receiver` 代表的是**当前属性访问操作的真正接收者**。大多数情况下，它就是 `proxy` 本身。但当 `proxy` 作为其他对象的原型时，`receiver` 就可能是那个继承了 `proxy` 的子对象：

```javascript
let original = {
  _secret: "机密信息",

  get secret() {
    // 这里的 this 会是谁？
    console.log(`[getter] this === receiver? ${this === receiver}`);
    return this._secret + " (已加密)";
  }
};

let proxy = new Proxy(original, {
  get(target, prop, receiver) {
    console.log(`[proxy get] prop="${prop}", receiver 类型=${receiver.constructor.name}`);
    // 关键选择：用哪种方式获取属性？
    // 方式 A：直接从 target 取（this 会指向 target）
    // return target[prop];

    // 方式 B：用 Reflect.get 并传入 receiver（this 会指向 receiver）
    return Reflect.get(target, prop, receiver);
  }
});

// 情况 1：直接通过 proxy 访问
console.log("--- 直接访问 ---");
proxy.secret;
// [proxy get] prop="secret", receiver 类型=Object
// [getter] this === receiver? true ✅ （this 正确地指向了 proxy）

// 情况 2：proxy 作为原型
console.log("\n--- 通过原型链访问 ---");
let child = Object.create(proxy);
child._secret = "我的秘密";  // 子对象有自己的 _secret

child.secret;
// [proxy get] prop="secret", receiver 类型=Object
// [getter] this === receiver? true ✅ （this 指向了 child！正确！）

// 如果用方式 A（return target[prop]），这里的 this 会错误地指向 original
// 导致 getter 使用 original._secret 而非 child._secret
```

**理论解释**：这个问题的根源在于 JavaScript 中 getter/setter 的 `this` 绑定机制。当一个对象上有 getter 属性时，getter 函数内部的 `this` 应该指向**发起属性访问的那个对象**（即 receiver）。如果你在 `get` 捕获器中简单地写 `return target[prop]`，那么 `target[prop]` 这个操作会让 `this` 指向 `target`，而不是真正的接收者。这在使用继承、getter 和 Proxy 的组合场景下会导致微妙的 bug。

**解决方案**：始终使用 `Reflect.get(target, prop, receiver)` 来转发 `get` 操作。`Reflect` 方法的设计目的之一就是确保 `receiver` 能被正确传递，让 getter 中的 `this` 指向正确的对象。

### 通俗类比：智能图书馆的图书管理员

如果把对象想象成一座图书馆的书架，把属性想象成书架上的书籍，那么 `get` 捕获器就像是图书馆的一位**智能图书管理员**。

当读者（代码中的表达式）想借阅一本书（读取属性）时，他不能直接走到书架前取书。他必须向图书管理员提出申请。这位管理员会：

1. **登记日志**（记录谁借了什么书、什么时候借的）
2. **权限检查**（这本书是否允许外借？读者是否有资格？）
3. **智能检索**（如果书架上没有这本书，管理员可以去其他分馆调取——即默认值功能）
4. **加工处理**（有些特殊藏书可能需要在借出前进行复制、脱敏等处理——即 getter 变换）
5. **最后才把书交给读者**

在整个过程中，读者根本不知道书是从哪个书架取的、是否经过了处理。他只知道：我向管理员要一本书，管理员给了我一个结果。这就实现了**访问控制与业务逻辑的解耦**。

## 属性写入：set 捕获器

### 触发时机与签名

`set` 捕获器在**属性赋值时触发**，它的签名如下：

```javascript
set(target, property, value, receiver)
// target   —— 目标对象
// property —— 要写入的属性名
// value    —— 要写入的新值
// receiver —— 接收者（同 get 的 receiver）
```

**重要约束**：`set` 捕获器在成功完成赋值操作后**必须返回 `true`**。如果返回 `false`（或任何真值以外的值），在严格模式下会抛出 `TypeError`。这是语言规范的强制要求，目的是让赋值操作的成败可以被可靠地检测。

### 最基本的 set 拦截

```javascript
let data = { value: 0 };

let validatedData = new Proxy(data, {
  set(target, prop, value, receiver) {
    console.log(`✏️ [SET] 设置 "${prop}" = ${value}`);

    // 执行实际的赋值操作
    target[prop] = value;

    // 必须 return true 表示操作成功！
    return true;
  }
});

validatedData.value = 100;  // ✏️ [SET] 设置 "value" = 100
console.log(data.value);    // 100 ← target 已更新
```

### 实战场景一：类型校验

这是 `set` 捕获器最经典的应用场景——确保写入对象的数据符合预期的类型和格式：

```javascript
// 创建一个具有类型约束的用户对象
function createTypedUser(initialData) {
  // 定义每个字段允许的类型
  const schema = {
    name: "string",       // 名字必须是字符串
    age: "number",        // 年龄必须是数字
    email: "string",      // 邮箱必须是字符串
    active: "boolean"     // 激活状态必须是布尔值
  };

  return new Proxy(initialData || {}, {
    set(target, prop, value) {
      // 检查该字段是否在 schema 中定义
      if (prop in schema) {
        let expectedType = schema[prop];
        let actualType = typeof value;

        if (actualType !== expectedType) {
          console.error(
            `❌ 类型错误: "${prop}" 期望 ${expectedType}，但收到 ${actualType} (${value})`
          );
          // 返回 false 阻止赋值（严格模式下会抛 TypeError）
          return false;
        }
      }

      // 类型检查通过，执行赋值
      target[prop] = value;

      // 可以在这里添加额外逻辑，比如通知变更
      console.log(`✅ "${prop}" 更新为: ${value}`);
      return true;
    }
  });
}

let user = createTypedUser({
  name: "王五",
  age: 28,
  email: "wangwu@test.com",
  active: true
});

user.name = "赵六";       // ✅ "name" 更新为: 赵六
user.age = 29;            // ✅ "age" 更新为: 29
user.active = false;      // ✅ "active" 更新为: false
user.age = "三十";        // ❌ 类型错误: "age" 期望 number，但收到 string (三十)
                         // 赋值被阻止！
console.log(user.age);    // 29 ← 仍然是之前的值，没有被破坏
```

**理论价值**：这种模式实现了一种轻量级的**运行时类型安全**。虽然 TypeScript 在编译阶段就能提供类型检查，但在某些场景下——比如处理来自 API 的不可信输入、用户填写的表单数据、第三方库返回的数据——运行时的类型校验仍然至关重要。Proxy 让你可以在不修改业务代码的情况下，为任意对象加上"类型防护罩"。

### 实战场景二：数值范围约束

对于数值类型的属性，除了类型检查外，常常还需要验证值的范围：

```javascript
function createBoundedNumber(obj, bounds) {
  // bounds 格式: { propName: { min, max } }
  return new Proxy(obj, {
    set(target, prop, value) {
      // 如果该属性有范围限制
      if (bounds[prop]) {
        let { min, max } = bounds[prop];
        if (typeof value !== "number" || isNaN(value)) {
          console.error(`❌ "${prop}" 必须是有效数字`);
          return false;
        }
        if (value < min || value > max) {
          console.error(
            `❌ "${prop}": ${value} 超出范围 [${min}, ${max}]`
          );
          return false;
        }
        // 自动 clamp 到合法范围（可选策略）
        // value = Math.max(min, Math.min(max, value));
      }

      target[prop] = value;
      console.log(`✅ "${prop}" = ${value}`);
      return true;
    }
  });
}

let slider = createBoundedNumber(
  { volume: 50, brightness: 80 },
  {
    volume: { min: 0, max: 100 },
    brightness: { min: 0, max: 100 }
  }
);

slider.volume = 75;     // ✅ "volume" = 75
slider.volume = 150;    // ❌ "volume": 150 超出范围 [0, 100]
slider.brightness = -10; // ❌ "brightness": -10 超出范围 [0, 100]
slider.brightness = 60;  // ✅ "brightness" = 60
```

### 实战场景三：只读保护

利用 `set` 捕获器可以轻松创建**只读对象**——任何写入尝试都会被拒绝：

```javascript
function makeReadOnly(obj) {
  return new Proxy(obj, {
    set(target, prop, value) {
      console.warn(`🚫 拒绝修改: "${obj.name || '匿名对象'}" 是只读的`);
      return false;  // 返回 false 阻止赋值
    },

    // 同时也要拦截 deleteProperty，防止属性被删除
    deleteProperty(target, prop) {
      console.warn(`🚫 拒绝删除: 只读对象的属性不可删除`);
      return false;
    }
  });
}

const APP_CONFIG = makeReadOnly({
  name: "MyApp",
  version: "1.0.0",
  apiBaseURL: "https://api.example.com",
  maxRetries: 3,
  debugMode: false
});

APP_CONFIG.version = "2.0.0";  // 🚫 拒绝修改: "MyApp" 是只读的
APP_CONFIG.apiBaseURL = "http://evil.com";  // 🚫 拒绝修改
delete APP_CONFIG.debugMode;    // 🚫 拒绝删除: 只读对象的属性不可删除

console.log(APP_CONFIG.version);  // "1.0.0" ← 安全！未被篡改
```

**注意**：这种方式实现的只读保护是"浅层"的——如果对象的属性本身又是一个对象（嵌套对象），那么对这个内层对象的修改不会被拦截。要实现深层冻结，需要递归地为每一层都创建 Proxy。

### 通俗类比：银行柜员

如果说 `get` 捕获器像图书管理员负责"借阅"，那 `set` 捕获器就像是**银行的存款柜员**。

当你拿着现金去银行存钱时，你不能把钱直接扔进金库。你需要把钱交给柜员，柜员会进行一系列操作：

1. **验钞**（类型检查：确认是真钞还是假钞/确认是不是数字类型）
2. **金额核对**（范围验证：存款金额是否合理，有没有超过限额）
3. **身份确认**（权限验证：你是不是账户持有者）
4. **记录交易**（日志：记录这笔存款操作）
5. **入账**（实际赋值：把钱存入账户）
6. **给你回单**（返回 true：确认操作成功）

如果验钞发现是假钞，柜员会拒收这笔钱（返回 false，阻止操作）。整个过程保证了银行系统的数据完整性和安全性——这与 `set` 捕获器保证对象数据的完整性是完全一致的思路。

## 属性存在性检查：has 捕获器

### 触发时机与签名

`has` 捕获器在 **`in` 操作符**执行时触发。它用于拦截属性存在性的检查操作：

```javascript
has(target, property)
// target   —— 目标对象
// property —— 要检查的属性名
// 返回值  ——布尔值，表示属性是否"被认为存在"
```

### 基本用法

```javascript
let person = {
  name: "Alice",
  age: 30,
  isAdmin: true
};

let filteredPerson = new Proxy(person, {
  has(target, prop) {
    console.log(`🔍 [HAS] 检查 "${prop}" 是否存在`);

    // 过滤掉以 _ 开头的"私有"属性
    if (prop.startsWith("_")) {
      console.log(`  → 🔒 私有属性，对外隐藏`);
      return false;  // 声称不存在
    }

    return prop in target;  // 其他属性正常检查
  }
});

"name" in filteredPerson;    // 🔍 [HAS] 检查 "name" 是否存在 → true
"age" in filteredPerson;     // 🔍 [HAS] 检查 "age" 是否存在 → true
"_password" in filteredPerson; // 🔍 [HAS] 检查 "_password" 是否存在
                               // → 🔒 私有属性，对外隐藏 → false
```

### 实战场景：数值区间检测

这是一个非常优雅的应用——用 `in` 操作符来判断一个数字是否落在某个范围内：

```javascript
// 创建一个表示数值区间的对象
function createRange(min, max) {
  let range = { min, max };

  return new Proxy(range, {
    has(target, value) {
      // 当执行 "value in range" 时，检查 value 是否在 [min, max] 区间内
      return Number(value) >= target.min && Number(value) <= target.max;
    }
  });
}

let scoreRange = createRange(0, 100);   // 分数区间 0~100
let tempRange = createRange(-20, 40);   // 温度区间 -20°C ~ 40°C

// 用 in 操作符检查数值是否在范围内
console.log(85 in scoreRange);   // true  ← 85 在 0~100 范围内
console.log(-5 in scoreRange);   // false ← -5 不在范围内
console.log(150 in scoreRange);  // false ← 超出上限
console.log(25 in tempRange);    // true  ← 25°C 在温度范围内
console.log(-30 in tempRange);   // false ← 太冷了
console.log(50 in tempRange);    // false ← 太热了

// 可以用在条件表达式中
let score = 76;
if (score in scoreRange) {
  console.log("分数有效");
}
```

**设计美学点评**：这个用法之所以优雅，是因为它**重载了 `in` 操作符的语义**。原本 `in` 的含义是"某个属性是否存在于对象中"，而通过 Proxy 我们把它变成了"某个值是否属于某个集合/区间"。这是一种典型的**领域特定语言（DSL）**技巧——用简洁的语法表达特定领域的概念。代码 `if (score in validScoreRange)` 比 `if (score >= 0 && score <= 100)` 更具表达力，也更接近自然语言的思维方式。

### 理论补充：has 与 get 的区别

需要注意的是，`has` 捕获器和 `get` 捕获器拦截的是不同的操作：

- **`in` 操作符 → 触发 `has`**：询问"这个东西在不在这个对象里？"
- **属性访问 `obj.prop` → 触发 `get`**：询问"这个东西的值是多少？"

它们之间有联系但不等同。一个属性可以"存在"但返回 `undefined`（属性值为 `undefined`）；也可以在 `has` 中返回 `false` 但在 `get` 中仍然能取到值（取决于你的捕获器逻辑如何编写）。通常你应该保持两者的行为一致，避免造成困惑。

### 通俗类比：前台接待员

`has` 捕获器就像是公司大楼的**前台接待员**。当有人来访并询问"某某某在不在你们公司？"时（`in` 操作符），接待员会根据公司的规则来回答：

- 对于公开的员工名单上的人员 → 回答"在的"（返回 true）
- 对于已离职但名片还在网上流传的人员 → 回答"不在了"（返回 false）
- 对于内部保密项目的成员 → 即使他在办公室里，也回答"没听说过这个人"（隐藏私有属性）

关键是：接待员只是回答"在不在"的问题，并不负责把人叫出来（那是 `get` 的工作）。她是一个守门人，控制的是**信息的可见性**而非**信息的访问权**。

## 属性删除：deleteProperty 捕获器

### 触发时机与签名

`deleteProperty` 捕获器在 **`delete` 操作符**执行时触发：

```javascript
deleteProperty(target, property)
// target   —— 目标对象
// property —— 要删除的属性名
// 返回值  —— 布尔值。成功删除必须返回 true
```

与 `set` 类似，`deleteProperty` 也有一个**不变量约束**：如果属性确实被成功删除（或者属性本来就不存在），必须返回 `true`。返回 `false` 表示删除失败。

### 基本用法与属性保护

```javascript
let config = {
  apiEndpoint: "https://api.example.com",
  timeout: 5000,
  retryCount: 3,
  _internalKey: "secret-12345"   // 内部密钥，不应被外部删除
};

let protectedConfig = new Proxy(config, {
  deleteProperty(target, prop) {
    // 保护以 _ 开头的内部属性
    if (prop.startsWith("_")) {
      console.warn(`🛡️ 禁止删除受保护的属性: "${prop}"`);
      return false;  // 阻止删除
    }

    console.log(`🗑️ 删除属性: "${prop}"`);
    delete target[prop];  // 或使用 Reflect.deleteProperty(target, prop)
    return true;
  }
});

delete protectedConfig.timeout;     // 🗑️ 删除属性: "timeout" → 成功
delete protectedConfig._internalKey; // 🛡️ 禁止删除受保护的属性: "_internalKey" → 被阻止

console.log(config.timeout);         // undefined（已被删除）
console.log(config._internalKey);    // "secret-12345"（仍然安全）
```

### 实战场景：软删除（Soft Delete）

在某些业务场景中，你可能不想真的从对象上移除属性，而是将其标记为"已删除"状态：

```javascript
function createSoftDeleteStore(initialData) {
  let deletedKeys = new Set();  // 记录被"软删除"的键

  return new Proxy(initialData, {
    has(target, prop) {
      // 如果键被软删除了，对外显示为不存在
      if (deletedKeys.has(prop)) return false;
      return prop in target;
    },

    get(target, prop, receiver) {
      // 如果键被软删除了，返回 undefined
      if (deletedKeys.has(prop)) return undefined;
      return Reflect.get(target, prop, receiver);
    },

    deleteProperty(target, prop) {
      console.log(`🗑️ 软删除: "${prop}"（数据保留在底层，仅标记为不可见）`);
      deletedKeys.add(prop);
      return true;  // 告诉引擎删除"成功"了
    }
  });
}

let store = createSoftDeleteStore({ a: 1, b: 2, c: 3 });

store.a;  // 1
"a" in store;  // true

delete store.a;  // 🗑️ 软删除: "a"

store.a;        // undefined（看起来像是真的没了）
"a" in store;   // false（看起来也像是没了）

// 但实际上数据还在！可以恢复
console.log("底层对象:", store); // Proxy 中仍能看到原始数据
```

**理论意义**：这种"软删除"模式在很多系统中都有对应物——操作系统中的"回收站"、数据库中的"逻辑删除"（加 `deleted_at` 时间戳而非物理删除记录）、版本控制系统中的"删除操作"（其实只是新增了一个删除事件）。核心思想都是一样的：**不要立刻销毁数据，而是先标记，给用户一个反悔的机会**。

### 通俗类比：档案室的管理员

`deleteProperty` 捕获器就像是**档案室的文件销毁管理员**。

当有人带着一份文件说"我要销毁这份档案"时（`delete` 操作），管理员会：

1. **检查文件密级**（属性保护：某些机密文件禁止销毁）
2. **确认销毁权限**（权限验证：你是否有权决定销毁？）
3. **执行销毁或归档**（实际删除或软删除）
4. **记录销毁日志**（审计跟踪）
5. **给出销毁证明**（返回 true/false）

如果是一份永久保存的国家级绝密档案，管理员会直接拒绝销毁请求。如果是普通文件，管理员可能会把它放入碎纸机（物理删除），或者先放到"待销毁箱"中保留30天（软删除），以防有人后悔。

## 对象键枚举：ownKeys 捕获器

### 触发时机与签名

`ownKeys` 捕获器会在以下操作触发时被调用——它们都需要获取对象的所有自有属性键名：

- `Object.keys(proxy)`
- `Object.getOwnPropertyNames(proxy)`
- `Object.getOwnPropertySymbols(proxy)`
- `for...in` 循环
- `JSON.stringify(proxy)` （序列化时需要知道有哪些属性）

```javascript
ownKeys(target)
// target  —— 目标对象
// 返回值 —— 数组或类数组对象，包含应该被枚举出的属性键名（字符串或 Symbol）
```

### 基本用法：过滤私有属性

```javascript
let userData = {
  name: "孙七",
  email: "sunqi@test.com",
  _passwordHash: "a1b2c3d4e5",
  _sessionToken: "xyz789",
  _lastLoginTime: "2026-04-20T08:30:00Z"
};

let publicProfile = new Proxy(userData, {
  ownKeys(target) {
    // 获取所有的键
    let keys = Reflect.ownKeys(target);
    // 过滤掉以 _ 开头的键（私有属性）
    let publicKeys = keys.filter(key => !key.toString().startsWith("_"));
    console.log(`🔑 枚举键: ${keys.join(", ")} → 公开: ${publicKeys.join(", ")}`);
    return publicKeys;
  },

  // 注意：通常还需要配合 getOwnPropertyDescriptor 来确保被过滤的属性不被意外暴露
  getOwnPropertyDescriptor(target, prop) {
    if (prop.startsWith("_")) {
      return undefined;  // 告诉引擎这个属性"不存在"
    }
    return Reflect.getOwnPropertyDescriptor(target, prop);
  }
});

// 只有非 _ 开头的属性会被枚举出来
console.log(Object.keys(publicProfile));
// ["name", "email"] ← _passwordHash 等被隐藏了！

for (let key in publicProfile) {
  console.log(key);     // 只输出 name 和 email
}

// JSON 序列化也只会包含公开属性
console.log(JSON.stringify(publicProfile));
// {"name":"孙七","email":"sunqi@test.com"}
```

**重要提示**：`ownKeys` 通常不能单独工作。为了让过滤效果完整可靠，你往往需要同时配合 `getOwnPropertyDescriptor` 捕获器一起使用。这是因为某些内置方法（如 `Object.keys`）不仅依赖 `ownKeys` 获取候选键列表，还会用 `getOwnPropertyDescriptor` 来验证每个键的真实性和可枚举性。如果你的 `ownKeys` 返回了一个键但 `getOwnPropertyDescriptor` 对该键返回 `undefined`，这个键就会被静默忽略。

### 实战场景：属性排序

有时你需要控制对象属性在被枚举时的顺序（JavaScript 引擎通常按属性添加顺序枚举，但 Proxy 让你可以自定义）：

```javascript
function createOrderedObject(obj, keyOrder) {
  // keyOrder: 指定属性的出现顺序
  return new Proxy(obj, {
    ownKeys(target) {
      // 按 keyOrder 指定的顺序排列
      let ordered = keyOrder.filter(k => k in target);
      // 再追加不在 order 中的其他属性
      let remaining = Reflect.ownKeys(target)
        .filter(k => !keyOrder.includes(String(k)));
      return [...ordered, ...remaining];
    }
  });
}

let product = createOrderedObject(
  {
    id: 1001,
    price: 299.00,
    name: "无线蓝牙耳机",
    category: "电子产品",
    stock: 500,
    weight: "250g",
    sku: "BT-EAR-001"
  },
  // 希望展示顺序：名称、价格、库存
  ["name", "price", "stock"]
);

console.log(Object.keys(product));
// ["name", "price", "stock", "id", "category", "weight", "sku"]
// name, price, stock 排在最前面！
```

### 通俗类比：展览馆的展品目录

`ownKeys` 捕获器就像是**展览馆的展品目录编辑**。

当一个游客想要了解"这个展厅里都有什么展品"时（`Object.keys` / `for...in`），他拿到的不是仓库里的完整清单，而是经过策展人精心编排的**参观指南**：

- 有些展品可能还在修复中，暂时不对外开放（过滤掉 `_` 开头的属性）
- 展品的排列顺序经过了精心设计——先看最重要的，再看次要的（属性排序）
- 有些展品可能只在特定的导览路线中才会提到（配合 `getOwnPropertyDescriptor` 控制可见性）

游客看到的永远是策展人希望他看到的那一部分，而不是仓库里的真实全貌。这就是 `ownKeys` 提供的能力：**控制对象"展示面"的形状**。

## 属性描述符获取：getOwnPropertyDescriptor 捕获器

### 触发时机与签名

`getOwnPropertyDescriptor` 捕获器在调用 `Object.getOwnPropertyDescriptor(proxy, property)` 时触发：

```javascript
getOwnPropertyDescriptor(target, property)
// target   —— 目标对象
// property —— 要查询的属性名
// 返回值  —— 属性描述符对象 或 undefined（表示属性不存在）
```

### 与 ownKeys 的协同工作

正如前面提到的，这个捕获器经常需要与 `ownKeys` 配合使用：

```javascript
let sensitiveData = {
  publicKey: "MIIBIjANBgkqhkiG9w0BAQE...",
  privateKey: "MIIEvQIBADANBgkqhkiG9w0...",
  apiVersion: "v2",
  endpoint: "https://api.example.com"
};

let safeData = new Proxy(sensitiveData, {
  ownKeys(target) {
    // 枚举时排除敏感键
    return Reflect.ownKeys(target).filter(k => !String(k).includes("private"));
  },

  getOwnPropertyDescriptor(target, prop) {
    // 对敏感属性返回 undefined，使其看起来"不存在"
    if (String(prop).toLowerCase().includes("private")) {
      console.log(`🔒 隐藏敏感属性描述符: "${prop}"`);
      return undefined;
    }
    // 其他属性正常返回描述符
    let desc = Reflect.getOwnPropertyDescriptor(target, prop);
    console.log(`📋 属性描述符 "${prop}":`, desc);
    return desc;
  }
});

// 测试
console.log(Object.keys(safeData));
// ["publicKey", "apiVersion", "endpoint"] — privateKey 不见了

console.log(Object.getOwnPropertyDescriptor(safeData, "privateKey"));
// 🔒 隐藏敏感属性描述符: "privateKey"
// undefined

console.log(Object.getOwnPropertyDescriptor(safeData, "publicKey"));
// { value: "MIIBIjANBgkqhkiG9w0BAQE...", writable: true, enumerable: true, configurable: true }
```

**理论解释**：为什么要两个捕获器配合？因为 JavaScript 的属性枚举算法分为两步：首先通过 `[[OwnPropertyKeys]]`（对应 `ownKeys`）获取候选键列表，然后对每个键通过 `[[GetOwnProperty]]`（对应 `getOwnPropertyDescriptor`）获取其描述符。只有描述符不为 `undefined` 且 `enumerable` 为 `true` 的属性才会出现在最终的枚举结果中。所以如果你想完整地隐藏一个属性，需要在两个地方都做处理。

### 通俗类比：房产局的档案查询窗口

`getOwnPropertyDescriptor` 就像是**房产局的档案查询窗口**。

当有人来查询某套房产的详细信息时（`Object.getOwnPropertyDescriptor`），工作人员会查阅档案系统，打印出一份详细的信息卡（属性描述符），上面写着：

- 房产地址（属性名 `value`）
- 能否转手买卖（`writable`）
- 是否列入公开房源名录（`enumerable`）
- 能否变更房产性质（`configurable`）

但对于某些涉密的军事用地或私人住宅，工作人员会回复："查无此档案"（返回 `undefined`），即使这套房产实际上是存在的。这就是**信息层面的屏蔽**——不是物理上不存在，而是在信息查询层面不可达。

## 属性定义：defineProperty 捕获器

### 触发时机与签名

`defineProperty` 捕获器在调用 `Object.defineProperty(proxy, property, descriptor)` 时触发：

```javascript
defineProperty(target, property, descriptor)
// target     —— 目标对象
// property   —— 要定义的属性名
// descriptor —— 属性描述符对象
// 返回值    —— 成功必须返回 true
```

### 基本用法：拦截属性定义

```javascript
let schema = {};

let controlledSchema = new Proxy(schema, {
  defineProperty(target, prop, descriptor) {
    console.log(`📝 [DEFINE] 定义属性 "${prop}", 描述符:`, descriptor);

    // 可以在这里添加验证逻辑
    if ("value" in descriptor && descriptor.value === "") {
      console.warn(`⚠️ 拒绝定义空字符串属性: "${prop}"`);
      return false;  // 阻止定义
    }

    // 执行真正的定义
    Object.defineProperty(target, prop, descriptor);
    return true;
  }
});

Object.defineProperty(controlledSchema, "title", {
  value: "Hello World",
  writable: true,
  enumerable: true
});
// 📝 [DEFINE] 定义属性 "title", 描述符: { value: "Hello World", ... }
// ✅ 成功
```

### 实际应用：强制属性约定

```javascript
function createStrictObject(baseObj, rules) {
  /*
   * rules 格式示例:
   * {
   *   allowedProps: ["name", "age"],  // 允许的属性列表
   *   requiredEnumerable: true,        // 新属性必须可枚举
   *   forbidWritable: false            // 是否禁止可写属性
   * }
   */
  return new Proxy(baseObj, {
    defineProperty(target, prop, descriptor) {
      // 规则 1：白名单检查
      if (rules.allowedProps && !rules.allowedProps.includes(prop)) {
        console.error(`❌ "${prop}" 不在允许的属性列表中`);
        return false;
      }

      // 规则 2：强制可枚举
      if (rules.requiredEnumerable && !descriptor.enumerable) {
        console.warn(`⚠️ 属性 "${prop}" 必须设置为 enumerable: true`);
        descriptor = { ...descriptor, enumerable: true };  // 自动修正
      }

      // 执行定义
      Reflect.defineProperty(target, prop, descriptor);
      console.log(`✅ 属性 "${prop}" 定义成功`);
      return true;
    }
  });
}

let strictObj = createStrictObject({}, {
  allowedProps: ["id", "name", "createdAt"],
  requiredEnumerable: true
});

  value: 1001,
  enumerable: true,
  configurable: true
});
// ✅ 属性 "id" 定义成功

// ❌ "illegalProp" 不在允许的属性列表中 → TypeError!
```

## 原型相关：getPrototypeOf 与 setPrototypeOf 捕获器

### getPrototypeOf 捕获器

`getPrototypeOf` 在调用 `Object.getPrototypeOf(proxy)` 时触发，用于拦截原型（`[[Prototype]]`）的读取：

```javascript
getPrototypeOf(target)
// target —— 目标对象
// 返回值 —— 对象 或 null
```

**不变量约束**：返回值必须是一个对象或 `null`，且必须与 `Object.getPrototypeOf(target)` 的返回值一致。也就是说，你不能伪造一个虚假的原型。

```javascript
let animal = { type: "生物", eat() { console.log("进食..."); } };
let dog = { breed: "柯基", __proto__: animal };

let dogProxy = new Proxy(dog, {
  getPrototypeOf(target) {
    let proto = Reflect.getPrototypeOf(target);
    console.log(`🧬 获取原型:`, proto === animal ? "Animal" : "Other");
    return proto;  // 必须返回真实的原型
  }
});

console.log(Object.getPrototypeOf(dogProxy) === animal);
// 🧬 获取原型: Animal
// true
```

### setPrototypeOf 捕获器

`setPrototypeOf` 在调用 `Object.setPrototypeOf(proxy, prototype)` 时触发，用于拦截原型的修改：

```javascript
setPrototypeOf(target, prototype)
// target    —— 目标对象
// prototype —— 要设置为新的原型的对象 或 null
// 返回值   —— 成功必须返回 true
```

```javascript
let base = { version: "1.0" };
let obj = { name: "test" };

let immutableProtoObj = new Proxy(obj, {
  setPrototypeOf(target, newProto) {
    console.warn(`🚫 拒绝修改原型: 当前对象的原型不允许变更`);
    return false;  // 阻止修改
  }
});

Object.setPrototypeOf(immutableProtoObj, base);
// 🚫 拒绝修改原型: 当前对象的原型不允许变更
// ❌ TypeError: setPrototypeOf returned false
```

### 理论背景：原型链的重要性

在 JavaScript 中，**原型（Prototype）是对象之间建立继承关系的基础设施**。每个普通对象都有一个内部的 `[[Prototype]]` 指针（可以通过 `__proto__` 访问或通过 `Object.getPrototypeOf`/`Object.setPrototypeOf` 操作），指向它的原型对象。当你在对象上找不到某个属性时，引擎会沿着原型链向上查找——这就是 JavaScript 实现属性继承和共享方法的机制。

拦截原型的读写能力在以下场景中有实用价值：
- **锁定继承体系**：防止恶意代码篡改对象的原型（原型污染攻击防护）
- **调试与监控**：追踪原型何时何地被修改
- **虚拟化原型**：在跨框架或跨域的场景中提供隔离的原型环境

### 通俗类比：家谱档案馆

原型就像是每个人的**家谱（家族血缘关系）**。`getPrototypeOf` 就像是去档案馆查询"这个人的父母是谁"（获取原型），而 `setPrototypeOf` 则像是试图**修改家谱记录**——声称"A 的父亲其实是 B"而不是原来记录的 C。

在现实世界中，修改家谱记录是一件极其严肃的事情——需要 DNA 证据、法律程序、多方见证。同理，在 JavaScript 中修改对象的原型也是一种影响深远的操作（会影响整个继承链上的所有属性查找行为），所以 `setPrototypeOf` 捕获器给了你一个"审批关口"，可以拒绝不当的原型修改请求。

## 可扩展性：isExtensible 与 preventExtensions 捕获器

### isExtensible 捕获器

`isExtensible` 捕获器在调用 `Object.isExtensible(proxy)` 时触发，用于检查对象是否可以添加新属性：

```javascript
isExtensible(target)
// target —— 目标对象
// 返回值 —— 必须与 Object.isExtensible(target) 返回一致
```

### preventExtensions 捕获器

`preventExtensions` 捕获器在调用 `Object.preventExtensions(proxy)` 时触发，用于阻止对象被添加新属性：

```javascript
preventExtensions(target)
// target —— 目标对象
// 返回值 —— 成功必须返回 true
```

### 基本用法演示

```javascript
let flexibleObj = { existing: "property" };

let monitoredObj = new Proxy(flexibleObj, {
  isExtensible(target) {
    let result = Reflect.isExtensible(target);
    console.log(`🔓 [isExtensible] 对象${result ? '可' : '不可'}扩展`);
    return result;  // 返回值必须与实际情况一致
  },

  preventExtensions(target) {
    console.log(`🔒 [preventExtensions] 即将锁定对象，无法再添加新属性`);
    Reflect.preventExtensions(target);
    return true;
  }
});

console.log(Object.isExtensible(monitoredObj));
// 🔓 [isExtensible] 对象可扩展
// true

Object.preventExtensions(monitoredObj);
// 🔒 [preventExtensions] 即将锁定对象，无法再添加新属性

monitoredObj.newProp = "hello";  // 静默失败（严格模式下报错）
console.log(monitoredObj.newProp);  // undefined
```

### 理论解释：什么是"可扩展性"？

在 JavaScript 规范中，每个对象都有一个内部的 `[[Extensible]]` 状态标志。当这个标志为 `true` 时，可以向对象添加新的属性；当它被设为 `false` 后（通过 `Object.preventExtensions`），任何尝试添加新属性的操作都会静默失败（或在严格模式下抛出 TypeError）。

**它与 `Object.freeze()` 的区别**：

| 操作 | 添加新属性 | 修改现有属性 | 删除属性 |
|------|-----------|-------------|---------|
| `preventExtensions` | ❌ 禁止 | ✅ 允许 | ✅ 允许 |
| `seal()`（封印） | ❌ 禁止 | ⚠️ 仅不可删属性 | ❌ 禁止 |
| `freeze()`（冻结） | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 |

`preventExtensions` 是最轻量的"锁定"操作，只禁止添加新属性，不影响已有属性的读写和删除。`seal` 和 `freeze` 在此基础上施加更严格的限制。

### 通俗类比：房屋扩建许可证

对象的"可扩展性"就像一块土地的**扩建许可状态**：

- **可扩展（extensible: true）**：这块土地上还可以继续盖新房子（添加新属性）
- **不可扩展（extensible: false）**：这块土地已经被政府划为"不得扩建区域"了，现有的房子可以装修（修改属性），但不能在旁边再盖新的了

`preventExtensions` 就是政府下达的**停建令**——从此以后不能再往这块地上加盖任何新建筑。而 `isExtensible` 就是去规划局查询这块土地当前的扩建许可状态。

## 函数调用：apply 捕获器

### 触发时机与签名

`apply` 捕获器可能是仅次于 `get` 和 `set` 之后最常用的捕获器。它在**函数被调用时触发**——前提是被代理的目标是一个函数：

```javascript
apply(target, thisArg, argumentsList)
// target        —— 被代理的目标函数
// thisArg       —— 调用时的 this 上下文
// argumentsList —— 调用时传入的参数数组
// 返回值       —— 函数执行的返回值（可以是任意值）
```

### 基本用法：函数调用日志

```javascript
function greet(name, greeting) {
  return `${greeting}, ${name}!`;
}

let loggedGreet = new Proxy(greet, {
  apply(target, thisArg, args) {
    console.log(`📞 [CALL] greet(${args.map(a => JSON.stringify(a)).join(", ")})`);
    // 转发调用到原函数
    let result = Reflect.apply(target, thisArg, args);
    console.log(`   ↩️ 返回: "${result}"`);
    return result;
  }
});

loggedGreet("世界", "你好");  // 📞 [CALL] greet("世界", "你好") → ↩️ 返回: "你好, 世界!"
loggedGreet("Proxy", "欢迎来到"); // 📞 [CALL] greet("Proxy", "欢迎来到") → ↩️ 返回: "欢迎来到, Proxy!"
```

### 实战场景一：函数节流（Throttle）

```javascript
function throttle(func, interval) {
  let lastCallTime = 0;
  let timerId = null;

  // 返回一个被代理过的函数
  return new Proxy(func, {
    apply(target, thisArg, args) {
      let now = Date.now();
      let elapsed = now - lastCallTime;

      if (elapsed < interval) {
        console.log(`⏳ 节流: 距上次调用仅 ${elapsed}ms，最小间隔 ${interval}ms`);
        return undefined;  // 丢弃这次调用
      }

      lastCallTime = now;
      return Reflect.apply(target, thisArg, args);
    }
  });
}

// 假设这是一个发送网络请求的函数
function sendAnalytics(event, data) {
  console.log(`📤 发送分析事件: ${event}`, data);
  return "sent";
}

let throttledSend = throttle(sendAnalytics, 1000);  // 最小间隔 1秒

throttledSend("click", { x: 100, y: 200 });  // 📤 发送分析事件: click
throttledSend("scroll", { y: 500 });         // ⏳ 节流: 距上次调用仅 5ms...
throttledSend("hover", { element: "btn" });  // ⏳ 节流: 距上次调用仅 12ms...

setTimeout(() => {
  throttledSend("click", { x: 300, y: 400 });  // 📤 发送分析事件: click（1秒后恢复）
}, 1100);
```

### 实战场景二：自动参数校验与转换

```javascript
function createValidatedFunction(fn, paramRules) {
  /*
   * paramRules 格式:
   * [
   *   { type: "number", min: 0 },      // 第1个参数: 数字且>=0
   *   { type: "string", minLength: 1 }, // 第2个参数: 非空字符串
   * ]
   */
  return new Proxy(fn, {
    apply(target, thisArg, args) {
      // 逐个校验参数
      for (let i = 0; i < paramRules.length; i++) {
        let rule = paramRules[i];
        let value = args[i];
        let paramName = `第${i + 1}个参数`;

        if (rule.type && typeof value !== rule.type) {
          throw new TypeError(`${paramName}: 期望 ${rule.type}，收到 ${typeof value}`);
        }
        if (rule.min !== undefined && value < rule.min) {
          throw new RangeError(`${paramName}: 值 ${value} 小于最小值 ${rule.min}`);
        }
        if (rule.minLength !== undefined && String(value).length < rule.minLength) {
          throw new RangeError(`${paramName}: 长度不足（最少 ${rule.minLength} 个字符）`);
        }
      }

      // 校验通过，执行原函数
      return Reflect.apply(target, thisArg, args);
    }
  });
}

// 定义一个需要参数校验的函数
function calculateArea(width, height) {
  return width * height;
}

let safeCalculateArea = createValidatedFunction(calculateArea, [
  { type: "number", min: 0 },   // width: 正数
  { type: "number", min: 0 }    // height: 正数
]);

console.log(safeCalculateArea(10, 20));    // 200 ✅
console.log(safeCalculateArea(5, 3));      // 15 ✅
safeCalculateArea(-5, 10);   // ❌ TypeError: 第1个参数: 值 -5 小于最小值 0
safeCalculateArea(10, "abc"); // ❌ TypeError: 第2个参数: 期望 number，收到 string
```

### 理论价值：为什么用 Proxy 而不用高阶函数？

你可能会问：上面的功能（日志、节流、校验）用普通的高阶函数也能实现啊，为什么要用 Proxy？

关键区别在于：**Proxy 保留了函数的身份（identity）**。

```javascript
// 高阶函数方式
function wrappedByHOF(fn) {
  return function(...args) {  // 创建了一个全新的函数！
    console.log("calling...");
    return fn(...args);
  };
}

// Proxy 方式
function wrappedByProxy(fn) {
  return new Proxy(fn, { apply(target, thisArg, args) {
    console.log("calling...");
    return Reflect.apply(target, thisArg, args);
  }};
}

let original = function hello() {};
let hofWrapped = wrappedByHOF(original);
let proxyWrapped = wrappedByProxy(original);

console.log(hofWrapped === original);   // false ← 全新的函数
console.log(proxyWrapped === original); // false ← 也不是同一个引用

// 但 Proxy 版本保留了更多原始信息
console.log(proxyWrapped.name);         // "hello" ← 保留了原始函数名！
console.log(proxyWrapped.length);       // 0     ← 保留了原始函数长度！
// 而 HOF 版本的 hofWrapped.name 是空字符串 ""
```

更重要的是，**如果原函数上有自定义属性或被用作特殊标识符**（比如事件回调的唯一标识、React 组件的类型比对等），高阶函数包装后会丢失这些关联，而 Proxy 包装后的对象在某些场景下能更好地维持原有关系。

### 通俗类比：电话总机的接线员

`apply` 捕获器就像是**公司电话总机的接线员**。

当外界打电话进来（函数被调用）时，电话首先接到接线员这里。接线员会：

1. **记录来电信息**（日志：谁打的、什么时候打的）
2. **身份核实**（参数校验：来电者的身份是否合法？）
3. **频率限制**（节流：这个号码最近打得太频繁了吧？）
4. **计时**（性能测量：通话持续了多久？）
5. **然后才转接给真正的负责人**（`Reflect.apply` 转发给原函数）

打电话的人不知道中间还有接线员这一层。他只知道自己拨了一个号码，然后得到了回应（返回值）。接线员的存在对他来说是完全透明的，但她却在幕后完成了许多重要的工作。

## 构造函数调用：construct 捕获器

### 触发时机与签名

`construct` 捕获器在**使用 `new` 操作符调用代理对象**时触发。这意味着被代理的目标必须是一个构造函数（或 class）：

```javascript
construct(target, argumentsList, newTarget)
// target        —— 被代理的构造函数
// argumentsList —— 传给 new 的参数数组
// newTarget     —— originally passed to new（通常就是 proxy 本身）
// 返回值       —— 必须返回一个对象
```

**重要约束**：`construct` 捕获器**必须返回一个对象**。如果返回的不是对象（如数字、字符串、undefined 等），引擎会抛出 `TypeError`。

### 基本用法：构造日志

```javascript
class User {
  constructor(name, age) {
    this.name = name;
    this.age = age;
    this.createdAt = new Date();
  }

  introduce() {
    return `我是 ${this.name}，今年 ${this.age} 岁`;
  }
}

let UserProxy = new Proxy(User, {
  construct(target, args, newTarget) {
    console.log(`🏗️ [NEW] 创建 User 实例: name="${args[0]}", age=${args[1]}`);

    // 转发构造调用
    let instance = Reflect.construct(target, args, newTarget);

    console.log(`  ✅ 实例已创建:`, instance);
    return instance;
  }
});

let u1 = new UserProxy("周八", 35);
// 🏗️ [NEW] 创建 User 实例: name="周八", age=35
//   ✅ 实例已创建: User { name: "周八", age: 35, createdAt: ... }

console.log(u1.introduce());  // 我是 周八，今年 35 岁
console.log(u1 instanceof User);  // true ← 原型关系保持正确
```

### 实战场景：强制单例模式

```javascript
function createSingleton(Constructor) {
  let instance = null;

  return new Proxy(Constructor, {
    construct(target, args, newTarget) {
      if (instance) {
        console.log(`♻️ [单例] 复用已有实例`);
        return instance;  // 返回已有的实例，不再创建新的
      }

      console.log(`🆕 [单例] 创建新实例`);
      instance = Reflect.construct(target, args, newTarget);
      return instance;
    }
  });
}

class DatabaseConnection {
  constructor(connectionString) {
    this.connectionString = connectionString;
    this.connected = false;
    console.log(`🔌 建立数据库连接: ${connectionString}`);
    // 模拟连接过程...
    this.connected = true;
  }

  query(sql) {
    if (!this.connected) throw new Error("数据库未连接");
    return `执行SQL: ${sql}`;
  }
}

let SingletonDB = createSingleton(DatabaseConnection);

let db1 = new SingletonDB("mysql://localhost:3306/mydb");
// 🆕 [单例] 创建新实例
// 🔌 建立数据库连接: mysql://localhost:3306/mydb

let db2 = new SingletonDB("mysql://localhost:3306/mydb");
// ♻️ [单例] 复用已有实例

console.log(db1 === db2);  // true ← 同一个实例！
db1.query("SELECT * FROM users");  // 执行SQL: SELECT * FROM users
db2.query("SELECT * FROM products"); // 执行SQL: SELECT * FROM products（同一个连接）
```

### 实战场景：依赖注入容器

```javascript
function createDIContainer() {
  let registry = new Map();   // 注册表：存储类及其依赖关系
  let instances = new Map();  // 单例缓存

  return {
    // 注册一个类及其依赖
    register(name, Class, dependencies = []) {
      registry.set(name, { Class, dependencies });
      return this;  // 支持链式调用
    },

    // 创建解析代理
    resolve(name) {
      let entry = registry.get(name);
      if (!entry) throw new Error(`未注册: ${name}`);

      return new Proxy(entry.Class, {
        construct(target, args, newTarget) {
          // 如果已经有缓存实例（简单单例策略）
          if (instances.has(name)) {
            return instances.get(name);
          }

          // 解析依赖：递归创建依赖对象
          let resolvedDeps = entry.dependencies.map(dep => {
            if (registry.has(dep)) {
              // 递归 resolve —— 这里简化处理
              let depEntry = registry.get(dep);
              return Reflect.construct(depEntry.Class, [], depEntry.Class);
            }
            throw new Error(`未注册的依赖: ${dep}`);
          });

          // 用解析好的依赖创建实例
          let instance = Reflect.construct(target, [...args, ...resolvedDeps], newTarget);
          instances.set(name, instance);
          return instance;
        }
      });
    }
  };
}

// 使用示例
let container = createDIContainer();

container.register('Database', class Database {
  constructor() { this.tables = []; }
  query(sql) { return `DB: ${sql}`; }
});

container.register('UserService', class UserService {
  constructor(db) {
    this.db = db;  // 依赖 Database
  }
  findUser(id) { return this.db.query(`SELECT * WHERE id=${id}`); }
});

// 通过 DI 容器创建服务
let UserServiceProxy = container.resolve('UserService');
let userService = new UserServiceProxy();
// userService 自动获得了 Database 依赖

console.log(userService.findUser(42));
// DB: SELECT * WHERE id=42
```

### 理论补充：new 操作符的内部流程

理解 `construct` 捕获器需要先理解 `new` 操作符在 JavaScript 引擎内部的执行步骤。当执行 `new Constructor(args...)` 时，引擎大致做了以下几件事：

1. 创建一个空的普通对象 `obj`
2. 将 `obj` 的 `[[Prototype]]` 设置为 `Constructor.prototype`
3. 以 `obj` 为 `this` 上下文执行 `Constructor` 函数体
4. 如果构造函数返回了一个对象，则使用该对象作为 `new` 的结果；否则返回 `obj`

`construct` 捕获器让你有机会在第 3 步之前插入自定义逻辑——你可以修改传入的参数、记录日志、返回已有的实例（单例）、甚至完全替换为另一个类的实例（工厂模式的变体）。

### 通俗类比：工厂的门禁闸机

`construct` 捕获器就像是**现代化工厂入口处的智能门禁闸机**。

每当有工人或物料要进入工厂开始生产时（`new` 操作），他们必须通过这道闸机。闸机会：

1. **扫描工牌**（检查调用资格：谁在尝试创建实例？）
2. **检查生产配额**（单例控制：今天已经生产了这个产品吗？如果有了就直接从库房取一个成品给他）
3. **准备原材料**（依赖注入：在生产之前先把所需的零部件准备好送进车间）
4. **记录生产日志**（审计追踪：什么时间、由谁、用什么参数创建了实例）
5. **放行进入车间**（`Reflect.construct`：让正常的构造流程继续进行）

没有闸机通行许可的人无法进入工厂。闸机控制着生产的入口——这与 `construct` 捕获器控制对象创建的入口是完全对应的。

## 可撤销代理：Proxy.revocable()

### 基本概念

除了 13 种捕获器之外，Proxy 还提供了一个重要的静态方法：`Proxy.revocable()`。它用于创建一个**可以随时"撤销"（ revoke ）的代理**——撤销后，代理对象将失去所有功能，对其的任何操作都会抛出 `TypeError`。

### 语法与基本用法

```javascript
let { proxy, revoke } = Proxy.revocable(target, handler);
// proxy —— 代理对象（使用起来和普通 Proxy 一样）
// revoke —— 一个函数，调用后立即撤销代理

// 使用 proxy ...
revoke();  // 撤销！此后 proxy 不可再用
```

```javascript
let sensitiveInfo = {
  apiKey: "sk-live-abcdef123456",
  secret: "sec_98765zyxwvu",
  permissions: ["read", "write"]
};

let { proxy: temporaryAccess, revoke: denyAccess } = Proxy.revocable(
  sensitiveInfo,
  {
    get(target, prop) {
      console.log(`📖 访问: ${prop}`);
      return Reflect.get(target, prop);
    }
  }
);

// 在授权期间可以正常使用
temporaryAccess.apiKey;     // 📖 访问: apiKey → "sk-live-abcdef123456"
temporaryAccess.permissions; // 📖 访问: permissions → ["read","write"]

// 授权到期，撤销访问权限！
denyAccess();
console.log("=== 权限已撤销 ===");

try {
  temporaryAccess.apiKey;  // 💥 TypeError: Cannot perform 'get' on a proxy that has been revoked
} catch (e) {
  console.error(`❌ 访问被拒绝: ${e.message}`);
}
```

### 实战场景：临时授权访问

```javascript
// 场景：给第三方库临时暴露一个内部对象，超时后自动收回权限
function grantTemporaryAccess(object, timeoutMs) {
  let { proxy, revoke } = Proxy.revocable(object, {
    get(target, prop, receiver) {
      console.log(`🔑 [临时访问] ${prop}`);
      return Reflect.get(target, prop, receiver);
    },
    set(target, prop, value, receiver) {
      console.log(`✏️ [临时写入] ${prop} = ${value}`);
      return Reflect.set(target, prop, value, receiver);
    }
  });

  // 设定定时器，超时后自动撤销
  setTimeout(() => {
    revoke();
    console.log(`\n⏰ [过期] 临时访问权限已收回 (${timeoutMs}ms 后)`);
  }, timeoutMs);

  return proxy;
}

let internalConfig = {
  dbHost: "192.168.1.100",
  dbPort: 3306,
  cacheSize: "512mb"
};

// 授予 3 秒的临时访问权限
let tempAccess = grantTemporaryAccess(internalConfig, 3000);

tempAccess.dbHost;   // 🔑 [临时访问] dbHost → "192.168.1.100"
tempAccess.cacheSize = "1gb";  // ✏️ [临时写入] cacheSize = 1gb

// 3秒之后......
// ⏰ [过期] 临时访问权限已收回 (3000ms 后)

// 此后再访问就会报错
```

### 实战场景：一次性令牌

```javascript
function createOneTimeToken(secretData) {
  let used = false;
  let { proxy, revoke } = Proxy.revocable(secretData, {
    get(target, prop) {
      if (used) {
        throw new Error("令牌已失效，无法重复使用！");
      }
      return Reflect.get(target, prop);
    }
  });

  return {
    getToken() {
      if (used) {
        throw new Error("令牌已被领取！");
      }
      used = true;
      setTimeout(() => revoke(), 0);  // 下一次事件循环后撤销
      return proxy;
    },

    get isUsed() {
      return used;
    }
  };
}

let passwordReset = createOneTimeToken({
  token: "reset_abc123",
  userId: 42,
  expiresAt: Date.now() + 3600000
});

console.log(passwordReset.isUsed);  // false

let token1 = passwordReset.getToken();
token1.token;  // "reset_abc123"  ✅ 正常访问

let token2 = passwordReset.getToken();
// ❌ Error: 令牌已被领取！

token1.token;
// ❌ Error: 令牌已失效，无法重复使用！（已被 revoke）
```

### 理论价值：安全边界与最小权限原则

`Proxy.revocable()` 体现了计算机科学中一条重要的安全原则：**最小权限原则（Principle of Least Privilege）**。这个原则要求：任何实体（进程、用户、代码模块）只应该拥有完成其工作所需的最小权限集，不多不少。

在没有 `revocable` 的世界里，一旦你把一个对象引用交给了其他代码，你就失去了对该引用的控制——对方可以随时随地访问这个对象，你无法在事后收回权限。而 `revocable` 让你可以在授予访问权的同时附上一个"撤回机制"——就像给了别人一把钥匙的同时保留了随时换锁的能力。

这在以下场景中尤为重要：
- **第三方插件系统**：给插件临时的 API 访问权限，卸载时立即收回
- **安全敏感的数据**：密码、密钥、令牌等信息的临时暴露
- **沙盒环境**：限制代码只能在特定时间段内访问受限资源

### 通俗类比：限时访客证

`Proxy.revocable()` 就像是大厦保安室发放的**限时访客证**。

这张访客证（proxy）可以让持有人在规定时间内自由进出大厦的特定区域（访问对象的属性和方法）。但它有几个特点：

1. **有时效性**：到了规定时间，这张证就会自动失效（定时 revoke）
2. **可即时注销**：如果发现持证人有违规行为，保安可以远程立即注销这张证（手动调用 `revoke()`）
3. **彻底无效化**：一旦失效，这张证就变成了一张废塑料片——任何闸机都不会再认它（所有操作都抛 TypeError）
4. **不影响原件**：注销访客证并不会影响大厦本身的结构和安全系统（target 对象不受影响）

这种机制让大厦管理者能够在享受"开放访问"带来的便利的同时，保留随时关闭大门的能力——安全性与便利性的完美平衡。

## Proxy 的局限性

尽管 Proxy 强大而灵活，但它并非万能。了解其局限性有助于你在技术选型时做出合理的判断。

### 限制一：内部插槽（Internal Slots）

这是 Proxy 最著名的限制。某些内置对象（如 `Map`、`Set`、`Date`、`Promise`、`RegExp` 等）使用了**内部插槽**来存储数据——这是一种引擎层面的私有存储机制，无法通过普通的属性访问来读写。

```javascript
let map = new Map();
map.set("key", "value");

let mapProxy = new Proxy(map, {});

// 💥 TypeError: Method Map.prototype.set called on incompatible receiver
mapProxy.set("key2", "value2");
```

为什么会出错？因为 `Map` 的 `set` 方法内部依赖于 `this` 对象上的内部插槽 `[[MapData]]` 来存储键值对。当我们通过 proxy 调用 `mapProxy.set()` 时，`set` 方法内的 `this` 指向的是 proxy 对象而不是原始的 `map`，而 proxy 对象上并没有 `[[MapData]]` 这个内部插槽。

**解决方案**：在 `get` 捕获器中将获取到的函数方法手动绑定（bind）到原始 target 上：

```javascript
let safeMapProxy = new Proxy(map, {
  get(target, prop, receiver) {
    let value = Reflect.get(target, prop, receiver);
    // 如果是方法，绑定 this 到原始 target
    if (typeof value === "function") {
      return value.bind(target);
    }
    return value;
  }
});

safeMapProxy.set("key2", "value2");  // ✅ 正常工作了！
console.log(safeMapProxy.get("key2")); // "value2"
```

### 限制二：严格相等性（===）

Proxy 无法拦截 `===` 操作符。一个 proxy 对象永远不会与它的 target 严格相等：

```javascript
let target = { name: "test" };
let proxy = new Proxy(target, {});

console.log(proxy === target);  // false
console.log(proxy === proxy);   // true（同一个 proxy 引用）
```

这是因为 `===` 在 JavaScript 中比较的是**引用（内存地址）**，而 proxy 和 target 是两个不同的对象，占据不同的内存位置。这不是 Proxy 的缺陷而是语言设计上的必然——如果 `===` 可以被重载，那么很多基础的相等性假设都会崩塌（比如 `Map` 和 `Set` 的键查找机制）。

### 限制三：私有类字段（Private Fields）

ES2022 引入了类的私有字段语法（`#fieldName`）。私有字段也是基于内部插槽实现的，因此同样面临与 `Map`/`Set` 相似的问题：

```javascript
class SecretHolder {
  #secret = "classified information";

  getSecret() {
    return this.#secret;  // 需要通过 this 访问内部插槽
  }
}

let holder = new SecretHolder();
let holderProxy = new Proxy(holder, {});

// 💥 TypeError: Cannot read private member #secret from an object whose class did not declare it
holderProxy.getSecret();
```

同样地，可以通过在 `get` 捕获器中 bind 到 target 来缓解这个问题。

### 限制四：性能开销

Proxy 不是免费的午餐。每次通过 proxy 进行属性访问时，都需要经过一层捕获器的分发和转发。对于绝大多数应用场景来说，这个开销微乎其微（纳秒级别），完全可以忽略。但是在**性能极其敏感的热路径代码**中——比如每秒执行数百万次的物理引擎循环、高频交易系统的心跳检测——Proxy 可能会成为瓶颈。

根据一些基准测试，通过 Proxy 进行的属性访问比直接属性访问大约慢 **5~100 倍**（取决于引擎优化程度和操作复杂度）。再次强调：对于 99% 的应用代码来说这不构成问题，但你需要意识到这个代价的存在。

### 通俗类比：国际快递的中转站

如果把对象之间的直接交互比作国内快递（直接送达，快速高效），那么 Proxy 就像是**国际快递的中转海关**。

每一件包裹（属性操作）都必须经过中转站的安检、报关、查验流程（捕获器处理）。对于偶尔寄件的人来说，多花一点时间走海关流程完全没问题。但如果你每天需要发送成千上万件紧急货物（热路径代码），海关的额外延迟就可能成为严重的瓶颈。

此外，有些特殊的"外交包裹"（内置对象如 Map/Set）携带了机密文件（内部插槽），这些文件在中转站是无法被正常处理的——因为中转站没有相应的机密阅读权限。你必须采取特殊手段（bind 到原始对象）才能让这类包裹顺利过关。

## Reflect API：Proxy 的最佳搭档

### 为什么需要 Reflect？

在前面的代码示例中，我们已经多次使用了 `Reflect` 对象的方法。但你可能还心存疑惑：为什么推荐用 `Reflect.get(target, prop, receiver)` 而不是直接用 `target[prop]`？为什么用 `Reflect.set(target, prop, value, receiver)` 而不是 `target[prop] = value`？

答案是：**`Reflect` 是专门为配合 Proxy 而设计的**。它的每一个静态方法都与 Proxy 的捕获器一一对应，并且正确处理了所有边缘情况和不变量约束。

### Reflect 与 Proxy 的对应关系

| Proxy 捕获器 | Reflect 方法 | 说明 |
|-------------|------------|------|
| `get` | `Reflect.get(target, prop, receiver)` | 获取属性值 |
| `set` | `Reflect.set(target, prop, value, receiver)` | 设置属性值 |
| `has` | `Reflect.has(target, prop)` | in 操作符 |
| `deleteProperty` | `Reflect.deleteProperty(target, prop)` | delete 操作符 |
| `ownKeys` | `Reflect.ownKeys(target)` | 获取所有自有键 |
| `getOwnPropertyDescriptor` | `Reflect.getOwnPropertyDescriptor(target, prop)` | 获取属性描述符 |
| `defineProperty` | `Reflect.defineProperty(target, prop, desc)` | 定义属性 |
| `getPrototypeOf` | `Reflect.getPrototypeOf(target)` | 获取原型 |
| `setPrototypeOf` | `Reflect.setPrototypeOf(target, proto)` | 设置原型 |
| `isExtensible` | `Reflect.isExtensible(target)` | 检查可扩展性 |
| `preventExtensions` | `Reflect.preventExtensions(target)` | 阻止扩展 |
| `apply` | `Reflect.apply(target, thisArg, args)` | 函数调用 |
| `construct` | `Reflect.construct(target, args, newTarget)` | 构造函数调用 |

### 三大优势

**优势一：返回值规范化**

很多 `Reflect` 方法会返回布尔值来表示操作是否成功，这与 Proxy 捕获器的返回值约定完全一致：

```javascript
// delete 操作
let result = Reflect.deleteProperty(obj, "prop");  // 返回 true/false
// 而直接 delete 语句没有返回值可用

// defineProperty 操作
let success = Reflect.defineProperty(obj, "prop", desc);  // 返回 true/false
// Object.defineProperty 在失败时会抛异常，而不是返回 false
```

**优势二：receiver 参数的正确传递**

这一点我们在 `get` 和 `set` 捕获器部分已经详细讨论过了。`Reflect` 方法接受 `receiver` 参数，确保 getter/setter 中的 `this` 指向正确。

**优势三：函数式编程友好**

`Reflect` 的所有方法都是纯函数形式的静态方法，不像 `Object` 的方法那样有时作为函数、有时作为构造器、命名还不一致（比如 `Object.keys` vs `Object.hasOwnProperty` ——后者其实不在 Object 上而是在原型上）。`Reflect` 提供了一套统一、干净的 API 风格：

```javascript
// 旧方式 —— 风格混乱
obj.hasOwnProperty("key");     // 原型上的方法
Object.keys(obj);              // Object 上的静态方法
"in" in obj;                   // 操作符，不是函数调用
delete obj["key"];             // 操作符/语句

// 新方式 —— 统一风格
Reflect.has(obj, "key");                    // 替代 in
Reflect.ownKeys(obj);                       // 替代 Object.keys
Reflect.deleteProperty(obj, "key");          // 替代 delete
Reflect.getOwnPropertyDescriptor(obj, "key"); // 替代 Object.getOwnPropertyDescriptor
```

### 通俗类比：标准的公文流转格式

如果 Proxy 捕获器是各个部门的审批窗口，那 **Reflect 就是标准的公文流转格式手册**。

以前，不同部门有不同的办事风格：有的部门口头答复（操作符如 `in`、`delete`），有的部门要书面申请（`Object.keys`），有的部门用红头文件（`Object.defineProperty` 还会抛异常）。办事人员（开发者在写 handler 时）需要记住每种情况的特殊性——很容易搞混。

有了 `Reflect` 之后，所有部门都统一了办事格式：一律使用标准化的申请书表格（`Reflect` 的静态方法），统一的返回格式（成功/失败的明确反馈），统一的附加信息栏（`receiver` 参数）。办事人员只需要学会一套流程就可以应对所有窗口——大大降低了出错的可能性。

## 综合实战：构建响应式系统

### 背景：从理论到实践

学习了 13 种捕获器之后，你可能会好奇：这些东西组合起来到底能做什么？最能体现 Proxy 价值的实战场景之一就是**构建响应式数据系统**——这正是 Vue.js 3.0 的核心实现原理。

下面我们将用 Proxy 从零构建一个**迷你版的响应式系统**，综合运用 `get`、`set`、`has`、`deleteProperty`、`ownKeys` 等多个捕获器。

### 核心思路

响应式系统的目标是：**当数据发生变化时，自动通知所有依赖这个数据的观察者**。这个过程分为两步：

1. **依赖收集（Track）**：在读取属性时，记录"谁正在使用这个属性"
2. **触发更新（Trigger）**：在修改属性时，通知"所有用过这个属性的人"重新执行

```javascript
// ====== 第一部分：响应式核心 ======

// 当前活跃的副作用函数（正在执行的观察者）
let activeEffect = null;

// 副作用栈（支持嵌套 effect）
let effectStack = [];

// 注册一个副作用（观察者）函数
function effect(fn) {
  const effectFn = () => {
    try {
      effectStack.push(activeEffect);
      activeEffect = effectFn;
      return fn();  // 执行过程中会触发属性的 get，从而收集依赖
    } finally {
      effectStack.pop();
      activeEffect = effectStack[effectStack.length - 1] || null;
    }
  };
  effectFn();  // 立即执行一次以收集初始依赖
  return effectFn;
}

// 存储依赖关系: { target -> { prop -> Set<effect> } }
const targetMap = new WeakMap();

// 收集依赖（在 get 捕获器中调用）
function track(target, prop) {
  if (!activeEffect) return;

  let depsMap = targetMap.get(target);
  if (!depsMap) {
    depsMap = new Map();
    targetMap.set(target, depsMap);
  }

  let dep = depsMap.get(prop);
  if (!dep) {
    dep = new Set();
    depsMap.set(prop, dep);
  }

  dep.add(activeEffect);
  console.log(`📡 [Track] "${String(prop)}" 被追踪，当前活跃 effect 数: ${dep.size}`);
}

// 触发更新（在 set/deleteProperty 捕获器中调用）
function trigger(target, prop) {
  const depsMap = targetMap.get(target);
  if (!depsMap) return;

  const dep = depsMap.get(prop);
  if (!dep) return;

  console.log(`🔥 [Trigger] "${String(prop)}" 变化了，通知 ${dep.size} 个 effect`);
  // 复制一份再遍历，避免 effect 执行过程中修改 Set 导致的问题
  [...dep].forEach(effect => effect());
}


// ====== 第二部分：创建响应式对象 ======

function reactive(target) {
  return new Proxy(target, {
    get(target, prop, receiver) {
      let result = Reflect.get(target, prop, receiver);

      // 如果值是对象，递归地将其也变为响应式
      if (result !== null && typeof result === "object" && !Array.isArray(result)) {
        result = reactive(result);
      }

      track(target, prop);  // 收集依赖
      return result;
    },

    set(target, prop, value, receiver) {
      // 检查值是否真的变了
      let oldValue = target[prop];
      let isChanged = oldValue !== value;

      let result = Reflect.set(target, prop, value, receiver);

      if (isChanged) {
        trigger(target, prop);  // 触发更新
      }

      return result;
    },

    has(target, prop) {
      track(target, prop);  // in 操作也会产生依赖
      return Reflect.has(target, prop);
    },

    deleteProperty(target, prop) {
      let hadKey = prop in target;
      let result = Reflect.deleteProperty(target, prop);

      if (hadKey) {
        trigger(target, prop);  // 删除也要触发更新
      }

      return result;
    },

    ownKeys(target) {
      track(target, "__iterate__");  // 遍历操作也会产生依赖
      return Reflect.ownKeys(target);
    }
  });
}


// ====== 第三部分：使用我们的响应式系统 ======

let state = reactive({
  count: 0,
  user: {
    name: "吴九",
    score: 95
  },
  tags: ["js", "proxy"]
});

// 注册观察者 1：当 count 变化时更新 UI
effect(() => {
  console.log(`📊 UI渲染: count = ${state.count}`);
});

// 注册观察者 2：当用户分数变化时计算等级
effect(() => {
  let level = state.user.score >= 90 ? "优秀" :
              state.user.score >= 70 ? "良好" : "及格";
  console.log(`🎖️ 等级评定: ${state.user.name} - ${level} (${state.user.score}分)`);
});

// 注册观察者 3：复合依赖
effect(() => {
  console.log(`📝 摘要: ${state.user.name} 有 ${state.count} 条消息, 标签: ${state.tags.join(", ")}`);
});

/*
 * 输出（初始执行）:
 * 📡 [Track] "count" 被追踪
 * 📊 UI渲染: count = 0
 *
 * 📡 [Track] "score" 被追踪
 * 📡 [Track] "name" 被追踪
 * 🎖️ 等级评定: 吴九 - 优秀 (95分)
 *
 * 📡 [Track] "count" 被追踪
 * 📡 [Track] "name" 被追踪
 * 📡 [Track] "__iterate__" 被追踪
 * 📡 [Track] "tags" 被追踪
 * 📝 摘要: 吴九 有 0 条消息, 标签: js, proxy
 */

console.log("\n--- 修改 count ---\n");
state.count = 5;
// 🔥 [Trigger] "count" 变化了，通知 2 个 effect
// 📊 UI渲染: count = 5        ← effect 1 重新执行
// 📝 摘要: 吴九 有 5 条消息, 标签: js, proxy  ← effect 3 重新执行（因为它依赖 count）

console.log("\n--- 修改 user.score ---\n");
state.user.score = 88;
// 🔥 [Trigger] "score" 变化了，通知 1 个 effect
// 🎖️ 等级评定: 吴九 - 良好 (88分)  ← effect 2 重新执行

console.log("\n--- 添加标签 ---\n");
state.tags.push("reactive");
// （tags 变化也会触发 __iterate__ 相关的更新）
```

### 系统架构解读

这个迷你响应式系统展示了 Proxy 多种捕获器的协同工作：

- **`get` 捕获器**：在属性被读取时收集依赖关系（track）。这是整个系统的起点——没有读取就没有依赖，也就没有后续的更新通知
- **`set` 捕获器**：在属性被修改时触发依赖更新（trigger）。这是系统的驱动力——数据变化推动视图刷新
- **`has` 捕获器**：让 `in` 操作符也能参与依赖追踪。比如模板中 `<div v-if="'name' in obj">` 这种用法也需要响应式
- **`deleteProperty` 捕获器**：让 `delete` 操作也能触发更新。数据结构的改变（不仅仅是值的改变）也应该驱动视图
- **`ownKeys` 捕获器**：让 `for...in` 循环和 `Object.keys()` 等遍历操作也被纳入响应式体系

**理论升华**：这个例子揭示了现代前端框架的核心思想——**声明式编程（Declarative Programming）**。开发者不需要手动编写"当 A 变化时更新 B"这样的命令式代码，只需声明"UI 依赖于哪些数据"，框架的响应式系统就会自动维护数据和视图之间的同步关系。而 Proxy 正是实现这种"自动维护"的关键基础设施。

### 通俗类比：报刊订阅系统

如果我们把这个响应式系统比作一个**报刊订阅系统**，那么：

- **`reactive()` 创建的对象** = 报刊出版商（数据源）
- **`effect()` 注册的观察者** = 订阅了报纸的读者（UI 组件/副作用）
- **`track()` 依赖收集** = 读者告诉邮局"我要订阅这份报纸"的过程
- **`trigger()` 更新触发** = 出版商出了新一版报纸，邮局通知所有订阅者"新版来了，快来取"
- **Proxy 的 `get` 捕获器** = 邮局柜台——读者来这里查看报纸内容（读取数据），同时顺便登记订阅（收集依赖）
- **Proxy 的 `set` 捕获器** = 编辑部——当新闻发生时（数据变化），编辑部通知发行部门（触发更新）

整个流程完全是自动化的：读者只需要说一声"我要订阅"（声明依赖），之后每次有新报纸出版（数据变化）都会自动送到手上（视图更新）。读者不需要每天跑去出版社问"出新版了吗？"——这正是响应式编程相对于命令式编程的根本效率提升。

## 总结：13 种捕获器速查表

| 编号 | 捕获器名称 | 触发方式 | 核心用途 | 返回值要求 |
|------|-----------|---------|---------|-----------|
| 1 | `get` | 读取属性 `obj.prop` | 默认值、属性翻译、日志 | 返回属性值 |
| 2 | `set` | 写入属性 `obj.prop = val` | 数据校验、只读保护 | **必须返回 true** |
| 3 | `has` | `in` 操作符 `prop in obj` | 区间检测、属性隐藏 | 返回布尔值 |
| 4 | `deleteProperty` | `delete obj.prop` | 属性保护、软删除 | **必须返回 true** |
| 5 | `ownKeys` | `Object.keys()` / `for...in` | 过滤私有属性、排序 | 返回数组 |
| 6 | `getOwnPropertyDescriptor` | `Object.getOwnPropertyDescriptor()` | 配合 ownKeys 隐藏属性 | 描述符或 undefined |
| 7 | `defineProperty` | `Object.defineProperty()` | 属性定义约束 | **必须返回 true** |
| 8 | `getPrototypeOf` | `Object.getPrototypeOf()` | 原型读取拦截 | 对象或 null |
| 9 | `setPrototypeOf` | `Object.setPrototypeOf()` | 锁定原型 | **必须返回 true** |
| 10 | `isExtensible` | `Object.isExtensible()` | 扩展性检查 | 必须与实际一致 |
| 11 | `preventExtensions` | `Object.preventExtensions()` | 锁定对象扩展 | **必须返回 true** |
| 12 | `apply` | 函数调用 `fn()` | 日志、节流、校验 | 任意返回值 |
| 13 | `construct` | `new Fn()` | 单例、依赖注入 | **必须返回对象** |

### 设计哲学总结

Proxy 的 13 种捕获器覆盖了 JavaScript 中对一个对象可能执行的全部基本操作。这种**全面的可拦截性**体现了 JavaScript 语言设计的一个重要理念：**信任开发者，赋予其足够的能力去控制和定制语言行为**。你不是语言的被动使用者——通过 Proxy，你可以成为语言的主动塑造者。

从实际工程角度来看，Proxy 的核心价值体现在三个维度：

1. **面向切面编程（AOP）**：在不修改原始代码的前提下，横切性地加入日志、鉴权、缓存、监控等关注点
2. **领域特定语言（DSL）**：通过重载基本操作的语义，创造更具表达力的 API（如 `number in range` 表示区间检测）
3. **运行时代理与虚拟化**：创建远程对象的本地代理、实现懒加载、构建响应式系统等高级模式

> **记住**：Proxy 是一把锋利的手术刀。用好了，它能帮你精准地解决复杂问题；用不好，它也可能让你的代码变得难以理解和调试。掌握它的最好方式就是在实践中不断尝试——从小规模的日志代理开始，逐步过渡到完整的响应式系统。当你能够熟练地在脑海中模拟每一次属性操作经过 Proxy 捕获器的完整流程时，你就真正掌握了这门技术。
