# 装饰器模式：ESnext 装饰器提案（Stage 3）详解

## 从一个简单的需求说起：什么是装饰器？

在深入技术细节之前，让我们从一个日常生活中的场景开始，建立对"装饰"这一概念的直觉认知。

想象你正在装修一间新房子。房子本身已经建好了——有墙壁、地板、窗户、门。这是**基础结构**。但你觉得白色的墙面太单调了，于是你请画师在墙上挂了一幅油画；你觉得地面太冷了，于是铺了一层厚厚的地毯；你觉得窗户透光太强了，于是装了一层纱帘。

注意这个过程中发生了什么：**你并没有改变房子的基础结构**——墙还是那堵墙，窗还是那扇窗。你所做的只是在已有的事物之上，一层一层地添加额外的功能或外观。每一层"装饰"都可以独立地被添加或移除，而不会影响房子本身。这就是"装饰"的核心思想：**在不修改原有对象的前提下，动态地为它添加新的能力**。

把这个思想迁移到编程世界中，**装饰器（Decorator）就是一种能够在不改变原有代码结构的情况下，为类、方法、属性等程序元素"附加"额外行为的语法机制**。它让你能够以一种声明式的、优雅的方式来实现横切关注点（Cross-cutting Concerns）的分离和复用——比如日志记录、性能监控、权限校验、数据验证、自动绑定 `this` 等。

本文将全面讲解 ECMAScript 装饰器提案（当前处于 **Stage 3** 阶段，即将成为标准的一部分），包括其理论基础、各种类型的装饰器、装饰器工厂、执行顺序、上下文对象以及大量实战案例。

## 装饰器模式的起源与理论基础

### 设计模式中的装饰器模式

装饰器并非 JavaScript 独有的概念，它是经典的 **GoF（Gang of Four）设计模式**之一，全称为 **装饰者模式（Decorator Pattern）**。GoF 在《设计模式：可复用面向对象软件的基础》一书中对它的定义是：

> **动态地给一个对象添加一些额外的职责。就增加功能来说，装饰器模式比生成子类更为灵活。**

这段定义中有两个关键词值得反复咀嚼：

**第一个关键词是"动态"**。传统的继承（Inheritance）是静态的——你在写代码的时候就必须确定类的继承关系，一旦编译完成就无法更改。而装饰器是运行时的——你可以根据不同的条件、在不同的时机、以不同的组合方式来为对象添加能力。这种灵活性使得同一个基础类可以衍生出无数种变体，而不需要创建大量的子类。

**第二个关键词是"比生成子类更为灵活"**。如果你用继承来扩展功能，每增加一种新的功能组合就需要创建一个新的子类。假设有一个基础类 `Component`，你想让它具备日志、缓存、权限检查三种能力的任意组合，那么你需要创建：`Component`、`LoggedComponent`、`CachedComponent`、`SecureComponent`、`LoggedCachedComponent`、`LoggedSecureComponent`、`CachedSecureComponent`、`LoggedCachedSecureComponent`——一共 **8 个类**（2^n 的组合爆炸）。而用装饰器模式，你只需要 3 个装饰器和 1 个基础类，就可以通过自由组合实现所有 8 种功能变体。

### 通俗类比：手机壳与手机

为了更直观地理解装饰器的价值，我们来看一个生活中的类比——**手机与手机壳**：

你的手机本身已经是一个功能完备的产品——它能打电话、发短信、拍照、上网。这就像你的**基础类**。但你可能会给它戴上几个"装饰"：
- 一个**防摔保护壳** → 增加了防摔能力（但不改变手机本身的通话功能）
- 一张**钢化膜** → 增加了屏幕防护（不影响手机的拍照功能）
- 一个**指环扣支架** → 增加了支架功能（不干扰手机的充电功能）

这些"装饰品"有几个共同特点：
1. 它们都是**可拆卸的**——你可以随时换掉保护壳，手机还是原来的手机
2. 它们可以**叠加使用**——保护壳 + 钢膜 + 指环扣同时存在也没问题
3. 它们**不侵入手机内部**——不需要拆开手机来改造内部电路
4. 每个装饰都有**独立的职责**——保护壳只管防摔，钢膜只管防刮

JavaScript 的装饰器正是这种思想的编码实现：每个装饰器只做一件事，它们可以自由组合、随时增减，而且不会污染原始类的代码。

### JavaScript 中装饰器的演进历程

JavaScript 的装饰器之路并不平坦。了解这段历史有助于你理解为什么当前提案是这个样子的：

**第一版提案（2015 年前后，Stage 1→2）**：由 Yehuda Katz 和 Ron Buckton 主导，基于 `descriptor`（属性描述符）的设计。TypeScript 和 Babel 早期都采用了这个版本。它的核心特点是装饰器接收三个参数：`(target, key, descriptor)`，直接操作属性描述符对象。这个版本的 API 与 Python 的装饰器风格相似，但在处理 `class` 表达式、私有字段等方面存在诸多问题。

**第二版提案（2018~2021，重新设计）**：TC39 委员会决定对装饰器提案进行彻底重写。新方案采用 `(value, context)` 的双参数签名，引入了统一的上下文对象（Context Object）概念。2022 年 3 月，新版提案成功进入 **Stage 3**，标志着规范趋于稳定。

**当前状态（2024~2026）**：Stage 3 意味着该提案已经基本定稿，各大浏览器和引擎开始实现。TypeScript 5.0+ 已经完全支持新版装饰器语法（无需任何实验性标志）。Node.js 22+ 也已原生支持。V8 引擎已经在 Chrome 118+ 中默认启用装饰器功能。

> 本文所介绍的内容均基于 **Stage 3 版本**（即最新版提案）。如果你在网上看到使用三参数形式 `function(target, propertyKey, descriptor) { ... }` 的装饰器教程，那是旧版（Legacy/Stage 1）语法，已被废弃，请注意区分。

## 装饰器的基本语法

### 核心规则一览

在正式学习各类装饰器之前，我们先掌握装饰器最基础的语法规则。这些规则适用于所有类型的装饰器：

**规则一：装饰器本质上就是一个普通函数**

```javascript
// 这就是一个最简单的装饰器
function myDecorator(value, context) {
  console.log("我被调用了！");
  console.log("被装饰的值:", value);
  console.log("上下文信息:", context);
}
```

装饰器函数接收**两个参数**：
- **`value`**：被装饰的那个东西本身（如果是类就是类本身，如果是方法就是方法函数，如果是字段就是初始值）
- **`context`**：上下文对象，包含关于"这个东西在哪里被装饰"的各种元信息（后面会详细展开）

**规则二：使用 `@` 符号将装饰器应用到目标上**

```javascript
// 装饰一个类
@myDecorator
class MyClass { }

// 装饰一个方法
class OtherClass {
  @myDecorator
  myMethod() { }
}

// 装饰一个字段（类属性）
class AnotherClass {
  @myDecorator
  myField = 42;
}
```

**规则三：装饰器函数可以选择返回一个新值来替换被装饰的值**

```javascript
function doubleTheValue(value, context) {
  // 如果是字段装饰器，value 是初始值
  // 返回一个新的值来替换原来的值
  return value * 2;
}

class Example {
  @doubleTheValue
  count = 5;  // 实际值会被替换为 10
}
```

**规则四：如果装饰器不需要返回值（或不返回任何东西），则保持原值不变**

```javascript
function logCreation(value, context) {
  // 只是打印日志，不修改原值
  console.log(`创建了 ${context.kind}: ${context.name}`);
  // 没有 return 或 return undefined → 保持原值不变
}
```

### 第一个完整示例

让我们把上面的规则整合起来，写出一个完整的、可运行的示例：

```javascript
// 定义一个简单的类装饰器
function loggedClass(value, context) {
  // value 就是被装饰的类（构造函数）
  // context 包含元信息
  console.log("装饰器被调用！");
  console.log("kind:", context.kind);    // "class"
  console.log("name:", context.name);    // "MyClass"

  // 可以选择返回一个新类来替换原类，这里我们不做替换
  // 返回 undefined 表示保持原样
}

// 使用装饰器
@loggedClass
class MyClass {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return `你好，我是 ${this.name}`;
  }
}

let obj = new MyClass("张三");
console.log(obj.greet());  // "你好，我是 张三"
// 控制台输出:
// 装饰器被调用！
// kind: class
// name: MyClass
```

在这个例子中，`@loggedClass` 出现在 `class MyClass` 的正上方。当 JavaScript 引擎解析到这个类时，它会先执行装饰器函数 `loggedClass`，把类本身作为 `value` 传入，然后才让类正常可用。装饰器的作用时机是在**类定义时**（定义阶段），而不是在**实例化时**（运行阶段）。这是一个非常关键的区别——装饰器只会在类第一次被定义时执行一次，之后无论你 `new` 多少次实例，都不会再次触发装饰器。

## 类装饰器（Class Decorators）

### 什么是类装饰器？

类装饰器是最直观的一类装饰器——它作用于整个类，可以用来修改或替换类的行为。从理论角度来说，类装饰器接收到的 `value` 参数就是**类构造函数本身**（即 `class` 声明所产生的构造函数对象），`context.kind` 的值为字符串 `"class"`。

类装饰器的典型用途包括：
- 为类添加静态方法或属性
- 修改类的原型链
- 用代理（Proxy）包装类以拦截操作
- 密封（seal）或冻结（freeze）类及其原型
- 注册类到某个全局容器中

### 基本用法：为类添加元数据

让我们从最简单也最常见的用法开始——给类打上标记或添加元信息：

```javascript
// 定义一个类装饰器，用于标记"实体类"
function entity(value, context) {
  // value = Entity 类的构造函数
  // context.kind = "class"
  // context.name = "User"

  // 在构造函数上添加自定义属性（类似 Java 的注解）
  value.__isEntity = true;        // 标记这是一个实体类
  value.__entityName = context.name; // 记录实体名称

  // 不需要返回值，保持原类不变
}

@entity
class User {
  constructor(id, name) {
    this.id = id;
    this.name = name;
  }
}

// 验证装饰效果
console.log(User.__isEntity);     // true ✅
console.log(User.__entityName);   // "User" ✅

let u = new User(1, "张三");
console.log(u.id, u.name);       // 1 "张三" —— 类的功能完全不受影响
```

这里发生的事情很清晰：装饰器函数 `entity` 在 `User` 类被定义时立即执行，它拿到了 `User` 的构造函数引用，然后在上面附加了两个自定义属性。之后 `User` 类的一切行为照常——你能实例化它、调用方法、访问属性，就像没有装饰器一样。唯一的区别是现在 `User` 构造函数身上多了一些"标签"。

### 进阶用法：替换整个类

类装饰器不仅可以给类"贴标签"，还可以**返回一个全新的类来完全替代原有的类**。这是一种强大的能力，但同时也需要谨慎使用——因为一旦你替换了原类，原有类的一些特征（如 `instanceof` 关系、原型链上的方法等）可能需要在新类中手动重建：

```javascript
// 定义一个装饰器，让类变得"不可变"——密封类及其原型
function sealed(value, context) {
  // value 是原始类
  // 我们对原始类进行密封处理后返回它
  Object.seal(value);         // 密封构造函数本身
  Object.seal(value.prototype); // 密封原型对象

  // 返回密封后的类（其实就是同一个引用）
  return value;
}

@sealed
class SafeBox {
  #contents;  // 私有字段

  constructor(initialContent) {
    this.#contents = initialContent;
  }

  getContent() {
    return this.#contents;
  }

  setContent(newContent) {
    this.#contents = newContent;
  }
}

let box = new SafeBox("机密文件");
console.log(box.getContent());  // "机密文件"
box.setContent("新文件");
console.log(box.getContent());  // "新文件"

// 尝试往原型上添加新方法 —— 失败！因为已经被密封了
SafeBox.prototype.hack = function () { return "被入侵了"; };
// 在严格模式下会抛出 TypeError；非严格模式下静默失败
console.log(box.hack);          // undefined —— 无法添加！

// 尝试往构造函数上添加静态属性 —— 同样失败！
SafeBox.newStaticProp = 42;
console.log(SafeBox.newStaticProp); // undefined
```

这个例子展示了一种实际有用的应用场景：当你发布了一个库或者框架的核心类，你不希望使用者（包括你自己）在运行时意外修改这个类的原型或构造函数时，可以用 `@sealed` 来保护它。这与 ES6 内置的 `Object.freeze()` / `Object.seal()` 思路一致，只是通过装饰器语法变得更加声明式和优雅。

### 高级用法：使用 Proxy 包装类

类装饰器最强大但也最复杂的应用之一是使用 `Proxy`（代理）来包装类。通过 Proxy，你可以在不修改原始类代码的前提下，拦截对其构造函数和原型方法的几乎所有操作：

```javascript
// 定义一个"可观测"的类装饰器 —— 拦截所有方法调用并打印日志
function observable(value, context) {
  // 创建一个代理构造函数
  return new Proxy(value, {
    construct(target, args) {
      // target 是原始类（构造函数）
      // args 是传给 new 的参数列表

      console.log(`[Observable] 正在创建 ${context.name} 的实例`);
      console.log(`[Observable] 构造参数:`, args);

      let instance = new target(...args);

      // 对实例进行代理，拦截方法调用
      return new Proxy(instance, {
        get(target, prop, receiver) {
          const val = Reflect.get(target, prop, receiver);
          if (typeof val === 'function') {
            return function (...methodArgs) {
              console.log(
                `[Observable] 调用了方法 ${String(prop)}`,
                `参数:`, methodArgs
              );
              const result = val.apply(this, methodArgs);
              console.log(
                `[Observable] 方法 ${String(prop)} 返回:`,
                result
              );
              return result;
            };
          }
          return val;
        }
      });
    }
  });
}

@observable
class TaskManager {
  #tasks = [];

  addTask(task) {
    this.#tasks.push(task);
    return this.#tasks.length;
  }

  getTaskCount() {
    return this.#tasks.length;
  }
}

// 使用被装饰后的类
let tm = new TaskManager();
// 输出:
// [Observable] 正在创建 TaskManager 的实例
// [Observable] 构造参数: []

tm.addTask("写报告");
// 输出:
// [Observable] 调用了方法 addTask 参数: ['写报告']
// [Observable] 方法 addTask 返回: 1

tm.getTaskCount();
// 输出:
// [Observable] 调用了方法 getTaskCount 参数: []
// [Observable] 方法 getTaskCount 返回: 1
```

这个例子中，`@observable` 装饰器做了两件重要的事：

**第一，它在构造阶段**（`construct` 拦截器）捕获了实例创建的过程，打印了类名和构造参数。这对于调试来说极其有用——你可以清楚地看到每一个实例是什么时候被创建的、用什么参数创建的。

**第二，它对返回的实例进行了二次代理**（在实例的 `get` 拦截器中），使得每次调用实例的方法时都会自动打印日志。这种"透明拦截"的能力是 Proxy 的精髓所在——调用方完全不知道自己使用的对象已经被代理过了，一切看起来跟原来一模一样，但实际上每次操作都被"监听"了。

### 类装饰器的通俗类比：汽车改装店

让我们用一个生活化的场景来巩固对类装饰器的理解：

想象有一家**汽车改装店**（类装饰器）。客户把自己的车（原始类）开进店里。改装店的技师（装饰器函数）会对车进行一系列操作：
- 给车贴上"已改装"的标签（添加元数据）
- 给车的引擎加上限速器（密封/限制行为）
- 在车上安装行车记录仪（Proxy 代理，记录所有操作）

改装完成后，车主拿回的车可能外表看起来没太大变化，但它已经有了额外的能力或限制。关键在于：**改装店并没有重新造一辆车**，而是在原有车辆的基础上进行增强或约束。车主也可以选择去不同的改装店（不同的装饰器），获得不同类型的改装效果。甚至可以去多家店，叠加多种改装（多个装饰器组合使用）。

## 方法装饰器与访问器装饰器（Method & Accessor Decorators）

### 什么是方法装饰器？

方法装饰器作用于类的方法之上，它可以用来修改方法的行为——比如在方法执行前后插入逻辑、替换方法的实现、对方法的输入输出进行处理等等。当装饰器应用于方法时，`value` 参数就是**那个方法函数本身**，`context.kind` 的值为 `"method"`，`context.name` 就是方法的名称字符串。

方法装饰器是日常开发中最常用的一类装饰器，因为它能解决大量重复性的横切关注点问题。

### 基础示例：方法调用日志

几乎每个项目都需要某种形式的日志功能。传统做法是在每个方法的开头和结尾手写 `console.log`，这不仅繁琐，还会让业务逻辑和日志逻辑混在一起，降低代码的可读性。有了方法装饰器，我们可以把日志逻辑抽取出来，通过一行 `@` 注解就应用到任意方法上：

```javascript
// 定义一个方法日志装饰器
function logMethod(value, context) {
  // value = 被装饰的方法函数
  // context.kind = "method"
  // context.name = 方法名，如 "greet"、"calculate"

  // 返回一个新函数来替代原方法
  return function (...args) {
    const methodName = context.name;

    console.log(`[LOG] 开始调用 ${methodName}()`);
    console.log(`[LOG] 参数列表:`, args);

    const startTime = performance.now();

    // 调用原始方法（注意 this 绑定）
    const result = value.apply(this, args);

    const endTime = performance.now();
    console.log(`[LOG] ${methodName}() 执行完毕`);
    console.log(`[LOG] 返回值:`, result);
    console.log(`[LOG] 耗时: ${(endTime - startTime).toFixed(2)}ms`);

    return result;
  };
}

class Calculator {
  @logMethod
  add(a, b) {
    // 模拟一个稍微耗时的计算
    let sum = 0;
    for (let i = a; i <= b; i++) sum += i;
    return sum;
  }

  @logMethod
  multiply(a, b) {
    return a * b;
  }
}

let calc = new Calculator();
calc.add(1, 1000000);
// 输出:
// [LOG] 开始调用 add()
// [LOG] 参数列表: [1, 1000000]
// [LOG] add() 执行完毕
// [LOG] 返回值: 500000500000
// [LOG] 耗时: x.xxms

calc.multiply(7, 8);
// 输出:
// [LOG] 开始调用 multiply()
// [LOG] 参数列表: [7, 8]
// [LOG] multiply() 执行完毕
// [LOG] 返回值: 56
// [LOG] 耗时: 0.00ms
```

仔细观察这个装饰器的实现细节，有几个关键点值得注意：

**关于 `this` 绑定的问题**：在装饰器返回的新函数中，我们使用 `value.apply(this, args)` 来调用原始方法。这里的 `this` 是谁？答案是——取决于方法最终是如何被调用的。如果通过 `calc.add(1, 1000000)` 调用，那么 `this` 就是 `calc` 实例。这一点非常重要，因为如果我们在新函数里写成 `value(args)` 或者 `value.call(undefined, args)`，原始方法内部的 `this` 就会丢失，导致访问 `this.xxx` 时出错。

**关于返回值的传递**：新函数必须把原始方法的返回值 `return` 出去。否则，调用方拿到的是 `undefined` 而非预期的结果。这是一个常见的错误来源——很多初学者在写装饰器时忘记返回结果。

### 访问器装饰器（Getter/Setter）

除了普通的方法装饰器，还有专门针对 **getter** 和 **setter** 访问器的装饰器。它们的用法与方法装饰器几乎相同，区别仅在于 `context.kind` 的值分别为 `"getter"` 和 `"setter"`：

```javascript
// 定义一个 getter 缓存装饰器 —— 只计算一次，后续直接返回缓存结果
function cachedGetter(value, context) {
  // value 就是 getter 函数本身
  // context.kind === "getter"

  const cacheKey = Symbol('__cached__');

  // 替换 getter 的实现，加入缓存逻辑
  return function () {
    // 如果还没有缓存过，计算并存入缓存
    if (!(cacheKey in this)) {
      this[cacheKey] = value.call(this);
    }
    return this[cacheKey];
  };
}

class ExpensiveComputation {
  #data;

  constructor(data) {
    this.#data = data;
  }

  @cachedGetter
  get expensiveResult() {
    console.log("正在进行昂贵计算...（只会看到一次）");
    // 模拟一个耗时计算
    let sum = 0;
    for (let i = 0; i < this.#data.length; i++) {
      sum += this.#data[i] ** 2;
    }
    return sum;
  }
}

let ec = new ExpensiveComputation([1, 2, 3, 4, 5]);

console.log(ec.expensiveResult);
// 输出: 正在进行昂贵计算...（只会看到一次）
//       55

console.log(ec.expensiveResult);  // 直接返回缓存！
// 输出: 55 （没有再次打印"正在进行昂贵计算"）

console.log(ec.expensiveResult);  // 还是缓存！
// 输出: 55
```

这个 `@cachedGetter` 装饰器展示了访问器装饰器的一个经典应用——**惰性计算与结果缓存**。第一次访问 `expensiveResult` 时，getter 会执行真正的计算并把结果存起来；之后再访问时，就直接从缓存中取值，跳过昂贵的计算过程。这在处理 DOM 计算、复杂数学运算、大数据聚合等场景中能显著提升性能。

### 通俗类比：快递代收点

方法装饰器和访问器装饰器的作用机制很像生活中的**快递代收点**：

假设你家门口有一个快递代收点（装饰器）。每当有人要给你寄东西（调用方法）时，包裹并不会直接送到你手上，而是先送到代收点。代收点的管理员会做以下事情：
- **登记信息**：记录是谁寄的、什么时候到的（记录调用参数和时间戳）
- **检查包裹**：确认包裹是否完好（参数校验）
- 可能还会**称重计费**（性能计时）

做完这些事后，管理员才会把包裹交到你手里（返回结果）。对于寄件人（调用方）来说，他只需要按正常的地址投递即可，完全不需要知道中间经过了代收点。对于收件人（方法本身）来说，他也只需要处理自己的事情，不需要关心外面有没有人在监控这个过程。

这就是装饰器带来的最大好处——**业务逻辑和横切逻辑完全解耦**。方法只需要关心"我该做什么"，而装饰器负责"在做之前/之后附带什么"。

## 字段装饰器（Field Decorators）

### 什么是字段装饰器？

字段装饰器作用于类的**字段（属性）**上，也就是那些在类体中声明的变量（如 `name = "default"`）。与方法装饰器不同的是，字段装饰器接收到的 `value` 是字段的**初始化表达式求值后的结果**（即初始值），而不是函数。`context.kind` 的值为 `"field"`。

字段装饰器的典型用途包括：
- 对字段的初始值进行转换或验证
- 将字段变为只读（不可写入）
- 为字段添加变更通知机制
- 将字段值存储到外部存储（如 localStorage）

### 基础用法：字段值转换

```javascript
// 定义一个字段装饰器，自动将字符串转为大写
function upperCase(value, context) {
  // value 是字段初始值的计算结果
  // 如果初始值不是字符串，原样返回
  if (typeof value === 'string') {
    return value.toUpperCase();
  }
  return value;
}

class UserProfile {
  @upperCase
  name = "john doe";  // 会被自动转为 "JOHN DOE"

  @upperCase
  country = "china";  // 会被自动转为 "CHINA"

  age = 25;           // 不是字符串，不受影响
}

let profile = new UserProfile();
console.log(profile.name);     // "JOHN DOE"
console.log(profile.country);  // "CHINA"
console.log(profile.age);      // 25
```

这个例子里，`@upperCase` 装饰器做的事情很简单：检查初始值是不是字符串，如果是就转成大写后返回。引擎会用返回的这个新值来设置字段的初始状态。需要注意的是，字段装饰器只在**初始化时**执行一次——之后你对这个字段的赋值（如 `profile.name = "new name"`）不会再经过装饰器。如果你想控制赋值行为，应该使用下面要介绍的 accessor 装饰器。

### 进阶用法：不可变字段

有时候我们希望某些字段在初始化之后就变成"只读"的——可以被读取但不能被重新赋值。这在配置对象、常量定义等场景中非常有用：

```javascript
// 定义一个"不可变"字段装饰器
function readonly(value, context) {
  // context.access 提供了对字段的读写访问能力
  // 我们用它来自定义字段的 setter 行为
  context.access.set = function (newValue) {
    // 当尝试修改时，抛出错误
    throw new Error(
      `无法修改只读字段 "${context.name}"：` +
      `当前值为 ${JSON.stringify(this[context.access.get.name || context.name])}，` +
      `试图设置为 ${JSON.stringify(newValue)}`
    );
  };

  // 不修改初始值，原样返回
  return value;
}

class AppConfig {
  @readonly
  appName = "My Awesome App";

  @readonly
  version = "1.0.0";

  debugMode = false;  // 这个字段没有被 readonly 保护，可以修改
}

let config = new AppConfig();

console.log(config.appName);   // "My Awesome App"
console.log(config.version);   // "1.0.0"

config.appName = "Hacked!";    // 💥 抛出 Error!
// Error: 无法修改只读字段 "appName"：
//       当前值为 "My Awesome App"，试图设置为 "Hacked!"

config.debugMode = true;       // ✅ 正常工作——这个字段没有被保护
console.log(config.debugMode); // true
```

这个例子引入了一个重要的新概念——**`context.access`**。这是字段装饰器独有的能力，它提供了对被装饰字段底层存储机制的访问权。通过覆盖 `context.access.set`，我们可以自定义"当有人对这个字段赋值时会发生什么"。在上面的例子中，我们把 set 改成了始终抛错，从而实现了只读效果。

### 字段装饰器的局限性与 accessor 装饰器

你可能已经注意到，字段装饰器有一些天然的局限性：

1. **只能干预初始化**：装饰器只在字段首次赋值时执行，之后的读写操作不受控制
2. **不能拦截 getter/setter**：字段装饰器本身不产生 getter/setter 对

为了解决这些问题，ECMAScript 引入了专门的 **accessor 装饰器**（下一节详细讲解）。简单来说，如果你需要在每次读写字段时都执行自定义逻辑（比如验证、转换、通知），accessor 装饰器是更好的选择。

### 通俗类比：机场安检通道

字段装饰器就像是机场的**行李安检入口**：

每位旅客（字段值）进入航站楼（类实例）之前，都必须经过安检口（装饰器）。安检人员（装饰器函数）会检查行李（初始值）：如果发现液体超过 100ml（不符合要求），会要求处理（值转换）；如果发现违禁品（无效值），会拒绝放行（报错或设为默认值）。

但是要注意的是——安检只在**入场时进行一次**。一旦旅客通过了安检进入了候机大厅（实例创建完成），他们在里面的活动就不受安检口管控了（后续赋值不会被拦截）。

如果你需要对旅客在大厅内的活动也持续监控（拦截每次读写），那就需要用到更高级的"实时监控系统"——这就是 accessor 装饰器的角色。

## Accessor 装饰器

### 什么是 accessor 装饰器？

`accessor` 是 ECMAScript 装饰器提案中一种特殊且强大的字段类型，也是最容易让初学者混淆的概念。理解它的关键是认识到：**`accessor` 本身不是一种装饰器类型，而是类的一种字段声明语法**。当你使用 `accessor` 关键字声明一个字段时，JavaScript 引擎会自动为这个字段生成一对 getter 和 setter，并将实际值存储在一个私有的后备槽（backing slot）中。

而 **accessor 装饰器**则是作用在这种 `accessor` 字段上的装饰器。它接收到的 `value` 是自动生成的 getter 函数，`context.kind` 的值为 `"accessor"`。

### 为什么需要 accessor？

在了解具体用法之前，我们需要先明白"为什么要发明 accessor 这个东西"。回顾一下前面的知识：

- **普通字段**（`field`）：`x = 10` —— 最简单的属性，直接存储值
- **手动 getter/setter**：`get x() { ... } set x(v) { ... }` —— 可以控制读写行为，但需要手动管理存储
- **accessor 字段**（`accessor x = 10`）—— 结合了两者的优势：既有自动的私有存储，又有可装饰的 getter/setter

accessor 的本质是一种**语法糖**。当你写下：

```javascript
class Example {
  accessor myValue = 42;
}
```

引擎实际上会把它展开成类似这样的代码：

```javascript
class Example {
  #myValue = 42;  // 私有后备槽，存放真实值

  get myValue() { return this.#myValue; }   // 自动生成的 getter
  set myValue(val) { this.#myValue = val; } // 自动生成的 setter
}
```

这意味着 accessor 天然拥有**封装性**（真实值存在私有字段中，外部无法直接访问）和**可拦截性**（getter/setter 可以被装饰器替换）。这正是 accessor 装饰器存在的意义。

### 基础用法：带验证的 accessor

```javascript
// 定义一个 accessor 装饰器，确保年龄值始终在合理范围内
function validateAge(value, context) {
  // value 是自动生成的 getter 函数
  // 我们需要同时替换 getter 和 setter 来实现完整的验证逻辑

  const MIN_AGE = 0;
  const MAX_AGE = 150;

  // 获取原始的 getter（用于读取真实值）
  const originalGetter = value;

  // 返回一个新的 getter
  return {
    get() {
      // 直接调用原始 getter 获取值
      return originalGetter.call(this);
    },
    set(newAge) {
      // 在设置之前进行验证
      if (typeof newAge !== 'number') {
        throw new TypeError(`${context.name} 必须是数字`);
      }
      if (!Number.isFinite(newAge)) {
        throw new RangeError(`${context.name} 不能是 Infinity`);
      }
      if (newAge < MIN_AGE || newAge > MAX_AGE) {
        throw new RangeError(
          `${context.name} 必须在 ${MIN_AGE} 到 ${MAX_AGE} 之间，收到: ${newAge}`
        );
      }
      // 通过原始 setter 存储值（这里利用了 accessor 的私有后备槽）
      // 注意：我们需要通过 context.access 来操作
    }
  };
}

class Person {
  @validateAge
  accessor age = 0;

  constructor(age) {
    this.age = age;  // 这里会触发 setter 验证
  }
}

let p1 = new Person(25);
console.log(p1.age);  // 25 ✅

let p2 = new Person(-5);   // 💥 RangeError: age 必须在 0 到 150 之间，收到: -5
let p3 = new Person(200);  // 💥 RangeError: age 必须在 0 到 150 之间，收到: 200
let p4 = new Person(NaN);  // 💥 TypeError: age 必须是数字
```

### 进阶用法：带变更通知的 accessor

在实际项目中，经常需要在某个属性的值发生变化时自动执行一些操作——比如更新 UI、同步到服务器、触发事件等。accessor 装饰器非常适合实现这类"响应式"的需求：

```javascript
// 定义一个 accessor 装饰器，在值变化时自动调用回调
function watchable(callback) {
  // 这是一个装饰器工厂（稍后会详细讲）
  // 返回实际的装饰器函数
  return function (value, context) {
    let lastValue = undefined; // 用于追踪上一个值
    let initialized = false;   // 是否已经初始化过

    return {
      get() {
        return value.call(this); // 调用原始 getter
      },
      set(newValue) {
        const oldValue = initialized ? value.call(this) : undefined;
        if (oldValue !== newValue) {
          // 调用回调函数，通知变化
          callback.call(this, {
            name: context.name,
            oldValue,
            newValue,
            target: this
          });
        }
        initialized = true;
        // 设置新值（通过原始 setter 语义）
      }
    };
  };
}

class ReactiveModel {
  @watchable(function (change) {
    console.log(
      `[Watch] 属性 "${change.name}" 发生变化:`,
      `${JSON.stringify(change.oldValue)} → ${JSON.stringify(change.newValue)}`
    );
  })
  accessor username = "guest";

  @watchable(function (change) {
    console.log(`[Watch] 分数更新为: ${change.newValue}`);
    // 可以在这里触发 UI 更新、发送网络请求等
  })
  accessor score = 0;
}

let model = new ReactiveModel();

model.username = "alarik";
// 输出: [Watch] 属性 "username" 发生变化: "guest" → "alarik"

model.score = 100;
// 输出: [Watch] 分数更新为: 100

model.username = "alarik"; // 值没变，不触发
model.score = 100;         // 值没变，不触发

model.score = 200;
// 输出: [Watch] 分数更新为: 200
```

这个 `@watchable` 装饰器展示了一个实用的响应式模式：每当被装饰的属性值发生变化时，自动执行传入的回调函数。回调函数接收变化的详细信息（属性名、旧值、新值、目标对象），可以根据这些信息做出相应的反应。这种模式在前端框架的数据绑定系统中非常常见——Vue 的 `reactive()`、MobX 的 `@observable` 等都在底层运用了类似的原理。

### 通俗类比：智能保险箱

accessor 装饰器的工作原理很像一个**带电子锁的智能保险箱**：

普通的字段就像一个**敞开的抽屉**——谁都可以随便放东西进去、拿出来（公开可读写的属性）。

手动写的 getter/setter 就像一把**普通锁**——你需要自己管理钥匙、自己决定什么时候开锁上锁（手动编写 getter/setter 逻辑）。

而 accessor 则像一个**智能保险箱**——它自带指纹识别系统（自动生成的 getter/setter）和一个隐藏的内部隔间（私有后备槽）。更重要的是，你可以在保险箱的锁具系统上安装**智能插件**（accessor 装饰器）：
- 安装**身份验证插件**：只有特定的人才能打开（值验证）
- 安装**操作记录插件**：每次开箱都会自动记录（变更通知）
- 安装**物品检测插件**：放入违禁品时自动报警（值过滤）

这些插件（装饰器）可以在不改变保险箱本身结构的前提下，为其添加各种各样的安全和管理功能。而且你可以针对同一款保险箱的不同格子安装不同的插件组合。

## 装饰器工厂（Decorator Factories）

### 为什么需要装饰器工厂？

到目前为止，我们见过的所有装饰器都是"无参数"的——你直接写 `@logMethod` 或 `@readonly`，不加括号，不传参数。但在实际开发中，你经常会遇到这种情况：**同一个装饰器在不同地方使用时需要有不同的行为**。

举个例子：假设你有一个 `@minLength` 装饰器用于验证字符串的最小长度。在用户名字段上你要求至少 2 个字符，在密码字段上要求至少 8 个字符，在地址字段上要求至少 10 个字符。如果每种长度都单独定义一个装饰器（`@minLength2`、`@minLength8`、`@minLength10`），那也太蠢了。

解决方案就是**装饰器工厂**——它不是一个装饰器，而是一个**返回装饰器的函数**。你可以把它理解为"装饰器的制造机器"——你喂给它参数，它吐出来一个定制化的装饰器。

### 基本语法与原理

```javascript
// 装饰器工厂的基本模式
function decoratorFactory(configParam1, configParam2) {
  // 这些参数是你使用时传入的配置
  // 比如 @factory(10, "hello") 中的 10 和 "hello"

  // 工厂函数返回一个真正的装饰器函数
  return function actualDecorator(value, context) {
    // 这里可以使用外层的 configParam1 和 configParam2
    // 因为闭包会捕获这些变量
    console.log("配置参数:", configParam1, configParam2);

    // 装饰器逻辑...
  };
}

// 使用时需要加括号（像函数调用一样）
@decoratorFactory(10, "hello")
class SomeClass { }
```

关键的理解点是：**`@decoratorFactory(10, "hello")` 这行代码会在类定义时立即执行**。执行的过程是：
1. 调用 `decoratorFactory(10, "hello")`
2. 工厂函数返回 `actualDecorator`
3. 引擎拿到 `actualDecorator`，把它当作装饰器来调用：`actualDecorator(classValue, classContext)`
4. 装饰器的逻辑开始执行

所以 `@decoratorFactory(10, "hello")` 本质上是两层函数调用，只不过第一层调用是由 `@` 语法触发的。

### 实战示例一：可配置的日志装饰器

```javascript
// 日志装饰器工厂 —— 可自定义日志前缀和是否显示耗时
function log(prefix = "[Log]", showTime = false) {
  // prefix 和 showTime 由外部传入
  return function (value, context) {
    // 只有方法才能被这个装饰器处理
    if (context.kind === "method") {
      return function (...args) {
        console.log(`${prefix} 调用 ${context.name}()`, showTime ? "" : `- 参数:`, args);

        const start = showTime ? performance.now() : 0;
        const result = value.apply(this, args);
        const end = showTime ? performance.now() : 0;

        if (showTime) {
          console.log(`${prefix} ${context.name}() 完成 - 耗时: ${(end - start).toFixed(2)}ms`);
        }
        return result;
      };
    }
    return value;
  };
}

class OrderService {
  @log("[订单]", true)
  createOrder(productId, quantity) {
    // 模拟数据库操作
    return { id: Date.now(), productId, quantity, total: productId * quantity * 99 };
  }

  @log("[查询]")
  getOrder(orderId) {
    return { id: orderId, status: "已完成" };
  }

  @log()  // 使用全部默认参数
  cancelOrder(orderId) {
    return { id: orderId, status: "已取消" };
  }
}

let service = new OrderService();
service.createOrder(1, 2);
// 输出:
// [订单] 调用 createOrder()
// [订单] createOrder() 完成 - 耗时: x.xxms

service.getOrder(12345);
// 输出:
// [查询] 调用 getOrder() - 参数: [12345]

service.cancelOrder(999);
// 输出:
// [Log] 调用 cancelOrder() - 参数: [999]
```

注意看三种不同的使用方式：
- `@log("[订单]", true)` —— 自定义前缀和开启耗时显示
- `@log("[查询]")` —— 自定义前缀，使用默认的关闭耗时
- `@log()` —— 全部使用默认值

同一段装饰器工厂代码，通过传入不同的参数就能适应不同的使用场景。这就是装饰器工厂的价值——**一份装饰器代码，无限种定制可能性**。

### 实战示例二：带条件的自动重试装饰器

在网络请求、文件 I/O 等可能失败的操作中，自动重试是非常常见的需求。我们可以用装饰器工厂来实现一个通用的重试机制：

```javascript
// 重试装饰器工厂
function retry(maxRetries = 3, delayMs = 1000, backoffMultiplier = 2) {
  return function (value, context) {
    if (context.kind !== 'method') {
      throw new Error('@retry 只能用于方法');
    }

    return async function (...args) {
      let lastError;

      for (let attempt = 1; attempt <= maxRetries; attempt++) {
        try {
          console.log(
            `[Retry] ${context.name}() 第 ${attempt}/${maxRetries} 次尝试`
          );
          return await value.apply(this, args);
        } catch (error) {
          lastError = error;
          console.warn(
            `[Retry] ${context.name}() 第 ${attempt} 次失败:`,
            error.message
          );

          if (attempt < maxRetries) {
            // 指数退避等待
            const waitTime = delayMs * Math.pow(backoffMultiplier, attempt - 1);
            console.log(`[Retry] 等待 ${waitTime}ms 后重试...`);
            await new Promise(resolve => setTimeout(resolve, waitTime));
          }
        }
      }

      // 所有重试都失败了，抛出最后一个错误
      throw lastError;
    };
  };
}

class ApiService {
  @retry(3, 500, 2)
  async fetchData(url) {
    // 模拟不稳定的网络请求
    if (Math.random() < 0.6) {
      throw new Error("网络连接超时");
    }
    return { url, data: "成功获取数据", timestamp: Date.now() };
  }
}

let api = new ApiService();
api.fetchData("https://api.example.com/data")
  .then(console.log)
  .catch(err => console.error("最终失败:", err.message));
// 可能的输出:
// [Retry] fetchData() 第 1/3 次尝试
// [Retry] fetchData() 第 1 次失败: 网络连接超时
// [Retry] 等待 500ms 后重试...
// [Retry] fetchData() 第 2/3 次尝试
// [Retry] fetchData() 第 2/3 次尝试 成功！✅
// { url: "...", data: "成功获取数据", timestamp: ... }
```

这个 `@retry` 装饰器工厂展示了几个高级特性：
- **异步支持**：返回的函数是 async 的，可以 await 异步方法
- **指数退避算法**：每次重试的等待时间是上次的 `backoffMultiplier` 倍，避免在服务端压力大时频繁冲击
- **详细的日志输出**：每次尝试的结果都会被记录，方便排查问题
- **可配置的重试次数、初始延迟、退避倍率**

最重要的是——被装饰的方法 `fetchData` 本身完全不关心重试的逻辑。它只需要做好自己的事（发起请求），重试的责任完全交给装饰器来承担。这种分离使得 `fetchData` 的代码更加干净、专注，而重试策略可以在任何需要的地方通过一行注解就应用上去。

### 实战示例三：权限控制的装饰器

在后台管理系统或 API 服务中，权限校验几乎是每个接口都要做的事。装饰器工厂可以让权限控制变得异常简洁：

```javascript
// 权限装饰器工厂
function requirePermission(...requiredPermissions) {
  return function (value, context) {
    if (context.kind !== 'method') {
      throw new Error('@requirePermission 只能用于方法');
    }

    return function (...args) {
      // 假设当前用户信息存储在实例上
      const currentUser = this.currentUser;

      if (!currentUser) {
        throw new Error("未登录，请先认证");
      }

      const userPermissions = currentUser.permissions || [];
      const hasAllPermissions = requiredPermissions.every(
        perm => userPermissions.includes(perm)
      );

      if (!hasAllPermissions) {
        const missing = requiredPermissions.filter(
          p => !userPermissions.includes(p)
        );
        throw new Error(
          `权限不足！缺少权限: [${missing.join(", ")}]。` +
          `当前用户权限: [${userPermissions.join(", ")}]`
        );
      }

      // 权限校验通过，执行原方法
      return value.apply(this, args);
    };
  };
}

class AdminPanel {
  currentUser = null;

  loginAs(user) {
    this.currentUser = user;
  }

  @requirePermission("user:read")
  viewUsers() {
    return ["张三", "李四", "王五"];
  }

  @requirePermission("user:write", "user:delete")
  deleteUser(userId) {
    return `用户 ${userId} 已删除`;
  }

  @requirePermission("system:admin")
  shutdownSystem() {
    return "系统即将关闭...";
  }
}

let panel = new AdminPanel();

// 以普通用户身份登录
panel.loginAs({
  name: "普通用户",
  permissions: ["user:read"]
});

panel.viewUsers();  // ✅ 有 user:read 权限
// panel.deleteUser(1);  // 💥 权限不足！缺少权限: [user:write, user:delete]
// panel.shutdownSystem(); // 💥 权限不足！缺少权限: [system:admin]

// 切换为超级管理员
panel.loginAs({
  name: "超级管理员",
  permissions: ["user:read", "user:write", "user:delete", "system:admin"]
});

panel.deleteUser(1);     // ✅ 权限充足
panel.shutdownSystem();   // ✅ 权限充足
```

这个 `@requirePermission` 装饰器展示了企业级应用中的一种常见模式。通过一行注解就能声明"执行这个方法需要哪些权限"，所有的权限校验逻辑都被封装在装饰器内部。方法本身只需要关心业务逻辑，完全不需要写 `if (hasPermission...)` 这样的样板代码。

### 通俗类比：调料瓶套装

装饰器工厂就像是厨房里的**调料瓶套装**：

基础版的 `@log` 装饰器就像一瓶**固定配方的调味料**——撒出来的味道永远是那样的，你不能调整咸淡。

而装饰器工厂 `@log(prefix, showTime)` 就像一个**可调节的调料研磨器**：
- 你可以调整粗细程度（prefix 参数——日志的前缀文字）
- 你可以调整用量大小（showTime 参数——是否显示额外信息）
- 不同的人可以根据自己的口味调节出不同的配方

同样的调料研磨器（同一个工厂函数），每个人拧出来的调料（返回的装饰器）都不一样，但底下的调料来源是相同的。这就是"工厂"的含义——**标准化生产 + 定制化输出**。

## 上下文对象（Context Object）详解

### context 对象的完整结构

在前面的所有示例中，我们都用到了 `context` 对象，但没有系统地介绍它。实际上，`context` 对象是理解装饰器如何工作的关键——它承载了被装饰元素的所有"环境信息"。无论是哪种类型的装饰器（类、方法、字段、accessor），`context` 都是一个具有以下结构的对象：

```javascript
// context 对象的完整结构
{
  kind: "class" | "method" | "getter" | "setter" | "field" | "accessor",
  name: string | undefined,
  access: {
    get: Function | undefined,
    set: Function | undefined,
    has: Function | undefined,
  } | undefined,
  isStatic: boolean,
  isPrivate: boolean,
  addInitializer(Function): void
}
```

让我们逐一深入理解每个属性的含义和用途。

### kind：标识装饰目标的类型

`context.kind` 是一个字符串，告诉你当前装饰的是什么类型的东西。这是装饰器内部进行条件判断的基础——因为不同类型的目标需要不同的处理逻辑：

```javascript
function universalDecorator(value, context) {
  switch (context.kind) {
    case "class":
      console.log("这是一个类装饰器，value 是构造函数");
      break;
    case "method":
      console.log("这是一个方法装饰器，value 是方法函数");
      break;
    case "getter":
      console.log("这是一个 getter 装饰器，value 是 getter 函数");
      break;
    case "setter":
      console.log("这是一个 setter 装饰器，value 是 setter 函数");
      break;
    case "field":
      console.log("这是一个字段装饰器，value 是初始值");
      break;
    case "accessor":
      console.log("这是一个 accessor 装饰器，value 是 getter 函数");
      break;
  }
  return value;
}

class Demo {
  @universalDecorator
  static staticField = 1;     // kind: field, isStatic: true

  @universalDecorator
  instanceField = 2;          // kind: field, isStatic: false

  @universalDecorator
  static staticMethod() {}    // kind: method, isStatic: true

  @universalDecorator
  instanceMethod() {}         // kind: method, isStatic: false

  @universalDecorator
  get computed() { return 0; } // kind: getter

  @universalDecorator
  accessor reactive = 0;      // kind: accessor
}
```

### name：被装饰元素的名称

`context.name` 是一个字符串（对于私有成员则为 `undefined`），表示被装饰的那个东西叫什么名字：

```javascript
function showName(value, context) {
  console.log(`装饰目标名称: ${context.name ?? "(私有成员)"}`);
  return value;
}

class Example {
  @showName
  firstName = "";     // "firstName"

  @showName
  lastName = "";      // "lastName"

  @showName
  #secretKey = "";    // undefined（私有成员没有公开名称）

  @showName
  calculateTotal() {} // "calculateTotal"
}
```

对于私有成员（以 `#` 开头），`name` 为 `undefined`。这是因为私有成员的名字在语言规范层面是不暴露的——它是一种"硬隐私"，外部代码无法通过名称来访问它。如果你需要在装饰器中区分不同的私有成员，可以通过其他手段（比如在定义时传入标识符）。

### isStatic 与 isPrivate：静态性和私有性标志

这两个布尔值分别表示被装饰的元素是否为**静态的**和**私有的**：

```javascript
function analyzeElement(value, context) {
  console.log({
    kind: context.kind,
    name: context.name,
    isStatic: context.isStatic ? "是（静态）" : "否（实例）",
    isPrivate: context.isPrivate ? "是（私有）" : "否（公有）"
  });
  return value;
}

class AnalysisDemo {
  @analyzeElement                    // isStatic: true,  isPrivate: false
  publicStaticField = 1;

  @analyzeElement                    // isStatic: false, isPrivate: false
  publicInstanceField = 2;

  @analyzeElement                    // isStatic: true,  isPrivate: true
  static #privateStaticField = 3;

  @analyzeElement                    // isStatic: false, isPrivate: true
  #privateInstanceField = 4;

  @analyzeElement                    // isStatic: true,  isPrivate: false
  static publicStaticMethod() {}

  @analyzeElement                    // isStatic: false, isPrivate: false
  publicInstanceMethod() {}
}
```

这两个标志在很多场景下非常重要。例如，你可能希望一个日志装饰器在静态方法和实例方法上有不同的输出格式（静态方法不显示 `this` 的信息）；或者一个验证装饰器对私有字段的校验规则与公有字段不同。

### access：对字段底层存储的访问接口

`context.access` 是一个可选的对象（只有在字段和 accessor 装饰器中才可用），它提供了对被装饰字段底层存储机制的访问能力。这个对象最多包含三个方法：

| 方法 | 说明 |
|------|------|
| `get()` | 读取字段的当前值 |
| `set(value)` | 设置字段的值 |
| `has()` | 检查字段是否存在 |

```javascript
// 利用 access 实现一个"双路绑定"的字段装饰器
function bindToStorage(storageKey) {
  return function (value, context) {
    return {
      get() {
        // 从 localStorage 读取（优先），如果没有则用内存值
        const stored = localStorage.getItem(storageKey);
        if (stored !== null) {
          try {
            return JSON.parse(stored);
          } catch {
            // 解析失败，使用内存值
          }
        }
        return context.access.get.call(this);
      },
      set(newValue) {
        // 同时写入内存和 localStorage
        context.access.set.call(this, newValue);
        localStorage.setItem(storageKey, JSON.stringify(newValue));
      }
    };
  };
}

class Settings {
  @bindToStorage("app-theme")
  accessor theme = "light";

  @bindToStorage("app-language")
  accessor language = "zh-CN";
}

let settings = new Settings();
console.log(settings.theme);     // "light"（默认值）

settings.theme = "dark";         // 写入 localStorage["app-theme"] = '"dark"'
// 刷新页面后...
let settings2 = new Settings();
console.log(settings2.theme);    // "dark"（从 localStorage 恢复）
```

这个 `@bindToStorage` 装饰器利用 `context.access.get` 和 `context.access.set` 实现了一个非常实用的功能：**字段值与 localStorage 自动双向同步**。每次读取字段时，优先从 localStorage 取值；每次写入字段时，同步保存到 localStorage。这样即使页面刷新，用户的设置也不会丢失。

### addInitializer：添加初始化钩子

`context.addInitializer` 是一个方法，允许你在装饰器中注册一个**初始化函数**。这个函数会在类被实例化之后（构造函数执行完毕之后）、但在实例被返回给调用方之前执行。它相当于给类的实例化流程插入了一个"后置钩子"。

```javascript
// 定义一个装饰器，用于自动绑定实例方法中的 this
function autobind(value, context) {
  if (context.kind === "method" && !context.isStatic) {
    // 注册一个初始化函数
    context.addInitializer(function () {
      // this 在这里是实例对象
      // 把方法绑定到实例上
      this[context.name] = value.bind(this);
    });
  }
  return value;
}

class Button {
  label = "点击我";

  constructor(label) {
    if (label) this.label = label;
  }

  @autobind
  onClick(event) {
    // 注意：这里的 this 应该指向 Button 实例
    console.log(`按钮 "${this.label}" 被点击了！`);
    console.log("事件对象:", event.type);
  }
}

let btn = new Button("提交");

// 将方法作为回调传递（this 可能丢失的场景）
const handler = btn.onClick;
// 由于 autobind 装饰器，handler 已经绑定了正确的 this
handler({ type: "click" });  // 即使脱离了 btn 对象也能正确工作
// 输出: 按钮 "提交" 被点击了！
// 输出: 事件对象: click
```

这个 `@autobind` 装饰器解决了一个经典的 JavaScript 问题：**方法作为回调函数传递时 `this` 丢失**。通常的做法是在构造函数中手动 `.bind(this)`，或者在调用时使用箭头函数。但有了 `@autobind` 装饰器，你只需要在方法上加一个注解，就能保证这个方法的 `this` 永远绑定到实例上。

`addInitializer` 的执行顺序规则如下：
- 所有装饰器中注册的初始化函数，按照**类中定义的顺序**依次执行
- 初始化函数在**父类构造函数（super）执行完毕后**、**子类构造函数剩余代码执行完毕后**执行
- 静态成员的初始化函数在类定义时执行（而非实例化时）
- 实例成员的初始化函数在 `new` 操作时执行

### 通俗类比：装修队的施工档案

如果把被装饰的元素比作一个房间，那么 `context` 对象就是装修队手中的**施工档案**：

- **kind**（房间类型）：这是卧室还是厨房？客厅还是卫生间？（决定了用什么材料、什么工艺）
- **name**（房间编号）：302 室还是 305 室？（用于标识和定位）
- **isStatic**（公共区域还是私人区域）：是走廊这种公用空间（static）还是业主的私人房间（instance）？
- **isPrivate**（是否保密房间）：是普通房间还是保险库（private field）？
- **access**（万能钥匙）：能够进入房间内部查看或修改设施的权限凭证
- **addInitializer**（完工验收单）：装修完成后需要执行的验收步骤（初始化钩子）

装修队（装饰器函数）拿到这份档案后，就能精确地知道自己在改造什么、怎么改造、有什么特殊的注意事项。没有这份档案，装修就只能盲目进行，很容易出问题。

## 多个装饰器的组合与执行顺序

### 组合多个装饰器

在实际开发中，同一个目标上经常需要同时应用多个装饰器。比如一个 API 方法可能既需要 `@log`（日志）、又需要 `@retry`（重试）、还需要 `@requirePermission`（权限校验）。ECMAScript 装饰器提案允许你在同一个目标上堆叠多个装饰器：

```javascript
class ApiService {
  // 多个装饰器从上到下排列
  @log("[API]", true)
  @retry(3, 1000)
  @requirePermission("api:access")
  async fetchUserData(userId) {
    // 业务逻辑：获取用户数据
    return { id: userId, name: "张三", role: "admin" };
  }
}
```

这里 `fetchUserData` 方法上同时使用了三个装饰器，它们形成了一条**装饰器链**。请求从最外层（`@log`）进入，逐层穿透到最内层（原始方法），然后结果再逐层返回。

### 执行顺序：定义时 vs 运行时

理解多装饰器的执行顺序是正确使用装饰器的前提。这里有**两个维度**的顺序需要区分：

**维度一：装饰器函数本身的执行顺序（定义阶段）**

当 JavaScript 引擎解析到一个带有多个装饰器的类成员时，装饰器函数的执行顺序是从**下往上**（从内到外）：

```javascript
function decoratorA(value, context) {
  console.log("A 执行（装饰器函数被调用）");
  return value;
}

function decoratorB(value, context) {
  console.log("B 执行（装饰器函数被调用）");
  return value;
}

function decoratorC(value, context) {
  console.log("C 执行（装饰器函数被调用）");
  return value;
}

class OrderTest {
  @decoratorA  // 第三执行
  @decoratorB  // 第二执行
  @decoratorC  // 第一执行
  someMethod() {
    console.log("方法执行");
  }
}
// 输出:
// C 执行（装饰器函数被调用）
// B 执行（装饰器函数被调用）
// A 执行（装饰器函数被调用）
```

这是因为装饰器是嵌套应用的——`@decoratorA` 包装的是 `@decoratorB` 包装的结果，而 `@decoratorB` 包装的是 `@decoratorC` 包装的结果。所以要先把最内层的 `decoratorC` 应用到原始方法上，得到一个中间结果；然后把 `decoratorB` 应用到这个中间结果上；最后才是 `decoratorA`。

**维度二：被装饰方法的实际调用顺序（运行阶段）**

虽然装饰器函数的定义执行是从下往上，但当方法被真正调用时，执行流却是从**最外层往下穿透**：

```javascript
function trace(name) {
  return function (value, context) {
    return function (...args) {
      console.log(`→ 进入 ${name}`);
      const result = value.apply(this, args);
      console.log(`← 退出 ${name}`);
      return result;
    };
  };
}

class TraceDemo {
  @trace("A")  // 最外层
  @trace("B")  // 中间层
  @trace("C")  // 最内层（紧贴原始方法）
  doWork(x) {
    console.log(`  doWork(${x}) 执行`);
    return x * 2;
  }
}

let demo = new TraceDemo();
demo.doWork(21);
// 输出:
// → 进入 A        ← 最外层先拦截
// → 进入 B        ← 第二层
// → 进入 C        ← 第三层（最内层）
//   doWork(21) 执行  ← 原始方法
// ← 退出 C
// ← 退出 B
// ← 退出 A
// 最终返回值: 42
```

这种"洋葱模型"（Onion Model）的执行顺序与 Express/Koa 等框架的中间件机制如出一辙。每个装饰器都像洋葱的一层皮，请求从外向内穿过，响应从内向外传出。

### 类成员之间的执行顺序

当一个类中有多个成员各自带有装饰器时，不同成员的装饰器之间按照**成员在类中出现的先后顺序**执行：

```javascript
function logMember(value, context) {
  console.log(`装饰器执行: ${context.kind} ${context.name ?? "(私有)"}`);
  return value;
}

class FullExample {
  @logMember  // ① 先执行（静态字段最先）
  static field1 = 1;

  @logMember  // ② 第二
  static method1() {}

  @logMember  // ③ 第三
  field2 = 2;

  @logMember  // ④ 第四（实例方法）
  method2() {}
}
// 输出:
// 装饰器执行: field1
// 装饰器执行: method1
// 装饰器执行: field2
// 装饰器执行: method2
```

执行规则总结：
1. **静态字段**的装饰器最先执行
2. **静态方法/访问器**的装饰器其次
3. **实例字段**的装饰器再次
4. **实例方法/访问器**的装饰器最后

这个顺序保证了在初始化实例字段时，静态成员已经完全准备好了。

### 通俗类比：俄罗斯套娃

多装饰器的执行顺序就像**俄罗斯套娃（Matryoshka Dolls）**：

**组装过程（定义阶段）**：你要把最大的娃（装饰器 A）放在最外面，中等大小的娃（装饰器 B）放在里面，最小的娃（装饰器 C）放在最中心。组装的顺序必须是**从最小的开始**——先把最小娃放进中等娃里，再把中等娃放进最大娃里。（对应装饰器函数从下往上执行）

**使用过程（运行阶段）**：当你想要拿出最小的娃（执行原始方法）时，必须**一层层打开**——先打开最大娃的外壳（装饰器 A 拦截），再打开中等娃的壳（装饰器 B 拦截），才能接触到最小的娃（原始方法执行）。拿完之后，再一层层套回去（返回值逐层向外传递）。

每一层外壳（装饰器）都可以在"打开"和"关闭"的时候做一些额外的事情（比如记录日志、验证参数、处理错误等），但它们都不会改变最里面那个娃娃的本质。

## 装饰器的实际应用场景汇总

### 场景一：单一职责原则的最佳实践

在软件工程中，**单一职责原则（Single Responsibility Principle, SRP）**要求一个类或方法只应该有一个引起它变化的原因。但在现实中，一个方法往往需要同时处理"本职工作"和一堆"杂活"——日志、鉴权、缓存、事务、监控……装饰器模式是践行 SRP 的绝佳工具：

```javascript
// 没有装饰器时：方法混杂了多种职责
class BadUserService {
  async updateUser(userId, data) {
    // ❌ 职责 1：日志记录
    console.log(`[LOG] updateUser called with userId=${userId}`);
    const start = Date.now();

    // ❌ 职责 2：权限校验
    const currentUser = getCurrentUser();
    if (!currentUser.canWrite('users')) {
      throw new Error('权限不足');
    }

    // ❌ 职责 3：参数验证
    if (!userId || typeof userId !== 'string') {
      throw new Error('userId 无效');
    }

    // ★ 唯一的真正职责：业务逻辑
    await db.users.update({ where: { id: userId }, data });

    // ❌ 职责 4：性能上报
    metrics.record('updateUser', Date.now() - start);
  }
}

// 使用装饰器后：每个职责独立封装，方法只关心业务逻辑
class GoodUserService {
  @log('[UserService]', true)
  @requirePermission('users:write')
  @validate({ userId: 'required|string', data: 'object' })
  @measurePerformance('updateUser')
  async updateUser(userId, data) {
    // ✅ 只有纯粹的業務邏輯！
    await db.users.update({ where: { id: userId }, data });
  }
}
```

对比两种写法，优劣一目了然。装饰器版本的业务方法只有 3 行代码，但拥有了日志、权限、验证、性能监控四项能力。每种能力都被封装在独立的装饰器中，可以自由组合、独立测试、单独维护。

### 场景二：框架与库中的装饰器应用

现代前端框架和 TypeScript 生态中，装饰器已经被广泛使用：

**Angular 框架**：Angular 从诞生之初就将装饰器作为核心语法。`@Component`、`@Injectable`、`@Input`、`@Output`、`@NgModule` 等都是类装饰器，它们为 Angular 的依赖注入系统和组件生命周期提供元数据支持。

**NestJS 框架**：Node.js 端的 NestJS 大量使用装饰器来声明路由、中间件、守卫、管道等。`@Controller('users')`、`@Get(':id')`、`@UseGuards(AuthGuard)`、`@Body()`、`@Query()` 让路由定义变得极其声明式和易读。

**TypeORM / Prisma**：ORM 库使用装饰器来定义实体类和字段映射。`@Entity()`、`@PrimaryGeneratedColumn()`、`@Column({ type: 'varchar', length: 255 })`、`@ManyToOne(() => User)` 让数据库模型的定义既类型安全又直观。

**TypeScript 的 emitDecoratorMetadata**：配合 `reflect-metadata` 库，装饰器可以在运行时获取类型的元信息，实现强大的依赖注入和反射能力。

### 场景三：与 TypeScript 类型系统的协同

虽然本文聚焦于 JavaScript 原生的 Stage 3 装饰器，但值得一提的是 TypeScript 5.0+ 已经完全支持这套标准。这意味着你可以在享受装饰器的运行时灵活性的同时，获得完整的静态类型检查和智能提示：

```typescript
import 'reflect-metadata';

// 类型安全的装饰器工厂
function Min(minValue: number) {
  return function (value: number, ctx: ClassFieldDecoratorContext): number {
    return function (this: unknown, newValue: number): void {
      if (newValue < minValue) {
        throw new RangeError(
          `${String(ctx.name)} 不能小于 ${minValue}，收到: ${newValue}`
        );
      }
    } as unknown as number;
  };
}

type Constructor<T = object> = new (...args: any[]) => T;

// 类型安全的类装饰器
function Singleton<T extends Constructor>(ctor: T) {
  let instance: InstanceType<T> | null = null;
  return class SingletonWrapper extends ctor {
    constructor(...args: any[]) {
      if (instance) return instance;
      super(...args);
      instance = this as InstanceType<T>;
    }
  } as T;
}

@Singleton
class DatabaseConnection {
  private connected = false;

  connect() { this.connected = true; return this; }
  disconnect() { this.connected = false; }
}

const db1 = new DatabaseConnection().connect();
const db2 = new DatabaseConnection().connect();
console.log(db1 === db2); // true —— 单例生效！
```

TypeScript 的类型推断系统能够正确识别装饰器的参数类型和返回类型，让装饰器的使用更加安全和可靠。

## 装饰器的局限性与注意事项

### 不能用于什么？

尽管装饰器功能强大，但它也有一些明确的限制：

**限制一：不能装饰函数**

目前的提案只支持装饰**类**和**类的成员**（方法、字段、访问器、accessor）。你不能用装饰器来修饰一个独立的普通函数：

```javascript
// ❌ 这样是不行的！
@logFunction
function standaloneFunction() { }

// ✅ 但可以把函数放到类里面
class Utils {
  @logMethod
  standaloneFunction() { }
}
```

这个限制的原因主要出于语法解析的复杂度考虑——如果允许装饰任意函数，会给引擎的解析器带来很大的歧义问题（比如箭头函数、函数表达式等的边界情况）。

**限制二：不能装饰对象的字面量属性**

同样，你也不能在普通对象上使用装饰器：

```javascript
// ❌ 不行
const obj = {
  @logProperty
  someProperty: 42
};

// ✅ 只能在类中使用
class MyClass {
  @logField
  someProperty = 42;
}
```

**限制三：装饰器的执行时机是固定的**

装饰器只在**类定义时**执行一次。你不能在运行时动态地添加或移除装饰器。如果你需要运行时的动态行为，应该结合 Proxy 或 Object.defineProperty 来实现。

### 性能考量

装饰器虽然带来了代码层面的优雅，但也有一定的运行时开销需要考虑：

1. **闭包开销**：每个装饰器返回的新函数都会形成闭包，捕获外部变量。大量使用装饰器会增加内存占用。
2. **调用栈深度**：多层装饰器嵌套会增加调用栈的深度，可能在极端情况下影响性能。
3. **启动时间**：如果类非常多且每个类都有复杂的装饰器，模块加载（类定义）阶段的初始化时间会变长。

不过，对于绝大多数 Web 应用和服务端应用来说，这些开销完全可以忽略不计。只有在性能极度敏感的场景（如游戏引擎的每帧循环、高频交易系统）下才需要特别关注。

### 调试技巧

由于装饰器会"隐藏"方法的原始实现，调试时可能会带来一些挑战。以下是一些实用建议：

1. **保留原始引用**：在装饰器中可以将原始方法保存在一个隐藏属性上，方便直接调用
2. **有意义的错误堆栈**：在装饰器包装的函数中抛出错误时，确保错误消息包含足够的上下文信息
3. **Source Map 支持**：确保构建工具正确生成 source map，以便在浏览器开发者工具中看到原始源码位置
4. **条件性地禁用装饰器**：在开发环境中可以提供一个开关来跳过某些装饰器

```javascript
// 可禁用的装饰器
const ENABLE_LOGGING = process.env.NODE_ENV !== 'test';

function conditionalLog(prefix) {
  if (!ENABLE_LOGGING) {
    // 如果日志未启用，返回一个"什么都不做"的装饰器
    return (value) => value;
  }
  return log(prefix);
}

class Service {
  @conditionalLog("[DevOnly]")
  sensitiveOperation() { /* ... */ }
}
```

## 总结：装饰器模式的核心价值

### 回顾全文的关键知识点

到这里，我们已经全面学习了 ECMAScript 装饰器提案（Stage 3）的所有核心内容。让我们做一个系统的回顾：

**关于装饰器本质**：装饰器是一种元编程（Metaprogramming）手段——它让你编写的代码可以操作其他代码。具体来说，装饰器是一个接收 `(value, context)` 两个参数的函数，通过 `@语法糖` 应用到类或类的成员上，在定义阶段对目标进行修改或替换。

**关于六种装饰目标**：
| 目标类型 | `context.kind` | `value` 的含义 | 典型用途 |
|---------|---------------|----------------|---------|
| 类 | `"class"` | 构造函数 | 添加元数据、密封/冻结、Proxy 包装 |
| 方法 | `"method"` | 方法函数 | 日志、权限、重试、性能监控 |
| Getter | `"getter"` | getter 函数 | 惰性计算、缓存 |
| Setter | `"setter"` | setter 函数 | 赋值验证、变更通知 |
| 字段 | `"field"` | 初始值 | 值转换、只读保护 |
| Accessor | `"accessor"` | getter 函数 | 完整的读写拦截 |

**关于装饰器工厂**：当需要让装饰器接受自定义参数时，使用工厂模式——返回装饰器的函数。这是实现可配置装饰器的标准方式。

**关于执行顺序**：装饰器函数在定义时从下往上执行，被装饰方法在运行时从外往里执行（洋葱模型）。

**关于 context 对象**：它提供了 kind、name、isStatic、isPrivate、access、addInitializer 六种元信息，是装饰器做出正确决策的信息基础。

### 装饰器的设计哲学

纵观装饰器模式的设计理念，可以发现它体现了几个重要的软件工程原则：

**开放-封闭原则（Open-Closed Principle）**：类和方法应该对扩展开放、对修改关闭。装饰器让你在不修改原有代码的前提下扩展其行为——完美契合这一原则。

**声明式编程（Declarative Programming）**：`@log @retry(3) async fetchData()` 这行代码告诉计算机"我要什么"（带日志和重试的数据获取），而不是"怎么做"（手写 try-catch 循环和 console.log）。声明式代码更加简洁、意图更加明确、更不容易出错。

**关注点分离（Separation of Concerns）**：业务逻辑（做什么）和横切逻辑（日志、验证、监控等怎么做）被彻底分开。每个装饰器只关注一件事，组合起来却能应对复杂的需求。

### 最后的建议

装饰器是一把锋利的工具。用好它，你的代码会变得更加优雅、可维护、富有表现力；滥用它，代码可能会变得难以追踪和调试。以下是一些实践建议：

- **保持装饰器简单**：每个装饰器只做一件事，做到名副其实
- **良好的命名**：装饰器的名字应该清楚表达它的功能，如 `@readonly`、`@debounce`、`@throttle`、`@memoize`
- **文档必不可少**：装饰器的参数、副作用、适用范围都应该有清晰的文档说明
- **不要过度装饰**：如果一个方法上有五六个装饰器堆叠，可能是时候考虑重构了
- **组合优于一个大而全的装饰器**：与其写一个 `@everything` 装饰器，不如用小的、专注的装饰器按需组合

> **装饰器的艺术不在于知道所有花哨的用法，而在于在最恰当的地方、以最简洁的方式，赋予代码恰到好处的能力。** 掌握了装饰器模式，你就掌握了 JavaScript 元编程的重要一环——它不仅是一种语法特性，更是一种"以声明式思维组织代码"的编程范式。
