# 装饰器的执行顺序、组合与实战应用

## 本文定位与阅读前提

ECMAScript Stage 3 装饰器提案的理论基础包括六种装饰目标（class/method/getter/setter/field/accessor）、context 对象的完整结构、装饰器工厂的原理等核心概念。如果你对这些基础知识还不熟悉，建议先打好基础再来阅读本文。

如果说基础理论是"教科书"——教你装饰器"是什么"和"为什么"，那么本文就是"实习手册"——带你动手解决真实项目中遇到的问题，包括：

1. **执行顺序的深度剖析**——不只是知道"从下往上定义、从外往里运行"，而是理解每一步的底层机制以及如何在复杂场景中正确编排多个装饰器
2. **四大实战场景的手把手实现**——日志系统、数据验证、this 绑定、性能监控与缓存，每个场景都从需求分析到最终实现
3. **装饰器与类结合的最佳实践**——如何在实际工程中优雅地组织装饰器代码、避免常见陷阱、处理继承和多态等进阶问题

本文假设你已经掌握了装饰器的基本语法。如果你对 `@` 语法、`(value, context)` 参数、`context.kind` 等概念还不熟悉，建议先阅读[《装饰器模式详解》](/frontend/javascript/language-async/decorator-pattern-stage3)一文。

## 执行顺序的深度剖析

### 为什么执行顺序如此重要？

在正式深入之前，我们需要先回答一个根本性的问题：**为什么要在意装饰器的执行顺序？**

答案在于：当你在同一个方法上叠加多个装饰器时，它们的执行顺序直接决定了程序的行为逻辑是否正确。一个最直观的例子是权限校验和日志的组合——你希望先记录"有人调用了这个方法"再进行权限检查，还是先检查权限通过后才记录调用？这两种顺序产生的效果截然不同：前者会记录所有调用（包括被拒绝的），后者只记录成功执行的调用。

如果搞错了顺序，你的日志系统可能会漏掉关键的失败记录；或者你的性能监控可能统计到了不该统计的数据；又或者你的重试机制在错误的地方触发，导致无限循环。

因此，准确理解和控制装饰器的执行顺序不是可有可无的知识点，而是写出可靠装饰器代码的必备技能。

### 定义阶段的执行顺序：从内到外的嵌套组装

让我们用一个精心设计的实验来彻底揭示定义阶段的行为。这次我们不只是打印简单的文字，而是追踪每个装饰器接收到的 `value` 到底是什么——这能帮你真正理解"嵌套组装"的含义：

```javascript
function traceDecorator(label) {
  return function (value, context) {
    console.log(
      `[定义阶段] ${label} 执行 | kind=${context.kind} name=${context.name} | ` +
      `value类型=${typeof value} ${value.name ? `(name=${value.name})` : ''}`
    );

    // 返回一个包装函数
    return function (...args) {
      console.log(`[运行阶段] → 进入 ${label}`);
      const result = value.apply(this, args);
      console.log(`[运行阶段] ← 退出 ${label}, 结果=`, result);
      return result;
    };
  };
}

class OrderSystem {
  @traceDecorator("A-日志")     // 最外层（第三执行）
  @traceDecorator("B-重试")     // 中间层（第二执行）
  @traceDecorator("C-鉴权")     // 最内层（第一执行）
  placeOrder(productId, quantity) {
    console.log("  ★ 原始方法执行：下单");
    return { id: Date.now(), productId, quantity };
  }
}
```

当你加载包含这段代码的模块时，控制台会输出以下内容（注意观察 value 的变化）：

```
[定义阶段] C-鉴权 执行 | kind=method name=placeOrder |
  value类型=function (name=placeOrder)
[定义阶段] B-重试 执行 | kind=method name=placeOrder |
  value类型=function (name=)        ← 注意：这里是匿名函数！C 的返回值
[定义阶段] A-日志 执行 | kind=method name=placeOrder |
  value类型=function (name=)        ← 同理：B 的返回值
```

这段输出揭示了三个关键事实：

**事实一：`C-鉴权` 最先执行**，此时它拿到的 `value` 是原始的 `placeOrder` 方法本身——它有名字（`name=placeOrder`），它是类体中定义的那个真正的函数。

**事实二：`B-重试` 第二个执行**，但它拿到的 `value` 不再是原始方法了，而是 `C-鉴权` 返回的那个匿名包装函数。也就是说，`B` 包装的是已经被 `C` 包装过的东西。

**事实三：`A-日志` 最后执行**，它拿到的 `value` 是 `B-重试` 返回的匿名函数——也就是包裹了"包裹了原始方法的 C 函数"的 B 函数。

这就像给一件衣服穿多层外套的过程：
1. 先把最里面的内衣（原始方法）穿上 —— C 先拿到原始方法
2. 在内衣外面套上毛衣（C 的包装）—— B 拿到的是"C 包装后的结果"
3. 在毛衣外面套上羽绒服（B 的包装）—— A 拿到的是"B 包装后的结果"
4. 最终别人看到的是穿着羽绒服的你（A 的包装结果作为方法的最终形态）

### 运行阶段的执行顺序：洋葱模型逐层穿透

定义完成后，当我们实际调用 `placeOrder()` 方法时，会发生什么呢？

```javascript
let os = new OrderSystem();
os.placeOrder("SKU-001", 5);
```

控制台输出：

```
[运行阶段] → 进入 A-日志          ← 最外层的 A 先拦截到请求
[运行阶段] → 进入 B-重试          ← A 调用内部的 value，进入 B
[运行阶段] → 进入 C-鉴权          ← B 调用内部的 value，进入 C
  ★ 原始方法执行：下单            ← C 调用内部的 value，终于到达原始方法
[运行阶段] ← 退出 C-鉴权, 结果= {id:..., ...}   ← 结果从原方法传回 C
[运行阶段] ← 退出 B-重试, 结果= {id:..., ...}   ← 从 C 传回 B
[运行阶段] ← 退出 A-日志, 结果= {id:..., ...}   ← 从 B 传回 A
// 最终返回值 = { id: ..., productId: "SKU-001", quantity: 5 }
```

这就是经典的**洋葱模型（Onion Model）**——请求从外层一层层向内穿透，到达最核心的原始方法后，结果再一层层向外传递回来。每一层都有机会在"进去的时候"和"出来的时候"做自己的事情。

为了更深刻地理解这个模型，让我们看看如果其中某一层"拦截"了请求（不继续往下传递）会发生什么：

```javascript
// 一个会在特定条件下中断链式调用的鉴权装饰器
function strictAuth(role) {
  return function (value, context) {
    return function (...args) {
      console.log(`[Auth] 检查权限... 需要: ${role}`);

      // 模拟：假设当前用户没有权限
      const currentUserRole = "guest";
      if (currentUserRole !== role) {
        console.log(`[Auth] ❌ 权限不足！当前角色: ${currentUserRole}`);
        // ⚠️ 注意这里：直接抛出错误，没有调用 value.apply(this, args)
        // 也就是说，请求不会继续穿透到更内层！
        throw new Error(`403 Forbidden: 需要 ${role} 权限`);
      }

      // 有权限才继续往下穿透
      return value.apply(this, args);
    };
  };
}

class SecureService {
  @traceDecorator("A-日志")
  @strictAuth("admin")
  deleteDatabase() {
    console.log("  💥 数据库已被删除！");
    return true;
  }
}

let svc = new SecureService();
svc.deleteDatabase();
```

输出结果：

```
[运行阶段] → 进入 A-日志
[Auth] 检查权限... 需要: admin
[Auth] ❌ 权限不足！当前角色: guest
// 抛出 Error: 403 Forbidden: 需要 admin 权限
```

注意看：**`deleteDatabase` 这个原始方法根本没有被执行**！因为 `strictAuth` 装饰器在中间就把请求截断了——就像洋葱剥到一半发现里面烂掉了，直接扔掉不再继续剥。这种"短路"行为在设计安全相关的装饰器时非常有用：一旦验证失败，立刻终止后续所有操作。

### 类成员之间的执行顺序

当一个类中有多个成员各自携带装饰器时，不同成员的装饰器之间也遵循严格的执行顺序。让我们做一个全面的实验：

```javascript
function mark(value, context) {
  const tag = `${context.isStatic ? '[静态]' : '[实例]'} ${
    context.kind.padEnd(10)
  } ${context.name ?? '(私有)'}`;
  console.log(`  👉 ${tag}`);
  return value;
}

class FullDemo {
  @mark                                    // ① 最先执行
  static staticField = '静态字段';

  @mark                                    // ② 第二执行
  static #privateStaticField = '私有静态字段';

  @mark                                    // ③ 第三执行
  static staticMethod() { return '静态方法'; }

  @mark                                    // ④ 第四执行
  instanceField = '实例字段';

  @mark                                    // ⑤ 第五执行
  #privateInstanceField = '私有实例字段';

  @mark                                    // ⑥ 第六执行
  instanceMethod() { return '实例方法'; }

  @mark                                    // ⑦ 第七执行
  get computedProp() { return '计算属性'; }

  @mark                                    // ⑧ 最后执行
  accessor reactiveField = 0;
}
```

执行输出：

```
  👉 [静态] field      staticField
  👉 [静态] field      (私有)           ← 私有静态字段
  👉 [静态] method     staticMethod
  👉 [实例] field      instanceField
  👉 [实例] field      (私有)           ← 私有实例字段
  👉 [实例] method     instanceMethod
  👉 [实例] getter     computedProp
  👉 [实例] accessor   reactiveField
```

从这个实验可以总结出完整的执行优先级规则：

**规则一：静态成员永远先于实例成员**。这是因为类的静态部分需要在任何实例存在之前就完全初始化完毕。你可以这样理解——静态成员属于"大楼的公共设施"（如走廊、电梯），而实例成员属于"每个房间内部的东西"。公共设施必须在大楼开放入住前就准备好。

**规则二：在同类型的成员之间，按照它们在源码中出现的从上到下的顺序依次执行**。`staticField` 在 `staticMethod` 上面，所以它的装饰器先执行。

**规则三：字段（field）的装饰器先于同级别的方法/访问器/accessor**。这是为了保证当方法被装饰时，同级别的字段已经完成初始化——方法可能会依赖这些字段的值。

### addInitializer 的执行时机

`context.addInitializer` 注册的回调函数有着自己独特的执行时机规则，这与普通装饰器函数本身的执行时机是完全不同的。让我们通过一个精确的实验来厘清：

```javascript
function trackInit(label) {
  return function (value, context) {
    console.log(`[装饰器] ${label} 执行`);

    if (!context.isStatic) {
      context.addInitializer(function () {
        console.log(`  [Initializer] ${label} 触发 | this 是实例?`, this instanceof TrackedClass);
      });
    } else {
      context.addInitializer(function () {
        console.log(`  [Static Initializer] ${label} 触发（类定义时立即执行）`);
      });
    }

    return value;
  };
}

class TrackedClass {
  @trackInit("字段A")
  fieldA = 100;

  @trackInit("方法X")
  methodX() {}

  constructor(initValue) {
    console.log("[Constructor] 构造函数执行");
    this.initValue = initValue;
  }
}

console.log("--- 开始 new ---");
let obj = new TrackedClass(42);
console.log("--- new 完成 ---");
```

输出结果：

```
[装饰器] 字段A 执行          ← 类定义时：字段A 的装饰器
[装饰器] 方法X 执行          ← 类定义时：方法X 的装饰器
  [Static Initializer] 方法X 触发（类定义时立即执行）  ← 静态 init 立即执行
--- 开始 new ---
[Constructor] 构造函数执行   ← 构造函数执行
  [Initializer] 字段A 触发 | this 是实例? true       ← 实例 init 在构造后执行
  [Initializer] 方法X 触发 | this 是实例? true       ← 实例 init 按声明顺序
--- new 完成 ---
```

这段输出揭示了几个至关重要的细节：

**细节一：静态成员的 addInitializer 在类定义时就立即同步执行**。你不需要 `new` 一个实例，只要类定义完成，静态初始化器就会被触发。这意味着你可以用它来做一些"类级别的一次性配置"工作。

**细节二：实例成员的 addInitializer 在构造函数执行完毕之后、实例返回给调用方之前执行**。注意看输出的顺序——`[Constructor]` 出现在两个 `[Initializer]` 之前。这说明初始化器相当于一个"构造后钩子（post-constructor hook）"。

**细节三：实例初始化器的执行顺序与成员声明的顺序一致**。`fieldA` 在 `methodX` 上面声明，所以它的初始化器先触发。

**细节四：在初始化器内部，`this` 已经正确指向新创建的实例**。你可以安全地使用 `this` 来访问或修改实例的状态。

### 继承中的装饰器执行顺序

当装饰器与类继承（`extends`）同时出现时，执行顺序变得更加有趣。子类的装饰器、父类的装饰器、构造函数、初始化器——这些元素之间的交互需要精确地理解：

```javascript
function label(name) {
  return function (value, context) {
    console.log(`  [Deco] ${name} (${context.kind}:${context.name ?? '-'})`);
    if (!context.isStatic && typeof context.addInitializer === 'function') {
      context.addInitializer(() => {
        console.log(`  [Init] ${name}`);
      });
    }
    return value;
  };
}

class Parent {
  @label('P-字段')
  parentField = '父类字段';

  @label('P-方法')
  parentMethod() {}
}

class Child extends Parent {
  @label('C-字段')
  childField = '子类字段';

  @label('C-方法')
  childMethod() {}

  constructor() {
    super();
    console.log('[Child Constructor] 子类构造函数');
  }
}
```

输出结果（按时间线排列）：

```
  [Deco] P-字段 (field:parentField)     ← 父类静态字段装饰器最先
  [Deco] P-方法 (method:parentMethod)   ← 父类静态方法装饰器
  [Deco] C-字段 (field:childField)      ← 子类静态字段装饰器
  [Deco] C-方法 (method:childMethod)    ← 子类静态方法装饰器
  -- 以上全部发生在 new Child() 之前 --

  [Init] P-字段                          ← super() 完成后，父类 init 先执行
  [Init] P-方法                          ← 父类 init 按声明顺序
  [Child Constructor] 子类构造函数       ← super() 返回后继续执行子类构造函数剩余部分
  [Init] C-字段                          ← 子类构造函数完成后，子类 init 执行
  [Init] C-方法                          ← 子类 init 按声明顺序
```

完整的执行时间线如下：

1. **类定义阶段**（不涉及 `new`）：先执行完父类所有成员的装饰器函数，再执行完子类所有成员的装饰器函数
2. **`new` 阶段——`super()` 内部**：父类构造函数执行 → 父类的 `addInitializer` 回调依次触发
3. **`new` 阶段——`super()` 之后**：子类构造函数剩余代码执行 → 子类的 `addInitializer` 回调依次触发

这个顺序的设计意图很明确：**父类的一切必须在子类之前完全就绪**。就像盖楼一样——地基必须打完才能建一楼，一楼封顶了才能建二楼。如果你想在子类的初始化器中使用父类初始化好的属性，这个顺序保证能让你做到这一点。

### 通俗类比：快递分拣中心的多道安检

装饰器的执行体系就像一个**现代化的快递分拣中心**，包裹（方法调用）要经过多道安检工序才能送达收件人：

**定义阶段（分拣中心的建立过程）**：
分拣中心在建站时，各个安检口按照从内到外的顺序安装设备。最靠近卸货区的安检门先装好（最内层装饰器），然后往外一层层装（中间层），最后装大门处的安检门（最外层）。这个安装顺序决定了包裹后续经过安检门的先后次序。

**运行阶段（包裹的分拣过程）**：
包裹到达后，首先经过大门安检（最外层装饰器 A）。检查通过后进入下一道安检（中间层装饰器 B），然后是最内侧的安检（最内层装饰器 C），最后送达目的地（原始方法）。返回的回执则沿相反的方向依次盖章确认。

**短路机制（问题包裹的处理）**：
如果在某道安检处发现问题（比如鉴权失败），包裹会被当场扣下，不会继续往后送。这就解释了为什么权限不足时，原始方法永远不会被执行。

**继承中的顺序（总仓与分仓的关系）**：
父类的安检流程就像总仓的标准安检流程，子类在此基础上增加了额外的安检步骤。包裹必须先通过总仓的所有安检，才能进入分仓的专属安检区域。

## 实战一：企业级日志装饰器

### 需求分析与设计思路

几乎每个非玩具项目都需要某种形式的日志系统。但很多项目的日志代码写得很糟糕——要么到处散落着 `console.log` 和 `console.error`，要么用一个简单的封装函数在每个方法里手动调用。这些做法的问题在于：

- **遗漏风险**：新增方法时容易忘记加日志
- **格式不一致**：张三写的日志格式是 `[INFO] method(args)`，李四写的是 `>> method called with: args`
- **难以统一管理**：想调整日志级别或输出目标时，需要改几十个地方
- **污染业务代码**：日志语句混在业务逻辑中，降低可读性

一个好的日志装饰器应该具备以下能力：
1. **自动捕获方法名、参数、返回值、异常、耗时**
2. **支持多种日志级别**（DEBUG/INFO/WARN/ERROR）
3. **允许自定义输出格式和目标**（控制台、远程服务器、文件等）
4. **不影响原有方法的正常工作**——包括返回值和 `this` 绑定
5. **性能友好**——不能让日志本身成为瓶颈

### 完整实现

```javascript
/**
 * 企业级日志装饰器工厂
 * @param {Object} options - 配置选项
 * @param {string} options.prefix - 日志前缀标签
 * @param {string} options.level - 默认日志级别: 'debug'|'info'|'warn'|'error'
 * @param {boolean} options.showArgs - 是否显示参数
 * @param {boolean} options.showResult - 是否显示返回值
 * @param {boolean} options.showDuration - 是否显示耗时
 * @param {boolean} options.showError - 是否显示错误堆栈
 * @param {Function} options.logger - 自定义日志输出函数
 */
function log(options = {}) {
  const {
    prefix = '',
    level = 'debug',
    showArgs = true,
    showResult = false,
    showDuration = true,
    showError = true,
    logger = console
  } = options;

  // 日志级别对应的输出方法
  const logMethods = {
    debug: logger.debug?.bind(logger) || logger.log.bind(logger),
    info: logger.info?.bind(logger) || logger.info.bind(logger),
    warn: logger.warn?.bind(logger) || logger.warn.bind(logger),
    error: logger.error?.bind(logger) || logger.error.bind(logger)
  };

  // 选择对应级别的输出方法
  const output = logMethods[level] || logMethods.debug;

  return function (value, context) {
    // 只处理方法和访问器（getter/setter）
    if (context.kind !== 'method' && context.kind !== 'getter') {
      return value;
    }

    const methodName = context.name ?? '(匿名)';
    // 构建带前缀的方法标识
    const tag = prefix ? `[${prefix}]` : '';

    return function (...args) {
      const timestamp = new Date().toISOString();
      const methodId = `${tag}${methodName}()`;

      // 输出调用信息
      output.call(logger, `${timestamp} ${methodId} 开始`);
      if (showArgs && args.length > 0) {
        output.call(logger, `${timestamp} ${methodId} 参数:`, ...args);
      }

      const startTime = performance.now();

      try {
        // 调用原始方法，保持 this 绑定
        const result = value.apply(this, args);

        const duration = performance.now() - startTime;

        // 处理异步结果（Promise）
        if (result instanceof Promise) {
          return result.then(
            (resolvedValue) => {
              const asyncDuration = performance.now() - startTime;
              if (showResult) {
                output.call(logger, `${timestamp} ${methodId} 已解析 ✅ (${asyncDuration.toFixed(2)}ms)`, resolvedValue);
              } else {
                output.call(logger, `${timestamp} ${methodId} 已解析 ✅ (${asyncDuration.toFixed(2)}ms)`);
              }
              return resolvedValue;
            },
            (error) => {
              const asyncDuration = performance.now() - startTime;
              output.call(logger, `${timestamp} ${methodId} 已拒绝 ❌ (${asyncDuration.toFixed(2)}ms):`, error.message);
              if (showError) output.call(logger, error.stack);
              throw error; // 重新抛出，不吞掉错误
            }
          );
        }

        // 同步结果
        if (showResult) {
          output.call(logger, `${timestamp} ${methodId} 完成 ✅ (${duration.toFixed(2)}ms):`, result);
        } else if (showDuration) {
          output.call(logger, `${timestamp} ${methodId} 完成 ✅ (${duration.toFixed(2)}ms)`);
        }

        return result;

      } catch (error) {
        const duration = performance.now() - startTime;
        output.call(logger, `${timestamp} ${methodId} 异常 ❌ (${duration.toFixed(2)}ms):`, error.message);
        if (showError && error.stack) {
          output.call(logger, error.stack);
        }
        throw error; // 必须重新抛出！否则调用方不知道出错了
      }
    };
  };
}
```

这个日志装饰器的完整程度已经可以用于生产环境。下面我们来逐一分析其中的关键设计决策。

### 设计决策解析

**决策一：使用工厂模式接受配置对象**

我们没有写死任何日志格式或输出方式，而是通过一个 `options` 对象让使用者自由定制。这意味着同一个 `log` 工厂可以在不同环境下产生不同的行为——开发环境输出详细日志到控制台，生产环境只输出 ERROR 级别到远程日志服务。这种灵活性是通过闭包实现的——每次调用 `log({...})` 都会创建一个新的作用域，捕获传入的配置参数，返回的装饰器函数在执行时会读取这些被捕获的变量。

**决策二：区分同步和异步方法**

这是一个经常被忽视的关键点。如果你的方法返回 Promise，而装饰器只做了同步的 try-catch，那么 Promise 的 rejection 不会被捕获到——它会变成一个 unhandled promise rejection，可能导致进程崩溃（Node.js 中）或者静默失败（浏览器中）。

我们的做法是检查 `result instanceof Promise`，如果是，就用 `.then()` 和 `.catch()` 来分别处理 resolve 和 reject 的情况。这样做的好处是无论方法是同步还是异步，日志行为都是一致的。需要注意的是，我们在 `.catch()` 中选择 `throw error` 重新抛出——确保调用方的 `.catch()` 或 `await` 能正常捕获到错误，而不是被装饰器"吃掉"。

**决策三：错误必须重新抛出**

你可能注意到代码中有两处 `throw error`——一处是同步 catch 块末尾，另一处是 Promise 的 `.catch()` 回调中。这两处都是绝对必要的。原因很简单：装饰器只是"旁观的记录者"，它不应该改变方法的正常错误传播路径。如果调用方写了 `try { await svc.doSomething() } catch(e) {...}` 来处理错误，而装饰器把错误吞掉了，那调用方的错误处理逻辑就会变成死代码。

**决策四：使用 `output.call(logger, ...)` 而非直接调用 `output(...)`**

这是一个微妙的细节。当我们做 `logger.info.bind(logger)` 时，得到的函数在被调用时 `this` 会指向 `logger` 对象本身。某些高级日志库（如 winston、pino）内部会通过 `this` 来获取额外的上下文信息（如日志器的名称、级别配置等）。如果我们直接调用 `output(message)` 而不绑 `this`，可能会导致这些库无法正常工作。

## 实战二：数据验证装饰器

### 为什么数据验证如此重要？

数据验证是应用程序防御的第一道防线。来自用户输入、API 请求、外部系统集成的数据永远是不可信的——即使前端做了校验，后端也必须独立验证，因为 HTTP 请求可以被伪造、API 可以被直接调用、数据库中的脏数据可能在某天突然冒出来。

传统的验证方式是在每个方法的开头手写一大堆 `if-else` 或者使用类似 Joi/Yup/Ajv 这样的验证库。但这会导致两种问题：一是验证逻辑和业务逻辑混杂在一起，方法变得很长很难读；二是同样的验证规则可能在多个地方重复编写。

装饰器为这个问题提供了一个优雅的方案：**将验证规则以声明式的方式附加到方法的参数上，让验证逻辑在方法执行之前自动运行**。

### 参数级验证装饰器

我们先来实现一组基础的参数验证装饰器，每个装饰器负责一种验证规则：

```javascript
// ====== 基础验证装饰器 ======

// 类型检查装饰器工厂
function typeCheck(expectedType) {
  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      // 检查第一个参数的类型
      const arg = args[0];
      const actualType = arg === null ? 'null' : typeof arg;

      if (actualType !== expectedType) {
        throw new TypeError(
          `[验证失败] ${context.name}() 的第 1 个参数期望类型 "${expectedType}"，` +
          `收到 "${actualType}"（值: ${JSON.stringify(arg)}）`
        );
      }

      return value.apply(this, args);
    };
  };
}

// 必填检查装饰器
function required(paramIndex = 0, paramName = '参数') {
  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      const arg = args[paramIndex];

      if (arg === undefined || arg === null || arg === '') {
        throw new Error(
          `[验证失败] ${context.name}() 的 "${paramName}" 不能为空` +
          `（收到: ${JSON.stringify(arg)}）`
        );
      }

      return value.apply(this, args);
    };
  };
}

// 范围检查装饰器工厂
function range(min, max, paramIndex = 0) {
  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      const arg = args[paramIndex];

      if (typeof arg === 'number' && (arg < min || arg > max)) {
        throw new RangeError(
          `[验证失败] ${context.name}() 的参数值 ${arg} 超出范围 [${min}, ${max}]`
        );
      }

      return value.apply(this, args);
    };
  };
}

// 字符串长度检查装饰器工厂
function minLength(minLen, paramIndex = 0) {
  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      const arg = args[paramIndex];

      if (typeof arg === 'string' && arg.length < minLen) {
        throw new RangeError(
          `[验证失败] ${context.name}() 的字符串参数长度 ${arg.length} 小于最小长度 ${minLen}`
        );
      }

      return value.apply(this, args);
    };
  };
}

// 正则匹配装饰器工厂
function pattern(regex, message, paramIndex = 0) {
  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      const arg = args[paramIndex];

      if (typeof arg === 'string' && !regex.test(arg)) {
        throw new Error(
          `[验证失败] ${context.name}(): ${message || `"${arg}" 不匹配模式 ${regex}"}`
        );
      }

      return value.apply(this, args);
    };
  };
}
```

### 使用示例

有了上面的基础装饰器，我们可以非常干净地定义带有完整验证规则的业务方法：

```javascript
class UserRegistrationService {

  @required(0, '用户名')
  @minLength(2)
  @pattern(/^[a-zA-Z\u4e00-\u9fa5]+$/, '用户名只能包含字母和中文')
  @typeCheck('string')
  createUser(username) {
    console.log(`✅ 创建用户: ${username}`);
    return { id: Date.now(), username, createdAt: new Date() };
  }

  @required(0, '年龄')
  @typeCheck('number')
  @range(0, 150)
  setAge(age) {
    console.log(`✅ 年龄设置为: ${age}`);
    return age;
  }

  @required(0, '邮箱')
  @pattern(/^[^\s@]+@[^\s@]+\.[^\s@]+$/, '请输入有效的邮箱地址')
  setEmail(email) {
    console.log(`✅ 邮箱设置为: ${email}`);
    return email;
  }
}

let regService = new UserRegistrationService();

// 合法调用
regService.createUser("张三");
regService.setAge(25);
regService.setEmail("zhangsan@example.com");

// 各种非法调用及其报错信息
regService.createUser("");     // Error: [验证失败] createUser() 的 "用户名" 不能为空
regService.createUser("A");    // Error: [验证失败] createUser() 的字符串参数长度 1 小于最小长度 2
regService.createUser("123");  // Error: [验证失败] createUser(): 用户名只能包含字母和中文
regService.setAge(-5);         // Error: [验证失败] setAge() 的参数值 -5 超出范围 [0, 150]
regService.setAge(200);        // Error: [验证失败] setAge() 的参数值 200 超出范围 [0, 150]
regService.setEmail("invalid");// Error: [验证失败] setEmail(): 请输入有效的邮箱地址
```

注意看 `createUser` 方法的定义——四个装饰器从上往下堆叠，形成了一条**验证链**。当方法被调用时，参数会依次经过这四道检查：先看是不是空值（`@required`）、再看够不够长（`@minLength`）、再看符不符合字符规范（`@pattern`）、最后确认类型对不对（`@typeCheck`）。任何一道没过，立刻抛出描述明确的错误信息，后续的检查不会执行。

这种写法带来的好处不仅是代码简洁。更重要的是**验证规则是自文档化的**——任何人看到方法签名上方的那几行 `@` 注解，就能立刻知道这个方法期望什么样的输入。这比写在注释里的"参数说明"可靠一万倍，因为注解是**强制执行的**，而注释只是建议。

### 进阶：基于 Schema 的综合验证

单个参数的单项验证虽然实用，但在实际业务中，我们更多面对的是"一个方法接收一个对象参数，对象的每个属性都需要不同的验证规则"。为此，我们需要一个基于 Schema 的综合验证装饰器：

```javascript
/**
 * 基于 Schema 的对象验证装饰器工厂
 * @param {Object} schema - 验证规则映射
 * @param {number} paramIndex - 要验证的参数位置（默认为 0）
 *
 * Schema 支持的规则:
 *   { type: 'string'|'number'|'boolean'|'object'|'array' }  - 类型检查
 *   { required: true }                                          - 必填
 *   { min: number, max: number }                                - 数值范围 / 字符串长度 / 数组长度
 *   { pattern: RegExp }                                         - 正则匹配
 *   { enum: Array }                                             - 枚举值
 *   { custom: Function }                                        - 自定义验证函数
 */
function validate(schema, paramIndex = 0) {
  return function (value, context) {
    if (context-kind !== 'method') return value;

    return function (...args) {
      const data = args[paramIndex];

      // 如果数据不是对象（或为 null），直接拒绝
      if (typeof data !== 'object' || data === null || Array.isArray(data)) {
        throw new TypeError(
          `${context.name}() 的第 ${paramIndex + 1} 个参数必须是对象`
        );
      }

      const errors = [];

      // 遍历 schema 中的每条规则
      for (const [fieldName, rules] of Object.entries(schema)) {
        const fieldValue = data[fieldName];

        // required 检查
        if (rules.required && (fieldValue === undefined || fieldValue === null)) {
          errors.push(`"${fieldName}" 是必填字段`);
          continue; // 其他检查没有意义了，跳过
        }

        // 如果字段不存在且不是必填，跳过
        if (fieldValue === undefined) continue;

        // type 检查
        if (rules.type) {
          let actualType = typeof fieldValue;
          if (Array.isArray(fieldValue)) actualType = 'array';
          if (fieldValue === null) actualType = 'null';
          if (actualType !== rules.type) {
            errors.push(`"${fieldName}" 类型应为 ${rules.type}，收到 ${actualType}`);
          }
        }

        // min/max 检查
        if (rules.min !== undefined) {
          const len = typeof fieldValue === 'string'
            ? fieldValue.length
            : Array.isArray(fieldValue)
              ? fieldValue.length
              : fieldValue;

          if (typeof len === 'number' && len < rules.min) {
            errors.push(`"${fieldName}" 的值/长度不能小于 ${rules.min}（当前: ${len}）`);
          }
        }

        if (rules.max !== undefined) {
          const len = typeof fieldValue === 'string'
            ? fieldValue.length
            : Array.isArray(fieldValue)
              ? fieldValue.length
              : fieldValue;

          if (typeof len === 'number' && len > rules.max) {
            errors.push(`"${fieldName}" 的值/长度不能超过 ${rules.max}（当前: ${len}）`);
          }
        }

        // pattern 检查
        if (rules.pattern instanceof RegExp && typeof fieldValue === 'string') {
          if (!rules.pattern.test(fieldValue)) {
            errors.push(`"${fieldName}" 不匹配模式 ${rules.pattern}`);
          }
        }

        // enum 检查
        if (Array.isArray(rules.enum) && !rules.enum.includes(fieldValue)) {
          errors.push(`"${fieldName}" 的值必须是 [${rules.enum.join(', ')}] 之一（当前: ${fieldValue}）`);
        }

        // custom 自定义检查
        if (typeof rules.custom === 'function') {
          const customResult = rules.custom(fieldValue, fieldName, data);
          if (customResult !== true) {
            errors.push(`"${fieldName}": ${customResult || '自定义验证失败'}`);
          }
        }
      }

      // 如果有错误，一次性抛出
      if (errors.length > 0) {
        throw new Error(
          `[验证失败] ${context.name}() 参数校验未通过:\n  - ${errors.join('\n  - ')}`
        );
      }

      // 全部通过，执行原始方法
      return value.apply(this, args);
    };
  };
}
```

## 实战三：this 自动绑定装饰器

### 问题背景：JavaScript 中 this 丢失的经典陷阱

`this` 绑定丢失可能是 JavaScript 中最高频的坑之一。它的典型场景是这样的：你有一个类，里面有一个方法，你需要把这个方法作为回调函数传给某个 API（比如事件监听器、定时器、Promise.then 等）。你以为传过去的方法会记住它所属的对象，但实际上——它忘了。

```javascript
class Timer {
  seconds = 0;

  start() {
    // 把 tick 方法作为 setInterval 的回调
    // 💥 这里 this 会丢失！
    setInterval(this.tick, 1000);
  }

  tick() {
    this.seconds++;
    console.log(`已计时 ${this.seconds} 秒`);
  }
}

let timer = new Timer();
timer.start();
// 1秒后:
// TypeError: Cannot read properties of undefined (reading 'seconds')
// 因为 setInterval 调用 tick 时，this 指向的是全局对象（严格模式下是 undefined）
```

为什么会这样？因为 `this.tick` 只是提取了方法的引用——一个纯粹的函数对象。当 `setInterval` 在 1 秒后调用这个函数时，没有任何机制告诉它"这个函数属于 timer 实例"。所以 `this` 就变成了默认值（取决于严格模式）。

传统的解决方案有三种，每种都有自己的缺点：

**方案一：箭头函数包装**

```javascript
start() {
  setInterval(() => this.tick(), 1000);  // 箭头函数保留外层 this
}
```

缺点：每次调用 `start()` 都会创建一个新的箭头函数对象（轻微内存开销），且写法稍显啰嗦。

**方案二：构造函数中 bind**

```javascript
constructor() {
  this.tick = this.tick.bind(this);
}
```

缺点：需要在每个需要绑定的方法都在构造函数中手动写一行 bind。方法多了以后构造函数会很臃肿，而且容易漏掉。

**方案三：使用箭头函数类属性**

```javascript
tick = () => {   // 箭头函数形式的类字段
  this.seconds++;
};
```

缺点：每个实例都会有自己的一份 tick 函数副本（不像原型方法那样共享），如果创建大量实例会有内存开销。而且这种方式不支持继承中的 `super` 调用。

### autobind 装饰器的完整实现

装饰器为我们提供了第四种、也是最优雅的解决方案——通过 `addInitializer` 在实例化时自动完成绑定：

```javascript
/**
 * this 自动绑定装饰器
 *
 * 将被装饰的方法永久绑定到其实例上，
 * 使得该方法可以作为回调函数安全地传递而不丢失 this。
 *
 * 特点：
 * - 只在实例化时绑定一次（不是每次调用都绑定）
 * - 不修改原始的原型方法（其他实例不受影响）
 * - 支持继承（子类覆盖方法后仍正确工作）
 */
function autobind(value, context) {
  // 只处理非静态方法
  if (context.kind !== 'method' || context.isStatic) {
    return value;
  }

  // 注册一个初始化回调
  context.addInitializer(function () {
    // 这里的 this 指向新创建的实例
    // 将方法绑定后赋值给实例的同名属性
    // 这样会"遮蔽"原型上的同名方法
    this[context.name] = value.bind(this);
  });

  // 返回原始方法不变（原型上的版本保持原样，
  // 但通过实例访问时会被绑定版遮蔽）
  return value;
}
```

这段精简的代码背后有几个值得深究的技术要点：

**要点一：利用实例属性的遮蔽效应**

当你在实例上设置了一个与原型方法同名的属性 `this.methodName = boundVersion` 时，JavaScript 引擎查找 `instance.methodName` 会先找到实例自身的属性，而不会继续往原型链上找。这是一种标准的"遮蔽（Shadowing）"机制。我们的装饰器正是利用了这个特性——原型上的原始方法保持不动（供继承等其他用途），实例上放一个绑定了 `this` 的版本供日常调用。

**要点二：bind 只执行一次**

`context.addInitializer` 中的回调只在 `new` 操作时执行一次。这意味着无论后续调用多少次方法，bind 操作不会重复发生。相比之下，箭头函数包装方案虽然也能正确绑定 `this`，但如果外层函数被多次调用（比如在循环中注册多个事件监听器），每次都会创建新的箭头函数。

**要点三：不影响原型和其他实例**

因为我们只是在"当前实例"上设置了绑定版本，原型方法没有被修改，其他实例也不受影响。每个实例有自己独立的绑定版本，互不干扰。

### 与继承的交互

`@autobind` 装饰器在继承体系中也能正确工作。来看一个稍微复杂的例子：

```javascript
class Animal {
  name = '无名动物';

  @autobind
  speak() {
    return `${this.name} 发出了声音`;
  }
}

class Dog extends Animal {
  breed = '未知品种';

  // 重写 speak 方法，也有 autobind
  @autobind
  speak() {
    // 调用父类方法 —— super 在这里仍然可用
    const baseSound = super.speak();  // ✅ 正常工作
    return `${baseSound}（${this.breed}汪汪叫！）`;
  }

  @autobind
  fetchStick() {
    return `${this.name} 去捡树枝了`;
  }
}

let dog = new Dog();
dog.name = '旺财';
dog.breed = '柯基';

// 将方法传出 —— this 绑定完好

const fetchFn = dog.fetchStick;

console.log(speakFn());
// "旺财 发出了声音（柯基汪汪叫！）"  ✅ this 正确，super 也正确

// "旺财 去捡树枝了"  ✅ this 正确

// 验证原型链未被破坏
console.log(dog instanceof Dog);      // true
console.log(dog instanceof Animal);   // true
console.log(dog.__proto__.speak === Dog.prototype.speak);  // true（原型方法完好）
```

这个例子展示了 `@autobind` 与继承体系的和谐共存。子类 `Dog` 重写了 `speak` 方法并加上自己的 `@autobind`，它既能正确绑定子类实例的 `this`，又能通过 `super.speak()` 调用父类的实现。原型链结构也没有被破坏——`Dog.prototype.speak` 仍然是原来的方法（未绑定版本），只是每个实例上有一个绑定后的版本遮蔽了它。

### 通俗类比：名片夹 vs 当面介绍

`this` 绑定的问题可以用社交场合的一个类比来理解：

想象你在一场大型会议上代表你们公司（实例）去做产品介绍（方法）。有三种自我介绍的方式：

**方式一：直接报名字（传原始方法引用）**
你走上台说："大家好，我是产品经理。"但没有说你是哪家公司的。台下的人听完一头雾水——"哪个公司的产品经理？"（`this` 丢失了上下文）

**方式二：每次都说全称（箭头函数包装）**
每次上台你都完整地说："大家好，我是某某科技有限公司的产品经理。"准确，但你每次都得重复一遍公司名称。（每次创建新的闭包）

**方式三：提前印好名片（autobind 装饰器）**
你提前把自己的姓名、职位、公司名称印在名片上。上台时只需递出名片，对方一眼就知道你是谁、来自哪里、做什么的。名片只需印一次，但可以在任意场合使用。（一次绑定，随处可用）

`@autobind` 就是帮你在实例化时自动"印制名片"的工具。有了它，你的方法无论被传递到哪里，都能清楚地表明"我属于谁"。

## 实战四：性能监控与缓存装饰器

### 性能监控装饰器

在生产环境中，了解每个关键方法的执行性能至关重要——哪些接口响应慢？哪些计算是性能热点？哪些地方出现了退化？一个性能监控装饰器可以帮助你自动收集这些数据：

```javascript
/**
 * 性能监控装饰器工厂
 *
 * 收集方法的调用次数、平均耗时、最大/最小耗时、成功率等指标。
 *
 * @param {string} metricName - 指标名称（用于上报标识）
 * @param {Object} options - 可选配置
 * @param {number} options.sampleRate - 采样率 (0~1)，1 表示全部采集
 * @param {number} options.slowThreshold - 慢调用阈值(ms)，超出则额外标记
 * @param {Function} options.reporter - 自定义上报函数
 */
function measure(metricName, options = {}) {
  const {
    sampleRate = 1,
    slowThreshold = 1000,
    reporter = defaultReporter
  } = options;

  // 指标收集器（存储在闭包中，跨实例共享）
  const metrics = {
    callCount: 0,
    totalDuration: 0,
    maxDuration: 0,
    minDuration: Infinity,
    errorCount: 0,
    slowCount: 0
  };

  // 默认上报函数
  function defaultReporter(data) {
    console.log(`[Metrics] ${data.metric}:`, {
      调用次数: data.callCount,
      平均耗时: `${(data.totalDuration / Math.max(1, data.callCount)).toFixed(2)}ms`,
      最大耗时: `${data.maxDuration.toFixed(2)}ms`,
      最小耗时: `${data.minDuration === Infinity ? 'N/A' : data.minDuration.toFixed(2)}ms`,
      错误率: `${((data.errorCount / Math.max(1, data.callCount)) * 100).toFixed(1)}%`,
      慢调用占比: `${((data.slowCount / Math.max(1, data.callCount)) * 100).toFixed(1)}%`
    });
  }

  // 定期上报（可选）
  const reportInterval = setInterval(() => reporter({ metric: metricName, ...metrics }), 30000);

  return function (value, context) {
    if (context.kind !== 'method') return value;

    return function (...args) {
      // 采样控制
      if (Math.random() > sampleRate) {
        return value.apply(this, args);
      }

      const start = performance.now();
      metrics.callCount++;

      try {
        const result = value.apply(this, args);

        // 处理异步结果
        if (result instanceof Promise) {
          return result.then(
            (resolvedValue) => {
              recordDuration(performance.now() - start);
              return resolvedValue;
            },
            (err) => {
              metrics.errorCount++;
              recordDuration(performance.now() - start);
              throw err;
            }
          );
        }

        // 同步结果
        recordDuration(performance.now() - start);
        return result;

      } catch (error) {
        metrics.errorCount++;
        recordDuration(performance.now() - start);
        throw error;
      }
    };

    function recordDuration(duration) {
      metrics.totalDuration += duration;
      if (duration > metrics.maxDuration) metrics.maxDuration = duration;
      if (duration < metrics.minDuration) metrics.minDuration = duration;
      if (duration > slowThreshold) {
        metrics.slowCount++;
        console.warn(
          `[Slow] ${metricName}/${context.name}() 耗时 ${duration.toFixed(2)}ms ` +
          `(阈值: ${slowThreshold}ms)`
        );
      }
    }
  };
}
```

### 缓存装饰器（Memoization）

对于纯函数（相同的输入总是产生相同的输出，无副作用），我们可以用缓存装饰器来避免重复计算。这是最常见的性能优化手段之一：

```javascript
/**
 * 缓存（记忆化）装饰器工厂
 *
 * 自动缓存方法的返回值。当相同参数再次传入时，
 * 直接返回缓存的结果，跳过实际的计算过程。
 *
 * 支持功能:
 * - 基于参数序列化的缓存键生成
 * - 可配置的最大缓存条目数（LRU 策略的简化版）
 * - 缓存命中率统计
 * - 手动清除缓存的接口
 *
 * @param {Object} options - 配置选项
 * @param {number} options.maxSize - 最大缓存数量（默认 100）
 * @param {number} options.ttl - 缓存过期时间毫秒数（默认不过期）
 * @param {Function} options.keyGen - 自定义缓存键生成函数
 */
function memoize(options = {}) {
  const {
    maxSize = 100,
    ttl = 0,  // 0 = 不过期
    keyGen = null
  } = options;

  // 缓存容器（闭包中共享）
  const cache = new Map();

  // 统计信息
  const stats = { hits: 0, misses: 0 };

  return function (value, context) {
    if (context.kind !== 'method' && context.kind !== 'getter') {
      return value;
    }

    return function (...args) {
      // 生成缓存键
      const cacheKey = keyGen
        ? keyGen(args, this)
        : JSON.stringify(args);

      // 查找缓存
      const cached = cache.get(cacheKey);

      if (cached) {
        // TTL 过期检查
        if (ttl > 0 && (Date.now() - cached.timestamp) > ttl) {
          cache.delete(cacheKey);
          stats.misses++;
        } else {
          stats.hits++;
          // LRU：删除后重新插入（移到最后）
          cache.delete(cacheKey);
          cache.set(cacheKey, cached);
          return cached.value;
        }
      }

      stats.misses++;

      // 执行实际方法
      const result = value.apply(this, args);

      // 存入缓存
      if (cache.size >= maxSize) {
        // 淘汰最早的条目（Map 保持插入顺序，keys().next().value 就是最早的）
        const oldestKey = cache.keys().next().value;
        cache.delete(oldestKey);
      }

      cache.set(cacheKey, {
        value: result,
        timestamp: Date.now()
      });

      return result;
    };
  };

  // 暴露辅助方法（可通过装饰器函数的属性访问）
  memoize.clearCache = function () { cache.clear(); };
  memoize.getStats = function () ({ ...stats, size: cache.size });
  memoize.getCache = function () => new Map(cache);
}
```

### 两种装饰器的协同使用

在实际项目中，性能监控和缓存经常会配合使用——你既想知道方法被调用了多少次、缓存命中率如何，也想享受缓存带来的速度提升。由于装饰器可以自由组合，这两个能力可以同时应用到同一个方法上：

```javascript
class HeavyComputationService {

  @measure('fib-calc', { slowThreshold: 100 })  // 外层：监控
  @memoize({ maxSize: 500 })                      // 内层：缓存
  computeHeavy(params) {
    // 非常重的计算...
    let result = 0;
    for (let i = 0; i < params.iterations; i++) {
      for (let j = 0; j < params.innerLoop; j++) {
        result += Math.sin(i) * Math.cos(j);
      }
    }
    return result;
  }
}
```

注意这里的装饰器顺序：`@measure` 在外层，`@memoize` 在内层。这意味着：
- 第一次调用（缓存未命中）：measure 记录到一次调用 → memoize 发现没有缓存 → 执行原始方法 → 缓存结果 → measure 记录耗时
- 第二次调用相同参数（缓存命中）：measure 记录到一次调用 → memoize 直接返回缓存 → measure 记录到一个很短的耗时

这样你就能在监控数据中清晰地看到缓存的效果——命中的调用耗时接近 0ms，未命中的调用才有真实的计算耗时。

### 通俗类比：高速公路收费站与快速通道

性能监控装饰器和缓存装饰器的关系很像**高速公路管理系统**：

**性能监控装饰器（`@measure`）就像高速公路上的**流量监测站**：
每辆车（方法调用）经过时，监测站自动记录车牌号（调用来源）、通行时间（耗时）、是否超速（是否超过慢阈值）、是否有事故（异常情况）。每隔一段时间，监测站会把统计数据上报给交通管理中心，帮助管理者了解路况。

**缓存装饰器（`@memoize`）就像高速上的**ETC 快速通道**：
如果你去过同一个目的地（相同参数），系统会认出你并直接抬杆放行，不需要再次停车缴费（重复计算）。快速通道有一定的容量限制（maxSize），满了之后最早进入的车会被清理出去。如果距离上次通行太久（TTL 过期），也需要重新缴费。

两者配合使用的体验就是：**监测站设在 ETC 通道入口**。每次车辆到来时，先记录一笔（monitor），然后判断是否能走 ETC（memoize hit/miss）。管理者可以通过监测站的报表看出有多少车走了 ETC（缓存命中率）、ETC 通道节省了多少时间（性能提升）。

## 装饰器与类结合的最佳实践

### 实践一：将装饰器集中管理

随着项目规模的增长，你可能会定义越来越多的装饰器。如果不加以组织，它们会散落在各个文件中，难以查找和复用。推荐的实践是将装饰器集中放在独立的模块中：

```javascript
// ===== decorators/index.js =====

// 日志相关
export { log } from './log.js';
export { measure } from './measure.js';

// 验证相关
export { required, typeCheck, range, minLength, pattern, validate } from './validation.js';

// 行为增强
export { autobind } from './autobind.js';
export { memoize } from './memoize.js';
export { retry } from './retry.js';
export { debounce, throttle } from './timing.js';

// 安全相关
export { requirePermission } from './auth.js';
export { rateLimit } from './rate-limit.js';

// 类级别
export { singleton } from './singleton.js';
export { sealed } from './sealed.js';
export { readonly } from './readonly.js';
```

然后在业务代码中统一导入使用：

```javascript
import {
  log,
  validate,
  autobind,
  measure,
  requirePermission,
  retry
} from '@/decorators';

class UserController {
  @log({ prefix: 'UserAPI' }, true)
  @measure('user-create')
  @requirePermission('user:create')
  @validate({ name: { type: 'string', required: true, min: 2 }, email: { type: 'string', required: true, pattern: EMAIL_REGEX } })
  async createUser(userData) {
    return await db.users.insert(userData);
  }
}
```

这种组织方式的好处显而易见：
- **单一来源**：所有装饰器在一个地方维护，修改影响全局一致
- **语义化导入**：通过命名导入清楚表明使用了哪些装饰器
- **便于团队协作**：新人可以通过浏览 `decorators/` 目录快速了解项目有哪些通用能力

### 实践二：装饰器的命名约定

良好的命名能让代码即文档。以下是推荐的装饰器命名约定：

| 命名风格 | 适用场景 | 示例 |
|---------|---------|------|
| **动词/动名词** | 改变行为或添加能力的装饰器 | `@autobind`、`@readonly`、`@sealed` |
| **名词** | 标记或分类性质的装饰器 | `@entity`、`@singleton`、`@deprecated` |
| **动词 + able/ible** | 表示"可以做某事"的能力 | `@memoizable`、`@observable`、`@serializable` |
| **形容词** | 描述状态的装饰器 | `@pure`、`@immutable`、`@async` |

避免使用过于简短或含义模糊的名字：
- ~~`@x`~~ → 应为 `@debounce` 或至少 `@delay`
- ~~`@check`~~ → 应为 `@validate` 或 `@require`
- ~~`@do`~~ → 应为具体的功能名

### 实践三：处理装饰器与 TypeScript 的协作

如果你的项目使用 TypeScript，有几个注意事项需要了解：

```typescript
import 'reflect-metadata';

/**
 * 类型安全的参数验证装饰器
 * 使用 TypeScript 的类型系统确保只能在方法上使用
 */
function TypedValidate<T extends object>(
  schema: Record<keyof T, ValidationRule>
): MethodDecorator {
  return function (value: Function, context: ClassMethodDecoratorContext<T>) {
    // TypeScript 5.0+ 提供了强类型的装饰器上下文
    // context 的类型会根据使用位置自动推断

    return function (this: T, ...args: any[]) {
      const data = args[0];

      for (const [key, rule] of Object.entries(schema)) {
        const fieldKey = key as keyof T;
        const fieldValue = (data as any)[fieldKey];

        // TypeScript 编译期间就能检查 schema 中的字段名是否存在于 T 上
        applyRule(fieldKey, fieldValue, rule);
      }

      return (value as Function).apply(this, args);
    } as unknown as Function;
  };
}

interface CreateUserInput {
  name: string;
  email: string;
  age: number;
}

class TypedUserService {
  @TypedValidate<CreateUserInput>({
    name: { type: 'string', required: true, min: 2 },
    email: { type: 'string', required: true, pattern: EMAIL_REGEX },
    age: { type: 'number', range: [0, 150] }
  })
  createUser(data: CreateUserInput): CreateUserInput {
    return db.users.create(data);
  }
}
```

TypeScript 5.0+ 对 Stage 3 装饰器提供了完整的类型支持，包括：
- `ClassMethodDecoratorContext`、`ClassFieldDecoratorContext`、`ClassDecoratorContext` 等内置类型
- 装饰器返回值的类型推断
- 泛型约束确保装饰器用在正确的目标上

### 实践四：避免常见的反模式

在使用装饰器的过程中，有一些常见的错误模式需要警惕：

**反模式一：过度堆叠装饰器**

```javascript
// ❌ 太多了！读起来像天书
@log({ prefix: 'API', level: 'debug', showArgs: true, showResult: true, showDuration: true })
@measure('endpoint', { sampleRate: 1, slowThreshold: 100 })
@retry(5, 1000, 2)
@circuitBreaker({ threshold: 5, resetTimeout: 30000 })
@requirePermission('admin')
@rateLimit({ windowMs: 60000, maxRequests: 100 })
@validate(userSchema)
@cache({ ttl: 300, maxSize: 50 })
@auditLog({ action: 'update' })
someComplexMethod(data) { /* ... */ }
```

如果一个方法上有七八个装饰器堆叠，说明这个方法承担了太多的横切关注点。考虑的改进方向：
- 将部分职责提升到类级别（比如 `@requirePermission` 可以做成类装饰器或中间件）
- 合并功能相近的装饰器（比如 `@log` 和 `@measure` 可以合并为一个 `@monitored`）
- 反思这个方法是否做了太多事情，是否需要拆分

**反模式二：在装饰器中有副作用却不清晰表达**

```javascript
// ❌ 这个装饰器偷偷修改了全局状态，但从名字上看不出来
function helper(value, context) {
  globalConfig.lastUsedMethod = context.name;  // 隐式的全局副作用！
  return value;
}

// ✅ 名字清晰地表达了副作用
function trackLastUsedMethod(value, context) {
  globalConfig.lastUsedMethod = context.name;
  return value;
}
```

**反模式三：装饰器吞掉异常或返回值**

```javascript
// ❌ 危险！错误被静默吞掉
function swallowErrors(value, context) {
  return function (...args) {
    try {
      return value.apply(this, args);
    } catch (e) {
      // 什么都不做... 错误消失了 😱
      return null;
    }
  };
}

// ✅ 正确：记录错误后重新抛出
function handleErrorsGracefully(value, context) {
  return function (...args) {
    try {
      return value.apply(this, args);
    } catch (e) {
      console.error(`[${context.name}] 发生错误:`, e);
      throw e;  // 必须重新抛出！
    }
  };
}
```

**反模式四：在装饰器中依赖执行顺序却不做防护**

```javascript
// ❌ 依赖于 B 在 A 之前执行，但没有明确保证
@decoratorA
@decoratorB  // 如果将来有人在中间插了一个装饰器，逻辑就可能出错
myMethod() {}

// ✅ 如果有顺序依赖，合并成一个装饰器
@combinedAB
myMethod() {}
```

### 实践五：测试装饰器的方法

装饰器也是代码，同样需要测试。以下是几种常用的测试策略：

```javascript
// ===== 策略一：直接测试装饰器函数 =====

describe('@required 装饰器', () => {
  it('应该在参数为空时抛出错误', () => {
    class TestClass {
      @required(0, 'name')
      greet(name) { return `你好 ${name}`; }
    }

    const obj = new TestClass();
    expect(() => obj.greet('')).toThrow('不能为空');
    expect(() => obj.greet(null)).toThrow('不能为空');
  });

  it('应该在参数有效时不干涉正常执行', () => {
    class TestClass {
      @required(0, 'name')
      greet(name) { return `你好 ${name}`; }
    }

    const obj = new TestClass();
    expect(obj.greet('世界')).toBe('你好 世界');
  });
});

// ===== 策略二：测试被装饰后的类行为 =====

describe('@autobind 装饰器', () => {
  it('应该使方法脱离实例后仍保持 this 绑定', () => {
    class TestClass {
      value = 42;
      @autobind
      getValue() { return this.value; }
    }

    const obj = new TestClass();
    const fn = obj.getValue;  // 提取方法引用
    expect(fn()).toBe(42);    // 即使脱离了 obj，this 仍然正确
  });

  it('不应该影响其他实例', () => {
    class TestClass {
      value = 0;
      @autobind
      setValue(v) { this.value = v; return this; }
    }

    const a = new TestClass();
    const b = new TestClass();
    const fnA = a.setValue;
    const fnB = b.setValue;

    fnA(10);  // a 的方法应该只修改 a
    expect(a.value).toBe(10);
    expect(b.value).toBe(0);  // b 不受影响

    fnB(20);
    expect(b.value).toBe(20);
    expect(a.value).toBe(10);  // a 也不受影响
  });
});


// ===== 策略三：测试装饰器组合 =====

describe('装饰器组合: @log + @retry', () => {
  it('应该在重试过程中正确记录每次尝试', async () => {
    let attemptCount = 0;
    const logs = [];

    // 劫持 console.log 来收集日志
    const originalLog = console.log;
    console.log = (...args) => logs.push(args.join(' '));

    class UnstableService {
      @log({ prefix: 'Test' }, true)
      @retry(3, 10)
      async flakyOperation() {
        attemptCount++;
        if (attemptCount < 3) throw new Error(`尝试 ${attemptCount} 失败`);
        return '成功!';
      }
    }

    const svc = new UnstableService();
    const result = await svc.flakyOperation();

    expect(result).toBe('成功!');
    expect(attemptCount).toBe(3);
    expect(logs.some(l => l.includes('第 1'))).toBe(true);
    expect(logs.some(l => l.includes('第 2'))).toBe(true);
    expect(logs.some(l => l.includes('第 3'))).toBe(true);

    console.log = originalLog;  // 还原
  });
});
```

### 通俗类比：装修公司的施工规范手册

装饰器的最佳实践就像一家**专业装修公司的施工规范手册**：

**集中管理**（decorators 目录）就像公司的**工具间**——所有电钻、锤子、尺子都整齐地摆放在固定位置，工人（开发者）随取随用，不会到处找工具或买重复的工具。

**命名约定**就像工具上的**标签**——"6mm 钻头"、"绝缘螺丝刀"、"激光测距仪"，而不是统称为"那个东西"或"A工具"、"B工具"。新手看了标签就知道该用什么。

**避免反模式**就像施工中的**安全守则**——不能在承重墙上随意开洞（不要过度堆叠装饰器），电线不能裸露在外（副作用要明确表达），发现隐患要及时上报（异常不能吞掉），工序不能乱序（不隐式依赖执行顺序）。

**测试**就像装修完工后的**验收检查**——不仅要看最终效果好不好看（功能是否正确），还要检查隐蔽工程（边界情况、组合场景、与其他功能的兼容性）是否符合标准。

### 四大实战装饰器速查表

| 装饰器 | 解决的核心问题 | 关键技术点 | 典型使用场景 |
|--------|---------------|-----------|-------------|
| **`@log`** | 日志分散、格式不一、遗漏风险 | 区分同步/异步、错误重抛、工厂配置 | 所有需要观测的方法 |
| **`@validate`** | 验证逻辑与业务耦合、规则重复 | Schema 声明式规则、批量错误收集 | API 接口、表单提交、数据处理 |
| **`@autobind`** | this 丢失导致运行时错误 | addInitializer、实例属性遮蔽原型 | 事件回调、定时器、Promise 链 |
| **`@measure` + `@memoize`** | 性能盲区、重复计算浪费资源 | 闭包指标收集、LRU 缓存淘汰、TTL 过期 | 计算密集型方法、高频调用的纯函数 |

### 关于执行顺序的核心结论

回顾全文关于执行顺序的讨论，有三句话值得牢记：

1. **定义时从内到外**：最靠近方法的装饰器最先执行，它的返回值会被外层装饰器继续包装
2. **运行时从外到内**：调用请求穿过层层装饰器到达原始方法，结果再逐层返回
3. **短路会阻断穿透链**：任何一层装饰器可以选择不调用内部的 value，从而阻止请求继续向下传递

这三条规律构成了装饰器组合行为的完整心智模型。掌握了它，你就能够自信地在任何场景中预测和掌控多个装饰器的交互行为。

### 给开发者的最终建议

装饰器是一种强大的元编程工具，但它终究只是一个工具。最好的代码不一定使用了最多的装饰器技巧，而是**在最合适的地方用了最合适的装饰器**。

当你下次准备为一个方法添加装饰器时，不妨先问自己三个问题：
1. **这个装饰器解决的是真正的痛点吗？** 还是只是为了看起来"高级"？
2. **这个装饰器是否足够简单、专注？** 还是它试图做太多事情？
3. **团队成员能一眼看懂这个装饰器的作用吗？** 还是需要查阅文档才能理解？

如果三个问题的答案都是正面的，那就放心地使用吧。装饰器会让你的代码更加简洁、更加声明式、更加易于维护。这正是装饰器模式的终极价值——**用最少的样板代码，表达最丰富的附加行为**。

> **掌握装饰器的实战用法，意味着你不仅学会了如何使用一种语法特性，更重要的是培养了一种"声明式思维"——用配置代替编码，用组合代替继承，用关注点分离代替面条代码。** 这种思维方式的价值远超装饰器本身，它会影响你写下的每一行代码。
