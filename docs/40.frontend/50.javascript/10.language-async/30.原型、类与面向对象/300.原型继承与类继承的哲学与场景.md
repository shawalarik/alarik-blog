# 原型继承与类继承的哲学与场景

## 两种编程世界观的碰撞

在计算机科学的历史长河中，关于"如何组织对象和代码"这个问题，诞生了两条截然不同的思想路线。一条是**基于类的编程（Class-based Programming）**——以 Java、C++、C# 为代表，强调类型、层级、模板和实例化；另一条是**基于原型的编程（Prototype-based Programming）**——以 Self、Io、JavaScript 为代表，强调克隆、委托、去中心化和动态演化。

JavaScript 是一个奇特的混合体。它诞生时选择了原型作为核心对象机制（因为要简单、轻量），但在 ES6 中又引入了 `class` 语法糖来迎合主流开发者的习惯。这导致了一个有趣的现象：同一个语言里同时存在两套"正统"的对象组织方式——你可以用 `class` + `extends` 写出标准的类继承代码，也可以用 `Object.create()` + 原型链操作实现纯原型风格的继承。

本文将从哲学层面出发，深入剖析这两种范式的本质差异，然后回到现实层面，讨论在实际项目中应该如何选择。

### 为什么这个话题如此重要？

很多 JavaScript 开发者在整个职业生涯中只使用过 `class` + `extends` 这一种方式。他们知道有"原型链"这个东西存在（毕竟面试会考），但从未真正用原型风格写过任何东西。这种单一视角带来的问题是：

- **你无法理解 JavaScript 的真正本质**。`class` 只是一层糖衣，剥开之后里面全是原型。不理解原型就等于不理解这门语言的根基。
- **你在某些场景下可能正在使用错误的工具**。有些问题用类继承来解决会非常别扭，而原型式的组合方案却天然契合。
- **你的设计思维被局限了**。只知道一种范式的人遇到问题时只能想到一种解法。掌握两种范式意味着你拥有双倍的设计空间。

这就好比一个人只会用锤子——在他眼里所有的问题都是钉子。但如果你还掌握了螺丝刀、扳手、电钻等工具，面对不同的问题就能选择最趁手的那个。

## 哲学篇：两种世界观的对立

### 类的世界观：柏拉图的理想国

基于类的编程思想可以追溯到古希腊哲学家**柏拉图的理念论（Theory of Forms）**。柏拉图认为：我们在现实中看到的每一个具体事物（比如一把椅子、一匹马）都只是不完美的"摹本"，而存在着一个完美的、永恒不变的"理念"（Form 或 Idea）——那就是椅子的本质、马的本质。

将这个思想映射到编程世界中：

- **类（Class）就是"理念"**——它是一个抽象的模板、一个蓝图、一个理想的定义。类本身并不直接参与运算（你不能"调用"一个类），它的存在是为了描述"这一类事物应该长什么样"。
- **实例（Instance）就是"摹本"**——根据类的蓝图制造出来的具体对象。每个实例都是类的"化身"，拥有类定义的所有特征，但各自有不同的数据值。
- **继承（Inheritance）就是理念的层级体系**——"动物"是一个更上层的理念，"狗"是"动物"的一个特化理念，"柯基犬"又是"狗"的一个进一步特化。下层理念自动拥有上层理念的所有特征。

这种世界观的魅力在于它的**秩序感和可预测性**。一切都预先规划好了——每个对象属于哪个类别一目了然，每个类别有什么能力和属性清清楚楚。编译器可以在编译阶段帮你检查类型错误，IDE 可以提供精确的代码补全。

```javascript
// 类式思维的典型写法 —— 层级分明，秩序井然
class Animal {
  constructor(name) {
    this.name = name;
  }
  eat() { console.log(`${this.name} 在吃东西`); }
  sleep() { console.log(`${this.name} 在睡觉`); }
}

class Dog extends Animal {          // Dog "is-a" Animal
  constructor(name, breed) {
    super(name);
    this.breed = breed;
  }
  bark() { console.log(`${this.name}(${this.breed}) 汪汪叫！`); }
}

class Corgi extends Dog {           // Corgi "is-a" Dog, 也 "is-a" Animal
  constructor(name) {
    super(name, '柯基');
    this.legShortness = 'extreme';
  }
  spin() { console.log(`${this.name} 转圈圈！小短腿真可爱~`); }
}

let corgi = new Corgi('小花');
corgi.eat();   // 来自 Animal ✅
corgi.bark();  // 来自 Dog     ✅
corgi.spin();  // 来自 Corgi   ✅
console.log(corgi instanceof Corgi);  // true
console.log(corgi instanceof Dog);    // true
console.log(corgi instanceof Animal); // true
```

这段代码读起来就像一份生物分类学报告——界门纲目科属种，层层递进，井然有序。每个类都在自己的位置上，继承了祖先的所有能力，又添加了自己特有的行为。`instanceof` 运算符就像是 DNA 检测仪，能准确告诉你某个对象属于哪些物种。

### 原型的世界观：达尔文的进化论

基于原型的编程思想则更像**达尔文的进化论**——不存在什么"完美蓝图"，一切都是从已有的东西演变而来的：

- **没有"类"的概念，只有对象**。第一个对象是怎么来的？它是凭空创造的（或者从一个基础对象克隆出来的）。之后的每个新对象都是基于某个已有对象修改/扩展而来。
- **继承变成了"委托"（Delegation）**。当一个对象无法响应某个请求时，它会把这个请求转交给另一个对象（它的原型）来处理。这不是"is-a"关系，而是"我搞不定，帮我问问我的师傅"的关系。
- **对象可以在运行时自由演化**。不需要预先定义类型层级。你可以随时给任何对象添加新方法、改变其原型链接、甚至彻底重组它的行为。

如果说类式编程像是**建筑工程**——先画好蓝图（定义类），再按照图纸盖楼（实例化）——那么原型式编程就像**生物进化**——一个物种通过基因突变和自然选择逐渐演变成新的物种，没有预设的方向，每一步都是对上一代的修改和扩展。

```javascript
// 原型式思维的典型写法 —— 自由演化，没有预设蓝图

// 第一个动物对象 —— 凭空创造
let animal = {
  name: '无名动物',
  eat() { console.log(`${this.name} 在吃东西`); },
  sleep() { console.log(`${this.name} 在睡觉`); }
};

// 一只狗 —— 基于 animal 对象创建，并添加狗的特征
let dog = Object.create(animal);  // dog 的原型是 animal
dog.name = '旺财';
dog.breed = '混血';
dog.bark = function () { console.log(`${this.name}(${this.breed}) 汪汪叫！`); };

// 一只柯基 —— 基于 dog 对象创建，继续演化
let corgi = Object.create(dog);   // corgi 的原型是 dog
corgi.name = '小花';
corgi.legShortness = 'extreme';
corgi.spin = function () { console.log(`${this.name} 转圈圈！小短腿真可爱~`); };

corgi.eat();   // 自己没有 eat → 委托给 dog → dog 也没有 → 委托给 animal ✅
corgi.bark();  // 自己没有 bark → 委托给 dog → dog 有！执行 ✅
corgi.spin();  // 自己有 spin → 直接执行 ✅
```

注意这里的核心区别：**不是"柯基是一只狗，狗是一种动物"，而是"柯基找不到答案就去问狗狗，狗狗找不到答案就去问动物"。** 这是一种链式的委托关系，而不是静态的类型归属关系。

### 哲学层面的根本分歧

让我们把两种世界观的差异总结为以下几个哲学命题上的对立：

| 命题 | 类的世界观 | 原型的世界观 |
|------|----------|------------|
| **本体论（什么是真实存在的？）** | 类是真实的、先验存在的；实例是类的影子 | 只有对象是真实存在的；没有独立的"类"实体 |
| **认识论（知识如何组织？）** | 分类法——万物各归其位 | 关联法——万物相互引用 |
| **变化观（事物如何演变？）** | 静态的——类一旦定义就基本不变；变化发生在实例层面 | 动态的——对象可以在任何时候改变结构和行为 |
| **关系观（对象之间如何关联？）** | "is-a"层级——严格的父子关系 | "delegate-to"网络——平行的委托关系 |
| **复杂度观（如何应对复杂性？）** | 抽象提炼——提取公共特征形成基类 | 组合拼装——用小的构件组装出大的功能 |

这些差异不只是学术游戏——它们直接影响你每天写代码时的决策方式。当你面临"这个功能应该放在父类还是子类？"这样的问题时，你实际上是在做一次微型的哲学选择。

### 通俗类比：官方标准 vs 自由市场

为了让你更直觉地感受两种范式的区别，我们来打两个比方：

**类继承 = 官方认证的职业资格体系**

想象一个严格的社会，每个人都有明确的职业分类：
- 最顶层是"劳动者"（基类）
- 下面分出"体力劳动者""脑力劳动者"
- "脑力劳动者"下面又分"工程师""教师""医生"
- "工程师"下面又分"软件工程师""机械工程师""土木工程师"

每个人出生时（实例化时）就被分配到一个确定的类别中，终身携带该类别的所有特征。如果你想成为"会做手术的工程师"，对不起——系统不允许跨界。"医生"和"工程师"是两条完全不同的职业路径（多重继承在很多语言中被禁止或限制）。如果你需要一种全新的职业角色，必须向"标准委员会"（设计者）申请，经过漫长的审批流程后才能新增一个类别。

这套体系的优点是**清晰、安全、可预测**。缺点是**僵化、难以适应变化、容易出现过度设计的中间层**。

**原型继承 = 技能市场的自由人模式**

在这个世界里，没有人天生属于某个"类别"。每个人都是一个独立的存在，拥有自己独特的技能组合：
- 小张最初什么都不会（空对象）
- 他跟老王学了编程（以老王为原型，获得了编程技能）
- 后来他又跟小李学了做饭（又融合了小李的能力）
- 再后来他自己摸索出了写作的能力（自己添加的方法）

小张既不是纯粹的"程序员"也不是纯粹的"厨师"，他就是小张——一个拥有编程+做饭+写作能力的独特个体。如果哪天他想学钢琴，找个钢琴老师（以钢琴家为原型）就行，不需要重新投胎或者申请"转行"。

这套体系的优点是**灵活、自然、能适应任何需求**。缺点是**缺乏统一规范，如果大家各自为政可能导致混乱**。

## 技术篇：两种继承方式在 JavaScript 中的实现

### 类继承的实现：class 与 extends

ES6 引入的 `class` 和 `extends` 语法让 JavaScript 的类继承变得和其他面向对象语言非常相似。但需要时刻记住：**这只是语法糖，底层仍然是原型链**。

```javascript
// ====== 基础类继承 ======

class Vehicle {
  // 私有字段（ES2022）
  #vin;
  #mileage;

  constructor(brand, model, vin) {
    this.brand = brand;       // 品牌
    this.model = model;       // 型号
    this.#vin = vin;          // 车架号（私有）
    this.#mileage = 0;        // 里程数（私有）
  }

  // 公共方法
  drive(distance) {
    this.#mileage += distance;
    return `${this.brand} ${this.model} 行驶了 ${distance}km`;
  }

  getMileage() {
    return this.#mileage;
  }

  // getter/setter
  get info() {
    return `${this.brand} ${this.model} (${this.#vin})`;
  }

  // 静态方法
  static compareMileage(v1, v2) {
    return v1.getMileage() - v2.getMileage();
  }
}

class Car extends Vehicle {
  #seatCount;

  constructor(brand, model, vin, seatCount) {
    super(brand, model, vin);  // 必须先调用 super()
    this.#seatCount = seatCount;
  }

  // 重写（override）父类方法
  drive(distance) {
    const result = super.drive(distance);  // 可以通过 super 调用父类实现
    result += ` (载客${this.#seatCount}人)`;
    return result;
  }

  // 新增子类独有方法
  honk() {
    return `${this.brand} 喇叭响！嘀嘀~`;
  }

  // 子类也可以有自己的静态方法
  static createSedan(brand, vin) {
    return new Car(brand, '轿车', vin, 5);
  }
}

let myCar = new Car('丰田', '凯美瑞', 'VIN2024001', 5);

myCar.drive(100);         // "丰田 凯美瑞 行驶了 100km (载客5人)"
myCar.honk();            // "丰田 凯美瑞 喇叭响！嘀嘀~"
Car.compareMileage(myCar, myCar);

console.log(myCar instanceof Vehicle);  // true  ← 类型层级清晰
console.log(myCar instanceof Car);      // true
```

这段代码展示了几种关键的类继承机制：

**`super` 的两种用法**：在构造函数中 `super(...)` 用于调用父类构造函数（必须在使用 `this` 之前调用）；在普通方法中 `super.methodName()` 用于调用父类的同名方法。这使得子类可以在父类行为的基础上进行扩展或修改，而不是完全替换。

**重写（Override）与多态**：`Car` 类重写了 `Vehicle` 的 `drive` 方法。当外部代码调用 `myCar.drive()` 时，执行的是 `Car` 版本的 `drive`——即使变量被声明为 `Vehicle` 类型也是如此。这就是运行时多态的基础。

**访问控制**：私有字段（`#vin`、`#mileage`）只能在定义它们的类内部访问，子类也无法直接触碰。这是类继承体系中封装性的重要保障。

### 原型继承的实现：Object.create 与原型链操作

虽然 `class` + `extends` 已经足够好用，但理解底层的原型操作仍然非常重要——这不仅有助于你调试复杂的继承问题，还能在某些特殊场景下提供更灵活的解决方案。

```javascript
// ====== 纯原型式继承 ======

// 步骤一：定义一个"基础"对象（相当于其他对象的原型/模具）
const vehiclePrototype = {
  init(brand, model, vin) {
    this.brand = brand;
    this.model = model;
    this._vin = vin;        // 用下划线约定"伪私有"
    this._mileage = 0;
    return this;             // 方便链式调用
  },

  drive(distance) {
    this._mileage += distance;
    return `${this.brand} ${this.model} 行驶了 ${distance}km`;
  },

  getMileage() {
    return this._mileage;
  },

  get info() {
    return `${this.brand} ${this.model} (${this._vin})`
  }
};

// 步骤二：创建 carPrototype，其原型指向 vehiclePrototype
const carPrototype = Object.create(vehiclePrototype);

// 扩展汽车特有的能力
carPrototype.init = function (brand, model, vin, seatCount) {
  // 先调用原型的初始化（手动实现类似 super 的效果）
  vehiclePrototype.init.call(this, brand, model, vin);
  this.seatCount = seatCount;
  return this;
};

// 重写 drive 方法（保留对原始版本的调用）
const _originalDrive = vehiclePrototype.drive;
carPrototype.drive = function (distance) {
  const result = _originalDrive.call(this, distance);
  result += ` (载客${this.seatCount}人)`;
  return result;
};

// 新增汽车特有方法
carPrototype.honk = function () {
  return `${this.brand} 喇叭响！嘀嘀~`;
};

// 步骤三：基于 carPrototype 创建实际的对象实例
let myCar2 = Object.create(carPrototype).init('本田', '雅阁', 'VIN2024002', 5);

myCar2.drive(80);         // "本田 雅阁 行驶了 80km (载客5人)"
myCar2.honk();            // "本田 喇叭响！嘀嘀~"

// 验证原型链
console.log(Object.getPrototypeOf(myCar2) === carPrototype);          // true
console.log(Object.getPrototypeOf(carPrototype) === vehiclePrototype); // true
```

对比两种写法，你会发现它们做的事情几乎一模一样——最终产生的对象结构和使用体验都非常相似。关键区别在于**构建过程**：

| 维度 | class 继承 | 原型继承 |
|------|-----------|---------|
| 定义方式 | 声明式（`class X extends Y {}`） | 命令式（`Object.create()` + 属性赋值） |
| 构建时机 | 类定义时就确定好了原型链 | 运行时可以动态修改原型链 |
| `super` 支持 | 语法内置，自动正确绑定 | 需要手动 `.call(this)` 实现 |
| 封装性 | 原生支持私有字段 `#` | 需要用闭包或约定（`_`前缀） |
| 可读性 | 高（一眼看出继承关系） | 低（需要追踪 `Object.create` 链） |

### 原型继承的高级用法：Mixin 模式

类继承最大的限制之一是**单继承**——一个子类只能有一个直接的父类。这在某些场景下会产生困扰：比如你想让一个类同时具备"可序列化的"、"可观察的"、"可验证的"三种能力，但它们之间并没有自然的"is-a"关系。

原型式编程中的 **Mixin（混入）模式**为此提供了一个优雅的解决方案——你不是从单个父类继承，而是从多个"能力模块"中组合你需要的功能：

```javascript
// ====== Mixin 能力模块 ======

// 能力一：可序列化
const Serializable = {
  toJSON() {
    const obj = {};
    for (let key of Object.keys(this)) {
      if (!key.startsWith('_')) {  // 排除"私有"属性
        obj[key] = this[key];
      }
    }
    return JSON.stringify(obj);
  },

  static fromJSON(jsonStr) {
    const data = JSON.parse(jsonStr);
    const instance = Object.create(this.prototype || this);
    Object.assign(instance, data);
    return instance;
  }
};

// 能力二：可变更通知
const Observable = {
  _listeners: {},

  onChange(prop, callback) {
    if (!this._listeners[prop]) this._listeners[prop] = [];
    this._listeners[prop].push(callback);
  },

  setProperty(prop, value) {
    const oldValue = this[prop];
    this[prop] = value;

    // 通知所有监听者
    if (this._listeners[prop]) {
      this._listeners[prop].forEach(cb => cb(value, oldValue, prop));
    }
  }
};

// 能力三：数据校验
const Validatable = {
  _rules: {},

  addRule(prop, validator, message) {
    if (!this._rules[prop]) this._rules[prop] = [];
    this._rules[prop].push({ validator, message });
  },

  validate() {
    const errors = [];
    for (let [prop, rules] of Object.entries(this._rules)) {
      for (let rule of rules) {
        if (!rule.validator(this[prop])) {
          errors.push(`[${prop}] ${rule.message}`);
        }
      }
    }
    if (errors.length > 0) {
      throw new Error('校验失败:\n  ' + errors.join('\n  '));
    }
    return true;
  }
};

// ====== 使用 Mixin 创建一个用户模型 ======
function createUserModel(name, email) {
  // 以空对象为基础
  let user = Object.assign(
    {},
    Serializable,
    Observable,
    Validatable
  );

  user.name = name;
  user.email = email;
  user._createdAt = Date.now();
  user._listeners = {};       // 初始化 Observable 需要的状态
  user._rules = {             // 初始化 Validatable 需要的状态
    name: [{ validator: v => v && v.length >= 2, message: '名字至少2个字符' }],
    email: [{ validator: v => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v), message: '邮箱格式无效' }]
  };

  return user;
}

let user = createUserModel("张三", "zhangsan@example.com");

// 使用 Observable 能力
user.onChange('name', (newVal, oldVal) => {
  console.log(`名字从 "${oldVal}" 改为 "${newVal}"`);
});
user.setProperty('name', '张三丰');   // 触发 onChange 回调
// 输出: 名字从 "张三" 改为 "张三丰"

// 使用 Validatable 能力
try {
  user.setProperty('name', '');  // 太短了！
  user.validate();
} catch (e) {
  console.log(e.message);
  // [name] 名字至少2个字符
}

// 使用 Serializable 能力
console.log(user.toJSON());
// {"name":"张三丰","email":"zhangsan@example.com"}
```

这个例子展示了 Mixin 模式的强大之处：`user` 对象同时具备了序列化、变更通知和数据校验三种能力，而这三种能力来自三个完全独立的模块。你不需要设计一个三层继承体系（比如 `ValidatableUser extends ObservableUser extends SerializableUser`），只需要把需要的功能"混"进来就行了。

### 类继承中也能用 Mixin

你可能认为 Mixin 是原型式编程的专利，但其实在 class 语法中也能实现类似的效果——通过工厂函数 + `Object.assign` 在类的 prototype 上混入方法：

```javascript
// Mixin 工厂函数（返回一个包含方法的对象）
function serializable(Class) {
  return class extends Class {
    toJSON() {
      const obj = {};
      for (let [k, v] of Object.entries(this)) {
        if (typeof k === 'string' && !k.startsWith('#') && typeof v !== 'function') {
          obj[k] = v;
        }
      }
      return obj;
    }

    static fromJSON(data) {
      return new this(data);
    }
  };
}

function observable(Class) {
  return class extends Class {
    #listeners = {};

    onChange(property, callback) {
      if (!this.#listeners[property]) this.#listeners[property] = [];
      this.#listeners[property].push(callback);
    }

    set(property, value) {
      const old = this[property];
      this[property] = value;
      this.#listeners[property]?.forEach(cb => cb(value, old));
    }
  };
}

// 通过嵌套 Mixin 包装来组合能力
const SmartUser = serializable(observable(class User {
  #name;
  #email;

  constructor(name, email) {
    this.#name = name;
    this.#email = email;
  }

  get name() { return this.#name; }
  set name(v) { this.#name = v; }

  greet() { return `你好，我是 ${this.#name}`; }
}));

let smartUser = new SmartUser('李四', 'lisi@test.com');
smartUser.onChange('name', (n, o) => console.log(`改名: ${o} → ${n}`));
smartUser.set('name', '李四海');  // 触发 observable 的 onChange
console.log(smartUser.toJSON());   // 调用 serializable 的 toJSON
// { name: "李四海", ... }
```

这种方式利用了 JavaScript 的**表达式形式的类声明（Class Expression）**特性——`class` 可以作为参数传给函数，函数返回的新类通过 `extends` 继承原来的类。这样就把 Mixin 的灵活性和 class 的语法便利性结合了起来。

不过要注意的是：这种 Mixin 方案本质上还是单继承链——只是每一层的父类是由工厂函数动态生成的。它不像真正的原型 Mixin 那样可以任意扁平地组合多个来源。

## 场景篇：何时用何者？

### 场景一：领域模型有清晰的"is-a"层级关系 → 类继承

如果你的项目涉及到的实体之间存在天然的泛化-特化关系，类继承是最自然的选择。典型场景包括：

- **电商系统**：`Product` → `PhysicalProduct` / `DigitalProduct` / `ServiceProduct` → 各种子类
- **权限系统**：`User` → `RegularUser` / `VIPUser` / `AdminUser` / `SuperAdmin`
- **游戏开发**：`Entity` → `Character` → `Player` / `NPC` / `Enemy` → 更细的角色类型
- **文件系统**：`FileSystemNode` → `File` / `Directory` / `Symlink`

这些场景的共同特点是：**层级结构稳定、每个层级都有明确的语义含义、"is-a"关系符合现实世界的直觉**。

```javascript
// 电商产品领域的类继承示例

class Product {
  #id;
  #name;
  #price;
  #stock;

  constructor(id, name, price, stock) {
    this.#id = id;
    this.#name = name;
    this.#price = price;
    this.#stock = stock;
  }

  get id() { return this.#id; }
  get name() { return this.#name; }
  get price() { return this.#price; }

  isAvailable() { return this.#stock > 0; }

  // 所有产品的通用逻辑：计算折扣价
  applyDiscount(rate) {
    if (rate < 0 || rate > 1) throw new Error('折扣率必须在 0-1 之间');
    return this.#price * (1 - rate);
  }

  // 钩子方法：子类可以覆盖来实现特定行为
  getShippingInfo() {
    return { method: 'standard', cost: 10, estimatedDays: '5-7' };
  }

  toString() {
    return `[Product#${this.#id}] ${this.#name} ¥${this.#price}`;
  }
}

// 实体商品：有重量、尺寸、物流信息
class PhysicalProduct extends Product {
  #weight;  // kg
  #dimensions; // { length, width, height }

  constructor(id, name, price, stock, weight, dimensions) {
    super(id, name, price, stock);
    this.#weight = weight;
    this.#dimensions = dimensions;
  }

  getShippingInfo() {
    const volumetricWeight = (
      this.#dimensions.length *
      this.#dimensions.width *
      this.#dimensions.height
    ) / 5000;

    const shippingCost = Math.max(this.#weight, volumetricWeight) * 8;
    return {
      method: this.#weight > 5 ? 'freight' : 'parcel',
      cost: shippingCost,
      estimatedDays: this.#weight > 10 ? '10-15' : '3-5'
    };
  }
}

// 数字商品：无需物流、即时交付
class DigitalProduct extends Product {
  #downloadUrl;
  #fileSize; // MB
  #expiryDays;

  constructor(id, name, price, stock, downloadUrl, fileSize, expiryDays = 365) {
    super(id, name, price, stock);
    this.#downloadUrl = downloadUrl;
    this.#fileSize = fileSize;
    this.#expiryDays = expiryDays;
  }

  getShippingInfo() {
    return { method: 'digital', cost: 0, estimatedDays: 'instant' };
  }

  getDownloadLink(customerId) {
    // 生成带有过期时间的下载链接
    const expiry = Date.now() + this.#expiryDays * 24 * 60 * 60 * 1000;
    return {
      url: `${this.#downloadUrl}?token=${generateToken(customerId)}&expires=${expiry}`,
      size: this.#fileSize,
      format: this.#name.endsWith('.pdf') ? 'PDF' : 'ZIP'
    };
  }
}

// 服务商品：有预约时间、服务人员、地点
class ServiceProduct extends Product {
  #duration;  // 分钟
  #location;
  #requiredInfo;

  constructor(id, name, price, stock, duration, location, requiredInfo) {
    super(id, name, price, stock);
    this.#duration = duration;
    this.#location = location;
    this.#requiredInfo = requiredInfo;
  }

  book(slot, customerInfo) {
    // 验证必要信息
    for (let info of this.#requiredInfo) {
      if (!customerInfo[info]) throw new Error(`缺少必要信息: ${info}`);
    }
    return {
      productId: this.id,
      slot,
      location: this.#location,
      duration: this.#duration,
      confirmed: true
    };
  }
}

// 多态分发：统一处理不同类型的商品
function processOrder(product, quantity) {
  if (!(product instanceof Product)) {
    throw new Error('必须是有效的产品对象');
  }

  if (!product.isAvailable(quantity)) {
    return { success: false, reason: '库存不足' };
  }

  const shipping = product.getShippingInfo(); // 多态调用！
  return {
    success: true,
    product: product.toString(),
    quantity,
    subtotal: product.applyDiscount(0.9) * quantity,
    shipping
  };
}

let book = new DigitalProduct(1, '《JavaScript高级程序设计》电子版', 89, 999, '/dl/book1.pdf', 45);
let shoes = new PhysicalProduct(2, '跑鞋', 599, 50, 0.8, { length: 40, width: 25, height: 12 });
let consult = new ServiceProduct(3, '技术咨询', 500, 20, 60, '线上', ['问题描述', '联系方式']);

processOrder(book, 1);    // digital delivery, instant
processOrder(shoes, 2);   // freight/parcel shipping with calculated cost
processOrder(consult, 1); // booking confirmation
```

这个例子的美妙之处在于 `processOrder` 函数——它不需要知道传入的具体是什么类型的产品。它只关心"这是一个 `Product`"，然后通过多态机制让每种产品自行决定如何计算运费、如何处理订单。这就是类继承最核心的价值所在：**多态让你写出针对接口而非具体实现的通用代码**。

### 场景二：需要灵活组合多种能力 → 原型/Mixin

当你的对象需要的各种能力之间没有明显的"is-a"关系，而是像插件一样可以随意搭配时，原型/Mixin 模式更加合适：

- **UI 组件**：一个按钮组件可能需要 `Clickable`、`Disabled`、`Themed`、`Animated`、`Accessible` 等能力，但这些能力之间的排列组合千变万化
- **中间件管道**：HTTP 请求处理器可能需要 `Logging`、`Auth`、`RateLimiting`、`Caching`、`Compression` 等中间件，不同的 API 端点需要不同的组合
- **游戏角色**：一个角色可能拥有 `Flyable`、`Swimmable` `Walkable` `Attackable` `MagicCastable` 等技能，不同角色的技能组合差异巨大

在这些场景下强行套用类继承会导致两种灾难：要么创建大量只有微小差异的子类（组合爆炸），要么把所有能力堆到一个巨型类中（违反单一职责原则）。

```javascript
// UI 组件的 Mixin 能力组合示例

// 能力模块
const Clickable = {
  #clickHandlers: [],

  onClick(handler) {
    this.#clickHandlers.push(handler);
    return this;  // 链式调用
  },

  click(event) {
    this.#clickHandlers.forEach(h => h.call(this, event));
    this.emit?.('click', event);  // 如果也有 Observable 能力的话
  }
};

const Disabled = {
  #disabled: false,

  get disabled() { return this.#disabled; },
  disable() { this.#disabled = true; return this; },
  enable() { this.#disabled = false; return this; },

  // 拦截 click：禁用时不可点击
  click(event) {
    if (this.#disabled) {
      console.warn('⚠️ 该组件已被禁用，忽略点击事件');
      return;
    }
    // 调用原始的 click（如果有的话）
    // 这里简化处理，实际可以用装饰器链
  }
};

const Themed = {
  #theme: { bg: '#fff', color: '#333', border: '#ccc', radius: '4px' },

  setTheme(theme) {
    Object.assign(this.#theme, theme);
    this.render?.();  // 主题变了就重新渲染
    return this;
  },

  get styles() {
    return {
      backgroundColor: this.#theme.bg,
      color: this.#theme.color,
      border: `1px solid ${this.#theme.border}`,
      borderRadius: this.#theme.radius
    };
  }
};

const Animated = {
  #animation: null,

  fadeIn(duration = 300) {
    return new Promise(resolve => {
      this.style.opacity = '0';
      this.#animation = requestAnimationFrame(() => {
        this.style.transition = `opacity ${duration}ms`;
        this.style.opacity = '1';
        setTimeout(resolve, duration);
      });
    });
  },

  shake(intensity = 5) {
    this.style.transform = `translateX(${intensity}px)`;
    setTimeout(() => this.style.transform = `translateX(${-intensity}px)`, 50);
    setTimeout(() => this.style.transform = 'translateX(0)`, 100);
  }
};

// 根据需求自由组合创建不同特性的按钮
function createButton(label) {
  return Object.assign({ label, render() {
    console.log(`渲染按钮: ${this.label}`, this.styles || '');
  }}, Themed, Animated);
}

// 一个普通的主题化动画按钮
let normalBtn = createButton('提交')
  .onClick(() => console.log('提交了！'))
  .setTheme({ bg: '#4CAF50', color: 'white', border: '#45a049' });

// 一个带禁用状态的按钮
let disabledBtn = createButton('保存')
  .setTheme({ bg: '#ccc', color: '#888', border: '#bbb' })
  .disable();

normalBtn.render();
normalBtn.click();
normalBtn.fadeIn().then(() => console.log('淡入完成'));

disabledBtn.render();
disabledBtn.click();  // ⚠️ 已被禁用，忽略点击
```

试想一下如果用类继承来实现同样的效果：你需要 `Button`、`ThemedButton`、`AnimatedButton`、`DisabledButton`、`ThemedAnimatedButton`、`ThemedDisabledButton`、`AnimatedDisabledButton`、`ThemedAnimatedDisabledButton`……仅仅三个能力模块的组合就需要至少 \(2^3 = 8\) 个类。而 Mixin 方案只需要 3 个能力模块 + 1 个基础创建函数，任意组合都能在一行代码内搞定。

### 场景三：需要运行时的动态行为扩展 → 原型

有些情况下，你需要在程序运行期间动态地给对象或"类"添加方法或修改继承关系。类继承在这方面比较吃力（虽然可以通过修改 `prototype` 来做到，但这违背了 class 语法的初衷），而原型式操作则天然支持这种动态性：

```javascript
// 插件系统的原型式实现

class PluginHost {
  #plugins = [];

  loadPlugin(plugin) {
    this.#plugins.push(plugin);
    // 将插件的所有方法混入到当前实例上！
    for (let [methodName, fn] of Object.entries(plugin.methods)) {
      // 不覆盖已有方法
      if (!(methodName in this)) {
        this[methodName] = fn.bind(plugin.context || this);
      }
    }
    plugin.loaded?.call(this);
  }

  unloadPlugin(pluginName) {
    const idx = this.#plugins.findIndex(p => p.name === pluginName);
    if (idx >= 0) {
      const plugin = this.#plugins[idx];
      // 移除该插件注入的方法
      for (let methodName of Object.keys(plugin.methods)) {
        delete this[methodName];
      }
      plugin.unloaded?.call(this);
      this.#plugins.splice(idx, 1);
    }
  }
}

// 插件定义：日志功能
const loggerPlugin = {
  name: 'logger',
  context: null,
  methods: {
    log(action, data) {
      const timestamp = new Date().toISOString();
      console.log(`[${timestamp}] [${action}]`, data);
    },

    logError(error) {
      this.log('ERROR', { message: error.message, stack: error.stack });
    }
  },
  loaded() { this.log('PLUGIN_LOADED', { plugin: this.name }); },
  unloaded() { console.log('Logger 插件已卸载'); }
};

// 插件定义：缓存功能
const cachePlugin = {
  name: 'cache',
  #store: new Map(),
  methods: {
    cache(key, factory) {
      if (this.#store.has(key)) {
        return this.#store.get(key);
      }
      const value = factory();
      this.#store.set(key, value);
      return value;
    },

    clearCache() {
      this.#store.clear();
      this.log?.('CACHE_CLEARED', { size: this.#store.size });  // 如果 logger 已加载
    }
  },
  loaded() { /* 初始化 */ }
};

let host = new PluginHost();
host.loadPlugin(loggerPlugin);
// [2026-04-20T...] [PLUGIN_LOADED] { plugin: "logger" }

host.loadPlugin(cachePlugin);
host.log('SYSTEM_READY', { plugins: 2 });  // logger 注入的方法可用！

let cachedResult = host.cache('expensiveData', () => {
  host.log('COMPUTE_START', {});
  let sum = 0;
  for (let i = 0; i < 1000000; i++) sum += Math.sqrt(i);
  host.log('COMPUTE_DONE', { sum });
  return sum;
});  // 第一次：执行计算并缓存
// 第二次 host.cache('expensiveData', ...) 直接返回缓存

host.unloadPlugin('logger');
// Logger 插件已卸载
// 现在 host.log 和 host.logError 方法已经不存在了
host.clearCache();  // 不会打印日志了（log 方法已被删除）
```

这个插件系统展示了原型式编程在动态扩展方面的强大能力：**在运行时往已有对象上注入或移除方法**。这种"热插拔"能力在 IDE 插件架构、游戏模组（Mod）系统、微服务等场景中都极为有用。

### 场景四：团队背景与生态兼容性 → 类继承

有时候技术选型不完全由技术因素决定。如果你的团队成员主要来自 Java、C#、Python 背景，他们对 `class`、`extends`、`interface`、`implements` 这些概念已经形成了肌肉记忆。在这种情况下，强制推行原型式风格只会增加团队的认知负担和学习成本。

同样，如果你使用的框架或库（如 Angular、NestJS、TypeORM）深度依赖类继承机制，那么跟随框架的惯例是最明智的选择——逆流而上只会让你在和框架搏斗的过程中消耗不必要的精力。

```typescript
// NestJS 控制器的典型写法 —— 框架强制要求使用 class + 装饰器
@Controller('users')
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Get()
  findAll(): Promise<User[]> {
    return this.userService.findAll();
  }

  @Post()
  @UsePipes(ValidationPipe)
  create(@Body() createUserDto: CreateUserDto): Promise<User> {
    return this.userService.create(createUserDto);
  }
}
```

在这样的项目中试图用 `Object.create` 和 Mixin 来替代 `class`，不仅会让框架的依赖注入、反射元数据和装饰器全部失效，还会让其他开发者完全看不懂你的代码。

## 进阶话题：超越二元对立

### 第三条路：组合式类设计

前面我们把类继承和原型继承描绘成了两种对立的范式。但实际上，在成熟的工程实践中，大多数项目采用的是一种**混合策略**——用 class 来定义核心的类型骨架，用组合（Composition）和 Mixin 来处理横切的能力扩展。

这种策略的核心原则来自 GoF 的**"组合优于继承"（Composition over Inheritance）**原则：

> **优先使用对象组合而不是类继承来达到复用的目的。**

```javascript
// 组合式类设计示例

// 定义可复用的"行为类"（不是用来继承的，是用来嵌入的）
class Validator {
  #rules = [];
  addRule(rule) { this.#rules.push(rule); return this; }
  validate(target) {
    for (let rule of this.#rules) {
      const result = rule.check(target);
      if (!result.valid) return { valid: false, error: result.error };
    }
    return { valid: true };
  }
}

class EventEmmiter {
  #events = {};
  on(event, handler) {
    (this.#events[event] ||= []).push(handler);
    return this;
  }
  emit(event, ...args) {
    (this.#events[event] ||= []).forEach(h => h(...args));
  }
  off(event, handler) {
    this.#events[event] = (this.#events[event] ||= [])
      .filter(h => h !== handler);
  }
}

class CacheManager {
  #cache = new Map();
  #ttl = new Map();
  get(key) { return this.#cache.get(key); }
  set(key, value, ttlMs = 0) {
    this.#cache.set(key, value);
    if (ttlMs > 0) {
      this.#ttl.set(key, setTimeout(() => this.#cache.delete(key), ttlMs));
    }
  }
  invalidate(key) {
    this.#cache.delete(key);
    clearTimeout(this.#ttl.get(key));
  }
}

// 主类通过组合（has-a）来获得这些能力，而非继承（is-a）
class UserService {
  // 组合：UserService "has-a" Validator、EventEmitter、CacheManager
  #validator = new Validator();
  #events = new EventEmmiter();
  #cache = new CacheManager();

  constructor(database) {
    this.db = database;
    this.#setupValidators();
  }

  #setupValidators() {
    this.#validator
      .addRule({
        check: (u) => ({ valid: typeof u.name === 'string' && u.name.length >= 2, error: '名字太短' })
      })
      .addRule({
        check: (u) => ({ valid: /^\w+@\w+\.\w+$/.test(u.email), error: '邮箱格式错误' })
      });
  }

  async createUser(userData) {
    // 使用组合来的 Validator
    const validation = this.#validator.validate(userData);
    if (!validation.valid) throw new Error(validation.error);

    // 数据库操作
    const user = await this.db.users.insert(userData);

    // 使用组合来的 EventEmitter
    this.#events.emit('user:created', user);

    // 使用组合来的 CacheManager
    this.#cache.set(`user:${user.id}`, user, 300000); // 缓存5分钟

    return user;
  }

  // 对外暴露订阅接口
  onUserCreated(callback) { this.#events.on('user:created', callback); return this; }

  // 对外暴露缓存查询
  getUserFromCache(id) { return this.#cache.get(`user:${id}`); }
}

// 使用
let userService = new UserService(dbConnection);

userService.onUserCreated(user => {
  console.log(`🎉 新用户注册: ${user.name}`);
});

await userService.createUser({ name: '王五', email: 'wangwu@test.com' });
// 🎉 新用户注册: 王五
```

注意这里的 `UserService` 并没有 `extends` 任何类——它通过**持有** `Validator`、`EventEmitter` 和 `CacheManager` 的实例来获得这些能力。这就是组合（Composition）：**UserService has a Validator**，而不是 **UserService is a Validator**。

组合的优势在于：
- 每个能力模块都可以**独立开发和测试**
- 能力的替换极其简单——换一个缓存策略只需传入不同的 `CacheManager` 实现
- 不存在多层继承带来的"脆弱基类问题"（ Fragile Base Class Problem）
- 类型关系保持简洁——`instanceof UserService` 就是 `UserService`，不会莫名其妙变成 `Validator` 的实例

### JavaScript 特有的灵活性：__proto__ 与动态原型链

JavaScript 提供了一些在其他语言中罕见的底层能力，让你可以在运行时修改对象的原型链。虽然日常开发中很少用到（也不推荐滥用），但在某些极端场景下它们能救命：

```javascript
// 动态切换行为模式的示例

// 定义一组不同的"行为原型"
const normalMode = {
  attack(target) { return `${this.name} 普通攻击了 ${target}，造成 ${this.str} 点伤害`; },
  defend() { return `${this.name} 进入防御姿态`; },
  describe() { return `${this.name} [普通模式] HP:${this.hp} STR:${this.str}`; }
};

const berserkMode = {
  attack(target) {
    const dmg = this.str * 2;
    this.hp -= 5;  // 狂暴模式每次攻击自损
    return `${this.name} 🔥狂暴攻击了 ${target}，造成 ${dmg} 点伤害！（自身损失5HP）`;
  },
  defend() { return `${this.name} 狂暴状态下无法防御！继续攻击！`; },
  describe() { return `${this.name} 🔥[狂暴模式] HP:${this.hp} STR:${this.str*2} ⚠️每回合自损5HP`; }
};

const stealthMode = {
  attack(target) {
    const dmg = this.str * 3;  // 暴击倍率高
    return `${this.name} 🗡️背刺了 ${target}，造成 ${dmg} 点暴击伤害！`;
  },
  defend() { return `${this.name} 🌫️ 进入潜行状态，闪避率大幅提升`; },
  describe() { return `${this.name} 🗡️[潜行模式] HP:${this.hp} STR:${this.str} 🌫️高闪避`; }
};

// 创建一个角色
const hero = {
  name: '暗影刺客',
  hp: 100,
  str: 20,
  __proto__: normalMode  // 初始原型指向 normalMode
};

hero.describe();  // 暗影刺客 [普通模式] HP:100 STR:20
hero.attack('史莱姆');  // 普通攻击了 史莱姆...

// 动态切换原型 —— 切换到狂暴模式
Object.setPrototypeOf(hero, berserkMode);
hero.describe();  // 暗影刺客 🔥[狂暴模式] HP:100 STR:40 ⚠️每回合自损5HP
hero.attack('哥布林');  // 🔥狂暴攻击了 哥布林...
// hero.hp 变成了 95

// 再切换到潜行模式
Object.setPrototypeOf(hero, stealthMode);
hero.describe();  // 暗影刺客 🗡️[潜行模式] HP:95 STR:20 🌫️高闪避
hero.attack('巨龙');  // 🗡️背刺了 巨龙...
```

`Object.setPrototypeof()` 允许你在运行时改变对象的原型指向。这意味着同一个对象在不同时期可以有完全不同的行为——而不需要创建新的实例、不需要修改对象的任何自有属性。这种能力在某些特定的设计模式（如状态模式 State Pattern、策略模式 Strategy Pattern）中非常有用。

> **性能警告**：现代引擎对 `__proto__` 的修改已经做了大量优化，但频繁修改原型链仍然会影响 V8 的优化编译（ICs / TurboFan）。在生产环境的性能敏感路径中应谨慎使用。

## 总结：超越非此即彼的思维陷阱

### 核心结论速查表

| 维度 | 类继承 (`class` + `extends`) | 原型继承 (`Object.create` + Mixin) |
|------|-------------------------------|-------------------------------------|
| **哲学根源** | 柏拉图理念论——先有模板再有实例 | 达尔文进化论——从现有事物演化出新事物 |
| **核心关系** | "is-a"（是一个） | "delegate-to"（委托给）/ "has-a"（拥有） |
| **最佳适用场景** | 清晰的类型层级、多态分发、框架约束的环境 | 灵活的能力组合、动态行为扩展、插件系统 |
| **优势** | 结构清晰、IDE友好、`instanceof`支持、多态 | 灵活无拘束、组合自由、运行时可变 |
| **劣势** | 单继承限制、耦合度高、过度设计风险 | 缺乏类型标识、调试困难、容易混乱 |
| **内存效率** | ★★★★★ 方法共享在原型上 | ★★☆☆☆ 取决于实现方式 |
| **学习曲线** | 对 OOP 背景者极低 | 需要深入理解原型链机制 |
| **TypeScript 友好度** | ★★★★★ 完美支持 | ★★☆☆☆ 类型推断困难 |

### 最终建议

不要把类继承和原型继承看作是"非此即彼"的对立关系。它们是同一门语言中两种互补的工具，各有各的最佳击球区：

- **当你需要表达"是什么"的关系时**——用户是一种账户、管理员是一种用户、超级管理员是一种管理员——使用 **类继承**
- **当你需要表达"能做什么"的关系时**——这个组件能点击、能禁用、能动画、能主题化——使用 **原型/Mixin**
- **当你需要两者兼得时**——用 class 定义类型骨架，用组合来引入外部能力

最重要的是：**不要因为只会其中一种就否认另一种的价值**。一个成熟的 JavaScript 开发者应该能够根据问题的性质自由切换范式，而不是拿着锤子到处找钉子。

> **编程范式的终极智慧不在于证明"我的方式比你的好"，而在于理解每种方式的本质和边界，在最恰当的时刻拿出最合适的工具。** 类继承和原型继承不是敌人——它们是同一枚硬币的两面，共同构成了 JavaScript 这个独特而强大的面向对象世界的完整图景。
