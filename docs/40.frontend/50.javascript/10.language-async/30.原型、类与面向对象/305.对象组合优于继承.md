# 对象组合优于继承：设计哲学、模式与实践

## 一条改变了整个软件行业的设计原则

在软件工程的历史长河中，很少有哪一条原则能像**"组合优于 inheritance）**这样简洁有力，却又影响深远。这八个字出自 1994 年出版的经典著作《设计模式：可复用面向对象软件的基础》（即大名鼎鼎的"GoF 之书"），由四位作者（Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides，合称"Gang of Four"）共同提出。

但这条原则的价值远不止于一句格言。它代表了一种深刻的思维转变——从"通过分类来组织世界"转向"通过组装来构建系统"。这种转变不仅影响你如何写代码，更从根本上重塑你对"什么是好的软件设计"的理解。

本文将从哲学根源出发，深入剖析"组合"与"继承"的本质差异，然后用大量 JavaScript 实例展示如何在实战中践行这条原则。无论你是刚接触面向对象设计的初学者，还是已经写了很多年 `class` + `extends` 的老手，都能从中获得新的启发。

### 为什么这条原则如此重要？

很多开发者在学习面向对象编程时，被灌输的第一件事就是"继承"——`class Dog extends Animal`、`class Manager extends Employee`。继承看起来那么自然、那么强大：子类自动获得父类的所有能力，只需添加或修改自己特有的部分。这似乎是代码复用的终极方案。

然而，当你在实际项目中大量使用继承后，迟早会撞上一堵无形的墙：

- **脆弱基类问题（Fragile Base Class Problem）**：修改父类的一个方法，可能导致所有子类出现意想不到的行为变化。因为子类可能以各种方式依赖于父类方法的实现细节。
- **组合爆炸问题**：当你需要让一个类同时具备多种能力时（比如既会飞又会游又能跑的动物），单继承体系迫使你创建大量的中间类来排列组合。
- **紧耦合问题**：子类与父类之间是强耦合关系——你不能在不影响子类的情况下替换父类的实现。
- **层级僵化问题**：一旦建立了深层继承链（A → B → C → D → E），任何层级的变更都会产生连锁反应，重构变得极其困难。

"组合优于继承"正是为了应对这些问题而提出的设计哲学。它不是说"永远不要用继承"，而是说：**在绝大多数情况下，组合是一种更灵活、更安全、更易维护的复用手段。**

### 通俗类比：乐高积木 vs 俄罗斯套娃

要理解"组合"和"继承"的区别，没有比玩具更好的类比了：

**继承就像俄罗斯套娃（Matryoshka Dolls）**：
每个套娃内部嵌套着一个更小的套娃。大的套着中的，中的套着小的，小的套着更小的。每一层都"继承"了外层的形状（都是圆滚滚的人形），但又在内层做了自己的修饰（不同的花纹、不同的表情）。问题是：
- 每个内层娃娃都被永久地锁定在外层里面——你不能把 A 家的大壳套在 B 家的小娃娃上
- 如果你想改变最外层娃娃的颜色，所有内层娃娃都会受影响（它们被包在里面）
- 你不能把同一个内层娃娃同时放到两个外层里

**组合就像乐高积木（LEGO Bricks）**：
每种零件都是一个独立的标准件——有车轮、有车窗、有底盘、有驾驶舱。你可以用这些零件自由拼装出汽车、飞机、城堡、机器人。关键特点：
- 零件之间没有永久的归属关系——同一批轮子今天装在跑车上，明天可以装在飞机上
- 更换任何一个零件都不会影响其他零件
- 新的零件随时可以被发明出来并融入现有的体系中
- 你可以用有限的零件类型拼装出几乎无限种不同的成品

GoF 之书的核心洞察就是：**大多数情况下，你应该用乐高的方式（组合）来构建系统，而不是俄罗斯套娃的方式（继承）。**

## 理论篇：深入理解"组合"与"继承"

### 继承的本质："is-a"关系及其代价

从语义上说，继承表达的是一种 **"is-a"（是一个）** 关系：

- 狗 **是 一种** 动物
- 圆形 **是一种** 形状
- 管理员 **是 一种** 用户
- 萨摩萨 **是一种** 披萨

这种关系在现实世界中非常直观，这也是为什么初学者觉得继承很自然的原因——它符合我们对世界的基本认知方式。

但问题在于，**"is-a"关系在编程世界中往往不像看起来那么稳固**。让我们看几个经典的反例：

**反例一：正方形不是矩形？**

在数学中，正方形确实是一种特殊的矩形（四边相等的长方形）。按照直觉，我们应该这样写：

```javascript
class Rectangle {
  constructor(width, height) {
    this.width = width;
    this.height = height;
  }
  setWidth(w) { this.width = w; }
  setHeight(h) { this.height = h; }
  getArea() { return this.width * this.height; }
}

class Square extends Rectangle {
  // 正方形的宽和高必须始终相等
  constructor(side) {
    super(side, side);
  }

  setWidth(w) {
    super.setWidth(w);   // 设置宽
    super.setHeight(w);  // 必须同步设置高！否则就不是正方形了
  }

  setHeight(h) {
    super.setHeight(h);
    super.setWidth(h);   // 同样必须同步
  }
}
```

这里出现了著名的**里氏替换原则（Liskov Substitution Principle, LSP）违反**。LSP 要求：**子类的实例应该可以在任何期望父类实例的地方使用，而不改变程序的正确性。**

但在上面的例子中，如果你有一个函数 `makeDouble(rect)` 通过分别设置宽和高为原来的两倍来放大矩形，传入一个 `Square` 实例时，行为就出了问题——`Square.setWidth(2w)` 会同时改变高度，导致最终结果不是预期的 \(4wh\) 而是 \(2w \times 2w = 4w^2\)。

问题的根源在于：**正方形虽然在几何定义上是矩形的特化，但在行为契约（Behavioral Contract）层面上，它与矩形并不兼容。** "保持宽高相等"这个约束破坏了父类"宽高可以独立设置"的隐含假设。这就是为什么数学上的"is-a"不能直接映射到程序中的继承关系的典型例子。

**反例二：鸵鸟不是鸟？**

```javascript
class Bird {
  fly() { console.log('正在飞行'); }
}

class Ostrich extends Bird {
  fly() {
    throw new Error("鸵鸟不会飞！");
  }
}

function makeBirdFly(bird) {
  bird.fly();  // 如果传入 Ostrich 实例... 💥
}
```

鸵鸟在生物学分类中属于鸟类（Aves 纲）。但如果你让 `Ostrich` 继承 `Bird` 并强制实现 `fly()` 方法，你要么抛出异常（违反 LSP），要么提供一个空实现（违反接口契约）。两种选择都很糟糕。

这个例子揭示了一个更深层次的问题：**继承要求子类完全兼容父类的行为接口，但现实世界的分类体系中，特化往往伴随着能力的丧失或变异。**

**反例三：能力组合导致的继承灾难**

这是最常见也最痛苦的问题。当一个实体需要同时具备多种不相关的能力时，继承体系会迅速崩塌：

```javascript
// 尝试用继承来表示"鸭子会走、会游泳、会飞"
class Animal { /* ... */ }
class Walker extends Animal { walk() { } }         // 会走的动物
class Swimmer extends Animal { swim() { } }       // 会游泳的动物
class Flyer extends Animal { fly() { } }           // 会飞的动物

// 鸭子需要三种能力！怎么办？

// 方案 A：多层继承（JavaScript 不支持多继承）
// class WalkingSwimmer extends Swimmer extends Walker { }  // 太荒谬了
// class Duck extends ???  // 应该继承谁？

// 方案 B：强行归入某一支
class Duck extends Walker { }     // 那游泳和飞呢？手动加？
Duck.prototype.swim = function () { };
Duck.prototype.fly = function () { };
// 结果：Duck 和其他 Walker 毫无关系，但继承了 Walker 可能不需要的东西

// 方案 C：搞一个大基类
class CapableAnimal extends Animal {
  walk() { }
  swim() { }
  fly() { }
}
class Duck extends CapableAnimal { }
class Fish extends CapableAnimal { }  // 但鱼不会走也不会飞啊...
// 大基类变成了"上帝类"（God Object），违背了接口隔离原则
```

无论怎么选，都不优雅。问题的本质是：**继承是一条单行道，而能力的组合是一个多维空间。** 用一维的结构去模拟多维的需求，必然产生扭曲。

### 组合的本质："has-a"关系及其力量

如果说继承表达的是 **"is-a"（是什么）** ，那么组合表达的则是 **"has-a"（有什么）** 或 **"can-do"（能做什么）**：

- 汽车 **拥有** 一个引擎、四个车轮、一个方向盘
- 用户 **拥有** 一个个人资料、一组权限列表、一个偏好设置
- 订单 **包含** 多个订单项、一个收货地址、一个支付记录

组合的思想极其简单：**不在对象内部通过继承来获得能力，而是将其他对象作为自己的组成部分（属性）持有，通过调用这些组成部分的方法来实现功能委托。**

```javascript
// ====== 继承方式 ======
class AuthenticatedUser extends User {
  login(password) { /* ... */ }
  logout() { /* ... */ }
  changePassword(oldPwd, newPwd) { /* ... */ }
}
// User 必须知道 Authentication 的所有细节
// 且 User 和 Authentication 永久绑定在一起

// ====== 组合方式 ======
class AuthenticationService {
  login(user, password) { /* ... */ }
  logout(user) { /* ... */ }
  changePassword(user, oldPwd, newPwd) { /* ... */ }
}

class User {
  #auth;
  constructor(authService) {
    this.#auth = authService;  // User 拥有一个认证服务
  }

  login(password) {
    return this.#auth.login(this, password);  // 委托给认证服务
  }
}
```

对比两种方式，组合的优势一目了然：

1. **解耦**：`User` 不需要知道 `AuthenticationService` 的内部实现。只要服务实现了正确的接口（login/logout/changePassword），User 就能正常工作。将来如果要从本地认证切换到 OAuth，只需换一个 `AuthenticationService` 的实现，`User` 类不需要改一行代码。

2. **灵活性**：同一个 `AuthenticationService` 实例可以被多个 `User` 共享（节省内存），也可以给每个 `User` 分配不同的认证策略（比如管理员用双因素认证，普通用户用密码认证）。

3. **可测试性**：单元测试时，你可以轻松地用一个 mock 对象替代真实的 `AuthenticationService`，而无需创建完整的继承体系。

4. **运行时可变**：你甚至可以在运行期间动态更换 `User` 的认证服务（比如用户升级到了 VIP，切换到更安全的认证方式）。而继承一旦在编译/定义阶段确定，就很难更改。

### GoF 之书的原话解读

让我们回到源头，看看 GoF 到底说了什么。在《设计模式》第一章的原则部分，原文写道：

> **"Prefer object composition over class inheritance."**
> （优先使用对象组合而非类继承。）

紧接着的解释更加深刻：

> **"You'll find more flexibility using composition to assemble behavior from contained objects than you'll get from inheriting it from a single parent class."**
> （你会发现在组合中使用包含对象来组装行为，比从单一父类继承行为具有更大的灵活性。）
>
> **"Ideally, you shouldn't have to create new components just to reuse parts of an existing component's implementation. You should be able to reuse the implementation simply by composing objects."**
> （理想情况下，你不应该仅仅为了复用现有组件的部分实现而去创建新的组件。你应该能够简单地通过组合对象来复用实现。）

这段话中有三个关键词值得反复品味：

**"Contained objects"（被包含的对象）**：组合的核心是被包含者（Component）与容器（Container）之间的协作关系。容器持有对被包含者的引用，在需要时将工作委派出去。这是一种**水平方向的协作**——对象与对象之间是平等的伙伴关系，而不是上下级的父子关系。

**"Assemble behavior"（组装行为）**：组合不是简单地"拥有"一个对象，而是通过精心设计各部件之间的交互来**组装出期望的行为**。这意味着你需要思考：部件之间如何通信？谁来协调？错误如何传播？状态如何共享？好的组合设计需要精心的接口规划。

**"Flexibility"（灵活性）**：这是组合相对于继承的最大优势所在。继承的灵活性受限于语言的单继承限制（大部分语言）、编译时的类型绑定、以及父类接口的刚性约束。而组合的灵活性只受限于你的想象力——你可以在运行时任意替换部件、增减能力、重组结构。

### 哲学延伸：从还原论到整体论

如果我们把视野拉得更远一些，"组合优于继承"其实反映了计算机科学乃至整个科学思想史上的一个宏大转变——**从还原论（Reductionism）到整体论（Holism/Holism）的转变**。

**还原论的思维方式**是：要理解一个复杂系统，就把分解成更小的部分，直到每个部分都简单到不能再分解为止。然后，理解了所有部分，你就理解了整体。在编程中，这表现为：把系统分解成一个个类，通过继承建立类之间的层级关系，认为只要每个类都正确了，整个系统就正确了。这是一种"自顶向下"的、分解式的思维方式。

**整体论的思维方式**是：整体大于部分之和。系统的性质不仅取决于它的组成部分，更取决于组成部分之间的**关系和交互方式**。你不能通过孤立地研究每个部分来理解整体——你必须研究它们是如何连接、如何协作、如何涌现出整体行为的。在编程中，这表现为：重要的不是单个类的完美设计，而是类与类之间如何组合、如何通信、如何形成更大的架构。

"组合优于继承"正是整体论思想在面向对象设计中的具体体现。它告诉我们：**不要执着于设计完美的类层级（还原论式的分解），而应该关注如何让独立、自治的组件通过良好的接口进行有机的组合（整体论式的集成）。**

> 这种思想的先驱可以追溯到哲学家亚里士多德的**"整体先于部分"（Whole precedes the part）**命题，以及后来系统论创始人贝塔朗菲（Ludwig von Bertalanffy）的一般系统理论（General Systems Theory）。虽然我们不需要成为哲学家才能写出好代码，但了解这些思想渊源能帮助我们更深刻地理解设计原则背后的智慧。

## JavaScript 中的组合模式详解

### 模式一：直接属性组合（Has-A Composition）

最基础也是最常见的组合形式：在一个类的实例中直接持有其他对象的引用，通过调用这些对象的方法来完成工作。

```javascript
// ====== 能力模块：独立的、可复用的类 ======

// 引擎 —— 只关心如何产生动力
class Engine {
  #horsepower;

  constructor(hp) {
    this.#horsepower = hp;
  }

  start() {
    console.log(`🔑 引擎启动！${this.#horsepower}HP 马力已就绪`);
    return { rpm: 800 + this.#horsepower * 10, torque: this.#horsepower * 1.5 };
  }

  stop() {
    console.log('🔌 引擎熄火');
    return { rpm: 0, torque: 0 };
  }

  get specs() { return { hp: this.#horsepower }; }
}

// 音响系统 —— 只关心如何播放声音
class SoundSystem {
  #brand;
  #speakers;

  constructor(brand, speakers) {
    this.#brand = brand;
    this.#speakers = speakers;
  }

  playMusic(song) {
    console.log(`🎵 ${this.#brand} ${this.#speakers}声道: 正在播放《${song}》`);
  }

  mute() {
    console.log('🔇 已静音');
  }

  get specs() { return { brand: this.#brand, speakers: this.#speakers }; }
}

// 导航系统 —— 只关心如何规划路线
class NavigationSystem {
  #mapVersion;
  constructor(version) { this.#mapVersion = version; }

  navigate(destination) {
    console.log(`🗺️ [地图 v${this.#mapVersion}] 规划路线 → ${destination}`);
    return { route: '最优路径', distance: '12.5km', eta: '18分钟' };
  }

  get specs() { return { mapVersion: this.#mapVersion }; }
}

// ====== 通过组合来"组装"汽车 ======

class Car {
  // 组合：Car "has-an" Engine, "has-a" SoundSystem, "has-a" NavigationSystem
  engine;
  sound;
  navigation;

  constructor(make, model, engine, sound, nav) {
    this.make = make;
    this.model = model;
    this.engine = engine;        // 注入引擎
    this.sound = sound;          // 注入音响
    this.navigation = nav;      // 注入导航
  }

  startTrip(destination) {
    console.log(`\n=== ${this.make} ${this.model} 出发！===`);

    // 委托给引擎
    const engineStatus = this.engine.start();

    // 委托给导航
    const route = this.navigation.navigate(destination);

    // 委托给音响
    this.sound.playMusic('公路之歌');

    return {
      vehicle: `${this.make} ${this.model}`,
      engine: this.engine.specs,
      sound: this.sound.specs,
      nav: this.navigation.specs,
      route,
      engineStatus
    };
  }
}

// ====== 使用：自由搭配不同配置 ======

// 经济型配置
let budgetCar = new Car(
  '五菱', '宏光MINI',
  new Engine(68),                    // 小马力引擎
  new SoundSystem('原厂', 2),        // 2喇叭音响
  null                               // 没有导航
);

// 豪华型配置
let luxuryCar = new Car(
  '奔驰', 'S500',
  new Engine(450),                   // 大马力引擎
  new SoundSystem('Burmester', 15), // 高端音响
  new NavigationSystem('2026')      // 最新版导航
);

budgetCar.startTrip('菜市场');
console.log('\n');
luxuryCar.startTrip('五星级酒店');

// 还可以随时更换配件
luxuryCar.engine = new Engine(600);  // 升级引擎！
luxuryCar.sound = new SoundSystem('B&O', 19);  // 升级音响！
luxuryCar.startTrip('赛车场');
```

这个例子的美妙之处在于**完全的解耦和自由度**：
- `Engine` 不需要知道它被安装在哪种车上，`SoundSystem` 不知道谁在使用它，`NavigationSystem` 不在乎目的地在哪里
- `Car` 不需要知道引擎是怎么工作的、音响是什么牌子的、导航用什么算法——它只知道这三个组件提供了哪些接口
- 创建不同配置的汽车只需要传入不同的组件实例，不需要创建任何子类
- 运行时可以随时更换任何组件（比如升级引擎），不需要重新定义一个新的汽车类

这就是组合的力量：**每个组件只做一件事并做好，然后通过组合创造出无限的可能。**

### 模式二：委托模式（Delegation Pattern）

委托是组合的一种特殊形式——容器对象不只是持有被包含对象的引用，而是将自己接收到的请求**原封不动地转发**给被包含对象。这在 JavaScript 中极其自然，因为语言本身就支持属性的动态查找和方法的 `call`/`apply` 机制。

```javascript
// ====== 经典委托模式 ======

// 一个"可保存"的功能模块
const Savable = {
  save() {
    if (!this.id) this.id = Date.now().toString(36);
    console.log(`💾 [SAVE] ${this.constructor.name || 'Object'}#${this.id} 已保存`);
    return { id: this.id, data: JSON.stringify(this), timestamp: Date.now() };
  },

  load(savedData) {
    const data = JSON.parse(savedData.data);
    Object.assign(this, data);
    console.log(`📂 [LOAD] ${this.constructor.name || 'Object'}#${this.id} 已恢复`);
    return this;
  }
};

// 一个"可验证"的功能模块
const Validatable = {
  validate(schema) {
    const errors = [];
    for (let [field, rules] of Object.entries(schema)) {
      const value = this[field];
      for (let rule of rules) {
        if (!rule.check(value)) {
          errors.push({ field, message: rule.message, value });
        }
      }
    }
    if (errors.length > 0) {
      console.error(`❌ [VALIDATE] 校验失败:`, errors);
      return { valid: false, errors };
    }
    console.log(`✅ [VALIDATE] 校验通过`);
    return { valid: true };
  }
};

// 一个"可序列化"的功能模块
const Serializable = {
  serialize() {
    const obj = {};
    for (let key of Object.getOwnPropertyNames(this)) {
      const val = this[key];
      if (typeof val !== 'function' && !key.startsWith('_')) {
        obj[key] = val;
      }
    }
    return JSON.stringify(obj);
  }
};

// 主类：通过委托获得上述所有能力
class Task {
  id;
  title;
  status = 'pending';
  priority = 'medium';
  createdAt;
  completedAt;

  constructor(title, priority = 'medium') {
    this.title = title;
    this.priority = priority;
    this.createdAt = new Date().toISOString();
  }

  complete() {
    this.status = 'completed';
    this.completedAt = new Date().toISOString();
    console.log(`✅ 任务完成: ${this.title}`);
    return this;
  }

  // ====== 委托方法 ======
  // 将调用转发给混入的能力模块
  save() { return Savable.save.call(this); }
  load(data) { return Savable.load.call(this, data); }
  validate(schema) { return Validatable.validate.call(this, schema); }
  serialize() { return Serializable.serialize.call(this); }
}

// 使用
let task1 = new Task('完成周报', 'high');
task1.validate({
  title: [
    { check: v => v && v.length >= 2, message: '标题至少2个字符' },
    { check: v => v.length <= 100, message: '标题不超过100字符' }
  ],
  priority: [
    { check: v => ['low', 'medium', 'high'].includes(v), message: '优先级必须是 low/medium/high' }
  ]
});
// ✅ [VALIDATE] 校验通过

task1.complete();
let savedData = task1.save();
// 💾 [SAVE] Task#xxx 已保存

// 从保存的数据恢复
let task2 = new Task();
task2.load(savedData);
// 📂 [LOAD] Task#xxx 已恢复
console.log(task2.title);       // "完成周报"
console.log(task2.status);      // "completed"

console.log(task1.serialize());
// {"title":"完成周报","status":"completed",...}
```

委托模式的精髓在于：**Task 类本身只定义核心业务逻辑（title、status、complete），而跨切关注点（保存、验证、序列化）全部通过委托交给外部模块处理。** 这些外部模块可以被任意数量的类复用——不仅是 `Task`，`User`、`Order`、`Document` 也同样可以通过委托来获得相同的能力。

### 模式三：Mixin 混入（JavaScript 特有的组合魔法）

JavaScript 作为一门动态语言，有一种独特的组合方式——利用 `Object.assign()` 或展开运算符将多个对象的能力"合并"到一个目标对象上。这种方式介于组合和继承之间，通常被称为 **Mixin（混入）模式**。

```javascript
// ====== 定义一组 Mixin 能力工厂 ======

// 能力：事件发射
function EventEmitter() {
  const listeners = {};

  return {
    on(event, handler) {
      (listeners[event] ??= []).push(handler);
      return this;  // 链式调用
    },

    emit(event, ...args) {
      (listeners[event] ?? []).forEach(h => h.apply(this, args));
      return this;
    },

    off(event, handler) {
      if (listeners[event]) {
        listeners[event] = listeners[event].filter(h => h !== handler);
      }
      return this;
    }
  };
}

// 能力：状态管理
function StateManager(initialState = {}) {
  let state = { ...initialState };
  const watchers = {};

  return {
    getState(key) {
      return key !== undefined ? state[key] : { ...state };
    },

    setState(partial) {
      const oldState = { ...state };
      Object.assign(state, partial);

      // 通知变化的字段
      for (let key of Object.keys(partial)) {
        (watchers[key] ??= []).forEach(cb =>
          cb(state[key], oldState[key], key)
        );
      }

      return state;
    },

    watch(key, callback) {
      (watchers[key] ??= []).push(callback);
      // 立即返回当前值
      callback(state[key], undefined, key);
      return this;  // 用于取消订阅的句柄
    }
  };
}

// 能力：日志装饰
function Logger(prefix = '') {
  return {
    log(action, data) {
      const ts = new Date().toISOString();
      console.log(`[${ts}] [${prefix || this.name || 'Obj'}] ${action}`, data ?? '');
      return this;
    },

    error(action, err) {
      const ts = new Date().toISOString();
      console.error(`[${ts}] [${prefix || this.name || 'Obj'}] ERROR ${action}:`, err?.message ?? err);
      return this;
    }
  };
}

// 能力：撤销/重做
function UndoRedo(maxHistory = 50) {
  const history = [];
  let index = -1;

  return {
    pushState(snapshot) {
      // 截断当前位置之后的历史
      history.splice(index + 1);
      history.push(JSON.stringify(snapshot));

      if (history.length > maxHistory) {
        history.shift();
      } else {
        index++;
      }
      return this;
    },

    undo() {
      if (index < 0) { console.log('⏪ 已经是最早的状态了'); return null; }
      index--;
      return JSON.parse(history[index]);
    },

    redo() {
      if (index >= history.length - 1) { console.log('⏩ 已经是最新状态了'); return null; }
      index++;
      return JSON.parse(history[index]);
    },

    get canUndo() { return index >= 0; },
    get canRedo() { return index < history.length - 1; },
    get historyLength() { return history.length; }
  };
}

// ====== 自由组合创建一个"智能表单" ======

function createSmartForm(formName, fields) {
  // 用展开运算符将所有 Mixin 能力合并到一个对象上
  const form = Object.assign(
    // 基础属性
    {
      name: formName,
      fields,
      values: {},
      errors: {},
      dirty: false
    },

    // 混入所有能力！
    EventEmitter(),
    StateManager({ values: {}, errors: {}, dirty: false }),
    Logger(formName),
    UndoRedo()
  );

  // 添加业务方法
  form.setFieldValue = function (fieldName, value) {
    const oldValues = { ...this.getState().values };
    this.setState({
      values: { ...this.getState().values, [fieldName]: value },
      dirty: true
    });

    this.pushState(oldValues);  // 记录到撤销历史
    this.emit('field:changed', { fieldName, value });
    this.log('FIELD_SET', { fieldName, value });
  };

  form.validateField = function (fieldName, rules) {
    const value = this.getState().values[fieldName];
    const fieldErrors = [];

    for (let rule of rules) {
      if (!rule.check(value)) {
        fieldErrors.push(rule.message);
      }
    }

    const newErrors = { ...this.getState().errors };
    if (fieldErrors.length > 0) {
      newErrors[fieldName] = fieldErrors;
    } else {
      delete newErrors[fieldName];
    }

    this.setState({ errors: newErrors });
    this.log('VALIDATE_FIELD', { fieldName, valid: fieldErrors.length === 0 });
    return fieldErrors.length === 0;
  };

  form.submit = function () {
    this.log('SUBMIT', this.getState().values);

    // 检查是否有错误
    const errorCount = Object.keys(this.getState().errors).length;
    if (errorCount > 0) {
      this.error('SUBMIT_FAILED', `${errorCount} 个字段校验未通过`);
      this.emit('submit:error', this.getState().errors);
      return false;
    }

    this.emit('submit:success', this.getState().values);
    this.setState({ dirty: false });
    this.log('SUBMIT_SUCCESS', this.getState().values);
    return true;
  };

  form.undoChange = function () {
    const prevState = this.undo();
    if (prevState) {
      this.setState(prevState);
      this.log('UNDO', { values: prevState.values });
      this.emit('change:undone', prevState.values);
    }
    return prevState;
  };

  return form;
}

// ====== 使用 ======

const registrationForm = createSmartForm('用户注册', {
  username: { label: '用户名', type: 'text' },
  email: { label: '邮箱', type: 'email' },
  age: { label: '年龄', type: 'number' }
});

// 监听状态变化
registrationForm.watch('dirty', (isDirty) => {
  console.log(`  👀 表单${isDirty ? '已被修改' : '已重置'}`);
});

registrationForm.on('field:changed', ({ fieldName }) => {
  console.log(`  📝 字段 "${fieldName}" 发生变化`);
});

// 操作表单
registrationForm.setFieldValue('username', 'zhangsan');
// [LOG] FIELD_SET ...
// 👀 表单已被修改
// 📝 字段 "username" 发生变化

registrationForm.setFieldValue('email', 'zhang@test.com');
registrationForm.setFieldValue('age', '25');

registrationForm.validateField('username', [
  { check: v => v && v.length >= 2, message: '太短' },
  { check: v => !/\d/.test(v), message: '不能含数字' }
]);

registrationForm.submit();  // ✅ 提交成功

// 撤销操作
registrationForm.undoChange();
// [LOG] UNDO ...
// 👀 表单已被重置
// 📝 变更已撤销
```

这个 `createSmartForm` 工厂函数展示了 Mixin 模式的极致威力：**四种完全独立的能力（事件发射、状态管理、日志、撤销重做）被无缝地融合到一个普通的对象上**，而这个对象还拥有自己独有的业务方法。使用者根本不需要关心这些能力来自哪里——他们看到的是一个统一的、功能丰富的 API 表面。

更重要的是：**同样的四种 Mixin 能力可以用来创建完全不同的东西**——智能表格、游戏角色编辑器、API 请求构建器……只要换个名字、加点业务方法就行了。这就是代码复用的最高境界：**能力的生产与消费完全解耦。**

### 模式四：前向-后端组合（Forward-to-Backend Composition）

这是一种更隐蔽但也更常见的组合形式：一个对象将自身作为参数传递给它持有的另一个对象，让后者"回过来"操作自己。这在回调、策略模式和访问者模式中广泛使用。

```javascript
// ====== 策略接口：排序策略 ======

// 冒泡排序策略
const BubbleSortStrategy = {
  name: '冒泡排序',
  sort(arr, comparator) {
    console.log(`  🫧 使用 ${this.name}`);
    const result = [...arr];
    for (let i = 0; i < result.length - 1; i++) {
      for (let j = 0; j < result.length - 1 - i; j++) {
        if (comparator(result[j], result[j + 1]) > 0) {
          [result[j], result[j + 1]] = [result[j + 1], result[j]];
        }
      }
    }
    return result;
  }
};

// 快速排序策略
const QuickSortStrategy = {
  name: '快速排序',
  sort(arr, comparator) {
    console.log(`  ⚡ 使用 ${this.name}`);

    const quickSort = (arr, lo, hi) => {
      if (lo < hi) {
        const pivot = arr[hi];
        let i = lo - 1;
        for (let j = lo; j < hi; j++) {
          if (comparator(arr[j], pivot) <= 0) {
            i++;
            [arr[i], arr[j]] = [arr[j], arr[i]];
          }
        }
        [arr[i + 1], arr[hi]] = [arr[hi], arr[i + 1]];
        quickSort(arr, lo, i);
        quickSort(arr, i + 2, hi);
      }
    };

    const result = [...arr];
    quickSort(result, 0, result.length - 1);
    return result;
  }
};

// 归并排序策略
const MergeSortStrategy = {
  name: '归并排序',
  sort(arr, comparator) {
    console.log(`  🔀 使用 ${this.name}`);

    const merge = (left, right) => {
      const result = [];
      let i = 0, j = 0;
      while (i < left.length && j < right.length) {
        result.push(comparator(left[i], right[j]) <= 0 ? left[i++] : right[j++]);
      }
      return [...result, ...left.slice(i), ...right.slice(j)];
    };

    const ms = (arr) => {
      if (arr.length <= 1) return arr;
      const mid = Math.floor(arr.length / 2);
      return ms(arr.slice(0, mid)), ms(arr.slice(mid)));
    };

    return ms([...arr]).flat(arr.length);
  }
};

// ====== 排序器：通过组合持有策略 ======

class Sorter {
  #strategy;
  #comparator;

  constructor(strategy, comparator = (a, b) => a - b) {
    this.#strategy = strategy;
    this.#comparator = comparator;
  }

  // 核心方法：将自身的数据传递给策略去排序
  sort(data) {
    console.log(`\n开始排序 ${data.length} 个元素:`);
    const start = performance.now();
    const sorted = this.#strategy.sort(data, this.#comparator);
    const elapsed = performance.now() - start;
    console.log(`  ⏱️ 耗时 ${elapsed.toFixed(3)}ms`);
    return sorted;
  }

  // 可以在运行时切换策略！
  setStrategy(newStrategy) {
    this.#strategy = newStrategy;
    return this;  // 链式调用
  }

  setComparator(newComparator) {
    this.#comparator = newComparator;
    return this;
  }
}

// ====== 使用：同一个 Sorter，不同的策略 ======

let data = Array.from({ length: 20 }, () => Math.random() * 100);

let sorter = new Sorter(BubbleSortStrategy, (a, b) => a - b);
sorter.sort([...data]);           // 冒泡排序

sorter.setStrategy(QuickSortStrategy);
sorter.sort([...data]);           // 快速排序

sorter.setStrategy(MergeSortStrategy).setComparator((a, b) => b - a);  // 链式调用+降序
sorter.sort([...data]);           // 归并排序（降序）
```

这里的组合体现在两个层面：

**层面一：Sorter 持有 Strategy（静态组合）**。`Sorter` 内部持有一个排序策略对象，`sort()` 方法将数据和比较器一起传给策略去执行实际的排序算法。

**层面二：Strategy 回调 Sorter 的 Comparator（动态组合/双向通信）**。策略在排序过程中反复调用 `comparator(a, b)` 来决定元素顺序——这个 `comparator` 是 `Sorter` 提供的。策略不需要知道比较的具体规则，它只是信任 `Sorter` 给的"比较标准"。

这种**双向的、基于接口的组合**是策略模式（Strategy Pattern）的核心，也是依赖注入（Dependency Injection）的基础。它在框架设计中无处不在——Express 的中间件、Redux 的中间件、Koa 的洋葱模型、Angular 的 Provider 系统……本质上都是同一种思想的变体：**"我持有一个不知道具体实现的对象，我只管调用它的接口；至于它怎么做，我不关心。"**

## 实战篇：组合在真实项目中的应用

### 应用一：前端组件的能力组合

现代前端开发中的组件体系天然适合组合式设计。React、Vue 等框架的核心理念之一就是**组件组合（Component Composition）**：

```javascript
// ====== 一组独立的能力组件（Hooks/Composables）======

// 能力：获取窗口尺寸
function useWindowSize() {
  const size = reactive({ width: window.innerWidth, height: window.innerHeight });

  const onResize = () => {
    size.width = window.innerWidth;
    size.height = window.innerHeight;
  };

  onMounted(() => window.addEventListener('resize', onResize));
  onUnmounted(() => window.removeEventListener('resize', onResize));

  return { size, isMobile: computed(() => size.width < 768) };
}

// 能力：网络请求（带缓存、错误处理、加载状态）
function useApiRequest(urlFn) {
  const state = reactive({
    data: null,
    loading: false,
    error: null,
    lastFetched: null
  });

  const execute = async (...args) => {
    state.loading = true;
    state.error = null;
    try {
      const url = typeof urlFn === 'function' ? urlFn(...args) : urlFn;
      const response = await fetch(url);
      state.data = await response.json();
      state.lastFetched = new Date().toISOString();
    } catch (err) {
      state.error = err.message;
      throw err;
    } finally {
      state.loading = false;
    }
    return state.data;
  };

  const clearCache = () => { state.data = null; state.lastFetched = null; };

  return { ...toRefs(state), execute, clearCache };
}

// 能力：无限滚动
function useInfiniteScroll(loadMoreFn, options = {}) {
  const { threshold = 200 } = options;
  const containerRef = ref(null);
  const canLoadMore = ref(true);
  const loading = ref(false);

  const handleScroll = async () => {
    if (!containerRef.value) return;
    const { scrollTop, scrollHeight, clientHeight } = containerRef.value;

    if (scrollHeight - (scrollTop + clientHeight) < threshold) {
      if (canLoadMore.value && !loading.value) {
        loading.value = true;
        await loadMoreFn();
        loading.value = false;
      }
    }
  };

  onMounted(() => {
    containerRef.value?.addEventListener('scroll', handleScroll);
  });
  onUnmounted(() => {
    containerRef.value?.removeEventListener('scroll', handleScroll);
  });

  return { containerRef, canLoadMore, loading, setCanLoadMore: (v) => canLoadMore.value = v };
}

// 能力：键盘快捷键
function useKeyboardShortcuts(shortcuts) {
  const pressedKeys = new Set();

  const onKeyDown = (e) => {
    pressedKeys.add(e.key);
    const combo = Array.from(pressedKeys).join('+');

    if (shortcuts[combo]) {
      e.preventDefault();
      shortcuts[combo]();
    }
  };

  const onKeyUp = (e) => {
    pressedKeys.delete(e.key);
  };

  onMounted(() => {
    window.addEventListener('keydown', onKeyDown);
    window.addEventListener('keyup', onKeyUp);
  });
  onUnmounted(() => {
    window.removeEventListener('keydown', onKeyDown);
    window.removeEventListener('keyup', onKeyUp);
  });
}

// ====== 通过组合创建一个复杂的列表页面组件 ======

export default defineComponent({
  name: 'ProductListPage',
  setup() {
    // 组合四种独立能力！
    const { size, isMobile } = useWindowSize();
    const { data: products, loading, error, execute: fetchProducts } = useApiRequest(
      '/api/products'
    );
    const { containerRef, canLoadMore, loading: loadingMore, setCanLoadMore } =
      useInfiniteScroll(async () => {
        const nextProducts = await fetchProducts({ page: products.page + 1 });
        products.items.push(...nextProducts.items);
        products.page++;
        if (nextProducts.isLastPage) setCanLoadMore(false);
      });

    useKeyboardShortcuts({
      'Control+f': () => console.log('搜索'),
      'Control+r': () => fetchProducts(),  // 刷新
      Escape: () => console.log('关闭')
    });

    // 业务逻辑（只关注业务本身）
    const searchQuery = ref('');
    const selectedCategory = ref('all');
    const sortBy = ref('name');

    const filteredProducts = computed(() => {
      if (!products?.items) return [];
      return products.items
        .filter(p => p.name.includes(searchQuery.value))
        .filter(p => selectedCategory.value === 'all' || p.category === selectedCategory.value)
        .sort((a, b) => a[sortBy.value].localeCompare(b[sortBy.value]));
    });

    onMounted(fetchProducts);

    return {
      isMobile, products, loading, error,
      containerRef, canLoadMore, loadingMore,
      filteredProducts, searchQuery, selectedCategory, sortBy,
      fetchProducts
    };
  }
});
```

这个 Vue 3 组件的 `setup()` 函数就是一个**组合的杰作**：四种完全不相关的能力（响应式窗口监听、带缓存的 API 请求、无限滚动加载、全局快捷键）被干净地组合在一起，而组件本身的代码只需要关心筛选逻辑和 UI 渲染。每一种能力都可以独立开发、独立测试、独立地在其他组件中复用。这就是前端框架推崇的组合式设计理念的实际体现——Vue 3 的 Composition API 甚至把这个概念提升到了语言级别。

### 应用二：后端服务的中间件管道

Node.js 后端的 Express/Koa 框架是组合式设计的另一个典范。中间件（Middleware）本质上就是通过组合来构建请求处理管道：

```javascript
// ====== 独立的中间件组件 ======

// 日志中间件
function loggerMiddleware(options = { level: 'info' }) {
  return (ctx, next) => {
    const start = Date.now();
    console.log(`[${options.level}] --> ${ctx.method} ${ctx.url}`);

    // 将控制权交给下一个中间件
    return next()
      .then(() => {
        const ms = Date.now() - start;
        console.log(`[${options.level}] <-- ${ctx.method} ${ctx.url} ${ctx.status} (${ms}ms)`);
      });
  };
}

// 认证中间件
function authMiddleware(tokenValidator) {
  return (ctx, next) => {
    const token = ctx.headers['authorization']?.replace('Bearer ', '');
    const user = tokenValidator(token);

    if (!user) {
      ctx.status = 401;
      ctx.body = { error: '未授权' };
      return;  // 不调用 next() → 短路，后续中间件不执行
    }

    ctx.user = user;  // 将用户信息挂载到上下文
    return next();     // 放行
  };
}

// 限流中间件
function rateLimitMiddleware(store, options = { maxRequests: 100, windowMs: 60000 }) {
  return (ctx, next) => {
    const key = ctx.ip || 'unknown';
    const now = Date.now();

    if (!store[key]) {
      store[key] = { count: 1, resetAt: now + options.windowMs };
    } else {
      if (now > store[key].resetAt) {
        store[key] = { count: 1, resetAt: now + options.windowMs };
      } else {
        store[key].count++;
      }
    }

    if (store[key].count > options.maxRequests) {
      ctx.status = 429;
      ctx.body = { error: '请求过于频繁', retryAfter: Math.ceil((store[key].resetAt - now) / 1000) };
      return;  // 短路
    }

    ctx.set('X-RateLimit-Remaining', options.maxRequests - store[key].count);
    return next();
  };
}

// 错误处理中间件
function errorHandlerMiddleware() {
  return (ctx, next) => {
    return next()
      .catch(err => {
        console.error('❌ 未捕获的错误:', err);
        ctx.status = err.status || 500;
        ctx.body = {
          error: err.message || '服务器内部错误',
          stack: process.env.NODE_ENV === 'development' ? err.stack : undefined
        };
      });
  };
}

// ====== 组合中间件构建应用 ======

const rateLimitStore = {};

function composeMiddlewares(middlewares) {
  // 将多个中间件组合成一个处理函数
  return (initialCtx) => {
    let idx = 0;

    const ctx = initialCtx;
    const next = () => {
      if (idx < middlewares.length) {
        const middleware = middlewares[idx++];
        return middleware(ctx, next);
      }
      return Promise.resolve();
    };

    return next().then(() => ctx);
  };
}

// 自由组合！顺序可以随意调整
const app = composeMiddlewares([
  loggerMiddleware({ level: 'debug' }),              // 最外层：最先进入
  rateLimitMiddleware(rateLimitStore, { maxRequests: 10, windowMs: 15000 }),
  authMiddleware((token) => token === 'valid-token' ? { id: 1, role: 'admin' } : null),
  errorHandlerMiddleware()                                // 最内层：最后兜底
]);

// 模拟请求
app({ method: 'GET', url: '/api/users', ip: '127.0.0.1', headers: { authorization: 'Bearer valid-token' }, body: {} })
  .then(ctx => console.log('\n最终响应:', ctx.status, ctx.body));
```

中间件管道是**运行时组合**的经典案例。每个中间件都是一个独立的、自包含的处理单元：
- 它可以选择放行（调用 `next()`）或者短路（直接返回响应）
- 它可以修改请求上下文（`ctx`）供后续中间件使用
- 中间的顺序可以随意调整——安全相关的放前面，性能相关的放后面

这与继承形成了鲜明对比：如果用继承来实现同样的功能，你可能需要一个 `BaseHandler` → `LoggedHandler` → `RateLimitedHandler` → `AuthHandler` → `ErrorHandlerHandler` 的深层继承链，每增加一种新能力就要插入一层新的子类。而组合模式下，你只需要把需要的中间件放进数组就行——增删改查都在一瞬间完成。

### 应用三：游戏实体系统的组件架构

游戏开发领域是将组合优于继承发挥到极致的行业。几乎所有现代游戏引擎（Unity 的 ECS、Unreal 的 Gameplay Ability System、Godot 的 Node/Resource 体系）都采用基于组件的组合架构：

```javascript
// ====== 游戏组件系统（简化 ECS 架构）=======

// 纯数据组件（Component）：只存储数据，没有任何行为
const Position = (x = 0, y = 0) => ({ x, y });

const Velocity = (vx = 0, vy = 0) => ({ vx, vy });

const Health = (max = 100) => ({
  max,
  current: max,
  shield: 0,

  takeDamage(amount) {
    const effectiveDamage = Math.max(0, amount - this.shield);
    this.shield = Math.max(0, this.shield - amount);
    this.current = Math.max(0, this.current - effectiveDamage);
    return { damaged: effectiveDamage > 0, remaining: this.current, dead: this.current <= 0 };
  },

  heal(amount) {
    this.current = Math.min(this.max, this.current + amount);
    return this.current;
  }
});

const Renderable = (sprite = '⬜', color = '#fff') => ({
  sprite,
  color,
  visible: true,
  zIndex: 0
});

const CombatStats = (attack = 10, defense = 5, speed = 3) => ({
  attack, defense, speed,
  level: 1,
  exp: 0,

  gainExp(amount) {
    this.exp += amount;
    while (this.exp >= this.level * 100) {
      this.exp -= this.level * 100;
      this.level++;
      this.attack += 2;
      this.defense += 1;
      this.speed += 0.5;
    }
  }
});

// 行为系统（System）：纯函数，操作组件数据
const MovementSystem = {
  update(entity, deltaTime) {
    if (!entity.velocity) return entity;

    entity.position.x += entity.velocity.vx * deltaTime;
    entity.position.y += entity.velocity.vy * deltaTime;

    // 边界反弹
    if (entity.position.x < 0 || entity.position.x > 800) {
      entity.velocity.vx *= -1;
    }
    if (entity.position.y < 0 || entity.position.y > 600) {
      entity.velocity.vy *= -1;
    }

    return entity;
  }
};

const CombatSystem = {
  attack(attacker, target) {
    if (!attacker.combatStats || !target.health) return null;

    const damage = Math.max(1, attacker.combatStats.attack - target.health.defense);
    const result = target.health.takeDamage(damage);

    if (result.dead) {
      attacker.combatStats.gainExp(target.health.max * 10);
      console.log(`💀 ${attacker.name} 击败了 ${target.name}！+${target.health.max * 10}EXP`);
    } else {
      console.log(`⚔️ ${attacker.name} 攻击了 ${target.name}，造成 ${damage} 点伤害`);
    }

    return result;
  }
};

const RenderingSystem = {
  render(entity) {
    if (!entity.renderable || !entity.renderable.visible) return '';
    const r = entity.renderable;
    const p = entity.position || { x: '?', y: '?' };
    return `${r.sprite} at(${p.x}, ${p.y})`;
  }
};

// ====== 实体工厂：通过组合创建游戏实体 ======

function createEntity(name) {
  return {
    name,
    components: {},
    add(componentType, componentData) {
      this.components[componentType] = componentData;
      return this;  // 链式调用
    },
    get(componentType) {
      return this.components[componentType];
    },
    has(...types) {
      return types.every(t => t in this.components);
    }
  };
}

// ====== 创建不同的游戏实体 ======

// 玩家角色：位置 + 血量 + 渲染 + 战斗
const player = createEntity('勇者')
  .add('position', Position(400, 300))
  .add('health', Health(200))
  .add('renderable', Renderable('🧙‍♂️', '#ff0'))
  .add('combatStats', CombatStats(25, 10, 5));

// 史莱姆怪物：位置 + 血量 + 游走 + 战斗（弱）
const slime = createEntity('史莱姆')
  .add('position', Position(200, 200))
  .add('health', Health(30))
  .add('velocity', Velocity(0.5, 0.3))
  .add('renderable', Renderable('🟢', '#0f0'))
  .add('combatStats', CombatStats(8, 2, 1));

// 宝箱：位置 + 渲染 + 无战斗
const treasureChest = createEntity('宝箱')
  .add('position', Position(600, 400))
  .add('renderable', Renderable('📦', '#ffa500'))
  // 没有 combatStats —— 无法攻击也无法被攻击

// NPC：位置 + 血量 + 渲染 + 无战斗
const villager = createEntity('村民')
  .add('position', Position(100, 450))
  .add('health', Health(50))
  .add('renderable', Renderable('👨', '#f90'));

// ====== 游戏循环 ======

const entities = [player, slime, treasureChest, villager];

console.log('=== 游戏开始！===\n');

for (let i = 0; i < 5; i++) {
  console.log(`--- 第 ${i + 1} 帧 ---`);

  // 移动更新
  entities.forEach(e => MovementSystem.update(e, 1));

  // 玩家攻击最近的怪物
  if (slime.has('health')) {
    CombatSystem.attack(player, slime);
  }

  // 渲染
  entities.forEach(e => {
    const rendered = RenderingSystem.render(e);
    if (rendered) console.log(rendered);
  });

  console.log('');
}

console.log('=== 最终状态 ===');
entities.forEach(e => {
  const pos = e.get('position');
  const hp = e.get('health');
  console.log(`${e.name}: 位置=${pos.x.toFixed(0)},${pos.y.toFixed(0)} | HP=${hp?.current ?? 'N/A'}/${hp?.max ?? 'N/A'}`);
});
```

这个简化的 ECS（Entity-Component-System）架构清晰地展示了组合在游戏开发中的威力：

- **勇者** 有位置、血量、渲染、战斗四个组件——能移动、能被打、能打人
- **史莱姆** 有位置、血量、速度、渲染、战斗五个组件——还能自主移动
- **宝箱** 只有位置和渲染两个组件——不能动也不能打，就是个摆设
- **村民** 有位置、血量和渲染三个组件——能动（如果加上速度的话）但不能打

如果用继承来表达这些差异，你需要 `Entity → MovableEntity → CombatEntity → Player`、`Entity → MovableEntity → Monster → Slime`、`Entity → StaticObject → Chest`、`Entity → MovableEntity → NPC → Villager`……而且一旦你想加一个"能飞的"能力，整个继承树就要重新洗牌。

而在 ECS 架构下，**新增"飞行"能力只需要新建一个 `Flying` 组件和一个 `FlightSystem`，然后在需要飞行能力的实体上加上这个组件即可**——已有的实体不受任何影响。Unity 引擎之所以能支撑百万级销量的大型游戏，ECS 的组合架构功不可没。

## 何时仍然应该使用继承？

在大力推崇组合的同时，我们也必须诚实面对一个问题：**继承在某些场景下仍然是更好的选择。** "组合优于继承"说的是"优先"（prefer），而不是"只用组合，永远不用继承"。

### 适合使用继承的场景

**场景一：真正的"is-a"关系且层级稳定**

如果你的领域模型中存在清晰的、稳定的泛化-特化层级，并且这种层级不太可能发生变化，继承是最自然的表达方式：

```javascript
class DOMNode { /* ... */ }          // DOM 节点基类
class Element extends DOMNode { /* ... */ }  // 元素节点
class HTMLElement extends Element { /* ... */ }  // HTML 元素
class HTMLInputElement extends HTMLElement { /* ... */ }  // 输入框元素
```

浏览器 DOM 就是经典的深层继承体系——每一层都有明确的语义含义，且这个体系几十年来基本不变。

**场景二：需要多态分发和类型标识**

当你的代码需要根据对象的类型来决定行为时（多态分发），继承配合 `instanceof` 提供了最直接的解决方案：

```javascript
function serialize(obj) {
  if (obj instanceof User) return serializeUser(obj);
  if (obj instanceof Order) return serializeOrder(obj);
  if (obj instanceof Product) return serializeProduct(obj);
  throw new Error(`未知类型: ${obj.constructor.name}`);
}
```

**场景三：框架强制要求或约定俗成**

如前所述，Angular、NestJS、Spring 等框架深度依赖类继承。在这种情况下遵循框架的惯例是明智的选择——不要为了"纯粹的设计原则"而跟整个生态作对。

### 继承与组合的决策指南

| 问题 | 选择继承的情况 | 选择组合的情况 |
|------|---------------|---------------|
| 关系本质 | 真正的 "is-a"，层级稳定 | "has-a"、"can-do"、"uses-a" |
| 层级深度 | 浅（1-3 层），不太可能变化 | 深（不确定），经常变动 |
| 复用的粒度 | 整体行为（整个接口） | 部分（若干方法或能力） |
| 子类数量 | 少量且可预见 | 大量或不可预见的组合 |
| 运行时变化 | 类型固定不变 | 行为需要在运行时动态改变 |
| 团队背景 | 熟悉传统 OOP（Java/C#） | 函数式/原型风格偏好 |
| 测试需求 | 需要mock整个类型 | 需要精确控制每个依赖 |

### 最终建议：用组合来构建能力，用继承来定义身份

在实践中，最成熟的设计往往是**混合型的**：

- 用 `class` + `extends` 来定义**类型的身份和公共接口**（Identity & Contract）
- 用组合（注入、委托、Mixin）来赋予**具体的行为和能力**（Behavior & Capability）

```javascript
// 身份：用继承定义"这是什么"
class Entity {
  id;
  constructor(id) { this.id = id; }
  toJSON() { return { id: this.id, type: this.constructor.name }; }
}

// 具体类型：继承身份
class Character extends Entity {
  name;
  constructor(id, name) {
    super(id);
    this.name = name;
  }
}

// 能力：用组合赋予行为
class WarriorBehavior {
  #weapon;
  constructor(weapon) { this.#weapon = weapon; }
  attack(target) {
    const dmg = this.#weapon.damage;
    console.log(`${this.name} 用 ${this.#weapon.name} 攻击了 ${target.name}！造成 ${dmg} 点伤害`);
    return dmg;
  }
}

class MagicUserBehavior {
  #mana;
  constructor(mana = 100) { this.#mana = mana; }
  castSpell(spell, target) {
    if (this.#mana < spell.cost) throw new Error('法力不足！');
    this.#mana -= spell.cost;
    console.log(`${this.name} 施放了 ${spell.name}！消耗 ${spell.cost} 法力`);
    return spell.effect(target);
  }
}

// 通过组合创建具体的角色
class Warrior extends Character {
  #behavior;
  constructor(id, name, weapon) {
    super(id, name);
    this.#behavior = new WarriorBehavior(weapon);
  }
  attack(target) { return this.#behavior.attack.call(this, target); }
  // 注意：这里用了 call(this) 把 warrior 的上下文传给 behavior
}

class Mage extends Character {
  #behavior;
  constructor(id, name, mana = 80) {
    super(id, name);
    this.#behavior = new MagicUserBehavior(mana);
  }
  castSpell(spell, target) { return this.#behavior.castSpell.call(this, spell, target); }
}
```

这种混合模式兼顾了两者的优势：**继承负责"是谁"，组合负责"能干什么"。** 这正是很多成熟项目的真实面貌——不是非此即彼的选择，而是在正确的地方用正确的工具。

## 总结：超越工具之争的设计智慧

### 核心要点回顾

让我们回到文章的开头，用全新的视角审视这条简单却深奥的设计原则：

**"组合优于继承"不仅仅是一句编码建议，它是一种关于如何组织复杂性的哲学立场。**

- **继承回答的是"它是什么"**——通过建立类型层级来分类和组织对象。适用于层级稳定、关系清晰、需要多态分发的场景。
- **组合回答的是"它能做什么"**——通过组装独立的能力模块来构建对象的行为。适用于能力多变、需要灵活复用、追求松耦合的场景。

### 设计原则的层次

在软件设计的知识体系中，"组合优于继承"位于哪个位置？它不是最底层的技术技巧，也不是最抽象的哲学信条，而是处于**中层设计原则**的关键位置：

```
价值观（Values）
├── 简单性（Simplicity）
├── 可维护性（Maintainability）
└── 灵活性（Flexibility）

原则（Principles）
├── 单一职责原则（SRP）
├── 开闭原则（OCP）
├── 里氏替换原则（LSP）
├── 接口隔离原则（ISP）
├── 依赖倒置原则（DIP）
└── ★ 组合优于继承（Composition over Inheritance）  ← 这里

模式（Patterns）
├── 策略模式（Strategy）
├── 装饰器模式（Decorator）
├── 适配器模式（Adapter）
├── 观察者模式（Observer）
└── ...
```

它与其他五大 SOLID 原则（SRP/OCP/LSP/ISP/DIP）并列，共同构成了面向对象设计的核心准则体系。掌握它意味着你不再只是一个会写 `class` 语法的程序员，而是一个真正理解"如何设计好软件"的工程师。

### 最后的建议

不要把"组合优于继承"当作教条来盲从。设计原则是指南针，不是法律条文。在实际项目中：

1. **先用组合来思考解决方案**——问自己："这个问题能不能通过组装已有的构件来解决？" 通常答案是肯定的
2. **只有当继承确实更自然时才用它**——如果真的是清晰的 "is-a" 关系，不要为了"原则正确"而故意绕路
3. **关注接口而非实现**——无论是组合还是继承，最重要的都是定义好清晰的接口（契约），让组件之间的协作基于接口而非具体实现
4. **在实践中学习和调整**——没有放之四海而皆准的设计法则。每次做完项目后回顾一下：哪些地方用对了？哪些地方用错了？为什么？这种反思比死记任何原则都有价值

> **真正的高级开发者不是那些知道最多设计模式的人，也不是那些最严格遵守原则的人——而是那些能够在每一个具体情境中做出最恰当判断、在"理论正确"和"实践有效"之间找到最佳平衡点的人。** 组合优于继承是你工具箱中的一件利器，但请记住：**工具本身不创造价值，创造价值的是使用工具的人。**
