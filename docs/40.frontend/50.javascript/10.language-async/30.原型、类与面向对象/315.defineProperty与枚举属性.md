# `Object.defineProperty` / `defineProperties` + 枚举属性全解

> **核心内容**：`Object.defineProperty` 与 `Object.defineProperties` 的完整 API 解析、属性描述符的六维模型、`enumerable`（可枚举性）的深层机制、枚举操作的行为差异、以及它们在实际工程中的应用哲学。

## 一段代码引发的认知震荡

在深入正式内容之前，先看一段看似简单却暗藏玄机的代码：

```javascript
const person = {
  name: "张三",
  age: 25,
};

// 用 for...in 遍历
for (let key in person) {
  console.log(key);  // 输出：name, age
}

// 用 Object.keys 获取所有键
console.log(Object.keys(person));  // ["name", "age"]

// 看起来一切正常，对吧？
// 但如果我们用 defineProperty 加一个"隐藏属性"
Object.defineProperty(person, "_secret", {
  value: "这是秘密",
  enumerable: false,   // 关键！标记为不可枚举
});

// 再来遍历一次
for (let key in person) {
  console.log(key);  // 依然只输出：name, age
}

console.log(Object.keys(person));       // ["name", "age"] —— _secret 不见了？
console.log(person._secret);            // "这是秘密" —— 但它明明还在啊！

console.log("_secret" in person);        // true —— in 操作符说它在
console.log(person.hasOwnProperty("_secret")); // true —— hasOwnProperty 也说它在
```

这段代码揭示了一个让很多 JavaScript 开发者困惑的现象：**同一个对象上的同一个属性，在不同的"查看方式"下，竟然呈现出截然不同的存在状态。** 它既"存在"又"不存在"——你能直接访问它的值，但遍历时却看不到它；`in` 操作符认为它是对象的一部分，但 `for...in` 却对它视而不见。

这种"薛定谔的属性"现象，根源就在于 JavaScript 属性系统中一个精妙且强大的设计——**可枚举性（enumerability）**。而控制这个特性的核心工具，就是本文的主角——`Object.defineProperty` 和 `Object.defineProperties`。

理解这套机制的意义远不止于"知道一个 API 怎么用"。它会改变你看待 JavaScript 对象的方式——从"一组键值对的容器"进化为**一个由精细元信息控制的、具有丰富行为边界的实体**。这是一种认知层级的跃迁。

## 什么是 Object.defineProperty？

### 基本定义与语法

`Object.defineProperty` 是 JavaScript 从 ES5 开始提供的静态方法，用于**在一个对象上精确地定义或修改一个属性的描述符（Property Descriptor）**。与普通的赋值操作（`obj.prop = value`）或字面量声明（`{ prop: value }`）不同，这个方法允许你对属性的每一个行为维度进行原子级别的精确控制：

```javascript
// 基本语法
Object.defineProperty(obj, propertyKey, descriptor)
// obj          → 目标对象
// propertyKey  → 属性名（字符串或 Symbol）
// descriptor   → 描述符对象，定义该属性的行为规则
// 返回值      → 目标对象 obj 本身（支持链式调用）
```

最基本的用法示例：

```javascript
const user = {};

// 使用 defineProperty 定义一个普通属性
Object.defineProperty(user, 'name', {
  value: '张三',         // 属性值
  writable: true,        // 可写（允许通过 = 赋值）
  enumerable: true,      // 可枚举（出现在 for...in / keys() 中）
  configurable: true     // 可配置（允许删除和重新定义）
});

console.log(user.name);        // "张三"
user.name = '李四';             // ✅ writable 为 true，赋值成功
console.log(user.name);        // "李四"

for (let key in user) {
  console.log(key);            // 输出 "name" —— enumerable 为 true
}
```

### 为什么需要 defineProperty？——从粗糙到精密

你可能会问：既然 `user.name = '张三'` 这么简洁好用，为什么还需要一个这么啰嗦的 API？

这就好比问：为什么有了菜刀还需要手术刀？菜刀可以切菜切肉，但你不会用它来做眼科手术。同样的道理：

- **普通赋值（`obj.x = 1`）是"菜刀"**：快速、便捷、适合日常使用，但对属性行为的控制极其有限——创建出来的属性默认全部都是"可写的、可枚举的、可配置的"，没有任何选择余地
- **`Object.defineProperty` 是"手术刀"**：虽然调用起来更繁琐，但它能让你精确指定每个属性在每个维度上的行为规则——不可写的、不可枚举的、不可配置的、带 getter/setter 的……你需要什么精度，就能获得什么精度

```javascript
// 场景：你要给一个库的核心对象添加一个"内部版本号"
// 这个版本号应该：
//   1. 只读 —— 外部代码不能随意修改
//   2. 隐藏   —— 遍历时不要暴露出去
//   3. 不可删 —— 不能被 delete 掉

const MyLibrary = {
  publicMethod() { /* ... */ }
};

MyLibrary.version = '1.0.0';  // ❌ 用普通赋值做不到以上三点

Object.defineProperty(MyLibrary, '__version__', {
  value: '1.0.0',
  writable: false,        // ① 只读
  enumerable: false,      // ② 隐藏
  configurable: false     // ③ 不可删除/重新定义
});
// 三条要求，一行代码全部满足
```

### 理论基础：ES5 规范化的属性元信息系统

从语言演进的角度来看，`Object.defineProperty` 的出现标志着 JavaScript 对象系统的一次重要升级。在 ES5 之前（2009 年之前），JavaScript 的属性本质上只有两种状态："存在"和"不存在"。你无法阻止外部代码修改某个属性的值，无法让某个属性在遍历时隐身，也无法为属性添加自定义的读写逻辑。

ES5 规范引入了**属性描述符（Property Descriptor）**这一概念，将每个属性的元信息规范化为六个维度：`value`、`writable`、`enumerable`、`configurable`、`get`、`set`。这六个维度组合在一起，完整地刻画了一个属性的全部行为特征。`Object.defineProperty` 就是我们操控这些维度的官方接口。

这项设计深受 **Self 语言**和 **Smalltalk** 等"基于原型（Prototype-based）"面向对象语言的启发。在这些语言中，对象的属性本身就携带有丰富的元数据（Metadata），而不是像 Java/C++ 那样将属性的行为完全交给类的访问修饰符（public/private/protected）来决定。JavaScript 沿袭了这一传统，并在此基础上发展出了自己独特的属性描述符体系。

> 关于属性描述符的六大维度及其相互关系，在《[不可变对象与属性描述符深入](/frontend/javascript/language-async/immutable-object-property-descriptor-deep)》一文中有更详尽的讲解。本文将聚焦于 `defineProperty` API 本身以及 `enumerable`（可枚举性）这一核心维度。

## 属性描述符的六维模型回顾

在正式进入 `defineProperty` 的深度解析之前，让我们快速回顾一下属性描述符的六个维度。这六个维度分为两大阵营——**数据描述符（Data Descriptor）** 和 **访问器描述符（Accessor Descriptor）**：

### 数据描述符（Data Descriptor）

拥有 `value` 和 `writable` 的属性称为数据描述符，用于存储实际的数据值：

| 维度 | 类型 | 说明 |
|------|------|------|
| `value` | Any | 属性持有的实际数据值，默认为 `undefined` |
| `writable` | Boolean | 是否允许通过 `=` 赋值操作符修改值。默认为 **`false`** |

```javascript
const config = {};
Object.defineProperty(config, 'maxRetries', {
  value: 3,
  writable: false    // 定义后变为只读常量
});
console.log(config.maxRetries);  // 3
config.maxRetries = 99;           // 严格模式下 TypeError，非严格模式静默失败
console.log(config.maxRetries);  // 依然是 3
```

### 访问器描述符（Accessor Descriptor）

拥有 `get` 和 `set` 的属性称为访问器描述符，每次读写都会执行对应的函数：

| 维度 | 类型 | 说明 |
|------|------|------|
| `get` | Function \| undefined | 读取属性时调用的函数（getter），默认为 `undefined` |
| `set` | Function \| undefined | 写入属性时调用的函数（setter），默认为 `undefined` |

```javascript
const circle = {
  _radius: 5
};

Object.defineProperty(circle, 'diameter', {
  get() {              // 读取 diameter 时自动计算
    return this._radius * 2;
  },
  set(val) {           // 设置直径时反算半径
    if (val <= 0) throw new Error('直径必须大于 0');
    this._radius = val / 2;
  },
  enumerable: true,
  configurable: true
});

console.log(circle.diameter);  // 10 （自动计算）
circle.diameter = 20;           // 调用 setter，_radius 变为 10
console.log(circle._radius);    // 10
```

**关键互斥规则**：一个属性不能同时拥有 `value/writable` 和 `get/set`——两者是互斥的。如果尝试同时指定，引擎会抛出 `TypeError`：

```javascript
const obj = {};
Object.defineProperty(obj, 'bad', {
  value: 42,           // 数据特征
  get() { return 99; } // 访问器特征
});
// ❌ TypeError: Invalid property descriptor.
// Cannot both specify accessors and a value or writable attribute
```

这个互斥规则的底层逻辑很清晰：数据描述符表达的是"这里有一个固定的存储槽位"，而访问器描述符表达的是"这里的值是动态计算的"。这两者在语义上就是矛盾的——一个东西不可能既是"静态存储的"又是"动态计算的"。

### 共享维度：enumerable 与 configurable

无论数据描述符还是访问器描述符，都共享以下两个维度：

| 维度 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enumerable` | Boolean | **`false`** | 控制属性是否会在枚举操作中出现 |
| `configurable` | Boolean | **`false`** | 控制属性能否被删除或重新定义描述符 |

注意这两个维度的**默认值是 `false`**——这一点至关重要，也是大量 bug 的来源之一，后面会详细讨论。

## Object.defineProperty 完整解析

### 参数详解与返回值

```javascript
const returnedObj = Object.defineProperty(targetObj, propName, descriptorObj);
```

三个参数的含义：

1. **targetObj（目标对象）**：要在其上定义属性的对象。可以是普通对象、数组、甚至 `null` 以外的任何对象（包括函数——因为函数也是对象）。**注意：如果传入基本类型（如数字、字符串），会先被包装为对应包装对象。**
2. **propName（属性名）**：字符串或 Symbol，表示要定义或修改的属性名。如果是已有的属性，则**修改**其描述符；如果是新属性，则**添加**到目标对象上。
3. **descriptorObj（描述符对象）**：包含属性行为规则的对象。必须是有效的描述符形式（纯数据描述符、纯访问器描述符、或混合有效形式）。
4. **返回值**：传入的 `targetObj` 本身。这意味着你可以进行链式调用：

```javascript
const obj = {};
Object.defineProperty(obj, 'x', { value: 1, enumerable: true, configurable: true, writable: true })
  .defineProperty(obj, 'y', { value: 2, enumerable: true, configurable: true, writable: true })
  .defineProperty(obj, 'z', { value: 3, enumerable: true, configurable: true, writable: true });

console.log(obj.x + obj.y + obj.z);  // 6
```

### 行为一：定义新属性

当指定的属性名在目标对象上不存在时，`defineProperty` 会**创建一个全新的属性**，并根据传入的描述符设置其行为规则：

```javascript
const emptyObj = {};

Object.defineProperty(emptyObj, 'newProp', {
  value: 'hello',
  writable: true,
  enumerable: true,
  configurable: true
});

console.log(emptyObj.newProp);  // "hello"
console.log(emptyObj.hasOwnProperty('newProp'));  // true
```

### 行为二：修改已有属性

当属性已存在时，`defineProperty` 可以**部分或全部修改其描述符**。但能否修改成功取决于当前属性的 `configurable` 状态：

```javascript
const obj = { existing: '原始值' };

// 修改已有属性的描述符
Object.defineProperty(obj, 'existing', {
  writable: false,        // 改为不可写
  enumerable: false       // 改为不可枚举
  // 注意：没有改 value，所以值保持不变
  // 注意：没有改 configurable，所以保持原来的 true
});

obj.existing = '尝试修改';  // 失败（writable: false）
console.log(obj.existing);  // "原始值"
for (let k in obj) {}       // existing 不再出现（enumerable: false）
```

### ⚠️ 致命陷阱：默认值不是你以为的那样

这是 `defineProperty` 最容易踩坑的地方，请务必刻入脑海：

**当你使用 `defineProperty` 创建新属性时，描述符中未显式指定的布尔型属性，默认值为 `false`，而不是 `true`！**

```javascript
const trap = {};

// 我只想设个值，其他的应该跟普通属性一样吧？
Object.defineProperty(trap, 'innocent', {
  value: 42
  // writable: ???     → 默认 false!
  // enumerable: ???   → 默认 false!
  // configurable: ??? → 默认 false!
});

// 让我们看看 innocent 到底变成了什么样
let desc = Object.getOwnPropertyDescriptor(trap, 'innocent');
console.log(desc);
// {
//   value: 42,
//   writable: false,      ← 不可写！
//   enumerable: false,    ← 不可枚举！
//   configurable: false   ← 不可配置！
// }

trap.innocent = 99;         // ❌ 静默失败（writable: false）
delete trap.innocent;       // ❌ 静默失败（configurable: false）
for (let k in trap) {}      // innocent 不出现（enumerable: false）
```

对比一下不同创建方式的默认值差异：

| 创建方式 | writable | enumerable | configurable |
|---------|----------|-----------|--------------|
| `obj.x = 1` 或 `{ x: 1 }` | `true` ✅ | `true` ✅ | `true` ✅ |
| `defineProperty(obj, 'x', { value })` | **`false`** ❌ | **`false`** ❌ | **`false`** ❌ |

为什么会这样设计？ECMAScript 规范委员会做出这个选择的逻辑是：**`defineProperty` 是一个"精确控制"的工具，它假设使用者清楚地知道自己想要什么。因此，未明确指定的选项采用最严格的默认值（即"关闭"状态），以避免意外泄露或被意外修改。** 这种"安全优先（Secure by Default）"的设计哲学在现代 API 设计中越来越常见——比如 HTTP 安全头的默认策略、CSP（Content Security Policy）的默认拒绝模式等。

**最佳实践：永远显式指定每一个你关心的描述符属性。**

## Object.defineProperties：批量定义的艺术

### 基本用法

如果你需要在同一对象上一次性定义多个属性，反复调用 `defineProperty` 显然不够优雅。ES5 同时提供了 `Object.defineProperties` 方法，支持批量操作：

```javascript
Object.defineProperties(targetObj, descriptorsObj);
// targetObj       → 目标对象
// descriptorsObj  → 一个对象，键是属性名，值是对应的描述符
// 返回值          → targetObj 本身
```

```javascript
const product = {};

Object.defineProperties(product, {
  id: {
    value: 'PROD-001',
    writable: false,
    enumerable: true,
    configurable: false
  },
  name: {
    value: '高性能无线耳机 Pro Max Ultra',
    writable: true,
    enumerable: true,
    configurable: true
  },
  price: {
    value: 299.00,
    writable: true,
    enumerable: true,
    configurable: true
  },
  _internalSku: {
    value: 'SKU-WH-2024-BLK-XL',
    writable: true,
    enumerable: false,       // 内部 SKU 不对外暴露
    configurable: false      // 且不允许删除或重定义
  }
});

// 批量验证
product.id = 'HACKED';               // 失败（writable: false）
product._internalSku = 'STOLEN';     // 赋值成功（writable: true），但...
console.log(Object.keys(product));
// ["id", "name", "price"] —— _internalSku 不可见（enumerable: false）
```

### defineProperty vs defineProperties：何时用哪个？

| 维度 | `defineProperty` | `defineProperties` |
|------|------------------|-------------------|
| **操作粒度** | 单个属性 | 多个属性 |
| **适用场景** | 动态添加单个属性、条件性定义 | 初始化时批量配置对象结构 |
| **性能** | 单次调用开销 | 减少多次调用的累积开销 |
| **可读性** | 关注点集中 | 结构清晰一目了然 |

在实际开发中，两者的选择通常取决于上下文：

```javascript
// 场景 A：运行时动态添加单个属性 —— 用 defineProperty
function addReadOnlyFlag(obj, flagName, value) {
  Object.defineProperty(obj, flagName, {
    value,
    writable: false,
    enumerable: true,
    configurable: false
  });
  return obj;
}

// 场景 B：初始化时构建完整的配置对象 —— 用 defineProperties
function createAppConfig(rawConfig) {
  const cfg = {};
  Object.defineProperties(cfg, {
    version: {
      value: rawConfig.version || '1.0.0',
      writable: false, enumerable: true, configurable: false
    },
    environment: {
      value: rawConfig.environment || 'development',
      writable: false, enumerable: true, configurable: false
    },
    debugMode: {
      value: rawConfig.debug === true,
      writable: false, enumerable: false, configurable: false  // 内部开关不暴露
    }
  });
  return cfg;
}
```

### 通俗类比：逐条登记 vs 表格录入

如果把 `defineProperty` 比作到房管局窗口**逐条办理房产变更手续**——每办一条就要排一次队、填一张表；那么 `defineProperties` 就是提前准备好一张**包含所有变更项的表格一次性提交**——效率更高，而且整体结构也更清晰。

在日常开发中，如果你的对象初始化需要定义多个具有特殊行为的属性，`defineProperties` 通常是更好的选择——它让你的意图更加声明式（Declarative），代码也更具可维护性。

## enumerable（可枚举性）：深入骨髓的机制

现在让我们把聚光灯打在本文的核心主题——**可枚举性（enumerability）** 上。这是属性描述符六个维度中最微妙、最容易误解、同时也是影响面最广的一个。

### 什么是"枚举"？——语义层面的界定

在编程语境中，**"枚举（Enumerate）"指的是按某种顺序逐一列出集合中元素的过程**。对于 JavaScript 对象来说，枚举就是遍历对象的所有属性名（键），然后依次处理每个属性。

但问题来了：JavaScript 中有多种方式可以"遍历"一个对象的属性——`for...in` 循环、`Object.keys()`、`Object.values()`、`Object.entries()`、`JSON.stringify()`、展开运算符 `...obj`——它们的行为是否一致？答案是否定的。而造成行为差异的关键因素，正是属性的 `enumerable` 标志位。

### enumerable 的基本行为

当一个属性的 `enumerable` 设置为 `true` 时，称其为**可枚举属性**；设置为 `false` 时，称为**不可枚举属性**。这个标志位唯一的作用是**决定该属性是否会被各种枚举类操作所"看到"**：

```javascript
const obj = {};

Object.defineProperty(obj, 'visibleProp', {
  value: '我是可见的',
  enumerable: true      // 可枚举
});

Object.defineProperty(obj, 'hiddenProp', {
  value: '我是隐形的',
  enumerable: false     // 不可枚举
});

// ====== 各种枚举操作的响应 ======

// 1. for...in 循环 —— 受 enumerable 影响
for (let key in obj) {
  console.log(key);     // 只输出 "visibleProp"
}

// 2. Object.keys() —— 受 enumerable 影响
console.log(Object.keys(obj));
// ["visibleProp"]

// 3. Object.values() —— 同样受影响
console.log(Object.values(obj));
// ["我是可见的"]

// 4. Object.entries() —— 同样受影响
console.log(Object.entries(obj));
// [["visibleProp", "我是可见的"]]

// 5. JSON.stringify() —— 受 enumerable 影响
console.log(JSON.stringify(obj));
// '{"visibleProp":"我是可见的"}'

// 6. 展开运算符 —— 受 enumerable 影响
const copy = { ...obj };
console.log(copy);
// { visibleProp: "我是可见的" } —— hiddenProp 没有被复制过来

// ====== 但是！以下操作不受 enumerable 影响 ======

// 直接访问 —— 完全不受影响
console.log(obj.hiddenProp);             // "我是隐形的" ✅ 正常访问

// in 操作符 —— 不受影响
console.log('hiddenProp' in obj);         // true ✅

// hasOwnProperty —— 不受影响
console.log(obj.hasOwnProperty('hiddenProp'));  // true ✅

// Object.getOwnPropertyNames() —— 不受影响！返回所有自有属性名（含不可枚举）
console.log(Object.getOwnPropertyNames(obj));
// ["visibleProp", "hiddenProp"] —— 两个都有！

// getOwnPropertyDescriptor —— 不受影响
console.log(Object.getOwnPropertyDescriptor(obj, 'hiddenProp'));
// { value: "我是隐形的", writable: false, enumerable: false, configurable: false }
```

这段代码清晰地展示了 `enumerable` 的作用边界：**它只影响那些"列举/收集/序列化"类型的操作，不影响直接的属性访问和存在性检测。** 你可以把 `enumerable: false` 理解为给属性穿上了"隐身衣"——它还在那里，功能完好，只是不会被常规的"扫描"手段发现。

### 为什么要有 enumerable？——设计动机

你可能会想：为什么要搞这么复杂？让所有属性都可枚举不就完了吗？

这是一个好问题。答案涉及几个重要的设计考量：

**第一，内置方法保护的需要。** JavaScript 内置对象（如 `Array.prototype`、`Object.prototype`）上有大量的方法——`toString`、`valueOf`、`hasOwnProperty`、`map`、`filter`、`forEach`……如果这些属性都是可枚举的，那么每当你对一个数组或对象做 `for...in` 遍历时，就会把这些方法名也遍历出来，那将是灾难性的：

```javascript
const arr = [1, 2, 3];

// 如果 Array.prototype 上的方法是可枚举的……
for (let key in arr) {
  console.log(key);
  // 将输出: 0, 1, 2, map, filter, reduce, find, every, some, forEach,
  //         flat, flatMap, includes, indexOf, keys, values, entries, ...
  // 几十个方法名全出来，你的循环逻辑就彻底乱套了
}

// 但实际上，这些方法的 enumerable 都是 false
// 所以 for...in 只输出数组的索引: 0, 1, 2
```

**第二，内部实现细节的封装。** 库或框架的开发者经常需要在对象上存放一些"仅供内部使用的辅助属性"。这些属性不应该被库的使用者看到或误操作。将它们的 `enumerable` 设为 `false`，就可以优雅地实现这一需求：

```javascript
function createObservable(target) {
  // 内部追踪属性，对外不可见
  Object.defineProperty(target, '__observers__', {
    value: [],                    // 存放观察者回调列表
    enumerable: false,            // 对外隐形
    configurable: true
  });

  Object.defineProperty(target, '__version__', {
    value: 0,                     // 版本号，用于优化
    enumerable: false,            // 对外隐形
    writable: true,
    configurable: true
  });

  return target;
}

const state = createObservable({ count: 0 });
for (let key in state) {
  console.log(key);  // 只输出 "count"，__observers__ 和 __version__ 不会出现
}
```

**第三，数据纯净性与序列化控制。** 当你需要将对象序列化为 JSON（比如发送到服务器或存入 localStorage）时，通常只希望包含"业务数据"，而不希望包含内部元信息、计算缓存、调试标记等。通过 `enumerable: false`，你可以精准控制哪些属性参与序列化：

```javascript
function createEntity(data) {
  const entity = Object.defineProperties({}, {
    id: {
      value: data.id,
      enumerable: true,       // 业务 ID，需要序列化
      writable: false,
      configurable: false
    },
    name: {
      value: data.name,
      enumerable: true,       // 业务名称，需要序列化
      writable: true,
      configurable: true
    },
    _rawData: {
      value: data,            // 原始数据备份，不需要序列化
      enumerable: false,      // 隐藏
      writable: false,
      configurable: false
    },
    _cacheHash: {
      value: null,            // 缓存的哈希值，不需要序列化
      enumerable: false,      // 隐藏
      writable: true,
      configurable: true
    }
  });

  return entity;
}
```

### 通俗类比：公开档案 vs 机密文件

想象一家公司的档案管理系统。公司里有两类文件：

- **公开档案（enumerable: true）**：员工姓名、部门职位、联系方式等基本信息。任何人都可以在公司的公共目录中查到这些信息，HR 系统导出报表时会自动包含它们，搜索功能也能检索到它们。
- **机密文件（enumerable: false）**：薪资详情、背景调查报告、绩效评分等敏感信息。这些文件确实存在于档案柜中（你知道具体编号的话可以直接取阅），但它们不会出现在公开目录中，批量导出时会被自动过滤掉，普通搜索也搜不到。

`enumerable` 标志位就是这个档案系统的**分类标签**——它不决定文件是否存在或能否单独访问，而是决定文件是否会出现在"批量展示"的场景中。

## 枚举操作全景对比表

为了让你对 JavaScript 中各种属性遍历/检测操作有全局性的认识，下面是一份完整的对比表：

| 操作 | 自身属性 | 原型链属性 | 过滤不可枚举 | 包含 Symbol | 典型用途 |
|------|---------|-----------|------------|-----------|---------|
| `for...in` | ✅ | ✅（沿原型链向上） | ✅ 过滤 | ❌ 不含 | 遍历"可用的键"（兼容旧代码） |
| `Object.keys()` | ✅ 仅自身 | ❌ | ✅ 过滤 | ❌ 不含 | 获取可枚举的自有属性名 |
| `Object.values()` | ✅ 仅自身 | ❌ | ✅ 过滤 | ❌ 不含 | 获取可枚举的自有属性值 |
| `Object.entries()` | ✅ 仅自身 | ❌ | ✅ 过滤 | ❌ 不含 | 获取 `[key, value]` 对 |
| `JSON.stringify()` | ✅ 仅自身 | ❌ | ✅ 过滤 | ❌ 不含 | 序列化为 JSON 字符串 |
| `Object.getOwnPropertyNames()` | ✅ 仅自身 | ❌ | ❌ **不过滤** | ❌ 不含（仅 String 键）| 调试/反射：获取所有自有属性名 |
| `Object.getOwnPropertySymbols()` | ✅ 仅自身 | ❌ | ❌ 不过滤 | ✅ **仅含** | 获取 Symbol 属性 |
| `Reflect.ownKeys()` | ✅ 仅自身 | ❌ | ❌ 不过滤 | ✅ 含 | 最全面的"自有键"获取 |
| `in` 操作符 | ✅ | ✅（沿原型链） | ❌ 不过滤 | ✅ 含 | 检测属性是否存在 |
| `hasOwnProperty()` | ✅ 仅自身 | ❌ | ❌ 不过滤 | ✅ 含 | 检测自有属性是否存在 |

### 关键洞察一：for...in vs Object.keys()

这是最常见的混淆点。两者都会跳过不可枚举属性，但有本质区别：

```javascript
function Parent() {
  this.inheritedProp = '来自父级';
}
Parent.prototype.protoMethod = function() {};  // 不可枚举的方法

function Child() {
  this.ownProp = '自身的';
}
Child.prototype = new Parent();

const child = new Child();
Object.defineProperty(child, 'hiddenOwn', {
  value: '隐藏的自有属性',
  enumerable: false
});

// for...in：遍历自身 + 原型链上的可枚举属性
console.log('--- for...in ---');
for (let key in child) {
  console.log(key);  // ownProp, inheritedProp（两个都输出！）
}

// Object.keys()：只遍历自身的可枚举属性
console.log('--- Object.keys ---');
console.log(Object.keys(child));  // ["ownProp"] （不含原型链的！）
```

**`for...in` 会沿原型链爬升**，而 `Object.keys()` 只关注自身。这也是现代代码中推荐优先使用 `Object.keys()`（或 `Object.entries()`、`for...of`）而非 `for...in` 的原因之一——前者更可控、更可预测。

### 关键洞察二：Reflect.ownKeys() —— 最诚实的枚举者

如果你需要一个**完全不被 `enumerable` 影响的操作**，`Reflect.ownKeys()` 是你的最佳选择。它会返回对象的所有自有键——无论是否可枚举、无论是字符串键还是 Symbol 键：

```javascript
const obj = {
  visible: '可见',
  [Symbol('symbolKey')]: 'Symbol属性'
};

Object.defineProperty(obj, 'hiddenString', {
  value: '隐藏的字符串属性',
  enumerable: false
});

Object.defineProperty(obj, Symbol('hiddenSymbol'), {
  value: '隐藏的Symbol属性',
  enumerable: false
});

console.log(Reflect.ownKeys(obj));
// [
//   "visible",
//   "hiddenString",        ← 不可枚举的字符串键也在！
//   Symbol(symbolKey),
//   Symbol(hiddenSymbol)   ← 不可枚举的 Symbol 键也在！
// ]

// 对比其他方法
console.log(Object.keys(obj));              // ["visible"]
console.log(Object.getOwnPropertyNames(obj)); // ["visible", "hiddenString"] — 含不可枚举字符串键，但不含 Symbol
console.log(Object.getOwnPropertySymbols(obj)); // [Symbol(symbolKey), Symbol(hiddenSymbol)] — 只含 Symbol
```

`Reflect.ownKeys()` 本质上是 `getOwnPropertyNames()` + `getOwnPropertySymbols()` 的合并版。它是你在需要"绝对完整"信息时的终极武器——比如调试工具、序列化库、深拷贝函数等场景。

## defineProperty 在实战中的典型应用

理论讲完了，让我们来看看 `Object.defineProperty`（特别是结合 `enumerable`）在实际项目中能解决哪些真实问题。

### 应用一：模拟真正的常量（CONSTANT）

JavaScript 的 `const` 关键字保证的是**绑定不变**（变量名不能再指向别的值），而不是**值本身不可变**。要创建真正的常量，需要借助 `defineProperty`：

```javascript
// 创建一个不可变的常量容器
const Constants = Object.defineProperties({}, {
  APP_NAME: {
    value: 'MyAwesomeApp',
    writable: false,       // 不可修改
    enumerable: true,      // 对外可见（毕竟是公开常量）
    configurable: false    // 不可删除/重定义
  },
  MAX_RETRY_COUNT: {
    value: 3,
    writable: false,
    enumerable: true,
    configurable: false
  },
  API_BASE_URL: {
    value: 'https://api.example.com/v1',
    writable: false,
    enumerable: true,
    configurable: false
  },
  __BUILD_TIME__: {
    value: Date.now(),
    writable: false,
    enumerable: false,     // 内部常量，不暴露
    configurable: false
  }
});

Constants.APP_NAME = 'Hacked';          // 严格模式 TypeError
delete Constants.MAX_RETRY_COUNT;        // 严格模式 TypeError
Constants.NEW_CONST = 'oops';            // 无法添加（因为对象未被 seal/freeze，
                                        // 实际上可以加！需要配合 Object.preventExtensions）
```

**进阶技巧——配合 Object.freeze 实现完全密封：**

```javascript
function createFrozenConstants(defs) {
  // 先用 defineProperties 定义所有属性（每个都不可写、不可配置）
  const consts = Object.defineProperties({}, 
    Object.fromEntries(
      Object.entries(defs).map(([key, val]) => [
        key, {
          value: val,
          writable: false,
          enumerable: !key.startsWith('_'),  // 下划线开头的为内部常量
          configurable: false
        }
      ])
    )
  );
  // 再冻结整个对象，阻止添加新属性
  return Object.freeze(consts);
}

const APP = createFrozenConstants({
  VERSION: '2.1.0',
  ENV: 'production',
  _buildHash: 'a1b2c3d4',
  _debug: false
});

APP.VERSION = '9.9.9';      // ❌ 冻结
APP.SECRET = 'leaked';       // ❌ 冻结（不可扩展）
console.log(APP.VERSION);    // "2.1.0" ✅
console.log(APP._debug);     // false ✅（可直接访问但不被枚举）
```

### 应用二：实现私有属性（Pre-ES2022 时代方案）

在 ES2022 引入 `#` 私有字段语法之前，`defineProperty` + 闭包是实现真正私有属性的主流方案：

```javascript
function createSecureAccount(owner, initialBalance) {
  // 这些变量完全封闭在闭包内部 —— 真正的私有
  let balance = initialBalance;
  let transactions = [];
  const pin = generatePin();  // 假设有生成密码的函数
  
  // 返回的对象只暴露"安全的接口"
  const account = {};
  
  Object.defineProperties(account, {
    owner: {
      value: owner,
      writable: false,        // 所有者不可更改
      enumerable: true,
      configurable: false
    },
    
    // 公开的操作方法
    deposit: {
      value: function(amount) {
        if (amount <= 0) throw new Error('存款金额必须为正');
        balance += amount;
        transactions.push({ type: 'deposit', amount, time: Date.now() });
        console.log(`存款 ${amount} 元，余额: ${balance} 元`);
      },
      writable: false,
      enumerable: true,
      configurable: false
    },
    
    withdraw: {
      value: function(amount, inputPin) {
        if (inputPin !== pin) throw new Error('密码错误');
        if (amount > balance) throw new Error('余额不足');
        if (amount <= 0) throw new Error('取款金额必须为正');
        balance -= amount;
        transactions.push({ type: 'withdraw', amount, time: Date.now() });
        console.log(`取款 ${amount} 元，余额: ${balance} 元`);
      },
      writable: false,
      enumerable: true,
      configurable: false
    },
    
    getBalance: {
      value: function(inputPin) {
        if (inputPin !== pin) throw new Error('密码错误');
        return balance;
      },
      writable: false,
      enumerable: true,
      configurable: false
    },
    
    // 内部方法（不对外暴露）
    _audit: {
      value: function(adminKey) {
        if (adminKey !== 'ADMIN_MASTER_KEY') throw new Error('无权限');
        return { balance, transactions, pin: '***' };
      },
      writable: false,
      enumerable: false,      // 审计方法不可枚举
      configurable: false
    }
  });
  
  return account;
}

const myAccount = createSecureAccount('张三', 10000);

myAccount.deposit(5000);                       // 存款 5000 元，余额: 15000 元
myAccount.withdraw(2000, '123456');            // 取款 2000 元，余额: 13000 元
console.log(myAccount.getBalance('123456'));   // 13000

// 尝试破坏
myAccount.balance = 999999;                    // 无效——根本就没有 balance 属性
myAccount.owner = '黑客';                      // 失败——writable: false
myAccount.pin = '000000';                      // 无效——pin 在闭包内，完全无法触及

for (let key in myAccount) {
  console.log(key);  // owner, deposit, withdraw, getBalance（_audit 不出现！）
}
```

这种方案的精髓在于：**私有数据的存储（闭包变量）与公开接口的定义（defineProperty）是完全分离的**。外部代码无论如何都无法绕过 getter/setter 直接接触到闭包内的变量——这不是靠约定，而是靠 JavaScript 作用域规则实现的物理隔离。

### 应用三：懒加载与缓存属性

利用访问器描述符 + 闭包，可以实现"首次访问时计算、后续直接返回缓存值"的惰性求值模式：

```javascript
function defineLazyProperty(obj, propName, computeFn) {
  let computed = false;     // 是否已计算
  let cachedValue;          // 缓存的值
  
  Object.defineProperty(obj, propName, {
    get() {
      if (!computed) {
        // 第一次访问时执行计算
        cachedValue = computeFn.call(obj);
        computed = true;
        
        // 可选：计算完成后，可以将属性改为普通数据属性
        // 这样后续读取就不需要经过 getter 函数了（微小性能优化）
        Object.defineProperty(obj, propName, {
          value: cachedValue,
          writable: false,
          enumerable: true,
          configurable: true
        });
      }
      return cachedValue;
    },
    enumerable: true,
    configurable: true  // 允许后续重新定义或删除
  });
  
  return obj;
}

// 使用示例：一个需要昂贵计算的属性
const heavyObject = {};

defineLazyProperty(heavyObject, 'expensiveResult', function() {
  console.log('⏳ 正在执行复杂计算...');
  
  // 模拟耗时操作
  let sum = 0;
  for (let i = 0; i < 100000000; i++) {
    sum += Math.sqrt(i);
  }
  
  return { result: sum, computedAt: Date.now() };
});

console.log('--- 第一次访问 ---');
console.log(heavyObject.expensiveResult);  // ⏳ 计算后返回结果

console.log('--- 第二次访问 ---');
console.log(heavyObject.expensiveResult);  // 直接返回缓存（不再打印 ⏳）

console.log('--- 第三次访问 ---');
console.log(heavyObject.expensiveResult);  // 依然直接返回缓存
```

这种模式在以下场景特别有价值：

- **DOM 计算**：首次访问时测量元素尺寸（触发 reflow），之后返回缓存值
- **复杂派生数据**：从多个来源聚合的数据（如用户权限列表）
- **异步资源加载**：配合 Promise 缓存异步加载的结果

```javascript
// DOM 尺寸缓存的实用案例
function createSizeCache(element) {
  const cache = {};
  
  defineLazyProperty(cache, 'boundingRect', () => {
    return element.getBoundingClientRect();
  });
  
  defineLazyProperty(cache, 'computedStyle', () => {
    return window.getComputedStyle(element);
  });
  
  // 当 DOM 可能发生变化时，使缓存失效
  cache.invalidate = function() {
    for (let key of Reflect.ownKeys(cache)) {
      if (key === 'invalidate') continue;
      delete cache[key];  // 删除后下次访问会重新计算
    }
  };
  
  return cache;
}

const divSize = createSizeCache(document.querySelector('#myDiv'));
console.log(divSize.boundingRect);   // 首次：测量 DOM
console.log(divSize.boundingRect);   // 后续：返回缓存

// DOM 变化后
divSize.invalidate();                // 清除缓存
console.log(divSize.boundingRect);   // 重新测量
```

### 应用四：观察者模式与响应式数据

这是 Vue.js 2.x 和许多状态管理库的核心技术——通过 `defineProperty` 拦截属性的读写操作，实现数据变化时的自动通知：

```javascript
function makeReactive(data, onChange) {
  // 遍历所有自有属性，将其转化为响应式的
  for (let key of Object.keys(data)) {
    let internalValue = data[key];  // 闭包保存内部值
    
    Object.defineProperty(data, key, {
      get() {
        // 可以在这里收集依赖（Dependency Tracking）
        console.log(`📖 读取 ${key}: ${internalValue}`);
        return internalValue;
      },
      
      set(newValue) {
        if (internalValue === newValue) return;  // 值没变则跳过
        
        const oldValue = internalValue;
        internalValue = newValue;
        
        console.log(`✏️ ${key} 变化: ${oldValue} → ${newValue}`);
        
        // 通知外部监听者
        if (typeof onChange === 'function') {
          onChange(key, newValue, oldValue);
        }
      },
      
      enumerable: true,
      configurable: true
    });
  }
  
  return data;
}

// 使用：创建一个响应式的状态对象
const state = makeReactive({
  user: '张三',
  age: 25,
  online: true
}, (key, newVal, oldVal) => {
  console.log(`🔔 状态更新通知: ${key} 从 "${oldVal}" 变为 "${newVal}"`);
  
  // 这里可以触发视图更新、持久化、日志记录等操作
});

// 正常读写，但每次变化都会被拦截和通知
state.user = '李四';
// ✏️ user 变化: 张三 → 李四
// 🔔 状态更新通知: user 从 "张三" 变为 "李四"

state.age = 26;
// ✏️ age 变化: 25 → 26
// 🔔 状态更新通知: age 从 "25" 变为 "26"

state.online = false;
// ✏️ online 变化: true → false
// 🔔 状态更新通知: online 从 "true" 变为 "false"
```

这就是**数据驱动视图（Data-Driven View）**的最简原型。Vue.js 2.x 正是基于这个原理构建了完整的响应式系统——只不过它还增加了依赖收集（Dependency Collection）、异步批处理（Async Batching）、深度观测（Deep Watching）等高级能力。（Vue 3.x 则转向了基于 Proxy 的方案，因为 Proxy 能更优雅地处理动态属性增删和数组索引检测等场景。关于 Proxy 的详细内容，参见《[Proxy代理详解](/frontend/javascript/language-async/proxy-detail)》）

### 应用五：创建只读的"视图"对象

有时候你需要暴露一个对象的"只读副本"给外部使用——允许读取所有属性，但禁止任何形式的修改。`defineProperty` 可以帮你做到：

```javascript
function createReadOnlyView(source) {
  const view = {};
  
  const descriptors = Object.getOwnPropertyDescriptors(source);
  
  for (let [key, desc] of Object.entries(descriptors)) {
    if (desc.get || desc.set) {
      // 如果是访问器属性，保留 getter，移除 setter
      Object.defineProperty(view, key, {
        get: desc.get,        // 保留 getter（可以正常读取）
        enumerable: desc.enumerable,
        configurable: false   // 不可重新定义
      });
    } else {
      // 如果是数据属性，设为不可写
      Object.defineProperty(view, key, {
        value: desc.value,
        writable: false,      // 不可写入
        enumerable: desc.enumerable,
        configurable: false   // 不可重新定义
      });
    }
  }
  
  // 冻结整个视图对象，阻止添加新属性
  return Object.freeze(view);
}

// 使用
const originalData = {
  name: '张三',
  score: 95,
  _meta: { version: 1 }
};

const readOnlyCopy = createReadOnlyView(originalData);

console.log(readOnlyCopy.name);     // "张三" ✅ 可读
console.log(readOnlyCopy.score);    // 95 ✅ 可读

readOnlyCopy.name = '黑客';         // ❌ TypeError（frozen + writable:false）
readOnlyCopy.hack = 'injected';     // ❌ TypeError（frozen，不可扩展）

// 原始对象不受影响
originalData.name = '李四';         // ✅ 原始对象仍然可修改
console.log(originalData.name);     // "李四"
console.log(readOnlyCopy.name);     // "张三"（视图是快照，不是引用）
```

这种"快照式只读视图"在以下场景中非常有用：

- **API 响应数据的保护**：防止组件意外修改共享状态
- **配置对象的导出**：允许读取配置但不允许运行时篡改
- **安全沙箱中的数据传递**：限制不可信代码对数据的修改能力

## defineProperty 的限制与注意事项

没有任何 API 是完美的。`Object.defineProperty` 有一些重要的局限性，了解它们可以帮助你在正确的场景选择正确的工具。

### 限制一：无法检测属性的添加或删除

`defineProperty` 必须预先知道属性的名字才能对其进行劫持。如果在 `defineProperty` 之后才动态添加新属性，这些新增属性不会有任何拦截能力：

```javascript
const data = {};

makeReactive(data, callback);  // 假设上面的响应式函数

data.existingProp = 'hello';   // ✅ 能被拦截到

// 但动态添加的新属性呢？
data.newDynamicProp = 'world'; // ❌ 不会被拦截！因为 defineProperty 时它还不存在
```

这正是 Vue 2.x 中 `Vue.set()` 和 `this.$set()` 存在的原因——它们内部会手动为新属性调用 `defineProperty` 来补充响应式能力。

如果你需要对动态属性也有拦截能力，**ES6 的 `Proxy` 是更好的选择**（参见《[Proxy代理详解](/frontend/javascript/language-async/proxy-detail)》）。Proxy 可以拦截任何属性的操作——无论属性是否已经存在。

### 限制二：无法高效地检测数组索引的变化

对于数组来说，通过 `defineProperty` 拦截每个索引（0, 1, 2, ..., n）的性能开销是很大的。Vue 2.x 不得不对数组的变异方法（push、pop、shift、unshift、splice、sort、reverse）进行特殊包装来解决这个问题——但这是一种 workaround 而非完美方案。

### 限制三：嵌套对象需要递归处理

`defineProperty` 只能拦截直接定义的那个对象上的属性。如果属性的值本身是一个对象，对这个子对象属性的修改是不会被感知到的：

```javascript
const data = makeReactive({
  user: {
    name: '张三',
    address: {
      city: '北京'
    }
  }
}, onChange);

data.user.name = '李四';        // ❌ 不会触发 onChange！
                                // 因为 name 是 user 子对象的属性，
                                // 而 user 子对象没有被 defineProperty 处理过
```

解决方案是递归地对所有嵌套对象执行 `makeReactive`——但这又会带来深度遍历的性能问题和循环引用的风险。

### 限制四：与其他机制的交互复杂性

`defineProperty` 定义的属性在与 `Object.assign()`、展开运算符、`JSON.parse()` 等操作交互时，可能产生不符合直觉的结果：

```javascript
const source = {};
Object.defineProperty(source, 'hidden', {
  value: 'secret',
  enumerable: false
});
source.visible = 'public';

// Object.assign 只复制可枚举属性
const copy1 = Object.assign({}, source);
console.log(copy1);  // { visible: 'public' } —— hidden 丢失了！

// 展开运算符同样如此
const copy2 = { ...source };
console.log(copy2);  // { visible: 'public' } —— hidden 也丢失了！

// 如果你需要完整复制（含不可枚举属性），需要特殊处理
function deepCopyWithNonEnumerable(source) {
  const copy = {};
  const descriptors = Object.getOwnPropertyDescriptors(source);
  for (let [key, desc] of Object.entries(descriptors)) {
    Object.defineProperty(copy, key, desc);
  }
  return copy;
}

const copy3 = deepCopyWithNonEnumerable(source);
console.log(copy3.hidden);  // "secret" ✅ 保留了！
```

## 哲学思考：控制与自由的平衡艺术

### "最小权限原则"在属性系统中的体现

`Object.defineProperty` 所体现的设计哲学，可以用信息安全领域的一条经典原则来概括——**最小权限原则（Principle of Least Privilege）**：每一个模块、每一个属性、每一行代码，都应该只拥有完成其工作所需的最小权限集，不多也不少。

在传统的对象模型中（比如 `obj.x = 1` 创建的属性），一个属性默认拥有"最大权限"——谁都可以读、谁都可以写、谁都能在遍历中看到它、谁都能把它删掉。这在快速原型开发和脚本编写场景下非常方便，但在构建健壮的系统时却是一个隐患。

`defineProperty` 把这种"默认全开放"的模式翻转成了"默认全锁定，按需开启"。你需要可写性？显式声明 `writable: true`。你需要可枚举性？显式声明 `enumerable: true`。你需要可配置性？显式声明 `configurable: true`。每一个维度都需要开发者经过深思熟虑后才赋予。

这种设计迫使你在创建属性时停下来思考：**这个属性应该允许外部修改吗？它应该在遍历时出现吗？它应该能被删除吗？** 这种"强制思考"本身就是一种质量保障——它让你在编码阶段就考虑到了封装性和安全性，而不是事后打补丁。

### 枚举性的哲学：可见性不等于存在性

`enumerable: false` 带来的一个有趣启示是：**在 JavaScript 的世界里，"可见"和"存在"是两回事。** 一个属性可以存在但不可见（`enumerable: false`），可以被访问但不能被遍历，可以通过特定手段探测到但不会在常规扫描中出现。

这与现实世界何其相似：

- **人体内部的器官**：你的肝脏确实存在于你的体内，但它不会出现在你的外表上——除非你去做 CT 或 MRI（类似于 `getOwnPropertyNames` 这样的"深度扫描"工具）。
- **企业的商业机密**：一份保密协议确实存在于公司档案中，但它不会出现在公开的企业介绍册中——只有授权人员才能查阅。
- **计算机的操作系统文件**：系统的核心文件确实存在于硬盘上，但普通用户的文件浏览器看不到它们——你需要管理员权限和特殊的查看设置。

`enumerable: false` 不是"让属性消失"，而是**让属性退居幕后**——它依然在那里发挥着自己的作用，只是不在常规的聚光灯下露面。这是一种优雅的信息隐藏机制——比"完全不可访问"更灵活，比"完全公开"更安全。

### "显式优于隐式"的体现

Python 社区著名的 **Zen of Python** 中有一句话："Explicit is better than implicit"（显式优于隐式）。`Object.defineProperty` 的 verbose（冗长）语法正是这一理念的体现。

是的，`obj.x = 1` 比 `Object.defineProperty(obj, 'x', { value: 1, writable: true, enumerable: true, configurable: true })` 简短得多。但这种简洁是有代价的——你放弃了精确控制的能力，接受了"一套默认规则套用所有场景"的妥协。

当你写出完整的描述符定义时，你实际上是在撰写一份**属性的"宪法"**——明确定义了这个属性的权力边界和行为准则。任何阅读这段代码的人（包括未来的你自己），都能立刻理解这个属性的设计意图：它是只读的吗？它是对外隐藏的吗？它是可以被删除的吗？这些意图都被显式地编码在了描述符中，而不需要额外的文档注释来解释。

### 工具的本质：能力与责任的统一

最后，让我们回到一个更宏大的话题：**编程工具的设计反映了语言设计者对"程序员应该如何工作"的理解。**

JavaScript 提供了 `Object.defineProperty` 这样一个低级别、高精度的工具，等于是在说：**我相信你有能力也有责任去精确控制你创建的每一个属性的每一个行为维度。我不会替你做太多假设，也不会给你太多的"免费便利"。你需要什么，就去声明什么；你不声明的，我就按最安全的方式处理。**

这是一种**信任但验证（Trust but Verify）**的态度——信任开发者知道自己在做什么，但同时通过严格的默认值来防止意外的错误。

相比之下，某些更高层次的抽象（比如 `class` 中的装饰器、或者 TypeScript 的类型注解）则提供了更多的"便利性"和"自动化"，代价是你需要接受它们预设的约定和限制。没有绝对的优劣之分——不同的场景需要不同层次的抽象。

真正的高手不是只会用一种工具的人，而是**知道什么时候该用手术刀（defineProperty）、什么时候该用菜刀（赋值操作符）、什么时候该用流水线（class）的人。** 工具没有高低，只有合适与否。

## 总结：知识体系全景

### 核心 API 速查

| 方法 | 功能 | 返回值 |
|------|------|--------|
| `Object.defineProperty(o, p, d)` | 定义/修改单个属性的描述符 | 目标对象 o |
| `Object.defineProperties(o, ds)` | 批量定义/修改多个属性 | 目标对象 o |
| `Object.getOwnPropertyDescriptor(o, p)` | 获取单个属性的描述符 | 描述符对象或 undefined |
| `Object.getOwnPropertyDescriptors(o)` | 获取所有自有属性的描述符 | 描述符字典 |

### 描述符维度速查

| 维度 | 类型 | 默认值(defineProperty) | 作用 |
|------|------|----------------------|------|
| `value` | Any | `undefined` | 数据属性的值 |
| `writable` | Boolean | **`false`** | 是否允许 `=` 赋值 |
| `enumerable` | Boolean | **`false`** | 是否出现在枚举操作中 |
| `configurable` | Boolean | **`false`** | 是否可删除/重定义 |
| `get` | Function | `undefined` | 读取时的拦截函数 |
| `set` | Function | `undefined` | 写入时的拦截函数 |

### 枚举操作速查

| 操作 | 受 enumerable 影响？ | 包含原型链？ | 包含 Symbol？ |
|------|---------------------|------------|--------------|
| `for...in` | ✅ 跳过不可枚举 | ✅ 沿原型链 | ❌ |
| `Object.keys/values/entries` | ✅ 跳过不可枚举 | ❌ 仅自身 | ❌ |
| `JSON.stringify()` | ✅ 跳过不可枚举 | ❌ 仅自身 | ❌ |
| `Object.getOwnPropertyNames()` | ❌ 全部包含 | ❌ 仅自身 | ❌ 仅字符串键 |
| `Reflect.ownKeys()` | ❌ 全部包含 | ❌ 仅自身 | ✅ 全部包含 |
| `in` 操作符 | ❌ 不受影响 | ✅ 沿原型链 | ✅ |

### 最佳实践清单

1. **永远显式指定描述符属性**——不要依赖 `defineProperty` 的默认值（它们全是 `false`）
2. **内部辅助属性用 `enumerable: false`**——避免污染遍历结果和 JSON 序列化
3. **只读数据用 `writable: false` + `configurable: false`**——双重保险
4. **需要拦截读写时使用 get/set**——但要小心内存泄漏（闭包引用）和 `this` 绑定问题
5. **批量初始化用 `defineProperties`**——代码更清晰、结构更声明式
6. **需要完整属性信息时用 `getOwnPropertyNames` 或 `Reflect.ownKeys`**——不要遗漏不可枚举属性
7. **动态属性拦截考虑 Proxy**——`defineProperty` 在这方面有先天局限

> **`Object.defineProperty` 是 JavaScript 对象系统中最接近"元编程（Metaprogramming）"层面的 API 之一。** 它让你从"对象的使用者"跃升为"对象的设计者"——不再被动地接受对象的行为规则，而是主动地去定义、塑造、约束这些规则。掌握它，意味着你拥有了更深层次的语言掌控力。而这种掌控力，正是从"写能跑的代码"到"写优雅、安全、可维护的架构"的关键一步。
