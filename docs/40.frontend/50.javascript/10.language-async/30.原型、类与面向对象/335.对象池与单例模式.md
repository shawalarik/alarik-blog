# 对象池模式 + 单例模式的多种 JS 实现

> **核心内容**：单例模式（Singleton）的本质、五种实现方式（全局变量/模块级闭包/惰性初始化/Proxy/装饰器）、对象池模式（Object Pool）的原理与实现、对象复用对性能的影响、两种模式在游戏开发、数据库连接管理、DOM 操作优化中的实战应用，以及"唯一性"和"复用性"的设计哲学。

## 一个关于"重复"与"唯一"的矛盾

让我们从一段看似简单却暗藏性能问题的代码开始：

```javascript
// 场景：一个动画库，每帧需要创建大量的向量对象来做插值计算
class Vector2 {
  constructor(x = 0, y = 0) {
    this.x = x;
    this.y = y;
  }
  
  add(v) { return new Vector2(this.x + v.x, this.y + v.y); }
  multiply(scalar) { return new Vector2(this.x * scalar, this.y * scalar); }
  normalize() {
    const len = Math.sqrt(this.x * this.x + this.y * this.y);
    return new Vector2(this.x / len, this.y / len);
  }
}

// 动画循环 —— 每秒 60 帧，每帧创建数十个临时向量
function animate(particles) {
  particles.forEach(p => {
    const velocity = new Vector2(p.vx, p.vy);
    const gravity = new Vector2(0, 9.8);
    const force = velocity.add(gravity).multiply(p.mass);
    // ... 更多计算，每步都 new Vector2(...)
    
    p.x += force.x * dt;
    p.y += force.y * dt;
  });
}

// 假设有 500 个粒子，每帧每个粒子平均产生 5 个临时向量：
// 每秒创建量 = 500 × 5 × 60 = 150,000 个 Vector2 对象！
```

这段代码的逻辑完全正确。但它在运行时会产生**海量的短生命周期对象**——每个 `Vector2` 只在当前计算步骤中存活几微秒，然后就被丢弃等待垃圾回收器处理。

这会带来三个问题：

1. **GC 压力**：大量对象的频繁创建和销毁会触发垃圾回收器的频繁运行，造成**停顿（GC Pause）**——在回收期间主线程被阻塞，用户感受到的就是画面卡顿或掉帧
2. **内存碎片化**：反复的分配和释放会导致堆内存中出现大量不连续的小块空间，降低内存分配效率
3. **缓存局部性差**：新分配的对象可能位于内存中完全不同的位置，不利于 CPU 缓存的命中

现在再看另一个场景：

```javascript
// 场景：应用中需要一个"全局配置管理器"
class ConfigManager {
  constructor() {
    this.config = {};
    this.listeners = [];
    this.changeLog = [];
    this.loadFromStorage();
  }
  
  loadFromStorage() { /* ... */ }
  get(key) { return this.config[key]; }
  set(key, value) { /* ... */ }
  subscribe(fn) { /* ... */ }
}

// 问题：如果在不同模块中被多次实例化……
const manager1 = new ConfigManager();  // 模块 A
const manager2 = new ConfigManager();  // 模块 B
const manager3 = new ConfigManager();  // 模块 C

// 现在你有了三个配置管理器，它们各自加载配置、各自维护状态。
// 在 manager1 中修改了某个设置，manager2 和 manager3 完全不知道。
// 整个应用的配置状态分裂了 —— 这几乎肯定是一个 Bug
```

这两个问题看似不同——一个是"对象太多"，另一个是"对象太多份"——但它们都指向了同一个根本性的设计命题：**如何控制对象的创建数量和使用方式？**

本文将围绕两个经典的设计模式来回答这个问题：

- **单例模式（Singleton Pattern）**：确保一个类只有一个实例，并提供一个全局访问点——解决"对象太多份"的问题
- **对象池模式（Object Pool Pattern）**：通过复用对象来减少创建和销毁的开销——解决"对象太多（太频繁）"的问题

## 第一部分：单例模式（Singleton Pattern）

### 核心思想：全局唯一的约束

单例模式是 GoF《设计模式》中创建型模式的一种，也是最广为人知的设计模式之一。它的定义极其简洁：**确保一个类只有一个实例，并提供一个全局访问点来访问该实例。**

这个定义包含两个不可分割的部分：

1. **唯一性约束**：无论代码中有多少处请求创建该类的实例，整个程序运行期间只能存在一个
2. **全局可访问性**：任何需要使用该实例的地方都能方便地获取它

为什么需要这种约束？因为有些事物在本质上就是**全系统共享且唯一的**：

| 实体 | 为什么应该是单例 |
|------|----------------|
| 数据库连接池 | 多个连接池意味着多个独立的连接集，浪费资源且可能导致数据不一致 |
| 应用配置中心 | 配置应该只有一份权威来源，分散的配置必然导致混乱 |
| 日志记录器 | 多个日志实例可能导致日志顺序错乱、文件竞争写入 |
| 窗口管理器 | 一个页面只有一个 window 对象，管理它的逻辑也应该只有一个 |
| 状态存储（Store） | Redux/Vuex/Pinia 的 store 就是典型的单例 |

### 单例 vs 全局变量：关键区别

很多人会把"把东西挂到 globalThis 上"当成单例模式。这是一个误解：

```javascript
// ❌ 这不是单例模式 —— 这是裸奔的全局变量
globalThis.appConfig = {
  debug: false,
  version: '1.0.0'
};

// 问题 1：任何地方都可以随意覆盖
globalThis.appConfig = '我被篡改了';  // 💥 类型都变了

// 问题 2：无法控制初始化时机
console.log(globalThis.appConfig.someDeepProperty);  // 如果还没初始化呢？

// 问题 3：无法防止重复"声明"
if (someCondition) {
  globalThis.mySingleton = new SomeClass();  // 又一个？
}
```

**单例模式的核心不是"全局可访问"，而是"受控的唯一性"。** 一个真正的单例实现应该：
- 隐藏构造函数（防止外部直接 `new`）
- 提供统一的访问入口（如 `getInstance()`）
- 控制初始化过程（通常是惰性的，首次访问时才创建）
- 保护内部状态不被外部意外破坏

## 单例模式的五种实现方式

### 方式一：模块级闭包单例（最常用）

JavaScript 的模块作用域天然提供了封装能力，使得实现单例变得异常简洁：

```javascript
// configManager.js
let instance = null;

class ConfigManager {
  #config;      // ES2022 私有字段
  #listeners;
  
  constructor() {
    if (instance) {
      throw new Error('ConfigManager 是单例类，请使用 getInstance() 获取实例');
    }
    
    this.#config = {};
    this.#listeners = [];
    this._loadDefaults();
  }
  
  _loadDefaults() {
    this.#config = {
      appName: 'MyApp',
      version: '1.0.0',
      environment: process.env.NODE_ENV || 'development'
    };
  }
  
  get(key) { return this.#config[key]; }
  set(key, value) {
    const oldVal = this.#config[key];
    this.#config[key] = value;
    this.#notifyListeners(key, value, oldVal);
  }
  
  #notifyListeners(key, newVal, oldVal) {
    this.#listeners.forEach(fn => fn(key, newVal, oldVal));
  }
  
  subscribe(fn) {
    this.#listeners.push(fn);
    return () => {  // 返回取消订阅函数
      const idx = this.#listeners.indexOf(fn);
      if (idx > -1) this.#listeners.splice(idx, 1);
    };
  }
  
  // ====== 静态工厂方法 ======
  static getInstance() {
    if (!instance) {
      instance = new ConfigManager();
    }
    return instance;
  }
}

export default ConfigManager.getInstance;
// 或者 export { ConfigManager } 让使用者自行调用 getInstance()
```

```javascript
// 使用方 A
import getConfig from './configManager.js';
const configA = getConfig();

// 使用方 B
import getConfig from './configManager.js';
const configB = getConfig();

console.log(configA === configB);  // true ✅ 同一个实例！

configA.set('debug', true);
console.log(configB.get('debug'));  // true —— 共享状态 ✅
```

**工作原理分析**：

由于 ES Module 的特性——同一个模块只会被执行一次并缓存其导出值——模块顶层变量 `instance` 在整个应用生命周期内只存在一份。无论有多少个文件 `import` 这个模块，它们拿到的都是同一个 `instance` 引用。

`getInstance()` 方法采用了经典的**双重检查**模式（虽然在这个同步版本中只有一次检查）：第一次调用时创建实例并存入 `instance` 变量；后续调用直接返回已有实例。

#### 为什么要在构造函数里做防御？

注意上面 `constructor` 中的那段防御代码：

```javascript
constructor() {
  if (instance) {
    throw new Error('ConfigManager 是单例类，请使用 getInstance() 获取实例');
  }
}
```

这看起来有点奇怪——既然我们已经通过 `getInstance()` 来控制创建了，为什么还要在构造函数里再检查一次？

答案是：**JavaScript 无法真正阻止有人直接调用 `new ConfigManager()`。** 不像 Java 或 C++ 可以将构造函数设为 private，JavaScript 的 class 构造函数总是可以被外部调用的。构造函数里的检查是最后一道防线——如果有人绕过了 `getInstance()` 直接 `new`，至少会收到一个明确的错误提示而不是静默地创建了第二个实例。

### 方式二：惰性初始化 + IIFE 封装

如果你希望连类本身也不对外暴露（更彻底的封装），可以使用 IIFE（立即执行函数表达式）：

```javascript
// database.js
const db = (function() {
  let instance = null;
  
  // 类定义完全封闭在 IIFE 内部
  class DatabaseConnection {
    #pool;
    #activeConnections;
    
    constructor(connectionString) {
      this.connectionString = connectionString;
      this.#pool = [];
      this.#activeConnections = new Set();
      console.log(`📡 数据库连接已建立: ${connectionString}`);
    }
    
    query(sql) {
      console.log(`🔎 执行查询: ${sql}`);
      return Promise.resolve([{ id: 1, name: '测试数据' }]);
    }
    
    close() {
      console.log('🔒 连接已关闭');
      this.#pool.forEach(c => c.release());
      this.#activeConnections.clear();
    }
    
    get stats() {
      return {
        poolSize: this.#pool.length,
        activeCount: this.#activeConnections.size
      };
    }
  }
  
  return {
    /**
     * 获取数据库单例实例
     * @param {string} [connectionString] - 仅首次调用时有效
     */
    getInstance(connectionString) {
      if (!instance) {
        if (!connectionString) {
          throw new Error('首次调用必须提供 connectionString');
        }
        instance = new DatabaseConnection(connectionString);
      } else if (connectionString && connectionString !== instance.connectionString) {
        console.warn('⚠️ 已有活跃连接，忽略新的连接字符串');
      }
      return instance;
    },
    
    // 可选：暴露重置方法用于测试
    _reset() {
      if (instance) instance.close();
      instance = null;
    }
  };
})();

export default db;
```

```javascript
// 使用
import db from './database.js';

const connection1 = db.getInstance('mysql://localhost:3306/mydb');
const connection2 = db.getInstance();  // 无需再次传参

console.log(connection1 === connection2);  // true ✅

connection1.query('SELECT * FROM users');

// 尝试创建第二个连接（会被忽略）
const connection3 = db.getInstance('postgres://...');
// ⚠️ 警告输出，但仍然返回原实例
console.log(connection3 === connection1);  // true
```

IIFE 方式的优势在于**完全不暴露类的构造函数**——外部代码连 `DatabaseConnection` 这个名字都不知道，更不可能直接 `new` 它。所有的创建行为都被 `db.getInstance()` 这一个入口牢牢把控。

### 方式三：Proxy 拦截构造

ES6 的 Proxy 提供了一种更优雅的方式来禁止直接 `new`：

```javascript
function createSingleton(ClassConstructor) {
  let instance = null;
  
  // 用 Proxy 包装构造函数
  const ProxiedClass = new Proxy(ClassConstructor, {
    construct(target, args) {
      if (!instance) {
        instance = new target(...args);  // 只允许创建一次
      }
      return instance;  // 后续所有 new 都返回同一实例
    }
  });
  
  // 同时提供一个显式获取方法（语义更清晰）
  ProxiedClass.getInstance = function(...args) {
    if (!instance) {
      instance = new ClassConstructor(...args);
    }
    return instance;
  };
  
  return ProxiedClass;
}

// 定义普通类
class Logger {
  #logs = [];
  
  log(level, message) {
    const entry = { timestamp: Date.now(), level, message };
    this.#logs.push(entry);
    console.log(`[${level.toUpperCase()}] ${message}`);
  }
  
  getHistory() { return [...this.#logs]; }
  clear() { this.#logs = []; }
}

// 将其变为单例类
const SingletonLogger = createSingleton(Logger);

export default SingletonLogger;
```

```javascript
// 使用 —— 无论用 new 还是 getInstance，都拿到同一个实例
import Logger from './logger.js';

const logger1 = new Logger();
const logger2 = new Logger();
const logger3 = Logger.getLogger();

console.log(logger1 === logger2);   // true ✅
console.log(logger2 === logger3);   // true ✅

logger1.log('info', '应用启动');   // [INFO] 应用启动
logger2.log('warn', '内存使用率高');// [WARN] 内存使用率高

console.log(logger3.getHistory());  // 两条记录都有 —— 同一个实例
```

Proxy 方案的精妙之处在于：**它让 `new` 操作符本身变成了获取单例的方式。** 调用者甚至不需要知道自己在使用单例——他们只是正常地 `new` 了一个类，而底层自动保证了唯一性。这种透明性让单例模式的侵入性降到最低。

### 方式四：ES2022 静态块 + 私有字段

ES2022 引入的静态初始化块（Static Initialization Blocks）为单例模式提供了另一种优雅的实现方式：

```javascript
class AppStore {
  // 静态私有字段 —— 存储唯一实例
  static #instance = null;
  
  // 实例私有字段
  #state;
  #subscribers;
  
  // 静态初始化块 —— 在类定义时执行一次
  static {
    // 这里可以做一些静态初始化工作
    Object.defineProperty(AppStore, 'version', {
      value: '1.0.0',
      writable: false,
      configurable: false
    });
  }
  
  constructor(initialState = {}) {
    // 防止外部直接 new
    if (AppStore.#instance) {
      throw new Error(
        'AppStore 是单例类。请使用 AppStore.getInstance() 获取实例。\n' +
        '或者使用 AppStore.create(initialState) 进行首次初始化。'
      );
    }
    
    this.#state = { ...initialState };
    this.#subscribers = new Map();
    
    AppStore.#instance = this;
  }
  
  // 创建/获取单例
  static create(initialState = {}) {
    if (!AppStore.#instance) {
      new AppStore(initialState);
    }
    return AppStore.#instance;
  }
  
  static getInstance() {
    if (!AppStore.#instance) {
      new AppStore();  // 默认空状态初始化
    }
    return AppStore.#instance;
  }
  
  // 状态读取
  getState() { return { ...this.#state }; }  // 返回副本，保护原始状态
  
  setState(partial) {
    const prevState = { ...this.#state };
    Object.assign(this.#state, partial);
    this.#notify(prevState, this.#state);
  }
  
  // 订阅状态变化
  subscribe(selector, callback) {
    const id = Symbol('subscriber');
    this.#subscribers.set(id, { selector, callback });
    return () => this.#subscribers.delete(id);  // 返回取消订阅函数
  }
  
  #notify(prevState, newState) {
    this.#subscribers.forEach(({ selector, callback }, id) => {
      const prevSelected = selector ? selector(prevState) : prevState;
      const newSelected = selector ? selector(newState) : newState;
      
      if (prevSelected !== newSelected) {
        callback(newSelected, prevSelected);
      }
    });
  }
}

export default AppStore;
```

```javascript
// 使用
import AppStore from './store.js';

// 初始化（只应在应用启动时调用一次）
const store = AppStore.create({
  user: null,
  theme: 'dark',
  locale: 'zh-CN'
});

// 其他地方获取
import AppStore from './store.js';
const sameStore = AppStore.getInstance();

console.log(store === sameStore);  // true ✅

// 订阅状态变化
store.subscribe(
  state => state.user,           // 选择器：只关注 user 部分
  (newUser, oldUser) => {
    console.log(`用户变化: ${oldUser?.name ?? '未登录'} → ${newUser?.name ?? '未登录'}`);
  }
);

store.setState({ user: { name: '张三', id: 1 } });
// 输出: 用户变化: 未登录 → 张三
```

### 方式五：装饰器模式（Decorator）

如果你在使用 TypeScript 或支持装饰器的环境，可以用一种声明式的方式来实现单例：

```javascript
// singleton.decorator.js
/**
 * 单例装饰器工厂
 * @returns {ClassDecorator}
 */
function Singleton() {
  return function(TargetClass) {
    let instance = null;
    
    // 保留原始构造函数的引用（以便内部使用）
    const OriginalConstructor = TargetClass;
    
    // 替换构造函数
    function SingletonConstructor(...args) {
      if (!instance) {
        instance = new OriginalConstructor(...args);
      }
      return instance;
    }
    
    // 复制原型链和静态属性
    SingletonConstructor.prototype = OriginalConstructor.prototype;
    SingletonConstructor.prototype.constructor = SingletonConstructor;
    Object.setPrototypeOf(SingletonConstructor, OriginalConstructor);
    
    // 添加便捷方法
    SingletonConstructor.getInstance = function(...args) {
      if (!instance) {
        instance = new OriginalConstructor(...args);
      }
      return instance;
    };
    
    SingletonConstructor.isInstantiated = function() {
      return instance !== null;
    };
    
    SingletonConstructor.destroyInstance = function() {
      instance = null;
    };
    
    return SingletonConstructor;
  };
}

export default Singleton;
```

```javascript
// 使用装饰器
@Singleton()
class EventBus {
  #handlers = {};
  
  on(event, handler) {
    if (!this.#handlers[event]) {
      this.#handlers[event] = [];
    }
    this.#handlers[event].push(handler);
  }
  
  off(event, handler) {
    const handlers = this.#handlers[event];
    if (handlers) {
      const idx = handlers.indexOf(handler);
      if (idx > -1) handlers.splice(idx, 1);
    }
  }
  
  emit(event, data) {
    const handlers = this.#handlers[event];
    if (handlers) {
      handlers.slice().forEach(handler => {
        try {
          handler(data);
        } catch (err) {
          console.error(`EventBus [${event}] handler error:`, err);
        }
      });
    }
  }
}

export default EventBus;
```

```javascript
import EventBus from './eventBus.js';

const bus1 = new EventBus();
const bus2 = new EventBus();

bus1.on('user-login', (data) => console.log('用户登录:', data));

bus2.emit('user-login', { name: '张三' });  // bus1 的监听器也会触发！✅

console.log(bus1 === bus2);  // true
console.log(EventBus.isInstantiated());  // true
```

装饰器方式的优势在于**声明式的语义表达**——你只需在类定义前加上 `@Singleton()` 就完成了单例转换，无需修改类的内部代码。这遵循了开闭原则（Open-Closed Principle）：对扩展开放（可以给任何类加上单例行为），对修改关闭（不需要改动类本身的实现）。

## 第二部分：对象池模式（Object Pool Pattern）

### 核心思想：以"租借"代替"创建"

如果说单例模式解决的是"不要创建太多份"的问题，那么对象池模式解决的是"不要创建太多次"的问题。

对象池的基本思路是：**预先创建一批对象放入"池子"中，当需要使用时从池中取出一个（借用），使用完毕后归还到池中（而非销毁）。** 这样就避免了频繁的对象创建和 GC 回收开销。

```javascript
// 最简单的对象池概念模型
class SimplePool {
  #available = [];  // 可用对象列表
  #inUse = new Set();  // 正在使用的对象
  
  /** 从池中获取一个对象 */
  acquire() {
    let obj;
    if (this.#available.length > 0) {
      obj = this.#available.pop();  // 复用已有的
    } else {
      obj = this._createNew();     // 池子空了才创建新的
    }
    this.#inUse.add(obj);
    return obj;
  }
  
  /** 归还对象到池中 */
  release(obj) {
    if (this.#inUse.has(obj)) {
      this.#inUse.delete(obj);
      this._reset(obj);       // 重置对象状态
      this.#available.push(obj);
    }
  }
  
  // 子类需要实现的方法
  _createNew() { throw new Error('子类必须实现 _createNew()'); }
  _reset(obj) {}  // 默认不做任何事
}
```

### 通俗类比：共享单车 vs 私家车

想象一下你在城市中需要用车出行：

- **每次 new 一个对象就像买一辆私家车**：你每次出门都买一辆新车，到达目的地后就把车扔掉。这不仅极度浪费（每辆车只用了一次），而且城市里很快就会堆满废弃车辆（内存泄漏/GC 压力）。当然，买车的好处是你拥有完全的控制权——想怎么改装都行，不用担心别人用过留下的痕迹。
- **对象池就像共享单车（Bike Sharing）**：运营公司预先在城市各处投放了一批单车（预分配）。你需要用车时扫码借一辆（acquire），骑到目的地上锁还回去（release）。下一辆车的人继续使用这辆车（复用）。车会被定期检修和清洁（reset），确保每位用户拿到的是干净可用的。整个城市的车辆总数是可控的，不会无限制增长。

对象池的本质就是**编程世界中的共享单车系统**——用"借还"机制替代"创建销毁"机制，用有限资源的循环利用替代无限资源的消耗。

### 为什么需要对象池？

对象池的价值体现在以下场景中：

**1. 对象创建成本高**

某些对象的构造过程涉及复杂的初始化操作（如建立网络连接、读取大文件、分配大块内存、解析复杂配置等），复用这些对象可以避免重复支付这些成本。

**2. 对象数量巨大且生命周期短**

如开篇例子中的粒子系统、游戏中的子弹/特效、高频交易中的订单对象——每秒可能创建和销毁成千上万个对象。

**3. 需要避免 GC 停顿**

在实时系统中（游戏引擎、音频处理、视频编码），GC 导致的毫秒级停顿可能是不可接受的。对象池通过维持固定数量的长生命周期对象，大幅减少了触达 GC 阈值的频率。

### 性能量化对比

让我们用一个基准测试来直观感受对象池的性能优势：

```javascript
// 测试对象：模拟一个轻量的 2D 向量
class Vec2 { constructor(x = 0, y = 0) { this.x = x; this.y = y; } }

// ====== 普通 new 方式 ======
function benchmarkNew(iterations = 1000000) {
  const start = performance.now();
  
  for (let i = 0; i < iterations; i++) {
    const v = new Vec2(i % 100, i % 50);
    // 模拟一些运算
    v.x *= 1.5;
    v.y *= 2.0;
    // v 在这里超出作用域，成为垃圾
  }
  
  return performance.now() - start;
}

// ====== 对象池方式 ======
class Vec2Pool {
  #pool = [];
  
  acquire(x = 0, y = 0) {
    const v = this.#pool.pop() || new Vec2(x, y);
    v.x = x;
    v.y = y;
    return v;
  }
  
  release(v) {
    this.#pool.push(v);
  }
}

function benchmarkPool(iterations = 1000000) {
  const pool = new Vec2Pool();
  const start = performance.now();
  
  for (let i = 0; i < iterations; i++) {
    const v = pool.acquire(i % 100, i % 50);
    v.x *= 1.5;
    v.y *= 2.0;
    pool.release(v);  // 归还而不是丢弃
  }
  
  return performance.now() - start;
}

// 运行对比
console.log('new 方式:', benchmarkNew(1000000).toFixed(2), 'ms');
console.log('池化方式:', benchmarkPool(1000000).toFixed(2), 'ms');

// 典型的输出结果（具体数值因设备而异）：
// new 方式: 180~300 ms （取决于 GC 触发频率）
// 池化方式: 15~30 ms    （稳定，几乎不受 GC 影响）
// 性能差距：约 6~10 倍！
```

> 注意：实际差距取决于对象大小、创建频率、GC 策略等因素。对于非常小的对象，差异可能不明显。但对于涉及 DOM 操作、网络请求、大数组分配的对象，差异会非常显著。

## 对象池的完整实现

### 通用对象池框架

下面是一个生产级的通用对象池实现，支持多种配置选项：

```javascript
/**
 * 通用对象池
 * @template T
 */
class ObjectPool {
  /** @type {T[]} */
  #available;
  
  /** @type {Set<T>} */
  #inUse;
  
  /** @type {number} 最大容量（0 表示无限制） */
  #maxSize;
  
  /** @type {() => T} 工厂函数：创建新对象 */
  #factory;
  
  /** @type {(obj: T) => void} 重置函数：清理归还的对象 */
  #resetter;
  
  /** @type {number} 当前池中可用对象数 */
  #availableCount = 0;
  
  /** @type {number} 总共创建过的对象数（含已销毁的） */
  #totalCreated = 0;
  
  /** @type {number} 总共借出的次数 */
  #totalAcquired = 0;
  
  /** @type {number} 总共归还的次数 */
  #totalReleased = 0;
  
  /**
   * @param {Object} options
   * @param {() => T} options.factory - 必填：创建新对象的工厂函数
   * @param {(obj: T) => void} [options.resetter] - 可选：归还时的重置逻辑
   * @param {number} [options.initialSize=10] - 初始预分配数量
   * @param {number} [options.maxSize=0] - 最大池容量（0=无限）
   * @param {boolean} [options.autoExpand=true] - 池空时是否自动扩展
   */
  constructor({
    factory,
    resetter = (obj) => {},
    initialSize = 10,
    maxSize = 0,
    autoExpand = true
  }) {
    if (typeof factory !== 'function') {
      throw new Error('factory 必须是一个函数');
    }
    
    this.#factory = factory;
    this.#resetter = resetter;
    this.#maxSize = maxSize;
    this.#autoExpand = autoExpand;
    this.#available = [];
    this.#inUse = new Set();
    
    // 预分配初始对象
    if (initialSize > 0) {
      for (let i = 0; i < initialSize; i++) {
        this.#available.push(factory());
        this.#totalCreated++;
      }
      this.#availableCount = initialSize;
    }
  }
  
  /**
   * 从池中获取一个对象
   * @returns {T}
   */
  acquire() {
    let obj;
    
    if (this.#available.length > 0) {
      // 从池中取出一个现有对象
      obj = this.#available.pop();
      this.#availableCount--;
    } else if (this.#autoExpand && (this.#maxSize === 0 || this.totalCreated < this.#maxSize)) {
      // 池为空但允许扩展 → 创建新的
      obj = this.#factory();
      this.#totalCreated++;
    } else {
      // 池满且不允许扩展 → 抛出异常（或根据策略等待/拒绝）
      throw new Error(
        `对象池已满（maxSize=${this.#maxSize}），无法分配新对象。` +
        `当前使用中: ${this.size}，可用: ${this.available}`
      );
    }
    
    this.#inUse.add(obj);
    this.#totalAcquired++;
    
    return obj;
  }
  
  /**
   * 归还对象到池中
   * @param {T} obj 
   * @returns {boolean} 是否成功归还
   */
  release(obj) {
    if (!this.#inUse.has(obj)) {
      console.warn('⚠️ 尝试归还一个不属于此池的对象，或已被归还过');
      return false;
    }
    
    this.#inUse.delete(obj);
    
    // 执行重置逻辑
    try {
      this.#resetter(obj);
    } catch (err) {
      console.error('对象重置失败:', err);
    }
    
    this.#available.push(obj);
    this.#availableCount++;
    this.#totalReleased++;
    
    return true;
  }
  
  /**
   * 使用回调自动管理对象的生命周期
   * 借出一个对象，执行回调后自动归还
   * @param {(obj: T) => any} callback - 使用对象的回调函数
   * @returns {ReturnType<typeof callback>} 回调的返回值
   */
  use(callback) {
    const obj = this.acquire();
    try {
      return callback(obj);
    } finally {
      this.release(obj);  // finally 确保即使回调抛错也能归还
    }
  }
  
  /**
   * 清空池中所有可用对象（正在使用的不受影响）
   */
  clearAvailable() {
    this.#available = [];
    this.#availableCount = 0;
  }
  
  /**
   * 强制收回所有对象（危险操作！）
   * 正在使用的对象也会被强制收回
   */
  forceClearAll() {
    this.#available = [];
    this.#inUse.clear();
    this.#availableCount = 0;
    this.#totalCreated = 0;
  }
  
  // ====== 只读属性 ======
  
  get size() { return this.#inUse.size; }
  get available() { return this.#availableCount; }
  get maxSize() { return this.#maxSize; }
  
  get stats() {
    return {
      inUse: this.size,
      available: this.available,
      totalCreated: this.#totalCreated,
      totalAcquired: this.#totalAcquired,
      totalReleased: this.#totalReleased,
      utilizationRate: this.#totalCreated > 0 
        ? (this.size / this.#totalCreated * 100).toFixed(1) + '%' 
        : 'N/A'
    };
  }
}
```

### 实战案例一：DOM 元素对象池

在动态列表、虚拟滚动、弹窗管理等场景中，频繁创建和销毁 DOM 元素是性能杀手之一：

```javascript
/**
 * DOM 元素对象池
 * 用于复用频繁创建/销毁的同类型 DOM 元素（如列表项、通知消息等）
 */
class DOMElementPool extends ObjectPool {
  /**
   * @param {string} tagName - 标签名
   * @param {Object} [options]
   * @param {number} options.initialSize - 初始池大小
   * @param {number} options.maxSize - 最大池大小
   * @param {Object} options.defaultAttributes - 默认属性
   * @param {string[]} options.defaultClasses - 默认 CSS 类名
   */
  constructor(tagName, {
    initialSize = 5,
    maxSize = 50,
    defaultAttributes = {},
    defaultClasses = []
  } = {}) {
    super({
      factory: () => {
        const el = document.createElement(tagName);
        
        // 设置默认属性
        Object.entries(defaultAttributes).forEach(([key, val]) => {
          el.setAttribute(key, val);
        });
        
        // 添加默认类名
        if (defaultClasses.length > 0) {
          el.classList.add(...defaultClasses);
        }
        
        return el;
      },
      
      resetter: (el) => {
        // 清除文本内容
        el.textContent = '';
        el.innerHTML = '';
        
        // 移除事件监听器（用 cloneNode 方案）
        const clone = el.cloneNode(false);
        el.parentNode?.replaceChild(clone, el);
        
        // 注意：这里实际上我们替换了元素本身，
        // 所以需要把克隆后的节点放回池中
        // 更好的做法是用事件委托而非逐个绑定
        return clone; // 但由于 resetter 不返回值，这里需要调整设计
        // 实际项目中建议用事件委托来彻底解决这个问题
      },
      
      initialSize,
      maxSize,
      autoExpand: true
    });
    
    this.tagName = tagName;
  }
  
  /**
   * 获取一个元素并设置内容
   */
  acquireWith(content, attributes = {}) {
    const el = this.acquire();
    
    if (typeof content === 'string') {
      el.textContent = content;
    } else if (content instanceof Node) {
      el.appendChild(content);
    }
    
    Object.entries(attributes).forEach(([key, val]) => {
      el.setAttribute(key, val);
    });
    
    return el;
  }
}

// 使用示例：高性能的通知消息系统
const notificationPool = new DOMElementPool('div', {
  initialSize: 3,
  defaultClasses: ['notification', 'animate-in'],
  defaultAttributes: { role: 'alert' }
});

function showNotification(message, type = 'info') {
  const el = notificationPool.acquireWith(message, {
    'data-type': type,
    'aria-live': 'polite'
  });
  el.classList.add(`notification--${type}`);
  
  document.body.appendChild(el);
  
  // 3 秒后自动隐藏并归还到池中
  setTimeout(() => {
    el.classList.remove('animate-in');
    el.classList.add('animate-out');
    
    // 动画结束后归还
    el.addEventListener('animationend', () => {
      el.remove();
      el.className = 'notification';  // 重置类名
      notificationPool.release(el);
    }, { once: true });
  }, 3000);
}

// 快速连续发送多条通知 —— 元素被高效复用
showNotification('欢迎回来！', 'success');
showNotification('您有 3 条新消息', 'info');
showNotification('磁盘空间不足', 'warning');
// 所有通知都从池中获取元素，消失后归还，没有浪费任何 DOM 创建
```

### 实战案例二：数据库连接池

这是对象池最经典的应用领域之一。数据库连接的创建代价极高（TCP 三次握手、认证协商、会话初始化等通常需要数百毫秒），因此复用连接是标准做法：

```javascript
/**
 * 简化的数据库连接池
 * （实际项目中应使用成熟的库如 pg-pool、mysql2/promise 的 pool 等）
 */
class ConnectionPool extends ObjectPool {
  #config;
  
  constructor(config, { maxConnections = 10, idleTimeout = 30000 } = {}) {
    super({
      factory: async () => await this.#createConnection(),
      resetter: async (conn) => {
        // 归还连接前的清理
        if (conn.transactionActive) {
          await conn.query('ROLLBACK');
        }
      },
      initialSize: Math.min(3, maxConnections),
      maxSize: maxConnections,
      autoExpand: true
    });
    
    this.#config = config;
    this.idleTimeout = idleTimeout;
    
    // 定期清理空闲超时的连接
    this.#idleCleaner = setInterval(() => this.#cleanupIdle(), idleTimeout / 2);
  }
  
  async #createConnection() {
    // 模拟连接创建（实际项目中替换为真实的驱动 API）
    const conn = {
      id: `conn_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`,
      connectedAt: Date.now(),
      lastUsedAt: Date.now(),
      queryCount: 0,
      transactionActive: false,
      
      async query(sql) {
        this.lastUsedAt = Date.now();
        this.queryCount++;
        console.log(`[${this.id}] 📤 ${sql}`);
        return { rows: [], rowCount: 0 };  // 模拟结果
      },
      
      async beginTransaction() {
        this.transactionActive = true;
        console.log(`[${this.id}] 🔒 事务开始`);
      },
      
      async commit() {
        this.transactionActive = false;
        console.log(`[${this.id}] ✅ 事务提交`);
      },
      
      async rollback() {
        this.transactionActive = false;
        console.log(`[${this.id}] ↩️ 事务回滚`);
      },
      
      async close() {
        console.log(`[${this.id}] 🔌 连接关闭`);
      }
    };
    
    console.log(`[Pool] 🔗 新连接已创建: ${conn.id}`);
    return conn;
  }
  
  async #cleanupIdle() {
    // 检查是否有空闲超时的连接需要释放
    // （简化版：实际实现需要遍历 available 列表）
  }
  
  /**
   * 执行查询（自动管理连接的借用和归还）
   */
  async query(sql) {
    const conn = this.acquire();
    try {
      const result = await conn.query(sql);
      return result;
    } catch (err) {
        console.error('查询出错:', err);
        throw err;
    } finally {
      // 注意：异步场景中 release 需要特别注意时序
      this.release(conn);
    }
  }
  
  /**
   * 在事务中执行操作
   */
  async transaction(workFn) {
    const conn = this.acquire();
    try {
      await conn.beginTransaction();
      const result = await workFn(conn);
      await conn.commit();
      return result;
    } catch (err) {
      await conn.rollback();
      throw err;
    } finally {
      this.release(conn);
    }
  }
  
  // 关闭连接池
  async destroy() {
    clearInterval(this.#idleCleaner);
    // 关闭所有连接...
  }
}

// 使用
const dbPool = new ConnectionPool({
  host: 'localhost',
  port: 3306,
  database: 'myapp',
  maxConnections: 20
});

async function exampleUsage() {
  // 自动借还
  const users = await dbPool.query('SELECT * FROM users LIMIT 10');
  
  // 事务操作
  const transferResult = await dbPool.transaction(async (conn) => {
    await conn.query("UPDATE accounts SET balance = balance - 100 WHERE id = 1");
    await conn.query("UPDATE accounts SET balance = balance + 100 WHERE id = 2");
    return { success: true };
  });
  
  console.log(dbPool.stats);
  // { inUse: 0, available: 3, totalCreated: 3, ... }
}
```

### 实战案例三：Canvas 2D 渲染对象池

游戏开发和 Canvas 动画是对象池的大显身手之地：

```javascript
/**
 * Canvas 2D 绘制上下文的对象池
 * 用于复用 Path2D、离屏 Canvas 等昂贵的绘制资源
 */
class CanvasResourcePool {
  pathPool;
  canvasPool;
  
  constructor() {
    // Path2D 对象池 —— Path2D 的创建有一定开销
    this.pathPool = new ObjectPool({
      factory: () => new Path2D(),
      resetter: (path) => {
        // Path2D 没有内置的 "clear" 方法
        // 我们通过重新赋值来清空路径
        // 注意：这是一种 workaround，更好的方案是维护一个干净的 Path2D 作为模板
        return path;
      },
      initialSize: 50,
      maxSize: 200
    });
    
    // 离屏 Canvas 池 —— Canvas 的创建和内存分配开销较大
    this.canvasPool = new ObjectPool({
      factory: () => {
        const canvas = document.createElement('canvas');
        const ctx = canvas.getContext('2d');
        return { canvas, ctx };
      },
      resetter: ({ ctx }) => {
        ctx.clearRect(0, 0, ctx.canvas.width, ctx.canvas.height);
        ctx.resetTransform();
      },
      initialSize: 5,
      maxSize: 15
    });
  }
  
  /**
   * 获取一个 Path2D 并绘制矩形
   */
  acquireRectPath(x, y, w, h) {
    const path = this.pathPool.acquire();
    path.rect(x, y, w, h);
    return path;
  }
  
  /**
   * 获取一个离屏 Canvas 用于双缓冲渲染
   */
  acquireOffscreenCanvas(width, height) {
    const { canvas, ctx } = this.canvasPool.acquire();
    canvas.width = width;
    canvas.height = height;
    return { canvas, ctx };
  }
  
  // 归还方法
  releasePath(path) { this.pathPool.release(path); }
  releaseCanvas(resource) { this.canvasPool.release(resource); }
}

// 在游戏循环中使用
const resourcePool = new CanvasResourcePool();
const activePaths = [];

function gameLoop(timestamp) {
  const ctx = mainCanvas.getContext('2d');
  
  ctx.clearRect(0, 0, mainCanvas.width, mainCanvas.height);
  
  // 绘制所有游戏实体
  entities.forEach(entity => {
    // 从池中获取 Path2D
    const path = resourcePool.acquireRectPath(
      entity.x, entity.y, entity.width, entity.height
    );
    
    activePaths.push(path);  // 记录以便帧结束时归还
    
    ctx.save();
    ctx.translate(entity.x + entity.width/2, entity.y + entity.height/2);
    ctx.rotate(entity.rotation);
    ctx.fill(path);
    ctx.restore();
  });
  
  // 帧结束 —— 归还所有借出的 Path2D
  activePaths.forEach(path => resourcePool.releasePath(path));
  activePaths.length = 0;
  
  requestAnimationFrame(gameLoop);
}
```

## 单例模式 vs 对象池模式：对比与选择

### 核心差异一览

| 维度 | 单例模式 | 对象池模式 |
|------|---------|-----------|
| **核心目标** | 限制实例数量为 **1** | 限制实例数量为 **N**（N ≥ 1）|
| **解决的问题** | 全局状态的统一管理 | 高频创建/销毁的性能优化 |
| **对象数量** | 固定 = 1 | 可变，但有上限（maxSize） |
| **生命周期** | 与应用同生共死 | 反复"借出→使用→归还"循环 |
| **典型场景** | 配置管理器、日志、Store | 粒子系统、连接池、DOM 复用 |
| **线程安全需求** | 低（JS 单线程） | 低（但需注意异步竞态） |
| **复杂度** | 低 | 中（需管理池状态） |

### 两者可以结合使用

事实上，**一个对象池本身就可以（而且经常）是一个单例**。你不希望在应用中创建多个独立的粒子对象池——那样每个池各自维护一套对象集合，反而失去了池化的意义：

```javascript
// 对象池作为单例的经典组合
class ParticleSystem {
  static #instance = null;
  
  #particlePool;
  #activeParticles;
  
  constructor(maxParticles = 10000) {
    // 单例防护
    if (ParticleSystem.#instance) {
      throw new Error('ParticleSystem 是单例');
    }
    
    this.#particlePool = new ObjectPool({
      factory: () => ({
        x: 0, y: 0, vx: 0, vy: 0,
        life: 0, maxLife: 60,
        color: '#fff',
        size: 2,
        active: false
      }),
      resetter: (p) => {
        p.active = false;
        p.life = 0;
        p.x = p.y = p.vx = p.vy = 0;
      },
      initialSize: 100,
      maxSize: maxParticles,
      autoExpand: false  // 池满后就不再创建新粒子
    });
    
    this.#activeParticles = [];
    
    ParticleSystem.#instance = this;
  }
  
  static getInstance(maxParticles) {
    if (!ParticleSystem.#instance) {
      new ParticleSystem(maxParticles);
    }
    return ParticleSystem.#instance;
  }
  
  emit(x, y, count = 10, config = {}) {
    for (let i = 0; i < count; i++) {
      let particle;
      try {
        particle = this.#particlePool.acquire();
      } catch {
        break;  // 池满了，停止发射
      }
      
      const angle = Math.random() * Math.PI * 2;
      const speed = 1 + Math.random() * config.speed || 3;
      
      particle.active = true;
      particle.x = x;
      particle.y = y;
      particle.vx = Math.cos(angle) * speed;
      particle.vy = Math.sin(angle) * speed;
      particle.life = config.maxLife || 60;
      particle.maxLife = particle.life;
      particle.color = config.color || '#ff6600';
      particle.size = config.size || 2;
      
      this.#activeParticles.push(particle);
    }
  }
  
  updateAndRender(ctx) {
    for (let i = this.#activeParticles.length - 1; i >= 0; i--) {
      const p = this.#activeParticles[i];
      
      // 更新物理
      p.x += p.vx;
      p.y += p.vy;
      p.vy += 0.1;  // 重力
      p.life--;
      
      if (p.life <= 0) {
        // 粒子死亡 → 归还到池中
        this.#particlePool.release(p);
        this.#activeParticles.splice(i, 1);
        continue;
      }
      
      // 渲染
      const alpha = p.life / p.maxLife;
      ctx.globalAlpha = alpha;
      ctx.fillStyle = p.color;
      ctx.beginPath();
      ctx.arc(p.x, p.y, p.size, 0, Math.PI * 2);
      ctx.fill();
    }
    ctx.globalAlpha = 1;
  }
  
  get stats() {
    return {
      ...this.#particlePool.stats,
      activeCount: this.#activeParticles.length
    };
  }
}

// 使用 —— 全局唯一的粒子系统
const ps = ParticleSystem.getInstance(5000);

// 发射粒子
canvas.addEventListener('click', (e) => {
  ps.emit(e.offsetX, e.offsetY, 30, { color: '#00aaff', speed: 5, maxLife: 90 });
});

// 游戏循环
function loop() {
  ctx.fillStyle = 'rgba(0, 0, 0, 0.2)';
  ctx.fillRect(0, 0, canvas.width, canvas.height);
  ps.updateAndRender(ctx);
  requestAnimationFrame(loop);
}
loop();
```

这个例子完美展示了单例和对象池的协同工作：**单例保证了粒子系统全局唯一（避免多个粒子系统互相冲突），对象池保证了粒子的创建/销复用高效可控（避免 GC 卡顿）。**

## 哲学思考：稀缺、共享与可持续

### "稀缺"是设计的起点

无论是单例还是对象池，它们的存在都源于同一个根本认知：**资源是稀缺的。**

内存不是无限的。CPU 周期不是免费的。数据库连接数有上限。DOM 操作有代价。每一个对象的创建都在向系统索取资源——而当资源被耗尽时，系统就会变慢、崩溃、或者做出不可预测的行为。

单例模式和对象池模式是对"稀缺性"的两种不同的回应策略：

- **单例模式说："这个东西只需要一份就够了。"** 它通过消除冗余来节约资源。与其每个人各持一份副本，不如所有人共用一份——前提是这个"东西"确实应该是全局共享的。
- **对象池模式说："这些东西需要很多份，但我们不必每次都从头造。"** 它通过循环利用来节约资源。与其用完即弃，不如建立一个"借用-归还"的生态系统。

### 共享的哲学：自由与秩序的平衡

单例模式本质上是一种**共享（Sharing）**策略。共享带来效率，但也引入了风险：

**共享的好处**：
- 内存效率：一份数据，到处可用
- 一致性保证：所有消费者看到的是同一份数据
- 协调便利：状态变更能被全局感知

**共享的风险**：
- 耦合增加：所有依赖单例的模块之间产生了隐式耦合
- 测试困难：单例的全局状态让单元测试难以隔离
- 并发问题：多线程环境中（Worker/线程）需要额外的同步机制
- "上帝对象"倾向：单例容易变成承载过多职责的庞然大物

对象池则是一种**受控的共享**——它允许同时存在多个对象（不像单例那样严格限定为一个），但总数受到控制。这是一种介于"完全自由（随便 new）"和"完全限制（只有一个）"之间的中间路线。

### 可持续性（Sustainability）的启示

如果把一个长期运行的 Web 应用看作一个小型的"生态系统"，那么对象管理模式就是这个生态系统的**可持续发展策略**：

- **不加管理的 new/delete** 就像一次性塑料文化——用完即扔，短期方便但长期污染严重（内存泄漏、GC 压力）
- **单例模式**就像公共基础设施——一座城市只需要一个供电网、一个供水系统，重复建设纯属浪费
- **对象池模式**就像共享经济——汽车共享、单车共享、办公空间共享——提高资源利用率，减少不必要的生产和废弃

优秀的软件架构需要在**灵活性**和**效率**之间找到平衡点。既不能过度复用导致耦合僵化（一切皆单例），也不能放任自流导致资源耗尽（一切皆随手 new）。

> **最好的设计不是选择某一个极端，而是在理解每种模式的适用边界之后，在最恰当的地方使用最恰当的工具。** 单例不是万能药，对象池也不是银弹。但当你的场景恰好落在它们的射程范围内时，它们能以最小的复杂度解决最本质的资源管理问题。

## 总结：知识体系全景

### 单例模式实现方式速查

| 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **模块级闭包** | 简洁自然、ES Module 天然支持 | 构造函数仍可被外部调用 | 大多数前端项目首选 |
| **IIFE 封装** | 完全隐藏类定义、API 干净 | 代码结构稍复杂 | 库/工具包的内部实现 |
| **Proxy 拦截** | 透明单例（`new` 即可获取）| 兼容性要求 ES6+ | 需要 `new` 语法的场景 |
| **静态块 + #私有字段** | 现代、类型安全、防御完善 | ES2022+ | 新项目、TypeScript 项目 |
| **装饰器** | 声明式、零侵入 | 需要装饰器支持 | TypeScript/框架开发 |

### 对象池核心要素

| 要素 | 说明 | 最佳实践 |
|------|------|---------|
| **factory（工厂）** | 创建新对象的函数 | 保持轻量，只做必要初始化 |
| **resetter（重置器）** | 归还时清理对象状态 | 确保"干净"的归还，避免状态泄漏 |
| **initialSize（初始大小）** | 预热数量 | 根据预期负载设置，避免冷启动抖动 |
| **maxSize（最大容量）** | 上限限制 | 必须设置！否则池失去意义 |
| **use() 方法** | 借用-自动归还 | 强烈推荐！配合 `try/finally` 使用 |

### 决策指南

```
需要管理对象的创建吗？
│
├─→ 这个东西应该只有一份吗？（全局配置、状态管理、日志）
│   └─→ **单例模式**
│       选择实现方式：模块闭包（首选）/ IIFE / Proxy / 静态块 / 装饰器
│
├─→ 这个东西需要很多份，但创建很昂贵吗？（DOM 元素、连接、粒子）
│   └─→ **对象池模式**
│       设计要点：factory / resetter / maxSize / use() 借还模式
│
├─→ 两者都需要吗？（粒子系统 = 单例的池化管理器）
│   └─→ **组合使用**：单例包装对象池
│
└─→ 都不需要？那就放心地 new 吧！
    不要过早优化——YAGNI 原则（You Aren't Gonna Need It）
```

> **单例模式和对象池模式表面上解决的是两个不同的问题——前者管"份量"，后者管"频次"。但深层次上，它们共同回应了软件工程中最持久的一个命题：如何在有限的资源条件下，构建出既能满足功能需求又能长期稳定运行的系统。** 理解这两种模式，就是理解"节制""复用""共享"这些基本价值观如何在代码层面得到体现。
