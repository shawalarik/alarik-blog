# 使用 `Proxy` 实现数据绑定（类似 Vue 响应式原理）

> **核心内容**：`Proxy` 的完整 API 与 13 种陷阱（Trap）详解、`Object.defineProperty` 与 `Proxy` 在数据劫持上的本质区别、从零实现一个 Vue 3 风格的响应式系统（依赖收集 + 触发更新）、Proxy 在数据验证、懒加载、日志、不可变代理中的高级应用、以及元编程（Metaprogramming）对 JavaScript 编程范式的影响和哲学思考。

## 一个问题：如何让数据的变化"自动"触发 UI 更新？

让我们从所有前端框架最核心的问题开始：

```javascript
// 最原始的做法 —— 手动同步
let userName = '张三';
const nameSpan = document.querySelector('#name');

function updateName() {
  nameSpan.textContent = userName;
}

updateName();  // 初始化

// 某个地方修改了名字
userName = '李四';

// 💥 问题：nameSpan 不会自动更新！你需要手动再调一次 updateName()
// 如果你忘了调 → UI 和数据不一致 → Bug
```

这个简单场景暴露了前端开发中最根本的矛盾之一：**数据（JavaScript 对象）和视图（DOM）是两个独立的存在，它们之间没有天然的同步机制。** 当数据发生变化时，视图不会自动知道；当用户在界面上操作时，数据也不会自动更新。

你可能会想：这有什么难的？每次改数据的时候顺便更新一下 DOM 不就行了吗？

```javascript
function setUserName(newName) {
  userName = newName;
  nameSpan.textContent = newName;     // 手动更新 DOM
  titleBar.textContent = newName;    // 手动更新另一处 DOM
  saveToLocalStorage(userName);      // 手动持久化
  notifyFriendList(userName);        // 手动通知其他模块
}
```

这种做法在小项目中勉强能用，但随着应用规模增长，它的缺陷会越来越明显：

1. **遗忘风险**：每新增一处需要同步的地方，你就得记得在这个函数里加一行代码。忘记一次就是一个 Bug。
2. **耦合爆炸**：`setUserName` 函数需要"知道"所有关心 `userName` 变化的地方——它变成了一个上帝函数。
3. **不可维护**：当有几十个状态、几百处 UI 组件时，手动同步的代码将变成一团乱麻。

我们真正想要的是这样的体验：

```javascript
const state = reactive({
  name: '张三',
  age: 25
});

// 只需要声明："当 name 被使用时，记住谁用了它"
// 然后当 name 改变时，"自动"通知所有用过它的人重新执行

state.name = '李四';  // ← 所有依赖 name 的地方自动更新！不需要手动调用任何东西
```

这就是**数据绑定（Data Binding）**的承诺——建立数据和视图之间的自动同步关系。而实现这一承诺的核心技术，就是 JavaScript 的 **`Proxy`**。

## 第一部分：理解 Proxy 的本质

### 什么是 Proxy？

`Proxy` 是 ES2015（ES6）引入的一个元编程（Metaprogramming）API。它允许你**拦截并自定义对象的基本操作**——如属性读取、属性赋值、属性删除、函数调用、`in` 操作符等。

如果说普通对象是一间房子，那么 **Proxy 就是在房子门口安装的一套智能门禁系统**。任何人要进入房子（读取属性）、往里面搬东西（写入属性）、或者拆除房间（删除属性），都必须经过门禁系统的检查。门禁系统可以决定：放行、拒绝、记录日志、修改行为、甚至完全替换操作的结果。

```javascript
const target = {          // 原始对象（被代理的目标）
  name: '张三',
  age: 25
};

const handler = {          // 处理器对象（定义拦截规则）
  get(target, key) {
    console.log(`📖 读取属性: ${key}`);
    return target[key];    // 允许读取，返回实际值
  },
  
  set(target, key, value) {
    console.log(`✏️ 设置属性: ${key} = ${value}`);
    target[key] = value;   // 允许设置
    return true;            // 表示设置成功
  }
};

const proxy = new Proxy(target, handler);  // 创建代理对象

// 现在通过 proxy 来访问 target
proxy.name;           // 📖 读取属性: name → "张三"
proxy.age = 26;       // ✏️ 设置属性: age = 26

console.log(target.age);   // 26 ✅ 原对象也被修改了（因为 handler 里写了 target[key] = value）
console.log(proxy.name);   // "张三"
```

### 为什么叫 "Proxy"？

"Proxy" 这个词源自拉丁语 *proxymitas*，意为"代表他人行事的人"——也就是**代理人/替身**。在我们的语境中：

- **target（目标对象）**是被代表的"本体"
- **proxy（代理对象）**是站在前面的"代理人"
- **handler（处理器）**定义了代理人的"行为准则"——什么该放行、什么该拦截、遇到特殊情况怎么处理

外部代码只与 `proxy` 打交道，不知道（也不需要知道）`target` 的存在。所有的操作请求都先经过 `handler` 的审核，由它决定是原样转发给 `target`、还是做些别的事情。

### Proxy vs Object.defineProperty 的根本区别

在深入 Proxy 的 API 之前，我们需要先厘清它与 `Object.defineProperty`（Vue 2.x 使用的响应式方案）的根本差异。关于 `defineProperty` 的详细内容参见《[defineProperty 与枚举属性详解](/frontend/javascript/language-async/defineProperty-enumerable-properties)》。

```javascript
// ====== Object.defineProperty 方式（Vue 2 风格）======

function defineReactive(obj, key, val) {
  // 必须预先知道要监听哪些属性！
  Object.defineProperty(obj, key, {
    get() {
      console.log(`📖 读取 ${key}`);
      return val;
    },
    set(newVal) {
      console.log(`✏️ 设置 ${key} = ${newVal}`);
      val = newVal;
      // 这里可以触发通知...
    }
  });
  
  return obj;
}

const obj1 = {};
defineReactive(obj1, 'name', '张三');
defineReactive(obj1, 'age', 25);

obj1.name;         // 📖 读取 name ✅
obj1.name = '李四'; // ✏️ 设置 name ✅

obj1.gender = '男';  // 💥 新增属性不会被拦截！defineProperty 无能为力
delete obj1.age;    // 💥 删除属性也不会被拦截！

// ====== Proxy 方式（Vue 3 风格）======

const handler = {
  get(target, key) {
    console.log(`📖 读取 ${key}`);
    return target[key];
  },
  set(target, key, value) {
    console.log(`✏️ 设置 ${key} = ${value}`);
    target[key] = value;
    return true;
  },
  deleteProperty(target, key) {
    console.log(`🗑️ 删除 ${key}`);
    delete target[key];
    return true;
  }
};

const obj2 = new Proxy({}, handler);
obj2.name = '张三';   // ✏️ 设置 name ✅ 动态属性也能拦截！
obj2.name;           // 📖 读取 name ✅
obj2.gender = '男';   // ✏️ 设置 gender ✅ 新增属性也能拦截！
delete obj2.name;    // 🗑️ 删除 name ✅ 删除也能拦截！
```

核心差异总结：

| 能力 | `Object.defineProperty` | `Proxy` |
|------|----------------------|--------|
| **拦截已有属性的读写** | ✅ | ✅ |
| **拦截动态新增的属性** | ❌ | ✅ |
| **拦截属性的删除** | ❌ | ✅ |
| **拦截 `in` 操作符** | ❌ | ✅ |
| **拦截属性的枚举（for...in）** | 部分 | ✅ |
| **拦截函数调用** | ❌ | ✅（apply trap）|
| **是否需要预知属性名** | **是**（必须遍历每个属性逐一 define）| **否**（统一拦截所有操作）|
| **性能开销** | 低（直接属性访问）| 中等（需经过代理层间接访问）|

**Proxy 最大的优势在于"全能性"**——它不关心对象的属性有哪些、什么时候添加、什么时候删除。它像一个全方位的门禁系统，守卫着对象的所有入口和出口。而 `defineProperty` 更像是给每个房间单独装锁——你得提前知道有多少个房间、分别叫什么名字。

### 通俗类比：门卫 vs 房间门锁

如果把对象比作一栋建筑：
- **`Object.defineProperty`** 就像给**每个房间单独装一把锁和监控器**。你必须提前知道建筑里有多少个房间，逐个安装。如果后来新建了一个房间（动态添加属性），它默认是没有锁的——除非你再跑一遍安装流程。而且有人从窗户翻进来（用 `delete`），你也管不了。
- **`Proxy`** 就像在大楼**唯一的出入口装了一套智能门禁系统**。不管楼里有几个房间、什么时候新建房间、什么时候拆掉房间，所有人进出都必须经过这道门禁。门禁系统统一记录、检查、控制一切出入行为。

显然，对于"房间数量会变化"的场景（即动态属性的对象），出入口门禁比逐房间上锁更加健壮可靠。

## 第二部分：Proxy 完整 API —— 13 种陷阱（Trap）

ES 规范为 Proxy 定义了 **13 种陷阱（Trap）**，对应着可以被拦截的 13 种基本操作：

### 一、属性读写相关（4 个）

#### 1. get(target, propertyKey, receiver)

拦截属性**读取**操作。这是数据绑定中最核心的陷阱——Vue 的依赖收集就发生在这里。

```javascript
const handler = {
  get(target, key, receiver) {
    // target: 被代理的原对象
    // key: 被读取的属性名（字符串或 Symbol）
    // receiver: 最初被调用的代理对象（或继承链中的对象）
    
    console.log(`[GET] 正在读取 "${key}"`);
    const value = target[key];
    
    // 可以在这里做一些额外的事情……
    if (typeof value === 'object' && value !== null) {
      // 可选：对嵌套对象也返回代理（深层代理）
      // return new Proxy(value, nestedHandler);
    }
    
    return value;
  }
};

const proxy = new Proxy({ x: 1, y: 2 }, handler);

proxy.x;       // [GET] 正在读取 "x" → 1
proxy.y;       // [GET] 正在读取 "y" → 2
proxy.z;       // [GET] 正在读取 "z" → undefined
```

**`receiver` 参数的意义**：当代理对象被继承时，`receiver` 可能不是代理自身而是子类实例。这在涉及 `this` 绑定时非常重要（后面会详细讨论）。

#### 2. set(target, propertyKey, value, receiver)

拦截属性**写入**操作。这是触发更新的关键点——Vue 的状态变更通知从这里开始。

```javascript
const handler = {
  set(target, key, value, receiver) {
    // value: 要设置的新值
    // 返回 boolean: true 表示设置成功，false（严格模式下）抛出 TypeError
    
    console.log(`[SET] "${key}" ← ${JSON.stringify(value)}`);
    
    // 可以在这里做校验
    if (key === 'age' && (typeof value !== 'number' || value < 0 || value > 150)) {
      console.warn(`⚠️ 无效的年龄值: ${value}`);
      return false;  // 拒绝设置
    }
    
    target[key] = value;
    
    // 可以在这里触发通知……
    // notifySubscribers(key, value);
    
    return true;
  }
};

const user = new Proxy({ name: '张三', age: 25 }, handler);

user.name = '李四';   // [SET] "name" ← "李四" ✅
user.age = -5;       // [SET] "age" ← -5 ⚠️ 无效的年龄值 + 拒绝设置
console.log(user.age); // 25 （保持原值）
```

#### 3. has(target, propertyKey)

拦截 `in` 操作符和 `Reflect.has()`。

```javascript
const handler = {
  has(target, key) {
    console.log(`[HAS] 检查 "${key}" 是否存在`);
    
    // 可以隐藏某些属性
    if (key.startsWith('_')) {
      return false;  // 以 _ 开头的属性对外"不存在"
    }
    
    return key in target;
  }
};

const proxy = new Proxy(
  { publicData: '可见', _secret: '机密' },
  handler
);

console.log('publicData' in proxy);  // [HAS] 检查 "publicData" 是否存在 → true
console.log('_secret' in proxy);     // [HAS] 检查 "_secret" 是否存在 → false 🔐
```

#### 4. deleteProperty(target, propertyKey)

拦截 `delete` 操作符。

```javascript
const handler = {
  deleteProperty(target, key) {
    console.log(`[DELETE] 尝试删除 "${key}"`);
    
    // 保护某些属性不被删除
    if (['id', 'createdAt'].includes(key)) {
      console.warn(`⛔ 属性 "${key}" 受保护，无法删除`);
      return false;
    }
    
    delete target[key];
    return true;
  }
};

const record = new Proxy({
  id: 'rec_001',
  name: '测试记录',
  createdAt: Date.now()
}, handler);

delete record.name;       // [DELETE] 尝试删除 "name" → 成功 ✅
delete record.id;         // [DELETE] 尝试删除 "id" → ⛔ 受保护，无法删除
```

### 二、函数调用相关（2 个）

#### 5. apply(target, thisArg, argumentsList)

拦截**函数作为函数调用**时的行为（即 `proxy(...args)`）。

```javascript
function greet(greeting) {
  return `${greeting}, ${this.name}!`;
}

const handler = {
  apply(target, thisArg, args) {
    // target: 被代理的函数
    // thisArg: 函数调用时的 this 上下文
    // args: 传入的参数数组
    
    console.log(`[APPLY] 函数被调用，参数: [${args.join(', ')}]`);
    
    // 可以修改参数、记录日志、限流等
    const startTime = performance.now();
    const result = target.apply(thisArg, args);
    const duration = performance.now() - startTime;
    console.log(`[APPLY] 执行耗时: ${duration.toFixed(2)}ms`);
    
    return result;
  }
};

const proxiedGreet = new Proxy(greet, handler);
const context = { name: '世界' };

proxiedGreet.call(context, '你好');
// [APPLY] 函数被调用，参数: [你好]
// 你好, 世界!
// [APPLY] 执行耗时: 0.xxms
```

#### 6. construct(target, argumentsList, newTarget)

拦截**使用 `new` 调用构造函数**时的行为。

```javascript
class User {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }
}

const handler = {
  construct(target, args, newTarget) {
    // target: 被代理的构造函数
    // args: 传给 new 的参数数组
    // newTarget: 最初被 new 的构造函数（用于正确的 prototype 链接）
    
    console.log(`[CONSTRUCT] 创建新实例，参数: [${args.join(', ')}]`);
    
    // 可以在构造前后注入逻辑
    const instance = Reflect.construct(target, args, newTarget);
    instance.createdAt = Date.now();
    
    return instance;
  }
};

const ProxiedUser = new Proxy(User, handler);
const user = new ProxiedUser('张三', 25);

console.log(user instanceof User);  // true ✅
console.log(user.createdAt);        // 时间戳（构造时注入的）
```

### 三、对象描述与枚举相关（3 个）

#### 7. ownKeys(target)

拦截 `Object.keys()`、`for...in`、`Object.getOwnPropertyNames()` 等获取自有键名的操作。

```javascript
const handler = {
  ownKeys(target) {
    console.log('[OWNKEYS] 获取所有键名');
    
    // 过滤掉以 _ 开头的私有属性
    return Reflect.ownKeys(target).filter(key => !key.startsWith('_'));
  }
};

const obj = new Proxy(
  { name: '公开', _internal: '隐藏', count: 42 },
  handler
);

console.log(Object.keys(obj));     // [OWNKEYS] → ["name", "count"] （_internal 被过滤了）
for (let key in obj) { console.log(key); }  // name, count
```

#### 8. getOwnPropertyDescriptor(target, propertyKey)

拦截 `Object.getOwnPropertyDescriptor()`。

```javascript
const handler = {
  getOwnPropertyDescriptor(target, key) {
    const desc = Object.getOwnPropertyDescriptor(target, key);
    
    // 可以修改返回的描述符
    if (desc && !key.startsWith('_')) {
      desc.enumerable = false;  // 对外都变成不可枚举
    }
    
    return desc;
  }
};
```

#### 9. defineProperty(target, propertyKey, descriptor)

拦截 `Object.defineProperty()` 和 `Object.defineProperties()`。

```javascript
const handler = {
  defineProperty(target, key, descriptor) {
    console.log(`[DEFINE] 定义属性 "${key}"`);
    
    // 可以强制覆盖描述符
    if (descriptor.value !== undefined) {
      descriptor.writable = true;
      descriptor.configurable = true;
      descriptor.enumerable = true;
    }
    
    return Object.defineProperty(target, key, descriptor);
  }
};
```

### 四、原型与扩展性相关（4 个）

#### 10. getPrototypeOf(target)

拦截 `Object.getPrototypeOf()`。

#### 11. setPrototypeOf(target, prototype)

拦截 `Object.setPrototypeOf()`。

#### 12. isExtensible(target)

拦截 `Object.isExtensible()`。

#### 13. preventExtensions(target)

拦截 `Object.preventExtensions()`。

这些原型相关的陷阱在日常开发中使用频率较低，但在构建框架级工具时非常有价值——它们允许你对对象的原型链和可扩展性进行精细控制。

### 陷阱速查表

| 陷阱方法 | 拦截的操作 | 默认行为（Reflect）|
|----------|-----------|------------------|
| `get` | 读取属性 | `target[key]` |
| `set` | 写入属性 | `target[key] = value` |
| `has` | `in` 操作符 | `key in target` |
| `deleteProperty` | `delete` 操作 | `delete target[key]` |
| `apply` | 函数调用 `f(...args)` | `target.apply(thisArg, args)` |
| `construct` | `new f(...args)` | `new target(...args)` |
| `ownKeys` | `keys()/for...in` 等 | `Reflect.ownKeys(target)` |
| `getOwnPropertyDescriptor` | 获取属性描述符 | `Object.getOwnPropertyDescriptor(target, key)` |
| `defineProperty` | 定义属性 | `Object.defineProperty(target, key, desc)` |
| `getPrototypeOf` | 获取原型 | `Object.getPrototypeOf(target)` |
| `setPrototypeOf` | 设置原型 | `Object.setPrototypeOf(target, proto)` |
| `isExtensible` | 检查可扩展性 | `Object.isExtensible(target)` |
| `preventExtensions` | 阻止扩展 | `Object.preventExtensions(target)` |

> **重要提示**：在实际编写 handler 时，推荐使用 `Reflect` 对象来调用对应的默认行为（如 `Reflect.get(target, key, receiver)`）。`Reflect` 的方法签名与 Proxy 的陷阱一一对应，它能确保操作的语义与原生行为一致，同时避免一些边界情况的坑。

## 第三部分：从零实现 Vue 3 风格的响应式系统

现在我们已经掌握了 Proxy 的全部武器。接下来让我们用它来构建真正的数据绑定系统——类似于 Vue 3 的 `reactive()` / `effect()` 核心。

### 核心原理概述

Vue 3 的响应式系统基于三个核心概念的协作：

```
┌───────────────────────────────────────────────┐
│                  响应式循环                     │
│                                               │
│  ┌──────────┐    收集依赖      ┌───────────┐ │
│  │ effect()  │ ─────────────→ │   reactive │ │
│  │ (观察者)  │    "我在用谁？"   │  (被观察者) │ │
│  └──────────┘                └─────┬─────┘ │
│        ▲                           │        │
│        │                    数据变更       │
│        │  触发重执行               │        │
│        │ ◄──────────────────────────┘        │
│        │                                      │
│  "我依赖的数据变了！"→ 重新执行 effect       │
└───────────────────────────────────────────────┘
```

这个过程分为两个阶段：

**阶段一：依赖收集（Dependency Tracking）**
- 当 `effect()` 函数执行时，如果内部读取了某个 reactive 对象的属性
- 该属性的 `get` 陷阱会被触发
- 在 `get` 中，把当前正在执行的 `effect` 记录为这个属性的"依赖者"
- 这样我们就知道了："这个 effect 用到了哪些属性"

**阶段二：触发更新（Trigger Update）**
- 当 reactive 对象的属性值被修改时
- 该属性的 `set` 陷阱会被触发
- 在 `set` 中，找到所有"依赖于此属性"的 effect
- 重新执行这些 effect → UI 自动更新

### 第一步：实现 reactive()

```javascript
/**
 * 将普通对象转换为响应式代理
 * @param {*} target - 要转换的对象
 * @returns {Proxy} 响应式代理对象
 */
function reactive(target) {
  if (typeof target !== 'object' || target === null) {
    console.warn('reactive() 只能接收对象类型');
    return target;
  }

  const handler = {
    get(target, key, receiver) {
      // 1. 读取原始值
      const value = Reflect.get(target, key, receiver);
      
      // 2. 如果当前有活跃的 effect，建立依赖关系
      if (activeEffect) {
        track(target, key, activeEffect);
      }
      
      // 3. 如果值是对象，递归地将其也变为响应式（深度响应式）
      if (value !== null && typeof value === 'object') {
        return reactive(value);
      }
      
      return value;
    },

    set(target, key, value, receiver) {
      // 1. 先检查值是否真的变了（避免无意义的重复触发）
      const oldValue = target[key];
      
      // NaN !== NaN 的特殊处理
      const hasChanged = oldValue !== value && 
                          !(Number.isNaN(oldValue) && Number.isNaN(value));
      
      if (!hasChanged) {
        return true;  // 值没变，但仍然返回 true 表示"设置成功"
      }
      
      // 2. 设置新值
      const result = Reflect.set(target, key, value, receiver);
      
      // 3. 触发所有依赖此属性 effect 的重新执行
      trigger(target, key);
      
      return result;
    }
  };
  
  return new Proxy(target, handler);
}
```

### 第二步：实现依赖管理（track / trigger）

```javascript
// 存储依赖关系的全局 WeakMap
// 结构：WeakMap<target, Map<key, Set<effect>>>
// 
// 解释：
// - 外层 WeakMap: 以目标对象为键 → 保证对象被 GC 后依赖关系也被清理
// - 中层 Map: 以属性名为键 → 同一对象不同属性各自维护依赖列表
// - 内层 Set: 存储所有依赖于此属性的 effect 函数
const targetMap = new WeakMap();

/**
 * 收集依赖：记录 "某个 effect 使用了 target 的 key 属性"
 */
function track(target, key, effect) {
  // 从 targetMap 中获取该对象的依赖映射表
  let depsMap = targetMap.get(target);
  if (!depsMap) {
    depsMap = new Map();
    targetMap.set(target, depsMap);
  }
  
  // 获取该属性的依赖集合
  let deps = depsMap.get(key);
  if (!deps) {
    deps = new Set();
    depsMap.set(key, deps);
  }
  
  // 将 effect 注册为该属性的依赖
  // Set 自动去重——同一个 effect 对同一个属性只会注册一次
  if (!deps.has(effect)) {
    deps.add(effect);
    
    // 开发模式下的调试信息
    if (__DEV__) {
      console.log(`📡 [Track] effect 注册依赖: target.${key}`);
    }
  }
}

/**
 * 触发更新：让所有依赖于 target.key 的 effect 重新执行
 */
function trigger(target, key) {
  const depsMap = targetMap.get(target);
  if (!depsMap) return;
  
  const effects = depsMap.get(key);
  if (!effects || effects.size === 0) return;
  
  if (__DEV__) {
    console.log(`⚡ [Trigger] 触发更新: target.${key}, 影响 ${effects.size} 个 effect`);
  }
  
  // 依次执行所有 effect
  // 注意：这里做了简化版调度，Vue 3 有更复杂的批处理和调度逻辑
  effects.forEach(effect => {
    effect();  // 重新执行 effect → 如果 effect 内部再次读取了该属性，又会重新注册依赖
  });
}
```

### 第三步：实现 effect()

```javascript
// 当前正在执行的 effect（全局变量，供 track() 读取）
let activeEffect = null;

/**
 * 响应式副作用函数
 * @param {Function} fn - 要执行的副作用函数
 * @returns {Function} 停止此 effect 的函数
 */
function effect(fn) {
  const wrapperEffect = () => {
    // 1. 将自己标记为"当前活跃的 effect"
    activeEffect = wrapperEffect;
    
    try {
      // 2. 执行用户传入的函数
      //    在执行过程中，如果读取了 reactive 对象的属性，
      //    那些属性的 get 会被触发 → track() 会把 activeEffect 记录下来
      fn();
    } finally {
      // 3. 无论成功还是失败，都要清除 activeEffect 标记
      activeEffect = null;
    }
  };
  
  // 立即执行一次（首次运行，用于收集初始依赖）
  wrapperEffect();
  
  // 返回停止函数
  return () => {
    // 从所有依赖集合中移除此 effect
    cleanupEffect(wrapperEffect);
  };
}

/**
 * 清理 effect 的所有依赖记录
 */
function cleanupEffect(effect) {
  targetMap.forEach(depsMap => {
    depsMap.forEach(deps => {
      deps.delete(effect);
    });
  });
}
```

### 第四步：组合使用 —— 完整演示

```javascript
// ============================================================
// 现在，让我们用这三个函数来搭建一个微型响应式系统
// ============================================================

// 1. 创建响应式数据
const state = reactive({
  user: {
    name: '张三',
    age: 25,
    address: {
      city: '北京',
      district: '朝阳区'
    }
  },
  showGreeting: true
});

// 2. 创建副作用（模拟组件渲染）
const stopRendering = effect(() => {
  console.log('\n=== 🔄 重新渲染 ===');
  console.log(`姓名: ${state.user.name}`);
  console.log(`年龄: ${state.user.age}`);
  console.log(`城市: ${state.user.address.city}`);
  console.log(`显示问候语: ${state.showGreeting ? '是' : '否'}`);
  if (state.showGreeting) {
    console.log(`💬 你好，${state.user.name}！今年${state.user.age}岁。`);
  }
});

// 首次渲染（effect 首次执行时会自动收集依赖）
// 输出: 姓名: 张三, 年龄: 25, 城市: 北京 ...

// 3. 修改状态 → 自动触发重新渲染
console.log('\n--- 修改名字 ---');
state.user.name = '李四';
// ⚡ [Trigger] 触发更新: .name
// === 🔄 重新渲染 ===
// 姓名: 李四, 年龄: 25 ...  ✅ 自动更新了！

console.log('\n--- 修改年龄 ---');
state.user.age = 26;
// ⚡ [Trigger]
// === 🔄 重新渲染 ===
// 姓名: 李四, 年龄: 26 ...  ✅

console.log('\n--- 修改嵌套属性 ---');
state.user.address.city = '上海';
// ⚡ [Trigger]
// === 🔄 重新渲染 ===
// 城市: 上海 ...  ✅ 深层嵌套也能追踪到！（因为 get 中递归调用了 reactive）

console.log('\n--- 修改未使用的属性 ---');
state.user.address.zipCode = '100000';
// 没有任何输出！因为 zipCode 没有在任何 effect 中被读取过
// → 没有依赖 → 不触发任何 effect ✅ 这就是精准更新的力量

// 4. 停止响应
stopRendering();

state.user.name = '王五';
// 此时没有任何输出了 —— effect 已经停止订阅 ✅
```

这就是 Vue 3 `reactive()` / `effect()` 的**精简原型**。当然，真实的 Vue 3 还包含大量本文未涉及的优化：
- **调度器（Scheduler）**：将多个状态合并为一次批量更新
- **计算属性（computed）**：带缓存的派生 effect
- **watch/watchEffect**：带有旧值对比和选项配置的观察者
- **ref()**：对基本类型的响应式包装
- ** shallowReactive**：浅层响应式（不递归代理嵌套对象）
- **toRaw()**：获取原始非代理对象

但这些增强都是在本文展示的核心原理之上构建的——**依赖收集 + 触发更新**这一基本架构始终不变。

## 第四部分：Proxy 高级应用实战

### 应用一：不可变代理（Immutable Proxy）

利用 Proxy 可以创建一种"看起来能修改、实际上创建了新版本"的对象——这是函数式编程中**结构共享（Structural Sharing）**的一种实现方式：

```javascript
/**
 * 创建一个代理：每次 set 时不会修改原对象，
 * 而是将修改应用到克隆后的新对象上
 */
function immutable(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      const value = Reflect.get(target, key, receiver);
      
      // 对子对象也返回 immutable 版本
      if (value && typeof value === 'object') {
        return immutable(value);
      }
      
      return value;
    },
    
    set(target, key, value) {
      // 不是修改 target，而是创建一个新对象
      // （注意：这是一个简化的实现，生产环境请使用 Immer 等成熟库）
      const clone = { ...target, [key]: value };
      // 将代理转移到新对象上
      return immutable(clone);
    }
  });
}

// 使用
let data = immutable({
  name: '原始',
  version: 1,
  meta: { created: '2024-01-01' }
});

data.name = '修改后';
// 注意：data 本身现在指向了一个新的代理对象（克隆体）
console.log(data.name);       // "修改后"

// 但原始数据不受影响
// （实际上在这个简化实现中原引用已丢失，Immer 用 current/base 的概念解决了这个问题）
```

> 对于生产级的不可变数据处理，推荐使用 **Immer** 库——它在底层使用了类似的 Proxy 技术（配合 Copy-on-Write 策略），提供了完善的 `produce()` API。参见《[浅拷贝与深拷贝](/frontend/javascript/language-async/shallow-deep-copy-with-prototype)》了解更多。

### 应用二：数据验证层

Proxy 可以作为数据模型的"守门人"，在每次赋值时进行实时校验：

```javascript
/**
 * 创建带有校验规则的代理
 */
function validated(target, rules = {}) {
  return new Proxy(target, {
    set(target, key, value) {
      const rule = rules[key];
      
      if (rule) {
        // 类型检查
        if (rule.type && typeof value !== rule.type) {
          throw new TypeError(
            `[Validation] "${key}" 应为 ${rule.type} 类型，收到 ${typeof value}`
          );
        }
        
        // 自定义校验器
        if (rule.validator && !rule.validator(value)) {
          throw new RangeError(
            `[Validation] "${key}" 校验失败: ${rule.message || '无效值'}`
          );
        }
        
        // 转换器（在存储前转换值的格式）
        if (rule.transform) {
          value = rule.transform(value);
        }
        
        // 范围检查
        if (rule.min !== undefined && value < rule.min) {
          throw new RangeError(`[Validation] "${key}" 不能小于 ${rule.min}`);
        }
        if (rule.max !== undefined && value > rule.max) {
          throw new RangeError(`[Validation] "${key}" 不能大于 ${rule.max}`);
        }
      }
      
      return Reflect.set(target, key, value);
    }
  });
}

// 使用示例：用户注册表单模型
const formData = validated({}, {
  email: {
    type: 'string',
    validator: (v) => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v),
    message: '邮箱格式无效'
  },
  password: {
    type: 'string',
    validator: (v) => v.length >= 8,
    message: '密码至少8位'
  },
  age: {
    type: 'number',
    min: 0,
    max: 150,
    transform: Number  // 输入可能是字符串，转为数字
  }
});

formData.email = 'valid@email.com';   // ✅
formData.password = 'abc12345';     // ✅
formData.age = '25';                 // ✅ (被 transform 转为数字 25)

formData.email = 'invalid';         // 💥 TypeError: 邮箱格式无效
formData.password = '123';           // 💥 RangeError: 密码至少8位
formData.age = -5;                   // 💥 RangeError: 不能小于 0
```

这种模式的优雅之处在于：**验证逻辑被透明地嵌入到普通的赋值操作中**。使用者感觉自己在正常地 `obj.prop = value`，但实际上每一行赋值都在经过严格的安检。这与 Python 的 `@property` decorator 或 Rust 的 struct field validation 有异曲同工之妙。

### 应用三：性能日志与分析代理

在不修改原始代码的前提下，通过 Proxy 为任何对象添加完整的操作日志：

```javascript
/**
 * 创建一个带详细日志的代理
 * @param {*} target - 目标对象
 * @param {string} [label='Obj'] - 日志标签
 */
function withLogging(target, label = 'Obj') {
  // 统计信息
  const stats = {
    reads: 0,
    writes: 0,
    deletes: 0,
    readKeys: new Set(),
    writeKeys: new Set()
  };
  
  const handler = {
    get(target, key, receiver) {
      stats.reads++;
      stats.readKeys.add(key);
      return Reflect.get(target, key, receiver);
    },
    
    set(target, key, value, receiver) {
      stats.writes++;
      stats.writeKeys.add(key);
      
      const oldValue = target[key];
      const result = Reflect.set(target, key, value, receiver);
      
      console.log(
        `[LOG][${label}] SET .${key}:`, oldValue, '→', value
      );
      
      return result;
    },
    
    deleteProperty(target, key) {
      stats.deletes++;
      console.log(`[LOG][${label}] DELETE .${key}`);
      return Reflect.deleteProperty(target, key);
    }
  };
  
  const proxy = new Proxy(target, handler);
  
  // 暴露统计信息的只读属性
  Object.defineProperty(proxy, '__stats__', {
    get() {
      return {
        ...stats,
        readKeys: [...stats.readKeys],
        writeKeys: [...stats.writeKeys],
        uniqueReads: stats.readKeys.size,
        uniqueWrites: stats.writeKeys.size
      };
    },
    enumerable: false,
    configurable: false
  });
  
  return proxy;
}

// 使用：给任意对象加上日志
const apiClient = withLogging({
  baseUrl: 'https://api.example.com',
  timeout: 5000,
  retries: 3,
  headers: {}
}, 'APIClient');

apiClient.timeout = 3000;   // [LOG][APIClient] SET .timeout: 5000 → 3000
apiClient.baseUrl;          // 读取（静默）
apiClient.retries = 10;     // [LOG][APIClient] SET .retries: 3 → 10
delete apiClient.headers;    // [LOG][APIClient] DELETE .headers

// 查看统计
console.log(apiClient.__stats__);
// {
//   reads: 1, writes: 2, deletes: 1,
//   readKeys: ['baseUrl'],
//   writeKeys: ['timeout', 'retries'],
//   uniqueReads: 1, uniqueWrites: 2
// }
```

这种技术在以下场景极其有用：
- **性能分析**：找出哪些属性被频繁读取/写入（热点分析）
- **调试**：追踪状态的变更历史
- **审计**：记录敏感数据的访问日志
- **开发工具**：在不侵入业务代码的情况下了解数据流向

### 应用四：懒加载代理（Lazy Loading Proxy）

Proxy 可以实现"按需加载"——只有当你真正访问某个属性时，才去执行昂贵的加载操作：

```javascript
/**
 * 创建懒加载代理
 * 只有在被访问时才执行 loader 加载数据
 * @param {*} target - 占位对象（定义属性名和 loader）
 * @returns {Proxy} 代理对象
 */
function lazyLoad(target) {
  const loaded = new Map();   // 已加载的缓存
  const loading = new Map();  // 正在加载的 Promise
  
  return new Proxy(target, {
    async get(target, key, receiver) {
      // 如果已经加载过了，直接返回缓存
      if (loaded.has(key)) {
        return loaded.get(key);
      }
      
      // 如果正在加载中（并发访问），复用同一个 Promise
      if (loading.has(key)) {
        return loading.get(key);
      }
      
      // 检查是否有对应的 loader 函数
      const loaderName = `_load_${key}`;
      if (typeof target[loaderName] !== 'function') {
        return Reflect.get(target, key, receiver);  // 没有 loader 则走默认行为
      }
      
      console.log(`⏳ [Lazy] 开始加载属性 "${key}"...`);
      
      // 创建并缓存 Promise（防止并发重复加载）
      const promise = target[loaderName]()
        .then(result => {
          loaded.set(key, result);
          loading.delete(key);
          console.log(`✅ [Lazy] 属性 "${key}" 加载完成`);
          return result;
        })
        .catch(err => {
          loading.delete(key);
          console.error(`❌ [Lazy] 属性 "${key}" 加载失败:`, err.message);
          throw err;
        });
      
      loading.set(key, promise);
      return promise;  // 返回 Promise，调用方可以用 await
    }
  });
}

// 使用
const heavyResource = lazyLoad({
  // 这些属性会被懒加载
  _load_userProfile() {
    return fetch('/api/user/profile').then(r => r.json());
    // 模拟耗时操作
    return new Promise(resolve => {
      setTimeout(() => resolve({ name: '张三', avatar: '/avatar.jpg', level: 15 }), 2000);
    });
  },
  
  _load_friendsList() {
    return new Promise(resolve => {
      setTimeout(() => resolve([
        { id: 1, name: '好友A' },
        { id: 2, name: '好友B' }
      ]), 1500);
    });
  },
  
  _load_achievements() {
    return new Promise(resolve => {
      setTimeout(() => resolve([
        { id: 'ach_1', name: '初次登录' },
        { id: 'ach_2', name: '社交达人' }
      ]), 3000);
    });
  },
  
  // 这个属性没有 loader，不会被懒加载
  timestamp: Date.now()
});

// 异步消费懒加载属性
(async () => {
  const profile = await heavyResource.userProfile;   // ⏳ 首次加载（2秒）
  console.log(profile);                               // ✅ { name: '张三', ... }
  
  const profile2 = await heavyResource.userProfile;  // 直接返回缓存（0ms）
  console.log(profile === profile2);                   // true ✅
})();
```

这种模式特别适合：
- 大型 JSON 配置文件的按字段加载
- 图片/视频资源的延迟加载
- 数据库查询结果的分页/按需获取
- GraphQL 字段级别的解析

### 应用五：多层数据管道（Pipeline Proxy）

通过嵌套多个 Proxy，可以为同一对象叠加多层不同的能力：

```javascript
/**
 * 组合多个 Proxy handler
 * @param {Object} target - 目标对象
 * @param {...Function} handlers - 多个 handler 工厂函数
 * @returns {Proxy} 经过所有 handler 包装的代理
 */
function pipeline(target, ...handlers) {
  let current = target;
  
  for (const createHandler of handlers) {
    const handler = createHandler(current);
    current = new Proxy(current, handler);
  }
  
  return current;
}

// Handler 工厂函数们
const loggingHandler = (target) => ({
  get(t, k, r) { console.log(`[LOG-GET] ${k}`); return Reflect.get(t, k, r); },
  set(t, k, v, r) { console.log(`[LOG-SET] ${k}=${v}`); return Reflect.set(t, k, v, r); }
});

const validatingHandler = (target) => ({
  set(t, k, v, r) {
    if (k.startsWith('_')) throw new Error(`不能修改私有属性: ${k}`);
    return Reflect.set(t, k, v, r);
  }
});

const auditingHandler = (target) => {
  const history = [];
  return {
    get(t, k, r) { return Reflect.get(t, k, r); },
    set(t, k, v, r) {
      history.push({ time: Date.now(), key: k, oldValue: t[k], newValue: v });
      t.__auditHistory__ = history;  // 直接挂在 target 上（仅供演示）
      return Reflect.set(t, k, v, r);
    }
  };
};

// 组合使用
const enhanced = pipeline(
  { name: '测试', _secret: 'xxx', score: 95 },
  loggingHandler,       // 第1层：日志
  validatingHandler,    // 第2层：校验
  auditingHandler      // 第3层：审计
);

enhanced.score = 100;
// [LOG-SET] score=100  ← 第1层（日志）
// 审计记录已生成       ← 第3层（审计）

enhanced._secret = 'hacked';
// [LOG-SET] _secret=hacked
// Error: 不能修改私有属性: _secret  ← 第2层（校验）阻止了！

console.log(enhanced.__auditHistory__);
// [{ time: ..., key: 'score', oldValue: 95, newValue: 100 }]
```

这种**管道式（Pipeline）**的 Proxy 组合让你能够像搭积木一样自由地叠加各种能力——日志、校验、审计、权限控制、缓存、节流……每种关注点都是一个独立的 handler，互不影响，可以随意插拔。

## 第五部分：Proxy 的局限性与替代方案

### Proxy 无法做到的事情

尽管 Proxy 功能强大，但它并非万能。以下是一些重要的限制：

#### 1. 无法拦截 `===` 比较

```javascript
const proxy = new Proxy({}, {});
const plain = {};

console.log(proxy === proxy);  // true（同一个代理）
console.log(proxy === plain);    // false（永远不可能相等）
console.log(typeof proxy);      // "object"（不是 "proxy" 这种特殊类型）
```

Proxy 对象在 `===` 比较中被视为普通对象——它无法伪装成另一个已有的对象。如果你需要让 `a === b` 返回 `true` 而 a、b 实际上是不同的对象，Proxy 做不到这一点。（`Object.is()` 也一样）

#### 2. 无法改变 `typeof` 或 `instanceof` 的结果

```javascript
const proxy = new Proxy([], {});
console.log(typeof proxy);           // "object"（不是 "array"！）
console.log(Array.isArray(proxy));     // true ✅ （Array.isArray 通过内部 [[IsArray]] 槽检测）
console.log(proxy instanceof Array);   // true ✅
console.log(proxy instanceof Number);  // false
```

`instanceof` 和大多数内置操作可以通过 `getPrototypeOf` trap 间接影响，但 `typeof` 是硬编码的行为，无法被拦截。

#### 3. 性能开销

Proxy 引入了一层间接寻址，在某些极端性能敏感的场景中可能成为瓶颈：

```javascript
// 基准测试：普通对象 vs Proxy 对象的属性访问速度
const N = 10000000;

// 普通
const plain = { x: 1, y: 2, z: 3 };
const startPlain = performance.now();
for (let i = 0; i < N; i++) {
  plain.x; plain.y; plain.z;
}
console.log(`Plain: ${(performance.now() - startPlain).toFixed(2)}ms`);

// Proxy
const proxied = new Proxy({ x: 1, y: 2, z: 3 }, {});
const startProxy = performance.now();
for (let i = 0; i < N; i++) {
  proxied.x; proxied.y; proxied.z;
}
console.log(`Proxy: ${(performance.now() - startProxy).toFixed(2)}ms`);

// 典型结果：Proxy 比 plain 慢 3~10 倍（取决于引擎和场景）
// 但绝对值通常仍在微秒级别（百万次操作差几毫秒）
// 对于绝大多数应用来说，这不是瓶颈
```

**何时需要担心 Proxy 的性能？**
- 游戏引擎的主循环（每帧调用数十万次）
- 高频交易算法的核心路径
- 大数据集的遍历操作
- 对于普通的 Web 应用 UI 更新（通常每秒几十到几百次属性访问），Proxy 的开销完全可以忽略

#### 4. `this` 绑定问题

这是 Proxy 最容易出 Bug 的地方之一：

```javascript
const handler = {
  get(target, key) {
    const value = target[key];
    
    // 如果值是函数，绑定 this 到 proxy（而不是 target）
    if (typeof value === 'function') {
      return value.bind(proxyInstance);  // ⚠️ 但这里引用了 proxyInstance！
    }
    
    return value;
  }
};

const target = {
  name: '原始',
  getName() { return this.name; }  // 这里的 this 应该指向谁？
};

const proxyInstance = new Proxy(target, handler);

console.log(target.getName());    // "原始" ✅ this === target
console.log(proxyInstance.getName()); // 取决于 handler 实现
// 如果没有 bind this → 可能返回 "原始" 或 undefined（取决于实现细节）
```

Vue 3 通过巧妙地传递 `receiver` 参数解决了这个问题——在 `get` trap 中使用 `Reflect.get(target, key, receiver)` 而非 `target[key]`，确保 `this` 始终指向最初的调用者（通常是代理对象本身）。

### 何时不用 Proxy？

| 场景 | 推荐替代方案 | 原因 |
|------|------------|------|
| 简单的配置对象 | **`Object.freeze()` + 普通对象** | 不需要响应式 |
| 仅需拦截已知属性 | **`Object.defineProperty()`** | 更好的浏览器兼容性和性能 |
| 需要 `===` 伪装 | **无法实现** | 这是语言层面的限制 |
| 极端性能热路径 | **直接操作普通对象** | Proxy 有固定开销 |
| 需要在不支持 Proxy 的环境中运行 | **Polyfill 或 defineProperty 降级方案** | IE11 及更早版本 |

## 哲学思考：元编程的力量与责任

### 元编程：操控代码的代码

**元编程（Metaprogramming）**是指"编写能够操纵程序自身行为的代码"。如果说普通编程是在建造房子，那么元编程就是在设计房子的"建造规则"——不是决定墙刷什么颜色，而是规定"谁来决定颜色、能否改颜色、改了之后会发生什么"。

Proxy 就是 JavaScript 中最强大的元编程工具之一（另一个是 `Reflect` 和 `Symbol`）。它让你能够在语言层面的基本操作（读写属性、调用函数、删除成员等）之上插入自定义的逻辑。这意味着你可以：

- **重新定义"等于"的含义**（通过拦截属性比较）
- **重新定义"存在"的含义**（通过拦截 `in` 操作符）
- **重新定义"函数调用"的含义**（通过拦截 `apply`）
- **重新定义"创建实例"的含义**（通过拦截 `construct`）

这是一种近乎**造物主级别**的能力——你在定义这个世界中"操作"本身的含义。

### 能力越大，责任越大

但这种能力也带来了独特的风险。普通的代码出错时，Bug 通常局限于特定的功能模块。而 **Proxy handler 中的错误会影响对象的所有操作**——因为它处于一个中心位置，所有经过它的请求都会受到影响。

```javascript
// handler 中的一个 bug 可能导致整个对象"瘫痪"
const buggyHandler = {
  get(target, key) {
    // 假设这里有一个偶发的 bug：
    if (Math.random() < 0.001) {
      throw new Error("随机故障");  // 万分之一的概率报错
    }
    return target[key];
  }
};

const fragile = new Proxy({ important: 'data' }, buggyHandler);

// 任何一次属性访问都有万分之一的概率崩溃
// 这种 Bug 极难复现、极难定位——因为它发生在"基础设施"层面
```

因此，使用 Proxy 时应当遵循以下原则：

1. **保持 handler 的简单和可靠**——复杂的 handler 逻辑本身就是巨大的风险源
2. **充分的测试**——Proxy 相关的 Bug 往往是非确定性的，需要高覆盖率的测试来捕获
3. **提供降级方案**——当环境不支持或出现异常时，能够退回到普通对象行为
4. **文档化约定**——明确告知使用者"这是一个代理对象"，其行为可能与普通对象有细微差别

### "透明性"的理想与现实

理想的 Proxy 应该是**完全透明的（Transparent）**——使用者不应该感知到自己正在与一个代理对象交互。所有的行为都应该与操作原始对象一致，只是附加了一些额外的功能（如日志、校验、通知等）。

但在实践中，**完美的透明性几乎是不可能实现的**。Proxy 总会在某些角落暴露自己的存在：
- `typeof` 和 `instanceof` 的行为差异
- 控制台输出中的 `[[Target]]` 内部槽位
- `JSON.stringify` 可能产生意外结果
- 某些原生方法（如 `Date` 的方法）可能因 this 绑定问题而失效

这意味着 Proxy 更像是一种**半透明的玻璃**——大部分时候你能看透它看到里面的东西，但在某些角度下它会反射光线，提醒你"这里有一层特殊的处理"。

接受这种"近似透明"的现实，而不是追求绝对的透明，是成熟的元编程态度。就像我们在现实生活中接受"没有任何系统能做到 100% 可靠"一样——我们追求的是"足够好"（Good Enough），而不是"完美无缺"（Perfect）。

### 控制反转（IoC）的极致体现

从架构设计的角度看，Proxy 实现的是**控制反转（Inversion of Control, IoC）**的极致形式：

- 在普通代码中，**对象的使用者**控制着如何使用对象（读哪个属性、写什么值、何时删除）
- 在 Proxy 模式中，**对象的创建者**通过 handler 控制着对象如何被使用——使用者失去了部分控制权

这种控制权的转移使得框架设计者能够：

- **强制执行不变量（Invariant）**——如"某些属性一旦设定就不能更改"
- **注入横切关注点（Cross-cutting Concern）**——如日志、权限检查、性能计量
- **虚拟化（Virtualization）**——让远程对象表现得像本地对象一样（RPC 框架的核心技术）
- **惰性计算（Lazy Evaluation）**——只在确实需要时才付出计算的代价

这些都是**框架级的能力**——它们不属于业务逻辑本身，而是属于支撑业务逻辑运行的"基础设施"。Proxy 让这些基础设施以一种优雅的、声明式的、非侵入性的方式融入你的代码。

> **Proxy 是 JavaScript 元编程能力的皇冠明珠。它赋予了你重新定义"对象行为"的权力——这是一项足以改变整个应用架构范式的力量。** Vue 3 选择它作为响应式的基石，MobX 选择它来实现可观察对象，无数库和框架选择它来构建更安全、更智能的数据管理层。理解 Proxy，不只是学会了一个 API，更是获得了一种"在代码之下操控代码"的思维方式。而这种思维方式，正是从"写应用程序的人"进化为"设计程序系统的人"的关键一步。
