# 类自动访问器（auto-accessor）提案

## 从一个反复出现的"样板代码"模式说起

在编写 JavaScript 类的过程中，你可能无数次写过类似这样的代码：

```javascript
class Circle {
  #radius;

  constructor(radius) {
    this.#radius = radius;
  }

  get radius() {
    return this.#radius;     // 读：直接返回私有字段
  }

  set radius(value) {        // 写：赋值前可能要做验证
    if (value < 0) throw new Error("半径不能为负数");
    this.#radius = value;
  }
}
```

这段代码的目的是什么？你希望 `radius` 这个属性在被**读取**时返回当前值，在被**写入**时先做合法性检查再存储。这是一个非常合理、非常常见的需求——几乎每个有经验的 JavaScript 开发者都写过几十上百次这样的模式。

但请注意其中的**重复与冗余**：

- 你需要声明一个私有字段 `#radius` 来存放真正的数据（这叫"后备字段" / Backing Field）
- 你需要写一个 `get radius()` 方法，它的全部工作就是把 `#radius` 的值原样返回
- 你需要写一个 `set radius()` 方法，其中包含验证逻辑，然后赋值给 `#radius`
- **getter 做的事情极其机械**——它只是一个"转发"操作，没有任何额外的逻辑

这种模式被称为**手动_accessor_ 模式（Manual Accessor Pattern）**。它在功能上完全正确，但在表达上却充满了"噪音"：为了实现一个带验证的属性，你需要写大约 8~12 行代码，其中至少一半是在做毫无创造性的"管道工作"（Plumbing）——声明后备字段、写 getter 转发值、写 setter 接收参数。

更令人困扰的是，随着类中这类属性的增多，代码会迅速膨胀：

```javascript
class Rectangle {
  #width;
  #height;
  #opacity;
  #borderWidth;
  // ... 四个私有字段

  get width()   { return this.#width; }
  set width(v)  { if (v < 0) throw new Error(); this.#width = v; }
  get height()  { return this.#height; }
  set height(v) { if (v < 0) throw new Error(); this.#height = v; }
  get opacity() { return this.#opacity; }
  set opacity(v) {
    if (v < 0 || v > 1) throw new Error("透明度需在 0~1 之间");
    this.#opacity = v;
  }
  get borderWidth() { return this.#borderWidth; }
  set borderWidth(v) {
    if (v < 0) throw new Error();
    this.#borderWidth = v;
    reRenderBorder(); // 额外副作用：触发重绘
  }
  // ... 仅仅 4 个属性就需要 20+ 行代码！
}
```

这不是臆造的例子。在实际的前端 UI 组件库中，一个典型的组件类往往有十几个甚至几十个这样的受控属性（尺寸、颜色、透明度、间距等），每个都需要 getter/setter 对来封装验证和副作用逻辑。**样板代码（Boilerplate Code）的比例有时会超过真正有意义的业务逻辑。**

ECMAScript 的**自动访问器提案（Auto Accessor Proposal）**正是为解决这一痛点而生的。它用一个新的关键字 `accessor`，将上述冗长的模式压缩为一行声明。

## 什么是自动访问器？

### 最简示例：一行替代八行

```javascript
// ====== 使用自动访问器（ES2023+）======
class Circle {
  accessor radius;

  constructor(radius) {
    this.radius = radius;  // 触发 setter
  }

  get area() {
    return Math.PI * this.radius * this.radius;  // 触发 getter
  }
}

const c = new Circle(5);
console.log(c.radius);  // 5 ← getter 自动生成，读取后备字段的值
c.radius = 10;          // setter 自动生成，写入后备字段
console.log(c.area);    // 314.159...
```

对比一下传统写法和新写法：

```javascript
// 传统写法（Manual Accessor）          // 自动访问器（Auto Accessor）
class Circle {                             class Circle {
  #radius;                                  accessor radius;

  get radius() {                            constructor(r) {
    return this.#radius;                      this.radius = r;
  }                                        }

  set radius(v) {                           get area() {
    if (v >= 0)                               return Math.PI * this.radius * this.radius;
      this.#radius = v;                     }
  }                                        }
}
// ~10 行                                   // ~5 行
```

**核心变化**：
1. 不再需要手动声明 `#radius` 后备字段
2. 不再需要手写 `get radius()` —— 引擎自动为你生成
3. 不再需要手写 `set radius(v)` —— 引擎自动为你生成（默认行为是直接赋值给后备字段）

`accessor` 关键字的语义可以精确地表述为：**为此属性自动创建后备字段 + 自动生成 getter/setter 对**。它是一个"语法糖"（Syntactic Sugar），但这个糖足够甜，足以消除日常开发中最常见的那一类样板代码。

### `accessor` 到底生成了什么？

理解自动访问器的关键在于搞清楚引擎在幕后做了什么。当你写下 `accessor propName;` 时，JavaScript 引擎会将其展开（Desugar）为以下等效代码：

```javascript
// 你写的：
class Example {
  accessor name;
}

// 引擎实际生成的（概念上的等价形式）：
class Example {
  #name;              // ① 自动创建一个同名的私有后备字段

  get name() {        // ② 自动生成 getter —— 返回后备字段的值
    return this.#name;
  }

  set name(value) {   // ③ 自动生成 setter —— 将值存入后备字段
    this.#name = value;
  }
}
```

注意几个关键的生成规则：

1. **后备字段名 = 属性名**，且始终是**私有的**（以 `#` 开头）。这意味着外部代码无法绕过 getter/setter 直接访问后备字段
2. **getter 和 setter 是公开的**（除非类本身是私有嵌套类或使用了特殊修饰符）。外部通过 `obj.propName` 访问时会自动走 getter/setter
3. **默认的 setter 是"透传"的**——不做任何校验或转换，直接把接收到的值存入后备字段。但你可以覆盖这个默认行为（稍后详述）

### 带初始值的自动访问器

自动访问器支持像普通字段一样指定初始值：

```javascript
class Counter {
  accessor count = 0;       // 初始值为 0

  increment() {
    this.count++;           // 读取(count getter) → 加1 → 写回(count setter)
  }

  reset() {
    this.count = 0;         // 直接通过 setter 设为 0
  }
}

const c = new Counter();
console.log(c.count);  // 0
c.increment();
console.log(c.count);  // 1
```

初始值的赋值发生在类的初始化阶段（类似于 `static {}` 执行阶段对于静态成员、构造函数执行之前对于实例成员），它走的是**自动生成的 setter** 而不是直接对后备字段赋值。这一点很重要——如果你的 setter 被覆盖了（见下文），初始值赋值也会走你的自定义逻辑。

### 静态自动访问器

`accessor` 不仅可以用在实例成员上，也可以用在**静态成员**上：

```javascript
class AppConfig {
  static accessor environment = "development";
  static accessor version = "1.0.0";
  static accessor #internalDebug = false;

  static {
    // 可以在静态块中读写静态自动访问器
    if (process.env.NODE_ENV === "production") {
      AppConfig.environment = "production";  // 走 setter
    }
    AppConfig.version = loadVersionFromPackageJson();

    // 注意：不能直接访问 #internalDebug 的后备字段
    // 但可以通过 setter/getter 访问
  }
}

console.log(AppConfig.environment); // "development"
AppConfig.environment = "staging";   // 走 setter
```

静态自动访问器的后备字段也是**静态私有字段**，只有类内部的其他方法才能访问它（通过自动生成的 getter/setter 或其他能访问该私有作用域的代码）。

## 自定义 setter：自动访问器的真正威力

如果自动访问器只能生成"透传"的 getter/setter，那它的价值就有限了——毕竟普通字段本身就已经是"可读可写"的了。自动访问器真正的威力在于：**你可以保留自动生成的后备字段和 getter，只覆盖 setter 来加入自定义逻辑。**

### 覆盖 setter 进行数据验证

这是最常见的使用场景：

```javascript
class Temperature {
  accessor celsius;  // 摄氏温度

  constructor(celsius) {
    this.celsius = celsius;  // 走自定义 setter
  }

  // 只覆盖 setter —— 加入验证逻辑
  set celsius(value) {
    if (typeof value !== "number") {
      throw new TypeError("温度必须是数字");
    }
    if (value < -273.15) {
      throw new RangeError("温度不能低于绝对零度 (-273.15°C)");
    }
    // 将合法值存入后备字段
    // ⚠️ 这里如何写入后备字段？见下文
  }

  // getter 保持默认行为 —— 直接返回后备字段的值
  // （不需要显式定义，引擎自动生成）

  get fahrenheit() {
    return (this.celsius * 9/5) + 32;  // 通过 getter 读取
  }

  get kelvin() {
    return this.celsius + 273.15;
  }
}

const t = new Temperature(25);
console.log(t.celsius);     // 25
console.log(t.fahrenheit);  // 77
console.log(t.kelvin);      // 298.15

t.celsius = -300;           // RangeError! 温度不能低于绝对零度
t.celsius = "hot";          // TypeError! 温度必须是数字
```

这里出现了一个关键问题：**在自定义的 setter 中，如何将验证通过的值写入自动生成的后备字段？**

如果你尝试写 `this.celsius = value`，那会**递归调用 setter 自己**，导致无限循环（Stack Overflow）。你需要一种方式来"绕过"setter，直接触碰后备字段。

### 方式一：使用 `$` 后备字段访问语法

自动访问器提案引入了一种特殊的语法来访问后备字段：**在属性名前面加 `$` 符号**：

```javascript
class Temperature {
  accessor celsius;

  set celsius(value) {
    if (typeof value !== "number") {
      throw new TypeError("温度必须是数字");
    }
    if (value < -273.15) {
      throw new RangeError("温度不能低于绝对零度 (-273.15°C)");
    }
    // ✅ this.$celsius 直接访问后备字段，不触发 setter
    this.$celsius = value;
  }

  // getter 保持自动生成
}

const t = new Temperature(25);
console.log(t.celsius);  // 25 ← 走自动 getter
t.$celsius = 100;         // ⚠️ 这行在外部调用会怎样？
```

**重要说明**：`$` 后备字段访问语法的具体规范细节取决于提案的最终定稿版本。在不同的提案迭代中，后备字段访问的方式经历过讨论（包括使用 `this.#celsius`、`arguments[0]` 的特殊约定、或其他语法）。本文采用 `$` 前缀作为示意性的表示方式。在实际使用时，请以你所使用的 JavaScript 引擎的实现为准。

### 方式二：使用 `Object.defineProperty` 配合描述符

另一种不依赖特殊语法的方式是通过 `Object.defineProperty` 在构造函数或另一个方法中来设置后备字段：

```javascript
class SmartString {
  accessor _value;

  constructor(initial) {
    // 利用 Object.getOwnPropertyDescriptor 获取后备字段信息
    const descriptor = Object.getOwnPropertyDescriptor(SmartString.prototype, "_value");
    console.log(descriptor);
    // 这种方式较为底层，通常推荐使用上述方式一
  }
}
```

这种方式比较底层且不够直观，一般不建议作为首选方案。

### 完整的数据验证示例

下面是一个更加完整的、展示了自动访问器在日常开发中的典型用法：

```javascript
class User {
  accessor name;
  accessor email;
  accessor age;

  constructor({ name, email, age }) {
    this.name = name;
    this.email = email;
    this.age = age;
  }

  // ====== name: 非空字符串检查 ======
  set name(value) {
    if (typeof value !== "string" || value.trim().length === 0) {
      throw new Error("姓名不能为空");
    }
    this.$name = value.trim();
  }

  // ====== email: 格式验证 ======
  set email(value) {
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (!emailRegex.test(value)) {
      throw new Error("邮箱格式无效");
    }
    this.$email = value.toLowerCase();  // 自动转小写
  }

  // ====== age: 范围检查 + 类型转换 ======
  set age(value) {
    const num = Number(value);
    if (!Number.isFinite(num)) {
      throw new Error("年龄必须是有效数字");
    }
    if (num < 0 || num > 150) {
      throw new Error("年龄应在 0~150 之间");
    }
    this.$age = Math.floor(num);  // 取整
  }
}

const u = new User({
  name: "  张三  ",
  email: "ZHANGSAN@Example.COM",
  age: "25.7"
});

console.log(u.name);   // "张三"     ← 自动 trim
console.log(u.email);  // "zhangsan@example.com"  ← 自动小写化
console.log(u.age);    // 25         ← 自动取整
```

注意这个例子中的精妙之处：**每个属性都有不同的验证和转换逻辑**，但它们都遵循同一个模式——用 `accessor` 声明属性，然后只覆盖 setter。getter 全部由引擎自动生成，不需要写任何代码。

## 自动访问器 vs 其他属性定义方式的全面对比

为了让你准确把握自动访问器的定位，我们将它与所有现有的属性定义方式进行逐一比较。

### 与普通数据属性（Data Field）对比

```javascript
// 普通数据属性
class A {
  count = 0;
}
const a = new A();
a.count = 10;  // 直接赋值，无拦截
console.log(a.count);  // 10

// 自动访问器
class B {
  accessor count = 0;
}
const b = new B();
b.count = 10;  // 走 setter（即使你没自定义 setter）
console.log(b.count);  // 10（走 getter）
```

| 维度 | 普通数据属性 (`x = v`) | 自动访问器 (`accessor x`) |
|--|----------------------|--------------------------|
| **存储方式** | 直接作为对象的自身属性 | 存储在私有后备字段中 |
| **读写行为** | 直接读写，不可拦截 | 通过 getter/setter 中转 |
| **能否拦截** | ❌ 不能 | ✅ 可以覆盖 setter/getter |
| **是否出现在枚举中** | ✅ 默认可枚举 | 取决于 getter 的 [[Enumerable]] |
| **属性描述符** | `{ value: ..., writable: true }` | `{ get: fn, set: fn, enumerable: true, configurable: true }` |
| **性能** | 略高（直接内存访问） | 略低（方法调用开销） |
| **适用场景** | 纯数据、无需验证 | 需要控制/验证/观察 |

**通俗类比：**
- 普通数据属性就像一个**没有门的敞开架子**——谁都可以直接拿取或放置东西，没有任何管控
- 自动访问器就像一个**带服务员的寄存柜台**——你要存东西时交给服务员（setter），服务员可以检查物品、给你一张号码牌；你要取东西时找服务员（getter），服务员从后台仓库取出物品交给你。你永远无法直接进入后台仓库

### 与手动 getter/setter 对比

这是最直接的对比——自动访问器本质上就是手动 getter/seter 的语法糖：

```javascript
// 手动写法（Manual）
class ManualCircle {
  #radius;

  constructor(r) {
    this.#radius = r;
  }

  get radius() { return this.#radius; }
  set radius(v) {
    if (v < 0) throw new Error("半径不能为负数");
    this.#radius = v;
  }
}

// 自动访问器写法（Auto Accessor）
class AutoCircle {
  accessor radius;

  constructor(r) {
    this.radius = r;
  }

  set radius(v) {
    if (v < 0) throw new Error("半径不能为负数");
    this.$radius = v;  // 写入后备字段
  }
  // getter 自动生成
}
```

| 维度 | 手动 getter/setter | 自动访问器 |
|--|-------------------|-----------|
| **代码量** | 较多（需声明后备字段 + getter + setter）| 较少（只需声明 + 可选覆盖 setter）|
| **后备字段管理** | 手动声明 `#field` | **自动创建** |
| **Getter 样板代码** | 每次都要写 `return this.#field` | **省略**（自动生成透传 getter）|
| **心智负担** | 需记住三个部分的关系 | **单一声明即完整** |
| **灵活性** | 完全控制 | 同样完全可控制 |
| **可读性** | 冗长但显式 | 简洁但隐式（隐藏了后备字段存在的事实）|

### 与 `Object.defineProperty` 定义属性对比

在 ES6 class 语法普及之前，开发者常用 `Object.defineProperty` 在构造函数中定义带有 getter/setter 的属性：

```javascript
// 旧式 defineProperty 写法
function OldStyleCircle(radius) {
  let _radius = radius;  // 闭包变量作为后备

  Object.defineProperty(this, 'radius', {
    get() { return _radius; },
    set(value) {
      if (value < 0) throw new Error();
      _radius = value;
    },
    enumerable: true,
    configurable: true
  });
}
```

| 维度 | `Object.defineProperty` | 自动访问器 |
|--|------------------------|-----------|
| **定义位置** | 构造函数内部（运行时）| 类体（编译时/解析时）|
| **封装性** | 闭包（更强——每次实例独享闭包）| 私有字段（类级别共享定义）|
| **性能影响** | 每个实例执行 defineProperty | 类定义时一次性处理 |
| **原型链支持** | 每个实例独立定义 | 自然支持原型继承 |
| **TypeScript 支持** | 类型推断困难 | 天然支持类型推导 |

## 进阶应用场景

### 场景 1：响应式属性 —— 变更通知

当属性的值发生变化时，你可能希望自动通知某些"订阅者"。这在 MVVM 框架（如 Vue、Angular）的数据绑定机制中是核心能力：

```javascript
class ReactiveModel {
  accessor data;
  #listeners = new Set();

  constructor(initialData) {
    this.data = initialData;
  }

  // 自定义 setter：在赋值后发送通知
  set data(newValue) {
    const oldValue = this.$data;  // 读取旧值
    if (oldValue === newValue) return;  // 值没变，跳过
    this.$data = newValue;             // 先更新
    this.#emitChange("data", oldValue, newValue);  // 再通知
  }

  onChange(callback) {
    this.#listeners.add(callback);
    return () => this.#listeners.delete(callback);  // 返回取消订阅函数
  }

  #emitChange(prop, oldValue, newValue) {
    this.#listeners.forEach(fn => fn(prop, oldValue, newValue));
  }
}

// 使用
const model = new ReactiveModel({ name: "Alice", score: 90 });

const unsub = model.onChange((prop, oldVal, newVal) => {
  console.log(`[${prop}] ${JSON.stringify(oldVal)} → ${JSON.stringify(newVal)}`);
});

model.data = { name: "Bob", score: 95 };
// [data] {"name":"Alice","score":90} → {"name":"Bob","score":95}

model.data = { name: "Bob", score: 95 };  // 相同值，不会触发通知
```

这种模式是[《Proxy 实现数据绑定》](/frontend/javascript/language-async/proxy-data-binding)文章中所讨论的轻量级替代方案。当你只需要对个别属性做变更检测时，自动访问器比 Proxy 更加精准和轻量——不需要代理整个对象，只需要"武装"特定的属性即可。

### 场景 2：计算属性的缓存（Memoization via Setter）

有时候，某个派生属性的值计算成本很高，但你又不想每次读取都重新计算。利用自动访问器的 setter，可以实现一种简单的缓存失效策略：

```javascript
class ExpensiveComputation {
  accessor #rawInput;
  accessor #cachedResult;

  constructor(input) {
    this.#rawInput = input;
    this.#cachedResult = null;  // 缓存未命中
  }

  // 输入数据发生变化时，使缓存失效
  set rawInput(value) {
    if (this.$rawInput !== value) {
      this.$rawInput = value;
      this.$cachedResult = null;  // 标记缓存失效
    }
  }

  // 读取结果时，按需计算
  get result() {
    if (this.#cachedResult === null) {
      console.log("正在执行昂贵计算...");
      // 模拟耗时计算
      this.$cachedResult = heavyCompute(this.#rawInput);
    }
    return this.#cachedResult;
  }
}

function heavyCompute(data) {
  // 模拟复杂计算
  return data.split("").reverse().join("").toUpperCase();
}

const ec = new ExpensiveComputation("hello world");
console.log(ec.result);   // "DLROW OLLEH"（首次：触发了计算）
console.log(ec.result);   // "DLROW OLLEH"（第二次：从缓存读取，不再打印日志）
ec.rawInput = "foo bar";  // 改变输入 → 缓存被清空
console.log(ec.result);   // RAB OOF（重新计算）
```

当然，这个简单实现有一些局限性（比如 `null` 可能是合法的计算结果，此时不能用 `null` 作为"未缓存"标记）。在生产环境中，你可以使用一个 `Symbol` 或者独立的标志位来做更可靠的缓存状态追踪。

### 场景 3：DOM 属性映射 —— 双向同步

在前端开发中，经常需要将 JavaScript 对象的属性与 DOM 元素的属性保持同步。自动访问器的 setter 是执行这种同步操作的理想位置：

```javascript
class SliderComponent {
  #element;
  accessor value;

  constructor(selector, initialValue = 50) {
    this.#element = document.querySelector(selector);
    this.value = initialValue;  // 初始值也会走 setter → 同步到 DOM

    // 监听 DOM 的 input 事件 → 回写到 JS 属性
    this.#element.addEventListener("input", (e) => {
      // 注意：这里直接设 $value 以避免触发 DOM 更新（避免循环）
      this.$value = parseFloat(e.target.value);
    });
  }

  // JS 属性 → DOM 同步
  set value(newValue) {
    const clamped = Math.max(0, Math.min(100, newValue));
    this.$value = clamped;
    this.#element.value = clamped;
    this.#element.style.setProperty("--percent", `${clamped}%`);
  }
}

// 使用
const slider = new SliderComponent("#my-slider", 75);
console.log(slider.value);  // 75
slider.value = 90;          // DOM 滑块自动移动到 90% 的位置
```

这种模式在构建自定义 Web Components 封装库时特别有价值——每个"受控属性"都是一个自动访问器，setter 负责将变化推送到 DOM，而 DOM 事件则直接写入后备字段（`$field`）来避免循环触发。

### 场景 4：序列化与反序列化的中间层

当对象需要在"内部表示"和"持久化格式"之间转换时，自动访问器可以作为天然的编解码边界：

```javascript
class DateRange {
  accessor startDate;
  accessor endDate;

  constructor(start, end) {
    this.startDate = start;
    this.endDate = end;
  }

  // 内部用 Date 对象，但接受 ISO 字符串输入
  set startDate(value) {
    this.$startDate = value instanceof Date ? value : new Date(value);
    if (isNaN(this.$startDate.getTime())) {
      throw new Error(`无效的日期: ${value}`);
    }
  }

  set endDate(value) {
    this.$endDate = value instanceof Date ? value : new Date(value);
    if (isNaN(this.$endDate.getTime())) {
      throw new Error(`无效的日期: ${value}`);
    }
    if (this.$endDate < this.$startDate) {
      throw new Error("结束日期不能早于开始日期");
    }
  }

  // 序列化时输出 ISO 字符串
  toJSON() {
    return {
      start: this.startDate.toISOString(),
      end: this.endDate.toISOString(),
      days: Math.ceil((this.endDate - this.startDate) / (1000 * 60 * 60 * 24))
    };
  }
}

const range = new DateRange("2024-01-01", "2024-12-31");
console.log(range.startDate instanceof Date);  // true
console.log(JSON.stringify(range));
// {"start":"2024-01-01T00:00:00.000Z","end":"2024-12-31T00:00:00.000Z","days":366}
```

在这个例子中，使用者可以用字符串、Date 对象等各种格式传入日期，自动访问器的 setter 负责统一转换为标准的 Date 对象存储；而 `toJSON()` 方法则在输出时统一转为 ISO 字符串。**属性的"对外接口"和"内部存储"之间有一个清晰的转换层**，而这个转换层的代码被优雅地封装在了 setter 内部。

## 继承与多态：子类中的自动访问器

自动访问器完全支持继承体系，并且表现得和你预期的一样自然。子类可以继承父类的自动访问器、覆盖其 setter/getter、或者引入新的自动访问器。

### 基本继承行为

```javascript
class Animal {
  accessor name;

  constructor(name) {
    this.name = name;
  }

  introduce() {
    return `我叫 ${this.name}`;
  }
}

class Dog extends Animal {
  accessor breed;

  constructor(name, breed) {
    super(name);
    this.breed = breed;
  }

  bark() {
    return `${this.name}（${this.breed}）汪汪叫！`;
  }
}

const dog = new Dog("旺财", "柯基");
console.log(dog.name);   // "旺财" —— 来自 Animal 的自动访问器
console.log(dog.breed);  // "柯基" —— Dog 自身的自动访问器
console.log(dog.bark()); // "旺财（柯基）汪汪叫！"
```

子类 `Dog` 继承了父类 `Animal` 的 `name` 自动访问器——包括其后备字段、getter 和 setter。对 `dog.name` 的读写操作会正确地沿着原型链找到 Animal 中定义的 getter/setter 并执行。

### 子类覆盖父类的 setter

子类可以强化或修改父类的验证规则：

```javascript
class Person {
  accessor age;

  constructor(age) {
    this.age = age;
  }

  set age(value) {
    if (!Number.isFinite(value)) {
      throw new Error("年龄必须是数字");
    }
    this.$age = value;  // 父类的 setter：基本类型检查
  }
}

class Employee extends Person {
  #minWorkingAge = 16;
  #maxRetirementAge = 65;

  // 覆盖 setter：添加就业相关约束
  set age(value) {
    // 先复用父类的基本验证
    super.age = value;  // 调用父类 setter（走父类的验证逻辑）
    // 再添加子类特有的约束
    if (value < this.#minWorkingAge || value > this.#maxRetirementAge) {
      throw new RangeError(`员工年龄必须在 ${this.#minWorkingAge}~${this.#maxRetirementAge} 之间`);
    }
  }
}

const p = new Person(80);        // ✅ 合法
const e = new Employee(15);      // ❌ RangeError! 员工年龄必须 ≥ 16
const e2 = new Employee(30);     // ✅ 合法
```

注意这里的 `super.age = value` 语法——它调用了父类的 setter，让父类的验证逻辑先执行一遍。这是一种良好的实践：**子类的 setter 应该在父类验证的基础上添加额外约束，而不是完全替代父类的验证。**

### 抽象基类 + 自动访问器

自动访问器非常适合用作"受控属性契约"的定义工具。抽象基类可以定义一个自动访问器但不提供完整实现，要求子类来填充具体的验证逻辑：

```javascript
// 抽象基类：定义"需要一个经过验证的 ID"的契约
abstract class Identifiable {
  abstract accessor id;  // 注：JavaScript 目前不支持 abstract accessor
                         // 这里是概念演示；实际可用普通 accessor + throw
}

// 实际可行的模式：
class IdentifiableBase {
  accessor id;

  set id(value) {
    this.$id = this.validateId(value);  // 由子类实现 validateId
  }

  validateId(value) {
    throw new Error("子类必须实现 validateId 方法");
  }
}

class UserId extends IdentifiableBase {
  validateId(value) {
    if (typeof value !== "string" || !/^usr_[a-z0-9]{8}$/.test(value)) {
      throw new Error('用户 ID 格式应为 "usr_" + 8位字母数字');
    }
    return value;
  }
}

class OrderId extends IdentifiableBase {
  validateId(value) {
    if (typeof value !== "string" !/^ORD-\d{6}-\d{4}$/.test(value)) {
      throw new Error('订单 ID 格式应为 "ORD-XXXXXX-XXXX"');
    }
    return value;
  }
}
```

这种模式体现了**模板方法模式（Template Method Pattern）**的思想：基类定义了算法的骨架（"ID 必须经过验证后存入"），而将具体的验证步骤留给子类来实现。

## 自动访问器的限制与注意事项

没有任何技术是银弹。了解自动访问器的边界同样重要。

### 限制 1：性能开销

每次通过自动访问器读写属性，都会涉及一次方法调用（getter 或 setter）。虽然现代 JavaScript 引擎对这类调用做了大量优化（内联缓存、JIT 编译），但在极端性能敏感的场景中（如每秒调用百万次的游戏物理引擎循环、高频交易系统），这种开销可能是不可忽略的。

```javascript
// 性能敏感场景：慎用自动访问器
class Particle {
  x;  // 普通字段 —— 直接内存访问
  y;  // 普通字段
  vx;
  vy;

  update(dt) {
    this.x += this.vx * dt;  // 每帧执行，数万次/秒
    this.y += this.vy * dt;
  }
}
```

**实用建议**：
- 对于普通的业务逻辑代码（UI 组件、数据处理、API 调用），自动访问器的性能开销完全可以忽略
- 对于确实需要极致性能的热点路径（如 Canvas 渲染循环、大型数组遍历），优先使用普通字段
- 不要过早优化（Premature Optimization）——先用最清晰的代码写出来，有明确的性能瓶颈时再做调整

### 限制 2：序列化行为差异

自动访问器的属性在序列化时的行为取决于 getter 的 `[[Enumerable]]` 特性。默认情况下，自动访问器是**可枚举的**，所以 `JSON.stringify` 会正常工作：

```javascript
class Example {
  accessor name = "test";
  accessor count = 42;
}

const e = new Example();
console.log(JSON.stringify(e));  // '{"name":"test","count":42}'
```

但如果你同时定义了自定义的 `toJSON` 方法，或者在自动访问器之外还定义了同名的方法，可能会出现意外情况。此外，自动访问器的后备字段是私有序列化时不会被包含——这是符合预期的行为。

### 限制 3：与装饰器（Decorator）的交互顺序

当自动访问器和[装饰器](https://github.com/tc39/decorators)一起使用时，需要注意应用的顺序。装饰器作用于自动访问器时，接收到的上下文信息包含了它是自动访问器的元信息：

```javascript
function logged(value, context) {
  if (context.kind === "accessor") {
    return {
      get() {
        console.log(`读取 ${context.name}`);
        return value.get.call(this);
      },
      set(newValue) {
        console.log(`设置 ${context.name} = ${newValue}`);
        return value.set.call(this, newValue);
      },
      initialize(initialValue) {
        console.log(`初始化 ${context.name} = ${initialValue}`);
        return initialValue;
      }
    };
  }
}

class DecoratedExample {
  @logged
  accessor x = 10;
}
```

具体的 API 细节取决于你所使用的装饰器提案版本（2022 版本 vs 2023 版本 vs 最终标准版）。

### 限制 4：不能在同一属性上混用 `accessor` 和手动 `get/set`

这是语法层面的限制——你不能既用 `accessor` 声明一个属性，又在同一个类体中为同名属性定义 `get` 或 `set` 方法（除非是用于覆盖）：

```javascript
class BadExample {
  accessor name;

  get name() { ... }  // ❌ 冲突！accessor 已经自动生成了 getter
  set name(v) { ... } // ❌ 冲突！accessor 已经自动生成了 setter
}
```

正确的做法是只用 `accessor` 声明，然后用**覆盖**的方式来定制 getter 或 setter（如前面的例子所示）。

## 设计哲学深度探讨

### 为什么不是"自动属性"而是"自动访问器"？

提案的命名选择本身就值得玩味。为什么叫 **Auto-Accessor** 而不是 **Auto-Property** 或 **Smart Field**？

因为"访问器（Accessor）"这个词精确地传达了本质：**这个特性生成的是 getter/setter 对，而不是某种特殊的属性。** 它与已有的 `get`/`set` 语法处于同一语义层面——只不过以前你必须手动写全，现在引擎帮你自动生成了一部分。

这也意味着自动访问器**不是一个全新的概念**——它不要求学习新的思维模型。你已经知道 getter/setter 是什么、怎么工作、什么时候用；自动访问器只是让你写更少的代码来达到同样的效果。这是一种**增量式（Incremental）**的语言改进，而非革命性（Revolutionary）的变化。

### "约定优于配置"在语言层面的一次体现

Ruby on Rails 框架推广了一个著名的哲学：**约定优于配置（Convention over Configuration）**——框架应该提供合理的默认行为，让你在没有额外配置的情况下就能正常工作；只有当默认行为不符合需求时才需要去配置。

自动访问器将这个哲学带到了 JavaScript 语言本身的层面：

- **默认行为**：`accessor name;` 生成的 getter/setter 是"透传"的——读取返回值，写入存值。这和普通字段的行为几乎一样，对使用者来说是透明的
- **按需配置**：当你需要验证、变换、通知等额外行为时，**只覆盖 setter 即可**。getter 通常不需要改（因为它的工作就是返回值）
- **最小惊讶原则**：一个只写了 `accessor name;` 而不做任何覆盖的类，其行为和一个写了 `name;` 普通字段的类几乎完全一致。使用者不会感到意外

这种设计降低了特性的学习成本和认知门槛。你不必一开始就深入理解所有的细节——从一个最简单的声明开始，当需求变得更复杂时再逐步引入更多能力。这与 Python 的 `@property` 装饰器、C# 的自动属性（`public string Name { get; set; }`）、Kotlin 的 ` backing field`（`var name: String by Delegates.observable(...)`）的设计思路异曲同工。

### 样板代码的本质代价

让我们退一步思考一个更根本的问题：**为什么样板代码是个问题？**

有人可能会说："多写几行 getter/setter 有什么大不了的？IDE 都能自动生成。" 确实，现代 IDE 的代码生成能力在很大程度上缓解了这个问题的表面症状。但样板代码的危害不仅仅是打字工作量的问题：

**1. 认知噪音（Cognitive Noise）**

每一行代码都在争夺阅读者的注意力。当一个类中有 10 个属性，每个都对应着 3 行 getter/setter 样板代码时，真正有意义的逻辑（验证规则、副作用）就被淹没在了大量的"管道代码"中。阅读者的眼睛必须学会过滤掉这些噪音——但这本身就是一种认知负担。

**2. 维护摩擦（Maintenance Friction）**

如果你想修改某个属性的行为（比如改变验证规则），你需要找到对应的 getter/setter 对并修改它们。如果属性是用 `accessor` 声明的，你一眼就知道"哦，这个属性可能有自定义 setter"，然后往下看几行就能找到。如果是手写的，你需要在几十行几乎长得一样的 getter/setter 代码中定位到正确的那个位置。

**3. 一致性风险（Consistency Risk）**

当每个属性都需要手写 getter/setter 时，不同开发者（甚至同一开发者在不同时间点）可能会采用略微不同的风格。有的用 `#fieldName`，有的用 `_fieldName`，有的在 getter 中加注释有的不加……这些微小的差异累积起来会增加代码库的整体熵值。而 `accessor` 提供了一种统一的、标准化的表达方式。

**4. 机会成本（Opportunity Cost）**

花在写和维护样板代码上的时间和精力，本可以用来做更有价值的事：更好的错误消息、更完善的测试、更清晰的文档。样板代码是一种隐形的税——它不一定阻止你到达目的地，但它消耗了你本可用于更重要工作的资源。

### 语言进化的方向：减少仪式感

纵观编程语言的进化史，有一条清晰的主线：**逐步减少完成同一件事所需的"仪式感"（Ceremony）**。

- C 语言需要你手动 `malloc/free` 内存 → Java/GC 带来了自动内存管理
- Java 需要为每个字段写 getter/setter → Kotlin/C# 带来了自动属性
- JavaScript 需要手动管理原型链 → `class` 语法带来了结构化的类型定义
- `class` 中需要手写 getter/setter 样板代码 → **`accessor` 带来了自动访问器**

每一次进化都不是在增加新的能力，而是在让**已经可以做到的事情变得更容易表达**。自动访问器并没有让你做以前做不到的事——你一直都能用手动的 getter/setter 实现相同的功能。它做的是让你能用**更少、更清晰**的代码来表达相同的意图。

这就是好的语言设计的标志之一：**它不应该强迫你在"表达能力"和"简洁性"之间做选择。你应该能够两者兼得。**

## 总结：何时使用自动访问器

### 适用场景速查表

| 场景 | 推荐 | 理由 |
|------|------|------|
| 属性需要验证 | ✅ 强烈推荐 | setter 覆盖是最自然的位置 |
| 属性需要格式转换 | ✅ 推荐 | 如 trim、toLowerCase 等 |
| 属性变更需要通知/副作用 | ✅ 推荐 | setter 是触发副作用的理想位置 |
| 属性需要在内部和外部有不同的表示形式 | ✅ 推荐 | setter 做 codec（编解码）|
| 纯数据容器，无需任何拦截 | ❌ 用普通字段 | 避免不必要的性能开销 |
| 极端性能敏感的热点路径 | ❌ 用普通字段 | 方法调用开销可能成为瓶颈 |
| 需要直接 JSON 序列化且关心键的顺序 | ⚠️ 需测试 | 确认序列化行为符合预期 |
| 项目目标环境不支持 ES2023+ | ❌ 不可用 | 需要转译器（TypeScript 4.9+/Swc/Babel）支持 |

### 最佳实践清单

1. **优先使用 `accessor` 替代手动 getter/setter**——除非你有特殊的理由保留手写版本
2. **只在 setter 中放入有意义的逻辑**——不要只是为了打印日志或调试而覆盖 setter；那样的话用普通字段 + Proxy 更合适
3. **保持 getter 为默认的透传行为**——除非你有充分的理由（如延迟计算、动态派生）
4. **在子类中使用 `super.property = value`** 来复用父类的 setter 验证逻辑
5. **不要过度使用**——如果一个类中每个字段都是 `accessor` 且每个都被覆盖了复杂的 setter，也许应该反思一下这个类的职责是否过于繁重
6. **配合 TypeScript 使用时**——`accessor` 字段可以被正确推断类型，享受完整的类型安全

> **最后一句忠告：自动访问器是一把精致的手术刀，不是一把锤子。它在你需要精确控制单个属性的读写行为时表现出色，但并不是所有属性都需要这种级别的控制。好的判断力来自经验——而经验来自于在合适的场景中使用合适的工具。**
