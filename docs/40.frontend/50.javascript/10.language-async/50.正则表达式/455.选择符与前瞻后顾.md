# 选择符与前瞻后顾 —— 分支优先级、正向/负向前瞻、正向/负向后顾

在[《分组与引用》](/40.frontend/50.javascript/10.language-async/50.正则表达式/450.分组与引用.md)一文中，定义圆括号把多个字符捆绑成整体、记住匹配内容并在后续引用的能力。但现实中的匹配需求往往更加微妙——有时候我们需要的不是"精确匹配某段文字"，而是"在满足某种条件的前提下匹配另一段文字"；有时候我们面对的是"多个备选方案，只要满足其中之一即可"。这就引出了正则表达式中两个极其重要却又经常被误解的概念：**选择符（Alternation）** 与 **前瞻后顾断言（Lookahead & Lookbehind Assertions）**。

如果说分组是正则表达式世界的"组织者"，那么选择符就是它的"决策者"，而断言则是它的"观察者"——三者协同工作，构成了正则表达式处理复杂文本模式的完整能力体系。

> **本文的目标**：系统讲解选择符的优先级陷阱与正确使用方式，深入剖析四种断言类型（正/负向前瞻、正/负向后顾）的工作原理、应用场景与性能特性，并通过大量实战案例展示这些工具如何解决那些"看似不可能"的匹配难题。

## 一、选择符 —— "或"逻辑的优雅表达

### 1.1 什么是选择符？

**选择符（Alternation）** 用竖线 `|` 表示，含义是"或"——它告诉正则引擎：**在竖线两侧的模式中，只要匹配上任意一个就算成功**。这是正则表达式中最直观的逻辑运算符之一：

```javascript
// 基本语法：A|B 表示匹配 A 或匹配 B
/cat|dog/.test('I have a cat');   // true ✓（匹配到了 cat）
/cat|dog/.test('I have a dog');   // true ✓（匹配到了 dog）
/cat|dog/.test('I have a bird');  // false ✗（两者都没匹配到）

// 提取操作
'I like cats and dogs'.match(/cat|dog/g);
// → ['cat', 'dog']
```

选择符的本质是一种**分支（Branch）**机制。你可以把它想象成一条分岔的道路——正则引擎站在路口，同时试探两条路，哪条先走通就走哪条。这种"尝试多条路径、取最先成功者"的行为，正是正则引擎**回溯（Backtracking）**能力的核心体现。

### 1.2 多路分支与优先级陷阱

当选择符连接超过两个选项时，它依然遵循同样的逻辑——从左到右依次尝试，**第一个成功的选项胜出**：

```javascript
// 三路选择
/red|green|blue/.test('My favorite color is green');  // true
/red|green|blue/.test('sky blue');                      // true（匹配到 'blue'）

// 匹配提取 —— 返回第一个成功匹配的内容
'apple banana cherry'.match(/apple|banana|cherry/);
// → ['apple']（只返回第一项！因为 match 不带 g 时只找第一个匹配）
'banana apple cherry'.match(/apple|banana|cherry/);
// → ['banana']（虽然 apple 也存在于字符串中，
//            但 banana 在字符串中位置更靠前且先被匹配规则尝试）
```

然而，这里藏着一个**极其常见且危险的陷阱**——**选择符的优先级极低**。低到什么程度？它几乎是正则表达式中优先级最低的操作符。这意味着如果你不加括号，`|` 的作用范围可能远超你的预期：

```javascript
// ⚠️ 陷阱演示：你以为的 vs 实际发生的

// 你的意图：匹配 'cat' 或 'dog'（作为完整的单词）
const badRegex = /cat|dog/;
'cattle'.match(badRegex);  // → ['cat']  😱
// 等等——'cattle' 里并没有 'cat' 这个独立的单词啊？
// 实际上 /cat|dog/ 的意思是：匹配 'cat' 或者匹配 'dog'
// 而 'cattle' 的前三个字母恰好是 'cat'，所以匹配成功了！

// 更隐蔽的问题：选择符的范围失控
const dangerousRegex = /abc|def/;
'xxxabcyyy'.test(dangerousRegex);  // true（匹配 abc）
'xxxdefyyy'.test(dangerousRegex);  // true（匹配 def）
// 到目前为止看起来没问题……但看看下面这个：
```

### 1.3 优先级问题的本质

要理解为什么优先级会成为问题，我们需要建立正确的心理模型。正则表达式中的操作符优先级（从高到低）大致如下：

| 优先级 | 操作符 | 说明 |
|--------|--------|------|
| **最高** | `\`（转义）、`[]`（字符组）、`()`（分组）、`(?=...)`（断言） | 原子级操作 |
| **高** | `+ * ? {n,m}`（量词） | 紧贴前一个元素 |
| **中** | 字符串拼接（`ab` 表示先匹配 a 再匹配 b） | 顺序组合 |
| **最低** | `\|`（选择符） | 分隔最大的可能范围 |

关键在于**最低**这个位置。看这个例子：

```javascript
// ❌ 危险写法：/abc|def/
// 引擎理解为：(abc) OR (def)
// 这在简单情况下没问题……

// ❌ 危险写法：/name|age|city/
// 看起来是匹配三个单词，但实际上：
'fullname'.match(/name|age|city/);
// → ['name']  😱 —— 'fullname' 中包含 'name' 子串！

// ❌ 更危险的情况
const regex = /^https?|ftp:/;
regex.test('http://example.com');     // true（匹配 http）
regex.test('ftp://example.com');      // true（匹配 ftp:）
regex.test('https://example.com');    // true（匹配 https）
// 但问题来了：
regex.test('not-ftp-but-has-ftp-inside');
// → true 😱 —— 因为字符串中包含 'ftp:' 就能通过！
// ^ 只作用于 https?，不作用于整个选择表达式！
```

这就是优先级陷阱的核心——**锚点符号（如 `^`、`$`、`\b`）无法跨越选择符的边界来约束所有分支**。当你写 `/^http|ftp/` 时，引擎的理解是 `(^http)|(ftp)`，而非 `^(http|ftp)`。前者表示"行首是 http **或者**（任意位置）出现 ftp"，后者才是你真正想要的"行首是 http 或 ftp"。

### 1.4 解决方案：用分组控制范围

解决方案简单而明确——**始终用圆括号将选择符的各个选项包裹起来**。这不仅能控制范围，还能配合量词使用：

```javascript
// ✅ 正确做法：用分组包裹选择项
/^(http|ftp)/.test('http://example.com');           // true
/^(http|ftp)/.test('ftp://example.com');            // true
/^(http|ftp)/.test('not-ftp-but-has-ftp-inside');   // false ✓（修正了！）

// ✅ 配合量词：让整组选项重复
/(cat|dog)+/.test('catdogcat');      // true（cat dog cat 各出现一次）
/(cat|dog)+/.test('birdfish');        // false（不含 cat 或 dog）
// 对比没有分组的情况：
/cat|dog+/.test('cat');               // true（匹配 cat）
/cat|dog+/.test('doggg');             // true（匹配 doggg —— 量词只作用于 g！）
/cat|dog+/.test('catcat');            // true（只匹配了第一个 cat）

// ✅ 提取多种日期格式
const dateRegex = /(\d{4}[-/]\d{2}[-/]\d{2}|(?:Jan|Feb|Mar)\s+\d{1,2},?\s+\d{4})/;
'2024-01-15'.match(dateRegex);              // → ['2024-01-15']
'January 15, 2024'.match(dateRegex);         // → ['January 15, 2024']
'Mar 8, 2024'.match(dateRegex);              // → ['Mar 8, 2024']
```

关于分组的选择，回顾[《分组与引用》](/40.frontend/50.javascript/10.language-async/50.正则表达式/450.分组与引用.md)中的原则——如果不需要捕获分组的内容，请使用**非捕获组 `(?:...)`** 来避免不必要的内存开销和索引占用：

```javascript
// ✅ 最佳实践：非捕获组 + 选择符
// 匹配常见的图片扩展名
/\.(?:png|jpe?g|webp|gif|svg|avif|bmp)$/i.test('photo.png');   // true
/\.(?:png|jpe?g|webp|gif|svg)$/i.test('photo.bmp');            // false

// 匹配 HTTP 方法
/^(?:GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS)$/.test('POST');   // true
/^(?:GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS)$/.test('FETCH');   // false

// 匹配编程语言注释风格
/(?:\/\/.*|\/\*[\s\S]*?\*\/)/.test('// This is a comment');       // true（单行注释）
/(?:\/\/.*|\/\*[\s\S]*?\*\/)/.test('/* multi\nline */');          // true（多行注释）
```

### 1.5 选择符的"惰性"：左者优先原则

正则引擎在选择符面前表现出一种**左偏偏好（Left-bias）**——当多个选项都能在同一位置匹配成功时，引擎会**选择最左边的那个**，而不会考虑哪个匹配更长或更"合理"：

```javascript
// 左优先原则示例
/a|ab|abc/.test('abc');
// → 匹配结果是 'a'，不是 'ab'，也不是 'abc'！
'abc'.match(/a|ab|abc/);
// → ['a']（index: 0）

// 为什么？因为在位置 0 处：
// 先尝试 'a' → 成功！立即返回，不再尝试后面的选项

// 即使后面的选项能产生"更好"的匹配结果
'abc'.match(/a(b|bc)/);
// → ['ab', 'b']
// 这里括号内先尝试 b → 成功（匹配到了 b），不再尝试 bc
// 如果想匹配 bc，需要调换顺序
'abc'.match(/a(bc|b)/);
// → ['abc', 'bc']（这次先尝试 bc → 成功！）
```

这种行为被称为**有序选择（Ordered Choice）**，它是 NFA（非确定性有限自动机）型正则引擎的标志性特征。理解这一点对于编写正确的正则至关重要——**选项的顺序有时比选项本身更重要**：

```javascript
// 实战案例：匹配颜色值的不同格式
const colorRegex = /(#(?:[0-9a-f]{3}){1,2})|(rgb\s*\(\s*\d+\s*,\s*\d+\s*,\s*\d+\s*\))|(transparent)/i;

'#fff'.match(colorRegex);                    // → ['#fff', undefined, undefined]
'rgb(255, 128, 0)'.match(colorRegex);        // → [undefined, 'rgb(255, 128, 0)', undefined]
'transparent'.match(colorRegex);              // → [undefined, undefined, 'transparent']

// 注意顺序的影响：如果把 transparent 放到第一位
const badColorRegex = /(transparent)|(#(?:[0-9a-f]{3}){1,2})|(rgb\s*\(\s*\d+\s*,\s*\d+\s*,\s*\d+\s*\))/i;
'transparent'.match(badColorRegex);           // → ['transparent', ...] ✓
'#fff'.match(badColorRegex);                  // → [undefined, '#fff', undefined] ✓（不受影响，因为 transparent 不匹配 #）
```

### 1.6 生活类比：餐厅菜单与点餐员

选择符的工作原理像极了餐厅点餐的场景：

想象一位顾客走进餐厅，菜单上写着三道菜："鱼 **或** 鸡 **或** 牛肉"。这里的"或"就是选择符 `|`。

- **基本功能**：顾客说"我要鱼或鸡或牛肉"——厨师做其中任意一道都可以。
  
- **优先级陷阱**：如果菜单写得不清楚，比如"米饭 **或** 鱼 **或** 鸡配汤"——顾客可能会困惑：到底是"（米饭）或（鱼）或（鸡配汤）"，还是"（米饭或鱼或鸡）配汤"？这就是选择符优先级歧义——缺少"括号"来明确分组时，每个人可能有不同的理解。

- **左优先原则**：假设厨房里有三道预制菜放在架子上——鱼在最左边，鸡在中间，牛肉在最右边。当订单进来时，厨师**总是先伸手拿最左边的那盘**，只有当拿不到（比如鱼卖完了），才会去拿中间的鸡。即使牛肉是顾客最喜欢的（"最长匹配"），但如果鱼还在架子上，端出去的就是鱼。这就是为什么选项顺序很重要——你应该把**最具体/最希望优先匹配**的选项放左边。

- **分组的作用**：如果你想让顾客选择"套餐A（鱼+饭）**或**套餐B（鸡+面）"，就需要用括号把套餐内容包起来——`(鱼+饭)|(鸡+面)`。否则就变成了"鱼 **或** 鸡 **或** 面"——完全不同的意思！

> **哲学思考**：选择符体现了**自由意志与确定性之间的张力**。在形式逻辑中，"或"（OR / ∨）是最基本的命题联结词之一——A∨B 为真，当且仅当 A 至少有一个为真。但在正则表达式的实际执行中，这种"非确定性"被引擎的**左优先策略**收敛为确定性行为。这就像人生中的选择——理论上你有无限的可能（所有分支都开放），但你的每一次实际决定都是具体的、排他的（选择了这条路就不能同时走那条路）。更重要的是，**选择的顺序往往比选择本身更能决定结果**——先尝试什么、后尝试什么，这条隐形的规则决定了你最终抵达哪里。代码如此，人生亦然。

## 二、前瞻断言 —— 向未来张望而不踏出一步

### 2.1 什么是前瞻断言？

**前瞻断言（Lookahead Assertion）** 是正则表达式中最具魔力的构造之一。它的核心能力可以用一句话概括：**检查当前位置之后的文本是否满足某个条件，但不消耗任何字符，也不将检查的内容纳入匹配结果**。

注意这里有两个关键约束：
1. **不消耗字符**——匹配位置不会前进
2. **不纳入结果**——检查的内容不会出现在最终的匹配字符串中

这就像一个人站在门口，往房间里张望一眼，确认"里面有一张桌子"后就把头缩回来——他看到了桌子的存在，但没有进入房间，也没有把桌子搬出来。

JavaScript 支持两种前瞻断言：

| 类型 | 语法 | 含义 |
|------|------|------|
| **正向前瞻（Positive Lookahead）** | `X(?=Y)` | 匹配 X，**前提是** X 后面紧跟 Y |
| **负向前瞻（Negative Lookahead）** | `X(?!Y)` | 匹配 X，**前提是** X 后面**不跟** Y |

### 2.2 正向前瞻：确认"后面有什么"

让我们从最经典的场景开始——**从混杂的文本中区分"价格"和"数量"**：

```javascript
// 场景：一段购物清单
const text = '3 apples cost $5, 2 oranges cost $3, total 8 fruits';

// 问题：如何只提取数字形式的"价格"（后面带 $ 的数字）？
// 普通方法会带上 $ 符号
text.match(/\$\d+/g);
// → ['$5', '$3']（包含了 $ 符号，但我们可能只需要数字部分）

// 用正向前瞻：匹配数字，条件是数字后面紧跟着 $
text.match(/\d+(?=\$)/g);
// → ['5', '3'] ✓（只有数字，$ 不在结果中！）
// 工作原理：
// \d+     → 匹配一个或多个数字（这是实际"消费"的部分）
// (?=\$)  → 往前看，确认下一个字符是 $（这只是"检查"，不消费）

// 同理，只提取"数量"（后面不带 $ 的数字）
text.match(/\d+\b(?! \$)/g);
// → ['3', '2', '8'] ✓（3个苹果、2个橙子、总共8个水果）
```

这个例子展示了前瞻断言的第一个核心价值：**在不想要某些上下文信息出现在结果中、但又必须依赖这些上下文来做判断时**，前瞻断言是最佳工具。

再来看一个更实用的例子——**密码强度校验**：

```javascript
// 要求：密码至少 8 位，且至少包含一个大写字母
const passwordRegex = /^(?=.*[A-Z]).{8,}$/;

passwordRegex.test('password');     // false（没有大写字母）
passwordRegex.test('PASSWORD');     // true（全大写也满足"至少一个大写"的条件）
passwordRegex.test('Pass1234');     // true（有大写 P，且 ≥8 位）
passwordRegex.test('Pass12');       // false（有大写但不够 8 位）

// 解构这个正则：
// ^                  → 从字符串开头开始
// (?=.*[A-Z])        → 【前瞻】往后看，确保某处至少有一个大写字母
//                     → .* 匹配任意字符（包括零个），[A-Z] 匹配大写字母
//                     → 整体意思是"在剩余的所有字符中，某处有大写字母"
// .{8,}              → 实际匹配 8 个或更多任意字符（这才是"吃掉"字符的部分）
// $                  → 到字符串结尾
```

这里有一个非常精妙的设计：**前瞻断言 `(?=.*[A-Z])` 和实际的量词 `.{8,}` 都从同一个位置开始出发**。前瞻往"未来"扫描一遍确认有大写字母，然后 `.{8,}` 重新从同一位置开始正式匹配并消费字符。它们像是两个人从同一起跑线出发，一个负责侦察，另一个负责跑步——侦察员跑完回来报告情况后，跑步的人才开始正式起跑。

### 2.3 叠加前瞻：多重条件的并行检查

前瞻断言最强大的特性之一是它可以**叠加使用**——在一个位置上同时施加多个"前瞻检查"条件。每个前瞻都从当前位置独立地向未来张望，互不影响：

```javascript
// 强密码规则：同时满足以下所有条件
// 1. 至少 8 位
// 2. 至少一个小写字母
// 3. 至少一个大写字母
// 4. 至少一个数字
// 5. 至少一个特殊字符
const strongPassword = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[@$!%*#?&]).{8,}$/;

strongPassword.test('Abc123');          // false（缺少特殊字符，长度也不够）
strongPassword.test('Password123');     // false（缺少特殊字符）
strongPassword.test('P@ssword');        // false（缺少数字，长度不够 8）
strongPassword.test('P@ssw0rd');        // false（只有 7 位）
strongPassword.test('Str0ng!Pass');     // true ✓

// 四个前瞻并列，每个负责检查一项条件：
// 位置 0 ──→ (?=.*[a-z]) 侦察：往后扫一遍，有小写吗？✓ 回到位置 0
// 位置 0 ──→ (?=.*[A-Z]) 侦察：往后扫一遍，有大写吗？✓ 回到位置 0
// 位置 0 ──→ (?=.*\d)     侦察：往后扫一遍，有数字吗？✓ 回到位置 0
// 位置 0 ──→ (?=.*[...])  侦察：往后扫一遍，有特殊字符吗？✓ 回到位置 0
// 位置 0 ──→ .{8,}        正式开始：匹配 8 个或更多字符
```

这种模式之所以有效，是因为每个前瞻都是**独立的观察者**——它们各自出发，各自回来报告，谁也不影响谁的视野。这就像四个安检通道，每个通道检查一项规定，你必须全部通过才能进入。

### 2.4 负向前瞻：确认"后面没有什么"

如果说正向前瞻是在问"后面有 X 吗？"，那么**负向前瞻（Negative Lookahead）**(?!Y)就是在问"**后面没有 X 对吧？**"。它用于排除那些虽然本身符合基本模式、但其上下文不符合要求的匹配：

```javascript
// 场景：匹配所有的 JavaScript 关键字，但要排除以 function 开头的函数声明名
// （简化版示例）
const text = 'const x = 1; let y = 2; function foo() {}; var z = 3;';

// 匹配所有"单词"，但要排除 JavaScript 保留字
// 负向前瞻：匹配单词，但它后面不能是 '('（即不能是函数调用）
/\w+(?!\()/.exec('function myFunc() { return 42; }');
// → ['function']（function 后面是空格不是括号，所以通过了负向前瞻）

// 更实用的例子：匹配 img 标签的 src 属性值
// 但只匹配 .png 和 .jpg，排除 .svg
const html = '<img src="logo.png"><img src="icon.jpg"><img src="diagram.svg">';
html.match(/src="[^"]+\.(?:png|jpg)(?!["'])/g);
// → ['src="logo.png"', 'src="icon.jpg"']（svg 被排除了）

// 另一个经典用途：匹配最后一个某物
// 匹配逗号后面的内容，但这个逗号后面不能再有其他逗号
// 即"最后一个逗号后的内容"
'apple, banana, cherry, date'.match(/,\s*([^,]+)$/);
// → [', cherry, date', 'date']（这不是负向前瞻，只是普通匹配）

// 用负向前瞻实现：匹配每个后面还跟着内容的逗号
'apple, banana, cherry'.match(/\w+, (?=\w+)/g);
// → ['apple, ', 'banana, ']（匹配了前两个逗号，因为它们后面还有单词）
'apple, banana, cherry'.match(/\w+, (?!.*\w+, )/g);
// → ['cherry'] 附近的内容（最后一个元素）
```

### 2.5 前瞻断言中的捕获组

默认情况下，前瞻断言内部的圆括号**不会创建可访问的捕获组**。如果你既想做前瞻检查，又想获取检查到的内容，需要在前瞻内部**额外添加一层捕获括号**：

```javascript
// 默认行为：前瞻内的分组不会被外部访问
'30€'.match(/\d+(?=€)/);
// → ['30']（只有数字，€ 没有被捕获到任何组中）

'Hello World'.match(/Hello(?= World)/);
// → ['Hello']（World 只是用来确认存在的，不在结果中）

// 如果你想同时拿到"检查条件"的内容：
'30€'.match(/\d+(?=(€))/);
// → ['30', '€']（现在 € 被第 1 个捕获组捕获了！）

// 实战：提取货币金额和单位
'$100 €200 ¥300 £400'.matchAll(/\d+(?=(\$|€|¥|£))/g);
// 使用 matchAll 可以遍历所有匹配
const results = [...'$100 €200 ¥300 £400'.matchAll(/\d+(?=(\$|€|¥|£))/g)];
console.log(results);
// → 每个匹配都是 [数字, 货币符号] 的形式
// [
//   ['100', '$'], index: 1,
//   ['200', '€'], index: 6,
//   ['300', '¥'], index: 11,
//   ['400', '£'], index: 16
// ]
```

这个技巧在实际开发中非常有用——当你需要根据后续的上下文来做分类，同时又想知道那个上下文是什么的时候。

### 2.6 生活类比：门口的安检预检员

前瞻断言就像是一位站在入口处的**安检预检员**：

想象你要进入一个高档会所。门口站着一位预检员（这就是前瞻断言），他的工作方式很特别：

- **正向前瞻 `(?=Y)` 就像肯定式预检员**：在你踏入大门之前，他先往前面的区域扫视一圈，确认"前面确实有接待处（Y 存在）"之后，才允许你通过闸机。但他自己不会走向前去——他只是在原地点头示意"可以进了"。最终登记簿上出现的只有你的名字（主匹配内容），不会有预检员的名字，也不会有"接待处"的字样。

- **负向前瞻 `(?!Y)` 就像否定式预检员**：他同样往前扫视，但他检查的是"前面**没有**警戒线（Y 不存在）"。如果前面拉起了警戒线，他会拦住你；如果没有，你就通过。同样地，他不出现在任何记录中。

- **叠加多个前瞻**就像**多个安检通道并行**：你同时要通过"身份检查""行李检查""安全检查"等通道。每个通道的安检员都只关注自己的职责范围，互不干扰。你必须全部通过才能进入——任何一个说"不行"，你就进不去。

- **前瞻内捕获**就像是预检员手里拿着一个**备忘录**：他不仅检查条件是否满足，还会把看到的关键信息记下来（比如"接待处的值班经理姓王"），供后续参考。

> **哲学思考**：前瞻断言体现了人类认知中的一种基础能力——**预期（Anticipation）**。我们在做任何事情之前都会下意识地进行"前瞻"：过马路前先看有没有车过来（正向前瞻），打开冰箱门先闻闻有没有异味（负向前瞻——确认"没有坏味"）。这种"在行动前先审视环境"的能力，是人类智慧的重要组成部分——它让我们能够避免危险、抓住机会、规划未来。在计算领域，这种思想被抽象为**断言（Assertion）**的概念——一种"不改变状态、只验证条件"的操作。它在编译器设计（语义分析阶段验证类型安全）、数据库系统（触发器中的条件判断）、乃至硬件设计（时钟信号前的建立时间检查）中都有广泛的应用。正则表达式的前瞻断言，不过是这一宏大思想在文本处理领域的具体实现罢了。

## 三、后顾断言 —— 回望过去却不倒退一步

### 3.1 什么是后顾断言？

**后顾断言（Lookbehind Assertion）** 是前瞻断言的镜像版本——它**检查当前位置之前的文本是否满足某个条件**，同样不消耗字符、不纳入匹配结果。如果前瞻是"向未来张望"，那后顾就是"回忆刚才走过的路"。

后顾断言在 ES2018（ECMAScript 9）中成为 JavaScript 标准的一部分。在此之前，开发者只能通过变通手段模拟类似的功能。四种后顾断言如下表所示：

| 类型 | 语法 | 含义 |
|------|------|------|
| **正向后顾（Positive Lookbehind）** | `(?<=Y)X` | 匹配 X，**前提是** X 前面紧挨着 Y |
| **负向后顾（Negative Lookbehind）** | `(?<!Y)X` | 匹配 X，**前提是** X 前面**不是** Y |

### 3.2 正向后顾：确认"前面有什么"

回到之前的价格/数量区分问题。这一次，我们换个角度——**根据数字前面的符号来判断**：

```javascript
// 场景：同样是购物清单
const text = 'Buy 3 apples for $5 each, 2 oranges for $3 each';

// 正向后顾：匹配数字，条件是数字前面紧邻 $
text.match(/(?<=\$)\d+/g);
// → ['5', '3'] ✓（价格数字）
// 注意：$ 符号不在结果中！

// 负向后顾：匹配数字，条件是数字前面不是 $
text.match(/(?<!\$)\b\d+/g);
// → ['3', '2'] ✓（数量数字）

// 对比三种方法的区别
// 方法 1：直接匹配（包含上下文）
text.match(/\$\d+/g);
// → ['$5', '$3']（包含 $ 符号）

// 方法 2：捕获组（包含上下文但可分离）
text.match(/\$(\d+)/g);
// → ['$5', '$3']（⚠️ g 模式下丢失分组信息！需要 matchAll）
// [...text.matchAll(/\$(\d+)/g)].map(m => m[1]);
// → ['5', '3']

// 方法 3：后顾断言（最干净）
text.match(/(?<=\$)\d+/g);
// → ['5', '3']（直接得到纯数字，无需后处理）
```

从这个对比可以看出，后顾断言在**需要排除前缀上下文**的场景下最为优雅。它避免了"匹配后再切片"的两步操作，一步到位。

### 3.3 后顾断言的限制：固定宽度

与前瞻断言不同，**后顾断言内部的模式必须是固定宽度的（Fixed-width）**。这是什么意思？

```javascript
// ✅ 固定宽度 —— 可以正常工作
// 精确知道要回看的字符数量
/(?<=\$\d{3})X/;     // 回看 4 个字符（$ + 3位数字）
/(?<=\d{2,4})X/;     // ❌ 错误！{2,4} 不是固定宽度
/(?<=a|bc)X/;        // ❌ 错误！a 是 1 位，bc 是 2 位，宽度不一致
/(?<=ab|cd)X/;       // ✅ 正确！ab 和 cd 都是 2 位
/(?<=word\s?)X/;     // ✅ 正确！\s? 表示 0 或 1 个空白，但引擎可以处理
                       // （实际上 JS 引擎对简单的可选量词做了兼容）

// 具体的限制示例
/(?<=\d+)\d{3}/.test('abc123456');
// SyntaxError: Invalid regular expression: invalid group specifier
// （在某些旧版引擎中）因为 \d+ 的长度不固定！

// ✅ 正确的固定宽度写法
/(?<=\d{3})\d{3}/.test('abc123456');  // true（精确回看 3 位）
/(?<=\d{5})\d{3}/.test('abc123456');  // true（精确回看 5 位）
```

为什么会有这个限制？这与正则引擎的实现方式有关。前瞻是向**前**看的——引擎可以随意前进任意距离然后回来；但后顾是向**后**看的——在当前实现中，引擎需要能够精确地计算出"应该回退多少个位置"。如果回看模式的长度不确定（比如 `\d+` 可能匹配 1 位也可能匹配 100 位），引擎就无法确定从哪个位置开始回看。

> **注意**：不同浏览器和 Node.js 版本对这个限制的实现略有差异。现代 V8 引擎（Chrome / Node.js）已经支持某些变长后顾模式，但为了最大兼容性，建议始终使用固定宽度的后顾模式。

### 3.4 负向后顾：确认"前面没有什么"

负向后顾 `(?<!Y)` 排除那些前面紧邻特定模式的匹配。它在实际开发中有一些非常巧妙的应用：

```javascript
// 应用 1：匹配不在引号内的内容（简化版）
// 匹配冒号，但它前面不能是转义字符 \
const cssText = 'color: red; background: \\: blue;';
cssText.match(/(?<!\\):/g);
// → 只匹配第一个 :（第二个 : 前面有 \\ 所以被排除）
// 注：这是一个简化的例子，真实场景更复杂

// 应用 2：匹配独立的变量名（不以 . 开头的标识符）
const code = 'user.name, user.age, address';
code.match(/(?<!\.)\b[a-z]+\b/g);
// → ['user', 'user', 'address']（name 和 age 前面有 . 被排除）

// 应用 3：在 Markdown 文本中匹配不在链接格式中的文本
const mdText = '[Click here](https://example.com) and also visit example.com';
// 匹配 URL，但不能是以 ]( 开头的（那是 Markdown 链接的 URL 部分）
mdText.match(/(?<!\]\()(https?:\/\/[^\s)]+)/g);
// → ['https://example.com']（只匹配了裸露的 URL，排除了链接内的 URL）
```

### 3.5 前瞻与后顾的对称美

前瞻和后顾形成了一种优美的对称关系。把它们放在一起比较，可以帮助你更好地理解和记忆：

```javascript
// 对称的场景：匹配被特定边界包围的内容
const text = '<div>Hello</div> <span>World</span>';

// 方案 A：用前后顾断言
// 匹配内容，条件是前面有 > 且后面有 <
text.matchAll(/(?<=>)([^<]+)(?=<)/g);
// → 每个匹配都是标签内的文本内容（不含标签本身）
[...text.matchAll(/(?<=>)([^<]+)(?=<)/g)].map(m => m[1]);
// → ['Hello', 'World']

// 方案 B：用捕获组
text.matchAll(/>([^<]+)</g);
// → 结果相同，但 [0] 会包含 > 和 < 的部分

// 更复杂的对称场景：匹配特定格式的引用
const quotes = `"He said 'hello'" and 'She replied "hi"'`;

// 匹配双引号内容（前后都必须是双引号）
quotes.matchAll(/(?<=")([^"]*)(?=")/g);
// → [['He said \'hello\'', ...]]（注意：外层是双引号）

// 匹配单引号内容（前后都必须是单引号）
quotes.matchAll(/(?<=')([^']*)(?=')/g);
// → [['She replied "hi"', ...]]

// 组合使用：同时利用前瞻和后顾
const data = 'name=Alice age=28 city=Beijing';

// 匹配 = 号后面的值，但不包含 = 号
data.matchAll(/(?<==)([^=\s]+)/g);
// → [['Alice'], ['28'], ['Beijing']]
```

### 3.6 生活类比：身后的守门人

如果前瞻是"门口看向里面的预检员"，那么后顾就是**身后回头看你的守门人**：

想象你刚刚穿过一道关卡（到达了当前位置）。身后的守门人（后顾断言）会检查你**是从哪个方向来的**：

- **正向后顾 `(?<=Y)` 就像查验通行证的守门人**：他要确认你确实是从"Y 通道"过来的。比如 Y 是 VIP 通道——守门人看你手里的 VIP 通行证（确认你前面确实经过了 VIP 验证），然后点头放行。通行证本身不会跟你一起进入场地——它只是一张入场资格证明。

- **负向后顾 `(?<!Y)` 就像安检排查员**：他要确认你**不是**从"禁止通道 Y"过来的。如果你的来路上出现了禁止通行的标记，你就会被拦下。

- **固定宽度限制的意义**：守门人的视力范围是有限的——他能看清**身后固定距离内**的情况（比如最近 3 米内的路面痕迹），但无法追踪你从无穷远处走过来的完整路径。如果他试图查看"任意长度"的来路，就会超出他的能力范围——这就是为什么后顾模式必须是固定宽度的原因。

> **哲学思考**：后顾断言引入了一个深刻的认识论问题——**我们对过去的"看见"究竟意味着什么？** 在人类的记忆中，"回忆"从来都不是完美的录像回放——它是重构的、有选择的、受当下情绪影响的。正则表达式中的后顾断言则是一种"机械性的完美回忆"——它准确地、无偏差地检查过去发生了什么。但这种"完美"是有代价的：它只能看到**固定距离内**的过去，而且它看到的只是**字符层面的存在与否**，无法理解语义上的因果关系。这就像我们常说的"事后诸葛亮"——事情发生之后，一切看起来都很清晰，但当时的决策者并不拥有这种"后顾"的全知视角。在软件工程中，日志系统（Logging）就是一种人工构建的后顾机制——它记录了过去发生的事情，以便在问题出现时能够"回头查看"。但正如后顾断言的固定宽度限制一样，日志也有存储成本和检索效率的制约——我们不可能记录一切，只能有选择地记录那些"值得回看"的信息。

## 四、断言实战 —— 让不可能变成可能

### 4.1 经典案例：密码强度渐进式校验

让我们用断言来实现一个**渐进式密码校验器**——不仅告诉你密码是否合格，还能告诉你**差在哪**：

```javascript
/**
 * 渐进式密码强度检测器
 * 利用多重前瞻断言逐项检查密码规则
 */
class PasswordValidator {
    constructor(password) {
        this.password = password;
        this.rules = {
            length: {
                label: '至少 8 个字符',
                // 用前瞻检查长度：从头开始，往后数至少 8 个字符到结尾
                test: /^(?=.{8,}).+$/,
                passed: false
            },
            hasLower: {
                label: '包含小写字母',
                test: /^(?=.*[a-z]).+$/,
                passed: false
            },
            hasUpper: {
                label: '包含大写字母',
                test: /^(?=.*[A-Z]).+$/,
                passed: false
            },
            hasDigit: {
                label: '包含数字',
                test: /^(?=.*\d).+$/,
                passed: false
            },
            hasSpecial: {
                label: '包含特殊字符 (!@#$%^&*)',
                test: /^(?=.*[!@#$%^&*]).+$/,
                passed: false
            },
            noSpaces: {
                label: '不含空格',
                test: /^\S*$/,
                passed: false
            },
            noSequential: {
                label: '无连续重复字符 (如 aaa)',
                // 负向前瞻：从头开始，不应存在"(任意字符)连续出现3次"的情况
                test: /^(?!.*(.)\1\1).*$/,
                passed: false
            }
        };
    }

    validate() {
        const results = {};
        
        for (const [key, rule] of Object.entries(this.rules)) {
            results[key] = {
                label: rule.label,
                passed: rule.test.test(this.password)
            };
        }
        
        const passedCount = Object.values(results).filter(r => r.passed).length;
        const totalCount = Object.keys(results).length;
        const score = Math.round((passedCount / totalCount) * 100);

        let level;
        if (score >= 90) level = '强';
        else if (score >= 70) level = '良好';
        else if (score >= 50) level = '一般';
        else level = '弱';

        return { score, level, details: results };
    }
}

// 测试
const v1 = new PasswordValidator('P@ssw0rd');
console.log(v1.validate());
// → { score: 86, level: '良好', details: { length: {passed:true}, ... } }
// （可能因为没有通过"无连续重复"规则——检查一下）

const v2 = new PasswordValidator('abc');
console.log(v2.validate());
// → { score: 29, level: '弱', 大部分规则未通过 }
```

这个例子的精髓在于：每条规则的检查都是**独立的、基于断言的正则表达式**。你可以轻松地增删规则、调整每条规则的权重，而不需要维护一个庞大的复合正则。

### 4.2 经典案例：智能数字格式化（根据上下文判断）

断言的一个强大用途是根据数字周围的上下文来决定如何处理它：

```javascript
/**
 * 智能数字识别器
 * 根据数字前后的上下文自动判断其语义
 */
function analyzeNumbers(text) {
    const results = [];

    // 价格：前面有 $ 或 ¥ 或 €
    const priceRegex = /(?<=[\$¥€])\d+(\.\d+)?/g;
    let match;
    while ((match = priceRegex.exec(text)) !== null) {
        results.push({ type: '价格', value: match[0], index: match.index });
    }

    // 百分比：后面跟 %
    const percentRegex = /\d+(\.\d+)?(?=%)/g;
    while ((match = percentRegex.exec(text)) !== null) {
        results.push({ type: '百分比', value: match[0], index: match.index });
    }

    // 独立数字（不带货币符号、不是百分比、不在句点后）
    const standaloneRegex = /(?<![.$¥€%\d])(?<!\.\d)\d+(\.\d+)?(?![.%\d])/g;
    while ((match = standaloneRegex.exec(text)) !== null) {
        results.push({ type: '数量', value: match[0], index: match.index });
    }

    return results;
}

const report = `
    Q3 Revenue: $15200.50 (up 15.5% from last year).
    Total units sold: 4200.
    Conversion rate increased to 23.75%.
    Budget remaining: €8500.
`;

console.log(analyzeNumbers(report));
// → [
//     { type: '价格', value: '15200.50', ... },   ($ 符号后)
//     { type: '百分比', value: '15.5', ... },      (% 符号前)
//     { type: '数量', value: '4200', ... },         (独立数字)
//     { type: '百分比', value: '23.75', ... },      (% 符号前)
//     { type: '价格', value: '8500', ... }          (€ 符号后)
//   ]
```

这个例子展示了断言如何帮助我们实现**上下文敏感的文本理解**——同样的数字字符 `\d+`，在不同的语境中被赋予了完全不同的语义。

### 4.3 经典案例：在特定位置插入内容

断言的"零宽度"特性使它非常适合做**定点插入操作**——在不破坏原有内容的前提下，在精确的位置插入新内容：

```javascript
// 场景 1：在每个英文句子末尾加上 emoji
const paragraph = `Hello world. How are you? I'm fine! Thanks.`;

// 匹配句子结束标点（.!?), 并在该位置插入 emoji
// 注意：标点本身不被替换，因为它在断言中
paragraph.replace(/([.!?])(?=\s|$)/g, '$1 🎉');
// → "Hello world.🎉 How are you?🎉 I'm fine!🎉 Thanks.🎉"
// 断言 (?=\s|$) 确保标点后面是空格或字符串结尾
// 替换中的 $1 引用了标点本身，然后在后面追加 emoji

// 场景 2：在 HTML 标签后面插入内容（不修改标签本身）
let html = '<div><p>Hello</p><p>World</p></div>';

// 在每个 <p> 标签后面插入 class
html.replace(/(?<=<p[^>]*?>)/g, ' class="content"');
// → '<div><p class="content">Hello</p class="content">...</div>'
// ⚠️ 注意：这也匹配到了 </p> 中的 <p 部分，实际场景需更精确的正则

// 更精确的做法：只在开标签后插入
html.replace(/(?<=<p(?=[\s>]))/g, ' class="content"');
// 利用嵌套断言：<p 后面紧跟空格或 >

// 场景 3：给每千位数字加逗号（从右到左每三位）
function formatNumber(numStr) {
    // 从右边开始，每三个数字前面插入一个逗号
    // 条件：该位置后面恰好是 3 的倍数个数字，直到字符串结尾
    // 并且前面要么是字符串开头，要么不是数字
    return numStr.replace(/\B(?=(\d{3})+(?!\d))/g, ',');
}

formatNumber('1000000');     // → '1,000,000'
formatNumber('4200');        // → '4,200'
formatNumber('123');         // → '123'（不足四位不加逗号）
formatNumber('1234567890');  // → '1,234,567,890'

// 解析这个精妙的正则：
// \B           → 非单词边界（确保不在数字的开头插入逗号）
// (?=(\d{3})+) → 向前看，后面是 3 的倍数个数字
// (?!\d)       → 再向前确认，在那之后不再是数字了
```

最后这个千位分隔符的正则被誉为**断言应用的巅峰之作**——短短十几个字符，却精准地实现了"从右往左每隔三位插一个逗号"的逻辑，而且完全不使用回调函数或循环。

### 4.4 经典案例：CSS 选择器的简化解析

让我们用断言来完成一个更有挑战性的任务——**从 CSS 代码中提取属性名和属性值**：

```javascript
/**
 * CSS 属性提取器 —— 利用断言精确定位
 */
function extractCSSProperties(cssText) {
    const results = [];
    
    // 匹配格式: property-name: value;
    // 要求：
    //   - 属性名由字母、连字符组成
    //   - 冒号后面有空白（可选）
    //   - 值到分号为止（但分号不纳入值）
    const propertyRegex = 
        /([a-z][-a-z]*)     // 属性名（捕获组 1）
        \s*:                // 冒号（可能周围有空格）
        \s*                 // 值前的可选空白
        (.*?)              // 属性值（捕获组 2 —— 非贪婪）
        (?=;|\s*$)          // 前瞻：值后面是分号或行尾（不纳入匹配）
        /gi;
    
    let match;
    while ((match = propertyRegex.exec(cssText)) !== null) {
        results.push({
            property: match[1].trim(),
            value: match[2].trim()
        });
    }
    
    return results;
}

const css = `
    color: red;
    background-color: #ffffff;
    font-size: 16px;
    margin: 10px 20px;
    border: 1px solid rgba(0, 0, 0, 0.5);
`;

console.log(extractCSSProperties(css));
// → [
//     { property: 'color', value: 'red' },
//     { property: 'background-color', value: '#ffffff' },
//     { property: 'font-size', value: '16px' },
//     { property: 'margin', value: '10px 20px' },
//     { property: 'border', value: '1px solid rgba(0, 0, 0, 0.5)' }
//   ]
```

注意这里的 `(?=;|\s*$)` —— 它确保了我们提取的值**不会包含末尾的分号**，同时也处理了最后一行属性可能没有分号的情况。

### 4.5 生活类比：外科医生的手术刀

断言在实战中的应用，就像一位外科医生手中的**精密手术刀**：

- **密码校验**就像**术前全身检查**：每一项前瞻条件都是一个独立的体检项目——血压正常吗？心率正常吗？血常规正常吗？这些检查之间互不影响，但全部通过才能进行手术。如果某一项不通过，你能准确知道是哪一项出了问题，而不是笼统地说"身体不合格"。

- **智能数字识别**就像**病理化验师**：同样的细胞（数字）在不同的组织环境（上下文）中有着完全不同的意义——在血管附近可能是红细胞计数（价格），在皮肤表面可能是病变面积（百分比），在器官内部可能是细胞数量（纯数字）。化验师的职责就是根据"位置"来赋予数据正确的解释。

- **定点插入**就像**微创手术**：医生需要在特定的解剖位置进行干预，但不能损伤周围的组织。断言就是手术刀——它能在精确的位置"切入"（插入内容），同时保证周围的结构（原始文本）完好无损。

- **CSS 解析**就像**拆解精密仪器**：你需要取出仪器中的每一个零件（属性值），但要把每个零件上的标签（属性名）对应好，还要确保不会把连接件（分号）也当作零件的一部分拿出来。

> **哲学思考**：断言的实战价值揭示了一个深刻的道理——**真正的力量往往来自于"克制"**。普通的匹配是"贪婪的"——它会把所有符合条件的字符都吞进去；而断言是"克制的"——它看到了更多，但索取更少。这种"多看少吃"的策略在许多领域都是智慧的象征：好的倾听者在说话前会先充分了解对方的情况（前瞻），也会反思自己说话的动机和背景（后顾）；优秀的领导者在做决策前会收集大量信息（多重断言并行检查），但最终的决策输出是简洁明确的。断言教会我们：**获取信息和做出判断可以是两件独立的事**——你完全可以充分了解上下文，却在最终的结果中只呈现最核心的部分。这是一种"知而不言"的智慧，也是一种"洞察而不干预"的分寸感。

## 五、性能考量与调试指南

### 5.1 断言的性能特征

断言虽然强大，但并非没有代价。理解它们的性能特征有助于你在效率和功能之间找到平衡：

```javascript
// 性能测试：断言 vs 普通匹配 vs 捕获组
const longText = 'price: $100, qty: 50, tax: $8.5, discount: $15, total: $142.5';

// 方案 A：后顾断言
console.time('lookbehind');
for (let i = 0; i < 10000; i++) {
    longText.match(/(?<=\$)\d+(\.\d+)?/g);
}
console.timeEnd('lookbehind');

// 方案 B：捕获组 + map
console.time('capture-group');
for (let i = 0; i < 10000; i++) {
    [...longText.matchAll(/\$(\d+(?:\.\d)?)/g)].map(m => m[1]);
}
console.timeEnd('capture-group');

// 方案 C：split + filter
console.time('string-methods');
for (let i = 0; i < 10000; i++) {
    longText.split(/\s/).filter(s => s.startsWith('$')).map(s => s.slice(1));
}
console.timeEnd('string-methods');

// 一般结论：
// - 对于短文本，差距微乎其微
// - 对于长文本 + 复杂断言，断言方案通常优于"匹配后处理"方案
// - 但叠加过多前瞻可能导致回溯爆炸（见下一节）
```

### 5.2 回溯陷阱：灾难性的断言组合

断言中最危险的性能问题是**回溯爆炸**——当断言内部的模式与外部的模式形成了"相互试探"的恶性循环时：

```javascript
// ⚠️ 危险模式：可能导致灾难性回溯
// 这个正则看起来无害，但对某些输入会导致指数级耗时
const dangerousRegex = /^(?=.*a).*$/;
// 对正常输入 'abc' → 快速完成
// 对精心构造的长字符串 'bbbbbb...bbba' → 可能导致严重回溯
// 因为 .* 先"贪心地"吃掉所有字符，然后逐步回退去找 a

// 更危险的：嵌套量词 + 断言
const veryDangerous = /^(?=.*a)(?=.*b)(?=.*c).*$/;
// 三个前瞻各有自己的 .*，每个都可能引发回溯
// 最坏情况下时间复杂度可达 O(3^n)

// ✅ 安全替代方案：使用占有量词（JS 原生不支持，但有其他方式优化）
// 或者使用具体的字符类代替 .*
const safeRegex = /^(?=[\s\S]*a)(?=[\s\S]*b)[\s\S]*c[\s\S]*$/;
// 将 . 换为 [\s\S] 不会减少回溯，但明确了意图
// 更好的方案：避免在断言内使用无约束的 .*

// 最安全的方案：用简单的字符检查
const safestRegex = /^[^a]*a[^b]*b.*c$/;
// 不用断言，直接按顺序描述结构
```

### 5.3 浏览器兼容性速查

由于后顾断言是 ES2018 才加入的特性，在使用时需要注意兼容性：

| 特性 | Chrome | Firefox | Safari | Node.js | Edge |
|------|--------|---------|--------|---------|------|
| 正向前瞻 `(?=)` | ✅ 全支持 | ✅ 全支持 | ✅ 全支持 | ✅ 8+ | ✅ 全支持 |
| 负向前瞻 `(?!` | ✅ 全支持 | ✅ 全支持 | ✅ 全支持 | ✅ 8+ | ✅ 全支持 |
| 正向后顾 `(?<=)` | ✅ 62+ | ✅ 78+ | ✅ 16.4+ | ✅ 60+ (V8) | ✅ 79+ |
| 负向后顾 `(?<!)` | ✅ 62+ | ✅ 78+ | ✅ 16.4+ | ✅ 60+ (V8) | ✅ 79+ |
| 变长后顾模式 | ⚠️ 部分支持 | ❌ 不支持 | ⚠️ 部分支持 | ⚠️ V8 支持 | ⚠️ 部分支持 |

如果需要支持旧版环境，可以使用 polyfill（如 [`regexp-core`](https://github.com/slevithan/regexp-core)）或者改用**捕获组 + 后处理**的方式来模拟后顾功能：

```javascript
// Polyfill 思路：用 exec 手动模拟后顾
function lookbehindSimulator(text, pattern, lookbehindPattern) {
    const results = [];
    const combinedRegex = new RegExp(
        `(${lookbehindPattern.source})(${pattern.source})`, 
        'g'
    );
    let match;
    while ((match = combinedRegex.exec(text)) !== null) {
        // match[2] 就是"后顾条件满足时的主匹配内容"
        results.push({
            match: match[2],
            lookbehindContent: match[1],
            index: match.index + match[1].length
        });
    }
    return results;
}

// 用法
lookbehindSimulator('$100 €200', '\\d+', '\\$');
// → [{ match: '100', lookbehindContent: '$', index: 1 }]
// 模拟了 /(?<=\$)\d+/ 的效果
```

### 5.4 调试断言的实用技巧

调试包含断言的正则表达式可能令人沮丧——因为断言的内容不出现在匹配结果中。以下是一些实用的调试方法：

```javascript
// 技巧 1：临时去掉断言，改为捕获组，看看"检查"到了什么
const originalRegex = /\d+(?=€)/;
// 调试版本：
const debugRegex = /\d+(?(€))/;   // 把前瞻改为捕获组
'30€'.match(debugRegex);
// → ['30', ' €'] —— 现在你能看到 € 确实在那里

// 技巧 2：用命名捕获组 + console.log 打印断言内容
function debugLookahead(str, regex) {
    // 给前瞻内的内容加上命名捕获组
    const debugRe = new RegExp(regex.source.replace(
        /\(\?=/, '(?=<debug:'
    ).replace(
        /\)(?=[^)]*$)/, ')>'
    ), 'g');
    
    const matches = [...str.matchAll(debugRe)];
    matches.forEach(m => {
        console.log(`匹配到: "${m[0]}" | 前瞻内容: "${m.groups?.debug}"`);
    });
}

// 技巧 3：使用在线工具的可视化功能
// 推荐：
// - https://regex101.com（支持调试断言）
// - https://debuggexex.com（图形化展示匹配过程）
// - VS Code 的 Regex Previewer 插件

// 技巧 4：分解复杂断言为多个简单断言
// 不要一步到位，而是逐步增加断言条件
const step1 = /^.{8,}$/;                        // 先测长度
const step2 = /^(?=.*[a-z]).{8,}$/;             // 再加小写字母
const step3 = /^(?=.*[a-z])(?=.*[A-Z]).{8,}$/; // 再加大写字母
// 每一步都单独测试，确认无误后再合并
```

## 六、总结：断言思维的心智模型

### 6.1 选择符与断言语法速查表

| 语法 | 名称 | 消耗字符？ | 出现在结果中？ | 主要用途 |
|------|------|-----------|---------------|---------|
| `\|` | **选择符** | 取决于选项内容 | ✅ | 多选一匹配 |
| `(?:a\|b)` | **分组内的选择符** | 取决于选项内容 | ❌（非捕获组） | 控制选择范围 |
| `(?=Y)` | **正向前瞻** | ❌ | ❌ | 确认后面"有"什么 |
| `(?!Y)` | **负向前瞻** | ❌ | ❌ | 确认后面"没有"什么 |
| `(?<=Y)` | **正向后顾** | ❌ | ❌ | 确认前面"有"什么 |
| `(?<!Y)` | **负向后顾** | ❌ | ❌ | 确认前面"没有"什么 |

### 6.2 选择决策流

```
你需要做什么？
│
├─ "多个选项中匹配其一" → 用选择符 │
│   ├─ 需要控制优先级范围吗？
│   │   ├─ 是 → 用 (...) 或 (?:...) 包裹
│   │   └─ 否 → 直接使用 a|b
│   └─ 选项的顺序重要吗？
│       ├─ 是 → 把最期望的/最长的选项放前面
│       └─ 否 → 无所谓
│
├─ "匹配 X，但要检查上下文" → 用断言
│   ├─ 检查的是 X **后面**的内容？ → 用前瞻 (?=) 或 (?!)
│   │   ├─ 要求后面**有** Y？ → 正向前瞻 X(?=Y)
│   │   └─ 要求后面**没有** Y？ → 负向前瞻 X(?!Y)
│   └─ 检查的是 X **前面**的内容？ → 用后顾 (?<=) 或 (?<!)
│       ├─ 要求前面**有** Y？ → 正向后顾 (?<=Y)X
│       ├─ 要求前面**没有** Y？ → 负向后顾 (?<!Y)X
│       └─ 注意：Y 必须是固定宽度！
│
└─ "既要检查上下文，又要提取上下文内容"？
    → 在断言内部额外加一层捕获括号
    → 例：/\d+(?=(€))/
```

### 6.3 断言 vs 其他方案的选型指南

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 快速原型、简单匹配 | 捕获组 + 数组索引 | 最直观，兼容性最好 |
| 需要干净的结果（不含上下文） | 断言 | 一步到位，无需后处理 |
| 需要同时获取内容和上下文 | 捕获组（或断言内嵌套捕获） | 信息最完整 |
| 需要叠加多项独立检查 | 多重前瞻 | 每项条件独立清晰 |
| 需要兼容 IE / 旧 Safari | 捕获组 + 后处理模拟 | 后顾断言不支持 |
| 性能敏感的超长文本 | 避免复杂断言 | 回溯风险高 |

> **最后的思考**：选择符和断言共同拓展了正则表达式的认知维度——选择符引入了**可能性空间**（多个候选路径），而断言引入了**上下文感知**（超越当前位置的环境信息）。如果说基础的字符匹配是"看到一个字符就认一个字符"的点对点映射，那么选择符让它变成了"面临岔路时做出选择"的决策过程，断言则让它变成了"在行动前环顾四周、在行动后回望来路"的自觉行为。这三层能力的叠加，让正则表达式从一种简单的"文本搜索工具"进化为一种具有**有限感知能力和决策能力**的微型语言。掌握选择符与断言，你就掌握了这门语言中关于"选择"与"觉察"的全部表达力。
