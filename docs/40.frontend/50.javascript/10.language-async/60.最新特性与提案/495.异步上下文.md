# 异步上下文 —— AsyncLocalStorage（Node.js）、AsyncContext（提案）

## 一、"数据跟谁走？"——异步编程中的身份困境

在 JavaScript 的世界里，有一件事看起来简单，做起来却异常困难：**让一段数据"跟着"一次完整的请求流程走，从入口到出口，穿过所有的回调、Promise、await、setTimeout，始终不丢失。**

这不是一个新问题。事实上，它是所有服务端开发者迟早会撞上的那堵墙。想象一下你在写一个 HTTP 服务：用户发来了请求，你生成了一个 `traceId` 用于全链路追踪——这个 ID 需要出现在访问日志里、数据库查询日志里、第三方 API 调用记录里、错误上报的堆栈信息里……总之，凡是这个请求触发的任何操作，都应该携带这个 ID。

那么问题来了：**你怎么把这个 ID 传到每一个角落？**

### 1.1 最直觉的想法与它的致命缺陷

最直觉的做法是——用一个全局变量：

```javascript
// ❌ 全局变量方案 —— 看起来能工作，实际上是个灾难
let currentTraceId = null;

http.createServer((req, res) => {
    currentTraceId = generateId();
    // ...处理请求...
    log(`Request ${currentTraceId} started`);
    db.query('SELECT * FROM users', (err, result) => {
        log(`Query under ${currentTraceId}`);  // 这里拿到的是哪个 ID？
        res.end(JSON.stringify(result));
    });
});
```

这段代码有一个致命的问题。Node.js 是**单线程事件循环模型**——它同时处理大量并发请求的方式不是多线程并行，而是通过事件循环不断切换任务。当请求 A 设置了 `currentTraceId = 'A-001'` 之后，如果事件循环在请求 A 的数据库回调执行之前切去处理了请求 B，那么请求 B 会把 `currentTraceId` 改为 `'B-002'`。等请求 A 的回调终于轮到执行时，它读到的 `currentTraceId` 已经是 `'B-002'` 了。

这就是所谓的**竞态条件（Race Condition）**。虽然 Node.js 是单线程的，但它的并发模型依然会产生这种"数据被覆盖"的问题——因为异步操作的完成顺序是不可预测的。

```javascript
// 一个更直观的演示
let requestId = null;

function handleRequest(id) {
    requestId = id;
    console.log('Set:', requestId);
    
    // 模拟异步操作
    setTimeout(() => {
        console.log('Get:', requestId);  // 这里的值是什么？
    }, Math.random() * 100);  // 随机延迟让问题更容易复现
}

handleRequest('req-A');
handleRequest('req-B');
handleRequest('req-C');

// 可能的输出：
// Set: req-A
// Set: req-B
// Set: req-C
// Get: req-C   ← 三次 setTimeout 回调都拿到了 'req-C'！
// Get: req-C
// Get: req-C
```

全局变量的方案彻底失败了。它就像一家只有一张名片夹的公司——每次有新客户来访，前台就把旧客户的名片扔掉换上新的。等旧客户的业务办完了想取回自己的联系方式时，发现名片夹里已经是别人的了。

### 1.2 参数透传方案——正确但不优雅

既然全局变量不可靠，那就老老实实传参吧：

```javascript
// ✅ 参数透传方案 —— 能工作，但侵入性极强
http.createServer((req, res) => {
    const traceId = generateId();
    handleRequest(traceId, req, res);
});

function handleRequest(traceId, req, res) {
    log(traceId, 'Request started');
    
    db.query(traceId, 'SELECT * FROM users', (err, result) => {  // traceId 往下传
        log(traceId, 'Query completed');
        
        callExternalApi(traceId, result, (apiErr, apiResult) => {  // 再往下传
            log(traceId, 'API call done');
            
            cache.set(traceId, apiResult, (cacheErr) => {  // 还得传
                log(traceId, 'Cache updated');
                res.end(JSON.stringify(apiResult));
            });
        });
    });
}
```

这个方案确实能工作——每个函数都显式接收 `traceId` 并继续传递下去。但它带来了几个令人痛苦的问题：

**第一，代码污染。** 每一层函数都要多加一个参数，不管这个函数本身是否关心 traceId。你的业务逻辑签名变成了 `(traceId, actualParam1, actualParam2, callback)`——traceId 像一个不速之客，强行挤进每一个函数签名的第一个位置。

**第二，维护噩梦。** 当你需要新增一种需要传递的上下文信息（比如 `userId`、`requestTime`、`clientIP`），你必须修改整条调用链上每一个函数的签名。在一个中等规模的项目里，这可能涉及几十甚至上百个文件。

**第三，第三方库无法配合。** 你使用的 express 中间件、ORM 框架、HTTP 客户端库——它们的内部函数不会接受你的 `traceId` 参数。你只能通过某种 hack 方式（比如挂载到 request 对象上）来间接传递，但这又回到了"非显式传递"的老路上。

参数透传就像一家严格执行"凭条办事"制度的银行——每一笔业务都必须出示凭证，连清洁工进入大厅打扫卫生也得先登记领取一张凭证纸条。安全是安全了，但所有人都被繁琐的流程折磨得苦不堪言。

### 1.3 理想的解决方案应该长什么样？

综合以上两种方案的教训，我们理想的上下文传递机制应该具备这些特质：

| 需求 | 说明 |
|------|------|
| **请求级隔离** | 不同请求之间的上下文互不干扰 |
| **自动传播** | 不需要手动传递，数据自动跟随异步调用链流动 |
| **零侵入** | 业务代码不需要因为上下文传递而改变签名或实现 |
| **任意位置可访问** | 在调用链的任何深度、任何回调中都能读取当前上下文 |
| **生命周期可控** | 上下文随请求开始而创建，随请求结束而销毁 |

这听起来像是一个不可能同时满足的需求列表——既要像全局变量一样随处可读，又要像局部变量一样作用域隔离；既要自动传播又不能污染代码。但 JavaScript 社区经过多年的探索，最终找到了一条可行的道路。

> **哲学思考**：异步上下文的本质问题是**"同一性（Identity）在时间中的保持"。** 当一个请求进来的时候，它是一个有着明确身份的实体（有自己的 traceId、userId、时间戳）。但随着这个请求的处理过程不断地被拆分为异步任务、放入队列、等待调度、重新拾起执行——每一次"暂停再恢复"都是一个潜在的身份断裂点。同步代码天然不存在这个问题，因为调用栈本身就是身份的载体——你永远知道"我是谁"，因为调用栈完整地记录了你从哪里来。但异步代码打破了调用栈的连续性，每一次 await 或回调都是对调用栈的"切断"。异步上下文技术所做的，就是在被切断的调用栈之间搭建一座隐形的桥，让身份信息能够跨越这道鸿沟。
>
> 这个问题不仅存在于编程领域。在人类社会中，我们用身份证号来标识一个人穿越时空的一致性；在分布式系统中，我们用 TraceID 来关联一次请求跨多个服务的完整路径；在物理学中，费曼路径积分描述了一个粒子如何同时在多条可能的路径上"存在"然后又在某一点汇聚——这些都是"身份在分散的结构中保持一致"这一基本问题的不同表现形式。JavaScript 的异步上下文，不过是这个问题在单线程事件循环模型中的一个特定解法而已。

## 二、演进之路——从 CLS 到 AsyncLocalStorage

在深入理解今天的解决方案之前，有必要回顾一下这条技术路线是如何一步步走到今天的。了解历史不是为了考古，而是为了理解每一种设计背后的权衡取舍。

### 2.1 第一代：Continuation-Local Storage（CLS）

早在 Node.js 的早期时代（2013 年左右），社区就意识到了异步上下文传递的需求。TJ Holowaychuk（Express/Koa 的作者）等人开发了 **continuation-local-storage** 这个 npm 包，引入了 "Namespace" 的概念：

```javascript
// CLS（第一代）的基本用法
const createNamespace = require('continuation-local-storage').createNamespace;

const session = createNamespace('my session');

http.createServer((req, res) => {
    session.run(() => {
        session.set('traceId', generateId());
        // 后续异步操作中可以获取
        setTimeout(() => {
            console.log(session.get('traceId'));  // 能拿到值
        }, 100);
    });
});
```

CLS 的设计理念借鉴自 Java 世界里的 ThreadLocal——只不过 Java 用线程作为隔离边界，而 Node.js 用"续体（Continuation）"作为隔离边界。"续体"这个词来自编程语言理论，大致可以理解为"程序执行到某个点之后剩余的所有待执行的代码"——也就是"接下来要发生的一切"。

CLS 的实现原理非常底层：它利用了 Node.js 内部的 `process.addAsyncListener` API（后来这个 API 被移除了），监听每一个异步操作的创建和触发，维护一个内部的栈结构来保存和恢复上下文。当一个新的异步操作被创建时，CLS 会把当前的上下文快照保存下来；当这个异步操作的回调被执行时，CLS 又会把保存的上下文恢复回去。

**但 CLS 有严重的缺陷：**

- 它依赖 Node.js 内部非公开的 API，每次 Node.js 版本升级都可能 break
- 性能开销很大——因为它 hook 了几乎所有的异步操作创建点
- 在某些边界场景下（特别是 Promise 和 generator 结合使用时）会出现上下文丢失

尽管如此，CLS 是一个开创性的工作。它证明了"异步本地存储"这个概念是可行且有用的，也为后来的官方实现奠定了设计基础。

### 2.2 第二代：async_hooks 底层模块

2017 年，Node.js v8 正式引入了 `async_hooks` 模块——这是第一个官方提供的异步资源生命周期监听机制：

```javascript
// async_hooks —— 底层能力强大但极其难用
const async_hooks = require('async_hooks');

const hook = async_hooks.createHook({
    init(asyncId, type, triggerAsyncId) {
        // 每当一个异步资源被创建时触发
        // 可以在这里记录父子关系
        console.log(`init: ${type} (id=${asyncId}, parent=${triggerAsyncId})`);
    },
    before(asyncId) {
        // 异步回调即将执行前触发
    },
    after(asyncId) {
        // 异步回调执行完成后触发
    },
    destroy(asyncId) {
        // 异步资源被 GC 回收时触发
    }
});

hook.enable();  // 启用钩子

// 之后的所有异步操作都会触发上面的回调
setTimeout(() => {}, 1000);
// 输出: init: Timeout (id=2, parent=1)
```

`async_hooks` 揭开了 Node.js 异步模型的底层面纱。原来每一个 `setTimeout`、每一个 Promise、每一个 `fs.readFile` 都会被分配一个唯一的 `asyncId`，并且记录着是谁（`triggerAsyncId`）创建了它。这形成了一棵**异步资源树**——根节点是脚本的顶层执行，每一个异步操作都是树上的一个节点，边表示的是"谁创建了谁"的关系。

理论上，有了这棵树和这些钩子，你就能精确地控制上下文的保存与恢复。**但实际上，直接使用 `async_hooks` 进行业务开发是一场噩梦：**

第一，**性能代价高昂**。启用 `createHook` 后，Node.js 的每一次异步操作（包括 `console.log`！包括内部的事件循环 tick！）都会触发你的钩子回调。如果你的回调里有任何稍微耗时的操作，整个事件循环都会被拖慢。

第二，**极易出错**。`init/before/after/destroy` 四个钩子的触发时机和语义并不直观，特别是在 Promise、AsyncFunction、Generator 这些复杂的异步原语组合使用时，行为更加难以预测。

第三，**安全风险**。由于钩子会在所有异步操作中触发，如果在钩子内部抛出未捕获的异常或者产生副作用，可能影响整个应用的稳定性。

`async_hooks` 就像是给你提供了一套手术室级别的工具——显微镜、激光刀、神经探测器——让你能看到每一个细胞的分裂和死亡。但对于"我想在请求处理过程中存一个 traceId"这种需求来说，这套工具过于精密且危险了。你需要的是一个体温计，而不是一台核磁共振仪。

### 2.3 第三代：AsyncLocalStorage——当下的标准答案

2019 年，Node.js v13.10.0 引入了基于 `async_hooks` 封装的高层 API：**AsyncLocalStorage（ALS）**。这是目前生产环境中异步上下文管理的标准答案：

```javascript
// AsyncLocalStorage —— 简洁优雅的生产级方案
const { AsyncLocalStorage } = require('node:async_hooks');

const storage = new AsyncLocalStorage();

http.createServer((req, res) => {
    const traceId = generateId();
    
    // run() 创建一个上下文作用域
    storage.run({ traceId, startTime: Date.now() }, () => {
        // 在这个回调及其产生的所有子异步操作中，
        // 都可以通过 storage.getStore() 获取到同一个 store 对象
        
        console.log(storage.getStore().traceId);  // ✅ 能拿到
        
        processNextStep(req, res);
    });
    
    // 这里 getStore() 返回 undefined —— 已经出了上下文范围
    console.log(storage.getStore());  // undefined
});

function processNextStep(req, res) {
    // 即使在这里（不在 run 的直接回调内），也能获取到 store
    console.log(storage.getStore().traceId);  // ✅ 仍然能拿到
    
    db.query('...', (err, result) => {
        // 即使在多层嵌套的异步回调深处，依然能拿到
        console.log(storage.getStore().traceId);  // ✅ 还是能拿到
        res.end(result);
    });
}
```

注意这段代码中最关键的一点：`processNextStep` 函数**没有接收任何关于 traceId 的参数**。它不需要——因为 traceId 存储在 `storage` 中，只要执行流还在 `run()` 创建的作用域内，任何位置的代码都可以通过 `storage.getStore()` 访问到同一个对象。

这就是 ALS 的核心价值所在：**它把"显式参数传递"变成了"隐式上下文感知"**。就像空气——你看不见它摸不着它，但只要你在这个房间里呼吸，你就自然而然地享受着它的存在。

> **生活类比：隐形工牌系统**
>
> 如果把一个 Web 服务器比作一栋大型办公楼：
>
> - **全局变量方案**就像是门口只有一个公共公告栏。每个人进门时把自己的名字写在上面（覆盖掉前一个人的名字）。当你走到三楼想要确认自己是谁的时候，回头看一眼公告栏——上面写的已经是后进门的人的名字了。
>
> - **参数透传方案**就像是每个人都必须随身携带一本厚厚的通行证册。你去会议室要出示它，去茶水间要出示它，上厕所也要出示它（万一保洁人员需要确认你的身份呢？）。而且如果你要托同事帮你去隔壁部门送个文件，你还必须把通行证册也交给他。
>
> - **AsyncLocalStorage 方案**就像是给每个人佩戴了一张**电子工牌**。你进门的时候，闸机自动激活你的工牌，上面显示着你的名字、部门、访问权限。之后无论你走到大楼的哪个角落——会议室、电梯、洗手间——任何一个感应器都能读到你的工牌信息。你不需要主动出示任何东西，不需要记住任何编号，也不需要向任何人解释你是谁。当你离开大楼走出大门时，工牌自动失效——下一秒走进来的另一个人会得到属于他自己的全新工牌。
>
> 这张"电子工牌"就是 AsyncLocalStorage 为每一次请求创建的那个上下文空间——它跟随你移动，对你完全透明，对外界完全可用，而且严格隔离。

## 三、AsyncLocalStorage 核心机制深度解析

了解了历史背景和使用动机之后，让我们深入到 AsyncLocalStorage 的内部世界，系统地理解它的工作机制。

### 3.1 基础 API：run 与 getStore

`AsyncLocalStorage` 类提供了两个核心方法，它们构成了整个 API 体系的基石：

#### run(store, callback[, ...args])

`run` 方法用于创建一个异步上下文作用域：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();

// 基本用法
const result = als.run(
    { userId: 42, role: 'admin' },   // store: 要存储的数据（可以是任意类型）
    () => {                           // callback: 在该上下文中执行的函数
        console.log(als.getStore());
        return 'hello world';          // 返回值会成为 run() 的返回值
    }
);

console.log(result);       // 'hello world'
console.log(als.getStore());  // undefined —— 已出作用域
```

关于 `run` 方法，有几个关键细节值得深入讨论：

**第一，`store` 可以是任意类型的值。** 虽然最常见的做法是传入一个对象（这样可以存放多个字段），但你完全可以传入字符串、数字、Map、Set 甚至另一个类的实例。这给了使用者极大的灵活性：

```javascript
// store 是字符串
als.run('trace-001', () => {
    console.log(als.getStore());  // 'trace-001'
});

// store 是 Map —— 更适合频繁增删键值对的场景
als.run(new Map([['key1', 'value1']]), () => {
    const store = als.getStore();
    store.set('key2', 'value2');   // 动态添加
    console.log(store.get('key1'));  // 'value1'
});

// store 是类实例 —— 更适合复杂的状态管理
class RequestContext {
    constructor(traceId) {
        this.traceId = traceId;
        this.timers = new Map();
    }
    startTimer(name) {
        this.timers.set(name, process.hrtime.bigint());
    }
    endTimer(name) {
        const start = this.timers.get(name);
        return Number(process.hrtime.bigint() - start) / 1e6;  // 毫秒
    }
}
als.run(new RequestContext('req-123'), () => {
    const ctx = als.getStore();
    ctx.startTimer('db-query');
    // ... 数据库操作 ...
    console.log(`DB query took ${ctx.endTimer('db-query')}ms`);
});
```

**第二，`callback` 是同步执行的。** 这是一个容易误解的地方——虽然 `run` 创建的上下文能够穿透异步边界，但 `run` 本身并不会等待异步操作完成。它会同步地调用 `callback`，并立即返回 `callback` 的返回值（如果有的话）。`callback` 内部启动的异步操作（setTimeout、Promise 等）会继续持有这个上下文，但这些异步操作的完成与否不影响 `run` 的返回。

```javascript
// run 同步返回的演示
console.log('before run');

const returnValue = als.run({ id: 1 }, () => {
    console.log('inside run - sync part');
    
    // 启动一个异步操作（它会在 run 返回后才执行）
    setTimeout(() => {
        console.log('async callback, store:', als.getStore()?.id);
    }, 100);
    
    return 'sync return value';
});

console.log('after run, got:', returnValue);

// 执行顺序：
// before run
// inside run - sync part
// after run, got: sync return value
// (100ms later) async callback, store: 1
```

**第三，支持额外的参数传递。** `run` 的第三个及之后的参数会原样传递给 `callback`：

```javascript
als.run({ id: 1 }, (x, y, z) => {
    console.log(x, y, z);  // 'a' 'b' 'c'
    console.log(als.getStore());  // { id: 1 }
}, 'a', 'b', 'c');
```

#### getStore()

`getStore` 是 `run` 的搭档——它在当前上下文中获取之前设置的 store 值：

```javascript
const store = als.getStore();

if (store) {
    // 在上下文内部 —— store 可用
    console.log(store.traceId);
} else {
    // 在上下文外部 —— store 为 undefined
    console.log('Not within an ALS context');
}
```

**关键规则：`getStore()` 只能在 `run()` 的回调链内部返回有效值。** 一旦执行流出 `run` 的作用域（包括同步流出和所有异步操作完成后自然结束），`getStore()` 就会返回 `undefined`。这意味着你不能在 `run` 外部"偷渡"出 store 的引用然后在别处使用——至少不能指望它还能通过 `getStore()` 再次获取：

```javascript
let leakedStore = null;

als.run({ secret: 'abc123' }, () => {
    leakedStore = als.getStore();  // 保存引用
    console.log(leakedStore.secret);  // 'abc123' ✅
});

// 出了 run 之后
console.log(als.getStore());      // undefined ❌
console.log(leakedStore?.secret);  // 'abc123' ✅ （因为你保留了对象的直接引用）
```

最后这行代码揭示了一个重要的事实：`getStore()` 返回的是 store 对象本身的引用，而不是副本。所以如果你在 `run` 内部拿到了 store 对象的引用并将其赋值给外部变量，即使离开了上下文，你依然可以通过这个引用操作那个对象本身。但这种做法是不推荐的——因为它绕过了 ALS 的生命周期管理机制，可能导致难以追踪的 bug。

### 3.2 上下文传播的边界

理解 AsyncLocalStorage 的核心在于搞清楚：**哪些情况下上下文会自动传播，哪些情况下不会？** 这决定了你在实际项目中能否放心地依赖 ALS 来管理状态。

#### 自动传播的场景

以下异步操作会**自动继承并传播** ALS 上下文：

```javascript
als.run({ id: 'test' }, () => {

    // 1. setTimeout / setInterval —— ✅ 传播
    setTimeout(() => {
        console.log('setTimeout:', als.getStore()?.id);  // 'test'
    }, 10);

    // 2. Promise.then() / .catch() / .finally() —— ✅ 传播
    Promise.resolve()
        .then(() => {
            console.log('Promise.then:', als.getStore()?.id);  // 'test'
        });

    // 3. async/await —— ✅ 传播（本质上也是 Promise）
    async function asyncOp() {
        await Promise.resolve();
        console.log('async/await:', als.getStore()?.id);  // 'test'
    }
    asyncOp();

    // 4. setImmediate / queueMicrotask —— ✅ 传播
    setImmediate(() => {
        console.log('setImmediate:', als.getStore()?.id);  // 'test'
    });

    // 5. process.nextTick —— ✅ 传播
    process.nextTick(() => {
        console.log('nextTick:', als.getStore()?.id);  // 'test'
    });

    // 6. EventEmitter 事件监听器 —— ✅ 传播
    const emitter = new (require('events'))();
    emitter.on('event', () => {
        console.log('EventEmitter:', als.getStore()?.id);  // 'test'
    });
    emitter.emit('event');

});
```

这些场景之所以能传播上下文，是因为它们都是 Node.js 原生的异步原语，其内部实现已经与 `async_hooks` 系统进行了集成。当你调用 `setTimeout` 时，Node.js 内部会创建一个 Timeout 类型的异步资源，并将当前的异步上下文绑定到这个资源上。当定时器到期执行回调时，Node.js 会自动恢复绑定的上下文。

#### 可能丢失上下文的场景

然而，并非所有情况都能保证上下文正确传播。以下是几种常见的"陷阱"：

**陷阱一：跨 worker_threads 的边界**

```javascript
const { Worker } = require('worker_threads');

als.run({ id: 'main-thread-context' }, () => {
    const worker = new Worker('./worker.js');
    
    // Worker 线程拥有独立的 JS 环境，不会继承主线程的 ALS 上下文
    // 需要通过 postMessage 手动传递
    worker.postMessage({ context: als.getStore() });
});
```

Worker 线程是完全独立的 JavaScript 执行环境——有自己的事件循环、自己的内存空间、当然也有自己的异步上下文映射。主线程的 ALS 上下文不会自动跨越这个物理边界。

**陷阱二：某些第三方库的异步实现**

一些第三方库可能使用了非标准的异步模式（比如通过 `setImmediate` 的 polyfill、自定义的事件调度器、或者 C++ addon 实现的异步接口），这些可能没有正确集成 `async_hooks`，导致上下文丢失。在实际项目中，如果发现某处 `getStore()` 意外返回 `undefined`，排查方向之一就是检查是否经过了某个可疑的第三方库调用。

**陷阱三：手动创建 Promise vs 原生 Promise**

绝大多数情况下原生 Promise 都能正确传播上下文，但如果你使用了自定义的 thenable 实现（即实现了 `then` 方法的非 Promise 对象），可能会遇到问题：

```javascript
// 自定义 thenable —— 可能导致上下文丢失
const customThenable = {
    then(resolve) {
        // 如果这里的 resolve 调用没有经过标准的 Promise reaction 机制，
        // 上下文可能不会被正确传播
        setTimeout(() => resolve('done'), 10);
    }
};

als.run({ id: 'test' }, async () => {
    await customThenable;  // ⚠️ 取决于具体实现，上下文可能丢失
    console.log(als.getStore()?.id);  // 可能是 undefined
});
```

### 3.3 enterWith、exit 与 disable——实验性 API

除了核心的 `run` 和 `getStore`，AsyncLocalStorage 还提供了几个实验性的 API。它们的功能强大但使用风险较高，需要谨慎对待。

#### enterWith(store)

`enterWith` 的作用是**将当前执行流切换到指定的上下文**，而不创建新的作用域边界：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();

als.run({ original: true }, () => {
    console.log(als.getStore());  // { original: true }
    
    // 使用 enterWith 切换上下文
    als.enterWith({ switched: true });
    
    // 从这里开始，后续所有代码都在新上下文中
    console.log(als.getStore());  // { switched: true }
    
    // 注意：enterWith 没有"回退"机制！
    // 你无法回到之前的 { original: true } 上下文
    // 除非再次调用 enterWith 切换回去
});
```

`enterWith` 与 `run` 的根本区别在于：`run` 有明确的边界——callback 结束后上下文自动退出。而 `enterWith` 是**永久性的切换**——它会影响到调用点之后所有的同步和异步代码，直到下一次 `enterWith` 或 `exit` 调用。

正因为这个特性，`enterWith` 被标记为实验性 API（Stability: 1），官方文档明确建议优先使用 `run()`。`enterWith` 的典型使用场景是在某些框架层面的代码中，当你需要在已有的上下文之外（比如在一个独立的中间件中）强制注入上下文信息时。

#### exit(callback[, ...args])

`exit` 的作用恰好相反——**临时退出当前上下文**：

```javascript
als.run({ inside: true }, () => {
    console.log(als.getStore());  // { inside: true }
    
    als.exit(() => {
        // 在这个回调中，处于上下文"外部"
        console.log(als.getStore());  // undefined
    });
    
    // exit 只影响其回调内部，出来后又恢复了
    console.log(als.getStore());  // { inside: true }
});
```

`exit` 也是实验性 API。它可以用来在某些特定的代码片段中"隐藏"上下文，防止被意外访问。

#### disable()

`disable` 用于完全禁用一个 AsyncLocalStorage 实例：

```javascript
als.disable();

// disable 之后：
// - getStore() 始终返回 undefined
// - run() 不再创建有效上下文
// - 所有已关联的上下文被清理
```

`disable` 的一个重要作用是**允许垃圾回收**。如果不调用 `disable()`，AsyncLocalStorage 内部会持有对所有已创建 store 的引用，阻止它们被 GC 回收。对于长期运行的服务端应用，如果一个 ALS 实例不再需要了（比如某个功能模块被卸载），应该调用 `disable()` 来释放内存。

> **哲学思考**：`run` 和 `enterWith` 代表了两种不同的世界观。`run` 信奉的是"作用域主义"——一切都有明确的开始和结束，就像人的一生，出生入世、离开离世，界限分明。`enterWith` 信奉的是"流变主义"——上下文是一条永不停歇的河流，你可以在其中随时跳转到另一条河道，但没有回头路可言。前者安全但受限，后者自由但危险。编程中的大多数选择都可以归结为这种权衡：**确定性与灵活性之间的博弈。** 而 `run` 被推荐为默认选择，说明在异步上下文管理这个领域中，社区倾向于认为确定性比灵活性更重要——宁可多写几行代码来明确定义边界，也不要留下一个可能在任何地方悄悄改变状态的"幽灵开关"。

## 四、Snapshot 与 Bind——高级上下文操控

Node.js v19.8.0+ 引入了两个强大的高级 API：`snapshot()` 和 `bind()`。它们解决了一些更复杂的场景，同时也标志着 ALS 设计理念的成熟。

### 4.1 snapshot——冻结时光的相机

`AsyncLocalStorage.snapshot()` 是一个静态方法，它能够**捕获当前时刻的完整异步上下文状态**，并返回一个函数——调用这个函数可以在任何时候恢复捕获时的上下文：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();

// 场景：在 run 内部拍摄"快照"
const restoreContext = als.run({ photo: 'taken-at-this-moment' }, () => {
    return AsyncLocalStorage.snapshot();  // 捕获当前上下文
});

// 此时我们已经在外部了
console.log(als.getStore());  // undefined —— 正常，已经出作用域

// 但通过快照恢复的函数，我们可以"穿越回去"
restoreContext(() => {
    console.log(als.getStore());  // { photo: 'taken-at-this-moment' } ✅
    
    // 甚至可以在完全不同的上下文中"穿越"
    als.run({ different: 'context' }, () => {
        console.log(als.getStore());  // { different: 'context' }
        
        // 调用快照恢复函数——瞬间回到拍照时的上下文
        restoreContext(() => {
            console.log(als.getStore());  // { photo: 'taken-at-this-moment' } 🎯
        });
        
        // 回来了
        console.log(als.getStore());  // { different: 'context' }
    });
});
```

`snapshot()` 解决的核心问题是：**如何在对象的生命周期跨越 `run` 边界的情况下保持上下文访问能力。** 考虑下面这个场景：

```javascript
// 问题场景：在 run 内创建的对象需要在 run 外部使用
als.run({ traceId: 'req-001' }, () => {
    // 创建一个数据库查询构建器
    const queryBuilder = createQueryBuilder();
    
    // 把 queryBuilder 返回到外部
    return queryBuilder;
});

const qb = als.run(...); // 拿到了 queryBuilder

// 在外部调用 queryBuilder 的方法
qb.findUsers({ active: true }, (err, users) => {
    // 这里想要获取 traceId —— 但已经不在 run 上下文内了！
    console.log(als.getStore());  // undefined 😢
});
```

使用 `snapshot()` 就能解决这个问题：

```javascript
// 解决方案：用 snapshot 保存上下文恢复能力
class QueryBuilder {
    constructor() {
        // 在构造时（假设在 run 上下文内）拍一张快照
        this._restore = AsyncLocalStorage.snapshot();
    }
    
    find(query, callback) {
        db.rawQuery(query, (err, data) => {
            // 通过快照恢复上下文后再执行回调
            this._restore(() => {
                callback(err, data);  // 回调执行时能访问到正确的上下文
            });
        });
    }
}
```

这种模式非常类似于早期 `AsyncResource` + `runInAsyncScope` 的用法，但代码更加简洁——不需要继承 `AsyncResource`，不需要管理资源的生命周期，只需要一行 `AsyncLocalStorage.snapshot()` 即可。

### 4.2 bind——给函数贴上"时空标签"

`AsyncLocalStorage.bind(fn)` 是另一个静态方法，它的功能是将一个函数**绑定到当前执行时的上下文**：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();

function logStore() {
    console.log('Current store:', als.getStore());
}

als.run({ bound: 'context' }, () => {
    // 将 logStore 绑定到当前上下文
    const boundLog = AsyncLocalStorage.bind(logStore);
    
    // boundLog 在任何地方调用都会恢复绑定时的上下文
    boundLog();  // Current store: { bound: 'context' } ✅
});

// 即使在外部调用 boundLog
boundLog();  // Current store: { bound: 'context' } ✅ （依然有效！）
```

`bind` 和 `snapshot` 的区别在于粒度不同：`snapshot` 捕获的是**整个当前上下文**，返回的是一个"上下文恢复器"；而 `bind` 绑定的是**单个函数**，返回的是一个已经被"打了标签"的新函数。

`bind` 特别适用于事件驱动的场景：

```javascript
const { EventEmitter } = require('events');
const emitter = new EventEmitter();

als.run({ eventId: 'e-42' }, () => {
    // 将事件处理器绑定到当前上下文
    emitter.on('data', AsyncLocalStorage.bind((data) => {
        // 当事件在未来某个时刻触发时，
        // 这个回调仍能访问到绑定时的上下文
        console.log(`Event ${als.getStore()?.eventId} received:`, data);
    }));
});

// 很久之后，在完全不同的上下文中触发事件
als.run({ eventId: 'different' }, () => {
    emitter.emit('data', { value: 123 });
    // 输出: Event e-42 received: { value: 123 }
    // 注意：打印的是 e-42（绑定时）而不是 different（触发时）
});
```

这里有一个微妙但重要的区别需要理解：**事件监听器的执行上下文取决于它何时被注册（bind 时），而非何时被触发。** 默认情况下，EventEmitter 的回调会在触发时的上下文中执行——但如果用了 `bind`，则会在注册时的上下文中执行。

> **生活类比：预录视频 vs 直播**
>
> `snapshot` 和 `bind` 的区别就像两种不同的录制方式：
>
> - **snapshot（快照）就像是一台全景摄像机**：它记录下了此刻周围环境的所有信息（光线、温度、背景音乐、在场的人）。以后你想"回到那一刻"，只需要播放这个录像——你会发现自己置身于完全相同的环境中。但你可以决定什么时候播放、在哪里播放、播放多久。
>
> - **bind（绑定）就像是在某人的背上贴了一段预录的话**：你当时对他说了一句话并录了下来，然后把录音设备粘在他身上。这个人之后可以去任何地方、参与任何对话，但当他决定"播放那段话"的时候，说出来的内容和你当初录的一模一样——带着当时的语气、情绪和语境。
>
> 在编程的世界里，这两种能力解决了同一个问题的不同侧面："我有一段代码需要在未来的某个时刻执行，但我希望它执行时的环境不是'那个时候'的环境，而是'这个时候'的环境。"

### 4.3 AsyncResource——重量级的上下文携带者

在 `snapshot()` 和 `bind()` 出现之前（以及某些 `snapshot()` 无法满足的复杂场景中），`AsyncResource` 是处理跨边界上下文传递的标准工具：

```javascript
const { AsyncLocalStorage, AsyncResource } = require('node:async_hooks');
const als = new AsyncLocalStorage();

// 让一个类继承 AsyncResource，使其具备"携带上下文"的能力
class DatabaseConnection extends AsyncResource {
    constructor(config) {
        super('DatabaseConnection');  // type 参数仅用于调试标识
        this.pool = createPool(config);
    }
    
    query(sql, params, callback) {
        this.pool.query(sql, params, (err, result) => {
            // 关键：使用 runInAsyncScope 在原始上下文中执行回调
            this.runInAsyncScope(callback, null, err, result);
        });
    }
    
    close() {
        this.pool.destroy();
        this.emitDestroy();  // 必须手动触发 destroy！
    }
}
```

`AsyncResource` 的工作原理是：当实例被创建时，它会记录当前的异步上下文（通过 `executionAsyncId()`）。之后任何时候调用 `runInAsyncScope`，都能恢复到创建时的上下文环境。

与 `snapshot()` 相比，`AsyncResource` 的优势在于：

1. **显式的生命周期管理**：你可以精确控制何时创建（`new`）、何时使用（`runInAsyncScope`）、何时销毁（`emitDestroy`）
2. **可用于 Worker Pool 等复杂场景**：在任务调度系统中，每个任务可以被包装成一个 `AsyncResource` 子类
3. **与事件系统集成**：可以配合 `AsyncResource.bind()` 将事件处理器绑定到特定资源

劣势则是：

1. **需要继承**——这意味着如果你的类已经有了父类（比如继承了 EventEmitter），就不能再继承 AsyncResource 了（JavaScript 单继承限制）
2. **需要手动管理 `emitDestroy()`**——忘记调用会导致内存泄漏
3. **API 更加冗长**——相比 `snapshot()` 的一行代码，`AsyncResource` 需要更多的样板代码

对于大多数场景而言，**优先考虑使用 `snapshot()` 和 `bind()`**，只有在确实需要精细的生命周期控制时才使用 `AsyncResource`。

## 五、实战案例——从理论到生产应用

理论知识只有在实际场景中才能真正生根发芽。下面我们通过几个具有代表性的实战案例，展示 AsyncLocalStorage 在真实项目中的应用方式。

### 5.1 案例 1：全链路日志追踪系统

这是 AsyncLocalStorage 最经典的使用场景。目标是为每一个 HTTP 请求生成唯一的追踪 ID，并确保这个 ID 自动出现在所有日志输出中：

```javascript
const http = require('http');
const { AsyncLocalStorage } = require('node:async_hooks');

// ============================================================
// 1. 定义上下文存储和辅助工具
// ============================================================
const requestContext = new AsyncLocalStorage();

/**
 * 生成类似 OpenTelemetry 格式的 traceId
 */
function generateTraceId() {
    const chars = 'abcdef0123456789';
    let result = '';
    for (let i = 0; i < 32; i++) {
        result += chars[Math.floor(Math.random() * chars.length)];
    }
    return result;
}

/**
 * 结构化日志工具 —— 自动携带当前请求上下文
 */
function logger(level, message, extra = {}) {
    const ctx = requestContext.getStore();
    const timestamp = new Date().toISOString();
    const logEntry = {
        timestamp,
        level,
        message,
        traceId: ctx?.traceId || 'no-context',
        userId: ctx?.userId || null,
        ...extra
    };
    
    const levelColors = { info: '\x1b[36m', warn: '\x1b[33m', error: '\x1b[31m' };
    const color = levelColors[level] || '';
    console.log(`${color}[${logEntry.traceId}] [${level.toUpperCase()}] ${message}\x1b[0m`, extra);
    
    // 生产环境中可以将 logEntry 发送到日志聚合系统
    return logEntry;
}

// 快捷方法
const log = {
    info: (msg, extra) => logger('info', msg, extra),
    warn: (msg, extra) => logger('warn', msg, extra),
    error: (msg, extra) => logger('error', msg, extra)
};

// ============================================================
// 2. 模拟数据库层
// ============================================================
const database = {
    query(sql, params = []) {
        const ctx = requestContext.getStore();
        log.info(`SQL: ${sql}`, { params, queryId: ctx?.queryCount ?? 0 });
        
        // 模拟查询延迟
        return new Promise((resolve) => {
            setTimeout(() => {
                if (ctx) ctx.queryCount = (ctx.queryCount || 0) + 1;
                resolve([{ id: 1, name: 'Test User' }]);
            }, Math.random() * 20);
        });
    }
};

// ============================================================
// 3. 模拟缓存层
// ============================================================
const cache = {
    get(key) {
        const ctx = requestContext.getStore();
        log.info(`Cache GET: ${key}`);
        return new Promise((resolve) => {
            setTimeout(() => resolve(null), 5);
        });
    },
    set(key, value, ttl) {
        log.info(`Cache SET: ${key} (TTL: ${ttl}s)`);
        return Promise.resolve(true);
    }
};

// ============================================================
// 4. 模拟外部 API 调用
// ============================================================
function callPaymentGateway(amount) {
    const ctx = requestContext.getStore();
    log.info(`Calling payment gateway: $${amount}`, { userId: ctx?.userId });
    
    return new Promise((resolve, reject) => {
        setTimeout(() => {
            if (Math.random() > 0.2) {
                resolve({ transactionId: `tx-${Date.now()}`, status: 'success' });
            } else {
                reject(new Error('Payment gateway timeout'));
            }
        }, Math.random() * 30);
    });
}

// ============================================================
// 5. 请求处理器
// ============================================================
async function handleRequest(req, res) {
    const ctx = requestContext.getStore();
    ctx.userId = extractUserIdFromToken(req.headers.authorization);
    ctx.queryCount = 0;
    ctx.startTime = Date.now();
    
    try {
        // 尝试从缓存获取
        let userData = await cache.get(`user:${ctx.userId}`);
        
        if (!userData) {
            // 缓存未命中，查数据库
            userData = await database.query('SELECT * FROM users WHERE id = ?', [ctx.userId]);
            await cache.set(`user:${ctx.userId}`, userData, 300);
        }
        
        // 调用支付网关
        const paymentResult = await callPaymentGateway(99.99);
        
        const duration = Date.now() - ctx.startTime;
        log.info('Request completed', { 
            duration: `${duration}ms`,
            queryCount: ctx.queryCount,
            paymentStatus: paymentResult.status 
        });
        
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({
            success: true,
            data: { user: userData, payment: paymentResult },
            meta: { traceId: ctx.traceId, duration }
        }));
        
    } catch (error) {
        log.error(`Request failed: ${error.message}`, { stack: error.stack });
        res.writeHead(500, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ error: error.message, traceId: ctx.traceId }));
    }
}

function extractUserIdFromToken(authHeader) {
    if (!authHeader) return 'anonymous';
    // 简化的 token 解析
    return authHeader.startsWith('Bearer ') ? 'user-42' : 'guest';
}

// ============================================================
// 6. 启动 HTTP 服务器
// ============================================================
const server = http.createServer((req, res) => {
    const traceId = generateTraceId();
    
    // 为每个请求创建独立的上下文
    requestContext.run({
        traceId,
        url: req.url,
        method: req.method,
        headers: req.headers
    }, () => {
        log.info(`Incoming ${req.method} ${req.url}`);
        handleRequest(req, res);
    });
});

server.listen(3000, () => {
    console.log('Server running on port 3000');
    console.log('每个请求都会自动获得唯一的 traceId 并贯穿整个处理链路\n');
});
```

观察这段代码的关键特征：**没有任何一个函数（`handleRequest`、`database.query`、`cache.get`、`callPaymentGateway`）接收 `traceId` 作为参数。** 每个函数内部都通过 `requestContext.getStore()` 自行获取当前上下文——而这个上下文是由 HTTP 服务器的入口层统一注入的。

这意味着：

1. **新增上下文信息无需改动下游代码。** 如果你明天想在每条日志中加入 `clientIP`，只需在入口层的 `run()` 中往 store 里多放一个字段即可。
2. **中间件和插件自动获得上下文能力。** 任何在请求处理链路上的代码——不管是你自己写的还是第三方库的——只要它调用了 `logger` 或 `getStore()`，就能拿到完整的上下文。
3. **代码解耦达到极致。** 日志层不关心谁是调用者，业务层不关心日志怎么写，两者通过隐式上下文松散耦合。

### 5.2 案例 2：性能度量收集器

AsyncLocalStorage 不仅适合存储静态元信息（如 traceId），也非常适合存储动态变化的状态——比如性能计时器：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const perfContext = new AsyncLocalStorage();

/**
 * 性能度量收集器
 * 支持嵌套计时、阶段标记、自动输出报告
 */
class PerformanceCollector {
    /**
     * 开始收集一次请求的性能数据
     */
    static measure(traceId, fn) {
        return perfContext.run({
            traceId,
            phases: [],         // 阶段记录
            timers: new Map(),  // 活跃计时器
            startTime: process.hrtime.bigint(),
            depth: 0            // 当前嵌套深度（用于缩进展示
        }, fn);
    }

    /**
     * 开始一个命名的时间段
     */
    static startPhase(name) {
        const ctx = perfContext.getStore();
        if (!ctx) return () => {};
        
        const phaseId = `${name}-${Date.now()}`;
        const indent = '  '.repeat(ctx.depth);
        
        ctx.depth++;
        ctx.timers.set(phaseId, {
            name,
            indent,
            startTime: process.hrtime.bigint(),
            parentPhase: ctx.currentPhase || null
        });
        ctx.currentPhase = phaseId;
        
        // 返回结束函数
        return () => PerformanceCollector.endPhase(phaseId);
    }

    /**
     * 结束一个时间段
     */
    static endPhase(phaseId) {
        const ctx = perfContext.getStore();
        if (!ctx) return;
        
        const timer = ctx.timers.get(phaseId);
        if (!timer) return;
        
        const duration = Number(process.hrtime.bigint() - timer.startTime) / 1e6;
        ctx.phases.push({
            name: timer.name,
            duration: Math.round(duration * 100) / 100,
            indent: timer.indent,
            depth: ctx.depth - 1
        });
        
        ctx.timers.delete(phaseId);
        ctx.depth--;
        ctx.currentPhase = timer.parentPhase;
        
        return duration;
    }

    /**
     * 添加一个自定义标记点
     */
    static mark(label) {
        const ctx = perfContext.getStore();
        if (!ctx) return;
        
        const elapsed = Number(process.hrtime.bigint() - ctx.startTime) / 1e6;
        ctx.phases.push({
            name: `[MARK] ${label}`,
            elapsed: Math.round(elapsed * 100) / 100,
            isMark: true
        });
    }

    /**
     * 获取完整的性能报告
     */
    static getReport() {
        const ctx = perfContext.getStore();
        if (!ctx) return null;
        
        const totalMs = Number(process.hrtime.bigint() - ctx.startTime) / 1e6;
        
        return {
            traceId: ctx.traceId,
            totalTime: Math.round(totalMs * 100) / 100,
            phases: ctx.phases,
            summary: PerformanceCollector._buildSummary(ctx.phases)
        };
    }

    static _buildSummary(phases) {
        const byName = new Map();
        phases.filter(p => !p.isMark).forEach(p => {
            const existing = byName.get(p.name) || { name: p.name, count: 0, totalTime: 0 };
            existing.count++;
            existing.totalTime += p.duration;
            byName.set(p.name, existing);
        });
        return Array.from(byName.values()).map(v => ({
            ...v,
            avgTime: Math.round(v.totalTime / v.count * 100) / 100
        }));
    }
}

// ============================================================
// 使用示例
// ============================================================

async function simulateBusinessLogic() {
    const endInit = PerformanceCollector.startPhase('Initialization');
    await new Promise(r => setTimeout(r, 5));   // 模拟初始化
    endInit();
    
    PerformanceCollector.mark('After initialization');
    
    const endAuth = PerformanceCollector.startPhase('Authentication');
    await new Promise(r => setTimeout(r, 15));  // 模拟认证
    endAuth();
    
    // 嵌套子阶段
    const endDb = PerformanceCollector.startPhase('Database Operations');
    
    const endQuery1 = PerformanceCollector.startPhase('User Query');
    await new Promise(r => setTimeout(r, 25));
    endQuery1();
    
    const endQuery2 = PerformanceCollector.startPhase('Permission Query');
    await new Promise(r => setTimeout(r, 10));
    endQuery2();
    
    endDb();
    
    const endApi = PerformanceCollector.startPhase('External API Call');
    await new Promise(r => setTimeout(r, 35));  // 模拟网络请求
    endApi();
    
    PerformanceCollector.mark('Before response');
    
    const endRender = PerformanceCollector.startPhase('Response Rendering');
    await new Promise(r => setTimeout(r, 3));
    endRender();
}

// 执行测量
PerformanceCollector.measure('trace-demo-001', async () => {
    await simulateBusinessLogic();
    
    const report = PerformanceCollector.getReport();
    console.log('\n=== Performance Report ===');
    console.log(`Trace ID: ${report.traceId}`);
    console.log(`Total Time: ${report.totalTime}ms\n`);
    
    console.log('Timeline:');
    report.phases.forEach(p => {
        if (p.isMark) {
            console.log(`  ${'─'.repeat(40)} ${p.name} (+${p.elapsed}ms)`);
        } else {
            console.log(`${p.indent}├─ ${p.name}: ${p.duration}ms`);
        }
    });
    
    console.log('\nSummary:');
    report.summary.forEach(s => {
        console.log(`  ${s.name}: ${s.count} calls, total ${Math.round(s.totalTime)}ms, avg ${s.avgTime}ms`);
    });
});
```

这个案例展示了 AsyncLocalStorage 在性能监控领域的威力：

1. **自动的层级关系**。通过 `startPhase/endPhase` 的配对调用，每个时间段都知道自己的父级是谁（通过 `parentPhase` 字段），从而构建出一棵完整的调用树。
2. **零侵入式埋点**。业务代码只需要在适当的位置调用 `startPhase` 和 `endPhase`，不需要把计时器对象传来传去。
3. **嵌套深度感知**。通过 `depth` 字段，输出报告时可以自动缩进，让读者一目了然地看到哪些操作是并列的、哪些是嵌套的。

### 5.3 案例 3：事务上下文管理

在数据库操作中，"事务"是一个核心概念——一组操作要么全部成功，要么全部回滚。传统的事务管理通常需要将事务连接对象（connection/transaction）层层传递。AsyncLocalStorage 可以让这个过程变得透明：

```javascript
const { AsyncLocalStorage } = require('node:async_hooks');
const txContext = new AsyncLocalStorage();

/**
 * 简化的事务管理器
 * 利用 ALS 隐藏事务连接的传递
 */
class TransactionManager {
    /**
     * 在事务中执行操作
     */
    static async transaction(fn) {
        const connection = await getConnectionFromPool();
        await connection.beginTransaction();
        
        try {
            // 将连接放入 ALS 上下文
            const result = await txContext.run(
                { connection, committed: false, rollbackOnly: false },
                fn
            );
            
            await connection.commit();
            txContext.getStore().committed = true;
            return result;
        } catch (error) {
            await connection.rollback();
            throw error;
        } finally {
            connection.release();
        }
    }

    /**
     * 在事务内获取当前连接
     */
    static getConnection() {
        const ctx = txContext.getStore();
        if (!ctx) {
            throw new Error('No active transaction context');
        }
        return ctx.connection;
    }

    /**
     * 标记事务为仅回滚
     */
    static setRollbackOnly() {
        const ctx = txContext.getStore();
        if (ctx) ctx.rollbackOnly = true;
    }
}

// ============================================================
// 数据仓库层 —— 无需接收 connection 参数！
// ============================================================
const UserRepository = {
    async findById(id) {
        const conn = TransactionManager.getConnection();
        const [rows] = await conn.execute('SELECT * FROM users WHERE id = ?', [id]);
        return rows[0];
    },

    async update(id, fields) {
        const conn = TransactionManager.getConnection();
        const sets = Object.keys(fields).map(k => `${k} = ?`).join(', ');
        const values = [...Object.values(fields), id];
        await conn.execute(`UPDATE users SET ${sets} WHERE id = ?`, values);
    }
};

const OrderRepository = {
    async create(userId, amount) {
        const conn = TransactionManager.getConnection();
        const [result] = await conn.execute(
            'INSERT INTO orders (user_id, amount) VALUES (?, ?)',
            [userId, amount]
        );
        return result.insertId;
    },

    async deductBalance(userId, amount) {
        const conn = TransactionManager.getConnection();
        await conn.execute(
            'UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?',
            [amount, userId, amount]
        );
    }
};

// ============================================================
// 业务服务层
// ============================================================
async function placeOrder(userId, orderAmount) {
    return TransactionManager.transaction(async () => {
        // 检查用户余额
        const user = await UserRepository.findById(userId);
        if (user.balance < orderAmount) {
            TransactionManager.setRollbackOnly();
            throw new Error('Insufficient balance');
        }

        // 扣减余额
        await OrderRepository.deductBalance(userId, orderAmount);

        // 创建订单
        const orderId = await OrderRepository.create(userId, orderAmount);

        return { orderId, remainingBalance: user.balance - orderAmount };
    });
}

// 执行
placeOrder('user-42', 99.99)
    .then(result => console.log('Order placed:', result))
    .catch(err => console.error('Order failed:', err.message));
```

这个案例展示了 AsyncLocalStorage 在架构层面的影响力：

- **Repository 层完全不感知事务的存在。** `UserRepository.findById` 不知道自己正在一个事务中被调用——它只是简单地从 ALS 中获取连接并执行 SQL。如果将来需要改为无事务的普通查询（直接从连接池拿连接），Repository 代码完全不需要改。
- **事务边界清晰可见。** `TransactionManager.transaction()` 明确地标示了事务的开始和结束，所有的数据库操作都被包裹在其中。
- **条件回滚支持。** 通过 `setRollbackOnly()`，可以在事务深处的业务逻辑中发现问题时标记回滚，而不需要抛出异常来中断流程。

这种模式在一些 ORM 框架（如 TypeORM、Prisma）和依赖注入容器（如 NestJS）中有广泛的应用。它们底层的实现思路都与上述示例类似——通过某种形式的上下文存储来管理事务连接的传递。

> **哲学思考**：这三个案例分别代表了 AsyncLocalStorage 应用的三个层次维度。**日志追踪是信息的维度**——它解决的问题是如何让"元数据"（谁在什么时候做了什么）自动流动，不污染业务逻辑。**性能度量是时间的维度**——它解决的问题是如何在不干扰执行流程的前提下精准地测量每一个环节的耗时，就像在暗处安放的传感器。**事务管理是状态的维度**——它解决的问题是如何让多个离散的操作共享一个一致的状态视图，要么一起成功要么一起失败。
>
> 三个维度对应着人类认知世界的三种基本方式：**叙事（Narrative）**——事情按什么顺序发生（日志）；**度量（Measurement）**——事情花了多少资源（性能）；**一致性（Consistency）**——事情的整体状态是否协调（事务）。AsyncLocalStorage 作为一个通用的基础设施，能够同时支撑这三个维度的需求，这正是它比那些只解决单一问题的方案（如全局变量、参数传递）更加强大的原因。

## 六、AsyncContext——走向 ECMAScript 标准的未来

AsyncLocalStorage 虽然强大，但它目前仍然是 **Node.js 特有的运行时 API**，而不是 JavaScript 语言规范的一部分。浏览器环境、Deno、Bun 以及其他 JavaScript 运行时并没有原生的 ALS 实现（虽然有 polyfill）。为了将这一能力提升到语言标准层面，TC39（ECMAScript 标准委员会）正在推进 **AsyncContext 提案**。

### 6.1 提案现状与定位

截至本文写作时，**AsyncContext 提案处于 TC39 Stage 2（草案阶段）**，由 Chengzhong Wu（阿里巴巴）和 Justin Ridgewell 主导推进。Stage 2 意味着提案已被委员会正式接受，规范文本初步完成，但尚未进入候选阶段（Stage 3）和最终定稿（Stage 4）。

提案的目标很明确：**定义一套标准的 ECMAScript API，使得 JavaScript 开发者能够在异步调用链中可靠地传递和访问上下文数据，且该能力由引擎级别提供保证，而非依赖于某个运行时的特殊实现。**

一旦 AsyncContext 成为标准：
- **浏览器端**可以直接使用（不再需要 Zone.js 等库来模拟）
- **Deno/Bun/Cloudflare Workers** 等现代运行时会原生支持
- **所有 JavaScript 引擎**（V8、SpiderMonkey、JavaScriptCore）的行为保持一致
- **工具链**（TypeScript 类型定义、调试器支持、lint 规则）可以围绕标准 API 构建

### 6.2 核心设计：Variable 与 Snapshot

AsyncContext 提案的 API 设计与现有的 AsyncLocalStorage 有相似之处，但在概念模型上有重要的升级：

#### AsyncContext.Variable——独立的上下文变量

```javascript
// AsyncContext 提案的设计（Stage 2 Draft）
// 注意：以下是提案语法，目前尚无引擎原生支持

// 创建一个命名的上下文变量
const traceId = new AsyncContext.Variable({
    name: 'com.example.trace-id',
    defaultValue: undefined
});

const userId = new AsyncContext.Variable({
    name: 'com.example.user-id',
    defaultValue: 'anonymous'
});

// 在某个作用域中设置值
traceId.run('abc-123-def', () => {
    console.log(traceId.get());  // 'abc-123-def'
    
    userId.run('user-42', () => {
        console.log(traceId.get());  // 'abc-123-def' —— 变量之间独立共存
        console.log(userId.get());   // 'user-42'
        
        // 异步操作自动继承
        setTimeout(() => {
            console.log(traceId.get());  // 'abc-123-def' ✅
            console.log(userId.get());   // 'user-42' ✅
        }, 100);
    });
    
    // userId 的作用域已结束
    console.log(userId.get());  // 'anonymous'（defaultValue）
});
```

AsyncContext.Variable 的设计理念与 AsyncLocalStorage 有一个根本性的区别：

| 维度 | AsyncLocalStorage | AsyncContext.Variable |
|------|-------------------|---------------------|
| **存储模型** | 单一 Store 对象（一个桶装所有东西） | 多个独立 Variable（每种数据一个专用容器） |
| **值访问方式** | `als.getStore()` 返回整个 store 对象 | `variable.get()` 直接返回该变量的值 |
| **类型安全性** | 需要自行约束 store 的形状 | 每个 Variable 可以在泛型中声明类型 `<T>` |
| **默认值支持** | 需要手动判断 `undefined` | 构造时可声明 `defaultValue` |
| **命名/调试** | 无内置标识 | 内置 `name` 属性用于调试 |

这种"多独立变量"的模型更符合现代 JavaScript 的声明式风格。你不再需要维护一个大而杂的 store 对象，而是为每种上下文信息声明一个专用的 Variable 实例。这不仅提高了代码的可读性，也让 TypeScript 的类型推断更加精准。

#### AsyncContext.Snapshot——一等公民的快照

```javascript
// Snapshot 在 AsyncContext 提案中是一等公民（不像 ALS 的 snapshot 是后来加的）

function captureContext() {
    // 创建当前所有 Variable 值的快照
    const snapshot = new AsyncContext.Snapshot();
    
    // snapshot 可以序列化、存储、传输
    return snapshot;
}

// 在任何地方恢复快照
function executeWithContext(snapshot, fn) {
    return snapshot.run(fn);
}

// 静态方法 wrap：将函数绑定到快照
const wrappedFn = AsyncContext.Snapshot.wrap(originalFn);
```

在 AsyncContext 提案中，Snapshot 不再是 AsyncLocalStorage 的附属品，而是一个与 Variable 平等的、拥有完整 API 的核心抽象。这反映了社区在过去几年使用 ALS 过程中获得的一个经验：**快照/恢复的能力和变量存取的能力同等重要**，不应该被视为次要功能。

### 6.3 异步边界传播规则

AsyncContext 提案的规范文档详细定义了各种异步边界下的上下文传播行为。这是一项至关重要的工作——因为只有引擎级别的保证才能消除"上下文会不会在某处丢失"的疑虑：

```javascript
// 提案规定的传播规则摘要

// 1. Promise .then()/.catch()/.finally()
//    → 创建 reaction 时自动快照当前上下文
//    → 执行 reaction job 时自动恢复快照的上下文
Promise.resolve().then(() => {
    variable.get();  // ✅ 恿创建 .then() 时的值
});

// 2. Generator yield
//    → 恢复生成器启动时的上下文映射
function* gen() {
    variable.get();  // ✅ 恿 gen() 调用时的值
}

// 3. AsyncGenerator yield
//    → 同上，支持异步生成器
async function* asyncGen() {
    variable.get();  // ✅ 恿 asyncGen() 调用时的值
}

// 4. yield* 委托迭代
//    → 每次 next() 后恢复原始调用者的上下文

// 5. FinalizationRegistry 回调
//    → 使用注册时的上下文执行清理

// 6. 模块顶层执行
//    → 空上下文映射隔离（不同模块互不干扰）
```

这些规则的制定经过了大量的讨论和实验。每一个异步原语（Promise、Generator、AsyncGenerator、FinalizationRegistry）都有自己的执行模型，AsyncContext 必须找到一种与每种模型兼容的集成方式，而不能破坏现有的语义。

### 6.4 与其他语言的对比

"异步本地存储"这个概念并非 JavaScript 独创。几乎所有主流编程平台都有类似的机制：

```java
// Java —— ThreadLocal
private static final ThreadLocal<UserContext> currentUser =
    ThreadLocal.withInitial(() -> new UserContext());

public void handleRequest(HttpServletRequest req) {
    currentUser.set(new UserContext(extractUserId(req)));
    try {
        processRequest();  // 内部可通过 currentUser.get() 获取
    } finally {
        currentUser.remove();  // 必须手动清理！
    }
}
```

```python
# Python —— threading.local
import threading

thread_data = threading.local()

def handle_request(request):
    thread_data.user_id = extract_user_id(request)
    process_request()  # 内部可通过 thread_data.user_id 获取
```

```go
// Go —— context.Context（最优雅的设计之一）
func HandleRequest(w http.ResponseWriter, r *http.Request) {
    ctx := context.WithValue(r.Context(), "userID", extractUserID(r))
    
    // Go 的惯例是把 ctx 作为第一个显式参数传递
    // 这是 Go 社区的一种文化选择，而非技术限制
    processData(ctx)
}
```

对比这些实现，可以发现一个有趣的规律：

- **多线程语言**（Java、Python）的实现基于操作系统线程作为隔离单位，简单直接
- **协程语言**（Go）选择了显式传递 `context.Context` 作为第一个参数的文化惯例
- **JavaScript（单线程事件循环）** 需要一套完全不同的机制——基于异步资源树（async resource tree）的隐式传播

Go 语言的设计特别值得一提。虽然 Go 也支持协程（goroutine）并发，但 Go 社区选择了**显式传递 context**而非隐式上下文。这是因为 Go 的创始人 Rob Pike 等人认为"显式优于隐式"（Explicit is better than implicit）——你应该清楚地看到函数依赖了哪些上下文信息，而不是通过某种魔法在背后传递。

这是一个合理的设计哲学争论。JavaScript 社区的选择（隐式传播）更多是出于实用性考虑：JavaScript 的回调嵌套已经很深了，如果再加上 context 参数，代码的可读性会进一步下降。而且 JavaScript 的动态特性和灵活的闭包机制使得隐式上下文在实践中更加自然。

> **哲学思考**：AsyncContext 提案的出现标志着一个重要趋势——**Node.js 的创新正在反向推动 ECMAScript 标准的发展。** 历史上，通常是 ECMA 先制定标准，然后各运行时（浏览器、Node.js）跟进实现。但 AsyncContext 的故事相反：先是 Node.js 社区在实践中发现了异步上下文传递的迫切需求，经历了 CLS、cls-hooked、async_hooks、AsyncLocalStorage 几代探索，最终沉淀出了一个成熟的设计。然后这个设计被提交给 TC39，有望成为所有 JavaScript 环境共享的语言标准。
>
> 这种"实践驱动标准化"的模式值得深思。它说明了**好的标准往往不是在设计室里空想出来的，而是在真实的战场中磨砺出来的。** AsyncLocalStorage 经历了几年的生产验证——被 Express、Fastify、NestJS、Prisma 等主流框架广泛采用——它的 API 设计、边界行为、性能特征都是在真实负载下检验过的。AsyncContext 提案站在了这个巨人的肩膀上，因此有更大的机会成为一个经得起时间考验的好标准。

## 七、最佳实践与避坑指南

掌握 API 只是第一步。在生产环境中正确、安全、高效地使用 AsyncLocalStorage，还需要注意一系列工程实践方面的问题。

### 7.1 Store 数据的选择原则

Store 中应该放什么、不该放什么？这看似是个小问题，但直接影响系统的可维护性和性能：

```javascript
// ✅ 推荐放入 Store 的数据类型

// 1. 不可变的元数据（Immutable Metadata）
{ traceId: 'abc-123', requestId: 'req-456', startTime: 1705000000000 }

// 2. 小型的标识符（Small Identifiers）
{ userId: 'user-42', sessionId: 'sess-99', tenantId: 'tenant-1' }

// 3. 配置标志位（Configuration Flags）
{ debugMode: false, featureFlags: { newCheckout: true }, logLevel: 'info' }


// ❌ 不建议放入 Store 的数据类型

// 1. 大型对象或数组（Large Objects）
{ requestBody: hugePayload, queryResults: [/* thousands */] }
// → 原因：store 会随异步调用链一直存活，大对象占用内存时间长

// 2. 可变的状态引用（Mutable Shared State）
{ sharedArray: someGlobalArray, eventEmitter: globalEmitter }
// → 原因：可能导致意外的副作用和内存泄漏

// 3. 敏感信息（Sensitive Data）
{ password: 'secret123', creditCard: '4111111111111111' }
// → 原因：store 可能被日志系统意外序列化输出
```

**黄金法则：Store 应该是轻量的、不可变的、安全的。** 把它当作"请求的身份证"而非"请求的手提箱"——身份证上只有姓名、照片、编号等关键标识信息，不会塞进去一堆行李。

### 7.2 内存泄漏防范

AsyncLocalStorage 的内存管理需要特别注意以下几个场景：

```javascript
// 危险模式 1：长期运行的定时器持有上下文
als.run({ heavyData: largeObject }, () => {
    // 这个 setInterval 永远不会停止
    setInterval(() => {
        doSomething();
    }, 60000);  // 每分钟执行
    
    // → heavyObject 将永远不会被 GC 回收！
    // → 因为 setInterval 保持了对回调的引用
    // → 回调持有的闭包包含了 store 的引用
});

// 安全做法：为长时间运行的定时器单独处理
function setupPeriodicTask(taskFn, interval) {
    // 不要在 run 内部创建持久的定时器
    // 或者使用 snapshot 只提取需要的数据
    const minimalCtx = extractMinimalContext(als.getStore());
    
    setInterval(() => {
        taskFn(minimalCtx);  // 只传递必要的数据，不保留 store 引用
    }, interval);
}


// 危险模式 2：EventEmitter 大量监听器累积
als.run({ ctx: data }, () => {
    const emitter = getSharedEmitter();
    
    // 每次请求都添加一个监听器，但从不移除
    emitter.on('some-event', handler);
    // → 监听器和它的闭包（包含 store 引用）永远不会被释放
});

// 安全做法：使用 once() 或及时 removeListener()
als.run({ ctx: data }, () => {
    const emitter = getSharedEmitter();
    
    function handler() { /* ... */ }
    emitter.once('response-for-this-request', handler);  // 自动移除
    // 或者
    emitter.on('response', handler);
    // 在请求结束后
    cleanupQueue.push(() => emitter.removeListener('response', handler));
});


// 危险模式 3：闭包逃逸
let escapedFn = null;

als.run({ sensitiveData: 'secret' }, () => {
    // 把一个持有 store 引用的函数"逃逸"出去
    escapedFn = () => als.getStore();
});

// 即使 run 已经结束了
// escapedFn 中的闭包仍然持有对 store 的引用
// （虽然此时 getStore() 返回 undefined，但 store 对象本身可能未被回收）
```

防范内存泄漏的核心原则是：**注意异步操作的生存周期是否超出了请求的正常生命周期。** 如果一个 setTimeout/setInterval/事件监听器的生命期远超过了一次请求的预期时长，就需要格外警惕上下文数据的持有情况。

### 7.3 调试技巧

当 `getStore()` 返回 `undefined` 但你不应该出现这种情况时，可以使用以下调试策略：

```javascript
/**
 * 调试辅助器：在可疑位置检测上下文是否存在
 */
function assertContext(location) {
    const store = requestContext.getStore();
    if (!store) {
        console.warn(`⚠️ Context lost at: ${location}`);
        console.warn(`   Call stack:\n${new Error().stack}`);
        // 可以在这里设置断点进行调试
    }
    return store;
}

// 使用方式：在关键位置插入断言
async function suspiciousFunction() {
    assertContext('suspiciousFunction-entry');  // 入口检查
    
    await someThirdPartyLibraryCall();
    
    assertContext('suspiciousFunction-after-call');  // 调用后检查
    // 如果这里丢了上下文，那一定是 thirdPartyLibrary 的问题
}
```

另一种有效的调试方式是**包装怀疑的第三方库调用**：

```javascript
/**
 * 包装一个异步函数，在前后检测上下文
 */
function withContextCheck(fn, name) {
    return (...args) => {
        const before = !!requestContext.getStore();
        const result = fn.apply(null, args);
        
        if (result && typeof result.then === 'function') {
            return result.then(
                val => {
                    const after = !!requestContext.getStore();
                    if (before && !after) {
                        console.warn(`🔴 Context lost after: ${name} (resolved)`);
                    }
                    return val;
                },
                err => {
                    const after = !!requestContext.getStore();
                    if (before && !after) {
                        console.warn(`🔴 Context lost after: ${name} (rejected)`);
                    }
                    throw err;
                }
            );
        }
        return result;
    };
}

// 使用
const safeDbQuery = withContextCheck(db.query.bind(db), 'db.query');
```

### 7.4 性能考量

AsyncLocalStorage 基于 `async_hooks` 实现，虽然经过了大量优化（特别是 Node.js v16+ 使用 V8 的 PromiseHook API 重构后性能显著提升），但仍有一定的开销：

| 操作 | 开销级别 | 说明 |
|------|---------|------|
| `run()` 调用 | 低 | 创建新的异步上下文映射，O(1) 操作 |
| `getStore()` 调用 | 极低 | 读取当前上下文指针，接近零开销 |
| 上下文切换（异步边界） | 低~中 | 每次 Promise.then/setTimeout 等都需要保存/恢复上下文 |
| `snapshot()` 调用 | 低 | 复制当前上下文映射的引用 |

**一般性建议：**
- 对于普通 Web 应用（QPS < 10000），ALS 的开销可以忽略不计
- 对于高吞吐量场景（QPS > 50000），建议进行基准测试以量化影响
- 避免在热循环（hot loop）中频繁调用 `run()` —— 虽然 `run()` 本身不贵，但不必要的上下文切换会增加 GC 压力
- `getStore()` 几乎没有性能成本，可以放心地在日志等高频调用的地方使用

## 八、总结：异步上下文的心智模型

### 8.1 技术体系总览

| 技术 | 层级 | 状态 | 适用场景 |
|------|------|------|---------|
| 全局变量 | 应用层 | ❌ 反模式 | 不推荐在任何场景使用 |
| 参数透传 | 应用层 | ✅ 可用但侵入性强 | 小型项目、快速原型 |
| CLS (continuation-local-storage) | 社区库 | ⚠️ 已过时 | 仅遗留系统维护 |
| async_hooks | Node.js 内部 API | ⚠️ 实验性 | APM 工具、性能分析器开发者 |
| **AsyncLocalStorage** | **Node.js 运行时 API** | **✅ 稳定（v13.10+）** | **当前生产环境的首选方案** |
| **AsyncContext (TC39 提案)** | **ECMAScript 语言标准** | **⚠️ Stage 2（草案）** | **未来的跨平台标准方案** |

### 8.2 选择决策指南

```
你需要传递异步上下文吗？
│
├─ 否 → 本文的内容暂时与你无关（但了解一下也没坏处）
│
└─ 是 → 你的运行环境是什么？
    │
    ├─ 纯 Node.js 服务端
    │   └─ ✅ 直接使用 AsyncLocalStorage（稳定、成熟、生态完善）
    │
    ├─ 需要跨平台（Node.js + 浏览器 + Workers）
    │   └─ ⚠️ 目前选择：
    │       ├─ Node.js 端用 AsyncLocalStorage
    │       ├─ 浏览器端用 Zone.js（Angular 生态）或 CLS polyfill
    │       └─ 关注 AsyncContext 提案进展，期待未来统一
    │
    └─ 需要在对象生命周期跨越 run 边界时保持上下文
        └─ 选择：
            ├─ 简单场景 → AsyncLocalStorage.snapshot()
            ├─ 函数绑定场景 → AsyncLocalStorage.bind()
            └─ 复杂生命周期管理 → AsyncResource + runInAsyncScope()
```

### 8.3 核心概念的类比总结

如果把异步上下文的整套技术体系讲给一个非技术人员听，我会这样说：

> 想象你是一家大型商场的安保主管。每天有成千上万的顾客进出商场，你需要确保每一位顾客从进门到离开的全过程都是**可追溯的**——他们在哪家店买了东西？有没有在停车场发生纠纷？有没有遗失物品？
>
> **全局变量方案**就像是只在商场门口放一块白板。每位顾客进门时在上面写下自己的名字（擦掉上一位的）。等到顾客在三楼买完东西想确认身份时，白板上写的已经是别人的名字了。
>
> **参数透传方案**就像是给每位顾客发一本厚厚的《通行证册》。他们要去每家店、坐电梯、上厕所都要出示这本册子并在上面盖章。安全是安全了，但顾客体验极差，而且经常有人忘了带册子。
>
> **AsyncLocalStorage 方案**就像是给每位顾客佩戴一张**智能腕带**。进门时自动激活，上面显示着顾客的唯一编号和基本信息。之后无论顾客走到哪里——商店、电梯、餐厅——任何感应器都能读取腕带信息。顾客不需要做任何事情，商家也不需要额外检查证件。当顾客离开商场走出大门时，腕带自动失效。下一位顾客会得到属于自己的全新腕带。
>
> 这张智能腕带就是 AsyncLocalStorage 为每次请求创建的**异步上下文空间**——它跟随请求流动，对所有参与者透明可见，在不同请求之间严格隔离，随请求结束而自动消亡。

### 8.4 最后的思考

异步上下文技术解决的不仅仅是一个工程问题——它反映的是 JavaScript 作为一门语言的独特挑战。JavaScript 的单线程事件循环模型赋予了它简洁的并发模型（不需要担心锁、死竞态条件），但也剥夺了多线程语言中那种天然的"线程局部存储"能力。Node.js 社区花了近十年时间，经历了 CLS → async_hooks → AsyncLocalStorage 的迭代演进，才找到了一个足够好用的答案。而现在，这个答案正试图通过 TC39 的 AsyncContext 提案成为所有 JavaScript 环境的共同财富。

在这个过程中，我们可以观察到几个有趣的现象：

**第一，隐式上下文是一种强大的抽象力量。** 就像空气压力一样——你感觉不到它的存在，但它实实在在地影响着一切。好的隐式上下文系统能够大幅减少样板代码，降低组件间的耦合度，让开发者聚焦于真正的业务逻辑。但同时，隐式的东西也更难调试——当上下文意外丢失时，你面对的是一片沉默的 `undefined`，而非清晰的编译错误。

**第二，标准化需要实践的土壤。** AsyncContext 提案之所以有希望成为好标准，是因为 AsyncLocalStorage 已经在真实世界中证明了这类能力的价值。标准不是空中楼阁——它是对最佳实践的提炼和固化。

**第三，技术的进步往往是螺旋上升的。** 从最初粗糙的全局变量方案，到侵入性强的参数透传，到底层的 async_hooks，再到高层封装的 AsyncLocalStorage，最终迈向标准化的 AsyncContext——每一步都在解决前一步遗留的问题，同时也会引入新的挑战。没有一步是"最终答案"，但每一步都比上一步更好。
