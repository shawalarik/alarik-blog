# 近期TC39提案汇总 —— JavaScript 进化的全景图谱

> **核心内容**：本文以 TC39 提案体系为线索，系统梳理 JavaScript 从 ES2024 到未来各阶段的演进全貌。从已落地的 Stage 4 特性（装饰器、Temporal、显式资源管理），到蓄势待发的 Stage 3 候选（Import Attributes、RegExp.escape、Promise.try），再到充满想象力的 Stage 2 前沿探索（Records & Tuples、Pipeline Operator、模式匹配、ShadowRealm），逐一拆解每个提案的设计动机、技术细节与哲学内涵。

---

## 一、认识 TC39：JavaScript 的"立法机构"

### 1.1 谁在决定 JavaScript 的未来？

如果你使用 JavaScript 已经有一段时间，你一定经历过这种感受：突然某一天，你发现一个从未见过的语法糖出现在别人的代码里；某个你手动实现了好几次的工具函数，居然变成了原生方法；或者你苦心研究的某种编程模式，被语言本身直接支持了。

这些变化不是随机发生的，也不是某个人拍脑袋决定的。它们来自 **TC39（Technical Committee 39）**——ECMA International 下属的一个技术委员会。这个由浏览器厂商代表（Chrome 的 V8 团队、Firefox 的 SpiderMonkey 团队、Safari 的 JavaScriptCore 团队）、学术界研究者、独立开发者共同组成的团体，每两个月召开一次会议，审议和推进各种 ECMAScript（即 JavaScript 的正式名称）标准提案。

```javascript
// 你可能不知道的是：你现在习以为常的这些特性，
// 每一个都经历了 TC39 严格的审议流程：

const arrow = () => {};           // 箭头函数 — ES2015, 2015年落地
const promise = Promise.resolve(); // Promise — ES2015
async function foo() {}           // async/await — ES2017
const arr = [1, 2, 3].flatMap(x => [x, x]); // flatMap — ES2019
arr.groupBy(x => x > 1);          // groupBy — ES2024
```

理解 TC39 的工作方式，就像理解一个国家的立法过程。每一项新语法的加入，都需要经过充分的讨论、实验、反馈和修正。这既保证了语言的稳定性（不会随意引入破坏性变更），也意味着真正的创新需要耐心等待——一个提案从诞生到成为标准，通常需要 **3 到 5 年**甚至更久。

### 1.2 五阶段流程：一个提案的"生命周期"

TC39 采用了一套严格的五阶段流程来管理提案的演进。这套流程就像是一个产品的完整研发周期——从概念验证到市场发布，每一步都有明确的质量门禁：

| 阶段 | 名称 | 含义 | 类比 |
|------|------|------|------|
| **Stage 0** | Strawman（稻草人） | 一个想法的初步记录，允许任何人提出 | 在咖啡馆里随手画的产品草图 |
| **Stage 1** | Proposal（提案） | 有价值的想法，有 Champion 推进，描述了问题和大致方案 | 产品立项书，获得初步认可 |
| **Stage 2** | Draft（草案） | 完成正式规范初稿，包含语法和语义的形式化描述 | 详细设计文档 + 原型 Demo |
| **Stage 2.7** | Near Review（接近审查） | *新增阶段*，强制要求完成测试用例编写 | 内部 QA 验收通过 |
| **Stage 3** | Candidate（候选） | 规范基本完成，实现者和用户开始试验性采用 | Beta 版发布，收集反馈 |
| **Stage 4** | Finished（完成） | 通过所有测试，将在下一个版本中正式发布 | 正式版 GA（General Availability） |

> **特别说明 Stage 2.7**：这是 TC39 在近期引入的一个新阶段，位于 Stage 2 和 Stage 3 之间。它的存在反映了一个深刻的教训——历史上曾有多位提案在进入 Stage 3 之后才发现重大缺陷，被迫回退。Stage 2.7 要求在进入候选阶段之前必须完成 Test262 测试套件的编写和验证，相当于给提案加了一道"安全网"。

```javascript
// 以 Decorators（装饰器）为例，看一个提案的典型时间线：
//
// 2015-04  TypeScript 1.5 引入实验性装饰器（基于旧版 Stage 1 提案）
// 2016-07  提案进入 Stage 2（草案）
// 2018-07  完全重写，新的 Class Fields 语义导致旧方案不可行
// 2019-03  新版提案进入 Stage 2
// 2022-03  进入 Stage 3（候选）
// 2023-03  仍在 Stage 3，继续打磨规范细节
// 2024-xx  进入 Stage 4，成为 ES2025 标准的一部分
//
// 从最初的想法到最终标准化，跨越了将近十年。
```

### 1.3 生活类比：城市交通法规的修订

如果把 JavaScript 想象成一个不断扩张的城市：

- **Stage 0** 是市民在社区论坛上发帖说"我觉得这里应该修一座桥"——只是一个想法，还没有任何正式程序。
- **Stage 1** 是市政厅觉得这个想法有道理，成立了专门的工作组来调研可行性。
- **Stage 2** 是工作组拿出了详细的桥梁设计方案（图纸、材料清单、预算估算），开始征求各方意见。
- **Stage 2.7** 是工程队按照图纸搭了一个模型，进行了风洞测试和结构强度验证。
- **Stage 3** 是桥梁开始试通车，允许市民体验并提出改进意见。
- **Stage 4** 是桥梁正式验收通车，成为城市基础设施的一部分。

这个类比揭示了 TC39 流程的核心哲学：**宁可慢一点，也不要犯错**。一旦一项语法进入了 Stage 4，它就成为了 Web 平台的永久组成部分——数以亿计的网站依赖于它，浏览器必须永远支持它。因此，谨慎不是缺点，而是必要的美德。

### 1.4 哲学思考：共识的价值

TC39 的多利益相关方模型体现了一种深刻的政治哲学：**重要的决策应该经过广泛的协商，而非独裁式的命令**。

这与很多其他编程语言的演进模式形成了鲜明对比。Python 有 BDFL（仁慈的终身独裁者 Guido van Rossum），Go 语言有一个小型的核心团队做最终裁决，Rust 有 RFC 流程但决策权相对集中。而 TC39 的每一次会议都有数十名来自不同公司的代表参与辩论——Google、Mozilla、Apple、Microsoft、Node.js 社区、学术界……

这意味着：
1. **没有单一公司可以主导 JavaScript 的方向**（虽然 Google 因 Chrome 的市场份额拥有事实上的巨大影响力）
2. **每一个提案都必须考虑多种运行环境的需求**（浏览器 vs Node.js vs 嵌入式设备）
3. **向后兼容是最高优先级之一**——Web 上已有的代码不能因为新特性而崩溃

当然，这种共识机制也有代价：速度慢、妥协多、有时会产生"设计委员会"式的平庸结果。但考虑到 JavaScript 运行在全球超过 **30 亿台设备**上，这种谨慎或许是值得的。

## 二、已落地的果实：近期 Stage 4 提案巡礼

当一个提案到达 Stage 4，就意味着它已经通过了所有关卡，即将或已经随某个 ECMAScript 版本正式发布。以下是近年来最值得关注的已完成提案。

### 2.1 装饰器（Decorators）：元编程的标准化

装饰器可能是近年来最受关注的提案之一，因为它直接改变了大量开发者（尤其是 TypeScript 和框架用户）的编码方式。

**核心思想**：装饰器是一种声明式语法，让你可以在不修改原有代码的前提下，为类、方法、属性、访问器添加额外的行为。它本质上是**高阶函数**的语法糖，但其威力在于将"横切关注点"（cross-cutting concerns）从业务逻辑中剥离出来。

```javascript
// ===== 基础用法 =====

@logged
class UserService {
  @readonly
  @validate
  name = 'default';

  @measurePerformance
  createUser(data) {
    return { id: Date.now(), ...data };
  }
}

function logged(target) {
  console.log(`[Class] Registering: ${target.name}`);
}

function readonly(target, context) {
  context.addInitializer(function() {});
  return function(initialValue) {
    return { get() { return initialValue; } };
  };
}
```

**为什么装饰器如此重要？** 它解决了一个普遍存在的代码组织问题：当多个方法需要共享同一种"横切行为"时（如日志、权限校验、缓存、性能度量），传统做法会导致大量重复代码。装饰器将这些行为提取为可复用的、可组合的声明式注解，让业务逻辑保持纯净。

> 更多关于装饰器的深度解析，请参阅 [《ES2025 提案》](/40.frontend/50.javascript/10.language-async/60.最新特性与提案/480.ES2025提案.md) 一文。

### 2.2 Temporal API：终结 Date 对象的时代

如果让 JavaScript 开发者投票选出"最令人沮丧的原生 API"，`Date` 对象大概率会高票当选。它的问题太多了：mutable 导致意外副作用、不支持国际化、时区处理一团混乱、API 设计不一致……

**Temporal API** 是对日期时间处理的彻底重新设计。它引入了一整套全新的类型系统，明确区分了不同的时间概念：

```javascript
// PlainDate — 只有日期，无时间，无时区
const date = Temporal.PlainDate.from('2026-04-22');
date.add({ days: 30 });        // → 2026-05-22（不可变！返回新对象）
date.year;                     // → 2026
date.dayOfWeek;                // → 3（星期三）

// ZonedDateTime — 最完整的类型：日期+时间+时区
const zdt = Temporal.ZonedDateTime.from(
  '2026-04-22T15:30:00+08:00[Asia/Shanghai]'
);
zdt.toInstant();               // 转换为 UTC 绝对时刻
zdt.withTimeZone('America/New_York');

// Duration — 时间跨度/时长
const duration = Temporal.Duration.from({ hours: 2, minutes: 30 });

// 时长比较 — 自动处理闰年等复杂情况
const d1 = Temporal.PlainDate.from('2026-01-01');
const d2 = Temporal.PlainDate.from('2026-03-01');
d1.until(d2);                  // → P59D（59天）

// Compare — 解决排序痛点
const dates = ['2024-06-15', '2023-12-01', '2025-03-20']
  .map(s => Temporal.PlainDate.from(s));
dates.sort((a, b) => Temporal.PlainDate.compare(a, b));
```

Temporal 的设计哲学可以概括为一句话：**显式优于隐式**。旧的 `Date` 对象把太多概念混在一起——一个 `new Date()` 既可能表示本地时间，也可能表示 UTC 时间。而 Temporal 强制你明确声明你要处理的是哪种类型的时间数据，从根本上杜绝了时区相关的各类 bug。

### 2.3 显式资源管理（Explicit Resource Management）：using 关键字

这是一个看似简单却影响深远的提案。它引入了 `Symbol.dispose` / `Symbol.asyncDispose` 以及 `using` / `await using` 关键字：

```javascript
{
  using file = new FileHandler('./data.txt');
  // 使用 file...
} // ← file[Symbol.dispose]() 自动调用

class FileHandler {
  #handle;
  constructor(path) {
    this.#handle = fs.openSync(path, 'r');
  }
  [Symbol.dispose]() {
    if (this.#handle !== undefined) {
      fs.closeSync(this.#handle);
      this.#handle = undefined;
    }
  }
}

// 异步版本
{
  await using conn = new DatabaseConnection('postgres://localhost/mydb');
  const users = await conn.query('SELECT * FROM users');
} // ← conn[Symbol.asyncDispose]() 自动调用
```

**生活类比**：租借共享充电宝。using 关键字就像是机柜的智能检测功能——当你走出覆盖范围时，系统自动帮你归还。这不仅减少了样板代码，更**消除了人为失误的可能性**——你不可能忘记释放资源，因为语言本身替你记住了。

### 2.4 Import Attributes & JSON Modules：模块导入的安全升级

```javascript
import config from './config.json' with { type: 'json' };
const data = await import('./data.json', {
  with: { type: 'json' }
});
```

`with` 子句告诉运行时期望模块的类型。如果实际类型不符则导入失败——这是**防御性编程**的语言级支持。

### 2.5 RegExp Modifiers：正则表达式的细粒度控制

```javascript
// 首字母忽略大小写，后续字母严格匹配
const reNew = /^[a-z](?-i:[a-z])+$/i;
reNew.test('Abc');   // true  — A 被 i 忽略，bc 严格
reNew.test('aBC');   // false — BC 不满足
```

更多正则知识请参考 [《基础元字符与量词》](/40.frontend/50.javascript/10.language-async/50.正则表达式/440.基础元字符与量词.md)、[《分组与引用》](/40.frontend/50.javascript/10.language-async/50.正则表达式/450.分组与引用.md)。

### 2.6 Iterator Helpers：迭代器的"数组方法化"

```javascript
function* naturalNumbers() {
  let i = 1;
  while (true) yield i++;
}

naturalNumbers()
  .filter(n => n % 2 === 0)
  .map(n => n * n)
  .take(5)
  .toArray();
  // → [4, 16, 36, 64, 100]

// 关键优势：惰性求值
// 无限序列 + 零内存占用（逐个处理）
```

**惰性求值（Lazy Evaluation）**：调用 `.filter()` / `.map()` 时不会立即遍历，而是创建新迭代器，在消费时才逐个处理。这意味着你可以对**无限序列**进行操作。

### 2.7 Set Methods：集合运算的首次原生支持

```javascript
const A = new Set([1, 2, 3, 4]);
const B = new Set([3, 4, 5, 6]);

A.union(B);              // → Set {1, 2, 3, 4, 5, 6}
A.intersection(B);       // → Set {3, 4}
A.difference(B);         // → Set {1, 2}
A.symmetricDifference(B);// → Set {1, 2, 5, 6}
A.isSubsetOf(B);         // → false
A.isDisjointFrom(B);     // → false
```

> 关于 Set 方法的详细用法，请参阅 [《标准库新成员》](/40.frontend/50.javascript/10.language-async/60.最新特性与提案/485.标准库新成员.md) 一文。

### 2.8 Array GroupBy：数据分组的原生方案

```javascript
const products = [
  { name: 'MacBook Pro', category: 'electronics', price: 1999 },
  { name: 'iPhone', category: 'electronics', price: 999 },
  { name: 'T-Shirt', category: 'clothing', price: 29 },
];

products.groupBy(p => p.category);
// → { electronics: [...], clothing: [...] }
```

### 2.9 Symbol 作为 WeakMap 键

ES2023 起，Symbol 也可以作为 WeakMap 的键了：

```javascript
const wm = new WeakMap();
const sym = Symbol('private-key');
wm.set(sym, 'secret data');  // ✅ OK
// 用于库内部的私有状态存储，不污染对象本身
```

## 三、蓄势待发：Stage 3 候选提案

### 3.1 RegExp.escape：正则转义的安全屏障

```javascript
const userInput = '(price + tax) * 0.8';

// ❌ 危险：直接拼接
new RegExp(`(${userInput})`);
// 括号变成捕获组，+ 变成量词...完全偏离意图

// ✅ 安全：先转义
new RegExp(`(${RegExp.escape(userInput)})`);
// → /\(price \+ tax\) \* 0\.8/
```

**哲学思考**：`RegExp.escape()` 提醒我们——**用户输入永远是不可信的**。"sanitize then use"（先净化再使用）始终是安全编程的第一原则。

### 3.2 Promise.try：同步/异步的统一入口

```javascript
function mightBeSyncOrAsync(input) {
  if (input < 0) throw new Error('negative');
  if (input > 100) return fetch(`/api/${input}`);
  return input * 2;  // 可能是同步
}

// ✅ Promise.try 统一处理
Promise.try(() => mightBeSyncOrAsync(50))
  .then(console.log)
  .catch(console.error);  // 同步异常和异步 rejection 都能捕获
```

**核心价值**：隐藏实现的差异，暴露一致的交互界面。无论原始函数是否异步，调用者的 `.then()/.catch()` 链都完全相同。

### 3.3 Math.sumPrecise：浮点数的精确求和

```javascript
let values = [1e20, 1, -1e20];
values.reduce((a, b) => a + b, 0);  // → 0 （精度丢失！）
Math.sumPrecise(values);             // → 1 （精确！）
```

Kahan 求和算法变体解决累加过程中的精度损失。注意：它不解决单个浮点数的表示误差（如 `0.1+0.2≠0.3`），而是保证多次加法的累积误差最小化。

**哲学思考**：即使是看起来最基本的算术运算，在数字计算机的世界里也不绝对可靠。`Math.sumPrecise` 代表了 JS 对数值计算严肃性的承认。

### 3.4 Atomics.pause：多线程的自旋优化

```javascript
const lock = new Int32Array(new SharedArrayBuffer(4));

function acquireLock() {
  let spins = 0;
  while (true) {
    if (Atomics.compareExchange(lock, 0, 0, 1) === 0) return;
    Atomics.pause(spins);  // 比 busy-wait 效率高得多
    if (++spins > 1000) break;
  }
  throw new Error('Failed to acquire lock');
}
```

利用 CPU 的 `PAUSE` 指令实现高效等待——告诉 CPU "当前线程正在自旋等待"，省力且不妨碍其他线程。

## 四、前沿探索：Stage 2 及以下的热门提案

### 4.1 Records & Tuples（记录与元组）：真正的不可变性

```javascript
const config = #{ host: 'localhost', port: 8080 };
const point = #[1, 2, 3];

#{ a: 1 } === #{ a: 1 };  // → true！（深度不可变 + 按值比较）
#[1, 2] === #[1, 2];      // → true！

const original = #{ count: 0 };
const updated = #{ ...original, count: 1 };
// original 未被修改（不可变！）

// 可作为 Map/Set 键（因为按值比较）
const map = new Map();
map.set(#{ id: 1 }, 'data');
map.get(#{ id: 1 });  // → 'data'
```

**为什么如此重要？** React 状态管理、Redux、Immutable.js 都试图解决同一问题——安全地共享不可变数据。Records & Tuples 从**语言层面**提供真正的不可变性，可能会彻底改变状态管理的范式。

**哲学思考**：与其修改现有的东西，不如创造一个新的更好的版本然后让旧的消亡。这是**函数式编程哲学向主流语言的渗透**——不仅是技术选择，更是世界观的转变。

> 详情请参阅 [《ES2025 提案》](/40.frontend/50.javascript/10.language-async/60.最新特性与提案/480.ES2025提案.md)。

### 4.2 Pipeline Operator（管道操作符）：函数式编程的优雅

```javascript
// 传统写法：嵌套地狱
const result = sortBy(filter(map(users, f), p => p.age >= 18), cmp);

// 管道写法：数据流一目了然
const result = users
  |> %.map(transform)
  |>.filter(isAdult)
  |>.sort(compareFn);

// await 管道
const processed = fetchData()
  |>.filter(isValid)
  |>.map(transform)
  |>.collect();
```

**争议**：F# 风格（隐式参数 `x |> f`）vs Hack 风格（显式占位符 `%`）。这正是 Stage 2 的典型特征——好的想法，细节还需大量磨合。

### 4.3 Pattern Matching（模式匹配）：解构的超级进化

```javascript
match (result) {
  case { status: 200, data } => renderSuccess(data),
  case { status: 404 } => showNotFound(),
  case { error: { code: 'AUTH_FAILED' } } => redirectToLogin(),
  case _ => showUnknownError(),
}

// 带守卫条件
match (value) {
  case { type: 'number', value: n } if n > 0 => 'positive',
  case _ => 'other',
}
```

**哲学思考**：if/switch 是命令式的（告诉怎么做）；模式匹配是声明式的（告诉长什么样以及每种情况做什么）。

### 4.4 ShadowRealm：JavaScript 中的沙箱执行环境

```javascript
const realm = new ShadowRealm();

const result = realm.evaluate(`
  function greet(name) {
    return 'Hello from shadow realm!';
  }
  greet
`);

result('World');  // → 'Hello from shadow realm!'
// realm 中无法访问主领域的全局变量
// 只有 ECMA 标准内置对象可用
```

| 特性 | ShadowRealm | iframe | Node.js vm |
|------|------------|--------|------------|
| 隔离程度 | 完全隔离全局 | 完全隔离 | 可配置 |
| 通信方式 | 结构化克隆 | postMessage | 上下文桥接 |
| 适用环境 | 浏览器 + Node | 仅浏览器 | 仅 Node |

**用途**：插件系统、DSL 执行、测试隔离、DOM 虚拟化。

### 4.5 Throw Expressions 与 String.dedent

```javascript
// Throw Expressions —— throw 变成表达式
const value = condition ? getResult() : throw new Error('bad');
const config = loadConfig() ?? throw new Error('missing');

// String.dedent —— 智能去除模板字符串缩进
const html = String.dedent`
  <div>
    <p>Hello</p>
  </div>
`;
// → "<div>\n<p>Hello</p>\n</div>"  缩进被智能移除
```

### 4.6 其他有趣的 Stage 2 提案

| 提案 | 核心内容 |
|------|---------|
| **Module Expressions** | 模块作为值，可传递和动态创建 |
| **Iterator.range** | 类似 Python 的 `range()` 函数 |
| **Iterator Sequencing** | 多个迭代器串联消费 |
| **Async Iterator Helpers** | 异步版本的迭代器工具链 |
| **Structs & Shared Structs** | 高性能固定布局对象 + 共享内存 |

## 五、提案背后的设计哲学

### 5.1 JavaScript 演进的三大趋势

纵观近期 TC39 提案，三条主线清晰可见：

**第一条线：安全性增强**
- `Import Attributes` 防 MIME 嗅探攻击
- `RegExp.escape` 防御正则注入
- `ShadowRealm` 隔离不可信代码
- **哲学**：在开放的环境中，默认应该是安全的

**第二条线：开发体验优化**
- `groupBy`、`Set Methods`、`Iterator Helpers` 减少 Lodash 依赖
- `Temporal` 替代 moment.js/dayjs/date-fns
- `String.dedent`、`Throw Expressions` 消除样板代码
- **哲学**：语言应该让常见操作变得简单

**第三条线：能力边界拓展**
- `Records & Tuples` 提供真正的不可变数据
- `Shared Structs` 支持多线程并行
- `Source Phase Imports` 支持元编程
- **哲学**：语言的能力应跟随使用场景增长

### 5.2 "不要破坏 Web"的铁律

TC39 不成文的首要原则：已有语法不改变语义、新增语法不与旧代码冲突、全局 API 不轻率删除、新关键字必须是上下文敏感的。这是 JavaScript 极致向后兼容的根本来源——也是历史包袱沉重的根本原因。

### 5.3 为什么有些提案进展缓慢

Decorators 花了近十年。Pipeline Operator 在 Stage 2 停留多年。Records & Tuples 语法反复变更。背后的博弈包括：浏览器厂商竞争与合作、多环境需求平衡、TypeScript 既有生态影响、学术理论约束。这不是低效——这是**民主决策的成本**。

## 七、总结：一张不断生长的蓝图

```
JavaScript 的进化方向
├── 语法增强
│   ├── Decorators（已落地）— 元编程标准化
│   ├── Pipeline Operator（Stage 2）— 函数式数据流
│   ├── Pattern Matching（Stage 2）— 结构化分支
│   └── Throw Expressions / String.dedent（Stage 2）
│
├── 数据类型
│   ├── Records & Tuples（Stage 2）— 深度不可变
│   ├── Temporal（已落地）— 工业级时间处理
│   └── Shared Structs（Stage 2）— 共享内存高性能
│
├── 标准库补全
│   ├── Iterator Helpers / Set Methods / groupBy（已落地）
│   ├── Math.sumPrecise / RegExp.escape / Promise.try（Stage 3）
│
├── 安全与隔离
│   ├── Import Attributes（已落地）
│   ├── ShadowRealm（Stage 2.7）
│   └── Dynamic Code Brand Checks（Stage 3）
│
├── 资源管理
│   ├── Explicit Resource Management（已落地）
│   └── Atomics.pause（Stage 3）
│
└── 异步与并发
    ├── Async Iterator Helpers（Stage 2）
    └── Async Context / Float16
```

**最后的思考**：TC39 提案体系是人类协作制定技术标准的典范——没有中央权威的强制命令，通过持续的讨论、实验、妥协和共识推动进步。过程虽慢，结果却稳健且经得起时间考验。作为使用者，我们既是受益者也可以是参与者。这种"共建共享"的精神，或许正是开源精神和开放 Web 理念的最美体现。
