# 历史 API —— pushState、replaceState、popstate 事件，单页应用路由实现

## 从"整页刷新"到"无感导航"的体验跃迁

在传统 Web 模型中，每次点击链接都意味着一次完整的页面加载——浏览器发送请求、服务器返回 HTML、浏览器清空当前页面、解析渲染新的页面。这个过程伴随着白屏闪烁、布局抖动和漫长的等待。**单页应用（SPA, Single Page Application）** 彻底改变了这一范式：所有的页面切换都在客户端完成，无需整页刷新。

但要实现 SPA 有一个关键挑战：**URL 必须随着页面内容的变化而更新**。否则，用户无法收藏特定的页面状态，也无法通过浏览器的后退/前进按钮导航。这正是 **History API** 要解决的问题——它允许 JavaScript 在**不刷新页面的前提下**操作浏览器的历史记录栈和地址栏 URL。

> **本文的目标**：深入剖析 History API 的每一个方法（pushState、replaceState、go、back、forward），理解 popstate 事件的触发时机，并通过实战实现一个功能完备的单页应用路由系统。

## 一、浏览器历史记录的本质

### 1.1 历史记录栈

浏览器维护着一个**历史记录栈（History Stack）**——每一页面对应一条记录：

```
用户操作历程：

访问 google.com          → 栈: [google]
点击搜索结果 wikipedia    → 栈: [google, wikipedia]
点击内部链接 article      → 栈: [google, wikipedia, article]
点击后退                  → 栈: [google, wikipedia] （article 弹出）
点击前进                  → 栈: [google, wikipedia, article] （article 再次入栈）
                                        ↑ 当前指针位置
```

History API 允许我们在这个栈上进行三种操作：

1. **pushState**：压入一条新记录（类似点击了一个链接）
2. **replaceState**：替换当前记录（不增加栈长度）
3. **popstate 事件监听**：当用户点击后退/前进按钮时触发

### 1.2 pushState：添加历史记录

```javascript
// 语法
history.pushState(state, title, url);

// state: 一个 JavaScript 对象（最多 640KB），与新记录关联的状态数据
// title: 目前大多数浏览器忽略此参数（传入空字符串即可）
// url: 新的地址栏 URL（必须同源）
```

```javascript
// 示例：导航到文章详情页
history.pushState(
    { articleId: 42, category: 'tech' },  // 状态对象
    '',                                      // 标题（忽略）
    '/articles/42'                           // 新 URL
);

// 执行后：
// 1. 地址栏变为 https://example.com/articles/42
// 2. 历史记录栈新增一条记录
// 3. 但页面没有刷新！没有请求发送！
// 4. 也没有触发 popstate 事件！
```

**关键理解**：`pushState` 只是**修改了 URL 和历史记录**，它不会触发任何页面加载或事件。你需要自己根据 URL 变化来更新页面内容。

### 1.3 replaceState：替换当前记录

```javascript
// 语法与 pushState 相同
history.replaceState(state, title, url);

// 区别：不会新增历史记录，而是替换当前那条
// 典型用途：登录成功后将 /login 替换为 /dashboard
// 这样用户按后退不会回到登录页
```

```javascript
// 登录成功的场景
async function handleLogin(credentials) {
    const result = await api.login(credentials);
    
    if (result.success) {
        // 替换当前记录：/login → /dashboard
        history.replaceState(
            { userId: result.userId, token: result.token },
            '',
            '/dashboard'
        );
        
        renderDashboard(result.user);
    }
}

// 此时历史栈中没有 /login 的记录了
// 后退会回到登录页之前的页面（比如首页）
```

### 1.4 go、back、forward：程序化导航

```javascript
// 后退一步
history.back();          // 等价于 history.go(-1)

// 前进一步
history.forward();       // 等价于 history.go(1)

// 跳转 N 步
history.go(-2);          // 后退两步
history.go(3);           // 前进三步

// 这些方法会触发 popstate 事件（如果目标记录存在的话）
```

### 1.5 popstate 事件：响应用户导航

```javascript
// 当用户点击后退/前进按钮、或者调用 history.back()/forward()/go() 时触发
window.addEventListener('popstate', (event) => {
    console.log('状态变化了！');
    console.log(event.state);  // pushState 时保存的状态对象
    
    // 你需要根据 event.state 来恢复对应的页面内容
    if (event.state?.articleId) {
        showArticle(event.state.articleId);
    }
});

// ⚠️ 注意：pushState 本身不会触发 popstate！
// popstate 只在"历史栈指针移动"时触发
```

### 1.6 生活类比：历史记录就像一本书的书签

- **pushState 就像在书中夹一枚新书签**：你翻到了新的一页（URL 变了），并在那里放了一枚书签（state 数据）。书变厚了（历史栈增长），以后可以翻回来找到这一页。
  
- **replaceState 就像替换当前这枚书签**：你还在同一页，但把书签上的备注改了（state 变了），或者把书签挪了一下位置（URL 变了）。书的厚度不变。
  
- **popstate 事件就像有人翻动了书页**：不管是你自己翻的（调用 back()）还是读者翻的（用户点后退按钮），只要页面变了，你就会收到通知："现在翻到了哪一页？"（event.state）。

> **哲学思考**：History API 的设计体现了一种叫做 **CQRS（Command Query Responsibility Segregation）** 的架构思想——**修改（Command）和查询（Query）分离**。`pushState` 是 Command——"往历史栈里加一条记录"。`popstate` 事件是 Query——"告诉我当前是什么状态"。两者之间没有直接的因果关联——pushState 不会触发 popstate，这给了开发者完全的控制权：什么时候修改 URL、什么时候响应 URL 变化，由你自行决定。这种解耦是构建灵活路由系统的基础。

## 二、实现一个单页应用路由

### 2.1 路由系统的基本架构

```javascript
/**
 * HashRouter — 基于 hash 的简易路由
 * （作为对比，先看 hash 方式）
 */
class HashRouter {
    constructor(routes) {
        this.routes = routes;  // { path: handler }
        this.currentPath = window.location.hash.slice(1) || '/';
        
        window.addEventListener('hashchange', () => {
            this._handleRouteChange();
        });
        
        // 初始化
        this._handleRouteChange();
    }

    navigate(path) {
        window.location.hash = path;
    }

    _handleRouteChange() {
        const path = window.location.hash.slice(1) || '/';
        this.currentPath = path;
        
        const handler = this.routes[path] || this.routes['404'];
        if (handler) {
            handler(path);
        }
    }
}
```

### 2.2 基于 History API 的路由（生产级）

```javascript
/**
 * BrowserRouter — 基于 History API 的完整路由系统
 */
class BrowserRouter {
    constructor(options = {}) {
        this.routes = [];           // [{ path, handler, params }]
        this.notFoundHandler = options.notFound || (() => {});
        this.beforeHooks = [];
        this.afterHooks = [];
        this.currentRoute = null;
        this.state = {};            // 共享状态
        
        this._init();
    }

    _init() {
        // 监听 popstate（后退/前进）
        window.addEventListener('popstate', (e) => {
            this._navigateTo(window.location.pathname, e.state);
        });

        // 拦截所有同源链接的点击
        document.addEventListener('click', (e) => {
            const link = e.target.closest('a[href]');
            if (!link) return;
            
            const href = link.getAttribute('href');
            
            // 只拦截同源的非特殊链接
            if (href.startsWith('/') || 
                href.startsWith(window.location.origin)) {
                e.preventDefault();
                const url = new URL(href, window.location.origin);
                this.push(url.pathname + url.search, null);
            }
        });

        // 初始加载
        this._navigateTo(window.location.pathname);
    }

    // 注册路由
    register(path, handler) {
        // 将路径转换为正则表达式以支持参数
        const paramNames = [];
        const regexStr = path.replace(/:([^/]+)/g, (_, name) => {
            paramNames.push(name);
            return '([^/]+)';
        });
        
        this.routes.push({
            pattern: new RegExp(`^${regexStr}$`),
            paramNames,
            originalPath: path,
            handler
        });
        
        return this;  // 链式调用
    }

    // 导航（pushState）
    push(path, state = {}) {
        history.pushState(state, '', path);
        this._navigateTo(path, state);
    }

    // 替换（replaceState）
    replace(path, state = {}) {
        history.replaceState(state, '', path);
        this._navigateTo(path, state);
    }

    // 后退
    back() {
        history.back();
    }

    // 前进
    forward() {
        history.forward();
    }

    // 跳转 N 步
    go(n) {
        history.go(n);
    }

    // 全局前置守卫
    beforeEach(hook) {
        this.beforeHooks.push(hook);
    }

    // 全局后置钩子
    afterEach(hook) {
        this.afterHooks.push(hook);
    }

    // 核心：路径匹配与导航
    async _navigateTo(path, state = null) {
        let matched = null;

        for (const route of this.routes) {
            const match = path.match(route.pattern);
            if (match) {
                // 提取参数
                const params = {};
                route.paramNames.forEach((name, i) => {
                    params[name] = decodeURIComponent(match[i + 1]);
                });

                matched = { route, params };
                break;
            }
        }

        if (!matched) {
            this.notFoundHandler(path);
            return;
        }

        // 执行前置守卫
        for (const hook of this.beforeHooks) {
            const result = await hook({
                to: { path, params, state },
                from: this.currentRoute
            });
            if (result === false) return;  // 取消导航
        }

        const { route, params } = matched;
        const context = {
            path,
            params,
            state: state || {},
            query: this._parseQuery(window.location.search)
        };

        // 执行路由处理器
        await route.handler(context);

        // 更新当前路由信息
        this.currentRoute = context;

        // 执行后置钩子
        for (const hook of this.afterHooks) {
            hook(context);
        }
    }

    _parseQuery(searchString) {
        const query = {};
        if (!searchString) return query;
        const params = new URLSearchParams(searchString);
        for (const [key, value] of params) {
            query[key] = value;
        }
        return query;
    }
}
```

### 2.3 使用示例

```javascript
// 创建路由实例
const router = new BrowserRouter({
    notFound: () => {
        document.getElementById('app').innerHTML = '<h1>404 - 页面不存在</h1>';
    }
});

// 全局前置守卫：检查登录状态
router.beforeEach(async ({ to }) => {
    if (to.path.startsWith('/admin') && !isLoggedIn()) {
        router.replace('/login', { redirect: to.path });
        return false;  // 取消导航
    }
});

// 注册路由
router.register('/', (ctx) => {
    renderHome();
}).register('/articles', (ctx) => {
    renderArticleList(ctx.query.page || 1);
}).register('/articles/:id', async (ctx) => {
    const article = await fetchArticle(ctx.params.id);
    renderArticle(article);
}).register('/about', (ctx) => {
    renderAbout();
});

// 编程式导航
function viewArticle(id) {
    router.push(`/articles/${id}`, { from: 'home' });
}

// 登录后替换当前记录
function afterLogin(user) {
    router.replace('/dashboard', { user });
}
```

## 三、服务端配置：避免 404 问题

### 3.1 为什么需要服务端配置？

当用户直接在地址栏输入 `https://example.com/articles/42` 或刷新该页面时，浏览器会向服务器请求 `/articles/42` 这个路径。但如果你的 SPA 只有一个入口文件 `index.html`，服务器会返回 404——因为这个物理路径并不存在。

解决方案：**让服务器对所有未知路径都返回 index.html**，然后由前端路由接管。

### 3.2 各服务器的配置

```nginx
# Nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

```apache
# Apache (.htaccess)
<IfModule mod_rewrite.c>
    RewriteEngine On
    RewriteBase /
    RewriteRule ^index\.html$ - [L]
    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteCond %{REQUEST_FILENAME} !-d
    RewriteRule . /index.html [L]
</IfModule>
```

```javascript
// Node.js (Express)
app.get('*', (req, res) => {
    res.sendFile(path.join(__dirname, 'dist', 'index.html'));
});
```

```json
// Vite 配置 (vite.config.js)
export default defineConfig({
    server: {
        proxy: {
            '*': {
                target: 'http://localhost:3000',
                rewrite: () => 'index.html'
            }
        }
    }
});
```

## 四、Hash 路由 vs History 路由

### 4.1 对比

| 维度 | Hash 模式 (`#/path`) | History 模式 (`/path`) |
|------|---------------------|------------------------|
| **URL 美观度** | 不好（有 # 号） | 好（标准 URL 格式） |
| **SEO 友好度** | 差（爬虫通常忽略 # 后内容） | 好（真实路径） |
| **服务端要求** | 无需配置 | 需要 fallback 配置 |
| **兼容性** | 极好（所有浏览器） | IE10+ |
| **服务器日志** | 无法区分不同路由 | 每个路径都有独立日志 |
| **第三方服务** | 可能导致问题（如微信分享） | 无兼容性问题 |

### 4.2 选择建议

- **内部管理系统 / 企业应用** → Hash 模式足够（SEO 无关，部署简单）
- **面向公众的内容网站** → History 模式（URL 美观、利于 SEO）
- **需要兼容老旧浏览器** → Hash 模式

> **最后的思考**：History API 的存在标志着 Web 从"文档集合"向"应用程序平台"转变的一个里程碑。传统的超链接模型假设每次导航都是一次独立的页面加载——这对于静态文档来说是合理的。但当 Google Maps、Gmail 这样的应用出现后，开发者迫切需要在不丢失客户端状态的前提下更新 URL。History API 正是这个需求的答案——它让 JavaScript 获得了对 URL 的完全控制权，同时保持了浏览器导航行为的完整性（后退/前进按钮、书签、分享链接都能正常工作）。关于 localStorage 和 sessionStorage 的详细使用，推荐阅读[《本地存储》](/40.frontend/50.javascript/20.browser-api/10.浏览器%20API%20与%20DOM%20操作/70.本地存储.md)。关于跨标签页通信的技术方案，推荐阅读[《跨标签页通信》](/40.frontend/50.javascript/20.browser-api/10.浏览器%20API%20与%20DOM%20操作/75.跨标签页通信.md)。
