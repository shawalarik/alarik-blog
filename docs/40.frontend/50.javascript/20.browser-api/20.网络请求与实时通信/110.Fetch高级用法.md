# Fetch 高级 —— 中断（AbortController）、流式读取（response.body）、取消请求

> **本文的目标**：深入 Fetch API 的进阶能力——掌握 AbortController 实现请求取消与超时控制、通过 ReadableStream 进行流式数据处理、以及这些能力在实际场景中的组合运用。这些知识将让你从"能发起请求"进阶到"精准掌控请求"。

## 一、请求的生命周期管理：从"发射后不管"到"主动干预"

在 [《Fetch API》](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/105.Fetch%20API.md) 的基础用法中，我们学会了如何发起请求并等待响应——这就像射出一支箭，你瞄准目标、拉弓、释放，然后等待它命中靶心。但现实世界中的网络请求远比这个模型复杂：用户可能在请求发出后点击了另一个按钮（旧请求变得多余），网络可能持续无响应（需要超时机制），或者组件卸载了但请求还在飞（可能导致内存泄漏或状态错误）。

这就需要一种机制来**主动终止一个已经发出的请求**——这就是 `AbortController` 要解决的问题。

```javascript
// 最基本的请求取消
const controller = new AbortController();        // ① 创建控制器
const signal = controller.signal;               // ② 获取信号对象

fetch('/api/slow-data', { signal })             // ③ 将信号传入 fetch
    .then(res => res.json())
    .then(data => console.log('拿到数据:', data))
    .catch(err => {
        if (err.name === 'AbortError') {
            console.log('请求被取消了');
        } else {
            console.error('其他错误:', err);
        }
    });

// 在某个时刻主动取消请求
setTimeout(() => {
    controller.abort();                          // ④ 触发取消！
}, 2000);   // 2秒后取消
```

### 生活类比：快递追踪的"拒收"

想象你在网上下单了一件商品，发货后发现买错了或者不需要了：

- **`new AbortController()` 就像在快递系统里创建了一个追踪单号**：这个单号和你的订单绑定在一起，你可以用它来随时查询包裹的状态，更重要的是——你可以用它在包裹到达之前通知物流公司"我不要了"。

- **`signal` 就像附在包裹上的电子标签**：物流系统的每一个环节（分拣中心、运输车辆、派送员）都能扫描到这个标签上的状态。一旦标签显示"已取消"，所有环节都会立即停止处理这个包裹。

- **`controller.abort()` 就是你在手机上点击"取消订单"的那一刻**：信号瞬间传递给整个系统，所有相关资源被释放，不再有后续操作。

- **`AbortError` 就是快递员告诉你"这个订单已被取消"的通知**：这不是"地址找不到"（404），也不是"仓库着火了"（500），而是一种专门的"主动放弃"状态。

## 二、AbortController 的完整工作原理

AbortController 基于 Web 标准的 **AbortSignal** 接口设计，它的架构体现了观察者模式的精髓：

```javascript
/**
 * AbortController 内部结构示意
 *
 *  controller ──拥有──▶ signal（AbortSignal 对象）
 *                       │
 *                       ├── aborted: false/true     （是否已中止）
 *                       ├── reason: DOMException     （中止原因）
 *                       └── abort event listener     （监听器列表）
 *
 *  当调用 controller.abort() 时：
 *    1. signal.aborted 立即变为 true
 *    2. signal.reason 被设置为 AbortError
 *    3. 所有注册在 signal 上的事件监听器被触发
 *    4. 正在使用该 signal 的 fetch/XHR 操作被中断
 */

// 深入理解 signal 属性
const controller = new AbortController();
const signal = controller.signal;

console.log(signal.aborted);   // false —— 初始状态：未被中止
console.log(signal.reason);    // null  —— 尚无中止原因

// 监听 abort 事件（与 fetch 无关，纯事件监听）
signal.addEventListener('abort', () => {
    console.log('abort 事件触发了！');
    console.log('reason:', signal.reason);  // AbortError: The user aborted a request.
});

controller.abort();

console.log(signal.aborted);   // true
// 输出：abort 事件触发了！
//       reason: AbortError: The user aborted a request.
```

### 一个信号控制多个请求

同一个 `AbortSignal` 可以同时传给多个 `fetch` 调用，实现"一键取消所有相关请求"的效果：

```javascript
// 场景：搜索建议 —— 用户每次输入都发起新请求，
// 但只需要保留最新的那一次
let currentController = null;

function searchSuggestions(query) {
    // 取消上一次尚未完成的请求
    if (currentController) {
        currentController.abort();
    }

    // 为新请求创建新的控制器
    currentController = new AbortController();

    fetch(`/api/search?q=${encodeURIComponent(query)}`, {
        signal: currentController.signal
    })
    .then(res => res.json())
    .then(data => {
        updateSuggestionList(data);   // 更新UI
        currentController = null;      // 清除引用
    })
    .catch(err => {
        if (err.name !== 'AbortError') {
            console.error('搜索失败:', err);
        }
        currentController = null;
    });
}

// 用户快速输入 "java"
searchSuggestions('j');    // 请求1发出
searchSuggestions('ja');   // 请求1被取消，请求2发出
searchSuggestions('jav');  // 请求2被取消，请求3发出
searchSuggestions('java'); // 请求3被取消，请求4发出
// 最终只有请求4的结果会更新UI
```

这种模式在实际开发中极其常见：搜索框实时查询、地图拖拽加载标记点、Tab 页面切换时的数据获取等场景都需要这种**"只保留最新一次"**的策略。

## 三、实现超时控制

XHR 有原生的 `timeout` 属性，而 Fetch 没有内置超时机制。但有了 `AbortController`，我们可以轻松实现——甚至比 XHR 更灵活：

```javascript
/**
 * 带超时的 fetch 函数
 * @param {string|Request} resource - 请求资源
 * @param {Object} [options] - fetch 配置项
 * @param {number} [timeout=8000] - 超时毫秒数
 */
function fetchWithTimeout(resource, options = {}, timeout = 8000) {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), timeout);

    return fetch(resource, {
        ...options,
        signal: controller.signal
    }).finally(() => clearTimeout(timer));   // 无论成功失败都清除定时器
}

// 使用示例
try {
    const res = await fetchWithTimeout('/api/slow-endpoint', {}, 5000);
    const data = await res.json();
} catch (err) {
    if (err.name === 'AbortError') {
        console.error('请求超过5秒未响应，已自动取消');
    }
}
```

### 更精细的超时策略：递增退避

对于可能因临时网络波动而失败的请求，简单的固定超时往往不够智能。下面实现一个带自动重试的超时策略：

```javascript
/**
 * 带重试和递增超时的智能 fetch
 * @async
 * @param {string} url - 请求URL
 * @param {Object} [opts] - 选项
 * @param {number} [opts.retries=3] - 最大重试次数
 * @param {number} [opts.baseTimeout=3000] - 基础超时(ms)
 * @param {number} [opts.backoffFactor=2] - 退避倍数
 */
async function smartFetch(url, opts = {}) {
    const { retries = 3, baseTimeout = 3000, backoffFactor = 2, ...fetchOpts } = opts;
    let lastError;

    for (let attempt = 0; attempt <= retries; attempt++) {
        const timeout = baseTimeout * Math.pow(backoffFactor, attempt);
        console.log(`第 ${attempt + 1} 次尝试，超时: ${timeout}ms`);

        try {
            const res = await fetchWithTimeout(url, fetchOpts, timeout);

            if (!res.ok && res.status >= 500 && attempt < retries) {
                // 服务器端错误且还有重试次数 → 继续重试
                console.log(`服务端错误 ${res.status}，准备重试...`);
                continue;
            }

            return res;   // 成功 或 客户端错误(不重试)
        } catch (err) {
            lastError = err;
            if (err.name === 'AbortError' && attempt < retries) {
                console.log(`超时，${timeout * backoffFactor / 1000}s 后重试...`);
                continue;
            }
            throw err;   // 非超时错误 或 已达最大重试次数
        }
    }

    throw lastError;
}

// 使用：首次3s超时，然后6s，然后12s
smartFetch('/api/unstable-service', { retries: 2, baseTimeout: 3000 })
    .then(res => res.json())
    .then(console.log)
    .catch(console.error);
```

> **哲学思考**：超时本质上是**对不确定性的一种风险管理策略**。当你发起一个网络请求时，你实际上是在做一个赌注："我相信服务器会在合理的时间内回应。"超时就是这个"合理时间"的具体化——它是你的耐心底线，也是你保护用户体验的最后防线。没有超时的请求就像没有截止日期的项目任务：理论上它可能会完成，但实际上你可能等到了地老天荒。而递增退避策略则体现了一种**适应性思维**：第一次失败可能是偶然，多给它一点时间；但如果连续失败，说明问题可能是结构性的，应该更快地放弃而不是无限等待。这种"有耐心但不固执"的态度，不仅是好的工程实践，也是生活的智慧。
