# 跨域资源请求（CORS）—— 简单请求、预检请求、凭证、通配符

> **本文的目标**：彻底理解浏览器的同源策略机制、CORS（跨源资源共享）的工作原理——从简单请求的自动放行，到预检请求的协商流程，再到凭证传递的安全边界。这些知识是每个前端开发者必须掌握的网络安全基础。

## 一、为什么需要"同源"这个概念？

浏览器有一个基本的安全假设：**来自不同"源"（origin）的页面之间应该相互隔离**。所谓"源"，由协议（protocol）、域名（host）和端口（port）三者共同决定：

```
https://example.com:443/app/page.html
│       │          │   │
协议     域名        端口 路径（不参与源的判断）
```

只有当**三者完全一致**时，才称为"同源"。以下都是**不同的源**：

| URL A | URL B | 是否同源 | 原因 |
|-------|-------|---------|------|
| `https://example.com` | `https://example.com/api` | **是** | 同协议/域名/端口 |
| `http://example.com` | `https://example.com` | **否** | 协议不同 |
| `https://example.com` | `https://app.example.com` | **否** | 域名不同 |
| `https://example.com` | `https://example.com:8080` | **否** | 端口不同 |
| `https://example.com` | `https://Example.com` | **是** | 域名不区分大小写 |

同源策略限制了以下行为：
- 无法读取其他源的 Cookie、LocalStorage、IndexedDB
- 无法操作其他源的 DOM
- **无法向其他源发起 AJAX/Fetch 请求并获取响应**

注意第三条的关键词：**"无法获取响应"**。浏览器并不会阻止你向其他源发送请求——请求确实会发出去，服务器也确实会处理它。但浏览器会**拦截返回的响应**，让 JavaScript 拿不到数据。

```javascript
// 这行代码会成功发出请求（可以在 Network 面板看到），
// 但 response 中的数据对 JS 是不可见的
fetch('https://other-api.com/data')
    .then(res => res.json())
    .catch(err => {
        // 浏览器会抛出 CORS 错误
        console.error(err);
        // "Access to fetch at '...' from origin '...' has been blocked by CORS policy"
    });
```

### 生活类比：公司的访客制度

把你的前端页面想象成一家公司（源A），你想访问的另一家公司的 API 想象成另一家公司（源B）：

- **你可以给那家公司打电话（发送请求）**：电话线路是通的，对方也能听到你说的内容。
- **但如果你们公司没有建立合作关系（CORS），对方回复的内容会被前台拦截（浏览器拦截响应）**。你打出了电话，但听不到回音。
- **建立合作关系的流程就是 CORS 协商**：你告诉前台你要联系谁（Origin 头部），前台检查白名单（Access-Control-Allow-Origin），如果在名单上就放行。
- 这个制度的存在是为了**防止恶意页面冒充用户身份访问敏感数据**——就像防止陌生人冒充你的员工进入内部区域。

## 二、简单请求：免检通道

并非所有跨域请求都需要复杂的协商流程。满足以下全部条件的请求被称为**简单请求（Simple Request）**，浏览器会直接发送，不做额外检查：

1. **方法限制**：只允许 `GET`、`HEAD`、`POST`
2. **头部限制**：只能使用以下标准头部：
   - `Accept`
   - `Accept-Language`
   - `Content-Language`
   - `Content-Type`（仅限 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`）
3. **没有自定义头部**
4. **没有在请求中注册事件监听器**
5. **使用的是 `ReadableStream` 对象**

如果服务器在响应中设置了正确的 CORS 头部，简单请求就能成功：

```javascript
// 这是一个简单请求 ✓
// 方法 = GET ✅ | 无自定义头部 ✅ | Content-Type 不涉及（GET无body）✅
fetch('https://api.other.com/users');

// 这也是简单请求 ✓
// 方法 = POST ✅ | Content-Type 在允许列表中 ✅
fetch('https://api.other.com/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: 'user=test&pass=123'
});

// ❌ 这不是简单请求 —— 使用了非标准的 Content-Type
fetch('https://api.other.com/data', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },   // ← 不在允许列表中！
    body: JSON.stringify({ name: 'test' })
});
// 这种请求会触发"预检请求"（见下文）
```

服务器端的响应需要包含关键的 CORS 头部：

```http
# 服务端必须返回此头部来声明哪些源可以访问
Access-Control-Allow-Origin: https://my-app.com

# 或者使用通配符允许所有源（生产环境慎用！）
Access-Control-Allow-Origin: *
```

## 三、预检请求（Preflight）：复杂操作的安检

当请求不满足"简单请求"的条件时——比如使用了 `PUT` 方法、设置了 `Content-Type: application/json`、或者添加了自定义头部如 `Authorization`——浏览器会在发送实际请求之前，先自动发出一个 **OPTIONS** 请求，询问服务器："我打算这样发一个请求，你允许吗？"

这就是**预检请求（Preflight Request）**：

```
浏览器                          服务器
 │                               │
 │  ── OPTIONS /api/data ──────▶  │   ① 预检请求
 │    Origin: https://a.com      │    (询问权限)
 │    Access-Control-Request-    │
 │      Method: PUT              │
 │    Access-Control-Request-    │
 │      Headers: content-type,   │
 │                 x-custom      │
 │                               │
 │  ◀── 200 OK ────────────────  │   ② 服务器回应
 │    Access-Control-Allow-      │    (批准或拒绝)
 │      Origin: https://a.com    │
 │    Access-Control-Allow-      │
 │      Methods: GET, PUT, POST  │
 │    Access-Control-Allow-      │
 │      Headers: content-type,   │
 │                 x-custom      │
 │                               │
 │  ── PUT /api/data ─────────▶  │   ③ 实际请求
 │    （携带真正的数据体）         │
 │                               │
 │  ◀── 200 OK + 数据 ─────────  │   ④ 正常响应
```

```javascript
// 这个请求会触发预检 —— 因为使用了 JSON 类型的 POST body
fetch('https://api.other.com/data', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',   // 触发预检的原因之一
        'X-Custom-Header': 'value'            // 自定义头部也是触发原因
    },
    body: JSON.stringify({ title: 'Hello' })
});

// 打开 Network 面板你会看到两个请求：
// ① OPTIONS /data   （预检请求，状态码通常为204或200）
// ② POST /data      （实际请求）
```

### 优化预检性能

预检请求意味着每次"复杂"请求都会多一次网络往返，这在高延迟网络环境下会影响性能。可以通过服务端配置来缓存预检结果：

```http
# 通知浏览器：在 86400 秒（24小时）内，
# 同样的预检结果可以被复用，不需要再次发起 OPTIONS
Access-Control-Max-Age: 86400
```

设置后，浏览器会在指定时间内缓存预检结果，后续相同类型的请求不再需要额外的 OPTIONS 往返。

## 四、凭证（Credentials）：Cookie 的跨域困境

默认情况下，跨域请求**不会携带 Cookie** 和 HTTP 认证信息（如 Authorization 头）。这是安全考虑——你不会希望第三方网站能以你的身份去访问其他网站的接口。

但某些场景确实需要跨域携带凭证（比如单点登录系统 SSO）。这需要在两端同时进行配置：

```javascript
// 前端：将 credentials 设为 'include'
fetch('https://auth.sso.com/check', {
    credentials: 'include'    // 携带跨域Cookie
});
```

```http
# 后端：不能使用通配符 * 了！必须明确指定源
Access-Control-Allow-Origin: https://my-app.com
Access-Control-Allow-Credentials: true

# ❌ 下面这种写法与 credentials 冲突，浏览器会报错：
# Access-Control-Allow-Origin: *
# Access-Control-Allow-Credentials: true
```

这是一个重要的约束：**当 `credentials: include` 时，`Access-Control-Allow-Origin` 不能使用 `*` 通配符**。你必须显式列出每一个允许的源。这是因为通配符代表"任何来源都可以"，而携带凭证意味着"以用户的身份访问"，两者结合会产生安全隐患。

> **哲学思考**：CORS 本质上是一种**信任委托模型**。浏览器作为用户的代理，替用户执行了一项安全策略：除非目标服务器明确说"我信任来自某个源的前端代码"，否则不允许该代码读取我的数据。这是一种"推卸责任但保留控制权"的设计——浏览器不判断请求是否合法（那是服务器的事），但它确保了只有被授权的前端才能拿到响应数据。这种设计哲学在计算机科学中随处可见：操作系统不决定哪个程序该运行，但它通过进程隔离来限制程序的能力；数据库引擎不决定 SQL 是否有意义，但它通过事务隔离来保证一致性。CORS 就是 Web 安全领域的"进程隔离"——每个源是一个独立的沙箱，跨沙箱的数据流动必须经过明确的许可。
