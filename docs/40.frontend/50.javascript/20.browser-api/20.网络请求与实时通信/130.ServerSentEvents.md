# Server-Sent Events（SSE）—— EventSource、与 WebSocket 对比

> **本文的目标**：掌握 Server-Sent Events 这一轻量级的单向实时推送技术——理解其基于 HTTP 的设计原理、EventSource API 的使用方法，以及它与 WebSocket、轮询等方案的取舍之道。

## 一、当只需要"服务器说话"的时候

在 [《WebSocket 实时通信》](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/125.WebSocket.md) 中我们学习了全双工的 WebSocket 协议——客户端和服务器可以随时向对方发送数据。但并非所有"实时推送"场景都需要双向通信。考虑以下场景：

- **新闻网站**的服务器每隔一段时间推送最新的头条新闻
- **股票行情板**持续更新价格数据
- **社交媒体**的通知栏显示"有3条新消息"
- **日志监控面板**滚动显示服务器日志

这些场景有一个共同特点：**数据的流动方向是单向的——从服务器到客户端**。客户端不需要主动发送任何业务数据（除了最初的连接建立），它只是一个被动的接收者。

Server-Sent Events (SSE) 正是为这类场景量身定制的方案。它使用标准的 HTTP 协议，服务端以**文本流（Text Stream）** 的方式持续向客户端推送格式化的事件数据。浏览器通过 `EventSource` API 来接收和解析这些事件。

```javascript
// 最简单的 SSE 连接
const eventSource = new EventSource('/api/news/stream');

eventSource.onmessage = function(event) {
    const data = JSON.parse(event.data);
    console.log('收到新闻:', data.title);
    displayNewsItem(data);
};

eventSource.onerror = function(err) {
    console.error('SSE 连接错误:', err);
    // 浏览器会自动尝试重连！
};

// 不需要时关闭连接
// eventSource.close();
```

注意代码的简洁程度——比 WebSocket 少了很多样板代码。没有 `onopen` 手动管理，没有心跳机制需要自己实现，没有二进制的复杂处理。这就是 SSE 的核心优势：**简单**。

### 生活类比：广播 vs 电话

如果把通信方式继续用生活场景类比：

- **WebSocket 就像电话专线**：你可以随时打给对方，对方也可以随时打给你。双向、实时、灵活。但你需要维护这条线路（心跳检测、断线重连），而且成本较高（需要维护一个持久的 TCP 连接）。
  
- **SSE 就像收音机广播**：电台（服务器）持续播放节目，你打开收音机（创建 EventSource）就能听到。你不能跟电台对话（单向），但你不需要拨号，不需要维护线路，而且如果你信号断了再调回来，广播可能还在继续。简单、可靠、够用。

- **轮询就像每隔5分钟去信箱看有没有新报纸**：低效且延迟大，但实现最简单。

## 二、SSE 的协议格式

SSE 的数据格式极其简洁。服务器返回的内容类型为 `text/event-stream`，每条消息由若干字段组成：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

id: 1
data: {"title":"第一条新闻","content":"..."}

id: 2
data: {"title":"第二条新闻","content":"..."}

data: 这是一条纯文本消息

event: customEventType
data: {"custom":"自定义事件"}

: 这是注释行，会被浏览器忽略

id: 3
retry: 5000
data: {"title":"第三条新闻"}
```

每条消息的字段说明：

| 字段 | 必填 | 说明 |
|------|------|------|
| `data` | **是** | 消息内容（可以是多行） |
| `id` | 否 | 事件 ID（用于断线重连时的恢复） |
| `event` | 否 | 自定义事件类型（默认为 `message`） |
| `retry` | 否 | 建议的重连间隔（毫秒） |
| `:` 开头 | 否 | 注释行（可用于保持连接活跃） |

### 多行 data 字段

如果一条消息的 `data` 需要多行（比如包含换行符的文本），可以用多个 `data:` 行表示，它们会被合并为一个值并用换行分隔：

```text
data: 第一行
data: 第二行
data: 第三行

// 解析后的 event.data = "第一行\n第二行\n第三行"
```

两条消息之间用空行（双换行符 `\n\n`）分隔。

## 三、EventSource API 详解

### 基础用法

```javascript
const es = new EventSource('/api/events');

// 方式一：监听默认的 message 事件
es.onmessage = (event) => {
    console.log('ID:', event.lastEventId);   // 服务端设置的 id 字段
    console.log('Data:', event.data);        // 数据内容（字符串）
    console.log('Origin:', event.origin);    // 事件来源地址
    console.log('Type:', event.type);        // 事件类型
};

// 方式二：使用 addEventListener 监听自定义事件
es.addEventListener('news', (event) => {
    const newsItem = JSON.parse(event.data);
    console.log('新闻更新:', newsItem.title);
});

es.addEventListener('price-update', (event) => {
    const prices = JSON.parse(event.data);
    updateStockPrices(prices);
});

// 错误处理
es.onerror = (event) => {
    console.error('SSE 错误:', event);
    // EventSource 会自动尝试重连（默认3秒间隔）
    // 可以检查 readyState 判断是否已关闭
    if (es.readyState === EventSource.CLOSED) {
        console.log('连接已被关闭');
    }
};
```

### readyState 状态

| 常量 | 值 | 含义 |
|------|-----|------|
| `EventSource.CONNECTING` | `0` | 正在连接或重连中 |
| `EventSource.OPEN` | `1` | 已连接，正在接收事件 |
| `EventSource.CLOSED` | `2` | 连接已关闭或失败 |

### 自动重连机制

EventSource 最令人省心的特性之一就是**内置自动重连**。当连接意外断开时，浏览器会自动尝试重新建立连接——你不需要像 WebSocket 那样自己实现重连逻辑：

```javascript
// 重连行为完全由浏览器控制：
// 1. 连接断开后等待 retry 字段指定的毫秒数（默认3000ms）
// 2. 自动发起新的 HTTP 请求
// 3. 如果服务端设置了 Last-Event-ID 头部，
//    浏览器会在请求中携带这个ID，让服务器从上次中断的地方继续发送
```

### 限制与注意事项

SSE 有一些重要的限制需要了解：

```javascript
// ❌ SSE 只支持 GET 请求（无法发送 POST body）
// const es = new EventSource('/api/events', { method: 'POST' });  // 不支持！

// ✅ 但可以通过查询参数传递信息
const userId = 'user_123';
const token = getAuthToken();
const es = new EventSource(`/api/events?userId=${userId}&token=${token}`);

// ⚠️ SSE 无法发送自定义请求头
// （这是 Fetch/WebSocket 能做但 SSE 做不到的事）

// ❌ SSE 是单向的 —— 无法向服务器发送数据
// es.send('hello');   // 不存在这个方法！
```

| 特性 | SSE | WebSocket |
|------|-----|-----------|
| 协议 | HTTP | 自定义协议（ws://, wss://） |
| 数据方向 | 服务器 → 客户端（单向） | 双向 |
| 数据格式 | 文本（UTF-8） | 文本 + 二进制 |
| 自动重连 | 内置 | 需自行实现 |
| 自定义头部 | 不支持 | 通过子协议可部分支持 |
| 断点续传 | 支持（Last-Event-ID） | 需自行实现 |
| 浏览器兼容性 | IE 不支持 | 广泛支持 |

## 四、何时选择 SSE？

根据实际场景的需求来选择合适的技术：

**选择 SSE 的场景**：
- 服务器需要持续推送通知/状态更新给客户端
- 数据量不大，主要是文本/JSON 格式
- 不需要客户端向服务器频繁发送业务数据
- 希望利用浏览器内置的重连机制减少开发工作量
- 服务端已有完善的 HTTP 基础设施，不想额外部署 WebSocket 服务

**选择 WebSocket 的场景**：
- 需要真正的双向实时通信（聊天、协作编辑）
- 需要传输大量二进制数据（音视频流、文件分片）
- 需要精确控制连接生命周期
- 需要极低延迟（游戏、金融交易）

> **哲学思考**：SSE 体现了工程领域的一条重要原则——**不要过度设计**。当你的问题只需要一把螺丝刀时，不需要带上一整个工具箱。WebSocket 强大而灵活，但它的复杂性也是真实的——你需要处理握手、心跳、重连、二进制帧、子协议协商等一堆事情。如果你的需求只是"让服务器能主动告诉客户端一些事"，SSE 用几行代码就能搞定，而且因为它基于标准 HTTP，现有的负载均衡器、CDN、代理服务器都能直接使用，无需任何特殊配置。好的工程师知道什么时候该用瑞士军刀，什么时候该用普通的刀——工具的价值不在于它有多少功能，而在于它能在正确的地方解决问题。
