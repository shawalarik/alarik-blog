# 长轮询与短轮询 —— 实现、优缺点、适用场景

> **本文的目标**：系统比较 Web 实时数据获取的各种轮询策略——从传统的短轮询（Short Polling）、长轮询（Long Polling），到现代的 [WebSocket](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/125.WebSocket.md) 和 [SSE](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/130.ServerSentEvents.md)。理解每种方案的设计思路、权衡取舍和适用边界，是做出合理技术选型决策的基础。

## 一、"服务器不会主动打电话给我"

Web 的基础架构建立在 **HTTP 请求-响应模型**之上。这是一个严格的"一来一回"范式：客户端发起请求，服务器返回响应，然后连接结束。服务器没有办法在没有收到请求的情况下主动向客户端推送数据。

但在很多应用中，我们需要的是**接近实时的数据更新**。想象一下这些场景：

- 一个在线聊天界面，别人发了消息后你应该尽快看到
- 一个电商后台的订单列表，新下单应该立刻出现
- 一个项目管理看板上的任务状态变化
- 一个体育比赛的比分直播页面

问题是：**服务器有了新数据，但它没办法告诉你。它只能等你来问。**

于是人类想出了一个朴素的解决方案：**你不告诉我？那我就不停地问！**

这就是**轮询（Polling）**的核心思想。

### 生活类比：查快递 vs 快递上门

- **短轮询（Short Polling）就像每隔10分钟去小区门口的快递柜前看看有没有包裹**：你走过去，看一眼，空的就回家；过10分钟再去。大多数时候都是白跑一趟，但偶尔会有惊喜。效率很低，但至少不会漏掉快递。

- **长轮询（Long Polling）就像你站在快递柜旁边不走**：问工作人员"有我的快递吗？"，工作人员说"还没有，你在这等着吧"。你就在那等，直到真的来了或者等了太久不耐烦了才回家。然后马上又跑回来继续等。

- **WebSocket 就像快递员直接把包裹送到你家门口**：不用你去取，快递到了他按门铃。最高效但也需要基础设施支持（你得在家、得有门铃、得和快递站约定好配送规则）。

- **SSE 就像订了一份报纸每天送到家门口**：报社（服务器）定期派送新闻，你只需要坐在门口等着收就行。单向的，但你总能拿到最新内容。

## 二、短轮询（Short Polling）：最原始的方案

短轮询是最直观的实现方式——客户端每隔固定的时间间隔就向服务器发起一次 HTTP 请求，询问"有没有新数据？"

```javascript
/**
 * 短轮询实现
 * @param {string} url - 请求地址
 * @param {number} interval - 轮询间隔（毫秒）
 * @param {Function} onSuccess - 成功回调
 */
function shortPoll(url, interval, onSuccess) {
    async function poll() {
        try {
            const res = await fetch(url);
            if (!res.ok) throw new Error(`HTTP ${res.status}`);
            const data = await res.json();

            if (data.hasNewData) {
                onSuccess(data);   // 有新数据则处理
            }
            // 无论结果如何，interval 后再次轮询
        } catch (err) {
            console.error('轮询请求失败:', err);
        }

        setTimeout(poll, interval);
    }

    poll();   // 启动第一次轮询
}

// 使用示例：每5秒查询一次是否有新消息
shortPoll('/api/messages/check', 5000, (data) => {
    showNotification(`你有 ${data.newCount} 条新消息`);
    updateMessageList(data.messages);
});
```

### 短轮询的核心参数：间隔时间的选择

间隔时间是短轮询最重要的参数——它直接决定了**实时性**和**资源消耗**之间的权衡：

```javascript
// 场景分析：不同间隔的影响
//
// interval = 1000ms (1秒)
// ├── 实时性：⭐⭐⭐⭐⭐ 极好（最多1秒延迟）
// └── 资源消耗：💀💀💀💀💀 极高（每天86400次请求！）
//     → 适用于：高频交易、实时竞拍等对延迟极度敏感的场景
//
// interval = 5000ms (5秒)
// ├── 实时性：⭐⭐⭐⭐ 良好（最多5秒延迟）
// └── 资源消耗：⚠️⚠️⚠️ 中等（每天17280次请求）
//     → 适用于：社交动态、消息通知等一般实时需求
//
// interval = 30000ms (30秒)
// ├── 实时性：⭐⭐ 一般（最多30秒延迟）
// └── 资源消耗：✅✅✅ 很低（每天2880次请求）
//     → 适用于：后台仪表盘、非紧急的数据刷新
```

### 短轮询的致命缺陷：浪费

短轮询最大的问题在于**绝大多数请求都是无效的**：

```javascript
// 现实中的数据统计
//
// 假设某用户的消息平均每2分钟收到一条新消息
// 如果轮询间隔为 5 秒：
//
// 2分钟内发出的请求数：120s / 5s = 24 次
// 其中有数据的请求：1 次
// 空请求（无新数据）：23 次
//
// 无效率 = 23 / 24 = 95.8%！！
//
// 也就是说，超过95%的请求都在问"有新消息吗？"
// 服务器回答："没有。" —— 然后你转身又问了一遍。
```

这种模式在网络带宽、服务器 CPU、电池电量等方面都是巨大的浪费。想象一下一个有 10 万用户的平台同时进行 5 秒间隔的短轮询——每秒产生 2 万次 HTTP 请求，其中大部分都是空转。

## 三、长轮询（Long Polling）：聪明地等待

长轮询是对短轮询的一种优化改进。核心思想很简单：**与其频繁地问"有新数据吗"，不如一次问完后就一直等着，直到真有新数据了再返回**。

```javascript
/**
 * 长轮询实现
 * 核心区别：服务器端在有新数据之前不会返回响应，
 *          请求会一直挂起（hang）直到超时或有数据。
 */
async function longPoll(url, maxWait = 30000) {
    while (true) {   // 无限循环，每次完成一轮后立即开始下一轮
        try {
            // 关键：这次请求可能会挂起很长时间！
            // 服务器会在以下情况之一返回：
            // ① 有新数据了 → 立即返回
            // ② 到达最大等待时间 → 返回空结果
            const res = await fetch(`${url}?timeout=${maxWait}`, {
                signal: AbortSignal.timeout(maxWait + 5000)  // 客户端也设个保险
            });

            if (!res.ok) throw new Error(`HTTP ${res.status}`);
            const data = await res.json();

            if (data.hasNewData && data.payload?.length > 0) {
                handleNewData(data.payload);   // 处理新数据
            }
            // 不管有没有数据，都立即发起新的长轮询请求
            // （这就是和短轮询的区别：不是等固定间隔，而是"立即下一次"）

        } catch (err) {
            if (err.name === 'TimeoutError') {
                console.warn('长轮询超时，重新发起');
            } else {
                console.error('长轮询出错:', err);
                await sleep(3000);   // 出错后稍等再试，避免疯狂重连
            }
        }
    }
}

function sleep(ms) { return new Promise(r => setTimeout(r, ms)); }

// 启动长轮询
longPoll('/api/messages/long-poll').catch(console.error);
```

### 长轮询的工作流程图解

```
时间轴 →

客户端:  ──GET────────────────────────────GET─────────────────────────GET──▶
             │                            │                           │
             │ (请求挂起中...)              │ (请求挂起中...)             │
             │                            │                           │
服务端:   ◀──(等待30s无数据)────────────◀──(第25s来了数据!)────────◀──────
             │ 返回空                       │ 立即返回数据               │
             ▼                            ▼                           ▼
客户端:  收到空→立即发下一请求           收到数据→处理后立即发下一请求    ...


对比短轮询:

客户端:  GET→空 GET→空 GET→空 GET→空 GET→空 GET→空 GET→空 GET→数据 GET→空 ...
         ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
         大量无效请求，服务器疲于应付
```

### 长轮询的优势与挑战

| 维度 | 短轮询 | 长轮询 |
|------|--------|--------|
| **消息及时性** | 取决于间隔，最长延迟 = 间隔 | 几乎即时（数据到达即返回） |
| **无效请求比例** | 极高（90%~99%） | 显著降低（仅在无数据期间末尾有一次空返） |
| **服务器压力** | 高频请求轰炸 | 连接长时间占用（每个用户持有一个挂起的请求） |
| **实现复杂度** | 低 | 中（需服务端配合实现挂起机制） |
| **资源消耗模式** | 大量短连接 | 少量长连接 |
| **适合数据频率** | 任意 | 中低频率更新 |

### 长轮询的服务端要求

长轮询能否有效工作，**关键取决于服务端的实现**。服务端必须具备"挂起请求直到有数据或超时"的能力：

```javascript
// Node.js Express 风格的长轮询服务端示意
app.get('/api/messages/long-poll', async (req, res) => {
    const timeout = parseInt(req.query.timeout) || 30000;
    const startTime = Date.now();

    // 循环检查是否有新消息
    while (true) {
        const newMessages = await checkForNewMessages(req.userId);

        if (newMessages.length > 0) {
            // 有新数据！立即返回
            return res.json({ hasNewData: true, payload: newMessages });
        }

        // 没有新数据，检查是否超时
        if (Date.now() - startTime >= timeout) {
            // 超时了，返回空结果让客户端重新请求
            return res.json({ hasNewData: false });
        }

        // 都没触发，等一小段时间再检查
        await new Promise(resolve => setTimeout(resolve, 2000));   // 每2秒检查一次
    }
});
```

```
├─────────────────┬──────────┬──────────┬──────────┬─────────────────┤

推荐选择指南：

① 只需要服务端推送少量文本数据？
   └─→ SSE（最简单，自带重连）

② 需要双向实时通信？
   └─→ WebSocket（功能最完整）

③ 无法使用 WebSocket/SSE（老IE、公司防火墙限制）？
   └─→ 长轮询（效果接近WebSocket）

④ 数据更新频率极低（几分钟甚至更久才变化一次）？
   └─→ 短轮询（足够用了，何必搞复杂的）

⑤ 需要兼容所有环境的最保守方案？
   └─→ 短轮询（零门槛，到处都能跑）
```

## 五、智能轮询：自适应策略

在实际项目中，最好的策略往往不是死守某一种方案，而是根据当前的网络条件、数据活跃度和设备状态**动态调整**策略：

```javascript
/**
 * AdaptivePoller —— 自适应智能轮询器
 *
 * 设计思路：
 * - 默认使用长轮询获得最佳实时性
 * - 当连续多次长轮询超时时，降级为短轮询（节省连接资源）
 * - 当网络恢复正常且有数据活跃时，升级回长轮询
 * - 页面不可见时（用户切换Tab）自动降频节省资源
 *
 */
class AdaptivePoller {
    constructor(url, options = {}) {
        this.url = url;
        this.options = {
            shortInterval: options.shortInterval || 15000,
            longTimeout: options.longTimeout || 25000,
            maxConsecutiveTimeouts: options.maxConsecutiveTimeouts || 3,
            ...options
        };

        this.mode = 'long';         // 当前模式: 'long' 或 'short'
        this.timeoutCount = 0;      // 连续超时计数
        this.isActive = true;       // 是否活跃
        this.onData = options.onData || (() => {});

        this._bindVisibilityListener();
        this.start();
    }

    start() {
        if (this.mode === 'long') {
            this._longPollLoop();
        } else {
            this._shortPollLoop();
        }
    }

    async _longPollLoop() {
        while (this.isActive && this.mode === 'long') {
            try {
                const controller = new AbortController();
                const timer = setTimeout(() => controller.abort(), this.options.longTimeout);

                const res = await fetch(this.url + '?mode=long-poll', {
                    signal: controller.signal
                });

                clearTimeout(timer);
                this.timeoutCount = 0;   // 成功则重置

                const data = await res.json();
                if (data.payload?.length) {
                    this.onData(data.payload);
                }

                // 短暂休眠后继续下一轮长轮询
                await this._sleep(500);

            } catch (err) {
                this.timeoutCount++;
                console.warn(`长轮询超时 (${this.timeoutCount}/${this.options.maxConsecutiveTimeouts})`);

                if (this.timeoutCount >= this.options.maxConsecutiveTimeouts) {
                    console.warn('连续超时过多，降级为短轮询');
                    this.downgradeToShort();
                }
            }
        }
    }

    async _shortPollLoop() {
        while (this.isActive && this.mode === 'short') {
            try {
                const res = await fetch(this.url + '?mode=short-poll');
                const data = await res.json();

                if (data.payload?.length) {
                    this.onData(data.payload);
                    this.timeoutCount = 0;

                    // 数据变活跃了，尝试升级回长轮询
                    if (this.timeoutCount === 0) {
                        console.log('检测到数据活跃，升级回长轮询');
                        this.upgradeToLong();
                        break;
                    }
                }
            } catch (err) {
                console.error('短轮询出错:', err);
            }

            await this._sleep(this.options.shortInterval);
        }
    }

    downgradeToShort() {
        this.mode = 'short';
        this.timeoutCount = 0;
        this.start();   // 启动短轮询循环
    }

    upgradeToLong() {
        this.mode = 'long';
        this.timeoutCount = 0;
        this.start();   // 启动长轮询循环
    }

    _bindVisibilityListener() {
        document.addEventListener('visibilitychange', () => {
            if (document.hidden) {
                // 用户切走了 → 降级为低频短轮询
                console.log('页面不可见，进入节能模式');
                this.savedMode = this.mode;
                this.mode = 'short';
                this.options.shortInterval = 60000;   // 降低到60秒
            } else {
                // 用户回来了 → 恢复之前的模式
                console.log('页面可见，恢复正常模式');
                if (this.savedMode === 'long') {
                    this.upgradeToLong();
                }
                this.options.shortInterval = 15000;   // 恢复默认
            }
        });
    }

    _sleep(ms) { return new Promise(r => setTimeout(r, ms)); }

    destroy() {
        this.isActive = false;   // 所有循环都会停止
    }
}

// 使用
const poller = new AdaptivePoller('/api/notifications', {
    onData(notifications) {
        showNotificationBadge(notifications.length);
    },
    longTimeout: 20000,
    shortInterval: 10000
});
```

> **哲学思考**：轮询模式的演进史，实际上是人类在面对技术约束时的创造力体现。短轮询是对"HTTP 不能主动推送"这一限制最笨拙但也最诚实的回应——我解决不了这个问题，但我可以用暴力绕过去。长轮询则是第一次智力飞跃：既然不能改变协议，那就改变使用协议的方式——把"快速往返"变成"耐心等待"。WebSocket 和 SSE 则是第二次飞跃：不再绕路，而是从根本上扩展协议的能力。但有趣的是，即使在今天，短轮询和长轮询仍然没有被淘汰——因为有时候最简单的方案恰恰是最可靠的。当你在地铁隧道中信号微弱的时候，当你面对一个不支持 WebSocket 的老旧代理服务器的时候，当你的项目预算不允许搭建专门的 WebSocket 集群的时候——那个最朴素的想法"我不停地问，直到你回答为止"仍然是你手中最锋利的剑。技术的价值不在于它的花哨程度，而在于它在特定约束下解决问题的能力。
