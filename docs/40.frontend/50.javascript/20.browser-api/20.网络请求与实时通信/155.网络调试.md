# 网络请求调试 —— Chrome Network 面板、Throttling、复制为 fetch

> **本文的目标**：掌握使用 Chrome DevTools 进行网络请求调试的核心技能——Network 面板的深度使用、网络限速模拟、请求复制与重放、以及常见网络问题的诊断方法。无论你使用 [Fetch](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/105.Fetch%20API.md)、[XHR](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/100.XMLHttpRequest.md) 还是 [WebSocket](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/125.WebSocket.md)，这些调试技能都是必备的生产力工具。

## 一、Network 面板：网络世界的显微镜

Chrome DevTools 的 Network 面板是每个前端开发者每天都会打开的工具之一。它像一台高倍显微镜，让你能看到每一个网络请求的完整生命周期——从发出请求的那一刻到收到最后一个字节。

打开方式：`F12`（或右键→检查）→ 点击 **Network** 标签页。

```javascript
// 为了演示，我们先发起一些不同类型的请求
fetch('/api/users');                    // 普通 GET
fetch('/api/login', {                   // POST with JSON
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ user: 'test' })
});
fetch('/static/image.png');             // 图片资源
const ws = new WebSocket('wss://...');  // WebSocket 连接
```

### 请求列表的核心列

Network 面板默认显示以下关键列（可通过右键表头自定义）：

| 列名 | 含义 | 示例 |
|------|------|------|
| **Name** | 请求的资源名称或URL | `users`, `login`, `image.png` |
| **Status** | HTTP 状态码 | `200`, `304`, `404`, `500` |
| **Type** | 资源类型 | `xhr`, `fetch`, `document`, `script`, `stylesheet`, `image`, `websocket` |
| **Initiator** | 发起请求的代码位置 | `index.js:42` 或 `Parser`（HTML解析器自动发起） |
| **Size** | 传输大小（含压缩） / 解压大小 | `24 KB / 78 KB` |
| **Time** | 总耗时 | `230 ms` |
| **Waterfall** | 时间线瀑布图 | 彩色条形图 |

### 状态码的颜色含义

Chrome 用颜色直观地标记了不同类别的状态码：

```
状态码颜色速查：
🟢 绿色/灰色  → 2xx 成功（200, 204, 206...）
🟡 黄色      → 3xx 重定向（301, 302, 304...）
🔴 红色      → 4xx/5xx 错误（400, 401, 403, 404, 500, 502...）
⚪ 灰色       → 来自缓存 (from disk cache / from memory cache)
🟣 紫色      → 预检请求 OPTIONS (CORS preflight)
```

```
│                                                      │
└──────────────────────────────────────────────────────┘
```

**Headers 选项卡**是最常用的，它分为三个区域：

#### General 区域

记录了请求的基础元信息。其中几个关键字段值得特别关注：

```http
# Request Method — 请求方法
GET    # 数据获取
POST   # 数据提交
PUT    # 更新（全量替换）
PATCH  # 更新（部分修改）
DELETE # 删除

# Status Code & Text — 状态码及说明
200 OK              # 成功
201 Created         # 创建成功（常用于 POST）
204 No Content      # 成功但无返回体
301 Moved Permanently  # 永久重定向
304 Not Modified       # 未修改（缓存命中）
400 Bad Request       # 请求参数错误
401 Unauthorized      # 未认证
403 Forbidden         # 无权限
404 Not Found         # 资源不存在
500 Internal Server Error  # 服务端内部错误
502 Bad Gateway       # 网关错误
503 Service Unavailable  # 服务不可用

# Remote Address — 目标服务器IP和端口
# 如果这里显示的不是预期的地址，
# 可能经过了代理/CDN/负载均衡

# Referrer Policy — 引用策略
# 控制请求头中 Referer 字段的发送范围
```

#### Response Headers 区域

服务器的响应头部包含了大量关于响应本身的信息：

```http
Content-Type: application/json; charset=utf-8
# 响应体的媒体类型和字符编码
# 常见值：application/json, text/html, text/plain,
#        image/png, application/pdf, text/event-stream(SSE)

Cache-Control: no-cache, must-revalidate
# 缓存控制策略：
#   no-store      → 不缓存任何内容
#   no-cache      → 缓存前必须验证（每次都要询问服务器）
#   max-age=3600  → 缓存3600秒后过期
#   private       → 仅浏览器可缓存（CDN不缓存）

ETag: W/"a29e-f8c1b2d3e4f5"
# 资源的版本标识（弱校验以W/开头）
# 用于条件请求 If-None-Match / If-Match

Set-Cookie: session=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
# Cookie 设置指令

Access-Control-Allow-Origin: *
# CORS 配置（详见[《CORS跨域》](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/115.CORS跨域.md)）
```

#### Request Headers 区域

浏览器自动附加的请求头部：

```http
Accept: */*
# 客户端期望的响应类型

Accept-Encoding: gzip, deflate, br
# 支持的内容压缩算法
# br = Brotli（压缩率最高）、gzip、deflate

Cookie: session=abc123; theme=dark
# 当前域名下的所有 Cookie
# 注意：HttpOnly 的 Cookie 不会出现在 JS 中，
#       但 DevTools 和实际网络请求中仍然会携带

Authorization: Bearer eyJhbGci...
# 认证令牌（如果代码中手动设置了的话）

Sec-Fetch-Dest: empty
Sec-Fetch-Mode: cors
Sec-Fetch-Site: same-site
Sec-Fetch-* 系列：安全相关的元数据头
# 帮助服务器判断请求是否可信
# Mode=cors 表示跨域请求
# Site=same-site 表示同站请求
```

## 二、Throttling：模拟真实网络环境

你的开发机器可能连接着千兆光纤，在 localhost 上开发一切飞快。但真实用户的网络环境可能是 3G 移动网络、拥挤的 WiFi 或者跨国访问。**网络限速（Throttling）** 让你在开发阶段就能发现慢网环境下的问题。

### 使用 Throttling

在 Network 面板顶部找到限速下拉菜单：

```
位置：Network 工具栏 → 🌐 No throttling 下拉菜单

预设选项：
├─ No throttling          （不限速，默认）
├─ Fast 3G               （下行1.5Mbps，上行750ms RTT）
├─ Slow 3G               （下行500Kbps，上行2000ms RTT）
├─ Regular 4G            （下行4Mbps，上行150ms RTT）
├─ Fast 4G/LTE           （下行20Mbps，上行33ms RTT）
└─ Custom...             （自定义速度）
```

选择一个限速配置后刷新页面，你会立刻感受到差异——那些在本地秒开的页面现在可能要加载好几秒了。

### 自定义限速配置

点击 **Custom...** 可以创建精确匹配目标用户环境的限速配置：

```javascript
// 常见的自定义配置参考：

// 场景1：地铁/高铁上的移动网络（信号不稳定+丢包率高）
// Download: 800 kbps
// Upload: 300 kbps
// Latency (RTT): 350ms
// Packet Loss: 5%

// 场景2：偏远地区的 ADSL 宽带
// Download: 2 Mbps
// Upload: 512 kbps
// Latency: 80ms
// Packet Loss: 0%

// 场景3：跨太平洋访问（高延迟为主因）
// Download: 50 Mbps
// Upload: 20 Mbps
// Latency: 200ms
// Packet Loss: 0%
```

### Throttling 能帮你发现什么？

```javascript
// 问题1：首屏白屏时间过长
// 原因：主JS文件太大，在3G网络下需要15秒才能下载完
// 解决：代码分割(code splitting)、懒加载(lazy loading)

// 问题2：图片渐进式加载体验差
// 原因：一张 2MB 的背景图阻塞渲染
// 解决：使用 WebP 格式、设置合理的尺寸、使用 loading="lazy"

// 问题3：API 请求超时
// 原因：在慢网络下请求超过了默认的超时时间
// 解决：增加超时阈值、实现重试机制（参考[《Fetch高级用法》](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/110.Fetch高级用法.md)）

// 问题4：竞态条件
// 原因：用户快速点击按钮，在慢网络上触发了多次重复请求
// 解决：请求防抖(debounce)、乐观锁(optimistic lock)、取消旧请求
```

## 三、"复制为 fetch"：从调试到代码的捷径

这是 Chrome 提供的一个极其实用的功能——**把 Network 面板中的请求一键转换为可执行的 fetch 代码**：

操作步骤：
1. 打开 Network 面板
2. 找到你想要复制的请求
3. 右键点击该请求
4. 选择 **Copy** → **Copy as fetch**

```javascript
// 点击后会自动复制到剪贴板，粘贴出来长这样：
fetch("https://api.example.com/v2/users?page=1&size=20", {
  "headers": {
    "accept": "application/json",
    "accept-language": "zh-CN,zh;q=0.9,en;q=0.8",
    "authorization": "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "content-type": "application/json",
    "sec-ch-ua": "\"Chromium\";v=\"122\", \"Not(A:Brand\";v=\"24\"",
    "sec-fetch-dest": "empty",
    "sec-fetch-mode": "cors",
    "sec-fetch-site": "same-site"
  },
  "referrerPolicy": "strict-origin-when-cross-origin",
  "body": "{\"filters\":{\"status\":\"active\"}}",
  "method": "POST",
  "mode": "cors",
  "credentials": "include"
});

// 你可以直接在 Console 里运行这段代码来重现请求！
```

### 其他复制选项

除了 `Copy as fetch`，还有多个有用的变体：

| 选项 | 输出格式 | 适用场景 |
|------|---------|---------|
| **Copy as fetch** | `fetch(...)` 代码 | 前端开发调试 |
| **Copy as cURL** | `curl` 命令 | 后端联调、分享给同事 |
| **Copy as Node.js fetch** | Node.js 版 fetch | 服务端脚本测试 |
| **Copy request body** | 仅请求体 | 快速查看 POST 数据 |
| **Copy request headers** | 仅请求头 | 检查头部配置 |

### cURL 的妙用

`Copy as cURL` 在跨团队协作时特别有价值——你可以把一个复杂的请求（包括所有自定义头部、Cookie、POST body）精确地分享给后端同事，让他们能完全复现你遇到的问题：

```bash
# 复制出的 curl 命令
curl 'https://api.example.com/v2/users' \
  -H 'accept: application/json' \
  -H 'authorization: Bearer eyJhb...' \
  -H 'content-type: application/json' \
  --data-raw '{"page":1,"size":20}'
```

## 四、常见网络问题的诊断流程

面对一个"请求失败了"的问题，建议按照以下步骤系统性排查：

```
诊断流程图：

① 确认请求是否发出了？
   └─ Network 面板中有这条请求吗？
       ├─ 没有 → 检查 JS 是否执行到了 fetch/xhr 调用处
       │          （加 breakpoint/console.log 确认）
       └─ 有 → 继续②

② 确认请求的状态码是什么？
   ├─ (pending) → 请求挂起了，检查是否被其他请求阻塞
   ├─ 2xx 绿色 → 请求成功了！问题可能在响应解析逻辑
   ├─ 3xx 黄色 → 重定向循环？检查 Location 头部
   ├─ 4xx 红色 → 客户端问题
   │   ├── 401 → Token 过期？未登录？
   │   ├── 403 → 权限不足？CORS 配置问题？
   │   ├── 404 → URL 拼写错误？路由不存在？
   │   └── 422 → 参数校验失败？（查看 Response Body）
   └─ 5xx 红色 → 服务端问题
       ├── 500 → 后端代码异常（联系后端排查日志）
       ├── 502 → 网关错误（Nginx/负载均衡配置问题）
       └── 503 → 服务不可用（正在部署？过载保护？）

③ 确认 CORS 相关问题？
   └─ 查看 Console 面板是否有红色 CORS 错误提示
       └─ 参考 [《CORS跨域》](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/115.CORS跨域.md) 排查

④ 确认响应内容是否符合预期？
   └─ Preview / Response 选项卡
       ├── JSON 格式是否正确？
       └── 是否返回了 HTML 错误页面而非预期 JSON？
           （比如 Nginx 的 502 Bad Gateway 页面）
```

### Timing 选项卡：性能瓶颈定位

Timing 选项卡展示了请求各个阶段的耗时分布，是优化网络性能的关键依据：

```
Timing 时间线分解：

Queueing        ████████░░  45ms    → 排队等待（浏览器对同域并发请求数有限制）
Stalled         ██░░░░░░░░  12ms    → 因其他原因等待（如只允许6个TCP连接）
DNS Lookup      ██████████  89ms    → DNS 解析（首次访问某域名时发生）
Initial connection ████████████  156ms → TCP 三次握手 + SSL/TLS 握手
Request Sent    █░░░░░░░░░   3ms    → 发送请求（通常极快）
Waiting (TTFB)  ████████████████████  420ms  → ★ 最关键的指标！
                                            Time To First Byte
                                            服务器处理时间（含数据库查询等）
Content Download ██████████████████  280ms  → 下载响应体

Total: ~1005ms

优化方向：
  TTFB过高 → 优化服务端查询、添加缓存、减少数据库往返
  下载时间长 → 启用gzip/brotli压缩、减小响应体积、使用CDN
  DNS耗时高 → 减少外部域名数量、预解析 dns-prefetch
```

> **哲学思考**：调试工具本质上是**人类感知能力的延伸**。我们的肉眼看不见网络包如何在光缆中穿梭，耳朵听不到 HTTP 请求在毫秒级的时间尺度上完成了握手、加密、传输、解密的全套舞蹈。DevTools 的 Network 面板就像一台时光机——它让这些发生在微观时间维度里的事件变得可见、可测量、可比对。好的工程师不只是会写代码的人，更是善于观察的人；而善于观察的前提是有好的观察工具。学会熟练使用 Network 面板，就等于给自己的开发技能装上了一副高清眼镜——以前模糊不清的问题，现在能看得清清楚楚。这不仅是效率的提升，更是思维方式的升级：从"猜测为什么出错"变成了"确切知道哪里出了错"，从"感觉有点慢"变成了"TTFB 是 420ms，瓶颈在服务端查询"。数据驱动的决策，从这里开始。
