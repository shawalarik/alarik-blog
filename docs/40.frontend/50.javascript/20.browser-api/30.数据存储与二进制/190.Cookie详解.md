# Cookie 详解 —— 属性、作用域、安全性、document.cookie 的读写

Cookie 是 Web 最古老的客户端存储机制，诞生于 1994 年。尽管如今有了 [localStorage](/40.frontend/50.javascript/20.browser-api/30.数据存储与二进制/195.localStoragesessionStorage.md)、[IndexedDB](/40.frontend/50.javascript/20.browser-api/30.数据存储与二进制/160.IndexedDB.md) 等更现代的替代方案，Cookie 依然在某些场景下不可或缺——特别是身份认证与会话管理。理解 Cookie 的工作原理，是掌握 Web 安全和 [CORS](/40.frontend/50.javascript/20.browser-api/20.网络请求与实时通信/115.CORS跨域.md) 的前提。

## 一、Cookie 是什么？

Cookie 是服务器通过 `Set-Cookie` 响应头发送到浏览器的一小段数据（通常不超过 4KB），浏览器会将其保存在本地，并在后续对该服务器的每次请求中自动附带发送回去。

```http
# 交互过程示意

① 客户端                              服务端
 │                                      │
 │ ── GET /login POST {user,pwd} ────▶ │
 │                                      │  验证凭据成功
 │ ◀── 200 OK                           │
 │     Set-Cookie: session=abc123       │ ← 服务端说："记住这个令牌"
 │     Set-Cookie: theme=dark           │
 │                                      │
 │ ── GET /dashboard ─────────────────▶│
 │     Cookie: session=abc123; theme=dark  │ ← 浏览器自动带上所有cookie
 │                                      │
 │ ◀── 200 OK  (个性化内容)             │  服务端根据 cookie 识别用户
```

### 生活类比：会员手牌

Cookie 就像健身房或洗浴中心的**电子手环/手牌**：
- 你首次进场时前台发给你一枚手环（服务器 Set-Cookie）
- 手环上印着你的会员信息和有效期（Cookie 的值和属性）
- 之后你在场馆内每到一个区域（发起新请求），都需要刷一下手环（自动携带 Cookie）
- 工作人员通过手环识别你是谁、有什么权限（服务端验证 Session）
- 手环有过期时间，到期后失效（Expires / Max-Age）
- 不同场馆的手环互不通用（Domain / Path 作用域限制）

## 二、document.cookie：读写 Cookie

浏览器提供了 `document.cookie` 这个 API 来操作 Cookie，但它有一些特殊的行为：

### 读取 Cookie

```javascript
// 读取所有 Cookie（当前页面可访问的）
console.log(document.cookie);
// → "session=abc123; theme=dark; lang=zh-CN; _ga=GA1.2.123456789"

// 返回的是一个字符串！以分号+空格分隔的名值对
// 注意：HttpOnly 的 Cookie 在这里读不到（安全设计）

// 解析为对象的工具函数
function parseCookies() {
    return Object.fromEntries(
        document.cookie.split('; ').map(pair => {
            const [key, ...valParts] = pair.split('=');
            return [key, valParts.join('=')];   // 值中可能包含 '=' 号
        })
    );
}

const cookies = parseCookies();
console.log(cookies.session);   // 'abc123'
console.log(cookies.theme);     // 'dark'
```

### 设置（写入）Cookie

```javascript
// 设置 Cookie —— 直接赋值即可（注意：不会覆盖其他 Cookie）
document.cookie = 'name=Alarik';
document.cookie = 'theme=dark';

// 设置带属性的 Cookie
document.cookie = 'session=xyz789; path=/; max-age=3600; SameSite=Lax';
document.cookie = 'prefs={"lang":"zh"}';  // 值可以是任意字符串

// 修改已有 Cookie —— 重新设置同名的就行
document.cookie = 'theme=light';   // dark → light

// 删除 Cookie —— 设置 max-age=0 且值清空
document.cookie = 'name=; max-age=0; path=/';
```

### ⚠️ document.cookie 的陷阱

```javascript
// 陷阱1：赋值是追加而非替换
document.cookie = 'a=1';
document.cookie = 'b=2';
console.log(document.cookie);   // "a=1; b=2" （两个都在！）

// 陷阱2：读取只能读到全部，无法单独读某一个
document.cookie = 'x=hello';
// 没有 document.cookie['x'] 这种写法！

// 陷阱3：一次只能设置一个 Cookie
document.cookie = 'a=1; b=2';   // ❌ 这会把 "; b=2" 当作第一个 Cookie 的值的一部分！
// 正确做法：分两次设置
document.cookie = 'a=1';
document.cookie = 'b=2';

// 陷阱4：特殊字符需要编码
document.cookie = 'msg=hello world; delicious!';
// 分号会被误认为是分隔符！应该 encodeURIComponent
document.cookie = 'msg=' + encodeURIComponent('hello world; delicious!');
// → "msg=hello%20world%3B%20delicious%21"
```

## 三、Cookie 属性详解

每个 Cookie 都可以通过属性来精细控制其行为：

### Expires / Max-Age：生存时间

```javascript
// Expires —— 绝对过期时间（GMT 格式字符串）
document.cookie = 'temp=v1; expires=Tue, 23 Apr 2027 10:00:00 GMT';
// 到指定日期后浏览器会自动删除此 Cookie

// Max-Age —— 相对存活秒数（推荐使用，更可靠）
document.cookie = 'temp=v2; max-age=3600';     // 1小时后过期
document.cookie = 'temp=v3; max-age=-1';        // 立即删除
document.cookie = 'temp=v4; max-age=0';          // 同上（立即删除）

// 不设过期时间 → Session Cookie（关闭浏览器标签页即消失）
document.cookie = 'temporal=temp-value';
```

### Domain / Path：作用域

```javascript
// Domain —— 哪些域名可以接收此 Cookie
//
// 默认值：当前页面的 hostname（不含子域名）
//
document.cookie = 'site=main; domain=example.com';
// example.com 和所有子域名 (app.example.com, api.example.com...) 都能收到
//
document.cookie = 'sub=only-here; domain=app.example.com';
// 只有 app.example.com 能收到，主域名和其他子域名不行
//
// ⚠️ 不能设置为其他完全不相关的域名！（安全限制）

// Path —— 域名下的哪些路径能接收此 Cookie
//
// 默认值：当前路径
//
document.cookie = 'global=g1; path=/';
// 整站都能访问（最宽泛）
//
document.cookie = 'area=a1; path=/dashboard';
// 只有 /dashboard 及其子路径 (/dashboard/settings ...) 能访问
//
document.cookie = 'strict=s1; path=/admin/users';
// 仅 /admin/users 及其子路径可用
```

### Secure / HttpOnly：安全属性

```javascript
// Secure —— 仅在 HTTPS 连接中发送
document.cookie = 'secret=value; Secure';
// 如果页面是 http:// 开头，浏览器不会把这个 Cookie 发送给服务器
// 即使你在 JS 中设置了它，它也不会被发送出去

// HttpOnly —— 防止 JavaScript 访问（防 XSS 窃取）
// 这个属性只能由服务端通过 Set-Cookie 头部设置！
// document.cookie 无法设置 HttpOnly 属性！
//
// Set-Cookie: sessionId=abc123; HttpOnly
// → JS 读不到这个 Cookie（document.cookie 不会包含它）
// → 但请求时会正常发送给服务器
// → 这是防止 XSS（跨站脚本攻击）窃取 Session 的第一道防线
```

### SameSite：跨站控制

SameSite 是近年来最重要的 Cookie 安全属性，用于防御 CSRF（跨站请求伪造）攻击：

```javascript
// SameSite=Strict（最严格）
// 完全禁止跨站携带 Cookie
// 即使用户从外部链接点击进入也不会带 Cookie
// 适用场景：银行转账等高敏感操作
Set-Cookie: bankToken=xxx; SameSite=Strict

// SameSite=Lax（默认值，推荐）
// 允许顶级导航（如点击链接跳转）携带 Cookie
// 但阻止第三方网站发出的 POST/PUT/DELETE 等请求携带 Cookie
// 适用场景：大多数网站的正常使用
Set-Cookie: sessionId=yyy; SameSite=Lax

// SameSite=None（宽松）
// 允许跨站请求携带 Cookie（必须配合 Secure 使用）
// 适用场景：嵌入第三方的组件（如视频播放器、社交分享按钮）
Set-Cookie: tracker=zzz; SameSite=None; Secure
```

| SameSite 值 | 点击外链跳转 | 第三方 iframe POST | 第三方 img/fetch | 配合 Secure？ |
|-------------|------------|-------------------|-------------------|-------------|
| `Strict` | 不携带 | 不携带 | 不携带 | 可选 |
| `Lax` | **携带** | 不携带 | 不携带 | 可选 |
| `None` | **携带** | **携带** | **携带** | **必须** |

## 四、Cookie vs 其他存储方案的对比

| 维度 | Cookie | localStorage | sessionStorage | IndexedDB |
|------|--------|--------------|-----------------|-----------|
| **容量** | ~4KB | ~5MB | ~5MB | 数百 MB ~ GB |
| **随请求发送** | 自动发送 | 不发送 | 不发送 | 不发送 |
| **可设置过期** | Max-Age/Expires | 永久（除非手动删） | 标签页关闭即删 | 永久（除非手动删） |
| **服务端可写** | Set-Cookie 头部 | 不能 | 不能 | 不能 |
| **HttpOnly 支持** | 支持 | 不支持 | 不支持 | 不适用 |
| **跨标签共享** | 可配 | 可配 | 否（仅同源同标签） | 可配 |
| **数据类型** | 字符串 | 字符串 | 字符串 | 任意对象/二进制 |

> **哲学思考**：Cookie 的设计反映了早期 Web 的信任模型——**服务器主导一切**。Cookie 由服务端创建（Set-Cookie）、由服务端规定规则（各种属性）、在服务端认为合适的时机由浏览器自动呈递。这种"服务器说了算"的模式在当时是合理的，因为 Web 还是一个相对单纯的信息展示平台。但随着 Web 应用越来越复杂、前后端职责日益分离，Cookie 的这种"被动携带"特性反而成为了安全隐患（CSRF）和性能负担（每次请求都带着可能不需要的 Cookie）。新的存储方案（localStorage、IndexedDB）把控制权还给了前端——数据什么时候存、怎么存、发给谁，全部由 JavaScript 决定。这不是倒退而是进化：**合适的事情交给合适的层级去做**。Cookie 回归到了它最擅长的领域——身份认证的状态维持；而纯粹的数据存储交给了更专业的工具。
