# CSRF —— 原理、防御（Token、SameSite）

## 什么是 CSRF

CSRF（Cross-Site Request Forgery，跨站请求伪造）这个名字本身就揭示了它的本质——**跨站的、伪造的请求**。

如果说 XSS 是"让受害者执行攻击者的代码"，那 CSRF 就是"以受害者的身份执行攻击者想要的操作"。区别在于：XSS 注入的是代码，CSRF 利用的是**身份凭证的自动携带机制**。

想象一个生活场景：你有一张签了名的空白支票放在桌上。小偷不需要知道你的签名长什么样——他只需要在支票上填上金额和收款人，然后拿去兑现。银行看到你的签名就会放行。CSRF 就是这个原理：浏览器自动带上 Cookie 发请求，服务器只认 Cookie 不认人。

```javascript
// 假设用户已登录 bank.com（拥有有效的 session cookie）

// 攻击者在 evil.com 页面中放置：
const img = new Image();
img.src = 'https://bank.com/transfer?to=attacker&amount=10000';

// 浏览器访问 evil.com 时，会自动向 bank.com 发送 GET 请求
// 关键点：该请求会**自动附带** bank.com 的 Cookie！
// 服务器收到请求 + 有效 Cookie → 认为这是用户的真实操作 → 执行转账
```

注意这里没有任何 JavaScript 脚本注入。整个攻击利用的就是浏览器**同源请求自动携带 Cookie**这一"贴心设计"。这个设计的初衷是好的——让用户不用每次都重新登录——但在 CSRF 场景下却成了致命漏洞。

## CSRF 的攻击条件

CSRF 要成功实施，必须同时满足三个条件：

1. **受害者已完成目标站点的认证**（Cookie 有效且未过期）
2. **攻击者能诱导受害者访问恶意页面**
3. **目标站点没有验证请求的真实来源**

```html
<!-- 攻击页面 evil.com/attack.html -->
<!-- 用户点击后，自动发起转账请求 -->

<h1>恭喜你中奖了！</h1>
<p>请点击下方按钮领取奖品：</p>

<!-- 隐藏表单，自动提交 -->
<form id="csrf-form"
      method="POST"
      action="https://bank.com/transfer">
  <input type="hidden" name="to" value="attacker_account" />
  <input type="hidden" name="amount" value="99999" />
</form>

<button onclick="document.getElementById('csrf-form').submit()">
  立即领取
</button>
```

**哲学思考**：CSRF 暴露了 HTTP 协议设计中一个根本性的张力——**便利性与安全性之间的权衡**。Cookie 自动携带是为了用户体验（免登录），但"自动"意味着"不经确认"，而不经确认的操作恰恰是安全的大忌。每一次便利性的提升，都在暗中扩大攻击面。这不仅是技术问题，更是一个关于信任边界的哲学命题：我们到底应该信任什么？浏览器？用户？还是每次交互都需要明确的授权？

## CSRF 的常见攻击载体

### GET 型 CSRF

GET 请求是最容易利用的，因为可以通过 `<img>`、`<script>` 等标签自动触发：

```html
<!-- 方式一：图片标签 -->
<img src="https://example.com/delete?id=123"
     style="display:none" />

<!-- 方式二：CSS background -->
<style>
  body {
    background: url('https://example.com/action?cmd=delete');
  }
</style>

<!-- 方式三：script 标签 -->
<script src="https://example.com/api/export?format=all"></script>
```

这些标签在加载资源时会自动发送 GET 请求，无需任何用户交互。这就是为什么 **GET 请求不应该用于改变状态的操作**——这是一个 RESTful 设计原则背后的安全考量。

### POST 型 CSRF

POST 需要 `<form>` 表单提交，通常需要用户点击：

```html
<!-- 自动提交的隐藏表单 -->
<form id="hack"
      method="POST"
      action="https://target.com/change-password">
  <input type="hidden" name="new_password" value="hacked123" />
  <input type="hidden" name="confirm_password" value="hacked123" />
</form>

<script>
  // 页面加载后自动提交
  window.onload = () => document.getElementById('hack').submit();
</script>
```

POST 型 CSRF 比 GET 型稍难利用（需要表单），但仍然非常常见。很多开发者误以为"POST 比 GET 安全"就高枕无忧了，这种想法本身就是危险的。

### JSON 型 CSRF

随着 API 普及使用 JSON 格式，出现了针对 JSON 接口的 CSRF 变体：

```javascript
// 使用 fetch 发起跨域 POST + JSON
fetch('https://api.example.com/user/update', {
  method: 'POST',
  credentials: 'include',  // 携带 Cookie
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email: 'attacker@evil.com' }),
});
```

但这里有一个关键限制：跨域请求如果带有自定义 Header（如 `Content-Type: application/json`），浏览器会先发预检请求（OPTIONS）。服务端如果没有正确配置 CORS，这个请求会被拦截。不过，如果 CORS 配置过于宽松（如 `Access-Control-Allow-Origin: *` 且 `Access-Control-Allow-Credentials: true`），攻击依然可以成功。

## CSRF 防御策略

### SameSite Cookie 属性

SameSite 是目前最推荐、最简单的 CSRF 防御手段。它控制第三方网站发起请求时是否携带 Cookie：

```javascript
// 服务端设置 SameSite 属性的三种模式

// Strict —— 最严格，所有跨站请求都不携带 Cookie
'Set-Cookie: session_id=abc; SameSite=Strict'

// Lax —— 允许安全的跨站 GET（如从搜索引擎跳转），
//        但阻止 POST 和其他可能改变状态的请求
'Set-Cookie: session_id=abc; SameSite=Lax'

// None —— 允许跨站携带（需要配合 Secure 属性）
'Set-Cookie: session_id=abc; SameSite=None; Secure'
```

三种模式的对比：

| 模式 | 同站请求 | 跨站导航 (GET) | 跨站 POST/子资源 | 适用场景 |
|------|---------|----------------|-----------------|---------|
| `Strict` | ✅ 携带 | ❌ 不携带 | ❌ 不携带 | 高安全需求 |
| `Lax` | ✅ 携带 | ✅ 携带 | ❌ 不携带 | **大多数场景的默认选择** |
| `None` | ✅ 搭带 | ✅ 携带 | ✅ 携带 | 第三方嵌入必需 |

```javascript
// Express 中设置 SameSite Cookie
app.use(session({
  secret: process.env.SESSION_SECRET,
  cookie: {
    sameSite: 'lax',  // 推荐 Lax 模式
    secure: process.env.NODE_ENV === 'production',  // 生产环境启用
    httpOnly: true,
    maxAge: 24 * 60 * 60 * 1000,  // 24 小时
  },
}));
```

**Lax 模式为什么成为默认推荐？** 因为它取得了最佳平衡——允许用户通过外部链接正常进入网站（搜索引擎、分享链接等），同时阻止恶意的跨站状态变更操作。

### CSRF Token（防伪令牌）

Token 方案的核心思想：**每个表单都附带一个随机生成的不可预测令牌，服务端验证令牌是否匹配**。

```javascript
/**
 * CSRF Token 工具类
 * 包含生成、验证、注入的完整逻辑
 */
class CsrfTokenManager {
  /**
   * 生成随机 CSRF Token
   * 使用 crypto.randomUUID() 或 fallback 到随机字符串
   */
  static generate() {
    if (typeof crypto !== 'undefined' && crypto.randomUUID) {
      return crypto.randomUUID();
    }
    // Fallback: 32 字节随机 hex
    const bytes = new Uint8Array(32);
    crypto.getRandomValues(bytes);
    return Array.from(bytes, b => b.toString(16).padStart(2, '0')).join('');
  }

  /**
   * 将 token 注入到 HTML 表单中
   */
  static injectIntoForm(formElement, token) {
    const input = document.createElement('input');
    input.type = 'hidden';
    input.name = '_csrf';           // 服务端期望的字段名
    input.value = token;
    formElement.appendChild(input);
  }

  /**
   * 将 token 设置到请求头中（适用于 AJAX）
   */
  static setHeader(token) {
    // 存储供后续请求使用
    this._token = token;
  }

  static getHeader() {
    return { 'X-CSRF-Token': this._token };
  }
}

// ====== 客户端使用示例 ======

// 1. 页面加载时获取 token（从 meta 标签或接口）
const csrfToken = document.querySelector('meta[name="csrf-token"]')
  ?.content;

// 2. 表单提交前注入
document.querySelectorAll('form[method="POST"]').forEach(form => {
  if (!form.querySelector('input[name="_csrf"]')) {
    CsrfTokenManager.injectIntoForm(form, csrfToken);
  }
});

// 3. AJAX 请求附加 token
async function submitData(data) {
  const res = await fetch('/api/data', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      ...CsrfTokenManager.getHeader(),
    },
    body: JSON.stringify(data),
  });
  return res.json();
}
```

```javascript
// ====== Node.js / Express 服务端实现 ======

const crypto = require('crypto');

class CsrfProtection {
  constructor(options = {}) {
    this.tokenLength = options.tokenLength || 48;
    this.sessionKey = options.sessionKey || 'csrfToken';
    this.headerName = options.headerName || 'x-csrf-token';
    this.fieldName = options.fieldName || '_csrf';
  }

  // 中间件：生成 token 并存入 session
  middleware() {
    return (req, res, next) => {
      const token = crypto.randomBytes(this.tokenLength).toString('hex');

      req.session.csrfToken = token;

      // 通过多种方式传递给前端
      res.locals.csrfToken = token;
      res.setHeader('X-CSRF-Token', token);

      next();
    };
  }

  // 验证 token
  verify(req) {
    const storedToken = req.session?.csrfToken;
    const submittedToken =
      req.headers[this.headerName.toLowerCase()] ||
      req.body?.[this.fieldName];

    if (!storedToken || !submittedToken) return false;

    // 使用时间恒定比较，防止时序攻击
    return crypto.timingSafeEqual(
      Buffer.from(storedToken),
      Buffer.from(submittedToken)
    );
  }
}

// 使用
const csrf = new CsrfProtection();

app.get('/form', csrf.middleware(), (req, res) => {
  res.render('form', { csrfToken: res.locals.csrfToken });
});

app.post('/submit', (req, res) => {
  if (!csrf.verify(req)) {
    return res.status(403).json({ error: 'CSRF validation failed' });
  }
  // 处理合法请求...
});
```

**Token 方案的关键细节**：
- Token 必须是不可预测的（使用密码学安全的随机数生成器）
- 每个 session 一个 token，或每个表单一个 token（更安全）
- Token 必须在验证后立即失效（一次性使用）或定期轮换
- 使用 `crypto.timingSafeEqual` 进行比较，防止基于响应时间的侧信道攻击

### 双重 Cookie 验证

这是一种轻量级替代方案，适合无法使用 Session 的场景：

```javascript
/**
 * 双重 Cookie 验证
 * 原理：将 CSRF token 同时存在 Cookie 和请求参数/头中，
 *       服务端比对两者是否一致。
 *
 * 攻击者可以读取 Cookie（通过 XSS），也可以设置子域名 Cookie，
 *       但无法同时做到两件事（同源策略限制）
 */

// 客户端：从 Cookie 中读取 token 并附加到请求
function getCsrfFromCookie() {
  return document.cookie
    .split('; ')
    .find(row => row.startsWith('_csrf_token='))
    ?.split('=')[1];
}

// AJAX 请求时附加
fetch('/api/action', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': getCsrfFromCookie(),
  },
  body: JSON.stringify(data),
});

// 服务端验证
function validateDoubleSubmit(req) {
  const cookieToken = req.cookies['_csrf_token'];
  const headerToken = req.headers['x-csrf-token'];

  return cookieToken && headerToken && cookieToken === headerToken;
}
```

**注意**：双重 Cookie 验证的安全性低于独立 Token，因为如果站点存在 XSS 漏洞，攻击者可以同时读取并重放 Cookie 中的 token。它适合作为辅助防御层，而非唯一防线。

## 综合防御架构

实际项目中，建议采用**多层防御组合**：

```javascript
/**
 * CSRF 防御配置清单
 * 按优先级排列，每层都是独立的防护
 */

const csrfDefenseLayers = [
  {
    name: 'SameSite Cookie',
    priority: 'P0',  // 必须有
    config: { sameSite: 'lax', secure: true, httpOnly: true },
    reason: '最简单有效，浏览器原生支持',
  },
  {
    name: 'CSRF Token',
    priority: 'P1',  // 强烈推荐
    config: {
      source: 'session-bound random token',
      delivery: ['meta tag', 'response header'],
      verification: 'timing-safe comparison',
    },
    reason: '即使 SameSite 配置错误也能兜底',
  },
  {
    name: 'Referer / Origin 检查',
    priority: 'P2',  // 辅助
    config: { allowList: ['mydomain.com'] },
    reason: '快速过滤明显不合法的来源',
  },
  {
    name: '二次确认（敏感操作）',
    priority: 'P3',  // 特定场景
    config: { operations: ['delete-account', 'change-password'] },
    reason: '给用户最后的机会发现异常',
  },
];
```

## CSRF 与 XSS 的关系

CSRF 和 XSS 经常被混淆，它们的关系可以这样理解：

| 维度 | XSS | CSRF |
|------|-----|------|
| 攻击位置 | 在目标站点内执行代码 | 在第三方站点发起请求 |
| 携带方式 | 恶意脚本注入 | 利用浏览器自动携带 Cookie |
| 防御重点 | 输出转义、CSP | Token、SameSite |
| 攻击者能力 | 可以做任何事 | 只能模拟用户已授权的操作 |

一个值得深思的事实：**XSS 可以绕过几乎所有 CSRF 防御**。如果攻击者能在目标站点执行 JavaScript，他就可以读取页面中的 CSRF Token 并将其附到伪造请求中。这就是为什么 XSS 的危害等级通常被认为高于 CSRF——前者是后者的超集。

这也再次印证了纵深防御的价值：每一道防线都不是完美的，但当多道防线叠加在一起时，攻击者的成本就会指数级上升。
