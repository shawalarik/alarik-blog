# 渲染优化 —— 关键渲染路径、defer/async、preload/preconnect

## 理解浏览器渲染流程

在讨论如何优化渲染之前，需要先理解浏览器是如何把代码变成屏幕上的像素的。这个过程称为**关键渲染路径（Critical Rendering Path，CRP）**。

想象你在装修一间房子。首先你需要拿到设计图纸（HTML），然后根据图纸采购材料（CSS/JS/图片），接着按顺序施工（构建 DOM 和 CSSOM），最后才能看到成品（绘制像素）。如果某个材料迟迟不到（比如 JavaScript 阻塞了），整个工程就得停下来等。关键渲染路径的优化，本质上就是**减少等待、并行施工、优先完成最重要的部分**。

浏览器的渲染流水线大致经历以下步骤：

```
1. 解析 HTML → 构建 DOM 树
2. 解析 CSS → 构建 CSSOM 树
3. 合并 DOM + CSSOM → 构建渲染树（Render Tree）
4. 布局（Layout）—— 计算每个元素的位置和尺寸
5. 绘制（Paint）—— 将元素填充到像素层
6. 合成（Composite）—— 将多个图层合并显示
```

每一步都依赖前一步的结果，形成了一条**串行链路**。优化的目标就是缩短这条链路的总耗时，或者在可能的地方引入并行。

## defer 与 async 的选择

`<script>` 标签是阻塞 HTML 解析的主要因素之一。默认情况下，浏览器遇到 `<script>` 会暂停 HTML 解析，下载并执行脚本后才能继续。这就像读小说读到一半突然被要求去做一道数学题——阅读体验完全被打断。

### 三种加载模式的对比

```html
<!-- 模式一：默认行为（阻塞） -->
<script src="/app.js"></script>
<!-- 浏览器暂停 HTML 解析 ↓
     下载 app.js ↓
     执行 app.js ↓
     继续解析 HTML -->

<!-- 模式二：defer（延迟执行） -->
<script defer src="/app.js"></script>
<!-- 异步下载 app.js（不阻塞解析）↓
     继续解析 HTML（同时下载）
     HTML 解析完成后 ↓
     按 document order 执行 app.js -->

<!-- 模式三：async（异步执行） -->
<script async src="/analytics.js"></script>
<!-- 异步下载 analytics.js（不阻塞解析）↓
     继续解析 HTML（同时下载）
     下载完成后立即执行（不保证顺序！） -->
```

```javascript
// defer 的执行时机示意：
// HTML:
//   <script defer src="a.js"></script>  // 耗时 100ms 下载
//   <script defer src="b.js"></script>  // 耗时 50ms 下载
//
// 执行顺序：a.js 先于 b.js（即使 b 先下完）
// 执行时机：DOMContentLoaded 事件之前

// async 的执行时机示意：
// HTML:
//   <script async src="a.js"></script>  // 耗时 100ms 下载
//   <script async src="b.js"></script>  // 耗时 50ms 下载
//
// 执行顺序：b.js 可能先于 a.js！（谁先下完谁先执行）
// 执行时机：可能在 DOMContentLoaded 之前或之后
```

| 特性 | `<script>` | `defer` | `async` |
|------|-----------|---------|---------|
| 是否阻塞 HTML 解析 | **阻塞** | 不阻塞 | 不阻塞 |
| 执行时机 | 立即 | DOM 解析完成后 | 下载完成后立即 |
| 执行顺序 | 按出现顺序 | **按出现顺序** | **不保证顺序** |
| 适用场景 | 无（应避免） | **主应用脚本** | **第三方独立脚本** |
| DOM 可用性 | 不一定 | ✅ 保证可用 | 不保证 |

```html
<!-- ✅ 推荐的主脚本加载方式 -->
<head>
  <meta charset="UTF-8">
  <!-- 内联关键 CSS（消除渲染阻塞） -->
  <style>/* 首屏必需的样式... */</style>

  <!-- 主应用 JS 使用 defer -->
  <script defer src="/main.bundle.js"></script>
  <script defer src="/vendor.chunk.js"></script>
</head>

<body>
  <!-- 第三方独立脚本使用 async -->
  <script async src="https://www.googletagmanager.com/gtag/js?id=GA_ID"></script>
</body>
```

## 资源提示（Resource Hints）

资源提示是一组让开发者提前告诉浏览器"我接下来会用到这些资源"的机制。它们不是强制指令而是"建议"——浏览器可以根据自身策略决定是否采纳。

这就像你告诉朋友："我大概五分钟后到你家，可以帮我倒杯水吗？"他可能会提前准备，也可能正忙着别的事来不及。但至少你表达了意图，大多数情况下会有正面效果。

### preconnect（预连接）

建立到服务器的早期连接（DNS + TCP + TLS 握手）：

```html
<!-- 在 <head> 中尽早声明 -->
<link rel="preconnect" href="https://cdn.example.com">
<link rel="preconnect" href="https://api.example.com">

<!-- 如果需要更精细的控制，可以加 crossorigin 属性 -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
```

```javascript
/**
 * 动态添加 preconnect
 * 用于运行时确定的目标域名
 */
function preconnectDomain(href, crossorigin = false) {
  const link = document.createElement('link');
  link.rel = 'preconnect';
  link.href = href;
  if (crossorigin) {
    link.crossOrigin = 'anonymous';
  }
  document.head.appendChild(link);
}

// 示例：API 客户端初始化时预连接
class ApiClient {
  constructor(baseUrl) {
    this.baseUrl = baseUrl;
    const url = new URL(this.baseUrl);
    preconnectDomain(url.origin, true);
  }

  async fetch(endpoint) {
    // 此时连接可能已经就绪
    return fetch(`${this.baseUrl}${endpoint}`);
  }
}
```

### prefetch / preload

两者容易混淆，但用途不同：

```html
<!--
  preload：当前页面就会用到的资源
  强制浏览器立即开始下载，优先级高
-->
<link rel="preload" as="font" type="font/woff2"
      href="/fonts/main.woff2" crossorigin>
<link rel="preload" as="image"
      href="/hero-image.webp">
<link rel="preload" as="script"
      href="/critical-module.js">
<link rel="preload" as="style"
      href="/styles.css">

<!--
  prefetch：下一页面可能会用到的资源
  低优先级，利用空闲时间下载
-->
<link rel="prefetch" as="document"
      href="/next-page.html">
<link rel="prefetch" as="script"
      href="/next-page-bundle.js">
```

```javascript
/**
 * 动态 Prefetch 工具
 * 用于预测用户下一步操作并提前加载
 */
class ResourcePrefetcher {
  constructor(options = {}) {
    this.maxPrefetches = options.maxPrefetches || 10;
    this.prefetchedUrls = new Set();
    this.priorityMap = new Map();
  }

  /**
   * 预取一个资源
   * @param {string} url 资源 URL
   * @param {number} priority 优先级（数字越小越高）
   */
  prefetch(url, priority = 5) {
    if (this.prefetchedUrls.has(url)) return;
    if (this.prefetchedUrls.size >= this.maxPrefetches) {
      this._evictLowestPriority();
    }

    const link = document.createElement('link');
    link.rel = 'prefetch';
    link.href = url;

    // 根据 URL 推断类型
    if (url.match(/\.(js|jsx|mjs)$/i)) link.as = 'script';
    else if (url.match(/\.(css)$/i)) link.as = 'style';
    else if (url.match(/\.(woff2?|ttf|otf)$/i)) link.as = 'font';
    else if (url.match(/\.(jpe?g|png|gif|webp|svg)$/i)) link.as = 'image';

    document.head.appendChild(link);
    this.prefetchedUrls.add(url);
    this.priorityMap.set(url, priority);
  }

  /**
   * 移除最低优先级的缓存项
   */
  _evictLowestPriority() {
    let lowestUrl, lowestPriority = Infinity;
    for (const [url, priority] of this.priorityMap) {
      if (priority > lowestPriority) {
        lowestPriority = priority;
        lowestUrl = url;
      }
    }
    if (lowestUrl) {
      this.prefetchedUrls.delete(lowestUrl);
      this.priorityMap.delete(lowestUrl);
    }
  }
}

// ====== 使用示例 ======
const prefetcher = new ResourcePrefetcher({ maxPrefetches: 8 });

// 用户鼠标悬停在导航链接上时，预取目标页面
document.querySelectorAll('a[data-prefetch]').forEach(link => {
  link.addEventListener('mouseenter', () => {
    prefetcher.prefetch(link.href, 1); // 高优先级
  }, { once: true });
});

// 预测用户下一步可能的操作
if (userIsLikelyToCheckout) {
  prefetcher.prefetch('/checkout', 2);
}
```

## 减少重排和重绘

每次 JavaScript 修改了影响布局的属性（如宽度、高度、位置、字体大小），浏览器都需要**重新计算所有受影响元素的位置和尺寸**——这就是**回流/重排（Reflow/Layout Thrashing）**。而只修改外观属性（如颜色、背景）则触发**重绘（Repaint）**。

频繁的重排是性能的大敌。想象你在整理书架上的书——每放一本书都要重新测量整个书架上所有书籍的位置，那效率可想而知。

### 触发回流的常见属性

```javascript
/**
 * 回流触发器检测工具
 * 列出最常导致性能问题的属性修改
 */

const REFLOW_TRIGGERS = {
  // 几乎必然触发布局重算
  layout: [
    'element.offsetWidth',
    'element.offsetHeight',
    'element.offsetTop',
    'element.offsetLeft',
    'element.scrollWidth',
    'element.scrollHeight',
    'element.getBoundingClientRect()',
    'element.getComputedStyle()',
    'window.getComputedStyle(element)',
  ],
  // 修改后会触发后续读取时的回流
  writes: [
    'element.style.width',
    'element.style.height',
    'element.style.margin/padding/border',
    'element.style.display',
    'element.style.position',
    'element.className',  // 如果关联的样式包含上述属性
    'element.classList.add/remove/toggle',
  ],
};

/**
 * 批量 DOM 操作 —— 减少 Layout Thrashing
 * 问题：读写交替会导致浏览器反复重排
 *
 * ❌ 反模式：循环中读写交替
 */
function badPattern(elements) {
  elements.forEach(el => {
    const width = el.offsetWidth;       // 读 → 触发回流
    el.style.width = (width + 10) + 'px'; // 写 → 使缓存失效
    // 下一次循环的 offsetWidth 又要重新计算...
  }); // N 次 → N 次回流
}

// ✅ 正确模式：先全部读完，再全部写完
function goodPattern(elements) {
  // Phase 1: 全部读取
  const widths = elements.map(el => el.offsetWidth);

  // Phase 2: 全部写入
  elements.forEach((el, i) => {
    el.style.width = (widths[i] + 10) + 'px';
  });
} // 1 次批量读取 + 1 次批量写入 → 最多 2 次回流
```

### 使用 DocumentFragment 或 cloneNode

```javascript
/**
 * 高效批量插入 DOM 元素
 */

// ❌ 直接循环 append —— 每次都触发回流
const list = document.getElementById('list');
items.forEach(item => {
  const li = document.createElement('li');
  li.textContent = item.name;
  list.appendChild(li);  // 每次 append 都可能导致回流
});

// ✅ 方案一：DocumentFragment（虚拟容器）
const fragment = document.createDocumentFragment();
items.forEach(item => {
  const li = document.createElement('li');
  li.textContent = item.name;
  fragment.appendChild(li);  // 向 fragment 添加不会触发回流
});
list.appendChild(fragment);  // 只触发一次回流

// ✅ 方案二：cloneNode + replace
const template = list.cloneNode(true);
items.forEach((item, i) => {
  template.children[i].textContent = item.name;
});
list.parentNode.replaceChild(template, list);
```

### 使用 CSS will-change 和 transform

```css
/* 将动画元素提升为独立合成层 */
.animated-element {
  /* 告诉浏览器这个属性将会变化 */
  will-change: transform;

  /* 使用 transform 替代 top/left 进行位移 */
  transform: translateX(0);
  transition: transform 0.3s ease;
}

.animated-element.moved {
  transform: translateX(200px);
}

/* 注意：will-change 不要滥用！
   每个提升的层都会占用额外的内存和 GPU 资源 */
```

```javascript
/**
 * 合理管理 GPU 合成层
 */
class CompositingManager {
  /**
   * 为动画元素启用硬件加速
   * 动画结束后及时移除以释放资源
   */
  static animateWithGpu(element, keyframes, options) {
    // 动画前：提升为独立层
    element.style.willChange = 'transform, opacity';

    const animation = element.animate(keyframes, {
      ...options,
      onFinish: () => {
        // 动画结束后：释放资源
        element.style.willChange = 'auto';
        options.onFinish?.();
      },
    });

    return animation;
  }
}

// 使用
CompositingManager.animateWithGpu(
  document.querySelector('.card'),
  [{ transform: 'translateY(0)' }, { transform: 'translateY(-20px)' }],
  {
    duration: 300,
    easing: 'ease-out',
    onFinish: () => console.log('动画结束，GPU 资源已释放'),
  }
);
```

## 关键渲染路径优化清单

```javascript
/**
 * CRP 优化检查器
 * 自动分析页面的关键渲染路径并提供优化建议
 */
class CRPAnalyzer {
  analyze() {
    const issues = [];
    const performanceEntries = performance.getEntriesByType('navigation')[0];

    // 1. 检查 TTFB
    const ttfb = performanceEntries.responseStart - performanceEntries.requestStart;
    if (ttfb > 600) {
      issues.push({
        level: 'error',
        metric: 'TTFB',
        value: `${Math.round(ttfb)}ms`,
        suggestion: '服务器响应时间过长，考虑 CDN 加速或服务端缓存',
      });
    }

    // 2. 检查阻塞渲染的资源
    const renderBlockingResources = performance.getEntriesByType('resource')
      .filter(r => r.renderBlockingStatus === 'blocking')
      .sort((a, b) => b.duration - a.duration)
      .slice(0, 5);

    if (renderBlockingResources.length > 0) {
      issues.push({
        level: 'warning',
        metric: 'Render Blocking Resources',
        value: `${renderBlockingResources.length} 个`,
        suggestion: renderBlockingResources.map(r =>
          `${r.name} (${Math.round(r.duration)}ms)`
        ).join('; ') + ' — 考虑使用 defer/async 或内联关键部分',
      });
    }

    // 3. 检查同步脚本数量
    const syncScripts = document.querySelectorAll('script:not([defer]):not([async])');
    if (syncScripts.length > 2 && !issues.find(i => i.metric === 'Sync Scripts')) {
      issues.push({
        level: 'warning',
        metric: 'Sync Scripts',
        value: syncScripts.length,
        suggestion: '存在多个同步 script 标签，建议改用 defer 或 async',
      });
    }

    return issues;
  }
}

// 页面加载完成后自动分析
window.addEventListener('load', () => {
  const analyzer = new CRPAnalyzer();
  const results = analyzer.analyze();

  if (results.length > 0) {
    console.group('%c⚠ CRP 优化建议', 'color:#e67e22;font-weight:bold');
    results.forEach(issue => {
      console.log(`[${issue.level.toUpperCase()}] ${issue.metric}: ${issue.value}`);
      console.log(`  → ${issue.suggestion}`);
    });
    console.groupEnd();
  } else {
    console.log('%c✓ CRP 分析通过', 'color:#27ae60;font-weight:bold');
  }
});
```

**哲学思考**：渲染优化的终极智慧在于**理解代价**。每一个 DOM 操作、每一次样式变更、每一张图片的加载都有其隐含的成本。优秀的开发者不是避免一切开销，而是在正确的地方付出正确的代价。首屏内容值得花更多时间优化，而用户看不到的内容则应该尽可能推迟。这种"分清轻重缓急"的能力，不仅是前端优化的核心，也是工程思维的精髓。
