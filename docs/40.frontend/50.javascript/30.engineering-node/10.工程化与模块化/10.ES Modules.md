# ES Modules —— import/export、动态导入、模块作用域、循环依赖

## 为什么需要模块化

在 JavaScript 的早期岁月，没有模块系统。所有的代码都写在一个文件里——或者更糟糕地，通过多个 `<script>` 标签按顺序加载。全局变量相互污染，依赖关系靠加载顺序隐式保证。这就像把所有家具都堆在一个房间里——找东西靠记忆，搬东西怕碰到别的。

想象一个没有隔间的办公室。所有人的桌子挤在一起，电话线缠着咖啡杯，文件随意散落。张三的"临时变量"可能被李四当成常量用了。这就是早期 JavaScript 开发的真实写照：**全局作用域是一个公共的垃圾场**。

模块化的本质是给代码划定边界。每个模块有自己的作用域，显式声明自己需要什么（import）、提供什么（export）。这不是语法糖，而是一种**组织思维的方式**——将复杂的系统拆分为可理解、可复用、可独立演进的单元。

## import 和 export 基础

### 命名导出与默认导出

```javascript
// ====== utils/math.js ======

// 命名导出 —— 可以有多个
// 每个 export 就像模块对外开的一扇门
export const PI = Math.PI;

export function add(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}

export class Calculator {
  constructor(initialValue = 0) {
    this.value = initialValue;
  }

  add(n) { this.value += n; return this; }
  result() { return this.value; }
}

// 默认导出 —— 每个模块只能有一个
// 通常用于模块的"主接口"
const mathUtils = {
  add,
  multiply,
  PI,
};

export default mathUtils;

// 注意：命名导出和默认导出可以共存
```

```javascript
// ====== 导入方 ======

// 方式一：导入命名导出（必须用花括号，名字必须匹配）
import { add, multiply, PI } from './utils/math.js';

console.log(add(2, 3));      // 5
console.log(PI);             // 3.14159...

// 方式二：导入默认导出（不需要花括号）
import mathUtils from './utils/math.js';
console.log(mathUtils.add(2, 3));

// 方式三：同时导入两种
import mathDefault, { Calculator } from './utils/math.js';

const calc = new Calculator(10);
calc.add(5);
console.log(calc.result());   // 15
```

### 导入的几种变体

```javascript
// 重命名导入 —— 解决命名冲突
import {
  add as sum,          // 将 add 重命名为 sum
  multiply as product,  // 将 multiply 重命名为 product
} from './math.js';

sum(1, 2);        // 调用的其实是 add
product(3, 4);    // 调用的实际上是 multiply

// 全量导入（命名空间导入）—— 所有导出挂在对象上
import * as Math from './math.js';

Math.add(1, 2);
Math.multiply(3, 4);
Math.PI;

// 仅执行副作用导入（不绑定任何值）
// 用于 polyfill 或注册全局行为
import './polyfills/fetch-polyfill.js';

// 空导入 + 副作用的实际场景
// 某些模块只在被导入时执行初始化逻辑：
//
// // analytics.js
// window.addEventListener('error', (e) => {
//   sendToAnalytics(e.message);
// });
// export const version = '1.0';
//
// import './analytics';  // 触发事件监听器注册
```

### re-export（重新导出）

```javascript
// ====== api/index.js ======
// 作为统一出口，聚合子模块的导出

// 直接转发
export { GET, POST } from './http-methods.js';

// 转发并重命名
export { fetchJson as fetch } from './fetch-wrapper.js';

// 转发默认导出（需要特殊语法）
export { default as Router } from './router.js';

// 合并所有导出
export * from './utils/index.js';

// 实际使用时只需从 index 导入
import { GET, POST, fetch, Router } from './api/index.js';
// 不需要关心内部文件结构如何组织
```

**哲学思考**：re-export 的存在体现了 **Facade（外观模式）** 在模块系统中的应用。调用者不需要了解内部的包结构，只需要面对一个统一的入口。这种"隐藏复杂性"的能力，是软件工程中最重要的抽象手段之一。一个好的模块设计应该让使用者用最少的认知负担获得最大的功能价值。

## 动态 import()

静态 `import` 必须出现在顶层，不能放在条件语句或函数内。但 `import()` 是一个函数，可以在任何地方调用，返回一个 Promise：

```javascript
/**
 * 动态导入的实际应用场景
 */

// 场景一：路由懒加载 —— SPA 中最常见的用法
async function navigateTo(route) {
  const routes = {
    home: () => import('./pages/HomePage.js'),
    dashboard: () => import('./pages/DashboardPage.js'),
    settings: () => import('./pages/SettingsPage.js'),
  };

  if (!routes[route]) throw new Error(`未知路由: ${route}`);

  // 此时才真正下载和解析该模块
  const module = await routes[route]();
  const Page = module.default || module;
  render(new Page());
}

document.getElementById('nav').addEventListener('click', (e) => {
  const page = e.target.dataset.route;
  navigateTo(page);  // 用户点击时才加载对应页面
});

// 场景二：条件性加载功能模块
async function initFeature(flag) {
  if (flag === 'chart') {
    const { ChartRenderer } = await import('./features/chart.js');
    return new ChartRenderer();
  }
  if (flag === 'editor') {
    const { RichEditor } = await import('./features/editor.js');
    return new RichEditor();
  }
}

// 场景三：带超时的动态导入
function dynamicImport(url, timeoutMs = 10000) {
  return Promise.race([
    import(url),
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error(`Import timeout: ${url}`)), timeoutMs)
    ),
  ]);
}
```

`import()` 与静态 `import` 的关键区别：

| 特性 | 静态 import | 动态 import() |
|------|------------|--------------|
| 出现位置 | 只能顶层 | 任意位置 |
| 绑定时机 | 编译阶段确定（静态分析） | 运行时决定 |
| Tree Shaking | ✅ 支持（可分析依赖图） | ❌ 无法静态消除 |
| 条件加载 | ❌ 不支持 | ✅ 支持 |
| 错误处理 | 同步抛出异常 | Promise catch |
| 返回值 | 命名空间对象 | `Promise<Module>` |

## 模块作用域

ES Module 有自己独立的**模块作用域**。模块内的变量不会泄露到全局，也不属于其他模块：

```javascript
// ====== counter.js ======

// 这些变量都是私有的，外部无法访问
let _count = 0;
const _listeners = [];

// 只有被 export 的内容才对外可见
export function increment() {
  _count++;
  notifyListeners();
}

export function getCount() {
  return _count;
}

export function subscribe(listener) {
  _listeners.push(listener);
  return () => unsubscribe(listener);  // 返回取消订阅函数
}

function notifyListeners() {
  _listeners.forEach(fn => fn(_count));
}

function unsubscribe(listener) {
  const idx = _listeners.indexOf(listener);
  if (idx > -1) _listeners.splice(idx, 1);
}

// ====== 外部使用 ======
import { increment, getCount, subscribe } from './counter.js';

increment();
increment();
console.log(getCount());     // 2

// _count? → ReferenceError! 不存在
// _listeners? → ReferenceError! 不存在
// notifyListeners? → ReferenceError! 不存在
// subscribe? → ✅ 可以访问（因为被导出了）
```

这就是**封装**的力量——模块可以自由选择暴露什么和隐藏什么。私有实现细节的变化不影响外部使用者。这就像一家餐厅：客人只看到菜单和菜品，看不到厨房里的混乱过程。

### import.meta

每个模块都可以通过 `import.meta` 获取关于自身的信息：

```javascript
// ====== config-loader.js ======

// import.meta.url —— 当前模块文件的绝对 URL
// 这对于根据模块位置加载资源非常有用

export async function loadConfig() {
  // 获取当前模块所在目录
  const moduleDir = new URL('.', import.meta.url).pathname;

  // 相对于当前模块加载配置文件
  const response = await fetch(
    new URL('./config.json', import.meta.url)
  );
  return response.json();
}

// import.meta.env —— 构建工具注入的环境变量
// Vite / Webpack 会在此处注入自定义变量
if (import.meta.env.PROD) {
  console.log('生产环境');
} else if (import.meta.env.DEV) {
  console.log('开发环境');
}

console.log(import.meta.env.VITE_API_URL);  // 自定义环境变量
```

## 循环依赖

循环依赖是模块系统的经典问题：A 依赖 B，B 又依赖 A。ES Modules 通过**实时绑定（live bindings）**来处理这种情况：

```javascript
// ====== a.js ======
import { getBValue } from './b.js';

export let aValue = 'initial A';

export function setAValue(val) {
  aValue = val;
}

export function showValues() {
  console.log('aValue:', aValue);
  console.log('bValue:', getBValue());
}

// 执行一些操作...
setAValue('updated by A');

// ====== b.js ======
import { aValue, setAValue } from './a.js';

let bValue = 'initial B';
export function getBValue() { return bValue; }
export function setBValue(val) { bValue = val; }

// B 可以读取到 A 的值（此时可能是 initial A）
console.log('B reads A:', aValue);  // undefined 或 'initial A'？

setAValue('modified by B');
```

**关键点**：ESM 的 `import` 创建的是**对导出绑定的只读引用**，而不是值的拷贝。这意味着如果模块 A 导出了一个变量 `x`，模块 B 拿到的不是 `x` 当前的值，而是一根指向 `x` 的"指针"。当 `x` 的值改变后，B 再去读就能拿到新值。

但这有一个陷阱——**初始化顺序问题**。如果 B 在 A 完全初始化之前就尝试读取 A 的导出，拿到的可能是 `undefined`：

```javascript
// 安全的处理方式：使用函数延迟访问

// a.js
export let data = null;

// 用函数包装，确保使用时已完成初始化
export function getData() { return data; }
export function setData(val) { data = val; }

// b.js
import { getData } from './a.js';

// 即使在循环依赖中，函数调用发生在运行时
// 到那时数据大概率已准备好
function useDataFromA() {
  const d = getData();  // 函数调用时取值，而非模块求值时
  return d?.toUpperCase();
}
```

**解决循环依赖的根本方法还是重新审视架构**——如果两个模块互相依赖，通常说明它们的职责划分不够清晰。考虑提取一个第三方的共享模块，让 A 和 B 都依赖它，而不是彼此依赖。

## ESM vs CommonJS 对比

虽然 CommonJS 的详细讨论在[下一篇文章](/frontend/javascript/engineering-node/commonjs)，这里先做一个核心对比：

| 维度 | ES Modules | CommonJS |
|------|-----------|----------|
| 关键字 | `import` / `export` | `require()` / `module.exports` |
| 加载时机 | 编译时静态分析（异步） | 运行时同步执行 |
| 值拷贝 vs 引用 | **实时绑定引用** | **值拷贝** |
| this 指向 | `undefined`（严格模式） | 当前模块对象 |
| 顶层 await | ✅ 支持 | ❌ 不支持 |
| 循环依赖 | 可工作（但需注意初始化顺序） | 可能拿到未完成的对象 |
| Tree Shaking | ✅ 天然支持 | ❌ 困难 |
| 浏览器原生支持 | ✅ 现代浏览器均支持 | ❌ 需要打包工具 |

**哲学思考**：ES Modules 的设计反映了一个重要的工程理念——**约束即能力**。静态 `import` 的限制（必须在顶层、不能条件引入）看似不便，但这些约束使得构建工具可以进行可靠的静态分析和 Tree Shaking。灵活性往往以牺牲可分析性为代价，而好的标准是在两者之间找到恰当的平衡点。
