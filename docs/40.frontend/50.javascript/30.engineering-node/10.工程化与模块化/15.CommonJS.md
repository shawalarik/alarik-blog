# CommonJS —— require、module.exports、与 ESM 的差异

## CommonJS 的历史

在 ES Modules 成为标准之前，JavaScript 没有官方的模块系统。2009 年 Node.js 诞生时，需要一个方式来组织服务端代码，于是采用了 CommonJS 规范——这就是 `require` 和 `module.exports` 的起源。

CommonJS 的名字来自一个社区驱动的规范项目，它比 ECMAScript 官方的模块标准早了将近十年。这就像在没有交通规则的城市里，居民们自发约定了一套通行手势——虽然不是法律（语言标准），但大家都遵守，所以它能正常运转。

即使今天 ESM 已经成为主流，CommonJS 仍然无处不在：npm 上绝大多数包仍然用 CommonJS 编写，Node.js 的生态深度依赖这套机制。

## require 与 module.exports

### 基础用法

```javascript
// ====== utils/math.js (CommonJS) ======

// 导出单个值
module.exports.PI = Math.PI;

// 导出函数
module.exports.add = function(a, b) {
  return a + b;
};

// 或者更常见的方式 —— 直接覆盖 exports 对象
const mathUtils = {
  add: function(a, b) { return a + b; },
  multiply: function(a, b) { return a * b; },
  PI: Math.PI,
};

module.exports = mathUtils;
```

```javascript
// ====== 使用方 ======

// 完整导入整个模块对象
const math = require('./utils/math');

console.log(math.add(2, 3));   // 5
console.log(math.multiply(4, 5)); // 20

// 解构获取需要的部分
const { add, PI } = require('./utils/math');
console.log(add(1, 2));       // 3
```

### exports vs module.exports

这是一个容易混淆的地方：

```javascript
/**
 * exports 和 module.exports 的关系：
 *
 * 初始状态下，exports === module.exports（指向同一个对象）
 * 但如果对 module.exports 重新赋值，两者就不再关联了！
 */

// ✅ 正确用法一：给 exports 添加属性
exports.name = 'myModule';
exports.hello = function() { return 'hello'; };

// ✅ 正确用法二：直接赋值 module.exports
module.exports = {
  name: 'myModule',
  hello: function() { return 'hello'; },
};

// ❌ 错误：直接给 exports 赋新值
exports = { name: 'myModule' };  // 无效！外部 require 得到的是空对象
// 因为模块内部实际导出的始终是 module.exports，
// 而 exports 只是它的初始引用的"别名"
```

用生活类比来理解：`module.exports` 是一个信箱，`exports` 是一张便利贴贴在信箱上。你可以往便利贴上写东西（往 `exports` 上添加属性），这些东西最终会进入信箱。但如果你把便利贴撕掉换了一张新的（重新赋值 `exports`），信箱里还是原来的内容——新的便利贴和信箱已经没有关系了。

### require 的解析机制

`require()` 接收一个模块标识符并返回该模块的导出对象。它的查找过程遵循一套精确的规则：

```javascript
// Node.js 中 require 的解析顺序：

require('./utils/helper');    // 1. 相对路径 → 从当前文件位置开始找
require('/abs/path/to/lib');  // 2. 绝对路径 → 直接定位
require('lodash');            // 3. 非路径标识符 → node_modules 查找

// 对于非路径标识符，查找顺序如下：
//
// 1. 内置模块（如 fs, path, http）→ 直接返回
// 2. 当前目录/node_modules/模块名
// 3. 父级目录/node_modules/模块名
// 4. 继续向上直到文件系统根目录
```

```javascript
/**
 * require 解析流程模拟（简化版）
 */
function simulateRequire(moduleId, currentDir) {
  // Step 1: 检查是否为内置模块
  if (isBuiltin(moduleId)) {
    return getBuiltinModule(moduleId);
  }

  let resolvedPath;

  // Step 2: 相对/绝对路径
  if (moduleId.startsWith('.') || moduleId.startsWith('/')) {
    resolvedPath = resolvePath(currentDir, moduleId);
  }
  // Step 3: node_modules 查找
  else {
    resolvedPath = findInNodeModules(moduleId, currentDir);
  }

  if (!resolvedPath) throw new Error(`Cannot find module '${moduleId}'`);

  // Step 4: 扩展名补全
  resolvedPath = resolveExtension(resolvedPath);  // .js → .json → .node

  // Step 5: 如果是目录，查找 package.json main 或 index.js
  if (isDirectory(resolvedPath)) {
    resolvedPath = resolveDirectory(resolvedPath);
  }

  // Step 6: 加载并缓存
  const cached = Module._cache[resolvedPath];
  if (cached) return cached.exports;  // 缓存命中，直接返回

  // 第一次加载 → 执行模块代码
  const mod = new Module(resolvedPath);
  Module._cache[resolvedPath] = mod;
  mod.load();  // 读取文件并执行
  return mod.exports;
}
```

## require 的缓存机制

CommonJS 有一个关键特性：**模块只执行一次**。第一次 `require` 之后，结果被缓存在 `require.cache` 中，后续调用直接返回缓存。

```javascript
// ====== counter.js ======
let count = 0;
module.exports = {
  increment: () => ++count,
  getCount: () => count,
};

console.log('[counter] 模块执行了');  // 只会打印一次！

// ====== a.js ======
const counterA = require('./counter');
console.log(counterA.increment());  // 1
console.log(counterA.getCount());   // 1

// ====== b.js ======
const counterB = require('./counter');
// 注意：不会再次打印 "[counter] 模块执行了"
console.log(counterB.increment());  // 2（同一个实例！）
console.log(counterB.getCount());   // 2
// counterA 和 counterB 指向完全相同的对象
```

这种单例行为意味着**有状态的模块在整个应用中共享状态**。这在某些场景下很方便（如数据库连接池、配置管理器），但在其他场景下可能引发意外的副作用。

```javascript
/**
 * 清除 require 缓存 —— 用于热重载等特殊场景
 * 生产环境中一般不需要这样做
 */
function clearCache(modulePath) {
  delete require.cache[require.resolve(modulePath)];
}

// 热更新时使用
function hotReload(modulePath) {
  clearCache(modulePath);
  const freshModule = require(modulePath);
  console.log('模块已重新加载:', modulePath);
  return freshModule;
}
```

## CommonJS 的值拷贝特性

这是与 [ES Modules](/frontend/javascript/engineering-node/es-modules) 最核心的区别之一：

```javascript
// ====== config.js (CommonJS) ======
let secret = 'initial value';

function setSecret(val) {
  secret = val;
}

function getSecret() {
  return secret;
}

module.exports = { secret, setSecret, getSecret };

// ====== consumer.js ======
const config = require('./config');

console.log(config.secret);        // 'initial value'
config.setSecret('changed!');

// 关键点：config.secret 仍然是 'initial value'！
// 因为 CommonJS 导出的是值的拷贝，而非绑定
console.log(config.secret);        // 'initial value' ← 旧值！

// 但通过函数可以拿到最新值（因为函数每次执行时读取的是当前的 secret）
console.log(config.getSecret());   // 'changed!' ✓
```

对比一下 ESM 在同样情况下的表现：

```javascript
// ====== config-esm.mjs (ESM) ======
let secret = 'initial value';

export function setSecret(val) { secret = val; }
export function getSecret() { return secret; }
export { secret };

// ====== consumer.mjs (ESM) ======
import { secret, setSecret, getSecret } from './config-esm.mjs';
console.log(secret);              // 'initial value'
setSecret('changed!');
console.log(secret);              // 'changed!' ← 实时绑定的最新值！
```

**哲学思考**：值拷贝 vs 实时绑定不仅是技术细节，更代表了两种不同的思维模型。CommonJS 的值拷贝像拍照——拍下的瞬间是什么就是什么，之后的变化不会影响照片。ESM 的实时绑定像视频通话——你看到的一直是最新的画面。前者简单可预测，后者灵活但需要理解其动态性。两种设计各有道理，取决于你更看重哪种语义保证。

## CommonJS 与 ESM 互操作

在实际项目中，CommonJS 和 ESM 经常混用。理解它们的互操作规则至关重要：

```javascript
// ====== ESM 中 import CommonJS ======

// CommonJS 的 module.exports 整体作为默认导入可用
import pkg from './commonjs-module.cjs';  // 默认导入 = module.exports

// 命名导入需要打包工具辅助（如 Webpack 会做转换）
import { namedExport } from './commonjs-module.cjs';  // 可能不工作！

// 安全做法：先默认导入再解构
import cjsPkg from './commonjs-module.cjs';
const { someFunc, someConst } = cjsPkg;

// ====== CommonJS 中 require ESM ======

// ❌ CommonJS 不能直接 require ESM 模块！
// 这会导致 ERR_REQUIRE_ESM 错误
// const esm = require('./esm-module.mjs');  // 报错！

// 解决方案一：动态 import() （返回 Promise）
async function loadEsmModule() {
  const esm = await import('./esm-module.mjs');
  return esm.default ?? esm;
}

// 解决方案二：将 ESM 转换为 CJS 格式（构建工具处理）
// 或者在 package.json 中设置 "type": "module" 来统一为 ESM
```

## 选择指南

| 场景 | 推荐 | 原因 |
|------|------|------|
| 新建前端项目 | **ESM** | Tree Shaking、浏览器原生支持、静态分析 |
| 新建 Node.js 项目（v18+） | **ESM** | Node 已稳定支持 `"type": "module"` |
| 维护老旧 Node.js 项目 | **CommonJS** | 改动成本高，生态兼容性好 |
| 发布 npm 包 | **双格式发布** | 同时提供 `.cjs` 和 `.mjs` 入口（`exports` 字段） |

```json
// package.json 双入口配置示例
{
  "name": "my-lib",
  "type": "module",
  "main": "./dist/index.cjs",      // CommonJS 入口
  "module": "./dist/index.mjs",    // ESM 入口（Webpack/Vite 用这个）
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./subpath": {
      "import": "./dist/subpath.mjs",
      "require": "./dist/subpath.cjs"
    }
  }
}
```

**总结**：CommonJS 是 JavaScript 模块化的先驱者，它在官方标准缺席的年代支撑起了整个 Node.js 生态。了解它不仅是为了维护遗留代码，更是为了理解模块系统的演进脉络——每一个今天的"标准"，都建立在昨天"非标准"探索的基础之上。
