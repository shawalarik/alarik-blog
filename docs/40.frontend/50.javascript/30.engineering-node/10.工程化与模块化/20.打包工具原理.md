# 打包工具原理 —— Webpack 核心（entry/output/loader/plugin）、Vite 的 ESM 优势

## 为什么需要打包工具

浏览器不能直接 `require` 一个文件，也不能直接 `import` 一个本地模块。ES Modules 虽然被现代浏览器支持，但裸导入（bare specifier）如 `import _ from 'lodash'` 仍然不被允许——浏览器需要完整的 URL。更不用说 TypeScript、JSX、SCSS 这些非标准格式了。

打包工具的存在就是为了解决这个**鸿沟**——将开发者友好的源代码转换为浏览器可执行的产物。

这就像厨师和食客之间的关系。你写代码时用的是"食材"（TypeScript、SCSS、各种 npm 包），浏览器只接受"成品菜"（原生 JS/CSS）。打包工具就是那个厨房：把所有食材按照食谱（配置文件）加工成最终可以上桌的菜肴。

## Webpack 核心概念

Webpack 的设计围绕五个核心概念展开：

### Entry（入口）

入口是依赖图的起点。从 entry 开始，Webpack 递归解析所有 import/require，构建出完整的模块依赖关系图。

```javascript
// webpack.config.js
module.exports = {
  // 单入口 —— 生成一个 bundle
  entry: './src/index.js',

  // 多入口 —— 生成多个独立 bundle
  entry: {
    main: './src/index.js',
    admin: './src/admin/index.js',
    vendor: ['react', 'react-dom'],  // 将第三方库单独打包
  },

  // 动态函数形式入口
  entry: () => ({
    main: ['./src/home.js', './src/global.css'],
  }),
};
```

**哲学思考**：Entry 不只是一个文件路径，它代表了**系统的边界**。就像一座城市的城门——从这里开始，道路网络向四面八方延伸（依赖图），每条路都通向某个目的地（输出 bundle）。选择哪个文件作为入口，本质上是在定义你的应用从哪里"启动"。一个好的架构应该让这个起点清晰、稳定、易于理解。

### Output（输出）

Output 定义了打包产物的存放位置和命名规则：

```javascript
module.exports = {
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash:8].js',
    // 输出结果示例：
    //   main.a1b2c3d4.js
    //   admin.e5f6g7h8.js
    clean: true,          // 每次构建前清空 dist 目录
    publicPath: '/',      // 公共资源访问路径前缀

    // 按需加载的 chunk 命名
    chunkFilename: 'chunks/[name].[contenthash:8].js',

    // 静态资源命名
    assetModuleFilename: 'assets/[name].[hash:8][ext]',
  },
};
```

`[contenthash]` 是一个重要的特性——只有当文件内容发生变化时 hash 才会改变。这使得长期缓存成为可能：未改变的文件名不变，浏览器可以直接使用缓存版本。

### Loader

Loader 是 Webpack 的**转换器**。Webpack 本身只理解 JavaScript 和 JSON，Loader 让它能够处理其他类型的文件：

```javascript
module.exports = {
  module: {
    rules: [
      // 处理 TypeScript → Babel 转换为 JS
      {
        test: /\.tsx?$/,
        use: [
          {
            loader: 'babel-loader',
            options: {
              presets: ['@babel/preset-typescript', '@babel/preset-react'],
            },
          },
        ],
        exclude: /node_modules/,
      },

      // 处理 CSS → 提取为独立文件或注入 style 标签
      {
        test: /\.css$/,
        use: [
          'style-loader',     // 创建 <style> 标签注入 DOM
          'css-loader',       // 解析 @import / url() 为 require()
          'postcss-loader',   // PostCSS 转换（autoprefixer 等）
        ],
      },

      // 图片处理 → 内联为 data URL 或输出为文件
      {
        test: /\.(png|jpe?g|gif|webp)$/i,
        type: 'asset',
        parser: {
          dataUrlCondition: { maxSize: 10 * 1024 },  // < 10KB 则内联
        },
        generator: {
          filename: 'images/[hash:8][ext]',
        },
      },
    ],
  },
};
```

**Loader 的执行顺序**：链式调用中，loader 从右到左（或从下到上）执行：

```css
/* 文件经过的处理流程：
 *
 * 原始 .scss 文件
 *   ↓ sass-loader (SCSS → CSS)
 *   ↓ postcss-loader (CSS → 加了前缀的 CSS)
 *   ↓ css-loader (CSS → JS module)
 *   ↓ style-loader (JS module → <style> 注入 DOM)
 */
```

### Plugin

Plugin 扩展了 Webpack 的能力范围，可以在整个构建生命周期的各个阶段注入自定义逻辑：

```javascript
const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');
const { CleanWebpackPlugin } = require('clean-webpack-plugin');
const CopyPlugin = require('copy-webpack-plugin');

module.exports = {
  plugins: [
    // 自动生成 HTML，自动注入 script 标签
    new HtmlWebpackPlugin({
      template: './public/index.html',
      title: 'My App',
      minify: process.env.NODE_ENV === 'production',
    }),

    // 将 CSS 提取为独立文件（替代 style-loader）
    new MiniCssExtractPlugin({
      filename: 'styles/[name].[contenthash:8].css',
      chunkFilename: 'styles/chunk.[contenthash:8].css',
    }),

    // 构建前清理输出目录
    new CleanWebpackPlugin(),

    // 复制静态资源
    new CopyPlugin({
      patterns: [
        { from: 'public/favicon.ico', to: 'favicon.ico' },
        { from: 'public/robots.txt', to: 'robots.txt' },
      ],
    }),

    // 定义全局常量
    new webpack.DefinePlugin({
      'process.env.NODE_ENV': JSON.stringify(process.env.NODE_ENV),
      '__VERSION__': JSON.stringify(require('./package.json').version),
    }),
  ],
};

/**
 * 自定义 Plugin 示例：构建耗时统计
 */
class BuildTimePlugin {
  apply(compiler) {
    const startTime = Date.now();

    compiler.hooks.compile.tap('BuildTimePlugin', () => {
      console.log('[BuildTime] 编译开始...');
    });

    compiler.hooks.done.tap('BuildTimePlugin', (stats) => {
      const duration = ((Date.now() - startTime) / 1000).toFixed(2);
      console.log(`[BuildTime] 构建完成! 耗时 ${duration}s`);
    });
  }
}

// 使用: plugins: [new BuildTimePlugin()]
```

## Vite 的 ESM 优势

Vite 代表了一种全新的构建范式。它的核心洞察是：**开发环境中不需要真正地打包**。

传统打包工具（如 Webpack）在开发模式下仍然会打包所有模块——无论改动多小，都要重新执行整个打包流程。Vite 利用浏览器原生支持 ESM 的能力，在开发模式下**跳过打包步骤**，直接启动一个服务器按需提供源码：

```
Webapck 开发模式:
  改动代码 → 重新打包整个项目 → 刷新页面（秒级）

Vite 开发模式:
  改动代码 → 浏览器请求对应模块 → HMR 更新（毫秒级）
```

```javascript
// vite.config.js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import path from 'path';

export default defineConfig({
  plugins: [react()],

  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src'),
      '@components': path.resolve(__dirname, './src/components'),
    },
  },

  server: {
    port: 3000,
    open: true,
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },

  build: {
    outDir: 'dist',
    sourcemap: false,
    // 生产环境使用 Rollup 打包（与开发模式不同！）
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ['react', 'react-dom', 'react-router-dom'],
          utils: ['lodash-es', 'dayjs'],
        },
      },
    },
  },
});
```

### Vite 与 Webpack 的对比

| 维度 | Webpack | Vite |
|------|---------|------|
| 开发模式启动速度 | 慢（需完整打包） | **极快**（按需编译） |
| 热更新速度 | 中等（取决于项目大小） | **极快**（精确到模块） |
| 生产构建 | 成熟稳定 | 基于 Rollup，同样优秀 |
| 生态插件 | 极其丰富 | 快速增长中 |
| 配置复杂度 | 相对复杂 | 通常较简洁 |
| 大型项目 | 经过充分验证 | 表现优异 |
| 非 ESM 依赖 | 兼容性好 | 需要预构建优化 |

### Vite 的依赖预构建（Deps Optimization）

Vite 在首次启动时会将 `node_modules` 中的依赖预构建为 ESM 格式。这样做的原因：

1. **CommonJS / UMD 转换为 ESM**——让浏览器能直接 import
2. **合并多个小模块**——减少 HTTP 请求数量
3. **性能优化**——利用 esbuild 进行极速转换

```javascript
// vite.config.js
export default defineConfig({
  optimizeDeps: {
    include: ['lodash', 'axios'],         // 强制预构建
    exclude: ['@some-large-native-lib'],   // 排除不需要预构建的
  },
});
```

**哲学思考**：Vite 的出现不是对 Webpack 的否定，而是**时代技术条件变化后的自然演进**。当年 Webpack 诞生时，浏览器不支持 ESM，打包是唯一的选择。今天浏览器已经普遍原生支持 ESM 了，那么为什么不在开发模式中充分利用这一点呢？好的工具设计总是顺应底层基础设施的变化，而不是逆势而行。
