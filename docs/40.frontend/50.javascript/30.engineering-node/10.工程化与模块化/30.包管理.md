# 包管理 —— npm/yarn/pnpm 对比、package.json、lock 文件、语义版本

## 包管理的本质

在 JavaScript 的世界里，几乎没有任何项目是从零开始写每一行代码的。我们站在巨人的肩膀上——这些巨人就是 npm（Node Package Manager）上的数十万个开源包。

包管理器解决的问题看似简单：**下载代码、管理依赖、控制版本**。但这个问题背后隐藏着工程领域最棘手的难题之一——**依赖地狱**：A 依赖 B 的 1.x 版本，C 也依赖 B 但需要 2.x 版本；B 又依赖 D，D 和 E 冲突了……这就像一个复杂的家庭关系图，每个人都要和其他人"和睦相处"，但每个人的需求各不相同。

想象你正在装修房子。你需要买地板、油漆、灯具……每个材料都有品牌和型号的选择。包管理器就是那个精明的采购经理——帮你找到所有需要的材料，确保它们互相兼容，记录下每样东西的精确型号以便日后维护，并且当某个材料出了问题时能快速定位和替换。

## 三大包管理器对比

| 特性 | npm | Yarn (v1/berry) | pnpm |
|------|-----|------------------|------|
| **安装方式** | 扁平 node_modules | 扁平 (v1) / Plug'n'Play (berry) | **内容寻址存储 + 符号链接** |
| **磁盘占用** | 高（所有依赖平铺） | 高 (v1) / 低 (berry) | **最低**（全局存储一份） |
| **安装速度** | 中等 | 较快 | **最快** |
| **幽灵依赖风险** | 有 | 无 (PnP) | **无** |
| **Lock 文件** | package-lock.json | yarn.lock | pnpm-lock.yaml |
| **工作区支持** | npm workspaces | Yarn workspaces | pnpm workspaces |

### pnpm 的内容寻址存储

pnpm 的设计最为独特，它从根本上解决了重复依赖的问题：

```
node_modules/
├── .pnpm/           # 内容寻址存储（全局去重）
│   ├── lodash@4.17.21/
│   │   └── node_modules/lodash → 实际文件
│   ├── react@18.2.0/
│   │   └── node_modules/react
│   └── ...
├── react → ../../.pnpm/react@18.2.0/node_modules/react   # 软链接
├── lodash -> ../../.pnpm/lodash@4.17.21/node_modules/lodash
└── my-app/
    └── node_modules/
        ├── react -> ../../../.pnpm/react@18.2.0/node_modules/react  # 嵌套软链接
        └── lodash -> ../../../.pnpm/lodash@4.17.21/node_modules/lodash

# 即使 100 个包都依赖 react@18.2.0，磁盘上也只存一份！
```

```bash
# pnpm 常用命令
pnpm install          # 安装所有依赖
pnpm add axios         # 添加生产依赖
pnpm add -D typescript # 添加开发依赖
pnpm remove lodash     # 移除依赖
pnpm update           # 更新依赖
pnpm outdated         # 检查过期的包
pnpm why lodash       # 查询某个包被哪些包依赖
pnpm audit            # 安全审计
pnpm store prune       # 清理未引用的全局存储
```

## package.json 深度解析

`package.json` 是 Node.js 项目的身份证：

```json
{
  "name": "my-awesome-app",
  "version": "1.2.3",
  "description": "A well-documented project",
  "type": "module",
  
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": {
      "import": "./dist/utils.mjs",
      "require": "./dist/utils.cjs"
    }
  },
  "files": ["dist"],
  
  "scripts": {
    "dev": "vite --port 3000",
    "build": "tsc && vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "lint": "eslint src/",
    "format": "prettier --write 'src/**/*.{ts,tsx}'",
    "clean": "rimraf dist",
    "prepare": "husky install"
  },
  
  "dependencies": {
    "react": "^18.2.0",
    "react-dom": "^18.2.0",
    "axios": "^1.6.0"
  },
  "devDependencies": {
    "typescript": "^5.3.0",
    "vite": "^5.0.0",
    "@types/react": "^18.2.0"
  },
  
  "peerDependencies": {
    "react": ">=16.8.0"
  },
  "peerDependenciesMeta": {
    "react": { "optional": true }
  },

  "engines": {
    "node": ">=18.0.0",
    "npm": ">=9.0.0"
  },

  "browserslist": [
    "> 1%",
    "last 2 versions",
    "not dead"
  ],

  "private": true,
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "https://github.com/user/my-app.git"
  }
}
```

关键字段说明：

**dependencies vs devDependencies**：
- `dependencies`：运行时必需的包，会打包进最终产物
- `devDependencies`：开发时才需要的包（构建工具、类型定义、测试框架等），不会进入产物
- `peerDependencies`：宿主环境应已提供的包（如 React 组件库要求使用者自行安装 React）

**exports 字段**是现代包的推荐方式，替代 `main` 和 `module`：

```javascript
// exports 支持条件导出 —— 不同环境使用不同入口
// package.json
{
  "exports": {
    ".": {
      "import": "./esm/index.mjs",       // import 时用这个
      "require": "./cjs/index.cjs",      // require() 时用这个
      "default": "./cjs/index.cjs"        // 兜底
    },
    "./subpath": "./lib/subpath.js",
    "./package/subpath": "./lib/deep/path.js"
  }
}
```

## Lock 文件的作用

Lock 文件锁定了项目中所有依赖的**精确版本号**，确保团队成员和生产环境的安装结果完全一致：

```yaml
# pnpm-lock.yaml 示例片段
lockfileVersion: '9.0'

settings:
  autoInstallPeers: true
  excludeLinksFromLockfile: false

importers:
  .:
    devDependencies:
      vite:
        specifier: ^5.0.0
        version: 5.0.12(@types/node@20.10.5)

packages:
  /@vitejs/plugin-react@4.2.1(react@18.2.0):
    resolution: {integrity: sha512-xxx...}
    engines: {node: ^14.18.0 || >=16.0.0}
    peerDependencies:
      react: ^16.8.0 || ^17.0.0 || ^18.0.0

  /vite@5.0.12:
    resolution: {integrity: sha256-yyy...}
    engines: {node: ^18.0.0 || >=20.0.0}

pnpmfileChecksum: abc123...
```

**重要原则**：Lock 文件应该提交到版本控制中。它保证了"在我电脑上能跑"等于"在你电脑上也能跑"。

```bash
# Lock 文件相关命令
pnpm install          # 按 lock 安装（如果 lock 与 package.json 一致）
pnpm install --no-frozen-lockfile  # 即使 lock 不匹配也尝试安装
CI=true pnpm install  # CI 环境：lock 和 package.json 不一致则报错退出
pnpm lock-file-fix    # 修复不一致的 lock 文件
```

## 语义版本（SemVer）

语义版本格式为 `MAJOR.MINOR.PATCH`：

| 变更类型 | 版本变化 | 含义 | 示例 |
|---------|---------|------|------|
| 不兼容的 API 修改 | **MAJOR** ↑ | 用新功能可能破坏旧代码 | 1.0.0 → 2.0.0 |
| 向下兼容的功能新增 | **MINOR** ↑ | 新增功能不影响现有用法 | 1.0.0 → 1.1.0 |
| 向下兼容的缺陷修复 | **PATCH** ↑ | 修复 bug，无行为变更 | 1.0.0 → 1.0.1 |

```json
// package.json 中的版本范围语法
{
  "dependencies": {
    // 精确版本
    "exact-lib": "1.2.3",

    // ~ 允许 patch 级别更新（>=1.2.3 <1.3.0）
    "tilde-lib": "~1.2.3",

    // ^ 允许 minor 级别更新（>=1.2.3 <2.0.0）
    // 最常用的方式
    "caret-lib": "^1.2.3",

    // >= / <= / > / < 范围约束
    "range-lib": ">=1.0.0 <2.0.0",

    // 或（满足任意即可）
    "or-lib": "^1.0.0 || ^2.0.0",

    // latest / next / * / x.x.x
    "any-lib": "*"
  }
}
```

**哲学思考**：语义版本的承诺是一种**社会契约**。发布者承诺遵守规则，使用者信任这种承诺。但这种信任是脆弱的——很多包作者并不严格遵守 SemVer 规范，一次"小小的内部改动"可能意外地破坏了公开 API。这就是为什么 Lock 文件如此重要：即使语义版本被违反，精确锁定也能保护你的项目不受影响。
