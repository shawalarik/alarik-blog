# Prettier —— 配置、与 ESLint 集成、husky + lint-staged

## Prettier 的哲学

Prettier 的设计理念可以用一句话概括：**停止为格式争论，让机器来决定**。

在任何一个团队中，关于"大括号换不换行"、"缩进用空格还是 tab"、"单引号还是双引号"、"末尾要不要分号"这类问题消耗的时间都多得惊人。每个人有自己的偏好，而且每个人都坚信自己的偏好是"最好的"。Prettier 的解决方案很简单：**没有偏好，只有一种格式**。

这就像一家公司统一了着装规范。你不能再穿自己喜欢的花衬衫了——所有人都穿同样的制服。听起来很无趣？也许吧。但好处是：没人再需要每天早上纠结穿什么，也不用担心自己的品味被同事评判。把精力花在做事情上，而不是花在外表上。

## 基础配置

```javascript
// .prettierrc (JSON 格式)
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "es5",
  "printWidth": 100,
  "bracketSpacing": true,
  "arrowParens": "always",
  "endOfLine": "lf"
}
```

```javascript
// .prettierrc.js (JS 格式，支持注释和条件配置)
/** @type {import('prettier').Config} */
module.exports = {
  // 分号：每行结尾是否加分号
  semi: true,

  // 引号：单引号（JSX 属性中会自动切换为双引号）
  singleQuote: true,

  // 缩进：2 个空格
  tabWidth: 2,
  useTabs: false,

  // 行宽：超过此长度自动折行
  printWidth: 100,

  // 尾逗号：ES5 兼容的位置添加逗号（数组、对象等）
  trailingComma: 'es5',

  // 对象字面量的大括号内是否加空格：{ foo: 1 } vs {foo: 1}
  bracketSpacing: true,

  // 箭头函数的参数括号：(x) => {} vs x => {}
  arrowParens: 'always',

  // 换行符风格：lf（Unix）vs crlf（Windows）vs auto
  endOfLine: 'lf',
};
```

各选项的详细说明和推荐值：

| 选项 | 推荐值 | 含义 |
|------|--------|------|
| `semi` | `true` | 每个语句后加分号（避免 ASI 陷阱） |
| `singleQuote` | `true` | 使用单引号（JSX 中自动转双引号） |
| `tabWidth` | `2` | 缩进宽度 |
| `printWidth` | `80~120` | 单行最大字符数（超长则自动折行） |
| `trailingComma` | `'es5'` | ES5 支持的位置加尾逗号 |
| `bracketSpacing` | `true` | 对象内 `{ key: value }` 加空格 |
| `arrowParens` | `'always'` | 箭头函数始终保留参数括号 |
| `endOfLine` | `'lf'` | 统一使用 LF 换行符 |

## 与 ESLint 协作

[ESLint](/frontend/javascript/engineering-node/eslint) 负责代码质量（逻辑正确性），Prettier 负责代码格式（外观一致性）。两者分工明确，但存在规则冲突的可能——比如 ESLint 可能有引号规则而 Prettier 也有引号规则。

### eslint-config-prettier

这个包禁用了所有与 Prettier 冲突的 ESLint 规则：

```bash
npm install --save-dev eslint-config-prettier
```

```javascript
// .eslintrc.cjs
module.exports = {
  extends: [
    'eslint:recommended',
    '@typescript-eslint/recommended',
    'prettier',           // ← 必须放在最后！覆盖前面所有冲突规则
  ],
};
```

**关键点**：`eslint-config-prettier` 必须放在 `extends` 数组的**最后一个位置**，因为它的工作就是关掉前面的冲突项。如果放在中间，后续的配置可能又重新启用了那些规则。

## husky + lint-staged 工作流

这是前端项目中质量保障的黄金组合：**提交前自动检查 + 格式化**。

```
git commit 触发
    ↓
husky 拦截 pre-commit 钩子
    ↓
lint-staged 筛选出本次变更的文件
    ↓
对 .js/.ts/.tsx 文件：
  1. Prettier 格式化
  2. ESLint 检查并修复
    ↓
通过 → 正常提交
失败 → 阻止提交，显示错误信息
```

```javascript
// 安装依赖
// npm install --save-dev husky lint-staged

// package.json
{
  "scripts": {
    "prepare": "husky install"
  },
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": [
      "prettier --write",
      "eslint --fix --max-warnings=0"
    ],
    "*.{json,md,yml,yaml}": [
      "prettier --write"
    ],
    "*.{css,scss,less}": [
      "prettier --write"
    ]
  }
}
```

```bash
# 初始化 husky（只需一次）
npx husky install

# 创建 pre-commit 钩子
npx husky add .husky/pre-commit "npx lint-staged"
```

```bash
# 完整工作流演示：

# 1. 开发者修改了文件
# 2. git add . && git commit -m "feat: add new component"

# 此时自动触发：
#   [lint-staged] src/components/NewComp.tsx
#     ↓ prettier --write （格式化完成）
#     ↓ eslint --fix --max-warnings=0 （检查并修复）
#
#   ✅ 无错误 → 提交成功
#   ❌ 有不可修复的错误 → 提交被阻止
#
#   Error: Unexpected 'var' keyword, use 'let' or 'const' instead (no-var)
#   at src/components/NewComp.tsx:12:5
#
#   开发者修复错误后重新提交即可
```

### 更精细的 lint-staged 配置

```javascript
// .lintstagedrc.js
export default {
  '*.{js,jsx,ts,tsx}': filenames => {
    const files = filenames.join(' ');
    return [
      `prettier --write ${files}`,
      // 只对有修改的文件跑 lint，速度极快
      `eslint --fix --max-warnings=0 ${files}`,
      // 可选：类型检查（较慢，可单独处理）
      // `tsc --noEmit --pretty`,
    ];
  },

  // 对特定路径的文件应用更严格的规则
  'src/**/*.{ts,tsx}': ['prettier --write', 'eslint --fix'],
  '!src/**/*': [],  // 其他目录跳过

  '*.vue': ['prettier --write', 'eslint --fix'],

  // Markdown 和 JSON 也保持格式一致
  '*.{md,json,yml,yaml,html}': ['prettier --write'],
};
```

**哲学思考**：Prettier 代表了一种 **Opinionated Tool（固执己见的工具）** 的设计哲学。它不接受定制化的诱惑，坚持一种"足够好"的标准格式。这种"少即是多"的理念在工具设计中极为罕见且珍贵。大多数工具倾向于不断增加配置选项来满足所有人的需求，结果是配置本身变成了负担。Prettier 反其道而行之——几乎零配置，开箱即用，把开发者从无意义的格式决策中解放出来。
