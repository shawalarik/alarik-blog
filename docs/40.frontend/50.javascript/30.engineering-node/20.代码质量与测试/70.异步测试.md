# 异步测试 —— async/await、done、Promise 测试

## 异步代码的测试挑战

JavaScript 中到处都是异步操作——网络请求、定时器、动画、事件监听。测试异步代码比同步代码困难得多，因为你不能简单地"执行然后断言"。你需要在正确的**时机**做断言——太早了数据还没回来，太晚了可能已经超时。

这就像寄快递。你不能在包裹刚交出去的瞬间就去收件箱查看，也不能等到明年才去查。你需要知道大概多久能到，并在合理的时间窗口内确认它是否到达。异步测试就是在处理这个时间窗口的问题。

## 三种异步测试模式

### 模式一：async/await（推荐）

最现代、最清晰的方式：

```javascript
/**
 * 异步 API 调用的测试 —— 使用 async/await
 */
import { fetchUser, updateUser } from './api';

describe('API 服务', () => {
  it('应该正确获取用户数据', async () => {
    // 函数签名加 async → 测试框架会等待 Promise 完成
    const user = await fetchUser(42);

    expect(user).toBeDefined();
    expect(user.id).toBe(42);
    expect(user.name).toMatch(/\w+/);
    expect(user.email).toContain('@');
  });

  it('应该在用户不存在时返回 null', async () => {
    const result = await fetchUser(999999);
    expect(result).toBeNull();
  });

  it('应该成功更新用户信息', async () => {
    const updated = await updateUser(42, { name: '新名字' });
    
    expect(updated.name).toBe('新名字');
    expect(updated.updatedAt).toBeInstanceOf(Date);
    // 验证其他字段未被修改
    expect(updated.id).toBe(42);
    expect(updated.email).toBeDefined();
  });

  it('应该处理并发请求', async () => {
    // Promise.all 同时发起多个请求
    const [user1, user2, user3] = await Promise.all([
      fetchUser(1),
      fetchUser(2),
      fetchUser(3),
    ]);

    expect([user1.id, user2.id, user3.id]).toEqual([1, 2, 3]);
  });
});
```

### 模式二：返回 Promise

不使用 `async/await` 时直接返回 Promise 对象：

```javascript
it('Promise 方式：应该返回用户列表', () => {
  // 返回一个 Promise → 测试框架自动 .then() 它
  return fetchUserList().then(users => {
    expect(users).toHaveLength(5);   // 在 then 内部断言
    expect(users[0]).toHaveProperty('id');
    expect(users[0]).toHaveProperty('name');
  });
});

// 配合 resolves/rejects 匹配器更优雅
it('应该解析为包含 name 的对象', () => {
  return expect(fetchUser(1)).resolves.toHaveProperty('name');
});

it('当 ID 无效时应该拒绝', () => {
  return expect(fetchUser(-1)).rejects.toThrow('Invalid ID');
});
```

### 模式三：done 回调（旧风格）

用于回调风格的异步代码：

```javascript
it('回调方式：应该在指定时间内完成', (done) => {
  const timer = setTimeout(() => {
    done();  // 手动通知测试完成
  }, 100);

  // 如果 done() 永远不被调用（比如 setTimeout 失败），
  // 测试框架会在默认超时时间（通常 5 秒）后报错
});
```

## 超时控制

异步测试最常见的失败原因就是超时——异步操作没有在预期时间内完成：

```javascript
describe('带超时的异步测试', () => {
  // 为单个测试设置超时
  it('网络请求应在 3 秒内完成', async () => {
    // Vitest/Jest 都支持此语法
    // 注意：vitest 用 vi，jest 直接写
  }, 3000);

  // 为整个 describe 设置默认超时
  describe.each([100, 500, 1000])('延迟 %dms', (delay) => {
    it(`应在 ${delay}ms 后 resolve`, async () => {
      const start = Date.now();
      await waitFor(delay);
      const elapsed = Date.now() - start;
      
      expect(elapsed).toBeGreaterThanOrEqual(delay - 10);
      expect(elapsed).toBeLessThan(delay + 200);  // 允许一定误差
    }, delay + 500);  // 超时 = 延迟值 + 缓冲
  });
});
```

## 定时器模拟

测试中不应该真的等待真实的时间——那样会让测试变得极慢且不稳定。解决方案是**控制时间的流逝**：

```javascript
/**
 * 定时器相关功能的测试
 */
import { debounce, throttle, pollStatus } from './utils';

describe('debounce', () => {
  beforeEach(() => {
    vi.useFakeTimers();  // 启用假定时器
  });

  afterEach(() => {
    vi.useRealTimers();  // 恢复真实定时器
  });

  it('应该在等待期结束后才调用', () => {
    const fn = vi.fn();
    const debouncedFn = debounce(fn, 500);

    // 快速调用 3 次
    debouncedFn('a');
    debouncedFn('b');
    debouncedFn('c');

    // 此时 fn 还没被调用
    expect(fn).not.toHaveBeenCalled();

    // 让时间前进 499ms → 还没到
    vi.advanceTimersByTime(499);
    expect(fn).not.toHaveBeenCalled();

    // 再进 1ms → 到了！
    vi.advanceTimersByTime(1);
    expect(fn).toHaveBeenCalledTimes(1);
    expect(fn).toHaveBeenCalledWith('c');  // 只用最后一次调用的参数
  });

  it('应该在每次重置后重新计时', () => {
    const fn = vi.fn();
    const debouncedFn = debounce(fn, 1000);

    debouncedFn();

    // 过了 800ms
    vi.advanceTimersByTime(800);
    // 再次调用 → 重置计时
    debouncedFn();

    // 再过 800ms（从第一次调用算已过 1600ms）
    vi.advanceTimersByTime(800);
    // 但因为被重置了，还没到 1000ms
    expect(fn).not.toHaveBeenCalled();

    // 再过 200ms
    vi.advanceTimersByTime(200);
    expect(fn).toHaveBeenCalledTimes(1);
  });
});
```

### runAllTimersAsync 与异步定时器

当定时器内有 `setTimeout(fn, 0)` 或 `requestAnimationFrame` 这类微任务时：

```javascript
it('处理嵌套的异步定时器', async () => {
  vi.useFakeTimers();

  const results = [];

  scheduleTasks(results);

  // 同步版本：只处理当前队列中的宏任务
  vi.runAllTimers();

  // 异步版本（推荐）：处理所有宏任务和微任务
  await vi.runAllTimersAsync();

  expect(results).toEqual(['task1', 'task2', 'cleanup']);

  vi.useRealTimers();
});
```

## 网络请求模拟

异步测试中最常见的就是模拟网络请求：

```javascript
/**
 * 使用 vi.spyOn 模拟 fetch
 */
describe('用户服务', () => {
  let fetchSpy;

  beforeEach(() => {
    fetchSpy = vi.spyOn(globalThis, 'fetch').mockImplementation(
      async (url) => {
        if (url.includes('/users/1')) {
          return Response.json({ id: 1, name: 'Alice' });
        }
        if (url.includes('/users/999')) {
          return Response.json(null, { status: 404 });
        }
        return Response.json({ error: 'Not found' }, { status: 404 });
      }
    );
  });

  afterEach(() => {
    fetchSpy.mockRestore();
  });

  it('应该获取用户并转换数据', async () => {
    const service = new UserService();
    const user = await service.getUser(1);

    expect(user).toEqual({ id: 1, name: 'Alice' });
    expect(fetchSpy).toHaveBeenCalledWith(
      expect.stringContaining('/users/1')
    );
  });
});
```

**哲学思考**：异步测试的核心矛盾在于**确定性与非确定性之间的对抗**。真实的异步操作是非确定的（网络可能快可能慢），但测试需要确定性（结果必须可预测）。解决之道不是让世界变确定，而是**将不确定的部分替换为可控的替身**——Mock 就是这种替身。理解了这个本质，各种 Mock 技术就不再是一堆 API 的堆砌，而是一种系统性的设计思维。
