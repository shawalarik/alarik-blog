# 代码覆盖率 —— istanbul、--coverage、分支覆盖

## 什么是代码覆盖率

代码覆盖率回答一个简单的问题：**你的测试到底跑过了多少代码？**

想象你有一张地图标注了你走过的所有路线。覆盖率就是那张地图上"已走过"的区域占比。100% 覆盖率意味着每一条路都走过；30% 意味着大部分区域都是盲区。

但覆盖率不是质量指标——它是**洞察指标**。高覆盖率不代表没有 bug（你可能测了很多无用的东西），低覆盖率则明确指出哪里缺少保护。就像体检报告上的各项指标——它们不能直接诊断疾病，但能告诉你哪些地方需要进一步关注。

## 四种覆盖率维度

### 1. 行覆盖（Statement Coverage）

最基础的指标——每行代码是否被执行过至少一次：

```javascript
function processPayment(amount, method) {
  if (!amount || amount <= 0) {         // 行 A
    throw new Error('金额无效');       // 行 B
  }

  if (method === 'credit') {           // 行 C
    return handleCredit(amount);       // 行 D
  } else if (method === 'paypal') {    // 行 E
    return handlePaypal(amount);       // 行 F
  } else {                             // 行 G
    return handleUnknown(method);      // 行 H
  }
}
```

如果测试只调用 `processPayment(100, 'credit')`：
- 覆盖的行：A, C, D → **行覆盖率 = 50%（4/8）**
- 未覆盖：B（未触发错误）、E/F/G/H（其他分支）

### 2. 分支覆盖（Branch Coverage）

每个条件判断的每个可能方向是否都被走过：

```javascript
// 同上函数的条件分支图：
//
// amount > 0?
//   ├─ true  → method === 'credit'?
//   │           ├─ true  → D ✓
//   │           └─ false → method === 'paypal'?  ← 未覆盖！
//   └─ false → B (throw)
```

上面的测试只走了 `amount>0=true` 和 `method==='credit'=true` 这两条分支路径。要达到更高覆盖率，需要补充更多测试用例：

```javascript
describe('processPayment 分支覆盖', () => {
  it('正常信用卡支付', () => {
    expect(processPayment(100, 'credit')).toBeDefined();
    // 走过: A(true), C(true), D
  });

  it('无效金额应抛错', () => {
    expect(() => processPayment(0, 'credit')).toThrow();
    // 走过: A(false), B
  });

  it('PayPal 支付', () => {
    expect(processPayment(50, 'paypal')).toBeDefined();
    // 走过: A(true), C(false), E(true), F
  });

  it('未知支付方式', () => {
    expect(() => processPayment(30, 'crypto')).toThrow();
    // 走过: A(true), C(false), E(false), G, H
  });
});

// 现在：行覆盖率 = 8/8 = 100%
//       分支覆盖率 = 所有 if/else 方向都已走过 = 100%
```

### 3. 函数覆盖（Function Coverage）

每个定义的函数是否被调用过：

```javascript
const utils = {
  formatName(first, last) { return `${first} ${last}`; },
  formatDate(date) { /* ... */ },       // 从未被任何测试调用
  validateEmail(email) { /* ... */ },   // 从未被任何测试调用
  calculateTax(income) { /* ... */ },   // 从未被任何测试调用
};

// 如果测试只用了 formatName：
// 函数覆盖率 = 25% (1/4)
```

函数覆盖通常作为第一层筛选工具——如果一个函数从未在任何测试中被调用，那它的逻辑几乎肯定没有被充分验证。

### 4. 条件覆盖（Condition Coverage）

最细粒度的指标——布尔表达式中的每一个子条件是否分别取过 true 和 false：

```javascript
if (age >= 18 && hasIdCard && !isBlacklisted) {
  allowEntry();
}
```

这个单一 `if` 语句包含三个子条件。完全的条件覆盖要求每个子条件都取过 true 和 false：

```javascript
// 需要的测试组合（至少）：
// age=18, hasIdCard=true, isBlacklisted=false → 全部 true/false 组合
// age=17 → age>=18 为 false
// hasIdCard=false → hasIdCard 为 false
// isBlacklisted=true → !isBlacklisted 为 false
```

## Istanbul / V8 覆盖率工具

### 配置与运行

```bash
# Jest / Vitest 运行覆盖率
npx vitest run --coverage

# 指定输出格式
npx vitest run --coverage --reporter=text  # 终端表格
npx vitest run --coverage --reporter=html  # HTML 报告（可视化）
npx vitest run --coverage --reporter=json  // JSON（供 CI 解析）
```

```javascript
// vitest.config.ts 中的 coverage 配置
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',                    // 使用 V8 内置覆盖率引擎
      reporter: [
        'text',                          // 终端摘要
        'text-summary',                   // 更简洁的终端摘要
        'html',                          // HTML 详细报告
        'json',                           // JSON 机器可读
        'lcov',                           // 与 CI 工具集成
      ],
      
      include: [
        'src/**/*.ts',
        'src/**/*.tsx',
      ],
      exclude: [
        'src/**/*.d.ts',                 // 类型声明文件
        'src/**/index.ts',                // 重导出入口
        'src/**/*.test.{ts,tsx}',         // 测试文件本身
        'src/mocks/**',                   // Mock 文件
        'src/types/**',                   // 类型定义
      ],

      // 覆盖率阈值 —— 低于此值构建失败
      thresholds: {
        statements: 80,                  // 语句覆盖 ≥ 80%
        branches: 75,                     // 分支覆盖 ≥ 75%
        functions: 85,                   // 函数覆盖 ≥ 85%
        lines: 80,                       // 行覆盖 ≥ 80%
      },
    },
  },
});
```

### 覆盖率报告解读

运行后会生成如下报告：

```
----------|---------|----------|---------|---------|
File        | % Stmts | % Branch | % Funcs | % Lines |
----------|---------|----------|---------|---------|
All files   |   82.3  |   71.2   |   86.5  |   82.3  |
 utils.ts   |   95.0  |   88.9   |  100    |   95.0  |
 api.ts     |   78.6  |   62.5   |   75.0  |   78.6  |
 auth.ts    |   60.0  |   45.5   |   66.7  |   60.0  | ← 需关注
 validator  |   90.9  |   83.3   |   87.5  |   90.9  |
----------|---------|----------|---------|---------|

⚠️ Thresholds not met: branches (71.2% < 75%)
```

HTML 报告中可以精确看到**哪些行没被覆盖**——通常用红色标记。这是最有价值的部分：它不只是告诉你覆盖率数字，而是指出**具体的盲区在哪里**。

## 排除不必要的代码

不是所有代码都需要被测试覆盖：

```javascript
// .eslintrc.cjs 中配合 eslint-disable-next-line
/* istanbul ignore next */  // 告诉 Istanbul 忽略下一行的覆盖率统计

// 或者在 vitest.config.ts 的 exclude 中排除
coverage: {
  exclude: [
    // 类型守卫函数（纯类型安全）
    '**/guards.ts',
    
    // 常量枚举（纯数据）
    '**/constants.ts',
    
    // 配置文件
    '**/*.config.ts',

    // 枚举定义（自动生成）
    '**/enums.ts',
  ],
}
```

**合理的忽略范围**：

| 可以忽略 | 不建议忽略 |
|---------|-----------|
| 类型转换辅助函数 | 业务逻辑中的条件判断 |
| 枚举常量定义 | API 请求处理 |
| 纯配置对象 | 数据转换和校验 |
| 错误消息常量 | 状态管理和副作用 |

## 覆盖率的陷阱

**高覆盖率 ≠ 高质量**。以下几种情况都能产生虚假的高覆盖率：

```javascript
// ❌ 虚假覆盖：测试只是触发了代码但没有验证行为
it('假测试', () => {
  processData({});  // 触发了函数内部的所有分支...
  // 但没有任何 assert！即使逻辑全错了也通过
});

// ❌ 虚假覆盖：Mock 一切导致测试毫无意义
vi.mock('./api');
vi.mock('./database');
vi.mock('./auth');
// 所有依赖都被替换为空壳，测试跑得飞快，
// 但实际运行的代码和你以为的完全不同

// ✅ 有意义的覆盖：验证了具体的行为和输出
it('有效测试', async () => {
  const result = await processOrder(validOrder);
  expect(result.status).toBe('confirmed');
  expect(result.orderId).toMatch(/^ORD-\d+$/);
  expect(result.timestamp).toBeInstanceOf(Date);
});
```

**哲学思考**：覆盖率是一个**下限保证而非上限追求**。70% 的覆盖率且每条测试都有意义，远胜于 95% 但大部分测试都是空壳。正确的态度是把覆盖率当作一张**热力图**——红色区域是需要补测试的地方，绿色区域说明已有一定保障，但绿色不代表完美。真正重要的永远是测试本身的质量——它是否在验证正确的行为、是否能捕获回归问题。
