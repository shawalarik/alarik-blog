# 模块系统 —— CommonJS 与 ESM 的互操作、require 缓存

> **核心内容**：CommonJS（`require/module.exports`）的完整机制、ESM（`import/export`）在 Node.js 中的特殊行为、两者互操作规则、`require.resolve` 解析算法、循环依赖的处理方式。

## 两套系统并存

Node.js 的模块系统经历了一次重大的范式转移：

| 维度 | CommonJS (CJS) | ES Modules (ESM) |
|------|---------------|------------------|
| **声明** | `require()` / `module.exports` | `import` / `export` |
| **加载时机** | 运行时同步加载 | 编译时静态分析 |
| **值绑定** | 值拷贝（浅拷贝） | 实时绑定（live binding） |
| **顶层 await** | 不支持 | 支持 |
| **this 指向** | 空对象 `{}` | `undefined` |
| **文件扩展名** | `.js` / `.cjs` / 无扩展名 | `.mjs` / `.js`(package.json type=module) |
| **__dirname** | 可用 | 不可用（需用 import.meta 替代） |

### 如何区分当前文件使用哪种系统？

Node.js 根据以下规则判断：

```
1. 文件扩展名是 .mjs → ESM
2. 文件扩展名是 .cjs → CommonJS
3. 扩展名是 .js → 查看 package.json 的 "type" 字段：
   - "type": "module"   → ESM
   - "type": "commonjs" 或未设置 → CJS
4. 无扩展名 → 同第3条，通过 package.json 判断
```

```jsonc
// package.json — 全局声明模块类型
{
  "name": "my-project",
  "type": "module",        // 所有 .js 文件默认按 ESM 处理
  // "type": "commonjs",    // 或显式声明为 CJS（默认行为）
}
```

## CommonJS 深度解析

### require 的工作原理

当执行 `require('./utils')` 时，Node.js 内部经历了以下步骤：

```
require('./utils')
    │
    ▼
① 解析路径 (Module._resolveFilename)
    │  — './utils' → 绝对路径
    │  — 尝试 utils.js → utils.json → utils.node → utils/index.js
    │
    ▼
② 检查缓存 (Module._cache)
    │  — 如果缓存命中 → 直接返回 exports 对象
    │  — 如果未命中 → 创建新 Module 实例
    │
    ▼
③ 加载模块 (Module._load)
    │  — 读取文件内容
    │  — 将代码包裹在函数中：(function(exports, require, module, __filename, __dirname){ ... })
    │  — 执行该函数
    │
    ▼
④ 缓存并返回
    └── module.exports 被缓存，后续 require 直接返回同一引用
```

### module.exports 与 exports 的关系

这是初学者最容易混淆的地方：

```js
// utils.cjs

// ✅ 正确：通过 module.exports 导出
module.exports.add = function(a, b) { return a + b; };
module.exports.PI = 3.14159;

// ✅ 也正确：exports 是 module.exports 的简写（初始时指向同一个对象）
exports.multiply = function(a, b) { return a * b; };

// ❌ 错误：重新赋值 exports 不会影响 module.exports
exports = {
  add: function(a, b) { return a + b; }
};
// 此时 exports 已经指向一个新对象，而 module.exports 仍指向旧对象
// require() 返回的是 module.exports，不是 exports！
```

可以用一个类比来理解：`module.exports` 是真正的出口信箱，`exports` 只是一个指向这个信箱的快捷标签。你可以往信箱里放东西（`exports.foo = ...`），但如果你把标签撕下来贴到另一个新信箱上（`exports = {...}`），原来的出口信箱不会变。

```js
// 推荐的导出模式
class Calculator {
  // ...
}

// 方式一：直接赋值 module.exports
module.exports = Calculator;

// 方式二：挂载属性（支持混合导出）
module.exports.Calculator = Calculator;
module.exports.helper = { version: '1.0' };

// 使用方
const Calc = require('./calculator');           // 方式一：直接拿到类
const { Calculator, helper } = require('./calculator'); // 方式二：解构获取
```

### require 缓存机制

```js
// a.cjs
console.log('模块 A 被加载');

let counter = 0;

function increment() {
  counter++;
  return counter;
}

module.exports = { increment };

// main.cjs
const modA1 = require('./a');
const modA2 = require('./a'); // 不会再次执行模块代码！

console.log(modA1.increment()); // 1
console.log(modA2.increment()); // 2 — 共享同一个 counter！

// 验证：两次 require 返回的是同一个对象
console.log(modA1 === modA2); // true
```

缓存可以通过 `delete` 手动清除（极少需要这样做）：

```js
// 清除特定模块缓存
delete require.cache[require.resolve('./utils')];

// 重新加载
const freshUtils = require('./utils');
```

**典型使用场景**：开发时的热重载（HMR）、测试中重置模块状态。生产环境一般不推荐清除缓存——它会破坏单例语义，可能导致不可预测的行为。

## ESM 在 Node.js 中的行为

### import/export 基本用法

```js
// math.mjs
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export default class Calculator {
  static multiply(a, b) { return a * b; }
}

// app.mjs
import Calculator, { add, PI } from './math.mjs';

console.log(add(2, 3));       // 5
console.log(PI);              // 3.14159
console.log(Calculator.multiply(4, 5)); // 20
```

### 动态 import()

ESM 支持动态导入，返回 Promise：

```js
// 条件性加载
if (process.env.NODE_ENV === 'production') {
  const { optimize } = await import('./optimizer.mjs');
  optimize();
}

// 懒加载重型模块
async function handleHeavyTask(data) {
  const { HeavyProcessor } = await import('./heavy-processor.mjs');
  const processor = new HeavyProcessor();
  return processor.process(data);
}
```

### import.meta

在 ESM 中，`__filename` 和 `__dirname` 不可用，取而代之的是 `import.meta`：

```js
// ESM 中获取文件信息
console.log(import.meta.url);        // file:///path/to/file.mjs

// 兼容写法：模拟 __dirname 和 __filename
import { fileURLToPath } from 'url';
import { dirname } from 'path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

console.log(__dirname);  // /path/to
console.log(__filename); // /path/to/file.mjs

// import.meta 还能告诉你主入口是什么
console.log(import.meta.main); // true 如果是主入口文件
```

## CJS 与 ESM 互操作

这是 Node.js 模块系统中最复杂的部分。两种系统的互操作存在**不对称性**：

### ESM 可以导入 CJS（有限制）

```js
// cjs-module.cjs
module.exports = {
  name: 'CJS Module',
  greet() { return 'Hello from CJS'; }
};

// esm-consumer.mjs
import cjsMod from './cjs-module.cjs';

console.log(cjsMod.name);      // 'CJS Module'
console.log(cjsMod.greet());   // 'Hello from CJS'
```

**关键限制**：ESM 只能用**默认导入**（default import）导入 CJS 模块，不能使用命名导入：

```js
// ❌ 错误：CJS 模块不支持命名导入
// import { name, greet } from './cjs-module.cjs';
// SyntaxError: Named export 'name' not found

// ✅ 正确：先默认导入，再解构
import cjsMod from './cjs-module.cjs';
const { name, greet } = cjsMod;
```

原因：CJS 的 `module.exports` 是一个运行时对象，编译阶段无法静态确定它有哪些属性。ESM 的命名导入需要在编译时就确定导出名称。

### CJS 不能直接 import ESM

```js
// esm-module.mjs
export const value = 42;
export default function hello() { return 'hi'; }

// ❌ 以下代码会报错
// cjs-consumer.cjs
// import { value } from './esm-module.mjs'; // SyntaxError!
// const mod = require('./esm-module.mjs');   // ERR_REQUIRE_ESM!
```

CJS 无法导入 ESM 模块。如果必须从 CJS 中使用 ESM 的功能，只能用动态 `import()`：

```js
// cjs-consumer.cjs — 通过动态 import() 间接使用 ESM
async function useEsmModule() {
  const esmMod = await import('./esm-module.mjs');
  console.log(esmMod.default());
  console.log(esmMod.value);
}
```

### 双格式发布策略

如果你正在编写一个 npm 包，希望同时兼容 CJS 和 ESM 用户，可以使用双格式发布：

```jsonc
// package.json
{
  "name": "universal-utils",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",         // CJS 入口（给 require 用）
  "module": "./dist/index.mjs",       // ESM 入口（给 bundler 用）
  "exports": {
    ".": {
      "import": "./dist/index.mjs",   // import 时用这个
      "require": "./dist/index.cjs"   // require 时用这个
    },
    "./helpers": {
      "import": "./dist/helpers.mjs",
      "require": "./dist/helpers.cjs"
    }
  }
}
```

目录结构示例：

```
universal-utils/
├── src/
│   ├── index.ts          # 公共 API
│   ├── index.cjs.ts      # CJS 包装器
│   └── helpers.ts
├── dist/
│   ├── index.mjs          # ESM 编译产物
│   ├── index.cjs          # CJS 编译产物
│   ├── helpers.mjs
│   └── helpers.cjs
└── package.json
```

## 循环依赖

### CommonJS 中的循环依赖

```js
// a.cjs
const b = require('./b');
console.log('in a.js, b.value =', b.value);

module.exports = {
  value: 'from A'
};

// b.cjs
const a = require('./a');
console.log('in b.js, a.value =', a.value);

module.exports = {
  value: 'from B'
};

// main.cjs
require('./a');
```

输出结果：

```
in b.js, a.value = undefined  ← a 还没完成导出！
in a.js, b.value = from B
```

**原因**：CJS 的 `module.exports` 默认是一个空对象 `{}`。当发生循环依赖时，被循环引用的模块还没执行完 `module.exports` 赋值，所以拿到的是一个**不完整的空对象**。

解决方案：

```js
// 延迟访问：在需要的时候才读取对方导出的属性
// a.cjs
let b;
function getB() {
  if (!b) b = require('./b');
  return b;
}

function doSomething() {
  console.log(getB().value); // 此时 b 已完全初始化
}

module.exports = { doSomething };
```

### ESM 中的循环依赖

```js
// a.mjs
import { getValue as getBValue } from './b.mjs';
export const value = 'from A';

function showB() {
  console.log('B says:', getBValue());
}

// b.mjs
import { value as aValue } from './a.mjs';
export const value = 'from B';

function showA() {
  console.log('A says:', aValue); // live binding — 此时已可访问
}
```

ESM 的循环依赖处理比 CJS 更优雅——因为 ESM 使用**实时绑定（live binding）**，即使发生了循环引用，导入的变量也会在导出模块完成赋值后自动更新。但要注意**暂时性死区（TDZ）**的问题：如果在模块顶层立即使用循环导入的值，仍然可能得到 `undefined` 或抛出引用错误。

## require.resolve：手动解析模块路径

有时你需要知道一个模块的实际文件路径（而不实际加载它）：

```js
// 解析模块到完整路径
const path = require('path');
const lodashPath = require.resolve('lodash');
console.log(lodashPath);
// /node_modules/lodash/lodash.js

// 解析本地模块
const utilPath = require.resolve('./utils');
// /project/src/utils.js

// 自定义解析路径（查找顺序）
const paths = require.resolve.paths('express');
// [
//   '/project/node_modules',
//   '/node_modules',
//   ...
// ]

// 检查模块是否安装（找不到会抛出错误）
try {
  require.resolve('some-package');
  console.log('已安装');
} catch (err) {
  if (err.code === 'MODULE_NOT_FOUND') {
    console.log('未安装:', err.requireStack[0]);
  }
}
```

### 自定义 require 钩子（高级）

Node.js 12+ 支持自定义模块加载逻辑：

```js
// register-hooks.mjs
import { register } from 'node:module';
import { fileURLToPath } from 'url';

const hooksPath = new URL('./custom-hooks.mjs', import.meta.url);
register(hooksPath);

// custom-hooks.mjs — 自定义加载钩子
export function resolve(specifier, context, nextResolve) {
  console.log(`正在解析: ${specifier}`);
  return nextResolve(specifier, context);
}

export function load(url, context, nextLoad) {
  console.log(`正在加载: ${url}`);
  return nextLoad(url, context);
}
```

## 最佳实践总结

| 场景 | 推荐 | 理由 |
|------|------|------|
| 新项目 | ESM (`"type": "module"`) | 未来标准，tree-shaking 友好 |
| npm 库发布 | 双格式（CJS + ESM） | 兼容所有消费者 |
| 配置/脚本工具 | CJS | 同步 API 简洁，__dirname 直接可用 |
| 大型应用 | ESM | 顶层 await、静态分析、更好的 IDE 支持 |
| 与旧生态集成 | CJS 或动态 import() | 很多老包只提供 CJS |

## 哲学思考：模块即边界

模块系统的本质是在定义**边界**。CommonJS 说"边界是柔性的"——你可以在任何地方调用 `require()`，像是在旅途中随时可以走进一家便利店。ESM 说"边界是刚性的"——所有进口必须在文件顶部声明完毕，像是过海关必须提前申报所有物品。

刚性边界的好处在于可预测性：编译器能在你运行代码之前就画出一张完整的依赖图谱。柔性边界的好处在于灵活性：你可以根据运行时的条件决定加载什么。没有绝对的优劣——就像生活中有些事情需要提前规划（刚性），有些事情需要随机应变（柔性）。好的工程师知道什么时候该画一条清晰的线，什么时候该留一道灵活的门。
