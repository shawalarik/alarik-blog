# Node.js 事件循环与浏览器的区别 —— process.nextTick、timers、I/O

> **核心内容**：Node.js 事件循环的六个阶段、microtask 的两套队列（nextTick 微任务队列 vs Promise 微任务队列）、与浏览器事件循环的本质差异、经典面试题深度拆解。

## 从一个面试题说起

先看这段代码，它的输出顺序是什么？

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

setImmediate(() => console.log('3'));

Promise.resolve().then(() => console.log('4'));

process.nextTick(() => console.log('5'));
```

输出结果是 `1 → 5 → 4 → 2 → 3` 或 `1 → 5 → 4 → 3 → 2`。

为什么 `2` 和 `3` 的顺序不确定？为什么 `5` 在 `4` 前面？这背后隐藏着 Node.js 事件循环与浏览器之间**根本性的架构差异**。理解这个差异，是掌握 Node.js 异步模型的第一步。

## 浏览器事件循环回顾

浏览器的事件循环模型相对简洁：

```
┌───────────────────────────────┐
│           Call Stack          │  ← 同步代码执行
└───────────┬───────────────────┘
            │
            ▼
┌───────────────────────────────┐     ┌──────────────┐
│      Microtask Queue          │◄────│ Promise.then │
│   (Promise.then/mutationObserver)│    │ .then/.catch │
└───────────┬───────────────────┘    └──────────────┘
            │ 每个宏任务结束后清空
            ▼
┌───────────────────────────────┐     ┌──────────────┐
│       Macrotask Queue         │◄────│ setTimeout   │
│ (setTimeout/setInterval/UI...)│     │ setInterval  │
│                               │     │ DOM事件       │
└───────────────────────────────┘     └──────────────┘
```

核心规则：

1. 执行一个**宏任务**（Macrotask）
2. 宏任务结束后，**清空所有微任务**（Microtask）
3. 渲染更新（如果需要）
4. 取下一个宏任务，回到步骤 1

浏览器的微任务队列**只有一套**——Promise.then、mutationObserver、queueMicrotask 都进入同一个队列，按入队顺序执行。

## Node.js 事件循环的六阶段

Node.js 基于 libuv 库实现事件循环，其模型比浏览器复杂得多，包含**六个阶段**，按顺序循环：

```
┌───────────────────────────┐
┌─>│         timers          │  ← setTimeout / setInterval 回调
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│  │   pending callbacks     │  ← I/O 操作的错误回调（如 ECONNREFUSED）
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│  │   idle, prepare         │  ← 内部使用（仅 libuv 使用）
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│  │          poll           │  ← 获取新的 I/O 事件；执行 I/O 相关回调
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│  │        check            │  ← setImmediate 回调在此执行
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│  │   close callbacks       │  ← socket.on('close', ...) 等关闭回调
│  └───────────┬─────────────┘
│  ┌───────────▼─────────────┐
│    │   ┌───────────────┐   │
│    │   │ nextTickQueue │   │  ← process.nextTick()
│    │   │ PromiseQueue  │   │  ← Promise.then() / async/await
│    │   └───────────────┘   │
│    │   （每个阶段过渡时清空）│
└────┴────────────────────────┘
```

### 各阶段详解

#### 1. Timers 阶段

执行 `setTimeout` 和 `setInterval` 的回调。**关键点**：不是时间一到就立即执行，而是检查是否有到期定时器。实际执行时间可能比设定值**延迟**，因为必须等当前阶段和前面的微任务都处理完。

```js
// 设定 0ms 定时器，但实际可能在 1ms+ 后才执行
const start = Date.now();
setTimeout(() => {
  console.log(`定时器在 ${Date.now() - start}ms 后执行`);
}, 0);

// 模拟同步阻塞 10ms
const end = Date.now() + 10;
while (Date.now() < end);
// 输出：定时器在 11ms 左右后执行（而非 0ms）
```

#### 2. Pending Callbacks 阶段

执行某些系统操作的延迟回调。典型场景：TCP 连接收到 `ECONNREFUSED` 错误时，有些类 Unix 系统会等待报告错误，此阶段就是用来执行这类"被推迟"的回调。

```js
// 这个阶段的回调通常不需要开发者直接操作
// 它由系统底层自动触发
const net = require('net');
const s = net.createServer();
s.close(); // close 事件会在 close callbacks 阶段触发
s.on('close', () => {
  console.log('这是 close callback'); // close callbacks 阶段
});
```

#### 3. Idle/Prepare 阶段

**仅供内部使用**。开发者无需关心。idle 用于 poll 阶段空闲时的内部操作，prepare 用于 check 阶段前的准备工作。

#### 4. Poll 阶段（最关键的阶段）

Poll 是整个事件循环的**核心引擎**，有两个主要职责：

1. **计算阻塞时间**：计算应该阻塞 I/O 多久（等待新事件到达）
2. **执行 I/O 回调**：处理 poll 队列中的回调

```js
const fs = require('fs');
// 文件读取完成后，回调会在 poll 阶段执行
fs.readFile('/etc/passwd', (err, data) => {
  console.log('文件读取完成 — poll 阶段执行');
});
```

Poll 阶段的特殊行为：

| 条件 | 行为 |
|------|------|
| poll 队列非空 | 按顺序执行所有回调 |
| poll 队列为空 + 有 setImmediate | 进入 **check** 阶段 |
| poll 队列为空 + 无 setImmediate | **等待**新的 I/O 事件（可阻塞） |
| poll 队列为空 + 有已到期的 timer | 回到 **timers** 阶段 |

这就是 `setTimeout(fn, 0)` 和 `setImmediate(fn)` 执行顺序不确定的根本原因——取决于事件循环当前处于哪个阶段。

#### 5. Check 阶段

专门用于执行 `setImmediate()` 的回调。**setImmediate 是 Node.js 特有的 API，浏览器中没有对应物**。

```js
// setImmediate 总是在 I/O 事件之后、 timers 之前执行
const fs = require('fs');
fs.readFile(__filename, () => {
  // 此时事件循环在 poll 阶段
  // 接下来会进入 check 阶段
  setImmediate(() => {
    console.log('setImmediate — check 阶段');
  });
  setTimeout(() => {
    console.log('setTimeout — 下一轮 timers 阶段');
  }, 0);
});
// 输出顺序确定：setImmediate 先于 setTimeout
```

#### 6. Close Callbacks 阶段

执行关闭事件的回调，如 `socket.on('close')`、`process.on('exit')` 等。

## 两套微任务队列：最大的差异点

### Node.js 的双队列设计

浏览器只有一套微任务队列。但 Node.js 有**两套**独立的微任务队列：

```
每个阶段之间的过渡：
                    ┌─────────────────┐
  当前阶段结束 ───► │  ① nextTickQueue │ ◄── process.nextTick()
                    │  (优先级更高)     │
                    ├─────────────────┤
                    │  ② PromiseQueue  │ ◄── Promise.then()
                    │  (次优先级)      │
                    └─────────────────┘
                         ↓ 全部清空后才进入下一阶段
                   下一个阶段开始
```

**执行顺序**：

1. 清空 `nextTickQueue`（全部）
2. 清空 `PromiseQueue`（全部）
3. 才能进入下一个阶段

这意味着 `nextTick` 的优先级**高于** Promise，且两者都会**阻断**事件循环的阶段推进。

```js
console.log('start');

process.nextTick(() => {
  console.log('nextTick 1');
  process.nextTick(() => {
    console.log('nextTick 2'); // 递归 nextTick，仍然在本次微任务中
  });
});

Promise.resolve().then(() => {
  console.log('Promise 1');
  process.nextTick(() => {
    console.log('nextTick in Promise'); // Promise 中注册的 nextTick
  });
});

console.log('end');
```

输出：

```
start
end
nextTick 1
nextTick 2
Promise 1
nextTick in Promise
```

注意 `nextTick in Promise` 在最后执行——因为它是在 Promise 回调执行期间才注册的 nextTick，需要等当前 PromiseQueue 处理完后才会处理新注册的 nextTick。

### 为什么需要两套队列？

设计哲学上的取舍：

- **nextTick**：设计初衷是让用户有机会在事件循环继续之前执行操作（错误处理后清理资源、确保某些逻辑在 I/O 之前运行）。它是**同步递归友好**的——允许在 nextTick 中再次调用 nextTick。
- **Promise**：遵循 ECMAScript 规范，行为与浏览器一致。但在 Node.js 中被放在第二优先级，以避免与 nextTick 产生冲突。

```js
// 典型的 nextTick 用例：确保在事件循环继续前完成清理
const server = require('http').createServer();

server.listen(3000);
server.on('request', (req, res) => {
  // 发送响应后做一些清理工作
  res.end('Hello');
  process.nextTick(() => {
    // 这里的逻辑保证在本轮 I/O 处理完之后、
    // 下一轮事件循环之前执行
    req.socket.ref(); // 恢复引用计数
  });
});
```

## setTimeout(0) vs setImmediate：谁先谁后？

这是一个经典的面试陷阱题。

### 在 I/O 回调内部——顺序确定

```js
const fs = require('fs');

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
```

**固定输出**：`immediate → timeout`

原因：readFile 回调在 **poll** 阶段执行。执行完回调后：
1. poll 阶段结束
2. 进入 **check** 阶段 → 执行 `setImmediate`
3. 下一轮循环进入 **timers** 阶段 → 执行 `setTimeout`

### 在顶层（不在 I/O 回调中）——不确定

```js
// 直接在模块顶层执行
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
```

**输出不确定**！可能 `timeout → immediate`，也可能 `immediate → timeout`。

原因：事件循环的启动时机不确定。Node.js 启动脚本时：
- 如果事件循环恰好从 **timers** 阶段开始 → `setTimeout` 先执行
- 如果从 **check** 阶段开始 → `setImmediate` 先执行

这取决于启动耗时是否跨过了定时器的阈值。

### 最佳实践

如果需要确定性顺序，**始终将两者放入同一个 I/O 回调中**，或者直接用 `setImmediate` 替代 `setTimeout(fn, 0)`——后者语义更明确，性能也更好。

## 与浏览器的完整对比表

| 维度 | 浏览器 | Node.js |
|------|--------|---------|
| **宏任务源** | setTimeout/setInterval/DOM事件/UI渲染 | timers/pending/callbacks/idle/poll/check/close |
| **微任务队列数** | **1 套** | **2 套**（nextTick > Promise） |
| **微任务来源** | Promise.then/mutationObserver/queueMicrotask | process.nextTick/Promise.then/async/await |
| **render 阶段** | 有（宏任务之间） | 无 |
| **特有 API** | requestAnimationFrame/mutationObserver | setImmediate/process.nextTick |
| **宏任务粒度** | 一个 task = 一次事件处理 | 六个阶段精细划分 |
| **I/O 处理** | 通过事件驱动（fetch/XMLHttpRequest） | 通过 poll 阶段统一管理 |

### 核心差异总结

1. **Phase-based vs Task-based**：浏览器是"任务驱动"，每完成一个宏任务就清空微任务；Node.js 是"阶段驱动"，有六个明确的处理阶段。
2. **nextTick 的存在**：这是 Node.js 最显著的差异。`process.nextTick()` 不属于任何阶段，它像是一个"特权公民"，在每个阶段过渡时最先被执行。
3. **无渲染阶段**：Node.js 不需要关心 UI 渲染，所以没有类似浏览器的 rendering pipeline。

## 实战：EventLoop 可视化工具

理解了原理后，写一个小工具来观察事件循环的实际行为：

```js
// event-loop-tracer.js
class EventLoopTracer {
  constructor() {
    this.logs = [];
    this.phase = 'init';
  }

  log(phase, message) {
    const timestamp = `${Date.now().toString().slice(-5)}`;
    const entry = `[${timestamp}] [${phase.padEnd(8)}] ${message}`;
    this.logs.push(entry);
    console.log(entry);
  }

  trace() {
    this.log('SCRIPT', '同步代码开始');

    // 模拟各阶段的回调
    setTimeout(() => {
      this.log('TIMER', 'setTimeout 回调');
      Promise.resolve().then(() =>
        this.log('PROMISE', 'timer 内的 Promise')
      );
    }, 0);

    setImmediate(() => {
      this.log('CHECK', 'setImmediate 回调');
      process.nextTick(() =>
        this.log('NEXTTICK', 'immediate 内的 nextTick')
      );
    });

    process.nextTick(() => {
      this.log('NEXTTICK', '第一个 nextTick');
      process.nextTick(() =>
        this.log('NEXTTICK', '嵌套的 nextTick')
      );
    });

    Promise.resolve().then(() => {
      this.log('PROMISE', '第一个 Promise');
    });

    this.log('SCRIPT', '同步代码结束');
  }

  getReport() {
    return '\n' + this.logs.join('\n') +
           `\n\n共 ${this.logs.length} 条记录`;
  }
}

const tracer = new EventLoopTracer();
tracer.trace();
// 稍后查看完整报告
setTimeout(() => console.log(tracer.getReport()), 20);
```

典型输出：

```
[12345] [SCRIPT  ] 同步代码开始
[12345] [SCRIPT  ] 同步代码结束
[12346] [NEXTTICK] 第一个 nextTick
[12346] [NEXTTICK] 嵌套的 nextTick
[12347] [PROMISE ] 第一个 Promise
[12348] [CHECK  ] setImmediate 回调
[12349] [NEXTTICK] immediate 内的 nextTick
[12350] [TIMER  ] setTimeout 回调
[12351] [PROMISE ] timer 内的 Promise
```

从这个日志可以清晰看到事件循环的流转过程：**同步代码 → nextTick 队列 → Promise 队列 → check 阶段 → timers 阶段**。

## process.nextTick 的正确用法与反模式

### 正确用法：确保异步操作后的同步式清理

```js
// 场景： EventEmitter 中发射 error 事件
const { EventEmitter } = require('events');

class SafeEmitter extends EventEmitter {
  emitError(error) {
    this.emit('error', error);
    // 使用 nextTick 确保监听器有机会处理错误
    // 再决定是否需要抛出到 uncaughtException
    process.nextTick(() => {
      if (this.listenerCount('error') === 0) {
        throw error; // 没有人监听 error，才抛出
      }
    });
  }
}
```

### 反模式：nextTick 递归导致饥饿

```js
// 危险：无限 nextTick 导致 I/O 饥饿
function dangerousRecursion() {
  // 这个函数永远占用事件循环
  // I/O 回调、定时器、setImmediate 都无法执行
  process.nextTick(dangerousRecursion);
}

dangerousRecursion();
// 事件循环卡死在这里！
```

正确的做法是用 `setImmediate` 来做递归调度：

```js
// 安全：setImmediate 让其他回调有机会执行
function safeRecursion() {
  // 每轮事件循环只执行一次
  // I/O、定时器等其他回调不会被饿死
  setImmediate(safeRecursion);
}

safeRecursion();
```

## 哲学思考：事件循环即时间的形状

事件循环本质上是 JavaScript 对"时间"这一概念的抽象方式。浏览器的时间观是面向用户的——每一次屏幕刷新都是一次心跳；Node.js 的时间观是面向机器的——每一个 I/O 操作的完成都是一个节拍。

`process.nextTick` 的存在揭示了一个深刻的工程权衡：有时候你需要**插队**——在正常流程中插入一个高优先生命周期钩子。但插队的能力是一把双刃剑，用好了是优雅的资源清理，用不好就是对事件循环的绑架。

理解事件循环，就是在理解你的代码在时间轴上究竟位于何处。每一行异步代码都不是悬浮在真空中的，它们都有自己确定的"坐标"——某个阶段的某次迭代。掌握了这些坐标，就能写出可预测、可调试、可维护的异步程序。
